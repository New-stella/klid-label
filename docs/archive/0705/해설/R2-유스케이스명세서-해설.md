# R2 유스케이스 명세서 — 종합 해설 (스터디가이드)

> 본 문서는 `docs/0705/R2-유스케이스명세서.md` 원문을 처음 접하는 사람도 어떤 질문에도 답할 수 있도록 상세히 풀어 쓴 **해설·학습 가이드**입니다.
> 원문에 실제로 기재된 내용만을 근거로 작성했으며, 원문에 없는 사항은 "원문에 명시되지 않음"으로 구분하여 표기합니다.

---

## 1. 이 문서는 무엇인가

### 1.1 한 줄 정의
R2 유스케이스 명세서는 **"AI 기반 지방정부 CCTV 관제지원시스템(2차)"의 서브시스템인 "학습데이터 저작도구"가 무슨 일을, 누가, 어떤 순서로 수행하는지**를 액터(사용자·외부 시스템)와 시스템 간의 상호작용 시나리오로 기술한 요구사항 단계 산출물입니다.

### 1.2 문서의 목적 (원문 "작성 목적" 기준)
원문은 작성 목적을 다음과 같이 밝힙니다.

> "시스템의 요구사항에 대하여 액터와 시스템 활동 및 상호간의 활동에 대하여 순서화된 시나리오를 상세하게 기술하고, 유스케이스의 이름·액터·그들 간의 연관관계를 다이어그램으로도 표현한다."

즉 두 축을 다룹니다.
1. **텍스트 시나리오** — 각 유스케이스(UC)를 "기본 시나리오 + 대안 시나리오" 형태로 순서화하여 기술.
2. **다이어그램(UCD)** — 유스케이스 이름·액터·연관관계를 그림(PlantUML)으로 표현.

원문은 추가로 "시스템 시퀀스 다이어그램(SSD)이나 오퍼레이션 약정(operation contract)은 **필수 산출물이 아니며 선택적**"이라고 명시합니다. 즉 본 R2 문서는 SSD·오퍼레이션 약정을 담지 않은, **유스케이스 텍스트 + UCD 중심** 산출물입니다.

### 1.3 R 산출물 vs D 산출물 — 문서의 위치
CBD(컴포넌트 기반 개발) 산출물 체계에서 문서는 크게 두 계열로 나뉩니다.

| 계열 | 성격 | 대표 산출물 | 답하는 질문 |
|------|------|-------------|-------------|
| **R (Requirements, 분석 단계)** | "무엇을 만들 것인가" | R1 요구사항정의서, **R2 유스케이스명세서**, R3 (요구사항 추적 등) | 시스템이 어떤 기능·행위를 제공해야 하는가 |
| **D (Design, 설계 단계)** | "어떻게 만들 것인가" | D1 클래스설계서, D2 UI설계서, D3, D5 아키텍처설계서, D8/D9 (DB/테이블), D10 통합시험시나리오, D11 | 그 요구를 어떤 구조·화면·데이터·검증으로 실현하는가 |

원문 헤더가 **"단계명: 분석"**으로 명시된 데서 드러나듯, R2는 **분석(요구) 단계** 산출물입니다. "무엇을 해야 하는가(행위·시나리오)"를 정의할 뿐, 클래스·테이블·API 등 구현 구조는 D 계열로 넘깁니다.

### 1.4 요구사항(R1)과의 관계
R2의 각 유스케이스는 **R1 요구사항정의서의 기능 요구(SFR) / 비기능 요구(NFR)와 명시적으로 연결**됩니다.

- 원문 "유스케이스 목록" 표의 **"관련 요구사항 ID"** 열이 각 UC를 `RQ-SFR-NN-NN`(기능) 요구사항에 매핑합니다.
- 각 UC 기술서의 "구현 시 고려 사항"에는 `NFR-001`, `NFR-004`, `NFR-005`, `NFR-013` 등 **비기능 요구사항**이 참조로 걸립니다.
- 즉 R2는 R1을 **"실행 가능한 시나리오"로 구체화한 다리** 역할을 합니다. "요구사항이 실제로 어떤 사용자 행위와 시스템 반응으로 나타나는가"를 보여줍니다.

원문 부록은 **R1 기능 요구(SFR)를 실현하는 유스케이스만 포함**한다는 편집 원칙을 밝힙니다(1.7 참조).

### 1.5 대상 시스템의 정체성 (프로젝트 맥락)
문서가 다루는 "학습데이터 저작도구"는 지방정부 CCTV 관제지원시스템의 **2차 사업 서브시스템**으로, 영상/이미지 라벨링·검수 워크플로우·비식별화·외부 생성 메타 검토를 담당합니다. 핵심 도메인은 다음과 같습니다.

- **마킹**(자동/수동 이벤트 시점 식별) · **배치 파이프라인**(비식별→마킹→시계열 메타→프레임추출→오토라벨링→보간) · **라벨링** · **검수**(REVIEWER 배정·승인) · **비식별화** · **버전관리**(DB 스냅샷) · **데이터 증강**(새 영상) · **포털**.
- **역할은 세 가지**: `REVIEWER`(검수자, 관리 권한 통합), `WORKER`(라벨링 작업자), `PORTAL_USER`(포털 회원). 단, R2는 뒤에서 보듯 REVIEWER·WORKER 중심이며 포털은 이번 버전 범위에서 유스케이스가 없습니다.
- **배치 파이프라인은 인증 불필요** — 관제서버가 공유 DB에 학습용으로 설정한 영상을 주기 배치가 픽업합니다.

### 1.6 문서 구조 한눈에 보기
원문은 다음 순서로 구성됩니다.

1. **ID 표기 규칙** — 모든 ID를 `KLID-AT-XX-NNN` 전체형으로 표기(약식 금지).
2. **작성 목적 / 작성 방법 / 산출물 양식**(제·개정 이력, 헤더).
3. **1. 서브시스템 목록** — SS-002~009(8종).
4. **2. 유스케이스 다이어그램(UCD)** — UCD-001(가공·검수 핵심 흐름), UCD-002(데이터 증강 흐름).
5. **3. 유스케이스 목록** — 18개 UC 요약 표(액터·UCD·요구사항 매핑).
6. **4. 액터 목록** — AC-001~007(7종).
7. **5. 유스케이스 기술서** — 18개 UC의 상세 8항목 기술.
8. **항목 설명** — 각 표 항목의 정의(양식 가이드).
9. **부록** — 빈 셀 및 범위(제외 UC) 처리 사유.

### 1.7 ID 체계 (원문 규칙)
| 접두어 | 의미 | 예시 |
|--------|------|------|
| `KLID-AT-SS-NNN` | 서브시스템(SubSystem) | KLID-AT-SS-002 (마킹) |
| `KLID-AT-UCD-NNN` | 유스케이스 다이어그램 | KLID-AT-UCD-001 |
| `KLID-AT-UC-NNN` | 유스케이스 | KLID-AT-UC-018 (영상 적재) |
| `KLID-AT-AC-NNN` | 액터(Actor) | KLID-AT-AC-002 (검수자) |
| `RQ-SFR-NN-NN` | R1 기능 요구(외부 체계, 원형 유지) | RQ-SFR-08-01 |
| `NFR-NNN` | R1 비기능 요구(외부 체계, 원형 유지) | NFR-013 |

- `KLID-AT`는 "KLID(한국지역정보개발원) — Authoring Tool(저작도구)"을 의미하는 접두어로 읽힙니다(원문은 접두어 확장을 명시하지 않으므로 문맥상 해석).
- 원문 규칙: 끝부분만(예: `UC-001`) 약식 표기 금지, 범위는 시작 ID만 전체형으로(예: `KLID-AT-UC-001~013`).

## 2. 섹션별 상세 해설

### 2.1 서브시스템 목록 (SS)
원문은 8개 서브시스템을 수록합니다. 각 서브시스템은 하나의 도메인 묶음입니다.

| SS ID | 서브시스템명 | 핵심 책임 |
|-------|-------------|-----------|
| KLID-AT-SS-002 | 마킹 | 비식별 영상에서 자동/수동으로 이벤트 시점을 식별·마킹하고 후속 배치를 시작 |
| KLID-AT-SS-003 | 배치 파이프라인 | 학습용 설정 영상을 적재하고 비식별·마킹·시계열 메타·프레임추출·자동 라벨링·추적 보간을 순차 처리 |
| KLID-AT-SS-004 | 비식별화 | 외부 비식별 솔루션 연동으로 전체 영상 개인정보 비식별 + 옵션 설정·상태/이력 확인·누락 신고 |
| KLID-AT-SS-005 | 시계열 메타 | 외부 시계열 분석 결과를 적재 → 검수자가 검토·수정·승인 |
| KLID-AT-SS-006 | 라벨링 | 프레임에 박스/폴리곤/세그멘테이션 라벨·속성 편집 + 자동 추적·외곽 밀착·정밀도 조절 |
| KLID-AT-SS-007 | 검수 | 작업자가 제출한 영상 단위 작업·증강 결과를 검수자가 승인/반려 |
| KLID-AT-SS-008 | 버전관리 | 검수 승인 시점 라벨 스냅샷 저장·이력 추적 + 버전 비교·복구 + 관제 통지 |
| KLID-AT-SS-009 | 데이터 증강 | 외부 생성형 AI에 증강 위탁 + 결과를 새 영상으로 수신·등록 + 해상도 변경 직접 수행 |

> **주의**: SS-001(사용자/권한)과 SS-010(포털)은 **의도적으로 미수록**입니다. 이유는 부록(2.5)에서 설명합니다. 즉 서브시스템 번호는 001~010이 존재하나, R2는 R1 기능 요구를 실현하는 002~009만 다룹니다.

### 2.2 유스케이스 다이어그램 (UCD) — 2개
원문은 18개 UC를 두 개의 다이어그램으로 묶어 액터-UC 연관을 시각화합니다(PlantUML 소스로 기재).

#### KLID-AT-UCD-001 — 가공·검수 핵심 흐름
- **관련 서브시스템**: SS-002~008 (마킹·배치·비식별·시계열메타·라벨링·검수·버전관리).
- **포함 UC(14개)**: UC-018(영상 적재), UC-011(비식별 요청), UC-013(비식별 옵션), UC-016(비식별 상태·이력), UC-019(이벤트 마킹), UC-022(시계열 메타 검토), UC-021(라벨 편집·임시저장), UC-004(객체 자동 추적), UC-005(외곽 밀착), UC-006(정밀도 조절), UC-023(검수 승인·반려), UC-007(버전 저장), UC-008(버전 비교·복구), UC-009(완료·수정 통지).
- **읽어야 할 관계선**:
  - `CTRL(관제서버) --> U18`: 관제서버가 영상 적재를 촉발(학습용 설정).
  - `U11 --> DEID`: 비식별 요청이 외부 비식별 솔루션을 호출.
  - `U23 ..> U7 : include`: 검수 승인(UC-023)이 버전 저장(UC-007)을 **포함(include)** — 승인 시 반드시 버전 스냅샷 생성.
  - `U23 --> U9 --> CTRL`: 검수 승인이 완료·수정 통지(UC-009)를 유발하고, 통지는 관제서버로 나감(단방향 outbound).
  - `U4/U5 --> AISRV`: 자동 추적·외곽 밀착이 AI 추론 서버를 호출.

#### KLID-AT-UCD-002 — 데이터 증강 흐름
- **관련 서브시스템**: SS-009 (데이터 증강).
- **포함 UC(4개)**: UC-001(증강 생성 요청), UC-002(증강 결과 수신·등록), UC-003(해상도 변경), UC-010(증강 활용 여부 검수).
- **읽어야 할 관계선**:
  - `REVIEWER --> U1 --> GENAI`: 검수자가 증강 요청 → 외부 생성형 AI 서비스로 위탁.
  - `GENAI --> U2`: 외부가 결과를 회신하면 UC-002가 새 영상으로 등록.
  - `REVIEWER --> U3 / U10`: 해상도 변경·증강 검수는 검수자가 직접 수행.

> **핵심 관찰**: 증강 흐름의 모든 주요 액터는 **검수자(REVIEWER)**이며, 외부 생성형 AI는 보조 액터입니다. 작업자(WORKER)는 증강 흐름에 관여하지 않습니다.

### 2.3 액터 목록 (AC) — 7종
| AC ID | 액터명 | 유형 | 설명 요지 |
|-------|--------|------|-----------|
| KLID-AT-AC-001 | 라벨링 작업자(WORKER) | 주요 | 본인 배정 영상의 마킹·라벨 편집·검수 제출·버전 저장·비식별 누락 신고 |
| KLID-AT-AC-002 | 검수자(REVIEWER) | 주요 | 작업 배정·검수 승인/반려·증강 요청/검수·비식별 요청/옵션·시계열 메타 검토·버전 비교/복구·시스템 설정 (**관리 권한 통합**) |
| KLID-AT-AC-003 | 생성형 AI 서비스[외부] | 보조 | 증강 영상 생성을 위탁받아 수행·회신하는 외부 시스템 |
| KLID-AT-AC-004 | 관제서버[외부] | 보조 | 영상을 학습용으로 설정 + 완료·수정 통지 수신·상세 조회 |
| KLID-AT-AC-005 | 비식별 솔루션[외부] | 보조 | 영상 개인정보 비식별 처리(발주기관 제공) |
| KLID-AT-AC-006 | 배치 시스템 | 보조 | 학습용 영상 픽업·적재 + 비식별·마킹·메타·프레임추출·자동 라벨링을 주기 처리하는 **내부 자동 시스템** |
| KLID-AT-AC-007 | 시계열 분석·AI 추론 서비스 | 보조 | 시계열 메타 분석 + 객체 추적·외곽 분할 추론(외부/내부 추론) |

- **주요 액터 2종(WORKER·REVIEWER)** — 사람이 목적을 수행하며 시스템 서비스를 직접 호출.
- **보조 액터 5종** — 외부 시스템(관제·비식별·생성형AI·시계열/AI추론)과 내부 자동 시스템(배치)이 서비스를 지원.
- **주목**: REVIEWER는 별도 ADMIN 없이 **모든 관리 권한을 통합**한 역할입니다(프로젝트 정책과 일치). 포털 회원(PORTAL_USER)은 액터 목록에 없습니다 — 이번 버전 범위 외이기 때문(부록 참조).

### 2.4 유스케이스 기술서 상세 해설 (18개)
각 UC는 8개 항목(주요 액터 / 이해관계자·관심사항 / 전제조건 / 종료조건 / 기본 시나리오 / 대안 시나리오 / 구현 시 고려 사항 / 발생 빈도)으로 기술됩니다. 아래는 UC별 핵심을 정리한 것입니다. 이해를 돕기 위해 원문에 나온 **관련 요구사항 ID**를 함께 적습니다.

### 2.5 항목 설명 & 부록 해설
원문 말미의 "항목 설명"은 각 표(서브시스템·UCD·유스케이스·액터·기술서) 항목의 **표준 정의(양식 가이드)**를 제공합니다. 학습 시 참고용이며, 특히 액터 유형 정의(주요/보조/숨은)와 기술서 8항목 정의(전제조건·종료조건·기본/대안 시나리오·구현 고려·발생 빈도)를 명확히 합니다.

**부록(빈 셀 및 범위 처리 사유)** — R2를 읽을 때 반드시 이해해야 할 "무엇이 빠졌고 왜 빠졌는가":

1. **SS-001(사용자/권한)·SS-010(포털) 미수록**: R1 기능 요구(SFR)를 실현하는 UC만 포함. 사용자/권한은 별도 기능 UC가 없고(접근 통제는 비기능 NFR-013으로 다룸), 포털은 본 버전에 활성 R1 기능 UC가 없어 제외.
2. **관련 AC 없는 UC의 AC 셀**: 일부 UC(영상 적재·이벤트 마킹·라벨 편집·검수 승인 등)는 해당 SFR(11/16/17 계열)의 검수기준이 요구사항 단위 포괄 기준이라 1:1 대응 AC가 없어 인접 검수기준 ID를 참조로 기재.
3. **제·개정 이력 작성자/승인자 `-`**: 초기 생성 기준선으로 담당자 배정 전, 확정 시 보완.
4. **범위 외(제외) UC** — 원문이 명시적으로 제외한 UC 번호들:
   - **UC-026 배치 파이프라인 처리** · **UC-025 라벨 프리셋 관리** · **UC-024 포털 라벨 작업** · **UC-020 작업 배정·이력 조회**: R1 전용 요구사항이 없는 **운영 워크플로우**로 분리(제외).
   - **UC-017 올가미 경계 지정**: RQ-SFR-08-01이 객체 추적·분할(UC-004)로 **재해석**되어 제외.
   - **UC-012 비식별 결과·이력 검토** · **UC-014 개인정보 보호대책 적용** · **UC-015 개인정보 유형 분류체계 관리**: **외부 솔루션·보안 인프라 책임**으로 제외.

> 이 부록은 "왜 UC 번호가 001~026 중 일부만 있는가?"라는 질문에 대한 공식 답변입니다. UC 번호가 비연속인 것은 편집상 제외의 결과이지 누락이 아닙니다.

## 3. 핵심 용어

| 용어 | 정의 |
|------|------|
| **유스케이스(Use Case, UC)** | 액터가 시스템을 사용해 특정 목적을 달성하는 상호작용의 단위. 하나의 "성공 시나리오 + 대안들"로 기술된다. 본 문서는 18개 UC를 담는다. |

| **유스케이스 다이어그램(UCD)** | 액터-UC 연관관계를 그림으로 표현. 본 문서는 UCD-001(가공·검수 핵심), UCD-002(증강) 2개. |
| **기본 시나리오(주 성공 경로)** | 이해관계자 관심사항을 충족하는 일반적 성공 경로. UC 기술서 5번 항목. |
| **대안 시나리오** | 성공·실패의 모든 분기·확장. 원문은 "대개 기본보다 더 길고 복잡하다"고 정의. UC 기술서 6번 항목. |

| **종료조건(Postcondition)** | 성공 시나리오·대안 경로의 성공적 완료 후 참이어야 할 조건. UC 기술서 4번. |
| **구현 시 고려 사항** | 비기능 요구·품질 속성·설계 제약. NFR 참조가 여기 기재됨. UC 기술서 7번. |

| **include(포함) 관계** | 한 UC가 다른 UC를 반드시 포함해 실행. 본 문서 `UC-023 ..> UC-007 : include`(검수 승인은 반드시 버전 저장을 포함). |
| **SFR (Software Functional Requirement)** | R1의 소프트웨어 기능 요구. `RQ-SFR-NN-NN`으로 참조되며 각 UC의 "관련 요구사항"에 연결. |
| **NFR (Non-Functional Requirement)** | R1의 비기능 요구. 접근 통제(NFR-013)·외부 연동 회복력(NFR-004)·비식별/통지 안전(NFR-005)·처리량(NFR-001) 등이 UC 구현 고려에 참조됨. |
| **AC (Acceptance Criteria / Actor)** | 문맥에 따라 다름 — 액터 ID는 `KLID-AT-AC`, 부록에서 언급하는 "AC 셀"은 요구사항의 **검수기준(Acceptance Criteria)**을 뜻함. |
| **REVIEWER / WORKER / PORTAL_USER** | 프로젝트 3역할. REVIEWER=검수자(관리 권한 통합), WORKER=라벨링 작업자, PORTAL_USER=포털 회원(본 문서 범위 외). |
| **배치 파이프라인** | 적재→비식별→마킹→시계열 메타→프레임추출→자동 라벨링→보간의 순차 자동 처리. 인증 불필요. |
| **2계층 분리** | ①작업 임시저장(작업본 영속, 버전 미생성) vs ②학습데이터 버전(검수 승인 시 스냅샷 생성). UC-021·UC-007에 반영. |
| **단방향 outbound 통지** | 저작도구→관제서버로 완료/수정 요약만 push하고, 상세는 관제가 조회 API로 가져가는 패턴(UC-009). 양방향 M2M 미운영. |

## 4. 예상 질문 Q&A (18문항)

**Q1. 이 문서는 요구(R) 산출물인가, 설계(D) 산출물인가?**
요구(R) 산출물입니다. 헤더 "단계명: 분석"이 명시하듯 분석 단계에 속하며, "무엇을 해야 하는가(행위·시나리오)"를 다룹니다. 클래스·테이블·API 등 "어떻게"는 D 계열(D1·D2·D5·D8·D9 등)로 넘깁니다.

**Q2. 유스케이스는 총 몇 개이고 어떻게 묶이나?**
총 **18개**입니다. UCD-001(가공·검수 핵심 흐름)에 14개, UCD-002(데이터 증강 흐름)에 4개가 묶입니다.

**Q3. 주요 액터(사람)는 누구인가?**
**WORKER(라벨링 작업자)**와 **REVIEWER(검수자)** 둘뿐입니다. 나머지 5종(생성형AI·관제서버·비식별 솔루션·배치 시스템·시계열/AI추론)은 보조 액터(시스템)입니다. 포털 회원(PORTAL_USER)은 액터에 없습니다.

**Q4. 검수자(REVIEWER)가 수행하는 UC는 어떤 것들인가?**
UC-011(비식별 요청)·UC-013(비식별 옵션)·UC-016(상태·이력)·UC-022(시계열 메타 검토)·UC-006(정밀도 조절)·UC-023(검수 승인·반려)·UC-007(버전 저장)·UC-008(버전 비교·복구)·UC-009(통지)·UC-001(증강 요청)·UC-002(증강 등록)·UC-003(해상도 변경)·UC-010(증강 검수). 관리 권한이 통합된 역할이라 폭이 넓습니다.

**Q5. 작업자(WORKER)가 수행하는 UC는?**
UC-019(이벤트 마킹)·UC-021(라벨 편집·임시저장)·UC-004(객체 자동 추적)·UC-005(외곽 밀착)·UC-016(비식별 누락 신고 부분)·UC-008(버전 비교·복구, 본인 배정 제한)·UC-023(검수 제출자로서). 공통 제약은 **본인 배정 영상/프레임만** 다룰 수 있다는 점(NFR-013).

**Q6. 영상은 어떻게 처음 시스템에 들어오나?**
UC-018(영상 적재)입니다. **관제서버가 공유 데이터에서 영상을 학습용으로 설정 → 주기 배치가 픽업·적재**합니다. 사람 업로드가 아니며, **배치는 인증 불필요**입니다. 포털 사용자 업로드는 미제공.

**Q7. 왜 마킹은 비식별 영상으로 하나? 원본이 아니라?**
개인정보 보호 때문입니다. UC-019 구현 고려에 "마킹 화면은 **항상 비식별 영상을 서빙**하며 비식별 미완료 시 원본 노출을 차단"(NFR-005)이라고 명시됩니다. 비식별이 파이프라인 선두 단계라 마킹 시점엔 이미 비식별본이 준비됩니다.

**Q8. "검수 승인 = 작업 완료"란 무슨 뜻인가?**
UC-023의 핵심 규칙입니다. 작업 상태가 "완료"로 전이되는 시점은 **검수자가 승인하는 순간뿐**입니다. 승인은 동시에 버전 스냅샷(UC-007)을 생성하고 완료 통지(UC-009)를 유발합니다. 라벨 저장이나 검수 제출만으로는 완료가 아닙니다.

**Q9. 버전(스냅샷)은 언제 만들어지나? 라벨 저장할 때마다?**
아닙니다. **검수 승인 시점에만** 생성됩니다(UC-007). 라벨 임시저장(UC-021)은 작업본만 영속하고 버전은 만들지 않습니다. 이것이 "2계층 분리" 정책입니다.

**Q10. 검수는 2차 검수가 있나?**
없습니다. UC-023 구현 고려에 "검수는 **1인 승인 반복 방식(2차 검수 폐지)**"라고 명시됩니다. 반려되면 작업자가 재작업·재제출하고 승인까지 반복합니다.

**Q11. 비식별 누락을 발견하면 어떻게 되나?**
UC-016입니다. 작업자가 **본인 배정 영상만** 신고 → 시스템이 **해당 영상 전체 라벨을 복원용 스냅샷+이력으로 보존 후 삭제 + 영상 잠금 + 비식별 실패 마킹** → 외부 솔루션으로 **수동 비식별화** → 신고 해소·작업락 해제. 자동 재비식별 큐는 폐기되었습니다. 검수 완료 영상이면 수정 통지가 나갑니다.

**Q12. UC-004(자동 추적)와 UC-005(외곽 밀착)의 예외 흐름은?**
- UC-004: (가) AI 호출 실패/타임아웃 → 서킷 브레이커 동작+원본 라벨 유지, (나) 가림·장면전환·빠른 이동으로 정확도 저하 → 작업자 키프레임 수동 보정 후 보간 재계산.
- UC-005: (가) 외곽 인식 실패 → 수동 폴리곤 전환, (나) 추론 호출 실패 → 안내+기존 지정 유지. 또한 **mock/테스트용 응답은 자동 적용 차단**.

**Q13. 왜 자동 라벨링(추적·분할)은 원본 프레임에만 실행하나?**
UC-004·UC-005 구현 고려에 "자동 라벨링/외곽 분할은 **원본 프레임에만 실행하고 비식별본은 좌표를 공유**"라고 되어 있습니다. 원본·비식별본은 해상도가 같아 좌표를 공유할 수 있으므로 추론을 두 번 돌리지 않습니다(자원 효율).

**Q14. 증강 영상은 원본을 덮어쓰나?**
아닙니다. UC-002에서 **새 영상(RAW_SN)으로 등록**하고 원본 참조를 연결하며 원본 라벨/메타를 복사합니다. 새 영상은 미검수로 시작해 UC-010에서 별도 검수·통지 단위가 됩니다. 증강 3종(WINTER/NIGHT/RAIN)은 해상도가 같아 좌표를 그대로 복사합니다.

**Q15. 해상도 변경은 증강과 무엇이 다른가?**
해상도 변경(UC-003)은 **저작도구가 직접 수행**하는 다운스케일이며, 외부 증강 위탁이 아닙니다. **업스케일 거부, 영상 재생성 없음, 라벨 좌표 미제공, 새 영상 미생성**의 제약이 있고 표준 하위 해상도 화이트리스트만 허용합니다. 반면 증강(UC-001/002)은 외부 생성형 AI 위탁으로 새 영상을 만듭니다.

**Q16. 관제서버 통지에 실제 라벨 데이터가 담기나?**
아닙니다. UC-009는 **요약만(이벤트 타입·작업 ID·영상 메타·완료 일시·프레임 개수·요약 카운트·요청 ID)** 담고 **개인정보·토큰·라벨/메타 본문은 미포함**(NFR-005)입니다. 관제서버가 통지 수신 후 **조회 인터페이스로 상세를 가져갑니다**(단방향 발송 + 수신측 조회 패턴). 멱등(요청 ID)·재등록 큐가 적용됩니다.

**Q17. UC 번호가 001~026 사이에 비어 있는데(017·020·024·025·026 등) 왜인가?**
부록의 "범위 외(제외) UC"로 편집상 제외되었기 때문입니다. UC-024(포털 라벨 작업)·UC-025(라벨 프리셋)·UC-026(배치 처리)·UC-020(작업 배정·이력)은 R1 전용 요구가 없는 운영 워크플로우, UC-017(올가미)은 SFR-08-01이 UC-004로 재해석되어, UC-012/014/015는 외부 솔루션·보안 인프라 책임으로 제외되었습니다. 누락이 아니라 의도적 범위 조정입니다.

**Q18. 포털(PORTAL_USER) 기능은 왜 하나도 없나?**
부록에 명시: 포털 서브시스템(SS-010)은 "본 버전에서 활성 R1 기능 유스케이스가 없어" 제외되었습니다. 저작도구의 이번 R2는 가공·검수·증강의 내부 워크플로우(REVIEWER·WORKER 중심)에 집중합니다.

**Q19. "대안 시나리오 — 해당 없음"인 UC는 무엇인가?**
UC-013(비식별 옵션 설정)·UC-007(버전 저장)·UC-001(증강 요청) 세 개입니다. 단순하거나 실패 분기가 별도 UC로 흡수되어 대안 흐름을 두지 않았습니다.

**Q20. 외부 연동 실패는 공통적으로 어떻게 처리되나?**
회복력 패턴이 일관됩니다 — **타임아웃·재시도·서킷 브레이커**(NFR-004, UC-011). AI 추론 실패 시 서킷 브레이커 동작+원본 유지(UC-004), 통지 실패 시 미발송 큐 후 재시도(UC-009), 비식별 실패 시 상태 실패 마킹+재시도 큐+원본 보존(UC-011/018). 공통 원칙: **원본·기존 데이터는 절대 손실되지 않는다**.

## 5. 다른 산출물과의 연계

R2 유스케이스 명세서는 CBD 산출물 그래프의 **허브** 역할을 합니다. R1(요구)을 입력으로 받아, D(설계)·시험 산출물의 근거가 됩니다.

### 5.1 상류(입력) — R1 요구사항정의서
- R2의 각 UC "관련 요구사항 ID"(RQ-SFR-NN-NN)와 구현 고려의 NFR이 **R1 요구를 직접 참조**합니다.
- 예: UC-004↔RQ-SFR-08-01, UC-009↔RQ-SFR-08-04/05, UC-001↔RQ-SFR-07-01, UC-018↔RQ-SFR-11-04.
- R2는 R1을 "실행 가능한 시나리오"로 구체화한 것이므로, **요구 변경 시 R2 UC부터 갱신**해야 추적성이 유지됩니다.

### 5.2 D1 클래스설계서 — 가장 밀접(구조)
- UC의 명사(영상·라벨·버전·스냅샷·마킹·검수·통지·증강)가 **도메인 클래스·엔티티**로 매핑됩니다.
- UC 흐름의 동사(승인·반려·복구·통지·마킹 완료)가 **클래스의 비즈니스 메서드**로 나타납니다.
- 예: UC-023의 "승인"→검수 서비스의 승인 메서드, UC-007의 "스냅샷 저장"→버전 엔티티, UC-009의 "통지 발행"→통지 클라이언트.

### 5.3 D2 UI설계서 — 가장 밀접(화면)
- 각 UC의 "기본 시나리오"는 **화면 단위 사용자 조작 순서**의 근거입니다.
- 예: UC-019(마킹 화면: 비식별 영상 스트리밍·배속·단축키)·UC-021(라벨링 캔버스)·UC-022(시계열 메타 검토 화면)·UC-023(검수 화면)·UC-006(시스템 설정 화면)·UC-010(증강 검수 화면).
- 대안 흐름(타인 배정 거부·사유 누락 거부·상태 충돌 등)은 **화면의 에러/검증 UX**로 설계됩니다.

### 5.4 D3 (인터페이스/연동 관련 설계)
- UC-009(통지)·UC-011(비식별 위탁)·UC-001/002(증강 위탁·회신)·UC-018(관제 학습용 설정 읽기)의 **외부 연동 지점**이 D3(연동규격/인터페이스 설계)의 입력이 됩니다.
- 단방향 outbound 통지 + 수신측 조회 패턴(UC-009)은 인터페이스 계약의 핵심 근거.

### 5.5 D5 아키텍처설계서
- 액터-UC 관계(UCD)와 "배치 파이프라인(적재→비식별→마킹→메타→추출→라벨링→보간)" 흐름은 **아키텍처 컴포넌트 경계·데이터 흐름**의 근거입니다.
- 외부/내부 경계(관제서버·비식별 솔루션·생성형AI·AI 추론 서버 vs 저작도구 본체)가 UCD의 `[외부]`/`[내부]` 표기로 이미 구분됩니다.
- NFR 참조(NFR-001 처리량·NFR-004 회복력·NFR-005 보안·NFR-013 접근통제)는 아키텍처 비기능 요구로 연결.

### 5.6 D8 / D9 (데이터·테이블 설계)
- UC의 "종료조건"에 나오는 저장 대상(영상 메타·비식별 이력·라벨 작업본·버전 스냅샷·통지 요청·증강 새 영상)이 **테이블(LS_* 계열)**로 설계됩니다.
- 예: UC-007 스냅샷→라벨 버전 테이블, UC-016 신고→비식별 신고 테이블, UC-002 새 영상→원본 참조(PARENT) 컬럼.
- 주의: 관제 공유 테이블(MNG_*)은 READ 대상이라 D8/D9 산출물 비대상(프로젝트 정책).

### 5.7 D10 통합시험시나리오 — UC 검증
- **R2 UC ↔ D10 테스트 시나리오는 1:1에 가까운 검증 쌍**입니다.
- 각 UC의 기본 시나리오는 **정상 케이스 테스트**, 대안 시나리오는 **예외/경계 케이스 테스트**로 변환됩니다.
- 예: UC-023 대안(가) 재제출 반복·(나) 검수완료 후 수정 → 통합시험의 반려-재제출-승인 시나리오, 수정 통지 발행 검증.
- 전제조건·종료조건은 테스트의 **사전 준비(setup)와 검증 지점(assertion)**이 됩니다.

### 5.8 D11 (연계 설계 산출물)
- 원문에 D11의 구체 내용은 명시되지 않으나(원문에 명시되지 않음), CBD 체계상 D11은 앞선 설계(D1~D10)를 종합·연계하는 산출물로 R2 UC를 최종 추적 대상으로 참조합니다.

### 5.9 요약 — 추적성 체인
```
R1 요구(SFR/NFR)
   └─▶ R2 유스케이스(UC 18개, UCD 2개, 액터 7종)   ← 본 문서
          ├─▶ D1 클래스(명사→엔티티, 동사→메서드)
          ├─▶ D2 UI(기본 시나리오→화면 조작, 대안→에러 UX)
          ├─▶ D3 인터페이스/연동(외부 연동 지점)
          ├─▶ D5 아키텍처(컴포넌트 경계·데이터 흐름·NFR)
          ├─▶ D8/D9 데이터·테이블(종료조건 저장 대상→LS_* 테이블)
          └─▶ D10 통합시험(UC↔테스트 시나리오 1:1 검증)
```
