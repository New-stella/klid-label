## 1. 이 문서는 무엇인가

### 1.1 한 문장 정의
D2 사용자 인터페이스 설계서는 **학습데이터 저작도구가 사용자에게 제공하는 화면(UI)의 전체 구조와 메뉴 체계, 화면 목록, 그리고 각 화면의 상세 설계 내역**을 규정하는 CBD(Component Based Development, 컴포넌트 기반 개발) 설계 산출물입니다.

원문 "작성 목적"의 표현을 그대로 옮기면 다음과 같습니다.
> "시스템이 제공하는 사용자 인터페이스의 전체 구조와 메뉴 형식, 화면 목록과 화면의 상세 설계 내역을 기술한다."

### 1.2 문서의 범위 (무엇을 다루고 무엇을 다루지 않는가)
D2는 **R1 기능 요구사항(SFR)을 실현하는 유스케이스에 매핑된 화면만** 본문에 담습니다. 이 원칙은 문서 전반을 관통하는 핵심 필터입니다.

- **본문에 포함**: R1 기능 요구사항 → 유스케이스(KLID-AT-UC-NNN) → 화면(KLID-AT-SC-NNN)으로 추적되는 10개 화면.
- **본문에서 제외**: 인증·진입 화면, 운영·조회 보조 화면(대시보드·작업 목록 등), 관리 화면(사용자 관리·프리셋 관리), 게시판, 포털 라벨링 등 "R1 기능 요구사항 매핑이 없는" 활성 화면과, 이미 폐기된 비활성 화면. 이들은 원문 맨 끝 **부록 "범위 제외 화면 및 빈 셀 사유"** 에 상태와 사유가 명시되어 있습니다.

즉 D2는 "저작도구의 모든 화면 카탈로그"가 아니라 "R1 요구사항을 실현하는 화면의 정식 설계서"입니다. 이 점을 이해하지 못하면 "왜 로그인 화면이 없지?", "왜 대시보드가 빠졌지?" 같은 혼란이 생깁니다. 답은 항상 "R1 기능 요구사항 매핑 여부"입니다.

### 1.3 CBD 산출물 체계에서의 위치
이 프로젝트는 CBD 방법론에 따라 요구사항(R 시리즈)과 설계(D 시리즈) 산출물을 생성합니다. D2는 그중 **설계 단계**의 UI 산출물로, 다음과 같은 연결 고리 위에 놓입니다.

```
R1 기능 요구사항(SFR)
      │  (실현)
      ▼
R2 유스케이스명세서 (KLID-AT-UC-NNN)  ── D2가 "관련 유스케이스 ID"로 참조
      │
      ▼
D1 클래스설계서 (시퀀스도 KLID-AT-SD-NNN) ── D2가 "관련 시퀀스도 ID"로 참조
      │
      ▼
D2 사용자 인터페이스 설계서  ← ★ 본 문서 (화면 KLID-AT-SC-NNN)
      │
      ├─→ D3 컴포넌트설계서 (화면을 구성하는 UI 컴포넌트)
      ├─→ D8 ERD / D9 DB설계서 (입출력 항목의 컨트롤명·타입이 데이터 모델과 연결)
      └─→ D10 통합시험시나리오 / D11 단위시험절차서 (화면 흐름·검증 규칙이 시험 케이스로)
```

D2는 위쪽으로는 유스케이스·시퀀스도를 참조해 "요구사항이 화면으로 어떻게 실현되는가"를 보이고, 아래쪽으로는 컴포넌트·데이터·시험 산출물에 "화면이 무엇을 입력받고 출력하는가"를 넘겨줍니다.

### 1.4 문서 생성 방식
제·개정 이력에 따르면 이 문서는 **LogiCraft 그래프 기반으로 `/cc-doc-gen` 명령을 통해 자동 생성**되었습니다. LogiCraft는 35종 ITEM으로 시스템 설계를 그래프로 추적·진화시키는 도구로, 화면(SCREEN) ITEM과 유스케이스(USE_CASE)·시퀀스도 ITEM 간의 링크가 D2의 "관련 유스케이스 ID / 관련 시퀀스도 ID" 표로 그대로 반영됩니다. 따라서 D2의 ID 매핑은 사람이 임의로 적은 것이 아니라 그래프 링크에서 파생된 것입니다.

### 1.5 ID 표기 규칙 (문서 첫 줄의 중요 규약)
원문 최상단은 모든 ID를 **전체 형식 `KLID-AT-XX-NNN`** 으로 표기하도록 규정합니다.
- 올바른 예: `KLID-AT-SC-005`, `KLID-AT-UC-021`, `KLID-AT-SD-004`
- 금지: 끝부분만 약식 표기(`UC-001` 같은 축약).
- 범위 표기: 시작 ID만 전체형으로(예: `KLID-AT-UC-001~013`).
- 예외: 요구사항(`RQ-SFR-NN-NN`)·시스템시험(`KLID-ST-NNN`) 등 타 체계 ID는 각자 원형 유지.

여기서 `XX`(중간 코드)의 의미는 문서 말미 "작성 시 참고사항"에 정리되어 있습니다.
- `SC` = 화면(Screen)
- `UC` = 유스케이스(Use Case, R2 참조)
- `SD` = 시퀀스도(Sequence Diagram, D1 참조)
- `OUT` = 출력물(Output)
- 그 외 문서 첫 줄에 열거된 CO/DC/DCD/AC/EN/ERD/TB/II/IC/IF/UCD/ACT 등은 다른 산출물에서 쓰는 코드입니다.

## 2. 섹션별 상세 해설

원문은 크게 다음 순서로 구성됩니다: ① 작성 목적·방법, ② 산출물 양식(이력·헤더), ③ **1. 사용자 인터페이스 구조도**, ④ **2. 사용자 인터페이스 목록**(화면·출력물), ⑤ **3. 화면 상세 설계**(화면 10개 반복), ⑥ 항목 설명·참고사항, ⑦ 부록(범위 제외·빈 셀 사유). 아래에서 순서대로 해설합니다.

### 2.0 헤더와 기본 메타
- 시스템명: AI 기반 지방정부 CCTV 관제지원시스템(2차)
- 서브시스템명: 학습데이터 저작도구
- 단계명: 설계 / 작성일자: 2026-06-23 / 버전: 1.0

저작도구는 관제 지원 시스템의 하위 서브시스템으로, CCTV 영상을 AI 학습데이터로 만드는(라벨링·검수·버전관리) 도구입니다. 이 정체성이 화면 구성 전반(마킹·라벨링 캔버스·검수·증강)에 반영됩니다.

### 2.1 사용자 인터페이스 구조도 (원문 §1)

**작성 원칙**: 전체 시스템에 대해 **1개만** 작성합니다(화면처럼 반복하지 않음). 최상위에서 Top-down으로, **저작도구 내부 채널(관제서버와 동일 도메인 SSO 진입) 기준의 LNB(Left Navigation Bar, 좌측 내비게이션) 메뉴 트리**로 표현합니다. 구조도에는 R1 유스케이스에 매핑된 화면이 속한 메뉴 경로만 기재합니다.

**메뉴 트리 (Level 1~4)**:

| 업무 영역 (Level 1) | Level 2 | Level 3 | Level 4 |
|---|---|---|---|
| 영상 | 영상 처리 현황 | 영상 목록(KLID-AT-SC-007) | - |
| 영상 | 영상 처리 현황 | 영상 상세(KLID-AT-SC-009) | - |
| 영상 | 영상 처리 현황 | 마킹(KLID-AT-SC-006) | - |
| 작업 | 검수 목록 | 검수 목록(KLID-AT-SC-018) | 검수 상세(KLID-AT-SC-019) |
| 작업 | 라벨링 캔버스 | 라벨링 캔버스(KLID-AT-SC-005) | - |
| 작업 | 라벨 이력 | 라벨 이력(KLID-AT-SC-010) | - |
| 데이터 | 증강 요청 | 증강 요청(KLID-AT-SC-022) | 증강 결과(KLID-AT-SC-023) |
| 관리 | 시스템 설정 | 시스템 설정(KLID-AT-SC-025) | - |

**4개의 최상위 업무 영역**으로 정보 구조(IA)가 나뉩니다.
- **영상**: 관제서버에서 인계받아 적재된 영상의 처리 현황·상세·마킹.
- **작업**: 검수(목록·상세), 라벨링 캔버스, 라벨 이력(버전관리).
- **데이터**: 증강 요청·증강 결과.
- **관리**: 시스템 설정.

**메뉴 노출 정책 (중요)**: 원문은 구조도 아래에 두 가지 노출 규칙을 명시합니다.
1. **직접 노출하지 않는 화면**(상위 목록/맥락 화면에서만 진입): 영상 상세, 마킹, 라벨링 캔버스, 라벨 이력, 검수 상세, 증강 결과. 즉 LNB에는 목록성 화면만 뜨고, 세부·편집 화면은 목록에서 클릭해 들어갑니다.
2. **권한 기반 노출**: 데이터(증강) 그룹과 관리(시스템 설정) 그룹은 **검수자(REVIEWER) 전용**으로만 노출됩니다.

이 정책은 "왜 라벨링 캔버스가 메뉴에 안 보이나?"(→ 영상/프레임 맥락에서 진입), "왜 작업자에게 증강·설정 메뉴가 없나?"(→ REVIEWER 전용) 같은 질문의 근거입니다.

화면과 별개로 **출력물(Output)** 2건이 정의됩니다. 출력물은 화면이 만들어내는 산출 데이터/문서를 의미합니다.

| 출력물 ID | 출력물명 | 관련 유스케이스 ID |
|---|---|---|
| KLID-AT-OUT-001 | 라벨 버전 변경 내역(Diff) | KLID-AT-UC-008 |

- **OUT-002 (해상도 변경 이미지셋)**: 증강 요청 화면(SC-022)에서 해상도 변경을 수행할 때 저작도구가 직접 다운스케일해 만드는 프레임 이미지셋입니다.

### 2.3 화면 상세 설계 개요 (원문 §3)

**작성 원칙**: 화면별로 1개씩 반복 작성합니다. 각 화면은 하나의 `<table>` 안에 다음을 모두 담습니다.
- 화면 ID / 화면명 / 관련 유스케이스 ID / 관련 시퀀스도 ID
- 화면유형(입력·조회·갱신·삭제 등) / 메뉴경로 / 화면개요
- **와이어프레임**(HTML 코드 블록으로 그린 화면 목업)
- **입출력 항목** 표: 항목명·컨트롤명·타입 및 길이·속성·Validation Check
- **처리 내용**: 각 처리 흐름과 대응하는 시퀀스도 ID
- **기술적 고려사항**

**속성 표기법**: Input(I) / Output(O) / ReadOnly(RO) / Editable(E) / Hidden(H). 복합 속성은 슬래시로 구분(예: `I/E` = 입력 가능하고 편집 가능).

아래 2.4.1~2.4.10에서 10개 화면을 원문 순서대로 해설합니다.

### 2.4.1 KLID-AT-SC-005 — 라벨링 캔버스 화면

- **관련 유스케이스**: KLID-AT-UC-021, UC-004, UC-005, UC-008, UC-016, UC-022 (6개)
- **관련 시퀀스도**: KLID-AT-SD-021, SD-004, SD-005, SD-008, SD-016, SD-022
- **화면유형**: 입력·갱신·삭제 / **메뉴경로**: 작업 > 라벨링 캔버스
- **사용 주체**: 라벨링 작업자(WORKER)·검수자(REVIEWER)

**목적**: 배정된 영상 프레임에 바운딩박스·폴리곤·세그멘테이션 라벨을 편집·임시저장하는 **풀스크린 캔버스**입니다. 저작도구의 핵심 작업 화면으로, 6개 유스케이스를 하나의 화면이 실현합니다.

**구성 요소(와이어프레임 기준)**:
- **헤더(상단 40px)**: 닫기(✕), 현재 위치(CCTV-01 / Frame 12), 이벤트 태그(쓰러짐), 프레임 진행(Frame 12/60), "● 편집 중" 상태, DEID 배지, **비식별 누락 신고 / 히스토리 / 저장 / 검수제출** 버튼.
- **좌측 도구바(48px)**: 선택 / 박스 / 폴리곤 / 분할 / 추적 / 삭제 도구.
- **라벨 마스터 사이드바(120px)**: 사람(1)·차량(2)·자전거(3) 등 활성 라벨 선택.

- **비활성(폐기)**: 비식별 목록/상세(1차 캔버스 블러 방식 폐기 → 2차 외부 비식별 솔루션 대체), 영상 처리 현황(전용)/작업 배정(전용)/오토라벨 요약/VLM 메타 검토/포털 홈(진입점 없어 다른 화면으로 기능 흡수).

**특기 사항**:
- VLM 시계열 메타 검토(UC-022) 전용 화면은 폐기되고 **라벨링 캔버스(SC-005)의 시계열 메타 패널로 이관**되었습니다. 그래서 SC-005의 관련 유스케이스에 UC-022가 포함됩니다.
- 비식별 옵션 설정(UC-013)은 전용 활성 화면 없이 외부 비식별 솔루션 옵션을 관리 화면에서 설정하는 운영 동선으로 처리됩니다.

**빈 셀(`-`) 사유**: 데이터 미상으로 인한 빈 셀은 없습니다. 모든 화면에 유스케이스·시퀀스도가 매핑되었고, `-` 표기는 성격상 부재(읽기 전용 항목의 Validation 등)를 의미합니다. 컴포넌트 명세·메뉴구조 보조 자료(ui_component·navigation_tree)는 화면 상세에 충분히 표현되어 별도 섹션을 두지 않았습니다.

## 3. 핵심 용어

| 용어 | 정의 (D2 맥락) |
|---|---|
| **CBD** | Component Based Development. 컴포넌트 기반 개발 방법론. R(요구)·D(설계) 시리즈 산출물 체계를 따르며 D2는 그중 UI 설계서. |
| **화면 ID (KLID-AT-SC-NNN)** | Screen. 화면마다 부여하는 유일 식별자. `KLID`(프로젝트)-`AT`(저작도구 서브시스템)-`SC`(화면)-일련번호. |
| **유스케이스 ID (KLID-AT-UC-NNN)** | Use Case. R2 유스케이스명세서의 유스케이스. D2 화면이 어떤 요구 시나리오를 실현하는지 가리킴. |
| **시퀀스도 ID (KLID-AT-SD-NNN)** | Sequence Diagram. D1 클래스설계서의 시퀀스도. 화면 처리 흐름이 내부적으로 어떤 객체 상호작용으로 실현되는지 연결. |
| **출력물 ID (KLID-AT-OUT-NNN)** | Output. 화면이 산출하는 문서/데이터(Diff, 이미지셋). |
| **IA (Information Architecture)** | 정보 구조. 여기서는 영상·작업·데이터·관리 4개 업무 영역으로 나뉜 LNB 메뉴 트리(Level 1~4). |
| **LNB (Left Navigation Bar)** | 좌측 내비게이션. 저작도구의 주 메뉴 표현 방식. |
| **입출력 속성 (I/O/RO/E/H)** | Input·Output·ReadOnly·Editable·Hidden. 화면 항목이 입력용인지 출력용인지 등 표기. 복합은 슬래시(`I/E`). |
| **컨트롤명** | 화면 항목의 프로그램 식별자(예: `activeLabelId`, `params.dataSttsCd`). FE 상태/API 파라미터·DB 컬럼과 연결되는 이름. |
| **Validation Check** | 입력 검증 규칙(필수 여부·범위·길이·형식). 화면과 서버에서 함께 검증. |
| **와이어프레임** | 화면 레이아웃 목업. D2는 HTML 코드 블록으로 각 화면의 배치를 표현. |
| **반응형(Responsive)** | 컨테이너/화면 크기 변화에 맞춰 레이아웃·캔버스가 자동 조정되는 렌더링. 라벨링 캔버스가 크기 변화를 자동 측정해 렌더링. |
| **라벨링 캔버스** | 프레임 이미지 위에 바운딩박스·폴리곤·세그멘테이션을 그리는 편집 영역. 프로젝트 맥락상 konva.js 기반. |
| **바운딩박스/폴리곤/세그멘테이션** | 라벨 유형. 사각형 박스 / 다각형 / 픽셀 단위 분할. |
| **객체 추적(Track)** | 시작 프레임 박스를 후속 프레임으로 전파 + 빈 프레임 보간(AI 보조, SD-004). |
| **외곽 경계 밀착** | 클릭/박스 한 번으로 AI가 외곽 폴리곤+신뢰도 산출 후 단순화 적용(SD-005). |
| **시계열 메타(VLM 텍스트)** | 외부 VLM(Vision-Language Model) 시계열 분석 결과 텍스트. 캔버스 우측 패널에서 검토·수정(SD-022). |
| **비식별(DEID)** | 개인정보 마스킹 처리된 영상. 마킹·스트리밍은 항상 비식별 영상만 서빙. |
| **비식별 누락 신고** | 개인정보 노출 발견 시 신고 → 영상 잠금 + 라벨 안전 삭제. 라벨링 캔버스(프레임)·마킹(영상 단위)에서 동선 제공. |
| **DB 스냅샷 버전관리** | 외부 형상관리(Git 등) 없이 검수 승인 시점의 라벨 전체 스냅샷을 DB에 저장·비교·롤백하는 방식. |
| **오토라벨** | YOLO/SAM2 등 AI가 자동 생성한 라벨. 영상 상세에서 총량·비율·신뢰도 분포 조회. |
| **역할(REVIEWER/WORKER/PORTAL_USER)** | 검수자 / 라벨링 작업자 / 포털 회원. D2에서는 REVIEWER·WORKER가 주로 등장(PORTAL_USER는 3.4 참조). |
| **WCAG** | Web Content Accessibility Guidelines. 웹 접근성 지침(프로젝트 맥락상 2.1 AA 준수 대상). ※ D2 원문에는 WCAG 명시 조항이 직접 등장하지 않음(3.4 Q&A 참조). |

## 4. 예상 질문 Q&A (15+)

**Q1. D2는 저작도구의 모든 화면을 담고 있나요?**
아니요. **R1 기능 요구사항(SFR)을 실현하는 유스케이스에 매핑된 10개 화면만** 본문에 담습니다. 인증·진입, 대시보드, 사용자 관리, 게시판, 포털 라벨링 등은 "R1 매핑 없음"으로 부록에서 제외 처리됩니다. 이는 산출물의 공통 범위 규칙입니다.

**Q2. 라벨링 캔버스(SC-005)는 왜 유스케이스가 6개나 되나요?**
하나의 풀스크린 캔버스가 라벨 편집(UC-021)·객체 추적(UC-004)·외곽 밀착(UC-005)·버전 비교/롤백(UC-008)·프레임 진입 맥락(UC-016)·시계열 메타 검토(UC-022)를 통합했기 때문입니다. 특히 VLM 메타 검토 전용 화면이 폐기되고 이 캔버스 패널로 이관되어 UC-022가 포함되었습니다.

**Q3. 각 화면은 누가 사용하나요? (권한별 차이)**
- **라벨링 캔버스(SC-005)**: WORKER·REVIEWER.
- **마킹(SC-006)**: 원문에 사용 주체 명시 없음(마킹 작업 화면). 프로젝트 맥락상 작업자가 비식별 영상에서 수행.
- **영상 목록(SC-007)**: 조회는 WORKER·REVIEWER 공통, **배정/재배정/일괄 배정은 REVIEWER 전용**.
- **영상 상세(SC-009)**: 조회 화면(권한 별도 명시 없음).
- **라벨 이력(SC-010)**: 조회·롤백. **작업자는 본인 배정 영상만 롤백** 가능.
- **검수 목록(SC-018)·검수 상세(SC-019)**: **REVIEWER 전용**.
- **증강 요청(SC-022)·증강 결과(SC-023)**: 데이터 그룹, **REVIEWER 전용**.
- **시스템 설정(SC-025)**: **REVIEWER 전용**.

**Q4. 왜 라벨링 캔버스·검수 상세·증강 결과 등은 LNB 메뉴에 직접 안 뜨나요?**
메뉴 노출 정책상 영상 상세·마킹·라벨링 캔버스·라벨 이력·검수 상세·증강 결과는 **상위 목록/맥락 화면에서 진입**하도록 설계되었기 때문입니다. LNB에는 목록성 화면만 노출됩니다.

**Q5. 영상 한 건을 라벨링하는 전체 화면 흐름은?**
① 영상 목록(SC-007)에서 REVIEWER가 작업자 배정 → ② 마킹(SC-006)에서 비식별 영상에 이벤트 마킹·마킹 완료(잔여 배치 시작) → ③ 영상 상세(SC-009)에서 프레임·오토라벨 확인, 확대 보기에서 라벨링 편집 진입 → ④ 라벨링 캔버스(SC-005)에서 라벨 편집·저장·검수제출 → ⑤ 검수 목록(SC-018)·검수 상세(SC-019)에서 REVIEWER 검수 → 승인 시 작업 완료 + 버전 스냅샷 저장 + 관제서버 완료 통지.

**Q6. 검수는 몇 단계인가요? 2차 검수가 있나요?**
**검수자 1인 승인 체계**로 2차 검수가 없습니다(SC-019 기술적 고려사항). 진입 시 검수 대기 → 검수중 자동 전이, 승인/반려로 종결하며 이벤트를 이력으로 기록합니다.

**Q7. 검수 승인이 되면 무슨 일이 일어나나요?**
① 작업이 완료로 전이되고, ② 승인 시점에 라벨 전체 스냅샷이 버전으로 저장되며(라벨 이력에서 조회·비교·롤백 가능), ③ 관제서버로 **완료 통지가 단방향 발행**됩니다. 완료 후 라벨·메타가 수정되면 **수정 요약 통지**(본문·민감정보 미포함)가 발행됩니다.

**Q8. 버전관리는 어떻게 동작하나요? Git을 쓰나요?**
아니요. **DB 스냅샷 기반**입니다(외부 형상관리 도구 미사용). 검수 승인 시점의 라벨 전체 스냅샷을 DB에 저장하고, 라벨 이력 화면(SC-010)·캔버스 히스토리 패널에서 두 버전 Diff(추가/수정/삭제, 출력물 OUT-001)를 비교하며, 최신이 아닌 버전 선택 시 롤백(새 이력 1건 생성)합니다.

**Q9. 증강 3종과 해상도 변경의 차이는?**
증강 3종(겨울·야간·우천)은 **외부 생성형 AI 서비스에 위탁**하고 결과를 받아 검수합니다. 해상도 변경은 **저작도구가 직접** 원본보다 낮은 해상도로 프레임 이미지셋을 다운스케일합니다(출력물 OUT-002). **업스케일은 거부**하고, 해상도 변경은 라벨 좌표를 변환·제공하지 않으며 새 영상을 생성하지 않습니다. 처리 종류·대상 영상 모두 단일 선택입니다.

**Q10. 증강 결과를 "채택"하면 어떻게 되나요?**
**새 영상이 생성**되어 원본을 부모로 연결하고, 원본 라벨·메타를 좌표·속성 그대로 복사해 **미검수 상태로 등록**됩니다. 이후 이 새 영상은 활용 여부 검수 대상이 됩니다. 거부 시에는 사유(1~500자)를 입력하며, 미검수 외 상태 중복 처리·사유 누락은 거부됩니다.

**Q11. 비식별 누락 신고는 어디서, 어떻게 하나요?**
두 곳에서 가능합니다. **라벨링 캔버스(SC-005)**에서 프레임 라벨링 중, **마킹 화면(SC-006)**에서 영상 단위로. 신고 시 해당 영상이 잠기고 라벨이 안전 삭제되며, 잠금 상태에서는 저장이 비활성화됩니다. 이미 잠긴 영상 중복 신고·타인 배정 영상 신고는 거부됩니다. 별도 "비식별 신고 관리" 화면은 R1 매핑이 없어 D2 본문에서 제외되었습니다.

**Q12. 마킹 화면에서 이벤트명은 어떻게 입력하나요?**
입력하지 않습니다. **이벤트명은 관제 클립 메타에서 자동 소싱**됩니다. 사용자는 자동(프레임 간격)/수동(단축키) 모드로 이벤트 시점만 마킹합니다.

**Q13. 목록 화면들은 대량 데이터를 어떻게 다루나요?**
모두 **페이지 단위 조회**로 대량 데이터를 분할 처리합니다(영상 목록·검수 목록·증강 대상 영상 목록). 조회·정렬·페이지 조건을 **화면 주소(URL)에 반영**해 뒤로가기·새로고침에서 유지하며, 정렬 변경 시 첫 페이지로 초기화합니다.

**Q14. 접근성(WCAG)은 어떻게 준수하나요?**
D2 원문에는 WCAG 조항이 직접 명시되어 있지 않습니다(**원문에 명시되지 않음**). 다만 프로젝트 CLAUDE.md 맥락상 포털은 WCAG 2.1 AA 준수 대상이며, D2에서 접근성과 연관되는 실질 조치로는 인증 토큰 기반 이미지 로딩, 상태 배지·색상 구분(Diff의 추가/수정/삭제 색상), 읽기 전용 캔버스 등이 등장합니다. 명시적 접근성 규정은 D2 범위가 아닌 컴포넌트/프론트엔드 규칙에서 다뤄집니다.

**Q15. 화면 항목의 "컨트롤명"은 무엇에 쓰이나요?**
컨트롤명(`activeLabelId`, `params.dataSttsCd`, `YOLO_CONF_THRESHOLD` 등)은 화면 항목의 프로그램 식별자로, FE 상태·API 파라미터·DB 컬럼과 연결되는 이름입니다. 따라서 D8 ERD/D9 DB설계서·D3 컴포넌트설계서로 추적하는 앵커 역할을 합니다.

**Q16. AI 보조 라벨링(추적·밀착)이 실패하면 화면은 어떻게 되나요?**
AI 보조 라벨링은 외부 추론 호출이므로 **타임아웃·재시도·장애 차단(서킷 브레이커) 정책**을 적용하고, 실패 시 **기존 라벨을 보존**합니다. 객체 추적 실패는 "추적 실패" 안내 후 기존 라벨 유지, 외곽 인식 실패는 수동 폴리곤으로 전환합니다.

**Q17. 시스템 설정에서 "라벨링 정밀도"를 바꾸면 무엇이 달라지나요?**
경계 세밀함(`POLYGON_SIMPLIFY_TOLERANCE`, 0.0~50.0)을 조절해 저장하면 이후 **객체 추적·외곽 밀착 결과의 경계 세밀함**이 제어됩니다. 설정은 짧은 유효시간 캐시로 반영되며, 조회 실패 시 기본값으로 안전 폴백합니다.

**Q18. 영상은 왜 항상 비식별본만 보여주나요?**
개인정보 보호를 위해 마킹·스트리밍은 **항상 비식별 영상만** 서빙하고, 비식별 미완료 영상은 노출하지 않습니다. 라벨 좌표는 원본과 동일 해상도이므로 비식별본과 공유합니다.

**Q19. 검수 목록의 KPI(검수 대기/검수중/승인/반려) 집계에서 제외되는 것은?**
**라벨링 진행 중 작업**은 검수 목록·집계에서 제외됩니다(아직 검수 대상이 아니므로).

**Q20. 포털 회원(PORTAL_USER) 화면은 D2에 있나요?**
없습니다. 포털은 데이터마트 영상 선택 전용으로 활성 R1 기능 요구사항 매핑이 없어 "포털 라벨링" 화면이 D2 본문에서 제외되었습니다(부록). D2 본문 10개 화면은 REVIEWER·WORKER 대상입니다.

## 5. 다른 산출물과의 연계

D2는 CBD 산출물 그래프에서 위·아래로 촘촘히 연결됩니다. 각 화면 상세 표의 "관련 유스케이스 ID / 관련 시퀀스도 ID / 입출력 항목"이 곧 연계 앵커입니다.

### 5.1 R2 유스케이스명세서 (상류 — 요구 시나리오)
- **연결 지점**: 각 화면의 "관련 유스케이스 ID"(KLID-AT-UC-NNN).
- D2 화면은 R2의 유스케이스를 화면으로 실현합니다. 예: SC-018/SC-019 ← UC-023(검수), SC-022 ← UC-001/UC-003(증강·해상도), SC-005 ← UC-021/004/005/008/016/022.
- 부록의 "범위 제외" 논리도 R2 부록(제외/비활성 항목)과 정합됩니다("R2 부록 비활성"·"R2 부록 제외 항목과 정합" 문구).

### 5.2 D1 클래스설계서 (측면 — 내부 실현)
- **연결 지점**: 각 화면의 "관련 시퀀스도 ID"(KLID-AT-SD-NNN).
- 화면의 각 처리 흐름(예: "화면 진입 (KLID-AT-SD-021)")은 D1 시퀀스도의 객체 상호작용으로 실현됩니다. 화면이 "무엇을 하는가"(D2)와 "어떻게 객체가 협력하는가"(D1)가 SD-ID로 연결됩니다.

### 5.3 D3 컴포넌트설계서 (하류 — UI 컴포넌트)
- D2 와이어프레임의 구성 요소(도구바·사이드바·캔버스·패널·KPI 카드·모달 등)와 입출력 항목이 D3의 UI 컴포넌트 명세로 상세화됩니다.
- 원문은 "컴포넌트 명세·메뉴구조 보조 자료(ui_component·navigation_tree)는 화면 상세에 포함된 정보로 충분해 별도 섹션을 두지 않았다"고 밝혀, D3와의 역할 분담을 명시합니다.

### 5.4 D5 아키텍처설계서 (측면 — 시스템 경계·연동)
- D2 기술적 고려사항의 외부 연동(AI 서버·비식별 서버·관제서버·포털서버, 타임아웃·재시도·서킷 브레이커, 비동기 배치, 관제서버 단방향 통지)은 D5의 시스템 경계·연동 아키텍처와 대응합니다.
- 시스템 설정 화면(SC-025)의 "외부 연동 헬스"(DB·디스크·관제·포털·AI·비식별)는 D5가 정의하는 외부 컴포넌트 집합과 일치합니다.

### 5.5 D8 ERD / D9 DB설계서 (하류 — 데이터 모델)
- **연결 지점**: 입출력 항목의 "컨트롤명·타입 및 길이".
- 예: `dataSttsCd`(처리 상태)·`eventTypeCd`(이벤트 유형)·`privacyTypeCd`(개인정보 분류)·`selectedSrcSn`(프레임)·라벨 좌표(left/top/right/bottom)·`vlmText`·라벨 버전 스냅샷 등은 D8 ERD 엔티티/D9 테이블 컬럼과 매핑됩니다.
- 라벨 버전 스냅샷(버전관리)은 프로젝트 맥락의 `LS_LABEL_VERSION` 등 데이터 모델로 이어집니다(구체 매핑은 D8/D9 소관).

### 5.6 D10 통합시험시나리오 (하류 — 통합 검증)
- D2의 화면 간 흐름(배정 → 마킹 → 라벨링 → 검수 → 승인/통지, 증강 요청 → 결과 채택)이 통합 시험 시나리오의 엔드투엔드 케이스로 전개됩니다.
- 상태 전이(검수 대기 → 검수중 → 승인/반려), 비동기 배치 시작, 관제서버 통지 발행 등이 통합 검증 항목이 됩니다.

### 5.7 D11 단위시험절차서 (하류 — 단위 검증)
- D2의 입출력 항목 "Validation Check"(필수·범위·길이·형식)와 처리 규칙(본인 배정 아닌 접근 거부, 완료 작업 재배정 차단, 반려 사유 필수, 업스케일 거부, 미검수 외 중복 처리 거부 등)이 단위 시험 케이스의 근거가 됩니다.
- 예: `intervalFrames` 1~3600, `YOLO_IMGSZ` 320~1920(32 배수), 반려 사유 1~1000자 등은 그대로 단위 검증 조건입니다.

### 5.8 출력물 연계 요약
- **OUT-001(라벨 버전 변경 내역 Diff)**: SC-010·SC-005 히스토리(UC-008/SD-008) → 버전관리·시험 검증 대상.
- **OUT-002(해상도 변경 이미지셋)**: SC-022(UC-003/SD-003) → 데이터 증강/해상도 처리 검증 대상.

### 부기 — 원문에 명시되지 않은 사항 정리
해설 중 다음은 D2 원문에 직접 조항이 없어 프로젝트 맥락으로 보완했음을 밝힙니다.
- WCAG 준수 조항(4-Q14): D2 원문 직접 명시 없음.
- 마킹 화면(SC-006)의 명시적 사용 주체(역할): 원문에 역할 라벨 직접 명시 없음(작업 성격상 작업자 수행으로 이해).
- 라벨링 캔버스가 konva.js 기반이라는 점: D2 원문이 아닌 프로젝트 기술 스택 맥락.
그 외 화면 목적·구성·처리·검증·연계는 모두 D2 원문 기재에 근거합니다.
