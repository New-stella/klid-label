# D1 클래스 설계서 — 종합 해설 (스터디가이드)

> 이 문서는 `docs/0705/D1-클래스설계서.md`(원문, 2,710행)를 처음 보는 사람도 어떤 질문에도 답할 수 있도록 풀어 쓴 **해설·학습 가이드**입니다. 원문을 그대로 옮기지 않고 "왜 그렇게 설계되었는가"를 설명하는 데 초점을 둡니다. 인용한 ID·클래스명·오퍼레이션은 모두 원문에 실재하는 것이며, 원문에 없는 내용은 "원문에 명시되지 않음"으로 표기합니다.
>
> 대상 시스템: **AI 기반 지방정부 CCTV 관제지원시스템(2차)** 의 서브시스템인 **학습데이터 저작도구**. 기술 구성은 Spring Boot 백엔드 + Python ai-server(YOLO/SAM2/VLM 추론) + React 프런트엔드의 모노레포입니다.

## 1. 이 문서는 무엇인가

### 1.1 한 줄 정의

D1 클래스 설계서는 **"저작도구의 각 유스케이스가 실제로 어떤 클래스들의 협력으로 실현되는가"** 를 그림(시퀀스도·클래스도)과 표(클래스 목록·클래스 정의)로 규정한 **소프트웨어/설계 관점의 정적·동적 클래스 모형** 문서입니다. 원문 "작성 목적"이 밝히듯 "소프트웨어 관점이나 설계 관점에서의 클래스 모형을 작성"하는 것이 목적입니다.

### 1.2 무엇을 답하는 문서인가

이 문서 하나만 있으면 다음 질문에 답할 수 있습니다.

- 어떤 유스케이스(예: "이벤트 마킹")를 처리하려면 **어떤 클래스들이 필요한가**? → §1 설계 클래스 목록
- 그 클래스들이 요청을 받았을 때 **서로 어떤 순서로 메시지를 주고받는가**? → §2 시퀀스도
- 그 클래스들의 **정적 구조와 의존 방향(누가 누구를 참조하는가)** 은 어떻게 되는가? → §3 설계 클래스도
- 개별 클래스가 **어떤 속성·오퍼레이션(메서드)** 을 갖고, 그 각각이 무엇을 의미하는가? → §4 설계 클래스 정의

즉 D1은 "유스케이스 → 시퀀스 → 클래스도 → 클래스 명세" 로 이어지는 **설계 추적 사슬(traceability chain)** 을 한 문서 안에 담고 있습니다.

### 1.3 CBD 산출물 체계에서의 위치

이 프로젝트는 **CBD(Component Based Development, 컴포넌트 기반 개발)** 표준 산출물 체계를 따릅니다. 산출물은 크게 요구(R계열)와 설계(D계열)로 나뉩니다. D1은 설계 단계의 첫 번째 클래스 산출물로서, 위로는 요구를, 아래로는 데이터·컴포넌트·시험 산출물을 잇는 **허브** 역할을 합니다.

```
R2 유스케이스명세서 ──(실현 단위)──▶ D1 클래스설계서 ──▶ D3 컴포넌트설계서(내부 클래스 ID)
        │                                  │
        │                                  ├──▶ D8 ERD (엔티티 = LS_* 클래스)
        │                                  ├──▶ D9 DB설계서 (테이블 컬럼)
        └──(화면 흐름)── D2 UI설계서        └──▶ D10 통합시험 / D11 단위시험 (검증 대상)
```

원문 헤더 아래 안내문은 이 관계를 명확히 규정합니다: "본 설계서는 유스케이스 명세서(R2)의 유스케이스를 **실현 단위**로 하여, 유스케이스별 시퀀스도(§2)와 설계 클래스도(§3)를 1:1로 작성"하고, "설계 클래스 ID(`KLID-AT-DC-NNN`)는 컴포넌트설계서(D3)의 내부 클래스 ID·엔티티관계모형설계서(D8)의 관련 클래스 ID와 **동일 체계**를 사용"한다고 명시합니다. 이는 **하나의 클래스 ID가 여러 산출물에 걸쳐 같은 대상을 가리킨다**는 뜻으로, 산출물 간 정합성의 근간입니다.

### 1.4 범위

원문 §1이 다루는 유스케이스는 **활성 18건**입니다. 부록에서 밝히듯, R2에서 결번 처리된 UC 번호(KLID-AT-UC-012·014·015·017·020 및 024 이상)는 D1에서도 동일하게 결번입니다. 따라서 D1은 "R2에 살아있는 모든 유스케이스를 빠짐없이, 그리고 결번은 결번대로 반영한" 완결적 대응 문서입니다.

### 1.5 ID 표기 규칙 (문서 전체 공통)

원문 맨 앞의 굵은 안내문은 **모든 ID를 전체 형식 `KLID-AT-XX-NNN` 으로 표기**하라고 못박습니다(예: `UC-001` 같은 약식 금지, 반드시 `KLID-AT-UC-001`). 범위 표기는 시작 ID만 전체형으로(예: `KLID-AT-UC-001~013`). 단 요구사항 ID(`RQ-SFR-NN-NN`)·시스템시험 ID(`KLID-ST-NNN`) 등 **타 체계 ID는 원형을 유지**합니다. 이 규칙 덕분에 접두어만 봐도 어느 산출물 체계의 식별자인지 즉시 구분됩니다.

ID 접두어 사전(이 문서에 등장하는 것):

| 접두어 | 의미 | 예시 |
|--------|------|------|
| `KLID-AT-UC` | 유스케이스(Use Case) | KLID-AT-UC-019 이벤트 마킹 |
| `KLID-AT-SD` | 시퀀스도(Sequence Diagram) | KLID-AT-SD-019 |
| `KLID-AT-DCD` | 설계 클래스도(Design Class Diagram) | KLID-AT-DCD-019 |
| `KLID-AT-DC` | 설계 클래스(Design Class) | KLID-AT-DC-061 MarkingService |

`AT` 는 Authoring Tool(저작도구)의 약어로, 관제서버 등 다른 서브시스템과 ID 공간을 구분합니다.

## 2. 섹션별 상세 해설

### 2.0 문서 머리말 — 작성 목적·방법·양식

원문은 본론 전에 세 가지를 규정합니다.

- **작성 목적**: 소프트웨어/설계 관점의 클래스 모형 작성.
- **작성 방법**: 설계 클래스를 도출하기 위해 **먼저 유스케이스별 시퀀스도를 그리고**, 거기서 튀어나온 객체·클래스를 연관관계로 묶어 유스케이스별 클래스도를 작성한다. 클래스도에는 클래스명·속성·오퍼레이션을 구체적으로 표현하고, 각 클래스는 상세 명세를 기술한다. → 이 방법론이 그대로 §2(시퀀스도) → §3(클래스도) → §4(클래스 정의) 의 문서 구조로 반영되어 있습니다. **"동적 흐름을 먼저 그려 클래스를 도출한다"** 는 것이 핵심 설계 철학입니다.
- **산출물 양식**: 제·개정 이력표(2026-06-23, v1.0, "LogiCraft 그래프 기반 생성 /cc-doc-gen")와 헤더표(시스템명/서브시스템명/단계/작성일자/버전). 제개정 이력의 "LogiCraft 그래프 기반 생성"은 이 문서가 **LogiCraft라는 산출물 그래프 관리 도구의 ITEM 데이터로부터 자동 생성**되었음을 의미합니다. 즉 D1의 클래스·ID·연결 관계는 사람이 손으로 표를 채운 것이 아니라 그래프 모델에서 파생되었고, 그래서 D3·D8과 ID 체계가 기계적으로 일치할 수 있습니다.

### 2.1 §1 설계 클래스 목록 — "유스케이스별 재료 명세서"

§1은 18개 유스케이스 각각에 대해 **그 유스케이스를 실현하는 데 동원되는 설계 클래스 목록**을 표로 나열합니다(1.1~1.18). 각 표의 컬럼은 `설계 클래스 ID | 설계 클래스명 | 관련 유스케이스ID` 3개입니다.

이 섹션의 핵심 성질은 서두 인용문에 있습니다: **"공통 클래스는 동일 설계 클래스 ID로 복수 목록에 교차 등장한다."** 예를 들어:

- `KLID-AT-DC-012 LsDataRaw`(원본 영상 엔티티)는 UC-002·003·011·016·018·019 등 다수 목록에 반복 등장합니다. 영상이 거의 모든 흐름의 중심이기 때문입니다.
- `KLID-AT-DC-003 LabelAccessGuard`(접근 가드)는 UC-004·005·008·021 등 라벨을 다루는 모든 유스케이스에 등장합니다.
- `KLID-AT-DC-091 VersionService`는 UC-007(버전 저장)·008(비교·복구)·016(신고 전 스냅샷)·023(검수 승인 스냅샷)에 걸쳐 재사용됩니다.

이렇게 **같은 ID가 여러 목록에 나타나는 것은 중복 오류가 아니라 재사용을 명시적으로 드러내는 설계 의도**입니다. 유스케이스마다 클래스를 새로 만들지 않고 공통 컴포넌트를 공유한다는 뜻이며, 이는 CBD의 컴포넌트 재사용 원칙과 맞닿아 있습니다.

### 2.2 §2 시퀀스도 — "동적 협력 시나리오"

§2는 18개 유스케이스마다 하나씩 Mermaid `sequenceDiagram` 을 제공합니다(KLID-AT-SD-001~023, 결번 제외). 각 시퀀스도 앞에는 메타표(시퀀스도 ID/명, 관련 UC ID, 주요 액터, 주요 클래스)가 붙습니다. 액터에는 사람 역할(REVIEWER 검수자, WORKER 라벨링 작업자)뿐 아니라 **외부 시스템**(생성형AI서비스[외부], 관제서버[외부], 비식별솔루션[외부], VLM서비스[외부])과 **배치시스템**이 등장합니다.

시퀀스도가 담고 있는 설계 결정을 몇 개 짚어 설명합니다.

**(1) 증강 요청/결과 — 비동기 위탁 + 멱등(SD-001, SD-002)**
- 요청(SD-001): 검수자가 대상 영상·증강 종류를 고르면, 서비스가 먼저 "원본이 **검수완료** 상태인지"를 확인하고, 증강 작업을 **대기 상태로 등록하며 멱등키를 발급**한 뒤 외부에 **비동기 위탁**합니다. 즉시 결과가 오지 않고 "위탁 접수"만 회신됩니다. → 이는 CLAUDE.md의 "증강 = 새 영상" 정책과 정합합니다.
- 결과 수신(SD-002): 외부가 결과를 보내면(멱등키·외부작업ID 포함) 서비스는 **멱등키 중복이면 무처리**, 아니면 **새 영상(RAW_SN)을 생성해 원본을 부모로 연결(미검수)**, **원본 라벨·메타를 새 영상에 복사**, **원본↔증강 라벨 매핑을 좌표 그대로 기록**합니다. 좌표를 그대로 복사하는 이유는 외부 증강 3종(겨울/야간/강수)이 해상도를 바꾸지 않기 때문입니다(→ §4 LsDataAugLblMap 의 `coordRecalcYn` 속성이 이를 뒷받침).

**(2) 해상도 변경 — 다운스케일 전용, 라벨 미제공(SD-003)**
검수자가 대상 영상·목표 하위 해상도를 지정하면, 서비스는 **"원본보다 낮은 해상도인지 검증(업스케일 거부)"** 후 프레임별 루프로 다운스케일하고, Persister가 **해상도 변경 이력 1건만 저장(영상·라벨 미생성)**, 최종 회신은 **"라벨 좌표 미제공"** 입니다. 이는 SFR-06-03 "해상도 변경은 증강이 아니라 저작도구 직접 수행"이라는 정책의 시퀀스 구현입니다.

**(3) 객체 자동 추적/밀착 — 접근 가드 + AI 호출 + 설정 기반 단순화(SD-004, SD-005)**
공통 패턴: `LabelAccessGuard 로 본인 배정 프레임 확인 → AiServerClient 로 추론 요청 → 좌표 범위 검증·폴리곤 단순화 → 저장`. 추적(SD-004)은 후속 프레임 루프를 돌며 매 프레임 `SystemConfigService.getDouble` 로 **폴리곤 단순화 정밀도를 조회**해 적용합니다. 밀착(SD-005)은 **"포인트·박스 중 하나만 허용"** 검증이 들어갑니다. mock 응답의 FE 자동적용 차단 등 세부는 CLAUDE.md에 있으나 D1 시퀀스는 "좌표 검증·단순화"까지를 명시합니다.

**(4) 정밀도 설정의 지연 반영(SD-006)**
검수자가 정밀도를 바꾸면 저장·캐시 갱신 후, 다이어그램 하단 `Note` 로 **"이후 추적·밀착 시 설정 정밀도로 폴리곤 단순화(조회 실패 시 기본값 폴백)"** 를 명시합니다. 설정 변경이 즉시 어딘가를 호출하는 게 아니라, **다음 추적/밀착 호출 때 조회되어 반영**되는 느슨한 결합임을 보여줍니다.

**(5) 검수 승인 시점의 버전 스냅샷(SD-007)**
검수자가 승인하면 `ReviewService → VersionService` 로 위임되어 **영상 전체 라벨 조회 → 스냅샷 구성 → 페이로드 해시 산출 → 검수 승인 스냅샷 저장(동일 해시 중복 식별) → 변경이력 기록** 순으로 진행됩니다. 라벨 저장 때가 아니라 **검수 승인 시점**에만 버전이 생기는 것이 핵심(→ CLAUDE.md "버전관리는 검수 완료 확정 단위 대상" 정책).

**(6) 버전 비교·복구(SD-008)**
한 시퀀스도 안에 조회→비교→복구 3개 사용자 상호작용이 순차로 담겨 있습니다. 비교는 "두 스냅샷 비교(추가·수정·삭제 산출)", 복구는 "대상 스냅샷을 새 활성 버전으로 복원"입니다. 접근 권한은 `LabelAccessGuard.requireAccessible`(검수자 전체·작업자 본인 배정)로 검증합니다.

**(7) 관제 통지 — 완료 vs 수정 분기, 디바운스(SD-009)**
`alt/else` 로 두 갈래를 나눕니다. **검수 완료**면 즉시 완료 페이로드(메타·요약 카운트, 본문 미포함)를 단방향 발행(요청ID 멱등). **검수 완료 후 수정**이면 `ControlNotifyDebouncer` 에 변경을 누적했다가 **디바운스(영상 1건 1회 집계)** 후 수정 통지를 발행합니다. 실패 시 미처리 큐 재시도, 수신측(관제서버)은 통지를 받은 뒤 **저작도구를 역조회해 상세를 확보**합니다. 이는 CLAUDE.md의 "단방향 outbound 통지 + inbound 조회 API" 정책과 일치합니다.

**(8) 비식별 처리 — 위탁 후 폴링(SD-011)**
`KpstDeidentService` 가 원본 업로드·프로젝트 생성으로 위탁하고 처리이력을 "완료 대기"로 기록합니다. 별도 `KpstDeidentPollJob` 이 **주기 폴링 루프**를 돌며 상태를 조회해 `alt` 로 완료/진행중/타임아웃을 분기합니다. 완료 시 결과 다운로드→**산출물 무결성 확인**→`KpstDeidentTxService` 로 **비식별 완료 전이(원본 보존)**, 진행중은 시도 증가·타임아웃 검사, 타임아웃은 실패 표시(재처리 대상). 상태 전이를 별도 Tx 서비스로 분리한 것이 특징입니다(원자적 전이 보장).

**(9) 비식별 상태·신고(SD-016)**
조회는 `VideoQueryService` 로 상태·이력 표시. 누락 발견 시 신고하면 `DeidentReportService` 가 **본인 배정 확인 → 삭제 전 복원 가능 비활성 스냅샷 기록(VersionService) → 해당 영상 전체 라벨 일괄 삭제·이력 보존 → 작업락 선점·비식별 실패 표시 → 신고 등록**. 외부 수동 비식별 후 신고 해소 시 미처리→해소 전이 + 작업락 해제. "삭제 전에 반드시 복원 스냅샷을 남긴다"는 안전장치가 시퀀스에 명시되어 있습니다.

**(10) 영상 적재 — 관제 학습용 설정 픽업 + 선두 비식별 자동(SD-018)**
관제서버가 공유 DB에 영상을 학습용으로 설정 → `ControlTrainingVideoScanJob`(주기 배치)이 스캔 → `TrainingVideoIngestService` 가 학습용 미적재 영상을 조회해 **1건 등록(대기 초기화)** → 적재 커밋 후 `IngestDeidentifyBridge` → `AsyncDeidentifyRunner` → `DeidentifyStep` 으로 **선두 비식별을 비동기 시작**. 대상이 없으면 무처리 종료. 이벤트-브리지-러너로 이어지는 **커밋 후 비동기 트리거** 패턴이 핵심입니다.

**(11) 이벤트 마킹 — 자동/수동, 완료 후 잔여 배치(SD-019)**
작업자가 **비식별 영상**을 재생하며 마킹하면, 서비스가 **본인 배정·비식별 완료 확인 → 영상 이벤트 유형 조회(이벤트명 자동 소싱)** 후 `alt` 로 자동(프레임 간격 기준 생성)/수동(입력 직렬화)을 분기해 저장하고, 커밋 후 `MarkingBatchBridge → BatchOrchestrator` 로 **잔여 배치(시계열·프레임추출·오토라벨링)를 시작**합니다.

**(12) 라벨 편집·임시저장(SD-021)**
조회·저장 모두 `LabelAccessGuard` 로 본인 배정을 확인(저장 시 재확인해 타인 거부)하고, 저장은 **"작업본 영속(버전 스냅샷 미생성)"** + 객체별 속성값 저장입니다. "임시저장은 버전이 아니다"라는 2계층 분리가 시퀀스에 박혀 있습니다.

**(13) VLM 시계열 메타 검토(SD-022)**
외부 VLM이 결과를 보내면(멱등키) `VlmResultService` 가 중복 확인→메타 적재→**검수큐 자동 진입**. 이후 검수자가 `MetaController/MetaService` 로 메타 수정·승인·반려하고, 승인 메타만 노출되도록 검수 상태를 전이합니다. **수신(자동)과 검토(사람)** 가 한 시퀀스에 함께 그려져 있습니다.

**(14) 검수 승인·반려(SD-023)**
작업자 제출 → `ReviewStateMachine.verify` 로 전이 검증 → 검수 대기 전이. 검수자 승인 시 **작업 완료 전이 + 스냅샷 생성 + 완료 통지**, 반려 시 **사유 기록 + 재작업 전이**. 상태 전이를 상태 머신으로 검증하는 것이 안전성의 핵심입니다.

### 2.3 §3 설계 클래스도 — "정적 구조와 의존 방향"

§3은 18개 유스케이스마다 Mermaid `classDiagram` 을 제공합니다(KLID-AT-DCD-001~023). 각 클래스 박스에는 **주요 속성(- 접두)과 오퍼레이션(+ 접두)** 이 축약 표기되고, 클래스 간 화살표로 의존을 나타냅니다.

화살표 기호의 의미(UML classDiagram 관례, 이 문서에서 사용):
- `A --> B` : A가 B를 **참조/의존**한다(보통 필드로 보유해 호출).
- `A ..> B : 라벨` : A가 B에 대해 **약한 의존(점선)**, 라벨로 관계 성격을 명시. 예: `MarkingService ..> MarkingCompletedEvent : 발행`, `MarkingBatchBridge ..> MarkingCompletedEvent : 수신`, `ReviewService ..> ControlNotifyService : 완료 통지(이벤트)`, `Sam2TrackService ..> SystemConfigService : 정밀도 조회`, `LsDataLbl --> LsLabel : 마스터 참조`.
- `<<interface>>` : 인터페이스 스테레오타입. 외부 연동 계약(ExternalAugmentClient, KpstDeidentifyClient)에 부여되어 **구현 교체 가능성**을 표현합니다.

클래스도가 시퀀스도와 **상호 보완**하는 지점을 이해하는 것이 중요합니다. 시퀀스도는 "시간 순 메시지"를, 클래스도는 "누가 누구를 필드로 갖는가(구조)"를 보여줍니다. 예를 들어 DCD-009(통지)에서:

```
ControlNotifyEventListener --> ControlNotifyService
ControlNotifyEventListener --> ControlNotifyDebouncer
ControlNotifyDebouncer --> ControlNotifyService
ControlNotifyService --> ControlNotifyClient
```

이 구조는 "리스너가 완료는 서비스로 직접, 수정은 디바운서로 우회시키고, 디바운서도 결국 서비스를 거쳐, 서비스가 클라이언트로 발행"하는 계층을 드러냅니다. 시퀀스도의 `alt` 분기가 왜 그렇게 흐르는지 구조적으로 설명해 줍니다.

또한 클래스도의 오퍼레이션 시그니처는 §4보다 **구체적인 타입**을 담습니다. 예: `AugmentController.request(command, actor) AugmentRequestResult`, `LsDataAug.createRequested() LsDataAug`(정적 팩토리), `LsLabelVersion.activate()/deactivate()`, `ReviewStateMachine.verify(from, to)`. 특히 엔티티 클래스가 **정적 팩토리 메서드(createXxx)** 와 **의미 있는 상태 변경 메서드**(markDeidentified, applyReviewStatus, resolve, transitionTo)를 갖고, `set` 계열이 없다는 점은 **"빈약한 도메인 모델을 피하고 로직을 엔티티에 캡슐화"** 하는 DDD 지향(프로젝트 ddd.md 규칙)과 정합합니다.

그룹별로 특기할 설계 포인트를 설명합니다.

**4.1 공통·기반**
- `LabelAccessGuard`(DC-003): **상태 없는 접근 검증 컴포넌트**. `requireAssignedFrame`(본인 배정 아니면 차단 = 수평 권한 상승 방어), `requireAccessible`(검수자 전체·작업자 본인 배정). 보안 규칙(IDOR/Broken Access Control 방어)이 클래스로 결정화되어 있습니다.
- `SystemConfigService`(DC-004): 설정을 **캐시 경유로 조회**(getInt/getDouble/getString), update 시 허용 키·범위 검증 후 **캐시 무효화**. 폴리곤 단순화 정밀도가 여기서 나옵니다.
- `AiServerClient`(DC-005): 속성에 `circuitBreaker`·`retry` 를 명시 → Resilience4j 정책이 클래스 속성으로 표현됨. predictYolo/segment/track/verifyObjects 4종 추론을 비동기 요청.

**4.2 영상·적재·해상도**
- `LsDataRaw`(DC-012): **작업 단위 ID = rawSn**. 속성에 `evntTypeCd`(마킹 이벤트명 자동 소싱 원천), `deIdntfYn`(비식별 상태), `parentRawSn`(증강 원본 참조), `dataSttsCd`(배치 상태) 등 핵심 필드가 총집합. 오퍼레이션 `createFromIngest`/`createFromAugment`/`needsDeidentify`/`markDeidentified`/`markMarkingReady` 는 영상 생애주기를 담습니다.
- 해상도 변경 3인방: `VideoResolutionService`(오케스트레이션, 업스케일 거부), `Java2DImageResizer`(상태 없는 다운스케일 변환), `VideoResolutionPersister`(결과를 **독립 트랜잭션**으로 기록). 변환 로직·기록을 분리한 이유는 "무거운 이미지 변환"과 "짧은 DB 기록"의 트랜잭션 경계를 분리하기 위함입니다.
- `LsResolutionExport`(DC-017): 결과를 **1행으로 추적**(원본·해상도 유일). 영상·라벨을 만들지 않는 "이미지셋 내보내기"의 흔적입니다.

**4.3 배치 파이프라인** — 이 그룹이 D1에서 가장 정교한 구조를 보입니다.
- `BatchOrchestrator`(DC-030): 파이프라인·상태전이서비스·재처리큐를 갖고 후속 배치 단계를 순차 실행.
- `BatchPipeline`(DC-031)/`BatchStep`(DC-032, 인터페이스)/`BatchContext`(DC-033): **선언적 파이프라인** 삼요소. `BatchStep` 은 `stage()`·`execute(ctx)`·`isEnabled(ctx)` 계약을 정의해 단계를 플러그인처럼 구성하게 합니다. `BatchContext` 는 rawSn·raw·markings·marks·hints 를 단계 간 공유합니다(탐지→분할 hints 전달).
- 개별 단계 클래스들: `DeidentifyStep`(034), `VlmTimeseriesStep`(035), `FfmpegFrameExtractor`(036, 마킹 위치 기준 원본·비식별 프레임 추출), `YoloAutolabelStep`(037, **원본 프레임에만** 탐지→힌트 반환), `Sam2SegmentStep`(038, 힌트로 분할), `TrackInterpolationStep`(039, 키프레임 사이 보간). 각 단계가 `stage/execute/run` 형태를 공유해 **동일 계약 하의 교체·재배치**가 가능합니다.
- `BatchTransitionService`(040): 작업/배치 상태 전이(processing/markingReady/failed)와 비식별 실패 이력 기록을 전담.
- `AsyncDeidentifyRunner`(041)/`IngestDeidentifyBridge`(042): 적재 이벤트를 받아 **선두 비식별을 비동기로** 트리거하는 브리지-러너 쌍.

### 2.5 "항목 설명" — 표 컬럼의 정의

원문 말미의 "항목 설명"은 §1~§4 각 표의 **컬럼이 무엇을 뜻하는지**를 정의하는 메타 규약입니다(설계 클래스 ID/명/관련 UC ID, 시퀀스도 ID/명/주요액터/주요클래스, 속성의 가시성·타입·기본값·설명 등). 표를 어떻게 읽어야 하는지의 범례이므로, 표 해석에 이견이 생길 때 근거로 삼습니다.

### 2.6 부록 — 식별자 정렬과 빈 셀 사유

두 가지를 규정합니다.
1. **DCD↔UC 정렬**: 설계 클래스도는 R2 활성 18건과 1:1(KLID-AT-DCD-001~003, 004~011, 013, 016, 018~019, 021~023). **결번(UC-012·014·015·017·020, 024+)은 D1에서도 결번** 유지. → 번호 건너뜀은 누락이 아니라 R2와의 의도적 정합입니다.
2. **빈 셀(`-`) 사유**: 속성표의 `-` 는 (a) 상태 없는 컴포넌트(접근 가드·이미지 변환기·재처리 진입점)나 (b) 인터페이스 계약(외부 연동 클라이언트)이라 인스턴스 속성이 없음을 뜻하고, 일부 도메인 이벤트 클래스는 데이터 전달 목적 불변 객체라 오퍼레이션을 기술하지 않습니다. → 빈 셀은 "미작성"이 아니라 "본질적으로 없음"임을 문서가 스스로 해명합니다.

## 3. 핵심 용어

이 문서 맥락에서의 정의입니다.

- **CBD (Component Based Development)**: 컴포넌트 기반 개발 방법론. 산출물을 R(요구)·D(설계) 계열로 표준화하며, D1은 그중 클래스 설계 산출물입니다.
- **유스케이스(Use Case, UC)**: 사용자/외부 시스템이 시스템으로 달성하려는 목표 단위. D1의 모든 다이어그램은 유스케이스를 "실현 단위"로 삼습니다.
- **시퀀스도(Sequence Diagram)**: 객체 간 메시지를 **시간 순서**로 나타낸 동적 다이어그램. 여기서는 Mermaid `sequenceDiagram` 으로 작성.
- **설계 클래스도(Design Class Diagram, DCD)**: 클래스의 속성·오퍼레이션과 **의존 관계(정적 구조)** 를 나타낸 다이어그램. Mermaid `classDiagram`.
- **설계 클래스(Design Class, DC)**: 구현 예정 클래스의 설계 단위. Controller/Service/Client/Entity/Guard/Job/Step/Event 등 다양한 성격을 포함.
- **레이어(Layer)**: Controller → Service → Repository/Entity 로 이어지는 계층 구조. 프로젝트 규칙상 Controller는 DTO만, Service는 비즈니스 로직·트랜잭션, Repository/Entity는 영속을 담당.
- **Entity(엔티티)**: DB 테이블에 대응하는 영속 객체. 이 문서에서 `Ls*` 로 시작하는 클래스(LsDataRaw, LsDataLbl, LsLabelVersion 등)가 엔티티이며, D8/D9의 테이블과 대응됩니다.
- **Aggregate / Aggregate Root(집합체/집합체 루트)**: DDD에서 하나의 일관성 경계로 묶이는 엔티티 그룹과 그 진입점. 원문이 "Aggregate"라는 단어를 직접 쓰지는 않으나, 엔티티가 **정적 팩토리(createXxx)와 의미 있는 상태변경 메서드**를 갖고 `set` 을 배제한 설계는 Aggregate Root 지향과 일치합니다(프로젝트 ddd.md).
- **VO (Value Object, 값 객체)**: 식별자 없이 값으로 동등성이 결정되는 불변 객체. 원문 클래스 표에 VO가 명시적으로 분리되어 있지는 않으며(대부분 엔티티/서비스/컴포넌트), pointCn·marksCn 같은 직렬화 문자열 속성이 좌표·시점 값을 담습니다. "명시적 VO 클래스"는 원문에 정의되지 않음.
- **정적 팩토리 메서드(Static Factory)**: 생성자 대신 `LsDataAug.createRequested(...)` 처럼 의미 있는 이름의 정적 메서드로 인스턴스를 만드는 패턴. 엔티티 생성 규칙을 캡슐화합니다.
- **QueryDSL**: 타입 안전한 동적 쿼리 라이브러리(프로젝트 기술스택). 원문 D1 표에는 QueryDSL 클래스가 직접 등장하지 않으나(개념적 "저장소"로 추상화), 복잡 검색은 QueryDSL로 구현될 대상입니다.
- **접근 가드(Access Guard)**: 리소스 접근 권한(본인 배정/검수 권한)을 검증하는 상태 없는 컴포넌트. `LabelAccessGuard`.
- **상태 머신(State Machine)**: 허용된 상태 전이만 통과시키는 검증기. `ReviewStateMachine`.
- **선언적 파이프라인(Declarative Pipeline)**: 배치 단계를 `BatchStep` 인터페이스 구현들의 순서 목록으로 구성해, 순서·on/off를 한 곳에서 재배치할 수 있게 한 구조(BatchPipeline/BatchStep/BatchContext).
- **멱등키(Idempotency Key)**: 같은 요청이 중복 도착해도 한 번만 처리되도록 하는 키. 증강·VLM·통지에서 사용(idempotencyKey, ledger 멱등 원장, 요청ID 멱등).
- **디바운스(Debounce)**: 짧은 시간 내 다수 변경을 모아 1회로 집계하는 기법. `ControlNotifyDebouncer` 가 영상 1건 1회 통지에 사용.
- **낙관적 잠금(Optimistic Lock)**: `version` 필드로 동시 수정 충돌을 감지하는 동시성 제어. LsDataIssue·LsRawDataStatus 에 적용.
- **서킷 브레이커(Circuit Breaker)/재시도(Retry)**: 외부 호출 장애 차단·재시도 정책(Resilience4j). AiServerClient·VlmClient·ControlNotifyClient 의 속성으로 명시.
- **비식별(Deidentification)**: 개인정보(얼굴·번호판 등) 마스킹 처리. 외부 KPST 솔루션에 위탁하며 폴링으로 완료를 확인.
- **KPST**: 원문에서 비식별 연동 클래스 접두어(`Kpst*`)로 쓰이는 **외부 비식별 솔루션**의 명칭. 원문은 이를 "비식별솔루션[외부]" 액터로 표기.
- **VLM (Vision-Language Model)**: 영상의 시계열 메타(사건 서술 등)를 생성하는 외부 모델. 저작도구는 호출·수신·검토만 담당.
- **SAM2 / YOLO**: 각각 세그멘테이션(외곽 분할·추적)·객체 탐지 모델. ai-server에서 추론, Spring이 오케스트레이션.
- **오토라벨링(Auto-labeling)**: YOLO/SAM2/보간으로 라벨을 자동 생성하는 배치 단계. 원본 프레임에만 실행하고 비식별본과 좌표 공유.
- **증강(Augmentation)**: 원본 영상을 겨울/야간/강수 조건으로 변형해 **새 영상(RAW_SN)** 을 만드는 외부 위탁 작업. 해상도는 불변이라 라벨 좌표를 그대로 복사.
- **관제 통지(Control Notify)**: 검수 완료/수정 시 관제서버로 보내는 단방향 outbound 이벤트(TASK_COMPLETED/TASK_MODIFIED). 본문 미포함, 관제가 역조회.
- **REVIEWER / WORKER / PORTAL_USER**: 역할 코드. 검수자(관리·검수), 라벨링 작업자(수정·제출), 포털 회원. D1 액터로는 REVIEWER·WORKER가 등장.
- **가시성(Visibility)**: 속성/오퍼레이션의 접근 범위(public/private). §4 표 컬럼.

## 4. 예상 질문 Q&A (심사·인수인계 대비)

**Q1. D1은 왜 유스케이스마다 시퀀스도와 클래스도를 따로 그리나요? 하나로 합치면 안 되나요?**
A. 둘은 서로 다른 관점을 담기 때문입니다. 시퀀스도는 "시간 순 메시지 흐름(동적)", 클래스도는 "누가 누구를 필드로 갖는가(정적 구조)"를 보여줍니다. 원문 작성 방법이 규정하듯 **시퀀스도에서 객체를 도출한 뒤 그 객체를 연관관계로 묶어 클래스도를 만드는** 순서라, 두 다이어그램은 같은 유스케이스의 두 단면입니다. 합치면 흐름과 구조 중 하나가 흐려집니다.

**Q2. 같은 클래스 ID가 여러 유스케이스 목록에 나오는데 중복 아닌가요?**
A. 의도된 재사용입니다. §1 서두가 "공통 클래스는 동일 설계 클래스 ID로 복수 목록에 교차 등장"한다고 명시합니다. 예컨대 `LsDataRaw`·`LabelAccessGuard`·`VersionService`·`SystemConfigService` 는 여러 흐름에서 공유됩니다. 하나의 컴포넌트를 여러 유스케이스가 호출하는 CBD 재사용 원칙의 표현입니다.

**Q3. `LsDataRaw.dataSttsCd` 와 `LsRawDataStatus.dataSttsCd` 는 이름이 비슷한데 왜 둘 다 있나요?**
A. **책임이 다릅니다.** `LsDataRaw.dataSttsCd`(DC-012)는 **배치 단계 상태**(대기→마킹 준비→완료)이고, `LsRawDataStatus.dataSttsCd`(DC-104)는 **작업/검수 워크플로우 상태**(배정·검수·완료)입니다. 배치 완료가 검수 완료를 앞질러 점프시키지 않도록 두 테이블로 분리했습니다(CLAUDE.md "두 테이블 책임 분리" 정책과 정합). 작업의 최종 `COMPLETED` 는 검수 승인(ReviewService.approve)에서만 전이됩니다.

**Q4. 비식별 처리에서 왜 `KpstDeidentService` 와 `KpstDeidentTxService` 를 나눴나요?**
A. 트랜잭션 경계 분리입니다. Service는 외부 업로드·폴링 등 **느리고 실패 가능한 I/O 오케스트레이션**을, TxService는 완료/실패/타임아웃의 **원자적 DB 상태 전이(독립 트랜잭션)**를 담당합니다. 외부 호출을 긴 트랜잭션 안에 두면 커넥션을 오래 점유하고 실패 시 롤백 범위가 커지므로, 상태 전이만 짧은 독립 트랜잭션으로 떼어낸 것입니다. `PollJob` 은 이를 주기 폴링으로 구동하며 건별 격리·동시 실행 금지를 명시합니다.

**Q5. 증강 라벨 매핑에 `coordRecalcYn` 속성이 있는 이유는?**
A. 외부 증강 3종(겨울/야간/강수)은 **해상도를 바꾸지 않아 좌표 재계산이 불필요**합니다(coordRecalcYn = 미재계산). 그래서 SD-002 시퀀스가 "좌표 그대로" 복사하고, 매핑 엔티티는 재계산 여부를 값으로 기록해 향후 해상도 변화가 있는 증강이 생기면 구분할 수 있게 확장 여지를 남겼습니다.

**Q6. 버전 스냅샷은 왜 라벨 저장 때가 아니라 검수 승인 때만 만드나요?**
A. 학습데이터 "버전"은 **검수 완료되어 확정된 단위**를 대상으로 하기 때문입니다(SFR-08 정책). 작업 중 임시저장(LabelService.bulkUpsert)은 `LsDataLbl` 에 upsert만 하고 스냅샷을 만들지 않으며(2계층 분리), `VersionService.commitApproved` 가 검수 승인 시점에 전체 라벨 스냅샷을 페이로드 해시로 **멱등 생성**합니다(동일 페이로드는 동일 해시로 중복 식별). 신고 삭제 직전에는 예외적으로 `snapshotDeidentReport` 가 복원용 비활성 스냅샷을 남깁니다.

**Q7. `ReviewStateMachine` 이 따로 있는 이유는? Service에서 if문으로 처리하면 안 되나요?**
A. 상태 전이 규칙을 한 곳(allowedTransitions)에 모아 **불허 전이를 일관되게 차단**하기 위함입니다. 예컨대 배치 완료가 작업 상태를 COMPLETED로 점프시키려 하면 상태 머신이 거부합니다. Service에 흩어진 if문은 규칙이 늘수록 누락·모순이 생기므로, verify(from,to) 단일 관문으로 캡슐화한 것입니다.

**Q8. `LabelAccessGuard` 는 왜 별도 클래스인가요? Spring Security로 충분하지 않나요?**
A. Spring Security는 URL·역할 수준의 인가(수직 권한)를 처리하지만, **"이 프레임이 이 작업자에게 배정된 것인가"** 같은 **비즈니스 레벨의 수평 권한(IDOR 방어)** 은 데이터를 봐야 판단됩니다. `requireAssignedFrame`/`requireAccessible` 은 그 검증을 재사용 가능한 상태 없는 컴포넌트로 묶어, 라벨·버전·신고 등 여러 서비스가 동일 규칙을 공유하게 합니다(보안 규칙 security.md의 Broken Access Control 대응).

**Q9. 배치 단계를 `BatchStep` 인터페이스로 추상화한 이점은?**
A. **선언적 재배치·조건부 실행**입니다. 각 단계가 `stage/execute/isEnabled` 계약을 공유하므로, `BatchPipeline` 의 단계 목록만 바꾸면 순서를 재조정하거나(pre-marking=[DEIDENTIFY], post-marking=[MARKING,VLM,FRAME_EXTRACT,YOLO,SAM2,INTERPOLATE]) 특정 단계를 dev에서 토글할 수 있습니다(BatchContext.isStageEnabled). 단계 추가/삭제가 오케스트레이터 코드 수정 없이 가능해집니다.

**Q10. 관제 통지에서 왜 완료는 즉시, 수정은 디바운스하나요?**
A. 완료(TASK_COMPLETED)는 유일 이벤트라 즉시 발행이 안전합니다. 반면 수정(TASK_MODIFIED)은 한 영상에 라벨·메타가 짧은 시간에 여러 번 바뀔 수 있어, 매 변경마다 통지하면 관제서버로 과도한 트래픽이 갑니다. `ControlNotifyDebouncer` 가 영상 단위 창(windows)에 변경을 모아 만료 시 **1건 1회**로 발행합니다. 통지 실패는 fallbackService(미처리 큐)로 재시도하고, 본문은 보내지 않아(메타·요약만) 개인정보 유출을 원천 차단합니다.

**Q11. 외부 연동 클라이언트를 왜 `<<interface>>` 로 표기했나요?**
A. `ExternalAugmentClient`·`KpstDeidentifyClient` 는 외부 시스템 연동 **계약**입니다. 인터페이스로 두면 실제 구현(HTTP·mock 등)을 교체할 수 있고, 테스트에서 스텁으로 대체하기 쉽습니다. 속성표가 `-` 인 것도 "상태 없는 계약"이라는 성격을 반영합니다(부록의 빈 셀 사유).

**Q12. `MarkingCompletedEvent` 같은 이벤트 클래스는 왜 오퍼레이션이 없나요?**
A. 데이터 전달 목적의 **불변 도메인 이벤트**이기 때문입니다(부록 명시). rawSn·markingSn 만 실어 발행자(MarkingService)와 수신자(MarkingBatchBridge)를 느슨하게 결합합니다. 커밋 후(AFTER_COMMIT) 수신해 잔여 배치를 시작하므로, 마킹 트랜잭션이 롤백되면 배치가 시작되지 않는 안전성도 얻습니다.

**Q13. 해상도 변경은 왜 새 영상을 만들지 않나요?**
A. SFR-06-03에 따라 해상도 변경은 "증강이 아니라 이미지셋 다운스케일 제공"입니다. `VideoResolutionService` 가 업스케일을 거부하고 프레임만 다운스케일하며, `LsResolutionExport` **1행**으로만 추적합니다(영상·라벨 미생성, 좌표 미제공). 반면 증강(UC-002)은 새 영상(RAW_SN)을 만들고 라벨을 복사합니다 — 둘은 성격이 다른 기능입니다.

**Q14. 자동 라벨링(YOLO/SAM2)은 원본과 비식별본 둘 다 실행하나요?**
A. §4의 `YoloAutolabelStep`(037)은 "**원본 프레임에** 객체 탐지를 실행"하고, `FfmpegFrameExtractor`(036)는 마킹 위치 기준으로 원본·비식별 프레임을 **둘 다 추출**합니다. 라벨 좌표는 동일 해상도라 비식별본과 공유합니다(CLAUDE.md "원본만 실행, 비식별본 결과 공유"). 즉 프레임은 2벌, 추론은 원본 1벌입니다.

**Q15. VLM 결과 수신(VlmResultService)과 시계열 배치 단계(VlmTimeseriesStep)는 어떻게 다르죠?**
A. 두 개는 VLM 연동의 서로 다른 방향입니다. `VlmTimeseriesStep`(035)은 배치 파이프라인에서 **마킹 결과로 시계열 분석을 호출(요청)**하고, `VlmResultService`(114)는 **외부 VLM이 콜백으로 보낸 결과를 멱등 적재하고 검수큐에 진입**시킵니다(수신). 요청은 동기 호출, 상세 결과는 콜백 수신이라는 비동기 이원 구조입니다.

**Q16. `LsLabel` 과 `LsDataLbl` 은 무엇이 다른가요?**
A. `LsLabel`(072)은 **라벨 마스터**(클래스 정의: 이름·색상·도형타입, 유일), `LsDataLbl`(073)은 **프레임에 실제로 찍힌 라벨 인스턴스**(좌표 pointCn, 트랙 trckId)입니다. `LsDataLbl --> LsLabel : 마스터 참조` 로 인스턴스가 마스터를 참조합니다. 마스터-인스턴스 분리로 라벨 종류(예: "차량") 정의와 프레임별 실제 박스를 독립적으로 관리합니다.

**Q17. 이 문서의 클래스 이름은 실제 코드와 일치하나요?**
A. 클래스명·오퍼레이션명은 실제 구현체(예: AsyncDeidentifyRunner, IngestDeidentifyBridge, BatchOrchestrator, ControlNotifyDebouncer 등)와 일관된 명명을 사용하며, 제·개정 이력이 밝히듯 LogiCraft 그래프에서 생성되어 D3(컴포넌트설계서)의 내부 클래스 ID와 동일 체계입니다. 다만 §4의 타입은 개념어("영상 저장소" 등)로 추상화되어 있어 실제 Java 타입(Repository 인터페이스명 등)은 D3/D9에서 구체화됩니다.

**Q18. 결번(UC-012·014·015·017·020)은 왜 생겼나요? 설계 누락인가요?**
A. 아닙니다. 부록이 명시하듯 R2(유스케이스명세서)에서 해당 번호가 결번이므로 D1도 동일하게 결번을 유지합니다. 번호를 재정렬하지 않고 **R2와 1:1 정렬을 우선**한 것이며, 산출물 간 ID 추적성을 위해 의도적으로 빈 번호를 둡니다.

**Q19. 낙관적 잠금(version)은 어디에 왜 걸려 있나요?**
A. `LsDataIssue`(103)와 `LsRawDataStatus`(104)에 `version` 속성이 있습니다. 검수 이슈와 작업 상태는 여러 사용자·배치가 동시에 전이시킬 수 있어, 낙관적 잠금으로 **동시 수정 충돌(lost update)** 을 감지합니다(성능·보안 규칙의 Race Condition 대응).

**Q20. 이 설계가 프로젝트 아키텍처 원칙(Controller→Service→Repository)을 지키나요?**
A. 지킵니다. §3 클래스도의 화살표가 대부분 `Controller --> Service --> (Client/Repository/Entity)` 단방향이고, Controller는 요청을 Service로 위임할 뿐 로직을 갖지 않으며, 엔티티는 비즈니스 메서드를 캡슐화합니다. 외부 호출은 전용 Client(AiServerClient·VlmClient·ExternalAugmentClient·KpstDeidentifyClient·ControlNotifyClient)로 분리되어 있어 CLAUDE.md의 공통 인프라·레이어 원칙과 정합합니다.

## 5. 다른 산출물과의 연계

D1은 CBD 산출물 그래프의 허브이므로, `docs/0705/` 의 다른 문서들과 명시적으로 맞물립니다.

### 5.1 R2 유스케이스명세서 (상류, 실현 대상)
- **연결 방식**: D1의 §1·§2·§3은 **R2의 유스케이스를 실현 단위**로 삼습니다(헤더 안내문). 모든 시퀀스도·클래스도의 메타표에 `관련 유스케이스 ID`(KLID-AT-UC-NNN)가 붙어 R2로 역추적됩니다.
- **정합 규칙**: R2 활성 18건 ↔ D1 DCD 18건 1:1, R2 결번 ↔ D1 결번(부록). R2가 "무엇을/왜"라면 D1은 "어떤 클래스가/어떻게"를 답합니다.

### 5.2 D2 사용자인터페이스설계서 (병렬, 화면 흐름)
- **연결 방식**: D2는 화면(SCR)과 사용자 조작을 규정하고, D1은 그 조작이 백엔드에서 어떤 클래스 협력을 일으키는지 규정합니다. 예: D2의 마킹 화면(비식별 영상 스트리밍·단축키) 조작 → D1의 SD-019(MarkingController→MarkingService→…). D2의 라벨링 캔버스(SAM2 클릭/박스) → D1의 SD-004/005.
- **정합 포인트**: D2의 액터(REVIEWER/WORKER)와 D1 시퀀스 액터가 일치해야 하며, 화면에서 노출되는 상태(검수 상태·비식별 상태)는 D1 엔티티 속성(dataSttsCd·deIdntfYn)에서 옵니다.

### 5.3 D3 컴포넌트설계서 (하류, 동일 클래스 ID 공유)
- **연결 방식**: D1 헤더 안내문이 명시하듯 **설계 클래스 ID(KLID-AT-DC-NNN)는 D3의 내부 클래스 ID와 동일 체계**입니다. 즉 D1의 클래스는 D3에서 어떤 컴포넌트(모듈)에 속하는지, 컴포넌트 인터페이스는 무엇인지로 이어집니다.
- **정합 포인트**: D1이 클래스 단위의 속성·오퍼레이션을 정의하면, D3는 이 클래스들을 컴포넌트로 묶고 컴포넌트 간 제공/요구 인터페이스를 규정합니다. D1의 개념적 타입("라벨 저장소")은 D3에서 구체 인터페이스명으로 구체화됩니다.

### 5.4 D5 아키텍처설계서 (상위 맥락)
- **연결 방식**: D5는 시스템 경계·계층·배치(Spring Boot / ai-server / 외부 시스템)와 비기능 요구를 다룹니다. D1의 외부 연동 클라이언트(AiServerClient·VlmClient·KpstDeidentifyClient·ExternalAugmentClient·ControlNotifyClient)는 D5의 시스템 경계·통합 지점을 클래스 수준으로 구현한 것입니다.
- **정합 포인트**: D5의 "Spring이 오케스트레이션, ai-server는 stateless 추론" 원칙이 D1에서 BatchOrchestrator·BatchStep 계열과 AiServerClient 분리로 나타납니다. Resilience4j(서킷/재시도)는 D1 클라이언트 속성(circuitBreaker·retry)으로 결정화됩니다.

### 5.5 D8 엔티티관계모형설계서 (하류, 엔티티 대응)
- **연결 방식**: D1 헤더 안내문이 "설계 클래스 ID는 **D8의 관련 클래스 ID와 동일 체계**"라고 명시합니다. D1의 `Ls*` 엔티티(LsDataRaw·LsDataLbl·LsLabelVersion·LsDeidentReport·LsDataAug 등)는 D8의 엔티티/관계로 대응됩니다.
- **정합 포인트**: D1이 엔티티의 주요 속성·상태변경 메서드를 정의하면, D8은 그 엔티티들의 관계(1:N, 참조)를 그립니다. 예: D1의 `parentRawSn`(증강 원본 참조), `LsDataAugLblMap`(원본↔증강 매핑)이 D8에서 관계선으로 표현됩니다. 단 관제 공유 MNG_* 테이블은 D8 산출물 비대상(CLAUDE.md, 공유 READ 스키마).

### 5.6 D9 데이터베이스설계서 (하류, 물리 스키마)
- **연결 방식**: D1 엔티티 속성이 D9의 테이블 컬럼으로 물리화됩니다. 예: `LsDataRaw.rawSn/evntTypeCd/deIdntfYn/rawFilePathNm` → LS_DATA_RAW 테이블의 RAW_SN/EVNT_TYPE_CD/DE_IDNTF_YN/RAW_FILE_PATH_NM. `LsLabelVersion.versionHash/labelPayload/saveReasonCd/activeYn` → LS_LABEL_VERSION 컬럼.
- **정합 포인트**: D1의 개념적 타입(식별자·문자열·정수·플래그)은 D9에서 구체 컬럼 타입·제약(PK·UK·인덱스)으로 확정됩니다. `LsResolutionExport`의 "원본·해상도 유일"은 D9의 UK(원본 RAW_SN+해상도)로, 낙관적 잠금 `version`은 version 컬럼으로 구현됩니다.

### 5.7 D10 통합시험시나리오 (검증, 흐름 단위)
- **연결 방식**: D10은 유스케이스 단위의 end-to-end 시나리오를 검증합니다. D1의 시퀀스도(SD-NNN)가 그대로 통합 시험 시나리오의 기대 흐름이 됩니다. 예: SD-018(적재→선두 비식별)·SD-019(마킹→잔여 배치)·SD-023(검수 승인→스냅샷→통지)의 다중 클래스 협력이 통합 시험의 검증 경로입니다.
- **정합 포인트**: D1이 "정상 흐름 + alt 분기(완료/수정, 완료/진행중/타임아웃 등)"를 명시하므로, D10은 그 분기들을 시험 케이스로 전개합니다.

### 5.8 D11 단위시험절차서 (검증, 클래스/메서드 단위)
- **연결 방식**: D11은 개별 클래스·메서드 단위 시험을 규정합니다. D1의 §4 오퍼레이션(예: `VideoResolutionService.changeResolution` 의 업스케일 거부, `ReviewStateMachine.verify` 의 불허 전이 차단, `VersionService.commitApproved` 의 멱등 스냅샷)이 그대로 단위 시험의 검증 대상(입력·기대 결과)이 됩니다.
- **정합 포인트**: D1의 "설명" 컬럼이 서술한 규칙(본인 배정 검증, 멱등 중복 무처리, 원본 보존 등)이 D11의 테스트 단언으로 번역됩니다. 프로젝트 규칙상 테스트 메서드명은 한글 서술형이므로, D1의 한글 설명이 시험명으로 자연스럽게 이어집니다.
