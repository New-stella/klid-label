## 1. 이 문서는 무엇인가

### 1.1 한 줄 요약
D9 데이터베이스 설계서는 **학습데이터 저작도구가 소유하는 39개 물리 테이블(LS_\* 전용)** 을
실제 데이터베이스 공간(PostgreSQL `klid_at` 스키마)에 매핑하고, 각 테이블의 컬럼·타입·제약·인덱스·
저장 용량 산정을 기술하는 **물리 데이터베이스 설계 산출물**입니다.

### 1.2 문서의 목적 (원문 "작성 목적")
> "최종적으로 설계된 테이블과 인덱스를 데이터베이스 공간에 매핑시키고 저장공간 등의 물리 모델을 기술한다."

즉 D9는 두 가지를 확정합니다.
1. **어떤 테이블·인덱스를 어느 데이터베이스/테이블스페이스에 놓을 것인가** (물리 배치)
2. **각 테이블이 차지할 저장 공간이 얼마인가** (용량 산정 — 최대건수 × 평균 row bytes)

### 1.3 작성 방법 (원문)
> "부서에서 운영하는 데이터베이스 목록을 작성하고, 데이터베이스의 물리적 상세내용을 작성한다."

이에 따라 문서는 다음 3개 실체 섹션으로 구성됩니다.
- **§1 데이터베이스 목록** — 운영 DB를 나열 (저작도구 DB + 공유 스키마)
- **§2 데이터베이스 정의** — 물리 배치(테이블스페이스, 버퍼풀, 용량) 및 39개 테이블 매핑 표
- **§3 테이블 명세** — 39개 테이블을 하나씩 반복 기술 (컬럼/PK/FK/IDX/기본값/제약)
- (부록) **항목 설명**, **작성 시 참고사항**(ID 체계)

### 1.4 물리 DB 설계의 위치 — CBD 산출물 흐름에서
CBD(Component Based Development) 표준 문서 체계에서 데이터 모델은 통상 **논리 → 물리** 순으로 정련됩니다.
- **D8 엔티티 관계 모형 설계서(ERD)** = **논리 모델**. 엔티티(개념/업무적 실체)와 관계를 정의합니다.
  (ID 체계: `KLID-AT-EN-NNN`, `KLID-AT-ERD-NNN`)
- **D9 데이터베이스 설계서** = **물리 모델**. 논리 엔티티를 실제 DBMS 테이블로 구현합니다.
  (ID 체계: `KLID-AT-TB-NNN`, `KLID-AT-TS-NNN`, `KLID-AT-ID-NNN`)

원문 §참고사항: "각 테이블은 D8 엔티티(`KLID-AT-EN-001~039`)와 **번호 정렬 1:1 매핑**된다."
즉 `KLID-AT-TB-001`(LS_DATA_RAW) ↔ `KLID-AT-EN-001`, `KLID-AT-TB-039`(LS_META) ↔ `KLID-AT-EN-039`
처럼 테이블 번호와 엔티티 번호가 정확히 짝을 이룹니다. (각 테이블 명세 표의 "관련 엔티티 ID" 행이 이 매핑을 명시)

### 1.5 D8(논리 ERD) vs D9(물리 DB)의 차이
| 관점 | D8 ERD (논리) | D9 DB설계 (물리) |
|------|--------------|-----------------|
| 다루는 대상 | 엔티티·속성·관계(개념) | 테이블·컬럼·타입·인덱스·저장공간(구현) |
| 데이터 타입 | 추상적(문자/숫자/일시 수준) | 구체적(`VARCHAR(128)`, `BIGINT`, `NUMERIC(6,5)`, `TIMESTAMP`, `TEXT`, `BOOLEAN`) |
| 키 표현 | 식별/비식별 관계 | PK/FK/UNIQUE/CHECK 제약 + 인덱스 |
| 관심사 | 업무 규칙의 정합성 | 성능(인덱스), 용량(TS 산정), DBMS 물리 개념 |
| 본 프로젝트 특이점 | — | 모든 FK는 **"논리 FK"**(물리 제약 미부여, 애플리케이션 레벨 무결성) |

### 1.6 이 문서가 다루는 범위와 다루지 않는 범위
- **다룸(물리 설계 대상)**: 저작도구가 직접 소유·구성하는 **LS_\* 39개 테이블**
  (`KLID-AT-TB-001` ~ `KLID-AT-TB-039`).
- **다루지 않음(물리 설계 비대상)**:
  - **MNG_\* 관제 공유 클립/계정 스키마** — 관제서버 소유, 저작도구는 읽기 위주 참조(검증)만.
  - **QRTZ_\* Quartz 스케줄러 JobStore** — 인프라 제공, 단일 인스턴스 JobStore.
  이 두 공유 스키마는 §1 데이터베이스 목록에 "공유(READ)"로만 표기하고, §3 테이블 명세에는
  별도 테이블 블록을 작성하지 않습니다. (원문 §3 서두 "공유 스키마 안내")

## 2. 섹션별 상세 해설

### 2.1 §1 데이터베이스 목록

| 데이터베이스 ID | 명칭 | 주관부서 | 비고 |
|-----------|------|--------|------|
| `KLID-AT-DB-001` | 학습데이터 저작도구 DB (`klid_system` / `klid_at` 스키마) | 저작도구 | PostgreSQL, UTF-8. LS_\* 39개 테이블 소유 |
| - | MNG_\* 관제 공유 클립/계정 스키마 | 관제서버 | 공유(READ) — 물리 설계 비대상 |
| - | QRTZ_\* Quartz 스케줄러 JobStore | 인프라 | 공유(READ) — 물리 설계 비대상, 단일 인스턴스 JobStore |

핵심:
- 물리 DB 식별자는 **`KLID-AT-DB-001` 하나**뿐입니다. 저작도구가 실제 소유·물리 설계하는 대상은
  이 하나의 데이터베이스(정확히는 `klid_system` DB 내 `klid_at` 스키마)입니다.
- 나머지 2개(MNG_\*, QRTZ_\*)는 DB ID를 부여하지 않고("-") **공유(READ)** 로만 기록합니다.
  저작도구는 이들을 소유하지 않고 검증(validate)·연동만 하기 때문입니다.

### 2.2 §2 데이터베이스 정의 — DB2 물리 개념의 PostgreSQL 적응 표기

D9 양식은 원래 **DB2 물리 모델**을 전제로 한 CBD 표준 양식입니다(Storage Group, Bufferpool,
인덱스 BP, Tablespace 개념). 본 프로젝트는 PostgreSQL이므로, 원문은 **작성 품질 규칙(CBD 적합성)** 에
따라 DB2 개념을 PostgreSQL 등가물로 **적응 표기**하고 그 적응 사실을 명시합니다(공란 금지).

| DB2 물리 개념 | PostgreSQL 등가물 (적응 표기) | 설명 |
|--------------|------------------------------|------|
| Storage Group | `pg_default` | PostgreSQL 기본 테이블스페이스 |
| Bufferpool | `shared_buffers` | 인스턴스 공유 버퍼 |
| 인덱스 BP | `shared_buffers` | PostgreSQL은 인덱스도 동일 공유 버퍼 사용 |
| TS(테이블스페이스) | `pg_default` (단일 논리 TS) | 객체별 버퍼풀을 분리 지정하지 않음 |

DB 정의 헤더 표:
- 데이터베이스 ID: `KLID-AT-DB-001` / 데이터베이스명: `klid_at (klid_system)`
- Storage Group: `pg_default` / Bufferpool: `shared_buffers` / 인덱스 BP: `shared_buffers`

**핵심 개념(원문 각주)**: PostgreSQL은 DB2와 달리 객체별로 버퍼풀을 나누지 않고 인스턴스 공통
`shared_buffers`를 사용합니다. 그래서 테이블용/인덱스용 버퍼풀이 모두 동일하게 표기됩니다.

#### 2.2.1 TS 용량 산정 (원문 "TS 용량 산정" 각주)
- 공식: **TS 용량 = Σ(테이블별 최대건수 × 평균 row bytes)**
- LS_\* 39개 합산 추정 ≈ **1.6GB** (인덱스 포함 시 ≈ 1.9GB)
- 최대 용량 기여 상위 테이블:
  - `LS_DATA_LBL`(라벨) — 최대 ~1,000,000행, ≈ 700MB (본 시스템 최대 적재 테이블)
  - `LS_DATA_LBL_AI_INFO` — ~1,000,000행, ≈ 250MB
  - `LS_DATA_SRC`(프레임)
  - `LS_LABEL_VERSION`(스냅샷 페이로드)
- 인덱스 용량은 각 테이블 PK + 보조 인덱스 합산으로 산정.

#### 2.2.2 합치 확인 (CBD 적합성 규칙)
원문은 세 곳의 테이블 개수를 **동일하게 맞춘 사실**을 명시합니다:
> 대상 LS_\* **39개** = §2 DB정의 테이블 매핑 **39개** = §3 테이블 명세 **39개**(`KLID-AT-TB-001~039`).

공유 MNG_\*/QRTZ_\*는 물리 설계 비대상이라 이 셈에서 제외됩니다.

#### 2.2.3 TS 매핑 표의 표기 규칙
§2의 큰 표는 39행(테이블마다 1행)으로, 각 행이
`TS ID | TS 용량 | 테이블 ID | 테이블 명 | 인덱스 ID | 인덱스 용량 | 비고` 를 담습니다.
- **TS ID**: 39개 테이블 모두 단일 논리 테이블스페이스 `KLID-AT-TS-001`(=`pg_default`)에 속합니다.
- **TS 용량**: 첫 행에만 총량 `≈ 1.6GB`를 적고, 이하 행은 `〃`(상동)으로 **같은 TS·같은 합산 용량**임을
  나타냅니다. (즉 `〃`는 개별 테이블 용량이 아니라 TS 전체 합산값)
- **인덱스 ID**: 테이블마다 `KLID-AT-ID-001` ~ `KLID-AT-ID-039`가 1:1 부여됩니다.
- **인덱스 용량**: 테이블별로 개별 추정 (예: LS_DATA_RAW ≈1.5MB, LS_DATA_LBL ≈60MB, LS_DEADLINE ≈0.01MB).

이 표의 "비고" 열은 각 테이블의 **주요 인덱스/UNIQUE 구성**을 요약합니다. 예:
- `KLID-AT-TB-001` LS_DATA_RAW → "PK + VMS_CLIP_ID UNIQUE + 상태/부모 인덱스"
- `KLID-AT-TB-007` LS_DATA_LBL_AI_INFO → "PK + DATA_LBL_SN·RAW·SRC·LBL_SRC_CD 인덱스 + (DATA_LBL_SN,AUTO_LBL_YN) 복합"
- `KLID-AT-TB-018` LS_DEIDENT_PROC_LOG → "PK + RAW 인덱스 + OTSD_JOB_ID UNIQUE + 처리상태/IX_LDPL_POLL_STTS"

### 2.3 §3 테이블 명세 — 공통 읽는 법

각 테이블 블록은 3개의 표로 구성됩니다.

1. **머리 표**: 테이블ID / 테이블명 / 데이터베이스명(`klid_at`) / TS명(`pg_default`) /
   관련 엔티티 ID(D8과 1:1) / **트리거 구성** / 테이블 설명.
   - **트리거 구성**은 39개 테이블 전부 **"없음"** 입니다. 감사·이력 적재는 DB 트리거가 아니라
     **애플리케이션 레벨**에서 처리한다는 설계 방침입니다(원문 반복 명시).
2. **용량 표**: 초기건수 / 증가량(일) / 보관주기 / 최대건수 / 용량 / 비고.
   - **보관주기**는 대부분 "영구"이며, 예외로 `LS_BATCH_PROC_LOG`만 **"365 — 운영 로그 1년"**.
3. **컬럼 표**: 컬럼명 / 컬럼ID / 타입 및 길이 / Not Null / PK / FK / IDX / 기본값 / 제약조건.

**공통 관례 (39개 테이블에서 반복되는 패턴)**:
- **PK**: 대부분 `BIGINT GENERATED BY DEFAULT AS IDENTITY`(PostgreSQL 자동증가 IDENTITY 컬럼).
  일부 마스터/매핑 테이블은 자연키를 PK로 사용 (예: `LS_SYSTEM_CONFIG.STNG_KEY`, `LS_META.META_KEY`,
  `LS_RAW_DATA_ENROLLMENT.RAW_DATA_ID`, `LS_WEBHOOK_IDEMPOTENCY.IDMP_KEY`, `LS_DEADLINE.DDLN_SEQ`).
- **FK 열의 "Y"**는 전부 **논리 FK**입니다. 제약조건 열에 "논리 FK(→테이블명)"으로 표기되며,
  물리적 FOREIGN KEY 제약을 걸지 않고 애플리케이션이 참조 무결성을 보장합니다.
- **감사 컬럼**: `REG_DT`(등록일시, 기본값 `CURRENT_TIMESTAMP`), `MDFCN_DT`(수정일시),
  `REG_ID`/`MDFR_ID`(등록/수정자) 등이 광범위하게 존재.
- **상태·유형 코드**: `VARCHAR(n)` + `CHECK` 제약 또는 코드 열거로 관리(매직 문자열이 아닌 명시적 코드값).

### 그룹 A. 원천 영상·프레임 데이터 (TB-001 ~ TB-005)

#### `KLID-AT-TB-001` LS_DATA_RAW — 원시 영상 (작업 단위 기준 테이블)
- 역할: 라벨링 대상 원시 영상 메타를 **영상 단위**로 보관. **작업 단위 = 영상 1건**의 진실원.
- 용량: 초기 0 / 일 30 증가 / 최대 20,000행(영상 5,000 + 증강분 ~15,000) / ≈12MB.
- 주요 컬럼:
  - `RAW_SN` (PK, IDENTITY) — 작업 단위 식별자. 프로젝트 전반에서 "작업 ID = RAW_SN".
  - `VMS_CLIP_ID` `VARCHAR(128)` NOT NULL, **UNIQUE** — 동일 VMS 클립 재수신 시 단일 행 갱신 기준.
  - `VMS_CCTV_ID` `VARCHAR(64)` — 관제 CCTV 식별자 (인덱스).
  - `PRVC_TYPE_CD` `VARCHAR(16)` NOT NULL, **CHECK(ANONY/PRVC/PSDO)** — 개인정보 유형 코드.
  - `PRVC_YN` `VARCHAR(1)` 기본값 `'N'` — 유형코드에서 파생한 개인정보 포함 여부.
  - `DE_IDENT_YN` `VARCHAR(1)` 기본값 `'N'` — 비식별 여부, 값 **Y/F/N**(F = 실패/신고).
  - `RAW_FILE_PATH_NM` `VARCHAR(500)` NOT NULL — 원본 경로(불변, 원본 보존).
  - `PARENT_RAW_SN` `BIGINT` — **자기참조 논리 FK**. 증강 영상이 원본을 가리킴.
  - `DATA_STTS_CD` `VARCHAR(32)` 기본값 `'PENDING'` — **배치 단계 상태**(PENDING→MARKING_READY→COMPLETED).
- 포인트: 이 테이블의 `DATA_STTS_CD`는 **배치 단계**를, TB-021의 상태는 **작업/검수 워크플로**를
  나타냅니다(책임 분리). 아래 TB-021 참조.

#### `KLID-AT-TB-002` LS_DATA_SRC — 키프레임
- 역할: 영상에서 추출한 키프레임. **원본 프레임 경로와 비식별 프레임 경로를 같은 행에서 짝**으로 관리.

### 2.4 데이터마트 적재용 View (V_COMPLETED_\*)에 관하여
- **원문(D9)에는 View 정의가 포함되어 있지 않습니다** ("원문에 명시되지 않음"). D9는 39개 물리 테이블의
  명세만 다룹니다.
- 프로젝트 맥락(CLAUDE.md)상 `klid_at` 스키마에는 데이터마트 적재용 4종 View가 존재합니다

  이들은 검수 완료(APPROVED) 영상만 노출하는 읽기 전용 뷰이나, **D9 문서 자체에는 기술되지 않았으므로**
  View의 컬럼 정의를 D9 근거로 답할 수는 없습니다. (View는 별도 산출물/마이그레이션에서 관리)

## 3. 핵심 용어

- **물리 모델(Physical Model)**: 논리 엔티티를 특정 DBMS(PostgreSQL)의 테이블·컬럼·타입·인덱스·저장공간으로
  구현한 설계. D9가 담당. (반대말: 논리 모델 = D8 ERD)
- **klid_at 스키마 / klid_system DB**: 저작도구 전용 테이블(LS_\*)이 사는 PostgreSQL 스키마.
  물리 DB는 `klid_system`, 그 안의 스키마가 `klid_at`. UTF-8, 표준 SQL DDL.
- **LS_\* 테이블**: 저작도구가 **직접 소유·구성**하는 39개 전용 테이블. Flyway로 자체 관리.
- **MNG_\* / QRTZ_\* (공유 READ)**: MNG_\*는 관제 공유 클립/계정, QRTZ_\*는 Quartz JobStore. 저작도구가
  소유하지 않고 읽기/검증(validate)만 하므로 **물리 설계 비대상**.
- **테이블스페이스(TS)**: 테이블·인덱스가 물리적으로 저장되는 논리 공간. 본 프로젝트는 단일 TS
  `KLID-AT-TS-001`(=`pg_default`).
- **pg_default / shared_buffers**: DB2의 Storage Group·Bufferpool을 PostgreSQL 등가물로 적응 표기한 것.
  `pg_default`=기본 테이블스페이스, `shared_buffers`=인스턴스 공유 버퍼(테이블·인덱스 공통).
- **인덱스(Index)**: 특정 컬럼 조회를 빠르게 하는 자료구조. D9는 PK 인덱스 외에 조회 술어에 맞춘 보조/복합
  인덱스를 부여(예: (DATA_LBL_SN, AUTO_LBL_YN) 복합, IX_LDPL_POLL_STTS).
- **제약조건(Constraint)**:
  - **PK(Primary Key)**: 행을 유일 식별. 대부분 `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
  - **FK(Foreign Key)**: 다른 테이블 참조. 본 프로젝트는 전부 **논리 FK**(물리 제약 미부여, 앱이 무결성 보장).
  - **UNIQUE**: 값(또는 조합)의 유일성 보장(예: VMS_CLIP_ID, (RAW_SN,FRM_NO), 멱등키).
  - **CHECK**: 값 범위 제한(예: PRVC_TYPE_CD CHECK(ANONY/PRVC/PSDO), LBL_TYPE_CD CHECK(BBOX/…)).
  - **NOT NULL**: 필수 입력. 컬럼 표의 "Not Null=Y".
  - **기본값(Default)**: 미입력 시 자동 값(예: 상태코드 'PENDING', REG_DT CURRENT_TIMESTAMP).
- **논리 FK**: 참조 관계는 존재하나 DB 레벨 FOREIGN KEY 제약을 걸지 않는 것. 대량 적재/삭제 유연성·성능·
  마이그레이션 편의를 위해 애플리케이션이 참조 무결성을 책임집니다.
- **IDENTITY 컬럼(GENERATED BY DEFAULT AS IDENTITY)**: PostgreSQL 표준 자동증가 PK. 명시값이 없으면
  시퀀스가 자동 채번, 명시하면 그 값 사용(대량 이관 시 유용).
- **soft delete(비활성 삭제)**: 물리 삭제 대신 `USE_YN='N'`로 비활성 처리(LS_LABEL, LS_LABEL_ATTR).
- **낙관적 잠금(Optimistic Lock)**: `VER` 정수 컬럼을 두고 갱신 시 버전 일치를 확인해 동시 수정 충돌을
  방어(LS_RAW_DATA_STATUS, LS_DATA_ISSUE). 검수 동시 승인 경합을 막습니다.
- **멱등키(Idempotency Key)**: 동일 요청의 중복 처리를 막는 키. `IDMP_KEY`(UNIQUE)로 재수신/재시도 시
  단일 처리 보장(LS_DATA_META, LS_DATA_AUG, LS_CONTROL_NOTIFY_FALLBACK, LS_WEBHOOK_IDEMPOTENCY).
- **사장큐(Dead Letter Queue)**: 최대 재시도 초과 시 격리하는 큐. `STTS_CD='DEAD_LETTER'`,
  `DEAD_LETTER_AT`/`DLQ_DT` 기록.
- **상태코드(dataSttsCd 계열)**: 상태 머신을 문자 코드로 표현. D9에서 두 개의 `DATA_STTS_CD`가 서로 다른
  머신을 담당 — TB-001은 **배치 단계**(PENDING→MARKING_READY→COMPLETED), TB-021은 **작업/검수 워크플로**.
- **폴링 모델(KPST)**: 외부 비식별 솔루션에 위탁 후 주기적으로 진행을 조회(POLLING)하다 완료 시
  다운로드(DOWNLOADED)하는 방식. `POLL_STTS_CD`, `POLL_ATTEMPT_CNT`로 추적.
- **Flyway 마이그레이션**: SQL 파일 기반 스키마 버전 관리 도구. LS_\* 전용 테이블은 저작도구가 자체 관리하며,
  MNG_\* 공유 테이블 변경 시에는 관제서버팀 선승인이 필요(프로젝트 정책).
- **ddl-auto=validate**: JPA/Hibernate가 기동 시 엔티티와 실제 스키마의 일치만 검증하고 스키마를
  변경하지 않는 모드. 저작도구는 공유 MNG_\* 등을 이 모드로 읽기만 하며, 불일치 시 기동 실패로 변경을 감지.
- **트리거 없음(애플리케이션 레벨 이력)**: 39개 테이블 전부 DB 트리거를 두지 않고, 감사/이력(_HSTRY,
  _EVENT_LOG 등)은 애플리케이션 코드가 적재.

## 4. 예상 질문 Q&A (15+)

**Q1. D9는 몇 개의 테이블을 물리 설계 대상으로 삼나요?**
A. 저작도구 소유 **LS_\* 39개**(`KLID-AT-TB-001~039`)입니다. 원문은 "대상 LS_\* 39개 = §2 DB정의 39개 =
§3 테이블 명세 39개"로 세 곳의 개수를 합치시켰습니다. MNG_\*·QRTZ_\* 공유 스키마는 비대상입니다.

**Q2. D8 ERD와 D9 DB설계서는 어떻게 다른가요?**
A. D8은 **논리 모델**(엔티티·관계), D9는 **물리 모델**(테이블·컬럼 타입·인덱스·저장공간)입니다. 각 D9 테이블은
D8 엔티티와 번호 정렬 **1:1 매핑**(`KLID-AT-TB-NNN` ↔ `KLID-AT-EN-NNN`)되며, 테이블 명세의 "관련 엔티티 ID"
행이 이를 명시합니다.

**Q3. 왜 Storage Group·Bufferpool 같은 DB2 용어가 나오나요? 이 프로젝트는 PostgreSQL 아닌가요?**
A. D9 양식이 DB2 기준 CBD 표준이기 때문입니다. 원문은 이를 PostgreSQL 등가물로 **적응 표기**합니다:
Storage Group→`pg_default`, Bufferpool→`shared_buffers`, 인덱스 BP→`shared_buffers`, TS→`pg_default`.
PostgreSQL은 객체별 버퍼풀을 분리하지 않고 공통 `shared_buffers`를 쓰므로 인덱스 BP도 동일 표기입니다.

**Q4. TS 용량 ≈1.6GB는 어떻게 산정했나요?**
A. `TS 용량 = Σ(테이블별 최대건수 × 평균 row bytes)` 공식으로 LS_\* 39개를 합산한 값입니다(인덱스 포함 시
≈1.9GB). §2 표의 `〃`는 개별 테이블 용량이 아니라 이 **TS 전체 합산값**을 의미하고, 첫 행에만 총량을 적습니다.

**Q5. 용량을 가장 많이 차지하는 테이블은?**
A. `LS_DATA_LBL`(라벨 좌표) — 최대 ~1,000,000행 ≈700MB로 **본 시스템 최대 적재 테이블**입니다. 다음으로
`LS_DATA_LBL_AI_INFO`(~1,000,000행, ≈250MB), `LS_DATA_SRC`(프레임), `LS_LABEL_VERSION`(스냅샷) 순입니다.

**Q6. 이 문서에서 FK는 실제 DB 제약인가요?**
A. 아니요. 컬럼 표의 FK 열 "Y"는 전부 **논리 FK**이며, 제약조건 열에 "논리 FK(→테이블명)"으로 표기됩니다.
물리 FOREIGN KEY 제약을 걸지 않고 애플리케이션이 참조 무결성을 보장합니다.

**Q7. PK 컬럼 타입은 왜 대부분 `BIGINT GENERATED BY DEFAULT AS IDENTITY`인가요?**
A. PostgreSQL 표준 자동증가 IDENTITY 방식으로, 대량 데이터를 다루므로 `BIGINT` 범위가 필요하고,
`BY DEFAULT`는 명시값 삽입(대량 이관·복원)도 허용하기 때문입니다. 단 마스터/자연키 테이블은 예외로
`STNG_KEY`·`META_KEY`·`IDMP_KEY`·`RAW_DATA_ID`·`DDLN_SEQ` 등을 PK로 씁니다.

**Q8. 좌표는 왜 TEXT이고 신뢰도는 왜 NUMERIC(6,5)인가요?**
A. `POINT_CN`(좌표 직렬화)·`LBL_PAYLOAD`(스냅샷)·페이로드는 길이가 가변이고 클 수 있어 `TEXT`를 씁니다.
`CONF_SCORE`는 0.00000~1.00000의 소수 5자리 신뢰도를 부동소수 오차 없이 정확히 저장하려고 `NUMERIC(6,5)`를
씁니다(전체 6자리 중 소수 5자리).

**Q9. 같은 이름 컬럼 `DATA_STTS_CD`가 여러 테이블에 있는데 같은 의미인가요?**
A. 아니요. **책임이 분리**됩니다. `LS_DATA_RAW.DATA_STTS_CD`=배치 단계(PENDING→MARKING_READY→COMPLETED),
`LS_RAW_DATA_STATUS.DATA_STTS_CD`=작업/검수 워크플로 상태입니다. 배치 완료가 작업 상태를 COMPLETED로
점프시키지 않도록 두 상태 머신을 분리했습니다.

**Q10. 인덱스 전략의 대표 예를 들어 설명해 주세요.**
A. 조회 술어에 맞춘 보조/복합 인덱스를 부여합니다.
- `LS_DATA_LBL_AI_INFO`의 **(DATA_LBL_SN, AUTO_LBL_YN) 복합 인덱스** — "특정 라벨의 자동라벨('Y')만"
  조회할 때 단일 인덱스 후필터를 제거.
- `LS_DEIDENT_PROC_LOG`의 **IX_LDPL_POLL_STTS(POLL_STTS_CD)** — 폴링 잡이 WAITING/POLLING 대상만
  스캔하도록.
- 대부분 FK 컬럼(RAW_SN, SRC_SN 등)과 상태 코드 컬럼에 인덱스를 부여.

**Q11. UNIQUE 제약이 걸린 곳과 그 목적은?**
A. 대표적으로 `LS_DATA_RAW.VMS_CLIP_ID`(재수신 시 단일 행 갱신), `LS_DATA_SRC (RAW_SN,FRM_NO)`(중복 프레임
차단), `LS_DATA_LBL_ATTR_VAL (LBL_SN,ATTR_ID)`, `LS_DATA_META (RAW_SN,META_KEY)`,
`LS_LABEL.LBL_NM`(전역 유일), `LS_TASK_ASSIGNMENT (RAW_DATA_ID,USER_NO,TASK_TYPE_CD)`(중복 배정 차단),
멱등키 UNIQUE(중복 통지/인계 차단) 등입니다.

**Q12. 상태 전이 코드값을 표별로 정리해 주세요(주요 것).**
A.
- LS_DATA_RAW.DATA_STTS_CD: PENDING → MARKING_READY → COMPLETED (배치 단계)
- LS_MARKING.STTS_CD: PENDING → VLM_REQUESTED → VLM_COMPLETED
- LS_DEIDENT_PROC_LOG.PROC_STTS_CD: REQUESTED / SUCCEEDED / FAILED ; POLL_STTS_CD: WAITING/POLLING/DOWNLOADED
- LS_DEIDENT_REPORT.REPORT_STTS_CD: OPEN / RESOLVED / DISMISSED
- LS_DATA_META_REVIEW.RVW_STTS_CD: PENDING / APPROVED / REJECTED / AUTO_GENERATED
- LS_DATA_ISSUE.ISSUE_STTS_CD: OPEN / ANSWERED / RESOLVED (ISSUE_TYPE_CD: REJECTION/INQUIRY)
- LS_TASK_EVENT_LOG.EVNT_TYPE_CD: ASSIGN / REASSIGN / SUBMIT / APPROVE / REJECT
- LS_DATA_AUG.AUG_PROC_STTS_CD & LS_DATA_AUG_RVW.RVW_STTS_CD: PENDING / ACCEPTED / REJECTED
- LS_BATCH_PROC_LOG.PROC_STTS_CD: STARTED / COMPLETED / FAILED
- LS_CONTROL_NOTIFY_FALLBACK.STTS_CD: PENDING / RETRYING / SUCCEEDED / DEAD_LETTER
- LS_WEBHOOK_IDEMPOTENCY.STTS_CD: ISSUED / PROCESSED / FAILED
- LS_AUTH_WORK_LOCK.LOCK_STTS_CD: LOCKED / RELEASED
- LS_NOTICE.PUB_STTS_CD: DRAFT / PUBLISHED

**Q13. MNG_\* 공유 테이블을 바꿔야 하면 어떻게 하나요?**
A. MNG_\*는 관제서버 소유 공유 스키마라 D9 물리 설계 비대상이며, 저작도구는 JPA `ddl-auto=validate`로
읽기/검증만 합니다. 변경이 필요하면 프로젝트 정책상 **Flyway 마이그레이션 전 관제서버팀 선승인**이
필수이고, 관제가 스키마를 바꾸면 validate 모드에서 저작도구 기동이 실패하여 변경을 감지합니다.

**Q14. 데이터마트 적재용 View(V_COMPLETED_\*)의 컬럼은 D9에서 확인할 수 있나요?**
A. **아니요, 원문(D9)에는 View 정의가 없습니다.** D9는 39개 물리 테이블 명세만 다룹니다. 4종 View는 프로젝트
전반(CLAUDE.md)에 존재하지만 그 컬럼 정의를 D9 근거로 답할 수 없으며, View는 별도 마이그레이션/산출물에서
관리됩니다.

**Q15. 보관주기가 "영구"가 아닌 테이블이 있나요?**
A. 39개 중 **`LS_BATCH_PROC_LOG` 하나만** "365 — 운영 로그 1년"입니다(운영 로그 성격). 나머지는 모두
"영구"이며, 특히 원본/학습데이터 관련(LS_DATA_RAW, LS_DATA_SRC, LS_DATA_LBL 등)은 원본 삭제 금지·학습데이터
원천으로 영구 보관합니다.

**Q16. 트리거는 어디에 걸려 있나요?**
A. **39개 테이블 전부 "트리거 없음"** 입니다. 감사·이력 적재(_HSTRY, _EVENT_LOG 등)는 DB 트리거가 아니라
애플리케이션 레벨에서 처리한다는 설계 방침입니다.

**Q17. 증강 데이터가 원본과 어떻게 연결되나요?**
A. 증강은 새 영상(RAW_SN)이며, `LS_DATA_RAW.PARENT_RAW_SN`(자기참조 논리 FK)으로 원본을 참조합니다.
증강 산출 상태는 `LS_DATA_AUG`, 검수는 `LS_DATA_AUG_RVW`, 원본↔증강 라벨 좌표 매핑은 `LS_DATA_AUG_LBL_MAP`
(SCALE_X/Y로 해상도 저하 시 좌표 재계산)에 저장됩니다.

**Q18. 낙관적 잠금은 어느 테이블에 있고 왜 필요한가요?**
A. `LS_RAW_DATA_STATUS.VER`, `LS_DATA_ISSUE.VER`(둘 다 INTEGER, 기본 0)에 있습니다. 검수 동시 승인·이슈
동시 수정 같은 경합에서 마지막 갱신이 이전 값을 덮어쓰는 lost update를 막기 위해, 갱신 시 버전 일치를
확인합니다.

**Q19. 단일 인스턴스라는 전제가 설계에 어떻게 반영되나요?**
A. 원문 참고사항은 "단일 PostgreSQL 인스턴스 기준(읽기 분산/클러스터 없음), Quartz도 단일 인스턴스
JobStore"임을 명시합니다. 다만 다중 인스턴스/재시작 환경 대비로 멱등 원장(LS_WEBHOOK_IDEMPOTENCY)과
통지 백킹 스토어(LS_CONTROL_NOTIFY_FALLBACK)를 DB에 영속화해 멱등키 손실·중복 적재를 차단합니다.

## 5. 다른 산출물과의 연계

> 아래 연계 중 **D8(엔티티 관계 모형 설계서)** 가 가장 밀접합니다. 그 외 산출물과의 연결은
> D9 원문에 직접 인용되지 않은 경우 프로젝트 문서 체계상의 일반적 관계로 이해하시기 바랍니다
> (원문에 명시된 연결은 D8·ID 체계뿐).

- **R2 요구사항정의서 / R시리즈**: D9의 테이블들은 요구 기능(SFR)을 데이터로 뒷받침합니다. 예: 이미지 10만장
  (SFR-16)→`LS_DATA_SRC` 최대 100,000행, 영상 5,000건(SFR-17)→`LS_DATA_RAW` 최대 20,000행(원본+증강),
  증강 3종+해상도(SFR-06·07)→`LS_DATA_AUG.AUG_TYPE_CD`(WINTER/NIGHT/RAIN/RESOLUTION),
  해상도 변경(SFR-06-03)→`LS_RESOLUTION_EXPORT`. (요구↔테이블 추적성)
- **D1 클래스 설계서**: 저작도구 도메인 엔티티 클래스(JPA @Entity)가 D9 테이블에 매핑됩니다. 클래스의 필드
  타입·명명이 D9 컬럼 타입·명명과 정합해야 하며, 논리 FK는 클래스에서 ID 참조(`Long rawSn`)로 표현됩니다.
- **D2 사용자 인터페이스 설계서 / 화면**: 라벨링·검수·마킹·배정·게시판 등 화면이 CRUD하는 대상이 D9 테이블
  입니다(예: 라벨 캔버스→`LS_DATA_LBL`, 검수 반려→`LS_DATA_ISSUE`, 공지→`LS_NOTICE`).
- **D3 프로그램 설계서 / 인터페이스**: 배치 파이프라인·외부 연동(비식별·VLM·증강·관제 통지)이 기록되는
  운영 테이블이 D9에 있습니다(`LS_BATCH_PROC_LOG`, `LS_DEIDENT_PROC_LOG`, `LS_WEBHOOK_IDEMPOTENCY`,
  `LS_CONTROL_NOTIFY_FALLBACK`). 멱등·재시도·사장큐 컬럼이 인터페이스 신뢰성 설계와 직결됩니다.
- **D5 아키텍처 설계서**: PostgreSQL 단일 인스턴스, `klid_at` 스키마, 공유 MNG_\*/QRTZ_\* 경계 같은
  물리 배치 전제가 아키텍처 결정과 일치합니다(읽기 분산/클러스터 없음).
- **D8 엔티티 관계 모형 설계서(ERD) — 가장 밀접**: D9의 각 테이블은 D8 엔티티와 **번호 1:1 매핑**
  (`KLID-AT-TB-NNN` ↔ `KLID-AT-EN-NNN`)됩니다. 논리 관계(D8)가 물리 논리 FK(D9)로 구현되며, D8 논리 엔티티
  39개 = D9 물리 테이블 39개로 개수도 합치됩니다. D9 각 테이블 명세의 "관련 엔티티 ID" 행이 이 다리입니다.
  ※ 공유 MNG_\* 클립 스키마의 진실원은 별도(ERD-024, D8/D9 산출물 비대상)로 관리됩니다.
- **D10·D11(테스트/단위 관련 설계서 등)**: D9의 제약(UNIQUE/CHECK/NOT NULL)·상태 전이 코드값·용량 산정은
  테스트 케이스(경계값·중복 차단·상태 머신 검증)의 근거가 됩니다. (구체 연결 내용은 D9 원문에 명시되지 않음)
