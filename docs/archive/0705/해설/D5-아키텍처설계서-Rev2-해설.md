## 1. 이 문서는 무엇인가

### 1.1 한 줄 요약

D5 아키텍처 설계서는 **AI 기반 지방정부 CCTV 관제지원시스템(2차)** 의 서브시스템인
**학습데이터 저작도구**의 전체 청사진(아키텍처)을 규정하는 CBD(Component Based Development)
표준 설계 산출물입니다. 크게 세 부분으로 구성됩니다.

1. **소프트웨어 아키텍처** — 응용 소프트웨어 내부 구조(레이어드 아키텍처, 컴포넌트·커넥션)
2. **시스템 아키텍처** — 응용 소프트웨어 + 이를 둘러싼 하드웨어·네트워크·연동 시스템의 관계
3. **아키텍처 요구사항 및 구현방안** — 품질·보안·성능·장애복구 관점의 비기능 요구사항과 그 구현 전략을 요구사항 1건당 1표로 매핑

### 1.2 문서의 목적 (원문 "작성 목적")

원문은 스스로의 목적을 다음과 같이 규정합니다.

- **시스템의 품질을 확보하기 위한 전체 시스템 청사진**으로서 아키텍처를 작성한다.
- **소프트웨어 아키텍처**는 개발 대상 응용 소프트웨어에 대한 아키텍처이다.
- **시스템 아키텍처**는 응용 소프트웨어 + 이와 상호작용하는 환경·네트워크가 포함된 아키텍처이다.

즉 "소프트웨어만"과 "소프트웨어 + 인프라·네트워크"를 서로 다른 두 관점으로 나누어 그리는 것이
이 문서의 뼈대입니다. 이는 CBD 표준(원문 §제·개정 이력에 나오는 **NIA 2011.12 CBD 표준**)의
아키텍처설계 양식을 따른 것입니다.

### 1.3 작성 방법 (원문 "작성 방법")

- **소프트웨어 아키텍처**: 선정된 아키텍처 패턴을 중심으로 컴포넌트·커넥션·가시적 속성을 표현.
- **시스템 아키텍처**: 개발 대상 시스템과 상호작용하는 하드웨어·시스템 소프트웨어·네트워크와의 관계를 표현.
- **아키텍처 요구사항 및 구현방안**: 아키텍처 관점의 품질·보안·성능·장애복구 요구사항과 구현방안을 기술.

### 1.4 CBD 체계에서 아키텍처설계(D5)의 위치

CBD 산출물 체계는 크게 요구(R)·분석(A)·설계(D) 단계로 이어집니다. D5는 설계 단계의
**최상위 청사진**에 해당합니다. 세부 컴포넌트·클래스·시퀀스·DB 설계(D1·D2·D3·D8·D9 등)가
그리는 "부품 도면"의 상위에서, 전체 시스템이 어떤 계층으로 나뉘고, 어떤 외부 시스템과
어떻게 연동하며, 비기능 품질을 어떻게 확보하는지를 먼저 규정하는 **설계의 기준점**입니다.
(다른 산출물과의 연계는 §5 참조.)

## 2. 섹션별 상세 해설

원문은 §1 소프트웨어 아키텍처, §2 시스템 아키텍처, §3 아키텍처 요구사항 및 구현방안의
세 절과 마지막 "항목 설명"으로 구성됩니다. 순서대로 해설합니다.

### 2.1 §1 소프트웨어 아키텍처

#### 2.1.1 채택 패턴 — 레이어드(Layered) 아키텍처

본 시스템은 **표현·업무·데이터 계층을 분리한 레이어드 아키텍처**를 채택한 "모듈형 단일 애플리케이션"입니다.
핵심 규칙은 다음과 같습니다.

- **표현 계층(웹 프론트엔드)** 은 **업무 계층(애플리케이션 서버)의 REST 인터페이스만** 호출한다.
- **업무 계층** 은 **컨트롤러 → 서비스 → 리포지토리**의 **단방향 의존**으로 구성한다.
- **데이터 계층(관계형 DB·파일 스토리지)** 은 **리포지토리를 통해서만** 접근한다.
- **AI 추론**은 업무 계층이 오케스트레이션하되, 실제 추론 연산은 **내부 추론 서버**
  (별도 프로세스, 무상태)로 분리하여 **GPU 자원을 격리**한다.

이 단방향 의존과 계층 간 인터페이스 고정이 레이어드 아키텍처의 본질이며, 상위 계층이 하위 계층에만
의존하고 역방향 의존을 금지함으로써 변경 파급을 억제합니다.

#### 2.1.2 §1 다이어그램(Mermaid) 구성요소 해설

다이어그램은 4개의 큰 계층/영역(subgraph)으로 구성됩니다.

**(1) 표현 계층 (PL, Presentation Layer)**
- `FE` — 웹 프론트엔드. 라벨링 캔버스·검수·관리·마킹 화면을 담당.

**(2) 업무 계층 (BL, Business Layer)** — 내부에 다시 여러 그룹을 둡니다.
- `CTRL` 컨트롤러 — 요청 수신·표준 응답·검증
- `SVC` 서비스 — 업무 로직·트랜잭션·상태 전이
- `REPO` 리포지토리 — 영속성 접근(ORM·동적 질의)
- `BATCH` 배치 파이프라인 — 비식별→마킹→시계열→프레임추출→오토라벨링→트랙보간(선언적 단계 구성·스케줄러 1건/분)
- `CC` **공통 인프라** 하위 그룹:
  - `SEC` 인증·인가 필터(JWT 검증·역할/채널 분기)
  - `RESP` 표준 응답·예외 처리
  - `DS` 듀얼 데이터소스(관제 참조 / 포털)
  - `LOG` 로깅·메트릭·추적ID(민감정보 마스킹)
- `INTEG` **연동 클라이언트(장애 차단 적용)** 하위 그룹:
  - `EXTC` 비식별·시계열·증강·관제통지 외부 연동 클라이언트
  - `AIC` 추론 호출 클라이언트(내부 추론 서버 호출)

**(3) AI 추론 영역 (AIL — 내부 추론 서버, 별도 프로세스)**
- `AISRV` — 객체탐지(YOLO)·세그멘테이션(SAM2) 추론. 무상태·GPU 수평 확장.

**(4) 데이터 계층 (DL, Data Layer)**
- `DB` 관계형 데이터베이스 — 저작도구 전용 테이블 소유 + 공유 테이블 참조검증 + 스케줄러 잡 저장
- `FS` 파일 스토리지 — 원본/비식별 영상·프레임 2벌

**흐름(엣지) 해설:**
- `FE → CTRL` : 표준 응답 기반 REST/JSON (표현↔업무 커넥션)
- `CTRL → SVC → REPO` : 업무 계층의 단방향 의존 체인
- `REPO → DB` : 영속성 접근
- `SVC → BATCH` : 서비스가 배치 파이프라인을 구동
- `SVC → FS` : 서비스가 파일 스토리지에 접근(영상·프레임 저장)
- `BATCH → AIC`, `BATCH → EXTC` : 배치가 추론·외부 연동 클라이언트를 호출
- `AIC ⇢ AISRV` : **프로세스 경계 호출**(점선) — 같은 운영 영역이지만 별도 프로세스로 넘어감
- `SVC ⇢ CC` : 서비스가 공통 인프라를 사용(점선)

#### 2.1.3 가시적 속성(원문 인용문)

원문은 커넥션의 성격을 다음과 같이 명시합니다.
- 표현↔업무: **표준 응답 래퍼 기반 REST/JSON**
- 업무↔데이터: **ORM·동적 질의**
- 업무↔내부 추론 서버: **프로세스 경계 호출(장애 차단 정책 적용)**
- 외부 연동(비식별·시계열·증강·관제통지): **전용 연동 클라이언트로 단일화**

여기서 "표준 응답 래퍼"는 프로젝트의 `ApiResponse<T>` 공통 응답 규약을, "장애 차단 정책"은
Resilience4j 기반 타임아웃·재시도·서킷 브레이커를 가리킵니다(프로젝트 CLAUDE.md 근거).

### 2.2 §2 시스템 아키텍처

#### 2.2.1 도입 서술 — 무엇을 어디에 배치하는가

개발 대상시스템(학습데이터 저작도구)은:
- **단일 인스턴스로 배포되는 애플리케이션 서버**를 중심으로,
- **내부 추론 서버**(GPU 워커, 다중 인스턴스 수평 확장 가능),
- **관계형 데이터베이스**, **파일 스토리지**로 구성됩니다.

핵심 경계 규정은 다음과 같습니다.
- 애플리케이션 서버와 내부 추론 서버는 **같은 운영 영역의 내부 컴포넌트**이다.
- 외부 **연동** 시스템(비식별 서버·외부 VLM 서비스·외부 증강 AI·관제서버·포털 DB)과는
  **시스템·인터페이스 경계**를 둔다.
- 이 연동 시스템들은 **모두 온프레미스 내부망에 배치되는 별도 서버/시스템**이며,
  경계의 성격은 **인터넷·보안 네트워크 경계가 아니라 소유·인터페이스 경계**이다.

이 문장이 v1.3 개정(경계 재정의)의 핵심 결과물입니다. "외부"라는 단어가 주는 "인터넷 너머,
방화벽 밖"이라는 오해를 걷어내고, 실제로는 같은 온프렘망 안에 있으나 **소유 주체와 연동
인터페이스만 다른** 시스템임을 분명히 한 것입니다.

#### 2.2.2 §2 다이어그램 구성요소 해설

**사용자 단말 (USER)**
- 검수자·작업자·포털 회원이 웹 브라우저(표준 HTTPS)로 접속.

**학습데이터 저작도구 (SYS — 개발 대상·내부 운영 영역)** 내부 컴포넌트:
- `WEB` 웹 프론트엔드 서버 — 정적 자원 서빙
- `APP` 애플리케이션 서버 — **기본 단일 인스턴스·스케줄러 내장**
  (온프레미스 이중화 시 Quartz 클러스터링 옵션 지원)
- `AISRV` 내부 추론 서버 — 객체탐지·세그멘테이션 추론, GPU 워커·다중 인스턴스 수평 확장
- `DB` 관계형 데이터베이스 — 저작도구 전용 스키마
- `STORE` 파일 스토리지 — 원본·비식별 영상/프레임 2벌

**연동 시스템 (EXT — 타 시스템 소유·온프렘 내부망)** 5종:
- `DEID` 비식별 서버
- `VLM` 외부 VLM 서비스(시계열 메타)
- `AUG` 외부 증강 AI(WINTER/NIGHT/RAIN/해상도)
- `CTRL` 관제서버(JWT 발급·공유 테이블·통지 수신)
- `PORTAL` 포털 DB(데이터마트 적재 소스)

**흐름(엣지) 해설:**
- `USER → WEB` : HTTPS. **JWT는 관제/포털이 발급한 것을 브라우저 공유 스토리지로 인계받아
  요청 헤더로 전달**.
- `WEB → APP` : REST/JSON
- `APP → AISRV` : 내부망 호출(**60초 타임아웃**)
- `APP → DB`, `APP → STORE` : 데이터·파일 접근
- `APP → DEID` : 비식별 요청
- `APP → VLM` : 시계열 요청(**45초**)·결과 콜백 수신
- `APP → AUG` : 증강 요청·결과 콜백 수신
- `APP → CTRL` : **완료/수정 통지(단방향 outbound)**
- `CTRL → APP` : 상세 조회(서버 간 API 호출) — 통지 수신 후 관제서버가 상세 데이터를 되물어옴
- `APP → PORTAL` : 라벨/메타 Load(포털 DB 직접 접속)

이 다이어그램에서 특히 주목할 점은 **관제서버와의 관계가 양방향처럼 보이지만 성격이 다른 두 화살표**라는
것입니다. `APP → CTRL`은 저작도구가 능동적으로 보내는 "단방향 outbound 통지"이고,
`CTRL → APP`은 그 통지를 받은 관제서버가 필요 시 저작도구 API를 호출해 상세를 조회하는
별개의 서버 간 호출입니다. 양방향 M2M 인증 채널이 상시 열려 있는 구조가 아닙니다.

#### 2.2.3 §2 인용문 — 세 가지 보충 규정

원문은 다이어그램 아래에 세 개의 인용 블록으로 중요한 설계 판단을 못박아 둡니다.

**(가) 내부 추론 서버 vs 외부 연동의 구분**
- 내부 추론 서버는 외부 시스템이 아니라 **저작도구 운영 영역 내부의 추론 인프라**(무상태·GPU 수평 확장)이다.
- 외부 연동 시스템은 **비식별·외부 VLM·외부 증강 AI·관제서버·포털 DB의 5종**이다.
- 저작도구와의 경계는 인터넷·보안 네트워크 경계가 아니라 **시스템·소유·인터페이스 경계**이며,
  관제서버는 **동일 도메인·공유 DB**, 포털은 **외부 채널로 포털 DB 직접 접속**이다.

**(나) JWT 인계 경로**
- 저작도구는 **토큰을 발급하지 않고**, 관제서버(내부)/포털(외부)이 발급한 JWT를 **인계받는다**.
- 관제서버와는 **동일 도메인 운영**이라 **브라우저 공유 스토리지(localStorage/sessionStorage)로
  토큰이 전달**되고, 사용자 브라우저가 저작도구로 보내는 **요청 헤더에 실려** 온다
  (서버 간 직접 토큰 전달 채널이 아님).
- 관제서버→저작도구의 서버 간 호출은 **통지 수신 후의 상세 데이터 조회(API 호출)에 한한다**.

**(다) 배포 토폴로지**
- 기본 배포는 **온프레미스 단일 리전·단일 인스턴스**(스케줄러 내장, 업무시간 기준)이다.
- 이중화(2노드 동시 기동)가 필요하면 `QUARTZ_CLUSTERED` 환경변수로 **Quartz 클러스터링
  (PostgreSQL JobStore `QRTZ_LOCKS` 기반 락)이 옵션으로 지원**되어 스케줄러 잡 **중복 실행을 방지**한다.
- **ai-server(추론)는 토폴로지와 무관하게 다중 인스턴스로 수평 확장 가능**하다.

즉, 애플리케이션 서버(상태·스케줄러 보유)는 기본 단일 인스턴스로 두되 필요 시 옵션으로만
이중화하고, 추론 서버(무상태)는 언제든 수평 확장하는 **비대칭 확장 전략**입니다.

### 2.3 §3 아키텍처 요구사항 및 구현방안

#### 2.3.1 §3의 도입문과 형식

원문은 §3 도입문에서 "아키텍처 관점에서 시스템에 크게 영향을 주는 품질·보안·성능·장애복구
요구사항과 구현방안을, **사용자 요구사항 정의서의 요구사항(비기능 요구사항 NFR 및 관련
품질·데이터 요구사항 RQ-QUR·RQ-DAR) 1건당 1표**로 기술한다"고 규정합니다.

각 표의 공통 구조는:
- **요구사항 ID** — 발주처 정의서/내부 도출 ID
- **요구사항 내용** — 무엇을 만족해야 하는가(핵심 정량목표·준수표준은 볼드 처리)
- **구현방안** — 어떻게 만족시키는가 + **품질목표 수준**(측정 기준) + 검증 방법

여기서 **품질목표 수준**은 v1.2 정합 검토에서 각 표에 명시적으로 넣은 정량/정성 목표치로,
"이 요구를 충족했다"고 판정할 측정 기준의 역할을 합니다.

#### 2.3.2 ID 체계 — 두 종류의 요구사항이 섞여 있음

§3의 요구사항 ID는 두 계열로 나뉩니다.

- **NFR-001 ~ NFR-007** : **저작도구 자체 도출분**(v1.4 개정에서 유지하기로 한 내부 도출 비기능).
  성능·확장성·가용성·보안·접근성·관찰가능성 등 아키텍처가 직접 책임지는 항목.
- **RQ-* 계열** : **발주처(사용자 요구사항 정의서 = 엑셀) 원본 ID**를 그대로 가져온 항목.
  - `RQ-QUR-*` : 품질(Quality) 요구
  - `RQ-DAR-*` : 데이터(Data) 요구
  - `RQ-PER-*` : 성능(Performance) 요구
  - `RQ-SER-*` : 보안(Security) 요구
  - `RQ-COR-*` : 규정 준수/호환(Conformance/Compatibility) 요구
  - `RQ-SIR-*` : (v1.5에서 삭제된) UX/UI·인터페이스 표준 요구

v1.4 개정의 핵심은 이전에 저작도구가 임의로 붙인 `NFR-011~017`(7행)을 발주처 엑셀의 원본
비기능 ID로 교체하되 **비기능 1건당 1행(1:1)** 원칙으로 분리하여 7행 → 11행으로 늘린 것입니다.
그 후 v1.5에서 매핑이 성립하지 않는 1행을 삭제해 **11행 → 10행**이 되었습니다.

#### 2.3.3 각 요구사항 표 해설

아래는 §3의 각 표를 순서대로 요약·해설한 것입니다. 나열 순서는 **NFR-001~007(저작도구 자체 도출분)** 이 앞 블록, 이어서 **RQ-\* 13건이 사용자 요구사항 정의서(발주처 엑셀 '요구사항정의서(비기능)' 시트) 순서** 인 성능(PER)→품질(QUR)→데이터(DAR)→보안(SER)→제약(COR)으로 배열됩니다(v1.6 정합).

**NFR-001 [성능] 배치 파이프라인 처리량**
- 내용: 비식별→마킹(비식별 영상)→시계열 메타→프레임 추출→오토라벨링(객체탐지·세그멘테이션)→
  트랙 보간으로 이어지는 배치를 **단일 인스턴스 스케줄러(클러스터 미적용)에서 1건/분 이상** 처리.
- 구현: 배치 단계를 **선언적 파이프라인**으로 구성해 단계 재배치(비식별 선두)·조건부 실행을 한 곳에서
  관리하고, 스케줄러가 1분 주기로 1건씩 유입. **품질목표: 처리율 ≥ 1건/분**. 단계별 소요·건수를
  메트릭 수집·대시보드 모니터링. 단일 인스턴스 장애 위험은 **잡 상태를 DB에 영속화**하여 재기동 시
  미완료 잡을 이어 처리하는 방식으로 완화.

**NFR-002 [성능·확장성] 이미지 학습데이터 처리 규모**
- 내용: **이미지 학습데이터 10만 장** 규모 수용(핵심 산출물 목표 SFR-16).
- 구현: 프레임 원천 테이블의 누적 건수를 적재 규모 기준으로 설계, 목록·조회는 **전수 조회 금지·페이징 필수**.
  **품질목표: 누적 이미지 ≥ 100,000장**. 조회 컬럼 인덱스 + 페이징(커서 기반 검토)으로 응답 성능 유지.

**NFR-003 [성능·확장성] 영상 학습데이터 처리 규모**
- 내용: **30초 이상 영상 학습데이터 5,000건** 수용(작업 단위 = 영상 1건, SFR-17).
- 구현: 원시 영상 테이블 누적 건수 설계, 영상 1건을 작업 단위로 하는 적재·배정·검수 흐름.
  **품질목표: 누적 영상 ≥ 5,000건**. 원본·비식별 영상을 별도 경로 동시 저장하여 스토리지 규모 산정.

**NFR-004 [가용성·장애복구] 외부 연동 및 내부 추론 호출 복원력**
- 내용: **외부 연동(비식별·시계열(VLM)·증강·관제 통지)** 과 **내부 추론 서버 호출** 등 모든
  원격·프로세스 경계 호출에 **타임아웃·재시도·서킷 브레이커(장애 차단)** 적용. 외부 연동은 4종,
  내부 추론 서버는 내부 인프라로 구분.
- 구현: 외부 연동 4종 + 내부 추론 호출 모두에 동일 복원력 정책 적용(외부 시스템이 아니어도
  프로세스 경계를 넘으므로 동일 보호). **품질목표: 복원력 적용률 100%, 시계열 45초·내부 추론 60초 타임아웃.**
  외부 장애 시에도 파이프라인 전면 중단 방지, 비식별 실패 영상은 실패 표시 후 재시도 큐로, **원본 절대 삭제 금지**.
- **각주 1(baseline 정정)**: R1 원문은 AI 추론 호출을 "모든 외부 연동 5종" 중 하나로 표기했으나,
  본 설계서는 아키텍처 정합(ai-server는 외부 시스템이 아니라 내부 추론 인프라)에 맞춰
  "**외부 연동 4종 + 내부 추론 서버 호출**"로 재분류. 적용 대상은 동일, 분류 관점만 정정.
- **각주 2(증강 연동 현행)**: 증강 외부 연동은 운영 기본 구현이 **무연동 스텁**(외부 HTTP 미호출)이라,
  복원력 정책은 **실 연동 구현체 활성화 시 적용**되며 현행 기준으로는 적용 대상이 없음.

**NFR-005 [보안] 민감정보 보호**
- 내용: 개인정보·토큰 로그 미출력, 영상 암호화 저장, 비식별 처리 이력 영상 단위 기록,
  관제 통지 페이로드에 개인정보·토큰·원본(비-비식별) 이미지 미포함. (**민감정보 노출 0건**)
- 구현: 로깅 계층 민감 필드 마스킹, 영상 암호화 저장, 통지 페이로드는 메타·수정 요약만 담아
  본문·원본 이미지·토큰 배제. **품질목표: 민감정보 로그/페이로드 노출 0건.** 정적 보안 점검으로 검증.

**NFR-006 [접근성] 포털 웹 접근성**
- 내용: 포털(외부 채널)은 반응형 웹(PC/태블릿/모바일), **WCAG 2.1 AA 준수**.
- 구현: 반응형 설계 + 시맨틱 마크업·대체 텍스트·키보드 접근·색상 외 정보 전달 등 지침 적용.
  **품질목표: WCAG 2.1 AA 준수.** 자동 점검 도구 + 수동 검수로 확인.

**NFR-007 [관찰가능성] 메트릭·추적성**
- 내용: 화면/API 응답시간·배치 처리량·외부 호출 메트릭 수집, 모든 요청에 추적ID 부여해
  로그·외부 호출 헤더로 전파. (**핵심 이벤트 메트릭 수집률 100%**)
- 구현: 메트릭 수집기로 응답시간·배치 처리량·외부 호출 수집→모니터링 시스템 노출. 요청 진입 시
  추적ID 생성→로그 컨텍스트에 심고 외부 호출 헤더로 전파(분산 추적). **품질목표: 핵심 이벤트 메트릭 수집률 100%.**

**RQ-PER-02-01 [성능] 화면 응답시간 기준**
- 내용: 전 화면 페이지 응답속도 **3초 이하**(초과 불가피 시 발주기관 협의), 페이지 용량·요청 최적화.
- 구현: 주요 화면·조회 응답 3초 이하 설계, FE 번들·요청 최적화 + 대량 라벨 조회 페이징. **품질목표:
  응답시간 ≤ 3초.** 성능테스트로 확인.

**RQ-PER-03-01 [성능] 기능 수행 지연 사전 안내**
- 내용: 10초 이상 소요 예상 대용량 질의·장시간 작업은 팝업·프로그레스바로 시작·끝 예측 가능하게
  사전 안내 + 취소 기능 제공.
- 구현: 대용량 질의·대량 라벨 조회·배치 트리거 등에 진행 안내(프로그레스)·취소 제공. **품질목표:
  10초 이상 지연 예상 작업에 진행 안내·취소 100% 제공.**

**RQ-PER-04-01 [성능] 오류 응답 속도**
- 내용: 입력 데이터 형식 오류 등을 입력 후 **3초 이내**에 적절한 오류 메시지로 제시.
- 구현: 입력 형식·처리 오류를 **표준 에러 응답 포맷(ApiResponse)** 으로 3초 이내 제시. **품질목표:
  오류 메시지 표시 ≤ 3초.**

**RQ-PER-05-03 [성능] 시스템 자원 효율**
- 내용: 시스템 자원(CPU·메모리) 평균 사용률 **80% 이하** 유지, 장시간 배치·스트리밍 구간 메모리 누수 방지.
- 구현: 배치 파이프라인(프레임 추출·추론 호출)·스케줄러 워커 자원 관리, **듀얼 데이터소스(관제 참조/포털)
  커넥션 풀 분리·최적화**. **품질목표: CPU·메모리 평균 ≤ 80%, 메모리 누수 부재.** 로그아웃·토큰 만료 시
  세션 자원 정리, 부하테스트 검증.
- (v1.5 정정) ID가 RQ-PER-05-01이 아니라 **RQ-PER-05-03**인 이유: PER-05-01은 발주처 제공
  가상화 인프라(HW/솔루션) 영역이고, 저작도구 SW 자원효율 기여분은 PER-05-03이기 때문.

**RQ-QUR-03-01 [규정 준수·품질] 학습데이터 단계별 품질관리 기준(수집·제작·검수)**
- 내용: 수집·제작·검수 각 단계 수행기준 수립·품질관리 방안 제시, 검수 이력·승인 버전 시스템 확인 가능.
- 구현: 수집(적재 검증)·제작(비식별→마킹→오토라벨링)·검수(승인/반려) 단계별 기준 수립,
  **검수 승인 시점에 라벨 전체를 스냅샷으로 버전 관리(페이로드 해시 기준)**. 검수 승인 데이터만
  학습데이터로 확정. **품질목표: 전 단계 수행기준 수립 + 검수 이력·승인 버전 시스템 확인 가능.**

**RQ-QUR-03-02 [규정 준수·품질] 학습데이터 종류·제작방법별 품질관리 기준**
- 내용: 학습데이터 종류·제작 방법(라벨링 방식·활용 기법)별 품질관리 기준 수립.
- 구현: 바운딩박스·폴리곤·세그멘테이션·트래킹 등 방식별 라벨 규격·검수 기준 + 오토라벨링·시계열
  메타 검토·생성형 증강 4종(WINTER/NIGHT/RAIN/해상도)별 제작기법 기준 수립. NFR-002·003 규모 목표와 연계.

**RQ-DAR-01-01 [규정 준수·데이터] 데이터 표준 준수**
- 내용: 저작도구 소유 데이터 객체(테이블·컬럼)를 범정부 데이터 표준사전과 정합 설계, 코드성 데이터는
  코드표준화 지침 정합, 라벨링 방식별 데이터 포맷 표준 정의.
- 구현: 저작도구 전용 테이블·컬럼의 단어·용어·도메인·코드를 범정부 표준 기반 표준사전과 정합 설계,
  마이그레이션 시 명명규칙 점검. 라벨링 방식별(바운딩박스·폴리곤·세그멘테이션·트래킹) 포맷 표준 정의.
  **공유 테이블은 관제서버 소유로 참조검증만 수행**(공유 스키마 변경 충돌은 변경 전 선승인·변경 알림
  프로세스로 완화). **품질목표: 신규 객체 표준 정합 + 라벨링 방식별 포맷 표준 정의.**

**RQ-DAR-06-02 [규정 준수·품질] 학습데이터 값 검증·정합성(공공데이터 품질진단 기준)**
- 내용: 시스템 생성 외 **제공되는** 학습데이터 원본 정합성 검증, 공공데이터 품질진단 기준·업무규칙(BR)
  값 검증으로 오류 입력 차단, 오류유형별 조치 이력 관리.
- 구현: 라벨 저장·검수 시 좌표 범위·필수 속성·코드 정합 등 업무규칙 값 검증으로 오류 차단, 원본
  정합성 검증 + 오류데이터 반려·재작업 + 오류유형별 조치 이력. **품질목표: 오류 라벨 입력 차단 +
  오류유형별 조치 이력 관리.** 검증 항목 정의서 제출.

**RQ-SER-01-01 [보안] 세션·계정 보안대책**
- 내용: 만료 세션 차단, 로그아웃·토큰 만료 시 세션 종료, 관리 화면 등 권한 페이지 비인가자 노출 차단,
  인증정보·시크릿 소스 하드코딩 금지·민감정보 암호화.
- 구현: 인증·인가 필터가 인계 토큰 검증하여 만료·위조 토큰 거부→상위 시스템 로그인 유도. 시크릿은
  **환경변수 주입(하드코딩 금지)**, 영상·민감정보 암호화 저장. **로그인 실패 제한·동시 로그인 차단은
  인증 발급 주체(관제/포털)의 책임이며 저작도구는 토큰 검증만 담당.** **품질목표: 만료 토큰 차단 +
  관리 화면 비인가 노출 0 + 시크릿 하드코딩 0.**

**RQ-SER-02-01 [보안] 역할별 접근제어**
- 내용: 전 화면·API에 역할 기반 접근제어, 관리 화면은 검수자 전용, 만료 계정·불필요 권한 차단.
- 구현: 역할(검수자/작업자/포털회원)·채널 클레임 기반 페이지·API 접근 구분, 관리 화면 검수자 전용.
  **품질목표: 전 화면·API 역할별 통제 100%.** 권한 없는 접근 403 통합테스트 확인.

**RQ-SER-03-01 [보안] 시큐어코딩(SW 개발보안)**
- 내용: '행정기관 및 공공기관 정보시스템 구축·운영 지침' 제50조 SW 개발보안 절차 준수.

**RQ-SER-04-01 [보안] 취약점 점검·모의해킹**
- 내용: 개발 소스 전체 보안약점 진단·모의해킹 등 취약점 점검 1회 이상 실시, 지적사항 보완 완료.
- 구현: 소스 전체 보안약점 진단 + 웹 취약점 표준 항목 기준 모의해킹 1회 이상 + 지적사항 후속 보완.
  **품질목표: 소스 전체 진단 1회 이상 + 지적사항 보완 완료.**

**RQ-COR-04-01 [규정 준수·품질] 웹표준·크로스브라우징**
- 내용: 비표준 플러그인 없이 표준 웹기술로 전 기능 동작, **3종 이상** 브라우저 동등 동작, 표준
  마크업·스타일 문법 준수.
- 구현: FE를 표준 웹기술로 구현, 라벨링 캔버스도 표준 캔버스 기술로 동작시켜 비표준 플러그인 배제.
  **품질목표: 3종 이상 브라우저 동등 동작 + 비표준 플러그인 0.** 포털 화면 반응형 제공.

#### 2.3.4 §3 마무리 인용문 — 외부 시스템 본체 범위 명시

원문은 §3 끝에 저작도구의 **범위 경계**를 다시 못박습니다.
- **외부 VLM 서비스·생성형 증강 AI·영상 합성 모델·데이터마트 본체는 저작도구 범위 외**(외부 시스템 책임).
- 저작도구는 **외부 VLM 시계열 호출 연동, 외부 증강 결과 수신·검수, 데이터마트 적재용 조회
  인터페이스 제공까지만** 담당한다.

이는 아키텍처 요구사항을 무한정 확장 해석하지 않도록 하는 "책임 울타리"입니다. AI 모델 본체의
학습·파인튜닝·프롬프트 관리 등은 모두 외부 시스템 책임이며, 저작도구는 그 결과를 받아 검수·라벨링·
버전관리하고 조회 인터페이스를 제공하는 데까지만 책임집니다.

### 2.4 "항목 설명" (원문 마지막)

CBD 양식의 각 항목이 무엇을 기입하는 칸인지를 규정하는 메타 설명입니다.
- 소프트웨어 아키텍처 / 시스템 아키텍처 각각을 기입.
- 아키텍처 요구사항 및 구현방안: 품질·보안·성능·장애복구 등의 요구사항·구현방안 기술.
  - 요구사항 ID = "사용자 요구사항 정의서"의 관련 요구사항 ID.
  - 요구사항 내용 = 요구사항 내용을 상세히.
  - 구현방안 = 구현방안을 상세히.

## 3. 핵심 용어

| 용어 | 정의(원문 맥락 기준) |
|------|-----------------------|
| **레이어드(Layered) 아키텍처** | 표현·업무·데이터 계층을 분리하고 상위→하위 단방향 의존만 허용하는 패턴. 본 시스템의 소프트웨어 아키텍처 패턴. |
| **표현 계층(Presentation Layer)** | 웹 프론트엔드. 라벨링 캔버스·검수·관리·마킹 화면. 업무 계층 REST 인터페이스만 호출. |
| **업무 계층(Business Layer)** | 애플리케이션 서버. 컨트롤러→서비스→리포지토리 단방향 의존 + 공통 인프라 + 연동 클라이언트 + 배치 파이프라인. |
| **데이터 계층(Data Layer)** | 관계형 DB + 파일 스토리지. 리포지토리를 통해서만 접근. |
| **내부 추론 서버(ai-server)** | 객체탐지(YOLO)·세그멘테이션(SAM2) 추론을 담당하는 별도 프로세스. **무상태**, GPU 워커, 다중 인스턴스 수평 확장. 외부 시스템이 아닌 저작도구 내부 인프라. |
| **시스템·인터페이스 경계** | 인터넷·방화벽 같은 네트워크 경계가 아니라, 같은 온프렘 내부망 안에서 **소유 주체와 연동 인터페이스만 다른** 경계. Rev2(v1.3)의 핵심 개념. |
| **연동 시스템(5종)** | 비식별 서버·외부 VLM 서비스·외부 증강 AI·관제서버·포털 DB. 타 시스템 소유·온프렘 내부망 배치. |
| **비기능 요구사항(NFR)** | 기능이 아닌 품질 속성(성능·확장성·가용성·보안·접근성·관찰가능성). §3에서 NFR-001~007은 저작도구 자체 도출분. |
| **RQ-* 계열 요구사항** | 발주처 사용자 요구사항 정의서(엑셀) 원본 ID. QUR(품질)·DAR(데이터)·PER(성능)·SER(보안)·COR(규정/호환). |
| **품질목표 수준** | 각 요구사항 구현방안에 명시된 정량/정성 측정 기준(예: 처리율 ≥ 1건/분, 응답 ≤ 3초, 노출 0건). |
| **선언적 파이프라인** | 배치 단계(비식별→마킹→...→트랙보간)를 한 곳에서 순서·조건부 실행으로 구성·재배치하는 방식. NFR-001 구현. |
| **장애 차단(서킷 브레이커) / 복원력 정책** | 타임아웃·재시도·서킷 브레이커. 원격·프로세스 경계 호출에 적용(NFR-004). 프로젝트에서는 **Resilience4j**로 구현. |
| **Resilience4j** | (프로젝트 스택) 외부·프로세스 경계 호출의 타임아웃·재시도·서킷 브레이커를 제공하는 Java 라이브러리. §1·§3의 "장애 차단"의 실제 구현체. |
| **Nuclio 스타일** | (프로젝트 맥락) CVAT의 서버리스 함수(Nuclio) 패턴을 참고해 추론을 함수 엔드포인트로 분리한 것. §1의 "내부 추론 서버 별도 프로세스·무상태" 구성이 이에 해당. *원문 D5 본문에는 'Nuclio' 표현이 직접 등장하지는 않으며, 프로젝트 CLAUDE.md에 근거한 배경 용어.* |
| **JWT 인계** | 저작도구가 토큰을 발급하지 않고 관제/포털 발급 JWT를 인증·인가 필터로 검증만 하는 방식. 관제와 동일 도메인이라 브라우저 공유 스토리지로 전달. |
| **듀얼 데이터소스** | 관제 참조용·포털용 두 데이터소스를 분리 운영(커넥션 풀 분리). §1 공통 인프라 `DS`, RQ-PER-05-03 구현. |
| **단방향 outbound 통지** | 저작도구→관제서버로 완료(TASK_COMPLETED)/수정(TASK_MODIFIED)을 능동 push. 상시 양방향 M2M 채널이 아님. |
| **Quartz 클러스터링** | 이중화(2노드) 시 `QUARTZ_CLUSTERED` 환경변수로 PostgreSQL JobStore `QRTZ_LOCKS` 락 기반 스케줄러 잡 중복 실행 방지. 기본은 단일 인스턴스라 미적용. |
| **표준 응답 래퍼(ApiResponse)** | 모든 API가 사용하는 공통 응답 구조. §1 커넥션 속성·RQ-PER-04-01 오류 응답의 기준 포맷. |

## 4. 예상 질문 Q&A

**Q1. 왜 애플리케이션 서버(BE)와 내부 추론 서버(ai-server)를 분리했나?**
A. GPU 자원을 격리하기 위해서입니다(§1). 추론 연산은 GPU 자원을 크게 소모하고 자원 경합이
발생하므로, 무상태 별도 프로세스로 떼어내면 애플리케이션 서버의 안정성을 지키면서 추론만 독립적으로
수평 확장할 수 있습니다. 애플리케이션 서버는 인증·DB·오케스트레이션·상태를 책임지고,
추론 서버는 무상태 추론만 담당합니다.

**Q2. 그렇다면 내부 추론 서버는 "외부 시스템"인가?**
A. 아닙니다(§2 인용문 (가), NFR-004 각주1). 별도 프로세스이긴 하나 **저작도구 운영 영역 내부의
추론 인프라**입니다. R1 원문이 이를 "외부 연동 5종" 중 하나로 표기했던 것을 Rev2에서
"외부 연동 4종 + 내부 추론 서버 호출"로 재분류했습니다. 다만 프로세스 경계를 넘는 호출이므로
복원력 정책(타임아웃·재시도·서킷 브레이커)은 외부 연동과 **동일하게** 적용합니다.

**Q3. 시스템 경계는 어디까지이고, 그 성격은 무엇인가?**
A. 개발 대상(SYS) 내부 = 웹 프론트엔드 서버·애플리케이션 서버·내부 추론 서버·DB·파일 스토리지입니다.
그 밖의 연동 시스템 5종과는 경계를 두되, 이 경계는 **인터넷·보안 네트워크 경계가 아니라
소유·인터페이스 경계**입니다(§2). 5종 모두 같은 온프레미스 내부망에 배치된 별도 서버/시스템이며,
소유 주체와 연동 규격만 다릅니다.

**Q4. 외부 연동 시스템은 정확히 무엇 무엇인가?**
A. 5종입니다: ① 비식별 서버 ② 외부 VLM 서비스(시계열 메타) ③ 외부 증강 AI(WINTER/NIGHT/RAIN/해상도)
④ 관제서버(JWT 발급·공유 테이블·통지 수신) ⑤ 포털 DB(데이터마트 적재 소스).

**Q5. 관제서버와의 통신은 양방향인가?**
A. 상시 양방향 M2M 채널은 아닙니다. 저작도구→관제서버는 **단방향 outbound 통지**(완료/수정)이고,
관제서버→저작도구는 그 통지를 받은 뒤 **상세 데이터를 되물어오는 API 호출**에 한합니다(§2 인용문 (나)).
두 화살표는 성격이 다른 별개의 호출입니다.

**Q6. JWT는 어떻게 저작도구에 전달되는가?**
A. 저작도구는 토큰을 발급하지 않습니다. 관제(내부)/포털(외부)이 발급한 JWT를 인계받는데,
관제서버와는 **동일 도메인 운영**이라 브라우저 공유 스토리지(localStorage/sessionStorage)에 담긴
토큰이 사용자 브라우저의 요청 헤더에 실려 옵니다. 서버 간 직접 토큰 전달 채널이 아닙니다(§2).

**Q7. 배포 구조(토폴로지)는 어떻게 되나?**
A. 기본은 **온프레미스 단일 리전·단일 인스턴스**(스케줄러 내장, 업무시간 기준)입니다. 이중화가
필요하면 `QUARTZ_CLUSTERED` 환경변수로 Quartz 클러스터링(PostgreSQL JobStore `QRTZ_LOCKS` 락)을
옵션 적용해 스케줄러 잡 중복 실행을 막습니다. 추론 서버는 토폴로지와 무관하게 다중 인스턴스로
수평 확장 가능합니다(§2 인용문 (다)).

**Q8. 애플리케이션 서버는 왜 단일 인스턴스인가? 이중화는 안 하나?**
A. 기본 배포가 단일 인스턴스입니다. 상태·스케줄러를 보유한 서버라 무분별한 다중 기동은 잡 중복
실행을 유발할 수 있어서입니다. 이중화가 필요한 온프레미스 환경에서는 옵션으로만 2노드 동시 기동 +
Quartz 클러스터링을 지원합니다. 반면 무상태인 추론 서버는 상시 수평 확장이 자유롭습니다(비대칭 확장).

**Q9. 단일 인스턴스 스케줄러의 장애 위험은 어떻게 완화하나?**
A. 잡 상태를 **데이터베이스에 영속화**하여, 재기동 시 미완료 잡을 이어 처리합니다(NFR-001 구현방안).
배치 파이프라인 데이터가 유실되지 않고 재개됩니다.

**Q10. 비기능 요구를 아키텍처가 어떻게 충족하나? (대표 예시)**
A. 성능(NFR-001~003·RQ-PER)은 선언적 파이프라인·페이징·인덱스·번들 최적화·듀얼 커넥션 풀로,
가용성(NFR-004)은 복원력 정책(타임아웃·재시도·서킷 브레이커)으로, 보안(NFR-005·RQ-SER)은
민감 필드 마스킹·토큰 검증·역할/채널 접근제어·환경변수 시크릿·정적 분석·모의해킹으로,
관찰가능성(NFR-007)은 메트릭 수집기 + 추적ID 전파로 충족합니다. 각 표의 "품질목표 수준"이
충족 판정 기준입니다.

**Q11. §3의 요구사항 ID가 두 종류인 이유는?**
A. `NFR-001~007`은 저작도구가 자체 도출한 아키텍처 책임 비기능이고, `RQ-*`는 발주처 사용자
요구사항 정의서(엑셀) 원본 ID입니다. v1.4에서 내부 임의 번호(NFR-011~017)를 발주처 원본 ID로
1:1 교체해 추적성을 확보했습니다.

**Q12. §3에서 삭제된 행이 있다는데, 왜인가?**
A. v1.5에서 'UX/UI·API 호출 표준' 행을 삭제했습니다. 저작도구의 API 호출 규약은 내부 설계규약이라
발주처 엑셀 비기능 요구에 대응 ID가 없고(SIR-01은 화면 UX/UI 표준 항목으로 성격이 상이),
매핑이 성립하지 않아 제거했습니다. 그 결과 11행 → 10행이 되었습니다.

**Q13. 자원 효율 요구의 ID가 RQ-PER-05-01이 아니라 -03인 이유는?**
A. PER-05-01은 발주처가 제공하는 가상화 인프라(HW/솔루션) 영역이고, 저작도구 SW의 자원효율
기여분은 PER-05-03이기 때문입니다(v1.5 정정).

**Q14. 증강(AUG) 연동은 실제로 동작하나?**
A. NFR-004 각주2에 따르면 증강 외부 연동의 운영 기본 구현은 **무연동 스텁**(외부 HTTP 미호출)입니다.
따라서 복원력 정책은 실 연동 구현체를 활성화할 때 적용되며, 현행 기준으로는 적용 대상이 없습니다.

**Q15. 비식별 실패 영상은 어떻게 처리하나?**
A. 실패 상태로 표시한 뒤 재시도 큐로 보냅니다. 이때 **원본은 절대 삭제하지 않습니다**(NFR-004).
외부 서비스 장애가 파이프라인 전면 중단으로 번지지 않게 막는 것이 원칙입니다.

**Q16. 데이터베이스는 어떤 스키마 구조인가?**
A. 저작도구 전용 스키마(프로젝트상 `klid_at`, PostgreSQL)에 **저작도구 전용 테이블을 소유**하고,
관제서버 소유 **공유 테이블은 참조검증만**(읽기 위주) 수행합니다. 스케줄러 잡도 DB에 저장합니다(§1 `DB`,
RQ-DAR-01-01). 공유 스키마 변경 충돌은 변경 전 선승인·변경 알림 프로세스로 완화합니다.

**Q17. 파일 스토리지에 "2벌"이란 무엇인가?**
A. 원본 영상/프레임과 비식별 영상/프레임을 **별도 경로에 동시 저장**한 것입니다(§1 `FS`, §2 `STORE`,
NFR-003). 원본과 비식별본이 서로 다른 경로에 공존하여 정합성과 추적성을 유지합니다.

**Q18. 라벨 버전관리는 언제·어떻게 이루어지나?**
A. **검수 승인(APPROVED) 시점**에 라벨 전체를 스냅샷으로 저장하며, 페이로드 해시를 버전 식별자로
삼습니다(RQ-QUR-03-01). 검수 승인 데이터만 학습데이터로 확정되고, 검수 이력·승인 버전을 시스템에서
추적할 수 있습니다.

**Q19. 접근성(WCAG)은 어디에 적용되나?**
A. 포털(외부 채널)에 적용됩니다. 반응형 웹(PC/태블릿/모바일) + WCAG 2.1 AA 준수이며, 시맨틱 마크업·
대체 텍스트·키보드 접근·색상 외 정보 전달 등을 자동 점검 + 수동 검수로 확인합니다(NFR-006).

**Q20. 로그인 실패 제한·동시 로그인 차단은 저작도구가 하나?**
A. 아닙니다. 그것은 인증 발급 주체(관제/포털)의 책임이고, **저작도구는 토큰 검증만** 담당합니다
(RQ-SER-01-01). 만료·위조 토큰은 401로 거부하고 상위 시스템 로그인으로 유도합니다.

**Q21. "품질목표 수준"은 무엇을 위한 항목인가?**
A. 각 요구사항이 충족되었는지 판정할 정량/정성 측정 기준입니다(예: 처리율 ≥ 1건/분, 응답 ≤ 3초,
CPU·메모리 ≤ 80%, 노출 0건, 수집률 100%). v1.2 정합 검토에서 각 구현방안에 명시했습니다.

**Q22. 이 문서가 규정하지 않는 것(범위 외)은?**
A. 외부 VLM 서비스·생성형 증강 AI·영상 합성 모델·데이터마트 **본체**는 저작도구 범위 외입니다(§3 마무리).
저작도구는 VLM 시계열 호출 연동, 증강 결과 수신·검수, 데이터마트 적재용 조회 인터페이스 제공까지만 담당합니다.

## 5. 다른 산출물과의 연계

D5는 CBD 설계 산출물 체계의 최상위 청사진이므로, 하위·인접 산출물과 다음과 같이 맞물립니다.
(아래 D 번호별 성격은 CBD 표준 문서 체계에 근거하며, 실제 연결 방향을 D5 내용 기준으로 설명합니다.)

- **R2(요구사항 정의서 = 발주처 엑셀)** — D5 §3의 `RQ-*` ID(PER/SER/COR/DAR/QUR)와 `NFR-001~007`이
  이 정의서로부터 추적됩니다. v1.4·v1.5 개정이 바로 이 R2와의 **1:1 ID 정합**을 맞춘 작업입니다.
  §3의 각 표 "요구사항 ID"는 R2의 요구사항을 가리키는 앵커입니다.

- **D1(클래스 설계서 등)** — D5 §1의 업무 계층 컴포넌트(컨트롤러·서비스·리포지토리·배치·공통 인프라·
  연동 클라이언트)가 D1 이하에서 실제 클래스로 상세화됩니다. D5는 "어떤 계층·컴포넌트가 있는가"를,
  D1은 "그 컴포넌트가 어떤 클래스로 구성되는가"를 규정합니다.

- **D2·D3(컴포넌트/인터페이스·시퀀스 설계 등)** — D5 §1·§2의 커넥션(REST/JSON, 프로세스 경계 호출,
  연동 클라이언트, 콜백 수신)과 배치 파이프라인 흐름(비식별→마킹→...→트랙보간)이 D2/D3에서
  인터페이스 규격·상호작용 시퀀스로 구체화됩니다. §2의 타임아웃 값(추론 60초·시계열 45초)·
  단방향 통지·상세 조회 호출 등이 시퀀스 설계의 입력이 됩니다.

- **D8(ERD)** — D5 §1의 `DB`(저작도구 전용 테이블 소유 + 공유 테이블 참조검증 + 스케줄러 잡 저장)와
  §2의 "저작도구 전용 스키마", RQ-DAR-01-01(데이터 표준 준수)이 D8 ERD에서 실제 엔티티·관계로
  구현됩니다. 공유 테이블(관제서버 소유)은 참조검증 대상이라 ERD에서 별도 취급됩니다
  (프로젝트 규칙상 MNG_* 공유 테이블은 D8/D9 산출물 비대상).

- **D9(DB 설계서)** — RQ-DAR-01-01의 "범정부 데이터 표준사전 정합·코드표준화·라벨링 방식별 포맷 표준",
  NFR-002·003의 누적 규모(이미지 10만·영상 5,000) 및 인덱스·페이징 설계, RQ-PER-05-03의 듀얼
  커넥션 풀, Quartz `QRTZ_*` 잡 저장 등이 D9에서 물리 테이블·컬럼·인덱스·커넥션 설정으로 상세화됩니다.

- **D10·D11** — CBD 체계상 배포·프로그램/단위(모듈) 설계 계열에 해당합니다. D5 §2의 배포 토폴로지
  (단일 인스턴스·Quartz 클러스터링 옵션·추론 서버 수평 확장), §1의 배치 파이프라인 단계 구성이
  D10/D11에서 배포 단위·프로그램 목록으로 전개됩니다.
  *(D10·D11 각각의 정확한 표제는 원문 D5에 명시되지 않았으므로, 위 설명은 D5가 규정한 배포·모듈
  관점이 하위 설계로 이어지는 방향에 한정합니다.)*

**연계의 큰 그림:** R2(요구) → **D5(아키텍처 청사진)** → D1·D2·D3(컴포넌트·인터페이스·시퀀스) →
