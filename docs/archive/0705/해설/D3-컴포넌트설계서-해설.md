# D3 컴포넌트 설계서 — 종합 해설 (스터디 가이드)

> 이 문서는 `docs/0705/D3-컴포넌트설계서.md` 원문을 처음 접하는 사람이 "어떤 질문을 받아도 답할 수 있도록" 정독·해설한 학습 자료입니다.
> 원문에 실제로 기재된 내용만을 근거로 하며, 원문에 없는 사항은 "원문에 명시되지 않음"으로 표기합니다.
> 대상 시스템: **AI 기반 지방정부 CCTV 관제지원시스템(2차) — 학습데이터 저작도구**(Spring Boot 백엔드 + ai-server(YOLO/SAM2/VLM) + React 프론트엔드 모노레포).

---

## 1. 이 문서는 무엇인가

### 1.1 한 줄 정의
D3 컴포넌트 설계서는 **"설계 클래스들을 C&V(공통성·변경성, Commonality & Variability) 기준으로 그룹핑하여 컴포넌트를 식별하고, 각 컴포넌트의 내부 클래스와 인터페이스(제공/요구)를 명세한 산출물"**입니다. 즉, 개별 클래스(D1)를 한 단계 위로 묶어 **재사용·배포·의존의 단위인 "컴포넌트"**를 정의하고, 컴포넌트 사이가 어떤 인터페이스로 맞물리는지를 규정합니다.

### 1.2 작성 목적과 방법 (원문 근거)
- **작성 목적**(원문 §작성 목적): 설계 클래스 모형에서 도출한 클래스들을 **C&V 기준에 따라 그룹핑**하여 컴포넌트를 식별하고, **패키지도(컴포넌트 구조도)**를 작성하며, 식별한 컴포넌트의 **내부 클래스 및 인터페이스**를 명세한다.
- **작성 방법**(원문 §작성 방법): ① 클래스를 그룹핑해 컴포넌트 패키지도를 그린다 → ② 컴포넌트 목록을 만든다 → ③ 각 컴포넌트의 내부 클래스를 명세한다 → ④ 인터페이스는 **사용자에게 제공하는 오퍼레이션별로** 상세 명세한다.

### 1.3 CBD 산출물 체계에서 컴포넌트 설계의 위치
이 프로젝트는 CBD(Component Based Development) 방법론의 산출물 체계(R·D 시리즈)를 따릅니다. D3는 그 중 설계(Design) 단계 산출물이며, 위·아래 산출물과 다음과 같이 연결됩니다.

```
요구사항(R2) → 유스케이스(UC) → D1 클래스설계 → D3 컴포넌트설계 → D5 아키텍처 → D8 ERD → D9 DB설계
                                     ↑ 개별 클래스        ↑ 클래스를 묶은 컴포넌트
```

- **입력**: D1 클래스설계서의 설계 클래스 목록(KLID-AT-DC-NNN), 유스케이스 명세(KLID-AT-UC-NNN).
- **출력**: 컴포넌트 목록·구조도·명세, 인터페이스 명세 — D5 아키텍처설계서(계층·배치)와 구현(패키지 구조)의 기준.

### 1.4 D1 클래스설계서와의 차이 (자주 헷갈리는 지점)
| 구분 | D1 클래스설계서 | D3 컴포넌트설계서 |
|------|----------------|-------------------|
| 다루는 단위 | **개별 클래스**(속성·오퍼레이션·관계) | **클래스를 묶은 컴포넌트**(재사용·의존·인터페이스 단위) |
| 관점 | 정적 구조·상세 설계 | 유스케이스 실현 단위의 조립·경계 |
| ID 체계 | 설계 클래스 ID `KLID-AT-DC-NNN` | 컴포넌트 ID `KLID-AT-CO-NNN`, 인터페이스 ID `KLID-AT-IF-NNN` |
| 클래스 ID의 처리 | 최초 정의처(진실원) | **D1의 DC-ID를 그대로 재사용**(별도 채번 없음) — "내부 클래스"로 교차 참조 |

> **핵심**: D3의 "내부 클래스 ID(IC)"는 **D1의 설계 클래스 ID(KLID-AT-DC-NNN)와 완전히 동일한 체계**입니다(원문 헤더 「내부 클래스 ID 일관성(Critical)」). 컴포넌트별로 클래스에 새 번호를 붙이지 않으며, 같은 클래스는 D1·D3·D8 전반에서 같은 ID를 갖습니다. 이것이 D3를 이해하는 첫 번째 열쇠입니다.

### 1.5 컴포넌트 도출 원칙 (원문 헤더의 5대 규칙)
원문 헤더에 명시된 도출 원칙을 반드시 기억해야 합니다.

1. **UC ↔ CO 1:1**: 컴포넌트는 유스케이스 실현 단위로 도출하며, **유스케이스 1건당 컴포넌트 1건**입니다. 활성 유스케이스 18건 → 컴포넌트 18건.
2. **번호 정렬**: 컴포넌트 번호는 실현 유스케이스 번호와 정렬합니다(예: `KLID-AT-CO-003` ↔ `KLID-AT-UC-003`).
3. **결번 동조**: 유스케이스 결번(UC-012/014/015/017/020)에 맞춰 **컴포넌트도 CO-012/014/015/017/020을 결번 처리**합니다(범위 외·비활성 유스케이스).
4. **도메인 단위로 묶지 않음**: 컴포넌트를 도메인별로 뭉뚱그리지 않고 유스케이스 실현 단위로 나눕니다.
5. **공통 기반은 별도 컴포넌트로 만들지 않음**: 공통 기반 요소는 독립 컴포넌트로 식별하지 않고, 그것을 사용하는 컴포넌트의 **내부 클래스로 동일 DC-ID를 교차 참조**(중복 정의 금지)합니다.

### 1.6 문서의 물리적 구조 (원문 목차)
원문은 다음 순서로 구성됩니다.
- **§0 헤더/제·개정 이력** — ID 표기 규칙, 도출 원칙, IC 일관성 규칙.
- **§1 컴포넌트 구조도** — 18개 컴포넌트별 Mermaid 다이어그램(계층·의존).
- **§2 컴포넌트 목록** — 18개 컴포넌트의 ID·명·개요·관련 UC 표.
- **§3 컴포넌트 명세** — 18개 컴포넌트별 (내부 클래스 표 + 인터페이스 클래스 표).
- **§4 인터페이스 명세** — 21개 인터페이스(IF-001~021)를 **오퍼레이션 개수만큼** 상세 명세.
- **§항목 설명** — 각 표 항목의 기입 규칙.
- **§부록** — 결번 사유, 빈 셀 처리, IC 체계 설명.

## 2. 섹션별 상세 해설

### 2.0 컴포넌트 구조도의 표기 규약 (§1 서두)
각 컴포넌트 구조도는 **Mermaid flowchart**로 그리며, 다음 규약을 따릅니다(원문 §1 서두).
- **박스(«component»)** = 컴포넌트, **점선 화살표** = 컴포넌트 간 의존(dependency).
- 시스템은 **계층으로 구분**해 표시: **Biz Logic Layer**(업무 로직 컴포넌트)와 **Integration Layer**(외부 연동 컴포넌트).
- **액터**(검수자·라벨링 작업자)와 **외부 시스템**(생성형 AI·비식별 솔루션·VLM·관제서버·AI 추론)은 **외부 박스**로 표기.
- 컴포넌트의 **내부 클래스는 구조도에 분해해 그리지 않고**, §3 「내부 클래스 표」에 텍스트로 기재.

> 이 프로젝트 맥락에서 Integration Layer의 컴포넌트들(외부 증강 연동, AI 추론 연동, 관제 통지 연동, 외부 비식별 연동, 시계열 결과 수신 채널)은 CLAUDE.md에서 언급된 **`common.client.*` 계열 클라이언트**(ExternalAugmentClient / AiServerClient / ControlNotifyClient / DeidentifyClient / VlmClient)에 대응합니다. Resilience4j로 타임아웃·재시도·서킷 브레이커가 적용되는 지점입니다.

---

이제 18개 컴포넌트를 원문 순서대로 하나씩 해설합니다. 각 컴포넌트는 **① 책임(개요) ② 내부 클래스 ③ 제공/요구 인터페이스 ④ 의존·상호작용**으로 정리합니다.

### 2.1 KLID-AT-CO-001 — 증강 생성 요청 컴포넌트 (UC-001)
- **책임**: 검수완료된 원본 영상과 증강 종류(겨울·야간·강수 = WINTER/NIGHT/RAIN)를 **외부 생성형 AI 서비스에 위탁 요청**하고, 증강 작업을 대기 상태로 등록하며 **멱등키를 발급**한다.
- **내부 클래스**: `AugmentController`(DC-120, 진입점), `AugmentRequestService`(DC-121, 검수 상태 검증·위탁 처리), `ExternalAugmentClient`(DC-126, 외부 위탁 연동 계약), `LsDataAug`(DC-123, 증강 작업 등록·상태), `LsRawDataStatus`(DC-104, 원본 작업·검수 상태).
- **제공(Serviced) 인터페이스**: IF-001 증강 요청 인터페이스 / 증강 생성 위탁 요청.
- **요구(Required) 인터페이스**: IF-002 외부 증강 연동 인터페이스 / 외부 증강 생성 위탁.
- **상호작용**: 액터 검수자 → CO-001 → (위탁 요청) → Integration Layer의 **외부 증강 연동** → 외부 **생성형AI 서비스**. 증강 결과가 돌아오는 흐름은 별개 컴포넌트 CO-002가 담당한다(요청/수신 분리).

### 2.2 KLID-AT-CO-002 — 증강 결과 수신·등록 컴포넌트 (UC-002)
- **책임**: 외부가 전송한 증강 결과를 **멱등 처리로 수신**해 **새 영상(RAW_SN)으로 등록**하고, 원본 라벨·메타를 **좌표 그대로 복사**하며 **원본↔증강 라벨 매핑을 기록**한다(증강 = 새 영상, 해상도 동일이므로 좌표 복사).
- **내부 클래스**: `AugmentResultController`(DC-127), `AugmentResultService`(DC-128, 멱등 확인·등록·복사), `LsDataRaw`(DC-012, 새 영상 생성 + 원본을 부모로 연결 = PARENT_RAW_SN), `LsDataLbl`(DC-073, 복사 라벨), `LsDataAugLblMap`(DC-124, 원본↔증강 라벨 매핑), `LsDataAug`(DC-123, 증강 작업 상태).
- **제공 인터페이스**: IF-003 증강 결과 수신 인터페이스 / 증강 결과 수신·등록.
- **요구 인터페이스**: 없음(수신 전용).
- **상호작용**: 외부 **생성형AI 서비스** → Integration Layer의 **외부 증강 결과 수신 채널** → (결과 전달) → CO-002. 등록된 새 영상은 미검수(PENDING)로 시작.

### 2.3 KLID-AT-CO-003 — 해상도 변경 컴포넌트 (UC-003)
- **책임**: 영상을 **원본보다 낮은 표준 하위 해상도**(RES_1080P/720P/480P 화이트리스트)로 다운스케일해 **프레임 이미지셋만 제공**하고 변경 이력 1건을 기록한다. **업스케일은 거부(400)**, **영상·라벨 좌표는 생성·제공하지 않음**(SFR-06-03 — 증강이 아닌 저작도구 직접 수행).
- **내부 클래스**: `VideoController`(DC-010, 영상 조회·스트리밍·해상도 변경 진입점), `VideoResolutionService`(DC-018, 업스케일 거부 검증·다운스케일), `Java2DImageResizer`(DC-019, 프레임 다운스케일·크기 측정), `VideoResolutionPersister`(DC-020, 변경 이력 기록), `LsResolutionExport`(DC-017, 이력), `LsDataRaw`(DC-012, 원본 정보).
- **제공 인터페이스**: IF-004 해상도 변경 인터페이스 / 표준 하위 해상도 변경 요청.
- **요구 인터페이스**: 없음(외부 연동 없이 내부 처리).
- **상호작용**: 검수자 → CO-003(단독). Integration Layer 없음.

### 2.4 KLID-AT-CO-004 — 객체 자동 추적 컴포넌트 (UC-004)
- **책임**: 시작 프레임에서 지정된 객체를 **AI 추론(SAM2 Track)으로 후속 프레임에 추적·전파**하고, 좌표 범위 검증·폴리곤 단순화 후 **자동 라벨로 저장**하며 빈 프레임을 **보간**한다. 본인 미배정 프레임 접근은 차단(수평 권한 상승 방어).
- **내부 클래스**: `LabelController`(DC-070), `Sam2TrackService`(DC-075, 추적 오케스트레이션), `LabelAccessGuard`(DC-003, 본인 배정 검증), `AiServerClient`(DC-005, AI 추론 연동 계약), `LsDataLbl`(DC-073, 자동 라벨), `LsDataLblAiInfo`(DC-078, 신뢰도), `SystemConfigService`(DC-004, 정밀도 설정 조회).
- **제공 인터페이스**: IF-005 객체 추적 인터페이스 / 객체 자동 추적 요청.
- **요구 인터페이스**: IF-006 AI 추론 연동 인터페이스 / 객체 추적 추론 요청.
- **상호작용**: 라벨링 작업자 → CO-004 → **(정밀도 설정 조회) → CO-006** + **(추론 요청) → AI 추론 연동 → 내부 AI 추론 서비스(ai-server)**. 즉 CO-004는 정밀도(CO-006)와 AI추론(ai-server) 두 방향에 의존한다.

### 2.5 KLID-AT-CO-005 — 객체 외곽 경계 자동 밀착 컴포넌트 (UC-005)
- **책임**: **클릭(포인트) 또는 박스 시드**를 AI 추론에 전달해 **외곽 경계 폴리곤과 신뢰도**를 산출(SAM2 Segment)하고, 실측 해상도 범위 검증·폴리곤 단순화 후 캔버스에 밀착. **포인트·박스 중 하나만 허용**.
- **내부 클래스**: `LabelController`(DC-070), `Sam2SegmentService`(DC-076, 분할 오케스트레이션), `LabelAccessGuard`(DC-003), `AiServerClient`(DC-005), `SystemConfigService`(DC-004).
- **제공 인터페이스**: IF-007 외곽 분할 인터페이스 / 외곽 경계 분할 요청.
- **요구 인터페이스**: IF-006 AI 추론 연동 인터페이스 / 외곽 경계 분할 추론 요청.
- **상호작용**: CO-004와 구조가 매우 유사(작업자 → CO-005 → CO-006 정밀도 조회 + AI 추론 연동). CO-004와 CO-005는 **같은 AI 추론 연동 인터페이스(IF-006)를 공유**하되 오퍼레이션이 다르다(추적 vs 분할).

### 2.6 KLID-AT-CO-006 — 라벨링 정밀도 조절 컴포넌트 (UC-006)

- **내부 클래스**: `LabelController`(DC-070), `LabelService`(DC-071, 작업본 영속), `LabelAccessGuard`(DC-003), `LsDataLbl`(DC-073), `LsDataLblAttrVal`(DC-074, 객체별 속성값), `LsLabel`(DC-072, 라벨 마스터 코드), `LabelAttrValueService`(DC-077, 속성값 저장).
- **제공 인터페이스**: IF-018 라벨 편집 인터페이스 / **프레임 라벨 조회** + **라벨 일괄 임시저장**.
- **요구 인터페이스**: 없음.
- **상호작용**: 라벨링 작업자 → CO-021(단독). CO-004/005와 `LabelController`(DC-070)·`LsDataLbl`(DC-073)를 공유하지만, CO-021은 AI 추론이 아닌 **수동 편집·임시저장** 담당.

### 2.17 KLID-AT-CO-022 — VLM 시계열 메타 검토 컴포넌트 (UC-022)
- **책임**: 외부 시계열 분석(VLM) 결과를 **멱등 수신해 메타로 적재**하고 **검수큐에 자동 진입**시킨다. 검수자가 메타를 **검토·수정·승인·반려**하여 **승인된 메타만 학습데이터에 노출**.
- **내부 클래스**: `VlmResultController`(DC-113, 결과 수신 진입점), `VlmResultService`(DC-114, 멱등 확인·적재·검수큐 진입), `MetaController`(DC-110, 검토·수정·검수 진입점), `MetaService`(DC-111, 수정·상태 전이), `LsDataMetaReview`(DC-112, 검수큐 항목), `LsDataMeta`(DC-044, 시계열 메타).
- **제공 인터페이스**: IF-019 시계열 결과 수신 인터페이스 / 시계열 분석 결과 수신, IF-020 메타 검토 인터페이스 / **메타 검토·수정** + **메타 승인·반려**.
- **요구 인터페이스**: 없음(수신은 외부→저작도구 방향, 구조도상 VLM -.-> 시계열 결과 수신 채널 -.결과 적재.-> CO-022).
- **상호작용**: 외부 **VLM 서비스** → 시계열 결과 수신 채널 → CO-022(적재·검수큐) ← 검수자(검토·수정·승인). CLAUDE.md의 "VLM 콜백 `POST /v1/vlm/result` → VlmResultService 적재 + LS_DATA_META_REVIEW 진입"에 대응.

### 2.18 KLID-AT-CO-023 — 검수 승인·반려 컴포넌트 (UC-023)
- **책임**: 작업자가 제출한 **영상 단위 작업**을 상태 전이 검증 하에 검수자가 **승인(작업 완료) 또는 사유 입력 반려**한다. **승인 시 검수 승인 스냅샷 생성과 완료 통지를 연계**.
- **내부 클래스**: `ReviewController`(DC-100, 제출·승인·반려 진입점), `ReviewService`(DC-101, 검수 처리·후속 연계 오케스트레이션), `ReviewStateMachine`(DC-102, 상태 전이 유효성 검증), `LsDataIssue`(DC-103, 반려 사유·이슈), `LsRawDataStatus`(DC-104, 작업·검수 상태), `VersionService`(DC-091, 승인 스냅샷 생성), `ControlNotifyService`(DC-130, 완료 통지 연계).
- **제공 인터페이스**: IF-021 검수 처리 인터페이스 / **작업 검수 제출** + **검수 승인** + **검수 반려**(오퍼레이션 3개).
- **요구 인터페이스**: 원문 표에는 별도 IF 미기재. 구조도에서 **CO-007(승인 시 스냅샷)·CO-009(완료 통지)에 대한 의존**.
- **상호작용**: 라벨링 작업자·검수자 → CO-023 → **(승인 시 스냅샷 생성) → CO-007** + **(완료 통지 발행) → CO-009**. `LsRawDataStatus.dataSttsCd`의 `COMPLETED` 전이는 **오직 이 컴포넌트의 승인에서만** 일어난다(CLAUDE.md 상태머신 규칙).

### 2.19 §4 인터페이스 명세 (IF-001 ~ IF-021)
§4는 각 인터페이스의 **오퍼레이션별로** 「사전조건 / 사후조건 / 파라미터 / 반환값」을 규정합니다(원문 §4 서두: "인터페이스별로 그 오퍼레이션 개수만큼 반복 작성"). 21개 인터페이스가 있으나 **오퍼레이션은 그보다 많습니다**(한 IF에 여러 오퍼레이션). 예를 들어:
- IF-002는 오퍼레이션 2개(외부 증강 생성 위탁, 활용 결정 외부 동기화).
- IF-006은 2개(객체 추적 추론 요청, 외곽 경계 분할 추론 요청) — CO-004·CO-005가 공유.
- IF-008은 2개(정밀도 설정 변경, 비식별 옵션 설정 변경) — CO-006·CO-013이 공유.
- IF-010은 2개(버전 차이 비교, 버전 복구).
- IF-011은 2개(완료 통지 발행, 수정 통지 발행) — 둘 다 Required.
- IF-012·IF-015·IF-018·IF-020은 각 2개, IF-014·IF-021은 각 3개.

**대표 예시 — IF-001 증강 생성 위탁 요청**:
- 사전조건: 검수자로 인증되어 있고 원본 영상이 검수완료 상태.
- 사후조건: 증강 작업이 대기 상태로 등록되고 멱등키 발급, 외부 위탁.
- 파라미터: 증강 대상 원본 식별자, 증강 종류(겨울·야간·강수), 요청 주체.
- 반환값: 증강 요청 접수 결과.

**대표 예시 — IF-016 학습용 영상 주기 적재**(배치형 인터페이스):
- 파라미터·반환값이 **모두 "없음"** — 주기 배치 트리거이기 때문(§부록 "빈 셀"에서 이 점을 명시).

> §4의 명세는 **업무 의미 단위**로 파라미터·반환값을 기술합니다(자료형이 아닌 "증강 종류", "요청 주체" 같은 도메인 용어). 이는 CBD 인터페이스 명세의 특성으로, 구현 시그니처(D1·코드)와 1:1로 대응하되 추상 수준이 한 단계 높습니다.

### 2.20 §항목 설명 / §부록
- **§항목 설명**: 구조도·목록·명세·인터페이스 각 표의 칸을 어떻게 채우는지 규정. 특히 "내부 클래스 ID는 설계 클래스 ID(D1)와 동일 체계로 일관성을 가진다"를 재확인.
- **§부록 — 데이터 부재·결번 사유**:
  - **컴포넌트 결번**: CO-012/014/015/017/020은 실현 UC가 범위 외(비활성)여서 결번. UC↔CO 1:1 정렬 원칙에 따라 동조 결번.
  - **빈 셀**: 없음(모든 셀 채움). IF-016만 파라미터·반환값을 "없음"으로 표기.
  - **내부 클래스 ID 체계**: D1 §1 설계 클래스 목록의 DC-ID를 동일 번호로 재사용(별개 채번 없음).

## 3. 핵심 용어

| 용어 | 정의 (이 문서 맥락) |
|------|---------------------|
| **컴포넌트(Component)** | 여러 설계 클래스를 C&V 기준으로 묶은 재사용·배포·의존의 단위. 원문에서는 **유스케이스 1건당 1개**(UC↔CO 1:1)로 도출. ID: `KLID-AT-CO-NNN`. |
| **C&V(공통성·변경성)** | Commonality & Variability. 함께 변하고 함께 재사용되는 클래스들을 같은 컴포넌트로 묶는 컴포넌트 식별 기준(원문 §작성 목적). |
| **내부 클래스(IC)** | 컴포넌트에 속한 설계 클래스. **D1의 설계 클래스 ID(KLID-AT-DC-NNN)를 그대로 사용**하며, 여러 컴포넌트가 같은 클래스를 재사용하면 동일 DC-ID를 교차 참조(중복 정의 금지). |
| **인터페이스(Interface)** | 컴포넌트가 외부에 노출하거나 외부에 요구하는 계약. ID: `KLID-AT-IF-NNN`. 하나의 인터페이스가 여러 **오퍼레이션**을 가질 수 있음. |
| **제공 인터페이스(Provided / Serviced)** | 해당 컴포넌트가 **외부에 제공**하는 서비스(그 컴포넌트가 구현). 원문 표기는 "Serviced". UML의 lollipop(제공)에 해당. |
| **요구 인터페이스(Required)** | 해당 컴포넌트가 **동작을 위해 외부에 요구**하는 서비스(다른 컴포넌트·외부 시스템이 구현). UML의 socket(요구)에 해당. 예: CO-001의 외부 증강 위탁, CO-009의 관제 통지. |
| **오퍼레이션(Operation)** | 인터페이스가 노출하는 개별 기능 단위(메서드에 대응). §4는 오퍼레이션마다 사전/사후조건·파라미터·반환값을 명세. |
| **의존(Dependency)** | 컴포넌트가 다른 컴포넌트의 인터페이스를 사용하는 방향 관계. 구조도의 **점선 화살표**. |
| **Biz Logic Layer** | 업무 로직 컴포넌트가 위치하는 계층(구조도). |
| **Integration Layer** | 외부 시스템 연동 컴포넌트(각종 `*Client`)가 위치하는 계층. Resilience4j 적용 지점. |
| **액터(Actor)** | 시스템 외부의 사용자·트리거. 이 문서에서는 검수자(REVIEWER)·라벨링 작업자(WORKER), 또는 "검수 완료·수정 이벤트"·"비식별 위탁 단계" 같은 비인격 트리거. |
| **외부 시스템** | 생성형AI 서비스, 비식별 솔루션(KPST), VLM 서비스, 관제서버, (내부) AI 추론 서비스(ai-server). |
| **멱등(Idempotency)** | 같은 요청이 여러 번 와도 결과가 1회로 유지되도록 멱등키·요청 ID로 처리(증강 위탁/수신, 통지 발행, 시계열 수신 등에서 반복 등장). |
| **디바운스(Debounce)** | 짧은 시간·같은 트랜잭션 내 다수 변경을 **영상 1건 1회 통지**로 집계(ControlNotifyDebouncer, DC-132). |
| **결번(缺番)** | UC-012/014/015/017/020이 범위 외라서 대응 컴포넌트 번호도 비워둔 것. |

## 4. 예상 질문 Q&A (18문)

**Q1. 이 문서(D3)의 한 문장 목적은?**
A. 설계 클래스들을 C&V 기준으로 묶어 컴포넌트를 식별하고, 각 컴포넌트의 내부 클래스·제공/요구 인터페이스를 명세하여 조립 단위와 경계를 규정하는 것입니다.

**Q2. 컴포넌트는 어떤 기준으로 도출했나? 왜 도메인 단위가 아닌가?**
A. **유스케이스 실현 단위(UC↔CO 1:1)**로 도출했습니다. 활성 유스케이스 18건 → 컴포넌트 18건. 원문 도출 원칙에서 "도메인 단위로 컴포넌트를 묶지 않는다"고 명시합니다. 유스케이스별로 나누면 요구사항 추적성이 명확하고, 변경이 발생한 유스케이스만 국소적으로 영향받습니다.

**Q3. 컴포넌트가 18개인데 번호는 왜 CO-023까지 있나?**
A. UC-012/014/015/017/020이 범위 외(비활성)라 **CO-012/014/015/017/020을 결번 처리**했기 때문입니다(§부록). UC↔CO 1:1 정렬을 유지하려고 번호를 당기지 않고 비워뒀습니다.

**Q4. 내부 클래스 ID(IC)와 D1의 설계 클래스 ID(DC)는 무슨 관계인가?**
A. **완전히 동일한 ID 체계**입니다. D3는 클래스에 새 번호를 붙이지 않고 D1의 `KLID-AT-DC-NNN`을 그대로 재사용합니다. 같은 클래스는 D1·D3·D8에서 같은 ID를 갖습니다(원문 「IC 일관성 Critical」·§부록).

**Q5. 여러 컴포넌트가 같은 클래스를 쓰면 어떻게 표기하나?**
A. **동일 DC-ID를 교차 참조**하고 중복 정의하지 않습니다. 예: `SystemConfigService`(DC-004)는 CO-004/005/006/013에, `LabelAccessGuard`(DC-003)는 CO-004/005/008/016/021에, `VersionService`(DC-091)는 CO-007/008/016/023에 동일 ID로 등장합니다. 공통 기반 요소는 별도 컴포넌트로 만들지 않는 원칙(원문)입니다.

**Q6. 제공(Serviced)과 요구(Required) 인터페이스의 차이는?**
A. **제공**은 그 컴포넌트가 외부에 노출하는 서비스(구현 주체가 자신), **요구**는 동작을 위해 외부에 의존하는 서비스(구현 주체가 다른 컴포넌트·외부 시스템)입니다. 예: CO-001은 IF-001(증강 요청)을 **제공**하고, IF-002(외부 증강 위탁)를 **요구**합니다.

**Q7. 외부 시스템과 연동하는 컴포넌트는 무엇이고 어떻게 격리했나?**
A. CO-001/002/010(생성형AI), CO-011(비식별 솔루션), CO-009(관제서버), CO-022(VLM), CO-004/005(내부 ai-server AI 추론)입니다. 모두 구조도의 **Integration Layer**에 연동 컴포넌트(`ExternalAugmentClient`·`KpstDeidentifyClient`·`ControlNotifyClient`·`AiServerClient` 등)를 두어 업무 로직과 분리했습니다. 이 계층이 CLAUDE.md의 Resilience4j(타임아웃·재시도·서킷 브레이커) 적용 지점입니다.

**Q8. CO-004와 CO-005는 왜 따로 있나? 거의 같아 보이는데?**
A. 각각 UC-004(객체 자동 추적=SAM2 Track)와 UC-005(외곽 경계 자동 밀착=SAM2 Segment)를 실현하는 **다른 유스케이스**이기 때문입니다(UC↔CO 1:1). 구조는 비슷하고 **같은 AI 추론 연동 인터페이스(IF-006)를 공유**하되 오퍼레이션이 다릅니다(추적 추론 vs 분할 추론). 둘 다 CO-006(정밀도)과 ai-server에 의존합니다.

**Q9. CO-004/005가 CO-006(정밀도)에 의존하는 방향은?**
A. **CO-004·CO-005 → CO-006**(정밀도 설정 조회) 방향입니다. CO-006은 설정을 제공하는 쪽, CO-004/005는 소비하는 쪽입니다. 설정 조회 실패 시 CO-006이 기본값으로 안전 폴백합니다(CLAUDE.md의 TTL 60s Caffeine 캐시와 연결).

**Q10. 버전 저장(CO-007)과 버전 비교·복구(CO-008)를 왜 분리했나?**
A. 유스케이스가 다릅니다(UC-007 저장/이력 vs UC-008 비교/복구). 저장은 **검수 승인 시점**에 CO-023이 트리거하고, 비교·복구는 사용자가 직접 실행합니다. 다만 두 컴포넌트는 `VersionService`(DC-091)·`LsLabelVersion`(DC-092)을 공유해 스냅샷 데이터 모델을 일관되게 씁니다.

**Q11. 라벨 임시저장(CO-021)과 버전 스냅샷(CO-007)은 어떻게 다른가?**
A. CLAUDE.md의 **2계층 분리**를 컴포넌트로 나눈 것입니다. CO-021은 작업 중 작업본을 `LsDataLbl`에 upsert(**버전 스냅샷 미생성**), CO-007은 **검수 승인 시점**에만 전체 스냅샷을 `LsLabelVersion`에 해시 식별해 저장합니다. 즉 "작업 임시저장 ≠ 학습데이터 버전".

**Q12. 검수 승인(CO-023) 한 번이 어떤 후속 컴포넌트를 연쇄 트리거하나?**
A. 승인 시 ① **CO-007**(검수 승인 스냅샷 생성)과 ② **CO-009**(완료 통지 발행)를 연계합니다. 상태 전이 `LsRawDataStatus.COMPLETED`는 오직 CO-023의 승인에서만 발생합니다(상태머신 `ReviewStateMachine` DC-102 검증).

**Q13. CO-009(통지)는 왜 제공 인터페이스가 없고 요구만 있나?**
A. CO-009는 액터의 요청을 받는 게 아니라 **"검수 완료·수정 이벤트"에 반응해 외부(관제서버)로 통지를 발행**하는 컴포넌트라, IF-011의 두 오퍼레이션(완료/수정 통지 발행)이 모두 **Required**입니다. 이벤트 리스너(DC-131) → 디바운서(DC-132) → 서비스(DC-130) → 클라이언트(DC-133) 구조입니다.

**Q14. 비식별(CO-011)은 콜백 방식인가 폴링 방식인가?**
A. **주기 폴링**입니다. IF-014 "진행 상태 조회" 오퍼레이션 개요에 "주기 폴링으로 조회(별도 결과 수신 콜백 미사용)"라고 명시되어 있고, 내부 클래스 `KpstDeidentPollJob`(DC-052)이 대기·진행중 건을 주기 폴링합니다.

**Q15. 영상 적재(CO-018)와 비식별(CO-011)의 관계는?**
A. CO-018이 관제 학습용 설정 영상을 주기 배치로 적재한 **직후 선두 비식별을 자동 트리거**해 CO-011로 연결합니다(`IngestDeidentifyBridge` DC-042 → `AsyncDeidentifyRunner` DC-041 → `DeidentifyStep` DC-034). 파이프라인 선두가 비식별이라는 CLAUDE.md 규칙의 컴포넌트 표현입니다.

**Q16. 마킹(CO-019)이 완료되면 무엇이 시작되나?**
A. 잔여 배치 파이프라인(**시계열 → 프레임추출 → 오토라벨링**)이 트리거됩니다. `MarkingCompletedEvent`(DC-063) → `MarkingBatchBridge`(DC-064) → `BatchOrchestrator`(DC-030) 흐름이며, 본인 배정·비식별 완료 영상만 허용합니다.

**Q17. 컴포넌트 간 결합도는 어떻게 관리됐나?**
A. ① 외부 연동을 Integration Layer로 격리(업무 로직과 외부 프로토콜 분리), ② 공통 클래스는 별도 컴포넌트가 아닌 내부 클래스 교차 참조로 공유(중복 없이 재사용), ③ 컴포넌트 간 협력은 **인터페이스(제공/요구)와 도메인 이벤트**(MarkingCompletedEvent, 검수 완료·수정 이벤트)로 느슨하게 연결. 이로써 유스케이스 단위 변경이 국소화됩니다.

**Q18. §4 인터페이스 명세의 파라미터가 자료형이 아니라 도메인 용어인 이유는?**
A. 컴포넌트 설계는 구현 시그니처보다 한 단계 추상적인 **계약** 수준을 다루기 때문입니다. "증강 종류(겨울·야간·강수)", "요청 주체"처럼 **업무 의미 단위**로 기술하고(원문 §항목 설명), 구체 자료형은 D1 클래스설계와 실제 코드에서 확정합니다.

## 5. 다른 산출물과의 연계

D3는 CBD 산출물 그래프의 **허브** 역할을 합니다. 각 산출물과의 연결은 다음과 같습니다(원문·프로젝트 규칙 근거).

### 5.1 R2 요구사항정의서
- 각 컴포넌트는 유스케이스(UC)를 실현하고, 유스케이스는 다시 요구사항(RQ-SFR-NN-NN)에 매핑됩니다. 예: CO-003 해상도 변경 ↔ **SFR-06-03**, 증강 3종(CO-001/002/010) ↔ **SFR-07**(WINTER/NIGHT/RAIN), 라벨링 정밀도·추적·밀착(CO-004/005/006) ↔ **SFR-08-01(VOS=추적+분할)**. D3의 컴포넌트 개요는 R2의 기능 요구를 조립 단위로 번역한 결과입니다.

### 5.2 D1 클래스설계서
- **가장 밀접**합니다. D3의 내부 클래스 ID(IC)는 **D1 §1 설계 클래스 목록의 KLID-AT-DC-NNN을 그대로 재사용**합니다(별개 채번 없음, §부록). D1은 각 클래스의 속성·오퍼레이션·관계를 정의하고, D3는 그 클래스들을 컴포넌트로 묶고 인터페이스로 경계를 그립니다. D3의 인터페이스 오퍼레이션은 D1의 Controller·Service 오퍼레이션과 대응합니다.

### 5.3 D2 UI 설계서
- 액터(검수자·라벨링 작업자)가 진입하는 컴포넌트의 제공 인터페이스는 D2의 화면·상호작용과 연결됩니다. 예: CO-021(라벨 편집·임시저장)·CO-019(이벤트 마킹)·CO-022(VLM 메타 검토)·CO-008(버전 비교·복구)은 각각 라벨링 캔버스(konva.js)·마킹 화면·검토 화면·버전 관리 화면 UI와 대응합니다. IF-018(프레임 라벨 조회/임시저장) 등이 화면 이벤트의 백엔드 계약입니다.

### 5.4 D5 아키텍처설계서
- D3의 **Biz Logic / Integration 2계층 구분**과 외부 시스템 경계는 D5의 아키텍처 계층·배치 다이어그램의 기초입니다. Integration Layer의 연동 컴포넌트(`*Client`)는 D5에서 Spring Boot ↔ ai-server(HTTP/WebClient), ↔ 외부 비식별/생성형AI/VLM/관제서버 연동 경계로 확장됩니다. 배치 파이프라인(CO-018·CO-019·CO-011)의 비동기·Quartz 흐름도 D5의 런타임 뷰와 연결됩니다.

### 5.5 D8 엔티티관계모형설계서(ERD)
- D3 내부 클래스 중 **엔티티 성격 클래스**(`LsDataRaw` DC-012, `LsDataLbl` DC-073, `LsLabelVersion` DC-092, `LsDataAug` DC-123, `LsDeidentProcLog` DC-053, `LsRawDataStatus` DC-104 등)는 D8의 테이블(LS_* / ERD)로 이어집니다. 원문에서 "동일 클래스는 D1·D3·D8 전반에서 같은 ID"라고 명시하므로, D3의 DC-ID로 D8의 대응 테이블을 역추적할 수 있습니다. 단 공유 MNG_* 테이블은 D8/D9 산출물 비대상(CLAUDE.md).

### 5.6 D9 DB설계서
- D8이 개념·논리 ERD라면 D9는 물리 테이블·컬럼 정의입니다. D3의 데이터 보유 내부 클래스(엔티티)가 D9의 실제 컬럼·타입·제약(PostgreSQL, `klid_at` 스키마, Flyway)으로 구체화됩니다. 예: CO-007의 `LsLabelVersion`은 `LABEL_PAYLOAD`·`VERSION_HASH`(SHA-256)·`SAVE_REASON` 컬럼으로, CO-011의 `LsDeidentProcLog`는 `DE_IDNTF_FILE_PATH_NM` 등으로 D9에서 정의됩니다.

### 5.7 D10·D11 (원문 명시 범위 밖)
- D3 원문에는 D10·D11의 구체 내용이 직접 등장하지 않아 **원문에 명시되지 않음**입니다. 일반적으로 CBD 체계에서 D10·D11은 프로그램/단위 설계(예: 프로그램 명세, 단위·컴포넌트 시험 관점)에 해당하며, D3의 컴포넌트·인터페이스 목록이 그 상세 설계와 시험 케이스 식별의 상위 기준이 됩니다. 정확한 D10·D11 정의는 해당 산출물 원문을 참조해야 합니다.

### 5.8 연계 요약도
```
R2 요구사항 ──매핑── UC 유스케이스 ──1:1── D3 컴포넌트(CO) ──인터페이스(IF)── D5 아키텍처(계층·연동)
                                          │
                          내부 클래스(IC=DC) ┼── D1 클래스설계(속성·오퍼레이션)
                                          │
                          엔티티 클래스(DC) ┼── D8 ERD ── D9 물리 DB설계
                                          │
                          진입 인터페이스 ──── D2 UI 설계(화면·상호작용)
```
