# D8 엔티티 관계 모형 설계서 — ERD 설명문

> 발표·검토 자리에서 D8의 ERD를 구두로 설명하기 위한 해설 문서.
> 원본: `docs/design-full/D8-엔티티관계모형설계서.md` (16 ERD · 45 엔티티 · v1.1, 전체 개발범위 통합본)

---

## 1. 한 문장 요약

> **D8은 학습데이터 저작도구가 직접 소유·구성하는 `LS_*` 전용 테이블 전수를, 작업 단위 식별자 두 개(영상 `RAW_SN` · 프레임 `SRC_SN`)를 앵커로 16개 도메인 ERD로 나눠 논리 모델링한 산출물이다.** 관제서버가 소유한 공유 스키마(`MNG_*`)는 읽기 참조만 하므로 물리 설계 대상에서 빼고 §3에 참조 사실만 남긴다.

## 2. 산출물의 위치 (왜 D8인가)

CBD 설계 흐름에서 D8은 **논리 데이터 모델** 단계다.

- **R1/R2/R3** (요구사항·유스케이스·추적표) → 무엇을 만들지
- **D1** 클래스 설계서 → 객체 모델 (설계 클래스)
- **D8 엔티티 관계 모형** → **논리 데이터 모델 (엔티티·관계·속성)** ← 지금 여기
- **D9** 데이터베이스 설계서 → 물리 모델 (DBMS 타입·길이·인덱스·제약·DDL)

즉 D8은 "D1 클래스 ↔ D9 물리 테이블"을 잇는 **논리 계층**이다. 그래서 각 엔티티 명세에 `관련 클래스 ID(KLID-AT-DC-NNN)`로 D1과, `관련 유스케이스 ID(KLID-AT-UC-NNN)`로 R2와 역추적선을 걸어둔다. 물리 타입·`ON DELETE`·`CHECK`·인덱스 정의는 **일부러 D8에서 다루지 않고 D9로 넘긴다** — 이 경계가 이 산출물을 설명할 때 가장 자주 나오는 질문이다.

## 3. 전체 구조 — 16개 ERD, 45개 엔티티

도메인별로 ERD를 쪼갠 이유는 저작도구 테이블이 45개에 달해 한 장의 ERD로는 가독성이 없기 때문이다. 업무 흐름 순서대로 묶었다.

| # | ERD | 핵심 엔티티 | 업무 의미 |
|---|-----|-----------|----------|
| 001 | 영상·프레임 수집 | LS_DATA_RAW, LS_DATA_SRC | **모든 관계의 뿌리.** 영상 1건 = 작업 1건 |
| 002 | 라벨링 | LS_DATA_LBL, LS_DATA_META | 프레임별 라벨 좌표 + 영상 시계열 메타 |
| 003 | 라벨 마스터·버전관리 | LS_LABEL, LS_LABEL_VERSION | 라벨 정의(코드성) + 검수완료 스냅샷 |
| 004 | 마킹 | LS_MARKING | 비식별 영상에서 이벤트 시점 마킹 |
| 005 | 비식별 | LS_DEIDENT_PROC_LOG, LS_DEIDENT_REPORT | 비식별 처리 이력 + 누락 신고 |
| 006 | 검수·영상상태 | LS_RAW_DATA_STATUS, LS_DATA_ISSUE | 작업/검수 워크플로우 상태 머신 |
| 007 | 작업 배정 | LS_TASK_ASSIGNMENT | REVIEWER→WORKER 배정·재배정 이력 |
| 008 | 이슈 스레드 | LS_DATA_ISSUE, LS_ISSUE_COMMENT | 반려 이슈의 스레드·댓글·재반려 계층 |
| 009 | 데이터 증강 | LS_DATA_AUG | 외부 증강(WINTER/NIGHT/RAIN) 수신·검수 |
| 010 | 배치·작업 인프라 | LS_BATCH_PROC_LOG, LS_AUTH_WORK_LOCK | 파이프라인 처리 이력 + 작업 잠금 |
| 011 | 관제 통지 | LS_CONTROL_NOTIFY_FALLBACK | 완료/수정 통지 큐 + 멱등 원장 |
| 012 | 포털 | LS_PORTAL_USER_LABEL | 포털 사용자별 작업 라벨(단방향) |
| 013 | 게시판 | LS_NOTICE, LS_NOTICE_ATTACH | 공지 게시글 + 첨부 |
| 014 | 시스템 설정 | LS_SYSTEM_CONFIG, LS_META | 전역 키-값 설정 |
| 015 | 영상 업로드 세션 | LS_TUS_UPLOAD | TUS 재개 업로드 세션(폐지 예정 경로) |
| 016 | 데이터마트 적재 View | V_COMPLETED_* 4종 (V114 재편) | 검수완료분만 노출하는 읽기 전용 인터페이스 |

## 4. 설계 핵심 — "두 개의 앵커"

이 ERD를 이해·설명하는 열쇠는 **모든 관계가 단 두 개의 식별자로 수렴한다**는 점이다.

- **`LS_DATA_RAW.RAW_SN` (원시영상 일련번호)** = **작업 단위 식별자.** "영상 1건 = 작업 1건"이 이 프로젝트의 대원칙이라, 배정·마킹·비식별·검수·통지·증강·포털이 전부 `RAW_SN`에 매달린다. 프로젝트 단위 개념은 쓰지 않는다.
- **`LS_DATA_SRC.SRC_SN` (프레임원천 일련번호)** = **라벨의 부착점.** 영상에서 추출한 키프레임이며, 라벨 좌표(`LS_DATA_LBL`)는 여기에 붙는다.

관계 표기도 두 종류다.
- **`||--o{` 실선** — 물리 FK가 있는 실제 참조 (예: 라벨→프레임)
- **`||..o{` 점선** — **물리 FK가 없는 논리 관계.** 전역 정책 엔티티(`LS_DEADLINE` 마감정의, `LS_WEBHOOK_IDEMPOTENCY` 멱등원장, `LS_META` 전역메타 등)는 특정 영상에 종속하지 않지만, 다이어그램 렌더 호환을 위해 앵커로 점선만 그어둔 것이다. **"점선 = 물리 FK 없음"** 이 설명 포인트다.

> 명세서의 FK 컬럼도 대부분 **"논리 FK"** 로 적혀 있다. 물리 제약(`FOREIGN KEY`)을 실제로 걸었는지는 D9 소관이고, D8은 "논리적으로 이 컬럼이 저 엔티티를 가리킨다"까지만 규정한다.

## 5. 업무 흐름으로 읽는 ERD (핵심 스토리라인)

ERD 번호 순서가 곧 **배치 파이프라인 순서**와 거의 일치한다. 이렇게 이야기하면 청중이 따라오기 쉽다.

1. **수집(001)** — 관제서버가 공유 DB에서 학습용으로 설정한 클립을 주기 배치가 픽업 → `LS_DATA_RAW` 1행 적재(`DATA_STTS_CD=PENDING`). `VMS_CLIP_ID`가 유니크라 같은 클립 재수신 시 갱신. 증강본은 `ORGNL_RAW_SN` 자기참조로 원본을 가리킨다.
2. **비식별(005)** — 적재 직후 선두 자동 실행. 처리 이력은 `LS_DEIDENT_PROC_LOG`, 누락 발견 시 `LS_DEIDENT_REPORT`. 성공하면 영상 상태가 `MARKING_READY`로.
3. **마킹(004)** — **비식별 영상**에서 이벤트 시점을 자동(프레임 간격)/수동(단축키)으로 마킹 → `LS_MARKING`.
4. **라벨링(002)** — 프레임(`SRC_SN`)마다 `LS_DATA_LBL`(bbox/폴리곤/세그멘테이션), AI 출처는 `LS_DATA_LBL_AI_INFO`, 객체 속성은 `LS_DATA_LBL_ATTR_VAL`. 영상 시계열 메타는 `LS_DATA_META`(+ 검토상태 `LS_DATA_META_REVIEW`).
5. **검수(006/008)** — `LS_RAW_DATA_STATUS`가 작업/검수 상태 머신. 반려는 `LS_DATA_ISSUE` 스레드(재반려는 `UP_DATA_ISSUE_SN` 자기참조 계층). `VER` 컬럼으로 낙관적 잠금.
6. **버전관리(003)** — 검수 **승인(APPROVED) 시점에만** 영상 단위 라벨 전체 스냅샷(JSON)을 `LS_LABEL_VERSION`에 저장. `VERSION_HASH`(SHA-256)로 중복 식별. 작업 중 임시저장은 버전이 아니다.
7. **통지(011)** — 검수 완료/수정 시 관제서버로 `TASK_COMPLETED`/`TASK_MODIFIED` 단방향 통지. 실패분은 `LS_CONTROL_NOTIFY_FALLBACK` 큐 + `IDMP_KEY` 멱등.
8. **소비(016)** — 관제서버는 통지를 받으면 `V_COMPLETED_*` 4종 View를 `RAW_SN`으로 단순 SELECT해 데이터마트에 1건=1행 UPSERT. **검수완료분만** 노출하는 평면 인터페이스. V114 재편으로 라벨 본문은 export 폴더 JSON(V_COMPLETED_VIDEO.EXPORT_PATH_NM)에서 픽업하고 뷰로는 변경점·메타만 쿼리한다.

곁가지: **배정(007)**, **증강(009)**, **배치 인프라(010)**, **포털(012)**, **게시판(013)**, **시스템설정(014)**, **업로드세션(015)** 은 위 주 흐름을 받치는 지원 도메인이다.

## 6. 데이터마트 View 4종 (016) — 설명 시 강조할 부분

`V_COMPLETED_VIDEO / FRAME / LABEL_CHANGE / META` 는 **물리 테이블이 아니라 읽기 전용 View**다(V114 재편 — 라벨 내용 뷰 `V_COMPLETED_LABEL`·`V_COMPLETED_LABEL_ATTR` 제거).

- 검수 완료(`LS_RAW_DATA_STATUS.DATA_STTS_CD='APPROVED'`, 메타는 `LS_DATA_META_REVIEW.RVW_STTS_CD='APPROVED'`)분만 노출.
- `CREATE OR REPLACE VIEW`라 **멱등** — Flyway 재실행에도 안전.
- 출력 컬럼명(소비 컨트랙트)은 물리 컬럼 rename 이후에도 **alias로 보존**한다. 즉 관제서버가 의존하는 인터페이스는 내부 리팩터링과 분리돼 있다.
- 프레임 View는 원본(`ORIGINAL_PATH`) · 비식별(`DEIDENTIFIED_PATH`) 경로를 **같은 행에서 페어**로 제공.
- **V114 재편(관제 연동 계약 변경·협의 대상)**: 라벨 본문은 검수 승인 export 폴더의 COCO JSON이 진실원이라 뷰에서 제거하고, `V_COMPLETED_VIDEO`에 export 폴더 경로(`EXPORT_PATH_NM`)·프레임수(`FRAME_CNT`)를 노출한다. 라벨 변경점은 `V_COMPLETED_LABEL_CHANGE`(`LS_DATA_LBL_HSTRY` 기반 ADDED/UPDATED/DELETED)로 조회한다.

## 7. 경계 — MNG_* 공유 스키마 (§3)

D8을 설명할 때 **범위(scope)** 를 분명히 하는 게 중요하다.

- `MNG_CLIP_MASTER`, `MNG_CLIP_EVNT_LST` 는 **관제서버가 소유**하는 공유 스키마. 저작도구는 학습용 클립 픽업 시 **READ만** 한다(`ddl-auto=validate`).
- 따라서 **D8/D9 물리 설계 대상이 아니다.** §3에 "참조 사실"만 적고, 진실원은 관제 공유 클립 ERD(ERD-024)에서 관리한다.
- 변경 시 관제서버팀 선승인 필수. — "우리가 만든 것과 남의 것"의 선을 명확히 그은 표시다.

## 8. 발표 시 예상 질문 & 대응

| 질문 | 답변 |
|------|------|
| "FK가 왜 '논리 FK'라고만 돼 있나?" | D8은 논리 모델이라 물리 제약(FOREIGN KEY) 실설정은 D9 소관. 여기선 참조 방향만 규정. |
| "점선 관계는 뭔가?" | 물리 FK 없는 전역 정책 엔티티(마감·멱등원장·전역메타). 특정 영상에 종속 안 하지만 렌더 호환용 논리선만 표기. |
| "ERD를 왜 16개로 쪼갰나?" | LS_* 테이블 45개를 한 장에 못 그린다. 업무 도메인별 분리 + 두 앵커(RAW_SN·SRC_SN)로 상호 연결. |
| "MNG_ 테이블은 왜 없나?" | 관제서버 소유 공유 스키마라 우리 물리 설계 대상 외. §3에 참조만. |
| "버전은 언제 생기나?" | 검수 승인 시점에만 영상 단위 전체 스냅샷. 작업 중 임시저장은 버전 아님(2계층 분리). |
| "View 4종은 테이블인가?" | 아니다. 검수완료분만 노출하는 읽기 전용 멱등 View. 데이터마트 적재 인터페이스. (V114 재편: 라벨 내용 뷰 제거, VIDEO에 export 폴더 경로 노출) |
| "증강본은 원본과 어떻게 연결되나?" | `LS_DATA_RAW.ORGNL_RAW_SN` 자기참조. 증강은 새 RAW_SN(새 영상). |

## 9. 30초 엘리베이터 스피치

> "D8은 저작도구가 직접 소유하는 LS_* 테이블 45개를 논리 데이터 모델로 정리한 산출물입니다. 핵심은 **영상 식별자 RAW_SN과 프레임 식별자 SRC_SN, 이 두 앵커로 모든 엔티티가 연결**된다는 겁니다. 영상 1건이 곧 작업 1건이라 배정·비식별·마킹·라벨링·검수·버전·통지가 전부 RAW_SN에 매달립니다. 가독성 때문에 수집→비식별→마킹→라벨링→검수→버전→통지→마트소비라는 업무 흐름 순서로 16개 도메인 ERD로 나눴고, 관제서버가 소유한 MNG_* 공유 스키마는 우리가 읽기만 하므로 물리 설계에서 빼고 참조 사실만 §3에 남겼습니다. 물리 타입·인덱스·DDL은 다음 산출물 D9에서 확정합니다."
