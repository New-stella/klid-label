# D11 단위시험 케이스

## 작성 목적
> 단위 프로그램 및 컴포넌트를 설계한 개발자가 컴포넌트 명세서에 정의된 바와 같이 설계한 컴포넌트 프로그램의 오류를 검출할 목적으로 배포하는 컴포넌트 단위로 시험하기 위한 시험 설계를 기술한다.

## 작성 방법
> 개발자가 설계한 컴포넌트 단위로 작성하며 컴포넌트별 시험케이스를 작성한다.

### 본문 양식

> **⟳ 단위시험(컴포넌트) 단위로 블록을 1개씩 반복 작성한다.** 블록 헤더는 단위시험 ID·설명·관련 컴포넌트 ID·관련 프로그램 ID, 본문은 케이스 행(1행 = 시험 케이스 1건).
> **작성 품질 규칙(CBD 적합성)**: ① 관련 컴포넌트 ID는 D3 컴포넌트설계서에 실존하는 ID만 기재한다. ② 시험 데이터는 실제 값 또는 조건으로 기술한다. ③ 예상결과 및 검증방법은 기대 결과 + 검증 수단(화면 확인·DB 조회 등)을 병기한다. ④ **시험결과는 설계단계에서 공란**으로 유지한다(I2 단위시험 결과서에서 기입).

> **본 산출물의 작성 근거**: 본 단위시험 케이스는 저작도구 백엔드의 단위테스트 코드를 진실원으로 하여 도출하였다. 각 시험케이스명은 단위테스트의 한글 서술형 케이스명을 그대로 사용하였고, 시험 데이터·처리절차·예상결과는 테스트의 입력·호출·검증 내용에서 도출하였다. 정상/경계/예외(권한 없음 403·입력 검증 실패 400·충돌 409 등) 케이스를 구분하여 기술한다.

WorkLockService는 전용 단위테스트 없이 협력 객체로만 검증되므로(UT-07/15/18/34에 흡수), QualityCheckService는 진실원 테스트 부재(품질 충돌 감지는 UT-28 QualityConflictDetector로 수록)이므로 별도 블록을 만들지 않았다.
- 시험케이스명은 단위테스트의 한글 케이스명을 사용하였으며(임의 작문 없음), 일부 행은 동일 대상의 유사 케이스(역할별·상태별·경계값)를 한 행으로 묶어 가독성을 높였다. 묶음 행의 시험항목·예상결과는 각 테스트의 검증 내용을 종합한 것이다.
- 시험 데이터·처리절차·예상결과는 테스트 본문의 given/when/then(입력값·호출·assert)에서 도출하였고, 코드에 없는 케이스는 기재하지 않았다(추측 금지).
- 작업권한 컬럼은 테스트가 사용한 토큰 역할(REVIEWER/WORKER/PORTAL_USER)을 기입하였다. 서비스/엔티티/유틸 단위 테스트 등 권한 검증이 대상이 아닌 케이스는 `-`로 표기했다.
- 시험결과 컬럼은 설계 단계에서 공란으로 유지하며, I2(단위시험 결과서)에서 실제 시험 수행 결과로 채운다.
- 테스트 더블(가짜 객체) 기법 및 ai-server 응답 더블 감지 로직은 일반 기술 용어("테스트 더블")로 표기했다.
- 빈 셀: 시험결과 컬럼을 제외하면 모든 케이스 행에 데이터가 채워져 있으며, 의도된 공란은 없다. (시험결과 컬럼만 설계 단계 규칙에 따라 전체 공란.)
- 마이그레이션 검증 테스트(V42/V43/V44/V57/V59 등)·일부 엔티티 비동기 표준 컬럼 테스트는 해당 도메인 블록 내 대표 케이스로 흡수하거나 인프라성 검증으로 분류하여 별도 블록을 만들지 않았다.
