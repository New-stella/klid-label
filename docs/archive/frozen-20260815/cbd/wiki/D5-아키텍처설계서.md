# D5 아키텍처설계서 (CBD 표준 산출물 위키)

> 출처: NIA CBD 가이드(2011.12) docs/CBD.pdf 인쇄면 p.60~66 (PDF 페이지 63~69). 가이드 §2.5 "아키텍처 설계서".
> 대응: 타 방법론의 "소프트웨어 아키텍처 정의서·시스템 구성도", 범정부 EA의 "기반구조관계도(TV2)"에 대응한다.

## 1. 작성 목적 (PDF 원문)

> 시스템의 품질을 확보하기 위하여 전체시스템에 대한 청사진으로서의 아키텍처를 작성한다. 소프트웨어 아키텍처는 개발 대상 응용 소프트웨어에 대한 아키텍처이며, 시스템 아키텍처는 응용 소프트웨어와 이에 상호작용하는 환경 및 네트워크가 포함된 아키텍처를 의미한다.

## 2. 작성 방법 (PDF 원문)

> 소프트웨어 아키텍처는 선정된 아키텍처 패턴을 중심으로 컴포넌트와 상호작용하는 커넥션 및 가시적인 속성을 표현한다. 시스템 아키텍처는 개발 대상시스템과 상호작용하는 하드웨어, 시스템 소프트웨어 및 네트워크와의 관계를 표현한다. 아키텍처 요구사항 및 구현방안은 아키텍처 관점에서의 시스템의 품질, 보안, 성능, 장애복구 등의 요구사항과 이에 대한 구현방안을 기술한다.

## 5. 작성 사례 요점 (PDF 원문 / 산출물코드 SS_REQ)

산출물코드: 요구사항 ID `SS_REQ_NNN`.

### 1. 소프트웨어 아키텍처 (사례 다이어그램)
.NET 기반 레이어드 컴포넌트 다이어그램:
- **Presentation Layer**: UI layer(`<<HTML,JavaScript>>` Web UI Component, `<<WinForm Assembly>>` UI Component) / UI Process Layer(`<<Graphical Algorithm>>` Presentation Logic Component, `<<Code behind>>` UI Process Component, `<<.NET Remoting>>` Data Management Component).
- **Business Layer**: Service Interface Layer(`<<.NET Remoting>>` Remoting Service Component) / Business Workflow Layer(`<<ServicedComponent>>` Application Component) / Business Logic Layer(`<<ServicedComponent>>` Business Logic Component).
- **Data Layer**: `<<ServicedComponent>>` Data Access Component → Data Base, File System.
- → 선정된 아키텍처 패턴(레이어드)과 컴포넌트 스테레오타입·의존(점선 화살표)을 표현.

### 2. 시스템 아키텍처 (사례 다이어그램)
"검색 하드웨어 및 네트워크 구성도" — 센터/기관별 영역(현장 정보, 대내 서버, 본점/지점, 전산센터 등)을 묶어 GPS 위성·무선·라우터·방화벽·Web 서버·DB 서버·OBS App 서버, LAN/100Mbps 등 HW·NW 요소와 사용자 단말 구성을 표현한 종합 구성도.

### 3. 아키텍처 요구사항 및 구현방안 (사례 4건)
- **SS_REQ_010 (품질)**: 결함예방·품질만족·사용자 신뢰도 확보를 위한 품질목표 수준 설정·관리. 구현방안 = 표로 **기능성·신뢰성·사용성·효율성·유지보수성·이식성**별 품질목표 측정 항목과 목표수준(예: 요구사항 반영율 97%, 통합시험 후 결함율 5% 이하, 교육 후 만족도 70점 이상, 응답속도 5~6초 응답, 산출물 일관성 95% 이상, 컴파일 자동화 100% 등) 정의.
- **SS_REQ_030 (보안)**: 대외기관과 내부시스템 간 메시지 송수신을 위한 중계시스템 데이터 유출 방지·기밀성 확보. 구현방안 = 중계시스템 암/복호화 구성도(Gateway–Library(암/복호화)–Mapper–Gateway).
- **SS_REQ_050 (성능)**: 시스템 노후화·DB 누적에 따른 응답속도 저하 대응, DB 성능 문제 파악·성능 제고 방안 확보. 구현방안 = 성능 이슈/성능 확보 방안/환경 추진 Task 표.
- **SS_REQ_060 (장애복구/가용성)**: 24시간 무정지 서비스를 위한 시스템 다운 대비·가용성 확보. 구현방안 = 네트워크 계층 이중화/서버 이중화/피이버 채널 이중화(Heart Beat, SAN Storage) 그림.

## 6. 함정 / 주의

- **다이어그램 2종(SW·시스템)은 필수 섹션**이며 빈 박스로 양식이 제공된다 — 둘 중 하나만 채우면 미완.
- §3은 단건이 아닌 **요구사항별 반복 블록** — 품질·보안·성능·장애복구 4관점을 최소한으로 커버하는지 확인.
- 요구사항 ID는 "사용자 요구사항 정의서"의 실존 ID와 연결해야 추적성이 성립한다.
- **§3 요구사항 ID = R1 실존 ID만**(`RQ-SFR`/`NFR`/`RQ-QUR`/`RQ-DAR`). ❌ 표의 연속 번호를 채우려 `NFR-008/009/010`처럼 **R1에 없는 ID를 날조 금지**(R1 NFR은 결번 존재) — 실존 ID를 그대로 인용한다.
- SW 아키텍처 사례가 .NET 스테레오타입이라 그대로 베끼면 안 됨 — 프로젝트 실제 스택의 패턴·컴포넌트로 재작성.

## 7. KLID 프로젝트 적용 메모

- §3은 **비기능 관점(품질·보안·성능·장애복구) 요구사항 블록 반복** — KLID에서는 R1 NFR-001~007 + RISK 대응이 주력 소스.
- 다이어그램은 SW(레이어드)·시스템(HW/NW) 2종이 필수 섹션. C4 모델 사용 시 SW 아키텍처=Container/Component, 시스템 아키텍처=Context/Deployment에 대응시켜 작성.
- **1. 소프트웨어 아키텍처 (KLID)**: 레이어드 — Controller → Service → Repository(JPA/QueryDSL) + 공통 인프라(ApiResponse, GlobalExceptionHandler, JwtAuthenticationFilter, 듀얼 DataSource `@ControlRepo`/`@PortalRepo`). 외부 연동 컴포넌트(DeidentifyClient/AiServerClient/VlmClient/ControlNotifyClient/ExternalAugmentClient, Resilience4j). 선언적 배치 파이프라인(BatchStep/BatchContext/BatchPipeline/BatchPipelineConfig).
- **2. 시스템 아키텍처 (KLID)**: 단일 인스턴스 Spring Boot(+Quartz, Docker/Pod 미사용·클러스터 미적용) ↔ ai-server(YOLO/SAM2/VLM, 다중 인스턴스 수평 확장 가능, GPU Worker) ↔ PostgreSQL(klid_at: LS_* 자체 소유 + MNG_*/QRTZ_* 공유 validate) ↔ 비식별 서버 ↔ 관제서버(inbound SPI) ↔ 포털 DB. React+Vite FE. STORAGE_RAW_PATH/STORAGE_DEIDENTIFIED_PATH 동시 저장.
- **3. 요구사항·구현방안 (KLID 매핑 예시)**:
  - **품질**: R1 NFR + 요구사항 추적표 일치 — `cc-doc-gen` 산출물 정합.
  - **보안**: 영상 암호화 저장, Logback MaskingPatternLayout, JWT 검증(JwtAuthenticationFilter), 통지 페이로드 PII·토큰·원본 미포함, IP 화이트리스트/인계 토큰.
  - **성능**: Quartz 1건/분 배치, ai-server GPU 모니터링, Micrometer+Prometheus 메트릭, Caffeine 캐시(시스템 설정 TTL 60s).
  - **장애복구**: 외부 API Resilience4j(타임아웃/재시도/서킷 브레이커), 비식별 실패 `DE_IDENT_YN='F'`+재시도, 통지 idempotency+dead-letter+재등록 큐, 원본 영상 절대 삭제 금지.
- 요구사항 ID는 R1 실존 ID(RQ-SFR + NFR)만 연결. 외부 시스템 본체(VLM/생성형 AI/영상 합성/데이터마트)는 범위 외 — 아키텍처 요구사항 블록에서 "외부 시스템 책임"으로 명시.
