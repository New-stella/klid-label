# D1 클래스 설계서 (CBD 표준 산출물 위키)

> 출처: NIA CBD 가이드(2011.12) docs/CBD.pdf 인쇄면 p.23~28 (설계 단계 2.1 클래스 설계서)

표준산출물 분류상 D1은 「클래스 설계서」이며, 다른 방법론의 "상세 클래스 설계서 / 클래스 명세서"에 대응한다. 시퀀스도 → 설계 클래스도 → 클래스 정의로 이어지는 객체지향 설계 모형을 담는다.

---

## 1. 작성 목적 (PDF 원문)

> 소프트웨어 관점이나 설계 관점에서의 클래스 모형을 작성한다.

---

## 2. 작성 방법 (PDF 원문)

> 설계 클래스를 도출하기 위하여 우선 **유스케이스별로 시퀀스도를 작성**하며, 여기에서 도출된 객체 및 클래스를 연관관계를 이용하여 **유스케이스별로 클래스도를 작성**한다. 설계 클래스도에서는 클래스명, 속성 및 오퍼레이션을 명확하고 구체적으로 표현하여야 하고 각각의 클래스는 상세한 명세를 기술한다.

→ 작성 흐름: 유스케이스 명세서 → (UC별) 시퀀스도 작성 → (UC별) 설계 클래스도 도출 → (클래스별) 설계 클래스 정의.

### 3.2 시퀀스도 (유스케이스별 작성)

헤더박스 + 시퀀스 다이어그램으로 구성.

| 컬럼명 | (옆 칸) | 의미 |
|--------|---------|------|
| 시퀀스도 ID |  | 시퀀스도별 유일 ID |
| 시퀀스도명 |  | 시퀀스도의 이름 |
| 관련 유스케이스 ID | (행 전체) | "유스케이스 명세서"의 유스케이스 ID |
| 주요 액터 | 주요 클래스(또는 객체) | 본 산출물 관련 액터들 / 관련 클래스(객체)들 |

- 헤더박스 아래 큰 빈 영역 = **시퀀스 다이어그램**(액터·객체 간 메시지 호출 순서). 액터 라이프라인, 객체 라이프라인, 동기/리턴 메시지, 활성화 막대를 표현한다.

### 3.3 설계 클래스도 (유스케이스별 작성)

헤더박스 + 클래스 다이어그램으로 구성.

| 컬럼명 | (옆 칸) | 의미 |
|--------|---------|------|
| 설계 클래스도 ID |  | 설계 클래스도별 유일 ID |
| 설계 클래스도명 |  | 설계 클래스도의 이름 |
| 관련 유스케이스 ID | (행 전체) | "유스케이스 명세서"의 유스케이스 ID |

- 헤더박스 아래 큰 빈 영역 = **클래스 다이어그램**. 클래스 박스(이름·속성·오퍼레이션 칸)와 클래스 간 연관/의존/상속 관계를 표현한다.

### 3.4 설계 클래스 정의 (클래스별 작성)

헤더 + 속성 표 + 오퍼레이션 표로 구성.

헤더:

| 컬럼명 | (옆 칸) | 의미 |
|--------|---------|------|
| 설계 클래스 ID | 설계 클래스명 | 정의 대상 클래스 ID / 명 |

**속성** 표:

| 컬럼명 | 의미 |
|--------|------|
| 속성명 | 속성의 정확한 명칭 |
| 가시성 | 속성의 가시성 유형(public/private/protected 등) |
| 타입 | 속성의 타입 |
| 기본값 | 속성이 기본값을 가질 경우 그 값 |
| 설명 | 속성의 의미와 역할 |

**오퍼레이션** 표:

| 컬럼명 | 의미 |
|--------|------|
| 오퍼레이션명 | 오퍼레이션의 정확한 명칭 |
| 가시성 | 오퍼레이션의 가시성 유형 |
| 파라미터 | 오퍼레이션이 파라미터를 가질 경우 기입 |
| 반환타입 | 오퍼레이션이 반환값을 제공할 경우 그 타입 |

## 4. 항목 설명 (전 항목 — PDF 원문)

### ■ 설계 클래스 목록 — *유스케이스별로 작성한다*
- **설계 클래스 ID**: 설계 클래스별로 유일한 ID를 부여하여 기입한다.
- **설계 클래스명**: 설계 클래스의 이름을 부여하여 기입한다.
- **관련 유스케이스 ID**: 본 산출물이 관련되는 "유스케이스 명세서"의 유스케이스 ID를 기입한다.

### ■ 시퀀스도 — *유스케이스별로 작성한다*
- **시퀀스도 ID**: 시퀀스도별로 유일한 ID를 부여하여 기입한다.
- **시퀀스도명**: 시퀀스도의 이름을 부여하여 기입한다.
- **관련 유스케이스 ID**: 본 산출물이 관련되는 "유스케이스 명세서"의 유스케이스 ID를 기입한다.
- **주요 액터**: 본 산출물과 관련되는 액터들을 기입한다.
- **주요 클래스**: 본 산출물과 관련되는 클래스들을 기입한다.

### ■ 설계 클래스도 — *유스케이스별로 작성한다*
- **설계 클래스도 ID**: 설계 클래스도별로 유일한 ID를 부여하여 기입한다.
- **설계 클래스도명**: 설계 클래스도의 이름을 부여하여 기입한다.
- **관련 유스케이스 ID**: 본 산출물이 관련되는 "유스케이스 명세서"의 유스케이스 ID를 기입한다.

### ■ 설계 클래스 정의 — *클래스별로 작성한다*
- **설계 클래스ID**: 정의하고자 하는 설계 클래스ID를 기입한다.
- **설계 클래스명**: 정의하고자 하는 설계 클래스명을 기입한다.
- **속성명**: 속성의 정확한 명칭을 기입한다.
- **가시성**(속성): 속성의 가시성의 유형을 기입한다.
- **타입**: 속성의 타입을 기입한다.
- **기본값**: 속성이 기본값을 가질 경우 그 값을 기술한다.
- **설명**(속성): 속성의 의미와 역할을 기술한다.
- **오퍼레이션명**: 오퍼레이션의 정확한 명칭을 기입한다.
- **가시성**(오퍼레이션): 오퍼레이션의 가시성의 유형을 기입한다.
- **파라미터**: 오퍼레이션이 파라미터를 가질 경우 기입한다.
- **반환타입**: 오퍼레이션이 반환값을 제공할 경우 그 타입을 기술한다.
- **설명**(오퍼레이션): 오퍼레이션의 의미와 역할을 기술한다.

## 5. 작성 사례 요점 (PDF 원문 값 + 산출물코드)

PDF 사례는 자금이체 시스템(서브시스템 SS)의 원화자금이체신청(SS_UC_010) 유스케이스 기준.

- **설계 클래스 목록** (산출물코드 패턴 — 클래스 ID 자리에 영문 클래스명을 쓰기도 함):

  | 설계 클래스 ID | 설계 클래스명 | 관련 유스케이스 ID |
  |---|---|---|
  | EBA001CodAction | 원화자금이체신청 | SS_UC_010 |
  | EBA001RdaAction | ProductCatalog | SS_UC_010 |

- **시퀀스도(SD)**: `SS_SD_010-01` | 시퀀스도명 "원화자금이체신청" | 관련 UC `SS_UC_010-01`. 주요 액터 = 원화자금이체책임자·주전산기·원화자금이체담당자. 주요 객체 = 공통코드정보·신청정보·사용자번호정보.

- **설계 클래스도(DCD)**: `SS_DCD_010-01` | 설계 클래스도명 "Process Sale" | 관련 UC `SS_UC_010-01`. 클래스 박스 예: JSafeLocaleSB, JCableXOISB, JTransmenSB, GsucaFrontServlet, GsucaWebActionSupport, EBA001CodAction(+perform/doExit/doStart), EBA001RdaAction, DTO/CommonDTO/DocDTO 등.

- **설계 클래스 정의(DC)**: `SS_DC_010-01` | 클래스명 EBA001CodAction.
  - 속성: `기관코드 | public | string | 없음 | 신청기관 명`, `담당자 | public | Text | 없음 | 원화자금이체 담당자`, `신청상태 | public | string | 없음 | (설명에 상태값 열거: 1.승인요청 2.처리 중 3.반려 4.승인 완료)`.
  - 오퍼레이션: `perform | public | request: HttpServletRequest, response: HttpServletResponse | Object | 요청에 대한 ejb수행을 위한 request의 작성 및 요청에 대한 일반수행을 한다`.

**산출물코드 체계(사례)**: SD=시퀀스도(`SS_SD_NNN`), DCD=설계 클래스도(`SS_DCD_NNN`), DC=설계 클래스 정의(`SS_DC_NNN`), UC=유스케이스(`SS_UC_NNN`).

## 6. 함정 / 주의

- **반복 단위가 핵심**: §3.1 목록·§3.2 시퀀스도·§3.3 클래스도 = **유스케이스별** 반복(전역 통합 1개로 묶기 금지), §3.4 정의 = **클래스별** 반복. UC 1건 ↔ SD/DCD 1건 정렬.
- **순서 의존**: 시퀀스도를 먼저 작성해 객체를 도출하고, 그 객체·연관을 클래스도로 옮긴 뒤, 각 클래스를 정의로 상세화한다(스킵 금지).
- **관련 유스케이스 ID는 반드시 "유스케이스 명세서" ID와 연결** — 추적성 단절 방지.
- 가시성/타입/반환타입은 빈 값 금지(없으면 "없음" 명기 — 사례 준수).
- **반환타입 칸 = 추상 설계 타입만**. ❌ `(비동기)` 등 프레임워크 구현 괄호주석 금지(`Mono`·`CompletableFuture` 등 구체 클래스도 금지) → 비동기성·동기성은 오퍼레이션 '설명' 칸에 서술한다.
- 시퀀스도의 "주요 클래스"는 곧 클래스도·클래스 정의의 클래스와 동일 어휘여야 한다.

## 7. KLID 프로젝트 적용 메모

- **ID 체계**: 본 프로젝트 산출물 ID는 `KLID-AT-XX-NNN` 체계. 설계 클래스 정의 ID는 `KLID-AT-DC-NNN`, 시퀀스도는 `KLID-AT-SD-NNN`, 설계 클래스도는 `KLID-AT-DCD-NNN`로 채번한다.
- **도메인 블록 10단위 채번**: 클래스 ID는 도메인 블록 단위(예: 마킹 010~019, 라벨링 020~029, 검수 030~039, 배치 040~049 …)로 10단위 블록을 할당한다.
- **DCD 번호 = 실현 UC 번호와 정렬**: UC 결번 시 DCD도 결번 유지. 공통 클래스(예: `ApiResponse`, `JwtAuthenticationFilter`, `AiServerClient`)는 동일 `KLID-AT-DC-NNN`으로 여러 클래스도에 교차 등장한다.
- **D8 교차 참조**: D8 엔티티 산출물의 "관련 클래스 ID"는 본 산출물 DC ID와 동일 체계여야 한다(추적성).
- **KLID 도메인 매핑 예**: 마킹(자동/수동), 라벨링(konva 캔버스), 검수(REVIEWER 배정), 배치 파이프라인(비식별→마킹→VLM→FFmpeg→YOLO/SAM2→보간), 비식별화 신고 등 R1 UC와 1:1 정렬.
- **레이어 컨벤션 반영**: Controller→Service→Repository 레이어 클래스는 가시성·반환타입을 Java 17 표준(record DTO, Optional 반환 등)으로 정의에 기입한다.
