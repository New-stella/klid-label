# D10 통합시험 시나리오 (CBD 표준 산출물 위키)

> 출처: docs/CBD.pdf 인쇄면 p.95~100 (§III 2.10 통합시험 시나리오)

---

## 1. 작성 목적 (PDF 원문)

> 각 응용 프로그램의 단위 프로그램 내에서의 작업 흐름 연계, 단위 프로그램간의 상호 연동 및 대내외 인터페이스를 포함한 사용자 요구사항을 만족하는지를 검증한다.

- 검증 대상: 단위 프로그램 **내 작업 흐름 연계** + 단위 프로그램 **간 상호 연동** + **대내외 인터페이스**.
- 검증 기준: **사용자 요구사항(유스케이스) 충족 여부**. 단위시험(D11, 컴포넌트 단위)보다 상위 — 흐름·연동 통합 관점.

## 2. 작성 방법 (PDF 원문)

> 시험시나리오별로 통합 시험 케이스를 기술하고 시험 예상결과와 시험결과를 비교 할 수 있도록 한다.

- 작성 단위: **시험 시나리오별**. 한 시나리오 안에 다수 시험 케이스를 포함.
- 핵심 의도: **예상결과 ↔ 시험결과**를 행 단위로 대조 가능하게 구성. (시험결과 컬럼은 설계단계 공란 — §6 참조)

## 4. 항목 설명 (PDF 원문 전 항목 — 누락 금지)

### 4.1 시험 시나리오
- **시험 시나리오 ID**: 통합 시험 시나리오에 대한 유일한 ID를 부여하여 기입한다.
- **시험 시나리오명**: 시험 시나리오의 명칭을 기입한다.
- **시험 시나리오 설명**: 시험에 대한 간략한 설명을 기술한다.
- **관련 유스케이스 ID**: 본 산출물이 관련되는 "유스케이스 명세서"의 유스케이스 ID를 기입한다.
- **시험 케이스 ID**: 시험 시나리오에 포함된 시험 케이스에 대한 식별자를 부여하여 기술한다.
- **시험 케이스 설명**: 시험 케이스의 간략한 설명을 기술한다.
- **시험 절차**: 시험 케이스별 시험을 수행하는 절차를 기술한다.
- **시나리오 설명**: 시험 절차의 각 단계별 실행 시나리오를 기술한다.
- **시나리오 설명**(중복 기재): 기타 고려사항 등을 기술한다. ⚠ 원문에 "시나리오 설명" 항목명이 **두 번 기재**되어 있으며, 두 번째 설명은 "기타 고려사항 등" — 사실상 **비고** 성격. (PDF 원문 그대로의 중복이며 오기 추정이나 임의 정정하지 않음 — PDF 확인 필요 사항)

### 4.2 시험 케이스
- **차수**: 시험 시나리오별 시험을 수행한 횟수를 기술한다.
- **시험 시나리오 ID**: 통합 시험 시나리오 ID를 기입한다.
- **시험 케이스 ID**: 시험 케이스 ID를 기술한다.
- **순번**: 시험 케이스별 업무 처리의 순서번호를 기입한다.
- **업무처리 내용**: 시험 케이스별 업무처리 내용을 기술한다.
- **시험항목**: 시험 데이터 및 시험 수행내용을 기술한다.
- **사전조건**: 시험 수행 사전 조건을 기술한다.
- **입력자료**: 시험을 위해 입력하는 값을 기술한다.
- **예상결과**: 시험이 성공적으로 수행되었을 경우의 예상 결과를 기술한다.
- **화면 ID**: 시험을 수행하는 화면 ID를 기술한다.
- **시험결과**: 설계단계에서는 기술하지 않으며, **통합 시험결과서로 활용될 경우** 실제 시험을 수행한 결과를 기술한다.
- **비고**: 기타 참조할 만한 사항을 기술한다.

## 6. 함정 / 주의

- ★ **시험결과 컬럼은 설계단계 공란**: D10은 설계 산출물이므로 시험결과 컬럼을 비워두고 예상결과만 기재한다. 실제 결과는 **T1 통합시험 결과서**로 현행화 시 기입한다. (사슬: **D10 통합시험 시나리오 → T1 통합시험 결과서**)
- **"시나리오 설명" 항목 중복**: 항목 설명에 동일 명칭이 2회 등장(두 번째는 "기타 고려사항"). 표 컬럼상 "시나리오 설명"은 1개 + "비고" 1개 구조이므로, 두 번째 설명은 비고 컬럼에 대응되는 것으로 해석. 임의 단정 금지 — PDF 확인 필요.
- **통합시험 = 유스케이스 단위**: 관련 유스케이스 ID로 추적. 단위시험(D11, 컴포넌트 단위)과 추적 키가 다름.
- **시험 절차 컬럼은 2분할**(순번 / 업무처리내용) — 마크다운 1컬럼으로 합치지 말 것.
- **차수(시험 수행 횟수)** 개념 존재 — 재시험 시 차수 증가하여 이력 누적.
- 화면 ID는 임의 부여 금지 — 화면설계서 실존 ID와 일치시켜야 함.

## 7. KLID 프로젝트 적용 메모

- **관련 유스케이스 ID**: KLID UC 식별자(`KLID-AT-UC-NNN` / LogiCraft USE_CASE)와 매핑. 통합시험은 파이프라인·연동 전체 흐름(적재→비식별→마킹→VLM→프레임추출→오토라벨링)을 유스케이스 단위로 검증.
- **코드 체계(KLID 적응)**:
  - 시험 시나리오 ID: `KLID-AT-IT-TS-NNN`
  - 시험 케이스 ID: `KLID-AT-IT-TC-NNN`
  - 화면 ID: D5/D6 화면설계 산출물의 KLID 화면 ID(`KLID-AT-SC-NNN`).
- **대내외 인터페이스 통합 시험 후보**(KLID): DeidentifyClient(비식별), AiServerClient(YOLO/SAM2/VLM), VlmClient 콜백, ControlNotifyClient(TASK_COMPLETED/TASK_MODIFIED outbound), ExternalAugmentClient(증강) — 각 연동을 통합 시나리오로 묶어 Resilience4j 재시도/타임아웃 동작 포함 검증.
- **상태 전이 시나리오**(KLID): `LsDataRaw.dataSttsCd` PENDING→MARKING_READY→COMPLETED, `LsRawDataStatus.dataSttsCd` 작업/검수 워크플로우(ASSIGNED→PENDING→APPROVED) — 두 테이블 책임 분리를 통합 시나리오로 검증.
- **시험결과 현행화**: 설계단계 공란 → **T1 통합시험 결과서**에서 실제 결과 기입. KLID 실행 환경: 백엔드 통합 테스트는 JUnit 5 + Testcontainers(PostgreSQL), 화면 플로우는 Playwright E2E(`/cc-e2e`, `/cc-verify`).
- **차수**: 재검증/회귀 시험 시 차수를 증가시켜 시험 결과 이력을 누적.
