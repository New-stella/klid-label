### 표준산출물과 타산출물 비교 (가이드 §II.2)

> 산출물명이 다른 방법론/범정부 EA와 어떻게 대응되는지 — 명칭 혼동 방지용.

| 코드 | 표준 산출물 | 다른 방법론 명칭 | 범정부 EA |
|:---:|---|---|---|
| R1 | 사용자 요구사항 정의서 | 상위 요구사항 정의서 · 과업대비표 | - |
| R2 | 유스케이스 명세서 | 요구사항 기술서 · 현행 시스템분석서 | AV2 응용시스템관계도 |
| D1 | (클래스 설계서) **클래스 명세서** | 상세 클래스 설계서 | - |
| D2 | 사용자 인터페이스 설계서 | 사용자화면정의서 · 화면설계서 · 메뉴구성도 · 인터페이스 상호작용 명세서 | AV3 응용기능분할도 |
| D3 | 컴포넌트 설계서 | 프로그램 명세서 · 컴포넌트 명세서 · 인터페이스 명세서 | - |
| D5 | 아키텍처 설계서 | 소프트웨어 아키텍처 정의서 · 시스템 구성도 | TV2 기반구조관계도 |
| D8 | 엔티티 관계 모형 설계서 | 데이터모형설계서 | **DV4 논리데이터모델** |
| D9 | 데이터베이스 설계서 | - | **DV6 물리데이터모델** |
| I1 | 프로그램 코드 | 프로그램 소스 · 프로그램 목록 | TV3 기반구조설계도 |

> KLID는 산출물 코드를 D1~D12·R1~R3·I1~I3·T1~T7로 통일(파일명 기준)하고, ID는 전체형 `KLID-AT-XX-NNN`을 쓴다.

## 모든 산출물 공통 규칙

### 산출물 구조 (가이드 §I.3 특징)
```
산출물 양식 → 작성 목적 → 작성 방법 → 항목 설명 → 작성 사례
```

### 제·개정 이력 (공통 — 25종 전부 동일)

| 날짜 | 버전 | 작성자 | 승인자 | 내용 |
|------|------|--------|--------|------|

> ⚠ `제·개정 내역/검토자` 가 아니라 **작성자/승인자/내용** 이 공식 컬럼.

### 헤더 박스 (공통)

| {코드} | {산출물명} |
|---|---|
| 시스템명 | … | 서브시스템명 | … |
| 단계명 | 분석/설계/구현/시험 | 작성일자 | … | 버전 | … |

> 단계명: R*=분석, D*=설계, I*=구현, T*=시험.

### 산출물 ID 부여 기본방법 (가이드 §II.3)

```
프로젝트 ID + 서브시스템 ID + 산출물 코드 + 순서번호
예) SS_SA_REQ_010 (판매시스템 사용자 요구사항 정의서)
```
- 프로젝트에 별도 ID 부여 방법이 있으면 그것을 따른다 → **KLID 프로젝트는 `KLID-AT-XX-NNN` 전체형 채택** (약식 표기 금지 — 각 산출물 ID 표기 규칙 참조).
- 가이드 사례에서 관찰되는 산출물 코드: REQ/RF(요구사항), UC, UCD, AC(액터), SC(화면), PR(출력물), SD(시퀀스도), DCD(설계 클래스도), DC(설계 클래스), CO(컴포넌트), IC(내부/인터페이스 클래스), IF(인터페이스), II(인터페이스 번호), EN(엔티티), ERD, DB, TS, TB(테이블), IDX, DP(프로그램), DD(생성 스크립트), UT_TS(단위시험), IT_TS(통합시험 시나리오), ST(시스템시험), TC(시험 케이스), CC/CCD(개념 클래스).

## 시험 산출물 체계 (설계 → 시험결과 현행화 사슬)

| 시험유형 | 설계단계 산출물 | 결과 산출물 | 작성자(사례 기준) | 시험결과 기입 시점 |
|---|---|---|---|---|
| 전체 | D6 총괄시험계획서 | - | 시험 관리자 | 설계단계 |
| 단위시험 | D11 단위시험 케이스 | I2 단위시험 결과서 | 응용개발팀(+프로젝트 시험팀) | 구현단계 |
| 통합시험 | D10 통합시험 시나리오 | T1 통합시험 결과서 | 프로젝트 시험팀 | 시험단계 |
| 시스템시험 | D7 시스템시험 시나리오 | T2 시스템시험 결과서 | 프로젝트 시험팀 | 시험단계 |
| 인수시험 | T6 인수시험 시나리오 | T7 인수시험 결과서 | 프로젝트 시험팀 + 고객 | 시험단계 |

> **공통 함정**: 시나리오/케이스 산출물의 **시험결과 컬럼은 설계단계에서 공란** — 결과서로 현행화될 때만 기입.
> 시험 4단계 비교(가이드 D6 사례): 단위(모듈·화면, 프로그램 명세서 기준, 개발환경) / 통합(서브시스템·인터페이스 검증, 요구사항정의서 기준, 개발환경) / 시스템(전체 시스템, 성능 등 기능 외적 요인, 운영환경) / 인수(전체 시스템, 인수 여부 결정, 고객 테스터, 계약서·합의된 정의서 기준, 운영환경).

## 추적성 사슬 (R3 매트릭스 기준)

```
요구사항(R1) → 유스케이스(R2) → 화면(D2)·컴포넌트(D3)·테이블(D9)
            → 프로그램(I1) → 단위시험(I2) → 통합시험(T1) → 시스템시험(T2)
```

## KLID 프로젝트 적용 메모

- 프로젝트 템플릿: `docs/cbd/templates/` (본 위키와 대조하여 유지). 글로벌: `~/.claude/setup/cbd-templates/`
- 관련 요구사항 ID는 **R1에 실존하는 ID만** 기재 (`RQ-SFR-NN-NN` + `NFR-NNN`) — 없으면 `-` + 부록 사유, 각주 의사값 금지
- D9 의 DB2 물리 용어(Storage Group/Bufferpool/TS)는 실제 DBMS(PostgreSQL) 등가물로 적응 표기
- 가이드 원문은 "내용의 유형 표시"용 — 실제 프로젝트 특성에 맞게 수정·추가 가능(§I.2 범위), 단 항목 누락 금지
