# IV. 선택사항 — 추가 산출물 사례 (CBD 표준 산출물 위키)

> 출처: docs/CBD.pdf 인쇄면 p.175~177 (§IV. 선택사항). 문서의 마지막 구간.

## 0. 선택사항 개요 (PDF 원문)

> 위의 'III. 산출물양식'에서 제시한 산출물은 **필수 산출물로 반드시 작성**하여야 한다. 그러나 **프로젝트 유형이나 특성에 따라 추가로 필요한 산출물이 생길 시에는 산출물을 추가하여 작성할 수 있다.**

- 즉, 본 장의 2종(개념적 클래스 모형 기술서, 용어집)은 **선택(생략 가능) 산출물**이다. 필수 산출물(III장)이 아니며, 프로젝트 판단으로 추가 작성한다.
- 두 사례 모두 **분석단계 추가 산출물**로 분류된다.

# 사례 1) 개념적 클래스 모형 기술서

> PDF 원문: "개념적 클래스 모형 기술서가 필요한 경우에 **분석단계 산출물로 추가하여 작성**할 수 있다." (선택)

## 1-1. 작성 목적 (PDF 근거)

PDF는 본 산출물에 대해 별도 [작성 목적]/[작성 방법]/[항목 설명] 블록 없이 **[작성 사례]만 제시**한다. 따라서 목적·방법은 사례 양식에서 도출된다: 서브시스템별로 **개념 클래스(BCE: Boundary/Control/Entity)를 도출·목록화하고, 클래스 간 관계를 개념 클래스도로 표현**하는 분석단계 보조 산출물이다.

> PDF에 명시적 목적문이 없으므로, 별도 목적 정의가 필요하면 **PDF 확인 필요** (사례 양식 기준 해석임).

## 1-2. 작성 방법 (사례 양식 기준)

- 개념 클래스 목록·개념 클래스도를 모두 **서브시스템별로 작성**한다(PDF 사례의 "- 서브시스템별로 작성" 주석).
- (명시적 작성 방법 문단은 PDF에 없음 — **PDF 확인 필요**.)

## 1-3. 산출물 양식 (표 구조 전수 — 헤더 코드 R3, 단계명=분석)

> 사례의 헤더박스가 **R3** 코드 자리에 배치됨(분석 단계).

```
┌──────┬────────────────────────────────────────────────┐
│  R3  │          개념적 클래스 모형 기술서              │
├──────┼──────────────────┬──────────────┬──────────────┤
│ 시스템명 │              │ 서브시스템명 │              │
├──────┼─────┬───────────┼──────────────┼──────┬───────┤
│ 단계명 │ 분석 │          │ 작성일자     │ 버전 │       │
└──────┴─────┴───────────┴──────────────┴──────┴───────┘
```

### 표 1 — 개념 클래스 목록 (서브시스템별 작성)
| 개념 클래스 ID | 개념 클래스명 | 개념 클래스 설명 | 속성 | 관련 유스케이스 ID | 관련 유스케이스명 |
|---|---|---|---|---|---|

> 마지막 "관련 유스케이스"는 묶음 헤더 아래 **ID / 유스케이스명** 2개 하위 컬럼.
> "개념 클래스 설명" 컬럼 값 = **Boundary / Control / Entity** 구분(BCE 분류). Boundary·Control은 속성 `-`, Entity는 속성을 나열.

### 표 2 — 개념 클래스도 (서브시스템별 작성)
헤더 키-값 블록:
| 라벨 | 값 | 라벨 | 값 |
|---|---|---|---|
| 개념 클래스도 ID | (값) | 개념 클래스도명 | (값) |
| 관련 서브시스템 ID | (값) | 관련 서브시스템명 | (값) |
| 관련 UCD ID | (값) | 관련 UCD명 | (값) |

그 아래 **개념 클래스 다이어그램**(Boundary→Control→Entity 관계 화살표).

## 1-4. 항목 설명

> PDF에 항목별 설명 문단 없음(사례만 제시). 컬럼 의미는 양식·사례에서 도출됨:
> 개념 클래스 ID(식별자), 개념 클래스명, 개념 클래스 설명(=BCE 구분), 속성(Entity만 나열), 관련 유스케이스 ID/명(연결된 UC). 클래스도는 ID/명 + 관련 서브시스템 + 관련 UCD + 다이어그램. **세부 항목 정의가 필요하면 PDF 확인 필요.**

### 코드 명명 패턴 (PDF 사례)
- 개념 클래스 ID: `SS_CC_NNN-NN` (CC=Conceptual Class)
- 개념 클래스도 ID: `SS_CCD_NNN` (CCD=Conceptual Class Diagram)
- 관련 UC/UCD: `SS_UC_NNN-NN` / `SS_UCD_NNN`

## 1-6. 함정 / 주의

- **선택 산출물**: 필수가 아님. 분석이 복잡하거나 객체모델 검증이 필요한 프로젝트에서만 추가.
- BCE 분류를 정확히: Boundary/Control은 속성을 `-`로, Entity만 속성을 나열한다.
- 목록·클래스도 모두 **서브시스템 단위**로 작성한다.
- PDF에 목적·방법·항목 설명 문단이 없어 사례 기반 해석이므로, 정식 정의가 필요한 부분은 **PDF 확인 필요**로 명시했다.

## 1-7. KLID 프로젝트 적용 메모

- 필수 산출물(III장)은 반드시 작성, 본 산출물은 KLID 프로젝트 판단으로 추가(현재 선택).
- D8(데이터베이스 설계서 등) 작성 시 "ERD와 개념적 클래스도를 비교"하는 참조 산출물로 활용 가능.
- KLID 도입 시 코드 체계 권장: **`KLID-AT-CC-NNN`**(개념 클래스), **`KLID-AT-CCD-NNN`**(개념 클래스도). 라벨링/검수/배치 등 KLID 도메인 단위로 BCE 분류 작성.

> PDF 원문: "용어집이 필요한 경우에 **분석단계 산출물로 추가하여 작성**할 수 있다." (선택)

## 2-1. 작성 목적 (PDF 근거)

PDF는 [작성사례]만 제시(별도 목적·방법·항목 설명 문단 없음). 사례 양식에서 도출: 프로젝트에서 사용하는 **용어를 표준화·정의**하여 이해관계자 간 의미 혼선을 방지하는 분석단계 보조 산출물이다.
> 명시적 목적문은 PDF에 없음 — 정식 정의 필요 시 **PDF 확인 필요**.

## 2-6. 함정 / 주의

- **선택 산출물**: 필수 아님. 도메인 용어가 많거나 표준화가 필요한 프로젝트에서 추가.
- 영문 약어 ≠ 별칭: 약어는 표준 약칭, 별칭은 시스템/코드에서 쓰는 alias로 구분 기재.
- PDF에 목적·방법·항목 설명 문단이 없어 사례 기반 해석이므로 정식 정의는 **PDF 확인 필요**.

## 2-7. KLID 프로젝트 적용 메모

- 필수 산출물(III장)은 반드시 작성, 용어집은 KLID 프로젝트 판단으로 추가(현재 선택).
- KLID는 행안부 공통표준용어(`gov_term_search`)를 적용하므로, 용어집 추가 시 **표준용어 검증과 병행**한다(영문명·약어를 표준용어/단어사전에 정합).
- KLID 도입 시 라벨링·검수·비식별·배치 등 도메인 용어를 우선 등재하고, LogiCraft 프로그램 용어사전(`program_glossary_*`)과 동기화 검토.
