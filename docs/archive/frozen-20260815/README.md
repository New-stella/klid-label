## 왜 옮겼나

**낡아서 판정에 끼어들면 안 되기 때문이다.** LogiCraft 도메인 감사(2026-08-14~15, 14도메인 ×
10차원 = 140 에이전트, 발견 1,263건)에서 이 산출물들이 구현·ITEM 과 어긋난 것이 반복 확인됐다.

실측 사례 — `KLID_AT_요구사항추적표.md` **주1**:

> *"비식별 옵션 설정은 저작도구 전용 화면 없이 외부 비식별 솔루션이 제공하는 옵션 관리 화면에서
> 설정하고 그 결과가 위탁 요청에 반영되는 운영 동선으로 처리한다."*

그런데 실제로는 `frontend/src/features/sysconfig/components/DeidentConfigCard.tsx`(+ 전용 테스트)가
실재하고, 설정 키(`kpst.deid.masking-type` 등)도 시드돼 있으며, `SCREEN-025`·`UC-013`·`SEQ-013`
세 ITEM 이 일관되게 "저작도구가 제공"을 서술한다. **주1 쪽이 낡았다.**

이런 문서가 자동참조 경로(`docs/design/*.md`)에 있으면 하네스의 설계 baseline 게이트·서브에이전트
프롬프트가 **낡은 전제를 주입**한다. 실제로 감사 중 주입 전제가 **10회 어긋났다.**

## 격리 효과

- `/cc` 의 「설계 baseline 준수」 규칙과 `cc-design-verifier` 는 `docs/design/*.md` 부재 시
  **graceful SKIP** 된다 → 낡은 baseline 으로 drift 판정을 내리지 않는다.
- `docs/design/` 은 이제 비어 있으므로, LogiCraft **구현 키트**(`docs/design/{도메인슬러그}-{DOMAIN-ID}/`)를
  새로 내려받으면 그 경로가 깨끗하게 재사용된다.

## 언제 푸나 (해제 조건)

**감사 결함 수정이 전부 끝난 뒤 한 번에 맞춘다**(사용자 확정, 2026-08-15). 그 전에는
개별 문서를 찔러 고치지 않는다 — 부분 수정하면 어느 것이 정합됐고 어느 것이 안 됐는지
구분되지 않아, 지금 이 문서들이 신뢰를 잃은 것과 같은 상태가 반복된다.

정합 시점의 진실원은 **실제 코드**다(사용자 확정: *"실제 코드를 기반으로 봐야할거야.
문서들은 너무 낡았어."*). 코드 → LogiCraft ITEM → 이 산출물 순으로 맞춘다.
