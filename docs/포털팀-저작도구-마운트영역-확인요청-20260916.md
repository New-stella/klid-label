# 포털 임베드 — 라벨링 화면 세로 공간 확대 요청

> 작성: 2026-09-16 | 저작도구 측 → 포털 측
> 대상: `/workspace/authoring` 마운트 슬롯(`.klid-authoring-slot`)의 세로 공간
> 실측 환경: 개발망 `https://192.168.102.103:38444/workspace/authoring/portal/label/1?source=upload&frame=5`
> (Chrome · 뷰포트 1470×697 · 루트 글꼴 10px)
> 관련: `INT-013`(포털 임베딩) · `SCREEN-029`(포털 라벨링 화면) · 포털 인계문서 `docs/authoring-mf-handover.md`

## 요청 한 줄

라벨링 화면이 세로 **455px** 만 쓰고 있어 캔버스가 **235px** 로 눌립니다.
**몰입 편집 화면에서 페이지 제목 줄과 상하 여백을 거두고, 그만큼 슬롯을 늘려 주시기를** 요청드립니다.

**저작도구 쪽 수정·재배포는 필요하지 않습니다.** 저작도구 화면은 슬롯 크기를 그대로 따라 그리므로
포털에서 슬롯이 커지면 그 자리에서 바로 커집니다.

## 1. 지금 상태 (실측)

뷰포트 697px 중 저작도구가 받는 것은 455px 이고, 나머지 239px 는 포털 화면 요소입니다.

|---|---:|---|

그 455px 안에서 라벨링 화면이 이렇게 배분됩니다.

- 우측 칸은 객체 목록 4줄까지만 보이고 속성·이미지 조절이 스크롤 뒤에 있습니다.

## 2. ★ `min-height` 숫자만 키우면 오히려 나빠집니다

지금의 `24rem` 은 임의 여백이 아니라 **위 §1 표의 합**이고, 그래서 슬롯 아래가 정확히 화면 끝에
닿습니다. 바깥 여백을 그대로 둔 채 슬롯만 키우면 **늘어난 만큼 프레임 줄과 재생 슬라이더가 화면
아래로 밀려나** 편집 중에 포털 페이지를 스크롤해야 합니다.

그래서 **여백을 거두고 그만큼 슬롯을 늘리는** 형태를 요청드립니다.
큰 작업은 아닐 것으로 봅니다 — 라벨링 화면을 감싸는 겹이 아래처럼 여러 층이고,
**그중 편집 화면에서 역할이 없는 층의 여백만 거두면** 됩니다.

```
뷰포트 697
└ 포털 GNB ............................................ 67
└ .klid-container.klid-page [data-wide] .......... 위 32 · 아래 80
  └ .klid-page-head  「저작도구 상세」 + 브레드크럼 ...... 36 (+ 간격 24)
  └ .klid-lnb-layout > .klid-lnb-body > .klid-authoring .. 0
    └ section.klid-authoring-slot .......... 패딩 24×2 · 테두리 1 · 모서리 16
      └ div.klid-portal-embed  ← 여기부터 저작도구
        └ 라벨링 화면 ................................ 1309 × 455
```

| 거둘 수 있어 보이는 자리 | 높이 |
|---|---:|
| 페이지 제목 「저작도구 상세」 + 브레드크럼 + 그 아래 간격 | 60 |
| 페이지 위 여백 | 32 |
| 페이지 아래 여백 | 80 |
| 슬롯 자체 패딩(24 × 2)·테두리 | 49 |
| **합계** | **약 221** |

저작도구 라벨링 화면은 **자기 머리 줄**(닫기 · 파일명 · 저장 상태 · 도움말)을 이미 갖고 있어
위쪽 페이지 제목 줄과 역할이 겹칩니다.

효과 추정 — `--klid-authoring-chrome` 을 **24rem → 6.7rem**(포털 GNB 만 남김) 수준으로 봤을 때:

| | 지금 | 반영 후 |
|---|---:|---:|
| 저작도구 상자 높이 | 455 | 약 630 (+38%) |
| 캔버스 높이 | 235 | 약 410 (+74%) |

1080p 최대화(뷰포트 약 900) 기준으로는 660 → 833 입니다.

**얼마나 거두실지는 포털 쪽 판단에 맡깁니다** — 일부만 거두셔도 그만큼 좋아집니다.

## 3. 화면별로 가르지 않으셔도 됩니다

`/workspace/authoring` 전체(목록·업로드·증강·라벨링·마킹)에 일괄 적용하셔도 저희는 괜찮습니다.
목록 화면은 카드 아래가 조금 비어 보일 뿐이고, 그 대가로 **「지금이 몰입 편집 화면인지」를 알리는
통로를 새로 만들 필요가 없습니다**(지금 저작도구에는 포털에 화면 전환을 알릴 수단이 없습니다).

화면별로 가르는 편이 낫다고 보시면 그 통로부터 함께 정해야 하므로 알려 주십시오.

---

## 4. 곁들여 확인 부탁드리는 것

- **푸터·페이지 스크롤** — 슬롯 아래에 포털 푸터 470px 가 있어 문서 전체가 1166px 이고
  **469px 만큼 페이지가 세로로 스크롤됩니다.** 편집 화면에서 캔버스 위에 굴린 휠이 포털 페이지를
  밀 수 있어, 이 화면에서는 푸터를 두지 않는 편이 좋아 보입니다. (필수는 아닙니다)
- **`contain: layout` · `overflow: hidden`** — 저희는 **유지하신다는 전제**로 맞추겠습니다.
  없애 달라고 요청드리지 않습니다(없애면 저작도구 판이 포털 GNB·좌측 메뉴를 덮습니다).
  나중에 빼시게 되면 저작도구의 모달·토스트 기준이 슬롯에서 뷰포트로 바뀌므로 미리 알려 주십시오.

폭은 이미 `[data-wide] { max-width: none }` 으로 해결돼 있어 요청드릴 것이 없습니다.

---

## 5. 회신 부탁드리는 내용

1. 여백을 거두고 슬롯을 늘리는 것이 가능한지, 가능하다면 어디까지 거두실지와 적용 시점
2. `/workspace/authoring` 전체에 일괄 적용할지, 화면별로 가를지(가른다면 전환 통로를 함께 정해야 합니다)
3. 몰입 편집 화면의 푸터·페이지 스크롤 처리
4. `contain: layout` · `overflow: hidden` 유지 여부

## 부록 — 재현·측정 절차

1. 포털에 로그인한 뒤 `/workspace/authoring/portal/label/1?source=upload&frame=5` 로 들어갑니다.
2. 개발자 도구 콘솔에서 아래를 실행하면 위 표의 수치가 그대로 나옵니다.

```js
const root = document.querySelector('[data-testid="labeling-page"]');
const slot = document.querySelector('.klid-authoring-slot');
console.table({
  viewport: { w: innerWidth, h: innerHeight },
  slot: slot.getBoundingClientRect().toJSON(),
  app: root.getBoundingClientRect().toJSON(),
  canvas: { w: root.querySelector('canvas').clientWidth, h: root.querySelector('canvas').clientHeight },
});
// 스크롤 뒤로 숨는 양
[...root.querySelectorAll('*')]
  .filter((e) => /auto|scroll/.test(getComputedStyle(e).overflowY) && e.scrollHeight - e.clientHeight > 8)
  .forEach((e) => console.log(e.className, e.clientHeight, '/', e.scrollHeight));
```

3. 실측일 기준 배포본의 관련 규칙은 다음과 같았습니다.

```css
.klid-authoring-slot{ --klid-authoring-chrome:24rem; contain:layout; overflow:hidden;
  min-height:40rem; padding:2.4rem; border:.1rem solid …; border-radius:1.6rem }
[data-wide] .klid-authoring-slot{ min-height:calc(100dvh - var(--klid-authoring-chrome)) }
[data-wide]{ max-width:none }
```
