# 포털 임베드 — 라벨링 화면 세로 공간 확대 요청

> 작성: 2026-09-16 | 저작도구 측 → 포털 측
> 대상: `/workspace/authoring` 마운트 슬롯(`.klid-authoring-slot`)의 세로 공간과 몰입 편집 화면 전환
> 실측 환경: 개발망 `https://192.168.102.103:38444/workspace/authoring/portal/label/1?source=upload&frame=5`
> (Chrome · 뷰포트 1470×697 · 루트 글꼴 10px)
> 관련: `INT-013`(포털 임베딩) · `SCREEN-029`(포털 라벨링 화면) · `ADR-012`(채널별 배포) · 포털 인계문서 `docs/authoring-mf-handover.md`

## 한 줄 요약

라벨링 화면이 **슬롯 안에 갇힌 채 세로 455px** 만 쓰고 있어 캔버스가 **235px**, 좌우 도구 칸은
**3분의 2 이상이 스크롤 뒤로 숨습니다.** 폭은 이미 해결돼 있으므로(`[data-wide] { max-width: none }`)
**세로 공간과 「몰입 편집 화면」 전환 신호** 두 가지만 요청드립니다. 저작도구 쪽에서 고칠 몫도
함께 적었습니다.

## 1. 실측 — 지금 화면이 쓰는 공간

뷰포트 697px 중 저작도구가 받는 것은 455px 이고, 나머지 239px 는 포털 화면 요소입니다.

| 구간 | 높이 | 비고 |
|---|---:|---|
| 포털 GNB | 67 | |
| 페이지 위 여백 | 32 | `.klid-page` padding-top |
| 페이지 제목 「저작도구 상세」 + 브레드크럼 | 36 | `.klid-page-head` |
| 제목 줄 ↔ 슬롯 사이 간격 | 24 | |
| **마운트 슬롯** | **457** | `min-height: calc(100dvh - 24rem)` |
| 페이지 아래 여백 | 80 | `.klid-page` padding-bottom |
| **합계** | **696** | 뷰포트 697 |

슬롯 안에서 저작도구가 실제로 그리는 상자는 **1309 × 455**(슬롯의 테두리 안쪽 박스)이고,
그 안의 배분은 이렇습니다.

| 영역 | 실측 | 필요한 높이 | 숨는 양 |
|---|---:|---:|---:|
| 머리 줄(파일명·저장 상태) | 56 | 56 | — |
| 본문(도구 칸 + 캔버스 + 객체 칸) | 279 | — | — |
| 프레임 줄 + 재생 슬라이더 | 120 | 120 | — |
| **캔버스(그림 그리는 면)** | **813 × 235** | — | — |
| 좌측 도구 칸 | 222 | 670 | **448 (67%)** |
| 우측 객체·속성 칸 | 238 | 840 | **602 (72%)** |

- 좌측 도구 칸은 「AI 보조」 묶음 머리에서 잘려 **AI 보조 항목 대부분이 처음부터 스크롤 뒤에 있습니다.**
- 우측 칸은 객체 목록 4줄까지만 보이고 속성·이미지 조절이 스크롤 뒤에 있습니다.
- 라벨링은 **캔버스를 보며 좌우 칸을 오가는 작업**이라, 세 영역이 동시에 보이지 않으면 조작이 왕복 스크롤이 됩니다.

### 페이지 자체도 세로로 스크롤됩니다

문서 전체 높이가 **1166px**(뷰포트 697)입니다. 슬롯 아래에 포털 푸터 **470px** 가 있어
**469px 만큼 페이지가 스크롤**됩니다. 몰입 편집 화면에서 바깥이 스크롤되면 캔버스 위에서 굴린
휠이 페이지를 밀어 편집 대상이 화면 밖으로 나갑니다.

## 2. 왜 이렇게 되나 — 원인은 셋이고, 그중 둘은 저작도구 몫입니다

### (1) 슬롯이 포털 화면 요소 24rem 을 빼고 시작합니다 — 포털 몫

`--klid-authoring-chrome: 24rem` 입니다. 그 24rem 의 내역이 위 §1 표이며,
이 중 **제목·브레드크럼(36) · 그 간격(24) · 페이지 상하 여백(112) · 슬롯 패딩(48)** 은
라벨링 화면에서는 회수할 수 있는 자리로 보입니다. 저작도구 라벨링 화면은 **자기 머리 줄**
(닫기 · 파일명 · 저장 상태 · 도움말)을 이미 갖고 있어 위쪽 제목 줄과 역할이 겹칩니다.

### (2) `contain: layout` 이 저작도구의 전체화면 판을 슬롯에 가둡니다 — 저작도구 몫

슬롯에 `contain: layout` 이 걸려 있어 그 안의 `position: fixed` 가 **뷰포트가 아니라 슬롯**을
기준으로 잡힙니다. 저작도구 라벨링 셸은 지금 `fixed; inset: 0` 으로 「화면 한 장」을 전제하는데,
그 전제가 여기서는 성립하지 않아 **슬롯 크기 그대로(1309×455) 눌립니다.**

**이 규칙을 없애 달라고 요청드리지 않습니다.** 없애면 저작도구 판이 포털 GNB·좌측 메뉴를 통째로
덮게 되는데, 그건 포털이 의도적으로 막아 두신 형태로 읽힙니다. 오히려 **저작도구가 「화면 한 장」
전제를 버리고 슬롯을 채우도록 고치는 것이 맞습니다** — 지금 우리 레이아웃이 상대 CSS 한 줄에
매달려 있는 상태이고, 그 줄이 있든 없든 깨지지 않게 만드는 것이 우리 책임입니다.

### (3) 저작도구 포털 셸이 슬롯 안에서 또 여백을 줍니다 — 저작도구 몫

슬롯 안쪽에서 우리 포털 셸이 위 32 · 아래 80 을 다시 더하고 있습니다(목록 화면 기준값).
몰입 편집 화면에서는 0 이어야 합니다.

---

## 3. 저작도구가 고칠 것 (요청 아님 · 우리 작업)

1. 포털 채널에서 라벨링 셸의 `fixed; inset: 0` 를 걷고 **슬롯 높이를 채우는 형태**로 바꾼다.
2. 몰입 편집 화면에서 우리 포털 셸의 본문 상하 여백(32 / 80)을 0 으로 한다.
3. 모달·토스트·도움말 패널이 `100vh`·`100vw` 로 계산하던 자리를 **슬롯 기준**으로 바꾼다.
4. 위 셋을 회귀 가드로 고정한다.

이 셋만으로도 지금보다 나아지지만, **슬롯이 455px 인 한 캔버스는 여전히 300px 대**입니다.
그래서 아래 요청을 함께 드립니다.

---

## 4. 포털에 요청드리는 것

### 요청 1 — 몰입 편집 화면에서 슬롯 여백을 회수해 주십시오

`--klid-authoring-chrome` 을 **24rem → 6.7rem 수준**(포털 GNB 만 남김)으로 낮추고,
그때 **페이지 제목·브레드크럼 · 페이지 상하 여백 · 슬롯 패딩·테두리·모서리 둥글기**를 함께
거두어 주시기를 요청드립니다. 이미 쓰고 계신 `data-wide` 기전을 한 단계 넓히는 형태면 충분해 보입니다.

효과 추정(이 창 기준, 뷰포트 697):

| | 지금 | 요청 반영 후 |
|---|---:|---:|
| 저작도구 상자 높이 | 455 | 약 630 (+38%) |
| 캔버스 높이 | 235 | 약 410 (+74%) |

1080p 최대화(뷰포트 약 900) 기준으로는 660 → 833 입니다.

### 요청 2 — 「몰입 편집 화면」을 알릴 통로를 함께 정해 주십시오

지금 저작도구에는 **포털에 화면 전환을 알릴 수단이 없습니다.** 목록 화면(내 작업·내 업로드·증강)은
지금 형태가 맞고, 라벨링·마킹 화면만 전체 높이가 필요합니다. 후보 셋을 적습니다 — 이름과 형태는
인계 창구 넷(`getAccessToken` 외)을 정할 때와 같은 합의가 필요합니다.

| 안 | 형태 | 평가 |
|---|---|---|
| **A (선호)** | Host 가 마운트 props 에 콜백을 하나 더 준다 — 저작도구가 화면이 바뀔 때 `normal` \| `immersive` 를 알림 | 소유가 분명하고 주소 규격에 묶이지 않음 |
| B | 저작도구가 슬롯 요소에 `data-*` 를 직접 쓴다 | 상대 요소를 우리가 만지는 형태라 이름이 바뀌면 조용히 깨짐 |
| C | Host 가 주소(`/portal/label/…`)로 판정한다 | 가장 빨리 되지만 **우리 라우트 규격을 포털이 복제**하는 형태 — 우리가 주소를 바꾸면 조용히 깨짐 |

당장 급하시면 **C 로 임시 적용하고 A 로 옮기는 것**도 저희는 받아들일 수 있습니다.
다만 그 경우 **저작도구가 주소를 바꿀 때 포털에 알린다**는 약속이 함께 필요합니다.

### 요청 3 — 몰입 편집 화면에서는 푸터와 페이지 스크롤을 두지 말아 주십시오

§1 마지막 항목입니다. 편집 화면 아래에 470px 푸터가 있어 페이지가 469px 스크롤됩니다.

### 확인 4 — `contain: layout` · `overflow: hidden` 을 앞으로도 유지하십니까

저희는 **유지하신다는 전제로** 레이아웃을 고치고 회귀 가드를 세우려 합니다(§3-1).
이견이 없으니 그대로 두셔도 됩니다. 다만 나중에 이 두 줄을 빼시게 되면 **저작도구의 모달·토스트
기준이 슬롯에서 뷰포트로 바뀌므로** 미리 알려 주십시오.

## 5. 검토했으나 요청하지 않은 안

| 안 | 요청하지 않는 이유 |
|---|---|
| `contain: layout` 제거 → 저작도구가 전체화면을 덮게 | 포털 GNB·좌측 메뉴가 가려짐. 포털이 의도적으로 막은 형태로 읽힘 |
| 저작도구를 iframe 전체화면으로 분리 | 임베딩 방식(`INT-013`) 자체를 바꾸는 일이라 범위가 다름 |
| 브라우저 Fullscreen API | 사용자 제스처가 매번 필요하고 포털에서 이탈한 느낌을 줌 |
| 라벨링 화면을 별도 탭·별도 주소로 여는 것 | 포털 안에서 작업한다는 전제(`ADR-013`)와 어긋남 |

## 6. 회신 부탁드리는 내용

1. **요청 1**(슬롯 여백 회수) 수용 가능 여부와 적용 시점
2. **요청 2**(전환 신호 통로) — A · B · C 중 어느 형태로 할지, A 라면 prop 이름과 값의 형태
3. **요청 3**(몰입 편집 화면의 푸터·페이지 스크롤) 수용 가능 여부
4. **확인 4** — `contain: layout` · `overflow: hidden` 유지 여부

## 부록 — 재현·측정 절차

1. 포털에 로그인한 뒤 `/workspace/authoring/portal/label/1?source=upload&frame=5` 로 들어갑니다.
2. 개발자 도구 콘솔에서 아래를 실행하면 위 표의 수치가 그대로 나옵니다.

```js
const root = document.querySelector('[data-testid="labeling-page"]');
const slot = document.querySelector('.klid-authoring-slot');
console.table({
  viewport: { w: innerWidth, h: innerHeight },
  slot: slot.getBoundingClientRect().toJSON(),
  app: root.getBoundingClientRect().toJSON(),
  canvas: { w: root.querySelector('canvas').clientWidth, h: root.querySelector('canvas').clientHeight },
});
// 스크롤 뒤로 숨는 양
[...root.querySelectorAll('*')]
  .filter((e) => /auto|scroll/.test(getComputedStyle(e).overflowY) && e.scrollHeight - e.clientHeight > 8)
  .forEach((e) => console.log(e.className, e.clientHeight, '/', e.scrollHeight));
```

3. 실측일 기준 배포본의 관련 규칙은 다음과 같았습니다.

```css
.klid-authoring-slot{ --klid-authoring-chrome:24rem; contain:layout; overflow:hidden;
  min-height:40rem; padding:2.4rem; border:.1rem solid …; border-radius:1.6rem }
[data-wide] .klid-authoring-slot{ min-height:calc(100dvh - var(--klid-authoring-chrome)) }
[data-wide]{ max-width:none }
```
