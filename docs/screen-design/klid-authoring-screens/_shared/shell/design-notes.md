## § 1. 증거 — 메뉴 항목 전수 대조

NAV-001 의 링크 노드는 **30개**이고, 그중 주 메뉴에 노출되는 것은 **19개**다.
(전체 30 − `[폐기]` 3 − 다른 화면에서 눌러 들어가는 항목 8 = 19)

⚠ **구 수치 폐기** — *"링크 노드 24개 · 노출 14개 (24 − 폐기 1 − 미노출 9)"*. 관리자 역할 분리로
「관리자」 묶음 7노드가 신설되고 「업로드」 묶음이 폐기되면서 셋 다 바뀌었다.

### 1-A. 관리자 기준 — 사양 19개 vs 시안 19개

직접 읽어 대조했고, 노출 역할 축은 구현 선언과도 일치함을 확인했다. 잘림·넘침 같은 렌더 수치는

| 공지 상세 · 공지 작성 · 공지 수정 | LNB 미노출 | 주 메뉴에 없음 · 참고 패널에 기재 |

**참고 패널에 남긴 이유**: 지우면 다음 사람이 "빠뜨린 것"으로 보고 메뉴에 되살린다.
패널은 실제 화면이 아니라 문서화 구간임을 점선 테두리와 「참고」 배지로 표시했다.

⚠ **시안 참고 패널의 `라벨 이력` 은 NAV-001 v26 의 링크 노드에 없다** — 패널이 9줄인데 사양은
8개인 이유다. 사양에서 빠진 것인지 시안이 앞서 그린 것인지 확인하지 못했다. **보고만 하고
패널에서 지우지 않았다** — 지우는 쪽이 되돌리기 어렵다.

### 1-C. 역할별 개수

| 역할 | 묶음 | 항목 | 사라지는 것 |
|---|:--:|:--:|---|
| 관리자 (ROLE-004) | 8 | **19** | — |
| 검수자 (ROLE-001) | 7 | **13** | 「관리자」 묶음이 **통째로**(제목까지) |
| 작업자 (ROLE-002) | 4 | **4** | 영상·데이터·관리·관리자 묶음이 **통째로**(제목까지) + 검수 목록 + 전체 구축 현황 |

**역할 계층은 「관리자 → 검수자」 한 단계**다. 관리자는 검수자 메뉴 13개를 그대로 물려받고
「관리자」 묶음 6개만 더 갖는다(13 + 6 = 19) — 관리자 전용 항목을 검수자 자리에 섞어 두지 않는다.

작업자에게서 사라지는 항목은 9개이며(13 − 4), 그중 7개가 영상·데이터·관리 묶음에 속해
그 묶음들은 항목이 0이 되어 **그룹 제목까지 렌더하지 않는다**(UI-036 Lnb: "보이지 않는 항목은 렌더하지 않는다").
「관리자」 묶음도 같은 규칙으로 검수자·작업자 양쪽에서 제목째 사라진다.

⚠ **구 수치 폐기** — *"검수자 7묶음·**14**항목 / 작업자 4묶음·**5**항목"*. 관리자 역할 분리 전 값이다.

## § 3. 증거 — 브라우저 실렌더 (1440 / 1280 두 폭)

Chromium 실렌더에서 `getBoundingClientRect` · `scrollWidth` 로 실측했다.

### 3-A. 셸 치수 — 두 폭 모두 사양대로

| 측정 | 1440px | 1280px | 사양 |
|---|---:|---:|---|
| 헤더 높이 | **56px** | **56px** | 56px 고정 ✓ |
| 주 메뉴 폭 | **240px** | **240px** | 240px 고정 ✓ |
| 본문 영역 폭 | 1185px | 1025px | (나머지 전부) |
| 주 메뉴 항목 높이 | 전부 **44px** | 전부 **44px** | DS hit area 44px 하한 ✓ |
| 문서 가로 오버플로 | **없음** | **없음** | — |
| 푸터가 프레임 하단에 붙는가 | **예** | **예** | UI-034 ✓ |
| 주 메뉴 세로 스크롤(검수자 14항목) | **없음**(843/843) | **없음** | — |

주 메뉴 폭이 두 폭에서 **동일하다는 것이 요점**이다 — SHELL-001 이 금지한 접기·서랍 전환을
넣지 않았으므로 `--lnb-w` 를 바꾸거나 `.lnb` 를 숨기는 미디어쿼리를 **한 줄도 두지 않았다.**

### 3-B. ⚠ 발견 1 — 검수자 주 메뉴가 세로로 딱 맞아 여유가 없다

⚠ **아래 수치는 관리자 역할 분리 이전(검수자 14항목) 실측이며 이번 갱신에서 다시 재지 않았다.**
지금 검수자는 13항목이라 조금 줄었고, 반대로 **관리자는 19항목이라 더 빡빡하다** — 잘림·스크롤
경향은 관리자 쪽에서 더 심해지는 방향이다. 정확한 값은 재측정이 필요하다.

검수자 기준 주 메뉴 콘텐츠 높이는 **843px**(14항목 × 44 + 묶음 제목 6개 + 상하 여백)이고,
시안 프레임의 주 메뉴 가용 높이도 **843px** 라 **여유가 0px** 다.

- 이 시안은 프레임 높이를 900px 로 두어 14개가 전부 보이지만, **실제 브라우저는 그렇지 않다.**
  1440×900 화면에서 브라우저 크롬(탭·주소창)을 빼면 뷰포트 높이는 보통 **760~790px** 이라
  주 메뉴 가용 높이는 **704~734px** 이 되어 **관리 묶음 뒷부분 3~4개가 잘리고 스크롤된다.**
- **결함이 아니라 사양의 귀결이다** — UI-036 Lnb 가 `overflow-y: auto` 를 이미 규정하고 있어
  잘리면 스크롤되도록 설계돼 있다. 다만 **검수자에게 「관리」 묶음이 첫 화면에서 안 보일 수 있다**는
  사실은 셸 사양이 명시하지 않은 부분이라 기록해 둔다.
- 시안에서 이 여유를 만들기 위해 한 조정은 **묶음 사이 여백 제거**(묶음 제목 자체의 위 여백으로 충분)와
  **주 메뉴 상하 여백 12px → 8px** 두 가지이며, 둘 다 토큰 값 안에서만 움직였다.

### 3-C. ⚠ 발견 2 — 대시보드 표가 셸 안에서 가로로 넘친다 (고치지 않음)

**SCREEN-011 시안을 고치지 말라는 지시에 따라 관찰만 하고 손대지 않았다.**

| 폭 | 본문 영역 | 「최근 완료 영상」 표 | 「내 작업 현황」 표 |
|---:|---:|---:|---:|
| 1440px | 1170px | **22px 넘침** | 0 |
| 1280px | 1010px | **102px 넘침** | **22px 넘침** |

- 넘친 만큼은 카드 안의 `.table-wrap`(`overflow-x: auto`) 안에서 가로 스크롤되므로
  **페이지 전체가 가로로 밀리지는 않는다.** 대신 1280px 에서 「완료일」 열이 `08-1…` 로 잘려 보이고
  「진행률」 막대도 오른쪽 끝에 붙는다(스크린샷으로 확인).
- **원인은 시안 결합이 아니라 미디어쿼리의 기준축이다.** SCREEN-011 CSS 는 `max-width: 1279px`
  에서 표를 1열로 접는데 이 조건은 **뷰포트 폭** 기준이다. 주 메뉴 240px 을 뺀 **본문 폭**은
  뷰포트보다 항상 240px 작으므로, 뷰포트 1280px(=접기 직전)일 때 본문은 1010px 밖에 안 되는데도
  2열을 유지해 최악이 된다. 뷰포트 1279px 이면 1열로 접혀 오히려 괜찮아진다.
- SCREEN-011 시안을 단독으로 열면(셸 없음) 본문 폭이 뷰포트와 같아 이 문제가 **드러나지 않는다.**
  셸과 합성해야만 보이는 문제라 이번 합성본의 수확이다.
- **고치는 방법은 SCREEN-011 담당 몫**이다. 방향만 적으면 뷰포트 기준 미디어쿼리 대신
  컨테이너 기준(`container-type: inline-size` + `@container`)으로 바꾸거나,
  접기 임계를 주 메뉴 폭만큼 올리는(1279 → 1519) 두 갈래다.

### 3-D. 오탐으로 확인한 것

`scrollWidth > clientWidth` 스캔에 걸렸으나 실제 넘침이 아닌 항목:

- `.skeleton` 8건 — 로딩 반짝임 의사요소(`::after`)의 `translateX(100%)` 때문이며 `overflow: hidden` 으로 잘린다.
- `.sr-only` 2건 — 스크린리더 전용으로 1px 로 클립한 표 캡션. 의도된 것이다.

## § 4. 해석 — 결정과 근거

### 4-A. 역할 분기를 어떻게 표현했는가

**두 파일이 서로 다른 역할을 주 렌더로 삼는다. 의도된 것이며 근거가 다르다.**

| 파일 | 주 렌더 | 참고 패널 | 왜 |
|---|---|---|---|
| `design-shell.html` | **검수자**(7묶음 13항목) | 관리자 · 작업자 | 셸 단독 시안의 기준 시점은 검수자다. 상위집합은 관리자(19)이지만 관리자 메뉴는 **검수자 메뉴 + 「관리자」 묶음**이라, 검수자를 주 렌더로 두어도 관리자 축은 참고 패널의 묶음 하나만 더 보면 전부 드러난다 |
| `design-first-screen.html` | **작업자**(4묶음 4항목) | 검수자 · 관리자 | 안에 넣은 대시보드 본문이 **작업자 시점 렌더**(KPI 4장 + 「내 작업 현황」 표)다. 셸만 다른 역할로 두면 한 문서 안에서 헤더와 본문이 **앞뒤가 맞지 않는다**. 대시보드 본문을 바꾸려면 KPI 카드 1장과 표 1개를 지워야 하는데, 그건 「본문을 고치지 마라」 위반이다 |

두 파일 모두 **나머지 두 역할의 주 메뉴 전체를 참고 패널에 나란히** 두었으므로, 어느 파일을
열어도 19 · 13 · 4 세 벌을 한 화면에서 비교할 수 있다.

역할 차이는 **색이 아니라 항목의 존재 여부**로 드러난다(UI-036 사양). 역할 배지만
관리자 = primary / 검수자 = secondary / 작업자 = neutral 로 색을 달리했고, 색만으로 구분하지
않도록 배지에는 항상 한글 라벨을 함께 뒀다(DS do_rule).

⚠ **구 서술 폐기** — *"참고 패널은 작업자(또는 검수자) 한 벌"* · *"검수자 메뉴(14)가 작업자
메뉴(5)의 상위집합"*. 관리자 역할이 분리되면서 상위집합은 **관리자(19)** 가 됐고 참고 패널도
**두 벌**로 늘었다.

### 4-B. 사양을 따르되 판단이 필요했던 지점

| 지점 | 사양 | 처리 |
|---|---|---|
| **아이콘** | NAV-001 에서 아이콘이 선언된 노드는 **대시보드 하나뿐**(`LayoutDashboard`). 나머지 13개는 아이콘 필드가 없다 | 선언된 것만 그렸다. 대시보드는 유일한 **최상위 링크**(다른 13개는 전부 묶음의 자식)라 구조적으로도 구분되는 자리여서, 혼자 아이콘을 갖는 것이 어색하지 않다. 나머지 13개에 아이콘을 **지어내지 않았다** |
| **경로 표기** | 노드마다 `route` 가 있다 | 정적 파일이라 `href="#"` 로 두었다. 클릭 시 깨진 상대경로로 이동하는 것을 피하려는 것이고, 경로 자체는 사양이 진실원이라 시안에 복제하지 않았다 |
| **사용자 이름** | header 에 `Text 사용자 이름` · `Avatar 이름 첫 글자` | **실존 인물처럼 보이는 이름을 만들지 않았다.** `사용자01`(검수자) / `사용자02`(작업자) 로 두고 아바타 이니셜은 `사`. 참고 패널에 "예시 표기"임을 명시했다 |
| **푸터 문안** | UI-038 이 근거법령·운영기관·문의처 + 버전 + 발주처를 규정하고 "기관명·연락처 확정 전까지 자리표시 텍스트" 라고 명시 | 자리표시 그대로 뒀다 — `[운영기관명]` · `[담당부서]` · `[000-0000-0000]` · `[example@example.go.kr]` |
| **현재 위치 표시(브레드크럼)** | SHELL-001: "셸의 구성 요소가 아니다 — 본문 상단 페이지 헤더가 선택적으로 노출" | 셸에 두지 않았다. 합성본에서도 대시보드 본문이 브레드크럼을 갖지 않아 나오지 않는다 |
| **프레임 높이** | 사양에 없음 | `--frame-h: 900px` 은 **디자인 토큰이 아니라 시안 장치**다. 지면 문서에서 `position: fixed` 를 쓰면 헤더가 아래 참고 패널까지 덮어 문서가 읽히지 않아, 프레임 안에서 grid + 내부 스크롤로 같은 결과(헤더·메뉴 고정, 본문만 스크롤)를 만들었다. CSS 주석에 그 취지를 적었다 |

### 4-C. 사양 안에서 어긋나 있던 것 — ① 해소됨 · ② 미해소 (보고만 — 고치지 않았다)

**① NAV-001 본문 서술 ↔ `nodes` 배열 불일치**

✅ **해소됨.** 구 `description` 은 *"'관리' 그룹은 사용자 관리·시스템 설정·라벨 관리·프리셋 관리·
비식별 신고 **5개**다"* 라고 적었는데 `nodes` 배열의 관리 묶음에는 **6개**가 있어(이벤트유형 관리)
서술문과 배열이 어긋나 있었다. NAV-001 **v26** 에서 서술문이 갱신됐고, `사용자 관리` 가 「관리자」
묶음으로 옮겨가 **양쪽 모두 관리 묶음 5개**(시스템 설정·라벨 관리·프리셋 관리·비식별 신고·
이벤트유형 관리)로 일치한다. 시안도 그대로 5개를 그린다.

**② SHELL-001 ↔ DS-001 의 좁은 폭 처리 충돌**

| 출처 | 말하는 것 |
|---|---|
| SHELL-001 `description` | "좁은 폭에서 메뉴를 서랍으로 바꾸는 분기를 **두지 않는다**" |
| DS-001 `responsive_breakpoints.mobile` | "< 768px — LNB 를 **숨기고 오버레이로 전환**" |

- 지시가 "`shell-nav.md` 가 정한 구조를 바꾸지 마라"고 못박았으므로 **SHELL-001 을 따랐다** —
  주 메뉴를 숨기거나 폭을 바꾸는 미디어쿼리가 이 시안에 **한 줄도 없다**.
- 다만 DS-001 쪽 서술이 살아 있는 한, 다른 사람이 같은 자리에서 반대로 구현할 수 있다.
  둘 중 하나를 폐기하는 정합이 필요하다.

### 4-D. 확인하지 못한 것 (정보 부족)

- **묶음 제목의 시각 표현이 사양에 없다.** UI-036 은 "그룹 헤더 + 메뉴 링크로 구성"이라고만 하고
  크기·색·대문자 여부를 정하지 않는다. DS ladder 의 `label`(14px/600) + `--n-6` 으로 배정했으나
  이는 **내 판단**이며 사양이 지정한 값이 아니다.
- **역할 배지의 역할별 색이 사양에 없다.** SHELL-001 은 "역할별 색상 구분"이라고만 한다.
  secondary(검수자) / neutral(작업자) 배정은 내 판단이다. 포털 회원은 이 셸의 대상이 아니라 그리지 않았다.
- **주 메뉴 항목이 240px 을 넘칠 때의 처리가 사양에 없다.** 현재 항목 중 가장 긴 「이벤트유형 관리」가
  여유 있게 들어가 이번에는 문제가 없었으나, 더 긴 항목이 생기면 줄바꿈·말줄임 어느 쪽인지 정해야 한다.
- **DEV 빌드 전용 「개발 도구」 묶음**이 UI-036 설명에 언급되지만 NAV-001 노드에는 없다.
  운영 형상이 아니므로 그리지 않았다.

## § 5. LogiCraft 등록 가능 여부 — 조사 결과

**결론: 이 시안을 SHELL-001 에 직접 붙일 수단이 현재 스키마에는 없다. 등록하지 않았다.**

### 5-A. 조사한 것 (스키마 조회 — 읽기 전용, 쓰기 0건)

| 확인 | 결과 |
|---|---|
| `app_shell` 에 렌더 필드가 있는가 | **없다.** `allowed_fields` = title / description / device / default_navigation_id / applies_to_screens / header / sidenav / footer / nav_regions / based_on_adrs / status / brownfield — 렌더·이미지·HTML 계열 필드가 하나도 없다 |
| `screen_design`(SD)을 SHELL 에 붙일 수 있는가 | **없다.** `designs_screen` 이 정규식 `^SCREEN-\d+$` 로 잠겨 있어 `SHELL-001` 이 값으로 들어가지 않는다 |
| `designs` 링크 타입의 대상 | `to_type: screen_spec` **단일**. app_shell 로 향하는 링크 타입이 없다 |
| `app_shell` 이 가질 수 있는 링크 | references / belongs_to_domain / applies_to(→SCREEN) / references(→NAV) / based_on(→ADR) / migrated_from — **디자인 산출물로 향하는 링크가 없다** |
| SHELL-001 의 현재 렌더 | **0건** (그래서 이 작업이 필요했다) |

### 5-B. 대안 3가지 — 제시만 하고 실행하지 않았다

| 안 | 방법 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **A. SCREEN-011 의 SD 에 렌더 하나 더 붙이기** | SCREEN-011 을 designs 하는 SD 를 만들고(현재 **미등록**), `renders[]` 에 `surface: page` 로 **합성본**을 추가. `label` 로 "셸 포함 — 로그인 후 첫 진입"임을 표시 | 스키마를 우회하지 않고 지금 바로 됨. 대시보드 디자인과 같은 자리에서 보임 | **셸 단독 시안은 여전히 갈 곳이 없다.** 셸이 대시보드에 종속된 것처럼 보임 |
| **B. 셸 전용 SCREEN 을 새로 만들고 그 SD 에 붙이기** | `screen_spec` 을 하나 만들어 SD 를 연결 | 셸 단독 시안도 등록됨 | **없는 화면을 만드는 것**이라 화면 목록이 오염된다. 화면정의서가 발주처 산출물이라 더 나쁘다. **권장하지 않음** |
| **C. 플랫폼에 스키마 확장 요청** | `app_shell` 에 렌더 필드를 추가하거나 `SD.designs_screen` 이 SHELL 을 받도록 | 제자리에 붙는 유일한 정공법 | 우리가 못 함. 회신을 기다려야 함 |

**권장은 A + C 병행**이다 — 지금은 A 로 합성본을 살려 두고, C 를 올려 셸 단독 시안이 제자리를 갖게 한다.
**어느 것도 사용자 확인 없이 실행하지 않았다.**

### 5-C. 등록 시 함께 넣어야 할 것 (실행 전 확인용)

- SD 렌더 업로드는 HTML + CSS 를 **분리**해서 올린다(`upload_design_render(html, css)`).
  합성본은 CSS 를 **두 개**(`design.css` + `design-dashboard.css`) 링크하므로 그대로는 안 되고,
  올릴 때 한 벌로 합치거나 셸 CSS 만 인라인해야 한다. **이 시안 파일은 그대로 두고 업로드본만 조정한다.**
- SHELL-001 · NAV-001 은 서버에서 **`stale: true`** 로 표시돼 있다(키트 205개 중 24개가 stale).
  **버전은 로컬과 라이브가 같아**(v6 / v10) 이 시안의 근거는 최신이지만,
  stale 표시가 남아 있는 동안 사양이 바뀔 수 있으므로 등록 전에 다시 대조하는 편이 안전하다.

### 6-A. 코드와 사양의 차이 3건 (사양을 따랐다)

구현 코드는 확정 사양보다 낡을 수 있으므로, 요소의 존재·위치는 **사양**을 따랐다.

| 차이 | 코드 | 사양(NAV-001) | 시안 |
|---|---|---|---|
| 이벤트유형 관리 | **없음** | 관리 묶음에 **있음** | 사양대로 **그렸다** |
| 대시보드의 자리 | 「대시보드」라는 **묶음 안**의 유일한 항목 | **최상위 링크**(묶음 없음) | 사양대로 **묶음 없이** 그렸다 |
| 영상 처리 현황 경로 | `/video/completed` | `/video/status` | 경로는 시안에 복제하지 않아 영향 없음 |

푸터 문안·헤더 구성은 코드와 UI-038 · SHELL-001 이 일치해 그대로 가져왔다.
다만 코드 푸터의 버전·발주 줄이 `gray-400` 이라 대비 미달인데, 시안은 `--n-6`(6.30:1)로 올렸다.
