# SD-011 (SCREEN-037 공지 수정 화면) — 관례 정합 노트

정본 파일: `design.css` + `design.html`
기준본(관례): SCREEN-009 `design/design.css`
같은 폴더의 `design-main.{html,css}` 는 서버 현재본의 로컬 미러이며 이번에 수정하지 않았다.

재디자인이 아니다. 바꾼 것은 ①색 토큰 이름 ②타이포 지정 방식 ③`lang="ko"` 뿐이고,
색·간격·구성요소·문구는 그대로다. **레이아웃은 한 줄도 바꾸지 않았다**(사유는 §4).

## 1. 색 토큰 — 이름 충돌 스케일의 안전한 변환

이 파일은 기준본과 **같은 접두어**(`--n-` `--p-` `--s-`)를 쓰면서 **스케일이 10단위**였다.
같은 이름이 정반대 색을 뜻하는 구간이 실재한다.

| 이름 | 이 파일(변환 전) | 기준본 |
|---|---|---|
| `--n-10` | `#e6e8ea` (거의 흰색) | `#131416` (가장 어두움) |
| `--p-10` | `#d8e5fd` | (기준본은 `--p-1`) |

### 변환 방법 — 문자열 순차 치환을 쓰지 않았다

순차 치환은 `--n-100 → --n-10` 이 다시 `--n-1` 로 **이중 변환**된다. 그래서:

1. 기준본 `:root` 를 파싱해 **hex → 기준본 토큰명** 역인덱스를 만들었다
2. 이 파일 `:root` 를 파싱해 **각 토큰의 값(hex)으로** 기준본 이름을 찾았다
3. 그렇게 얻은 old→new 사전을 만들고, 파일 전체에 정규식 `--[A-Za-z0-9_-]+` 로
   **토큰 이름 전체를 한 번에 매칭해 사전 조회로 치환**했다.
   최장 매칭이라 `--n-100` 은 통째로 잡혀 `--n-10` 이 되고, 결과를 다시 스캔하지 않으므로
   이중 변환이 원리적으로 불가능하다.

**값 기준 매핑의 결과**: 색 토큰 32개 전부가 기준본에 같은 hex 로 존재했고, 자릿수 규칙
(`10→1`, `100→10` …)과 **어긋난 자리는 한 건도 없었다**. SD-009 에서 나왔던
`--su-70`/`--wn-40` 류의 불일치는 이 파일엔 없다. 다만 그것은 **검증 결과이지 전제가 아니다** —
규칙이 아니라 값으로 찾은 뒤 확인한 것이다.

| 접두어 | 변환 |
|---|---|
| `--n-0/10/20/…/100` | `--n-0/1/2/…/10` |
| `--p-0/10/20/50/60/70` | `--p-0/1/2/5/6/7` |
| `--s-0/70` | `--s-0/7` |
| `--success-*` | `--su-*` (0/50/70 → 0/5/7) |
| `--warn-*` | `--w-*` (0/50/70 → 0/5/7) |
| `--error-*` | `--e-*` (0/50/60/70 → 0/5/6/7) |
| `--info-*` | `--i-*` (0/70 → 0/7) |
| `--surface-white` | `--bg-page` (둘 다 `#ffffff`) |
| `--dur-base` | `--duration-base` (기준본 이름) |

### 표면·경계 토큰 신설

`--bg-page` `--bg-alt`(=n-0) `--border`(=n-2) `--border-strong`(=n-4) 을 정의하고,
**값이 이미 그 단계이던 자리에만** 적용했다(치환해도 색이 바뀌지 않는 자리).

| 적용 | 자리 |
|---|---|
| `--bg-alt` | `.ne-state-ref` 배경 · `.attach-row` 배경 |
| `--border` | `.ne-state-ref` 점선 · `.ne-form-card` · `.ne-attach-card` · `.input`/`.textarea` |
| `--border-strong` | `.input:hover`/`.textarea:hover` |

**적용하지 않은 자리**
- `.checkbox { border: 1px solid var(--n-4) }` — 원본에 *"n-3(2.01:1)은 비텍스트 UI 3:1 미달이라
  n-4 로 컨트롤 경계 대비 확보"* 주석이 달려 있다. `--border-strong` 로 바꾸면 그 근거가 이름 뒤로
  숨는다. 이름만 rename 하고 **주석을 그대로 옮겼다**.
- `n-1` 경계 4곳(`.state-preview` · `.skeleton` · `.ne-form-actions` 상단선 · `.attach-row`)은
  `--border`(=n-2)로 바꾸면 **선이 진해져 시각이 달라진다**. `var(--n-1)` 그대로 뒀다.
- `.btn-ghost:hover { background: var(--n-0) }` — 표면이 아니라 hover 상태색이라 `--bg-alt` 를
  쓰지 않았다.

## 2. 타이포 — 사다리 유틸 `.t-*` 12종

CSS 에 사다리를 정의하고 **HTML 에서 클래스로 지정**한다(기준본 방식). 값은 기준본 verbatim.
원본의 `--fs-* --fw-* --lh-*` 21개 변수는 사다리가 대체하므로 전부 제거했다.

HTML 유틸 사용: `t-button` 8 · `t-caption` 9 · `t-label` 5 · `t-body-sm` 3 · `t-body-md` 2 ·
`t-title-lg` 1 · `t-title-sm` 1.

컴포넌트 CSS 에 남긴 `font-size` 는 **1건**뿐이다.

| 남긴 것 | 값 | 사유 |
|---|---|---|
| `.error-state-preview .title` | 15px/600 | **사다리에 없는 조합**(body-sm 은 15/400, label 은 14/600) |

기준본 자신도 사다리 밖 `font-size` 를 10건 갖고 있으므로 이건 관례 위반이 아니다.
`body`(또는 컨테이너) base font-size 는 **넣지 않았다** — 원본에 없고 기준본 SCREEN-009 에도 없으며,
넣으면 크기를 명시하지 않은 요소가 16px→17px 로 조용히 커진다.

## 4. 레이아웃 — 손대지 않았다 (의도적)

지시서 §5 의 두 결함 유형을 모두 찾아봤고 **이 화면엔 없다.**

- **(a) 내용이 폭을 지배** — 이 폼은 **세로 스택**이다. `.field { flex-direction: column }` 이고
  한 줄에 한 필드씩 놓이며, `.input`/`.textarea` 는 `width: 100%` 라 폭이 컨테이너
  (`max-width: 840px`)에서 내려온다. 도움말 문장이 폭 계산에 개입할 경로가 없다.
- **(b) `margin-left: auto`** — 파일 전체에 **0건**.
- **가로 flex 행의 밑단 정렬 붕괴**(SCREEN-024 에서 발견된 유형) — `align-items: flex-end` 가
  **0건**이다. `align-items: center` 인 행은 있으나(`.ne-header` · `.ne-attach-card__head` ·
  `.attach-row`) 이들은 자식 키가 변해도 중심 기준이라 어긋나지 않는다.
  실측으로 확인했다 — `li.attach-row` 는 높이 무변화(**dh 0**)이고, 그 안에서 키가 4px 커진
  `__name`·`__size` 는 위로 2~3px 이동했다(= 중앙 정렬 유지, 1px 은 반올림 오차).
  행 높이가 `min-height: 44px` 에 지배되므로 자식이 커져도 행이 밀리지 않는다.

**없는 결함을 만들지 않기 위해 아무것도 고치지 않았다.**

## 5. `--font-body` — 기준본 문자열로 교체 (가로 변화 11건 수용)

```css
--font-body: 'Pretendard GOV', -apple-system, 'Apple SD Gothic Neo', 'Noto Sans KR', sans-serif;
--font-mono: 'D2Coding', ui-monospace, SFMono-Regular, Menlo, Consolas, monospace;
```

원본은 여기에 `'Pretendard'`(비-GOV)와 `BlinkMacSystemFont` 가 더 있었다. **뺐다.**

**교체 사유** — 이미 정합돼 게시된 SD **6건 전부**(SD-002·004·012·013·014·015)가 위 문자열을
**verbatim** 으로 쓴다. 즉 관례는 *"`-apple-system` 을 포함할 것"* 이 아니라 **"이 문자열 그대로"**
이며, 9건이 서로 다른 스택을 갖는 것 자체가 이번에 없애려는 드리프트다.
(작업 중 한때 "원본 스택 유지" 로 판단했으나, 게시본 6건 실측 근거로 뒤집었다.)

두 문자열 모두 기준본 SCREEN-009 와 **바이트 일치**를 확인했다.

### 이 교체가 만드는 가로 변화 11건 — 전건

| 요소 | 변화 | 성격 |
|---|---|---|
| `h1` | dw **+1** | 제목 글자 폭 |
| `span.title` | dw **−1**, dh −1 | 오류 상태 제목 |
| `span.msg` | dw **−2** | 오류 상태 본문 |
| `span.req` ×2 | dw **−2** | 라벨의 필수 표시 `*` |
| `span.attach-row__name` ×3 | dw **+4** | 아래 설명 |
| `span.attach-row__size` ×3 | dx **+4**, dw **−4** | 아래 설명 |

1280px·480px 두 뷰포트 **모두 정확히 11건**이고, 폰트 교체 이전에 측정한 11건과 **건수·대상이 같다**
(그 이상 늘지 않았다).

`attach-row` 의 두 건은 **한 쌍**이다. `.attach-row__size`("1.2 MB" 등)는 `flex-shrink: 0` 이라
글자 폭이 4px 줄면 그만큼 오른쪽으로 밀리고, 남은 4px 을 `flex: 1 1 auto` 인 `.attach-row__name`
이 흡수한다. **행 전체 폭은 변하지 않는다**(`li.attach-row` dw 0).

### 왜 수용 가능한가

전부 **폰트 폴백 차이**다. 이 개발 기기에 비-GOV `Pretendard` 가 설치돼 있어, 제거 시 다른 face
(`-apple-system`)로 떨어지면서 글자 폭이 1~4px 달라진 것이다. 레이아웃 규칙·색·크기 지정은
한 줄도 바뀌지 않았고, 실제로 `fontSize`·`fontWeight`·`color`·`background`·`border*` 는 여전히
**전부 0건**이다. 배포 환경에는 `Pretendard GOV` 또는 시스템 폴백만 있으므로 해당하지 않는다.

> ⚠ **한계 — 확인하지 못했다.** 배포 환경에 비-GOV `Pretendard` 가 설치돼 있는지는 이 작업에서
> 확인할 수 없었다. 만약 설치돼 있다면 이 11건은 배포 환경에서도 나타난다. 다만 그 경우
> **게시된 SD 6건도 같은 조건**이므로 화면 간 불일치는 생기지 않는다.

## 6. 고치지 않고 기록만 남긴 관찰 2건

둘 다 **공지 작성(SCREEN-036) 등 같은 계열 화면에도 있을 수 있다.** 확인 필요.

### (1) 입력 경계 대비 미달 — WCAG 1.4.11

`.input` / `.textarea` 의 경계가 `n-2`(`#cdd1d5`)인데 순백 위 대비가 **1.54:1** 로
비텍스트 UI 기준 3:1 에 미달한다. 기준본 계열 화면(SCREEN-024)은 같은 사유로 입력 경계에
**진한 단계(`n-5`)** 를 쓰고 그 근거를 주석으로 남긴다.

**고치지 않았다** — 이번 작업의 통과 기준이 *"색·border 차이 0건"* 이라 색을 바꾸면
정합 작업의 판정을 스스로 깬다. 색 결정은 디자인 소관으로 올린다. CSS 에 `⚠ 대비 확인 필요`
주석만 남겼다. (같은 파일의 `.checkbox` 는 이미 이 사유로 `n-4` 를 쓰고 있어 **한 파일 안에서
컨트롤 경계 정책이 갈려 있다.**)

### (2) `.field:last-of-type` 이 아무것도 매칭하지 않는다 (死 규칙)

`.field:last-of-type { margin-bottom: 0 }` 은 **0개 요소에 적용된다.** `form` 의 마지막 `div`
형제가 `.ne-form-actions` 라 `:last-of-type` 이 그쪽을 가리키고, 그건 `.field` 가 아니기 때문이다.
브라우저 실측: `form > .field:last-of-type` 매칭 **0건**, 세 필드 모두 `margin-bottom: 24px`
(원본·정합본 동일).

**고치지 않았다** — 의도대로 고치면 마지막 필드와 액션 영역 사이 간격이 24px 줄어 **간격이 바뀐다**.
간격 변경은 이번 범위 밖이다.

> ⏩ **후속 스윕에서 이 규칙을 삭제했다** — 아래 §8-3 참조. 원래 의도는 여기 기록으로 남는다.

# 최종 정리 스윕 (#9) — 사용자 확정 4항 반영

앞의 §1~§7 은 **관례 정합** 라운드의 기록이고 그대로 유효하다. 아래 §8 은 그 위에 얹은
정리 스윕이며, 이번엔 **렌더가 의도적으로 바뀐다**(경계 색 1축).

## 8-1. 입력·셀렉트 경계 → `--border-strong` (렌더 변경 · 승인된 변화)

§6-(1) 에서 "고치지 않고 기록만 남긴다"고 했던 항목을 이번에 고쳤다.

| 자리 | 전 | 후 | 흰 배경 대비 |
|---|---|---|---|
| `.input` · `.textarea` 기본 경계 | `--border` (= n-2 `#cdd1d5`) | **`--border-strong`** (= n-4 `#8a949e`) | 1.54:1 → **3.08:1** (WCAG 1.4.11 통과) |
| `.input:hover` · `.textarea:hover` | `--border-strong` (n-4) | **`--n-5`** (`#6d7882`) | 3.08:1 → 4.51:1 |

**hover 를 올린 이유**: 기본이 `--border-strong` 이 되면서 hover 가 **같은 값**이 되어 상태 구분이
사라진다. 이 화면의 hover 는 경계색만 바꾸므로(배경 변화 없음) 그대로 두면 hover 선언이 무효가 된다.
지시서 §1 이 규정한 처리대로 한 단계(`n-5`) 올려 구분을 유지했다.

**`.checkbox` 는 값을 바꾸지 않았다** — 이미 `n-4`(3.08:1)였다. 다만 참조를 팔레트 직접 지정
(`var(--n-4)`)에서 별칭 `var(--border-strong)` 으로 통일했다(**값 동일 · 렌더 영향 0**).
이로써 §6-(1) 이 지적한 *"한 파일 안에서 컨트롤 경계 정책이 갈려 있다"* 가 해소된다.
같이 있던 주석의 토큰 표기 `n-30`/`n-40` 은 이 파일에 존재하지 않는 이름이라 `n-3`/`n-4` 로 정정했다.

**올리지 않은 것**: `.ne-form-card`·`.ne-attach-card`·`.ne-state-ref` 의 `--border`, `.attach-row`·
`.state-preview`·`.ne-form-actions` 상단선의 `n-1` — 전부 **카드·구획선이라 컨트롤이 아니다**(지시서 §1).

### 8-1b. 유색 표면 재점검 — 이 화면은 **추가 상향 없음**

목표가 토큰이 아니라 **"실제로 맞닿는 표면 대비 3:1"** 로 바뀐 뒤(사용자 확정) 전 컨트롤을
다시 실측했다. 감사기는 경계의 **안쪽(자기 배경)·바깥쪽(조상 불투명 배경) 양쪽을 재고 더 불리한
쪽**으로 판정하며, 흰 배경을 가정하지 않는다.

| 컨트롤 | 위치 | 안 / 밖 표면 | 최저 대비 |
|---|---|---|---|
| `.input` · `.textarea` | `.ne-form-card > form > .field` | `#ffffff` / `#ffffff` | **3.08 ✅** |
| `.btn-outline` ×4 | 헤더 · 오류 프리뷰 · 폼 액션 · 첨부 헤드 | `#ffffff` / `#ffffff` | 4.55 ✅ |

→ **유색 표면(`--bg-alt`·`--e-0`) 위에 놓인 경계형 컨트롤이 이 화면엔 없다.**
입력·텍스트영역은 흰 카드 안이라 `--border-strong` 으로 충분하다. `.attach-row`(배경 `--bg-alt`)
안의 삭제 버튼은 `.btn-ghost` 계열이라 **경계가 투명**해 이 축의 대상이 아니다.

**상태 역전 재점검 — `n-6` 승격 불필요.** 기본이 `n-4` 로 유지되므로 hover(`n-5`)와 겹치지 않는다.
(`기본 n-4 → hover n-5` 순서 유지.)

> ⚠ 감사기가 `span.checkbox.checkbox--checked` 를 "1.00:1" 로 표시하지만 **결함이 아니다** —
> 체크된 상태는 경계색과 면색이 둘 다 `--p-5`(`#256ef4`)라 안쪽 대비가 정의상 1.00 이다.
> 이 컨트롤의 실제 경계는 **면과 바깥 흰 표면의 경계이고 4.55:1** 로 통과한다. `.btn-primary` 도
> 같은 유형이다. "더 불리한 쪽" 규칙을 채움 컨트롤에 기계적으로 적용하면 오탐이 된다 — 손대지 않았다.
> 체크 해제 상태의 `.checkbox` 는 흰 면 + `--border-strong` 경계라 3.08:1 이다.

## 8-2. `color-scheme` 보정

`html { color-scheme: only light; }` 이 없어(정정 이전 작성분) 기준본 `SCREEN-009/design/design.css`
와 **같은 위치·형태**(리셋 블록 머리, `* { box-sizing }` 바로 아래)에 추가했다.
넣기 전 `grep -c color-scheme` = 0 으로 중복이 아님을 확인했다.
→ §3 의 *"관례상 넣지 않는다"* 는 **폐기**된 판단이다.

## 8-3. 死 규칙 삭제 — `.field:last-of-type`

§6-(2) 에서 실측한 매칭 0건 규칙 `.field:last-of-type { margin-bottom: 0 }` 을 **삭제**했다.
이번 스윕에서 다시 확인했다(브라우저 `querySelectorAll`): `.field:last-of-type` **0건** ·
`form > .field:last-of-type` **0건** · `.field` 3건.

**원래 의도(되살릴 수 있게 남긴다)**: 폼의 **마지막 필드 아래 여백 24px 을 없애려던 것**이다.
`form` 의 마지막 `div` 형제가 `.ne-form-actions` 라 `:last-of-type` 이 그쪽을 가리켜 성립하지 않았다.
의도대로 고치려면 `.field:last-of-type` 이 아니라 `.field:has(+ .ne-form-actions)` 또는
`.ne-form-actions` 의 `margin-top` 조정이 필요하다. **이번에 살리지 않았다** — 살리면 간격이 24px
줄어 눈에 보이는 변화가 되고, 그건 이번 승인 범위(대비·플레이스홀더·오타) 밖이다(지시서 §3).

## 8-4. 남은 매칭 0건 6건은 전부 보존 (§3 보존 사유)

|---|---|
| `.t-title-md` · `.t-body-lg` · `.t-nav-link` · `.t-mono` · `.t-display-sm` | 사다리 12종 카탈로그 — 관례가 12종 정의를 요구 |

## 8-5. 검사기의 사각 (수치와 함께 밝혀 둔다)

- **死 규칙 스캔**은 `design.html` **1개 렌더**만 대상으로 한다. 다른 화면에서 공유하는 정의는
  이 스캔으로 판정하지 않는다(그래서 위 6건을 사유 판단으로 보존했다).
- **명시도 눌림 스캔**은 상태 의사클래스 규칙을 건너뛰고 14개 속성만 본다
  (font-size/weight/line-height, color, background-color, border-top/bottom-color, margin, padding-left,
  text-align, width, height). 이 화면 결과는 **0건**이다.
- 미정의 `var()` 참조 **0건**(정의 49 / 참조 32).
- **死 규칙 스캔의 `:not(:disabled)` 파싱 버그**를 발견해 수정 후 재실행했다(수정 전에는
  `:hover:not(:disabled)` 계열이 어느 버킷에도 안 잡히고 조용히 `ERR` 로 빠졌다).
- **명시도 눌림 스캔**은 조정자가 지적한 함정 2건을 막고 재실행했다 —
  ① `*, *::before, *::after { transition: none !important; animation: none !important }` 주입
  (안 막으면 전환 대상 속성이 전부 "무효"로 오판된다) → 결과 **여전히 0건**.
  ② `getComputedStyle().cssText` 미사용(전부 `getPropertyValue`). 이 Chromium 에서
  `cssText.length === 0` 임을 직접 확인했다.

## 8-5b. `viewbox`(소문자) — 지시서 §4(b) 전제가 틀렸고, 표기를 정규화했다

지시서는 *"소문자면 속성이 무시돼 스케일링이 안 된다"* 고 했으나 **HTML 문서에서는 사실이 아니다.**
HTML 파서가 외래 요소(SVG) 속성의 대소문자를 보정해 DOM 에는 `viewBox` 로 들어간다.
브라우저 실측: 속성명 `viewBox` · `viewBox.baseVal = 0 0 24 24` · 아이콘 18×18/24×24 정상.
(다른 담당도 독립적으로 같은 결론에 도달해 확정됐다.)

따라서 **"고치면 깨진다"가 아니라 "고쳐도 아무 일이 없다"** 이고, 조정자 지시대로 표기를
정규화했다 — `viewbox=` → `viewBox=` **11곳**. 검증: 파일 길이 7087 → **7087**(동일),
되돌리면 원문과 **바이트 동일**(이 속성 외 문자 차이 0), `compare-render` 결과가 정규화
**전/후 완전 동일**. 미러(`design-main.html`)는 소문자 그대로 두었다(읽기 전용).
