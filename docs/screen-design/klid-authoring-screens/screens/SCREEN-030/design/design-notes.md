# SD-007 (SCREEN-030 공지 목록 화면) — 관례 정합 노트

정본 파일: `design.css` + `design.html`
기준본(관례): SCREEN-009 `design/design.css`
같은 폴더의 `design-main.{html,css}` 는 서버 현재본의 로컬 미러이며 **이번에 수정하지 않았다**.

재디자인이 아니다. 바꾼 것은 ①색 토큰 이름 ②타이포 지정 방식 ③`lang="ko"` + `color-scheme`
④`--font-body`/`--font-mono` 스택 뿐이다. **레이아웃·색·간격·구성요소·문구는 한 줄도 바꾸지 않았다**
(결함 수정 0건 — 사유는 §6).

---

## 1. 색 토큰 — "이름 충돌" 유형이었다

이 파일은 기준본과 **같은 접두어**(`--n-` `--p-` `--s-`)를 쓰면서 **스케일이 10단위**였다.
같은 이름이 정반대 밝기를 뜻하는 구간이 실재했다.

| 이름 | 이 파일(변환 전) | 기준본 |
|---|---|---|
| `--n-10` | `#e6e8ea` (거의 흰색) | `#131416` (가장 어두움) |
| `--p-10` | `#d8e5fd` | `#0b50d0` |
| `--s-10` | `#d6e0eb` | `#02162c` |

### 변환 방법 — 문자열 순차 치환을 쓰지 않았다

순차 치환은 `--n-100 → --n-10` 의 **결과가 다시** `--n-10 → --n-1` 규칙에 걸려 **이중 변환**된다
(`--n-100 → --n-1`). 그래서 다음 순서로 했다.

1. 기준본 `:root` 를 파싱해 **hex → 기준본 토큰명 역인덱스**를 만들었다.
   기준본 색 토큰 **78개에 중복 hex 가 하나도 없어** 역인덱스가 1:1 로 성립했다(실측).
2. 이 파일 `:root` 를 파싱해 **각 토큰의 값(hex)으로** 기준본 이름을 찾았다.
   자릿수 규칙이 아니라 **값**으로 찾은 이유는, 원본 파일들의 토큰 이름이 DS 스케일과 어긋나 있을 수
   있기 때문이다(SD-009 에서 `--wn-40`·`--su-70` 2건이 실제로 어긋나 있었다).
3. 치환은 정규식 `--[A-Za-z0-9_-]+` 로 **파일 전체를 한 번만 훑으며 사전 조회**로 바꿨다.
   정규식이 최장 매칭이라 `--n-100` 이 통째로 잡혀 `--n-10` 이 되고, **그 출력이 다시 입력으로
   돌아오지 않으므로 이중 변환이 원리적으로 불가능**하다.
4. 최종 판정은 **hex 다중집합 완전일치**(주석 제외)로 했다 — §7.

**값 기준 매핑의 결과**: 색 토큰 **38개 전부**가 기준본에 같은 hex 로 존재했고, 자릿수 규칙과
**어긋난 자리는 한 건도 없었다**. 다만 이것은 **검증 결과이지 전제가 아니다** — 규칙으로 옮긴 뒤
확인한 것이 아니라, 값으로 찾은 뒤 규칙과 우연히 일치함을 확인한 것이다.

| 접두어 | 변환 |
|---|---|
| `--n-0/10/20/…/100` | `--n-0/1/2/…/10` |
| `--p-0/10/20/50/60/70` | `--p-0/1/2/5/6/7` |
| `--s-0/10/50/70` | `--s-0/1/5/7` |
| `--success-0/50/60/70` | `--su-0/5/6/7` |
| `--warn-0/50/60/70` | `--w-0/5/6/7` |
| `--error-0/50/60/70` | `--e-0/5/6/7` |
| `--info-0/50/60/70` | `--i-0/5/6/7` |
| `--surface-white` | `--bg-page` (둘 다 `#ffffff`) |
| `--dur-base` / `--dur-fast` | `--duration-base` / `--duration-fast` (기준본 이름) |

### 기준본에 없는 값 1건 — 그대로 뒀다

`--row-hover: #FFFBEB`. 지시서 §4 가 명시한 **DS 정본이 규정한 고정값**(표 행 hover 표면)이라
이름·값 모두 유지하고 근거 주석도 그대로 옮겼다.

### 미사용 토큰도 지우지 않았다

`--i-0/5/6/7` · `--su-5/6` · `--w-5/6` · `--e-0/6/7` · `--p-1/2` · `--s-1/5` · `--n-8` ·
`--shadow-md/lg` · `--sp-2xl` · `--duration-fast` 는 이 화면에서 참조되지 않는다. **원본에서도
참조되지 않았고**, 지우면 hex 다중집합이 달라져 §7 의 판정 자체가 성립하지 않는다. 그대로 뒀다.

### 표면·경계 토큰 신설

`--bg-page` `--bg-alt`(=n-0) `--border`(=n-2) `--border-strong`(=n-4) 을 정의하고,
**값이 이미 그 단계이던 자리에만** 적용했다(치환해도 색이 1비트도 바뀌지 않는 자리).

| 적용 | 자리 |
|---|---|
| `--bg-alt` | `.nl-filter` 배경 |
| `--border` | `.input`/`.select-trigger` 경계 · `.btn-secondary` 경계 · `.nl-table-card` 경계 · `.nl-table thead th` 하단선 · `.state-showcase` 상단 점선 |
| `--border-strong` | `.input:hover`/`.select-trigger:hover` 경계 |

**적용하지 않은 자리 (의도)**

- `n-1` 경계 4곳(`.nl-filter` 테두리 · `.nl-table-scroll` · `.nl-table tbody td` 구분선 ·
  `.state-preview`)은 `--border`(=n-2)로 바꾸면 **선이 진해져 시각이 달라진다**. `var(--n-1)` 유지.
- `.btn-secondary:hover`/`.btn-ghost:hover`/`.page-btn:hover` 의 `background: var(--n-0)` 은
  표면이 아니라 **hover 상태색**이라 `--bg-alt` 를 쓰지 않았다.
- `.status-badge--draft` 배경 · `.skeleton` 배경의 `n-1` 도 상태·플레이스홀더 색이라 그대로.
- `.nl-row-chevron { color: var(--n-4) }` — 원본에 *"n-3(2.01:1)은 non-text UI 3:1 미달 —
  n-4(3.08:1)로 교체"* 라는 **접근성 근거 주석**이 달려 있다. `--border-strong` 로 바꾸면 그 근거가
  이름 뒤로 숨는다(그리고 border 가 아니라 아이콘 색이다). 이름만 rename 하고 **주석을 그대로 옮겼다**.
- `.input::placeholder { color: var(--n-6) }` 의 AA 근거 주석도 동일하게 보존했다.

## 2. 타이포 — 사다리 유틸 `.t-*` 12종

CSS 에 사다리를 정의하고 **HTML 에서 클래스로 지정**한다(기준본 방식). 값은 기준본 verbatim.
원본의 `--fs-* --fw-* --lh-*` **24개 변수는 사다리가 대체하므로 전부 제거**했다(잔재 0건).

HTML 유틸 사용 **57곳**: `t-body-md` 30 · `t-label` 17 · `t-caption` 5 · `t-button` 3 ·
`t-title-lg` 1 · `t-title-sm` 1.

> `t-body-md` 30 = `<td>` 27 + `<input>` + `<select>` + 헤더 `<p>`
> `t-label` 17 = `<th>` 3 + `.field__label` 2 + `.pin-badge` 2 + `.status-badge` 9 + `.state-showcase__label` 1

**표 헤더 클래스는 `<th>` 에 직접 달았다** — `<tr>` 에만 걸면 UA 기본 `font-weight: bold` 가
상속을 이겨 굵기만 어긋난다.

컴포넌트 CSS 에 남긴 `font-size` 는 **4건**이며 전부 **사다리 밖 조합**이다.

| 남긴 것 | 값 | 사유 |
|---|---|---|
| `.btn-sm` | 14px/500 | label 은 14/600, button 은 17/500 — 둘 다 아니다 |
| `.page-btn` | 14px/500 | 위와 동일 |
| `.error-state-preview .title` | 15px/600 | body-sm 은 15/400 |
| `.empty-state-preview .title` | 15px/600 | 위와 동일 |

기준본 자신도 사다리 밖 `font-size` 를 10건 갖고 있으므로 관례 위반이 아니다.
`body`(또는 컨테이너) base font-size 는 **넣지 않았다** — 원본에도 기준본에도 없고, 넣으면 크기를
명시하지 않은 요소가 16px→17px 로 조용히 커진다.

- `html { color-scheme: only light; }` 를 **넣었다**(기준본 SCREEN-009 와 동일).

## 4. `--font-body` — 기준본 문자열로 교체 (가로 변화 95건 수용)

```css
--font-body: 'Pretendard GOV', -apple-system, 'Apple SD Gothic Neo', 'Noto Sans KR', sans-serif;
--font-mono: 'D2Coding', ui-monospace, SFMono-Regular, Menlo, Consolas, monospace;
```

원본은 여기에 `'Pretendard'`(비-GOV)와 `BlinkMacSystemFont` 가 더 있었다. **뺐다.**
두 문자열 모두 기준본 SCREEN-009 와 **바이트 일치**를 확인했다.

### 이 교체가 만드는 변화를 실측으로 분리했다

폰트 스택만 원본으로 되돌린 **대조군**(`probe`)을 만들어 같은 도구로 재측정했다.

| 대조 | 가로 변화 | 세로 변화 |
|---|---|---|
| 원본 vs 정합본 | **95건**(1280) / 92건(480) | 30건 / 30건 |
| 원본 vs 대조군(폰트만 원본) | **0건 — "가로 리플로우 없음"** | 33건 / 33건 |

즉 **가로 변화 전량이 폰트 스택 교체의 결과**이고, 사다리 채택은 가로에 아무 영향이 없다.
추가로 `.nl-table-scroll` 영역을 DPR 2 로 캡처해 대조군과 원본이 **픽셀 단위로 완전 동일**함을
확인했다(표 전체가 폰트 외 요인으로는 1픽셀도 안 바뀌었다).

### 가로 변화가 표 전체에 번진 이유 (dw −9)

`.nl-table` 은 `width: 100%` 이지만 **실제 폭은 max-content 가 지배**한다 — 두 번째 행 제목이
매우 길고 `.cell-title__text` 의 `nowrap`+ellipsis 가 셀의 preferred width 를 키우기 때문이다.
실측: 스크롤 컨테이너 `clientWidth` **1132** < 표 폭 **1157**(원본) → **1148**(정합본).
긴 한글 제목이 새 스택에서 9px 좁게 그려져 표 폭이 그만큼 줄었고, 그 9px 이 열·셀·배지·chevron 의
`dx`/`dw` 로 95건에 번진 것이다. **레이아웃 규칙은 한 줄도 바뀌지 않았다.**

### 왜 수용 가능한가

전부 **폰트 폴백 차이**다. 이 개발 기기에 비-GOV `Pretendard` 가 설치돼 있어, 제거 시 다른 face
(`-apple-system`)로 떨어지면서 글자 폭이 1~13px 달라진 것이다. `fontSize`·`fontWeight`·`color`·
`backgroundColor`·`border*` 는 **여전히 전부 0건**이다.
지시서가 이 교체로 인한 가로 변화를 **예외로 인정**하고 있으며, 근거는 이미 정합돼 게시된 SD 6건이
이 문자열을 verbatim 으로 쓴다는 것이다(관례는 "-apple-system 을 포함할 것"이 아니라 "이 문자열 그대로").

> ⚠ **확인하지 못했다.** 배포 환경에 비-GOV `Pretendard` 가 설치돼 있는지는 이 작업에서 확인할 수
> 없었다. 설치돼 있다면 이 변화는 배포 환경에서도 나타난다. 다만 그 경우 **게시된 SD 6건도 같은
> 조건**이므로 화면 간 불일치는 생기지 않는다.

## 5. 세로 변화 30건 — 사다리 채택의 의도된 귀결

`lineHeight` 차이 **11건**이 전부 `normal → 사다리 규정값`이다.

| 요소 | 변화 |
|---|---|
| `select.select-trigger` + `option` ×3 | normal → 27.2px (t-body-md 1.6) |
| `input.input` | normal → 27.2px |
| `p.state-showcase__label` | normal → 19.6px (t-label 1.4) |
| `p.state-preview__caption` ×3 | normal → 21px (t-caption 1.5) |
| `span.msg` ×2 | normal → 21px |

세로 변화는 **전부 `.state-showcase` 서브트리 안에서만** 기하로 드러난다(문서 높이 +7px @1280 ·
+14px @480). 입력·셀렉트는 높이가 `44px` 로 고정돼 있어 행 높이가 밀리지 않는다.

### 다만 `<select>` 안의 글자는 약 1px 위로 이동한다 (실측)

`t-body-md` 의 `line-height: 1.6` 이 `<select>` 의 line box 를 바꿔, 옵션 텍스트의 세로 무게중심이
**DPR 2 기준 44.63 → 42.72 device px = 약 0.95 CSS px 상승**했다(대조군으로 폰트 요인을 제거한 뒤 측정).
`<input>`·`.field-actions`·라벨은 같은 조건에서 **픽셀 단위 완전 동일**이라 셀렉트 하나만 해당한다.

**그대로 뒀다** — 같은 `.select-trigger` 컴포넌트를 쓰는 **정합 완료본 SCREEN-018 이 `<select>` 에
`t-body-md` 를 달고 있다**. 여기서만 예외를 두면 같은 컴포넌트가 화면마다 다르게 지정된다.
요소 박스 기하로는 잡히지 않는 차이라 기록으로 남긴다.

## 6. 결함 — 고치지 않고 기록만 남긴 관찰 3건

지시서 §5 의 두 유형과 §"공지 계열 관찰" 3건을 모두 찾아봤다.

### (1) 입력·버튼 경계 대비 미달 — WCAG 1.4.11 (고치지 않음)

이 화면에서 순백 위에 놓이는 컨트롤 경계는 **`--border`(=n-2, `#cdd1d5`)** 이고 실측 대비는 다음과 같다.

| 색 | vs `#ffffff`(입력 내부) | vs `n-0 #f4f5f6`(필터 박스 배경) | 3:1 |
|---|---|---|---|
| `n-1 #e6e8ea` | 1.23:1 | 1.13:1 | ✗ |
| **`n-2 #cdd1d5` (=`--border`)** | **1.54:1** | **1.41:1** | **✗** |
| `n-3 #b1b8be` | 2.01:1 | 1.84:1 | ✗ |
| **`n-4 #8a949e` (=`--border-strong`)** | **3.08:1** | 2.82:1 | ○(백색 기준) |
| `n-5 #6d7882` | 4.51:1 | 4.13:1 | ○ |

해당 자리 — `.input`/`.select-trigger` 기본 경계(**미달**) · `.btn-secondary` 경계(**미달**) ·
`.nl-filter` 테두리(n-1) · `.nl-table tbody td` 구분선(n-1).
`.input:hover` 는 `--border-strong`(3.08:1)이라 **hover 때만 기준을 넘는다.**

**고치지 않았다** — 이번 작업의 통과 기준이 *"색 차이 0건"* 이라 색을 바꾸면 정합 판정을 스스로 깬다.
CSS `.input, .select-trigger` 에 `⚠ 대비 확인 필요` 주석만 남겼다. 색 결정은 디자인 소관으로 올린다.
같은 파일의 `.nl-row-chevron` 은 이미 이 사유로 `n-4` 를 쓰고 있어 **한 파일 안에서 컨트롤 경계
정책이 갈려 있다**(아이콘은 3:1 확보, 입력·버튼 경계는 미확보).

### (2) `.select-trigger` 의 flex 4선언이 아무 효과가 없다 (死 선언, 고치지 않음)

`.select-trigger { display: flex; align-items: center; justify-content: space-between; gap: 8px; }`
는 `<select>` 에서 **관측 가능한 효과가 0**이다. 화살표는 `appearance: none` + `background-image`
가 그린다. 네 선언을 지운 변형본을 만들어 `.nl-filter` 영역을 DPR 2 로 캡처 비교한 결과
**다른 픽셀 0개 / 최대 채널 차이 0** 이었다.

**고치지 않았다** — 렌더 결과가 완전히 동일하므로 지울 이유가 시각적으로는 없고, 같은 컴포넌트를 쓰는
**정합 완료본 SCREEN-018 도 이 네 줄을 그대로 갖고 있어** 여기서만 지우면 컴포넌트 정의가 갈린다.
사실만 CSS 주석 + 이 노트에 남긴다.

> 지시서가 예로 든 `.field:last-of-type` 류의 **매칭 0 선택자는 이 파일에 없다** — 브라우저에서

### 8.1 컨트롤 경계 → `--border-strong`, hover 는 한 단계 위로

| 자리 | 전 → 후 | 안쪽면(흰) 대비 | 바깥면(`--bg-alt` n-0) 대비 |
|---|---|---|---|
| `.input` · `.select-trigger` 기본 경계 | `--border`(n-2) → `--border-strong`(n-4) | 1.54 → **3.08** | 1.41 → 2.82 |
| `.btn-secondary` 경계 | `--border`(n-2) → `--border-strong`(n-4) | 1.54 → **3.08** | 1.41 → 2.82 |
| `.input:hover` · `.select-trigger:hover` | `--border-strong`(n-4) → **`--n-5`** | 3.08 → **4.51** | 2.82 → 4.13 |
| `.btn-secondary:hover` | `--n-3` → **`--n-5`** | 2.01 → **4.51** | 1.84 → 4.13 |

**hover 두 자리를 함께 올린 이유(지시서 §1 의 "상태 구분이 사라지면" 조항)**

- `.input:hover` 는 **원래 `--border-strong` 이었다.** 기본을 `--border-strong` 으로 올리는 순간
  기본과 hover 가 **같은 `#8a949e`** 가 되어 hover 피드백이 사라진다 → hover 를 `--n-5` 로 올려 구분 유지.
- `.btn-secondary:hover` 는 `--n-3`(`#b1b8be`)였다. 기본이 n-4(`#8a949e`)가 되면 **hover 가 기본보다
  오히려 옅어져 방향이 뒤집힌다**(그리고 2.01:1 로 3:1 미달). 같은 사유로 `--n-5` 로 올렸다.
  ⚠ 이 자리는 지시서가 예로 든 `.input:hover` 케이스가 아니라 **반전(inversion)** 케이스다 — 기본을
  올릴 때 hover 가 기본보다 옅어지지 않는지도 함께 봐야 한다는 사례로 남긴다.

**올리지 않은 자리** — `.nl-filter` 테두리(n-1) · `.nl-table-scroll` · `.nl-table thead th` 하단선 ·

**컨테이너 경계·표 괘선**이라 지시서 §1 의 "올리지 않는 것"이다.
`.btn-primary`(p-5) · `.btn-outline`(p-5) · `.btn-ghost`(transparent) 도 대상이 아니다.
`.nl-row-chevron` 은 **원래부터 `n-4`** 였다 — 한 파일 안에서 갈려 있던 정책(§6-(1) 말미)이 이번에 통일됐다.

### 8.6 `viewbox`(소문자) → `viewBox` 18건 수정 — 렌더 무변화 실측

### 8.8 기계 검출기 — 함정 2건 차단 후 재판정 (결론 불변)

| 함정 | 차단 방법 | 확인 |

### 8.10 확정 기준 재적용 — **표면 기준 3:1**, §8.5-4 의 잔존 미달 해소

조율자 최종 확정으로 목표가 **토큰 이름에서 "실제로 맞닿는 표면 대비 3:1(불리한 쪽 기준)"** 으로
바뀌었다. 이 화면의 컨트롤 3종은 전부 **필터 박스(`.nl-filter`, `background: var(--bg-alt)` = n-0)**
안에 있어 **바깥면이 불리**하다 — n-4 로는 2.82 로 미달이었다. §8.5-4 에서 *"수치만 남긴다"* 고 적었던
유보를 **`--n-5` 로 올려 해소**했다.

| 자리 | 전 → 후 | 안쪽면 | 바깥면 | 불리한 쪽 전→후 |
|---|---|---|---|---|
| `.input` · `.select-trigger` 기본 | `--border-strong`(n-4) → **`--n-5`** | `#ffffff` | `#f4f5f6` | **2.82 → 4.13** |
| `.btn-secondary` 기본 | `--border-strong`(n-4) → **`--n-5`** | `#ffffff` | `#f4f5f6` | **2.82 → 4.13** |
| `.btn-outline` | `p-5` **유지** | `#ffffff` | `#ffffff` | 4.55 (이미 통과, **내리지 않음**) |

**상태 역전 재점검 — hover 2자리를 한 단계 더 밀었다(필수 항목).**
기본이 `n-5` 가 되면서 직전 라운드에 `n-5` 로 올려 뒀던 hover 와 **값이 겹치므로** `n-6` 으로 밀었다.

| 상태 | 경계 | 맞닿는 면 | 불리한 쪽 |
|---|---|---|---|
| 기본 | `#6d7882` n-5 | 흰 / n-0 | **4.13** |
| `:hover` | `#58616a` n-6 | 흰 / n-0 | **5.77** |
| `:focus` | `#256ef4` p-5 | 흰 / n-0 | **4.17** (색상축이 달라 구분) |
| `.btn-secondary:hover` | `#58616a` n-6 | 채움 n-0 / 바깥 n-0 | **5.77** |

`기본 n-5 → hover n-6` 순서가 **단조 증가**로 유지된다. 역전·중복 **0건**.
(이 화면의 hover 는 이 스윕에서 두 번 올라갔다: `n-3`/`n-4` → `n-5` → `n-6`. 매번 기본이 올라가
겹치거나 뒤집혔기 때문이며, 최종값만 소스에 남는다.)

**미달 잔존 0종** — 상호작용 요소 전수 재감사에서 새 기준 미달 **0종**이다.
