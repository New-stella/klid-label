### 골격이 못박은 것 — 화면에 드러냈다

- **입력 부담을 낮추는 것이 설계 기준이다.** 필수는 식별 정보 네 항목뿐이고, 나머지 세 묶음은 **처음에 접혀 있다.** 카드 설명문에도 `반드시 채우는 것은 식별 정보 네 항목뿐` 이라고 적었다.
- **영상 기술메타는 전부 비워도 된다.** 그 사실이 **묶음을 열기 전에** 보이도록 요약 줄에 적었다 — 열어야만 알 수 있으면 안 열어 본 사람은 12칸을 채워야 하는 줄 안다.
- **영상 길이는 아예 입력하지 않는다.** 비활성 입력이 아니라 안내 박스이며, 기술메타 묶음 안에서 **다른 입력보다 먼저** 나온다.
- **기본값을 미리 채웠다** — 영상 클립 ID(`test-20260814-0917`) · CCTV ID(`CCTV-001`) · 지자체코드(`11680`).
- **500MB 는 전송 방식의 한도다.** 적재 경로 선택지 두 장에 각각 `한 번에 통째로 보내는 방식이라 500MB까지만` / `청크로 나눠 보내 … 크기 한도를 받지 않습니다` 를 적어 **고르는 자리에서** 읽히게 했고, 파일 입력 도움말에도 같은 취지를 한 번 더 적었다.
- **단계별 실행 선택 기능을 두지 않았다.** 체크박스·토글·단계 선택 목록이 한 개도 없다. 대신 `업로드 → 비식별(항상 자동 실행) → 마킹 대기 정지` 를 **고를 수 없는 태그 사슬**로 보여주고 배너 제목을 `실행 흐름은 고정입니다` 로 못박았다.
- **비식별은 예외 없이 자동 실행된다는 사실**을 개인정보 유형 도움말과 고정 흐름 배너 두 곳에 적었다.
- **② 는 완료 상태로 가지 않는다.** 참고 패널 ② 안내문에 `이 경로에서 완료 상태까지 가는 일은 없다` 를 명시했다.
- **이벤트유형은 고정 목록이 아니다.** 도움말에 `정해진 몇 종이 아니라 관제가 운영하는 코드 전체가 대상` 과 저장값이 코드라는 것을 적었고, 이름 옆에 코드를 붙였다.
- **③ 의 `직접 입력` 은 전송값이 아니다.** 도움말에 `화면 모드를 바꾸는 표시라 전송되지 않습니다` 와 서버 판정이 형식임을 적었다.
- **위치·CCTV 제원은 촬영 시점 값으로 고정 저장된다** 는 사실을 요약 줄과 묶음 안내에 적었다.
- **완료 안내 2종은 색만으로 구분하지 않는다** — 색·아이콘·제목 문구가 모두 다르다.
- **전송 중에는 폼 전체가 잠긴다** — 참고 패널 ①-① 에 비활성 입력과 함께 그렸다.

### 골격에 없어 그리지 않은 것

- **업로드 이력·과거 실행 목록**, **단계별 재실행 버튼**, **폴링 주기 조절·수동 새로고침**, **배치 단계 타임라인·로그** — 골격에 없다.
- **드래그 앤 드롭 드롭존** — 골격은 `type=file` 입력만 규정했고 카탈로그 `FileInput` 도 라벨+입력이 함께 보이는 폼 필드용이다.
- **`durationSec` 외 다른 자동 추출 값의 미리보기** — 골격에 없다.
- **적재 경로에 따라 입력 항목을 바꾸는 분기** — 골격이 `입력 폼은 두 경로가 완전히 같다` 고 못박았다.

## § 디자인 결정 (골격이 규정하지 않은 부분)

### 1. 두 경로가 다른 폼처럼 보이지 않게 했다 — 갈라 보이던 장치를 전부 걷어냈다

v16 은 업로드가 두 섹션이라 **경로가 별개임을 알리는 장치**(독립 배지 · 구분선 · 좌측 강조선)를 세 겹으로 뒀다.
v17 에서 두 경로의 실제 차이가 **올린 뒤 어디로 보내는가 하나뿐**임이 확정되면서 그 장치들은
없애야 할 것이 됐다 — 남겨 두면 "입력이 다른가" 하는 잘못된 기대를 만든다.

대신 차이가 나는 지점 하나에 정보를 모았다. **적재 경로 라디오 카드 두 장**에 각 경로의 성질을 한 줄씩 적고,
그 아래 도움말에 `입력 항목은 두 경로가 완전히 같습니다` 를 못박았다.

### 2. 500MB 한도를 파일 입력이 아니라 경로 선택 자리에 놓았다

500MB 는 **영상 크기 제한이 아니라 전송 방식의 한도**이고 즉시 실행에만 걸린다. 파일 입력 도움말에만
적으면 "이 화면은 500MB까지"로 읽혀 **큰 영상을 올릴 수 있는데도 포기하는** 오해가 난다.
그래서 **고르는 자리(라디오 카드)에 경로별로** 적고, 파일 입력 도움말에는 "즉시 실행에만 걸린다"는
단서를 붙인 형태로 한 번 더 적었다.

### 3. 선택 묶음 세 개를 접었다 — 체크박스 + 라벨, 스크립트 없이 열린다

요약 줄은 **제목 + 그 묶음을 왜 비워도 되는지** 두 조각으로 구성했다 — 접힌 상태에서 정보가 0이면
사용자는 일단 다 열어 보게 되고, 그러면 접은 의미가 사라진다.

구조는 `input[type="checkbox"]`(`sr-only`) + `label[for]` + 형제 선택자(`:checked + …` / `:checked ~ …`)다.
체크박스는 화면에서만 감추고 **포커스는 받으므로** Tab 으로 도달하고 Space 로 토글된다.
포커스 링은 보이지 않는 체크박스가 아니라 **눈에 보이는 요약 줄**에 그린다(`:focus-visible + .collapse-summary`).
요약 줄 높이는 44px 이상이고, 화살표는 `:checked` 에서 CSS `transform` 으로 90도 돌아 상태를 알린다
(열림·닫힘은 화살표만이 아니라 내용의 유무가 함께 알린다).

### 3-1. `details`/`summary` 를 쓰지 않는 이유 (게시 왕복 대조에서 확인)

**게시 서버가 `<details>`·`<summary>` 태그를 지우고 자식만 남긴다.** 내용은 보존되지만
**접기 동작이 통째로 사라져 세 묶음이 영구히 펼쳐진 모습**이 되고, 요약 줄의 제목·부연·꺾쇠는
그냥 인라인 텍스트로 남는다. 「입력을 쉽게」의 핵심 장치가 게시 산출물에서만 없어지는 것이다.
`colspan`·`optgroup` 과 같은 부류 — **속성이 아니라 구조가 사라지고 CSS 로 되살릴 수 없다.**

`checked`·`class`·`id`·`for`·`aria-*`·`role` 은 게시본에서 보존되는 것이 실측으로 확인됐으므로
체크박스로 같은 동작을 만들었다. 이 저장소에 이미 있는 **무 JS 상호작용은 radio/checkbox + label**
관례를 따른 것이고 새 방식을 발명한 것이 아니다.

**⚠ 이것은 시안·게시본 한정 제약이지 구현 제약이 아니다.** 실제 앱에서는 `<details>` 를 쓰는 편이
시맨틱상 낫다 — 게시 렌더 서버를 거치지 않기 때문이다.

**⚠ 이 교체로 잃는 것 (숨기지 않고 적는다)**

| 잃는 것 | 영향 |
|---|---|
| 네이티브 disclosure 시맨틱 | 보조기술이 `group`(details)이 아니라 `checkbox` 로 읽는다. "펼치기/접기"임은 접근 가능한 이름(`눌러서 펼치거나 접습니다`)과 체크 상태로만 전달된다 |
| `open` 속성으로 상태를 읽는 경로 | DOM 에서 `details.open` 대신 `input.checked` 를 봐야 한다. 구현에서 `details` 로 되돌리면 이 축도 함께 돌아온다 |
| `aria-expanded` | 무 JS 로는 정적 값밖에 못 넣어 한쪽 상태에서 반드시 거짓말이 되므로 **넣지 않았다.** 상태는 체크박스의 checked 로 전달된다 |
| 폼 제출 시 잡음 | 접기용 체크박스가 폼 안에 있어 실제 구현에서는 전송 대상에서 빼야 한다(`name` 을 두지 않았다) |

### 4. 본문은 「업로드 전」 장면, 결과 패널은 「진행 중」 장면이다

한 장면으로 통일하면 둘 중 하나가 정보를 잃는다 — 전송 중으로 맞추면 폼 전체가 잠긴 회색이 되어
**폼 설계가 안 보이고**, 업로드 전으로 맞추면 결과 패널이 통째로 사라진다. 그래서 폼은 편집 가능한
상태로, 결과 패널은 직전 실행이 진행 중인 상태로 그렸다. **두 패널은 같은 순간이 아니다** —
실제 화면에서 전송 중에는 폼이 잠긴다(참고 패널 ①-①).

같은 이유로 진행률은 본문에서 `대기 중 · 0%` 다. 전송 중·일시정지·오류·완료 네 상태는 참고 패널에 있다.

### 5. 선택 목록을 `optgroup` 으로 묶지 않았다 (게시 왕복 대조에서 확인)

**게시 서버가 `<optgroup>` 을 통째로 지운다** — 여는·닫는 태그가 사라지면서 그 묶음 라벨(한글 표시 텍스트)이
게시본에서 완전히 소실된다. 속성을 지우는 축(`accept`·`inputmode` 등)과 달리 **구조가 사라지는 것이라
CSS 로 되살릴 수 없다.** 이 저장소가 표에서 열 병합에 의존하지 않는 것과 같은 부류다.

그래서 시계열 이벤트유형 select 를 **평평한 목록**으로 두고, 묶음 라벨이 담고 있던 정보
— 가운데 여섯이 **외부 시계열 분석이 받아 주는 유형 전부**라는 것 — 을 **도움말 문장에 값 이름까지 적어** 옮겼다.

⚠ **이것은 시안·게시본에 대한 제약이지 구현 제약이 아니다.** 실제 앱에서는 `optgroup` 을 써도 된다 —
게시 렌더 서버를 거치지 않기 때문이다.

### 6. 개발 전용임을 배지 하나로 끝내지 않았다

`DevOnlyNotice`(UI-117)가 규정한 대로 **조작 영역보다 위에** warn 톤 띠를 뒀다. 헤더 배지는 짧아서
무엇이 위험한지 말하지 못하므로, 띠에 실제 위험 — `여기서 올린 영상은 실제 파이프라인을 그대로 탑니다` — 을 적었다.

### 7. `단계 선택 없음` 을 빈자리가 아니라 그림으로 보였다

"두지 않는다"는 규정은 아무것도 그리지 않으면 지켜지지만 **전달되지는 않는다.** 사용자는 단계를 고르는
화면을 기대했다가 못 찾으면 화면이 덜 만들어졌다고 읽는다. 그래서 고정 흐름을 **고를 수 없는 태그 사슬**로
그렸다. pill 을 쓰지 않고 사각 태그로 둔 것도 의도다 — pill 은 DS 에서 status badge 전용이고,
버튼·칩처럼 보이면 누를 수 있는 것으로 오해된다.

### 8. 결과 메타 `3열` 을 세로로 쌓았다

골격은 `파일 경로 / 프레임 수 / 트리거 시각` 3열이라고 적지만 이 패널은 `role=side` 이고 폭이 320px 다.
3열로 만들면 파일 경로가 열 하나에 대여섯 글자만 남는다. DS `iteration_guide` 가
**"좁으면 크기를 낮추지 말고 열 수를 줄인다"** 고 규정하므로 세로로 쌓고 값에 `word-break` 를 걸었다.
`프레임 수` 는 본문 상태에서 아직 값이 없어 `— 아직 추출 전` 이다 — `0` 을 적으면 "0장이 추출됐다"는 다른 사실이 된다.

### 9. 게시본이 지우는 제약을 화면 글자로 한 번 더 실었다

게시 렌더는 `accept`·`inputmode`·`maxlength` 속성을 지운다. 로컬 원본에는 그대로 두되
(그 파일이 진실원이다) 같은 정보를 **도움말 문장으로도** 적었다 — 파일 확장자·500MB, 지자체코드 자릿수,
관제일지 4,000자, 직접 입력값 형식. SVG `stroke-width` 도 같은 축이라 **CSS 에 같은 값을 다시 선언**해
게시본에서 되살렸다. `stroke-linecap`·`stroke-linejoin` 은 다수 시안 관례를 따라 쓰지 않았다.

### 10. 진행률에는 진행바를, 파이프라인에는 스피너를 썼다

카탈로그가 둘의 경계를 규정한다 — **퍼센트를 아는 결정론적 작업은 `ProgressBar`, 알 수 없는 대기는 `Spinner`**.
전송은 보낸 바이트를 알 수 있어 진행바이고, 파이프라인은 언제 끝날지 알 수 없어 스피너다.
진행바에는 `role="progressbar"` + `aria-valuenow`, 스피너에는 `role="status"` 를 걸었고
스피너 회전은 `prefers-reduced-motion` 에서 멈춘다. 상태마다 진행바 색을 갈랐지만
같은 줄의 상태 텍스트(`대기 중`/`전송 중`/`일시정지됨`/`오류로 멈춤`/`전송 완료`)가 항상 같은 사실을 글자로 전달한다.

### 11. 페이지 헤더 메타 묶음에서 `flex-shrink: 0` 을 걷어냈다 (실측 지적 반영)

`.page-head-meta` 에 `flex-shrink: 0` 이 걸려 있으면 그 묶음이 **max-content**(배지 2개 + 라우트 칩을
한 줄에 늘어놓은 폭) 아래로 줄지 못해 **안쪽 `flex-wrap: wrap` 이 발동할 기회를 잃고**, 좁은 폭에서
라우트 칩이 뷰포트 밖으로 밀려 문서가 가로로 늘어났다. `flex-shrink` 선언을 없애고 `min-width: 0` 만
남겨 묶음이 줄 수 있게 하니 배지·칩이 스스로 줄바꿈된다. **되돌리지 말 것** — 그 자리에 사유 주석이 있다.

### 12. 「이벤트유형」과 「시계열 이벤트유형」이 같은 값으로 읽히지 않게 갈랐다 — 이름까지 바꿨다

두 항목은 **완전히 다른 축**이다.

| | 「이벤트유형」 | 「시계열 이벤트유형」 |
|---|---|---|
| 축 | 관제의 이벤트 분류 | 외부 시계열 분석에 보내는 값 |
| 값 형태 | `EV` + 숫자 8자리 (`EV03000101`) | 영문 소문자 (`fire`) |
| 쓰이는 곳 | 영상 분류 · 목록 필터 · 라벨 프리셋 매핑 | 외부 시계열 분석 요청 하나 |
| 목록 주인 | 관제(우리가 조회해 채운다) | 외부 벤더(규격이 여섯만 열거) |

**서로 변환 관계가 없고 하나가 다른 하나를 대신하지도 않는다.**

그런데 화면에서 이 둘은 **이름이 거의 같고 자리도 떨어져 있다** — 「이벤트유형」은 폼 위쪽(개인정보 유형 옆),
「시계열 이벤트유형」은 접힌 「이벤트 · 관제일지」 묶음 안이다. 이름이 비슷한데 멀리 있으면 **같은 값의 다른 표기**로
오해하기 쉽다(골격의 「이벤트 ID」 note 에 *"이벤트유형코드가 아니다"* 라는 방어 문구가 이미 있는 것이
그 혼동이 전에도 있었다는 증거다).

**그래서 이름을 바꿨다 — 「검증이벤트유형」 → 「시계열 이벤트유형」**(사용자 확정). 구 이름은
「이벤트유형」 앞에 「검증」만 붙은 꼴이라 *"이벤트유형을 검증한 결과"* 처럼도 읽혔다. 새 이름은
**어디에 쓰는 값인지를 이름 자체가 말한다** — 그 값이 가는 곳이 외부 시계열 분석이기 때문이다.
설명이 아니라 이름이 구분을 지므로, 접힌 묶음 안에 있어 도움말을 펴 보기 전이라도 갈린다.

배치는 골격대로 두고, 두 도움말에 서로를 배제하는 문장을 각각 한 줄씩 넣고
값의 형태(`EV03000101` 꼴 / `fire` 꼴)를 함께 적어 눈으로도 갈리게 했다.

⚠ 선택지 안의 `미지정 (시계열 검증 위탁 생략)` 은 **그대로 뒀다** — 골격이 규정한 값이고 이미 「시계열」을 쓴다.
여섯 값과 순서, 형식 판정 설명도 불변이다. 바뀐 것은 **이름뿐**이다.

- 「이벤트유형」: `이 값은 관제의 이벤트 분류라 영상 분류 · 목록 필터 · 라벨 프리셋 매핑에 쓰이며, 외부 시계열 분석에 보내는 값이 아닙니다 — 그 값은 아래 「이벤트 · 관제일지」의 시계열 이벤트유형(fire 꼴)입니다.`
- 「시계열 이벤트유형」: `이 값은 외부 시계열 분석 요청에만 쓰입니다 — 위 「이벤트유형」(EV03000101 꼴)과 다른 값이고 서로 변환되지 않습니다.`

「이벤트 ID」의 `이벤트유형코드가 아닙니다` 방어 문구는 같은 종류의 혼동을 막는 것이라 **그대로 뒀다.**

### 13. 시계열 이벤트유형 여섯의 성격을 도움말에서 바로잡았다

구 문구는 그 여섯을 **"자주 쓰는 값일 뿐 허용 목록이 아니다"** 라고 적고 *"여섯 밖의 값도 형식만 맞으면 그대로 위탁된다"*
로 이어져, **"형식만 맞으면 아무 값이나 써도 된다"** 로 읽혔다. 사실이 아니다 — 그 여섯은 **현재 외부 시계열 분석이
받아 주는 유형 전부**이고, 목록 밖 값은 우리 서버를 통과하더라도 **외부가 거부해 위탁이 실패로 끝난다.**

다만 **서버가 목록이 아니라 형식으로만 판정한다는 것은 사실이자 확정 정책**이라 그 부분은 지우지 않았다.
대신 **왜 막지 않는지**를 함께 적었다 — 그 목록의 주인이 외부이기 때문이다. 외부가 유형을 늘리면 우리를
고치지 않고 바로 쓸 수 있어야 하고, 반대로 우리가 사본을 들고 막으면 **외부가 넓힌 정상 값을 우리가 먼저
차단**하게 된다. 그래서 `직접 입력` 은 **외부가 유형을 늘렸을 때 쓰는 통로**로 설명했다.

### 14. `select` 의 네이티브 드롭다운을 끄고 커스텀 화살표를 썼다

이 시안의 `.select` 에는 `appearance: none` 이 없어 **OS 기본 드롭다운이 그대로 그려지고 있었다.**
증거는 계산 스타일이다 — `select` 만 `line-height: normal` 이고 CSS 에 적은 `1.6` 이 먹지 않았다.
네이티브 컨트롤이라 **브라우저·OS 마다 글자 위치·안쪽 여백·실제로 보이는 크기가 달라져** 바로 옆
입력칸과 어긋나 보인다. 높이만 재면 44px 로 같은데도 "드롭다운이 작아 보인다"는 인상이 생기는 이유다.

**높이는 44px 그대로 뒀다.** 입력칸과 같은 값이고 `select` 를 쓰는 기존 시안이 전부 같은 값이라,
키우면 오히려 관례에서 이탈한다. 실제 문제는 크기가 아니라 렌더 주체였다.

방식은 **기존 시안(SCREEN-012 · 022 · 024 · 025)이 이미 쓰는 것을 그대로** 가져왔다 —
`appearance: none` + `background-image` 꺾쇠 + `background-position: right 12px center` +
`padding-right: var(--sp-xl)`(화살표와 글자가 겹치지 않게). 화살표 색은 새로 만들지 않고
그 원문의 `--n-6` 값을 그대로 쓴다.

⚠ **data URI 안의 `stroke-linecap`·`stroke-linejoin` 과 색 리터럴은 이 저장소의 금지 축이 아니다** —
그건 HTML 속성이 아니라 **CSS 값 안의 문자열**이라 게시 서버의 속성 삭제 대상이 아니고,
CSS 는 원문이 해시까지 보존되는 것이 왕복 대조로 확인돼 있다. `<svg>` 요소에 그 속성을 쓰지 않는 규칙과는
**다른 축**이므로 혼동해 이 선언을 걷어내지 말 것.

## § 접근성 검증 (WCAG)

> 실측 수치는 아래 `§ 실측 검증` 에서 PM 이 채운다. 이 절에는 **설계상 지킨 원칙**만 적는다.

- **모든 입력을 `label[for]` 로 연결**했고 도움말은 `aria-describedby` 로 이었다. 라디오는 `label` 로 감싸 암시 연결했다.
- **필수 표시를 색·기호에만 맡기지 않았다** — `*` 옆에 `sr-only` 로 `필수` 를 함께 실었다.
- **라디오 묶음과 입력 그룹을 `fieldset` + `legend` 로 묶었다.** 접힌 묶음은 `summary` 가 제목을 보이고
  안쪽 `fieldset` 에 같은 이름의 `sr-only` `legend` 를 둬 그룹 이름이 보조기술에도 남는다.
- **접기는 네이티브 `details`** 라 키보드로 열고 닫히며 열림 상태가 보조기술에 전달된다. 스크립트 의존이 없다.
- **색만으로 상태를 구분하는 곳이 없다** — 진행률 5상태, 완료 안내 2종, 파이프라인 상태 배지 모두 아이콘 또는 글자를 동반한다.
- **역할을 상태에 맞게 배정**했다 — 오류는 `role="alert"`, 진행·완료 안내는 `role="status"`, 안내 문단은 `role="note"`, 진행바는 `role="progressbar"` + `aria-valuenow/min/max`.
- **hit area** — 버튼·입력·선택·라디오 카드·요약 줄을 44px 이상으로 두고, 빵부스러기 링크는 시각 크기를 유지한 채 `min-*` + 음수 margin 으로 44×44 를 확보했다.
- **비활성 주버튼은 흐림이 아니라 채도를 뺀 면**으로 표현했다 — 흐리면 글자 대비가 함께 무너진다.
- **경계가 유일한 식별 수단인 컨트롤**의 테두리는 neutral 40단 이상으로 뒀다 — 20·30단은 비문자 대비 기준에 미달한다.
- **회색 표면 위 보조 텍스트는 neutral 60단 이상**을 썼다(DS `do_rules`). warn 가장 옅은 면 위에서는 warn 50단을 쓰지 않고 70단·neutral 80단으로 올렸다.
- **동작 축소 설정을 존중**한다 — `prefers-reduced-motion` 에서 스피너 회전이 멈춘다.
- **포커스 링**은 3px outline + 2px offset, `focus-visible` 한정으로 공통 적용했고 `summary` 도 대상에 포함했다.

### ⚠ 기준 미달을 알고 남긴 것

| 항목 | 판단 |
|---|---|
| `.btn-sm` · 파일 선택 버튼 높이 36px | DS `do_rule` 44×44 미달. **전 시안 공통 관례**라 이 화면만 바꾸면 관례가 갈린다. WCAG 2.2 AA(24×24)는 통과. 기준본 축 후속 과제로 승계 |
| 참고 영역 점선 `2px dashed --n-4` | 확정 관례·기준본 동일 조합. 컨트롤 경계가 아니다 |
| 표 헤더 배경 · 행 hover 규칙 | **해당 없음** — 이 화면에 표가 없다 |

### 게시본에서 접기가 실제로 동작하는지 확인했다

로컬이 아니라 **게시 URL 을 브라우저로 열어** 확인했다 — 토글 3개, 초기 전부 접힘(첫 묶음 높이 **46px**,

`<script>` 가 0건이므로 전부 CSS·네이티브 동작이다.

⚠ **측정 함정 하나** — 클릭 직후 바로 읽으면 꺾쇠가 `matrix(1,0,0,1,0,0)`(회전 없음)으로 나온다.
`transition: transform 120ms` 가 아직 진행 중이기 때문이며 결함이 아니다. **전환 시간보다 길게 기다린 뒤 읽어야 한다.**

### 320px 에서 긴 선택지 글자가 잘린다 — 수용 (관례 대조로 확인)

`시계열 이벤트유형` 의 선택값 `미지정 (시계열 검증 위탁 생략)` 은 320px 에서 글자 **205px** 가
가용 **162px** 를 넘어 끝이 잘린다. 네이티브 `select` 는 선택된 옵션 글자를 스스로 줄이므로
브라우저 표준 동작이고 스크롤로 읽을 수 없다.

**이번 변경으로 생긴 것이 아니다** — `appearance` 리셋 전에도 같은 폭에서 가용 173px < 205px 로
잘렸고, 화살표 자리(`padding-right` +24px)만큼 잘리는 지점이 앞당겨졌을 뿐이다.
**관례 대조**: 같은 320px 에서 기준본 SCREEN-012 도 select 3건이 같은 방식으로 잘린다
(SCREEN-022·024 는 0건 — 선택지 글자가 짧다). 이 저장소에서 처음 생긴 조건이 아니므로
골격이 정한 문구를 줄이지 않고 그대로 뒀다.

### 수정으로 이어진 실측 2건

1. **360·320px 에서 문서가 33~73px 밀렸다** — `.page-head-meta` 의 `flex-shrink: 0` 때문에 그 묶음이
   max-content 아래로 줄지 못해 안쪽 `flex-wrap` 이 발동하지 못했고 라우트 칩이 뷰포트 밖으로 나갔다.
   `flex-shrink` 를 걷고 `min-width: 0` 으로 교체해 해소(그 선언 위에 사유 주석을 남겼다).
2. **게시본에서 `optgroup`·`details`/`summary` 가 사라졌다** — 왕복 대조로 발견. 두 구조에 의존하지 않도록

시맨틱상 낫다.

⚠ 시각에 영향을 주는 획 관련 속성은 같은 값을 **CSS 로도 선언**해 게시본에서 되살렸다. 나머지는
CSS 로 대체할 수 없는 정보라 게시본에서 복원되지 않는다 — **로컬 원본이 진실원**이며 구현은 로컬
파일을 따라야 한다.

  못박는다. 시안은 **설명과 [12] 를 따라** 기술메타에서 영상길이 입력칸을 빼고 그 자리에 [12] 안내 박스를 뒀다
  (기술메타는 나머지 11칸). 두 규정을 다 그리면 같은 화면에서 "적어라"와 "적지 마라"가 동시에 보인다.
  **[11] 의 항목 목록에서 영상길이를 빼는 정정이 필요하다.**

  `선택하세요` 자리표시만 두고 값을 지어내지 않았다. **확정 필요.**
- **SCREEN-026 · SCREEN-033 시안도 `select` 의 `appearance` 리셋이 없어 같은 이탈 상태다.**

  어떤 상태가 지나가는지, 한글로 무엇이라 부르는지 말하지 않는다. 시안은 `비식별 처리 중` 한 장면으로 두고 원문 값을 병기했다.
- **관제일지의 전송 경로는 화면 밖이다.** 골격은 `헤더가 아니라 요청 바디로 전송된다` 를 규정하지만 구현 사실이라
  화면 글자로 옮기지 않았다. 화면에는 최대 글자 수만 노출한다.

- **웹폰트 소스 미정** — `@font-face` 없이 family 선언 + 시스템 한글 산세리프 폴백만 뒀다.
- **스크린리더 읽기 순서·탭 순서 미측정.** 특히 접힌 묶음이 닫혀 있을 때 탭 순서가 요약 줄에서 바로 다음 묶음으로 넘어가는지,
  좁은 폭에서 ①→② 로 접힐 때 순서가 맞는지는 실제 사용으로 확인해야 한다.
