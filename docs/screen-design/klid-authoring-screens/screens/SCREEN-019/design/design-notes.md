# SD-005 (SCREEN-019 검수 상세 화면) — 관례 정합 노트

정본 파일: `design.css` + `design.html`
기준본(관례): SCREEN-009 `design/design.css` · 직전 실례: SCREEN-024 `design/`
같은 폴더의 `design-main.{html,css}` 는 서버 현재본의 로컬 미러이며 이번에 수정하지 않았다.

이번 작업은 재디자인이 아니다. 바꾼 것은 ①색 토큰 이름 ②타이포 지정 방식 ③`lang="ko"` 뿐이고,
색·간격·구성요소·문구는 그대로다. **레이아웃 결함은 발견되지 않아 아무것도 고치지 않았다**(§5).

변환은 손으로 옮겨 적지 않고 결정적 스크립트(원본 → 정본)로 수행했다. 모든 치환은 기대 건수를
`assert` 로 고정했고, 한 건이라도 어긋나면 스크립트가 중단되도록 했다.

## 1. 색 토큰 이름 — 값은 보존, 이름만 기준본 체계로

`--nt-→--n-` `--pr-→--p-` `--sc-→--s-` `--in-→--i-` `--wn-→--w-` `--er-→--e-` `--sx-→--su-`
단계는 원본이 이미 한 자리(`0..10`)라 그대로다.

**자릿수 규칙이 아니라 값(hex)으로 매핑했다.** 기준본 `:root` 의 hex → 토큰명 역인덱스(78건, 중복 0)를
만들어 대상 파일의 색 토큰 53개를 값으로 조회했고, **53개 전부가 기준본에 정확히 한 이름으로 존재**했다.
SD-009 에서 나왔던 "이름은 규칙대로인데 값이 어긋난" 케이스(`--su-70`·`--wn-40`)는 이 파일에 없다.
특히 `--sx-7`(`#285d33`)은 기준본 `--su-7` 과 값이 같아 그대로 옮겨진다 — SD-009 의 `--su-8` 사례와
혼동하지 말 것.

값이 기준본에 없는 것은 `--row-hover: #fffbeb` 하나이며, `_shared/design-system.md` 의 `do_rules` 가
명시한 지정값이라 이름·값·설명 주석을 모두 유지했다.

### 수동 판단분

| 원본 | 조치 |
|---|---|
| `#ffffff` 18건(`:root` 밖 raw hex) | 전부 `var(--bg-page)`. `--bg-page: #ffffff` 는 `:root` 에 신설 |
| `--bg-alt` 신설(`var(--n-0)`) | **`body` 배경 1곳에만** 적용. hover 표면·댓글 말풍선 등 다른 `var(--n-0)` 은 페이지 대체 표면이 아니라 그대로 뒀다 |
| `--border` 신설(`var(--n-2)`) | 값이 이미 `n-2` 이던 **경계 8곳**에 적용(헤더 하단선·필름스트립 토글·진행 표시 좌측선·우측 패널 좌측선·탭 하단선·속성 카드·문의 스레드·갤러리 카드) |
| `--border-strong` 신설(`var(--n-4)`) | 정의만 두었다. 이 화면에 `n-4` 경계가 없어 참조처 0 |
| `--dur-base`/`--dur-fast` | `--duration-base`/`--duration-fast` 로 개명(기준본 이름). 값 동일 |
| `--font-body` | 기준본 값 채택 — `-apple-system` 추가 + 따옴표를 홑따옴표로 |
| `--font-mono` | 기준본 값 채택 — `Menlo, Consolas` 추가. **이 화면에서 유일하게 측정된 가로 변화의 원인이다(§6)** |
| `--hit-area: 44px` | 유지. 기준본에 없지만 색·타이포 축이 아니고 버튼 높이·최소 터치 영역의 단일 원천이다 |

`.rv-thumb` 의 `3px solid` 는 컨테이너 경계가 아니라 **선택 링**이라 `--border` 별칭을 쓰지 않고
`var(--n-2)` 로 두었다(값은 동일).

## 2. 타이포 — 사다리 유틸 `.t-*` 12종

CSS 에 사다리를 정의하고 **HTML 에서 클래스로 지정**한다(기준본 방식). 값은 기준본 verbatim.
원본이 `:root` 에 갖고 있던 `--tp-*-size/-weight/-lh` 27개는 사다리로 흡수되어 제거했다.

`font-size` 선언은 **62 → 28건**(사다리 12 + 컴포넌트 16)이고, HTML 은 `.t-*` 를 **132곳**에서 쓴다.

### 판정 기준 — "명시된 값은 바꾸지 않는다"

원본 규칙이 **명시한** size/weight/line-height 는 한 개도 바꾸지 않았다. 사다리로 옮기면서
어긋나는 것이 생기면 그 속성만 컴포넌트에 남겨 뒤에서 이기게 했다(사다리는 파일 앞, 컴포넌트는 뒤).

- `.badge` — `line-height: 1.3` 을 명시하고 있어 `.t-label`(1.4) 대신 **1.3 을 유지**
- `.memo-item-body` · `.issue-thread-body` · `.meta-textarea` — 명시된 `1.55` 유지
- `.rv-tab` · `.obj-group-header` · `.rv-readonly-badge` · `.empty-state-title` ·
  `.design-ref-gallery-title` · `.design-ref-card h3` · `.attr-val` — 명시된 `font-weight` 유지

반대로 원본이 **선언하지 않아 상속받던** line-height 는 사다리 값으로 바뀐다. 이것이 아래 §6 의
`lineHeight` 131건이며, 사다리 채택의 의도된 귀결이다.

### 컴포넌트에 남긴 `font-size` 16건

| 남긴 것 | 값 | 사유 |
|---|---|---|
| `body` | 17px | 사다리가 아니라 base — `.t-*` 를 달지 않은 요소의 기준 크기 |
| `.btn-sm` · `.btn-xs` | 14/500 | 사다리에 없는 조합(label 은 600, caption 은 400) |
| `.type-badge` · `.badge-count` · `.rv-count-badge` · `.memo-item-tag` · `.rv-box-chip` · `.issue-comment-time` | 12px | 사다리 밖 장식 크기 |
| `.memo-legacy-tag` | 11px | 사다리 밖 |
| `.rv-thumb-num` | 10px | 사다리 밖 |
| `.tech-kv-val` | mono 15px | 사다리 밖 조합(`.t-mono` 는 14px) |
| `.memo-add-input` | 15px | **textarea 라 높이가 내용으로 정해진다.** `.t-body-sm` 의 `line-height: 1.6` 을 얹으면 UA 기본(`normal`)보다 줄높이가 커져 입력창 높이가 실제로 늘어난다. 같은 이유가 없는 `.meta-textarea` 는 원본이 `1.55` 를 명시하고 있어 사다리로 옮겼다 |
| `.attr-val.mono` | 14px | 사다리 밖이 아니라 **특이성 때문**이다. `.attr-val`(0,1,0)이 사다리보다 뒤에 있어 `.t-mono` 를 달면 15px 가 이긴다. `.attr-val.mono`(0,2,0)로 남겨야 원본과 같다 |
| `.rv-header-actions-note` · `.meta-readonly-value` | 14 / 15px | **사다리 밖이 아니라 붙일 노드가 없어서**다. 두 규칙은 HTML 에 대응 요소가 없다(CSS 에만 존재) |

`.rv-header-id` 는 `font-weight: 400` 을 컴포넌트에 남겼다. `.t-mono` 는 weight 를 정하지 않는데
이 span 은 `h1`(600) 안에 있어 명시하지 않으면 굵어진다.

## 3. `:root` 밖에 남긴 반투명 색 7건 — 억지 토큰화하지 않았다

대응 토큰이 없어 **그대로 두었다**. 전부 미디어 매트(어두운 캔버스) 위의 오버레이·장식이며 KRDS
팔레트에 알파 채널 토큰이 없다.

| 값 | 쓰임 |
|---|---|
| `rgba(19,20,22,0.72)` | 캔버스 위 "읽기 전용" 배지 배경 |
| `rgba(19,20,22,0.55)` | 다이얼로그 backdrop |
| `rgba(255,255,255,0.85)` / `rgba(0,0,0,0.4)` | 썸네일 프레임 번호 글자색 / 배경 |
| `rgba(255,255,255,0.06)` / `rgba(255,255,255,0.14)` | 캔버스 하이라이트 그라디언트 / 차선 |
| `rgba(255,224,163,0.25)` | 선택 박스 글로우(= `--w-1` 의 25% 알파) |

`--shadow-*` 의 `rgba(14,21,40,…)` 는 `:root` 안이고 기준본과 값이 같다.

## 4. `lang="ko"` · `color-scheme`

- `<html>` → `<html lang="ko">`.
- `html { color-scheme: only light; }` 를 **CSS 에 둔다.** 원본에 이미 있었고 기준본
  `SCREEN-009/design/design.css` 와 **문자열까지 동일**하다(원본 124행 / 기준본 80행).
  지시서 초판은 "넣지 않는다(관제 22건 중 0건)"였으나, 그 모집단이 잘못됐다는 조율자 정정에 따라
  **우리 저작도구의 이미 정합된 6건이 6/6 으로 보유**한다는 근거로 존치가 확정됐다. 결과적으로
  파일은 변경 없이 관례를 만족한다.
- `<head>` 의 스타일시트 링크는 `design-main.css` → `design.css`. 로컬에서 바로 열기 위한 것이며,
  업로드 시에는 지시서 §7.5 대로 제거해 보낸다.

## 5. 결함 — 찾았으나 **없었다**. 고친 것 0건

지시서 §5 의 두 유형과 조율자 정정(SCREEN-024 필터 폼 정렬 붕괴)을 이 화면에서 실제로 찾아봤다.

### (a) 내용이 폭을 지배하는 컨트롤 — 없음

이 화면의 입력 컨트롤은 전부 폭이 명시돼 있다: `.meta-select`/`.meta-input`/`.meta-textarea` 는
`width: 100%`, `.memo-add-input`/`.issue-comment-input` 은 `flex: 1`(= `flex-basis: 0`),
`.rv-frame-input` 은 `width: 64px`. **flex base size 계산에 max-content 가 들어오는 자리가 없다.**

### (b) 조율자가 경고한 "정렬 붕괴" 구조 — 이 화면에 없음

`align-items: flex-end` 컨테이너가 **0개**다(`center` 는 있으나 전부 높이가 고정된 바·칩·행이다).
도움말류(`.meta-help`·`.meta-panel-help`·`.memo-context-hint`)는 모두 **세로 흐름(block/column)** 안에
있어 옆 컨트롤과 밑단을 맞추지 않는다. 필터 폼 자체가 없다.
→ **없는 결함을 만들지 않기 위해 아무것도 손대지 않았다.**

### (c) 의도 없는 `margin-left: auto` — 없음

`margin-left: auto` 는 `.issue-thread-author` 하나다. 이건 "필터와 그 실행 버튼"이 아니라
**스레드 헤더에서 작성자를 오른쪽 끝에 두는 의도된 정렬**이라 유지했다(주석으로 의도를 명시).
`.memo-add-row { margin-top: auto }` 는 세로축이며 입력 폼을 패널 바닥에 붙이는 의도다.

### 관측만 하고 고치지 않은 것 (판단 대기 — §7 판단 3)

헤더의 `.rv-header-meta`(작업자·제출일시 줄)는 `nowrap`/ellipsis 가 없어, 문장이 길어지면
`.rv-header-title` 블록 폭을 밀어낸다. 실측:

- 원본 문장(29자): `.rv-header-title` = **272px**, "축소"로 줄여도 **272px** → 지금은 `h1` 이 폭을 정한다
- 2배 = 485px, 4배 = 854px → 문장이 길어지면 그때부터 메타 줄이 폭을 정한다

**현재 콘텐츠에서는 아무 영향이 없고 A/B 가 동일하다.** `h1` 에는 이미 `max-width: 480px` +
ellipsis 가 있으나 메타 줄에는 없다. 고치려면 헤더 동작을 바꾸는 것이라 4개 변경 축 밖이고,
현재 시안에서 눈에 보이는 문제가 아니어서 **보고만 하고 두었다.**

## 5-A. 관찰 — 입력 경계 대비가 WCAG 1.4.11(3:1) 미달 (고치지 않음)

이 화면의 **폼 컨트롤 경계는 전부 `--n-3`(`#b1b8be`)** 이다. 흰 배경 대비 **2.01:1** 로 3:1 미달이다.

| 요소 | 경계 토큰 |
|---|---|
| `.meta-select` · `.meta-input` · `.meta-textarea` · `.memo-add-input` · `.issue-comment-input` · `.rv-frame-input` | `var(--n-3)` |
| `.btn-secondary`(테두리 버튼) | `var(--n-3)` |
| `.rv-filmstrip-toggle` | `var(--border)`(=`--n-2`) |

직접 계산한 흰 배경 대비값(조율자가 제시한 수치와 일치):

```
--n-1                      #e6e8ea  vs #ffffff = 1.23:1  ★미달
--n-2 (=--border)          #cdd1d5  vs #ffffff = 1.54:1  ★미달
--n-3                      #b1b8be  vs #ffffff = 2.01:1  ★미달
--n-4 (=--border-strong)   #8a949e  vs #ffffff = 3.08:1  통과
--n-5                      #6d7882  vs #ffffff = 4.51:1  통과
```

**고치지 않았다.** 경계색을 바꾸면 §6 의 "색 차이 0건" 판정을 스스로 깨고, 9건 공통 결정 사안이기
때문이다. 참고로 SD-009(SCREEN-024)는 같은 이유로 입력·셀렉트 경계에 `--n-5`(4.51:1)를 쓰고
"WCAG 1.4.11 대비 3:1 확보" 주석을 달아 두었다 — 이 화면에는 그 조치가 없다.

## 5-B. 관찰 — 매칭 0인 죽은 규칙 7건 (전부 원본부터 존재 · 그대로 둠)

숨은 탭·다이얼로그를 전부 펼친 상태로 스타일시트의 모든 셀렉터를 문서에 대조했다.

| `.rv-header-actions-note` | 대응 노드 없음 |
| `.meta-readonly-value` | 대응 노드 없음 |
| `.origin-badge--manual` | 대응 노드 없음(자동 배지만 쓰임) |

무관하게 전부 정의하며 기준본 SCREEN-009 와 SD-009 도 같다.

**"명시도에 눌린" 유형은 발견되지 않았다.** §6 의 `fontSize`/`fontWeight`/`color`/`border*` 0건이

## 6. 시각 회귀 검증 (Chromium, `bin/compare-render.mjs`)

요소 **408개**를 1:1 대조했다. 뷰포트 1440 / 1280 / 1024 / 480 네 폭 모두 동일 결과다.

- **`fontSize` 0건 · `fontWeight` 0건**
- **`color` / `backgroundColor` / `border*Color` / `border*Width` 전부 0건**
  → 색 토큰 rename 과 `#ffffff`→`--bg-page` 흡수가 값을 보존했다는 실측 증거
- `lineHeight` **131건** — 전부 §2 에서 설명한 "원본이 선언하지 않아 상속받던 줄높이"가 사다리 값으로
  바뀐 것이다. 대표 패턴: 22.4px→21px(caption 1.6→1.5) · 22.4px→19.6px(label 1.6→1.4) ·
  27.2px→25.5px(title-sm) · 28.8px→26.1px(title-md) · `normal`→24px(버튼·인풋)

### 가로 변화 — 4건, 원인 1개

`div.rv-header-left` · `div.rv-header-title` · `h1` · `p.rv-header-meta` 가 각각 **`dw +1px`**
(1440px 에서는 `.rv-slider-thumb` 의 `dx +1` 이 하나 더 붙는다 — 같은 원인의 연쇄).

원인을 격리해 확정했다. `--font-body` 의 `-apple-system` 을 되돌려도 +1px 는 남았고,
**`--font-mono` 만 원본값으로 되돌리자 가로 변화가 0건이 됐다.**

```
--font-mono 만 원본값으로 되돌린 프로브
  변화 있는 요소: 131건
  그중 가로 변화(dx≠0 또는 dw≠0): 0건  ← 가로 리플로우 없음
```

즉 `Menlo, Consolas` 추가로 `#RAW-1042`(mono 14px)의 실제 폭이 1px 달라졌고, 그 span 을 품은
`h1` 의 콘텐츠 폭이 1px 커졌다. `--font-mono` 를 기준본 값으로 맞추는 것은 SD-009 가 명시한 조치라
그대로 채택했다. → §7 판단 2

부수적으로 **`-apple-system` 추가는 이 화면에서 측정 가능한 변화가 0이었다**(SD-009 노트의 우려 항목).

### 세로 변화

문서 전체 높이 1522 → **1512px**(-10px, -0.7%). 1024px 에서 -12px, 480px 에서 -44px(카드가 좁아져
줄바꿈이 늘고 그만큼 줄높이 축소가 누적된다).

내역은 전부 사다리 줄높이다. 가장 큰 것이 검토용 갤러리 -10px, 메모 목록 항목이 최대 8px 위로
올라간다(스크롤되는 패널 안). 캔버스·필름스트립·헤더·탭바 등 **높이가 고정된 골격은 변화 0**이다.
44px 고정 높이 버튼 안의 span 들은 줄높이가 늘었지만(`dh +5`) 버튼 높이가 고정이라 화면상 변화가 없다.

### 눈으로 확인

`--intended` 로 판정에서 제외한 영역이 **없다**(레이아웃을 고치지 않았으므로). 위 차이 전부가

## 7. 판단이 필요했던 지점 (지시서가 답을 주지 않아 스스로 정한 것)

1. ~~`color-scheme` 처리~~ → **판단 불필요로 해소됨.** 조율자 정정 2 로 "넣는다"가 확정됐고
   원본이 이미 기준본과 같은 형태로 갖고 있어 파일 변경이 없다(§4).
2. **`--font-mono` 를 기준본 값으로 맞췄다(가로 +1px 발생).** 관례표는 `--font-body` 의
   `-apple-system` 만 명시하고 mono 는 언급이 없다. SD-009 노트가 "`--font-mono` 기준본 값으로 맞춤"을
   기록했고 이번 라운드의 목적이 관례 정합이라 따랐다. **되돌리려면 `:root` 한 줄이다** —
   `--font-mono` 에서 `Menlo, Consolas` 를 빼면 가로 변화가 0건이 된다(§6 프로브로 실증).
3. **헤더 메타 줄의 폭 지배를 고치지 않았다.** §5 참조. 현재 콘텐츠에서 영향 0이고 4개 변경 축 밖이다.
4. **`--dur-*` → `--duration-*` 개명.** 관례표에 모션 토큰 항목이 없다. 색 토큰 개명과 같은 성격
   (이름만·값 동일)이고 기준본·SD-009 가 `--duration-*` 라 맞췄다. 렌더 영향 0.
5. **`--bg-alt` 를 `body` 배경 1곳에만 적용했다.** 이 화면에는 SD-009 의 `--surface-alt` 같은 전용
   토큰이 없어 `var(--n-0)` 이 페이지 대체 표면·hover 표면·말풍선 배경으로 **섞여 쓰인다.**
   전부 바꾸면 의미가 뭉개져, 페이지 바탕 하나만 별칭으로 올렸다.
6. **`.badge` 와 `.status-badge` 의 줄높이가 서로 달라졌다.** `.badge` 는 원본이 `1.3` 을 명시해
   유지했고, `.status-badge` 는 선언이 없어 사다리 `1.4` 가 들어갔다(높이 2.8px 축소).
   "명시된 값은 안 바꾼다" 원칙의 결과이며, 둘을 같게 맞추려면 원본이 명시한 값을 바꿔야 해서
   하지 않았다.
7. **입력 경계 대비 미달(`--n-3`, 2.01:1)을 고치지 않았다.** §5-A 참조. 9건 공통 결정 사안이고,
   경계색을 바꾸면 §6 의 "색 차이 0건" 판정이 깨진다. 관찰만 기록했다.
8. **죽은 규칙 7건을 지우지 않았다.** §5-B 참조. 전부 원본부터 있던 것이고 삭제가 렌더에 영향은
   없지만 사양 축소로 읽힐 수 있어 사실만 남겼다.

# 9. 최종 정리 스윕 — 경계 상향 · 죽은 규칙 정리

앞의 §1~§8 은 "렌더 무변경"이 판정 기준이던 관례 정합 라운드의 기록이다. 이 절은 그 위에 얹은
별도 라운드이며, **색이 의도적으로 바뀐다**(사용자가 시각 변화를 인지·승인).

## 9.1 폼 컨트롤 경계 상향 — §5-A 의 관찰을 실제로 조치했다

`--n-3`(#b1b8be, **2.01:1**) → `--border-strong`(=`--n-4`, #8a949e, **3.08:1**). WCAG 1.4.11 통과.

| 규칙 | 성격 |
|---|---|
| `.meta-select, .meta-input` · `.meta-textarea` · `.memo-add-input` · `.issue-comment-input` · `.rv-frame-input` | 폼 컨트롤 6종 — 상향 대상 |
| `.btn-secondary` | **버튼이지만 상향했다** — 배경이 `--bg-page`(흰색)라 경계가 유일한 식별 수단이다 |

**hover 충돌 없음**: 이 화면의 폼 컨트롤에는 hover 경계 규칙이 하나도 없다(`.btn-secondary:hover`
는 배경만 바꾸고 `.rv-frame-input:focus-visible` 은 `--p-5`). 따라서 기본을 올려도 상태 구분이
사라지지 않아 hover 를 한 단계 올릴 필요가 없었다.

**실측**: 요소 16개의 경계색이 `rgb(177,184,190)` → `rgb(138,148,158)` 으로 바뀌었고
(폼 컨트롤 9 + `.btn-secondary` 7), **기하 변화 0건 · 문서 높이 ±0px · 그 외 computed 속성 전부 0건**
(1280 / 480 동일). CSS 파일의 hex 집합은 55종으로 **변화 없다** — 이미 있던 토큰을 참조만 바꿨다.

### 올리지 않은 것 — `.rv-filmstrip-toggle` (판단 · 조율자 확인 필요)

`border: 1px solid var(--border)`(=`--n-2`, **1.54:1**)로 이 화면에서 **가장 낮은 대비의 상호작용 경계**다.
32×44 아이콘 토글이라 `.btn-secondary` 와 같은 "경계가 유일한 식별 수단인 버튼" 조항에 해당할 수 있다.
그럼에도 올리지 않은 이유는 지시서 §1 이 대상을 **폼 컨트롤**로 한정하고 버튼은 예외 조항으로만
열어 두었으며, 이번 배정이 판단 위임한 버튼은 `.btn-secondary` 하나였기 때문이다.
**올리는 것이 맞다고 보면 이 한 줄만 `--border-strong` 으로 바꾸면 된다.**

### 관찰 — 상향 대상 아님

`.memo-add-input::placeholder { color: var(--n-4) }` 는 #8a949e 로 흰 배경 대비 **3.08:1** 이다.
경계(1.4.11, 3:1)로는 통과지만 **텍스트(1.4.3, 4.5:1)로는 미달**이다. 플레이스홀더 텍스트 대비는
이번 승인 범위(경계 대비) 밖이라 손대지 않았다. `--text-faint`/`--text-muted` 토큰은 이 파일에 없어
지시서 §4(a) 는 해당 없음.

# 10. 추가 라운드 — 조율자 판정 기준 확정 반영

§9.1 에서 "올릴지 말지" 판단으로 올려 둔 항목을 조율자가 결정했다.

> **판정 기준(확정)**: 경계선이 그 상호작용 컨트롤의 **유일한 시각적 식별 수단**이고 현재 **3:1 미만**이면
> `--border-strong` 으로 올린다. **컨테이너 경계(카드·구획선·표 괘선)는 대상이 아니다.**

## 10.1 `.rv-filmstrip-toggle` 상향 — §9.1 에서 보류했던 것

`--border`(=`--n-2`, #cdd1d5, **1.54:1**) → `--border-strong`(=`--n-4`, #8a949e, **3.08:1**).
32×44 아이콘 토글이고 자기 배경이 `--bg-page`(흰색)로 **주변 필름스트립 바와 같아** 경계 말고는
식별 수단이 없다.

**상태 역전 확인**: `.rv-filmstrip-toggle:hover` 는 **배경만** 바꾸고(`var(--n-0)`) 경계는 건드리지
않는다. 포커스는 전역 `:focus-visible { outline: 3px solid var(--p-5) }` 로 **outline** 이라 경계와
축이 다르다. → **역전 없음. hover 를 올릴 필요가 없다**(018 `.input`·`.btn-secondary` 와 다른 점).

**실측**: `button.rv-filmstrip-toggle` **1개**만 `rgb(205,209,213)` → `rgb(138,148,158)`.
기하 0건 · 문서 높이 ±0px(1280 / 480) · 그 외 computed 속성 전부 0건.

## 10.2 전수 재조사 — 같은 기준의 컨트롤이 더 있는지

브라우저에서 **상호작용 요소를 전부 열거**해(button·a·input·select·textarea·label·summary·
`role=button|tab|checkbox|...`·`tabindex`·`cursor:pointer`) 각 경계색을 **그 요소 뒤의 실제 배경**과
대비 계산했다(투명이면 조상으로 거슬러 올라감).

결과 — 이 화면에서 3:1 미만은 **아래 1건뿐이고 대상이 아니다.**

|---|---|---|

# 11. `viewbox` → `viewBox` 표기 정규화 (조율자 판정 번복 반영)

§10.3 은 *"이 화면에 소문자 `viewbox` 가 있어도 손대지 않는다"* 였다. **그 판단이 뒤집혔다.**

**뒤집은 사유는 렌더가 아니라 표기 일관성이다.** 렌더 무영향 판정(§7.1 에서 처음 실측, 다른 두
담당이 독립 확인)은 그대로 유효하다. 다만 다른 배치들이 정규화를 마치면서 같은 산출물 세트 안에서
표기가 갈렸고(정규화 036·012·037·031 / 소문자 024·026·030·018·019), 그 자체가 이번 라운드가
지우려던 드리프트라 조율자가 전체 정규화로 통일했다.

## 적용

`design.html` 의 `viewbox=` **22건** → `viewBox=`. **다른 것은 한 글자도 바꾸지 않았다.**
`design-main.html`(서버 미러)은 건드리지 않았다.

## 검증 — 순수 표기 정규화임을 3중으로 고정했다

1. **대상 확인**: `viewbox=` 22건이 **전부 `<svg>` 태그 안**이고 data URI 안에는 0건이다
   (텍스트·CSS 문자열에 섞인 것을 건드릴 위험 없음).
2. **바이트**: 파일 길이 **30,978 → 30,978 (불변)**. 되돌리면 원본과 **바이트 완전 동일**
   (대소문자 외 어떤 변경도 없음을 기계적으로 보증).
3. **렌더**: 전/후 `compare-render diff`(1280 / 480) — computed style **전 항목 0건**,
   기하 변화 **0건**, 문서 높이 **±0px**.
4. **SVG 실측**: 아이콘 **22개**의 박스·잉크 범위·오버플로·`hasViewBox` 가 전/후 **완전 동일**.
   전부 `hasViewBox=true`(파서 보정 확인) · 오버플로 최대 `+0.00`(잘림 없음).
