## 1. 와이어프레임 대비 추가한 디자인 결정

와이어프레임은 섹션 순서·컴포넌트·정보 항목만 정하고 배치는 전부 세로 스택이다. 아래는 **골격을 바꾸지 않고
입힌 결정**이며, 섹션·컴포넌트를 더하거나 뺀 곳은 없다.

### 1-1. 레이아웃 리듬 — 세로 스택을 2열 2단으로 접었다

| 구간 | 와이어프레임 | 디자인 | 근거 |
|---|---|---|---|
| ② KPI | 카드 4장 인라인 | 4열 균등 그리드 (`--sp-md` gap) | 섹션 `layout: grid`, role `hero` |
| ③ 데이터 개수 | 카드 2장 세로 스택 | **2열** 그리드 | 섹션 description 원문 "**2열 카드**" |
| ④ 최근 완료 영상 / ⑤ 내 작업 현황 | 각각 전폭 세로 스택 | **좌우 2열 병치** | UI-077 description "대시보드의 '최근 완료 영상' 표와 **나란히 배치된다**" |

세로 스택은 와이어프레임 생성기의 기본값이지 설계된 배치가 아니다(생성기는 sections 를 순서대로 쌓는다).
스펙 본문과 카탈로그가 명시한 배치를 따랐고, **DOM 순서는 ①②③④⑤⑥ 그대로** 유지했다.

### 1-2. 수치 위계 — 두 단계로 갈랐다

- ② KPI 수치 = `display-sm` **26px** (ladder use_for: "KPI 카드 수치")
- ③ 데이터 개수 주 수치 = `display-md` **31px** (ladder use_for: "통계 대시보드의 핵심 수치 등 시선을 먼저 끌어야 하는 숫자")

③이 ②보다 큰 것은 의도다. ②는 "지금 처리할 일"의 건수고, ③은 사업 핵심 산출물(이미지 10만장·영상 5,000건)의
누적 달성치라 화면에서 먼저 읽혀야 한다. 두 섹션을 같은 크기로 두면 4+2 = 6개 숫자가 같은 무게로 경쟁한다.

### 1-3. 섹션 ⑥ 에러 배너를 참고 패널로 내렸다

⑥ description 은 "조회 실패 시 **상단에** 노출"이다. 정상 데이터와 동시에 성립하지 않는 상태라 본문에 함께
그리면 거짓 화면이 된다. SCREEN-009 가 세운 관례(점선 `reference-panel` 로 대체 상태를 문서화)를 그대로 따라
**조회 상태별 대체 표시** 패널 안에 배치했다. 같은 패널에 ②④⑤의 Skeleton 과 ④⑤의 빈 상태 문구도 함께 두었다.

- 로딩 / 빈 결과 / 조회 실패를 **세 칸으로 분리**한 것은 UI-007·UI-020·UI-021 이 공통으로 요구하는 규칙
  ("데이터 0건과 조회 실패는 항상 구분해서 표시한다")을 시안에서 눈으로 확인시키기 위해서다.

### 1-4. 역할 분기를 별도 참고 패널로 명시했다

본문 렌더는 **WORKER 시점(KPI 4카드 + 내 작업 현황 표)**이다. REVIEWER 시점(KPI 3카드, 내 작업 현황 표 없음)은
두 번째가 아니라 첫 번째 참고 패널에 3카드 그리드로 그렸다. 카드 안에 "작업자 전용" 같은 주석을 넣지 않은 이유는
그게 제품 UI 가 아니라 문서화이기 때문이다 — 실제 REVIEWER 화면에는 그 카드가 아예 없다.

### 1-5. 새로고침 시각을 버튼 좌측 정적 표기로 붙였다

②컴포넌트 note 가 지정한 그대로다(시계 아이콘 + `YYYY-MM-DD HH:mm:ss`). `<time datetime>` 로 마크업하고
mono 14px 로 두어 자릿수가 흔들리지 않게 했다. **자동 갱신이 없다**는 사실을 사용자가 알아야 하므로 이 표기가
버튼과 한 덩어리로 붙어 있어야 한다고 판단했다.

### 1-6. 완료율 미터 — **골격 밖으로 판정해 제거했다** (2회차 렌더 검증에서 확정)

1회차 시안은 ③ 보조 텍스트가 이미 말하는 완료율(77% / 69%)을 8px 막대로 한 번 더 인코딩하고, 스스로
"골격에 없던 요소일 수 있다"고 표기해 두었다. 2회차에서 골격을 다시 대조해 **골격 밖으로 확정하고 제거**했다.

판정 근거 — `SCREEN-011.md` 와 `wireframe.html` 이 같은 내용으로 일치한다:

| 근거 | 내용 |
|---|---|
| ③ 섹션의 components 열거 | **Card · Card · List** 3종이 전부다. `Progress` 가 없다 |
| `Progress` 타입의 유일한 출처 | ⑤ 내 작업 현황 (`ProgressBar 진행률`) — ③ 이 아니다 |
| ③ 에서 완료율이 등장하는 형태 | 컴포넌트가 아니라 **보조 텍스트 문자열** — `'검수완료 기준 · 전체 {N}장 (완료율 N%)'` |
| wireframe 의 ③ Components | `Card(이미지 데이터 개수) · Card(영상 데이터 개수) · List(이벤트 유형 분포)` — 동일 |

즉 완료율이라는 **값**은 골격에 있지만 그것을 그리는 **막대**는 골격에 없다. 골격 보존 원칙상 없는 것을
그리지 않는다는 판단으로 `.count-meta` 안의 `<div class="meter">` 2블록과 `.meter`/`.meter-fill` CSS 를 삭제했다.

- **완료율 값 자체는 그대로 남는다** — `완료율 77%` 배지가 보조 텍스트의 괄호 부분을 담당한다. 정보 손실 0.
- 제거 후 렌더로 레이아웃 성립을 확인했다 — ③ 카드 높이 435.9px → **418.9px**(미터 8px + `--sp-sm` gap 8px 분),
  두 카드 높이는 여전히 동일(418.9 = 418.9), 가로 오버플로·클리핑·요소 이탈 0건. `.count-meta` 는 자식이
  하나 남지만 상위 `.card-content` 의 `--sp-md` gap 이 간격을 그대로 유지해 이탈이 없다.
- ⑤ 의 `.progress-cell`(ProgressBar)은 **골격에 명시된 컴포넌트라 그대로 둔다.** 제거 후 5개 막대가
  모두 정상 렌더됨을 재확인했다(50/100/50/0/0%).

### 1-6a. 분포 리스트의 열 끝 구분선을 없앴다 (2회차 렌더에서 발견한 결함 수정)

`.dist-row` 는 모두 `border-bottom` 을 갖고 있었는데, 항목 수가 **홀수**면 2열 row-major 그리드에서
각 열의 마지막 항목이 서로 다른 행에 놓여 **구분선 두 줄이 계단처럼 허공에 남았다**(9종 카드에서 `납치(유괴)`
아래와 `산사태` 아래). 6종 카드는 짝수라 마지막 행이 가지런해 같은 결함이 보이지 않았다 — **같은 컴포넌트가
한 화면에서 다르게 무너진 것**이 단서였다.

이 분포는 "고정 슬롯이 아니라 서버 카테고리를 **개수 무관**하게 순회 렌더"가 명시된 컴포넌트라, 홀·짝
어느 쪽에서도 성립해야 한다. `.dist-row:nth-last-child(-n + 2) { border-bottom: none }` 로 고쳤다 —
2열 row-major 에서 **마지막 두 항목이 곧 두 열의 각 마지막 항목**이므로 개수와 무관하게 성립한다
(9종 → 8·9번째, 6종 → 5·6번째가 해제됨을 렌더로 확인).

### 1-7. 이벤트 분포는 막대 없이 라벨+건수 2열로만 그렸다 (의도적 절제)

UI-078 variants 가 **compact = "대시보드 — 파이차트 없이 라벨+건수 2열 그리드만 표시"**, withPie = "전체 통계
화면"으로 갈라 놓았다. 대시보드는 compact 이므로 비율 막대·파이를 넣지 않았다. 두 카드의 항목 수를 **9종 / 6종으로
다르게** 그린 것은 "고정 6개 슬롯이 아니라 서버가 내려주는 카테고리를 그대로 순회 렌더(개수 무관)"라는 컴포넌트
note 를 시안이 스스로 증명하게 하려는 것이다.

### 1-8. 차트 색 관련

**이 화면에는 차트가 없다.** 파이·막대 차트를 쓰지 않기로 한 근거는 1-7 이고, 남은 색 사용은 상태 배지와 진행률
막대뿐이다. 둘 다 색 단독으로 정보를 전달하지 않는다 — 배지는 한글 라벨을 항상 병기하고, 진행률 막대는 `50%` 같은
수치를 옆에 붙였다.

### 컴포넌트 규약을 따른 지점

- **KpiCard 에 장식 아이콘을 두지 않았다** — UI-010 이 `icon`·`iconBgClassName` 을 `[폐기]` 로 명시한다
  ("지표명과 값 텍스트가 카드의 정보를 모두 전달하므로 아이콘은 시각적 잡음만 더한다").
- **`trend`(증감) 를 그리지 않았다** — UI-010 에 optional 로 존재하지만 API-055 응답에 이전 기간 값이 없어
  근거가 없다. 지어내지 않았다. → **정보 부족**
- **DataTable 의 `max-height: 60vh` + `thead` sticky** 를 구현했다(행이 5건이라 시안에서는 스크롤되지 않는다).
- **로딩 시 표를 렌더하지 않고 스켈레톤으로 통째 대체**하는 규약을 참고 패널에 그대로 표현했다.

### ⚠️ 카탈로그에 근거가 없어 판단한 것 (미정)

### 3-5. 브라우저 실렌더 검증 (2회차 — 1회차의 미검증 항목을 해소)

**콘솔**: `favicon.ico` 404 **1건뿐**(요건상 무시 대상). 그 외 에러·경고 0건.

### 3-6. 죽은 CSS 선택자 점검

스타일시트 139개 규칙 전수를 DOM 과 대조했다. `.refresh-stamp .icon` 이 **어떤 요소에도 걸리지 않는
죽은 규칙**이었다 — 마크업은 `.icon-sm` 을 쓴다. 선택자를 실제 요소에 맞춰 고쳤고, **값은 죽은 규칙이
의도했던 `--n-5` 가 아니라 실제로 렌더되던 `--n-6` 을 고정**했다. `--n-5` 로 "복원"하면 아이콘이
오히려 옅어지므로 진한 쪽을 택했다(렌더 변화 0).

> ⚠️ 이 점검의 1차 시도는 **`walked: 0` 으로 아무것도 검사하지 않고 "죽은 규칙 0건"을 반환**했다.
> Chrome 의 CSS 중첩 지원 이후 `CSSStyleRule` 도 빈 `cssRules` 를 갖기 때문에 재귀가 그쪽으로 새어
> 규칙 본체에 도달하지 못한 것이다. `r.type === 1` 검사로 고친 뒤에야 실제 139개를 훑었다.

나머지 미사용 선택자 16종(`.btn-primary`·`.btn-outline`·`.btn-ghost`·`.btn-sm`·`.badge-error`·
`.t-body-lg`·`.t-nav-link`·`.text-strong`·`.data-table .cell-empty`·`.alert .alert-actions`·
`.kpi-card[data-zero]` 등)은 **결함이 아니다** — 이 시안이 쓰지 않을 뿐 공유 컴포넌트 계열이 갖춰야 할
변형이고, SCREEN-005·009 관례가 같은 방식으로 전체 세트를 싣는다. 그대로 뒀다.

## 검증하지 못한 것 (정직한 한계)

- **1280 미만 폭의 반응형 동작은 검증 대상 밖이다.** 다만 경계에서 **불연속**을 관측해 기록한다 —
  1280 에서 KPI 4장이 4열(각 288px)인데 **1279 에서 2열(각 607.5px)로 접힌다**. 288px 가 1280 에서
  성립하므로 1279 에서 접혀야 할 폭 제약은 없다. 게다가 같은 1279 에서 `data-cards="3"`(REVIEWER 참고
  패널)은 **3열을 그대로 유지**해, 한 화면 안에서 4장짜리는 2열·3장짜리는 3열이 되는 비대칭이 생긴다.
  1440·1280 두 기준 폭은 영향이 없고(둘 다 4열) 1279 에서도 오버플로·클리핑은 0건이라 **이번에 고치지
  않았다** — 브레이크포인트 위치 조정은 렌더 결함 수정이 아니라 반응형 설계 변경이라 작성자 판단이 필요하다.
- **폰트 폴백 상태에서만 봤다.** DS 지정 폰트(Pretendard GOV·D2Coding)가 로컬에 없어 시스템 폴백으로
  렌더됐다. 자간·숫자 폭·`tabular-nums` 실동작은 실폰트 환경에서 재확인이 필요하다. 다만 폴백에서도
  줄바꿈·클리핑이 0건이므로, 실폰트에서 폭이 크게 늘지 않는 한 여유는 있다.
- **상호작용 상태는 hover 만 우연히 확인**했다(표 행 `#FFFBEB` 가 실제로 칠해지는 것을 스크린샷에서 봄).
  `:focus-visible` 링·`:disabled`·버튼 hover 는 CSS 선언만 있고 **실제로 트리거해 보지 않았다**.
- **참고 패널의 대체 상태는 정적 표현이라 전이를 보지 않았다** — 로딩→성공/실패 전환, Skeleton 애니메이션의
  `prefers-reduced-motion` 분기는 선언만 확인했다.
- **DS 폰트(Pretendard GOV·D2Coding)가 실제로 로드되는 환경에서 보지 않았다.** 폰트 폴백 상태의 자간·
  숫자 폭은 미확인이며, `font-variant-numeric: tabular-nums` 가 폴백 폰트에서 먹는지도 미확인이다.
- **기존 고충실 시안이 11건이라고 전달받았으나 착수 시점 로컬 키트에는 2건(SCREEN-005·SCREEN-009)뿐이었다.**
  관례 판단은 그 2건에 근거한다. 작업 중 SCREEN-008·SCREEN-025 가 병행 생성돼 파일명·토큰 표기·ladder
  클래스가 내 시안과 일치함을 확인했으나, **그 두 건의 레이아웃·상태 표현까지 대조하지는 않았다.**
  나머지 시안에 이 노트와 어긋나는 관례가 있을 가능성은 남아 있다.


## 게시본 안전 마크업 전환 (재업로드 회차)

LogiCraft 게시 sanitizer 가 일부 태그·속성을 떨어뜨려 게시 프리뷰가 로컬과 달라지던 것을 바로잡았다.
**서버가 저장한 CSS 는 바이트 단위로 그대로 통과하는 것을 실측**했으므로, 잘리는 표현은 모두 CSS 로 옮겼다.
로컬 렌더가 달라지지 않았는지는 전환 전후 **전체 화면 픽셀 대조**로 확인했다.

- `<time datetime>` → `<span>`(클래스 유지). sanitizer 가 `<time>` 을 벗기면서 `.stamp-time` 색이 빠지던 것을 막는다.
- 픽셀 대조 결과 **차이 0**. 지어낸 화면 문구는 **0건**이었다.

## 셸 합성 시 표가 넘치던 문제 (가로 넘침 수정)

셸(좌측 주 메뉴 240px)과 합성하면 본문 폭이 뷰포트보다 240px 좁아지는데, 접기 임계가 **뷰포트 기준**이라
그 차이를 몰라 2열을 유지한 채 표가 넘쳤다 — 1280px 에서 **+87px**, 1440px 에서 **+7px**(단독 시안은 0).

**컨테이너 쿼리로 전환**했다. 접기 기준을 본문이 실제로 쓸 수 있는 폭(`.screen-root` 콘텐츠 박스)으로 바꾼 것이다.

- **임계 조정(1279 → 1519)안은 택하지 않았다.** 그러면 **단독 시안이 1440px 에서 1열로 접혀** 게시하는
  렌더의 구성 자체가 바뀐다. 넘치는 것은 합성일 때뿐인데 단독 렌더를 희생할 이유가 없다.
- 임계 **1199 = 종전 뷰포트 임계 1279 − 좌우 여백 40px×2** 이라, 단독 시안은 모든 폭에서 종전과 동일하게
  렌더되고 셸 합성일 때만 한 열 앞당겨 접힌다. 열을 지우거나 항목을 빼지 않았다.
- 여백(`.screen-root { padding }`)만 뷰포트 기준으로 남겼다 — `@container` 규칙은 컨테이너 **자손**에만
  적용되므로 컨테이너 자신의 여백은 바꿀 수 없다. 넘침의 원인도 아니었다.
- 실측: 합성·단독 모두 **1280·1366·1440·1520·1600 전 폭에서 넘침 0**, 단독 렌더는 픽셀 대조 **차이 0**.
  자바스크립트는 쓰지 않았다.
