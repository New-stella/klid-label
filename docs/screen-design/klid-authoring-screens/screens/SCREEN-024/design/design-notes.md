## 1. 색 토큰 이름 — 값은 보존, 이름만 기준본 체계로

`--nt-→--n-` `--pr-→--p-` `--sc-→--s-` `--er-→--e-` `--in-→--i-` `--wn-→--w-` `--su-→--su-`
단계 `05→0 10→1 … 90→9 95→10`.

두 자리 색 토큰 **49개** 중 **47개**가 이 규칙 그대로 값이 일치했다. 나머지 **2개는 값이 어긋나
규칙이 아니라 값을 기준으로 매핑**했다.

| 원본 | 값 | 규칙대로면 | 그 이름의 기준본 값 | 채택 |
|---|---|---|---|---|
| `--su-70` | `#1f4727` | `--su-7` | `#285d33` ✗ | **`--su-8`** |
| `--wn-40` | `#ffb114` | `--w-4` | `#c78500` ✗ | **`--w-3`** |

근거는 `_shared/design-system.md` 의 scale 배열이다. success 배열의 `#1f4727` 은 index 8,
warn 배열의 `#ffb114` 는 index 3 이며 기준본 SCREEN-009 도 그렇게 정의한다. 원본 SD-009 가
두 자리 유사 스케일(05/40/50/60/70)을 쓰면서 이 두 자리만 DS 인덱스와 어긋나 있었다.

규칙대로 `--su-7` 로 옮겼다면 hex 가 `#1f4727 → #285d33` 으로 **바뀌었을 것**이다.
`--su-70` 은 `.du-badge--active`(활성 배지 글자색)에 실제로 쓰이므로 눈에 보이는 변화가 됐다.
`--wn-40` 은 `:root` 에만 있고 사용처가 0 이라 무해했지만 같은 원칙으로 맞췄다.

### 수동 판단분

| 원본 | 조치 |
|---|---|
| `--white` | 제거. 쓰이던 5곳은 `--bg-page`(`#ffffff`, 동일값) 로 대체 |
| `--surface-page`, `--surface-card` | `--bg-page` 로 통합 |
| `--surface-alt` | `--bg-alt` |
| `--row-hover: #fffbeb` | 유지. design-system.md `do_rules` 가 명시한 지정값이라 임의색이 아니다. 설명 주석도 유지 |
| `--border` / `--border-strong` | 신설(`var(--n-2)` / `var(--n-4)`). **값이 이미 `n-2` 이던 경계 3곳에만** `--border` 를 적용했다(표 헤더 하단선·역할 배지 테두리·상태 스트립 상단선). `n-1` 경계를 `--border` 로 바꾸면 선이 진해져 시각이 달라지므로 `var(--n-1)` 그대로 뒀다 |
| `--font-body` / `--font-mono` / `--shadow-*` | 기준본 값으로 맞춤 |

`.du-input`·`.du-select`·`.du-btn--secondary` 의 테두리는 `--border`(=n-2)가 아니라 **`--n-5`** 다.
WCAG 1.4.11(비텍스트 UI 3:1)을 맞추려고 의도적으로 진한 단계를 고른 것이며 그 주석도 함께 옮겼다.
**`--border` 로 바꾸지 말 것.**

## 3. 결함 (a) — 도움말 문장이 입력 필드 폭을 정했다

### 전

```css
.du-filter-form { display: flex; flex-wrap: wrap; align-items: flex-end; gap: var(--sp-md); }
.du-field       { display: flex; flex-direction: column; gap: var(--sp-xs); min-width: 240px; }
```

`.du-field` 에 `flex` 도 `max-width` 도 없어 flex base size 가 `auto` → 내용의 max-content 가 된다.
열 안에서 가장 긴 자식이 `.du-help` 문장이라 **도움말이 검색 입력의 폭을 결정**했다.

### 후

```css
.du-field { display: flex; flex-direction: column; gap: var(--sp-xs); }

.du-filter-form > .du-field         { flex: 1 1 280px; min-width: 240px; max-width: 420px; }
.du-filter-form > .du-field--select { flex: 0 1 180px; min-width: 180px; }
```

`flex-basis` 를 명시값 `280px` 로 두면 flex base size 계산에 max-content 가 개입하지 않고,
사용폭은 `[240px, 420px]` 로만 클램프된다. 세 값 모두 내용과 무관하므로 도움말 길이는
폭 계산식에 아예 들어오지 않는다.

**실측(Chromium, 뷰포트 1280px, 검색 입력 폭 px)**

| 도움말 | 전 | 후 |
|---|---:|---:|
| 원본(약 40자) | 435 | **420** |
| 2배 | 873 | **420** |
| 4배 | — | **420** |
| "짧게." 로 축소 | 240 | **420** |

전에는 도움말을 2배로 늘리면 입력도 2배(435→873)가 됐고 짧게 줄이면 `min-width` 바닥(240)까지
쪼그라들었다. 후에는 네 경우 모두 420 으로 고정이다.

> ⚠ 지시서 예시의 `.du-help { flex-basis: 100% }` 는 **넣지 않았다.** `.du-field` 는
> `flex-direction: column` 이라 그 안에서 `flex-basis` 는 주축인 **세로(높이)** 로 해석된다.
> 폭에는 영향이 없고 높이만 흔든다. 위 `flex-basis: 280px` 만으로 목적이 달성된다.

> ⚠ `.du-field` 는 모달 본문(`.du-modal-body`, 이것도 column flex)에서도 쓴다. 그래서 폭 규칙을
> `.du-field` 에 직접 걸지 않고 **`.du-filter-form >` 로 한정**했다. 한정하지 않으면 모달의 필드가
> `flex-basis: 280px` 를 **높이**로 받아 레이아웃이 무너진다. 실측으로 모달 필드는 위치·크기 무변화 확인.

## 4. 결함 (b) — 필터 버튼이 카드 오른쪽 끝까지 밀렸다

### 전 → 후

```css
.du-filter-actions { display: flex; gap: var(--sp-sm); margin-left: auto; }   /* 전 */
.du-filter-actions { display: flex; gap: var(--sp-sm); }                       /* 후 */
```

`margin-left: auto` 가 남은 공간을 전부 먹어 버튼이 필드에서 떨어져 카드 끝에 붙었다.

**실측(1280px)**: 역할 필드 오른쪽 끝 → 버튼 그룹 시작 간격이 **305px → 16px**(= `--sp-md`, 폼의 gap).
버튼 그룹이 폼 오른쪽 끝에 붙어 있던 것(여백 0)이 이제 필드 바로 뒤를 따라온다.

**줄바꿈 동작**

| 뷰포트 | 전 | 후 |
|---|---|---|
| 1024px | 한 줄, 버튼은 오른쪽 끝(간격 49px) | 한 줄, 간격 16px |
| 900px | 버튼이 다음 줄로 내려가 오른쪽 정렬 | 검색이 344px 로 줄며 **한 줄에 다 들어감** |
| 820px | 다음 줄 + 오른쪽 정렬 | 다음 줄 + **왼쪽 정렬**(필드와 같은 왼쪽 기준선) |
| ≤767px | 세로 스택, 버튼 오른쪽 정렬 | **원본과 완전 동일** |

820px 대(768~약 880px의 좁은 구간)에서 줄바꿈 시 버튼이 왼쪽에 놓인다. 오른쪽으로 보내려면
제거한 `margin-left:auto` 가 다시 필요하므로, 필드와 같은 왼쪽 기준선에 두어 한 덩어리로 읽히게 했다.

모바일 미디어쿼리의 `margin-left: 0` 은 base 에서 `margin-left` 를 없앴으므로 함께 제거했다.

## 5. 시각 회귀 검증

원본과 정합본을 같은 오리진의 iframe 두 개에 나란히 올려 요소 223개를 1:1 대조했다(Chromium 1280px).

- **`font-size` 차이 0건**
- **`color` / `background-color` / `border-*-color` / `border-*-width` 차이 0건** — 색 토큰 rename 이 값을 보존했다는 실측 증거
- **필터 폼 밖 요소의 `dx`(가로 이동) 0, `dw`(폭 변화) 0 — 전부** — 가로 리플로우가 전혀 없다. 표는 열 폭까지 동일
- 세로로는 문서 전체 높이 **2256 → 2267px (+11px, +0.5%)**. 내역은 두 가지뿐이다:
  - 필터 카드 **+21px** — 검색 필드가 420px 로 좁아져 도움말이 2줄이 됐다. 결함 (a) 수정의 직접 결과
  - 사다리 line-height 적용으로 상태 스트립·모달의 제목/캡션이 **각 1~4px 축소**(예: `h3` 28.8→26.1px = 18×1.45)

line-height 변화는 원본이 `body` 의 1.6 을 상속하던 자리에 사다리 규정값(title-md 1.45, label 1.4,
caption 1.5)이 들어간 것으로, 사다리 채택의 의도된 귀결이다. 배지·아바타·페이지 버튼처럼
flex 로 가운데 정렬되는 요소는 line-height 가 바뀌어도 실측 크기·위치가 그대로였다(`dh` 0).

## 6. 결함 (a) 수정이 부른 회귀 — 검색 입력만 위로 들려 올라갔다

### 무엇이 깨졌나

§3 의 폭 고정(`max-width: 420px`)은 **의도한 대로 동작했다.** 그런데 폭이 435px → 420px 로 좁아지면서
도움말이 **1줄 → 2줄**이 됐고, 폼이 `align-items: flex-end`(밑단 정렬)라 **도움말 높이만큼 검색 필드가
길어져 그 안의 입력 상자가 혼자 위로 밀려 올라갔다.** 역할 셀렉트와 버튼은 도움말 둘째 줄 높이에 남았다.

실측(1280px, 컨트롤 밑단 좌표 검색/역할/버튼):

| | 검색 입력 | 역할 셀렉트 | 버튼 | 어긋남 | 라벨 상단(검색/역할) |
|---|---|---|---|---|---|
| 원본 `design-main` | 281 | 306 | 306 | **25px** | 213 / 238 |
| 회귀본(§3 직후) | 281 | 327 | 327 | **46px** | 213 / 259 |
| 현재 | 281 | 281 | 281 | **0** | 213 / 213 |

**원본도 이미 25px 어긋나 있었다.** 도움말이 1줄이라 눈에 덜 띄었을 뿐이고, 폭 고정이 그 줄 수를
2줄로 늘리자 어긋남이 두 배가 되어 드러났다. 즉 결함 (a)가 이 결함을 덮고 있었다.

### 왜 정적 검사가 놓쳤나

§5 의 원본↔정합본 대조를 `--intended '.du-filter-form'` 으로 돌렸다. 그 플래그는 지정 서브트리의
기하 변화를 **'의도된 변경'으로 분리 집계**한다 — 필터 폼을 고치는 중이었으니 그 안의 변화는 당연하다고
본 것이다. 그 결과 **정확히 회귀가 일어난 영역만 판정에서 빠졌다.** 이번 수정의 검증은 `--intended`
없이 필터 영역 안쪽 좌표를 전부 출력해 확인했다.

> 교훈: `--intended` 는 "여기는 바뀔 예정"이라는 표시일 뿐 "여기는 검사 안 해도 된다"가 아니다.
> 고치는 영역이야말로 좌표를 직접 읽어야 한다.

### 전 → 후

```html
<!-- 전: 도움말이 필드 안에 있다 → 그 높이가 필드 높이에 더해진다 -->
<div class="du-field">
  <label for="du-search">검색</label>
  <input class="du-input" id="du-search">
  <p class="du-help">이름 또는 이메일 부분일치로 …</p>
</div>

<!-- 후: 도움말을 폼의 직계 자식으로 꺼내고 aria-describedby 로 잇는다 -->
<div class="du-field">
  <label for="du-search">검색</label>
  <input class="du-input" id="du-search" aria-describedby="du-search-help">
</div>
<p class="du-help" id="du-search-help">이름 또는 이메일 부분일치로 …</p>
```

```css
/* 전 */
.du-filter-form { display: flex; flex-wrap: wrap; align-items: flex-end; gap: var(--sp-md); }
.du-filter-form > .du-field { flex: 1 1 280px; min-width: 240px; max-width: 420px; }
.du-filter-form > .du-field--select { flex: 0 1 180px; min-width: 180px; }

/* 후 */
.du-filter-form {
  display: grid;
  grid-template-columns: minmax(0, 420px) 180px auto;
  gap: var(--sp-xs) var(--sp-md);
  align-items: end;
}
.du-filter-form > .du-field { min-width: 0; }
.du-filter-form > .du-field,
.du-filter-form > .du-filter-actions { grid-row: 1; }
.du-filter-form > .du-filter-actions { justify-self: start; }
.du-filter-form > .du-help { grid-row: 2; grid-column: 1; }
```

### 왜 이 해법이 도움말 줄 수에 견고한가

**도움말이 정렬에 참여하는 행에서 아예 빠졌다.** 라벨·컨트롤은 1행, 도움말은 2행이므로 도움말이 몇 줄이
되든 1행의 밑단 정렬은 계산에 도움말을 포함하지 않는다. 실측(1280px, 도움말 텍스트를 늘려가며):

| 도움말 | 도움말 높이 | 검색 입력 폭 | 컨트롤 밑단(검색/역할/버튼) |
|---|---|---|---|
| 원본(2줄) | 42px | 420 | 281 / 281 / 281 |
| ×2(3줄) | 63px | 420 | 281 / 281 / 281 |
| ×4(5줄) | 105px | 420 | 281 / 281 / 281 |

**폭 고정(§3 의 성과)도 그대로다.** 폭을 정하는 것이 이제 `max-width` 가 아니라 **그리드 트랙**
(`minmax(0, 420px)`)이라, 트랙 상한이 고정값이므로 내용이 폭 계산에 개입할 여지 자체가 없다.
`compare-render.mjs width` 판정: 원본·2배·4배·축소·복원 **전부 420px**.

### 채택하지 않은 대안

| 안 | 기각 사유 |
|---|---|
| 셀렉트·버튼에 `padding-bottom` 고정값으로 도움말 자리 확보 | 도움말이 3줄이 되면 다시 깨진다. 위 ×2/×4 표를 통과 못 한다 |
| `.du-help` 를 `position: absolute` 로 흐름에서 제거 | 같은 이유로 취약하고, 좁은 뷰포트에서 아래 요소와 겹친다 |
| `max-width` 를 키워 도움말을 1줄에 넣기 | §3 이 고친 취약성을 되살리는 것이다. 뷰포트가 좁아지면 다시 2줄이 되어 같은 붕괴가 난다 |

### 판단한 지점 3가지

1. **트랙 하한을 `240px` 이 아니라 `0` 으로 뒀다.** 240px 하한이면 `240 + 180 + 199(버튼) + 32(gap) = 651px`
   가 필요한데, 미디어쿼리 경계 바로 위(768px)의 폼 폭은 638px 라 **13px 가로 넘침**이 난다.
   하한이 0 이어도 폭 고정은 유지된다 — 상한이 고정값이라 내용이 트랙을 넓힐 수 없기 때문이다.
   768px 에서 검색 폭은 227px 로 줄어들 뿐 넘치지 않는다.
2. **행을 자동 배치에 맡기지 않고 `grid-row` 로 명시했다.** 도움말이 DOM 상 2번째 자식이라, `grid-column: 1`
   만 주면 자동 배치 커서가 2행으로 넘어가 **역할·버튼까지 함께 2행으로 끌려 내려간다**(실측으로 확인).
   명시 배치는 DOM 순서와 무관해지고, 모바일에서는 `grid-row: auto` 로 풀어 DOM 순서(검색 → 도움말 →

### 7.6 `viewbox`(소문자) → `viewBox` 5건 수정 — 렌더 무변화 실측

지시서 §4-(b)의 전제(*"소문자면 속성이 무시돼 스케일링이 안 된다"*)는 **HTML 문서에서는 사실이 아니다.**

따라서 **"고치면 깨진다"를 근거로 보류하지 않았고**, 대신 **소스 위생**을 근거로 고쳤다 —
이 마크업을 XML 로 직렬화하거나 JSX/`.svg` 로 옮기면 그때는 대소문자가 유효해져 **실제로 깨진다.**

`design.html` 의 `viewbox=` **5건**을 `viewBox=` 로 치환했다(문자열 길이 불변, 다른 변경 0).

3:1 을 넘으므로(회색 표면 위 2.82) 토큰 이름이 아니라 표면이 목표를 정한다.
