## § 디자인 결정 (와이어프레임 대비 추가분)

### 레이아웃·시각 위계

- **좌측 레일 폭을 168px → 280px(1440 기준)로 넓혔다.** 와이어프레임의 168px 는 생성기 기본값이고,
  그 폭에서는 카드 패딩(24×2)을 빼면 버튼 내부가 **118px** 인데 '비식별 누락 신고' 라벨(112px) +
  아이콘(20px) + gap(6px) = 138px 이라 **10px 넘친다**(브라우저 실측). DS 가 강제하는 44px 타깃과
  17px 버튼 텍스트를 지키면서 3분할 골격을 유지하려면 레일이 넓어져야 한다. 1279px 이하에서는
  260px, 우측 패널은 아래로 내린다.
- **여백 리듬**: 섹션 간 `sp-lg 24px`, 카드 안쪽 `sp-lg 24px`(DS `card_padding_px` 24), 화면 좌우
  `sp-xl 40px`, 밀집 패널 내부 `sp-sm~md 8~16px`. DS `whitespace_principle` 의 "밀집 영역은
  8~16px 까지 좁히되 44px 타깃 유지"를 좌·우 패널에 적용했다.
- **1차/보조 액션 구분**: 화면에서 primary(채움)는 **'마킹 완료' 하나뿐**이다. 초기화·비식별 신고는
  secondary(테두리), 재생/일시정지도 secondary. DS `color_usage` 의 "강조는 면적이 아니라 위계로
  만든다"를 따랐고, 파괴적이지 않은 액션에 error 색을 쓰지 않았다(신고는 경고가 아니라 보고 행위다).
- **비식별 신고를 툴바 맨 아래 `danger-slot`(구분선 아래)으로 격리**했다. 마킹 흐름(모드→단축키→
  건수→초기화→완료)과 성격이 다른 이탈성 액션이라, 순서는 와이어프레임대로 두되 구분선으로 갈랐다.
  버튼 아래에 결과 안내("신고하면 영상이 잠기고 재비식별 후 마킹부터 다시 시작합니다")를 상시 노출해
  누르기 전에 대가를 알 수 있게 했다 — UC-019 대체 흐름과 UI-057 의 사전 안내 요구를 따른 것이다.

### 미디어 매트 (이 화면 고유 결정)

- **화면에서 어두운 표면은 매트 하나뿐이다.** DS `overview_md` 가 "앱에 다크 표면은 없다. 유일한
  예외는 영상 프레임을 얹는 미디어 매트와 그 위 오버레이"라고 명시했고, 그 예외 범위를 정확히
  지켰다 — 매트 배경 `--n-10`, 프레임 표면 `--n-9`, 경계 `--n-5`, 전경 흰색.
- **재생 컨트롤은 매트 위에 얹지 않고 아래 밝은 바(`--n-0`)에 두었다.** 어두운 배경 위 컨트롤은
  대비 여유가 사라지는 이 화면 최대의 위험 지점인데, 밝은 표면으로 내리면 그 문제가 통째로
  사라지고 프레임을 가리지도 않는다. 매트 위 오버레이는 **읽기 전용 칩 2개**(비식별 적용 / 프레임·시각)로
  한정했고 둘 다 흰 글자 18.43:1 이다.
- **프레임 자리는 실제 인물처럼 보이는 것을 만들지 않았다.** 하늘·지면·건물 블록·차량 블록만 있는
  추상 도식이고, 그 위에 **마스킹 박스 2개**(점선 테두리 + '마스킹' 라벨)를 얹었다. 비식별 영상이라는
  사실 자체가 이 도식이 전달해야 할 유일한 정보이기 때문이다. 그라데이션·노이즈·일러스트는 쓰지
  않았다(DS `dont_rules`).

### 상태별 표현

- **마킹은 세 곳에서 같은 선택 상태를 공유한다** — 타임라인 핀(선택 시 `p-7` + `p-1` 링, 폭 6→10px),
  칩(선택 시 `p-0` 표면 + `p-5` 테두리 + 굵기 600), 매트 오버레이의 프레임 번호. 기본 렌더는 다섯 마크
  중 **F540(00:18)** 이 선택된 상태이고 재생 위치도 같은 지점이라 세 표시가 한 사실을 가리킨다.
  선택은 색만이 아니라 **크기·굵기**로도 구분한다(DS "색만으로 상태를 구분하지 않는다").
- **플레이헤드를 선택 마크(30px)보다 길게(44px + 삼각 헤드) 뽑았다.** 둘이 같은 위치에 겹치는 것이
  정상 상황인데, 길이가 같으면 한 덩어리로 읽혀 "재생 위치"가 사라진다.
- **배치 스테퍼는 색이 아니라 캡션이 상태를 말한다** — '비식별 완료 / 마킹 진행 중 / VLM 대기 …'.
  UI-018 이 명시한 요구(점은 상태와 무관하게 모양·크기가 같으므로 캡션이 유일한 구분 수단)를 그대로
  지켰고, 화면에 보이지 않는 `role=status aria-live` 로 "전체 7단계 중 1단계 완료 — 마킹 진행 중"을
  함께 알린다.
- **모드에 따라 갈리는 두 블록은 동시에 그리지 않았다.** 기본 렌더는 **수동 모드**(단축키 안내)이고,
  자동 모드의 **간격(프레임) 입력**은 참고 패널에 따로 뒀다 — UI-043 이 "수동 모드에서는 단축키 안내를
  *대신* 노출한다"고 규정하므로 한 화면에 둘 다 그리면 거짓이 된다.
- **대체 상태 4종**(버퍼링/탐색 스피너 · 마크 0건 토스트 경고 · 칩 목록 빈 상태 · 신고 불가 툴팁 2종)은
  본문 자리를 대신하는 표시라 동시에 그릴 수 없다. SCREEN-009 가 쓴 **참고 패널(점선 테두리 + 배지)**
  관례로 나란히 정적 노출했다.
- **'마킹 완료' 버튼은 비활성 상태를 만들지 않았다.** 골격 note 가 "항상 클릭 가능(비활성 상태 없음),
  마크 0건이면 토스트 경고로 제출만 막는다"고 명시했고, 그 토스트를 참고 패널에 실물로 그렸다.

### 타이포·수치 표기

- 프레임 번호·타임코드·배속은 전부 **mono(D2Coding 14px) + `tabular-nums`** 로 고정했다. 목록에서
  세로로 비교되는 값이라 자릿수가 흔들리면 눈이 따라가지 못한다.
- 한글이 실제로 줄바꿈되는 자리(`stage-caption` · 단축키 설명 · 범례 · 도움말 · 빈 상태)에만
  `word-break: keep-all` 을 걸었다. 1280px 에서 '프레임추출 대기'가 '프레임추출 대/기'로,
  '선택 마킹 삭제'가 3줄로 쪼개지던 것을 실측 확인 후 잡은 것이다(현재 각각 어절 단위 2줄 / 1줄).

## § 확신 없는 것 · 확인하지 못한 것

- **stale 사유(`API-043의 data.responses 변경`)가 골격에 반영됐는지 확인하지 못했다.** 키트에
  `_shared/api/` 가 비어 있어 API-043 의 현재 응답 스키마를 볼 수 없다. 그래서 골격
  (`SCREEN-006.md` v32)에 적힌 것만 그렸다 — `stages[]` 7단계와 `Progress` 하나. 응답 필드를
  추측해 화면에 추가하지 않았다.
- **`단계 진행률` 의 값 산출 근거는 화면 표시 결정이다.** 골격은 컴포넌트 이름만 주고 값의 출처를
  말하지 않아, 스테퍼가 이미 보여주는 사실(7단계 중 1단계 완료)을 백분율로 옮겨 `14%` 로 적고
  **수치 문구를 함께 병기**했다. 서버가 내려주는 별도 필드를 가정하지 않았다.
- **fps 30 · 총 1,050프레임 · 길이 00:35 · rawSn 1284 는 예시 데이터다.** 골격 description 이
  `getCurrentFrame(30fps)` 라고 적어 30 을 썼지만, UI-042·UI-044 는 **fps 를 고정값으로 두지 말라**고
  명시한다. 그래서 화면에 '30fps 기준'이라고 드러나게 적었다. 마크 5건의 프레임/시각은 30fps 기준으로
  서로 어긋나지 않게 계산했다(F540 = 18.0초 = 00:18, 재생 위치와 동일).
- **비식별 신고 사유 입력 모달을 그리지 않았다.** UI-057 이 자체 제공하는 모달이고 **골격에 그 섹션이
  없다.** 영역을 더하지 않는다는 원칙에 따라 버튼과 사전 안내까지만 그렸다.
- **비식별 미완료(404) 화면과 서명 URL 재발급 실패 표시를 그리지 않았다.** purpose 문단에 서술은
  있으나 **섹션·컴포넌트로 선언되지 않았다.** 추측으로 UI 를 만들지 않았다.
- **`durationSec` 미확보 시 타임라인 미렌더**(UI-044 규정)도 표현하지 않았다. 같은 이유로 골격에
  상태 선언이 없다.
- **영상 식별 정보(CCTV명·이벤트유형·배정자 등)를 헤더에 넣지 않았다.** 골격 헤더에 없는 정보다.
  화면 컨텍스트로 넣은 것은 와이어프레임이 이미 표기하던 **route 뿐**(`/marking/1284`)이다.
- **`Kbd` 는 카탈로그에 없다.** 골격 note 가 그 이름을 쓰지만 UI-NNN 이 없어 `⚠️ 미정` 으로 남기고
  임의 등록하지 않았다.
- **'AI탐지 / AI분할' 표기는 UI-018 규정을 따랐고 'VLM' 은 그대로 뒀다.** UI-018 이 모델명 비노출
  대상으로 지목한 것은 YOLO·SAM2 뿐이고, 골격·SCREEN-009 시안 모두 'VLM' 을 그대로 쓴다. VLM 도
  가려야 하는지는 **확인하지 못했다.**

## 게시본 안전 마크업 전환 (재업로드 회차)

LogiCraft 게시 sanitizer 가 일부 태그·속성을 떨어뜨려 게시 프리뷰가 로컬과 달라지던 것을 바로잡았다.
**서버가 저장한 CSS 는 바이트 단위로 그대로 통과하는 것을 실측**했으므로, 잘리는 표현은 모두 CSS 로 옮겼다.
로컬 렌더가 달라지지 않았는지는 전환 전후 **전체 화면 픽셀 대조**로 확인했다.

- `<kbd>` 8개 → `<span class="kbd">`. CSS 가 이미 `.kbd` 클래스 기반이라 CSS 변경은 없다.
  sanitizer 가 `<kbd>` 를 벗기면 `Del`·`Backspace` 두 칩의 글자가 `DelBackspace` 로 붙던 문제가 사라진다.
- 탐색 슬라이더를 **0~100 백분율 척도**로 재척도했다(`min/max/step` 이 잘리는데 그 기본값이 0/100/1 이라,
  백분율로 두면 게시본에서도 손잡이 위치가 유지된다). 실제 값(0~35초, 18초)은 `aria-value*` 로 보존했다.
  그 대가로 손잡이가 로컬 기준 약 3px 이동한다.

### 지어낸 화면 문구 제거

- `완료하면 잔여 배치가 이어서 시작됩니다.` (부제) — `잔여 배치` 는 내부 파이프라인 용어다. 앞문장만 남겼다.
- `비식별 영상만 서빙합니다 — …` (플레이어 카드 헤더) — `서빙` 은 서버 용어이고, 재생되지 않는 영상은
  애초에 이 화면에 도달하지 않는다. 같은 사실은 영상 위 **'비식별 적용' 뱃지**가 이미 화면 언어로 보여준다.
  죽은 `.player-note` 규칙도 함께 지웠다.
- `비식별이 선두 단계입니다` (배치 처리 단계 헤더) — 파이프라인 설계 서술이고, 순서는 단계 표시가 이미 보여준다.


## 오토라벨 묶음 표시 (UI-018 v7 반영)

배치 단계 표시기가 응답의 7단계를 그대로 7칸으로 그리던 것을, 오토라벨에 해당하는 세 단계
(AI 탐지 · AI 분할 · 트랙 보간)를 **오토라벨링 한 칸으로 접어 5칸**으로 바꿨다.

표시 단위를 조작 단위에 맞추기 위함이다 — 재수행·건너뛰기가 오토라벨 묶음 단위로만 동작하는데
세 칸으로 나뉘어 보이면 각 칸을 따로 조작할 수 있다고 읽힌다.

- 접은 칸의 상태는 세 단계를 합쳐 판정한다: 하나라도 실패면 실패, 실패가 없고 하나라도 진행 중이면
  진행 중, 셋 다 끝났으면 완료.
- 세부 단계는 그 칸에 **글자 보조 표기**로 병기해 진행 해상도를 잃지 않는다(`.stage-substep`).
  진행 중이면 어느 세부 단계인지, 실패면 어느 세부 단계에서 실패했는지를 적는다.
  **백분율 진행률 바가 아니다** — 색이 아니라 글자로 알린다.
- 접은 칸도 캡션 규칙을 그대로 따른다(묶음 이름 + 상태 병기). 점은 상태와 무관하게 모양·크기가
  같으므로 캡션이 색을 대신하는 유일한 구분 수단이다.
- 보조 표기 색은 `--n-6`(#58616a) on `--bg-page`(#ffffff) = **6.3:1 — WCAG AA 통과**(본문 4.5:1 하한).
  실패 칸에서도 보조 표기는 중립색으로 둔다 — 색 신호를 하나 더 얹지 않기 위함이다.

이 화면의 현재 시안 상태는 마킹 진행 중이라 오토라벨링 칸이 아직 **대기**다. 대기 칸에는 보조 표기를
붙이지 않는다 — 진행 중이거나 실패한 세부 단계가 없어 적을 대상이 없기 때문이다.

### 단계 진행률 수치 정합

표시가 5칸이 되면서 `7단계 중 1단계 완료 · 14%` 가 화면의 점 개수와 어긋나 `5단계 중 1단계 완료 · 20%`
로 맞췄다(`aria-valuenow` 와 막대 폭 동반).

> ⚠ **막대 자체는 그대로 두었다.** `Progress 단계 진행률` 은 SCREEN-006 v34 사양이 여전히 갖고 있는
> 원소이고, UI-018 이 금지하는 것은 *접은 칸의 보조 표기*를 진행률 바로 그리는 것이다. 다만 UI-018 은
> props 설명에서 `progress` 를 백분율 바로 표시하지 않는다고도 적어, 두 사양이 완전히 겹치지는 않는다.
> 이 시안은 **사양을 바꾸지 않고 숫자만 맞췄다** — 막대의 존폐는 화면 사양 쪽 결정이다.

## 검증 질문 선택 반영 (회차 — 섹션⑤ 신설)

사양(SCREEN-006 v49)의 `검증 질문 선택` 섹션이 시안에만 빠져 있어 이번에 채웠다. 사양·와이어프레임·
구현(FE `VerificationQuestionSelect` / BE `VerificationEventQuestionResolver`)에는 이미 반영돼 있었고
**시안 한 층만 뒤처져 있던 드리프트**다. 위 머리글의 "5개 섹션 … ⑤배치단계 인디케이터" 서술이
그 시점(섹션⑤가 배치단계이던 판)에 멈춰 있던 것도 같은 회차에 정정했다.

### 배치
본문 가운데 컬럼의 **마킹 타임라인 카드 바로 아래**. 사양이 `role: main` 이고 와이어프레임도
본문 컬럼에 ②→⑤ 순으로 두었다. 좌측 툴바·우측 칩 목록은 건드리지 않았다.

### 와이어프레임에 없는 디자인 결정
- **네이티브 `select` 유지 + 토큰 chevron** — OS 기본 화살표를 `appearance:none` 으로 걷어내고
  `--n-6` chevron 을 얹었다. 커스텀 트리거(button)로 바꾸지 않은 것은 **의도**다: 이 화면은
  Space·Enter·Delete 를 전역 단축키로 받는데 그 핸들러가 INPUT·TEXTAREA·**SELECT** 일 때만
  비켜서므로, button 트리거면 드롭다운 조작이 마킹 추가·제출로 새어 나간다.
- **선택한 질문 전문 블록** — 단순 텍스트가 아니라 `--bg-alt` 배경 + 좌측 `--p-5` 3px 강조선으로
  "지금 저장될 값"임을 카드 안에서 한 단계 올렸다. 긴 문구를 위해 `white-space: pre-wrap`.
- **필드 라벨과 카드 제목의 위계 분리** — 카드 제목은 `검증 질문`(t-title-md), 필드 라벨은
  `마킹과 함께 저장할 질문`(t-label), 도움말은 `고르지 않으면 첫 번째 질문이 쓰입니다`(t-caption).
- **`select:focus-visible` 추가** — 기존 포커스 규칙 셀렉터에 select 가 없었다(그 전까지 화면에
  select 가 없었으므로). DS `do_rule`(3px outline + 2px offset)을 그대로 적용했고 기존 요소 영향은 0.

### 무열화 증명
기준선(게시본 미러)과 문자 단위 diff 에서 **`replace`·`delete` opcode 0건 · 순수 삽입만**이다
(HTML 의 head 래퍼 교체분 제외 — 로컬 원본 형식으로 되돌린 것). 즉 기존 본문은 한 글자도
바뀌지 않았고 한글 손상이 원리적으로 불가능하다.

### ui_component 보강 (권고만 — 등록하지 않음)
이 회차에서 새로 그린 UI 단위는 **네이티브 select 필드**와 **선택값 전문 병기 블록** 둘이다.
카탈로그의 `UI-003 input: Select` 는 Radix 조합형이라 트리거가 `button` 이고, 이 화면의 전역
단축키(Space·Enter·Delete)와 충돌해 **의도적으로 쓰지 않았다**. 다만 두 단위 모두 이 화면 전용이라
재사용 가치가 낮아 `ui_component` 신규 등록은 하지 않았다. 필요해지면 별도 회차에서 판단한다.
