# SD-001 (SCREEN-018 검수 목록 화면) — 관례 정합 노트

정본 파일: `design.css` + `design.html`
기준본(관례): SCREEN-009 `design/design.css`
같은 폴더의 `design-main.{html,css}` 는 서버 현재본의 로컬 미러이며 이번에 수정하지 않았다.

이번 작업은 재디자인이 아니다. 바꾼 것은 ①색 토큰 이름 ②타이포 지정 방식 ③`lang="ko"`

## 1. 색 토큰 이름 — 이 파일은 "이름 충돌" 유형이었다

이 파일은 기준본과 **같은 접두어**(`--n-` `--p-` `--s-`)를 쓰면서 **스케일이 달랐다**.
같은 이름이 정반대 밝기를 뜻했다.

| 이름 | 기준본 | 이 파일(변환 전) |
|---|---|---|
| `--n-10` | `#131416` (가장 어두움) | `#e6e8ea` (거의 흰색) |
| `--p-10` | `#0b50d0` | `#d8e5fd` |
| `--s-10` | `#02162c` | `#d6e0eb` |

### 변환 방법 — 문자열 순차 치환을 쓰지 않았다

`--n-100 → --n-10` 을 문자열로 치환하면 그 결과가 다시 `--n-10 → --n-1` 규칙에 걸려
**이중 변환**된다. 그래서 다음 순서로 했다.

1. 기준본 `:root` 를 파싱해 **hex → 기준본 토큰명 역인덱스**를 만들었다.
   기준본 색 토큰 78개에 **중복 hex 가 하나도 없어** 역인덱스가 1:1 로 성립했다.
2. 이 파일의 `:root` 를 파싱해 **각 토큰의 값(hex)으로** 기준본 이름을 찾았다. 자릿수 규칙이
   아니라 값으로 찾았다 — SD-009 에서 원본 이름이 DS 스케일과 어긋난 사례가 2건 있었기 때문이다.
   **이 파일에서는 어긋난 자리가 없었다**(37개 색 토큰 전부 값 기준 매핑이 자릿수 규칙과 일치).
3. 치환은 정규식 `--[A-Za-z0-9_-]+` 로 **파일 전체를 한 번 훑으면서 사전 조회**로 바꿨다.
   한 번의 패스라 치환 결과가 다시 치환 대상이 되지 않는다.

매핑 결과(37건):

```
n-0→n-0  n-10→n-1  n-20→n-2  n-30→n-3  n-40→n-4  n-50→n-5
n-60→n-6  n-70→n-7  n-80→n-8  n-90→n-9  n-100→n-10
p-0→p-0  p-10→p-1  p-20→p-2  p-50→p-5  p-60→p-6  p-70→p-7
s-0→s-0  s-10→s-1  s-50→s-5  s-70→s-7
success-{0,50,60,70}→su-{0,5,6,7}   warn-{0,50,60,70}→w-{0,5,6,7}
error-{0,50,60,70}→e-{0,5,6,7}      info-{0,50,60,70}→i-{0,5,6,7}
```

## 2. 타이포 — 사다리 유틸 `.t-*` 12종

원본은 사다리를 `--fs-* / --fw-* / --lh-*` **30개 변수**로 두고 컴포넌트 규칙에서 3개씩 꺼내
쓰는 방식이었다. 이걸 걷어내고 CSS 에 사다리 12종을 정의한 뒤 **HTML 에서 클래스로 지정**한다
(기준본 방식). 사다리 값은 기준본 verbatim.

HTML 에서 `.t-*` 를 109곳에 달았다(`t-body-md` 39 · `t-label` 26 · `t-mono` 12 · `t-body-sm` 10 ·
`t-button` 10 · `t-caption` 6 · `t-display-sm` 4 · `t-title-lg` 1 · `t-title-sm` 1).

컴포넌트 규칙에 남긴 `font-size` 는 5건이다. 기준본 자신도 사다리 밖 `font-size` 를 10건 갖고
있으므로 이건 결함이 아니다.

| 남긴 것 | 값 | 사유 |
|---|---|---|
| `.btn-sm` | 14px/500 | 사다리에 없는 조합 |
| `.recheck-chip` | 14px/500/1.5 | 사다리에 없는 조합(caption 크기에 medium 굵기) |
| `.page-btn` | 14px/500 | 사다리에 없는 조합 |
| `.error-state-preview .title` | 15px/600 | 사다리에 없는 조합 |
| `.empty-state-preview .title` | 15px/600 | 사다리에 없는 조합 |

`base font-size 는 두지 않았다.` 원본이 `.review-list-page` 에 `font-size` 를 선언하지 않아
`.t-*` 를 달지 않은 요소는 브라우저 기본 16px 로 렌더돼 왔다(페이지네이션 말줄임표 `…` 등).
여기에 17px base 를 새로 넣으면 그 요소들이 조용히 커지므로 넣지 않았다. SD-009 가 base 17px 을
둔 것은 **그 원본이 이미 갖고 있던 값을 옮긴 것**이라 이 파일과 사정이 다르다.

## 3. `.rl-filter` — 결함이 없어서 아무것도 하지 않았다

조율자 정정(SD-024 필터 폼 정렬 붕괴)을 받아 이 화면의 필터 행을 따로 확인했다.

- `.rl-filter` 는 `align-items: flex-end` 다 — 정정이 지목한 조건에 해당한다.
- 그러나 **도움말·설명 문장을 가진 자식이 없다.** 세 자식이 전부 `라벨 + 컨트롤`(14px/1.4 라벨 +
  4px gap + 44px 컨트롤) 또는 버튼 두 개뿐이라 **키가 서로 같고 여러 줄로 늘어날 텍스트가 없다.**
- 폭도 이미 `flex: 1 1 260px` / `flex: 0 1 200px` 로 **명시값**이 잡혀 있어 내용이 폭을 지배하지
  않는다. 실측으로 확인했다 — 라벨 텍스트를 ×2·×4·축소로 바꿔도 검색 입력 폭이 **752px 고정**이다
  (원본·정합본 동일).
- `margin-left: auto` 는 파일 전체에 0건이라 결함 (b) 도 해당 없음.

따라서 지시 4항("이 구조가 없으면 아무것도 하지 마세요")대로 **필터 레이아웃을 건드리지 않았다.**
`--intended` 도 쓰지 않았다 — 의도한 레이아웃 변경이 하나도 없으므로 판정에서 제외할 영역이 없고,
모든 기하 변화를 그대로 출력해 확인했다.

## 4. 결함 — 라벨 수 열의 `font-size` 가 한 번도 적용되지 않고 있었다

브라우저 대조가 잡아낸 유일한 실제 결함이다. 육안으로는 드러나지 않았다.

```css
.rl-table tbody td   { font-size: var(--fs-body-md); }   /* 명시도 (0,1,2) → 17px */
.cell-labelcount     { font-size: var(--fs-mono);    }   /* 명시도 (0,1,0) → 14px, 패배 */
```

`.cell-labelcount` 는 `<td>` **자신에게** 붙는 클래스라 `.rl-table tbody td` 와 같은 요소를
가리키는데 명시도가 낮다. 그래서 의도한 14px 은 한 번도 적용된 적이 없고 **실렌더는 17px** 이었다
(`font-family: var(--font-mono)` 는 td 규칙이 선언하지 않아 정상 적용됐다 — 즉 mono 서체의 17px).

같은 파일의 `.cell-video__id` 는 `<td>` 안의 `<span>` 이라 td 의 17px 을 **상속**으로만 받는다.
자기 선언이 상속을 이기므로 그쪽은 14px 이 정상 적용돼 왔다. 두 자리의 차이는 여기에 있다.

**조치**: 렌더 결과를 보존했다. `.cell-labelcount` 에 `.t-mono`(14px)를 달면 이 열만 17→14px 로
줄어드는 **눈에 보이는 변화**가 되므로, `.t-body-md`(17px)를 달아 지금 보이는 것을 그대로 유지하고
mono 서체는 컴포넌트 규칙에 남겼다. 한 번도 적용된 적 없는 `font-size` 선언은 걷어내고 그 사실을
CSS 주석으로 남겼다.

> ⚠ 이 열을 **원저자 의도대로 14px mono 로 되돌릴지는 판단 대기**다. 그건 시각 변경이라
> 이번 정합(재디자인 아님)의 범위 밖으로 봤다. 되돌리려면 `design.html` 의 `cell-labelcount`
> 6곳을 `t-body-md` → `t-mono` 로 바꾸기만 하면 된다.

## 5. 서체 스택 — 지시대로 기준본에 맞췄고, macOS 에서 폭이 달라진다

```
전  'Pretendard GOV', 'Pretendard', -apple-system, BlinkMacSystemFont, 'Apple SD Gothic Neo', 'Noto Sans KR', sans-serif
후  'Pretendard GOV', -apple-system, 'Apple SD Gothic Neo', 'Noto Sans KR', sans-serif
```

지시서가 "`-apple-system` 을 넣는다, 기준본과 동일하게, 렌더 차이 우려는 성립하지 않는다"고
확정해 그대로 따랐다. 다만 **측정된 사실은 기록해 둔다.**

측정기(Chromium/macOS)에서 문자열 `산불_감시_A구역_014.mp4 video-00142 48건`(17px) 폭:

| 스택 | 폭 |
|---|---:|
| 전(원본) | 335.70 px |
| 후(기준본) | **312.80 px** |
| `-apple-system` 단독 | 328.08 px |
| `BlinkMacSystemFont` 단독 | 335.70 px |
| `'Apple SD Gothic Neo'` 단독 | 312.80 px |
| `'Pretendard'` 단독 | 328.08 px (= 미설치, 시스템 기본으로 폴백) |

즉 `'Pretendard'` 는 이 측정기에 없고, 실제 원인은 **`BlinkMacSystemFont` 제거**다. 한글 문자에
대해 `-apple-system` 이 글리프를 대지 못해 다음 항목으로 내려가는데, 전 스택에서는 그 다음이
`BlinkMacSystemFont` 였고 후 스택에서는 `Apple SD Gothic Neo` 다.

**실배포 OS(비 macOS)에서는 세 이름이 모두 해석되지 않아 양쪽이 똑같이 `Noto Sans KR`/sans-serif
로 떨어진다** — 지시서의 판단대로 배포 환경에서는 차이가 없다. 아래 §6 의 가로 변화 111건은
전부 이 macOS 한정 차이이며, 서체 스택을 원본으로 고정하고 다시 재면 **1건**으로 줄어든다.

## 6. 시각 회귀 검증

Chromium 으로 원본과 정합본의 요소를 1:1 대조했다. 두 가지를 따로 쟀다.

### (A) 서체 스택을 원본으로 고정 — 토큰 rename + 사다리 전환만의 효과 (1280px)

- **`fontSize` 차이 0건 · `fontWeight` 차이 0건**
- **`color` / `backgroundColor` / `border-*-color` / `border-*-width` 차이 0건**
  → 이름 충돌 스케일 변환이 값을 보존했다는 실측 증거다. 이 파일에서 가장 중요한 결과다.
- **가로 변화 1건** — `span.spinner` 뿐이고 그것도 `@keyframes rl-spin` 으로 **회전 중인 정사각형**의
  `getBoundingClientRect` 가 각도에 따라 최대 √2 배까지 커지는 측정 아티팩트다(실행마다 값이 달라진다:
  `dw-1` → `dw5`). **레이아웃 리플로우는 0이다.**
- 세로: 문서 높이 1482 → 1490px (+8px). 내역은 `lineHeight` 23건 전부이며 아래 §6-1 로 나눈다.

### (B) 실제 정합본 (design-main.html → design.html, 1280/1024/480px)

- `fontSize` 0건 · `fontWeight` 0건 · 색/경계 전부 0건 — (A)와 동일
- 가로 변화 111건 — **전부 §5 의 서체 스택 차이**다. (A)에서 1건인 것이 근거다.

### 6-1. `lineHeight` 23건 — 사다리 채택의 의도된 귀결

| 대상 | 전 → 후 | 사유 |
|---|---|---|

## 판단이 필요했던 지점 (지시서가 답을 주지 않아 스스로 정한 것)

1. **라벨 수 열을 17px 로 유지** — §4. "시각 결과물은 지금과 같아야 한다"를 원저자 의도보다 앞세웠다.
   되돌리는 방법을 §4 에 적어 뒀다.
2. **base `font-size` 를 새로 두지 않음** — §2. SD-009 와 다른 선택이며 사유를 적었다.
3. **`--dur-*` → `--duration-*` 개명** — 지시서 3축(색·타이포·`lang`) 밖이다. 값이 바뀌지 않는
   순수 개명이고 기준본 이름에 맞추는 것이 이번 라운드의 취지라 포함했다. 되돌리기 쉽다.
4. **`--border` 를 n-2 경계에만, `--border-strong` 을 n-4 hover 경계에만 적용** — n-1 경계는 그대로.
   SD-009 와 같은 원칙(값이 바뀌는 치환은 하지 않는다)이다.
5. **`html { color-scheme: only light; }` 를 넣지 않음** — 기준본 CSS 에는 있으나 지시서가
   "`color-scheme` 은 넣지 않는다"고 확정했다. HTML `<meta>` 축과 CSS 축을 구분해 지시한 것인지
   확실치 않아 **지시 문구 그대로 넣지 않는 쪽**을 택했다. 판단 대기 항목이다.
6. **배지·표 셀까지 `.t-*` 클래스로 옮김** — 기준본 SCREEN-009 는 `.badge`(14/600/1.4)처럼
   사다리 값을 CSS 에 그대로 둔 곳이 있어 관례가 둘로 읽힌다. 직전 실례 SD-009 가 배지까지
   클래스로 옮겼으므로 그쪽에 맞췄다.

## 확인 필요 (지어내지 않고 남긴다)

- **입력 경계 대비** — `.input` / `.select-trigger` 의 경계가 `--border`(= n-2, `#cdd1d5`)다.
  흰 배경 대비 약 1.6:1 로 WCAG 1.4.11(비텍스트 UI 3:1) 미달로 보인다. 기준본과 SD-009 는 같은
  자리에 `--n-5` 를 쓰고 그 사유를 주석으로 달고 있다. **이번에 바꾸지 않았다** — 색이 눈에 띄게
  진해지는 변경이라 이 정합의 범위를 넘고, 9개 파일에 공통으로 걸리는 결정이라 개별 판단할 일이
  아니라고 봤다. 별도 판단 요청.
- **`rgba(255,255,255,0.6)`** — 스켈레톤 반짝임 그라디언트 1건. 대응 토큰이 없어 그대로 뒀다
  (지시서 §3 "대응 토큰 없는 반투명은 그대로" 규칙 적용). 원본에도 있던 값이다.

# 7. 최종 정리 스윕 — 경계 상향 · `color-scheme` · 죽은 규칙

앞의 §1~§6 은 "렌더 무변경"이 판정 기준이던 관례 정합 라운드의 기록이다. 이 절은 그 위에 얹은
별도 라운드이며, **색이 의도적으로 바뀐다**(사용자가 시각 변화를 인지·승인).

## 7.1 입력·셀렉트 경계 상향 — "확인 필요"로 남겼던 항목의 결론

`--border`(=`--n-2`, #cdd1d5, **1.54:1**) → `--border-strong`(=`--n-4`, #8a949e, **3.08:1**).
§6 말미 "확인 필요"에 적어 둔 판단 요청이 9건 공통 결정으로 확정돼 반영했다.

```
--n-2 (=--border)          #cdd1d5  vs #ffffff = 1.54:1   ★미달  (전)
--n-4 (=--border-strong)   #8a949e  vs #ffffff = 3.08:1   통과   (후)
--n-5                      #6d7882  vs #ffffff = 4.51:1   통과   (hover)
```

### ★hover 를 한 단계 올렸다 — 안 올리면 상태 구분이 사라진다

이 파일은 `.input:hover, .select-trigger:hover { border-color: var(--border-strong); }` 로
**hover 가 이미 `--n-4`** 였다. 기본을 `--n-4` 로 올리면 기본과 hover 가 **같은 색**이 되어
hover 피드백이 통째로 사라진다. 지시서 §1 의 단서대로 hover 를 `--n-5`(4.51:1)로 한 단계 올려
구분을 유지했다.

```
전  기본 n-2(1.54:1)  →  hover n-4(3.08:1)
후  기본 n-4(3.08:1)  →  hover n-5(4.51:1)
```

**실측**: `input.input` · `select.select-trigger` **2개**의 경계색이 `rgb(205,209,213)` →
`rgb(138,148,158)`. 기하 변화 0 · 문서 높이 ±0px · 그 외 computed 속성 전부 0건(1280 / 480).
hover 변경은 정적 목업에서 렌더에 나타나지 않는다. CSS hex 집합 39종 **변화 없음**.

### 올리지 않은 것 — `.btn-secondary` (판단 · 조율자 확인 필요)

`.btn-secondary { background: var(--bg-page); border-color: var(--border); }` 로 **흰 배경 위
1.54:1** 이며, hover 는 `--n-3`(2.01:1)이다. SCREEN-019 에서는 같은 성격의 `.btn-secondary` 를
**올렸는데 이 화면에서는 올리지 않았다** — 019 는 배정이 버튼 판단을 명시적으로 위임했고 이
화면은 대상을 `.input`/`.select-trigger` 로 한정했기 때문이다. **두 화면의 처리가 갈리므로
조율자 판단이 필요하다.** 올린다면 hover(`--n-3`)가 기본(`--n-4`)보다 옅어져 상태가 역전되므로
hover 도 `--n-5` 로 함께 올려야 한다.

`.kpi-card`(카드) · `.rl-table-card` · `thead` 하단선 · `.state-showcase` 점선은 **컨테이너 경계**라
지시서 §1 대로 손대지 않았다.

## 7.2 `color-scheme` 누락 보정

`html { color-scheme: only light; }` 를 추가했다. §6 "판단이 필요했던 지점" 5번에서 지시 문구를
좁게 읽어 넣지 않았던 항목이며, 이번 라운드에서 누락 3건 중 하나로 확정됐다.
넣기 전 `grep -c color-scheme` = **0** 을 확인했고, 위치·문자열은 기준본
`SCREEN-009/design/design.css`(79~80행)와 동일하게 `* { box-sizing: border-box; }` 바로 다음이다.
라이트 전용 문서라 렌더 변화는 없다(실측 0건).

## 7.3 죽은 규칙 — 기계 검출 결과 **삭제 대상 0건**

스타일시트 전 규칙을 브라우저에서 재판정했다. 판정기는 **선언을 실제로 제거했다 되돌리며
computed style 을 재측정**한다(`* { transition: none }` 로 전환을 끄지 않으면 `.btn`·`.kpi-card`·
`.input` 의 transition 대상 속성이 전부 "inert" 로 오판된다 — 이 파일에서 실제로 발생했다).

### `.cell-labelcount` — §4 의 죽은 선언은 **이미 제거돼 있다**

§4 가 기록한 `font-size: var(--fs-mono)`(14px, `.rl-table tbody td` 의 17px 에 눌려 한 번도
적용되지 않음)는 앞 라운드에서 이미 걷어냈고 CSS 주석과 §4 에 의도가 남아 있다. 이번 재판정에서
**명시도에 눌린 선언은 0건**으로 확인됐다.

> **원저자 의도 기록(살리지 않는다)**: 라벨 수 열은 원래 **mono 14px** 로 의도됐다. 지금은
> **mono 17px** 로 렌더된다(`.t-body-md`). 살리면 이 열만 17→14px 로 작아지는 눈에 보이는 변화가
> 되어 이번 승인 범위 밖이다. 되돌리려면 `design.html` 의 `cell-labelcount` 6곳을
> `t-body-md` → `t-mono` 로 바꾸면 된다.

### 매칭 0 규칙 4건 — 전부 보존

| 보존 | 사유 |
|---|---|
| `.t-title-md` · `.t-body-lg` · `.t-nav-link` | 관례가 사다리 **12종 전부 정의**를 요구한다 |
| `.event-badge--violence` | 사건유형 배지의 **변형 카탈로그**다. 형제 5종(`--fire` `--flood` `--accident` `--fall` `--none`) 중 넷이 실제로 쓰이고 있어 하나만 지우면 사양이 빈다 |

## 7.4 `.spinner` 는 3회 실행으로 판별했다 — 측정 아티팩트

`@keyframes rl-spin` 으로 회전 중인 정사각형이라 `getBoundingClientRect` 가 각도에 따라 최대 √2 배까지
커진다. 3회 실행 결과 **매번 부호와 크기가 달랐다**:

```
run 1   1280: dx1 dy1 dw-2 dh-2      480: dx1 dy1 dw-1 dh-1
run 2   1280: dx2 dy2 dw-4 dh-4      480: dx2 dy1 dw-3 dh-3
run 3   1280: dx-1 dy-1 dw2 dh2      480: dx1 dy1 dw-1 dh-1
```

→ 리플로우가 아니다. 이 요소를 제외하면 이번 편집의 기하 변화는 **0건**이다.

# 8. 추가 라운드 — 조율자 판정 기준 확정 + `.select-trigger` 死 선언

> **판정 기준(확정)**: 경계선이 그 상호작용 컨트롤의 **유일한 시각적 식별 수단**이고 현재 **3:1 미만**이면
> `--border-strong` 으로 올린다. **컨테이너 경계(카드·구획선·표 괘선)는 대상이 아니다.**

## 8.1 `.btn-secondary` 상향 — §7.1 에서 "화면마다 갈린다"고 올린 항목의 결론

`--border`(=`--n-2`, **1.54:1**) → `--border-strong`(=`--n-4`, **3.08:1**).
SCREEN-019 는 같은 컴포넌트를 이미 올렸는데 이 화면(**더 낮은 1.54:1**)을 두면 지우려던 드리프트를
새로 만드는 셈이라는 것이 확정 사유다.

### hover 도 함께 올렸다 — 안 올리면 **상태가 역전된다**

hover 가 `--n-3`(2.01:1)이라 기본이 `--n-4`(3.08:1)로 올라가면 **hover 가 기본보다 옅어진다.**
`--n-5`(4.51:1)로 올려 순서를 유지했다(`.input` 에 적용한 것과 같은 형태).

```
전  기본 n-2(1.54:1)  →  hover n-3(2.01:1)
후  기본 n-4(3.08:1)  →  hover n-5(4.51:1)
```

**실측**: `button.btn.btn-secondary` ×1 + `.btn-secondary.btn-sm` ×2 = **3개**가
`rgb(205,209,213)` → `rgb(138,148,158)`. 기하 0 · 문서 높이 ±0px(1280 / 480).

## 8.2 ★남은 미달 2건 — 회색 표면 위라 `--border-strong` 으로도 3:1 에 못 미친다 (판단 요청)

전수 재조사에서 나온 **새 사실**이다. `.input`·`.select-trigger` 는 흰 배경이 아니라
**`.rl-filter` 의 회색 표면(`--bg-alt` = `--n-0`, #f4f5f6) 위에** 놓인다.

```
경계 vs 흰색 #ffffff        경계 vs 회색표면 #f4f5f6
  --n-2  1.54:1               --n-2  1.41:1
  --n-4  3.08:1  ← 통과       --n-4  2.82:1  ← ★여전히 미달
  --n-5  4.51:1               --n-5  4.13:1  ← 통과
  --n-6  6.30:1               --n-6  5.77:1
```

**입력의 흰 채움(`--bg-page`)은 그 회색 표면 대비 1.09:1** 이라 채움만으로는 컨트롤이 구분되지
않는다 — 즉 **경계가 유일한 식별 수단이 맞고, 확정 기준에 정확히 해당하는데 목표 토큰이 기준을
충족하지 못하는 경우**다.

**바꾸지 않았다.** ①확정 지시가 지정한 토큰은 `--border-strong` 이고 ②`--n-5` 로 올리면 hover 를
`--n-6` 로 또 밀어야 하며 ③**9개 화면에 공통으로 걸리는 정책 문제**(다른 화면도 회색 표면 위에
컨트롤을 둘 수 있다)라 개별 판단할 일이 아니라고 봤다. 1차 상향으로 1.41:1 → 2.82:1 개선은 유지된다.

> 참고: 이 저장소의 DS 는 이미 **표면별 토큰 조정** 선례를 갖고 있다 — SCREEN-019 에
> *"n-0 회색 표면 위라 n-5 대신 n-6 사용 — DS do_rules"* 주석이 텍스트 축에 존재한다.

## 8.3 `.kpi-card` — 대상 아님(확정 지시의 제외 항목)

`button.kpi-card` ×3 이 흰 배경 위 **1.54:1** 이다. `<button>` + `aria-pressed` 인 필터 토글이지만
**시각적으로 카드**이고 조율자가 "카드·구획선·표 괘선은 대상이 아니다"라고 명시해 **손대지 않았다.**
`box-shadow: var(--shadow-sm)` 와 큰 수치 텍스트가 있어 경계가 유일한 식별 수단이라고 보기도 어렵다.
선택된 카드는 `border: 2px solid var(--p-5)`(4.55:1)로 상태를 따로 표현한다. **기록만 남긴다.**

## 8.4 `.select-trigger` 의 flex 4선언 삭제 — 픽셀 대조 `diffPx 0`

`display:flex` · `align-items:center` · `justify-content:space-between` · `gap` 4선언이
**`<select>` 에 걸려 효과가 0** 이었다(UA 가 내부 렌더를 소유한다). 지시서 §3 의
"그 요소 타입에 무효한 속성" 삭제 대상이다.

**선행 확인(조율자 요청)** — 이 4선언은 **`.select-trigger` 단독 규칙**에 있고, 공용 선택자
`.input, .select-trigger` 와 **분리돼 있다.** `.select-trigger` 는 HTML 에서 `<select>` 1곳에만
쓰인다(`<div>` 등 다른 요소와 묶여 있지 않다). → **쪼갤 필요 없이 안전.**

**검증** — 전체 페이지 스냅샷은 이 페이지에서 **비결정적**이라(같은 파일끼리 대조해도 불일치가 났다)
판정 근거로 쓸 수 없었다. 대신 **영역 클립 대조**로 바꾸고 **대조군(before vs before)** 을 함께 돌렸다:

```
대조군 before vs before   1280 .select-trigger 동일 · .rl-filter 동일
                           480 .select-trigger 동일 · .rl-filter 동일
본검사 before vs after    1280 .select-trigger diffPx 0 (2회) · .rl-filter diffPx 0 (2회)
                           480 .select-trigger diffPx 0 (2회) · .rl-filter diffPx 0 (2회)
```

박스 크기도 동일(1280: 200×44 / 480: 382×44). computed `display` 만 `flex` → `block` 으로 바뀌고
**렌더는 한 픽셀도 다르지 않다.** 화살표는 flex 정렬이 아니라 `background-image` +
`background-position: right 12px center` 가 그리므로 영향이 없다.
경계·패딩·타이포·`appearance`·`cursor` 등 나머지 선언은 **건드리지 않았다.**

공유 컴포넌트 정합: SCREEN-012 는 애초에 없고 SCREEN-030 도 같은 근거로 삭제됐다 — 이제 셋이 같다.

## 8.5 `viewbox` — 이 화면은 추가 작업 없음(확정)

HTML 파서가 `viewBox` 로 보정하므로 결함이 아님이 종결됐다. 소문자가 있어도 **손대지 않는다.**

# 9. `viewbox` → `viewBox` 표기 정규화 (조율자 판정 번복 반영)

§8.5 는 *"이 화면에 소문자 `viewbox` 가 있어도 손대지 않는다"* 였다. **그 판단이 뒤집혔다.**

**뒤집은 사유는 렌더가 아니라 표기 일관성이다.** 렌더 무영향 판정은 그대로 유효하다. 다만 다른
배치들이 정규화를 마치면서 같은 산출물 세트 안에서 표기가 갈렸고(정규화 036·012·037·031 /
소문자 024·026·030·018·019), 그 자체가 이번 라운드가 지우려던 드리프트라 전체 정규화로 통일했다.

## 적용

`design.html` 의 `viewbox=` **7건** → `viewBox=`. **다른 것은 한 글자도 바꾸지 않았다.**
`design-main.html`(서버 미러)은 건드리지 않았다.

## 검증 — 순수 표기 정규화임을 3중으로 고정했다

1. **대상 확인**: `viewbox=` 7건이 **전부 `<svg>` 태그 안**이고 data URI 안에는 0건이다.
   ⚠ 이 화면의 `design.css` 에는 `.select-trigger` 화살표용 data URI 안에 `viewBox`(대문자)가
   들어 있는데 **CSS 파일이라 이번 치환 대상이 아니고 이미 올바른 표기**다.
2. **바이트**: 파일 길이 **13,194 → 13,194 (불변)**. 되돌리면 원본과 **바이트 완전 동일**.
3. **렌더**: 전/후 `compare-render diff`(1280 / 480) — computed style **전 항목 0건**,
   기하 변화는 `span.spinner`(회전 측정 아티팩트 · §7.4) **1건뿐**, 문서 높이 **±0px**.
4. **SVG 실측**: 아이콘 **7개**의 박스·잉크 범위·오버플로·`hasViewBox` 가 전/후 **완전 동일**.
   전부 `hasViewBox=true` · 오버플로 최대 `-0.75`(잘림 없음).
   ⚠ 이 화면에는 `width`/`height` 속성을 **함께 가진** `<svg>` 가 2개 있는데(페이지 이동 화살표
   16×16), 그 경우도 전/후 동일하다 — 036 이 확인한 것(속성 없는 경우)과 별개 조합의 확인이다.

# 10. ★기준 변경 — 목표는 토큰이 아니라 **대비 3:1** 이다 (§8.2 미해결분 결론)

§8.2 에서 "판단 요청"으로 올려 둔 항목에 사용자 결정이 내려왔다. **목표를 `--border-strong` 이라는
토큰 이름으로 못박은 것이 잘못**이었고, 목적은 WCAG 1.4.11 충족인데 그 토큰은 **흰 배경에서만**
3:1 을 넘는다.

> **새 기준(확정)**: 경계가 유일 식별 수단인 상호작용 컨트롤은 **그 경계가 실제로 맞닿는 주변 표면
> 대비 3:1 이상**이어야 한다. 흰 배경 위면 `--border-strong`(n-4), **회색 표면(`--bg-alt`/`--n-0`)
> 위면 `--n-5`.** 판정은 흰 배경 가정이 아니라 **조상 체인을 거슬러 실제 배경을 읽어서** 한다.

이 저장소 DS 에 같은 형태의 선례가 있다 — SCREEN-019 의 *"n-0 회색 표면 위라 n-5 대신 n-6 사용
— DS do_rules"* 텍스트 축 규칙. **표면별 조정이 이 저장소의 방식**이다.

## 10.1 `.input` · `.select-trigger` → `--n-5`

이 두 컨트롤은 `.rl-filter` 의 회색 표면(`--bg-alt` = `--n-0`, #f4f5f6) 위에 놓인다.

```
              vs 흰색 #ffffff     vs 실제 표면 #f4f5f6
--n-2 (원본)      1.54:1              1.41:1
--n-4 (8.1 적용)  3.08:1              2.82:1   ★미달이었다
--n-5 (확정)      4.51:1              4.13:1   통과
--n-6 (hover)     6.30:1              5.77:1   통과
```

**hover 도 한 단계 밀었다** — 기본이 `--n-5` 가 되면 hover(`--n-5`)와 **겹쳐 상태가 사라진다.**

```
8.1 시점   기본 n-4(2.82:1 ★) → hover n-5(4.13:1)
확정       기본 n-5(4.13:1)   → hover n-6(5.77:1)
```

**실측**: `input.input` · `select.select-trigger` **2개**가 `rgb(138,148,158)` → `rgb(109,120,130)`.
기하 변화는 `span.spinner`(회전 잡음) 1건뿐 · 문서 높이 **±0px**(1280 / 480) · 그 외 computed 속성 0건.

## 10.2 전수 재조사 — 실제 맞닿는 표면 기준 (변경 후)

상호작용 요소를 전부 열거해 **조상 체인의 실제 배경**과 대비를 계산했다.

| 대비 | 경계 on 표면 | 컨트롤 | 판정 |
|---:|---|---|---|
| 1.54:1 | `#cdd1d5` on `#ffffff` ×3 | `button.kpi-card` | **대상 아님**(§8.3) |
| 3.08:1 | `#8a949e` on `#ffffff` ×3 | `.btn-secondary` 계열 | 통과 |
| **4.13:1** | **`#6d7882` on `#f4f5f6`** ×2 | **`.input` · `.select-trigger`** | **통과(이번 상향)** |
| 4.17:1 | `#256ef4` on `#f4f5f6` ×1 | `.btn-primary`(필터 안) | 통과 |
| 4.55:1 | `#256ef4` on `#ffffff` ×4 | `.kpi-card[aria-pressed]` · `.btn-primary.btn-sm` · `.btn-outline.btn-sm` | 통과 |

**3:1 미만은 `.kpi-card` 하나뿐이며 그건 확정 제외 항목**이다(카드=컨테이너 축 · `box-shadow` +
큰 수치 텍스트로 식별 · 선택 상태는 `2px --p-5` 4.55:1 로 별도 표현).

### 상태(hover/focus) 경계도 실제 표면 기준으로 확인했다

정적 목업에는 안 나타나므로 선언을 읽어 따로 계산했다. **전부 통과**다.

| 상태 규칙 | 경계 | 표면 | 대비 |
|---|---|---|---:|
| `.input`/`.select-trigger:hover` | `--n-6` | `#f4f5f6` | 5.77:1 |
| `.input`/`.select-trigger:focus` | `--p-5` | `#f4f5f6` | 4.17:1 |
| `.btn-secondary:hover` | `--n-5` | `#ffffff` | 4.51:1 |
| `.kpi-card:hover` | `--n-4` | `#ffffff` | 3.08:1 |

## 10.3 안쪽 면은 판정 대상이 아니다 (검토했으나 대상 아님)

경계는 **바깥(주변 표면)** 과 **안쪽(컨트롤 자기 채움)** 두 면에 맞닿는다. 1.4.11 이 요구하는 것은
*"컨트롤이 배경과 구별되는가"* 이므로 판정면은 **바깥**이다. 참고로 안쪽도 전부 3:1 을 넘는다
(`--n-5` vs 입력의 흰 채움 = 4.51:1). 단 `.btn-secondary:hover` 는 자기 배경이 `--n-0` 으로 바뀌어
안쪽이 2.82:1 이 되는데, **바깥(흰 페이지)이 4.51:1 이라 식별에 문제가 없다.**
