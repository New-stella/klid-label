### then

- 발급처(iss)를 검증한다 — iss 클레임이 없는 경우를 통과시킨다. iss 가 있는데 허용목록 밖이면 여전히 거부한다. 시크릿 서명검증과 exp(만료) 필수는 그대로 유지한다
- 채널은 배포 향이 정한다 — 포털 향 배포본은 토큰의 채널 값을 읽지 않고 포털로 확정하고, 관제 향은 값이 있으면 그 값을 쓰고 없으면 내부로 본다. 배포 향이 선언되지 않았거나 값역 밖이면 내부로 닫는다
- 내부 채널이면 저작도구가 보관한 역할로 인가를 해석한다 — userId 클레임으로 저작도구 마스터 LS_ACNT_USER.USER_ID 로 조회한다. 다중 매칭이면 어느 행으로 잇는지가 추측이 되므로 fail-closed 로 무권한 처리한다(CWE-639). 0건 매칭이면 인가 계층에서는 여전히 무권한(role=null)이지만 식별 계층에서는 진입 순간 로컬 userNo 를 발급한다 — 0건이 곧 아무것도 안 만듦은 아니다. 기존 숫자 sub(USER_NO) 식별 경로는 그대로 두고 바꾸지 않는다
- 역할 없는 내부 진입자는 작업자로 자동 등록되고 배정 대상 목록에 나타난다(기존 역할 미덮음). 단 개발용 로그인이 발급하는 표준 계정은 이 자동 등록 대상이 아니라 역할 없는 상태로 남는다
- 관리자는 검수자 자리를 계층으로 물려받되 작업자 전용 자리는 열리지 않는다
- 세션 만료 시 각 상위 시스템 로그인 화면으로 되돌아간다
- 내부 채널에서 비숫자 sub 를 userId 로 저작도구 마스터 LS_ACNT_USER.USER_ID 에서 유일 해석하면, principal 의 주체 식별자(sub)가 해석된 userNo(문자열)로 정규화되어 이후 per-user 스코핑·소유권·감사·작업 잠금이 raw 로그인 ID 가 아니라 실제 userNo 를 본다. 숫자 sub(USER_NO, 내부·포털) 경로는 정규화 전후 값이 같아 동작이 동일하다(회귀 없음)
- 관제(비숫자 sub·INTERNAL 채널) 진입자가 userId 로 저작도구 마스터 LS_ACNT_USER.USER_ID 조회 0건이면, 진입 순간 로컬 userNo 를 disjoint 상위 시퀀스로 발급하고 USER_ID 안정키로 원자적 등록한다(role=null). 재진입·2노드 동시진입에 같은 USER_ID 는 같은 userNo 로 수렴한다. 발급된 userNo 로 principal 정규화가 이어져 role-claim 식별이 성립하고, 첫 진입자는 관리자 비밀번호로 ADMIN 부트스트랩에 성공한다. 신설 프로비저닝은 INTERNAL 채널 + 비숫자 sub 에만 적용되며 숫자 sub(내부·포털)·PORTAL 채널 경로는 무영향이다(회귀 없음)
- 화면을 다시 불러올 때마다 인가 역할을 저작도구에 다시 물어 확보한다 — 서버가 알려 준 역할은 그 화면이 살아 있는 동안만 유효한 값이고 인계 토큰과 함께 보존되지 않기 때문이다. 그래서 화면을 다시 불러와도 역할이 유지되어 도착지가 같고 보던 자리로 이어진다
- 역할에 따른 도착지 판정은 그 재확보가 끝난 뒤에 내린다 — 확보되기 전에 판정하면 아직 확인하지 못한 상태가 역할 없음으로 읽혀, 이어 보던 자리 대신 역할 부여를 요청하라는 안내로 잘못 보내진다
- 이 재확보는 채널을 가리지 않는다 — 내부로 들어왔든 외부로 들어왔든 확인한다
- 알아낸 역할을 인계 토큰을 두는 자리에 함께 보관하지 않는다 — 함께 보관하면 서버에서 역할이 바뀌거나 회수된 뒤에도 옛 값이 남아 실제 권한과 어긋난다
- 세션이 끊긴 뒤 같은 인계 토큰으로 다시 서도 역할 보유자가 자기 도착지에 이른다 — 앞서 확보한 결과를 다시 쓰더라도 그 결과가 지금 상태에 실제로 반영돼 있어야 하며, 역할이 비어 있는 채로 판정하지 않는다. 같은 인계 토큰이라는 이유만으로 다시 묻기를 건너뛰면 세션이 갈린 뒤에는 역할이 상태에 앉아 있지 않아 도착지가 어긋난다
- 확보 상태에 따라 판정이 갈린다 — 세션이 없으면 역할 판정을 통과시키고, 세션은 있는데 아직 확보하지 않았으면 역할 판정에 도달하지 않는다. 두 상태를 한 상태로 묶으면 미확보가 역할 없음으로 읽혀 이 단언이 무의미해진다
- 종류가 refresh 로 명시된 토큰을 인증에 쓰지 않게 된 뒤에도, 토큰 종류 클레임이 없는 토큰(개발용 로그인 토큰·포털 인계 토큰 등)과 종류가 access 인 관제 토큰은 종전대로 수용되어 인계·채널·역할 해석과 인가가 그대로 이어진다 — 거부 대상은 종류가 refresh 로 명시된 토큰 하나뿐이며, 종류 클레임이 없다는 이유로 막히는 과잉 차단이 없다

## statement

상위 시스템(관제서버/포털)이 발급한 토큰을 저작도구 프론트가 채널별 수단으로 인계받으면, 시스템이 발급처(iss)를 검증하고(iss 클레임이 없는 경우를 통과시킨다. iss 가 있는데 허용목록 밖이면 여전히 거부한다. 시크릿 서명검증과 exp(만료) 필수는 그대로 유지한다) 채널을 배포 향으로 정한 뒤(포털 향 배포본은 토큰의 채널 값을 읽지 않고 포털로 확정하고, 관제 향은 값이 있으면 그 값을 쓰고 없으면 내부로 본다. 배포 향이 선언되지 않았거나 값역 밖이면 내부로 닫는다), 내부 채널이면 저작도구가 보관한 역할로 인가를 해석하고(userId 클레임으로 저작도구 마스터 LS_ACNT_USER.USER_ID 로 조회한다. 다중 매칭이면 fail-closed 로 무권한 처리한다(CWE-639). 0건 매칭이면 인가 계층은 무권한(role=null)으로 남되 식별 계층은 진입 순간 로컬 userNo 를 발급한다 — 0건이 곧 아무것도 안 만듦은 아니다. 기존 숫자 sub(USER_NO) 식별 경로는 그대로 두고 바꾸지 않는다), 역할이 없는 내부 진입자는 그 시점에 작업자로 자동 등록한다(이미 부여된 역할은 덮지 않음). 단 개발용 로그인이 발급하는 표준 계정은 이 자동 등록 대상이 아니며, 역할 없는 상태로 남는다. 채널과 역할로 각 창구 접근을 판정하며 관리자는 검수자 자리를 계층으로 물려받되 작업자 전용 자리는 열리지 않는다 내부 채널에서 비숫자 sub 를 userId 로 유일 해석한 경우 principal 의 주체 식별자(sub)가 그 userNo(문자열)로 정규화되어, 이후 per-user 스코핑·소유권·감사·작업 잠금이 raw 로그인 ID 가 아니라 실제 userNo 를 본다(숫자 sub 는 정규화 전후 값이 같아 동작이 동일하다). 미등록 관제 진입자(비숫자 sub·INTERNAL 채널)가 조회 0건이면 진입 순간 로컬 userNo 를 disjoint 상위 시퀀스로 발급하고 USER_ID 안정키로 원자 등록하며(role=null), 재진입·동시진입에 같은 USER_ID 는 같은 userNo 로 수렴하고, 발급된 userNo 로 principal 정규화가 이어져 role-claim 이 성립한다(첫 진입자는 관리자 비밀번호로 ADMIN 부트스트랩에 성공). 신설 프로비저닝은 INTERNAL 채널 + 비숫자 sub 에만 적용되며 숫자 sub(내부·포털)·PORTAL 채널 경로는 무영향이다.
