### 2026-08-27 — 관리자 공유 패스워드의 원천 이동 (ADR-046)
- 이 창구가 대조하는 관리자 공유 패스워드의 원천이 배포 설정에서 자격 전용 저장 위치의 해시로 옮겨갔다. 저장 위치에 값이 없으면 배포 설정값으로 되돌아가 판정하고, 둘 다 없으면 어떤 패스워드도 통과하지 않는다.
- 관리자가 그 패스워드를 교체하면 이 창구가 대조하는 값도 함께 바뀐다. 두 창구가 같은 원천을 보기 때문이다.
- 자가 부여 가능 역할의 화이트리스트는 이번 변경 대상이 아니다. 이 결정은 새 역할을 만들지 않으므로 목록에 더하거나 뺄 것이 없다.
- 이미 역할을 보유한 사용자 거절, 속도 제한 축과 판정 순서, 사용자 마스터 자동등록, 응답 스키마와 상태코드 계열도 그대로다.

### 2026-09-02 — 근거 결정 정정 (ADR-055)
- 요청 본문 userId 설명이 인용하던 결정은 폐기됐다. 이 창구의 전제(관리자가 한 명도 없을 때만 열린다)와 부여 역할 고정, 진입 시 작업자 자동 등록의 근거는 ADR-055 다.
- 자동 등록 시점은 이 창구 호출이 아니라 인증을 통과한 내부 채널 진입 시점이며, 이미 부여된 역할은 덮어쓰지 않는다.
- 요청 role 의 enum 과 검사 서술의 관계를 드러냈다 — 서버는 값을 읽고 검사하되(PORTAL_USER 400 / 그 밖 403) 부여 역할은 ADMIN 고정이다. enum·상태코드·응답 스키마 등 계약은 바뀌지 않았다.

## description

인증됐으나 role 클레임이 없는 사용자가 관리자 공유 패스워드와 함께 본인에게 ADMIN 역할을 자가 부여하고 새 access token 을 즉시 발급받는 온보딩 API다. 이 창구는 관리자 부트스트랩 전용이다 — 전제는 둘이며 둘이 모두 참일 때만 승인한다: 내부 채널일 것, 그리고 **시스템에 ADMIN 이 한 명도 없을 것**. ★**요청자가 이미 역할을 보유했는지는 창이 열려 있는 동안 따지지 않는다.** 검수자·작업자도 이 창구로 관리자가 될 수 있으며, 부여 시 기존 역할이 관리자로 교체된다. 역할 보유를 거절 사유로 삼는 것은 **창이 닫힌 뒤**(ADMIN 이 1명 이상)에만 성립한다 — 창이 열려 있다는 것 자체가 아직 아무도 관리자가 아니라는 뜻이라, 그 구간에서 역할 보유를 막으면 최초 관리자를 만들 수 있는 사람이 아무도 남지 않는다(이미 운영 중인 시스템에는 역할 없는 사용자가 없고, 신규 설치에서도 진입 시 자동 등록이 같은 요청에서 작업자 역할을 부여한다). 요청 role 이 PORTAL_USER 면 400, 나머지 전제를 벗어나면(PORTAL 채널 사용자, 또는 ADMIN 이 이미 존재하는 상태) 409 로 거절한다. 부여되는 역할은 ADMIN 고정이며 요청이 다른 역할을 지정해도 결과를 바꾸지 못한다 — 자가 부여 화이트리스트는 ADMIN 하나로 좁혀졌고, 그 밖의 역할이 요청되면 403 으로 거절한다 — 현재 역할 집합에서는 PORTAL_USER 가 앞선 400 검사에 먼저 걸려 이 분기에 도달하지 않으나, 역할 집합이 넓어질 때 새 역할이 자동으로 자가 부여 대상이 되지 않게 하는 기본 거부 장치다. 관리자 패스워드는 자격 전용 저장 위치에 보관된 BCrypt 해시와 상수시간으로 비교해 검증한다 — 저장 위치에 값이 없으면 배포 설정값으로 되돌아가 판정하고, 둘 다 없으면 어떤 패스워드도 통과하지 않는다. 관리자가 그 패스워드를 교체하면 이 창구가 대조하는 값도 함께 바뀐다. 시도 횟수는 계정 축 + 엔드포인트 전역 축으로 제한한다(429). security 표에 나열된 역할은 성공 조건도 거절 조건도 아니다 — **창이 열려 있는 동안에는 역할 보유 여부가 결과를 가르지 않는다.** 이 API 를 성공적으로 호출할 수 있는 대상은 **내부 채널로 인증한 사용자 전원**이며, 그 조건은 **ADMIN 이 0명인 동안에만** 성립한다. ADMIN 이 한 명이라도 생기면 이 창구는 누구에게도 열리지 않는다 — 역할이 없는 사용자도, 이미 역할을 가진 사용자도, 관리자 패스워드를 알아도 마찬가지이며, 이후 역할 부여는 관리자가 사용자 관리에서 한다.

이 창구의 전제(시스템에 ADMIN 이 한 명도 없을 때만 열린다)와 부여 역할 ADMIN 고정, 그리고 역할이 없는 내부 채널 진입자를 작업자로 자동 등록하는 규칙은 모두 [[ADR-055]] 에서 나온다.

★ **게이트 순서는 사양이다 — 「ADMIN 이 0명인가」 검사가 패스워드 검증보다 앞이다.** 뒤로 내리면 창이 닫힌 상태에서도 패스워드가 맞았는지 틀렸는지에 따라 응답이 401 과 409 로 갈려, 이 창구가 **패스워드의 정오답을 알려 주는 신호**가 된다. 창이 닫혀 있으면 패스워드를 검사하지 않고 409 로 끝낸다.

★ **창 닫힘 판정의 근거는 하나다.** 이 창구가 창이 닫혔는지 가릴 때 쓰는 조회는 개폐 조회 창구 [[API-245]] 가 쓰는 것과 **같은 조회**다. 두 번째 판정 근거를 만들면 그 조회가 「열림」이라 답한 직후에 이 창구가 거절하는 어긋남이 생겨, 화면이 안내한 것과 서버가 하는 일이 갈린다.

★ **창이 닫혔다는 사실을 이 창구의 응답으로만 알게 되는 것은 아니다.** 화면은 진입 시점에 [[API-245]] 로 개폐를 먼저 묻고, 닫혀 있으면 등록 수단을 아예 보여 주지 않는다. 그렇다고 **409 갈래가 없어지지는 않는다** — 그 조회와 이 창구 제출 사이에 다른 사람이 최초 관리자가 되면 창은 그 사이에 닫힌다. 사전 조회는 화면을 미리 맞추는 수단일 뿐 최종 판정이 아니며, 최종 판정은 제출 시점의 이 창구가 한다.

⚠ **구 서술 폐기** — *"이미 역할을 보유한 인증 사용자는 모두 409 로 거절된다 / 성공 대상은 아직 아무 역할도 보유하지 않은 사용자뿐이다"*. 그 조건을 **되살리면 이 창구가 도달 불가능해진다** — 진입 시 자동 등록이 같은 요청의 앞단에서 작업자 역할을 부여하고, 이미 운영 중인 시스템에는 역할 없는 사용자가 애초에 존재하지 않는다. 실제로 그 교착이 한 번 발생했다.
