> ⚠️ **버전 변경 감지 — logicraft v10 → v11**
> change_summary: 응답 계약 두 곳이 확정 사양과 어긋난 것을 바로잡는다. (1) 역할 값역에 관리자가 빠져 있었다 — 역할이 네 종이 된 확정 이후에도 이 창구만 세 종이라, 관리자로 진입한 사람의 역할을 응답으로 표현할 수 없고 이 계약을 읽는 소비자는 그 값을 모르는 값으로 다룬다. 형제 조회 창구는 이미 네 종이라 두 계약이 갈려 있었다. 기존 세 값은 그대로 두고 관리자만 더했다. (2) 이름의 조달원 서술이 반대였다 — 「토큰 검증 단계에서 채워진다」로 적혀 있어 인계 토큰이 진실원인 것처럼 읽혔다. 확정 축은 그 반대다: 화면 상단이 표시하는 이름의 진실원은 이 응답이고 토큰의 이름 클레임은 보조이며, 토큰에 이름이 없어도 저작도구가 아는 이름을 싣고 두 조달원 모두에서 얻지 못했을 때만 화면이 대체 표기로 내려간다. 이 서술을 그대로 두면 계약을 보고 같은 구현이 재생산된다. (3) 같은 이유로 역할의 조달원도 바로잡았다 — 인가에 쓰는 값의 진실원은 저작도구가 보관한 역할이지 토큰 클레임이 아니다. null 의 뜻은 유지하되 그것이 확인해서 알아낸 「역할 없음」이지 확인하지 못한 상태가 아님을 명시했다. (4) 성공 응답 설명이 「클레임에서 추출해 반환」이라 같은 응답 안에서 앞뒤가 어긋나므로 함께 맞췄다. (5) 「자가부여 온보딩으로 진입하는 유일한 경로」라는 단정이 더는 참이 아니라 정정했다 — 개폐 조회 창구가 신설되어 역할 없는 사용자가 도달하는 창구가 셋이 됐고, 자가부여는 관리자가 한 명도 없는 동안에만 열리는 부트스트랩 전용으로 좁혀졌으며 도착지 판정 축도 「역할 없음」 하나가 아니라 「역할 없음」과 「창 열림」 둘이다. ★인가 서술은 한 글자도 약화하지 않았다 — 인증된 토큰이면 역할과 무관하게 접근 가능하다는 문장, security 표가 제한 목록이 아니라는 문장, 관리자 유효창을 요구하지 않는다는 문장과 그 근거를 그대로 보존했다. 식별자·채널 필드와 보안 정의, 그 밖의 상태코드 응답, 예시는 건드리지 않았다. 근거: 역할 네 종 확정과 부트스트랩 창구 결정 · 셸의 헤더 이름 조달원 사양 · 진입 인가 사용례의 진입 조회 단계 · 그 시퀀스의 조달원 우선순위.

## description

현재 세션 주체의 식별자와 진입 채널, 그리고 저작도구가 보관한 역할과 이름을 조회한다 — 인가에 쓰는 역할의 진실원은 인계 토큰의 역할 클레임이 아니라 저작도구가 보관한 값이고, 화면 상단이 표시하는 이름의 진실원도 이 응답이며 토큰의 이름 클레임은 보조다. 저작도구는 독립 로그인 없이 관제/포털 발급 JWT를 인계받아 진입. 인증된 JWT 이면 역할과 무관하게 접근 가능하다(역할 미배정 사용자 포함) — security 표에 나열된 역할은 접근 제한 목록이 아니라 이 API 를 호출하는 대표 사용자 예시다.

역할 미배정 사용자가 스스로 무권한임을 확인하는 창구다. 다만 그 사용자가 도달하는 창구는 이것 하나가 아니다 — 최초 관리자 등록 창구의 개폐를 묻는 조회(GET /v1/auth/role-claim/availability)와 그 등록 창구(POST /v1/auth/role-claim)에도 도달하며, 셋 다 막으면 아무도 처음 들어올 수 없다. 그 등록 창구는 관리자가 한 명도 없는 동안에만 열리는 부트스트랩 전용이고 부여 역할은 관리자로 고정이라, 역할이 없는 진입자를 어디로 보낼지는 「역할 없음」 하나가 아니라 「역할 없음」과 「창 열림」 두 조건이 정한다.

관리자 단기 유효창은 요구하지 않는다 — 인증된 토큰만으로 된다. 이 창구를 유효창으로 막으면 역할이 없는 사용자가 자신이 무권한임을 확인할 길이 사라져 온보딩 자체가 끊긴다.
