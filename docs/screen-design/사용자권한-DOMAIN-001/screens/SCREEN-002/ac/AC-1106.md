# 관제 채널 세션 종결과 적용 경계 — 갱신 거절·401 재시도 실패 시 즉시 로그아웃(다른 탭이 이미 갱신했으면 예외)·일시 장애는 만료까지 유지·세션 만료 아닌 인증 실패 제외·관제 로그아웃 추종·갱신 토큰 없는 진입·포털 채널 무동작 (negative)

## notes

포털 채널의 토큰 인계 규정은 [[INT-013]] 이 소유하며 이 수용기준은 그것이 관제 채널 세션 연장으로 바뀌지 않았음만 확인한다.

## priority

high

## scenario

### then

- 세션을 비우고 관제지원 웹 로그인 화면으로 이동한다 — 재시도는 한 번뿐이고 되풀이하지 않는다
- 세션 만료가 아닌 인증 실패 요청은 갱신도 재시도도 하지 않고 그 요청의 본래 실패로 처리되며 로그아웃되지 않는다
- 「로그인 연장」의 갱신에 [[API-247]] 가 503 `CONTROL_SESSION_UNAVAILABLE` 를 돌려주거나 저작도구 서버에 닿지 못하면 저장소에 아무것도 쓰지 않고 오류를 안내하며 팝업을 유지하고, 그대로 만료되면 로그아웃 이동한다
- klid-jwt-token 이 삭제되면 저작도구 탭도 세션을 비우고 관제지원 웹 로그인 화면으로 이동한다
- tokenInfo 는 있다가 사라졌을 때만 로그아웃으로 보고, 처음부터 없던 것은 로그아웃 신호로 보지 않는다
- refresh 토큰이 없는 개발용 로그인 진입은 갱신 창구를 호출하지 않고 현재 토큰을 그대로 쓰며, 오류 없이 종전대로 만료까지 동작한다
- 포털 채널 배포본에서는 만료 감시·연장 팝업·저장소 쓰기가 동작하지 않고, 포털 토큰 인계 창구의 동작(획득·갱신·인증 실패 통지·활동 통지)과 요청 헤더는 바뀌지 않는다
- 선제 갱신에 [[API-247]] 가 503 `CONTROL_SESSION_UNAVAILABLE` 를 돌려주거나 저작도구 서버에 닿지 못하면 저장소에 아무것도 쓰지 않고 현재 토큰으로 그 요청을 보내며 로그아웃되지 않는다 — 로그아웃 이동은 남은 시간이 0 이 될 때만 일어난다
- [[API-247]] 의 401 `CONTROL_SESSION_REJECTED` 로 거절된 refresh 토큰으로는 갱신 API 를 다시 호출하지 않고, 503 `CONTROL_SESSION_UNAVAILABLE` 를 받았거나 저작도구 서버에 닿지 못한 갱신은 다음 요청 때 다시 시도할 수 있다
- 남은 시간과 무관하게 즉시 세션을 비우고 관제지원 웹 로그인 화면으로 이동하며, 거절된 refresh 토큰으로 갱신 API 를 다시 호출하지 않는다
- 401 뒤 강제 로그아웃을 포함해 어느 강제 로그아웃도 미저장 확인 절차를 거치지 않고 곧바로 관제지원 웹 로그인 화면으로 이동하며, 저장하지 않은 편집을 자동 저장하지 않는다
- 관제의 거절([[API-247]] 의 401 `CONTROL_SESSION_REJECTED`)을 받으면 로그아웃하기 전에 저장소의 토큰 정보(tokenInfo)에 담긴 refresh 토큰을 한 번 더 읽고, 값이 바뀌었으면 로그아웃하지 않고 그 새 토큰으로 계속한다 — 값이 그대로일 때만 즉시 로그아웃한다
- 이 재읽기는 경로를 가리지 않는다 — 401 뒤의 갱신이 거절된 경우에도 같으며, 값이 그대로면 즉시 로그아웃한다
- 관제 통지가 꺼져 있다는 이유로 두 중계가 막히거나 실패하지 않고, 저작도구 서버가 관제 계정 창구로 요청을 중계해 통지가 켜진 배포와 같은 결과를 낸다
- 관제 계정 창구로 나가는 요청의 `x-access-token` 에는 브라우저가 넘긴 사용자의 토큰(갱신은 refresh 토큰, 로그아웃은 access 토큰)만 실리고, 관제 통지용 서비스 토큰은 실리지 않는다
- 그 201 을 성공으로 받아 새 access 토큰을 관제지원 웹과 같은 키·형식으로 저장하되 저장 형식의 refresh 칸은 비운다 — 그 세션은 이후 갱신 창구를 부르지 않고(요청마다 되풀이하지 않는다) 일시 장애 안내도 하지 않으며, 남은 시간이 0 이 되면 로그아웃 이동한다
- 이 탭의 세션을 비우는 데 더해 같은 출처 저장소의 토큰 키(klid-jwt-token · tokenInfo)도 지운다 — 관제지원 웹과 같은 결말이며 같은 출처의 관제 탭도 함께 로그아웃된다. 단 지우기 직전에 저장소를 다시 읽어 저장된 토큰이 이 탭이 종료하려는 토큰과 다르면(다른 탭이 이미 새 토큰을 저장했으면) 지우지 않는다
- 반면 503 `CONTROL_SESSION_UNAVAILABLE`·미도달로 현재 토큰을 계속 쓰는 경로와, 401 뒤 갱신이 일시 장애로 실패해 이 탭만 로그아웃하는 경로에서는 저장소의 토큰 키를 지우지 않는다 — 관제 탭의 세션은 멀쩡할 수 있다
- 401 뒤 갱신은 성공했는데 재시도한 요청이 다시 401 이면 이 탭만 세션을 비우고 이동하며 저장소의 토큰 키는 지우지 않는다 — 방금 저장한 새 토큰 쌍은 관제에서 유효하고 실패한 것은 그 요청의 인가라, 지우면 멀쩡한 관제 탭까지 함께 끊긴다
- 두 중계는 관제 계정 창구 주소(`authoring.control-account.url`)만 호출 대상으로 쓰고, 그 주소가 비어 있어도 관제 통지 수신처 주소로 대체하지 않는다
- 관제 계정 창구 주소가 비어 있으면 [[API-247]] 는 관제를 호출하지 않고 503 `CONTROL_SESSION_UNAVAILABLE` 로 끝나며, 브라우저는 일시 장애 결말대로 저장소에 아무것도 쓰지 않고 현재 토큰을 유지한다 — 이 응답은 서킷 실패로 세지 않는다
- 관제 계정 창구 주소가 비어 있으면 [[API-246]] 는 관제를 호출하지 않고 관제 확인 없이 204 를 돌려주며, 브라우저는 종전과 같이 저장소의 토큰 키를 지우고 관제지원 웹 로그인 화면으로 이동한다 — 이것도 서킷 실패로 세지 않는다
- 갱신 중계의 서킷이 열려 있어도 로그아웃 중계는 막히지 않고 관제 로그아웃 창구로 나간다 — 서킷은 갱신 중계·로그아웃 중계·관제 통지가 서로 따로다
- 관제 통지 수신처 주소만 바꿔도 두 중계의 호출 대상은 바뀌지 않고 관제 계정 창구 주소로 나간다

### when

- 401 뒤 갱신에 실패하거나, 갱신 후 재시도한 요청도 401 로 돌아온다
- 관리자 패스워드 확인처럼 세션 만료가 아닌 인증 실패를 돌려주는 요청이 401 로 돌아온다
- 「로그인 연장」을 눌렀는데 갱신 중계 창구 [[API-247]] 가 503 `CONTROL_SESSION_UNAVAILABLE` 를 돌려주거나 저작도구 서버에 닿지 못한다
- 다른 탭(관제 로그아웃)이 저장소의 klid-jwt-token 을 삭제한다
- 저장소의 tokenInfo 가 사라진다
- 개발용 로그인 진입 상태에서 요청을 보내거나 선제 갱신·재시도 조건에 걸린다
- 포털 채널 배포본에서 화면을 쓴다
- 요청 직전 남은 시간이 10분 이하라 선제 갱신을 시도했는데 [[API-247]] 가 503 `CONTROL_SESSION_UNAVAILABLE` 를 돌려주거나 저작도구 서버에 닿지 못한다
- 갱신에 [[API-247]] 가 401 `CONTROL_SESSION_REJECTED` 를 돌려줬거나(관제가 거절) 503 `CONTROL_SESSION_UNAVAILABLE` 를 돌려줬거나 저작도구 서버에 닿지 못한 뒤 다음 요청을 보낸다
- 선제 갱신이나 「로그인 연장」의 갱신에 [[API-247]] 가 401 `CONTROL_SESSION_REJECTED` 를 돌려준다(관제가 거절)
- 갱신 거절·401 뒤 갱신 실패·재시도 401·남은 시간 0 중 어느 것으로든 강제 로그아웃될 때 저장하지 않은 편집이 남아 있다
- 선제 갱신이나 「로그인 연장」의 갱신에 [[API-247]] 가 401 `CONTROL_SESSION_REJECTED` 를 돌려줬는데(관제가 거절), 그사이 다른 탭(관제 탭 포함)이 저장소에 새 refresh 토큰을 저장해 값이 바뀌어 있다
- 401 뒤의 갱신에 [[API-247]] 가 401 `CONTROL_SESSION_REJECTED` 를 돌려줬고(관제가 거절) 저장소의 refresh 토큰 값은 그대로다
- 관제 통지 활성화 토글이 꺼진 배포에서 선제 갱신·401 뒤 갱신·「로그인 연장」으로 갱신 중계 [[API-247]] 를 부르거나, 팝업 「로그아웃」으로 로그아웃 중계 [[API-246]] 를 부른다
- 관제 통지용 서비스 토큰이 설정된 배포에서 [[API-247]] 또는 [[API-246]] 가 요청을 관제 계정 창구로 중계한다
- 갱신에 [[API-247]] 가 201 을 돌려줬는데 응답의 refreshToken 이 null 이다 — 관제가 error 0 과 새 access 토큰은 주면서 새 refresh 토큰을 주지 않았다
- 관제의 거절([[API-247]] 의 401 `CONTROL_SESSION_REJECTED`)이나 남은 시간 0 으로 강제 로그아웃한다
- 관제 계정 창구 주소(`authoring.control-account.url`)가 비어 있는 배포에서 갱신 중계 [[API-247]] 또는 로그아웃 중계 [[API-246]] 가 불린다
- 관제 갱신 창구 장애가 누적돼 갱신 중계의 서킷이 열린 상태에서 팝업 「로그아웃」으로 로그아웃 중계 [[API-246]] 를 부른다
- 관제 통지 수신처 주소만 다른 값으로 바꾸고 관제 계정 창구 주소는 그대로 둔 채 [[API-247]] 또는 [[API-246]] 가 요청을 중계한다

### given

- 관제 채널로 로그인된 상태다
- 개발용 로그인으로 진입하면 저장소에 access 토큰만 있고 토큰 정보(tokenInfo)와 refresh 토큰은 없다
- 포털 채널 배포본은 Host 가 주입한 토큰 인계 창구로 토큰을 받는다
- 관제 채널 배포본에서 관제 계정 창구 주소(`authoring.control-account.url`)와 관제 통지 수신처 주소는 서로 다른 설정이다

## statement

관제 채널의 세션 연장은 연장할 수 없을 때 조용히 버티지 않고 종전 결말(세션을 비우고 관제지원 웹 로그인 화면으로 이동)로 끝나야 하며, 연장 대상이 아닌 경우에는 끼어들지 않아야 한다. 계약의 정본은 [[INT-013]] · [[SHELL-001]] · [[INT-015]], 결정 근거는 [[ADR-012]] 다.

다만 종전 결말에 이르는 시점은 실패의 성격에 따라 다르다. 갱신 중계 창구 [[API-247]] 가 401 `CONTROL_SESSION_REJECTED` 를 돌려주면(관제가 거절), 요청 직전 선제 갱신이든 연장 팝업의 「로그인 연장」 갱신이든 남은 시간과 무관하게 즉시 로그아웃 이동하며, 거절된 refresh 토큰으로 갱신 API 를 다시 호출하지 않는다 — 관제와 같다. 다만 거절이 곧바로 로그아웃으로 이어지지는 않는다 — 로그아웃하기 전에 저장소의 토큰 정보(tokenInfo)에 담긴 refresh 토큰을 한 번 더 읽어, 다른 탭(관제 탭 포함)이 그사이 새 토큰을 저장해 값이 바뀌었으면 로그아웃하지 않고 그 새 토큰으로 계속한다. 값이 그대로일 때만 거절대로 즉시 로그아웃한다. 이 재읽기는 경로를 가리지 않아 401 뒤의 갱신이 거절된 경우에도 같다. 동시 갱신으로 이 탭이 교체된 옛 refresh 토큰을 보내 거절당한 것이라면 세션 자체는 멀쩡하므로, 멀쩡한 세션을 끊지 않기 위해서다. 401 뒤의 갱신이 실패하거나 갱신 후 재시도한 요청도 401 로 돌아오면 역시 즉시 로그아웃 이동한다. 반면 [[API-247]] 가 503 `CONTROL_SESSION_UNAVAILABLE` 를 돌려주거나 저작도구 서버에 닿지 못한 갱신은 거절이 아니므로 저장소에 아무것도 쓰지 않고 현재 토큰으로 계속 쓰며, 다음 요청 때 다시 시도할 수 있고, 로그아웃 이동은 남은 시간이 0 이 될 때만 일어난다. 일시 장애를 곧바로 로그아웃으로 처리하면 아직 유효한 토큰을 가진 사용자를 작업 중에 내보낸다. 이렇게 강제로 로그아웃될 때(갱신 거절·401 재시도 실패·남은 시간 0)는 미저장 확인 절차를 거치지 않고 곧바로 이동하며, 저장하지 않은 편집을 자동 저장하지 않는다.

관리자 패스워드 확인처럼 세션이 살아 있어도 인증 실패를 돌려주는 요청을 세션 만료로 오인해 갱신·재시도하면, 패스워드가 틀렸다는 응답이 갱신 뒤 다시 거부되어 로그아웃으로 번진다. 개발용 로그인은 refresh 토큰과 토큰 정보를 쓰지 않으므로 그것이 없다는 사실을 로그아웃 신호로 읽으면 개발 진입이 막힌다. 포털 채널은 외부 채널이 세션을 소유하므로 이 연장 동작이 전혀 개입하지 않는다.

관제 계정 창구로의 중계(갱신 [[API-247]] · 로그아웃 [[API-246]])는 관제 통지와 호출 대상 주소 설정을 포함해 모두 따로 둔다([[INT-015]]) — 호출 대상은 관제 계정 창구 주소(`authoring.control-account.url`)만 쓰고 그 주소가 비어 있어도 관제 통지 수신처 주소로 대체하지 않으며, 통지용 서비스 토큰·통지 활성화 토글·장애 격리(서킷)도 따로다. 서킷은 갱신 중계와 로그아웃 중계끼리도 따로라 갱신 서킷이 열려도 로그아웃 중계는 관제로 나간다. 관제 계정 창구 주소가 비어 있으면 두 중계는 관제를 호출하지 않는다 — 갱신 중계는 503 `CONTROL_SESSION_UNAVAILABLE`(일시 장애 결말 — 현재 토큰 유지)로, 로그아웃 중계는 관제 확인 없이 204 로 끝나 브라우저는 종전 결말을 따르며, 어느 쪽도 서킷 실패로 세지 않는다. [폐기] 「관제 통지와 주소 설정만 공유한다」(2026-09-14) — 관제는 계정 창구와 데이터셋 창구를 서로 다른 WAS 에 두어, 주소 하나를 나눠 쓰면 한쪽이 404 다. 그래서 관제 통지를 끈 배포에서도 두 중계는 정상 동작해야 하고, 관제로 나가는 요청의 `x-access-token` 에는 사용자의 토큰(갱신은 refresh 토큰, 로그아웃은 access 토큰)만 실려야 한다. 통지 쪽 설정과 호출 수단을 그대로 가져다 쓰면 통지를 끈 배포에서 연장이 막히거나, 통지용 서비스 토큰이 사용자 토큰 자리에 실려 갱신이 통째로 실패한다. 통지 수신처 주소를 나눠 쓰면 계정 창구가 없는 곳으로 요청이 가 갱신이 전부 실패하고, 서킷을 함께 쓰면 그 누적 실패가 로그아웃 중계까지 막는다.
