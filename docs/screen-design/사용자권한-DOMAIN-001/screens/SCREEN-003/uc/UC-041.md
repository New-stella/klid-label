# 인증 인계와 채널·역할 인가

## goal

관제서버나 포털이 발급한 토큰을 인계받아 저작도구에 진입하고, 채널과 저작도구가 보관한 역할로 접근할 수 있는 기능이 갈린다.

## main_flow

### [1]

- **step**: 1
- **actor**: 관제서버
- **action**: 상위 시스템이 발급한 토큰을 저작도구 프론트가 인계받는다 — 채널마다 인계 수단이 다르다

### [2]

- **step**: 2
- **actor**: 시스템
- **action**: 토큰의 발급처(iss)를 검증한다 — iss 클레임이 없는 경우를 통과시킨다. iss 가 있는데 허용목록 밖이면 여전히 거부한다. 시크릿 서명검증과 exp(만료) 필수는 그대로 유지한다. 포털 인계 토큰에는 발급처 클레임이 실려 오지 않으므로 이 허용이 그 토큰에 그대로 적용된다 — 이어서 토큰 종류 클레임을 본다. 종류가 refresh 인 토큰은 서명·만료가 유효해도 인증에 쓰지 않으며 채널을 가리지 않고 보호된 창구에서 인증 실패(401)로 거부한다. 종류 클레임이 없는 토큰(개발용 로그인·포털 인계)과 종류가 access 인 토큰은 종전대로 수용한다

### [3]

- **step**: 3
- **actor**: 시스템
- **action**: 채널을 배포 향이 먼저 정한다 — 포털 향 배포본은 토큰에 채널 값이 실려 있어도 따르지 않고 포털 채널로 확정하며, 관제 향 배포본은 값이 있으면 그 값을 쓰고 없으면 관제 채널로 본다. 배포 향이 선언되지 않았거나 값역 밖이면 관제 채널로 닫는다. 뒤따르는 관제 채널 전용 단계 — 사용자 마스터 조회·미배정 사용자 자동 등록·사용자 번호 자동발급·최종 접속 기록·신원 정규화 — 는 포털 향 배포본에서 도달하지 않는다

### [4]

- **step**: 4
- **actor**: 시스템
- **action**: 내부 채널이면 저작도구가 보관한 역할로 인가를 해석한다 — userId 클레임으로 저작도구 마스터 LS_ACNT_USER.USER_ID 로 조회한다. 다중 매칭이면 fail-closed 로 무권한 처리한다(CWE-639). 0건 매칭이면 다음 단계(step5, 자동발급)로 이어진다. 기존 숫자 sub(USER_NO) 식별 경로는 그대로 두고 바꾸지 않는다. 이어서 해석된 신원(userNo)을 principal 의 주체 식별자로 정규화해, 이후 per-user 스코핑·소유권·감사·작업 잠금이 raw 로그인 ID 가 아니라 실제 userNo 를 본다 — 해석 실패면 raw 를 유지하며 fail-closed 가 그대로 성립하고, 숫자 sub(내부·포털) 경로는 정규화 전후 값이 같아 무변경이다

### [5]

- **step**: 5
- **actor**: 시스템
- **action**: 내부·비숫자 sub 진입자가 userId 클레임으로 저작도구 마스터 LS_ACNT_USER.USER_ID 로 조회해 0건 매칭이면, 로컬 식별 레코드(userNo)를 disjoint 상위 시퀀스로 발급하고 USER_ID 안정키로 원자적 등록한다 — 역할은 미부여(role=null)라 인가 계층에서는 여전히 무권한이지만 식별 계층에서는 userNo 를 발급한다(0건이 곧 아무것도 안 만듦은 아니다). 재진입·동시진입에 같은 USER_ID 는 같은 userNo 로 수렴한다. 발급된 userNo 로 principal 정규화가 이어져 role-claim 식별이 성립하고, 이 진입자는 role=null 로 남아 관리자 부트스트랩·배정을 기다린다 — step6 의 작업자 자동 등록 대상이 아니다. 숫자 sub 와 포털 채널은 무영향이다

### [6]

- **step**: 6
- **actor**: 시스템
- **action**: 역할이 없는 내부 진입자는 그 시점에 작업자로 자동 등록한다 — 이미 부여된 역할은 덮지 않으며, 개발용 로그인이 발급하는 표준 계정은 이 자동 등록 대상이 아니다

### [7]

- **step**: 7
- **actor**: 시스템
- **action**: 진입 처리가 저작도구에 자기 정보를 물어 역할과 이름을 함께 받아 보관한다 — 역할만 취하고 이름을 버리지 않는다. 화면 상단에 표시하는 이름의 진실원은 이 응답이고 인계 토큰의 이름 클레임은 보조라, 토큰에 이름이 실려 오지 않아도 저작도구가 아는 이름이 표시된다. 두 조달원 모두에서 이름을 얻지 못했을 때만 대체 표기로 내려간다.

### [8]

- **step**: 8
- **actor**: 시스템
- **action**: 채널과 역할로 각 창구의 접근을 판정한다 — 관리자는 검수자 자리를 계층으로 물려받되 작업자 전용 자리는 열리지 않는다

### [9]

- **step**: 9
- **actor**: 시스템
- **action**: 역할이 없는 채로 남은 내부 진입자를 어디로 보낼지는 두 조건이 정한다 — 역할 없음과 창구 열림이다. 최초 관리자 등록 창구가 열려 있으면 그 등록 화면으로 안내하고, 닫혀 있으면 관리자에게 역할 부여를 요청하라는 안내로 보내며 등록 수단 자체를 보여 주지 않는다. 개폐는 진입 시점에 조회로 미리 확인한다 — 제출해 보고 거절당해 뒤늦게 아는 것이 아니다. 다만 그 조회는 순간의 상태라, 조회와 제출 사이에 다른 사람이 최초 관리자가 되어 제출이 창 닫힘으로 거절되는 갈래는 그대로 남는다.

### [10]

- **step**: 10
- **actor**: 인계 진입 사용자
- **action**: 세션이 만료되면 각 상위 시스템의 로그인 화면으로 되돌아간다

### [11]

- **step**: 11
- **actor**: 시스템
- **action**: 화면을 다시 불러올 때마다 인가 역할을 저작도구에 다시 물어 확보한다 — 서버가 알려 준 역할은 그 화면이 살아 있는 동안만 유효한 값이고 인계 토큰과 함께 보존되지 않기 때문이다. 이 재확보는 채널을 가리지 않는다 — 내부로 들어왔든 외부로 들어왔든 확인한다. 알아낸 역할은 인계 토큰을 두는 자리에 함께 보관하지 않는다 — 함께 보관하면 서버에서 역할이 바뀌거나 회수된 뒤에도 옛 값이 남아 실제 권한과 어긋난다

### [12]

- **step**: 12
- **actor**: 시스템
- **action**: 역할에 따른 도착지 판정은 그 재확보가 끝난 뒤에 내린다 — 확보되기 전에 판정하면 아직 확인하지 못한 상태가 역할 없음으로 읽혀, 이어 보던 자리 대신 역할 부여를 요청하라는 안내로 잘못 보내진다

### [13]

- **step**: 13
- **actor**: 시스템
- **action**: 역할 확보의 상태를 갈라 판정에 닿을 수 있는지를 정한다 — 세션이 없으면 물을 것이 없어 판정을 통과시키고, 세션은 있는데 아직 확보하지 않은 미확보 상태에서는 역할 판정에 도달하지 않는다. 확보하는 동안은 판정을 보류하고, 확보에 실패한 것은 확인하지 못한 상태라 역할 없음과 같지 않다. 세션 없음과 미확보를 한 값으로 겸하면 미확보가 조용히 통과해, 토큰이 역할을 싣고 온 세션에서 저작도구가 보관한 역할을 한 번도 확인하지 않은 채 화면이 열린다

### [14]

- **step**: 14
- **actor**: 시스템
- **action**: 앞서 확보한 결과를 다시 쓰는 근거는 세션에 묶인다 — 세션이 끊겼다 같은 인계 토큰으로 다시 서면 역할을 다시 확보한다. 같은 토큰이라는 것만으로 다시 묻지 않으면 역할이 상태에 앉지 않은 채 확보 절차만 건너뛰어, 역할을 가진 사람이 권한을 요청하라는 안내로 갈린다. 다시 쓰더라도 그 결과가 지금 상태에 실제로 반영돼 있어야 한다

### [15]

- **step**: 15
- **actor**: 시스템
- **action**: 관제 채널로 진입해 작업하는 동안, 보호된 요청을 보내기 직전에 토큰의 남은 시간이 10분 이하이면 저작도구 서버를 거쳐 관제 계정 갱신을 요청해([[API-247]]) 조용히 연장하고 새 토큰을 실어 보낸다 — 사용자가 할 일은 없다. 갱신 중에 들어온 요청은 같은 갱신을 기다리며 갱신은 한 번만 나간다. 이 단계부터 뒤따르는 연장 단계는 관제 채널에만 있고 포털 채널에는 없다

### [16]

- **step**: 16
- **actor**: 시스템
- **action**: 사용자가 화면을 방치해 남은 시간이 연장 안내 임계 이하가 되면 연장 팝업을 띄우고 남은 시간을 실시간으로 보여 준다 — 임계에 닿으면 띄우되 매 감시 주기마다 되풀이하지 않는다. 임계는 저장된 세션 정보의 sessionExpAlarm(분) → 없으면 토큰 클레임의 같은 값 → 없으면 30분 순으로 정한다. 팝업은 관제 채널의 로그인된 모든 화면 — 전체 화면으로 여는 작업 화면 포함 — 에서 뜬다. 현재 화면에 저장하지 않은 편집이 있으면 팝업에 그 사실을 알리는 경고를 함께 보인다 — 저장하지 않은 편집이 없으면 경고는 보이지 않는다

### [17]

- **step**: 17
- **actor**: 인계 진입 사용자
- **action**: 팝업에서 「로그인 연장」을 누르면 저작도구 서버를 거쳐 관제 계정을 갱신해 연장된다. 「로그아웃」을 누르면 현재 화면에 저장하지 않은 편집이 있을 때 화면 이탈 공통 확인 절차를 거친다 — 취소하면 로그아웃하지 않고 화면에 남고, 계속을 고르면 저작도구 서버에 관제 로그아웃을 맡기고, 그 호출의 성공·실패와 무관하게 저장소의 토큰과 토큰 정보를 지운 뒤 관제 로그인 화면으로 보낸다 — 저장소를 공유하는 같은 출처의 관제 탭도 함께 로그아웃된다. 팝업의 버튼은 이 둘뿐이라 닫기 버튼도 닫기 아이콘도 두지 않고, ESC 를 누르거나 배경을 눌러도 닫히지 않는다 — 안내를 실수로 놓치지 않게 하기 위해서다. 둘 중 하나를 누르면 팝업이 닫힌다 — 다만 그 토큰 수명 동안 다시 묻지 않는 것은 「로그인 연장」을 눌렀을 때와 「로그아웃」으로 실제 이탈했을 때뿐이고, 「로그아웃」을 눌렀다가 미저장 확인에서 취소해 화면에 남으면 그 재표시 억제가 풀려 다음 감시 주기에 임계 이하면 다시 안내한다

### [18]

- **step**: 18
- **actor**: 시스템
- **action**: 연장이 성공하면 — 이 탭에서든 다른 탭에서든 — 새 토큰의 만료 시각을 기준으로 다시 감시하고, 떠 있던 팝업을 닫으며 한 번 띄웠다는 표시도 함께 지워 새 토큰 수명에서는 임계에 닿을 때 다시 한 번 띄운다 — 그 표시는 연장 성공만이 아니라 「로그아웃」을 눌렀다가 미저장 확인에서 취소해 화면에 남았을 때도 풀린다. 연장하지 않은 채 남은 시간이 0 이 되면 팝업을 닫고 관제 로그인 화면으로 보낸다 — 저장하지 않은 편집이 남아 있어도 미저장 변경 확인 절차 없이 이동하며, 그 편집을 자동으로 저장하지 않는다

### [19]

- **step**: 19
- **actor**: 시스템
- **action**: 다른 탭(관제 탭 포함)에서 연장하거나 로그아웃하면 이 탭도 따라간다 — 연장이면 새로고침 없이 다음 요청부터 새 토큰을 싣고, 로그아웃이면 이 탭도 관제 로그인 화면으로 간다

## description

저작도구는 독립 로그인 화면을 두지 않고 상위 시스템이 발급한 토큰을 인계받아 진입한다. 진입 이후 무엇에 닿을 수 있는지는 두 축이 함께 정한다 — 어느 채널로 들어왔는지와 어떤 역할을 가졌는지다.

[채널은 배포 향이 정한다] 포털 향 배포본은 토큰이 무엇을 싣고 오든 포털 채널로 확정하고, 관제 향 배포본만 토큰의 채널 값을 읽되 값이 없으면 관제 채널로 본다. 배포 향이 선언되지 않았거나 값역 밖이면 관제 채널로 닫는다.

[인가에 쓰는 역할은 저작도구가 보관한 값이다] 토큰에 다른 체계의 역할만 실려 있어도 저작도구가 보관한 값으로 인가하며, 그 값이 해석되지 않으면 보호된 창구에서 거부한다. 포털 채널은 보관값 없이 포털 역할로 인가한다.

[채널 격리는 역할로 뚫리지 않는다] 포털 채널로 해석된 진입은 내부 창구와 관리 창구에 닿지 못하고 내부 채널로 해석된 진입은 포털 창구에 닿지 못한다. 관리자에게 검수자 권한을 물려주는 계층도 이 격리를 열지 않는다.

[역할이 없어도 들어올 길은 남긴다] 역할이 배정되지 않은 내부 사용자는 보호된 창구에서 거부되지만 자기 정보 조회와 관리자 등록 창구에는 도달한다 — 그 둘까지 막으면 아무도 처음 들어올 수 없다.

[해석된 신원은 principal 로 정규화한다] 관제 인계 토큰(비숫자 sub)을 userId 로 유일 해석하면 그 신원(userNo)을 principal 의 주체 식별자로 정규화해 내부·포털 토큰과 동형으로 만든다 — 이후 per-user 스코핑·소유권·감사·작업 잠금이 raw 로그인 ID 가 아니라 실제 userNo 를 일관되게 본다. 해석 실패면 raw 를 유지하며 fail-closed 가 그대로 성립한다([[ADR-063]]).

[관제 채널은 세션을 스스로 연장한다] 관제는 저작도구를 새 탭으로 열어 관제의 만료 감시·연장 안내가 저작도구 탭에는 미치지 않고, 관제 토큰의 수명은 짧다. 그래서 관제 채널 저작도구는 보호된 호출마다 같은 출처 저장소의 현재 토큰을 쓰고, 작업 중 만료가 가까우면 저작도구 서버를 거쳐 관제 계정 갱신을 요청해 조용히 연장하며, 방치돼 만료가 다가오면 연장 팝업으로 묻는다. 연장 결과는 관제와 같은 키·형식으로 저장소에 써 관제 탭과 공유한다. 이것은 저작도구 서버가 관제의 갱신 창구를 대신 부르는 것이지([[API-247]]) 저작도구가 토큰을 발급하는 것이 아니다([[ADR-012]] · [[INT-015]]). 포털 채널은 이 연장과 무관하다.

## postconditions

- 채널과 역할이 해석되어 이후 요청의 인가 판정에 쓰인다
- 역할이 없던 내부 진입자는 작업자로 등록되어 배정 대상 목록에 나타난다 — 단 개발용 로그인이 발급하는 표준 계정은 역할 없는 상태로 남아, 최초 관리자 등록 창구가 열려 있으면 그리로 유도되고 닫혀 있으면 관리자에게 역할 부여를 요청하라는 안내를 본다
- 진입 시 받은 역할과 이름이 함께 보관되어, 이후 화면 상단의 사용자 표시가 저작도구가 아는 이름을 쓴다
- 화면을 다시 불러온 뒤에도 인가 역할이 다시 확보되어, 채널을 가리지 않고 이어 보던 자리가 유지된다
- 세션이 갈린 뒤에도 역할을 다시 확보한 뒤에 도착지가 정해지고, 확보하지 않은 상태가 역할 없음으로 통과하지 않는다
- 관제 채널에서 연장이 성공하면 같은 출처 저장소의 토큰과 토큰 정보가 관제와 같은 키·형식으로 갱신되어, 관제 탭도 새 토큰으로 계속 동작한다
- 관제 채널에서 연장 팝업의 「로그아웃」을 누르면 — 저장하지 않은 편집이 있을 때는 화면 이탈 공통 확인 절차에서 계속을 고른 뒤 — 관제 로그아웃 창구 호출의 성공·실패와 무관하게 같은 출처 저장소의 토큰과 토큰 정보가 지워지고 관제 로그인 화면으로 이동해, 저장소를 공유하는 관제 탭도 함께 로그아웃된다
- 관제 채널에서 연장 팝업의 「로그아웃」을 눌렀더라도 미저장 변경 확인에서 취소하면 로그아웃하지 않고 화면에 남아, 저장소의 토큰과 토큰 정보가 그대로 유지되고 만료 전까지 작업을 이어 갈 수 있다 — 재표시 억제가 풀려 다음 감시 주기에 임계 이하면 다시 안내된다

## alternate_flows

### 역할이 해석되지 않음

**steps**:

- 보호된 창구에서 거부된다
- 자기 정보 조회에는 도달하고, 최초 관리자 등록 창구에는 그 창이 열려 있을 때만 안내된다 — 닫혀 있으면 관리자에게 역할 부여를 요청하라는 안내를 본다
- 라벨 마스터 읽기 같은 내부 조회에서는 거부된다

- **trigger**: 내부 채널인데 보관된 역할이 없거나 허용 목록 밖 값이다

### 채널이 어긋남

**steps**:

- 양쪽 모두 권한 없음으로 거부된다
- 역할 계층으로도 열리지 않는다
- 포털 향 배포본에서는 채널이 배포 향으로 확정되어 이 갈래가 성립하지 않는다 — 토큰의 채널 표식으로 갈리던 시절의 조건부 갈래다

- **trigger**: 관제 향 배포본에서 토큰에 실린 채널 값이 포털이라 내부 창구를 부르거나, 그 반대로 내부 채널 진입이 포털 창구를 부른다

### 토큰이 없거나 만료됨

**steps**:

- 인증 실패로 거부된다
- 자원의 존재 여부가 드러나지 않는다

- **trigger**: 토큰이 없거나 유효기간이 지났다

### 진입 시 역할 조회에 실패함

**steps**:

- 인증이 유효하지 않으면(토큰 없음·만료·검증 실패) 상위 시스템의 로그인 화면으로 되돌아간다
- 그 밖의 조회 장애는 오류로 알린다
- 어느 쪽도 최초 관리자 등록 창구로 보내지 않는다 — 확인하지 못한 것을 역할 없음으로 뭉개면 오류가 사양으로 위장되어, 세션이 만료된 사람이 관리자가 없다는 안내를 보게 된다
- 역할이 없다는 것은 확인해서 알아낸 사실일 때만 성립하며 확인하지 못한 상태와 같지 않다 — 이 흐름은 서버가 요청을 거절하는 축(토큰이 없거나 만료됨)과 달리 진입 처리가 조회에 실패하는 축이다

- **trigger**: 진입 처리가 저작도구에 자기 정보를 묻는 조회 자체가 실패한다 — 인증이 유효하지 않거나 그 밖의 조회 장애다

### 화면을 다시 불러온 뒤 역할 재확보에 실패함

**steps**:

- 인증이 유효하지 않으면(토큰 없음·만료·검증 실패) 상위 시스템의 로그인 화면으로 되돌아간다
- 그 밖의 조회 장애는 오류로 알린다
- 확인하지 못한 것을 역할 없음으로 다루지 않는다 — 최초 관리자 등록 창구로도, 관리자에게 역할 부여를 요청하라는 안내로도 보내지 않는다
- 역할에 따른 도착지 판정을 내리지 않은 채로 둔다 — 실패를 사양 안내로 바꾸면 장애가 드러나지 않는다
- 확인하지 못했다는 안내에서 사람이 다시 시도할 수 있다 — 스스로 반복해서 다시 묻지 않고 사람이 요청할 때만 다시 확보한다. 안내가 시도를 권하면서 시도할 수단이 없는 상태를 두지 않는다

- **trigger**: 화면을 다시 불러오면서 인가 역할을 다시 묻는 조회가 실패한다 — 인증이 유효하지 않거나 그 밖의 조회 장애다

### 확보 응답이 세션이 갈린 뒤에 도착함

**steps**:

- 성공한 응답도 실패한 응답도 반영하지 않는다 — 이 갈래는 조회가 실패한 축이 아니라 응답을 어느 세션에 귀속시키느냐의 축이라, 성공 쪽에도 똑같이 적용된다
- 앞 세션의 응답으로 새 세션의 역할을 채우지 않는다 — 채우면 진행 중인 확보의 대기가 먼저 풀려 확보 상태를 가른 순서가 무너진다
- 세션이 없는 상태에 확인 실패를 남기지 않는다 — 남기면 다음 진입이 근거 없이 오류 안내로 떨어진다
- 새 세션은 자기 조회로 역할을 다시 확보하고 그 확보가 끝난 뒤에 도착지를 판정한다

- **trigger**: 역할 확보 조회의 응답이 도착했을 때 그 조회를 시작한 세션이 이미 갈렸다

### 세션 연장 갱신에 실패함

**steps**:

- 갱신 결과를 저장하지 않는다 — 실패한 갱신의 응답으로 저장소의 토큰과 토큰 정보를 덮어쓰지 않는다
- (A) 관제가 갱신을 거절했으면(저작도구가 거절(401)로 답함 — 관제 서버의 세션이 이미 정리됐다) 선제 연장이든 팝업의 「로그인 연장」이든 경로를 가리지 않고, 미저장 변경 확인 절차 없이 즉시 세션을 비우고 관제 로그인 화면으로 보낸다
- (A) 다만 거절을 받으면 로그아웃하기 전에 저장소를 다시 읽어, 다른 탭이 이미 새 토큰을 저장해 두었으면 로그아웃하지 않고 그 토큰으로 이어 간다 — 거절은 이 탭이 쥐고 있던 옛 갱신 토큰에 대한 것이기 때문이다
- (A) 거절된 갱신 토큰으로는 다시 갱신하지 않는다
- (B) 저작도구가 일시 장애(503)로 답했거나 네트워크 오류로 응답을 받지 못했으면 쥐고 있던 토큰과 갱신 토큰을 그대로 두고, 아직 유효한 현재 토큰으로 작업을 이어 가며 다음 요청 때 다시 갱신을 시도한다
- (B) 팝업에서 누른 연장이 일시 장애로 실패했으면 연장하지 못했다고 안내한다
- (B) 연장하지 못한 채 남은 시간이 0 이 되면 미저장 변경 확인 절차 없이 관제 로그인 화면으로 보낸다
- 보호된 요청이 인증 실패(401)로 돌아온 뒤의 갱신 실패는 이 갈래가 아니다 — 「보호된 요청이 인증 실패로 돌아옴 — 관제 채널」 갈래대로 즉시 로그아웃한다

- **trigger**: 관제 채널에서 선제 연장이나 팝업의 「로그인 연장」으로 저작도구 서버를 거쳐 요청한 관제 계정 갱신([[API-247]])이 실패한다 — 관제가 갱신을 거절해 저작도구가 거절(401)로 답한 경우와, 저작도구가 일시 장애(503)로 답했거나 네트워크 오류로 응답을 받지 못한 경우를 가른다

### 보호된 요청이 인증 실패로 돌아옴 — 관제 채널

**steps**:

- 저작도구 서버를 거쳐 관제 계정 갱신을 요청한 뒤([[API-247]]) 원 요청을 한 번만 다시 보낸다
- 다시 보낸 요청도 인증 실패이거나 갱신이 실패하면 미저장 변경 확인 절차 없이 세션을 비우고 관제 로그인 화면으로 보낸다
- 관리자 패스워드 확인처럼 세션 만료가 아닌 인증 실패를 돌려주는 요청은 이 갈래의 대상이 아니다

- **trigger**: 관제 채널에서 갱신 토큰을 가진 진입의 보호된 요청이 인증 실패(401)로 돌아온다

### 갱신 토큰이 없는 진입

**steps**:

- 연장하지 않고 인계받은 토큰을 만료까지 쓴다
- 오류로 다루지 않는다 — 진입과 요청은 종전과 같이 동작한다
- 만료되면 상위 시스템의 로그인 화면으로 되돌아간다

- **trigger**: 관제 채널이지만 갱신 토큰을 보유하지 않은 진입이다 — 개발용 로그인처럼

### 사용자가 로그아웃을 선택함

**steps**:

- 현재 화면에 저장하지 않은 편집이 있으면 화면 이탈 공통 확인 절차를 거친다 — 저장하지 않은 편집이 없으면 확인 없이 이어 간다
- 사용자가 취소하면 로그아웃하지 않고 화면에 남는다 — 팝업은 이미 닫혔고, 만료 전까지 작업을 이어 가며 다음 요청의 선제 갱신으로 연장된다. 다만 취소는 「지금 나가지 않겠다」이지 「안내를 그만 받겠다」가 아니므로 「같은 토큰 수명 동안 재표시 안 함」 상태를 푼다 — 다음 감시 주기에 남은 시간이 여전히 임계 이하면 연장 팝업이 다시 뜬다. 풀지 않으면 만료까지 아무 안내 없이 로그아웃된다
- 사용자가 계속을 고르면 저작도구 서버를 거쳐 관제 로그아웃을 요청한다([[API-246]])
- 그 호출의 성공·실패와 무관하게 같은 출처 저장소의 토큰과 토큰 정보를 지운다 — 로그아웃 호출이 실패해도 토큰을 남기지 않는다
- 관제 로그인 화면으로 보낸다 — 저장소를 공유하는 같은 출처의 관제 탭도 함께 로그아웃된다
- 팝업은 어느 갈래에서든 닫히지만, 그 토큰 수명 동안 다시 뜨지 않는 것은 「로그아웃」으로 실제 이탈했을 때다 — 미저장 확인에서 취소해 화면에 남은 경우는 앞 단계대로 재표시 억제가 풀린다

- **trigger**: 관제 채널의 연장 팝업에서 사용자가 「로그아웃」을 누른다

### refresh 토큰으로 호출함

**steps**:

- 서명과 만료가 유효해도 인증 실패(401)로 거부되고 인증 컨텍스트가 서지 않는다
- 채널을 가리지 않는다 — 관제 채널과 포털 채널에서 똑같이 거부된다
- 종류 클레임이 없는 토큰(개발용 로그인·포털 인계)과 종류가 access 인 토큰은 이 갈래가 아니며 종전대로 수용된다
- 토큰이 유효하지 않아 거부되는 「토큰이 없거나 만료됨」과는 다른 축이다 — 이 갈래의 토큰은 유효하지만 종류 때문에 거부된다

- **trigger**: 토큰 종류 클레임이 refresh 인 토큰을 인증 헤더에 실어 보호된 창구를 호출한다 — 서명과 만료는 유효하다

## tech_considerations

- 역할 해석이 되지 않을 때 열어 주지 않고 닫는다 — 의심스러울 때 통과시키면 인가가 무력해진다
- 채널 판정과 역할 판정은 서로 다른 축이라 한쪽을 통과했다고 다른 쪽이 열리지 않는다
- 자동 등록은 조건부 갱신으로 한 번만 일어나며 매 요청마다 쓰지 않는다
- 확인하지 못한 상태를 역할 없음으로 뭉개지 않는다 — 조회 실패는 실패로 다루고 사양 안내로 바꾸지 않는다
- 창구 개폐를 미리 묻는 조회와 제출 시점의 판정은 같은 근거를 써야 한다 — 근거가 갈리면 조회가 열림이라 답한 직후에 제출이 거절되는 어긋남이 생긴다
- 서버가 알려 준 인가 역할은 그 화면 수명 동안만 유효한 값이라 인계 토큰과 함께 보관하지 않는다 — 함께 보관하면 회수되거나 바뀐 옛 값이 남아 실제 권한과 어긋난다
- 확보 응답은 그것을 요청한 세션에만 귀속시킨다 — 늦게 도착한 응답을 다른 세션에 반영하면 성공은 확보 상태를 가른 순서를 무너뜨리고 실패는 근거 없는 오류 안내를 남긴다
- 확인 실패의 회복은 사람이 누르는 재시도로 둔다 — 스스로 반복하면 장애 구간에 조회가 몰리고, 재시도 수단이 없으면 실패가 화면 수명 내내 고착된다
- 채널은 토큰이 아니라 배포 향이 정한다 — 포털 향 배포본은 토큰의 채널 값을 따르지 않고, 배포 향을 알 수 없으면 관제 채널로 닫는다
- 연장 결과는 관제가 쓰는 것과 같은 키·필드 이름·단위로 저장한다 — 한 글자라도 다르면 같은 저장소를 읽는 관제 탭이 깨진다. 저장 형식의 정본은 관제 채널 토큰 인계 규격(INT-013)이다
- 관제 탭과 동시에 갱신하지 않도록 갱신 직전 저장된 갱신 토큰을 다시 읽어, 다른 탭이 이미 갱신했으면 갱신을 부르지 않는다 — 관제 탭은 저작도구 쪽 직렬화를 모르므로 완전한 배제는 불가능하다(인지·수용)
- 세션 연장은 관제 채널에만 있다 — 포털 채널의 Host 인계 창구와 Host 메모리 보관은 이 연장의 영향을 받지 않는다
- 다른 기기에서 관제 세션이 끊겨도 이 브라우저 저장소의 토큰 값은 그대로 남아 저장소 추종으로는 그 종료를 알 수 없다 — 그래서 갱신 시점에 잡는다. 관제가 갱신을 거절하면 경로를 가리지 않고 즉시 로그아웃하고, 거절이 아닌 일시 장애는 다음 요청 때 다시 시도한다
- 미저장 변경 확인 절차를 거치는지는 그 시점에 세션이 살아 있어 저장이 가능한가로 가른다 — 사용자가 누른 로그아웃은 세션이 아직 유효하므로 확인을 거치고, 갱신 거절·인증 실패 뒤 갱신 실패·남은 시간 0 같은 강제 로그아웃은 저장할 수단이 이미 없어 확인 없이 이동한다
- 브라우저는 관제를 직접 부르지 않는다 — 관제 계정 호출은 저작도구 서버가 중계한다(사용자 확정)
- refresh 토큰의 정당한 쓰임은 관제 세션 갱신 중계 창구([[API-247]])의 요청 본문뿐이다 — 인증 헤더로 실려 온 refresh 토큰은 채널을 가리지 않고 인증에 쓰지 않는다
