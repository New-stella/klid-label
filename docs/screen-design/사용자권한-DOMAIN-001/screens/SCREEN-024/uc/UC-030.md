# 사용자 계정·역할 관리

## goal

관리자가 사용자 목록을 검색·역할로 필터링해 조회하고 사용자의 역할(관리자/검수자/작업자/포털)과 표시 이름을 변경한다 — 화면 진입에 관리자 역할이 필요하고, 저장에는 거기에 관리자 단기 유효창이 함께 필요하다 — 역할을 고치든 표시 이름만 고치든 같다.

## actor

관리자(ADMIN)

## title

사용자 계정·역할 관리

## status

draft

## priority

should

## frequency

비정기 — 사용자가 들어오거나 역할을 바꿔야 할 때만 수행하는 저빈도 관리 작업이다.

## main_flow

### [1]

- **step**: 1
- **actor**: 관리자(ADMIN)
- **action**: 관리자 페이지에 속한 사용자 관리 화면(/admin/users)에서 사용자 목록을 조회한다(GET /v1/users = API-001, 서버 페이징 20건/페이지, 정렬은 등록 순서 고정) — 화면 진입에 관리자 역할이 필요하며, 조회 자체에는 관리자 단기 유효창까지는 요구하지 않는다

### [2]

- **step**: 2
- **actor**: 관리자(ADMIN)
- **action**: 검색어(이름/이메일 부분일치)와 역할 필터(전체/관리자/검수자/작업자/포털)를 입력한 뒤 Enter 또는 검색 버튼으로 확정한다 — 확정 시에만 서버 재조회되고 1페이지로 리셋된다

### [3]

- **step**: 3
- **actor**: 시스템
- **action**: 각 행의 계정 활성 상태(활성/비활성) 배지를 표시한다 — 이 값은 외부 시스템(관제서버) 소유이며 이 화면에서 변경 대상이 아니다(읽기 전용)

### [4]

- **step**: 4
- **actor**: 관리자(ADMIN)
- **action**: 행의 '수정' 버튼으로 사용자 정보 수정 모달을 연다(테이블 행 데이터 기반, 별도 단건 조회 없음)

### [5]

- **step**: 5
- **actor**: 시스템
- **action**: 이 창구의 저장은 운영·관리 성격의 쓰기라 유효한 관리자 단기 유효창을 함께 요구한다 — 역할을 고치든 표시 이름만 고치든 같으며, 관리자 역할을 대체하지 않고 그 위에 가산되고 유효창은 역할을 승격시키지 않는다

### [6]

- **step**: 6
- **actor**: 관리자(ADMIN)
- **action**: 역할(관리자/검수자/작업자/포털)과 표시 이름을 고쳐 저장한다 — 두 축은 각각 선택이라 보내지 않은 축은 바뀌지 않으며, 고친 축만 PATCH /v1/users/{userNo}(API-004)로 전송한다(고친 축이 하나도 없거나 보낸 값이 전부 원래 값과 같으면 저장 버튼이 비활성화된다)

### [7]

- **step**: 7
- **actor**: 시스템
- **action**: 표시 이름은 앞뒤 공백과 제어문자를 걷어낸 뒤 판정한다 — 그러고 나서 아무 글자도 남지 않으면 거부하고, 저장할 수 있는 폭을 넘으면 잘라 담지 않고 거부한다. 이름은 사람을 알아보는 값이라 조용히 잘리면 다른 사람으로 보이기 때문이다

### [8]

- **step**: 8
- **actor**: 시스템
- **action**: 서버가 허용 역할(ADMIN/REVIEWER/WORKER/PORTAL_USER) 화이트리스트로 재검증하고 그 외 값은 400으로 거부한다

### [9]

- **step**: 9
- **actor**: 시스템
- **action**: 바꾸려는 대상이 마지막 남은 관리자이고 그 역할을 관리자가 아닌 값으로 내리려 하면 409 로 거절한다 — 관리자가 0명이 되면 자가부여 부트스트랩 창구가 다시 열리기 때문이다. 이 판정은 조회 후 갱신이 아니라 갱신 문장 자체가 조건을 함께 판정해야 한다. 두 관리자가 서로를 동시에 내리면 각자 조회 시점에는 둘 다 통과한다

### [10]

- **step**: 10
- **actor**: 시스템
- **action**: 역할을 보내지 않고 표시 이름만 고친 요청은 앞의 두 역할 축 판정(허용 역할 재검증·마지막 관리자 보호)을 타지 않는다 — 마지막 남은 관리자여도 이름만 바꾸는 요청은 통과하고, 역할은 원래 값 그대로 남는다

### [11]

- **step**: 11
- **actor**: 시스템
- **action**: 보낸 값이 이미 저장된 값과 같으면 그 축은 아무것도 바꾸지 않는다 — 수정 일시도 밀리지 않는다

### [12]

- **step**: 12
- **actor**: 시스템
- **action**: 유효창 토큰이 발급받은 사람에게 묶여 있고 요청은 본인 자격으로 인증되므로, 역할을 바꾼 사람이 변경 기록에 개인 단위로 남는다

### [13]

- **step**: 13
- **actor**: 시스템
- **action**: 성공 시 안내 토스트를 표시하고 목록을 최신화한다

### [14]

- **step**: 14
- **actor**: 시스템
- **action**: 고친 이름은 저장값을 읽는 자리(사용자 목록·작업 배정·검수 화면·이력 작성자 표시)에 반영되고, 본인 화면 상단의 이름에는 반영되지 않는다 — 본인 프로필 응답은 인계 토큰의 이름을 먼저 쓰고 보관값은 토큰에 이름이 없을 때만 조달하기 때문이며, 설계된 동작이다

## brownfield

### notes

2026-08-27 — 역할 변경에 관리자 단기 유효창이 가산됐다. 관리자 역할은 그대로 필요하고 유효창이 그것을 대체하지 않으며 역할을 승격시키지도 않는다. 조회는 유효창 없이 검수자 권한만으로 되며, 이 화면의 목록·상세뿐 아니라 다른 업무 화면이 작업자 목록을 읽는 경로도 그렇다 — 조회까지 막으면 작업 배정 흐름이 끊긴다. 역할만 쓰기 가능하고 계정 활성 여부는 외부 시스템 소유값이라 읽기 전용이라는 기존 계약은 그대로다. 2026-08-28 — 관리 권한이 관리자 역할로 분리되어 이 유스케이스의 행위자가 검수자에서 관리자로 바뀌었고, 마지막 관리자 보호 단계가 더해졌다. 2026-09-16 — 수정 모달의 쓰기 축이 역할 하나에서 역할·표시 이름 둘로 늘었다. 두 축은 각각 선택이며 보내지 않은 축은 바뀌지 않는다. 앞 문단의 '역할만 쓰기 가능'은 이 시점부터 표시 이름을 포함하도록 넓어졌고, 계정 활성 여부가 외부 시스템 소유값이라 읽기 전용인 것은 그대로다. 관리자 단기 유효창 요구도 역할 축에만 걸리는 것이 아니라 이 창구의 저장 전체에 걸린다 — 표시 이름만 고치는 요청에도 필요하다.

## description

관리자가 사용자 목록을 검색(이름/이메일 부분일치)·역할(관리자/검수자/작업자/포털) 필터로 서버 조회하고, 행의 '수정' 모달에서 역할과 표시 이름을 변경한다 — 두 축은 각각 선택이라 보내지 않은 축은 바뀌지 않는다. 계정 활성/비활성 상태는 외부 시스템(관제서버) 소유값이라 이 화면에서는 읽기 전용 배지로만 노출되며 변경 대상이 아니다 — 과거 활성/비활성 토글 기능은 쓰기 권한이 외부 시스템으로 이관되며 폐기되었다 — SCREEN-024 화면 사양에는 그 토글이 더 이상 존재하지 않는다. 역할 변경은 서버가 허용 역할 화이트리스트로 재검증하며 그 외 값은 400으로 거부한다. 이 창구의 저장은 운영·관리 성격의 쓰기라 유효한 관리자 단기 유효창을 함께 요구한다 — 역할을 고치든 표시 이름만 고치든 같으며, 관리자 역할을 대체하지 않고 그 위에 가산되고 유효창은 역할을 승격시키지 않는다. 유효창은 유효기간이 끝나면 다시 확인해야 하고, 유효 여부 판정은 서버가 소유한다. 반면 조회 창구 자체는 유효창 없이 검수자 권한으로도 응답한다 — 이 화면의 목록·상세뿐 아니라 다른 업무 화면이 작업자 목록 같은 사용자 정보를 읽는 경로도 마찬가지이며, 조회까지 막으면 작업 배정 흐름이 끊긴다. 창구가 그렇게 열려 있어도 이 화면에 들어오는 것은 관리자뿐이다 — 창구 축과 화면 축은 다르다. 이 화면은 관리자 페이지에 속한다. 유효창 토큰이 발급받은 사람에게 묶여 있고 요청은 본인 자격으로 인증되므로, 공유 패스워드로 여는 방식인데도 누가 역할을 바꿨는지가 개인 단위로 남는다. 표시 이름은 앞뒤 공백과 제어문자를 걷어낸 뒤 판정하며, 그러고 나서 아무 글자도 남지 않으면 거부한다. 저장할 수 있는 폭을 넘으면 잘라 담지 않고 거부한다 — 이름은 사람을 알아보는 값이라 조용히 잘리면 다른 사람으로 보이기 때문이다. 역할을 보내지 않고 표시 이름만 고친 요청은 역할 축 판정(허용 역할 재검증·마지막 관리자 보호)을 타지 않으므로, 마지막 남은 관리자여도 이름만 바꾸는 요청은 통과한다. 보낸 값이 이미 저장된 값과 같으면 그 축은 아무것도 바꾸지 않으며 수정 일시도 밀리지 않는다. 거부 응답은 어느 필드인지의 경로나 배열 순번을 담지 않는다. 고친 이름은 저장값을 읽는 자리(사용자 목록·작업 배정·검수 화면·이력 작성자 표시)에 반영되지만 본인 화면 상단의 이름에는 반영되지 않는다 — 본인 프로필 응답은 인계 토큰의 이름을 먼저 쓰고 보관값은 토큰에 이름이 없을 때만 조달하기 때문이며, 설계된 동작이다. 보관하는 이름의 소유자는 이 시스템이다(등록 이후 단방향) — 소유 축과 조달 순서 축은 다르다.

## alternate_flows

### 고칠 축 없음 또는 변경 없음

**steps**:

- 저장 버튼을 비활성화한다

- **trigger**: 역할과 표시 이름 중 어느 축도 고치지 않았거나 보낸 값이 전부 원래 값과 동일

### 허용 역할 밖 값 전송

**steps**:

- 400으로 거부한다

- **trigger**: 화이트리스트(ADMIN/REVIEWER/WORKER/PORTAL_USER) 밖 값으로 요청

### 필터 미활성

**steps**:

- '필터 초기화' 버튼을 비활성화한다

- **trigger**: 검색어·역할 필터가 모두 비어있음

### 관리자 유효창 없음 또는 만료

**steps**:

- 저장을 거부한다 — 역할을 고치든 표시 이름만 고치든 같으며, 관리자 역할만으로는 이 쓰기가 열리지 않는다
- 관리자가 패스워드를 다시 제출해 유효창을 새로 연 뒤 저장을 다시 시도한다
- 유효 여부 판정은 서버가 소유하며, 클라이언트가 스스로 아직 유효하다고 정하지 못한다
- 조회는 이 거부와 무관하게 그대로 동작한다

- **trigger**: 역할이든 표시 이름이든 저장하는 시점에 유효한 관리자 단기 유효창이 없다(아직 열지 않았거나 유효기간이 끝났다)

### 표시 이름이 빈 값

**steps**:

- 거부한다 — 빈 이름은 저장하지 않는다
- 거부 응답은 어느 필드인지의 경로나 배열 순번을 담지 않는다

- **trigger**: 표시 이름을 공백·제어문자만으로 보냈거나 정규화하고 나니 아무 글자도 남지 않았다

### 표시 이름이 저장 폭 초과

**steps**:

- 잘라 담지 않고 거부한다 — 이름은 사람을 알아보는 값이라 조용히 잘리면 다른 사람으로 보인다
- 거부 응답은 어느 필드인지의 경로나 배열 순번을 담지 않는다

- **trigger**: 표시 이름이 저장할 수 있는 폭을 넘었다

### 표시 이름만 고침 — 역할 축 판정 없음

**steps**:

- 허용 역할 재검증과 마지막 관리자 보호 판정을 타지 않는다
- 마지막 남은 관리자여도 통과한다
- 역할은 원래 값 그대로 남는다 — 다만 유효창은 이 요청에도 그대로 필요하다. 유효창 축과 역할 축은 다르다

- **trigger**: 역할을 보내지 않고 표시 이름만 보냈다

- 계정 활성 상태 변경 권한은 이 시스템이 아니라 외부 시스템(관제서버)에 있다 — 관리 화면에서 계정을 비활성화하려면 관제서버에서 처리해야 한다
- 관리자 단기 유효창은 인가를 대체하지 않고 가산된다 — 관리자 역할은 그대로 필요하며 유효창이 역할을 승격시키지 않는다
- 유효창을 요구하는 대상은 운영·관리 성격의 쓰기이며, 이 유스케이스에서는 이 창구의 저장이 그에 해당한다 — 역할 부여·변경과 표시 이름 변경이 모두 포함된다. 이름 칸이 더해졌다고 이 창구에 걸린 요건이 달라지지 않는다
- 조회 창구 자체는 유효창 없이 검수자 권한으로도 응답한다 — 이 화면의 목록·상세뿐 아니라 다른 업무 화면이 작업자 목록 같은 사용자 정보를 읽는 경로도 포함된다. 조회까지 막으면 작업 배정 흐름이 끊긴다. 창구가 그렇게 열려 있어도 이 화면에 들어오는 것은 관리자뿐이다
- 유효창은 유효기간이 끝나면 다시 확인해야 하며, 유효 여부 판정은 서버가 소유한다
- 이 화면은 관리자 페이지에 속한다
- 표시 이름은 정규화(앞뒤 공백·제어문자 제거) 뒤에 판정하며, 빈 값과 저장 폭 초과는 모두 거부한다 — 절단하지 않는다. 이름은 식별에 쓰이는 값이라 조용히 잘리면 다른 사람으로 보인다
- 보관하는 표시 이름의 소유자는 이 시스템이다(등록 이후 단방향). 다만 본인 프로필 응답의 조달 순서는 인계 토큰이 먼저이고 보관값은 토큰에 이름이 없을 때만 쓰인다 — 소유 축과 조달 순서 축은 다르다
