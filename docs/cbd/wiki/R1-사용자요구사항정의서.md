# R1 사용자 요구사항 정의서 (CBD 표준 산출물 위키)
> 출처: NIA CBD SW개발 표준 산출물 관리 가이드(2011.12) docs/CBD.pdf 인쇄면 p.7~8 (작성 사례 p.9~10)

## 1. 작성 목적
> PDF 원문 [작성 목적]

시스템의 요구사항을 도출하여 발주자와 내용을 합의하고, 하나의 업무 단위로서 가치를 가지고 수행될 수 있는 단위로서의 업무를 도출하여 업무 내용을 기술한다.

## 2. 작성 방법
> PDF 원문 [작성 방법] 전문

산출물 양식의 표를 이용하여 해당 항목에 기술하며 이해하기 쉽고 구체적인 언어표현을 사용한다. **기능적 요구사항과 비기능 요구사항을 그룹핑하여 별도의 표로 작성한다.**

## 3. 산출물 양식 (표 구조 전수)

### 3.1 제·개정 이력 (공통표)
| 날짜 | 버전 | 작성자 | 승인자 | 내용 |
|---|---|---|---|---|

- 날짜: 개정 발생일 / 버전: 문서 버전 / 작성자: 작성 담당 / 승인자: 승인 담당 / 내용: 제·개정 사유·범위

### 3.2 헤더 박스 구조
산출물 코드 `R1` 라벨 + 제목 `사용자 요구사항 정의서` 를 한 행으로 두고, 그 아래에 다음 항목을 배치한다.

| 항목 | 항목 | 항목 |
|---|---|---|
| 시스템명 | 서브시스템명 | — |
| 단계명 = `분석` | 작성일자 | 버전 |

- 시스템명 / 서브시스템명: 대상 (서브)시스템 명칭
- 단계명: 본 산출물의 개발 단계 = **분석** (고정)
- 작성일자 / 버전: 작성 기준일과 문서 버전

### 3.3 본문 표 (1행 = 요구사항 1건)
원문 컬럼(좌→우 순서) 전수:

| 요구사항 ID | 요구사항명 | 구분 | 요구사항 설명 | 요구사항 출처 | 제약사항 | 중요도 | 해결방안 | 검수기준 | 비고 |
|---|---|---|---|---|---|---|---|---|---|

- 요구사항 ID: 요구사항별 유일 ID
- 요구사항명: 요구사항 요약 명칭
- 구분: 요구사항 유형 (아래 4. 항목 설명의 구분 목록 중 택1)
- 요구사항 설명: 사용자 요구사항 상세
- 요구사항 출처: 제시 문서의 문서번호 + 문서명
- 제약사항: 수행에 필요한 법적·기술적 조건
- 중요도: 상 / 중 / 하
- 해결방안: 구체적 해결방안
- 검수기준: 구현 품질의 정량/정성 측정 기준
- 비고: 그 외 고려사항

> ※ 양식 상 컬럼 배치 순서는 **… 중요도 → 해결방안 → 검수기준 → 비고** 다. [항목 설명] 문단의 서술 순서(중요도 → 검수기준 → 해결방안)와 양식 표 컬럼 순서가 다르므로 양식 표를 기준으로 삼는다.

### 3.4 다이어그램
본 산출물에는 다이어그램이 없다 (표 형식 전용).

## 4. 항목 설명 (전 항목 — 누락 금지)
> PDF [항목 설명] 전 항목

- **요구사항 ID**: 요구사항별로 유일한 ID를 부여하여 기입한다.
- **요구사항명**: 도출된 요구사항을 요약할 수 있는 명칭을 기입한다.
- **구분**: 도출된 요구사항을 다음 중에서 선택하여 기재한다 — 정보시스템 개요 및 기능목록 / 기능 요구사항 / 성능 요구사항 / 품질 요구사항 / 인터페이스 요구사항 / 데이터 요구사항 / 운영 요구사항 / 제약사항. ※ "제안요청서의 요구사항 작성가이드"의 요구사항 구성요소 참조.
- **요구사항 설명**: 사용자 요구사항을 구체적이고 상세하게 기술한다.
- **요구사항 출처**: 요구사항이 제시된 문서에 대하여 문서번호와 문서명을 기술한다.
- **제약사항**: 요구사항이 수행되기 위하여 필요로 하는 법적 또는 기술적인 조건을 기술한다.
- **중요도**: 해당 요구사항의 전체 시스템 구현 측면에서의 중요도를 기술한다. (**상, 중, 하** 중에서 선택)
- **검수 기준**: 요구사항을 구현한 후 구현에 대한 품질을 정량적 또는 정성적으로 측정할 수 있는 기준을 기술한다.
- **해결방안**: 요구사항의 해결방안을 구체적으로 기재한다.
- **비고**: 위의 항목에 포함되지 않으나, 고려해야 할 사항이 있으면 기술한다.

## 5. 작성 사례 요점
> PDF 작성 사례 (인쇄면 p.9~10) 관찰값

- 헤더 예: 시스템명=`결제시스템 관리`, 서브시스템명=`총액결제관리`, 단계명=`분석`, 작성일자=`2011. 11. 07`, 버전=`1.0`.
- 요구사항 ID 예:
  - `SS_RF01001` (구분=**기능**) 원화자금이체신청 — 설명 "망 참가기관이 개설된 당좌예금계좌를 통한 자금거래 결제를 처리할 수 있어야 한다 …"
  - `SS_RQ03001` (구분=**성능**) 권한변경 용이성 — 설명 "시스템관리자가 조직변경에 따른 권한 변경이 있을 경우, 이를 1분 이내에 적용할 수 있어야 한다 …"
- 출처 예: "RFP(개발요구서 4):2p / 프로젝트수행계획서(별첨3):11p", "회의록-공통-아키텍처요구사항_20111106.doc" — 문서명+쪽까지 정밀 인용.
- 중요도 예: `상`.
- 해결방안 예: "관련 망을 접속 후 Push 기능 구현", "사용자 등록 후 접근 권한 통제".
- 검수기준 예(정성): "사용자의 체처리가 정의되고, 신청기관에 통지된다", 검수기준 예(정량): "시스템관리자가 1분 이내의 권한 변경".
- 비고 예: "신청기관 목록 확보 필요".
- ID 명명 패턴: `SS_` 접두 + 유형코드(`RF`=기능, `RQ`=성능 등) + 일련번호.

## 6. 함정 / 주의 (작성 시 흔한 실수)
- **기능/비기능 표 분리는 공식 요구사항**: "기능적 요구사항과 비기능 요구사항을 그룹핑하여 별도의 표로 작성한다." 한 표에 섞으면 안 된다.
- **양식 컬럼 순서 vs 항목 설명 서술 순서 불일치 주의**: 양식 표는 `중요도 → 해결방안 → 검수기준`, 항목 설명 문단은 `중요도 → 검수기준 → 해결방안` 순. 표 작성 시 양식 컬럼 순서를 따른다.
- **중요도는 상/중/하 3값만** — 우선순위 숫자·기타 표기 금지.
- **단계명은 `분석` 고정** — 다른 단계명 기입 오류 주의.
- **출처는 문서번호+문서명+쪽**까지 정밀 인용 (단순 "RFP" 만 기입 금지).
- **요구사항 ID는 전역 유일** — 후속 산출물(R2/R3 및 D-시리즈)이 인용하므로 중복·재사용 금지.

## 7. KLID 프로젝트 적용 메모
- 기능(SFR)·비기능(NFR) **별도 표** 분리는 공식 요구 — KLID R1은 「본문 — 기능 요구사항(SFR)」 + 「본문 — 비기능 요구사항(NFR)」 2개 표로 충족한다.
- KLID 기능 요구사항 ID는 발주처 원본 체계 `RQ-SFR-NN-NN` 을 그대로 사용하고, 비기능은 `NFR-NNN` 을 사용한다 (CBD 사례의 `SS_RFxxxxx`/`SS_RQxxxxx` 와 동일한 "유형코드+일련번호" 원리).
- 단계명=`분석` 고정, 헤더 시스템명/서브시스템명은 KLID 저작도구 기준으로 채운다.
- D4/D5/D7/T6 등 후속 산출물의 "관련 요구사항 ID"는 모두 본 산출물의 ID를 인용한다 — **R1에 실존하는 ID만 인용 가능**.
- LogiCraft ITEM 연계 시 요구사항 단위 식별자 적응: KLID 전체형 `KLID-AT-XX-NNN` 체계를 사용하되, R1 요구사항 자체의 원본 ID(`RQ-SFR-NN-NN`/`NFR-NNN`)는 발주처 추적성을 위해 보존한다.
