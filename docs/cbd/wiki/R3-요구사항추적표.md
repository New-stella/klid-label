# R3 요구사항 추적표 (CBD 표준 산출물 위키)
> 출처: NIA CBD SW개발 표준 산출물 관리 가이드(2011.12) docs/CBD.pdf 인쇄면 p.23~24 (작성 사례 p.25)

## 1. 작성 목적
> PDF 원문 [작성 목적]

시스템의 요구사항을 도출하여 개발의 각 단계별로 작성한 산출물이 일관성을 가지는지를 추적할 수 있도록, 각 단계별 산출물의 추적성을 관리하기 위하여 작성한다.

## 2. 작성 방법
> PDF 원문 [작성 방법] 전문

사용자 요구사항 정의서로부터 시작하여 분석, 설계, 구현, 시험의 각 단계별 산출물에 ID를 식별하고, 전단계 산출물과 후속단계 산출물 간의 연계관계에 맵핑 작업을 하여, 산출물이 단계별 연관관계가 끊어지지 않고 추적할 수 있도록 한다.

## 3. 산출물 양식 (표 구조 전수)

### 3.1 제·개정 이력 (공통표)
| 날짜 | 버전 | 작성자 | 승인자 | 내용 |
|---|---|---|---|---|

### 3.2 헤더 박스 구조
산출물 코드 `R3` 라벨 + 제목 `요구사항 추적표` + (시스템명 / 서브시스템명 / 단계명=`분석` / 작성일자 / 버전).

### 3.3 본문 — 전체 시스템에 대하여 **한 개의 가로 매트릭스 표** (1행 = 추적 사슬 1건)

3단 헤더 구조: 최상단 = **단계**, 중간 = **산출물명**, 하단 = **컬럼**. 단계별로 ID 컬럼과 이름/설명 컬럼(원문 표기 `D`)이 쌍을 이룬다.

| 단계 | 산출물 | 컬럼 1 (ID) | 컬럼 2 (이름/설명) |
|---|---|---|---|
| 분석 | 사용자 요구사항 명세서 | 요구사항 ID | 요구사항명 |
| 분석 | 유스케이스 명세서 | 유스케이스 ID | 유스케이스명 |
| 설계 | 사용자 인터페이스 설계서 | 화면 ID | D (화면명/설명) |
| 설계 | 컴포넌트 설계서 | 컴포넌트 ID | D (컴포넌트명/설명) |
| 설계 | 데이터베이스 설계서 | 테이블 ID | D (테이블명/설명) |
| 구현 | 프로그램 코드 | 파일 ID | D (파일명/설명) |
| 구현 | 단위시험 결과서 | 단위시험 ID | D (단위시험명/설명) |
| 시험 | 통합시험 결과서 | 시나리오 ID | D (시나리오명/설명) |
| 시험 | 시스템시험 결과서 | 시나리오 ID | D (시나리오명/설명) |

> 한 행이 좌→우로 분석→설계→구현→시험 전 단계의 산출물 ID를 사슬로 연결한다. ID 컬럼 옆 `D` 컬럼은 해당 산출물의 이름/설명(description)을 담는 짝 컬럼이다. (원문 표 헤더에서 ID 컬럼 우측마다 `D` 라벨이 반복 표기됨)

### 3.4 다이어그램
본 산출물에는 다이어그램이 없다 (가로 매트릭스 표 전용).

## 4. 항목 설명 (전 항목 — 누락 금지)
> PDF [항목 설명] 전문

전체 시스템에 대하여 한 개의 표로 작성하며, 각 산출물의 ID와 이름을 기술한다.

- 각 단계 컬럼에는 해당 산출물의 **ID + 이름(D)** 을 기입한다.
- 사용자 요구사항 명세서·유스케이스 명세서는 ID + 명칭을 모두 적고, 후속 단계 산출물도 ID 옆 `D` 컬럼에 이름/설명을 적는다.
- 산출물 단계 사슬(좌→우): 사용자 요구사항 명세서 → 유스케이스 명세서 → 사용자 인터페이스 설계서 → 컴포넌트 설계서 → 데이터베이스 설계서 → 프로그램 코드 → 단위시험 결과서 → 통합시험 결과서 → 시스템시험 결과서.

## 5. 작성 사례 요점
> PDF 작성 사례 (인쇄면 p.25) 관찰값

- 1행 사슬 예:
  `SS_RF01001 원화자금이체신청` → `SS_UCD_010-01 원화자금이체신청` → 화면 `SS_SC_010` → 컴포넌트 `SS_CO_040` → 테이블 `SS_TB_020` → 프로그램 `SS_DP_010` → 단위시험 `SS_UT_TS_010` → 통합시험 `SS_IT_TS_010` → 시스템시험 `SS_ST_010`.
- 다른 행 예:
  `SS_RF01002 미결제지정시점예약자금이체취소신청` → `SS_UCD_010-03 미결제지정시점예약자금이체취소신청` → 화면 `SS_SC_240` → 컴포넌트 `SS_CO_250` → 테이블 `SS_TB_230` → 프로그램 `SS_DP_210` → 단위시험 `SS_UT_TS_210` → 통합시험 `SS_IT_TS_210` → 시스템시험 `SS_ST_210`.
- 헤더: 단계명=`분석`.
- 요구사항·유스케이스는 **ID + 명칭 병기**, 이후 설계/구현/시험 단계는 사례상 주로 **ID 위주**로 기입(이름 컬럼 `D` 는 채울 수 있음).
- ID 명명 패턴: 화면 `SS_SC_NNN`, 컴포넌트 `SS_CO_NNN`, 테이블 `SS_TB_NNN`, 프로그램 `SS_DP_NNN`, 단위시험 `SS_UT_TS_NNN`, 통합시험 `SS_IT_TS_NNN`, 시스템시험 `SS_ST_NNN`.

## 6. 함정 / 주의 (작성 시 흔한 실수)
- **단위 = 전체 시스템 1개 표**: 서브시스템별로 쪼개지 않는다. 한 표에 전 사슬을 담는다.
- **3단 헤더 구조 유지**: 단계(분석/설계/구현/시험) → 산출물명 → 컬럼(ID + D). 헤더 단을 누락하면 어느 단계 산출물인지 식별 불가.
- **ID + D 짝 컬럼**: 각 산출물 ID 컬럼에는 우측에 이름/설명(`D`) 컬럼이 짝으로 붙는다. ID만 적고 D 컬럼 헤더를 빠뜨리지 않는다.
- **추적 단절 금지**: "단계별 연관관계가 끊어지지 않고 추적" 이 원칙. 한 행에서 중간 단계가 비면 사슬이 끊겨 추적성 상실.
- **시작점은 R1 요구사항 ID**: 사슬은 반드시 사용자 요구사항 정의서(R1) ID에서 출발한다. 유스케이스(R2)·화면·컴포넌트·테이블 등은 각 산출물에 실존하는 ID를 인용한다.
- **통합/시스템시험 둘 다 시나리오 ID**: 두 컬럼 모두 컬럼명이 "시나리오 ID" 로 동일하므로, 어느 결과서 소속인지는 헤더 산출물명으로만 구분된다 — 혼동 주의.

## 7. KLID 프로젝트 적용 메모
- 매핑 단절 셀은 만들지 않는 것이 원칙("끊어지지 않고 추적") — 불가피한 단절은 `-` + 사유를 부록으로 관리한다(KLID 컨벤션).
- KLID 추적 사슬: `RQ-SFR-NN-NN`(R1) → `KLID-AT-UC-NNN`(R2) → `KLID-AT-SC-NNN`(화면/UI) · `KLID-AT-CO-NNN`(컴포넌트) · `KLID-AT-TB-NNN`(테이블) → 프로그램 파일 ID → 단위시험 ID → 통합시험·시스템시험 시나리오 ID.
- CBD 사례의 `SS_SC/SS_CO/SS_TB/SS_DP/SS_UT_TS/SS_IT_TS/SS_ST` 컬럼은 KLID 전체형 `KLID-AT-XX-NNN` 으로 매핑한다(SC=화면, CO=컴포넌트, TB=테이블 등).
- 분석 단계 시작점(R1 요구사항·R2 유스케이스)은 ID + 명칭을 병기하고, 설계 이후 단계는 ID 위주로 채우되 LogiCraft 그래프 추적성을 위해 가능하면 D(이름) 컬럼도 채운다.
- 단계명=`분석` 고정(추적표 자체의 작성 단계).
