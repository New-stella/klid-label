# R2 유스케이스 명세서 (CBD 표준 산출물 위키)
> 출처: NIA CBD SW개발 표준 산출물 관리 가이드(2011.12) docs/CBD.pdf 인쇄면 p.11~16 (작성 사례 p.17~22)

## 1. 작성 목적
> PDF 원문 [작성 목적]

시스템의 요구사항에 대하여 액터와 시스템 활동 및 상호간의 활동에 대하여 순서화된 시나리오를 상세하게 기술하고, 유스케이스의 이름, 액터, 그들 간의 연관관계를 보여주는 시스템 환경을 다이어그램으로도 표현한다. 또한 주요한 유스케이스에 대하여 대상 시스템과 액터 간의 오퍼레이션을 상세하게 표시하는 **시스템 시퀀스 다이어그램 및 오퍼레이션의 약정**을 나타낼 수 있는데, 이 부분은 **필수 산출물에 포함되지 않으며 선택적으로 작성**할 수 있다.

## 2. 작성 방법
> PDF 원문 [작성 방법] 전문

유스케이스는 시나리오를 구체적인 언어표현으로 기술하고, 유스케이스 다이어그램은 그림으로 작성하며 작성도구를 사용할 수 있다.

### 3.2 헤더 박스 구조
산출물 코드 `R2` 라벨 + 제목 `유스케이스 명세서` + (시스템명 / 서브시스템명 / 단계명=`분석` / 작성일자 / 버전).

### 3.3 본문 구성 (5개 구성요소)

**① 서브시스템 목록** — 전체 시스템에 대하여 **한 개의 표**로 작성

| 서브시스템 ID | 서브시스템명 | 서브시스템 설명 |
|---|---|---|

- 서브시스템 ID: 서브시스템별 유일 ID / 서브시스템명: 이름 / 서브시스템 설명: 간략 설명

**② 유스케이스 다이어그램(UCD)** — 서브시스템별 작성. 헤더 박스 + 다이어그램(그림)

| UCD ID | (값) | UCD 명 | (값) |
|---|---|---|---|
| 관련 서브시스템 ID | (값) | 관련 서브시스템명 | (값) |

- 박스 아래에 **유스케이스 다이어그램(그림)** 을 그린다.
- 다이어그램은 **액터(좌우 배치) + 유스케이스(타원, 타원 안에 `UCD ID-NN.유스케이스명` 표기) + 연관관계 선** 을 표현한다.

**③ 유스케이스 목록** — 서브시스템별 작성

| 유스케이스 ID | 유스케이스명 | 유스케이스 설명 | 관련액터 ID | 관련 UCD ID | 관련 요구사항 ID |
|---|---|---|---|---|---|

- 유스케이스 ID / 유스케이스명 / 유스케이스 설명(간략)
- 관련액터 ID: 관련 액터 ID (복수 가능, 줄바꿈 나열)
- 관련 UCD ID: 소속 UCD ID
- 관련 요구사항 ID: **"사용자 요구사항 정의서(R1)"의 관련 요구사항 ID**

**④ 액터 목록** — 서브시스템별 작성

| 액터 ID | 액터명 | 액터유형 (주요/보조/숨은) | 액터설명 |
|---|---|---|---|

- 액터 ID: 액터별 유일 ID / 액터명: 이름 / 액터유형: 주요·보조·숨은 중 택1 / 액터설명: 간략 설명

**⑤ 유스케이스 기술서** — 유스케이스별 작성. 헤더(유스케이스ID / 유스케이스명) + 본문 8항목

| 유스케이스ID | (값) | 유스케이스명 | (값) |
|---|---|---|---|

본문 8항목 (번호·순서 고정):
1. 주요 액터
2. 이해관계자와 관심사항
3. 전제조건
4. 종료조건
5. 기본 시나리오
6. 대안 시나리오
7. 구현 시 고려 사항
8. 발생 빈도

### 3.4 (선택) 시스템 시퀀스 다이어그램 / 오퍼레이션 약정
필수 산출물 아님. 주요 유스케이스에 한해 선택적으로 작성 가능.

## 4. 항목 설명 (전 항목 — 누락 금지)
> PDF [항목 설명] 전 항목

### ■ 서브시스템 목록 (전체 시스템에 대하여 한 개의 표로 작성)
- **서브시스템 ID**: 서브시스템별로 유일한 ID를 부여하여 기입한다.
- **서브시스템명**: 서브시스템의 이름을 기입한다.
- **서브시스템 설명**: 서브시스템에 대한 설명을 간략하게 기입한다.

### ■ 유스케이스 다이어그램(UCD) (서브시스템별로 작성)
- **UCD ID**: 유스케이스 다이어그램별로 유일한 ID를 부여하여 기입한다.
- **UCD 명**: 유스케이스 다이어그램의 이름을 기입한다.
- **관련 서브시스템 ID**: 유스케이스 다이어그램이 속하는 서브시스템 ID를 기입한다.
- **관련 서브시스템명**: 유스케이스 다이어그램이 속하는 서브시스템명을 기입한다. (※ 원문 항목명이 "관련 서브시스템 ID"로 중복 표기되어 있으나, 양식 표상 두 번째 칸은 **관련 서브시스템명**이다.)

### ■ 유스케이스 목록 (서브시스템별로 작성)
- **유스케이스 ID**: 유스케이스별로 유일한 ID를 부여하여 기입한다.
- **유스케이스명**: 유스케이스의 이름을 기입한다.
- **유스케이스 설명**: 유스케이스에 대한 설명을 간략히 기입한다.
- **관련액터 ID**: 관련된 액터 ID를 기입한다.
- **관련UCD ID**: 관련된 UCD ID를 기입한다.
- **관련요구사항 ID**: "사용자 요구사항 정의서"의 관련된 요구사항 ID를 기입한다.

### ■ 액터 목록 (서브시스템별로 작성)
- **액터 ID**: 액터별로 유일한 ID를 부여하여 기입한다.
- **액터명**: 액터의 이름을 기입한다.
- **액터 유형**:
  - 가) **주요 액터**: 서비스를 사용하여 사용자의 목적을 수행하는 액터
  - 나) **보조 액터**: 서비스를 지원하는 액터, 주로 컴퓨터 시스템이지만 조직이나 사람일 수도 있다. 예) CD기
  - 다) **숨은 액터**: 주요 액터나 보조 액터도 아니지만 유스케이스의 행위에서 이해관계를 가진다. 예) 세무서
- **액터설명**: 액터에 대한 설명을 간략히 기입한다.

### ■ 유스케이스 기술서 (유스케이스별로 작성)
- **유스케이스ID**: 유스케이스 ID를 기입한다.
- **유스케이스명**: 유스케이스 이름을 기입한다.
- **주요 액터**: 목적을 수행하는 시스템의 서비스를 호출하는 주된 액터를 기술한다.
- **이해관계자와 관심사항**: 유스케이스 내에 있어야 하는 사람, 조직, 컴퓨터 시스템들과 이들이 시스템에 대하여 요구하는 사항을 기술한다.
- **전제조건**: 시나리오가 유스케이스에서 시작되기 전에 항상 참이어야 하는 조건을 기술한다.
- **종료조건**: 유스케이스의 주요 성공 시나리오나 다른 대안 경로의 성공적인 완료 후에 참이어야 하는 조건을 기술한다.
- **기본 시나리오**: 이해관계자의 관심사항을 충족시키는 일반적인 성공 경로를 기술한다.
- **대안 시나리오**: 성공과 실패의 경우에 관한 모든 시나리오나 분기를 기술한다. 주요 성공 시나리오 항목보다 확장 항목이 더 길고 복잡한 경우가 대부분이다.
- **구현 시 고려사항**: 비기능적 요구사항, 품질 속성, 설계 제약사항들이 유스케이스와 관련되면 기술한다. 어떤 기능에 대하여 구현하는 기술적 변화가 있을 경우, 데이터구조의 변화가능성 등도 기재한다.
- **발생 빈도**: 유스케이스가 발생하는 빈도 유형을 기술한다.

## 5. 작성 사례 요점

- **서브시스템 목록**: `SS_TOT_010` 총액결제관리 "총액을 결제하는 업무를 총괄하는 시스템" / `SS_MIX_020` 혼합형결제관리 "혼합형 결제 업무를 총괄하는 시스템".
- **UCD**: UCD ID=`SS_UCD_010`, UCD명=`총액결제시스템`, 관련 서브시스템 ID=`SS_TOT_010`, 관련 서브시스템명=`총액결제관리`. 다이어그램은 액터(원화자금이체책임자·원화자금이체담당자 좌측, 주전산기 우측) + 타원 유스케이스 6개(`SS_UCD_010-01.원화자금이체신청` … `SS_UCD_010-06.지정시점예약자금이체거래현황조회`).
- **유스케이스 목록**: `SS_UCD_010-01` 원화자금이체신청 / `SS_UCD_010-02` 수취인지정자금이체신청 / `SS_UCD_010-03` 미결제지정시점예약자금이체취소신청. 관련액터 ID 복수(`SS_AC_010`, `SS_AC_020`, `SS_AC_030`), 관련 UCD ID=`SS_UCD_010`, 관련 요구사항 ID=`SS_RF01001`/`SS_RF01002`.
- **액터 목록**: `SS_AC_010` 주전산기(**보조**) "실제 거래를 발생시키고 회계 처리하는 시스템" / `SS_AC_020` 원화자금이체책임자(**주요**) / `SS_AC_030` 원화자금이체담당자(**주요**) / `SS_AC_040` 증권대금이체책임자(주요) / `SS_AC_050` 증권대금이체담당자(주요).
- **유스케이스 기술서 사례**: 유스케이스ID=`SS_UC_010-03`, 유스케이스명=`미결제 지정시점 예약자금이체 취소 신청`.
  - 주요 액터: 주전산기, 원화자금이체책임자, 원화자금이체담당자.
  - 이해관계자와 관심사항: "한 화면에서 처리하기를 원한다", 입력 항목 1)~8) 나열(신청기관 계정 개설처 … 의뢰기관).
  - 전제조건: "원화자금이체 담당자가 시스템에 Login 하고 있어야 한다."
  - 종료조건: "이체 취소 신청 자료는 저장된다. 시스템은 (입금완료, 입금대기, 지정시점입금예약) 처리가 완료되었음을 알린다 … 수취기관앞으로 취소내역을 통보한다."
  - 기본 시나리오: 번호 단계 "1) 원화자금이체담당자는 자금이체 취소 신청을 선택하고 … 2) 시스템은 입력화면을 출력한다 … 7) 본 유스케이스는 종료한다."
  - 대안 시나리오: "가. 취소 신청" 서브흐름 + "가) 현단말기에서 승인요청 흐름 / 나) 책임자 단말기에서 승인요청 흐름" 분기.
  - 구현 시 고려사항: "가능한 많은 건수를 입력할 수 있도록 전산시스템 구성", "수취기관 담당자 변경 정보를 real time 으로 어떻게 일치시킬 것인가?", "원격 처리 시 Network 장애 처리 및 책임 소재 명확화 문제" 등.

## 6. 함정 / 주의 (작성 시 흔한 실수)
- **반복 단위 혼동**: 서브시스템 목록은 전체 시스템 **1개 표**, UCD·유스케이스 목록·액터 목록·기술서는 **서브시스템별(또는 유스케이스별) 반복**. 단위를 섞지 않는다.
- **유스케이스 ID 표기 불일치**: 작성 사례에서 유스케이스 목록은 `SS_UCD_010-NN` 표기, 기술서 헤더는 `SS_UC_010-NN` 표기로 prefix 가 다르다. 같은 유스케이스를 가리키더라도 양식 위치에 따른 표기 차이가 있으니 프로젝트 내 표기 규칙을 사전 통일할 것. (PDF 사례 자체가 두 표기를 혼용)
- **액터유형 3값 고정**: 주요 / 보조 / 숨은 만 허용. 보조=주로 시스템(예 CD기), 숨은=이해관계만 가짐(예 세무서)의 구분을 정확히.
- **관련 요구사항 ID는 R1 실존 ID만**: 유스케이스 목록의 "관련 요구사항 ID"는 사용자 요구사항 정의서에 실재하는 ID여야 한다 (추적표 R3의 사슬 시작점).
- **기술서 8항목 누락 금지**: 1~8 항목은 빈 항목이라도 항목 자체를 생략하지 않는다. 특히 5(기본)·6(대안) 시나리오는 번호 단계/서브흐름 형식 유지.
- **시퀀스 다이어그램·오퍼레이션 약정은 선택**: 필수 산출물 아님. 누락해도 표준 위반 아님(설계 단계 D1 시퀀스도와 별개).
- **UCD 박스 두 번째 항목명 오기**: 원문 항목 설명에 "관련 서브시스템 ID"가 두 번 적혀 있으나 양식 표 두 번째 칸은 **관련 서브시스템명**이다.
- **UCD(PlantUML) 타원 라벨 = 실제 유스케이스 ID**(`KLID-AT-UC-NNN.유스케이스명`). ❌ 다이어그램-로컬 순번(`UCD-001-NN`)을 라벨로 쓰지 말 것 — 유스케이스 목록 ↔ 다이어그램 ID가 추적 일치해야 한다.

## 7. KLID 프로젝트 적용 메모
- 시스템 시퀀스 다이어그램·오퍼레이션 약정은 **선택**(필수 아님 — 설계 단계 D1 시퀀스도와 별개)이므로 KLID는 핵심 유스케이스에 한해 선택적으로만 작성한다.
- KLID는 UC ↔ 컴포넌트(D3 CO)·클래스도(D1 DCD) 1:1 도출 기준의 출발점으로 R2를 사용한다.
- 유스케이스 목록의 "관련 요구사항 ID"는 **R1 실존 ID(`RQ-SFR-NN-NN`/`NFR-NNN`)만** 인용한다.
- KLID 유스케이스 식별자는 전체형 `KLID-AT-UC-NNN` 을 사용한다 (CBD 사례 `SS_UCD_010-NN`/`SS_UC_010-NN` 에 대응). UCD·액터도 동일 전체형 체계로 `KLID-AT-UCD-NNN`, `KLID-AT-AC-NNN` 식으로 부여한다.
- KLID 액터 예: WORKER(라벨링 작업자, 주요) / REVIEWER(검수자, 주요) / PORTAL_USER(포털 회원, 주요) + 외부 시스템(관제서버·비식별 서버·VLM·ai-server 등)은 **보조 액터**, 데이터마트 등 이해관계만 갖는 외부는 **숨은 액터** 로 분류한다(역할 정의 표 기준).
