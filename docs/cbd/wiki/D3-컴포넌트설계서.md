# D3 컴포넌트 설계서

> 출처: CBD.pdf §III.2.3 (문서 p37~44)

## 양식 구조

1. **컴포넌트 구조도** (유스케이스별 작성): 헤더 | 컴포넌트 ID | 컴포넌트명 | 관련 유스케이스 ID | + 다이어그램 (사례: 컴포넌트 간 의존관계를 **Layer(Biz Logic, Integration)로 구분**하여 표시)
2. **컴포넌트 목록**: | 컴포넌트ID | 컴포넌트명 | 개요 | 관련 유스케이스 ID |
3. **컴포넌트 명세** (컴포넌트별 작성): 헤더(컴포넌트 ID/명) + 컴포넌트 개요 +
   - 내부 클래스: | ID | 클래스명 | 설명 |
   - 인터페이스 클래스: | ID | 인터페이스명 | 오퍼레이션명 | 구분(Serviced/Required) |
4. **인터페이스 명세** (인터페이스별 × 오퍼레이션 개수만큼 작성): | 인터페이스 ID | 인터페이스명 | 오퍼레이션명 | 오퍼레이션 개요 | 사전조건 | 사후조건 | 파라미터 | 반환값 |

## 작성 목적 (원문)
설계 클래스 모형에서 도출한 클래스들을 **C&V(공통성과 변경성) 기준에 따라 그룹핑하여 컴포넌트를 식별**하여 패키지도를 작성하고 식별한 컴포넌트의 내부 클래스 및 인터페이스의 명세를 기술한다.

## 작성 방법 (원문)
클래스를 그룹핑하여 도출한 컴포넌트의 패키지도를 작성하고, 식별한 컴포넌트의 목록을 작성한다. 또한 각각의 컴포넌트에 포함하고 있는 내부 클래스들을 명세하고, 인터페이스는 사용자에게 제공하는 오퍼레이션별로 상세한 명세를 작성한다.

## 항목 설명 (원문 요지)

- **컴포넌트 구조도** — *유스케이스별로 작성한다*: 컴포넌트 ID(유일)/명, 관련 유스케이스 ID.
- **컴포넌트 목록** — *유스케이스별로 작성한다*: ID/명/개요(간략 설명)/관련 유스케이스 ID.
- **컴포넌트 명세** — *컴포넌트별로 작성한다*:
  - 내부 클래스 ID: 컴포넌트에 속한 내부 클래스별 유일 ID. **(이 ID는 설계 클래스 ID와 일관성을 가져야 한다.)**
  - 내부 클래스명/설명
  - 인터페이스 클래스 ID/인터페이스명/오퍼레이션명
  - **구분**: 서비스를 제공하는 오퍼레이션(**Serviced**)과 서비스를 요청하는 오퍼레이션(**Required**)으로 구분
- **인터페이스 명세** — *인터페이스별로 오퍼레이션 개수만큼 작성한다*: 인터페이스 ID(컴포넌트의 인터페이스별 유일)/명, 오퍼레이션명/개요(제공·요청 서비스의 기능·역할), 사전조건(작동 전 항상 참), 사후조건(작동 후 항상 참), 파라미터, 반환값(있는 경우).

## 작성 사례 요점
- 구조도: `SS_CO_010 | 총액결제시스템 | SS_UC_010` — Layer(Biz Logic / Integration) 박스로 구분된 컴포넌트 의존도.
- 목록: `SS_CO_010 원화자금이체 | … | SS_UC_010-01`.
- 명세: 내부 클래스 `SS_IC_010 Cteba001SBBean`, `SS_DC_010 TransManager`(설계 클래스 ID 재사용 — 일관성), 인터페이스 클래스 `SS_IC_030 HS_IF11110 | getEventList | Serviced`.
- 인터페이스 명세: `SS_IC_030 | HS_IF11110 | requestAfterSave | … | 사전조건: transmanager 컴포넌트가 기동 중 | 파라미터: reqDTO: org.bok.wire.dto.common.DocDTO …`.

## 주의 / KLID 적용
- **내부 클래스 ID ↔ D1 설계 클래스 ID 일관성**이 명문 규칙.
- 반복 단위: 구조도 = 컴포넌트(UC)별 1개씩, 명세 = 컴포넌트별, 인터페이스 명세 = **오퍼레이션 1건당 1블록**.
- KLID: UC ↔ CO 1:1 도출, CO 번호 = UC 번호 정렬(결번 유지), 공통 클래스는 동일 IC ID 교차 참조. 구조도 Layer는 Presentation/Biz Logic/Persistence/Integration 구분 + 액터·외부 시스템은 외부 박스.
