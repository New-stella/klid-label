## 1. 작성 목적 (PDF 원문)

> 설계 클래스 모형에서 도출한 클래스들을 **C&V(공통성과 변경성) 기준에 따라 그룹핑하여 컴포넌트를 식별**하여 패키지도를 작성하고 식별한 컴포넌트의 내부 클래스 및 인터페이스의 명세를 기술한다.

## 2. 작성 방법 (PDF 원문)

> 클래스를 그룹핑하여 도출한 컴포넌트의 **패키지도**를 작성하고, 식별한 컴포넌트의 **목록**을 작성한다. 또한 각각의 컴포넌트에 포함하고 있는 **내부 클래스들을 명세**하고, **인터페이스는 사용자에게 제공하는 오퍼레이션별로** 상세한 명세를 작성한다.

> ※ **시스템을 구성하는 컴포넌트간의 의존관계(dependency)를 Layer(Biz Logic, Integration)로 구분하여 표시한다.**

이 캡션과 그림은 구조도가 **"시스템(=해당 유스케이스 범위)을 구성하는 컴포넌트 박스들 사이의 의존관계"** 를 Layer로 묶어 표현하는 패키지/컴포넌트 다이어그램임을 명확히 한다. **컴포넌트 한 개의 내부 클래스 분해도가 아니다.** (상세 그림 관찰은 §5)

## 4. 항목 설명 (전 항목 — PDF 원문 전수)

### 4.1 컴포넌트 구조도 — *유스케이스별로 작성한다*

- **컴포넌트 ID**: 컴포넌트별로 유일한 ID를 부여하여 기입한다.
- **컴포넌트명**: 컴포넌트 이름을 부여하여 기입한다.
- **관련 유스케이스 ID**: 본 산출물이 관련되는 "유스케이스 명세서"의 유스케이스 ID를 기입한다.

### 4.2 컴포넌트 목록 — *유스케이스별로 작성한다*

- **컴포넌트 ID**: 컴포넌트 ID를 기입한다.
- **컴포넌트명**: 컴포넌트 이름을 기입한다.
- **개요**: 컴포넌트에 대한 설명을 간략히 기입한다.
- **관련 유스케이스 ID**: 본 산출물이 관련되는 "유스케이스 명세서"의 유스케이스 ID를 기입한다.

### 4.3 컴포넌트 명세 — *컴포넌트별로 작성한다*

- **컴포넌트 ID**: 컴포넌트 ID를 기입한다.
- **컴포넌트명**: 컴포넌트 이름을 기입한다.
- **컴포넌트 개요**: 컴포넌트에 대한 설명을 간략히 기입한다.
- **내부 클래스 ID**: 컴포넌트에 속한 내부 클래스별로 유일한 ID를 기입한다. **(이 ID는 설계 클래스 ID와 일관성을 가져야 한다.)**
- **내부 클래스명**: 컴포넌트에 속한 내부 클래스의 명칭을 기입한다.
- **내부 클래스 설명**: 컴포넌트에 속한 내부 클래스에 대한 설명을 간략하게 기입한다.
- **인터페이스 클래스 ID**: 컴포넌트에 속한 인터페이스 클래스별로 유일한 ID를 기입한다.
- **인터페이스명**: 컴포넌트에 속한 인터페이스의 명칭을 기입한다.
- **오퍼레이션명**: 인터페이스에 속한 오퍼레이션명을 기술한다.
- **구분**: 인터페이스의 오퍼레이션에 대한 **서비스를 제공하는 오퍼레이션(Serviced)** 과 **서비스를 요청하는 오퍼레이션(Required)** 으로 구분하여 기술한다.

### 4.4 인터페이스 명세 — *인터페이스별로 오퍼레이션 개수만큼 작성한다*

- **인터페이스 ID**: 컴포넌트의 인터페이스별로 유일한 ID를 부여하여 기입한다.
- **인터페이스명**: 컴포넌트의 인터페이스별 이름을 부여하여 기입한다.
- **오퍼레이션명**: 인터페이스에 속한 오퍼레이션명을 기술한다.
- **오퍼레이션 개요**: 오퍼레이션이 제공하는 또는 요청하는 서비스의 기능 및 역할을 간략하게 기술한다.
- **사전조건**: 오퍼레이션이 작동하기 전에 항상 참이어야 하는 조건을 기술한다.
- **사후조건**: 오퍼레이션이 작동한 후에 항상 참이어야 하는 조건을 기술한다.
- **파라미터**: 오퍼레이션이 가지는 파라미터를 기술한다.
- **반환값**: 오퍼레이션이 작동 후 제공하는 반환값이 있는 경우 그 값을 기술한다.

## 5. 작성 사례 요점 (PDF 사례 그림·표에서 관찰되는 실제 구조)

PDF 사례는 한국은행 BOK-Wire+ 류 "총액결제시스템" 예시다.

### 5.1 컴포넌트 구조도 그림 (PDF p.50) — 실제로 그려진 것

- **헤더**: `컴포넌트 ID = SS_CO_010` / `컴포넌트명 = 총액결제시스템` / `관련 유스케이스 ID = SS_UC_010`.
- **그림 안에 그려진 것 = 컴포넌트 박스들(UML «component» 아이콘)** 이며, 클래스 박스가 아니다.
- **레이어 구성 (관찰)**:
  - 상단의 큰 **"Biz Logic" 레이어 박스** 하나 — 그 안에 다수의 컴포넌트 박스가 들어 있다.
    - 좌측: 이름 표기가 흐려 식별이 어려운 컴포넌트 박스들이 격자(예: `SS_CO_0xx` 류)로 다수 배치됨(PDF 사례 그림상 ID 라벨로 보이나 해상도상 정확 판독 불가 — 확인 필요).
    - 중앙·우측: 명명된 컴포넌트 박스 — `transmanager`, `terminalmanager`, `usermanager`, `apormanager`(판독 불명확), `otpmanager`, `rolemanager` 등(좌열) 및 `messagemanager`, `publishmanager`, `ptzmmanager`(판독 불명확), `codemanager`, `hostmanager`, `logmanager` 등(우열).
  - 하단의 별도 **"Integration" 레이어 박스** — 그 안에 `hostsystem`, `terminalsystem` 컴포넌트 박스(외부 연동 대상)가 들어 있다.
  - 레이어 라벨로 "Biz Logic"과 "Integration"이 그림 내 텍스트로 표기되어 있다(양식 캡션이 명시한 두 Layer와 일치). (양식 캡션은 Biz Logic·Integration 2개만 명시; Presentation/Persistence 레이어는 사례 그림에 보이지 않음.)
- **화살표(의존)**: 컴포넌트 박스 ↔ 컴포넌트 박스 간 **점선 의존(dependency) 화살표**가 다수 연결되어 있다. 좌측/중앙 Biz Logic 컴포넌트들이 우측 manager 컴포넌트 및 하단 Integration 컴포넌트(hostsystem/terminalsystem)로 의존 화살표를 그린다. → 즉 **의존 화살표의 대상은 다른 "컴포넌트 박스"** 다(클래스가 아님).
- **캡션 원문**: "시스템을 구성하는 컴포넌트간의 의존관계(dependency)를 Layer(Biz Logic, Integration)로 구분하여 표시한다."

## 6. 함정 / 주의

### 6.1 ★★ 컴포넌트 구조도 대상 확정 (해석 A 확정 — 표준 근거)

> **최종 판정: 해석 A.** 구조도는 **시스템(해당 유스케이스 범위)을 구성하는 컴포넌트 박스들 간의 의존관계(dependency)를 Layer(Biz Logic, Integration)로 묶어 표시**한다.

근거(모두 PDF 원문):
1. **양식·사례 캡션 원문** (PDF p.50): "시스템을 구성하는 **컴포넌트간의 의존관계(dependency)**를 Layer(Biz Logic, Integration)로 구분하여 표시한다." → 화살표의 양끝이 **컴포넌트**다.
2. **그림에 그려진 박스 = 컴포넌트(«component») 박스**다. 클래스 박스가 아니다(클래스 분해는 「3. 컴포넌트 명세」의 *내부 클래스 표*가 담당).
3. **작성 목적·방법 원문**: 구조도는 "**패키지도**(컴포넌트의 패키지도)"이며, "각 컴포넌트의 **내부 클래스**는 [구조도가 아니라] **명세**에서 기술"한다고 명시.

> ❌ 오해(해석 B) = "컴포넌트별로 1장씩, 그 컴포넌트의 내부 클래스를 Layer별로 그린다"는 **표준 위반**이다. 내부 클래스는 구조도가 아니라 「3. 컴포넌트 명세 → 내부 클래스 표」에 텍스트로 들어간다.
>
> ⚠️ 단, 구조도의 **헤더 칸(컴포넌트 ID/명)** 은 컴포넌트 단위로 적게 되어 있어 "컴포넌트별 1장"으로 오인되기 쉽다. 항목 설명은 구조도를 **"유스케이스별로 작성"** 이라 규정하므로, 반복 단위는 **유스케이스**다(§6.2).

### 6.2 반복 단위 (산출물 4종 각각 다름)

| 산출물 | 반복 단위 (PDF 원문) |
|--------|----------------------|
| 1. 컴포넌트 구조도 | **유스케이스별로 작성** (시스템/유스케이스 범위 1장에 컴포넌트 다수 + 의존) |
| 2. 컴포넌트 목록 | **유스케이스별로 작성** |
| 3. 컴포넌트 명세 | **컴포넌트별로 작성** |
| 4. 인터페이스 명세 | **인터페이스별로 오퍼레이션 개수만큼 작성** (오퍼레이션 1건 = 1블록) |

### 6.3 IC/DC ID 일관성 (명문 규칙)

- 「컴포넌트 명세」의 **내부 클래스 ID는 D1(설계 클래스) ID와 일관성을 가져야 한다** — PDF 항목 설명 명문.
- 사례에서 `SS_DC_010 TransManager`처럼 설계 클래스 ID(`*_DC_*`)를 그대로 재사용한다.
- 같은 인터페이스 클래스 ID(예 `SS_IC_030`/`HS_IF11110`)는 「컴포넌트 명세」의 인터페이스 클래스 표와 「인터페이스 명세」 블록에서 **동일하게 교차 참조**되어야 한다(사례 일치 확인).

### 6.4 구분(Serviced/Required) 누락 주의

- 인터페이스 클래스 표의 모든 오퍼레이션에 **구분(Serviced=제공 / Required=요청)** 을 표기해야 한다. 외부에 제공하는 오퍼레이션과 외부 서비스를 호출(요청)하는 오퍼레이션을 구분한다.

### 6.5 칼럼 헤더 표기 흔들림

- 내부 클래스 칼럼은 빈 양식에서 "설명", 작성 사례에서 "비고"로 표기된다 — **동일 칼럼**이며 내부 클래스 설명을 적는다.

## 7. KLID 프로젝트 적용 메모

> 아래는 기존 KLID 적응을 보존·정리한 것이다. PDF 표준(§1~6)을 KLID 학습데이터 저작도구(Spring Boot, `kr.co.cudo.authoring`)에 맞춰 ID 체계·도출 규칙을 매핑한다.

### 7.1 ID 체계

- 시스템 접두를 `KLID-AT`로 둔다.
- 컴포넌트 ID: **`KLID-AT-CO-NNN`** (구조도/목록/명세 공통).
- 내부 클래스 ID: **`KLID-AT-DC-NNN`** (설계 클래스 = D1 설계 클래스 ID 재사용 — §6.3 일관성 규칙 준수).
- 인터페이스 클래스 ID: **`KLID-AT-IC-NNN`**.
- 유스케이스 ID는 D-단계 UC 산출물의 `KLID-AT-UC-NNN` 정렬을 따른다.

### 7.2 UC ↔ CO 1:1 도출

- KLID는 **유스케이스 1건 ↔ 컴포넌트 1건을 1:1로 도출**한다.
- CO 번호는 대응 UC 번호와 정렬(010↔010 …)하고, **결번을 유지**(중간 UC 폐지 시 빈 번호 채우지 않음)하여 UC↔CO 추적성을 보존한다(PDF 사례의 010/020/030 정렬 패턴과 동일 컨벤션).

### 7.3 common 클래스 비식별 (컴포넌트 미귀속)

- 여러 컴포넌트가 공유하는 `common.*`(예: `ApiResponse`, `ErrorCode`, `CustomException`, `JwtAuthenticationFilter`, 듀얼 데이터소스 설정, 로깅 필터 등)은 **특정 컴포넌트의 내부 클래스로 식별(비식별 처리)하지 않는다.** 컴포넌트 명세의 내부 클래스 표에 공통 인프라 클래스를 중복 나열하지 않고, 도메인 고유 클래스만 귀속시킨다.
- 단, 두 컴포넌트가 동일 공통 인터페이스를 사용할 경우 **동일 IC ID를 교차 참조**한다(§6.3).

### 7.4 외부 클라이언트 = 인터페이스 클래스

- 외부 시스템 연동 클라이언트(`DeidentifyClient`, `AiServerClient`, `VlmClient`, `ControlNotifyClient`, `ExternalAugmentClient`)는 **인터페이스 클래스(IC)** 로 식별한다.
- 이들 오퍼레이션의 **구분(§4.3)은 Required**(외부 서비스를 요청·호출)다. 반대로 저작도구가 관제서버 조회용으로 제공하는 API 오퍼레이션은 **Serviced**.
- 구조도(§6.1·해석 A)에서는 이 외부 클라이언트가 향하는 외부 시스템(비식별 서버 / ai-server / VLM / 관제서버)을 **Integration Layer 박스**로 두고, Biz Logic 컴포넌트 → Integration 컴포넌트로 의존 화살표를 그린다(PDF 사례의 hostsystem/terminalsystem 배치와 동형).

### 7.5 구조도 Layer 매핑(KLID)

- PDF 양식 캡션이 명시한 Layer는 **Biz Logic / Integration** 2종이다. KLID 구조도는 이 표준 2-Layer 골격을 따르되, 필요 시 표준 본문(설계 일반)에서 통용되는 Presentation/Persistence를 보조 레이어로 추가할 수 있다 — 단 PDF **D3 사례 그림에는 Biz Logic·Integration 2개만 등장**했으므로(확인됨), 표준 충실도를 위해 2-Layer를 기준으로 삼고 추가 레이어는 KLID 자체 결정임을 명시한다.
- 액터·외부 시스템은 Integration Layer의 외부 박스로 표현한다.
