# D11 단위시험 케이스 (CBD 표준 산출물 위키)

> 출처: docs/CBD.pdf 인쇄면 p.101~104 (§III 3.2.11 단위시험 케이스)

---

## 1. 작성 목적 (PDF 원문)

> 단위 프로그램 및 컴포넌트를 설계한 개발자가 컴포넌트 명세서에 정의된 바와 같이 설계한 컴포넌트 프로그램의 오류를 검출할 목적으로 배포하는 컴포넌트 단위로 시험하기 위한 시험 설계를 기술한다.

- 작성 주체: **컴포넌트를 설계한 개발자**.
- 기준 문서: **컴포넌트 명세서**(D3 컴포넌트 설계서)에 정의된 명세.
- 목적: 설계한 컴포넌트 프로그램의 **오류 검출**. 배포 단위인 **컴포넌트 단위**로 시험 설계.

## 2. 작성 방법 (PDF 원문)

> 개발자가 설계한 컴포넌트 단위로 작성하며 컴포넌트별 시험케이스를 작성한다.

- 작성 단위: **컴포넌트 단위**. 컴포넌트마다 단위시험 블록 1개.
- 한 컴포넌트 블록 안에 **다수 시험케이스(케이스ID별 행)** 작성 — 정상/예외 케이스 분리 권장(사례 참조).

## 4. 항목 설명 (PDF 원문 전 항목 — 누락 금지)

- **단위시험 ID**: 단위 컴포넌트(프로그램)별 유일한 ID를 부여하여 기입한다.
- **설명**: 단위 컴포넌트(프로그램)에 대한 간략한 설명을 기입한다.
- **관련 컴포넌트 ID**: 본 산출물이 관련되는 "컴포넌트 설계서"의 컴포넌트 ID를 기술한다.
- **관련 프로그램 ID**: 본 산출물이 관련되는 프로그램 ID를 기술한다.
- **케이스 ID**: 단위 컴포넌트(프로그램)에 수행할 시험 케이스별 식별자를 부여하여 기술한다.
- **케이스명**: 시험 케이스의 명칭을 기입한다.
- **작업권한**: 적용하는 사용자 권한을 표기한다.
- **시험 데이터**: 해당 시험 케이스를 실행하는데 필요한 시험 데이터를 기술한다. (실제 데이터 값이 아닐 경우는 **조건을 표시**할 수 있다.)
- **시험항목 및 처리절차**: 시험 데이터를 입력하여 시험하는 단계와 단계별 처리 절차 및 방법을 기술한다.
- **시험결과**: 설계단계에서는 기술하지 않으며, **시험결과서로 활용될 경우** 실제 시험을 수행한 결과를 기술한다.
- ⚠ **예상결과 및 검증방법**: 본 항목은 **항목 설명 목록에는 누락**되어 있으나 **산출물 양식·작성 사례 표에는 존재**하는 컬럼이다. 기대 결과 + 검증 수단(화면 표시 확인·SQL DB 확인 등)을 병기한다. (항목 설명 누락은 PDF 원문 상태 그대로 — 임의 보완하지 않음)

## 5. 작성 사례 요점 (PDF 인쇄면 p.103~104)

### 단위시험 블록 (헤더)
- 단위시험 ID: `KK_UT_TS_030`
- 설명: `커뮤니티사용자와 커뮤니티관리자가 업무 영역별 게시판에 게시물을 등록/수정/삭제/조회 한다. - 게시판, FAQ, Q&A 유형 모두 포함한다. - 장애예약자료, 장애중점개선사항, 고지사항, 전자게약FAQ …`
- 관련 컴포넌트 ID: `KK_CO_110`
- 관련 프로그램 ID: `UI.OSZBI.1.1.1`

### 케이스 표
- `TC_01_010 | 게시판목록 조회-일반 | 전체 | 게시물데이터(오늘, 이전일 데이터) | 1.메뉴에서 화면 선택 / 2.초기화면에 게시판목록 Display 확인: 오늘일자가 게시기간에 포함된 것… | 화면에 목록 디스플레이 + SQL로 DB확인 `SELECT * FROM 게시판 WHERE ~~` | (시험결과 공란)`
- `TC_01_020 | 게시판목록 조회-데이터없음 | 전체 | 데이터없음 | 1.메뉴에서 화면 선택 / 2.초기화면에 게시판목록 Display 확인 | 해당데이터 없음 메시지 표기 + SQL로 DB확인 `SELECT * FROM 게시판 WHERE ~~` | (시험결과 공란)`

### 패턴 정리
- **코드 체계(사례)**: 단위시험 ID `{prefix}_UT_TS_{nnn}` (UT = Unit Test), 케이스 ID `TC_{nn}_{nnn}`, 컴포넌트 ID `{prefix}_CO_{nnn}`, 프로그램 ID는 구현 식별자(`UI.OSZBI.1.1.1`).
- **정상/예외 케이스 분리**: `조회-일반`(정상) ↔ `조회-데이터없음`(예외)을 별도 케이스 ID로 분리.
- **검증방법 병기**: 화면 표시 확인 + DB 직접 확인(SQL)을 "예상결과 및 검증방법"에 함께 기술.

## 6. 함정 / 주의

- ★ **시험결과 컬럼은 설계단계 공란**: D11은 설계 산출물이므로 시험결과를 비워두고 "예상결과 및 검증방법"만 기재한다. 실제 결과는 **I2 단위시험 결과서**로 현행화 시 기입한다. (사슬: **D11 단위시험 케이스 → I2 단위시험 결과서**)
- ⚠ **「예상결과 및 검증방법」 컬럼 누락 주의**: 항목 설명에는 빠져 있으나 양식·사례 표에는 반드시 존재하는 컬럼. 작성 시 누락 금지 — 검증 수단(화면 확인/SQL 등)까지 명시.
- **컴포넌트 단위 = 단위시험 단위**: 통합시험(D10, 유스케이스 단위)과 추적 키가 다름. D11은 D3 컴포넌트 설계서의 컴포넌트 ID로 추적.
- **시험 데이터는 조건 표시 가능**: 실제 값이 없으면 조건(예: "오늘/이전일 데이터", "데이터없음")으로 표기.
- 관련 컴포넌트 ID / 관련 프로그램 ID는 임의 부여 금지 — 컴포넌트 설계서 실존 ID와 일치시켜야 함.

## 7. KLID 프로젝트 적용 메모

- **작업권한**: KLID 역할 코드 사용 — `REVIEWER` / `WORKER` / `PORTAL_USER`. (전체 공개 케이스는 "전체").
- **관련 컴포넌트 ID**: D3 컴포넌트 설계서 실존 ID(`KLID-AT-CO-NNN` / LogiCraft 컴포넌트)와 매핑.
- **관련 프로그램 ID**: KLID 구현 식별자(`KLID-AT-IC-NNN`) 또는 실제 구현 클래스명(예: `LabelService`, `BatchOrchestrator`, `DeidentifyStep`).
- **코드 체계(KLID 적응)**: 단위시험 ID `KLID-AT-UT-TS-NNN`, 케이스 ID `KLID-AT-UT-TC-NNN`(또는 `TC_NN_NNN` 사례 형식).
- **검증방법(KLID)**: 화면 표시 확인 + DB 확인은 PostgreSQL(`klid_at` 스키마, LS_* 테이블) SQL로 수행. 정상/예외/경계 케이스 분리 작성.
- **시험결과 현행화**: 설계단계 공란 → **I2 단위시험 결과서**에서 실제 결과 기입. KLID 실행 환경: **JUnit 5 + Testcontainers(PostgreSQL)**, 프론트는 Vitest/RTL 단위 테스트. 테스트 메서드명은 한글 서술형 컨벤션(`@DisplayName("본인_배정이_아닌_프레임_편집_시_403")`).
- **예외/보안 케이스 권장**(KLID): IDOR(본인 배정 외 프레임 편집 403), 권한 분기(REVIEWER 전용 관리 API), 비식별 미완료 시 원본 스트리밍 차단(NOT_FOUND) 등 보안·접근제어 단위 케이스를 명시적으로 포함.
