## 1 시험 대상 시스템

### 1.1 시스템 개요

본 도구(KLID-AT-SS-001, AI CCTV 학습데이터 저작도구)는 다음 3개 응용 시스템으로 구성된다.

- **Backend (Spring Boot 3.3 / Java 17)**: 31개 컨트롤러 + 36개 도메인 서비스 + 14개 컴포넌트
- **Frontend (React 18 / TypeScript / Vite)**: 26개 화면, INTERNAL/PORTAL 2채널 라우팅
- **AI Server (Python / FastAPI)**: YOLO/SAM2 추론 + VLM 객체 검증

본 시험 계획은 위 3개 시스템 + 6개 외부 인터페이스(D4 인터페이스설계서)에 대한 단위/통합/시스템/인수 시험을 포괄한다.

### 1.2 하드웨어 구성도

```text
[VPC]
├─ Web Tier (Nginx) ......... 2 vCPU / 4GB x N (정적 React 호스팅)
├─ App Tier (Spring Boot) ... 4 vCPU / 8GB (단일 서비스, REST + Webhook + Quartz 내장)
├─ (Quartz 내장) ............ 마킹→VLM(콜백)→비식별→프레임추출(마킹 위치)→YOLO(원본만)→SAM2→보간
├─ AI Tier (FastAPI + GPU) .. 8 vCPU / 32GB + GPU x 1+
├─ DB Tier (MariaDB) ........ 8 vCPU / 32GB (Primary + Replica)
├─ Object Storage ........... S3 호환 (원본/비식별/프레임/증강 prefix 분리)
├─ Gitea Server ............. 4 vCPU / 8GB (라벨 버전 저장)
└─ Observability ............ Prometheus + Grafana + Loki
```

### 1.3 응용 목표시스템 구성도

D5 2.1절 시스템 배포 토폴로지 PlantUML 참조.

## 2. 가정 또는 제약사항

- (가정) 외부 시스템(관제/포털/비식별/VLM/생성형AI/Gitea/내부 ai-server)은 시험 환경에서 가용하며, 시험 데이터로 응답 가능
- (가정) 시스템시험은 운영환경과 동일한 자원/네트워크에서 수행
- (가정) 본 도구는 자체 로그인이 없으므로 관제/포털서버 발급 JWT를 모사하는 `/v1/dev/tokens`(local/dev 한정)로 인증
- (제약) 외부 비식별솔루션/VLM/생성형AI는 분리발주 항목으로, 가용성 SLA 변동 시 본 도구 SLA에 영향 -- 본 도구는 폴백 큐로 데이터 유실 0건 보장만 책임
- (제약) GPU 자원 한계로 ai-server는 단일 인스턴스 GPU 1대 기준 처리량 산정 (수평 확장 시 비례 증가)
- (제약) 라벨 좌표 점은 1라벨당 1000점으로 상한 (CWE-770 DoS 방어)
- (범위) UC-014/UC-015(관제서버 통지)는 본 계획의 단위/통합/시스템 시험에 관제서버 통지 컴포넌트 4종(`ControlNotify*`) 및 외부 인터페이스 2건(KLID-AT-II-011/012)을 포함

## 3. 시험 전략

### 3.1 시험 범위

| 구분 | 시험 항목 |
|------|-----------|
| Backend | 컴포넌트 14종(KLID-AT-CO-001~014) 단위 시험, 외부 인터페이스 14건(KLID-AT-II-001~014) 통합 시험 |
| Frontend | 화면 26종(KLID-AT-SC-001~026) 컴포넌트 단위 시험(Vitest) + e2e(Playwright) |

| DB | 테이블/인덱스/제약 정합성 시험(Flyway 마이그레이션 단위) |
| 비기능 | 성능/부하/볼륨/보안/장애복구/관측성 시스템 시험(D7) |

### 3.2 개발 단계별 수행할 시험 종류

#### 3.2.1 단위시험

- **대상**: 개별 클래스/함수/컴포넌트 (Backend Service, Frontend Component, AI Server Endpoint)
- **도구**: JUnit 5 + Mockito + Spring Boot Test (Backend), Vitest + Testing Library (Frontend), pytest + httpx (AI Server)
- **수행**: 개발자(1차) → 프로젝트 시험팀(2차)
- **산출물**: 단위시험 케이스(D11) -- `KLID-AT-UT-NNN`, 단위시험 결과서(I2)
- **커버리지 목표**: 라인 80% 이상, 분기 70% 이상 (핵심 도메인 서비스 90%+)

#### 3.2.2 통합시험

- **대상**: 컴포넌트 간 연동 + 외부 시스템 모의 연동(WireMock/MockWebServer)
- **도구**: Testcontainers (MariaDB) + MockWebServer (외부 HTTP) + Spring Boot @SpringBootTest
- **수행**: 프로젝트 시험팀
- **산출물**: 통합시험 시나리오(D10) -- `KLID-IT-TS-NNN` / `KLID-IT-TC-NNN`, 통합시험 결과서(T1)
- **시나리오**: 14개 인터페이스 x 정상/4xx/5xx/타임아웃/CB Open/중복 콜백 시나리오

#### 3.2.3 시스템시험

- **대상**: 비기능 전반(성능/부하/볼륨/보안/장애복구/관측성)
- **도구**: k6 / JMeter (부하/성능), OWASP ZAP / Burp (보안), Chaos Mesh (장애 주입)
- **수행**: 프로젝트 시험팀
- **산출물**: 시스템시험 시나리오(D7) -- `KLID-ST-NNN`, 시스템시험 결과서(T2)

#### 3.2.4 인수시험

- **대상**: UC-001~UC-015 전체 시나리오를 발주처(KLID) 주도로 운영환경 동일 환경에서 검증
- **도구**: Cypress/Playwright 시나리오 자동화 + 수동 확인
- **수행**: 발주처 + 사업자 합동
- **산출물**: 인수시험 시나리오(T6), 인수시험 결과서(T7)

| 시험 종류 | 단위시험 | 통합시험 | 시스템시험 | 인수시험 |
|-----------|----------|----------|------------|----------|
| 대상 | 클래스/함수/컴포넌트 | 서브시스템 간 연동 | 전체 시스템 비기능 | 전체 시스템 기능/요구사항 |
| 목적 | 단위 정확성 | 인터페이스 정합성 | 성능/보안/장애복구 | 요구사항 만족도 |
| 테스터 | 개발자, 시험팀 | 시험팀 | 시험팀 | 발주처 + 시험팀 |
| 기준선 | 컴포넌트 명세(D3) | 인터페이스 설계(D4) | 아키텍처 요구사항(D5) | 유스케이스(R2) |
| 환경 | local / dev | dev | stg | stg → prd 시뮬레이션 |

### 4.2 발견된 문제점(결함)에 대한 수정 절차

1. 테스터: 결함 발견 시 결함 추적 시스템(Jira/Redmine 등)에 등록 -- 재현 절차/예상결과/실제결과/로그 첨부

3. 개발자: 해결방안 도출 → 코드 수정 → PR 리뷰 → 머지 → 재배포
4. 설계 변경 필요 시: 프로젝트 변경 절차에 따라 D1~D5 산출물 갱신
5. 테스터: 재시험 → 회귀 시험(연관 영역) → 결함 종료
