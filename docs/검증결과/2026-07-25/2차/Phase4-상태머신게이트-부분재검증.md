## 1. 이 Phase 가 어려웠던 이유 — 방어를 "추가"하는 작업이었다

Phase 1~3 은 잘못된 동작을 **고치는** 작업이라 고친 코드가 곧 실행 경로였다. Phase 4 는 **없던 게이트를 새로 얹는** 작업이고, 얹은 게이트가 실제 트래픽 경로에 놓였는지는 코드만 봐서는 드러나지 않는다.

실제로 **적대적 검증이 두 번 모두 "구현은 됐는데 실경로가 안 지나간다"** 를 잡았다.

| 회차 | 판정 | 무엇이 문제였나 |
|:---:|:---:|---|
| 1차 (4-A) | BROKEN | 가드가 배치 **출구**에만 붙어, 입구에서 APPROVED 가 `BATCH_QUEUED` 로 선덮여 **가드가 한 번도 발화하지 않음** |
| 1차 (4-B) | BROKEN | CAS 기준값이 **락 획득 前 값**(1차 캐시) + FE 미연동으로 **프로덕션 미발화** |
| 2차 (통합) | WEAK | 1차 지적은 닫힘 확인. 대신 **가드가 만든 신규 결함** 6건 |

### 2-2. DEV_FIX 2차가 고친 신규 결함 — H10 런타임 재현

가드가 만든 결함 중 가장 심각했던 **수동 재처리 stage 고착**을 실제 상태를 만들어 재현했다.

```
준비: rawSn=16 (stage=FAILED) → 배정 201 → WORKER 검수제출 200
      ⇒ work=PENDING, stage=FAILED  (검수 소유 + 재처리 가능 조합)

POST /v1/videos/16/batch/retry
  → HTTP 409 "검수 진행/완료(또는 반려) 상태의 영상은 배치를 재처리할 수 없습니다."
     stage = FAILED   ← 고착 없음 (수정 전에는 PROCESSING 고착)
     work  = PENDING  ← 검수 제출 보존
  2회차 → HTTP 409    ← 영구잠김 아님(게이트 재개방)
```

## 3. 세 번 반복된 실패 유형 — "고쳤지만 실경로가 안 지나간다"

| # | 사례 | 어떻게 드러났나 |
|:-:|---|---|
| 1 | 4-A: 배치 **입구**(`MarkingBatchBridge.SKIP_STATUSES`)에 검수 소유 상태 누락 | 적대검증이 호출 순서를 추적 |
| 2 | 4-B: `labelVersion` 이 optional 인데 **FE 가 전송하지 않음**(변경분에 frontend 0건) | `grep -rc labelVersion frontend/src` = 0 |
| 3 | 4-B: 마킹 상한이 **BE 실 fps vs FE 30fps 하드코딩** 불일치 → 정상 마킹을 400 거부 | 적대검증이 FE 소스까지 확인 |

**공통점**: 단위 테스트는 전부 GREEN 이었다. 서비스 메서드를 직접 호출하는 테스트는 그 위 계층(브리지·FE·응답 계약)을 지나가지 않는다.

**대응으로 채택한 것** — `BatchReviewOwnedEntryGuardIT` 는 브리지 진입부터 파이프라인 종료까지를 타면서 **①상태 보존 ②step 미실행(배치로그 부재 + 라벨 0건)** 을 동시에 단언한다. "상태만 지켰다"로는 통과하지 못한다.

## 4. 인벤토리 표를 요구하는 것만으로는 부족했다

지금까지의 교훈은 "뿌리가 닿는 지점을 전부 열거 — **인벤토리 표를 산출물로 요구**" 였다. 이번에 그 한계가 드러났다.

**4-A 는 표를 제출했고, 그 표에 형제 경로가 적혀 있었다.** 그런데 "스코프 밖"으로 남겼고, 그 사유("차단 집합을 넓히면 정상 흐름이 깨진다")가 **사실이 아니었다**. 적대검증이 호출자를 직접 추적해서야 드러났다 — 실제 반례는 `ASSIGNED` 하나뿐이고 `PENDING`·`REJECTED` 출발 정상 경로는 0개였다.

→ **교훈 갱신**: 표에 오른 항목을 "스코프 밖 / 영향 없음"으로 남길 때는 **그 사유 자체가 코드 근거로 검증돼야 한다.**

이 규칙을 4-B 위임에 넣은 결과, 4-B 는 면제 판정마다 근거를 붙였고 그중 하나는 **스스로 뒤집었다** — `TrackMergeService` 가 rawSn 전체를 bump 하던 사유("재보간 터치 프레임을 알 수 없다")가 거짓이었고(같은 컴포넌트에 `interpolateSingleTrackTouched` 존재), 결과적으로 좁히지 못한 경로가 0건이 됐다.

## 5. 검증자도 틀린다 — 이번에 확인된 3건

| 주장 | 실제 | 확인 방법 |
|---|---|---|

## 8. 잔여

> 검증 과정에서 "반려 후 재마킹 동선 부재"(`MarkingGuards` 의 `stage==MARKING_READY` 조건 때문에 배치가 돈 영상은 반려돼도 재마킹이 412)를 설계 공백으로 올렸으나, **사용자 확인 결과 반려 후 마킹 시나리오는 존재하지 않는다**(2026-07-27). 반려는 라벨을 수정해 재제출하는 흐름이고 마킹은 그 앞단 배치 단계다. 따라서 현재 동작이 정상이며 공백이 아니다.
