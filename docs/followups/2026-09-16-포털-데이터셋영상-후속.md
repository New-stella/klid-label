## 0. 지금 바로 할 일 — 개발망 설정 3줄 넣기 ★이것부터

**지금 상태** — 포털 데이터셋 화면에 들어가면 **소재 가져오기에서 멈춘다.** 설정 세 값이 비면 그 창구가
닫히도록(fail-closed) 만들어 뒀기 때문이다. **결함이 아니라 설정 누락이다.**

값 세 개 중 **둘은 확정됐고 하나만 조회하면 된다.**

| 키 | 값 | 확정 근거 |
|---|---|---|
| `PORTAL_MATERIALS_BASE_URL` | `http://127.0.0.1:39080` | 포털 WAS 레포 `standalone_jboss_portal.xml` 의 `http` 포트가 39080 · 아파치도 `balancer://klid-jboss → 127.0.0.1:39080` · 개발은 저작도구 WAS 와 **같은 장비**(아파치 주석 「개발은 로컬」 + 포털 레포 `Jenkinsfile-author-api` 가 저작도구 WAR 를 로컬 경로에 배포) |
| `PORTAL_MATERIALS_API_KEY` | 포털이 알려 준 64자 키 | 포털 개발 설정(`portal-ingest/src/main/resources-dev/application.yml`)의 `portal.ingest.api-key` 기본값과 같은 값. 그 필터가 `/api/internal/**` 전 경로를 검사한다 |
| `PORTAL_MATERIALS_REPO_ROOT_ALLOWLIST` | **아래 ①에서 조회** | 포털 운영설정 `dataset_repo_root_dir` 값. 배포마다 다를 수 있어 예시를 베끼지 않는다 |

> **아파치를 안 거치는 주소를 쓰는 이유** — `/api/internal/**` 은 아파치가 파트너망 IP 만 허용한다.
> WAS 를 직접 부르면 그 검사에 걸릴 일이 없고 자체 서명 인증서 문제도 없다.
> 인증은 WAS 의 `x-api-key` 가 그대로 검사하므로 **보안이 약해지지 않는다.**

### ① 허용 루트 값 조회 (포털 DB)

```sql
SELECT stng_key, stng_value FROM portal.tb_oper_stng
 WHERE stng_key = 'dataset_repo_root_dir';
```

나온 값이 ③에 넣을 값이다. 이어서 **그 경로가 저작도구 WAS 장비에서 보이는지** 확인한다.

```bash
ls -ld <조회한 값>          # 예: /nas-storage/data/portal/repo
```

⚠ 안 보이면 설정을 넣어도 조달이 실패한다. **NAS 동일 마운트가 먼저다**(포털·저작도구가 같은 경로로
마운트하기로 확정돼 있다). 마운트가 없으면 인프라에 요청한다.

### ② 설정 파일 위치 확인 (변경 없음 — 반드시 먼저)

```bash
ps -ef | grep '[j]boss' | tr ' ' '\n' | grep spring.config
```

- `file:/etc/klid/` 가 보이면 ③으로.
- **안 보이면 ③을 하지 말 것** — 자리가 다르면 **아무 반응 없이 그대로 실패**한다. 그 출력을 들고 확인한다.

### ③ 세 줄 추가

```bash
sudo cp -a /etc/klid/application.properties /etc/klid/application.properties.bak.$(date +%Y%m%d%H%M)
sudo vi /etc/klid/application.properties
```

넣을 내용 (키 값과 허용 루트는 실제 값으로 바꾼다):

```properties
PORTAL_MATERIALS_BASE_URL=http://127.0.0.1:39080
PORTAL_MATERIALS_API_KEY=<포털이 알려 준 64자 키>
PORTAL_MATERIALS_REPO_ROOT_ALLOWLIST=<①에서 조회한 값>
```

⚠ 같은 키가 이미 있으면 덧붙이지 말고 **그 줄의 값만** 바꾼다(뒤에 또 쓰면 어느 쪽이 먹는지 헷갈린다).
⚠ 대상은 **저작도구 JBoss** 다. 아파치(38081)·포털 웹(38444)은 건드리지 않는다.

### ④ 재기동

```bash
systemctl list-units --type=service | grep -iE 'jboss|eap'
sudo systemctl restart <유닛명>       # 저작도구 인스턴스 (예: jboss8-3rd)
```

### ⑤ 검증 1 — 포털 창구가 실제로 답하는지 (재기동 없이 먼저 해도 된다)

```bash
curl -sS -o /tmp/mat.json -w '%{http_code}\n' \
  -H "x-api-key: <포털이 알려 준 64자 키>" \
  "http://127.0.0.1:39080/api/internal/v1/datasets/<데이터셋번호>/materials"
head -c 400 /tmp/mat.json; echo
```

| 결과 | 뜻 |
|---|---|
| `200` + `repoRootDir`·`files[]` 가 보인다 | 주소·키 둘 다 맞다 → ⑥으로 |
| `401` | 키가 틀렸거나 헤더가 안 실렸다 |
| `404` | 주소는 맞고 그 데이터셋 번호가 없다 (다른 번호로 재시도) |
| 연결 거부 | 포트가 다르거나 **같은 장비가 아니다** — 포털 WAS 장비 주소로 바꿔 본다 |

⚠ 응답에 NAS 절대경로가 들어 있다. **로그·티켓에 붙이지 않는다**(내부 전용).

### ⑥ 검증 2 — 저작도구 기동 로그

```bash
JH=$(ps -eo args= | tr ' ' '\n' | grep -m1 -- '-Djboss.home.dir=' | cut -d= -f2-)
grep -iE 'PortalMaterials|허용 루트|fail-closed' "$JH/standalone/log/server.log" | tail -5
```

「허용 루트가 비어 있어 … 닫힌다」류 경고가 **없으면** 설정이 들어간 것이다.

### ⑦ 검증 3 — 화면

포털에서 학습데이터 하나를 골라 **「저작도구로 열기」**.

1. 소재 가져오기가 **준비 완료**까지 간다 → 조달 성공.
2. 이어서 **데이터셋 영상 목록**이 뜬다 → 등록 성공. 영상을 눌러 라벨링까지 들어가 본다.
3. 목록 자리에 **등록 실패**가 뜨면 → **압축본 구조가 우리 가정과 다른 것이다.** 아래 1번 항목으로 간다.
   화면의 실패 사유 문구와 아래 로그를 남긴다.

```bash
grep -iE 'PortalDataset' "$JH/standalone/log/server.log" | tail -30
```

> ★ **3번이 나오는 것도 성과다** — 지금까지 확인할 수 없던 「실물 구조가 가정과 같은가」가
> 그 순간 판정된다. 실패 사유가 어디서 어긋났는지 지목한다.

**되돌리려면** — 백업으로 되돌리고 재기동하면 원래대로 닫힌다. 이미 등록된 행은 지워지지 않는다.

상세 근거와 예외 상황은 `docs/operations/WAS-설정추가-요청-포털소재조달-20260916.md`.

## 1. 실제 배포 압축본 샘플로 파서를 확인한다 (0번을 하면 바로 판정된다)

**지금 상태** — 해제본 구성을 **우리 검수 승인 산출물 구조로 가정**했다(`{영상 키}/v{n}/deid/NNNN.jpg` + 같은 이름 `NNNN.json`).
시험은 그 가정대로 만든 압축본으로만 돌았다. **실물로 한 번도 왕복하지 않았다.**

**왜 이렇게 뒀나** — 포털 원장에도 압축본 내부 구성에 대한 확정 서술이 없어, 추측으로 채우는 대신
**구조가 다르면 등록 실패로 알리는 쪽**을 골랐다(사용자 확정 2026-09-15).

**할 일**
- 샘플 한 건을 받아 `PortalDatasetLayoutReader` 가 읽는지 확인한다.
- 다르면 **파서만** 고친다. 원장 적재·판정·창구는 구조와 무관하게 그대로다.
- `ADR-068` 의 가정 서술을 실물 기준으로 개정한다.

⚠ 샘플 없이 운영에 올리면 **모든 데이터셋이 FAILED** 로 끝난다. 그 상태에서 목록 창구는 정상 응답(FAILED)을 주므로
화면만 보고는 「기능이 죽었다」와 구분되지 않는다.

## 2. 등록이 실패한 뒤 다시 시도할 길을 만든다

**지금 상태** — 실패(FAILED)는 **종착**이다. 상태 표식 파일을 사람이 지우기 전에는 자동으로도 수동으로도 다시 시작하지 않는다.
목록 창구가 다시 시작하는 것은 「표식이 없음」과 「10분 넘게 멈춘 진행 중」 두 경우뿐이다.

**정해야 할 것** — 실패 사유를 두 갈래로 가른다.
- **구조 불일치·영상 키 이상** → 다시 해도 같은 결과다. 종착이 맞다.
- **입출력 실패·적재 실패** → 일시 장애일 수 있다. 재시작 대상이다.

**할 일** — 그 구분을 `API-253`·`ADR-068` 에 먼저 적고, 그 다음 코드에 반영한다(설계 먼저).

## 3. 같은 데이터셋의 새 버전이 오면 다시 등록되게 한다

**지금 상태** — 멱등 키가 `PORTAL_DATASET_{데이터셋 번호}_{영상 키}` 라 **버전이 없다.**
같은 데이터셋의 새 버전 소재가 준비돼도 이미 등록된 영상은 「이미 있음」으로 건너뛴다.
⇒ **갱신된 프레임·라벨이 원장에 반영되지 않고**, 원천 위치도 옛 해제본을 가리킨 채 남는다.

**정해야 할 것**
- 버전을 키에 넣을 것인가(그러면 같은 영상이 버전마다 다른 행이 된다).
- 넣는다면 **이미 쌓인 사용자 저장 오버레이**를 새 행으로 옮길지, 옛 행에 남길지.

⚠ 이 결정은 「내 작업」 목록·ZIP 내려받기·보존기간 삭제에 모두 닿는다. 키만 바꾸고 끝나지 않는다.

## 4. 오래된 등록 행·남은 파일을 정리한다

**지금 상태** — 정리 경로가 **없다**.
- 포털 정리 트리거는 **데이터셋 코드 + 버전**으로 오는데 등록 행은 **데이터셋 번호**로 이어져 있어 둘을 맞출 수단이 없다.
- 등록 도중 노드가 죽으면 작업 중 자리(`.portal-dataset-staging-*`)와 옮겨 둔 이미지 묶음이 남는다. 쓸어 담는 배치가 없다.

**할 일** — 포털과 식별자 대응을 먼저 합의한다. 그 전에는 삭제 조건을 안전하게 쓸 수 없다.

⚠ **삭제 조건은 반드시 「출처 판별자 + 데이터셋 대응 + 경과」를 동시에** 걸고, 후보 조회가 아니라 **최종 삭제 실행문에 박는다.**
하나라도 빠지면 관제 영상을 지운다(파생영상 폐기 삭제와 같은 원칙).

## 5. 데이터셋 단위 권한(누가 어느 데이터셋을 볼 수 있는가)을 정한다

**지금 상태** — 포털 회원이면 **아무 데이터셋 번호·영상이나** 목록 조회와 작업이 된다.
기존 데이터마트 모델과 같은 형태라 이번에 결함으로 보지 않았다.

**정해야 할 것** — 포털이 데이터셋별 열람 권한을 관리하는지, 관리한다면 그 판정을 우리가 받아야 하는지.
받아야 한다면 창구가 하나 더 필요하다(포털 → 저작도구).

## 참고 — 이번에 인지하고 수용한 것 (결함 아님, 되돌리지 말 것)

- **검수 상태를 꾸며 넣지 않는다.** 데이터셋 영상은 승인이 아니라 **출처**로 작업 대상이 된다.
  상태 행을 만들면 관제 조회 뷰·통지·산출물 연동이 그 영상에 반응한다.
- **프레임 이미지를 비식별 프레임 영역으로 복사**한다(해제본과 이중 저장). 서빙 규약이 그 영역 밖 파일을 허용하지 않는다.
  최종 위치는 `frames/deid/{rawSn}/portal-dataset-{식별자}/` 로 한 겹 더 깊다 — 식별자가 적재 시점에 정해져 복사를 먼저 할 수 없기 때문이다.
- **메타·이벤트 어노테이션의 403 문구는 다르다.** 남의 자산과 미노출을 같은 문구로 숨기는 자리라 그대로 뒀다.
- **ZIP 410 판정이 저장 라벨만 본다** — 기존 결손이며 이번 범위 밖이다.
