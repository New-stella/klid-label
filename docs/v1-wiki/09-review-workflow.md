## 9.1 전체 흐름

> ⚠ **구 서술 정정 — 검수 단계는 고정 2단계가 아니라 프로젝트마다 설정하는 값이다 (2026-08-19 원문 실측, 구속).** `02-관리자매뉴얼.txt 3.1`(프로젝트 생성 절차)은 다음과 같이 명시한다: *"데이터 작업은 '1단계의 가공 → 1차 검수 → 2차 검수 → 2단계의 가공 → 1차 검수 → 2차 검수'로 진행됩니다. 기본 데이터 작업 프로세스는 '1단계의 가공 → 1차 검수'이며, 더 짧게 줄이는 것은 불가능합니다. '검수 추가' 버튼을 클릭하면 검수 과정을 추가할 수 있으며, 검수는 최대 2단계까지 설정 가능합니다. '단계 추가' 버튼을 클릭하면 가공 단계를 추가할 수 있으며, 단계 또한 최대 2단계까지 구성할 수 있습니다."* 즉 **가공 단계 1~2개 × (각 가공 단계마다) 검수 0~2차**가 프로젝트 생성 시점에 관리자가 정하는 값이며, 최소 구성은 "가공 → 1차 검수"뿐이다. 아래 다이어그램은 **2단계 가공 + 각 단계 2차 검수까지 있는 최대 구성**을 예시로 보여준다 — 모든 프로젝트가 이 흐름을 따르는 것이 아니다. 근거: `02-관리자매뉴얼.txt 3.1`.

```
[작업자] 라벨링 작업 (1단계 가공)
    ↓ 모든 프레임 저장 완료 (모두 연두색) → 제출
[1차 검수자] 프레임별 검토 → 승인 or 반려
    ↓
[2차 검수자] 최종 검토 (프로젝트에 2차 검수가 설정된 경우만)
    ↓ 승인 → 다음 가공 단계(2단계, 설정된 경우) 또는 최종 완료
    ↓ 반려 → 1차 검수자에게 반환
         (단, 2차 반려 건은 1차가 작업자에게 재반려 불가)
```

작업자(가공) → 검수자(1차) → [검수자(2차)] → [다음 가공 단계 반복] → 최종 완료. (관리자의 최종 승인/반려 게이트에 대해서는 아래 신규 항목 참고.)

> ★ **신규 확인 — 관리자에게도 최종 단계의 승인/반려/제출 권한이 있다 (구 서술이 놓친 부분).** 관리자가 "작업 내용 확인" 화면(`SKKLID-UI-03-02-14~15`)에 들어가면 상단에 "확인 및 재배정/폐기" 버튼 외에 **"승인/반려/제출" 버튼도 그대로 노출**되며, 주석은 *"(최종) 관리자의 반려 기능은 제외하고 문제가 있을 경우 관리자/프로젝트 담당자가 직접 수정하는 프로세스로 진행"* · *"'반려' 버튼 클릭 시 마지막 검수자에게 돌아감(반려 사유 창은 검수자와 동일하게 노출) — 관리자 반려는 검수자 반려와 동일"* · *"'제출' 버튼 클릭 시 작업자, 검수자와 동일하게 다음 단계/전 단계로 데이터 이동 — 관리자 제출은 작업자/검수자 제출과 동일"* 이라고 적는다. `03-UI설계서V1.1.txt` SC-009(검수 작업)도 대칭 규칙을 하나 더 준다: *"2차 검수자가 최종 승인한 작업을 관리자가 반려했을 경우, 2차 검수자는 해당 작업을 1차 검수자에게 반려할 수 없음(반려 버튼 비활성화)"*. 즉 **관리자는 (설정된 검수 단계를 다 거친 뒤) 최종 게이트로서 승인/반려/제출을 수행할 수 있고, 그 반려는 2차 검수자에게 돌아가며 2차 검수자는 다시 1차에게 반려할 수 없다.** 근거: `01-UIUX설계서.txt`(화면ID `SKKLID-UI-03-02-14~15` 세부 설명 열) · `03-UI설계서V1.1.txt` SC-009 "반려".

## 9.2 프레임 테두리 색상 체계

| 색상 | 상태 | 의미 |
|------|------|------|
| **연두색** | 저장됨 | 정상 처리된 프레임 |
| **주황색** | 반려됨 | 재작업 필요 프레임 |
| **빨간색** | 관리자확인요청 | 관리자에게 확인 요청 중 |
| *(모두 연두색)* | 제출 가능 | 모든 프레임이 연두색일 때만 검수 제출 가능 |

> 현재 보고 있는 프레임은 약간 크게 표시.

## 9.3 역할별 작업 제약

### 작업자
- 관리자 확인 요청 프레임이 없고 **모든 프레임 저장** 완료 시 제출 가능
- 반려된 프레임만 재작업 가능 (승인된 프레임은 볼 수만 있음)
- 관리자 확인 요청 프레임은 처리 후 실시간 반환
- **자동 저장**: 프레임 이동 시 자동 저장. 수동 저장(Ctrl+S)도 가능
- 제출 버튼은 마지막 프레임에서만 노출

### 검수자(1차/2차 공통)
- 검수자 화면은 '반려'·'승인(작업자의 '저장' 기능에 해당)' 버튼 외에는 작업자 화면과 동일 — 검수자도 라벨을 직접 수정 가능
- 검수하면서 프레임 단위로 승인해야 함. **제출 전까지는 프레임의 상태값(승인/반려)을 계속 변경 가능**
- 반려는 개별 프레임 단위 처리, 반려 시 해당 프레임 테두리가 주황색으로 변경
- 반려 내역은 누적되다가 마지막 프레임에서 '제출' 클릭 시 확정 — 반려가 있으면 작업자에게, 반려가 없으면 다음 검수자(2차) 또는 관리자에게 전달
- 모든 프레임에 1회 이상 승인/반려가 발생하고, 관리자 확인 요청이 완료되지 않은 프레임이 없어야 '제출' 버튼 활성화
- **2차 검수자에게 반려된 건은 1차 검수자가 작업자에게 재반려 불가**(반려 버튼 비활성화)
- ★ **신규 확인**: **관리자가 최종 승인 건을 반려했을 경우, 2차 검수자는 해당 작업을 1차 검수자에게 반려할 수 없다**(반려 버튼 비활성화) — §9.1 "관리자 최종 게이트" 참고. 근거: `03-UI설계서V1.1.txt` SC-009 "반려".

### 관리자
- **일상적으로는** 관리자 확인 요청 프레임만 실시간 처리 가능 — 다른 프레임도 확인은 가능하나 수정 불가능(근거: `01-UIUX설계서.txt` IA 개요, "관리자(작업 완료)" 작업방식 표: *"작업자가 보낸 관리자 확인 요청 프레임이 있을 경우 실시간으로 처리 가능 / 관리자 확인 요청 프레임 외에 다른 프레임도 확인은 가능하나, 수정 불가능"*)
- 작업을 옮길 때는 실시간 처리 불가
- ★ **신규 확인 — 위 "수정 불가"는 일반 라벨 편집을 말하며, 워크플로 마지막 단계의 승인/반려/제출은 별개다.** 관리자가 "작업 내용 확인" 화면에 들어가면 승인/반려/제출 버튼도 노출되고, 문제가 있는 프레임은 관리자/프로젝트 담당자가 직접 수정하는 프로세스로 진행한다는 주석이 있다(§9.1 참고). 두 문장을 원문 그대로 병기한다 — 세부 조건(어느 시점에 이 권한이 열리는지)까지는 원문만으로 확정 못함.

## 9.4 관리자 확인 요청

화면: `SKKLID-UI-03-02-14~15` (확인 및 재배정)

작업자/검수자가 문의·문제 프레임을 관리자에게 보내는 기능.

**요청 (작업자/검수자)**:
- 용도: 작업 중 문의, 프레임 추출 문제로 폐기 요청 등
- 방법: "관리자 확인 요청" 버튼 → 사유 입력/선택 → "확인"
- 결과: 관리자에게 전달 + 이슈 탭 기재. 해당 프레임은 작업 불가(볼 수는 있음)

**관리자 처리**:
| 액션 | 결과 |
|------|------|
| **확인 및 재배정** | 문제 없음 확인 → 사유 입력/"문제 없음" → 프레임 재배정 + 이슈탭 기재 |
| **폐기** | 프레임 삭제 처리 → 작업 대상에서 제외 |

> ⚠ *"관리자가 '작업 프로젝트'에서 직접 라벨링할 때는 관리자 확인 요청 기능 사용 불가(직접 판단)"* — 이번 1차 원문 3종에서 이 문장을 확인하지 못했다(원문 미확인). 삭제하지 않고 남겨두되 근거 불명으로 표기한다.

## 9.5 검수자 반려

- 용도: 작업자가 라벨링을 잘못 진행했을 경우
- 방법: "반려" 버튼 → 반려 사유 입력/선택 → "확인"
- 결과: 저장 후 데이터 제출 시 작업자에게 전달, 이슈 탭 기재

## 9.6 이슈 탭에 노출되는 이력

> ⚠ **구 서술 정정(2026-08-19 원문 실측)** — 옛 표는 "작업자 작업 제출 이력"·"검수자 승인 이력"·"라벨/원천/메타 데이터 변경 이력"까지 5종을 열거했으나, 이번 1차 원문에서 개별 항목으로 확인되는 것은 **반려 이력 + 관리자 확인 요청 이력** 뿐이다("승인 이력"·"제출 이력"이 별도 열람 화면으로 존재한다는 서술은 원문 미확인). 근거: `03-UI설계서V1.1.txt` SC-008(이슈 확인) "이슈 사항" 처리 내용.

- "이슈 사항" 클릭 시 **반려 이력**과 **관리자 확인 요청 이력**이 노출된다.
- 이슈 사항은 클립 영상 전체 단위로 관리되며, 모든 프레임의 내용을 포함한다.
- 상단 숫자는 반려된 횟수(영상 클립 단위)로 노출된다.
- 사유는 최근 일자를 기준으로 노출되며, 프레임별로 ①검수자가 반려한 사유 ②관리자 확인 요청으로 데이터를 보낸 사유 ③관리자가 확인하여 재배정한 사유를 확인할 수 있다.
- 반려된 작업자가 재작업을 위해 데이터를 클릭하거나, 관리자 확인 요청으로 보냈던 데이터가 재배정되어 다시 클릭할 경우 이슈 사항이 **열린 상태**로 노출된다.

## 9.7 데이터 상태 분류 / 우선순위

작업자 리스트 정렬 우선순위(근거: `01-UIUX설계서.txt` UI Guide_세부항목):
```
반려 > 작업중 > 배정 > 관리자 확인 요청 > 보류 → 이후 날짜 순 → 동일 날짜 시 ID(명칭) 내림차순
```

데이터 상태 플로우 예시(근거: `02-관리자매뉴얼.txt 7.1` 담당 프로젝트 대시보드 조회 및 다운로드 — 대시보드의 "전체 작업내역" 표):
```
배정대기 → 배정 → 가공완료 → 1차 검수완료 → 2차 검수완료 → (다음 가공 단계가 있으면 반복) → 최종완료
```
> ⚠ **구 서술 폐기(2026-08-19 원문 실측)** — *"데이터 상태 플로우(관리자매뉴얼 §16.2)"* 는 존재하지 않는 절 번호다(이 매뉴얼은 §1~§11 까지만 있음). 위 흐름의 실제 출처는 **§7.1 담당 프로젝트 대시보드**의 "전체 작업내역" 표이며, 그 표는 **1단계**(배정대기→배정→가공완료→1차검수완료→2차검수완료)와 **2단계**(배정→가공완료→1차검수완료→최종완료)를 별도 열로 병기한다 — "(선택) 2차 검수완료"라는 단일 선형 흐름이 아니라, **§9.1 에서 정정한 대로 가공 단계·검수 차수 자체가 프로젝트별 설정값**이다. 위 예시는 그 중 가장 흔한 조합을 정리한 것.

리스트 항목(근거: `02-관리자매뉴얼.txt 4.2` 작업 프로젝트 데이터 목록 조회): 단계-작업(동일 프로젝트에서 여러 권한 보유 가능), 남은 작업/전체 프레임 수(전체 프레임 수="폐기" 제외 프레임 수, 남은 작업=저장/제출하지 않은 프레임 수 — 작업자 남은 작업은 배정완료·검수반려, 검수자 남은 작업은 검수요청·검수반려), 데이터 상태, 배정일.
