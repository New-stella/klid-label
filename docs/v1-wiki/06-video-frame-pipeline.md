## 6.2 프레임 자동 추출 (FFmpeg Batch)

> **원문(3종) 미확인** — "FFmpeg"·"II-001"·"II-002" 문자열이 3종 원문 전체에 0건이다. 근거는 이번 대조 세트 밖의 인터페이스규격서이며, 그 원문은 확인하지 못했다. 단 이 절 하단의 **"영상 처리는 자원 집중 → 1건씩 배치 처리 구현 필수"**(§6.6에서도 재인용) 문장만은 `03-UI설계서V1.1.txt`("1영상 처리 시, 시스템 자원을 많이 사용하므로 1건씩 배치 처리로 진행될 수 있도록 구현이 필요함")로 직접 확인된다 — 이 한 문장은 신뢰할 수 있다.
>
> ⚠ **이 절과 [§6.6 프레임 분할(배정)](#66-프레임-분할-배정)을 같은 메커니즘으로 혼동하지 말 것(2026-08-19 재확인, V1-FIX 정리 라운드).** 이 절(§6.2)이 서술하는 "이벤트 인입 직후 배치 프로그램이 1분마다 매핑 테이블을 조회해 FFmpeg로 자동 추출"하는 흐름은 **이번 3-PDF 대조 세트 안에서 확인도 반증도 되지 않은 별개 인터페이스**(II-001/002, 인터페이스규격서 소관)다. 반면 §6.5·§6.6이 서술하는 **"프로젝트 배정 시 관리자가 분할 단위(초당/분당/시간당/전체)와 프레임 수를 직접 입력"**하는 흐름은 `02-관리자매뉴얼.txt` §5.2로 **이번 라운드에서 실측 확인**됐다(원문 그대로: "분할 단위: 초당/분당/시간당/전체", 데이터 상태 "변환대기 → 변환중 → (변환오류) → 배정대기"). 이 둘은 트리거 시점(인입 직후 vs 프로젝트 배정 시)과 FPS 결정 주체(자동 계산 vs 관리자 수동 입력)가 다른 **별개 서술**이며, §6.2를 근거로 §6.6의 "관리자 수동 설정"을 "자동 배치"로 다시 고쳐 쓰지 말 것.

인터페이스: `KLID-AI-II-001`(요청) / `II-002`(상태 응답) — **Batch, 1회/분** ([14](14-interfaces-api.md))

```
[배치 프로그램] 1분마다 데이터 변환 매핑 테이블 조회
    ↓ (원본 영상 경로, 요청 FPS, 프로젝트 ID)
이미지변환 API 요청 → 원본 파일 존재 여부 검증
    ↓
프로젝트 ID 디렉토리 생성
    ↓
FFmpeg로 지정 FPS에 따라 프레임 추출
    (파일명: frame_0001.png, frame_0002.png ... 자동 증가)
    ↓
매핑 테이블 상태 업데이트 (완료 / 실패 + 오류 로그)
```

## 6.3 이미지 자동 분류

> **원문(3종) 미확인, DB설계서 근거** — "자동 분류"·"분류 기준"에 해당하는 서술이 화면정의서·관리자매뉴얼·UI설계서V1.1 3종 텍스트 어디에도 없다(계수 명령: `grep -a "자동.*분류\|분류.*저장\|분류 기준" 01-UIUX설계서.txt 02-관리자매뉴얼.txt 03-UI설계서V1.1.txt` → 무결과). 아래 컬럼명(`LS_DATA_SRC.EVNT_TYPE_CD` 등)은 `docs/v1-wiki/15-database.md`가 인용하는 **KLID-AI-데이터베이스설계서 V1.4**(이번 3-PDF 세트 밖) 근거다. 관리자매뉴얼 §5.1 "영상/이미지 목록 조회"의 상세검색 필터(날씨·시간대·계절 등, [06.5](#65-영상이미지-프로젝트-배정) 참고)는 이 필드들이 **검색 필터로 실재**함을 뒷받침하지만, "프레임 추출 시 자동 분류·저장된다"는 파이프라인 동작 자체는 3-PDF 세트로 확인도 반증도 하지 못했다.

추출된 프레임은 원본 클립의 메타데이터(**이벤트 유형, 시간대, 날씨, 계절, 위치** 등)를 기반으로 자동 분류·저장된다. 분류 기준 코드는 `LS_DATA_SRC`의 `EVNT_TYPE_CD`/`HR_TYPE_CD`/`WTHR_CD`/`SESN_CD`/`LCLGV_CD` ([15](15-database.md)).

> - **"밝기/대비 자동 보정"**은 실재한다 — `03-UI설계서V1.1.txt`(화면 `KLID-AI-SC-005` 이미지 조절 패널) 화면개요: "밝기와 대비는 이미지 로드 시점에 자동으로 최적화되는 조정 기능 포함", 처리 내용: "이미지가 HTML 캔버스에 그려지면, 밝기/대비 등은 아키텍처 설계서에 정의된 알고리즘을 통해 최적의 값으로 설정되어 노출된다." (구체 알고리즘 자체는 3-PDF 세트 밖의 아키텍처설계서 소관, 원문 미확인).
> - **"사용자 수동 조정 (-100~100)"·"투명도 조정 (0~100)"의 구체 수치 범위**는 3종 원문 텍스트에 없다(입출력 항목 타입은 "number(3)"까지만 명시, 상하한 수치는 없음). 관리자매뉴얼 §4.3.2는 "라벨러는 작업 또는 검수 과정에서 이미지의 밝기와 대비를 조정하여 어두운 영상이나 화질이 낮은 이미지를 보다 명확하게 확인할 수 있습니다", "투명도 슬라이더를 조절하면 전체 라벨의 투명도가 변경되고, 선택된 항목 투명도 슬라이더를 조절하면 선택한 항목의 라벨만 투명도가 변경됩니다"라고만 적는다. 구체 수치 범위는 확인 불가로 남기고 표에서 뺐다(2차 참고자료 `docs/v1-wiki/sources/KLID-AI-사용자인터페이스설계서_V1_1_분석.md`에는 "-100~100"/"0~100"이 있으나 원문 텍스트로 재확인되지 않으므로 진실원으로 쓰지 않았다).
> - **"Circle 크기 조정"**은 실재한다 — `02-관리자매뉴얼.txt` §4.3.2: "추가로, 라벨링 Circle 크기 슬라이더를 통해 라벨 포인트의 크기를 조절할 수 있습니다."
> 근거: `03-UI설계서V1.1.txt`(화면 `KLID-AI-SC-005`), `02-관리자매뉴얼.txt` §4.3.2.

> ⚠️ **좌표계 원칙**: 모든 좌표 연산은 반드시 **원본 이미지의 해상도·좌표계** 기준으로 처리. 이미지 회전·사이즈 변경은 좌표에 영향을 주므로 원본 기준 변환 필수. 2026-08-19 `03-UI설계서V1.1.txt`(기술적 고려사항 절)로 재확인: "이미지 사이즈나 회전 기능 등의 영향으로 인해 좌표가 달라질 수 있으므로, 모든 연산은 반드시 원본 이미지의 해상도와 좌표계를 기준으로 처리해야함." 그대로 정확하다.

| 분할 단위 | 초당 / 분당 / 시간당 / 전체 |
| 프레임 수 | 숫자만 |

**규칙**: 분할 프레임 수는 원본 FPS보다 작아야 함 / 분당 분할은 1분 이상 영상 / 시간당 분할은 1시간 이상 영상.

"업로드" → 프레임 분할 → 프로젝트 배정. 영상 처리는 자원 집중 → **1건씩 배치 처리** 구현 필수.

### 데이터 상태 흐름

```
변환 대기 → 변환중 → (변환오류) → 배정대기
```
- **배정대기** 상태에서만 라벨러에게 작업 배정 가능
- 프레임 번호: `F`(실제 추출 번호), `I`(분할 시 순차 번호)

## 6.7 관련 데이터 (DB)

`LS_DATA_SRC`(원천 데이터·메타), `LS_PJT_DATA_MPNG`(프로젝트-데이터 매핑), `LS_PJT_DATA_STTS`(상태·변환 프레임 수·FPS 유형), `LS_PJT_STG_PRC`(가공 처리·`TRSF_FRM_CNT`/`FPS_TYPE_CD`). 상세 → [15](15-database.md).

> **v2 참고**: v2 파이프라인은 **⭐마킹(자동=프레임 간격/수동=단축키) → 외부 VLM 시계열(콜백) → 비식별화 → FFmpeg(원본+비식별 2벌) → YOLO(원본만) → SAM2 → 트랙 보간** 순으로, Quartz 1건/분 처리. v1의 "프로젝트 배정 시 프레임 분할" 대신 v2는 마킹 위치 기반 추출을 사용한다.
