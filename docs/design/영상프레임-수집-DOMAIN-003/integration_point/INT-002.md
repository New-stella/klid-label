## description

저작도구가 외부 VLM 서비스에 영상 시계열 메타(설명) 생성을 위탁하는 outbound 호출. 결과 상세는 콜백(INT-003)으로 비동기 수신한다. 기계적 요청·응답 계약은 이 ITEM 의 인라인 스펙이 담고, 여기서는 설계 결정과 그 함의를 적는다.

## 위탁 대상 (KLID 연동 API v1.2.0, 개정일 2026-09-07)
저작도구가 연동하는 위탁 창구는 둘이며, 한 영상에 대해 이중으로 위탁한다.
- `POST {vlm.client.url}/v1/videovlm-klid/describe` — 묘사. 이벤트 관점에서 영상 상황(장소·환경·상황)을 서술한다. `event_type` 을 싣는다.
- `POST {vlm.client.url}/v1/videovlm-klid/custom` — 추가 질문. 저작도구가 검증 이벤트 유형별로 보관하는 질문 문구를 `prompt` 에 직접 싣고 그 답과 근거를 서술받는다. `event_type` 을 싣지 않는다.
- 두 호출은 각각 **별도 `request_id`** 를 발급한다. 콜백이 그 값으로 역조회해 어느 위탁의 결과인지 가리므로, 같은 값을 쓰면 한쪽 결과가 덮여 유실된다.
- 추가 질문 축은 `event_type` 을 보내지 않으므로 **그 축에서는 event_type 미수신·미지원으로 인한 4xx 가 구조적으로 발생하지 않는다.** 묘사 축에는 그대로 남는다.
- [폐기] `POST /v1/videovlm-klid/describe-sub` — 벤더는 이 창구를 계속 제공하나 저작도구는 추가 질문 축에 **두지 않는다.** 질문 문구를 실을 자리가 없어 벤더가 유형별로 관리하는 질문에 의존해야 했고, 우리가 보관·선택한 문구와 실제 쓰인 문구가 갈릴 수 있었다.
- 판정 창구(`verify`)는 연동하지 않는다(ADR-051). 추가 질문 축을 `custom` 으로 옮긴 것이 판정 창구를 열 근거가 되지 않는다.
- ⚠ 근거로 삼은 규격서는 파일명 접미가 `_pre` 라 사전배포판일 가능성이 있다 — 벤더 확답 대기.

## 인증 (규격 §2.1)
- 서버에 API 키가 설정된 경우 분석 요청은 **`X-API-Key: <발급받은 키>`** 헤더가 필수다. **`Bearer ` 접두를 쓰지 않는다.**
- 헤더가 없거나 값이 다르면 **401 이며 이때 콜백은 전송되지 않는다.** 설계상 함의는 **위탁이 아무 신호도 없이 사라진다**는 것이다 — 미결 회수 경로가 재위탁해도 같은 401 이라 회복되지 않는다. 키 불일치는 회수로 메울 수 없고 설정을 고쳐야 풀린다.
- 조회용 GET(`status`·`events`)은 키 없이 호출할 수 있다.
- ⚠ 키 사용 여부와 값은 규격 밖에서 별도로 전달되며 **아직 받지 못했다 — 확인 대기.** 값이나 사용 여부를 추정해 채우지 않는다.

## 우리 쪽 조립·게이트 정책
- 프레임 선택은 두 축이 같은 조립 규칙을 쓴다 — 마킹 본문에서 프레임 인덱스를 얻으면 `frame_selected` + `selected_frames` 로 싣고(정렬·중복 제거·음수 제거, 상한 600 초과분 절단), 하나도 얻지 못할 때만 `frame_interval` 로 내린다. **빈 `selected_frames` 는 규격 위반이다.**
- 추출 간격·장수 세부값은 연동 시스템이 지정하지 않고 벤더 서버가 관리한다(요청에 추출 간격 필드를 두지 않는다).
- **위탁 전 확장자 게이트를 두지 않는다.** 벤더 허용목록의 사본을 우리가 들면 그 사본이 두 번째 진실원이 되어, 벤더가 목록을 넓힐 때 정상 위탁을 우리가 먼저 막는다. 이벤트 유형 허용목록을 폐기한 것과 같은 축이다.
- 이벤트 유형도 사전 차단하지 않고 벤더 응답이 판정하게 한다. 미지원 유형 판정의 단일 근거는 응답 code `40001` 이다.
- 규격의 분석 제한 900초는 **추론 대기·수행 구간 기준**이라 프레임 추출 시간이 별도로 더해진다. 저작도구의 콜백 대기 창은 **다른 것을 재는 별개 값이고 훨씬 길다** — 900초를 전체 소요 상한으로 읽어 대기 창을 좁히면 정상 위탁이 미결로 회수된다.

## 보류·재개
- 신고 구간(`DE_IDNTF_YN='F'`) 위탁은 스텝 내부에서 **보류(SKIPPED)** — 실패가 아니라 보류이며, 해소 시 자동으로 재위탁한다(멱등 조건: 시계열 메타 0건).
- 응답 신호가 없어도 미결 스위퍼가 회수하고, 검수자가 사유를 남기고 누르는 수동 스킵 게이트로 미연동 구간의 재수행을 통제한다.

## 신뢰성 정책
- HTTP 클라이언트 타임아웃 `vlm.client.timeout-seconds` 기본 **10s**.
- Retry `vlmClient`: 3회, 1s, ×2 backoff — **재시도 대상은 `429`(동시 처리 한도 초과) 하나뿐**이다. 잠시 뒤 다시 보내면 되는 일시 상태이므로 `401`·`40001` 을 포함한 다른 4xx 와 함께 비재시도로 묶지 않는다.
- CircuitBreaker `vlmClient`: failure-rate 50% / sliding-window 10 / min-calls 5 / open 30s
- 배치는 응답을 기다리지 않고 **제출만 개시한다(논블로킹 제출).** 스텝이 확정적으로 말하는 사실은 「제출을 개시했다」 뿐이고, 수락 여부는 완료 핸들러가 비동기로 기록한다.
- **마킹의 위탁 상태 표시는 묘사 축 기준**이다 — 추가 질문 축의 실패는 기록만 남기고 마킹을 실패로 내리지 않는다.

## ★★ 활성화 상태 — 설정 토글은 폐지됐다 (ADR-049)
연동 여부를 설정으로 켜고 끄던 토글은 폐지됐다. 연동 주소가 주입되어 있지 않으면 위탁은 **실패**하며 조용히 건너뛰지 않는다. 구 동작은 토글이 꺼져 있으면 외부 호출 없이 즉시 건너뛴 것으로 처리하고 아무 기록도 남기지 않았는데, 그 기본값이 비활성이라 시계열이 꺼진 채로 납품될 수 있었다.

벤더 미연동 구간의 운영은 **검수자가 사유를 남기고 누르는 시계열 묶음 스킵**으로 처리한다(단건·일괄 모두 제공). 설정으로 끄는 것과 달리 누가 언제 왜 건너뛰었는지가 배치 이력에 남고, 벤더 연동 시점에 해제·재수행으로 되돌릴 수 있다.

⚠ **미연동 구간에는 먼저 스킵한다** — 스킵 없이 돌려 실패시키면 마킹이 위탁 실패 상태로 종결되고, 마킹 상태 전이는 위탁 대기 상태에서만 일어나므로 이후 재수행해도 마킹 표시가 실패로 남는다(시계열 적재·검수 진입·산출물 재생성은 정상 동작한다).

# 위탁 요청 계약 (KLID 연동 API v1.2.0, 개정일 2026-09-07)

> 근거 규격서는 파일명 접미가 `_pre` 라 사전배포판일 가능성이 있다 — 벤더 확답 대기.
> 버전·승인 트레일의 진실원은 INTSPEC-003 이며, 여기에는 위탁 호출에 필요한 최소 계약만 둔다.

## 창구

| 축 | 창구 | 축 고유 필드 |
|---|---|---|
| 묘사 | `POST /v1/videovlm-klid/describe` | `event_type` |
| 추가 질문 | `POST /v1/videovlm-klid/custom` | `prompt`(질문 문구, 최대 4,000자) — `event_type` 없음 |
| 사전 확인 | `GET /v1/videovlm-klid/status` | 없음(ready/busy/loading) |
| 사전 확인 | `GET /v1/videovlm-klid/events` | 없음(지원 이벤트 목록) |

- [폐기] `POST /v1/videovlm-klid/describe-sub` — 벤더 제공은 유지되나 저작도구는 두지 않는다.
- 판정 창구(`verify`)는 연동하지 않는다.
- `events` 목록 확인은 묘사 축의 사전 절차다. 추가 질문은 `event_type` 을 쓰지 않으므로 그 목록과 무관하게 호출할 수 있다(규격 §5.2).

## 요청 바디

- 공통: `request_id` · `callback_url` · `media{type, source_type, path, frame_policy}`
- 축 고유 필드는 위 표대로 하나씩만 다르고, 그 외 요청 형식은 두 축이 같다(규격 §3.4).
- 파일 본문은 전송하지 않는다 — `media.path` 로 경로만 전달한다.
- 두 축은 각각 별도 `request_id` 를 발급한다.

### `frame_policy`

- `mode` 값역은 **`frame_interval` · `frame_selected` 둘뿐**이다. 정의되지 않은 mode 는 400.
  - [폐기] `uniform` — 규격 v1.2.0 에서 삭제됐으므로 두지 않는다.
- `frame_selected` 는 `selected_frames`(프레임 인덱스 목록, 상한 600)를 함께 싣는다. 빈 목록은 규격 위반이다.
- 추출 간격·장수를 지정하는 필드는 두지 않는다(벤더 서버가 관리한다).
- 영상 요청이면 `frame_policy` 는 두 축 모두에 필수다.

## 동기 응답

- `{request_id, status}` — 정상값은 `accepted` 만 인정한다. 결과 상세는 콜백으로 받는다.

## 오류 (규격 §2.10)

| 코드 | 사유 | 재시도 |
|---|---|---|
| `400` | 요청 형식 오류 · 정의되지 않은 `frame_policy.mode` · 허용 밖 확장자 | 아니오 |
| `401` | API 키 없음·불일치. **이때 콜백은 전송되지 않는다** | 아니오 |
| `415` | Content-Type 불일치 | 아니오 |
| `429` | 동시 처리 한도(32건) 초과 | **예** |
| `503` | 서버 미준비 | 아니오 |

- 응답 본문은 `detail` 만 담는 것이 기본이다. **정의되지 않은 `event_type` 인 경우에 한해** `{"code": 40001, "detail": "..."}` 로 code 가 함께 실린다.
- `40001` 이 나올 수 있는 축은 묘사 하나다 — 추가 질문은 `event_type` 을 보내지 않는다.

## 인증 (규격 §2.1)

- 서버에 API 키가 설정된 경우 분석 요청에 `X-API-Key: <발급받은 키>` 헤더가 필수다. `Bearer ` 접두를 쓰지 않는다.

- 키 사용 여부와 값은 규격 밖에서 별도로 전달되며 아직 받지 못했다 — 확인 대기.
