#### 1. 시험 대상 시스템

##### 1.1 시스템 개요 (서술)

학습데이터 저작도구(AT)는 AI 기반 지방정부 CCTV 관제지원시스템(2차)의 서브시스템으로, 영상/이미지 라벨링·검수 워크플로우·비식별화·외부 생성 메타데이터 검토 및 학습데이터 버전관리를 담당한다. 시험 대상 범위는 R1 사용자요구사항정의서의 **기능 요구사항(SFR) 16건**과 **비기능 요구사항(NFR) 7건**이다.

시험 대상 시스템은 다음 3개 실행 단위로 구성된다.

- **backend** — Spring Boot 3.3 / Java 17 메인 애플리케이션. 인증/DB/오케스트레이션/큐 관리/라벨 CRUD/외부 연동 담당. Controller → Service → Repository 레이어, 공통 `ApiResponse<T>` 응답, JWT 검증(`JwtAuthenticationFilter`), Quartz 배치(단일 인스턴스, PostgreSQL JobStore).
- **ai-server** — Python 3.11 / FastAPI 경량 추론 서버. YOLO/SAM2/VLM 추론 전용(stateless, 인증·DB 없음). GPU Worker 별도 프로세스로 수평 확장 가능.
- **frontend** — React 18 + TypeScript 5 + Vite 5. 라벨링 캔버스는 konva.js. 포털(외부 채널)은 반응형 웹·WCAG 2.1 AA 준수.

핵심 검증 도메인: 사용자/권한(REVIEWER·WORKER·PORTAL_USER), 마킹·배치 파이프라인(비식별→마킹→VLM→FFmpeg→YOLO/SAM2→트랙보간), 라벨링, 검수, 비식별화, 버전관리(DB 스냅샷), 데이터 증강(새 영상), 포털(데이터마트 Load), 관제서버 단방향 outbound 통지(TASK_COMPLETED/TASK_MODIFIED).

##### 1.2 하드웨어 구성도 (그림)

- (그림 미정 — kickoff 확정 인프라: on-premise 단일 서비스 인스턴스 기준. 상세 토폴로지는 D5 아키텍처설계서 배치도 참조. 부록 사유 ①)

##### 1.3 응용 목표시스템 구성도 (그림)

- (그림 미정 — backend(Spring Boot) → ai-server(FastAPI, HTTP/WebClient) 호출 + 외부 연동(비식별·VLM·증강·관제통지). 상세 구성은 D5 아키텍처설계서 컨테이너/컴포넌트 다이어그램 참조. 부록 사유 ①)

#### 2. 가정(Assumptions) 또는 제약사항(Constraints)

- **인프라(kickoff 확정)**: on-premise 환경. RDB는 **PostgreSQL 단일 인스턴스**(`klid_at` 스키마). Quartz 배치는 **단일 인스턴스**(PostgreSQL JobStore, 클러스터 미적용). ai-server는 **stateless**(GPU Worker 별도 프로세스). 런타임은 Java 17 / Spring Boot 3.3 / React 18.
- **DB 소유권**: 저작도구 전용 LS_* 테이블은 자체 소유·구성, 관제서버 공유 MNG_* 9개는 JPA `ddl-auto=validate`로 읽기 참조한다. MNG_* 변경은 관제서버팀 선승인 필수이므로 통합시험 환경에서 공유 스키마 정합이 전제된다(RISK-002).
- **외부 의존성**: 비식별 솔루션은 발주기관이 직접 구매·제공(RQ-SFR-09-01). 생성형 AI 증강 본체·VLM 모델 본체·영상 합성 본체는 외부 시스템 책임이며, 저작도구는 연동(호출/콜백 수신)과 결과 검수만 시험 대상으로 한다. 외부 미가용 시 통합시험은 Mock/스텁으로 대체한다.
- **인증**: 저작도구는 독립 로그인 UI가 없으며 관제서버/포털이 발급한 JWT를 인계받아 검증한다. 시험 시 발급기와 동일 시크릿으로 생성한 테스트 토큰을 사용한다.
- **연동 deprecated**: 관제/포털 양방향 M2M 통합 인프라는 deprecated이며 시험 대상이 아니다(RISK-004). 단, 저작도구 → 관제서버 단방향 outbound 통지(TASK_COMPLETED/TASK_MODIFIED)는 시험 대상에 포함한다.
- **범위 외**: 데이터마트 구축·검색·다운로드, 생성형 AI 모델 학습/파인튜닝, 학습데이터셋 Export, 포털 사용자 업로드·오토라벨링·버전관리·검수(ADR-013)는 시험 대상에서 제외한다.
- **일정 표기**: 본 계획서는 설계 단계 산출물로, 절대 날짜·담당자 실명 미확정 항목은 **상대 단계·역할 추상 표기**로 기재한다(부록 사유 ②).

###### 3.2.1 단위시험

- **대상**: backend 도메인/서비스 로직(라벨링·버전 스냅샷·검수 전이·통지 발행·비식별 호출), ai-server 추론 함수(YOLO/SAM2/VLM 어댑터). CVAT 포팅 모듈(트랙 보간·MASK↔RLE↔Polygon·좌표 변환)은 단위시험 필수.
- **방법**: JUnit 5 + Testcontainers(PostgreSQL)로 영속성·트랜잭션 포함 검증, ai-server는 pytest. 테스트 메서드명은 한글 서술형(`본인_배정이_아닌_프레임_편집_시_403`).
- **합격기준**: `verification_method=automated_test`인 AC(AC-002~008, AC-010, AC-011)의 then·and_examples 단계가 단위/슬라이스 테스트로 검증됨. 에러 케이스(400/403/409, 서킷브레이커 동작)도 포함.
- **산출물 ID**: 단위시험 ID `KLID-AT-UT-NNN`(D11 참조).

###### 3.2.2 통합시험

- **대상**: API 엔드포인트 통합 흐름, 배치 파이프라인 단계 연계(MarkingCompletedEvent → BATCH_QUEUED → BatchOrchestrator → 각 Step → COMPLETED/FAILED 전이), 외부 연동(DeidentifyClient·AiServerClient·VlmClient·ExternalAugmentClient·ControlNotifyClient).
- **방법**: Spring Boot Test 기반 API 통합 테스트. 외부 연동은 Mock(WireMock/스텁) 우선, dev 환경 가용 시 실연동 보조. 콜백 흐름(VLM result·증강 result·관제 통지)은 idempotency·dead-letter·재등록 큐까지 검증.
- **합격기준**: AC scenario(given/when/then) 및 and_examples(콜백 검증 실패·상태 충돌·디바운스 등)가 통합 시나리오로 충족됨. 비식별 비대상(ANONY) 미호출·원본 보존, PRVC/PSDO만 비식별 호출 등 분기 검증.
- **산출물 ID**: 통합시험 시나리오 ID `KLID-IT-TS-NNN`(D10 참조).

###### 3.2.3 시스템시험

- **대상**: 비기능 요구사항 NFR-001~007 전체.
- **방법 및 합격기준**(NFR 목표값 = 합격기준):
  - NFR-001 성능: 배치 파이프라인 처리율 **≥ 1건/분** — Micrometer Timer/Counter 수집, Prometheus 집계로 측정.
  - NFR-002 확장성: 누적 이미지 학습데이터 **≥ 100,000장** — LS_DATA_SRC 누적 건수 집계.
  - NFR-003 확장성: 누적 영상 학습데이터 **≥ 5,000건**(30초 이상/건) — LS_DATA_RAW 누적 건수 집계.
  - NFR-004 가용성: 외부 API 연동 Resilience4j 적용률 **= 100%** — common.client.* 빈별 정책 적용 점검 + external.api.duration Timer 수집.
  - NFR-005 보안: 민감정보(PII·토큰) 로그/페이로드 노출 **= 0건** — Logback 마스킹 패턴 점검 + Fortify/CodeQL(Privacy Violation) 정적 검사.
  - NFR-006 접근성: 포털 웹 **WCAG 2.1 AA** — axe 등 자동 점검 + 수동 검수.
  - NFR-007 관찰가능성: 핵심 이벤트(API·배치·외부호출) 메트릭 수집률 **= 100%**, traceId MDC 부여·X-Trace-Id 전파 — /actuator/prometheus 노출 점검 + 로그 traceId 포함 확인.
- **산출물 ID**: 시스템시험 ID `KLID-ST-NNN`(D7 참조).

###### 3.2.4 인수시험

- **대상**: R1 SFR 16 + NFR 7의 발주 요구사항 충족 여부, 핵심 업무 시나리오(라벨링→검수 승인→완료 통지, 증강 수신→검수, 비식별 처리, 버전 비교·복구, 포털 Load·저장·다운로드).
- **방법**: 발주자(지방정부) 주도, prd(운영) 환경에서 인수 체크리스트 기반 수동 검증. 프로젝트시험팀이 지원한다.
- **합격기준**: 각 AC statement 및 R1 검수기준 충족, NFR 목표값 시스템시험 통과 증빙 확인.

#### 4. 시험 실행 계획

##### 4.1 시험 수행 절차

##### 4.2 발견된 문제점(결함)에 대한 수정 절차

- 결함 발견 → 결함 등록(심각도·재현절차·기대/실제 결과) → 응용개발팀 분석·수정 → 단위/회귀 테스트 통과 확인 → 시험팀 재시험(retest) → 종결.
- 심각도 분류: Critical(시험 중단·핵심 기능 불가) / High(우회 불가 결함) / Medium(우회 가능) / Low(경미). Critical/High는 차기 시험 단계 진입 차단 조건으로 둔다.
- 회귀 방지: 결함 수정 시 해당 결함을 재현하는 자동화 테스트(단위/통합) 추가를 원칙으로 한다.
- 보안 결함: Fortify/CodeQL 지적 항목은 security.md 기준(OWASP Top 10 2025 / CWE Top 25) 통과 전까지 종결하지 않는다.

##### 4.3 시험 툴 사용 계획

- **단위**: JUnit 5, Testcontainers(PostgreSQL), Mockito, AssertJ / ai-server: pytest.
- **통합**: Spring Boot Test(`@SpringBootTest`), WireMock/스텁(외부 연동 Mock), QueryDSL 검증, Playwright(FE E2E).
- **성능/부하**: Micrometer + Prometheus(메트릭 수집), k6 또는 JMeter(부하 — 도구 최종 선정 미정, 부록 사유 ③).
- **보안**: Fortify Static Code Analyzer, GitHub Advanced Security(CodeQL), Dependabot(의존성 CVE 스캔).
- **접근성**: axe 등 자동 점검 도구 + 수동 검수.
- **관찰가능성**: /actuator/prometheus, traceId(X-Trace-Id) 전파 점검.
