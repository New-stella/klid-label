## description

검수 완료(APPROVED) 영상을 수정했을 때 관제서버로 TASK_MODIFIED 를 push 하는 흐름. LabelService.bulkUpsert 는 먼저 비식별 신고 게이트를 평가해 DE_IDNTF_YN='F' 면 412 로 차단하고(락 검사보다 먼저 — 응답 코드가 잠금 상태 오라클이 되지 않게 409/412 로 갈리지 않게 한다), 정상이면 full-replace upsert 후 isReviewApproved 가 true 일 때만 TaskModifiedEvent(exportRegenerated=true)를 발행한다. ★재생성·통지의 트리거 = 재검수 승인이고 발송 시점 = export 성공 이후다(2026-08-07 확정, 구속) — 수정 이벤트는 항상 활성인 TaskModifiedAccumulateListener(AFTER_COMMIT)가 영상 1건 단위로 디바운스 축적하고, 같은 이벤트가 재검토 표시(LS_RAW_DATA_STATUS.REVLT_YN='Y')를 세워 그 표시가 서 있는 동안 만료 flush 를 보류시킨다(LsMonNotiAcmlRepository 가 flush 후보 조회와 클레임 UPDATE 두 곳에서 축적분을 제외한다). 검수자가 그 수정을 다시 검수해 승인하고 ReviewService.approve 가 표시를 해제하면, 풀린 축적분을 다음 flush tick 이 DatasetExportBridge → AsyncDatasetExportRunner 로 위임해 산출물을 <새 버전 폴더 v{n+1} 으로 전량 재생성>한 뒤, SUCCEEDED 가 되면 DatasetExportCompletedEvent 를 발행해 ControlNotifyEventListener 가 비로소 통지를 보낸다. 재승인은 ReviewApprovedEvent 를 발행하지 않으므로(중복 방지) 재생성과 TASK_MODIFIED 는 디바운서가 내고, 최초 승인만 그 이벤트로 강제 재생성 후 TASK_COMPLETED 를 낸다. 수정 횟수와 무관하게 재승인 1건이 새 버전 폴더 1개와 통지 1건에 대응한다. 수정 후 재승인 전까지 관제는 직전 승인본을 본다 — 학습데이터는 검수를 통과한 것만 확정이므로 인지하고 수용한 선택이다. ⚠ 구 정책 — 디바운스 창이 만료되는 것만으로 재생성·통지가 나간다 — 는 폐기됐다. export 가 @Async 라 통지가 앞서면 관제가 V_COMPLETED_VIDEO.OUTPUT_PATH_NM 을 조회할 때 <구 버전 폴더>를 픽업하게 되기 때문이다. export 가 실패하면 통지를 <보류>하고 DatasetExportFailureRecoverer 가 재산출 성공 후 재개한다(통지 유실이 아니라 성공 시점으로 지연). ⚠ 재-export 트리거(DatasetExportBridge·수정 축적·디바운스 flush)는 authoring.control-notify.enabled 토글과 <무관하게 항상 동작>한다 — 그 토글은 발송(sendCompleted/sendModified)만 게이팅하며, 그래서 수정 이벤트 소비가 ControlNotifyEventListener 에서 분리된 것이다(구 구조에선 토글 off 시 수정 이벤트가 소비자 없이 드롭돼 export 가 재생성되지 않았다). 페이로드는 다음으로 구성된다 — job_id(RAW_SN) + changed_items(images·jsons = 산출 폴더의 실제 파일명 {FRM_NO 4자리 zero-pad}.jpg/.json) + ver_expln(선택) + output_ver_no(선택). changed_items 의 범위는 export 재생성을 동반했는지로 갈린다 — 동반이면 전 프레임 이미지·JSON 을 싣고(비우면 관제가 재픽업을 안 해 보유본이 stale 로 고착된다), 재생성이 없으면 빈 리스트가 정상이며(없는 파일을 실으면 관제가 404 를 맞는다) 어느 경우든 통지 자체는 발송된다. output_ver_no 는 이 통지가 대응하는 산출 폴더 버전 번호이고 ver_expln 과 같은 규약으로 null 이면 키를 생략하며, 관제는 키 없음을 "산출물 변경 없음 — 재픽업 불요" 로 읽는다. ★ 마지막 수정 일시 · 변경 종류(LABEL_ADDED|LABEL_UPDATED|LABEL_DELETED|META_UPDATED) · 변경 요약 카운트 · 요청 ID 는 지금은 관제로 보내지 않는다 — 변경 종류는 내부 디바운스 축적 키와 감사 기록으로만 쓰고, 요청 식별자(UUID)는 폴백·재등록 큐의 내부 키다. data_info 도 싣지 않는다(관제 명세에 키 스키마가 없어 추정 스키마로 만들면 422 로 거부되거나 잘못된 값이 적재된다). 라벨/메타 본문 데이터는 포함하지 않으며 관제는 수신 후 저작도구 조회 API 를 호출해 상세를 가져간다. ver_expln 은 관제 dataset_versions.ver_expln(NOT NULL) 조달용이고 판정 단일 원천은 VersionExplanationPolicy 다(복제 금지). optional 이라 null 이면 키를 생략하는데(@JsonInclude NON_NULL) 이는 NOT NULL 컬럼에 명시적 null 을 보내는 것보다 안전하기 때문이며, 완료 통지(TASK_COMPLETED)의 "required 는 null 이어도 키를 남긴다"와 정반대인 <의도된 비대칭>이다. 전송 실패 시 fallbackService.enqueuePending 으로 dead-letter·재등록 큐에 쌓는다. 같은 재-export·재통지 경로를 타는 수정은 개수가 아니라 성질로 정해진다 — 사람이 콘텐츠를 고치는 모든 경로가 대상이고 제외는 넷뿐이다(외부 시계열 콜백 · 비식별 누락 신고 접수 · 운영자 정정 배치 · 이벤트 어노테이션 지연 승인). 판정 기준은 사람이 산출물에 들어가는 내용을 바꿨는가 하나다. 예시 — 라벨 수정(LabelService) · 트랙 편집(TrackEditService) · 트랙 병합(TrackMergeService) · 버전 롤백(VersionService) · 촬영환경 수정(EnvironmentMetaService) · 프레임 설명 수정(FrameDescriptionService) · 개인정보 메타 수정(영상 축 VideoPrivacyMetaService · 프레임 축 FramePrivacyMetaService) · 메타 수동 편집(MetaService) · 이벤트 어노테이션 저장(EvntAnnoService). 산출물은 버전마다 전체 자기완결이고 전 버전을 보존한다(retention 정리 로직을 만들지 않는다) — 델타만 두면 사업 요구의 '복구(rollback)' 가 성립하지 않기 때문이며, OUTPUT_PATH_NM 은 버전 루트가 아니라 영상 루트({rawSn})를 가리켜 관제가 v1·v2 를 한 경로 아래에서 보고 고를 수 있게 한다. 경로·필드명은 관제 정본과 정합 완료이며, 인증만 미확정으로 남아 관제 회신 대기 중이다 — 관제 정본은 x-access-token 헤더를 요구하나 아웃바운드 통지는 인증 헤더를 부착하지 않는다.
