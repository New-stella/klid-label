# D8 엔티티 관계 모형 설계서

> **ID 표기 규칙(공통)**: 본 산출물의 모든 ID(KLID-AT-UC/CO/DC/DCD/SD/SC/AC/EN/ERD/TB/II/IC/IF/UCD/ACT 등)는 **전체 형식 `KLID-AT-XX-NNN`** 으로 표기한다. 끝부분만(예: `UC-001`) 약식 표기 금지. 범위는 시작 ID만 전체형으로(예: `KLID-AT-UC-001~013`). ※ 요구사항(RQ-SFR-NN-NN)·시스템시험(KLID-ST-NNN) 등 타 체계 ID는 각 체계 원형 유지.

## 작성 목적
> 시스템의 요구사항을 만족하기 위한 주요 엔티티 및 엔티티간의 관계를 표현하고 엔티티에 대한 명세를 기술한다.

## 작성 방법
> 논리적 데이터 모델링을 통한 엔티티 관계 모형도(ERD)를 작성하여 엔티티를 식별한다. 작성한 엔티티 관계 모형도와 개념적 클래스도를 비교하여 볼 필요가 있다. ERD에서는 엔티티가 모두 속성을 가져야하나 개념 클래스는 속성이 없는 기능만을 가진 클래스가 존재할 수 있다. 식별한 엔티티는 각각 상세한 명세를 작성한다.

### 1. 엔티티 관계도(ERD)

> 학습데이터 저작도구가 직접 소유·구성하는 엔티티를 업무 도메인별 17개 ERD로 분리하여 작성한다. 모든 엔티티 관계는 작업 단위 식별자인 **원시영상**과 **프레임원천**을 앵커로 연결된다. 관제지원시스템이 소유하는 공유 스키마와 스케줄러 운영 스키마는 물리 설계 비대상이므로 본 산출물의 엔티티 목록에서 제외하고 부록에 참조 사실만 남긴다.
>
> **ERD 표기 규칙**: 엔티티명·속성명은 **논리 업무 한글명**으로 표기하고, 속성 앞의 타입은 이해를 돕기 위한 약식 표기다(정식 타입·길이는 §2 속성표, 물리 저장 정의는 D9 데이터베이스설계서). 실선(`--`)은 참조 무결성이 선언된 관계, **점선(`..`)은 물리 외래키를 선언하지 않은 논리 참조·운영 연관**을 뜻한다.

### 2. 엔티티 명세서

> 엔티티를 ERD 순서로 오름차순 명세한다. `타입`은 물리 DBMS 타입(PostgreSQL 기준)으로 표기하고 길이는 별도 칸에 기입한다. `동의어`는 표준용어에 정합하지 않은 별칭 속성이 있을 때만 기입한다. `PK`·`FK`·`INX` 칸은 해당하는 경우에만 `Y`를 표기한다. 인덱스 정의·삭제 규칙·검사 제약 등 물리 저장 상세는 D9(데이터베이스설계서)에서 다룬다. `관련 클래스 ID`는 D1(클래스 설계서)의 설계 클래스 ID(`KLID-AT-DC-NNN`)와 동일 체계로 매핑하며, D1에 설계 클래스로 정의되지 않은 부속·이력·인프라 엔티티와 R1 기능 요구사항 유스케이스가 사용하지 않는 도메인 엔티티는 `- ※` + 사유로 표기한다.

### 엔티티 관계도(ERD)

- **ERD ID**: ERD별로 유일한 ID를 부여하여 기입한다.
- **ERD 명**: ERD의 이름을 부여하여 기입한다.

### 엔티티 명세서

- **엔티티 ID**: 엔티티별로 유일한 ID를 부여하여 기입한다.
- **엔티티명**: 도출된 엔티티의 명칭을 기입한다.
- **관련 클래스 ID/명**: 엔티티에 대응하는 D1 "클래스 설계서"의 설계 클래스 ID(`KLID-AT-DC-NNN`)와 명칭을 기입한다.
- **관련 유스케이스 ID**: 본 엔티티를 사용하는 "유스케이스 명세서"(R2)의 유스케이스 ID를 기입한다(R1 요구사항 연관은 R2·R3 경유).
- **엔티티 설명**: 엔티티에 대한 간단한 설명을 기술한다.
- **속성명**: 논리 업무 한글명을 기입한다.
- **동의어**: 표준화되지 못한 별칭 속성명이 있을 때만 기입하고, 없으면 공란으로 둔다.
- **타입**: 물리 DBMS 타입(PostgreSQL 기준)을 기입한다.
- **길이**: 속성의 최대 허용 길이를 기술한다.
- **NOT NULL**: 필수항목 여부를 `Y`/`N`로 기술한다(필수=`Y`, 선택=`N`).
- **PK(Primary Key)**: 주키인 경우만 `Y`, 아닌 경우 공란.
- **FK(Foreign Key)**: 외래키인 경우만 `Y`, 아닌 경우 공란.
- **INX(Index)**: 인덱스에 포함되는 경우만 `Y`, 아닌 경우 공란.
- **기본값**: 속성의 기본값이 있는 경우에 그 값을 기재한다.
- **제약조건**: 속성의 특이한 제약조건이 있는 경우 기재한다.

## 작성 시 참고사항

> **ID 체계 (프로젝트 공식)**
> - 프로젝트 ID: `KLID`
> - 서브시스템 ID (저작도구): `AT`
> - 산출물 파일명: `KLID_AT_엔티티관계모형설계서_Rev {버전}`
> - 본 산출물에서 사용하는 ID:
>   - ERD ID: `KLID-AT-ERD-NNN`
>   - 엔티티 ID: `KLID-AT-EN-NNN`
>   - 관련 클래스 ID: `KLID-AT-DC-NNN` (D1 참조)

## 부록. 데이터 부재·범위 제외 사유

### A. 범위 제외 — 공유 스키마 (물리 설계 비대상)

| 구분 | 대상 | 제외 사유 |
|------|------|-----------|
| 관제지원시스템 공유 스키마 | 관제 소유 영상·CCTV·계정·이벤트 마스터 | 관제지원시스템이 소유·구성하는 공유(READ) 스키마다. 저작도구는 참조만 하며 물리 설계 책임이 없다. 관제 인입 경로 전환에 따라 저작도구의 직접 참조는 관제인입(KLID-AT-EN-005)으로 일원화되었다. |
| 스케줄러 운영 스키마 | 배치 스케줄러 운영 테이블군 | 스케줄러 제품이 정의·제공하는 운영 스키마다. 저작도구가 설계하지 않으며 인프라 구성 산출물에서 다룬다. |
| 공통 코드 | 공통 코드 저장소 | 관제지원시스템과 공유하는 공통 코드 테이블로, 변경 시 관제서버팀 사전 승인이 필요한 공유 자산이다. 저작도구 소유 엔티티가 아니므로 목록에서 제외한다. |

### B. `- ※` 표기 사유 구분

| 표기 위치 | 사유 유형 | 해당 엔티티 |
|-----------|-----------|-------------|
| 관련 클래스 ID | D1에서 별도 설계 클래스로 분리하지 않은 부속·이력·마스터·인프라 엔티티 (성격상 부재) | 각 엔티티 설명의 ※ 문구 참조 |
| 관련 유스케이스 ID | R1 기능 요구사항에서 도출된 R2 유스케이스가 직접 사용하지 않는 도메인 엔티티 — 사용자·권한, 게시판, 포털 채널, 작업 배정 운영, 운영 인프라 (성격상 부재) | 각 엔티티 설명의 ※ 문구 참조 |

### C. 속성표 `-` 표기

- `길이` 칸의 `-` : 고정 길이가 정의되지 않는 타입(정수형·타임스탬프·대용량 텍스트·JSON 등)이다.
- `기본값` 칸의 `-` : 기본값을 정의하지 않은 속성이다.
- `제약조건` 칸의 `-` : 유일성·참조·값 범위 등 별도로 명시할 제약이 없는 속성이다.

### D. 표준용어 정합 확인 필요 속성 (후속 정정 대상)

> 아래 속성은 물리 명칭이 사업 표준용어 조합 규칙에 정합하지 않는다. 본 산출물은 확정된 현행 모델을 기술하는 것이 목적이므로 명칭을 임의로 바꾸지 않고 `동의어` 칸에 별칭으로 표기하며, 정정은 별도 표준 정합 작업에서 수행한다.

| 엔티티 | 속성명 | 확인 필요 사유 |
