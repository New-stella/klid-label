# 비식별 처리 요청

## goal

전체 영상(ANONY 포함)을 외부 KPST 비식별 솔루션에 위탁(폴링 연동)해 개인정보를 비식별하고 원본·비식별본을 각각 저장한다. 배포 설정 제외 목록에 든 출처유형 영상은 위탁 없이 원본 복사로 비식별을 완료한다.

## description

전체 영상(PRVC/PSDO/ANONY 구분 없이)을 Resilience4j 정책을 적용한 연동으로 외부 KPST 비식별 솔루션에 위탁한다 — 비식별이 파이프라인 선두 단계다(게이팅 폐지).

[출처유형 제외] 위 전체 영상 위탁에는 출처유형 제외라는 예외가 있다([[ADR-066]] — ADR-006 을 대체하지 않고 예외를 더한다). 선두 비식별 단계가 영상을 처리하는 시점에 한 번, 영상의 출처유형(LS_DATA_RAW.SRC_TYPE)이 배포 설정 authoring.deidentify.excluded-src-types(기본값 GENERATED)의 제외 목록과 정확히 일치하면 외부 솔루션에 위탁하지 않는다. 대신 원본 영상을 비식별 영상 쓰기 위치에 원본 파일명 그대로 일반 파일로 복사하고, LS_DEIDENT_PROC_LOG 에 요청종류코드 REQ_KND_CD=EXCLUDED 인 성공 행(비식별 영상 경로=복사본 경로)을 남긴 뒤 영상 비식별 여부 'Y'·배치 단계 MARKING_READY 로 전이한다 — 외부 호출도 진행 상태 폴링도 없다. 복사에 실패하면 영상 비식별 여부 'F' 와 요청종류 EXCLUDED 인 FAILED 행을 남기고 MARKING_READY 로 전이하지 않으며 원본은 삭제하거나 수정하지 않는다. 판정 결과는 영상별 이력에 고정돼 설정 변경을 소급하지 않고, 설정이 비면 모든 영상을 위탁한다. 검수 완료 영상의 재비식별은 이 제외 축을 타지 않고 항상 외부 솔루션에 위탁한다. 출처유형이 잘못 인입된 영상의 회수 지점은 검수다 — 검수자가 검수 중 비식별이 필요하다고 판단하면 기존과 같이 비식별 누락 신고 → 외부 비식별 솔루션으로 재비식별 → 신고 해소로 회수하며, 승인 이력이 있는 영상은 신고를 받지 않는 기존 정책이 그대로라 승인 이후와 그 파생본은 이 경로 밖이다.

[위탁·수신] 위탁(경로 참조로 프로젝트 생성) 후 주기 폴링(진행조회)으로 완료를 감지하고 산출 경로를 회수한다(별도 결과 콜백 없음 — 구 수신 경로 POST /v1/deidentify/result 폐기). 비식별본은 STORAGE_DEIDENTIFIED_PATH 에 저장하고 원본은 보존한다.

[★제출은 논블로킹] createProject 를 동기로 기다리지 않고 WAITING 원장 행을 선커밋한 뒤 비동기 디스패치한다(VLM 위탁과 대칭). 스텝이 확정적으로 말하는 사실은 '제출을 개시했다' 뿐이다. 4노드 Active-Active 에서 같은 후보를 둘이 집어 두 번 회수하지 않도록 조건부 UPDATE 원자 클레임으로 막는다 — 원자 클레임 원칙 자체는 두 축 공통이다. ⚠ [폐기] 구 서술 '2노드 중복 재위탁은 조건부 UPDATE 원자 클레임으로 막는다' — 비식별 축은 재위탁을 하지 않으므로 중복되면 안 되는 것은 재위탁이 아니라 회수다.

[★회수 경로는 축마다 다르다] 시계열은 전용 미결 스위퍼가 집어 재위탁하고, 비식별은 전용 스위퍼가 없이 폴링 잡이 ACK 대기 유예 만료로 회수해 실패 코드로 원장을 마감한다(재위탁하지 않는다). 비식별 쪽 회수는 「우리가 ACK 를 관측하지 못했다」는 뜻이지 「외부에서 실패했다」가 아니다 — 다만 그 회수는 제출 확정 실패와 같은 종결 경로를 타므로 원장을 실패로 마감하고 영상 비식별 여부도 'F' 로 내린다. 유예 만료 회수에 별도 종료 사유 코드(KPST_ACK_MISSING)를 두는 까닭은 영상 상태를 달리하기 위해서가 아니라 운영 조치를 가르기 위해서다 — 그 코드가 남았다는 것은 우리 프로세스가 수락 응답을 관측하지 못했다는 뜻이라 외부에는 프로젝트가 실제로 생성돼 있을 수 있어, 사람이 외부 상태를 확인해야 하는 건으로 식별된다. 외부 터미널 상태·폴링 경과 만료·불완전 산출물·제출 확정 실패(KPST_SUBMIT_FAILED)도 같은 종료값을 세우며, 영상 비식별 여부가 불변인 예외는 호출자 트랜잭션 롤백에 따른 취소 종결(KPST_SUBMIT_CANCELED) 하나뿐이다 — 외부로 아무것도 나가지 않았기 때문이다. 제출 신호가 노드와 함께 사라지면 실패 행조차 남지 않아 재시도 큐·실패 회수기가 집지 못하므로, 각 축의 이 회수 경로가 유일하다. ⚠ [폐기] 구 서술 '아무 신호도 오지 않으면 실패 행조차 없으므로 미결 스위퍼가 유일한 회수 경로다' — 비식별 축의 회수 주체는 스위퍼가 아니라 폴링 잡이고, 그 회수는 재위탁이 아니라 실패 코드 마감이다. 되살리지 말 것. ⚠ [폐기] 구 서술 '수락 응답 미관측에 따른 유예 만료 회수는 영상 비식별 상태를 실패로 내리지 않는다' — 코드 실측 결과 거짓이다. 그 회수도 제출 확정 실패와 같은 종결 경로를 타 영상 비식별 여부를 'F' 로 내린다. 되살리지 말 것.

[재생 인덱스 재배치 — ADR-072] 외부 솔루션이 만든 산출물은 재생 인덱스가 파일 끝에 있을 수 있어 브라우저가 부분 요청으로 재생할 때 시작이 늦고 재생 중 끊긴다. 그래서 비식별 완료가 확정돼 산출 경로가 기록된 뒤 인덱스가 파일 앞에 있지 않으면 재인코딩 없이 인덱스만 앞으로 옮긴다. 경로·파일명은 바꾸지 않고(관제는 기록된 경로로 산출물을 가져간다), 작업용 파일은 결과 회수가 산출물로 오인하지 않는 위치에 두며, 대용량 파일 입출력은 데이터 트랜잭션 밖에서 한다. 실패해도 비식별 완료를 되돌리지 않고 실패 사실만 기록한다. 인덱스가 이미 앞에 있으면 아무것도 하지 않으며, 동시에 실행되는 수를 제한한다. 검수 완료 후 재비식별 회차에도 같다. 출처유형 제외 복사본은 대상이 아니다.

[★실패 처리 — 자동 재시도 큐 없음] 실패 시 DE_IDNTF_YN='F' 마킹 + 원본 절대 삭제 금지. 구 서술의 '재시도'는 자동 재비식별 큐를 뜻하지 않는다 — 그 큐는 폐기됐고, 작업자/검수자가 외부 솔루션으로 **수동 재비식별** 한 뒤 resolve 로 해소한다(UC-016). [선두 비식별 실패의 수동 재시작] 신고 없이 선두 비식별 단계가 실패해 마킹 준비에 이르지 못한 영상(영상 비식별 여부 'F' · 배치 단계 PENDING)은 비식별 실패도 배치 실패로 보고, 검수자가 기존 배치 재시작(건별 [[API-167]] · 일괄 [[API-199]])으로 선두 비식별 단계를 다시 요청할 수 있다. 새 창구·새 버튼은 두지 않는다. 사람이 눌러야만 도는 수동 재시작이라 자동 재비식별 큐를 두지 않는다는 결정([[ADR-006]])과 양립하며, 자동 재시도·스윕·스케줄은 추가하지 않는다. (R2 UC-011, RQ-SFR-09-01/02)

- 출처유형 제외 복사 실패 — 영상 비식별 여부 'F', REQ_KND_CD=EXCLUDED 인 FAILED 행이 남고 MARKING_READY 로 전이하지 않으며 원본은 바뀌지 않는다
- 외부 솔루션 위탁으로 완료된 산출물은 재생 인덱스가 파일 앞에 있다 — 재배치가 실패한 경우에는 원래 산출물과 기록된 경로가 그대로다
- 선두 비식별 실패 후 배치 재시작이 성공하면 영상 비식별 여부 'Y' · 배치 단계 MARKING_READY 가 되고, 성공·실패와 무관하게 그 요청이 잡은 작업 잠금이 풀려 다시 요청할 수 있다

## alternate_flows

### 비식별 연동 실패

**steps**:

- DE_IDNTF_YN='F' 로 마킹하고 원본을 보존한다(원본 절대 삭제 금지)
- LS_DEIDENT_PROC_LOG 에 실패 상태와 오류 정보를 기록한다
- ⚠ 자동 재비식별 큐는 없다 — 작업자/검수자가 외부 솔루션으로 수동 재비식별한 뒤 resolve 로 해소한다(UC-016)
- 신고 없이 선두 비식별 단계가 실패해 마킹 준비에 이르지 못한 영상은 검수자가 배치 재시작으로 다시 요청할 수 있다 — 대안 흐름 「선두 비식별 실패 후 배치 재시작」

- **trigger**: 외부 호출 실패

### 응답 유실

**steps**:

- 수락 응답도 결과 회신도 관측되지 않은 건은 폴링 잡이 ACK 대기 유예 만료로 회수해 실패 코드로 원장을 마감한다 — 비식별 축에는 전용 미결 스위퍼가 없고 재위탁도 하지 않는다. 제출 신호가 노드와 함께 사라지면 실패 행조차 남지 않아 재시도 큐·실패 회수기가 집지 못하므로 이 회수 경로가 유일하다
- 이 회수도 제출 확정 실패와 같은 종결 경로를 타 원장을 실패로 마감하고 영상 비식별 여부를 'F' 로 내린다 — 종료 사유 코드(KPST_ACK_MISSING)를 따로 두는 까닭은 영상 상태를 달리하기 위해서가 아니라 운영 조치를 가르기 위해서다. 그 코드가 남았다는 것은 우리가 수락 응답을 관측하지 못했다는 뜻이라 외부에는 프로젝트가 실제로 생성돼 있을 수 있어, 사람이 외부 상태를 확인해야 하는 건으로 식별된다
- 수락 대기 창(ACK)과 결과 대기 창(콜백)을 구분해 정상 위탁 건을 잘못 회수하지 않는다
- 4노드 Active-Active 에서 같은 후보를 둘이 집어 두 번 회수하지 않도록 조건부 UPDATE 로 원자 클레임한다 — 원자 클레임 원칙 자체는 두 축 공통이다

- **trigger**: 제출 후 아무 신호도 관측되지 않음

### 비식별 누락 신고 구간

**steps**:

- 해당 영상에 열린 비식별 누락 신고가 있어 비식별 재처리 대기(DE_IDNTF_YN='F') 상태이면 외부 위탁을 개시하지 않고 보류한다
- 열린 신고가 있는 영상의 배치 재시작 요청은 409 로 거부한다 — 그 'F' 는 신고 표식이며 해소는 외부 솔루션 수동 재비식별 뒤 신고 해소 경로(UC-016)로 한다

- **trigger**: 신고 구간 영상의 재처리 요청·배치 재처리

### 출처유형 제외(원본 복사)

**steps**:

- 외부 비식별 솔루션에 위탁하지 않는다 — 외부 호출이 없고 진행 상태 폴링도 하지 않는다
- 원본 영상을 비식별 영상 쓰기 위치에 원본 파일명 그대로 일반 파일로 복사한다(링크를 두지 않는다). 원본은 보존한다
- LS_DEIDENT_PROC_LOG 에 REQ_KND_CD=EXCLUDED 인 성공 행(PROC_STTS_CD=SUCCEEDED, DE_IDNTF_FILE_PATH_NM=복사본 경로)을 남긴다
- 영상 비식별 여부를 'Y' 로, 배치 단계를 MARKING_READY 로 전이한다 — 외부 위탁이 동기로 완료된 경우와 같은 흐름으로 이어진다
- 제외 행은 외부 진행 상태를 갖지 않으므로 진행 상태 폴링과 ACK 대기 유예 만료 회수의 대상이 아니다. 판정 결과는 영상별 이력에 고정돼 설정 변경을 소급하지 않는다
- 검수 완료 영상의 재비식별은 이 흐름을 타지 않고 항상 외부 솔루션에 위탁한다. 출처유형이 잘못 인입된 영상은 검수에서 회수한다 — 검수자가 비식별이 필요하다고 판단하면 기존 비식별 누락 신고 → 외부 재비식별 → 신고 해소 경로를 타며, 승인 이력이 있는 영상은 신고를 받지 않는다

- **trigger**: 선두 비식별 단계가 처리하는 영상의 출처유형(LS_DATA_RAW.SRC_TYPE)이 배포 설정 authoring.deidentify.excluded-src-types 제외 목록(기본값 GENERATED)과 정확히 일치한다

### 출처유형 제외 복사 실패

**steps**:

- 영상 비식별 여부를 'F' 로 둔다
- LS_DEIDENT_PROC_LOG 에 REQ_KND_CD=EXCLUDED 인 FAILED 행을 남긴다
- 배치 단계를 MARKING_READY 로 전이하지 않는다
- 반쯤 쓴 임시 파일은 정리하고 원본은 삭제하거나 수정하지 않는다

- **trigger**: 제외 대상 영상의 원본이 없거나 경로 위반·입출력 오류로 복사할 수 없다

### 재생 인덱스 재배치 실패

**steps**:

- 원래 산출물을 그대로 두고 실패 사실을 기록한다
- 영상 비식별 여부·배치 단계 전이·기록된 산출 경로는 되돌리지 않는다 — 재배치 실패는 재생이 불편해질 뿐 데이터는 온전하다
- 반쯤 쓴 작업용 파일은 정리한다. 작업용 파일은 결과 회수가 산출물로 오인하지 않는 위치에 둔다
- 재생 인덱스를 판정할 수 없는 산출물은 건드리지 않는다

- **trigger**: 완료 확정 뒤 재생 인덱스 재배치가 실패하거나 산출물의 재생 인덱스를 판정할 수 없다

### 선두 비식별 실패 후 배치 재시작

**steps**:

- 검수자가 영상 상세(SCREEN-009)의 배치 실패 패널에서 재시작을 누르거나(건별 API-167), 영상 목록(SCREEN-008)에서 여러 영상을 골라 일괄 재시작한다(API-199 — 1~100건, 건마다 건별과 같은 판정). 새 버튼은 없다
- 대상 영상이 없으면 404 로 거부한다. 작업자는 요청할 수 없다(403) — 검수자 전용이며 관리자는 역할 계층으로 포함된다
- 다음이면 거부하고 비식별을 다시 요청하지 않는다: 파생영상 400 · 승인 이력 있음 409 · 열린 비식별 누락 신고 있음 409 · 진행 중인 위탁 있음 409 · 같은 영상에 대한 동시 요청 409(여러 노드에서도 정확히 1건만 수락한다)
- 수락하면 접수만 하고 실행은 비동기로 한다 — 건별 응답은 {rawSn, stage} 200 이며 stage 는 접수 시점의 실제 단계(PENDING)다. 배치 단계를 PROCESSING 으로 선점하지 않는다. 일괄은 부분 성공을 허용하고 전건 거부여도 200 으로 접수 0건과 건별 사유를 돌려주며, 화면은 결과 창에 이를 보인다
- 적재 직후와 같은 선두 비식별 단계를 다시 수행한다 — 외부 솔루션 위탁 또는 출처유형 제외 원본 복사 중 어느 쪽인지는 처리 시점 설정으로 판정한다. 영상 비식별 여부를 'N' 으로 되돌리지 않는다
- 성공하면 영상 비식별 여부 'Y' · 배치 단계 MARKING_READY 가 되어 마킹에 들어갈 수 있다. 실패하면 비식별 연동 실패 흐름과 같이 'F' 로 남는다
- 성공이든 어떤 실패 종결이든 이 요청이 잡은 영상 단위 작업 잠금을 풀어 다시 요청할 수 있게 한다. 다른 기능이 잡은 잠금은 풀지 않는다
- 자동 재시도·스윕·스케줄은 없다 — 사람이 다시 누를 때만 재요청한다

- **trigger**: 선두 비식별 단계가 실패해 영상 비식별 여부 'F' · 배치 단계 PENDING(마킹 준비 미도달)인 영상에 대해, 검수자가 영상 상세의 배치 실패 재시작 또는 영상 목록의 일괄 재시작을 요청한다
