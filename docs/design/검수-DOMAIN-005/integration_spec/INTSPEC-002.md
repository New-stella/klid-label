## change_summary

이벤트 검증(verify) 콜백 규격을 폐기하고 describe(CoT)·describe-sub(VQA) 공용 콜백 수신 규격으로 재작성. results 는 description 단일이며 accuracy·detected 는 verify 전용이라 수신되지 않는다. 콜백 바디에 API 종류 식별자가 없어 request_id 로 축을 역조회한다. 5초 내 2xx·최대 3회 재전송·멱등·순서 무보장·유실 시 회수 수단 없음이라는 벤더 연동 유의사항을 명시했다. 무서명 3계층 방어·멱등 원장·직렬화·원자성은 유지. v4.1.0 — 수신 결과의 내부 귀속을 칸 단위로 확정(5·5-1 절): 묘사 전문은 시계열 서술 전문과 캡션 후보 c1 의 사고 단계 1단계(「상황」 줄 파싱), 추가 질문 응답은 같은 후보의 캡션 본문, 질문 칸은 저작도구 보관 목록에서 조달, 답변·근거 서술·2단계 이후는 공란. 두 창구의 캡션 후보 공유와 도착 순서 무보장 대응, 2026-08-24 확정 대비 반전 경위를 함께 기재했다. 외부 규격 자체는 무변경. v4.2.0 — 근거 판번호를 KLID 연동 API v1.2.0(개정일 2026-09-07)으로 올리고 제목의 판번호도 함께 고쳤다. ⚠ 규격서 파일명 접미가 `_pre` 라 사전배포판일 가능성이 있어 벤더 확답 대기 상태임을 근거 표기에 남겼다. ★ 콜백 규격 자체는 v1.1.0 과 동일하며(바디 모양·필드·재전송 최대 3회 각 5초·멱등 요구·순서 무보장 전부 무변경) 바꾼 것은 넷뿐이다. ① 추가 질문 축의 위탁 창구가 `describe-sub` → `custom` 으로 교체된 사실을 반영했다 — 위 v4.0 서술의 `describe-sub` 는 그 시점 기록이며 지금은 [폐기]다. 벤더는 그 창구를 계속 제공하고 우리가 쓰지 않는 것이며, 이미 그 창구로 받아 적재된 결과는 작업 결과라 보존한다. 콜백 바디에 창구 구분자가 없어 창구마다 별개 요청 식별자를 발급하고 원장 채널로 역조회해 축을 판정하는 구조는 그대로이고, 원장 채널 식별자 문자열은 창구가 바뀐 것이지 축이 바뀐 것이 아니므로 유지한다(1-2 절 신설). ② 인증 실패(401) 시 콜백이 아예 전송되지 않는다는 v1.2.0 §2.1 신설 조항을 수신측 관점으로 반영해, 콜백 미도착을 인증 실패·재전송 소진·분석 지연 셋으로 구분해 판정하도록 4절에 명시했다. 이에 맞춰 「무응답으로 끝나는 경우는 규격에 없다」는 기존 서술을 「수락된 요청에 한한다」로 정합했다. ③ 실패 콜백의 `error` 가 객체 `{code, message}` 로 적혀 있던 드리프트를 규격대로 문자열로 정정했다(예시·필드 정의 표 양쪽). 객체 스키마로 검증하면 실패 콜백이 전량 400 으로 거부되어 실패 사실 자체를 잃으므로 되살리지 말 것. ④ 일치도(accuracy)·탐지결과(detected) 가 판정 창구 전용이라 저작도구 경로에 애초에 생기지 않는다는 사실을 명시해, 산출물·데이터마트에 정확도가 없는 것을 결함으로 재보고하는 오분류를 차단했다. `custom` 을 여는 것이 `verify` 를 열 근거가 아님도 함께 못 박았다. API 키 값과 사용 여부는 규격서 밖 별도 전달이며 미수신이라 추정해 채우지 않고 확인 대기로 남겼다. 수신 규율 5개 줄·성공 예시·무서명 3계층 방어·이벤트 어노테이션 칸 단위 귀속·5-1 반전 경위·레거시 구간 키 보존은 바이트 그대로 두었고 삭제한 표제는 0건이다.

# VLM 시계열 서술 콜백 수신 규격 (저작도구 인바운드)

> 근거: 외부 벤더 확정 계약(KLID 연동 API v1.2.0, 개정일 2026-09-07) + 벤더 가이드(*"결론적으로 describe-sub 대신 custom 을 사용하시면 됩니다."*). ⚠ 규격서 파일명 접미가 `_pre` 라 사전배포판일 가능성이 있다 — 벤더 확답 대기. 저작도구가 위탁 요청 시 제공한 `callback_url` 로 벤더가 결과를 POST 한다.
> 결정: ① 인증 = **무서명** ② 범위 = 서술 생성 두 축(`describe` = 묘사·CoT, `custom` = 추가 질문·VQA)의 **공용 수신**. 경로는 `/v1/vlm/callback`.
> ★ **콜백 규격 자체는 v1.1.0 과 동일하다** — 바디 모양·필드·재전송 정책·멱등 요구·순서 무보장이 그대로다. v1.2.0 에서 이 수신 규격에 닿는 것은 ① 추가 질문 축의 위탁 창구가 `describe-sub` → `custom` 으로 바뀐 것 ② 인증 실패(401) 시 콜백이 아예 전송되지 않는다는 조항이 신설된 것 둘뿐이다. 그 밖의 값을 「갱신」이라며 바꾸지 말 것.

## ★ 이벤트 검증(verify) 은 연동 대상이 아니다
연동하는 위탁 엔드포인트는 `describe`(묘사)·`custom`(추가 질문) 둘뿐이며 `verify` 는 호출하지 않는다. 따라서 콜백의 `results` 에는 **일치도(accuracy)·탐지결과(detected) 가 없다** — 그 둘은 벤더 규격상 `verify` 전용 응답 필드다. 구 규격이 규정하던 `results.accuracy` 수신·검증·적재와, 그 값이 화면 전용이라 데이터마트 뷰·학습데이터 산출물에 나오지 않는다는 규율은 **규율 대상 자체가 사라져 함께 폐기**한다. 되살리지 말 것.

★★ **일치도(accuracy)·탐지결과(detected) 는 저작도구 경로에 애초에 생기지 않는다.** 두 값은 `verify` 창구에서만 제공되는데 우리는 그 창구를 연동하지 않으므로, 검수 화면·데이터마트 뷰·학습데이터 산출물 어디에도 정확도 값이 없는 것이 **정상이며 설계된 결과**다. *"산출물·데이터마트에 정확도가 없다"* 를 결함으로 **재보고하지 말 것** — 실제로 그 오분류가 있었다. 두 축에서 우리가 받는 결과 항목은 **`description` 하나뿐**이다.

★ **`custom` 을 여는 것이 `verify` 를 열 근거가 아니다.** 추가 질문 축의 위탁 창구가 교체된 것과 판정 창구를 연동하지 않는다는 결정은 별개 축이다.

그보다 앞선 구 규격이 `results` 를 `[{start_sec, end_sec, description}, …]` 구간 배열로 받던 방식도 **폐기 상태 그대로**다. 신·구 양쪽을 받아주는 무단 하위호환은 벤더 버그를 숨기므로 관대한 파싱 없이 거부하고 구조 힌트만 로그로 남긴다.

## 1. 엔드포인트

| 항목 | 값 |
|------|-----|
| Method | POST |
| Path | `/v1/vlm/callback` (저작도구가 `callback_url` 로 벤더에 제공) |
| Content-Type | application/json |
| 인증 | **없음**(벤더가 서명 헤더를 제공하지 않는다) |
| 수신 범위 | `describe`(묘사·CoT)·`custom`(추가 질문·VQA) 공용 |

## 1-1. ★ 인증 대체 — 무서명 3계층 방어
벤더가 서명 헤더를 제공하지 않아 서명 검증 미적용은 **확정 설계**다(임시 방편 아님). 대신:
1. **IP allowlist** `webhook.vlm.allowed-ip-cidrs` — 빈 값이면 미적용이다. local/dev 는 그대로 기동하고 운영 프로파일(stg/prd)은 기동을 막으며, `none` 은 명시적 미적용이다. 미설정 시 전면 차단(fail-closed)인 증강 콜백과 이 점이 다르다. 값 형식은 INT-003 을 따른다.
2. **rate limit + 본문 크기 상한** — 인증 이전 자원 소모 방지.
3. **요청 식별자 발급 게이트** — 저작도구가 발급한 적 없는 `request_id` 는 거부한다.

## 1-2. ★ 추가 질문 축의 위탁 창구가 바뀌었다 — 콜백 해석 구조는 그대로다
- **[폐기] `describe-sub`** — 추가 질문 축의 위탁 창구로 **두지 않는다**(설계 결정). 근거는 벤더 가이드 *"결론적으로 describe-sub 대신 custom 을 사용하시면 됩니다."* 다. ⚠ **벤더는 그 창구를 계속 제공하며 우리가 쓰지 않는 것**이지 창구가 없어진 것이 아니다.
- **이미 `describe-sub` 로 받아 적재된 결과는 보존한다** — 작업 결과다. 삭제·숨김 금지.
- **콜백 해석 구조는 무변경이다** — 콜백 바디에 **창구 구분자가 없으므로** 창구마다 **별개 `request_id`** 를 발급하고 **원장 채널로 역조회**해 어느 축의 결과인지 판정한다. 이 구조는 그대로이고, 바뀌는 것은 **그 채널이 가리키는 창구 이름**뿐이다.
- ⚠⚠ **원장 채널 식별자 문자열은 바꾸지 않는다** — 창구가 바뀐 것이지 **축이 바뀐 것이 아니다.** 그 문자열은 이미 적재된 행의 역조회 키이자 미결 회수의 대상 목록이라, 바꾸면 앞서 나간 위탁의 결과가 도착해도 어느 축인지 판정하지 못한다.
- **같은 `request_id` 로 두 창구를 부르지 않는다** — 부르면 한쪽 결과가 유실된다.

## 2. 콜백 바디

### 2.1 성공
```json
{
  "request_id": "00000001",
  "status": "completed",
  "results": {
    "description": "한 남성이 전봇대 옆에서 쓰러진 상태로 확인됩니다."
  }
}
```

### 2.2 실패
```json
{
  "request_id": "00000001",
  "status": "failed",
  "error": "Video VLM inference failed"
}
```

실패해도 **콜백은 반드시 전송된다** — **수락된** 요청이 무응답으로 끝나는 경우는 규격에 없다. ⚠ 단 **수락되지 못한 요청은 다르다** — 인증 실패(401)로 거부된 요청에는 콜백이 아예 오지 않는다(§4).

★★ **`error` 는 객체가 아니라 문자열이다**(규격 §2.7). ⚠ **구 서술 폐기** — `{code, message}` 객체로 적던 것은 규격과 다르다. 객체 스키마로 검증하면 **실패 콜백이 전량 400 으로 거부되어 실패 사실 자체를 잃는다.** 되받을 조회 API 가 없는 입구에서의 엄격함은 곧 손실이다. **되살리지 말 것.**

### 2.3 응답 (저작도구 → 벤더)
- 200 OK. 바디는 표준 래퍼이며 적용 여부와 요청 식별자를 담는다.

## 3. 필드 정의

| 필드 | 타입 | 필수 | 설명 |
|------|------|:---:|------|
| request_id | String | Y | 위탁 요청 시 저작도구가 발급한 식별자. 콜백 상관관계 키 겸 멱등키. 영숫자·대시·언더스코어 64자 이내 |
| status | String | Y | `completed` \| `failed` — 화이트리스트 |
| results | Object | 조건부 | status=completed 시 필수. **객체 하나**(배열 아님)이며 `description` 단일 필드를 담는다 |
| results.description | String | Y | 자연어 서술 전문. 최대 2000자, 공백만 있으면 거부 |
| error | String | 조건부 | status=failed 시 필수. **문자열**이며 오류 사유가 평문으로 담긴다. 객체 아님 — 오류 코드 칸을 따로 기대하지 말 것 |

★ `completed` 인데 `results.description` 이 비어 있으면 **400** 이다 — 적재부에서 터지면 500 이 되므로 입구에서 막는다(fail-secure).

★ 콜백 바디에는 **어느 API 의 결과인지 알려 주는 식별자가 없다.** 축(묘사 / 추가 질문) 판별은 오로지 `request_id` 역조회로 한다 — 창구마다 별개 식별자를 발급하고 원장 채널로 되짚는다(§1-2). 창구 이름이 바뀌어도 이 판별 구조와 채널 식별자는 그대로다.

## 4. 수신 규율 (벤더 연동 유의사항)

- **응답 시한** — 콜백을 받으면 **5초 안에 2xx** 를 반환한다. 늦거나 2xx 가 아니면 벤더가 재전송한다(**최대 3회, 각 5초 간격**). 따라서 무거운 후속 작업은 2xx 를 돌려준 뒤에 수행한다.
- **멱등** — 같은 콜백을 여러 번 받을 수 있으므로 `request_id` 기준으로 멱등 처리한다. 이미 처리한 식별자면 본문을 무시하고 2xx 만 반환한다.
- **순서 무보장** — 요청 순서와 콜백 도착 순서가 일치하지 않는다. 요청과 결과의 대응은 `request_id` 로만 판정하고 도착 순서에 의존하지 않는다.
- **유실 시 회수 수단 없음** — 재전송 3회가 모두 실패하면 그 결과는 유실되며, **다시 받아올 조회 API 가 없다.** 재수행은 새 위탁으로만 가능하다.
- **본문 형식 무보장** — `description` 은 자연어 평문이고 형식이 고정돼 있지 않다. 문자열 파싱으로 구조를 뽑아내는 처리에 의존하지 않는다.
- **★ 콜백 미도착 사유에 「인증 실패」가 있다 (v1.2.0 §2.1 신설)** — 분석 요청에 `X-API-Key` 가 없거나 값이 다르면 벤더가 **401 로 거부하고 콜백을 전송하지 않는다.** 결과가 **아무 신호도 없이 사라지므로**, 콜백이 오지 않는 상황을 「분석 지연」으로만 해석하면 안 된다. 미도착은 ① **인증 실패 — 위탁이 수락되지 않아 콜백 자체가 없다** ② **재전송 3회 소진 — 결과가 유실됐다** ③ **분석 지연 — 아직 오는 중이다** 셋을 구분해 판정한다.
- ⚠ **API 키 값과 사용 여부는 확인 대기다** — 규격서 밖에서 별도로 전달되는 값이며 아직 수신하지 못했다. 추정해 채우지 않는다.

## 5. 저작도구 내부 매핑

- **request_id → 영상 · 축**: 콜백 바디에 영상 식별자도 API 종류도 없으므로, 위탁 시 발급한 요청 식별자에 대상 영상과 축(묘사 / 추가 질문)을 함께 영속해 둔 멱등 원장으로 역조회한다. 발급된 적 없는 식별자는 거부. **원장 채널 식별자 문자열은 창구 교체와 무관하게 유지한다**(§1-2).
- **status=completed** — 서술 전문을 시계열 서술 축(`vlm.description`)으로 적재한다. 이 값이 검수큐에 들어가며 화면에서 편집 가능하다.
- **이벤트 어노테이션 자동채움 — 칸 단위 귀속 (2026-08-25 확정)**: 수신 결과가 이벤트 어노테이션의 **어느 칸에 들어가는지**를 칸 단위로 못 박는다. 두 창구는 **같은 캡션 후보 `c1` 을 공유**한다.
  - 묘사(`describe`) 응답 서술 전문 → ① 시계열 서술 전문(영상 블록) ② 캡션 후보 `c1` 의 **사고 단계 `1단계`**(전문에서 「상황」 라벨 줄만 파싱한 값).
  - 추가 질문(`custom`) 응답 서술 → 캡션 후보 `c1` 의 **캡션 본문**. ⚠ 위탁 창구가 `describe-sub` 에서 바뀌었을 뿐 **귀속 칸은 그대로**이며, 이미 그 창구로 받아 적재된 결과도 같은 칸에 있고 보존한다.
  - **질문 칸** → **위탁 시점에 조달해 요청 본문에 실어 보낸 그 문구**를 원장 보관값에서 읽는다 — **콜백 시점에 재조달하지 않는다**(조달 규칙은 마킹에서 고른 값 → 없으면 그 유형의 첫 번째이며, 유형이 미수신이어도 마킹 선택값이 있으면 그 질문). 마킹 화면을 거친 영상은 검증 이벤트 유형과 질문이 반드시 있다 — 유형 선택이 노출된 영상은 유형을 고르지 않으면 마킹을 완료할 수 없고, 자동 마킹도 그 유형의 첫 번째 질문을 자동으로 고른다. 그래서 이 갈래는 마킹 화면을 거치지 않는 경로와 이 규칙 이전에 저장된 기존 행에만 남는다. 재조달하면 질문 목록이 전체 교체된 사이에 **보낸 질문과 기록된 질문이 갈린다**. **위탁 응답에서 오지 않는다** — 질문 문장은 이벤트별로 벤더 서버가 관리하며 연동 시스템이 지정하지 않는다.
  - **답변 · 근거 서술 · 사고 단계 2단계 이후** → **자동으로 채우지 않는다.** 사람이 확정할 공란이다.
  - **「상황」 파싱** — 묘사 전문은 `- 라벨: 값` 줄 단위로 오므로 「상황」 라벨 줄을 찾아 **그 줄의 줄바꿈까지**를 값으로 쓰고 다음 라벨 줄로 이어붙이지 않는다. 선행 공백·콜론 앞뒤 공백은 관용 처리한다. 같은 라벨이 여러 번 나오면 **첫 번째**를 쓴다. 「상황」 줄이 없으면 **채우지 않는다 — 빈 값도 넣지 않는다.**
  - ⚠ **라벨 목록에 의존하지 않는다** — 규격이 「장소·날씨·상황 등」이라고만 쓰고 전체 목록·순서·필수 여부를 정의하지 않는다. 「상황」 줄 하나만 찾는 방식이라야 항목이 늘거나 순서가 바뀌어도 성립한다.
  - **사고 단계는 `1단계` 키만 만든다** — 2단계 이후 키를 만들지 않는다.
  - **근거 서술은 파싱으로 채우지 않는다** — 자유 서술이라 형식이 고정돼 있지 않다(§4 「본문 형식 무보장」). 「상황」 파싱은 별개다 — 그건 규격 콜백 예시에 형식이 명시된 묘사 축이다.
  - **도착 순서에 의존하지 않는다** — 두 창구의 콜백 도착 순서는 보장되지 않는다. 나중에 도착한 축이 캡션 후보를 통째로 교체해 먼저 도착한 축의 값을 지우면 안 되고, **자기 칸만 채운다.**
  - ⚠ **인지·수용한 잔여 위험** — 지금 위탁 요청 본문에는 우리가 고른 질문을 실을 자리가 없다. 첫 번째가 아닌 질문을 고르면 **기록된 질문과 벤더가 실제로 쓴 질문이 달라진다.** 이를 알고 수용했다(되돌리지 말 것).
  - **보호 경계는 전부 유지한다** — 승인 이력이 있으면 자동채움하지 않음 · 값이 이미 있으면 덮지 않음 · 어노테이션 검토가 종결됐으면 하지 않음 · 중복 콜백 멱등 · 자동채움은 재검수를 발화시키지 않음 · 이벤트 분류 조달값이 없으면 행을 만들지 않음.
  - **기적재분은 백필하지 않는다** — 신규 수신분부터 적용한다.
- **레거시 구간 키 보존**: 구 규격으로 이미 적재된 구간 키(`0-8`·`8-16` …)는 **작업 결과라 보존**하며 화면과 산출물이 계속 읽는다. 삭제·숨김 금지.
- **status=failed** — 적재 없이 해당 위탁을 실패로 종결해 고착을 푼다. 자동 재요청 잡은 없으며 수동 재처리가 필요하다.
- **멱등·직렬화·원자성**: 동일 요청 식별자 재수신은 원장으로 replay 스킵. 동시 콜백은 잠금으로 직렬화한다. 트랜잭션 롤백 시 처리완료 표식도 함께 롤백되어 벤더 재전송을 유도한다.
### 5-1. 이 귀속은 직전 확정을 되돌린 반전이다
2026-08-24 확정은 *"추가 질문 결과는 **답변** 축 초안으로 간다"* 였고, 그때 *"묘사 결과를 캡션·사고 단계 축으로 보낸다"* 는 지시를 명시적으로 폐기했다. 2026-08-25 사업 담당 회신이 그것을 **다시 캡션·사고 단계 축으로 되돌린다** — 추가 질문 응답은 답변이 아니라 캡션 본문이고, 답변 칸은 사람이 확정할 공란이다. 같은 축이 이틀 만에 두 번 뒤집혔으므로, 언제 무엇으로 확정했고 무슨 근거로 바뀌었는지를 남겨 세 번째 반전을 막는다. **되살리지 말 것.**

## 6. 승인된 영상의 서술이 갱신되면 재검수로 되돌린다
이미 승인된 영상의 시계열 서술이 **실제로 달라진 경우에만** 검토행을 미처리로 되돌리고 수정 통지 축을 타게 한다. 값이 같으면 아무것도 하지 않는다(멱등 — 재검수·통지 폭주 방지). 근거: 데이터마트 뷰가 라이브 메타를 조인하므로 상태를 승인으로 둔 채 값만 갱신하면 검수자가 한 번도 보지 않은 서술이 그대로 관제로 나간다. 반려된 검토행도 되돌린다 — 반려 판단은 *바뀌기 전 본문*에 대한 것이라 새 본문에 적용되지 않는다.

## 7. 비식별 신고 구간 재개 흐름
비식별 누락 신고(`DE_IDNTF_YN='F'`) 구간에서는 위탁 자체가 보류되므로 콜백이 발생하지 않는다. 신고 해소 시 보류 기록을 근거로 **재위탁**하고, 그 결과로 본 콜백이 정상 수신된다(멱등 조건: 시계열 메타 0건).
