서명·토큰 인증 없음 — 벤더 계약(KLID 연동 API v1.1.0)이 **무서명 콜백** 규격이라 HMAC 을 적용할 수 없다(2026-07-07 확정). 대신 3계층 방어로 대체: ① IP allowlist `webhook.vlm.allowed-ip-cidrs` ② rate limit + 본문 크기 상한 ③ `request_id` 발급 게이트(우리가 발급하지 않은 request_id 는 거부). 증강 콜백(INT-006)이 HMAC 필수인 것과 대비되는 지점이며, 벤더 규격 차이에 따른 의도된 설계다.

## data_format

json

## description

외부 VLM 서비스가 시계열 메타 생성 결과를 저작도구로 push 하는 inbound 콜백.

## 연동 계약 (KLID 연동 API v1.1.0)
- 수신 엔드포인트 `POST /v1/vlm/callback` — 콜백 본문을 검증하고 결과를 적재한다(우리 쪽 경로).
- 연동 대상은 묘사(describe)·추가 질문(describe-sub) 두 축이며 verify 는 미연동이다.
- 요청 `VlmResultRequest`: `request_id` · `status`(`completed` | `failed`) · `results{description}`(단일 서술) · `error{code, message}`
- describe·describe-sub 는 `accuracy` 와 `detected` 를 반환하지 않는다(KLID §2.8 — 두 필드는 verify 전용). 따라서 콜백 결과에 일치도(accuracy) 축은 존재하지 않는다.
- 콜백 본문에는 API 종류 식별자가 없으므로, `request_id` 로 어느 축(describe/describe-sub)인지 역조회해 적재한다.
- `description` 은 자연어 평문이라 결과 처리는 문자열 파싱에 의존하지 않는다. 예외는 묘사 축의 「상황」 항목 하나뿐이며, 그 줄 단위 형식은 연동 규격 콜백 예시에 명시돼 있다.

## 성공 시 적재·검수 흐름 — 어노테이션 적재 축 (2026-08-25 확정)
- 성공 시 시계열 메타 적재 + 검수큐 진입을 유지한다.
- 두 창구의 결과가 이벤트 어노테이션의 어느 칸으로 가는지는 아래로 확정한다.
  · `video.vd_description` ← 묘사(describe) 전문(장소·날씨·상황·환경·심각성). 종전과 같다.
  · `event.question` ← 저작도구가 보관하는 검증 이벤트 유형별 질문 문구 목록(마킹에서 고른 값, 없으면 그 유형의 첫 번째). 위탁 응답에서 오지 않는다.
  · `event.caption.c1.caption_text` ← 추가 질문(describe-sub)의 답변 서술.
  · `event.caption.c1.cot["1단계"]` ← 묘사 전문 중 「상황」 항목만 파싱한 값.
- 묘사 축은 적재처가 하나 늘었다 — 시계열 서술 전문에 더해 CoT 1단계로도 흐른다.
- 「상황」 파싱은 `- 라벨: 값` 줄 단위 형식이 연동 규격 콜백 예시에 명시된 묘사 축에만 적용한다. 「상황」 라벨 줄을 찾아 그 줄의 줄바꿈까지를 값으로 쓰고 다음 라벨 줄로 이어붙이지 않는다.
- 라벨 목록에 의존하지 않는다 — 규격이 전체 목록·순서·필수 여부를 정의하지 않으므로, 「상황」 줄 하나만 찾는 방식이라야 항목이 늘거나 순서가 바뀌어도 성립한다.
- 「상황」 줄이 없으면 채우지 않는다(빈 값을 넣지 않는다).
- CoT 는 1단계 키만 만든다. 2단계 이후 키를 만들지 않고 공란으로 두어 사람이 입력한다.
- 질문 문장은 이벤트별로 외부 서버가 관리하며 연동 시스템이 지정하지도 응답으로 받지도 않는다. 따라서 이벤트유형별 문구를 지어내지 않고, 저작도구가 보관하는 검증 이벤트 유형별 질문 문구 목록에서 조달한다 — 마킹에서 고른 질문이 있으면 그 값, 없으면 그 유형의 첫 번째 질문을 쓰고, 유형이나 등록된 질문이 없으면 비워 둔다.
- 답변(answer) 칸은 자동으로 채우지 않는다 — 사람이 확정한다.
- 근거 서술(evidence)은 채우지 않는다 — 자유 서술이라 프레임·객체 지시로 쪼개려면 문자열 파싱이 필요한데, 규격이 그 서술은 형식이 고정돼 있지 않으니 파싱에 의존하지 말라고 못 박는다.
- 두 창구는 같은 캡션 후보 `c1` 을 공유하고 도착 순서가 보장되지 않는다. 나중에 도착한 축이 먼저 도착한 축의 값을 지우지 않도록, 후보를 통째로 교체하지 않고 자기 칸만 채운다.
- 기적재분은 백필하지 않는다 — 신규 수신분부터 적용한다.
- 자동채움은 신규 적재에만 적용하며 기존 보호 경계를 모두 유지한다 — 승인 이력이 있으면 자동채움하지 않고, 값이 이미 있으면 덮지 않으며, 어노테이션 검토가 종결됐으면 하지 않고, 중복 콜백은 멱등 처리하며, 자동채움은 재검수를 발화시키지 않는다.
- REVIEWER 가 라벨링 캔버스 화면(SCREEN-005)에서 검토·수정·승인한다.

## ⚠ 적재 축은 이틀 만에 두 번 뒤집혔다 — 세 번째로 되돌리지 말 것
2026-08-24 확정은 「추가 질문 결과는 어노테이션의 답변(answer) 축 초안으로 간다」였고, 그때 그보다 앞선 「묘사 → caption/cot 축」 지시를 명시적으로 폐기했다. 2026-08-25 사업 담당 회신이 그것을 다시 caption/cot 축으로 되돌렸다 — 폐기됐던 앞선 지시가 결과적으로 맞았다. 위 적재 축이 현재 확정이며, 답변(answer) 축 자동채움으로 되돌리지 않는다.

## 인증 — 무서명(벤더 규격) + 3계층 대체 방어
콜백 규격이 서명 헤더를 제공하지 않으므로 HMAC 미적용(증강 콜백 INT-006 과 다른 지점). 대신:
1. IP allowlist `webhook.vlm.allowed-ip-cidrs`
2. rate limit + 본문 크기 상한
3. `request_id` 발급 게이트 — 저작도구가 발급한 적 없는 request_id 는 거부

## 멱등·동시성·재전송 (KLID §5.1)
- 콜백 수신 후 2xx 응답을 5초 내 반환한다(무거운 후속 처리는 반환 후 수행).
- 벤더는 실패 시 최대 3회·각 5초 간격으로 재전송하며, `request_id` 기준 멱등 처리로 재수신을 흡수한다.
- 웹훅 멱등 원장으로 `request_id` 기준 멱등 — 이미 PROCESSED 면 재수신 skip.
- 요청과 콜백의 순서가 일치하지 않을 수 있어 `request_id` 로 매칭한다.
- 동시 콜백은 비관적 락으로 직렬화한다.
- 트랜잭션 롤백 시 PROCESSED 마킹도 함께 롤백되어 벤더 재전송을 유도하는 구조다.

## ⚠ dead-letter 부재
실패는 `VLM_FAILED` 로 종결 실패 상태를 마킹할 뿐이고 자동 재요청 잡을 두지 않는다. 관제 통지(INT-007)가 dead-letter + 백오프 재시도 큐를 갖춘 것과 대비되는 미비점 — 운영 시 수동 재처리 경로가 필요하다.
