# R3 요구사항 추적표

> **ID 표기 규칙(공통)**: 본 산출물의 모든 ID(KLID-AT-UC/CO/DC/DCD/SD/SC/AC/EN/ERD/TB/II/IC/IF/UCD/ACT 등)는 **전체 형식 `KLID-AT-XX-NNN`** 으로 표기한다. 끝부분만(예: `UC-001`) 약식 표기 금지. 범위는 시작 ID만 전체형으로(예: `KLID-AT-UC-001~013`). ※ 요구사항(RQ-SFR-NN-NN)·시스템시험(KLID-ST-NNN) 등 타 체계 ID는 각 체계 원형 유지.

## 작성 목적
> 시스템의 요구사항을 도출하여 개발의 각 단계별로 작성한 산출물이 일관성을 가지는지를 추적할 수 있도록 각 단계별 산출물의 추적성을 관리하기 위하여 작성한다.

## 작성 방법
> 사용자 요구사항 정의서로부터 시작하여 분석, 설계, 구현, 시험의 각 단계별 산출물에 ID를 식별하고 전단계 산출물과 후속단계 산출물간의 연계관계에 매핑 작업을 하여 산출물이 단계별 연관관계가 끊어지지 않고 추적할 수 있도록 한다.

### 본문 양식 (비기능 요구사항 추적)

> 비기능 요구사항(`NFR-008`~`NFR-021`, 14건)은 특정 화면·컴포넌트·테이블 1건에 귀속되지 않고 아키텍처 전반에서 실현되므로 기능 매트릭스와 분리하여 별도 표로 추적한다. `실현 산출물`은 아키텍처 설계서의 「아키텍처 요구사항 및 구현방안」 절에 요구사항 1건당 1표로 구현방안이 기술된 위치를 가리키며, `관련 유스케이스 ID`는 유스케이스 명세서의 「구현 시 고려 사항」에서 해당 비기능 요구사항을 인용한 유스케이스다. 저작도구 자체 도출 비기능 7건은 발주처 요구사항 기준선에서 제외되어 본 표의 추적 대상이 아니다(부록 2 「비기능 요구사항 제외 7건」).

> 전체 시스템에 대하여 한 개의 표로 작성하며, 각 산출물의 ID와 이름을 기술한다.

- 각 단계 컬럼에는 해당 산출물의 **ID + 이름(D)** 을 기입한다. ID 컬럼마다 우측에 이름/설명(`D`) 짝 컬럼이 붙는다.
- 분석 단계: 요구사항 ID + D(요구사항명), RFP ID, 유스케이스 ID + D(유스케이스명)
- 설계 단계: 화면 ID + D, 컴포넌트 ID + D, 테이블 ID + D
- 구현 단계: 프로그램 파일 ID + D, 단위시험 ID + D
- 시험 단계: 통합시험 시나리오 ID + D, 시스템시험 시나리오 ID + D
- 산출물 단계 사슬(좌→우): 사용자 요구사항 명세서 → 유스케이스 명세서 → 사용자 인터페이스 설계서 → 컴포넌트 설계서 → 데이터베이스 설계서 → 프로그램 코드 → 단위시험 결과서 → 통합시험 결과서 → 시스템시험 결과서.
- 하나의 요구사항이 여러 유스케이스/화면/컴포넌트/테이블에 매핑될 수 있으므로 1:N 관계를 허용한다.
- **RFP ID**: 요구사항이 제시된 제안요청서 요구사항 분류 번호(`SFR-NN` / `PER-NN` / `SER-NN` / `QUR-NN` / `DAR-NN` / `COR-NN`)이며, 사용자 요구사항 정의서의 「요구사항 출처」·「비고(발주처 원본 비기능 ID)」에서 도출한다.
- **매핑 도출 규칙(기계적 도출 — 임의 판단 없음)**
  - 요구사항 → 유스케이스: 유스케이스 명세서 「유스케이스 목록」의 `관련 요구사항 ID` 를 역방향으로 집계한다.
  - 유스케이스 → 화면: 사용자 인터페이스 설계서 「사용자 인터페이스 목록」의 `관련 유스케이스 ID` 를 역방향으로 집계한다.
  - 유스케이스 → 컴포넌트: 컴포넌트 설계서 「컴포넌트 목록」의 `관련 유스케이스 ID`(유스케이스 1건 = 컴포넌트 1건)를 사용한다.
  - 유스케이스 → 테이블: 엔티티 관계 모형 설계서 「엔티티 명세서」의 `관련 유스케이스 ID` 를 역방향으로 집계하고, 엔티티 ID와 테이블 ID가 1:1·동일 번호로 대응하므로 그대로 테이블 ID로 환산한다. 테이블명(D)은 엔티티명(논리명)을 사용한다.
  - 요구사항 → 통합시험 시나리오: 통합시험 시나리오가 검증 대상으로 명시한 유스케이스를 요구사항으로 되짚어 연결한다.

> 아래 비기능 요구사항 7건은 제안요청서에 대응 항목이 없는 **저작도구 자체 도출분**으로, 발주처 요구사항 기준선에서 제외하기로 결정(2026-08-06)하였다. LogiCraft 설계 그래프의 해당 항목 7건도 같은 날 `deprecated` 로 비활성화하였다. 이에 따라 비기능 추적 대상은 `NFR-008`~`NFR-021` 14건이며, 제외 7건의 ID는 결번으로 두고 재사용하지 않는다.

## 작성 시 참고사항

> **ID 체계 (프로젝트 공식)**
> - 프로젝트 ID: `KLID` / 서브시스템 ID(저작도구): `AT`
> - 산출물 파일명: `KLID_AT_요구사항추적표_Rev {버전}`
> - 본 산출물에서 참조하는 ID:
>   - 요구사항 ID: `RQ-SFR-NN-NN`(기능) · `NFR-NNN`(비기능) — 사용자 요구사항 정의서 실존 ID만
>   - RFP ID: `SFR-NN` / `PER-NN` / `SER-NN` / `QUR-NN` / `DAR-NN` / `COR-NN` — 요구사항 출처에서 도출
>   - 유스케이스 ID: `KLID-AT-UC-NNN` — 유스케이스 명세서 참조
>   - 화면 ID: `KLID-AT-SC-NNN` — 사용자 인터페이스 설계서 참조
>   - 컴포넌트 ID: `KLID-AT-CO-NNN` — 컴포넌트 설계서 참조
>   - 테이블 ID: `KLID-AT-TB-NNN` — 데이터베이스 설계서 참조(테이블명 D 컬럼은 엔티티 관계 모형 설계서의 엔티티 논리명)
>   - 시퀀스도 ID: `KLID-AT-SD-NNN` / 설계 클래스도 ID: `KLID-AT-DCD-NNN` / 설계 클래스 ID: `KLID-AT-DC-NNN` — 클래스 설계서 참조
>   - 연동 ID: `KLID-AT-II-NNN` — 인터페이스 설계서 참조
>   - 통합시험 시나리오 ID: `KLID-AT-IT-TS-NNN` / 단위시험 ID: `KLID-AT-UT-NNN` / 시스템시험 시나리오 ID: `KLID-ST-NNN`
> - 사용자 요구사항 정의서의 요구사항 ID를 시작점으로 유스케이스 → 화면 · 컴포넌트 · 데이터베이스 → 프로그램 코드 → 단위시험 → 통합시험 → 시스템시험까지 추적 체인을 연결한다.
> - 하나의 요구사항이 여러 유스케이스·화면·컴포넌트·테이블에 매핑될 수 있으므로 1:N 관계를 허용한다.
> - 빈 셀이 있으면 추적성이 끊긴 것이므로 반드시 부록에 사유를 기재하여 관리한다("끊어지지 않고 추적" 원칙).
