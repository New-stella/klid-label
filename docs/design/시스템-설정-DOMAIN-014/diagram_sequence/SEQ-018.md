    LR-->>US: USER_NO 별 ROLE_CD — 역할 행이 없으면 미배정이며 기본값을 부여하지 않는다
    US->>US: 역할 필터가 지정되면 조회된 페이지 안에서 걸러낸다
    US-->>UC: 사용자 목록(역할·계정 활성 여부 포함)
    UC-->>R: 200 OK — 계정 활성 여부는 읽기 전용 표시이며 이 화면의 변경 대상이 아니다

    R->>ACTL: POST /v1/manage/admin-session {adminPassword} — 역할을 바꾸려면 먼저 관리자 패스워드로 유효창을 연다
    ACTL->>ASVC: open(req, actor)
    ASVC->>ASVC: 검수자가 아니면 거절하고, 시도 횟수를 제한하며, 관리자 공유 패스워드를 해시로 대조한다
    ASVC->>TOK: issue(subject, now) — 유효창을 여는 것은 역할 승격이 아니다
    TOK-->>ASVC: 발급 대상자에게 묶인 단기 토큰과 만료 일시 — 유효기간은 기본 10분이고 상한 30분을 넘길 수 없다
    ASVC-->>ACTL: 토큰·만료 일시
    ACTL-->>R: 200 OK — 화면은 남은 유효 시간을 보여주고 패스워드 입력값은 다시 표시하지 않는다

    R->>GATE: PATCH /v1/users/{userNo} {role} + X-Admin-Session 헤더 — 역할 변경은 검수자 권한에 유효창이 가산된다
    GATE->>GATE: 요청이 닿을 창구에 유효창 요구 표식이 걸려 있는지 읽는다 — 창구는 요구를 선언할 뿐 판정하지 않는다
    GATE->>TOK: verify(token, subject, now) — 유효 판정은 단일 지점이 소유하고 어느 창구도 그것을 복제하지 않는다
    TOK-->>GATE: 통과 — 없거나 유효기간이 끝났거나 위조됐거나 타인에게 발급된 토큰이면 거부한다
    GATE->>UC: 표식 판정을 통과한 요청만 창구 본문에 닿는다
    UC->>UC: role 값을 REVIEWER·WORKER·PORTAL_USER 화이트리스트로 재검증한다
    UC->>US: update(userNo, req) — 수행 계층은 요청 헤더도 유효창도 알지 않는다
    US->>UR: findByUserNo(userNo)
    UR-->>US: 사용자 — 없으면 404 로 끝난다
    US->>LR: findByUserNo(userNo) — 현재 역할
    LR-->>US: 현재 ROLE_CD
    opt 요청 역할이 현재 역할과 다른 경우에만
        US->>ROLE: USER_NO 충돌 시 ROLE_CD·UPD_DT 를 갱신하는 원자 upsert
        US-)RR: 커밋 이후 해당 USER_NO 의 역할 캐시를 무효화한다(커밋 전에 지우면 동시 요청이 옛 값을 다시 담는다)
    end
    US-->>UC: 갱신된 역할을 실은 프로필
    UC-->>R: 200 OK

    alt 화이트리스트 밖 값

        UC-->>R: 400 Bad Request
    else 현재와 같은 역할
        R->>UC: PATCH /v1/users/{userNo} — 현재와 같은 역할 값(유효창 판정을 통과한 뒤다)
        UC->>US: update(userNo, req)
        US->>US: 현재 역할과 같으면 갱신도 캐시 무효화도 건너뛴다
        UC-->>R: 200 OK — 화면은 이 경우 저장 버튼을 비활성화해 요청이 나가지 않게 한다
    else 유효창 없음 또는 만료
        R->>GATE: PATCH /v1/users/{userNo} — 유효창이 없거나 유효기간이 끝난 상태
        GATE->>TOK: verify(token, subject, now)
        TOK-->>GATE: 거부 — 창구 본문은 실행되지 않고 역할도 바뀌지 않는다
        GATE-->>R: 403 Forbidden — 상태코드와 오류 코드로는 검수자 권한이 없을 때와 구분되지 않는다
        Note over R,GATE: 안내 문구는 다르다 — 유효창 거부는 다시 인증할 자리를 안내하고 그 문구는 실패 사유가 무엇이든 같다. 두 요청을 비교하면 자기 자신의 역할 상태를 짐작할 수 있다는 대가는 인지하고 받아들인다
        R->>ACTL: 관리자 패스워드 재확인 — 화면은 만료를 알리고 다시 확인을 요구하며, 확인에 성공하면 저장을 이어서 시도한다
        Note over R,UC: 조회는 이 거부와 무관하다 — 목록·단건 조회는 검수자 권한만으로 되며 유효창을 요구하지 않는다
    end

## description

사용자 관리 화면에서 REVIEWER 가 사용자를 조회하고 역할을 바꾸는 흐름의 시퀀스 다이어그램. 이 시스템은 자체 로그인 화면이나 자체 인증 엔드포인트를 두지 않는다 — 관제서버가 발급한 JWT 를 인계받아 JwtAuthenticationFilter 가 서명·발급자·만료를 검증하고 주체·채널·이름 클레임만 읽는다. 인가 역할은 토큰의 역할 클레임에서 읽지 않고 저작도구가 소유한 LS_USER_ROLE 에서 다시 조회하며, 그 값이 인가의 단일 진실원이다. 사용자 행은 관리 화면이 만들지 않는다 — 역할 자가부여 시점의 원자 upsert 가 유일한 생성 지점이라, 역할을 받은 적 없는 사람은 이 목록에 나타나지 않는다. 자가부여는 관리자 공유 패스워드로 보호되고 시도 횟수가 제한되며 REVIEWER 와 WORKER 를 부여할 수 있고 PORTAL_USER 는 거절한다. 따라서 관리자 지위는 별도 역할이 아니라 그 공유 패스워드를 아는 사람이며, 시스템에 ADMIN 역할은 존재하지 않고 관리 권한은 REVIEWER 에 통합되어 있다. 목록 조회는 이름·아이디·전자우편 부분일치와 역할 필터를 받고 정렬은 사용자 번호 오름차순으로 고정되어 호출자가 바꿀 수 없다. 역할 필터는 조회된 페이지 안에서 적용되므로 필터를 걸면 전체 건수가 실제 일치 건수보다 클 수 있다. 역할 변경은 값을 화이트리스트로 재검증한 뒤 원자 upsert 로 반영하고, 현재 값과 같으면 갱신을 건너뛴다. 바뀐 경우에는 커밋 이후에 역할 캐시를 무효화한다 — 커밋 전에 지우면 동시 요청이 옛 역할을 다시 캐시에 담아 권한 강등이 즉시 반영되지 않는다. 계정 활성 여부는 외부 시스템이 소유한 값이라 이 화면에서는 읽기 전용으로만 보인다. 역할 변경은 운영·관리 성격의 쓰기라 검수자 권한만으로 열리지 않는다 — 관리자 패스워드를 제출해 연 단기 유효창을 함께 요구한다. 유효창은 인가를 대체하지 않고 가산되므로 검수자 권한은 그대로 필요하고, 유효창이 역할을 승격시키지도 않는다. 유효창은 발급받은 사람에게 묶이고 요청은 여전히 본인 자격으로 인증되므로, 공유 패스워드로 여는 방식인데도 누가 역할을 바꿨는지가 개인 단위로 남는다. 유효기간은 기본 10분이고 상한 30분을 넘길 수 없으며, 아직 유효한지는 서버가 판정한다 — 화면이 스스로 정하지 못한다. 유효창을 제시하는 자리는 요청 헤더다. 유효한지 판정하는 일은 단일 지점이 소유하며 어느 창구도 그 판정을 복제하지 않는다 — 판정 규칙이 바뀔 때 고칠 자리가 하나여야 하기 때문이다. 어느 요청에 이 요구가 걸리는지는 창구가 스스로 표식으로 선언하고, 그 선언을 읽어 판정 지점에 넘기는 것은 공통 배선의 몫이다. 창구가 들고 있는 것은 요구가 걸린다는 선언뿐이고 판정 자체가 아니므로 이것은 판정의 복제가 아니다. 역할 변경 창구는 창구 전체에 예외 없이 이 요구가 걸리므로 표식을 쓴다 — 그래서 이 흐름에는 공통 배선이 실제로 개입해 창구 본문이 실행되기 전에 판정이 끝난다. 판정을 수행 계층으로 내리는 안은 채택하지 않는다 — 그러면 수행 계층이 요청 헤더를 알아야 해 계층 규칙과 충돌하고, 결국 창구에서 값을 넘겨주는 배선이 다시 생겨 같은 자리로 돌아온다. 경계해야 할 실패 양식은 역할을 바꾸는 진입점이 새로 생겼는데 표식이 조용히 빠지는 것이다 — 표식은 사람이 붙이는 것이라 빠뜨려도 아무 신호가 나지 않으므로, 그 부재는 사람의 주의력이 아니라 기계가 잡는 정적 검사가 맡는다. 유효창이 없거나 유효기간이 끝난 뒤 역할 변경을 시도하면 거부된다. 상태코드와 오류 코드로는 그 거부가 검수자 권한이 없을 때와 구분되지 않지만 안내 문구는 다르다 — 유효창 거부는 다시 인증할 수 있는 자리를 안내하고, 역할 거부는 권한이 없다고만 말한다. 그러지 않으면 막힌 사람이 왜 막혔는지 알 수 없어 재인증 동선 자체가 성립하지 않는다. 그 대가로 두 요청을 비교하면 자기 자신의 역할 상태를 짐작할 수 있는데, 짐작 대상이 자기 자신의 역할이라 인지하고 받아들인다. 유효창 거부의 문구는 실패 사유가 무엇이든 같다 — 없든, 유효기간이 끝났든, 위조됐든, 다른 사람의 것이든 한 가지 문구이며 남은 시간이나 발급 여부 같은 상태값을 싣지 않는다. 화면은 거부만 알리고 끝내지 않는다 — 만료 사실을 안내하고 관리자 패스워드 재확인을 요구한 뒤 저장을 이어서 시도한다. 반면 목록·단건 조회에는 유효창을 요구하지 않는다 — 조회까지 막으면 작업 배정 흐름이 끊긴다.
