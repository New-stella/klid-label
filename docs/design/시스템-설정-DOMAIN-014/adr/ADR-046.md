# 연동 서버 주소를 운영 화면에서 재기동 없이 교체 — 저장 축 IP 대역 차단 폐지 + 관리자 단기 유효창

## context

외부 연동 대상의 주소가 배포 설정에만 있어, 대상 서버가 바뀌면 재기동해야 반영됐다. 대상은 넷이다 — 비식별(kpst.deid.base-url) · AI 추론(authoring.integration.ai-server.base-url) · 외부 시계열 분석 벤더(vlm.client.url) · 관제 통지(authoring.control-notify.url). 데이터베이스 접속 정보는 대상이 아니다.

주소를 사람이 바꿀 수 있게 하면서 서버측 요청 위조(SSRF)를 막으려고, 처음에는 도메인을 IP 로 해석한 뒤 사설·링크로컬·루프백 대역과 클라우드 메타데이터 주소를 차단하고 요청 전송 직전에 다시 해석해 검증하는 방어를 함께 넣었다.

그런데 이 연동 넷은 실제로 내부망의 별도 서버에 있을 가능성이 높다. 배포 기본값 자체가 같은 망을 가리키므로, 대역 차단은 공격자가 아니라 정당한 대상을 막는다. 시스템 전체는 내부망 온프렘 배포이고 외부에 노출되는 것은 포털향뿐인데 이 설정 화면은 포털 채널에 노출되지 않는다. 아웃바운드·인바운드 통제는 인프라 계층이 담당한다.

## decision

### chosen_option

연동 주소 넷을 운영 화면에서 재기동 없이 교체 — 저장 축 IP 대역 차단 폐지 + 관리자 단기 유효창(채택)

### justification

### 무엇이 진실원인가
설정에 값이 있으면 그 값을, 없으면 배포 기본값을 쓴다. 설정 키는 애플리케이션 속성명을 그대로 쓴다 — 별도 키명을 만들면 그 매핑표가 두 번째 진실원이 된다. 시드 행을 만들지 않으며 행이 없는 것이 정상 상태다. 따라서 최초 저장 시점에 행이 생기고, 저장 전까지는 목록 조회에 나타나지 않는다. 설정 조회가 실패하면 예외를 던지지 않고 '설정 없음'으로 낮춰 배포 기본값을 쓴다.

비식별 축의 설정 키는 kpst.deid.base-url 이다. 구 후보였던 authoring.integration.deidentify.base-url 은 실제 위탁 경로를 구동하지 않으므로 이 축의 키로 두지 않는다 — 실효가 없는 칸을 화면에 남기지 않는다.

### 반영 시점
재기동 없이 다음 호출부터 반영된다. 연결 클라이언트의 기준 주소는 생성 시점에 고정되므로, 저장된 값을 호출 시점에 다시 읽어 요청 주소의 앞부분을 갈아끼운다. 변경한 노드에서는 즉시, 다른 노드에서는 설정 캐시 수명만큼 지연되어 반영된다.

비식별 축은 배선이 두 겹이다 — 위탁 요청은 연결 클라이언트 경로로 나가지만 진행 상태 조회는 저수준 경로라 그 훅이 닿지 않으므로, 그 경로가 직접 저장값을 읽어 주소를 만든다. 한쪽만 배선하면 위탁은 새 서버로 가는데 조회만 옛 서버로 나가 그 작업이 영원히 완료되지 않는다. 부분 반영은 미반영보다 위험하다.

### 저장 값에 남는 검증
빈 값 거부 · 길이 상한 · 주소 형식 · 스킴은 http 또는 https · 호스트 존재 · 자격증명을 담은 형태(사용자이름과 비밀번호를 주소에 넣는 표기) 거부. 마지막 항목은 대역 판정이 아니라 감사 로그에 평문 자격증명이 남는 것을 막기 위한 것이다.

위반은 400 이며, 거부 사유에 입력 원문·호스트·해석 결과를 싣지 않는다. 실으면 그 응답이 내부망을 훑는 수단이 된다.

### IP 대역으로는 막지 않는다
사설·링크로컬·루프백·클라우드 메타데이터 대역 차단과 요청 전송 직전 재검증을 모두 폐지한다. 막을 대역이 없으면 재검증할 내용도 없다. **이 저장 축이 서버측 요청 위조를 막는다고 적지 말 것 — 막지 않는다.**

### 축이 둘이라는 사실을 함께 못박는다
이 결정이 규율하는 것은 **운영 화면에서 저장하는 값**이다. **기동 시점의 배포 기본값을 판정하는 축은 그대로 남아 있고 이 결정의 대상이 아니다.** 외부 시계열 분석 벤더 주소는 운영 프로파일에서 배포 기본값이 여전히 https 전용·대역 차단으로 판정되어 위반하면 기동이 막힌다. 그 판정은 운영 화면 저장값에는 다시 적용되지 않는다.

그 결과 같은 주소가 배포 설정으로 넣으면 기동을 막고 운영 화면으로 넣으면 통과한다. **이것은 결함이 아니라 판정 대상이 다른 두 축이며, 회귀 가드로 고정돼 있다.** '이 연동은 항상 https 이고 공인망이다'라고 읽지 말 것.

### 비식별 축에만 관문이 하나 더 있다
운영 배포에서는 알려진 목·시뮬레이터 호스트명으로 비식별 주소를 저장할 수 없다(400). 이 관문의 판정 축은 **알려진 목 호스트명**이지 IP 대역이 아니다. 루프백이 그 목록에 들어 있는 근거도 대역이 아니라 '애플리케이션과 같은 머신은 벤더 실서버일 수 없다'는 배포 형상이다. 결과적으로 운영 배포에서 비식별 주소만은 루프백으로 저장되지 않는다 — 저장 축 전반이 루프백을 허용한다는 서술과 이 한 지점을 함께 읽어야 한다.

### 변경 행위를 좁히는 방법
검수자가 관리자 공유 패스워드를 제출하면 서버가 무상태 서명 토큰을 발급한다. 유효기간은 기본 10분이고 상한 30분은 설정으로도 넘을 수 없다. 유효 여부 판정은 서버가 소유한다 — 클라이언트가 스스로 아직 유효하다고 정하지 못한다. 이 토큰은 **연동 주소 설정 변경에만** 효력이 있고 역할을 승격시키지 않으며 다른 설정 키에는 아무 효력이 없다. 인가는 대체되지 않고 가산된다 — 검수자 권한은 그대로 필요하다.

게이트는 컨트롤러가 아니라 **저장을 수행하는 지점 한 곳**에 둔다. 호출처마다 배선하면 새 진입점이 생길 때 샌다.

진입점은 역할 자가부여와 분리하되 패스워드 해시와 속도 제한은 **공유한다** — 버킷을 나누면 두 진입점을 번갈아 써서 실효 한도가 두 배가 된다. 그 대가로 역할 자가부여 호출이 몰리면 관리자 창 발급이 함께 제한되는데, 이는 알고 받아들인 것이다. 판정 순서는 인가(403) → 속도 제한(429) → 패스워드 비교(401) 다. 권한 없는 사람이 속도 제한 몫을 갉아먹지 못하게 하기 위해서다.

### 감사
새 테이블을 만들지 않는다. 시스템 설정 테이블(LS_SYSTEM_CONFIG)의 수정자·수정일시 컬럼이 '누가·언제·어느 키·현재값'을 담고, 그 위에 변경 사실을 정보 수준 로그로 남긴다. 주소는 남기되 자격증명 부분은 가리며, **패스워드와 토큰은 어떤 로그에도 남기지 않는다.**

### 노출 경계
설정 화면은 내부 채널 + 검수자 전용이며 포털 채널에는 노출되지 않는다.

### 되돌리기 금지
대역 차단을 '보안 강화' 명목으로 되살리면 **정당한 연동이 전부 막힌다** — 배포 기본값 자체가 내부망 주소다. 되살리려면 그 전에 연동 대상이 공인망에 있다는 배포 전제부터 성립해야 한다.

## consequences

### risks

- 관리자 공유 패스워드를 얻은 자가 주소를 바꿔 영상·라벨을 다른 서버로 내보낼 수 있다. 다만 이는 대역 차단으로는 애초에 막히지 않던 위험이며(공인망 주소로 바꾸면 그만) 이 결정으로 새로 생긴 것이 아니다 — 인지하고 수용한 잔여 위험이다.
- 클라우드 메타데이터 탈취 경로는 온프렘 내부망 배포라 성립하지 않는다는 전제 위에 서 있다. 배포 형상이 클라우드로 바뀌면 이 전제가 무너지므로 그때 재검토해야 한다.
- 비식별 축은 위탁 경로와 진행 조회 경로에 각각 배선이 필요해, 한쪽을 빠뜨리면 위탁은 새 서버로 가는데 조회만 옛 서버로 나가 그 작업이 영원히 완료되지 않는다.

### neutral

- 설정 행을 시드하지 않으므로 저장 전까지는 목록 조회에 그 키가 나타나지 않는다 — 행이 없는 것이 정상 상태다
- 감사에 새 테이블을 만들지 않고 기존 시스템 설정 테이블의 수정자·수정일시와 로그로 충당한다

### negative

- 대역 판정이 있는 축(기동 시점 배포 기본값)과 없는 축(운영 화면 저장값)이 공존해, 같은 주소가 경로에 따라 다르게 판정된다
- 비식별 축만 목·시뮬레이터 호스트 거부 관문이 하나 더 있어 저장 축의 규칙이 연동마다 완전히 같지는 않다
- 설정 변경이 다른 노드에 반영되기까지 설정 캐시 수명만큼 지연된다

### positive

- 대상 서버 교체가 재기동 없이 가능해져 운영 중 연동 전환이 성립한다
- 내부망에 있는 실제 연동 대상을 정상적으로 가리킬 수 있다
- 설정 키가 애플리케이션 속성명과 같아 매핑표라는 두 번째 진실원이 생기지 않는다
- 변경 권한이 주소 설정에만 한정되고 역할을 승격시키지 않는다
- 망 통제 책임이 인프라 계층으로 분명해진다
- 거부 응답에 해석 결과를 싣지 않아 응답이 내부망 탐색 수단이 되지 않는다

## decision_drivers

- 연동 대상이 내부망의 별도 서버일 가능성이 높아 대역 차단이 정당한 대상을 막는다 — 배포 기본값조차 거부된다
- 주소를 바꾼 뒤 재기동해야 하면 운영 중 대상 교체가 사실상 불가능하다
- 설정 키를 새로 만들면 그 매핑표가 두 번째 진실원이 되어, 한쪽만 갱신되는 순간 화면에서 바꾼 주소가 엉뚱한 연동에 반영된다
- 주소 변경 권한이 역할 승격으로 번지면 안 된다
- 거부 응답이 내부망을 탐색하는 수단이 되면 안 된다
- 망 통제의 책임 경계가 애플리케이션과 인프라 사이에서 분명해야 한다

## considered_options

### 배포 설정 고정 유지(구 상태)

**cons**:

- 대상 서버 교체 때마다 재기동이 필요해 운영 중 교체가 사실상 불가능하다
- 연동 대상이 바뀌는 동안 그 연동이 통째로 멈춘다

**pros**:

- 사람이 바꿀 수 없으므로 이 축의 공격 표면이 없다

- **description**: 주소를 애플리케이션 배포 설정에만 두고 운영 화면에서는 바꾸지 못하게 한다. 대상 서버가 바뀌면 설정을 고쳐 재기동한다.

### 설정화 + IP 대역 차단 유지(도입 시 채택, 폐기)

**cons**:

- 내부망 대상을 정당하게 가리키지 못한다 — 배포 기본값 자체가 거부된다
- 공인망 주소로 바꾸면 어차피 우회되므로 실효가 제한적이다
- 막을 대역이 사라지면 전송 직전 재검증도 검증할 내용이 없어 함께 무의미해진다

**pros**:

- 서버측 요청 위조 표면을 좁힌다는 통상의 보안 검토 기대에 부합한다

- **description**: 운영 화면에서 주소를 바꾸되, 도메인을 IP 로 해석해 사설·링크로컬·루프백·클라우드 메타데이터 대역을 차단하고 요청 전송 직전에 다시 해석해 재검증한다.

### 설정화 + 저장 축 대역 차단 폐지 + 관리자 단기 유효창(채택)

**cons**:

- 관리자 공유 패스워드를 얻은 자가 주소를 바꿔 데이터를 다른 서버로 내보낼 수 있다
- 대역 판정이 있는 축(기동 시점 배포 기본값)과 없는 축(운영 화면 저장값)이 공존해, 같은 주소가 경로에 따라 다르게 판정된다

**pros**:

- 내부망의 실제 대상을 정상적으로 가리킬 수 있다
- 재기동 없이 다음 호출부터 반영된다
- 변경 권한이 주소 설정에만 한정되고 역할을 승격시키지 않는다
- 망 통제 책임이 인프라 계층으로 분명해진다

- **description**: 연동 주소 넷을 운영 화면에서 재기동 없이 교체한다. 저장 값에는 IP 대역 판정을 하지 않고 스킴·형식 계열 검증만 남기며, 변경 행위는 역할을 승격시키지 않는 관리자 단기 유효창으로 좁힌다. 망 통제는 인프라 계층이 담당한다.
