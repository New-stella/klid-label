## description

인증·세션 통제 기준:
- 로그아웃·토큰 만료 시 세션 종료 — 만료 JWT 거부 및 상위 시스템(관제/포털) 로그인 페이지 리다이렉트
- 접근 토큰의 보관 위치는 채널마다 다르다 — 관제 채널은 상위 시스템과 같은 출처의 브라우저 저장소로 JWT 를 인계받고, 포털 임베딩 채널은 Host 가 주입한 인계 창구로 토큰을 얻어 브라우저 저장소를 쓰지 않고 Host 메모리에만 둔다. 두 채널 모두 URL 쿼리 파라미터로 토큰을 전달하지 않으며, 저작도구는 토큰을 발급하지 않고 검증만 한다. 인계 창구와 전용 요청 헤더의 이름·규약은 INT-013 이 소유한다.
- 인증정보·시크릿은 소스코드에 하드코딩하지 않고 환경변수로 주입, 민감정보 암호화
- 관리 화면(/manage/* · /admin/*) 등 권한 페이지는 비인가자에게 노출되지 않도록 함
※ 로그인 실패 5회 제한·동시 로그인 차단은 인증 발급 주체(관제/포털) 책임 — 저작도구는 JWT 검증만 담당
※ 예외 — 관리자 페이지 진입에 쓰이는 관리자 단기 유효창은 저작도구가 스스로 발급·검증·만료시키는 유일한 자체 세션이다. 관리자 공유 패스워드를 대조해 발급하며 유효기간은 기본 10분이고 상한 30분은 설정으로도 넘을 수 없다. 유효 여부 판정은 서버가 소유한다 — 클라이언트가 스스로 아직 유효하다고 정하지 못한다. 이 유효창은 역할을 승격시키지 않는다 — 인가는 대체되지 않고 가산되므로 본래 요구되던 권한은 그대로 필요하다.
※ 관리자 단기 유효창이 요구되는 범위는 관리 기능 공통 진입이다. 대상은 성질로 정한다 — 운영·관리 성격의 쓰기 행위. 사용자 역할 부여·변경, 연동 서버 주소 변경, 영상 업로드의 시작, 관리자 패스워드 변경이 그런 행위다. 이 열거는 전수 목록이 아니라 예시이며 판정 기준은 '운영·관리 성격의 쓰기인가' 하나다. 요구되지 않는 것도 명시한다 — 조회(읽기)에는 요구하지 않으며, 포털 채널 이용자가 자신의 자산을 올리는 업로드도 대상이 아니다. 업로드는 시작 시점에 한 번만 확인하고 이어 올리기·취소·진행 위치 조회에는 요구하지 않는다.
※ 관리자 패스워드의 보관·교체 — 해시로만 보관하고 평문은 어디에도 두지 않는다. 일반 설정 저장소에 두지 않는다: 그 저장소는 목록 조회로 값이 그대로 노출되어 해시가 권한 보유자 전원에게 읽히고 오프라인 대입 대상이 되기 때문이며, 자격 전용 저장 위치를 따로 둔다. 운영 화면에서 교체할 수 있고 교체에는 현재 패스워드 재확인을 요구한다 — 유효창만으로 바꿀 수 있으면 유효창 탈취가 곧 자격 완전 탈취가 된다. 교체하면 그 전에 발급된 유효창은 모두 무효가 된다. 별도의 무효화 장부를 두지 않고 토큰 서명이 현재 패스워드에 의존하게 하여 자연히 검증에 실패하도록 한다. 저장 위치에 값이 아직 없으면 배포 설정값으로 되돌아가 판정하고, 둘 다 없으면 어떤 패스워드도 통과하지 않는다. 패스워드와 토큰은 어떤 로그에도 남기지 않는다.
※ 구 서술 폐기 — '관리자 단기 유효창은 연동 서버 주소 변경용이며 주소 설정 변경에만 효력이 있다'는 더 이상 이 대책의 범위가 아니다. 되살리면 그 밖의 운영·관리 성격의 쓰기가 관리자 확인 없이 열린다.
※ 채널별 보관 위치 차이의 함의 — 포털 임베딩 채널이 브라우저 저장소를 쓰지 않는 것은 그 채널에서 스크립트 삽입(XSS)으로 접근 토큰이 탈취될 표면을 줄인다. 다만 관제 채널은 여전히 브라우저 저장소를 쓰므로 그 채널의 기존 보호 대책은 그대로 유효하다 — 한쪽 채널의 성질을 두 채널 전체로 일반화하지 않는다.
※ 관제 채널의 브라우저 저장소에는 갱신용 토큰도 놓인다 — 인지·수용한 위험. 관제 채널에서는 수명 30분의 접근 토큰뿐 아니라 수명 7일의 갱신용(refresh) 토큰도 같은 출처 브라우저 저장소(tokenInfo)에 놓이고, 저작도구는 세션을 연장하려고 그 값을 읽어 상위 시스템(관제) 계정 갱신에 쓴다. 갱신 창구의 규약은 INT-013 이 소유한다. 그 결과 관제 채널에서 스크립트 삽입(XSS)이 한 번 성공하면 탈취되는 것이 30분짜리 접근 토큰이 아니라 7일 동안 접근 토큰을 다시 발급받을 수 있는 자격증명으로 커진다. 이 저장 방식은 저작도구가 새로 만든 것이 아니다 — 관제지원 웹이 이미 같은 위치·형식으로 저장하고 있어, 같은 출처인 관제 화면의 XSS 로도 같은 값이 노출된다. 저작도구는 관제와 같은 형식을 따를 뿐 저장 위치를 바꿀 권한이 없다. 완화는 둘이다 — 저작도구 화면의 XSS 방어 규칙(사용자 입력을 HTML 로 해석해 렌더하지 않는 것 등 기존 항목)을 그대로 유지하고, 갱신용 토큰 원문을 어떤 로그에도 싣지 않는다. 근본 해결(갱신용 토큰을 스크립트가 읽을 수 없는 쿠키로 옮기는 것 등)은 관제지원 시스템이 정할 사항이라 저작도구 단독으로 할 수 없으며 관제 협의 대상이다.
※ 관리자가 관제 통지 수신처 주소를 바꾸면 관제 채널 사용자의 관제 세션 자격증명이 그 주소로 전송된다 — 인지·수용한 위험. 저작도구 서버는 관제 계정 창구(갱신·로그아웃)를 중계할 때 관제 통지 수신처 주소 설정을 재사용하므로([[INT-015]]), 그 주소가 바뀌면 세션 갱신 때는 사용자의 갱신용(refresh) 토큰(수명 7일)이, 로그아웃 때는 접근 토큰이 바뀐 주소로 실려 나간다. 이 경로에는 호스트가 바뀌면 자격증명을 떼어 내는 가드를 둘 수 없다 — 떼면 세션 연장 기능 자체가 동작하지 않는다. 성질은 연동 서버 주소 설정의 기존 수용 위험(주소를 바꿀 권한이 있는 자가 데이터를 다른 서버로 내보낼 수 있다)과 같지만, 새로 걸리는 대상이 영상·라벨이 아니라 사용자 세션 자격증명이라는 점이 다르다. 완화는 기존 장치를 그대로 쓴다 — 주소 변경은 관리자 단기 유효창을 거쳐야 하고 변경자·변경 시각이 감사 기록으로 남는다. 주소 형식 검증은 스킴과 URL 형식만 보며 주소 대역은 차단하지 않는다(기존 결정).

잔여 위험(인지·수용, 2026-09-10 사용자 확정) — 갱신 중계 창구([[API-247]])는 만료된 토큰으로도 갱신해야 하므로 저작도구 로그인 검사가 없고 호출 횟수 제한도 두지 않는다. 임의 토큰으로 반복 호출하면 요청마다 관제 계정 서비스로 외부 호출이 한 번씩 나가고, 관제의 거절은 장애 격리 집계에 들어가지 않아 그 반복이 관제로 그대로 증폭된다. 받아들이는 근거는 관제 채널 배포본이 내부망 배포이고, 외부에 노출되는 포털 채널 배포본에서는 이 창구가 404 로 닫혀 있으며, 판정은 관제가 하므로 거절된 토큰으로는 아무것도 얻지 못한다는 것이다. 같은 축의 작은 노출로, 포털 채널에서 두 중계 창구([[API-247]]·[[API-246]])는 404 이지만 허용되지 않은 메서드로 부르면 405 가 나 경로의 존재가 드러난다 — 기능·자격증명 노출이 없어 함께 수용한다.

## measurement_method

만료·위조 토큰 401, 관리 화면 비인가 접근 차단을 통합테스트로 확인한다. 포털 임베딩 채널은 접근 토큰이 브라우저 저장소에 기록되지 않는 것도 함께 확인한다. 관리자 단기 유효창 없이 운영·관리 성격의 쓰기가 거부되고 조회는 통과하는 것, 관리자 패스워드 교체 후 그 전에 발급된 유효창이 무효가 되는 것도 함께 확인한다. 표식이 빠진 진입점을 사람의 주의력이 아니라 정적 검사가 잡는 것도 확인 대상이다 — 그 검사가 표식을 찾는 축이 둘인지까지 확인한다: 창구 자체에 붙은 표식과, 그 창구를 담은 타입에 붙어 그 안의 창구 전체에 걸리는 표식. 설정 저장 창구는 이 검사의 예외이므로 확인 대상에서 제외한다 — 요구 여부가 창구가 아니라 설정 키 단위로 갈려 표식을 쓰지 않고 저장 지점에서 판정 지점을 직접 부른다.
