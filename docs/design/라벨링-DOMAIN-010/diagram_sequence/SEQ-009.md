## description

버전 비교·복구 흐름(VersionController / VersionService). 버전은 검수 승인(APPROVED) 시점의 영상 단위 라벨 전체 스냅샷이며, 비교는 선택 건수에 따라 두 경로로 갈린다. ★버전 1건 선택 = 현재 작업본과 비교하며 전용 sub-resource GET /v1/versions/{version}/diff-with-working 를 쓴다 — 승인 버전이 1건뿐인 프레임은 기존 /diff?compareWith= 로는 비교 대상이 없어 변경 내역을 아예 볼 수 없었기 때문이고(사용자 신고), 같은 URL 에 쿼리 파라미터로 행위를 분기하지 않는다는 원칙을 따라 별도 경로로 둔 것이다(기존 /diff 의 URL·파라미터·응답 스키마·상태코드는 무변경). 작업본 payload 는 승인 스냅샷과 <동일 방식>으로 구성해야 한다(같은 구성 인자, LBL_SN 오름차순, 같은 직렬화 경로, 1MB 초과 폴리곤 단순화도 양쪽 재현) — 어긋나면 수정이 없는데 diff 가 나오는 오탐이 난다. 손상 스냅샷은 신규 경로에서만 items 가 명시적 배열일 때만 통과하고 아니면 400 이다(빈 결과는 화면에서 “변경 없음” 으로 표시돼 거짓말이 된다). 기존 /diff 의 장애격리(파싱 실패 → 빈 리스트)는 그대로 유지하며 두 경로의 차이는 의도이니 “일관성”을 이유로 통일하지 말 것. ★비교축(R7)은 id·lblTypeCd·label·labelId·points·trackId 이며 구 동작(lblTypeCd·label·points 3개만)은 폐기됐다 — 트랙 병합처럼 시스템 자신이 수정 통지를 발행하고 export 를 새 버전으로 재생성한 변경이 diff 에선 “변경 없음”이었기 때문이고, 판정축은 라벨 내용 해시(LabelContentHasher)의 입력과 srcSn 제외 합동으로 맞춘다. AI 메타(autoLblYn/confScore/lblSrcCd)와 표시용 labelName/color 는 의도적으로 제외한다. 비교기를 /diff 와 공유하므로 그 엔드포인트의 판정 결과도 함께 바뀐다(계약은 무변경). ★롤백은 새 버전 행을 적층하지 않고 <대상 스냅샷 행을 재활성>한다 — 롤백 결과 페이로드가 대상 스냅샷 그 자체라 재계산 해시가 대상 행과 같고 (DATA_SRC_SN, VERSION_HASH) UNIQUE 로 적층이 물리적으로 불가능하기 때문이고, 구 SAVE_REASON_CD='ROLLBACK' 적층 분기는 프로덕션 도달 불가한 죽은 코드라 제거됐다. 롤백은 라벨 본문을 작업본(LS_DATA_LBL)으로 실제 복원하며 LBL_SN·AI 메타(AUTO_LBL_YN/신뢰도/출처)·TRCK_ID 까지 보존 복원하고(점유된 PK 만 신규 발급 폴백 — PK 재발급 시 diff 가 “전량 교체”로 오분류된다), 롤백 행위(누가·언제·어느 VERSION_HASH 로)를 LS_DATA_LBL_HSTRY 에 기록한다. 현재 active 가 이미 대상 스냅샷이고 작업본도 동일하면 진짜 no-op 이다(라벨 재작성·이력·통지 모두 없음). 세 경로 모두 권한은 REVIEWER 전체 / WORKER 본인 배정이고, 비식별 누락 신고 구간(DE_IDNTF_YN='F')에서는 diff·롤백이 412 로 차단된다. 승인 후 롤백은 export 를 v{n+1} 로 전량 재생성하고 SUCCEEDED 이후 TASK_MODIFIED 를 발송한다. 알려진 한계(인지·수용): items[] 원소에 id 가 없으면 조용히 skip 되어 과대보고 / MAX_LABELS=500 절단을 응답이 알리지 않음 / 롤백 PK 충돌 폴백 시 내용이 같아도 REMOVED+ADDED 쌍. ★화면에서 쓰는 복구 동선은 되돌리기 엔드포인트가 아니라 <회차 불러오기 → 확정 저장> 2단계다 — 되돌리기 엔드포인트의 동작 자체는 그대로 남아 있지만 화면 동선이 없다. 불러오기(GET /v1/videos/{rawSn}/versions/{version}/labels)는 고른 회차 시점의 라벨과 프레임 폐기 상태를 영상 전체 범위로 읽어 화면에 올리기만 하고 서버에는 아무것도 쓰지 않는다(감사 이력·상태 전이·재검토 표시·산출 재생성 모두 없음). 확정 저장(PUT /v1/videos/{rawSn}/labels)이 유일한 쓰기 지점이며, 영상 전체를 한 트랜잭션으로 확정하고 프레임별 판번호를 전수 검증해 하나라도 어긋나면 409 로 전량 거부한다(일부만 저장하면 서로 다른 시점의 프레임이 섞인다). ★불러오거나 저장한다고 새 산출 버전이 생기지는 않는다 — 확정 저장은 버전 축을 건드리지 않아 회차와 스냅샷의 매핑도 그대로이며, 새 산출 버전은 검수 승인 시점에만 만들어진다. 구 즉시 적용 경로(고르는 즉시 서버에 반영)는 확정 게이트를 우회하는 두 번째 쓰기 경로가 되어 폐기됐다 — 사용자가 확인하기 전에 라벨이 통째로 과거화되고 되돌릴 창이 없기 때문이다. ★한번이라도 검수가 완료된 영상은 프레임 폐기·복원을 새로 바꿀 수 없어 400 이지만, 불러온 회차의 폐기 상태를 그대로 확정하는 저장은 예외다 — 판정은 프레임 단위 값 비교이며 기준선은 그 회차의 스냅샷 값이고 회차를 알 수 없는 프레임은 라이브 현재 값이다.
