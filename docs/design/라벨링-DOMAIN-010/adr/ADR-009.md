# 라벨 버전관리 Gitea 제거 — DB 스냅샷 기반 전환

## context

초기 고도화는 라벨 버전관리를 외부 Gitea(VCS) 커밋으로 구현했으나, 운영에 Gitea를 올릴 수 없어 DB 기반으로 전환한다. 라벨 저장 시 전체 스냅샷(JSON)을 LS_LABEL_VERSION.LABEL_PAYLOAD에 저장하고 버전 식별자는 payload의 SHA-256(VERSION_HASH)로 한다. diff/롤백은 두 스냅샷을 앱에서 비교·복원하며 외부 VCS에 의존하지 않는다. V53에서 Gitea 컬럼/큐를 제거했다. 이후 실제 구현을 재검토한 결과 구 롤백 시맨틱('새 active 버전으로 복원', SAVE_REASON_CD='ROLLBACK' 적층)이 도달 불가능한 분기였음이 드러났다 — 롤백 결과 페이로드가 대상 스냅샷 그 자체이므로 재계산 해시가 대상 행과 동일해 (DATA_SRC_SN, VERSION_HASH) UNIQUE 제약상 새 행 적층이 애초에 불가능했다. 이를 정정해 롤백은 대상 스냅샷 행을 재활성하는 방식으로 재정의되었다(2026-07-28).

## deciders

- 박찬기
- 김현욱

## decision

### chosen_option

DB 스냅샷 전환 + 롤백=대상 행 재활성(정정)

### justification

라벨 전체 스냅샷을 LS_LABEL_VERSION에 저장하고 VERSION_HASH로 식별하는 원 결정은 유지한다. 다만 롤백 시맨틱을 '대상 스냅샷 행 재활성'으로 정정한다(새 버전 행 적층 아님). 롤백 행위는 LS_DATA_LBL_HSTRY에 누가·언제·어느 버전으로 기록한다. 라벨 본문은 작업본(LS_DATA_LBL)으로 실제 복원하며 LBL_SN·AI 메타(신뢰도/출처)·TRCK_ID까지 보존 복원한다(PK 재발급 시 diff가 '전량 교체'로 오분류되는 것을 방지). 멱등 롤백(현재 active가 이미 대상 스냅샷)은 진짜 no-op — 라벨 재작성·이력·통지를 발행하지 않는다.

## consequences

### risks

- 멱등 롤백 판정 로직 결함 시 no-op이 실제로는 라벨을 조용히 덮어쓸 위험 — 회귀 테스트 필요

## considered_options

### Gitea(VCS) 유지

**cons**:

- 운영 인프라 불가
- 외부 의존·장애점

**pros**:

- Git diff 활용

- **description**: 외부 Git 커밋 기반 버전관리

### 새 active 버전 적층(구 설계, 도달불가 분기로 폐기)

**cons**:

- 롤백 결과 페이로드=대상 스냅샷이라 재계산 해시가 대상 행과 동일 — (DATA_SRC_SN, VERSION_HASH) UNIQUE 제약상 적층 자체가 도달불가 분기였음

**pros**:

- 버전 이력이 순차적으로 단순 누적

- **description**: 롤백 시 SAVE_REASON_CD='ROLLBACK'으로 새 버전 행을 적층해 active로 전환

### 대상 스냅샷 행 재활성(현 채택)

**cons**:

- 구 SAVE_REASON_CD='ROLLBACK' 코드 경로 폐기 필요

**pros**:

- UNIQUE 제약과 정합(도달불가 분기 제거)
- LBL_SN·AI메타·TRCK_ID 보존으로 diff가 실제 변경만 반영
- 멱등 롤백이 진짜 no-op

- **description**: 롤백은 대상 LS_LABEL_VERSION 행을 재활성하고, 라벨 본문을 작업본(LS_DATA_LBL)으로 실제 복원(LBL_SN·AI메타·TRCK_ID 보존). 롤백 행위는 LS_DATA_LBL_HSTRY에 기록. 멱등 롤백은 no-op.
