# 관리자 역할(ADMIN) 신설과 역할 계층 — 자가부여는 부트스트랩 전용, 진입자는 작업자로 자동 등록 (ADR-003·ADR-043 supersede)

## context

역할은 검수자·작업자·포털회원 3종이고 관리 권한이 검수자에 통합돼 있다. 관리 화면은 별도 주소로 분리하고 진입에 관리자 공유 패스워드로 여는 단기 유효창을 요구해 좁혔다. 그런데 역할 자가부여와 관리자 유효창이 같은 패스워드를 판정 근거로 공유한다. 그래서 비밀 하나로 검수자 획득 → 관리자 진입 → 관리 기능 전부가 이어지고, 서로 다른 관문처럼 설계된 둘이 실질적으로 하나의 관문이다. 또 검수자 화면에는 관리 메뉴가 그대로 노출된다 — 역할이 하나뿐이라 메뉴를 가를 축이 없고, 유효창을 노출 조건으로 삼으면 그 유효창을 여는 화면으로 들어갈 길 자체가 사라지기 때문이다. 한편 사용자 행이 만들어지는 경로도 자가부여 하나뿐이라 그 창구를 좁힐 수 없었고, 작업을 배정하려면 대상자가 먼저 자가부여를 해야 목록에 뜨는 제약도 있었다.

## decision

### chosen_option

관리자 역할 신설 + 역할 계층 + 부트스트랩 전용 자가부여 + 진입 시 작업자 자동 등록(채택)

### justification

관리자(ADMIN) 역할을 신설해 역할을 4종으로 두고, 관리자가 검수자 권한을 물려받는 계층을 둔다. 계층은 관리자에서 검수자로 가는 한 단계뿐이다 — 작업자는 작업자 전용으로 열린 자리가 따로 있어 계층에 넣으면 관리자·검수자가 그 자리에 흘러들고, 포털회원은 채널이 달라 계층에 넣으면 외부 채널 사용자가 내부 권한을 얻는다. 역할 자가부여는 관리자가 0명일 때만 열리고 부여 역할은 관리자 고정이다. 요청이 다른 역할을 지정해도 결과를 바꾸지 못한다. 관리자가 한 명이라도 생기면 창구가 닫혀, 그 뒤에는 관리자 패스워드를 알아도 역할을 얻을 수 없다. ★그 창이 열려 있는 동안에는 **이미 역할을 가진 사람도** 관리자가 될 수 있다 — 창이 닫힌 뒤에만 역할 보유자를 거절한다. 이 완화가 없으면 최초 관리자를 만들 수 있는 사람이 아무도 없다: 이미 운영 중인 시스템에는 역할 없는 사용자가 존재하지 않고, 신규 설치에서도 진입 시 자동 등록이 같은 요청에서 작업자 역할을 부여해 그 뒤의 판정에 걸린다. 즉 자가부여 창구와 자동 등록이 서로를 막는 교착이 생긴다. 창이 열려 있다는 것 자체가 '아직 아무도 관리자가 아니다'라는 뜻이므로, 그 구간에서 역할 보유 여부를 따지는 것은 보호가 아니라 잠금이다. 마지막 관리자의 강등·비활성은 거부한다 — 관리자가 0명이 되면 그 창이 다시 열린다. 인증을 통과한 내부 채널 사용자에게 역할이 없으면 그 시점에 사용자 행과 작업자 역할을 만든다. 이미 부여된 역할은 덮어쓰지 않는다 — 관리자가 지정한 역할이 되돌려지면 안 된다. 이후 역할 부여는 관리자가 사용자 관리에서 관리자·검수자·작업자 중 하나로 지정한다. 관리 메뉴는 역할로 가른다 — 검수자에게는 관리 항목이 보이지 않으며, 노출 조건을 역할로 삼으면 유효창을 노출 조건으로 쓸 때 생기던 진입 불가 문제가 성립하지 않는다.

## brownfield

### notes

ADR-003(관리자 역할 폐기)과 ADR-043(자가부여 시 자동등록 + 검수자 자가부여 허용)을 함께 대체한다. 둘을 하나로 묶는 이유는 두 결정이 서로를 전제하기 때문이다 — 계층이 있어야 겸직 문제가 사라지고, 자가부여를 조건화해야 부트스트랩 락아웃이 풀린다. 어느 하나만 바꾸면 성립하지 않는다. 역할 판정의 진실원이 저작도구 소유 역할 테이블이라는 ADR-021 의 결정은 변경 없다.

### diff_summary

역할 3종 → 4종(관리자 신설) + 관리자에서 검수자로 가는 한 단계 계층. 자가부여: 항상 열림·검수자/작업자 선택 → 관리자 0명일 때만·관리자 고정. 사용자 등록 시점: 자가부여 때만 → 인증 통과 시 작업자로 자동. 관리 메뉴 노출 축: 유효창 보유 여부를 쓰지 않음 → 역할.

## consequences

### risks

- 최초 부트스트랩 순간에는 여전히 관리자 패스워드를 아는 사람이 관리자가 된다. 1회뿐이고 관리자가 생기는 즉시 닫히지만, 그 창을 누가 먼저 차지하느냐는 경쟁이다 — 배포 직후 운영자가 곧바로 잡는 것으로 흡수한다
- 관리자를 전부 잃으면 저장소를 직접 고치는 것이 유일한 복구 경로다. 마지막 관리자를 보호하는 대가이며, 복구 절차를 운영 문서에 남겨야 한다
- 관리자 패스워드는 사라지지 않는다 — 최초 부트스트랩과 관리자 유효창에 계속 쓰이므로 그 관리 수준은 여전히 중요하다
- 부트스트랩 창이 열려 있는 동안에는 관리자 패스워드를 아는 역할 보유자(검수자·작업자)도 관리자가 될 수 있다. 창은 최초 1회로 닫히고 그 뒤에는 누구에게도 열리지 않으므로 상시 노출이 아니다 — 인지하고 수용한다.

### negative

- 배포 직후에는 관리자가 0명이라 누군가 부트스트랩으로 최초 관리자를 만들 때까지 관리 기능이 잠긴다
- 자동 등록으로 사용자 행이 늘어난다 — 다만 배정 전에는 아무 데이터도 볼 수 없다

### positive

- 역할 획득과 관리자 진입이 서로 다른 근거를 갖는다 — 비밀 하나로 끝까지 가던 경로가 끊긴다
- 관리 메뉴를 역할로 가를 수 있어 검수자 화면에서 관리 항목이 사라진다
- 부트스트랩 락아웃이 조건으로 해소된다 — 관리자를 만들 최초 1회 창이 열리고 그 뒤 닫힌다
- 작업 배정 제약이 풀린다 — 대상자가 자가부여를 하지 않아도 접속만 하면 배정 목록에 뜬다
- 기존 검수자 권한 지점을 바꾸지 않는다 — 계층이 그 지점들을 그대로 통과시킨다

## considered_options

### 현행 유지 — 관리자 역할 없이 별도 주소 + 공유 패스워드 유효창

**cons**:

- 역할 획득과 관리자 진입이 같은 패스워드를 쓰므로 비밀 하나가 끝까지 연다
- 역할이 하나뿐이라 검수자 화면에서 관리 메뉴를 감출 축이 없다

**pros**:

- 역할 체계 무변경
- 기존 권한 지점을 하나도 건드리지 않음

- **description**: 역할 체계를 손대지 않고 관리 화면을 별도 주소로 두며 진입에 관리자 패스워드를 요구한다.

### 관리자 역할 신설 + 역할 계층 + 부트스트랩 전용 자가부여 + 진입 시 작업자 자동 등록(채택)

**cons**:

- 배포 직후 관리자가 0명인 구간이 생긴다
- 마지막 관리자를 보호하는 대가로, 관리자를 전부 잃으면 저장소 직접 수정이 유일한 복구다

**pros**:

- 두 관문의 근거가 갈린다
- 계층 덕분에 기존 검수자 권한 지점을 바꾸지 않는다
- 관리 메뉴를 역할로 가를 수 있다
- 자동 등록이 배정 제약을 함께 해소한다

- **description**: 관리자 역할을 두고 관리자가 검수자 권한을 물려받게 한다. 자가부여는 관리자가 0명일 때만 열려 관리자를 만들고, 그 외 진입자는 작업자로 자동 등록되며 이후 역할은 관리자가 지정한다.

### 관리자 역할 신설 + 계층 없음(순수 분리)

**cons**:

- 겸직이 필요하면 한 사람에게 계정이 둘 있어야 하는데 사용자 식별자가 인계 토큰의 주체 값 하나라 우리가 만들 수 없다
- 검수자 권한 지점 전부를 관리 성격과 검수 성격으로 다시 분류해야 한다

**pros**:

- 권한 경계가 가장 깔끔하다

- **description**: 관리자와 검수자를 겹치지 않는 별개 역할로 두어 관리자는 검수를 하지 않는다.

### 사전 등록 명부

**cons**:

- 접속자와 명부 행을 이을 키가 없다 — 인계 토큰에 이메일이 없고, 이름은 유일하지 않으며, 계정 표시값은 요청 본문으로 오는 위조 가능한 값이라 매칭 키로 쓰면 남의 행을 가로챌 수 있다
- 진입 시 자동 등록이 같은 목적을 달성하므로 미리 만들 이유가 없다

**pros**:

- 시스템을 쓸 사람을 미리 통제할 수 있다

- **description**: 관리자가 이름·이메일을 미리 등록해 두고 접속 시 그 행에 사용자 식별자를 채워 잇는다.
