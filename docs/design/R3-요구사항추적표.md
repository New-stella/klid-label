# R3 요구사항 추적표

## 작성 목적
> 시스템의 요구사항을 도출하여 개발의 각 단계별로 작성한 산출물이 일관성을 가지는지를 추적할 수 있도록 각 단계별 산출물의 추적성을 관리하기 위하여 작성한다.

## 작성 방법
> 사용자 요구사항 정의서(R1)로부터 시작하여 분석(R2), 설계(D2/D3/D9), 구현(I1/D11), 시험(D10/D7)의 각 단계별 산출물에 ID를 식별하고, 전단계 산출물과 후속단계 산출물 간의 연계관계를 매핑하여 산출물이 단계별로 끊어지지 않고 추적되도록 한다. 모든 매핑은 이미 작성된 실제 산출물 문서에서 ID를 직접 읽어 연결하였다(추측 금지).

## 1. 개요

### 1.1 추적 대상 산출물 및 ID 체계

| 단계 | 산출물 | ID 형식 | 출처 | 작성 상태 |
|------|--------|---------|------|-----------|
| 분석 | 사용자 요구사항 정의서(R1) | `RQ-SFR-NN-NN` | R1 | 작성 완료 |
| 분석 | 유스케이스 명세서(R2) | `KLID-AT-UC-NNN` | R2 | 작성 완료 |
| 분석 | 검수기준(Acceptance) | `AC-NNN` | LogiCraft | 작성 완료 |

> **빈 셀(`-`) 정책**: 추적성 단절은 `-`로 표기한다. 단절에는 두 종류가 있다 — ① 후속 단계라 아직 산출물이 없는 경우(I1·D11·D10), ② 해당 요구사항 성격상 산출물이 존재할 수 없는 경우(예: 화면 없는 시스템 유스케이스). 사유는 §4 부록에 정리한다.
> **I1 프로그램코드 표기**: 설계 단계로 I1(프로그램코드) 산출물 문서는 아직 작성 전이다(`backend/` 코드는 존재하나 I1 추적 문서 미산출). 따라서 I1 컬럼은 D1 클래스설계서의 클래스 ID(`KLID-AT-DC-NNN`)와 예상 파일명(`{클래스명}.java`)을 **참조 ID**로 기입한다. 실제 구현이 동일 클래스명으로 이루어지면 추적이 그대로 연결된다.

### 1.2 행(Row) 구성 원칙
- 본문 추적표의 행은 **R1에 등재된 SFR 기능 요구사항 17건**(`RQ-SFR-06-03`~`RQ-SFR-09-07`) 기준으로 구성한다.
  - **건수 주석(17 추적대상 / 18 전체)**: LogiCraft requirement 항목은 총 18건(`REQ-001`~`REQ-018`)이나, 그중 `REQ-002`(=`RQ-SFR-06-04` 프롬프트 편의성)는 외부 생성 시스템 책임으로 deprecated 처리되어 추적 대상에서 제외된다. 따라서 **본문 추적 대상은 17건**이다. (06-04은 §4.1에 성격상 부재로 기재)
- D7 시스템시험에는 R1 미등재 ID(`RQ-SFR-10-01/02` VLM 시계열, `RQ-SFR-16-01` 이미지 볼륨, `RQ-SFR-17-01` 영상 볼륨)가 일부 섞여 있다. 이는 §4.3 부록 표에 분리 기재하고 본문 행에서는 제외한다.
- 화면 ID는 D2, 컴포넌트 ID는 D3, 테이블 ID는 D9를 진실원(source of truth)으로 한다. (D5의 구(舊) 컴포넌트 ID 체계는 사용하지 않는다.)
- 매핑 근거: R2 §유스케이스 목록(관련 요구사항 ID 컬럼) 및 R2 §추적 요약표(R1→UC), D2 §2.1 화면목록(관련 UC + 관련 요구사항), D3 §2 컴포넌트목록(관련 UC), D9 §테이블 목록, D1 §1 설계 클래스 목록(관련 UC), D7 §2 시험 시나리오(관련요구사항ID).
