# 관제 인계 JWT 검증 규격 — iss 부재 허용 + userId 식별 + userNm 이름 폴백 + principal 신원 정규화 + 미등록 진입자 userNo 자동발급

## context

저작도구는 독립 로그인 UI 가 없고 관제서버가 발급한 JWT 를 인계받아 진입한다. ADR-012 가 인계 수단(관제 채널은 호스트와 동일 origin 을 공유하므로 브라우저 스토리지로 JWT 를 인계받는다)을 정했으나, 그 토큰을 받은 뒤 검증하는 규격은 어느 결정에도 없었다. 그래서 실제 관제 토큰이 우리 검증에서 막힌다. 이 결정은 인계받은 토큰을 검증하는 규격을 정하며, 어긋나는 세 지점을 우리 쪽에서 흡수한다.

실측(2026-09-04) — 관제 관리자 계정의 실제 토큰으로 우리 검증 흐름을 재현했다. 서명 알고리즘은 HS512 이고 시크릿 서명검증을 통과하며 만료(exp)가 있다(30분). channel 클레임이 없고 iss 클레임이 없다. sub 는 문자열 "admin" 이고, 관제가 사용자 ID 로 넣은 값은 userId="admin" 이다. name 클레임이 없고 이름은 userNm 클레임에 들어 있다. 그 밖에 관제 고유 클레임(authority=SYSTEM_ADMIN 등)이 실려 온다.

어긋나는 세 지점 — ① 우리는 iss 가 없거나 비면 거부하는데 관제 토큰에는 iss 가 없어 여기서 막힌다. ② 역할 조회 키를 표준 필드 sub 로 잡으면 관제가 그 자리에 무엇을 넣을지 계약 보장이 없다. ③ 표시 이름을 name 클레임으로 읽는데 관제는 userNm 에 넣는다.

⚠ 정정(2026-09-05 실측 — 실제 브라우저 로그인 디코드가 정본) — 위 「실측(2026-09-04)」 단락의 가정은 실제와 정반대였다. 관제 admin(userNo 9001) 로그인 실토큰을 브라우저 localStorage 에서 디코드한 결과: header alg=HS256(HS512 아님) · payload sub="9001"(숫자 userNo, 문자열 "admin" 아님) · iss="klid-auth"(있음, 없지 않음) · role="ADMIN"(있음) · channel="INTERNAL"(있음) · name="시스템관리자"(name 클레임, userNm 아님) · exp=iat+3600. 저장 위치는 localStorage['klid-jwt-token'] + sessionStorage['klid_jwt'] 이며, 관제팀이 「1차개발」로 안내한 sessionStorage['label-studio-auth-token'] 키는 현재 시스템에 없다(webroot 번들 0건).

⚠ 따라서 이 ADR 결정 ①(iss 부재 허용)·③(name→userNm 폴백)·⑤(비숫자 sub→userId 조회→userNo 시퀀스 자동발급)이 만든 로직은 실제 관제 토큰에서 한 번도 발동하지 않는 휴면 코드다(무해하나 불필요). 되살려 설계 근거로 삼지 말 것.

⚠ 2026-09-05 「관제→저작도구 로그인 루프」의 진짜 원인은 토큰이 아니라 인프라였다 — apache RO 단일파일 마운트 stale 로 /label-studio/api 404 + 옛 placeholder FE + 브라우저 토큰 만료가 겹쳤다. 이 ADR 결정 자체가 로그인 루프를 고친 것이 아니다.

## decision

### chosen_option

우리 검증을 관제 토큰에 맞춘다 — iss 부재 허용 + userId 식별 + userNm 이름 폴백 + principal 신원 정규화 + 미등록 진입자 userNo 자동발급·자동등록

### justification

인계받은 관제 토큰을 검증하는 규격을 아래 지점들로 확정한다. 인계 수단은 ADR-012 가 정한 그대로 두고(관제 채널은 동일 origin 브라우저 스토리지), 이 결정은 그 수단으로 받은 토큰을 우리가 어떻게 검증하는지만 정한다.

① issuer 게이트 — iss 부재를 허용한다. 지금 우리는 iss 가 없거나 비면 거부하며 관제 토큰이 여기서 막힌다. iss 클레임이 없는 경우를 통과시킨다. ⚠ iss 가 있는데 허용목록 밖이면 여전히 거부한다 — 「iss 없음 허용」과 「아무 iss 허용」은 다르며 전자만 연다. 시크릿 서명검증과 exp(만료) 필수는 그대로 유지한다. iss 를 완화한 뒤 발급자에 대해 남는 방어는 시크릿 서명검증과 exp 둘이다.

② 식별 — userId 클레임으로 한다. 역할 조회 키를 표준 필드 sub(관제가 그 자리에 무엇을 넣을지 계약 보장이 없다)가 아니라 관제가 사용자 ID 로 의도해 넣은 userId 클레임으로 한다. 저작도구 마스터 LS_ACNT_USER.USER_ID(길이 20)로 조회한다. ⚠ USER_ID 에 유일 제약이 없어 다중 매칭이거나 0건 매칭이면 어느 행으로 잇는지가 추측이 되므로(CWE-639) 그 경우는 fail-closed 로 무권한 처리한다. 기존 숫자 sub(USER_NO) 식별 경로는 그대로 두고 바꾸지 않는다.

③ 이름 — name 이 없으면 userNm 을 읽는다. 표시 이름을 name 클레임으로 읽어 자동 등록 사용자의 표시명으로 쓰는데 관제는 그 값을 userNm 에 넣는다. name 을 먼저 읽고 없으면 userNm 으로 폴백한다. 이름은 표시용이며 인가에 쓰지 않는다.

★ 권한(역할)은 매핑하지 않는다 — 핵심 불변. 관제 권한 클레임(authority=SYSTEM_ADMIN 등)을 우리 Role 로 변환하지 않는다. 토큰에서 인가에 쓰는 것은 userId(식별) 하나뿐이고 역할은 저작도구 DB LS_USER_ROLE 가 정한다([[ADR-021]]). 이 결정은 그 원칙 위에서 식별 경로만 관제 토큰에 맞추는 것이다. 인계 수단은 [[ADR-012]] 가 소유하며 이 결정과 공존한다.

④ principal 신원 정규화 — 인가 신원과 principal 신원을 하나로 통일한다. 위 ② 는 userId 클레임으로 userNo 를 해석하도록 정했으나, 그 해석된 신원이 principal 에 실리지 않으면 다운스트림의 per-user 스코핑·소유권·감사가 여전히 raw sub(관제 로그인 ID)를 신원 키로 쓴다 — 숫자 파싱 경로는 비숫자 sub 를 null 로 떨궈 per-user 작업이 막히고, 문자열 직접사용 경로(감사 식별자·작업 잠금 키·소유자 비교)는 raw 로그인 ID 를 그대로 저장해 관제 관리자 여럿이 한 값으로 붕괴돼 부인방지가 약해진다(CWE-807·CWE-778). 그래서 인계 토큰의 principal 신원을 인증 필터 한 곳에서 「해석된 userNo」로 정규화한다 — 비숫자 sub 인 관제 토큰을 userId 클레임으로 유일 해석했을 때 principal 의 주체 식별자(sub)를 그 해석된 userNo(문자열)로 치환한다. 그 결과 관제 토큰이 내부·포털 토큰(sub 가 이미 숫자 userNo)과 동형이 되어, 다운스트림의 숫자 파싱 경로와 문자열 직접사용 경로가 모두 실제 사용자 식별자를 일관되게 본다. 정규화는 「해석 성공(유일 매칭)」일 때만 한다 — 다중·0건 매칭 등 해석 실패 시 raw 를 유지하며, 그때 숫자 파싱은 null 이 되어 기존 fail-closed(무권한)가 그대로 성립한다(정규화가 fail-closed 를 풀지 않는다). 내부·포털 토큰(숫자 sub) 경로는 정규화 전후 값이 같아 무변경이다. 다운스트림 코드는 바꾸지 않고 필터 한 곳에서 흡수하며, 이 결정은 신원(식별) 축이지 권한 축이 아니다 — 권한 매핑 금지 불변은 그대로다.

⑤ 미등록 관제 진입자 로컬 식별 레코드 자동발급 — 위 ② 는 userId 클레임으로 저작도구 마스터 LS_ACNT_USER.USER_ID 를 조회하도록 정했으나, USER_ID 행이 아예 없는 신규 관제 사용자는 조회가 0건이라 userNo 를 얻지 못해 무권한으로 막히고 부트스트랩(role-claim)도 성립하지 않는다. 상용은 사용자 시드가 없어 관제 사용자 전원이 이 상태가 되어 관제 채널이 통째로 잠긴다. 그래서 관제(비숫자 sub·INTERNAL 채널) 진입자가 userId 로 조회 0건이면 진입 순간 우리 DB 에 로컬 식별 레코드(userNo)를 투명하게 발급·등록한다. 이는 회원가입 화면이 아니라 관제가 이미 인증한 사용자에 대한 로컬 식별 레코드 생성이며, 관제가 인증·관리하고 우리는 토큰으로 신원만 받는다는 원칙(내부 사용자 등록 시나리오는 없다) 위에서 역할 클레임 시점 자동등록의 연장이다 — 실제 토큰이 숫자 userNo 대신 로그인 ID 를 싣는다는 사실을 메운다. userNo 는 자동증가 시퀀스로 발급하되 관제가 sub 에 싣는 숫자 userNo·시드와 겹치지 않는 높은 disjoint 범위에서 뽑는다(충돌 금지). USER_ID 를 안정 키(부분 유니크, USER_ID IS NOT NULL)로 삼고 발급은 USER_ID 기준 원자적 upsert 로 한다 — 재진입·2노드 동시진입에 같은 사용자가 두 행으로 갈리면 이후 조회가 다중매칭 fail-closed 로 다시 잠기기 때문이다. 역할은 자동부여하지 않는다(role=null 유지) — 관제 authority 를 우리 역할로 매핑하지 않는 원칙([[ADR-021]]) 그대로다. 발급 후 첫 진입자는 관리자 비밀번호로 ADMIN 부트스트랩(role-claim)하고 이후 사용자는 관리자가 역할을 부여한다. 발급된 userNo 로 위 ④ principal 신원 정규화가 이어져 role-claim 의 식별이 성립한다. 신설 프로비저닝은 INTERNAL 채널 + 비숫자 sub 에만 적용되며 숫자 sub(내부·포털)·PORTAL 채널 경로는 무영향이다.

⑥ 아웃바운드 관제 통지 토큰 발급 — 위 ①~⑤ 는 관제에서 인계받은 토큰을 우리가 검증하는 인바운드 축이고, 이 ⑥ 은 우리가 관제로 나가는 아웃바운드 통지에 토큰을 발급하는 축이다. 같은 관제 채널 JWT 축이라 이 결정에 공존한다. 저작도구 → 관제 아웃바운드 완료/수정 통지(ControlNotifyClient → POST {base}/api/data-set/v2/jobs/{jobId}/notify-completed | notify-updated)는 관제 inbound SPI 가 x-access-token 헤더의 JWT 를 검증한다. 이 통지는 사용자 요청 스레드가 아니라 백그라운드(디바운서 flush·폴백 재시도 잡·export 복구기)에서 나가므로 사용자 인계 토큰을 실을 수 없다(요청 컨텍스트가 없고 인계 토큰은 이미 만료됐을 수 있다) — 그래서 우리가 서비스 토큰을 발급한다.

발급 규칙은 관제 발급 토큰과 형식을 맞춘다 — alg=HS256 · iss="klid-auth"(설정 가능, 기본 klid-auth) · exp=now+token-ttl-seconds(설정값, 하드코딩 금지, 짧은 기본 예 300s) · 공유 시크릿(JWT_SECRET) HMAC 서명. sub 는 서비스 식별자(예 klid-authoring-notify)로, 사용자 신원이 아니라 서비스 신원이다. 발송은 발송 시점 동적 발급으로 한다 — WebClientConfig.controlNotifyWebClient 의 정적 defaultHeader(x-access-token)를 발송 시점 ExchangeFilterFunction 으로 교체해 매 통지마다 새 토큰을 싣는다.

하위호환 — 정적 authoring.control-notify.token 설정값이 있으면 그것을 우선한다(관제팀이 별도 토큰을 주는 경우). 없으면 동적 발급하고, 둘 다 없고 시크릿도 없으면 헤더 미부착 fail-safe 로 둔다(통지 자체는 죽지 않으며 폴백 큐가 흡수한다. enabled 인데 발급 불가면 WARN). 수명은 짧은 고정 수명 = 설정값(token-ttl-seconds)으로 하고 관제 수명 자동 미러나 인바운드 관측은 하지 않는다(사용자 확정 2026-09-05) — 발송 즉시 사용이라 exp>now 만 성립하면 되고, 짧게 두면 관제 정책 변화와 무관하게 항상 유효하다.

보안 — 시크릿·토큰 값은 로그에 노출하지 않는다(CWE-532). 권한 매핑 금지 불변([[ADR-021]])은 그대로다 — 이 토큰은 서비스 신원일 뿐 역할을 나르지 않는다.

## consequences

### risks

- 관제 userId 가 저작도구 마스터 LS_ACNT_USER.USER_ID 에 실제로 존재하는지는 운영 DB 미확인이다 — 없으면 무권한 진입(fail-closed)이며, 규격은 그 경우를 견뎌야 한다

### neutral

- iss 완화는 「iss 없음」에만 적용되고 iss 가 있는데 허용목록 밖인 토큰은 여전히 거부된다
- 기존 숫자 sub(USER_NO) 식별 경로는 무변경으로 공존한다 — 관제 토큰의 문자열 userId 경로가 별도로 더해질 뿐이다
- 내부·포털 토큰(sub 가 이미 숫자 userNo) 경로는 정규화 전후 값이 같아 영향이 없다
- 관제 사용자가 저작도구 마스터에 없으면 해석 실패로 정규화가 일어나지 않고 무권한 fail-closed 로 남는다 — 없는 사용자 진입 정책은 별개 축이며 이 결정이 바꾸지 않는다
- 시퀀스 발급 userNo 는 관제 자체 USER_NO 와 별개인 우리 로컬 식별자다 — 관제로 나가는 통지의 job_id 등은 여전히 RAW_SN 축이라 무관하다
- 신설 자동발급 프로비저닝은 INTERNAL 채널 + 비숫자 sub 에만 적용되며 숫자 sub(내부·포털)·PORTAL 채널 경로는 무영향이다
- 결정 ①③⑤ 는 실제 관제 토큰(숫자 sub·iss 있음·name 있음)에서 발동하지 않는 휴면 경로다(2026-09-05 실측) — 무해하나 불필요하며 되살려 설계 근거로 삼지 않는다

### negative

- iss 부재를 허용하는 만큼 발급자 검증이 약해진다 — 발급자에 대해 남는 방어는 시크릿 서명검증과 exp 둘뿐이다
- userId 가 저작도구 마스터에 다중이거나 0건으로 매칭되면 무권한 진입이 되며, 이는 fail-closed 이므로 권한을 잘못 부여하는 것보다 안전하지만 정당한 사용자도 막힐 수 있다
- 관제 인계 토큰의 저장 식별자 의미가 로그인 ID 에서 userNo 로 바뀐다 — 내부·포털 토큰과 일치하므로 정합이며, raw 로그인 ID 를 필요로 하는 다운스트림은 없다(전부 파싱 대상이거나 opaque 식별자)
- USER_ID 부분 유니크 제약은 관제가 userNo 를 주던 시절 의도적으로 걸지 않았던 제약을 되돌리는 것이다 — 기존 중복 USER_ID 가 있으면 제약 생성이 fail-closed 로 실패하므로 사전 중복 점검이 필요하다
- 발송 시점 발급이라 시크릿/발급기 장애 시 헤더 미부착으로 통지가 인증 실패할 수 있다 — fail-safe 로 헤더를 빼고 폴백 큐가 재시도를 흡수한다

### positive

- 실제 관제 관리자 토큰이 우리 검증을 통과해 진입에 성공한다
- 역할 판정 진실원(LS_USER_ROLE)을 건드리지 않고 식별 경로만 관제 토큰에 맞춘다
- iss 를 완화해도 시크릿 서명검증과 exp 필수가 남아 위조·만료 토큰은 그대로 막힌다
- 관제 인계 사용자가 진입 후 per-user 스코프 작업까지 수행할 수 있다(기능 완결) — 해석된 userNo 가 principal 에 실려 숫자 파싱 경로가 비숫자 sub 에서 막히지 않는다
- 감사·소유권·작업 잠금이 실제 userNo 로 기록돼, 관제 관리자 여럿이 한 로그인 ID 로 붕괴되던 부인방지 약화(CWE-778)가 해소된다
- 신원 해석 지점이 인증 필터 한 곳으로 수렴해, 다운스트림에 흩어진 식별이 개별적으로 틀릴 여지가 제거된다(잠재 fail-open 봉쇄)
- 미등록 관제 사용자도 진입 후 실제로 사용 가능하다 — 첫 진입자는 관리자 비밀번호로 ADMIN 부트스트랩하고 이후 사용자는 관리자가 역할을 부여한다. 관제 채널이 통째로 잠기던 결함이 해소된다
- 사전 수동 등록 없이 성립한다 — 사용자 시드가 없는 상용 빈 테이블에서도 관제 진입만으로 로컬 식별 레코드가 생겨 부트스트랩 경로가 열린다
- 관제 통지 인증이 관제 발급 규칙과 형식 정합(HS256·iss=klid-auth·짧은 exp)이 되고, 20년 고정 정적 자격증명이 제거된다

## decision_drivers

- 독립 로그인 UI 부재 — 관제서버가 발급한 JWT 를 인계받아 진입하며 저작도구는 토큰을 발급하지 않는다
- ADR-012 는 인계 수단만 정했고 인계받은 토큰을 검증하는 규격은 어느 결정에도 없었다
- 관제는 이미 운영 중이고 우리가 인계받는 쪽이라 발급 형식을 우리가 바꿀 수 없다 — 우리 검증을 관제 토큰에 맞춘다
- 역할 판정 진실원은 저작도구 자체 LS_USER_ROLE(ADR-021)이며 토큰의 권한 클레임을 우리 역할로 변환하지 않는다
- 보안 관점 정합(2026-09-04) — 인가에 쓰는 해석된 신원(userNo)과 principal 이 나르는 신원(raw sub)이 갈려, 다운스트림 per-user 스코핑·소유권·감사가 raw 로그인 ID 를 신원 키로 썼다(CWE-807·CWE-778)
- 실토큰 E2E 결함(2026-09-05) — 관제 계정이 진입은 되나 USER_ID 행이 없어 무권한이고 부트스트랩도 못 해 관제 채널이 잠긴다. userId 조회 0건인 신규 관제 사용자에게 userNo 를 발급하는 경로가 없었다
- 실토큰 실측(2026-09-05) — 관제 통지 x-access-token 은 우리 시크릿 서명 JWT 를 수용한다(정적키→401, 유효서명→422 업무검증 도달). 20년 고정 HS512 정적 토큰(임시 상태)은 CWE-798 이라 관제 규칙(HS256·iss·짧은 수명)으로 발송 시점 발급으로 전환한다

## considered_options

### 우리 검증을 관제 토큰에 맞춘다 — iss 부재 허용 + userId 식별 + userNm 이름 폴백

**cons**:

- iss 부재를 허용하는 만큼 발급자 검증이 약해진다 — 남는 방어는 시크릿 서명검증과 exp 다
- userId 가 우리 마스터에 다중이거나 0건으로 매칭되면 무권한 진입이 된다

**pros**:

- 실제 관제 토큰이 진입에 성공한다
- 발급 주체(관제)에 형식 변경을 요구하지 않는다 — 우리가 인계받는 쪽이다
- 역할 판정 진실원(LS_USER_ROLE)을 건드리지 않고 식별 경로만 관제 토큰에 맞춘다

- **description**: 인계받은 관제 토큰의 실제 모양에 맞춰 우리 검증 세 지점을 조정한다. iss 클레임의 부재를 통과시키고, 역할 조회 키를 관제가 사용자 ID 로 넣은 userId 클레임으로 하며, 표시 이름을 name 이 없으면 userNm 으로 읽는다. 시크릿 서명검증과 exp 필수는 유지하며 권한 클레임은 우리 역할로 변환하지 않는다.

### 관제가 발급 형식을 바꾼다(iss 추가·sub 에 숫자 번호)

**cons**:

- 관제는 이미 운영 중이고 우리가 토큰을 인계받는 쪽이라 발급 주체에 형식 변경을 요구할 위치가 아니다
- 관제 발급 형식에 의존하는 다른 소비자가 함께 영향을 받는다

**pros**:

- 우리 검증 로직을 바꾸지 않아도 된다

- **description**: 관제서버가 JWT 발급 형식을 우리 기존 검증에 맞춰 iss 클레임을 넣고 sub 에 숫자 사용자 번호를 담도록 바꾼다.
