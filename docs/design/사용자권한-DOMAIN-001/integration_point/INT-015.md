### 2026-09-10 — 갱신 거절 시 즉시 로그아웃 확정 반영
- 실패 처리와 재시도 정책을 경로별 서술에서 실패 종류별 규칙으로 바꿨다(관제 거절은 호출 경로와 무관하게 즉시 로그아웃 / 일시 장애는 현재 토큰으로 계속 · 남은 시간 0 이면 로그아웃 / 401 뒤 실패·재시도 401 은 즉시 로그아웃).
- 세션 선정리 관측(900205)을 거절 즉시 로그아웃 규칙의 근거로 이었다.

### 2026-09-10 — 세션 팝업을 관제와 동일하게(「로그아웃」·「로그인 연장」) 확정 반영
- 팝업 「로그아웃」이 관제 계정 서비스의 로그아웃 창구를 부르게 되어 같은 연동점에 담았다(같은 외부 시스템·같은 계정 서비스·같은 인증 방식). 사양은 관제지원 웹 번들의 호출 동작을 실측해 옮겼다 — access 토큰 헤더 · 바디 없음 · 성공 `{error: 0}` · 응답과 무관하게 토큰 키 삭제 후 관제 로그인.
- 제목을 갱신 한정에서 두 창구를 담는 이름으로 넓혔다. 전송 메타가 단일 경로 구조라 갱신 창구를 대표로 두고 두 창구의 계약은 설명 본문이 갖는다.
- 관제 거절 즉시 로그아웃 규칙(①)에 저장소 재확인 예외를 더했다 — 다른 탭이 이미 새 토큰을 저장했으면 로그아웃하지 않고 그 토큰을 쓴다. 「동시 갱신 경쟁」·「미확인 — 관제 확인 대상」 절과 이었다.

### 2026-09-10 — 사용자가 누른 로그아웃의 미저장 확인 반영
- 로그아웃 창구의 호출 시점에 선행 조건을 더했다 — 저장하지 않은 편집이 있을 때만 화면 이탈 공통 확인 절차를 거치고, 계속을 골라야 부르며 취소하면 부르지 않는다.
- 강제 로그아웃(갱신 거절·401 뒤 갱신 실패·남은 시간 0)은 이 확인을 거치지 않는다 — 그 규칙은 무변경이다.

### 2026-09-10 — 브라우저 직접 호출 → 저작도구 서버(WAS) 경유 (사용자 확정)
- 사용자 확정 「관제 호출은 저작도구 WAS 를 통해 한다」로 연동 방향을 바꿨다. 옛 사양은 관제 채널 브라우저가 같은 출처에서 관제 계정 창구를 직접 부르고 저작도구 백엔드는 끼지 않는다고 적었다.
- 이제 브라우저는 저작도구의 갱신·로그아웃 API 를 부르고 저작도구 서버가 관제 창구로 중계한다. 주소는 관제 통지 수신처 주소 설정을 재사용한다(2026-09-14 폐기 — 아래 항목).
- 통지와 분리: 통지용 서비스 토큰 미적재 · 통지 활성화 토글 무관 · 장애 격리 별도. 짧은 타임아웃·자동 재시도 없음. 실패 분류(거절/일시 장애)는 저작도구 API 응답 코드로 브라우저에 전달된다.
- 브라우저 쪽 실패 결말 규칙(거절 즉시 로그아웃·저장소 재확인 예외·일시 장애 계속·401 뒤 실패 즉시 로그아웃)과 저장 규칙은 무변경이다.
- 설명 상한 때문에 외부 문서 차이 비고는 응답 항목 한 줄로 흡수하고, 세션 선정리 관측·인계 창구 관계·동시 갱신 경쟁·미확인 서술을 뜻을 바꾸지 않고 짧게 줄였다. 도입 문단의 목적 문장·왜 필요한가의 부연·인계 창구 괄호 열거를 줄였다(뜻 불변). 토큰 로그 금지 문장에 서버 미저장·본문 로깅 시 가림을 더했다.

### 2026-09-14 — 관제 계정 창구 주소 분리 (사용자 확정)
- 대상 주소를 관제 통지 수신처 주소 재사용에서 관제 계정 창구 주소(`authoring.control-account.url`) 단독으로 바꿨다. 통지 주소로 폴백하지 않는다 — 판정 원천이 둘이면 같은 사고가 조용히 재발한다.
- 근거: 관제는 계정 창구와 데이터셋 창구를 서로 다른 WAS 에 두고 관제 웹서버가 경로별로 나눠 보낸다(개발 서버 실측 — 통지 WAS 직접은 HTML 404, 계정 WAS 직접·관제 웹서버 경유는 401 JSON). 운영 현장에서 통지 수신처에 통지 WAS 를 넣자 세션 연장이 404 로 전부 실패했고 누적 실패로 서킷이 열려 로그아웃 중계까지 막혔다.
- 미설정이면 관제를 호출하지 않고 일시 장애(로그아웃은 관제 확인 없음)로 끝나며, 결정적 상태라 서킷 실패로 세지 않는다. 배포 기본값은 비어 있고 관제 채널 배포본은 설치 때 반드시 설정한다. 관리자 설정 화면에서 재기동 없이 바꾼다.
- 서킷을 갱신 전용·로그아웃 전용으로 나눴다(통지 서킷과도 별개).
- 설명 상한 때문에 뜻을 바꾸지 않고 중복 문장을 덜어냈다 — 인증 줄의 헤더 축 대비(인증 상세 비고에 있다) · 실패 처리 첫 줄의 호출 경로 열거(「호출 경로와 무관하게」와 같은 뜻) · 성공 판정의 「그 밖은 모두 실패다」(「때만」과 같은 뜻) · 저장소 재확인 예외의 동시 갱신 근거(동시 갱신 경쟁 절에 있다) · 로그아웃 인증의 창구별 반대 대비(인증 상세 비고에 있다) · 분류 줄의 응답 코드 전달(실패 처리 절 첫 줄에 있다). 타임아웃 근거·거절 재시도 무의미 근거·로그아웃 결말 근거는 짧게 줄였다.

## auth_detail

### notes

헤더에 **refresh 토큰** 원문을 싣는다(access 토큰이 아니다 — 헤더 이름은 관제지원 시스템 자신의 API 인증(`x-access-token` 에 access 토큰)과 같지만 담는 값이 다르며, access 토큰을 넣으면 갱신되지 않는다). Bearer 스킴을 쓰지 않는다. 이 헤더는 저작도구 서버가 관제 창구로 중계할 때 싣는 것이며, 브라우저가 저작도구 API 를 부르는 구간의 요청 헤더와는 다른 축이다. 담는 값은 브라우저가 넘긴 **사용자의** 토큰 그대로이고, 관제 통지용 서비스 토큰은 싣지 않는다(그 토큰이 이 자리에 실리면 갱신이 통째로 실패한다). 성공 시 refresh 토큰도 교체되므로 다음 갱신에는 새 refresh 토큰을 쓴다. 같은 계정 서비스의 로그아웃 창구는 같은 헤더에 **access 토큰**을 싣는다 — 창구마다 담는 값이 반대이므로 섞지 않는다.

## description

저작도구 서버(WAS)가 관제지원 계정 서비스의 세션 창구를 부르는 서버 간 연동이다 — 갱신 창구로 access 토큰을 재발급받고, 로그아웃 창구로 관제 세션을 닫는다. 관제 채널 브라우저는 관제를 직접 부르지 않고 저작도구의 갱신·로그아웃 API 를 부르며, 저작도구 서버가 그 요청을 관제 창구로 중계한다.

## 왜 필요한가
관제 access 토큰의 수명은 30분이다. 저작도구는 새 탭에서 열리므로 관제 탭의 만료 감시·연장이 미치지 않는다. 이 연동이 없으면 관제 채널 사용자는 30분마다 관제 로그인으로 되돌아가야 하고, 라벨링·검수처럼 한 화면에 오래 머무는 작업은 반드시 끊긴다. 로그아웃 창구는 세션 만료 연장 팝업을 관제지원 웹과 같은 동작(「로그아웃」·「로그인 연장」)으로 맞추려고 부른다.

## 갱신 호출 계약
- 창구: `POST /api/account/auth/refresh` · 요청 바디 없음.
- 인증: 헤더 `x-access-token` 에 브라우저가 넘긴 사용자의 **refresh 토큰**을 싣는다(Bearer 미사용). 같은 헤더에 access 토큰을 넣으면 갱신되지 않는다.
- 응답: `{error: 0, message: "success", data: {session_token, refresh_token}}` — 외부 문서의 `{sessionToken, refreshToken}` 표기가 아니라 이 실측 형태가 계약이다.
- 성공 판정: HTTP 200 **이고** `error` 가 0 **이고** `data.session_token` 이 문자열일 때만 성공이다.

## 서버 간 중계
- 주소: 관제 계정 창구 주소(`authoring.control-account.url`)만 쓴다 — 관제 웹서버 또는 계정 창구를 가진 WAS 주소. 기본값이 비어 설치 때 반드시 설정하고, 바꾸면 재기동 없이 다음 호출부터 반영된다. 비어 있으면 관제를 부르지 않고 일시 장애로 끝난다(서킷 실패로 세지 않는다).
- 폐기(2026-09-14): 통지 수신처 주소([[INT-007]]) 재사용·폴백 — 관제는 계정·데이터셋 창구를 다른 WAS 에 두어 한 주소로는 한쪽이 404 다.
- 통지와 분리: 통지용 서비스 토큰을 싣지 않는다(사용자 토큰 자리에 실리면 갱신이 실패한다). 통지 활성화 토글과 무관하게 동작한다(통지를 꺼도 연장돼야 한다). 서킷은 통지와도, 갱신·로그아웃끼리도 따로다(갱신 서킷이 열려도 로그아웃은 나간다).
- 짧은 타임아웃, 자동 재시도 없음(비멱등 — 재시도가 refresh 토큰 이중 교체를 부른다).
- 분류: 관제 HTTP 401 또는 `error` ≠ 0 → 「거절」 / 연결 실패·타임아웃·5xx·응답 형식 불일치 → 「일시 장애」.

## 갱신 결과
- 세션 식별자(`sessionId`)는 유지된다.
- refresh 토큰도 새로 발급된다(교체). 이후 갱신에는 새 refresh 토큰을 쓴다.
- 옛 access 토큰은 갱신 뒤에도 자기 만료 시각까지 유효하다.

## 토큰
| 구분 | 서명 | 수명 | 비고 |
|---|---|---|---|
| access | HS512 | 30분(`sessionTime`) | 클레임에 연장 팝업 임계 `sessionExpAlarm`(분)이 실린다 |
| refresh | HS512 | 7일 | `type=refresh` |

토큰 클레임에 사용자 이름·계정 식별자가 실리므로 서버는 토큰을 저장하지 않고 원문을 로그에 남기지 않는다(본문 로깅 시 가린다).

## 갱신 호출 시점 — 세 경우뿐
1. 요청 직전 access 토큰의 남은 시간이 10분 이하일 때(선제 갱신). 갱신 중에 들어온 요청은 같은 갱신을 기다리며, 갱신은 한 번만 나간다.
2. 요청이 401 로 돌아왔을 때 — 갱신 후 원 요청을 1회만 재시도한다.
3. 앱 전역 세션 만료 연장 팝업(관제 채널의 로그인된 모든 화면, 상세 [[SHELL-001]])에서 사용자가 「로그인 연장」을 눌렀을 때.

refresh 토큰을 보유하지 않은 진입(개발용 진입 등)에서는 호출하지 않고 현재 토큰을 그대로 쓴다.

## 갱신 실패 처리 — 실패의 종류가 결말을 정한다
브라우저는 거절·일시 장애 판정을 저작도구 API 의 응답 코드로 받는다(분류는 「서버 간 중계」).
- **관제가 갱신을 거절하면(`error` 가 0 이 아님 — 예: 900205 「리프레시 토큰이 없습니다」) 호출 경로와 무관하게 즉시 세션을 비우고 상위 시스템(관제) 로그인으로 이동한다.** 거절된 refresh 토큰으로는 다시 갱신하지 않는다 — 같은 토큰은 결과도 같다(관제와 같다).
- **예외 — 거절을 받으면 로그아웃하기 전에 저장소의 refresh 토큰을 한 번 더 읽는다.** 호출에 쓴 값과 다르면(관제 탭을 포함한 다른 탭이 이미 갱신해 새 토큰을 저장했으면) 로그아웃하지 않고 저장소의 새 토큰을 쓴다. 같으면 위 규칙대로 즉시 로그아웃한다. 이 예외는 호출 경로와 무관하다(401 뒤 갱신이 거절된 경우 포함).
- **네트워크 오류·5xx 같은 일시 장애면** 결과를 저장하지 않고 현재 토큰으로 계속 쓴다(팝업 경로는 연장하지 못했다고 안내한다). 다음 갱신 시점(다음 요청)에 다시 시도할 수 있으며, 남은 시간이 0 이 되면 세션을 비우고 상위 시스템(관제) 로그인으로 이동한다.
- **401 뒤 갱신이 실패하거나 재시도도 401 이면** 결과를 저장하지 않고 **즉시** 세션을 비우고 상위 시스템(관제) 로그인으로 이동한다.

## 저장
갱신 결과는 관제지원 웹이 쓰는 것과 **같은 키·같은 형식**으로 브라우저 저장소에 쓴다 — 관제 탭이 저작도구가 쓴 값을 그대로 읽기 때문이다. 저장 키·형식은 관제 채널 토큰 인계 계약이 다룬다([[INT-013]] · [[ADR-012]]).

## 로그아웃 호출 계약
- 창구: `POST /api/account/auth/logout` · 요청 바디 없음 · 성공 응답 `{error: 0}`.
- 인증: 헤더 `x-access-token` 에 **access 토큰**을 싣는다.
- 호출 시점: 세션 만료 연장 팝업에서 사용자가 「로그아웃」을 눌렀을 때뿐이다. 저장하지 않은 편집이 있을 때만 화면 이탈 공통 확인 절차를 거치며, 계속을 골라야 부르고 취소하면 부르지 않는다.
- 결말: 응답의 성공·실패와 **무관하게** 저장소의 토큰 키(`klid-jwt-token` · `tokenInfo`)를 지우고 상위 시스템(관제) 로그인으로 이동한다. 호출이 실패해도 세션이 남지 않게 하기 위해서이며 관제지원 웹도 같다.
- 같은 출처의 관제 탭은 저장소 변경을 받아 함께 로그아웃된다.

## 토큰 인계 창구와의 관계
[[INT-013]] 은 Host 와 저작도구 사이의 토큰 인계 창구 계약이고, 이 연동점은 **관제 채널에서 그 갱신 창구가 저작도구 서버를 거쳐 닿는 외부 호출**이다. 인계 창구의 이름 계약은 이 연동으로 바뀌지 않는다.

## 동시 갱신 경쟁 (인지·수용)
관제 탭과 저작도구 탭(여럿일 수 있다)이 같은 refresh 토큰으로 동시에 갱신하면 한쪽이 교체 전 토큰을 쥔 채 남는다. 갱신 직전 저장소의 refresh 토큰을 다시 읽어 쥔 값과 다르면(다른 탭이 이미 갱신) 호출하지 않는다. 관제 탭은 이 직렬화를 모르므로 완전한 배제는 불가능하나, 옛 토큰이 거절되면 「갱신 실패 처리」의 저장소 재확인 예외가 세션을 지킨다.

## 미확인 — 관제 확인 대상
- 교체 전 refresh 토큰을 다시 쓰면 관제가 그 요청만 거부하는지 세션 전체를 무효화하는지 확인되지 않았다. 후자라면 동시 갱신 경쟁에서 드물게 양쪽 탭이 모두 로그아웃되며, 저장소 재확인 예외로도 막지 못한다(다른 탭이 저장한 새 토큰도 함께 무효다).

## 비고 — 세션 선정리 관측
2026-09-10 — 관제 서버가 access 토큰 만료 전에 세션을 정리하면 일반 API 는 401 `error` 1111(세션 비활성), 갱신 창구는 401 `error` 900205 를 낸다(원인 미확정). 거절 즉시 로그아웃 규칙의 근거다.

## retry_policy

저작도구 서버→관제 호출은 짧은 타임아웃, 자동 재시도 없음(비멱등 — 재시도가 refresh 토큰 이중 교체를 부른다). 서킷은 갱신·로그아웃·통지가 따로이며 주소 미설정은 서킷 실패로 세지 않는다. 브라우저 쪽: 요청이 401 이면 갱신 후 원 요청을 1회만 재시도한다. 결말은 저작도구 API 가 알린 실패 종류가 정한다 — ①거절: 저장소의 refresh 토큰이 호출에 쓴 값과 다르면 그 새 토큰을 쓰고, 같으면 즉시 세션을 비우고 관제 로그인(거절된 토큰으로 재갱신 금지) ②일시 장애: 저장하지 않고 현재 토큰으로 계속, 남은 시간 0 이면 관제 로그인 ③401 뒤 갱신 실패·재시도 401: 즉시 관제 로그인. 로그아웃은 재시도 없이 응답과 무관하게 토큰 키를 지운다.
