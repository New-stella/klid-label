## auth_detail

### notes

상위 시스템이 발급한 서명 토큰을 인계받으며 저작도구가 발급하지 않는다. 포털 채널은 Host 가 주입한 인계 창구(토큰 획득 · 갱신 · 인증 실패 통지 · 활동 통지)에서 토큰을 얻어 전용 요청 헤더 x-access-token 으로 싣는다. 포털 채널은 Bearer 스킴을 쓰지 않으므로 auth_type 은 other 다(주 대상인 포털 채널 기준). 내부 채널은 저작도구 서버로 가는 요청에 표준 Authorization 헤더의 Bearer 스킴을 쓴다. 포털 채널의 access token 은 Host 메모리에만 두고 브라우저 저장소에 쓰지 않는다. 내부 채널은 같은 출처 브라우저 저장소에서 서명 토큰을 넘겨받으며, 저작도구는 그 직접 읽기를 토큰 획득 창구 뒤로 추상화해 두 Host 를 분기 없이 지원한다. [폐기] 「내부 채널은 기존 방식을 그대로 쓴다」에 담겼던 「갱신이 없다」는 함의는 폐기한다 — 내부 채널 창구는 저장소의 현재값을 매 호출 읽고, 만료 임박·인증 실패·사용자 연장 요청 때 저작도구 갱신 중계 창구(API-247)를 거쳐 상위 시스템(관제) 계정 갱신 창구로 재발급받아 관제와 같은 키·형식으로 저장소에 쓴다(인라인 스펙 「내부(관제) 채널 창구의 동작」). 토큰은 매 호출 시점에 획득 창구로 취득하며 자체 캐시나 자체 스토어 폴백을 두지 않는다. 갱신 주체가 Host(포털 채널)이거나 다른 탭·저작도구 자신(내부 채널)이라 저장 위치와 무관하게 캐시하면 죽은 토큰을 잡기 때문이다.

## description

포털(외부 채널) 화면 안에 저작도구 프론트엔드를 런타임으로 끼워 넣는 연동이다. 포털이 Host, 저작도구가 Remote 이며 두 번들이 같은 브라우저 문서에서 함께 실행된다.

저작도구 쪽에는 이 연동을 결정한 문서가 따로 없다 — 아래 「저작도구 측 결정」이 그 자리다.

## 확정 사실 (포털 측)
- 포털이 자기 프로젝트의 결정 문서로 Host/Remote 구조를 확정하고 연동점으로 등록했다. 저작도구는 Remote 를 제공하는 쪽이다.
- 포털은 통합 지점을 작업공간 하위의 저작도구 경로 한 곳만 두고, 그 영역 안의 화면 내용은 저작도구 화면정의서를 정본으로 삼는다고 명시한다.
- 그 영역에 대응하는 저작도구 화면에는 SCREEN-028(포털 홈) · SCREEN-029(포털 라벨링) · SCREEN-033(포털 업로드)가 있다.
- 포털이 스스로 규정하는 범위는 마운트 조건(로그인 상태 · 데스크톱 폭)과 영역 밖 상태화면(비로그인 잠금 안내 · 데스크톱 전용 안내)뿐이다.
- 저작도구 정적 자원은 포털 웹서버가 **같은 출처의 하위 경로**로 서빙한다. 저작도구 백엔드가 별도 서버로 분리되어도 이 사실은 바뀌지 않아 교차 출처 설정이 필요 없다.
- 번들은 **로그인된 사용자에게만** 로드된다 — 비로그인 분기는 Host 가 먼저 처리하고 저작도구 안에 또 하나의 인증 분기를 두지 않는다.
- 번들 로드·실행 오류는 Host 와 같은 문서에서 발생하므로 **오류 경계가 규정돼 있다**.
- 포털 채널이 쓰는 저작도구 API 는 브라우저가 **같은 출처로 직접 호출**한다.

## 저작도구 측 결정

- **셸 소유권 — 포털 셸 안으로 들어간다.** 포털이 규정한 「포털 셸 + 그 안의 저작도구 영역」 구조를 그대로 받는다. 저작도구 포털 채널의 머리 영역(SHELL-002)과 좌측 주 메뉴는 렌더하지 않는다. 다만 **그 구성을 지우지 않고 끄기만 한다** — 전체 화면 방식으로 뒤집히더라도 되돌릴 수 있어야 하고, 그때 초점 표시·링크 접근성 처리까지 재현돼야 하기 때문이다.
- **Remote 로 내보내는 산출물은 납품본이다.** 포털 결정 문서가 전제한 기술 스택과 주 버전이 그쪽에서 일치한다. 다만 그 산출물은 별도 조직이 관리하므로 이 설계가 직접 바꾸지 않는다 — 여기서는 **기준 구현본이 그 자리에 그대로 올라가도 동작하도록** 갖춰 두는 것까지가 범위다.
- **그래서 기준 구현본의 주 버전을 생태계에 맞춘다.** 포털·관제·납품본이 모두 같은 세대의 렌더링 라이브러리와 스타일 도구를 쓰는데 기준 구현본만 한 세대 뒤였다. 정렬하면 Host 가 어느 쪽이든 공유 협상 없이 올라가고, 기준 구현으로서의 역할도 정확해진다(뒤처진 세대가 기준이면 맞추는 쪽이 매번 차이를 흡수한다).
- **산출물은 채널별로 따로 만든다.** 내부 채널과 포털 채널의 배포 대상이 서로 다른 서버라 하나의 산출물을 두 곳이 나눠 쓰는 구성이 성립하지 않는다. 공통 소스는 한 벌로 두고 **산출만 채널별로 가른다** — 그러면 ①반대 채널 화면이 산출물에 섞이지 않고 ②채널마다 다른 팔레트를 산출 시점에 정할 수 있으며 ③채널을 가르는 지점이 진입점·라우팅·셸 세 곳으로 좁혀진다. 공통 화면 부품은 채널을 스스로 알지 않고 넘겨받은 값으로만 동작하므로 갈래마다 복제되지 않는다.
- **토큰 인계 수단은 채널마다 갈린다.** 포털 채널은 Host 가 주입한 인계 창구에서 토큰을 얻어 **전용 요청 헤더**로 싣고, access token 은 **Host 메모리에만** 둔다(브라우저 저장소 미사용). 근거(포털 비협상) — 저장소나 그 스냅샷을 직접 읽으면 갱신 뒤 **죽은 토큰**을 잡고, 수십 분 체류하는 저작 화면은 반드시 파손된다. 내부 채널은 인계 결정(ADR-012)대로 같은 출처 저장소를 쓰고 갱신도 한다(인라인 스펙).
  ⇒ 조치: 저장소 직접 읽기를 **획득 창구 뒤로 추상화**해 두 Host 를 분기 없이 지원한다. 앞선 「변경 0」 주장은 **어댑터 한 겹**으로 조정된다.
  ⇒ 매 호출 취득·캐시 금지.
  ⚠ 「포털 서술이 두 갈래」라던 경고는 **폐기한다** — 두 방식은 상충이 아니라 **상보**였다.
- **Host 화면을 벗어나지 않는다.** 저작도구는 인증 실패·권한 없음을 자기 화면 이동으로 처리하는데, Host 안에 마운트되면 그 이동이 **Host 문서 전체**에 걸린다. 그런데 Host 가 선언한 화면 목록에 저작도구가 보내는 자리가 없어 **찾을 수 없는 화면**이 된다(전수 확인). 그러므로 포털 채널 빌드에서는 **이동하지 않고 그 자리에 안내를 그린다**. 기본값인 내부 채널에서는 지금처럼 이동한다 — 거기서는 그 자리가 실재하기 때문이다.
  ⚠ **토큰 만료로 상위 시스템 로그인 화면에 보내는 것은 그대로 둔다.** 그건 Host 도 해야 할 일이고, 저작도구는 복귀 주소에 현재 위치를 실어 보내므로 임베드된 상태에서 오히려 정확하다. 이것까지 막으면 만료된 세션에 갇힌다.
  ⚠ 이 결정으로 **Host 위임 규약 자체가 필요 없어진다** — 저작도구가 Host 를 건드리지 않고 자기 영역 안에서 끝내기 때문이다.
- **이 결정이 뒤집혀도 나머지는 다시 하지 않는다.** 두 방식의 차이는 머리 영역과 좌측 주 메뉴를 그리느냐 둘뿐이고, Host 하위 마운트에 필요한 나머지(경로 구조 재편 · 이탈 경로 위임 · 산출 분리 · 색 토큰 정리)는 어느 쪽이든 동일하다.
- **화면 사이 이동은 셸에 기대지 않는다.** 포털 채널 화면 네 건은 화면 안의 링크로 서로를 오간다(영상 선택 · 업로드 진입 · 목록 복귀). 내비게이션 영역이 없어도 이동이 끊기지 않으며, 이 성질이 위 결정을 되돌릴 수 있게 만드는 조건이다.
- **진입점·마운트·서빙 이름은 포털이 정한 값을 따른다.** 구체 값은 인라인 스펙에 있다.
- **이 경로로 진입한 사용자는 포털 권한 사용자로 본다 — 화면 축 한정.** 포털 채널 빌드가 그 권한으로 화면·메뉴·기능을 게이팅한다.
  ⚠ **서버 인가의 진실원은 배포 향(채널)과 저작도구 역할이며, 진입 경로는 클라이언트가 주장하는 값이라 권한을 올리지 않는다.**

## 협의 대상 — 해소
1. **스타일 격리.** 포털 디자인 스타일이 정본이므로 **격리 책임은 저작도구**다. 구체 규약은 인라인 스펙 「스타일 격리 규약」이 정본이다(구 수단 「범위 한정 스타일 계층」은 폐기).
2. **디자인 토큰.** 「어느 팔레트로 뜨는가」가 답을 얻었다 — **포털 채널 산출물은 포털 주색(코발트 계열)으로 뜬다.** 팔레트는 산출 시점에 정해지며 뜬 뒤 갈아끼우지 않는다. 색을 고정값으로 박으면 갈아끼울 수 없어 **시맨틱 색의 토큰 분리가 선행**된다(범주 구분에 쓰는 색은 대상이 아니다 — 의미가 아니라 구분이라 채널이 달라도 같아야 한다).
3. **동일 Remote 재사용 전제.** 관제 쪽 설계에 프론트엔드 임베딩 서술이 없다는 실측을 포털이 **수용**했다. 통합 방식은 유지된다(캔버스 이벤트 간섭 회피·독립 배포·화면 일관성 근거 유효). 성립하지 않는 재사용 이점 한 줄은 포털이 정리한다.
4. **가드 중복.** 포털이 저작도구 UX 가드를 **허용**했다 — 서버가 최종 인가를 판정하고 가드가 Host 를 이탈시키지 않아 무해하며 포털 셸 인증 분기와 공존한다.

## 협의 미결
- **디자인 토큰의 기준 단위 환산.** 양쪽 설계 어디에도 명시가 없다(포털 회신 범위 밖). 상세는 인라인 스펙.

## 인증
상위 시스템이 발급한 서명 토큰을 인계받으며 저작도구가 발급하지 않는다. 전달 수단은 위 「토큰 인계 수단은 채널마다 갈린다」가 정본이고, 요청 헤더는 채널마다 다르다(인라인 스펙).

| 진입 파일 캐시 | 재검증을 강제하는 캐시 헤더(`no-cache`) — 이 헤더를 거는 주체는 **포털 웹서버**이고 저작도구 번들이 아니다. 우리는 맞춰야 할 값으로 기록할 뿐 강제하지 못하므로, 실제로 걸렸는지 **확인이 필요**하다. 빠지면 배포 직후 옛 진입 파일이 이미 지워진 청크를 가리켜 **포털 화면이 통째로 깨진다** |

## 채널 산출물은 향마다 따로 만든다 — 런타임 설정으로 대체되지 않는다
채널을 가르는 값은 **산출 시점에 굳는 상수**다. 그 하나가 아래 넷을 한꺼번에 가른다.

| 가르는 지점 | 포털 채널 | 기본(내부) 채널 |
|---|---|---|
| 자기 머리 영역 | 렌더하지 않는다(포털 셸 안으로 들어간다) | 렌더한다 |
| 좌측 주 메뉴(NAV-002) | 두지 않는다(포털 셸이 소유한다) | 렌더한다 |
| 라우터 기준 경로 | 마운트 경로를 기준 경로로 문다 | 기준 경로를 두지 않는다 |
| 이탈 분기 **네 곳** | 화면 이동 대신 제자리 안내를 그린다 | 지금처럼 이동한다 |

⚠ **좌측 주 메뉴가 포털 채널에서 빠지는 것은 Host 소유이기 때문이다** — Host 가 머리 영역과 좌측 주 메뉴를 모두 소유하고, 저작도구는 그 아래 본문만 그린다. 저작도구가 자기 좌측 주 메뉴를 두면 **왼쪽 레일이 둘이 되어** Host 화면과 부딪힌다.

⚠ **설치 시점에 정하는 배포 향 설정으로는 이 값을 바꾸지 못한다.** 그 설정은 서버 쪽 배선을 가를 뿐 **이미 만들어진 화면 산출물**을 바꾸지 않는다. 그러므로 향마다 산출을 따로 만들고, **반입 절차가 그 값을 산출 단계에 명시적으로 넘겨야 한다.**

⚠ **다만 「서버 쪽 배선을 가를 뿐」으로 좁혀 읽지 말 것 — 배포 향은 서버가 채널을 확정하는 축이기도 하다.** 아래 「채널은 배포 향이 확정한다」가 그 축을 규정한다.

⚠ 넘기지 않으면 **기본값이 적용돼 내부 채널 산출물이 포털에 올라간다** — 빌드는 성공하고 오류도 없어 **조용히** 어긋난다. 증상은 포털에서 저작도구 머리 영역이 겹쳐 뜨고 **왼쪽 레일이 둘로 겹치며**, 기준 경로가 없어 하위 화면이 전부 없는 화면이 되는 형태로 나타난다.

## Host 없이 단독으로 띄우는 경우 — 개발 환경 한정

포털 채널 산출물은 **Host 가 있다고 전제한다.** 그 전제가 성립하지 않는 형상이 하나 있다 — 포털 연동 배포본을 **포털 없이 단독으로 띄워 확인하는 개발 환경**이다. 그 형상에서는 두 가지가 동시에 막힌다.

| 막히는 것 | 왜 |
|---|---|
| 화면에 닿지 못한다 | 마운트 경로가 라우터 기준 경로라, 그 밖의 주소로 들어오면 어떤 화면도 걸리지 않는다 |
| 토큰을 얻지 못한다 | 인계 창구가 없고, **없을 때 브라우저 저장소로 폴백하지 않는 것이 규정**이다. 개발용 토큰을 발급해도 요청에 실리지 않는다 |

⇒ **개발 환경에 한해 Host 를 대신하는 임시 창구를 둔다.** 규정은 아래와 같다.

- **계약을 새로 만들지 않는다.** 임시 창구는 실제 Host 가 쓰는 것과 **같은 네 이름**(토큰 획득 · 갱신 · 인증 실패 통지 · 활동 통지)을 그대로 구현한다. 그래야 실제 Host 계약을 어겼을 때 개발 단계에서 드러난다 — 따로 판 우회로는 그 검증을 못 한다.
- **기준 경로 밖으로 들어온 진입은 마운트 경로 아래로 보낸다.** ⚠ 이것은 「이탈 분기 네 곳은 제자리 안내」와 **다른 축**이다. 그건 앱이 그린 화면 안에서의 분기이고, 이것은 앱이 시작되기 전의 진입 지점 보정이다. 그 규정을 되돌리는 것이 아니다.
- **이동 목적지는 산출 시점에 굳은 값에서만 나온다.** 실행 중 입력(주소의 질의 문자열 · Host 가 건넨 값)이 목적지에 섞이면 안 된다 — 기준 경로가 곧 이동 표면이 되어 바깥 주소로 끌려간다. 마운트 경로 값에 이미 걸려 있는 금지와 같은 것이다.
- **임시 창구가 자기 몫의 토큰을 스스로 보관한다.** 본체가 포털 채널에서 브라우저 저장소를 쓰지 않는다는 규정은 그대로다 — 구조는 「본체가 저장소를 읽는다」가 아니라 **「Host 역할을 하는 쪽이 토큰을 갖고 창구로 건넨다」**여야 한다.
- **단독 구동 진입점에만 둔다.** 진입점은 둘이다 — 문서를 소유하는 단독 진입점과 Host 안에 실리는 원격 진입점. 임시 창구를 앞쪽에만 두면 실제 Host 안에서는 **구조적으로 활성화될 수 없다.** 조건 검사에 기대지 않고 배치로 보장하는 편이 안전하다.

### 운영 산출물에 포함되지 않는다
이 장치는 임의 권한의 토큰을 요청에 실어 주므로, 운영 산출물에 남으면 **그 자체가 인증 우회 경로**다. 그러므로 개발 노출 조건 하나로 가르지 말고 **산출 시점에 굳는 조건을 함께** 걸어 산출물에서 빠지게 한다.

⚠ 폐쇄망 반입 산출은 개발용 로그인 노출 값을 **기본으로 켜서** 만든다. 그 값 하나에만 기대면 **반입 산출물에 이 장치가 들어간다.**

## 채널은 배포 향이 확정한다 — 인계 토큰의 채널 값을 읽지 않는다

포털 채널 배포본에 도착한 인계 토큰은 **항상 포털 채널로 해석**한다. 토큰에 채널 값이 실려 있어도 그 값을 따르지 않는다. 판정 축은 **설치 시점에 정하는 배포 향** 하나이며, 배포 향이 선언되지 않았거나 값역 밖이면 **관제 채널로 해석한다**(fail-closed).

### 계약 경계 — 상대에게 채널 값을 요구하지 않는다
저작도구는 상대 시스템에 **채널 클레임 추가를 요구하지 않는다.** 저작도구가 채널마다 별도로 배포되므로 배포본이 **이미 알고 있는 사실**이고, 그것을 상대의 토큰에 실어 달라고 요청하는 것은 **우리 배포 형상을 상대에게 떠넘기는 것**이기 때문이다.

⚠ **서명키로 채널을 가를 수도 없다.** 상대는 사용자 주체 토큰과 시스템 주체 토큰을 **같은 공유 서명키로 서명**하고 주체를 **주체 식별자 클레임**으로 가른다. 서명키는 주체 축을 가를 뿐 채널 축을 가르지 않는다.

## 토큰 인계 창구 (Host 주입)
Host 가 Remote 에 인계 창구를 주입한다 — 토큰 획득 · 갱신 · 인증 실패 통지 · 활동 통지. 얻은 access token 은 전용 요청 헤더 `x-access-token` 으로 싣고 Bearer 스킴은 쓰지 않는다(포털 채널 — 내부 채널의 요청 헤더는 아래 「내부(관제) 채널 창구의 동작」). 포털 채널에서 토큰은 Host 메모리에만 두고 브라우저 저장소에 쓰지 않는다 — **이 규정은 포털 채널 한정**이며, 내부 채널이 관제와 같은 형식으로 저장소에 쓰는 것은 아래 「내부(관제) 채널 창구의 동작」이 규정한다.

저작도구는 같은 출처 저장소를 직접 읽던 지점을 토큰 획득 창구 뒤로 추상화해, 저장소를 쓰는 Host 와 메모리에 두는 Host 를 분기 없이 지원한다.

### 인계 토큰의 구성
포털 채널로 인계되는 토큰은 아래와 같이 구성된다.

| 항목 | 값 |
|---|---|
| 서명 | **HMAC 대칭 서명** — 실물의 다이제스트는 **SHA-384** |
| 클레임 | 주체 식별자 · 로그인 아이디 · 상대 시스템의 역할(저작도구 인가 축에 쓰지 않는다) · 토큰 종류 · 발급 시각 · 만료 시각 |
| 발급자 클레임 | **없다** |
| 채널 클레임 | **없다** |
| 유효기간 | **30분** |

⚠ **서명 다이제스트는 규격 문서와 실물이 어긋난다** — 규격 문서는 SHA-256 으로 적었고 실물은 SHA-384 다. 정본이 갈리기 전까지 **어느 한쪽을 계약값으로 단정하지 않는다.**

⚠ **채널 클레임이 없는 것은 누락이 아니다** — 상대가 클레임 구성을 열거했을 때 그 목록에 채널이 없었고, 저작도구도 그것을 요구하지 않는다(위 「계약 경계」). 채널은 배포 향이 확정한다.

⚠ **주체 식별자는 상대 시스템의 회원 식별자 체계다** — 저작도구의 사용자 번호 체계와 **다른 공간**이라 두 값을 같은 식별자로 다루면 서로 다른 사람이 겹친다.

### 매 호출 취득 · 캐시 금지
Remote 는 **매 호출 시점에** 토큰 획득 창구(`getAccessToken`)로 토큰을 취득한다. **자체 캐시를 두지 않고, 자체 스토어 폴백도 두지 않는다.**

근거 — 갱신 주체가 Host 이고 access token 만료가 짧다. 그러므로 **저장 위치와 무관하게** 캐시하면 Host 가 갱신한 시점 이후로 **죽은 토큰**을 잡는다. 저장소를 쓰지 않는 것만으로는 모자라며, 메모리에 들고 있어도 같은 파손이 난다.

★ **이 원칙은 내부(관제) 채널에도 그대로 적용된다 (2026-09-10 사용자 확정).** 내부 채널에서 저작도구는 상위 시스템 화면 안이 아니라 **별도 탭**으로 열리므로, 상위 시스템의 만료 감시·연장 동작이 저작도구 탭에서 돌지 않는다. 그리고 상위 시스템 access token 의 수명이 **30분**이라 진입 시점에 복사해 둔 토큰은 30분 뒤 무효가 된다 — 포털 채널에서 막으려던 「죽은 토큰」이 내부 채널에서도 똑같이 성립한다. 그러므로 내부 채널 창구도 **진입 시 복사본을 쓰지 않고 매 호출 저장소의 현재값을 읽는다.**

⚠ 이 금지는 **개발 환경 임시 창구에도 그대로 적용된다.** 임시 창구가 Host 역할로 자기 몫의 토큰을 보관하는 것은 위 「Host 없이 단독으로 띄우는 경우」가 허용한 것이지만, **본체가 창구에서 받은 값을 캐시해 두는 것은 허용이 아니다.**

### [해소] 포털측 저장소 서술 충돌 — 철회로 닫혔다
포털이 「브라우저 저장소의 토큰을 웹과 같은 방식으로」라고 적었던 대목을 **자기 오류로 인정하고 철회·정정**했다. 그러므로 두 갈래로 읽을 서술이 남아 있지 않다.

| 축 | 정본 |
|---|---|
| 저장소 미사용 | **[포털]GUIDE-003** — access token 은 Host 애플리케이션 메모리에만 보관하고 브라우저 저장소를 쓰지 않는다 |
| 만료 시간 상수 | 포털의 별개 상수 — **저장소 규칙이 아니다** |

⚠ 그 둘을 같은 축으로 읽지 말 것. 철회된 서술을 현행처럼 인용하지 말 것.

⚠ **포털 채널은 저장소를 쓰지 않으므로 읽을 키 이름이 존재하지 않는다.** (내부 채널의 저장소 키는 아래 「내부(관제) 채널 창구의 동작」에 있다 — 채널이 다르다.) 저작도구가 키를 추측해 읽지 않은 판단이 옳다고 포털이 확인했다. 전용 요청 헤더 사용과 Bearer 미사용도 함께 재확정됐다.

### 인계 창구의 계약 이름
| 창구 | 이름 | 역할 |
|---|---|---|
| 토큰 획득 | `getAccessToken` | 현재 유효한 access token 을 돌려준다 |
| 갱신 | `refresh` | 만료 임박·만료 시 재발급을 요청한다 |
| 인증 실패 통지 | `onUnauthorized` | 인증이 끊겼음을 Host 에 알린다 — 안내·재로그인은 Host 가 소유한다 |
| 활동 통지 | `notifyActivity` | 사용자 활동을 Host 에 알려 세션 유지 판단에 쓰게 한다 |

이름은 **포털이 정본으로 제시한 계약**이라 저작도구가 바꾸지 않는다. Host 가 주입하는 객체의 키이므로 **이름이 어긋나면 실행 시점에 창구를 찾지 못한다** — 개념만 맞추고 이름을 새로 짓지 말 것.

⚠ 인계 창구와 전용 요청 헤더는 **상충이 아니라 상보**다 — 창구로 얻어 헤더로 싣는 **한 모델**이며, 두 갈래 중 택일하는 것이 아니다.

### 내부(관제) 채널 창구의 동작 (2026-09-10 사용자 확정, 구속)

내부 채널에는 창구를 주입하는 Host 가 없다. 저작도구가 **같은 네 이름**의 창구를 스스로 갖추며, 위 이름 계약과 포털 채널 규정은 이 절로 바뀌지 않는다.

| 창구 | 내부 채널 동작 |
|---|---|
| 토큰 획득 `getAccessToken` | 같은 출처 저장소 키 `klid-jwt-token` 의 **현재값**을 매 호출 읽는다. 진입 시점에 복사해 둔 값을 쓰지 않는다 |
| 갱신 `refresh` | 저작도구 갱신 중계 창구 [[API-247]] 에 refresh 토큰을 본문으로 보내 재발급받고, 아래 저장 형식으로 저장소에 쓴다. 저작도구 서버가 관제 계정 갱신 창구([[INT-015]])로 중계한다 — **브라우저는 관제를 직접 부르지 않는다.** refresh 토큰이 없는 진입(개발용 로그인)은 갱신하지 않고 현재 토큰을 돌려준다 — 오류로 다루지 않는다 |
| 인증 실패 통지 `onUnauthorized` | 알릴 Host 가 없으므로 **아무것도 하지 않는다.** 인증 끊김 처리(상위 시스템 로그인 화면으로 이동)는 요청 경로가 소유한다 |
| 활동 통지 `notifyActivity` | 같은 이유로 **아무것도 하지 않는다** |

#### 요청 헤더
내부 채널은 저작도구 서버로 가는 요청에 access 토큰을 표준 `Authorization` 헤더의 Bearer 스킴(`Bearer <토큰>`)으로 싣는다. 포털 채널의 전용 헤더 `x-access-token`(Bearer 접두 없음)과 다르다.

- 저작도구 서버는 내부 채널 요청을 `Authorization: Bearer` 로, 포털 채널 요청을 `x-access-token` 으로 받는다. **두 헤더가 함께 오고 값이 다르면 거부한다.**
- 포털 헤더에 Bearer 접두를 붙이면 그 문자열 전체가 토큰으로 해석돼 **서명 검증에서 거부**된다.

⚠ 관제 계정 갱신 창구가 `x-access-token` 에 refresh 토큰을 싣는 것은 **저작도구 서버가 관제를 부를 때의 규칙**이다(상세 [[INT-015]]). 브라우저가 저작도구 서버로 보내는 요청 헤더와 **다른 축**이므로 둘을 섞지 말 것 — 브라우저는 갱신 중계 창구에 refresh 토큰을 헤더가 아니라 **본문**으로 보낸다.

#### 갱신 중계 창구
브라우저는 관제 계정 갱신 창구를 직접 부르지 않는다. 저작도구 서버의 갱신 중계 창구 [[API-247]] 을 부르고, 저작도구 서버가 관제 계정 갱신 창구([[INT-015]])로 중계한다.

| 항목 | 값 |
|---|---|
| 요청 | `POST /v1/auth/control-tokens` · 본문 `refreshToken` 에 **refresh 토큰**을 싣는다 — 헤더가 아니라 본문이다 |
| 201 | 성공 — 새 access 토큰과 새 refresh 토큰 쌍을 받아 아래 저장 형식으로 저장소에 쓴다. **refresh 토큰도 교체**되므로 다음 갱신에는 새 refresh 토큰을 쓴다. 옛 access 토큰은 갱신 뒤에도 만료 전까지 유효하다 |
| 401 `CONTROL_SESSION_REJECTED` | 관제가 갱신을 **거절**했다 — 저장하지 않고 아래 「갱신 실패의 결말」의 거절 행을 따른다 |
| 503 `CONTROL_SESSION_UNAVAILABLE` | 관제에 닿지 못했거나 응답을 해석할 수 없다 — **일시 장애**이며 저장하지 않고 아래 「갱신 실패의 결말」의 일시 장애 행을 따른다 |

⚠ 관제 응답을 성공과 거절로 가르는 판정(HTTP 상태 · 응답의 `error` 값 · 새 토큰의 형식)은 **저작도구 서버의 몫**이며 [[INT-015]] 가 소유한다. 브라우저는 위 응답 코드만으로 결말을 가른다.

#### 로그아웃 중계 창구
세션 만료 연장 팝업(상세 [[SHELL-001]])에서 「로그아웃」을 누르면 브라우저는 저작도구 서버의 로그아웃 중계 창구 [[API-246]] 을 부른다 — access 토큰을 `Authorization: Bearer` 로 싣고, 저작도구 서버가 관제 로그아웃 창구([[INT-015]])로 중계한다. 응답은 관제 결과와 무관하게 **항상 204** 이며, 브라우저는 응답과 무관하게 저장소의 토큰 키(`klid-jwt-token` · `tokenInfo`)를 지우고 상위 시스템(관제) 로그인 화면으로 이동한다. 저장하지 않은 편집이 있으면 화면 이탈 공통 확인 절차에서 계속을 고른 뒤에만 부른다.

#### 갱신 시점
- **선제 갱신** — 요청 직전 남은 시간이 **10분 이하**이고 refresh 토큰이 있으면 먼저 갱신하고 새 토큰을 싣는다. 갱신 중에 들어온 요청은 **같은 갱신을 기다린다**(갱신은 한 번만 나간다). 갱신이 실패했을 때의 결말은 아래 「갱신 실패의 결말」을 따른다 — 실패 원인이 관제의 거절인지 일시 장애인지로 갈린다.
- **인증 실패 재시도** — 요청이 인증 실패로 돌아오면 갱신 후 **1회** 재시도한다. 재시도도 인증 실패로 돌아오거나 갱신이 실패하면 실패 원인과 무관하게 **즉시** 로그아웃한다(아래 「갱신 실패의 결말」). 관리자 패스워드 확인처럼 세션 만료가 아닌 인증 실패를 돌려주는 요청은 대상이 아니다.
- **사용자 연장** — 앱 전역 세션 만료 연장 팝업(관제 채널의 로그인된 모든 화면 — 셸 밖 전체 화면 포함, 상세 [[SHELL-001]])에서 사용자가 「로그인 연장」을 누를 때. 실패했을 때의 결말은 아래 「갱신 실패의 결말」을 따른다.

#### 갱신 실패의 결말 (2026-09-10 사용자 확정, 구속)

갱신 실패의 결말은 **실패 원인**으로 가른다. 어느 시점(선제 갱신 · 인증 실패 재시도 · 사용자 연장)에서 났는지로 가르지 않는다.

| 실패 원인 | 결말 |
|---|---|
| **관제가 갱신을 거절** — 갱신 중계 창구가 401 `CONTROL_SESSION_REJECTED` 로 답한다(관제 응답의 `error` 가 0 이 아니다 — 예: 「리프레시 토큰이 없습니다」) | 시점과 무관하게 **즉시** 세션을 비우고 상위 시스템(관제) 로그인 화면으로 이동한다. 거절된 refresh 토큰으로 **다시 갱신하지 않는다**. 단 로그아웃하기 전에 저장소를 한 번 더 읽는다(아래 예외) |
| **일시 장애** — 갱신 중계 창구가 503 `CONTROL_SESSION_UNAVAILABLE` 로 답했거나 네트워크 오류 · 5xx 등으로 선제 갱신이나 사용자 연장이 실패 | **저장하지 않고 현재 토큰으로 계속**한다 — 로그인 화면으로 보내지 않는다. 다음 요청 때 다시 갱신할 수 있다. 사용자 연장이면 연장하지 못했다고 안내한다. 남은 시간이 0 이 되면 로그아웃한다 |
| **인증 실패 뒤의 실패** — 인증 실패로 갱신했는데 갱신이 실패했거나, 재시도도 인증 실패 | 실패 원인과 무관하게 **즉시** 로그아웃한다 |

- **예외 — 다른 탭이 이미 갱신한 경우.** 관제의 거절을 받으면 로그아웃하기 전에 저장소의 refresh 토큰을 **한 번 더 읽는다.** 다른 탭(관제 탭 포함)이 그사이 새 토큰을 저장해 값이 바뀌었으면 로그아웃하지 않고 **그 새 토큰을 쓴다.** 이 탭이 동시 갱신으로 **교체된 옛 refresh 토큰**을 보내 거절당한 것이라 세션 자체는 멀쩡하기 때문이다 — 멀쩡한 세션을 끊지 않는다. 값이 그대로면 거절대로 즉시 로그아웃한다. 이 재읽기는 아래 「탭 간 동기화」의 **갱신 직전 재읽기(동시 갱신 방지)** 를 거절을 받은 뒤 한 번 더 하는 것이다.
- **거절을 즉시 결말로 두는 이유** — 다른 기기 등에서 관제 서버 세션이 끊겨도 저장소의 토큰 값은 그대로라 **저장소 추종(아래 「탭 간 동기화」)으로는 잡히지 않는다.** 그 끊김이 드러나는 곳이 갱신 시점의 거절이다. 거절을 일시 장애처럼 다루면 이미 끊긴 세션으로 작업을 이어 가게 된다.
- ⚠ 관제의 거절 「리프레시 토큰이 없습니다」는 **서버가 보낸 refresh 토큰을 인정하지 않는다**는 뜻이다. 저작도구 쪽에 refresh 토큰이 애초에 없는 진입(개발용 로그인)은 갱신을 부르지 않는 **별개 경우**이며 로그아웃 대상이 아니다(위 창구 표의 갱신 행).
- **강제 로그아웃은 미저장 변경 확인 절차를 거치지 않는다** — 관제의 거절 · 인증 실패 뒤의 실패 · 남은 시간 0 이 이에 해당한다. 상세는 [[SHELL-001]].

#### 저장 형식 — 관제와 글자 그대로 같아야 한다
갱신 결과는 관제가 쓰는 것과 **같은 키 · 필드 이름 · 단위**로 쓴다. 한 글자라도 다르면 같은 저장소를 읽는 **관제 탭이 깨진다**(관제는 만료 시각 필드를 읽어 곧바로 로그아웃할 수 있다).

| 키 | 값 |
|---|---|
| `klid-jwt-token` | 새 access 토큰 원문 |
| `tokenInfo` | JSON `{access_token, refresh_token, authority, userSido, userSgg, userOgCd, expiresAt, issuedAt, sessionExpAlarm, sessionTime, eventDate, rawVideoDate, inAccessibleMenus}` — 값은 새 access 토큰의 클레임에서 채운다. `expiresAt` = `exp`×1000(밀리초) · `issuedAt` = `iat`×1000 · `inAccessibleMenus` = `inaccessible_menus` 클레임(없으면 빈 배열) |
| `userNm` | `userNm` 클레임 |

- 관제가 **로그인 때만** 쓰는 저장소 키(`authority` · `pwd_change_recommended` · `contextMenu`)는 쓰지 않는다 — 관제 자신도 갱신 때는 쓰지 않는다.
- 저장소에 쓰는 권한 문자열을 **인가 판정에 읽지 않는다.** 인가 역할의 진실원은 서버이며, 저장소 쪽은 쓰기만 관제 형식에 맞춘다.
- 토큰과 refresh 토큰 원문을 로그에 싣지 않는다.

#### 탭 간 동기화
- 저장소 변경 이벤트로 **다른 탭(관제 탭 포함)의 갱신을 따라간다** — `klid-jwt-token` 값이 바뀌면 새로고침 없이 다음 요청부터 새 토큰을 싣는다.
- `klid-jwt-token` 이 **삭제되면**(관제 로그아웃) 로그아웃으로 보고 기존 결말을 따른다.
- `tokenInfo` 는 **있다가 사라졌을 때만** 로그아웃으로 본다. 개발용 로그인은 그 키를 애초에 쓰지 않으므로, 처음부터 없던 것을 로그아웃으로 보면 개발 진입이 막힌다.
- **동시 갱신 방지** — 갱신 직전 저장소의 refresh 토큰을 **다시 읽어**, 쥐고 있던 값과 다르면(다른 탭이 이미 갱신) 갱신하지 않고 새 값을 쓴다. 갱신이 거절된 뒤에도 로그아웃하기 전에 같은 재읽기를 한 번 더 한다(위 「갱신 실패의 결말」의 예외).

⚠ **인지·수용한 위험** — 관제 탭과 동시에 갱신하면 한쪽이 **교체된 옛 refresh 토큰**을 쥘 수 있다. 관제 탭은 저작도구 쪽 직렬화를 모르므로 완전한 배제는 불가능하며, 위 재읽기 비교가 1차 방어다. 옛 refresh 토큰을 다시 쓸 때 관제 서버가 **세션 전체를 끊는지는 관제 확인 대상**이다 — 끊는다면 드물게 두 탭이 함께 로그아웃될 수 있다.

#### [폐기] 내부 채널에 대한 구 서술
- 「내부 채널은 같은 출처 브라우저 저장소에서 넘겨받는 기존 방식을 그대로 쓴다」 — 저장소를 쓰는 것은 그대로이나 **「갱신이 없다」는 함의는 폐기**한다. 창구가 매 호출 현재값을 읽고 스스로 갱신한다.
- 「내부 채널에는 갱신 창구가 없다」 · 「세션 수명은 상위 시스템 토큰이 정하며 저작도구가 연장하지 못한다」 — **폐기.** 내부 채널 갱신 창구는 위 갱신 중계 창구([[API-247]])로 동작하고 사용자 연장도 받는다.
- 「브라우저가 관제 계정 갱신 창구를 같은 출처로 직접 부른다(`x-access-token` 에 refresh 토큰)」 — **폐기.** 관제 계정 서비스 호출은 저작도구 서버를 경유한다(위 「갱신 중계 창구」·「로그아웃 중계 창구」).
- 「저작도구는 브라우저 저장소에 쓰지 않는다」 — **포털 채널 한정 규정**이다. 내부 채널에서는 위 저장 형식으로 **쓴다.** 두 규정을 한 채널의 규정으로 합쳐 읽지 말 것.
- 「선제 갱신·사용자 연장이 실패하면 저장하지 않고 현재 토큰으로 계속한다」를 **실패 원인과 무관한 규칙으로 읽는 것** — **폐기.** 그 결말은 일시 장애에만 해당하고, 관제가 갱신을 거절하면 같은 시점이라도 **즉시** 로그아웃한다(위 「갱신 실패의 결말」).

## 저작 진입 경로 — 새로쓰기와 이어쓰기를 가른다 (2026-09-01 사용자 확정, 구속)

**진입은 두 갈래이고, 그중 외부 계약이 필요한 것은 하나뿐이다.**

| 진입 | 출발 화면 | 소유 | 대상 | 성격 |
|---|---|---|---|---|
| **새로쓰기** | 데이터마트 목록 | **Host(포털)** | 관제에서 전달받은 **사용자 편집 전 배포본** | **외부 계약** |
| **이어쓰기** | 내 저장 작업 목록 | **저작도구** | 사용자가 이미 저장한 작업 | **내부 이동** |

### 역할 분담 — Host 가 하는 것은 둘뿐이다
Host 는 ①데이터마트 목록 화면과 ②거기서 저작 화면으로 보내는 **진입 링크**만 제공한다.
**화면·세션 생성·소재 적재·저장·작업 목록·내려받기는 전부 저작도구가 소유한다.**

⚠ **진입 주소의 규격은 저작도구가 정의하고 Host 가 그 주소로 링크를 건다.** 반대가 아니다 —
Host 가 주소를 지어내면 저작도구 라우팅과 어긋나 진입이 통째로 실패한다. 주소는 위 「진입점·마운트·서빙
규약」의 마운트 경로 하위에 둔다.

### 진입 주소 — 대상 학습데이터를 가리키는 경로 변수 (2026-09-10 상호 확정, 구속)

Host 가 데이터마트 목록에서 저작 화면으로 보낼 때, **진입 주소의 경로 변수**로 대상 학습데이터의
**숫자 식별자**를 싣는다. 저작도구 Remote 가 그 값을 **주소에서 직접 읽는다.**

| 항목 | 값 |
|---|---|
| 진입 주소 | 마운트 경로 아래 **`/portal/datasets/{대상 학습데이터의 숫자 식별자}`** |
| 통로 | **경로 변수** — 주소의 한 구간이다 |
| 값 | 포털이 보유한 대상 학습데이터의 숫자 식별자 |
| 읽는 쪽 | 저작도구 Remote — 우리 라우터가 그 구간을 잡는다 |
| 이름 표기 | 포털이 조립한 그대로 쓴다. **대소문자를 바꾸지 않는다** |

- **Host 는 이 값을 마운트 시 넘겨주지 않는다.** 인계 창구로도 주지 않으므로 **우리가 주소에서 읽는다.**
- 같은 창·같은 문서를 공유하는 임베딩이라(별도 문서도 아니고 분리된 틀도 아니다) 주소를 직접 읽을 수 있다.
- ★ **파일의 절대경로는 주소에 싣지 않는다** — 그것은 **서버간 조회**로 받는다. 주소에 실리는 것은
  「무엇을 열지 가리키는 식별자」 하나뿐이고, 그 식별자로 소재를 조달하는 축은 [[INT-014]] 가 소유한다.
  **이 구분이 이 확정의 핵심**이다.

#### ★ 식별자 축이 다르다 — 데이터셋에서 프레임으로 푸는 일은 저작도구 몫이다
우리가 이미 정의해 둔 포털 진입은 **프레임 단위 둘뿐**이고 그 경로 변수는 **프레임·업로드 자산의 내부 키**다.
포털이 싣고 오는 것은 **학습데이터 한 건의 식별자**라 **축이 다르다** — 학습데이터를 통째로 여는 진입이
우리 규격에 없었다.

⇒ **저작도구가 이 진입을 신설하고, 학습데이터에서 프레임으로 푸는 일도 저작도구 백엔드가 한다.**
포털에 프레임 목록을 요구하지 않는다. **이 풀이 책임이 우리에게 있다는 사실을 지우지 말 것** — 지우면
다음 사람이 포털에 새 창구를 요구하는 협의를 다시 연다.

#### 지금 상태 — 포털은 이미 이 주소로 보내고 있다
**포털이 보내는 `/portal/datasets/{대상 학습데이터의 숫자 식별자}` 를 그대로 채택한다(2026-09-10 확정).**
근거 — 포털이 이미 이 주소로 보내고 있어 추가 조율이 필요 없고, 우리 관례에 맞춰 다른 모양을 회신하면
양쪽이 각각 고쳐야 하는데 얻는 것이 없다.
포털이 주소 조립을 **함수 한 곳**에 묶어 두었다는 사실은 **운영 정보로만 적어 둔다 — 미확정의 근거가 아니다.**
우리 진입이 신설되기 전까지는 포털 채널 안내 화면으로 떨어지며, 포털은 그것을 **의도한 상태**로 두고 있다.

⚠ **[폐기] 「진입 주소의 질의 문자열로 그 식별자를 받는다」는 구 규격이다.** 규격 문서가 먼저 그렇게 적었고
그 형태를 **실제로 시도했다가 실패**했다 — 그 값이 우리 라우터 어디에도 걸리지 않아 사용자가 **조용히
홈으로 떨어졌고**, 대상이 넘어가지 않았다는 사실조차 화면에 남지 않았다. 뒤에 나온 포털 실물이 **경로
변수**로 바꿨고 그것이 정본이다. **규격 문서에 그렇게 적혀 있다는 이유로 되돌리지 말 것.**

#### ★ 「토큰을 주소에 실어 전달하지 않는다」와 축이 다르다 — 위반으로 읽지 말 것
이 연동점과 인계 결정(ADR-012)이 가진 **「두 채널 모두 주소에 토큰을 실어 전달하지 않는다」**는 **그대로
유지되며 약화되지 않는다.** 그 금지의 대상은 **인증 토큰 축 한정**이다 — 토큰은 비밀이라 주소·기록·이력에
남는 것 자체가 유출이기 때문이다.

여기서 받는 것은 **토큰이 아니라 대상 학습데이터의 식별자**이고 비밀이 아니다. 게다가 이번 확정으로 통로가
**경로 변수**가 되어 그 금지와 **낱말조차 겹치지 않는다.** 그러므로 그 금지의 대상이 아니다.

⚠ 이 구분을 지우면 다음 사람이 이 규약을 **「금지 위반」으로 보고 지운다.** 이 설계는 「낡은 지시문이 다음
라운드의 작업 지시로 읽혀 확정 축을 되돌린다」를 반복 사고로 갖고 있다.

#### 값이 없을 때 — 필수 진입 조건으로 다루지 않는다 (저작도구 확정)
식별자가 없거나 숫자가 아니면 **평소의 작업 목록 화면으로 진입한다.** 안내 화면이나 오류로 막지 않는다.

근거 — 포털 업로드·증강은 그 식별자 **없이** 쓰는 정상 경로다. 필수 진입 조건으로 다루면 멀쩡한 동선이
함께 죽는다. 이 판정 권한은 포털이 저작도구에 **명시적으로 넘겼다.**

⚠ 이것은 아래 「열린 항목」의 **이어쓰기 대상 식별 방식과 다른 축**이다 — 그 항목은 여전히 열려 있다.

### 두 진입을 하나로 합치지 않는다
같은 식별자로 들어왔을 때 「이어쓸지 새로 팔지」를 서버가 **추측하게 되기 때문**이다. 추측이 틀리면
사용자 작업이 새 자리에 묻히거나 이전 작업 위에 겹친다. **진입을 갈라 두면 그 판단이 필요 없다.**

### ★ 「원본」이라는 낱말을 설계에 쓰지 않는다
사용자·협의 문서에서 이 배포본을 「원본」이라 부르는데, 그 뜻은 **「사용자가 아직 편집하지 않은 상태」**다.
**비식별 이전을 뜻하는 것이 아니다** — 전달되는 것은 **비식별본뿐**이다.

⚠ 그런데 이 저장소에서 「원본」은 **비식별 이전**을 가리키는 자리가 많다(영상 경로·프레임·폴백 금지 규칙).
같은 낱말이 두 축을 가리키면 **누군가 「원본을 읽는다」를 비식별 이전으로 읽어 개인정보 경로를 연다.**
그래서 설계 본문에는 **「사용자 편집 전 배포본」**으로 적는다. 협의 문서에서 「원본」을 만나면 어느 축인지
먼저 가른다.

### 열린 항목
- **이어쓰기 대상의 식별 방식** — 저장 작업을 무엇으로 지목하는지(작업 식별자 / 영상 식별자)
- **압축 해제 자리** — 받은 배포본을 어디에 푸는지가 아직 정해지지 않았다. Host 는 **읽기 권한만** 전제하고
  있어 쓸 자리를 아무도 정하지 않은 상태다. **읽는 자리와 푸는 자리는 반드시 가른다**(§소재 조달 참조)
- **누적 용량과 정리 책임** — 여러 사용자가 같은 배포본을 각자 풀면 해제본이 사람 수만큼 쌓인다.
  ⚠ **동시 요청 자체는 우려 대상이 아니다** — 배포본은 읽기 전용이고 작업 자리·결과가 사용자별로
  격리되므로 충돌 지점이 구조적으로 없다. 남는 것은 **누적**이지 경합이 아니다

## 채널 디자인 규약 — 향마다 다른 디자인 시스템을 쓴다 (2026-09-01 사용자 확정, 구속)

**관제 채널과 포털 채널은 서로 다른 디자인 시스템을 쓴다.** 하나로 수렴시키지 않는다.

| | 관제 채널 산출물 | 포털 채널 산출물 |
|---|---|---|
| 디자인 시스템 | **저작도구 것**(정부 디자인시스템 계열, 공공 표준 축) | **포털 것**(같은 계열이나 별개 시스템) |
| 주색 | 저작도구 주색 | **포털 코발트 `#2e45dc`** |
| 본문 기준 크기 | **17px** 이상 | **15px** |
| 모서리 | **4 · 6 · 8** (단정한 라운드) | **6 · 8 · 12 · 16 · 24** |
| 그림자 | 단일 3단 | **2겹 소프트**(가까운 1px + 멀고 흐린 30px) |
| 컨트롤 높이 | — | **36 · 44 · 52** 한 스케일(글자는 높이의 약 1/3) |
| 간격 | — | **4px 격자** · 세로 리듬 20/32/48 · 페이지 구획 80 |
| 굵기 상한 | — | **600**(700+ 미사용, 위계는 크기·색으로) |
| 장식 | **최소** — 정보 전달 우선 | 도메인 아트·모션 포함 |

**포털 채널은 포털 디자인 시스템을 전면 채택한다** — 주색만이 아니라 형태·타이포·간격·그림자·컨트롤 높이까지 그대로 따른다. Host 화면 안에 마운트되므로 그 안에서 이질감이 없는 것이 우선이다.

⚠ **본문 크기 차이는 뒤집는 결정이 아니다 — 근거의 무게를 정확히 적는다.** 저작도구 본문 17px 은 **공공 표준 디자인시스템 정합 과정에서 도출된 값**이고, 저작도구 디자인 시스템이 그 이유를 「고령층·장시간 작업 가독성」으로 **서술**하고 있다. 그러나 그것은 **디자인 시스템 문서의 서술이지 별도로 확정된 제약이 아니며**, 표준 원문이 단계별 픽셀을 명시한 것도 아니라는 사실이 그 시스템의 미해결 항목에 이미 기록돼 있다. 실제로 이 저장소에는 **본문이 너무 크게 느껴진다**는 지적이 제기돼 규정값 여부를 되짚은 이력이 있다.

⇒ 따라서 포털 채널에서 15px 를 쓰는 것은 **확정된 제약을 뒤집는 것이 아니라, 채널마다 다른 디자인 시스템을 쓰기로 한 규약을 그대로 따르는 것**이다. 「가독성 규정 위반」으로 읽지 말 것 — 위반할 규정이 그 자리에 없다.

⚠ 다만 **작업면의 밀도와 가독성은 별개로 지켜본다.** 라벨링은 장시간 정밀 작업이므로, 포털 채널 시안을 뜬 뒤 실제 화면에서 읽기 어려움이 확인되면 그때는 **채널 규약을 다시 정하는 방식으로** 다룬다(개별 화면에서 크기를 예외 처리하지 않는다 — 그렇게 하면 두 체계가 한 화면에 섞인다).

⚠ **관제 채널은 아무것도 바뀌지 않는다.** 위 포털 값은 **포털 채널 산출물에만** 적용된다. 관제 채널 화면에 포털 토큰을 섞지 말 것.

⚠ **두 시스템의 항목 번호가 겹친다** — 양쪽 다 같은 번호의 디자인 시스템을 갖고 있다. **어느 쪽 것인지 밝히지 않고 인용하면 화면에 다른 색·다른 크기가 들어간다.** 인용할 때 반드시 소속을 밝힌다.

⚠ **포털의 화면 부품 카탈로그는 별개 프로젝트 소유**라 링크로 끌어다 쓸 수 없다. 시각·구조를 참조해 우리 카탈로그에 대응물을 두는 형태가 된다.

## [해소] 디자인 토큰의 기준 단위 환산

**이 미결은 위 채널 규약으로 닫혔다.** 구 서술은 *"두 번들이 같은 문서에서 실행되므로 기준값은 Host 가 정한 하나로 수렴한다 — 그 값이 저작도구가 전제한 값과 다르면 같은 토큰이 채널마다 다른 크기로 뜬다"* 였고, 그것을 **문제로** 보아 협의로 맞추려 했다.

**맞추지 않는다.** 채널마다 **다른 디자인 시스템을 쓰기로 확정**했으므로 토큰이 갈리는 것이 정상이며 오히려 의도한 결과다. 포털 채널 산출물은 처음부터 포털 값으로 만들어지므로 「전제와 다른 기준값을 만나 어긋나는」 상황 자체가 생기지 않는다.

⚠ 남는 실무 조건은 하나다 — **포털 디자인 시스템이 절대 단위(px)로 토큰을 정의**하고 있으므로, 포털 채널 산출물도 그 자리에서 상대 단위로 환산하지 않는다. 환산하면 Host 의 기준값에 따라 크기가 흔들려 없앤 문제가 되살아난다.

## 스타일 격리 규약 (2026-09-15 사용자 확정, 구속)

**격리 책임은 저작도구다**(협의 해소 1번). 이 절이 정본.

1. **리셋 범위** — 문서 수준 초기화(리셋)는 **마운트 앵커와 그 하위에만** 적용하고 문서 전체를 가리키는 선택자를 두지 않는다. **판정 기준** — Host 주 메뉴 링크의 계산된 테두리 «양식»이 마운트 후에도 「없음」으로 남는다. ⚠ 기전 — 리셋이 «양식»을 「실선」으로 바꾸면, «굵기»만 지정하고 양식을 기본값에 맡긴 Host 자리에서 **숨어 있던 굵기가 그려진다.**
2. **앵커 소유권** — 앵커는 **저작도구가 소유한 요소**이며 표식은 클래스 이름 **`klid-portal-embed`** 다. Host 가 만든 자리 요소에 기대지 않는다(상대가 이름을 바꾸면 조용히 깨진다). **앵커 자신도 범위에 포함**한다.
3. **덧띄움 요소** — 본문 직하로 옮겨 그려지는 대화상자·서랍·떠 있는 창은 앵커 밖으로 떨어지므로 **같은 표식을 가진 공용 담을 곳**에 그린다. ※ 같은 이유로 그 요소들이 앵커의 간격 기준(§[해소] 디자인 토큰의 기준 단위 환산)을 못 받던 결함도 닫힌다.
4. **채널별 차이** — **포털 채널 산출물에만** 적용한다. 관제 채널 산출물은 문서를 소유한 독립 앱이라 전역 리셋을 그대로 둔다. ⚠ 두 채널이 함께 전역 리셋을 잃으면 **관제 화면이 깨진 것**이다.

★ **판단 근거 — 「계층」은 격리 수단이 아니다.** 계층 우선순위는 **같은 속성을 두고 맞붙을 때만** 작동하므로 Host 가 선언하지 않은 속성에는 저작도구 규칙이 그대로 적용된다. **격리는 선택자 범위로만 얻어진다.** ⇒ 구 수단 「범위 한정 스타일 계층」은 **폐기**이고 「빌드타임 접두어」는 유효하다.
⚠ **반대 축과 혼동 금지** — 유틸리티를 계층 밖에 두는 기존 결정은 Host 를 **이겨야 하는** 축이고, 이 규약은 Host 를 **건드리지 말아야 하는** 축이다.
⚠ **범위를 좁힐 때 우선순위를 올리지 않는다** — 올리면 리셋이 저작도구 유틸리티를 이겨 화면이 통째로 깨진다.

## 범위 밖 — 서버간 API 축은 INT-014 가 소유한다

**포털과 저작도구의 서버가 서로의 창구를 직접 호출하는 축은 이 연동점 범위가 아니다 — 그 자리는 [[INT-014]] 다.** 이 연동점이 다루는 것은 브라우저 안에서 두 화면이 함께 실행되는 축뿐이다.

INT-014 가 담는 창구는 아래와 같다. **개수를 못박지 않고 열거만 남긴다** — 수를 적으면 그 수가 틀렸을 때 목록보다 먼저 눈에 들어와 잘못된 확신을 준다.

| 방향 | 창구 |
|---|---|
| 저작도구가 여는 것 | 저작 현황 요약 제공 · 일일 저작 집계 제공 · 배포본 정리 삭제 트리거 수신 |
| 저작도구가 부르는 것 | AI 사용량 보고 · 그 되돌림(환불) |

⚠ **[폐기] 구 열거 「완료 저작결과 조회 · 일일 저작집계」는 확정 전 이해였다.** 완료 저작결과 조회는 확정 창구에 들어가지 않았고, 사용량 보고 · 되돌림 · 배포본 정리 삭제 트리거는 그 열거에 없었다. **그 둘로 범위를 가늠하지 말 것.**

⚠ 구 서술은 이 축을 **「별도 트랙」**이라 부르며 밀어냈는데 **그 트랙은 그때 실재하지 않았다.** 이제 INT-014 가 그 자리다.

| 소유 | 서술 |
|---|---|
| **이 연동점** | 브라우저에서의 토큰 인계 창구(획득 · 갱신 · 인증 실패 통지 · 활동 통지)와 그 보관 규칙 |
