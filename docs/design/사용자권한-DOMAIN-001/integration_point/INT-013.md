### notes

상위 시스템이 발급한 서명 토큰을 인계받으며 저작도구가 발급하지 않는다. 포털 채널은 Host 가 주입한 인계 창구(토큰 획득 · 갱신 · 인증 실패 통지 · 활동 통지)에서 토큰을 얻어 전용 요청 헤더 x-access-token 으로 싣는다. ## description

포털(외부 채널) 화면 안에 저작도구 프론트엔드를 런타임으로 끼워 넣는 연동이다. 포털이 Host, 저작도구가 Remote 이며 두 번들이 같은 브라우저 문서에서 함께 실행된다.

저작도구 쪽에는 이 연동을 결정한 문서가 따로 없다 — 아래 「저작도구 측 결정」이 그 자리다.

## 확정 사실 (포털 측)
- 포털이 자기 프로젝트의 결정 문서로 Host/Remote 구조를 확정하고 연동점으로 등록했다. 저작도구는 Remote 를 제공하는 쪽이다.
- 포털은 통합 지점을 작업공간 하위의 저작도구 경로 한 곳만 두고, 그 영역 안의 화면 내용은 저작도구 화면정의서를 정본으로 삼는다고 명시한다.
- 그 영역에 대응하는 저작도구 화면에는 SCREEN-028(포털 홈) · SCREEN-029(포털 라벨링) · SCREEN-033(포털 업로드)가 있다.
- 포털이 스스로 규정하는 범위는 마운트 조건(로그인 상태 · 데스크톱 폭)과 영역 밖 상태화면(비로그인 잠금 안내 · 데스크톱 전용 안내)뿐이다.
- 저작도구 정적 자원은 포털 웹서버가 **같은 출처의 하위 경로**로 서빙한다. 저작도구 백엔드가 별도 서버로 분리되어도 이 사실은 바뀌지 않아 교차 출처 설정이 필요 없다.
- 번들은 **로그인된 사용자에게만** 로드된다 — 비로그인 분기는 Host 가 먼저 처리하고 저작도구 안에 또 하나의 인증 분기를 두지 않는다.
- 번들 로드·실행 오류는 Host 와 같은 문서에서 발생하므로 **오류 경계가 규정돼 있다**.
- 포털 채널이 쓰는 저작도구 API 는 브라우저가 **같은 출처로 직접 호출**한다.

## 저작도구 측 결정

- **셸 소유권 — 포털 셸 안으로 들어간다.** 포털이 규정한 「포털 셸 + 그 안의 저작도구 영역」 구조를 그대로 받는다. 저작도구 포털 채널의 머리 영역(SHELL-002)과 좌측 주 메뉴는 렌더하지 않는다. 다만 **그 구성을 지우지 않고 끄기만 한다** — 전체 화면 방식으로 뒤집히더라도 되돌릴 수 있어야 하고, 그때 초점 표시·링크 접근성 처리까지 재현돼야 하기 때문이다.
- **Remote 로 내보내는 산출물은 납품본이다.** 포털 결정 문서가 전제한 기술 스택과 주 버전이 그쪽에서 일치한다. 다만 그 산출물은 별도 조직이 관리하므로 이 설계가 직접 바꾸지 않는다 — 여기서는 **기준 구현본이 그 자리에 그대로 올라가도 동작하도록** 갖춰 두는 것까지가 범위다.
- **그래서 기준 구현본의 주 버전을 생태계에 맞춘다.** 포털·관제·납품본이 모두 같은 세대의 렌더링 라이브러리와 스타일 도구를 쓰는데 기준 구현본만 한 세대 뒤였다. 정렬하면 Host 가 어느 쪽이든 공유 협상 없이 올라가고, 기준 구현으로서의 역할도 정확해진다(뒤처진 세대가 기준이면 맞추는 쪽이 매번 차이를 흡수한다).
- **산출물은 채널별로 따로 만든다.** 내부 채널과 포털 채널의 배포 대상이 서로 다른 서버라 하나의 산출물을 두 곳이 나눠 쓰는 구성이 성립하지 않는다. 공통 소스는 한 벌로 두고 **산출만 채널별로 가른다** — 그러면 ①반대 채널 화면이 산출물에 섞이지 않고 ②채널마다 다른 팔레트를 산출 시점에 정할 수 있으며 ③채널을 가르는 지점이 진입점·라우팅·셸 세 곳으로 좁혀진다. 공통 화면 부품은 채널을 스스로 알지 않고 넘겨받은 값으로만 동작하므로 갈래마다 복제되지 않는다.
- **토큰 인계 수단은 채널마다 갈린다.** 포털 채널은 Host 가 주입한 인계 창구에서 토큰을 얻어 **전용 요청 헤더**로 싣고, access token 은 **Host 메모리에만** 둔다(브라우저 저장소 미사용). 근거(포털 비협상) — 저장소나 그 스냅샷을 직접 읽으면 갱신 뒤 **죽은 토큰**을 잡고, 수십 분 체류하는 저작 화면은 반드시 파손된다. 내부 채널은 인계 결정(ADR-012)대로 같은 출처 브라우저 저장소를 쓴다.
  ⇒ 조치: 저장소 직접 읽기를 **획득 창구 뒤로 추상화**해 두 Host 를 분기 없이 지원한다. 앞선 「변경 0」 주장은 **어댑터 한 겹**으로 조정된다.
  ⚠ 「포털 서술이 두 갈래」라던 경고는 **폐기한다** — 두 방식은 상충이 아니라 **상보**였다.
- **Host 화면을 벗어나지 않는다.** 저작도구는 인증 실패·권한 없음을 자기 화면 이동으로 처리하는데, Host 안에 마운트되면 그 이동이 **Host 문서 전체**에 걸린다. 그런데 Host 가 선언한 화면 목록에 저작도구가 보내는 자리가 없어 **찾을 수 없는 화면**이 된다(전수 확인). 그러므로 포털 채널 빌드에서는 **이동하지 않고 그 자리에 안내를 그린다**. 기본값인 내부 채널에서는 지금처럼 이동한다 — 거기서는 그 자리가 실재하기 때문이다.
  ⚠ **토큰 만료로 상위 시스템 로그인 화면에 보내는 것은 그대로 둔다.** 그건 Host 도 해야 할 일이고, 저작도구는 복귀 주소에 현재 위치를 실어 보내므로 임베드된 상태에서 오히려 정확하다. 이것까지 막으면 만료된 세션에 갇힌다.
  ⚠ 이 결정으로 **Host 위임 규약 자체가 필요 없어진다** — 저작도구가 Host 를 건드리지 않고 자기 영역 안에서 끝내기 때문이다.
- **이 결정이 뒤집혀도 나머지는 다시 하지 않는다.** 두 방식의 차이는 머리 영역과 좌측 주 메뉴를 그리느냐 둘뿐이고, Host 하위 마운트에 필요한 나머지(경로 구조 재편 · 이탈 경로 위임 · 산출 분리 · 색 토큰 정리)는 어느 쪽이든 동일하다.
- **화면 사이 이동은 셸에 기대지 않는다.** 포털 채널 화면 네 건은 화면 안의 링크로 서로를 오간다(영상 선택 · 업로드 진입 · 목록 복귀). 내비게이션 영역이 없어도 이동이 끊기지 않으며, 이 성질이 위 결정을 되돌릴 수 있게 만드는 조건이다.
- **진입점·마운트·서빙 이름은 포털이 정한 값을 따른다.** 구체 값은 인라인 스펙에 있다.
- **이 경로로 진입한 사용자는 포털 권한 사용자로 본다 — 화면 축 한정.** 포털 채널 빌드가 그 권한으로 화면·메뉴·기능을 게이팅한다.
  ⚠ **서버 인가의 진실원은 토큰 클레임(채널·역할)이며 진입 경로가 권한을 올리지 않는다.** 진입 경로는 클라이언트가 주장하는 값이라 위조할 수 있다.

## 협의 대상 — 해소
1. **스타일 격리.** 포털 디자인 스타일이 정본이므로 **격리 책임은 저작도구**다. 번들이 빌드타임 접두어 또는 범위 한정 스타일 계층으로 자기 스타일을 격리해 Host 전역 스타일을 침범하지 않는다.
2. **디자인 토큰.** 「어느 팔레트로 뜨는가」가 답을 얻었다 — **포털 채널 산출물은 포털 주색(코발트 계열)으로 뜬다.** 팔레트는 산출 시점에 정해지며 뜬 뒤 갈아끼우지 않는다. 색을 고정값으로 박으면 갈아끼울 수 없어 **시맨틱 색의 토큰 분리가 선행**된다(범주 구분에 쓰는 색은 대상이 아니다 — 의미가 아니라 구분이라 채널이 달라도 같아야 한다).
3. **동일 Remote 재사용 전제.** 관제 쪽 설계에 프론트엔드 임베딩 서술이 없다는 실측을 포털이 **수용**했다. 통합 방식은 유지된다(캔버스 이벤트 간섭 회피·독립 배포·화면 일관성 근거 유효). 성립하지 않는 재사용 이점 한 줄은 포털이 정리한다.
4. **가드 중복.** 포털이 저작도구 UX 가드를 **허용**했다 — 서버가 최종 인가를 판정하고 가드가 Host 를 이탈시키지 않아 무해하며 포털 셸 인증 분기와 공존한다.

## 협의 미결
- **디자인 토큰의 기준 단위 환산.** 양쪽 설계 어디에도 명시가 없다(포털 회신 범위 밖). 상세는 인라인 스펙.

## 인증
상위 시스템이 발급한 서명 토큰을 인계받으며 저작도구가 발급하지 않는다. 전달 수단은 위 「토큰 인계 수단은 채널마다 갈린다」가 정본이고, 어느 채널도 Bearer 스킴을 쓰지 않는다.

## 범위 밖
서버간 API(완료 저작결과 조회 · 일일 저작집계)는 **별도 트랙**이며 이 연동점 범위가 아니다.

## 참조 주의
포털은 별개 프로젝트라 식별자 체계가 저작도구와 겹치지 않는다. 위에서 「포털 측」이라고 밝힌 문서는 모두 포털 프로젝트의 것이며 같은 번호의 저작도구 항목과 다른 문서다.

## 채널 산출물은 향마다 따로 만든다 — 런타임 설정으로 대체되지 않는다
채널을 가르는 값은 **산출 시점에 굳는 상수**다. 그 하나가 아래 넷을 한꺼번에 가른다.

| 가르는 지점 | 포털 채널 | 기본(내부) 채널 |
|---|---|---|
| 자기 머리 영역 | 렌더하지 않는다(포털 셸 안으로 들어간다) | 렌더한다 |
| 좌측 주 메뉴(NAV-002) | 두지 않는다(포털 셸이 소유한다) | 렌더한다 |
| 라우터 기준 경로 | 마운트 경로를 기준 경로로 문다 | 기준 경로를 두지 않는다 |
| 이탈 분기 **네 곳** | 화면 이동 대신 제자리 안내를 그린다 | 지금처럼 이동한다 |

⚠ **좌측 주 메뉴가 포털 채널에서 빠지는 것은 Host 소유이기 때문이다** — Host 가 머리 영역과 좌측 주 메뉴를 모두 소유하고, 저작도구는 그 아래 본문만 그린다. 저작도구가 자기 좌측 주 메뉴를 두면 **왼쪽 레일이 둘이 되어** Host 화면과 부딪힌다.

⚠ **설치 시점에 정하는 배포 향 설정으로는 이 값을 바꾸지 못한다.** 그 설정은 서버 쪽 배선을 가를 뿐 **이미 만들어진 화면 산출물**을 바꾸지 않는다. 그러므로 향마다 산출을 따로 만들고, **반입 절차가 그 값을 산출 단계에 명시적으로 넘겨야 한다.**

⚠ 넘기지 않으면 **기본값이 적용돼 내부 채널 산출물이 포털에 올라간다** — 빌드는 성공하고 오류도 없어 **조용히** 어긋난다. 증상은 포털에서 저작도구 머리 영역이 겹쳐 뜨고 **왼쪽 레일이 둘로 겹치며**, 기준 경로가 없어 하위 화면이 전부 없는 화면이 되는 형태로 나타난다.

## Host 없이 단독으로 띄우는 경우 — 개발 환경 한정

포털 채널 산출물은 **Host 가 있다고 전제한다.** 그 전제가 성립하지 않는 형상이 하나 있다 — 포털 연동 배포본을 **포털 없이 단독으로 띄워 확인하는 개발 환경**이다. 그 형상에서는 두 가지가 동시에 막힌다.

| 막히는 것 | 왜 |
|---|---|
| 화면에 닿지 못한다 | 마운트 경로가 라우터 기준 경로라, 그 밖의 주소로 들어오면 어떤 화면도 걸리지 않는다 |
| 토큰을 얻지 못한다 | 인계 창구가 없고, **없을 때 브라우저 저장소로 폴백하지 않는 것이 규정**이다. 개발용 토큰을 발급해도 요청에 실리지 않는다 |

⇒ **개발 환경에 한해 Host 를 대신하는 임시 창구를 둔다.** 규정은 아래와 같다.

- **계약을 새로 만들지 않는다.** 임시 창구는 실제 Host 가 쓰는 것과 **같은 네 이름**(토큰 획득 · 갱신 · 인증 실패 통지 · 활동 통지)을 그대로 구현한다. 그래야 실제 Host 계약을 어겼을 때 개발 단계에서 드러난다 — 따로 판 우회로는 그 검증을 못 한다.
- **기준 경로 밖으로 들어온 진입은 마운트 경로 아래로 보낸다.** ⚠ 이것은 「이탈 분기 네 곳은 제자리 안내」와 **다른 축**이다. 그건 앱이 그린 화면 안에서의 분기이고, 이것은 앱이 시작되기 전의 진입 지점 보정이다. 그 규정을 되돌리는 것이 아니다.
- **이동 목적지는 산출 시점에 굳은 값에서만 나온다.** 실행 중 입력(주소의 질의 문자열 · Host 가 건넨 값)이 목적지에 섞이면 안 된다 — 기준 경로가 곧 이동 표면이 되어 바깥 주소로 끌려간다. 마운트 경로 값에 이미 걸려 있는 금지와 같은 것이다.
- **임시 창구가 자기 몫의 토큰을 스스로 보관한다.** 본체가 포털 채널에서 브라우저 저장소를 쓰지 않는다는 규정은 그대로다 — 구조는 「본체가 저장소를 읽는다」가 아니라 **「Host 역할을 하는 쪽이 토큰을 갖고 창구로 건넨다」**여야 한다.
- **단독 구동 진입점에만 둔다.** 진입점은 둘이다 — 문서를 소유하는 단독 진입점과 Host 안에 실리는 원격 진입점. 임시 창구를 앞쪽에만 두면 실제 Host 안에서는 **구조적으로 활성화될 수 없다.** 조건 검사에 기대지 않고 배치로 보장하는 편이 안전하다.

### 운영 산출물에 포함되지 않는다
이 장치는 임의 권한의 토큰을 요청에 실어 주므로, 운영 산출물에 남으면 **그 자체가 인증 우회 경로**다. 그러므로 개발 노출 조건 하나로 가르지 말고 **산출 시점에 굳는 조건을 함께** 걸어 산출물에서 빠지게 한다.

⚠ 폐쇄망 반입 산출은 개발용 로그인 노출 값을 **기본으로 켜서** 만든다. 그 값 하나에만 기대면 **반입 산출물에 이 장치가 들어간다.**

## 토큰 인계 창구 (Host 주입)
Host 가 Remote 에 인계 창구를 주입한다 — 토큰 획득 · 갱신 · 인증 실패 통지 · 활동 통지. 얻은 access token 은 전용 요청 헤더 `x-access-token` 으로 싣고 Bearer 스킴은 쓰지 않는다. 토큰은 Host 메모리에만 두고 브라우저 저장소에 쓰지 않는다.

저작도구는 같은 출처 저장소를 직접 읽던 지점을 토큰 획득 창구 뒤로 추상화해, 저장소를 쓰는 Host 와 메모리에 두는 Host 를 분기 없이 지원한다.

### 인계 창구의 계약 이름
| 창구 | 이름 | 역할 |
|---|---|---|
| 토큰 획득 | `getAccessToken` | 현재 유효한 access token 을 돌려준다 |
| 갱신 | `refresh` | 만료 임박·만료 시 재발급을 요청한다 |
| 인증 실패 통지 | `onUnauthorized` | 인증이 끊겼음을 Host 에 알린다 — 안내·재로그인은 Host 가 소유한다 |
| 활동 통지 | `notifyActivity` | 사용자 활동을 Host 에 알려 세션 유지 판단에 쓰게 한다 |

이름은 **포털이 정본으로 제시한 계약**이라 저작도구가 바꾸지 않는다. Host 가 주입하는 객체의 키이므로 **이름이 어긋나면 실행 시점에 창구를 찾지 못한다** — 개념만 맞추고 이름을 새로 짓지 말 것.

⚠ 인계 창구와 전용 요청 헤더는 **상충이 아니라 상보**다 — 창구로 얻어 헤더로 싣는 **한 모델**이며, 두 갈래 중 택일하는 것이 아니다.

## 저작 진입 경로 — 새로쓰기와 이어쓰기를 가른다 (2026-09-01 사용자 확정, 구속)

**진입은 두 갈래이고, 그중 외부 계약이 필요한 것은 하나뿐이다.**

| 진입 | 출발 화면 | 소유 | 대상 | 성격 |
|---|---|---|---|---|
| **새로쓰기** | 데이터마트 목록 | **Host(포털)** | 관제에서 전달받은 **사용자 편집 전 배포본** | **외부 계약** |
| **이어쓰기** | 내 저장 작업 목록 | **저작도구** | 사용자가 이미 저장한 작업 | **내부 이동** |

### 역할 분담 — Host 가 하는 것은 둘뿐이다
Host 는 ①데이터마트 목록 화면과 ②거기서 저작 화면으로 보내는 **진입 링크**만 제공한다.
**화면·세션 생성·소재 적재·저장·작업 목록·내려받기는 전부 저작도구가 소유한다.**

⚠ **진입 주소의 규격은 저작도구가 정의하고 Host 가 그 주소로 링크를 건다.** 반대가 아니다 —
Host 가 주소를 지어내면 저작도구 라우팅과 어긋나 진입이 통째로 실패한다. 주소는 위 「진입점·마운트·서빙
규약」의 마운트 경로 하위에 둔다.

### 두 진입을 하나로 합치지 않는다
같은 식별자로 들어왔을 때 「이어쓸지 새로 팔지」를 서버가 **추측하게 되기 때문**이다. 추측이 틀리면
사용자 작업이 새 자리에 묻히거나 이전 작업 위에 겹친다. **진입을 갈라 두면 그 판단이 필요 없다.**

### ★ 「원본」이라는 낱말을 설계에 쓰지 않는다
사용자·협의 문서에서 이 배포본을 「원본」이라 부르는데, 그 뜻은 **「사용자가 아직 편집하지 않은 상태」**다.
**비식별 이전을 뜻하는 것이 아니다** — 전달되는 것은 **비식별본뿐**이다.

⚠ 그런데 이 저장소에서 「원본」은 **비식별 이전**을 가리키는 자리가 많다(영상 경로·프레임·폴백 금지 규칙).
같은 낱말이 두 축을 가리키면 **누군가 「원본을 읽는다」를 비식별 이전으로 읽어 개인정보 경로를 연다.**
그래서 설계 본문에는 **「사용자 편집 전 배포본」**으로 적는다. 협의 문서에서 「원본」을 만나면 어느 축인지
먼저 가른다.

### 열린 항목
- **이어쓰기 대상의 식별 방식** — 저장 작업을 무엇으로 지목하는지(작업 식별자 / 영상 식별자)
- **압축 해제 자리** — 받은 배포본을 어디에 푸는지가 아직 정해지지 않았다. Host 는 **읽기 권한만** 전제하고
  있어 쓸 자리를 아무도 정하지 않은 상태다. **읽는 자리와 푸는 자리는 반드시 가른다**(§소재 조달 참조)
- **누적 용량과 정리 책임** — 여러 사용자가 같은 배포본을 각자 풀면 해제본이 사람 수만큼 쌓인다.
  ⚠ **동시 요청 자체는 우려 대상이 아니다** — 배포본은 읽기 전용이고 작업 자리·결과가 사용자별로
  격리되므로 충돌 지점이 구조적으로 없다. 남는 것은 **누적**이지 경합이 아니다

## 채널 디자인 규약 — 향마다 다른 디자인 시스템을 쓴다 (2026-09-01 사용자 확정, 구속)

**관제 채널과 포털 채널은 서로 다른 디자인 시스템을 쓴다.** 하나로 수렴시키지 않는다.

| | 관제 채널 산출물 | 포털 채널 산출물 |
|---|---|---|
| 디자인 시스템 | **저작도구 것**(정부 디자인시스템 계열, 공공 표준 축) | **포털 것**(같은 계열이나 별개 시스템) |
| 주색 | 저작도구 주색 | **포털 코발트 `#2e45dc`** |
| 본문 기준 크기 | **17px** 이상 | **15px** |
| 모서리 | **4 · 6 · 8** (단정한 라운드) | **6 · 8 · 12 · 16 · 24** |
| 그림자 | 단일 3단 | **2겹 소프트**(가까운 1px + 멀고 흐린 30px) |
| 컨트롤 높이 | — | **36 · 44 · 52** 한 스케일(글자는 높이의 약 1/3) |
| 간격 | — | **4px 격자** · 세로 리듬 20/32/48 · 페이지 구획 80 |
| 굵기 상한 | — | **600**(700+ 미사용, 위계는 크기·색으로) |
| 장식 | **최소** — 정보 전달 우선 | 도메인 아트·모션 포함 |

**포털 채널은 포털 디자인 시스템을 전면 채택한다** — 주색만이 아니라 형태·타이포·간격·그림자·컨트롤 높이까지 그대로 따른다. Host 화면 안에 마운트되므로 그 안에서 이질감이 없는 것이 우선이다.

⚠ **본문 크기 차이는 뒤집는 결정이 아니다 — 근거의 무게를 정확히 적는다.** 저작도구 본문 17px 은 **공공 표준 디자인시스템 정합 과정에서 도출된 값**이고, 저작도구 디자인 시스템이 그 이유를 「고령층·장시간 작업 가독성」으로 **서술**하고 있다. 그러나 그것은 **디자인 시스템 문서의 서술이지 별도로 확정된 제약이 아니며**, 표준 원문이 단계별 픽셀을 명시한 것도 아니라는 사실이 그 시스템의 미해결 항목에 이미 기록돼 있다. 실제로 이 저장소에는 **본문이 너무 크게 느껴진다**는 지적이 제기돼 규정값 여부를 되짚은 이력이 있다.

⇒ 따라서 포털 채널에서 15px 를 쓰는 것은 **확정된 제약을 뒤집는 것이 아니라, 채널마다 다른 디자인 시스템을 쓰기로 한 규약을 그대로 따르는 것**이다. 「가독성 규정 위반」으로 읽지 말 것 — 위반할 규정이 그 자리에 없다.

⚠ 다만 **작업면의 밀도와 가독성은 별개로 지켜본다.** 라벨링은 장시간 정밀 작업이므로, 포털 채널 시안을 뜬 뒤 실제 화면에서 읽기 어려움이 확인되면 그때는 **채널 규약을 다시 정하는 방식으로** 다룬다(개별 화면에서 크기를 예외 처리하지 않는다 — 그렇게 하면 두 체계가 한 화면에 섞인다).

⚠ **관제 채널은 아무것도 바뀌지 않는다.** 위 포털 값은 **포털 채널 산출물에만** 적용된다. 관제 채널 화면에 포털 토큰을 섞지 말 것.

⚠ **두 시스템의 항목 번호가 겹친다** — 양쪽 다 같은 번호의 디자인 시스템을 갖고 있다. **어느 쪽 것인지 밝히지 않고 인용하면 화면에 다른 색·다른 크기가 들어간다.** 인용할 때 반드시 소속을 밝힌다.

⚠ **포털의 화면 부품 카탈로그는 별개 프로젝트 소유**라 링크로 끌어다 쓸 수 없다. 시각·구조를 참조해 우리 카탈로그에 대응물을 두는 형태가 된다.

## [해소] 디자인 토큰의 기준 단위 환산

**이 미결은 위 채널 규약으로 닫혔다.** 구 서술은 *"두 번들이 같은 문서에서 실행되므로 기준값은 Host 가 정한 하나로 수렴한다 — 그 값이 저작도구가 전제한 값과 다르면 같은 토큰이 채널마다 다른 크기로 뜬다"* 였고, 그것을 **문제로** 보아 협의로 맞추려 했다.

**맞추지 않는다.** 채널마다 **다른 디자인 시스템을 쓰기로 확정**했으므로 토큰이 갈리는 것이 정상이며 오히려 의도한 결과다. 포털 채널 산출물은 처음부터 포털 값으로 만들어지므로 「전제와 다른 기준값을 만나 어긋나는」 상황 자체가 생기지 않는다.

⚠ 남는 실무 조건은 하나다 — **포털 디자인 시스템이 절대 단위(px)로 토큰을 정의**하고 있으므로, 포털 채널 산출물도 그 자리에서 상대 단위로 환산하지 않는다. 환산하면 Host 의 기준값에 따라 크기가 흔들려 없앤 문제가 되살아난다.
