## description

REVIEWER 가 POST /v1/augments/request (AugmentController, @PreAuthorize REVIEWER) 로 검수 완료 영상에 증강을 요청한다. 한 요청 = 영상 1건 × 종류 1개 (DTO @Size(max=1) + AugmentRequestService.requireSingleSelection 로 fail-closed 재확인 — 초과분을 조용히 잘라 첫 건만 처리하지 않는다). 요청마다 생성 조건 5필드(time/season/weather/terrain/severity)를 받으며 전부 필수다 — 「생성형 AI API 연동명세서 v1.3」 §4.1 의 최상위 mtdt 로 전송되고 동시에 LS_DATA_AUG.PROMPT_CN(V147)에 자유 지시문과 분리한 형태로 남는다. v1.3 이 다섯 항목의 허용 코드를 닫아 두어 자유 문자열이 아니다 — 구 서술(자유 문자열을 prompt 객체로 가공 없이 전송)은 폐기다. 증강 종류(AUG_TYPE_CD)는 prompt 에서 파생하지 않고 별도 types[] enum 이 단일 원천이다(그 값이 유형으로 흘러가면 산출물 경로 순회 CWE-22 · RESL_ 네임스페이스 침범이 열린다). 게이트 순서는 고정된다 — 인가(403) → 단건 계약(400) → prompt 검증(400) → ①파생 영상 차단(400) → ②외부 증강 미연동(503) → ③APPROVED 검증(400 NOT_REVIEWED) → ④비식별 신고 구간(412) → ⑤대표 프레임 미추출(412). 미연동 거부가 뒤 셋보다 앞이라, 외부가 연동되지 않은 환경에서는 그 셋이 나타나지 않는다 — 어차피 증강이 일어날 수 없으므로 의도된 순서이고, 미연동은 요청자가 해소할 수 있는 조건이 아니라 배포 환경 구성이라 신고 구간의 412 와 같은 코드를 쓰지 않는다. 파생 차단을 먼저 두는 이유는 파생본이 통상 미검수라 순서가 어긋나면 「미검수」 같은 엉뚱한 사유가 먼저 뜨고 요청자가 진짜 사유에 도달하지 못하기 때문이며, 해상도 변경 경로(VideoResolutionService.loadAndValidate)와 같은 순서다. 파생 거부는 400(영구 조건)이고 신고 거부는 412(일시 조건, 해소 후 재요청 가능)로 구분한다. 같은 (영상 × 종류) 재요청은 몇 번이든 허용한다 — 생성 결과가 매번 달라 동일 조건 재요청이 정당한 운영 동선이므로 사전 조회 가드·409 응답·부분 유니크 인덱스(UK_LS_DATA_AUG_ACTVTN, V143→DROP)를 모두 제거했고 속도 제한도 두지 않는다(연타 방어는 FE 단독 책임). 게이트를 통과하면 LS_DATA_AUG 에 PENDING 행을 멱등키(IDMP_KEY UNIQUE)·prompt 원문과 함께 단일 INSERT 하고, 외부 위탁은 AugmentRequestedItemEvent 로 커밋 이후 AugmentJobSubmitService(전송 진입점 단일 fail-closed)에 위임한다 — 요청 응답 시점에 동기 외부 호출을 하지 않는다(고아 멱등키 방지).
