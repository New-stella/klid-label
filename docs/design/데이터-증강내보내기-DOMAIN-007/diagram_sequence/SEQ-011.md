## description

REVIEWER 가 증강 결과 목록(GET /v1/augments)에서 결과를 확인하고 사용(accept) 또는 폐기(reject, 사유 필수)를 결정한다. 증강 본체는 외부 SFR-07 책임이고 저작도구는 결과 검수만 담당한다. ★두 상태축 분리(ADR-045, 2026-07-31) — 구 구현은 accept 를 'AUG_PROC_STTS_CD PENDING→ACCEPTED', reject 를 'PENDING→REJECTED' 로 적었으나 그 컬럼은 <생성 결과 전용(웹훅 소유)>이다. 검수 결정은 LS_DATA_AUG_RVW.RVW_STTS_CD 가 단독으로 소유하며 검수자(RVW_ID)·검수일시(RVW_DT)·반려사유(RJCT_RSN)를 동반한다. ⚠ 경위(같은 실수 반복 방지): 두 주체가 한 컬럼에 쓰고 있었다. 외부 증강은 웹훅이 항상 먼저 도착해 aug 행을 ACCEPTED 로 옮기는데 상태 전이가 PENDING 에서만 허용돼 REVIEWER 의 승인·반려가 영구히 409('이미 처리된 증강 결과')로 막혀 있었다 — 즉 사용/폐기 워크플로 자체가 도달 불가였고, 테스트가 aug 를 PENDING 으로 심어놓고 accept() 를 호출해 이 조합을 한 번도 통과시키지 않아 커버리지 밖이었다. 현재 accept()/reject() 는 aug 상태를 건드리지 않고 리뷰 행만 쓴다(재결정 차단은 검수 행 자신의 ensurePending 가 담당). ★등재 게이트 — '승인해야 작업목록·배정에 등재' 판정도 리뷰 축(RVW_STTS_CD='ACCEPTED')으로 한다 — 생성 결과축으로 게이팅하면 생성 성공만으로 전부 통과해 기능이 무의미해진다. ⚠ 해상도 파생(RESL_*)은 검수 대상이 아니라 리뷰 행이 영영 생기지 않으므로 통과 예외를 명시적으로 박고(빠뜨리면 해상도 파생이 전부 작업목록에서 사라진다), 매핑 행(NEW_RAW_SN, V155)이 없는 도입 이전 파생은 그랜드퍼더링 통과시킨다(고아 배정 방지). 해상도 파생은 증강 이력·집계에는 함께 노출되나 accept/reject 진입 자체가 차단된다(loadOrThrow → 400). [반려 후 폐기] 반려된 파생은 등재 게이트가 리뷰 축이라 즉시 작업 대상에서 빠지고, 유예기간(설정값, 기본 7일) 경과 후 배치(AugmentDiscardPurgeSweeper)가 DB 행과 생성 파일까지 실삭제한다. 삭제 대상은 파생(ORGNL_RAW_SN non-null)·반려·유예 경과·<검수 승인 이력 없음>을 모두 충족한 것만이며, 하나라도 빠지면 원본이나 이미 관제에 통지된 파생이 지워지므로 조건을 서비스 레이어뿐 아니라 <최종 DELETE SQL 자체에 리터럴로> 박아 검사~삭제 사이 창을 닫고(조회로 걸러 두고 지우면 그사이 상태가 바뀐다), ★검수 승인 이력이 있는 파생은 제외한다(ADR-045) — 「검수 완료·통지 건에 대한 관제 접근은 무조건 보장한다」는 구속 정책이 근거이며 이미 통지된 파생을 지우는 것은 비가역이다. NEW_RAW_SN 이 NULL 인 그랜드퍼더링 증강은 실삭제 대상에서 완전 제외한다(어느 파생을 지워야 하는지 알 수 없고 시각 기반 역추정은 다른 요청의 파생본을 지운다). 삭제 순서는 DB 커밋 먼저 → 그다음 파일이며, 배치는 원자 클레임(조건부 UPDATE)으로 중복 실행을 막고 최종 DELETE 에도 조건을 다시 건다(클레임 이후 복구가 끼어들 수 있다). [복구] POST /v1/augments/{id}/restore 는 폐기 표식 해제에 그치지 않고 <반려 자체를 되돌려> 검수를 재오픈한다(표식만 지우면 리뷰가 REJECTED 로 남아 목록에 계속 안 보이는 반쪽 복구가 된다). '재결정 금지' 불변식을 여는 것이므로 되돌린 이력(누가·언제·왜)을 반드시 남긴다. 유예가 지나 실삭제된 항목은 복구할 수 없고 증강을 다시 요청해야 한다.
