# 증강 '생성 결과' 축과 '검수 결정' 축 분리 + 미사용 파생 폐기(소프트삭제 → 유예 후 실삭제)

## context

한 컬럼(LS_DATA_AUG.AUG_PROC_STTS_CD)에 두 주체가 쓰고 있었다. 외부 증강 웹훅은 생성 성공 시 이 컬럼을 ACCEPTED 로 전이시키는데, 검수 상태 전이는 PENDING 에서만 허용된다. 외부 증강은 웹훅이 항상 먼저 도착하므로 REVIEWER 의 승인·반려가 영구히 409('이미 처리된 증강 결과입니다')로 막혀 있었다 — 즉 사용/폐기 워크플로 자체가 도달 불가였다. 기존 테스트는 증강 행을 PENDING 으로 심어놓고 승인을 호출해 이 조합을 한 번도 통과시키지 않아 커버리지 밖이었다. 또 증강 결과를 반려해도 파생 영상과 생성 파일이 그대로 남아 저장소를 잠식했다.

## deciders

- 프로젝트 PM (ck.park)

## decision

### chosen_option

축 분리 + 소프트삭제 후 유예 경과 시 실삭제(채택)

### justification

① 축 분리 — AUG_PROC_STTS_CD 는 생성 결과 전용(웹훅 소유: 성공 ACCEPTED / 실패 REJECTED / 취소 CANCELED)이고, REVIEWER 의 사용·폐기 결정은 LS_DATA_AUG_RVW.RVW_STTS_CD 가 단독으로 소유한다(검수자·검수일시·반려사유 동반). 증강 검수의 승인·반려 처리는 생성 결과 컬럼의 상태 전이를 호출하지 않고 리뷰 행만 쓴다. 두 축을 다시 합치지 않는다. ② 등재 게이트 — '승인되어야 작업목록·배정에 등재' 판정은 RVW_STTS_CD='ACCEPTED' 로 한다. 단 해상도 파생(RESL_*)은 내부 생성물이라 accept/reject 가 차단돼 리뷰 행이 영영 생기지 않으므로 게이트 통과 예외를 명시적으로 박는다(빼면 해상도 파생이 전부 목록에서 사라진다). 게이트 도입 이전 파생은 매핑 컬럼(NEW_RAW_SN, V155)도 리뷰 행도 없어 무조건 미등재로 판정되므로 그랜드퍼더링한다(이미 배정된 WORKER 의 영상이 화면에서 사라져 고아 배정이 되는 것을 막는다). ③ 폐기 — 반려 시 즉시 작업 대상에서 빠지고, 유예기간(설정값, 기본 7일) 경과 후 배치가 DB 행과 생성 파일을 지운다. 삭제 대상은 파생 영상(ORGNL_RAW_SN IS NOT NULL) · 반려 · 유예 경과를 모두 충족해야 하며, 검수 승인 이력이 있으면 대상에서 제외한다(관제 접근 보장 정책). 조건을 서비스뿐 아니라 최종 DELETE SQL 자체에 리터럴로 박아 검사~삭제 사이 창을 단일 문장으로 폐쇄한다. 원본 rawSn 만 받는 삭제 메서드는 만들지 않는다. 유예기간 하한 검증을 기동 가드로 걸어 0·음수·파싱 실패면 기동을 실패시킨다(파괴적 기능이 fail-open 되면 '반려 즉시 실삭제'로 전락한다). ④ 복구는 반려 자체를 되돌린다 — 폐기 표식 해제 + 리뷰 재오픈으로 다시 채택/반려를 고를 수 있게 하고, '재결정 금지' 불변식을 여는 조치이므로 되돌린 이력(누가·언제·왜)을 반드시 남긴다. ⑤ 안전 규약 — NEW_RAW_SN 이 NULL 인 그랜드퍼더링 증강은 실삭제 대상에서 완전 제외한다(시각 기반 역추정은 중복 요청 허용 이후 다른 요청의 파생본을 지운다). 파일 삭제는 저장소 하위경로 정책으로 실경로를 검증하고 그 실경로로 지우며(lexical 검증+lexical 삭제는 심링크 교체로 원본이 삭제된다 — CWE-59/367), 판정이 OK 가 아니면 건너뛰고 WARN 한다(원본 삭제보다 고아 파일 존치가 안전). 삭제 순서는 DB 커밋 뒤 파일이다.

## consequences

### risks

- 실삭제 조건(파생 영상 · 반려 · 유예 경과 · 검수 승인 이력 없음) 중 하나라도 빠지면 원본이 지워진다 — 조건을 최종 DELETE SQL 에 리터럴로 박고 배치는 원자 클레임 후에도 조건을 다시 건다(클레임 이후 복구가 끼어들 수 있음)
- LS_DATA_LBL·LS_DATA_AUG_LBL_MAP·LS_DATA_LBL_HSTRY·LS_DATA_AUG_RVW 는 FK 가 없거나 부모를 가리켜 CASCADE 로 정리되지 않는다 — 명시적으로 지우지 않으면 FK 위반 없이 조용히 고아가 남는다
- ⚠ LS_LABEL_ATTR 은 삭제 대상이 아니다 — 라벨 마스터의 속성 '정의'이고 FK 는 LABEL_ID→LS_LABEL(V33)이다. 데이터 라벨을 참조하는 것은 LS_DATA_LBL_ATTR_VAL 이다. 폐기 배치가 이를 지우면 프로젝트 전체의 라벨 속성 정의가 사라진다(회귀 가드 존재)
- Quartz 클러스터링은 트리거 중복만 막고 잡 내부 레이스는 막지 않는다 — 원자 클레임(조건부 UPDATE) 별도 필요

### negative

- AUG_PROC_STTS_CD 를 '검수 상태'로 읽던 코드·화면·통계를 전부 리뷰 축으로 이동해야 함
- 해상도 파생 예외를 누락하면 해상도 파생이 작업목록에서 전부 사라짐
- 그랜드퍼더링 구간(NEW_RAW_SN NULL)은 자동 정리가 불가해 수동 정리 대상으로 남음

### positive

- 증강 검수 승인·반려가 실제로 동작(기존엔 외부 웹훅이 먼저 ACCEPTED 로 전이시켜 영구 409 였다)
- 생성 결과와 사람의 채택 여부가 별도 컬럼으로 구분돼 통계·화면이 정확해짐
- 반려 파생의 저장소가 유예 후 회수되면서도 기간 내 복구 가능

## considered_options

### 단일 컬럼 유지 + 전이 규칙 완화

**cons**:

- '생성 성공'과 '사람이 채택함'이 같은 값으로 섞여 구분 불가
- 등재 게이팅을 이 컬럼으로 하면 생성 성공만으로 전부 통과해 기능이 무의미해짐
- 웹훅과 사람의 쓰기 경합이 그대로 남음

**pros**:

- 스키마 변경 없음

- **description**: AUG_PROC_STTS_CD 하나로 생성·검수를 계속 표현하되 ACCEPTED 에서도 검수 전이를 허용한다.

### 반려 즉시 실삭제

**cons**:

- 오조작·오판 시 복구 불가(비가역)
- 관제에 이미 통지된 건이 사라질 수 있음

**pros**:

- 저장소 즉시 회수
- 구현 단순

- **description**: REVIEWER 가 반려하면 파생 행과 파일을 즉시 지운다.

### 축 분리 + 소프트삭제 후 유예 경과 시 실삭제(채택)

**cons**:

- 테이블 1종·컬럼 1개 신설
- 실삭제 배치의 조건 판정을 틀리면 원본이 지워질 수 있는 고위험 경로

**pros**:

- 두 주체가 각자 자기 컬럼만 쓰므로 경합 소멸
- 검수 워크플로가 실제로 동작
- 유예 기간 내 복구 가능
- 저장소도 결국 회수됨

- **description**: 생성 결과는 AUG_PROC_STTS_CD(웹훅 소유), 사용/폐기 결정은 LS_DATA_AUG_RVW.RVW_STTS_CD(REVIEWER 소유)가 단독으로 갖는다. 반려된 파생은 즉시 목록에서 빠지고(등재 게이트가 리뷰 축이라 자동), 폐기 원장(LS_DATA_AUG_DSCD)에 기록한 뒤 유예기간이 지나면 배치가 DB 행과 생성 파일을 지운다.
