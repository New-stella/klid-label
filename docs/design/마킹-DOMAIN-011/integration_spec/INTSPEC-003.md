## change_summary

KLID 연동 API v1.2.0(개정일 2026-09-07) + 벤더 가이드 회신에 맞춰 위탁 규격을 개정했다. ⚠ 규격서 파일명 접미가 `_pre` 라 사전배포판일 가능성이 있어 벤더 확답 대기이며 그 단서를 본문 근거 표기에 남겼다.

① **추가 질문 축의 창구 교체** — `POST /v1/videovlm-klid/describe-sub` → `POST /v1/videovlm-klid/custom`(벤더 회신: "describe-sub 대신 custom 을 사용하시면 됩니다"). 묘사 축은 `event_type` 필수, 추가 질문 축은 `event_type` 을 보내지 않고 질문 문구를 `prompt`(최상위·문자열·최대 4,000자)에 직접 싣는다. 나머지 요청 형식(`request_id`·`callback_url`·`media`+`frame_policy`)은 두 축이 같다. 이 전환으로 추가 질문 축에서 `event_type` 미수신·미지원으로 인한 4xx 가 구조적으로 사라진다(묘사 축에는 그대로 남는다). `describe-sub` 는 벤더가 계속 제공하므로 삭제하지 않고 [폐기] 행으로 남겼고, 이미 그 창구로 받아 적재된 결과와 원장의 채널 식별자 문자열은 바꾸지 않는다 — 창구가 바뀐 것이지 축이 바뀐 것이 아니며 그 값은 콜백 역조회 키이자 미결 회수 대상 목록이다.

② **미결 4항목이 닫혔다.** 이전 개정이 벤더 회신 대기로 남겨 둔 넷 — 필드명·타입·위치=`prompt`/문자열 4,000자/최상위 · 받는 창구=`custom` · 미전송 시 기본 동작=해당 없음(필수) · 문구인지 식별자인지=문구. 함께 "첫 번째가 아닌 질문을 고르면 기록된 질문과 벤더가 실제로 쓴 질문이 달라진다"는 인지·수용 위험도 닫혔다.

③ **질문 문구 조달·보관 신설.** 조달 시점이 콜백 이후에서 **위탁 시점**으로 옮겨진다. 마킹 선택값이 1순위, 없거나 그 유형 소속이 아니면 그 유형의 첫 번째이며, 검증 이벤트 유형이 미수신이어도 마킹 선택값이 있으면 그 질문을 쓴다. 위탁 시점에 조달한 **문구 전문**을 멱등 원장 행에 보관하고 콜백 시점에는 재조달하지 않고 그 값을 읽는다 — 질문 목록은 전체 교체로 저장되며 가리키던 행이 사라지는 것이 정상 동선이라 재조달하면 보낸 질문과 기록된 질문이 갈린다. 식별자가 아니라 문구 전문을 보관한다. 조달이 비면 추가 질문 축만 건너뛰고 묘사 축은 정상 위탁한다.

④ **`event_type` 조달 순서 명시** — 관제 인입 값 → 마킹에서 작업자가 고른 값 → `null`. 관제가 유형을 보내지 않는 영상은 작업자가 마킹 화면에서 직접 고른다(관제 값이 없을 때만 노출). `null` 폴백과 "우리 허용목록으로 사전 차단하지 않는다"는 그대로 유지한다.

⑤ **인증 신설** — 서버에 API 키가 설정된 경우 위탁 2종은 `X-API-Key: <키>` 필수이며 `Bearer ` 접두를 쓰지 않는다. 조회용 GET 은 키 없이 호출 가능. 기존 `Authorization: Bearer` 기재는 v1.1.0 에 인증 절 자체가 없었으므로 **규격 근거가 없던 것**이라 폐기 표기했다. 401 은 **콜백이 전송되지 않아 위탁이 아무 신호 없이 사라지며 회수가 재위탁해도 같은 401 이라 회복되지 않는다**는 함의를 명시했다. 키 사용 여부·값은 규격 밖 별도 전달이며 미수신이라 §12 확인 대기로 뒀다.

⑥ **`frame_policy.mode` 는 `frame_interval`·`frame_selected` 둘뿐**이다(`uniform` 벤더 삭제 — 두지 않는다). 정의되지 않은 mode 는 400. `frame_policy` 는 `custom` 에도 적용되며 두 창구가 같은 조립 로직을 쓴다. 조립 규칙(정렬·중복제거·음수 제거·상한 600 절단·빈 목록 금지·파싱 실패는 frame_interval 폴백·선커밋 이전 조립)은 무변경이고 `framerate` 는 되살리지 않는다.

⑦ **오류 재구성** — 401·40001 신설, 기존 400·415·429·503 유지. **재시도 대상은 429 하나뿐**이며 이 분류를 바꾸지 않는다. 40001 은 정의되지 않은 `event_type` 에 한해 본문에 code 를 실어 주며 **적용 축은 묘사 하나**다(custom 은 event_type 미전송이라 나올 수 없다). 이 코드가 미지원 event_type 판별의 단일 근거다.

⑧ **처리 제한·허용 확장자 절 신설** — 영상 4GB / 이미지 64MB / prompt 4,000자 / selected_frames 600 / 동시 32건 / 분석 900초. 900초의 기준을 "추론 대기·수행 구간"으로 정정했고, 프레임 추출 시간은 별도로 더해지며 저작도구 콜백 대기 창은 이와 다른 것을 재는 별개 값이라 900초로 좁히면 안 됨을 명시했다. 허용 확장자(mp4·avi·mov·mkv·webm)를 적되 **저작도구는 위탁 전 확장자 게이트를 두지 않는다** — 벤더 목록의 사본이 두 번째 진실원이 되어 벤더가 목록을 넓힐 때 정상 위탁을 우리가 먼저 막기 때문이며, 이벤트 유형 허용목록 폐기와 같은 축이다.

⑨ **연동 범위는 넓히지 않는다** — 분석 창구는 describe·custom 둘, 사전 확인 GET /status. verify(판정) 미연동 확정이 유지되며 **custom 을 여는 것이 verify 를 열 근거가 아님**을 명시했다. `media.type: "image"` 도 미연동.

판번호·시행일을 v1.1.0 / 2026-08-13 → **v1.2.0 / 2026-09-07** 로 올리고 **제목의 판번호도 함께** 고쳤다. 기존 절은 하나도 지우지 않았고 §6(처리 제한·허용 확장자)·§12(확인 대기) 두 절이 신설되며 뒤 절 번호가 밀렸다.

# VLM 시계열 위탁 요청 규격 (저작도구 아웃바운드)

> 근거: 외부 벤더 확정 규격 『KLID 연동 API v1.2.0』(개정일 2026-09-07, IntelliVIX Video VLM) + 벤더 가이드 회신 — *"결론적으로 describe-sub 대신 custom 을 사용하시면 됩니다."*
> ⚠ **규격서 파일명 접미가 `_pre` 라 사전배포판일 가능성이 있다(벤더 확답 대기).** 확답 전까지 이 규격을 확정본으로 인용할 때는 그 단서를 함께 남긴다.
> 저작도구가 마킹 완료된 비식별 영상의 시계열 서술 생성을 벤더에 위탁한다. 짝 콜백 = INT-003 / INTSPEC-002.
> 위탁은 **묘사(CoT)** 와 **추가 질문(VQA)** 두 창구로 **이중 위탁**한다. 이벤트 판정(verify) endpoint 는 연동하지 않는다.
> ★ **`custom` 창구를 여는 것이 `verify` 를 열 근거가 아니다.** 두 창구는 서술을 받는 축이고 verify 는 판정을 받는 축이다. 판정 창구만 제공하는 값이 우리 확정 경로(화면 확정·산출물·데이터마트) 어디에도 쓰이지 않는다는 미연동 근거는 이번 개정으로 바뀌지 않는다.

## 1. 엔드포인트

| 용도 | Method | Path | 비고 |
|------|:---:|------|------|
| 묘사(CoT) 위탁 | POST | `/v1/videovlm-klid/describe` | 이벤트 관점에서 영상 상황(장소·환경·상황)을 서술한다. `event_type` **필수** |
| 추가 질문(VQA) 위탁 | POST | `/v1/videovlm-klid/custom` | 이벤트 발생 여부와 근거를 서술한다. `event_type` 을 **보내지 않고** 질문 문구를 `prompt` 에 직접 싣는다 |
| 지원 이벤트 조회 | GET | `/v1/videovlm-klid/events` | 묘사 창구의 `event_type` 가용 목록 |
| 서버 상태 조회 | GET | `/v1/videovlm-klid/status` | `ready` / `busy` / `loading` |
| [폐기] 추가 질문 위탁 | POST | `/v1/videovlm-klid/describe-sub` | **연동 대상으로 두지 않는다.** 벤더는 이 창구를 계속 제공하나 저작도구는 `custom` 으로 대체했다(벤더 가이드 회신). 이 경로로 보내지 않는다 |

| 항목 | 값 |
|------|-----|
| base-url | 장비 원장에서 고른 **시계열 유형 장비의 주소**. 배포 설정값 `vlm.client.url` 은 그 유형의 장비가 하나도 없을 때 첫 행을 심는 **씨앗**으로만 쓰인다 — 조달 규칙은 §9 |
| Content-Type | application/json (위탁 2종). 다른 타입은 벤더가 `415` 로 거부한다 |
| 인증 | 서버에 API 키가 설정된 경우 분석 요청(위탁 2종)은 **`X-API-Key: <발급받은 키>` 필수**. **`Bearer ` 접두를 쓰지 않는다.** 조회용 GET(`events`·`status`)은 키 없이 호출 가능 |
| 타임아웃 | HTTP 클라이언트 `vlm.client.timeout-seconds` 기본 10s. 배치 단계는 응답을 기다리지 않고 제출만 개시한다(구 45초 블로킹 폐기 — 외부가 느려지면 배치 풀이 통째로 마른다) |

> ⚠ **구 서술 폐기 — 인증**: `vlm.client.token` 설정 시 `Authorization: Bearer <token>` 을 조건부 부착한다는 기재는 **규격 근거가 없던 것**이다. v1.1.0 에는 인증 절 자체가 없었고, v1.2.0 §2.1 이 신설한 방식은 `X-API-Key` 헤더다. Bearer 접두를 되살리지 말 것.
> ⚠ **구 규격 폐기 — 창구**: 단일 위탁 endpoint `POST /v1/videovlm/verify`(『Video VLM API v2.0.1』 기준, 일치도+서술 1회 회신)는 연동 대상이 아니다. 그 경로로 보내지 않는다.

## 2. 요청 바디

공통 골격은 두 창구가 같다 — `request_id` · `callback_url` · `media`(+`frame_policy`). 다른 것은 경로와, **이벤트 유형을 싣는가 질문 문구를 싣는가**뿐이다.

### 2.1 묘사 — `POST /v1/videovlm-klid/describe`

```json
{
  "request_id": "00000001",
  "event_type": "fall",
  "media": {
    "type": "video",
    "source_type": "path",
    "path": "/data/videos/deid_sample.mp4",
    "frame_policy": { "mode": "frame_selected", "selected_frames": [0, 10, 13, 970] }
  },
  "callback_url": "http://저작도구/v1/vlm/callback"
}
```

### 2.2 추가 질문 — `POST /v1/videovlm-klid/custom`

```json
{
  "request_id": "00000002",
  "prompt": "영상에 쓰러진 사람이 있는가? 있다면 그렇게 판단한 근거를 함께 서술하라.",
  "media": {
    "type": "video",
    "source_type": "path",
    "path": "/data/videos/deid_sample.mp4",
    "frame_policy": { "mode": "frame_selected", "selected_frames": [0, 10, 13, 970] }
  },
  "callback_url": "http://저작도구/v1/vlm/callback"
}
```

- 한 영상에 대해 두 창구를 **각각 별도 `request_id` 로** 위탁한다. 콜백 바디에는 어느 창구의 결과인지 알려주는 식별자가 없으므로 수신 측은 `request_id` 로 역조회해 위탁 종류를 구분한다. **같은 값을 쓰면 역조회가 한쪽을 덮어 결과가 유실된다.**
- ★ **`custom` 은 `event_type` 을 보내지 않는다** — 지원 이벤트 목록과 무관하게 호출할 수 있다. 그 결과 **추가 질문 축에서는 `event_type` 미수신·미지원으로 인한 4xx 가 구조적으로 사라진다.** 묘사 축에는 그대로 남는다.

## 3. 동기 응답 (벤더 → 저작도구)

```json
{ "request_id": "00000001", "status": "accepted" }
```

- 접수만 의미한다. `accepted` 만 정상으로 인정하며, 결과 상세는 `callback_url`(INT-003, `/v1/vlm/callback`)로 별도 콜백된다. 두 창구 모두 판정 없이 서술만 회신한다.

## 4. 필드 정의

| 필드 | 타입 | describe | custom | 설명 |
|------|------|:---:|:---:|------|
| request_id | String | 필수 | 필수 | 위탁 상관관계 키. 콜백 request_id 로 회신되어 RAW_SN 및 위탁 종류(묘사 / 추가 질문) 매칭에 쓰인다 |
| event_type | String | 필수 | **미전송** | 검증 대상 이벤트 유형. 조달 순서는 §7 |
| prompt | String | **미전송** | 필수 | 질문 문구(자연어). **최대 4,000자.** 요청 본문 **최상위**에 싣는다 |
| media.type | String | 필수 | 필수 | image \| video (시계열은 video) |
| media.source_type | String | 필수 | 필수 | path \| upload (공유 경로 접근은 path) |
| media.path | String | 조건부 | 조건부 | source_type=path 시 필수. 비식별 영상 경로 |
| media.frame_policy | Object | 조건부 | 조건부 | media.type=video 시 필수 |
| media.frame_policy.mode | String | 필수 | 필수 | `frame_interval` \| `frame_selected` |
| media.frame_policy.selected_frames | Integer[] | 조건부 | 조건부 | mode=frame_selected 시 필수. 분석 대상 프레임 인덱스 배열. **상한 600**, 음수 불가 |
| callback_url | String | 필수 | 필수 | 결과(INT-003) 회신 URL |

- ★ **`mode` 는 `frame_interval` · `frame_selected` 둘뿐이다.** 구 규격의 `uniform` 은 벤더가 삭제해 **두지 않는다.** 정의되지 않은 mode 는 `400` 으로 거부된다.
- ★ **`frame_policy` 에 추출 간격(`framerate`) 필드를 두지 않는다.** 연동 시스템이 지정하는 것은 `mode` 뿐이고 프레임 추출 간격·장수의 세부값은 벤더 서버가 관리한다. 규격에 그 필드가 없으므로 되살리지 말 것.
- ★ **`frame_policy` 는 `custom` 에도 그대로 적용된다**(영상일 때 필수). 두 창구가 **같은 조립 로직**을 쓴다.
- ★ **`selected_frames` 상한은 600 이다.** 구 규격의 상한 8 과 그에 딸린 sliding window(window=stride=8) 분할 서술은 폐기됐다.

## 5. 위탁 전 사전 확인

- `GET /v1/videovlm-klid/status` 로 서버 처리 가능 여부(`ready` / `busy` / `loading`)를 확인한다. 미준비 상태는 `503` 으로 거부된다. 저작도구가 이 값을 어떻게 쓰는지는 §5.1 이 정한다.
- `GET /v1/videovlm-klid/events` 로 해당 `event_type` 의 묘사 창구 가용성을 확인한다. **이 확인은 묘사 축 한정**이다 — `custom` 은 이벤트 목록과 무관하게 호출할 수 있다.

### 5.1 ★ 저작도구가 이 상태 창구를 어떻게 쓰는가

> 이 절은 벤더가 정한 규격이 아니라 **우리가 그 값을 어떻게 쓰는지**를 정한 것이다. §1 의 엔드포인트 표와 위 두 줄은 벤더가 소유한 규격이고, 이 절은 그 값의 **소비 규칙**이다. 두 층을 섞지 말 것 — 이 절을 근거로 벤더 규격을 고쳐 적지 않는다.

**같은 창구를 두 목적이 쓴다 — 목적이 다르면 한 번의 실패가 뜻하는 것도 다르다.**

| 목적 | 무엇을 하는가 | 한 번의 실패가 뜻하는 것 |
|------|------|------|
| 위탁 전 사전 확인 | 위탁을 보내기 직전에 서버가 지금 받을 수 있는지 본다 | **게이트가 아니다** — 한 번의 확인 실패로 그 위탁을 막지 않는다 |
| 장비 상태점검 | 장비 원장의 가용·이용불가 표식을 세운다 | **연속 실패 임계에 누적**되며, 임계를 넘으면 그 장비가 라우팅 후보에서 빠진다 |

⚠ **두 축을 섞지 말 것.** 사전 확인은 **그 위탁 한 건**을 두고 하는 판단이고, 상태점검은 **그 장비를 앞으로 후보에 둘지**를 두고 하는 판단이다. 사전 확인 실패를 곧바로 장비 배제로 옮기면 일시적인 미준비 한 번으로 그 유형의 장비가 사라지고, 반대로 상태점검 결과를 위탁 게이트로 삼으면 이미 후보에서 빠진 장비를 두고 같은 판정을 두 번 하게 된다.

**상태 값의 상태점검 축 매핑**

| 상태 값 | 뜻 | 상태점검 축 판정 |
|:---:|------|------|
| `ready` | 즉시 접수 가능 | **살아 있음** |
| `busy` | 접수는 되나 결과가 지연된다 | **살아 있음** — 이것은 **부하 축**이라 이 값으로 장비를 내리지 않는다 |
| `loading` | 준비 중이라 지금은 처리할 수 없다 | **살아 있지 않음** — 연속 실패로 센다 |

- ★ **`loading` 을 살아 있지 않음으로 세는 근거는 벤더가 스스로 처리 불가를 밝혔다는 것이다.** 응답이 도달했더라도 그 응답이 지금은 못 받는다고 말하고 있으므로 그대로 받아들이는 것은 오판이 아니다. 원장의 가용·이용불가가 재는 것은 「살아 있는가」가 아니라 **「지금 이 장비로 보내도 되는가」**이기 때문이다.
- ★ **`busy` 로는 내리지 않는다.** 부하로 장비를 내리면 포화를 이유로 멀쩡한 장비가 배제되고 남은 장비에 전부 몰리는 역효과가 난다. 살아 있는지와 여유가 있는지는 다른 축이며, 그 둘을 한 값에 엉키게 하지 않는 것이 이 매핑의 요지다.
- ★ **한 번의 `loading` 관측으로 장비가 내려가지 않는다** — 일시적인 처리 불가는 연속 실패 임계가 흡수한다.
- ★ **응답 본문을 버리고 「도달했으니 살아 있다」로 판정하지 말 것.** 이 매핑은 응답 **본문의 상태 값을 읽어야만** 성립한다. 도달 여부만 보면 `loading` 까지 살아 있음으로 세어져 준비되지 않은 장비로 위탁이 계속 나간다.
- ⚠ **오류표의 `503`(서버 미준비)은 위탁 축이며 이 절의 판정과 별개다.** 그것은 위탁 요청이 거부된 사실이고, 이 절이 정하는 것은 상태 조회 창구의 응답을 읽는 상태점검 축이다. 두 축이 같은 말(「미준비」)을 쓰더라도 재는 대상이 다르니 한 값으로 읽지 말 것.
- ⚠ **이 기준에는 사각이 남는다** — 벤더가 처리 불가를 밝히지 않은 채 응답만 돌려주면서 실제로는 위탁을 처리하지 못하는 상태는 살아 있음으로 세어진다. 알아낼 수단이 없어 인지·수용한 위험이며, 그런 상태는 상태점검이 아니라 **위탁 결과로 드러난다.**

## 6. 처리 제한 · 허용 확장자

| 항목 | 값 |
|------|-----|
| 업로드 영상 크기 | 4GB |
| 업로드 이미지 크기 | 64MB |
| `prompt` 길이 | 4,000자 |
| `selected_frames` 개수 | 600 |
| 동시 처리 | 32건 (초과 시 `429`) |
| 분석 제한 | 900초 |

- ★ **900초의 기준은 「추론 대기·수행 구간」이다.** 프레임 추출을 마치고 추론 대기열에 올라간 뒤부터 재며 **프레임 추출 시간은 별도로 더해진다.** 저작도구의 콜백 대기 창은 이 900초와 **다른 것을 재는 별개 값**이며 훨씬 길다. **900초를 전체 소요 상한으로 읽어 대기 창을 좁히지 말 것** — 그러면 정상 분석 중인 위탁을 우리가 먼저 미결로 회수한다.
- **허용 확장자**: 영상 `.mp4` `.avi` `.mov` `.mkv` `.webm`. 그 외는 `path`·`upload` 어느 방식이든 `400` 으로 거부된다.
- ★ **저작도구는 위탁 전 확장자 게이트를 두지 않는다.** 벤더 허용목록의 **사본을 우리가 들면 그 사본이 두 번째 진실원**이 되어, 벤더가 목록을 넓힐 때 정상 위탁을 우리가 먼저 막는다. 이벤트 유형 허용목록을 폐기한 것과 같은 축이며, 수용 여부는 **벤더 응답이 판정**한다.
- `media.type: "image"` 는 미연동이다 — `custom` 창구가 제공하는 기능이나 저작도구는 영상만 보낸다.

## 7. 저작도구 매핑 / 제약

- **media.path**: 비식별 영상 경로(`LS_DEIDENT_PROC_LOG.DE_IDNTF_FILE_PATH_NM`). 원본 미전송.
- **request_id**: 위탁 발급 상관관계 키. 콜백 수신 시 웹훅 멱등 원장으로 rawSn 과 위탁 종류를 역매핑한다(INTSPEC-002 §4).
  - ★ **원장의 채널 식별자 문자열은 이번 개정으로 바꾸지 않는다.** 바뀐 것은 **창구(경로)이지 축이 아니다.** 그 값은 이미 적재된 행의 콜백 역조회 키이자 미결 회수의 대상 목록이라, 바꾸면 기존 미결분이 회수 대상에서 사라진다.
  - ★ **이미 `describe-sub` 로 받아 적재된 결과는 보존한다** — 작업 결과이며 화면·산출물이 계속 읽는다. 삭제·숨김 대상이 아니다.
- **event_type 조달 순서 — 관제 인입 값 → 마킹에서 작업자가 고른 값 → `null`** (묘사 축 한정)
  - 관제가 검증 이벤트 유형을 보내지 않는 영상이 실재한다. 그런 영상은 **마킹 화면에 유형 선택이 노출되며, 작업자가 유형을 고르지 않으면 마킹을 완료할 수 없다**(관제 값이 있는 영상에는 그 선택 자체가 노출되지 않는다). 따라서 **마킹 화면을 거치는 경로에서는 이 값이 반드시 채워진다** — 고를 수 있는 값이 아니라 채워져야 하는 값이다.
    - **근거**: 위탁 본문에 싣는 질문 문구(`prompt`)는 어느 마킹 방식에서도 값이 있다 — 수동은 작업자가 직접 고르고, 자동은 그 이벤트의 첫 번째 질문이 자동 선택된다. 질문을 고르려면 유형이 먼저 정해져야 하므로, 유형 선택은 **질문이 성립하기 위한 전제**다.
    - 거부 방식은 완료 조작 자체를 막는 것이 아니라 **사유를 알리고 제출만 막는다**(화면 축 사항이라 상세는 화면 사양이 갖는다).
    - ⚠ **이 필수는 화면 축이다.** 마킹 등록 요청의 필수 항목 목록과 마킹 원장 유형 컬럼의 NULL 허용은 **어느 것도 올리지 않는다** — 관제 값이 있는 영상은 그 항목을 애초에 보내지 않으므로, 올리면 그 영상들의 마킹이 전량 거부된다.
  - **`null` 이 도달하는 범위** — 마킹 화면을 거치지 않는 경로와 **이미 저장된 기존 마킹 행**에서는 조달값이 비어 마지막 폴백에 도달한다. 즉 이 필수화로 폴백이 사라지는 것이 아니라 **도달 범위만 좁아진다.**
  - ⚠ **`null` 폴백을 없애지 말 것.** 조달값이 없으면 `null` 을 그대로 보낸다 — **값을 지어내지 않는다**가 확정 정책이다. 벤더 필수 필드라 4xx 가 예상되며 그 거부를 기록한다.
  - ⚠ **우리 허용목록으로 사전 차단하지 않는다.** 값이 우리가 아는 목록 밖이어도 조달값을 그대로 실어 위탁하며, 수용 여부는 **벤더 응답이 판정**한다.
- **selected_frames 조달**: 마킹 본문에서 프레임 인덱스를 얻으면 그것을 싣는다(수동이면 작업자가 지정한 프레임, 자동이면 간격으로 자동 선택된 프레임). **정렬·중복제거·음수 제거** 후 **상한 600 초과분은 절단**한다. 하나도 얻지 못하면 `frame_interval` mode 로 내리고 `selected_frames` 를 싣지 않는다 — **빈 목록은 규격 위반**이라 거부된다. 마킹 JSON 파싱 실패는 예외가 아니라 `frame_interval` 폴백이며, 요청 조립은 **선커밋 이전**에 끝낸다(선커밋 뒤에서 실패하면 상관키만 남은 영구 대기가 된다). 마킹 이벤트 컨텍스트(이벤트명·마킹 시점 배열)는 전송하지 않는다 — 마킹 결과는 `frame_policy` 로만 반영된다.
- **질문 문구(`prompt`) 조달·보관** (추가 질문 축 한정)
  - **조달 시점은 위탁 시점이다.** 종전에는 콜백 이후에만 조달했으나, `prompt` 를 채우려면 요청을 만드는 시점에 문구가 있어야 한다.
  - **조달 규칙**: 마킹에서 작업자가 고른 질문이 1순위, 없거나 그 유형 소속이 아니면 **그 유형의 첫 번째**. **검증 이벤트 유형이 미수신이어도 마킹 선택값이 있으면 그 질문을 쓴다.**
  - ★ **보낸 질문 = 기록된 질문**: 위탁 시점에 조달한 **문구 전문**을 멱등 원장 행에 보관하고, 콜백 시점에는 **재조달하지 않고 그 값을 읽는다.** 질문 목록은 **전체 교체로 저장**되며 가리키던 행이 사라지는 것이 **정상 동선**이라, 재조달하면 보낸 질문과 기록된 질문이 갈린다. 콜백이 요청 식별자로 그 행을 역조회하므로 보관 위치로 자연스럽고, **재위탁·도착 순서 문제가 구조적으로 해결된다.**
  - ⚠ **식별자가 아니라 문구 전문을 보관한다** — 가리키던 행이 사라지면 식별자로는 읽을 수 없다.
  - **조달이 비면 추가 질문 축을 건너뛴다** — 묘사 축은 정상 위탁한다.
  - ✅ **종전의 미결 4항목이 닫혔다.** `custom` 창구가 그 답이다.

    | 미결 항목 | 답 |
    |------|------|
    | 질문을 실을 필드명·타입·위치 | **`prompt`** · 문자열 **최대 4,000자** · 요청 본문 **최상위** |
    | 어느 창구가 받는지 | **`custom`** |
    | 미전송 시 벤더 기본 동작 | **해당 없음** — `custom` 은 `prompt` 가 **필수**다 |
    | 문구인지 식별자인지 | **문구**(자연어 질문) |

  - ✅ **인지·수용했던 잔여 위험이 닫혔다.** 종전에는 질문 문장을 실을 자리가 없어 *"첫 번째가 아닌 질문을 고르면 기록된 질문과 벤더가 실제로 쓴 질문이 달라진다"* 를 인지·수용한 위험으로 두었다. **이제 그 자리가 생겼고 보낸 문구를 그대로 보관하므로 그 위험은 닫혔다.**

## 8. 전송 항목

호출 주체는 시계열 위탁 배치 단계다. 이 규격이 정하는 전송 항목은 다음과 같다:

| 항목 | 규격 |
|------|------|
| endpoint | `/v1/videovlm-klid/describe` · `/v1/videovlm-klid/custom` (**이중 위탁**) |
| 상관관계 | `request_id`(바디) — 위탁 2건에 각각 별도 발급 |
| 영상 지정 | `media{type,source_type,path}` |
| 프레임 정책 | `frame_policy{mode, selected_frames}` — 두 창구 공통, 추출 간격 필드 없음 |
| 이벤트 유형 | `event_type` — **묘사 축만** 전송 |
| 질문 문구 | `prompt` — **추가 질문 축만** 전송(최대 4,000자) |
| callback_url | **필수 전송**(생략하지 않는다) |
| 동기 응답 | `request_id`+`status(accepted)` — `accepted` 만 정상으로 인정한다 |
| 사전 확인 | `GET …/status` · `GET …/events`(묘사 축 한정) |
| 인증 | `X-API-Key`(서버에 키가 설정된 경우 필수) — Bearer 접두 없음 |

## 9. ★ 목적지 조달 · 활성화 — 환경별 (INT-002 참조)

위탁 목적지는 **장비 원장에서 고른 시계열 유형 장비의 주소**다. 배포 설정값(`vlm.client.url`)은 그 유형의 장비가 하나도 없을 때 **최초 1회 씨앗**으로 원장에 첫 행을 심는 데만 쓰이며, 이미 있으면 값이 달라도 덮어쓰지 않는다.

⚠ **원장에 행이 없을 때 설정값으로 대신 호출하는 폴백은 두지 않는다** — 두면 진실원이 둘이 된다. 씨앗은 **원장에 행을 심는 것**이지 그 값으로 대신 호출하는 것이 아니다.

연동 여부를 설정으로 켜고 끄던 토글은 폐지됐다. **그 유형에 쓸 수 있는 후보가 하나도 없으면 위탁을 거부**하며 조용히 건너뛰지 않는다. 사유는 가리지 않는다 — 장비 식별자 형식 위반이든 상태점검 실패로 그 유형의 장비가 전부 이용불가가 된 것이든 같다. 벤더 미연동 구간의 운영은 검수자가 사유를 남기고 누르는 **시계열 묶음 스킵**(단건·일괄)으로 처리한다.

> ⚠ **구 서술 폐기(2026-09-08)** — *"base-url 은 `vlm.client.url` 이다"* · *"연동 주소가 주입되어 있지 않으면 위탁은 **실패**한다"* · *"stg·prd 는 실제 연동 주소 주입 필요"*. 셋 다 목적지를 단일 설정값으로 읽은 서술이라 더 이상 사실이 아니다. 거부를 정하는 것은 설정값의 유무가 아니라 **원장에 쓸 수 있는 장비가 있는가**이며, 설정값은 씨앗 축으로만 남는다.
> ⚠ **이번 정정의 대상은 「기준 주소를 어디서 조달하는가」 하나다.** 벤더가 소유한 창구 경로·요청 바디·동기 응답·필드 정의·오류표·처리 제한·콜백 규격은 **어느 것도 바뀌지 않았다.** 두 축을 섞지 말 것.
> ★ **「토글 폐지」 자체는 그대로 참이다** — 위 폐기 표기와 함께 지우지 말 것.

| 환경 | 연동 대상 |
|---|---|
| local | 목업 벤더 서버 |
| dev | 목업 벤더 서버 |
| stg | 실제 벤더 장비를 원장에 등록해야 한다 |
| prd | 실제 벤더 장비를 원장에 등록해야 한다 — 콜백 허용 출처 설정이 선행돼야 한다 |

## 10. ★ 신고 구간 위탁 보류

비식별 신고(`DE_IDNTF_YN='F'`) 구간에서는 시계열 위탁 배치 단계가 위탁 전송 자체를 그 단계 안에서 **보류(SKIPPED)** 한다 — 실패가 아니라 보류이며 `LS_BATCH_PROC_LOG` 에 사유가 적재된다. 신고 해소 시 `DeidentGateReopened`(EVT-007) 발행을 계기로 보류분을 재위탁한다. 위탁 2종은 같은 조건으로 함께 보류·재위탁된다.

## 11. 오류 · 신뢰성

| 코드 | 사유 | 재시도 |
|:---:|------|:---:|
| 400 | 요청 형식 위반(정의되지 않은 `mode`, 허용 밖 확장자, 필수 필드 누락 등) | ✗ |
| 401 | API 키 없음 · 불일치 | ✗ |
| 415 | 지원하지 않는 Content-Type | ✗ |
| 429 | 동시 처리 한도(32건) 초과 | **○** |
| 503 | 서버 미준비 | ✗ (사전 확인 대상) |
| 40001 | 정의되지 않은 `event_type` | ✗ |

- ★ **재시도 대상은 `429` 하나뿐이다.** 429 는 잠시 뒤 다시 보내면 되는 **일시 상태**이지 요청이 잘못된 것이 아니다. 나머지는 같은 요청을 다시 보내도 같은 결과라 비재시도로 분류해 재시도·서킷 집계에서 제외한다. **이 분류를 바꾸지 말 것.**
- ★ **`40001`**: 본문에 `{"code": 40001, "detail": "..."}` 형태로 회신된다(그 외 오류는 `detail` 만). **적용 축은 묘사(`describe`) 하나**다 — `custom` 은 `event_type` 을 보내지 않아 이 코드가 나올 수 없다. ★ **이 코드가 「미지원 `event_type` 판별의 단일 근거」다** — 우리가 목록 사본으로 미리 판정하지 않는 이유가 여기에 있다.
- ★★ **`401` 은 콜백이 전송되지 않는다.** 헤더가 없거나 키가 맞지 않으면 요청이 401 로 거부되고 **그 위탁은 아무 신호 없이 사라진다** — 수락 응답도 실패 콜백도 오지 않는다. 미결 회수가 재위탁해도 **같은 401 이라 회복되지 않는다.** 즉 키 설정이 곧 연동 성립 조건이며, 키가 틀린 채로 운영하면 위탁 전량이 조용히 유실된다.
- ★ **`503` 은 위탁 축이며 상태점검 축의 판정과 별개다.** 위탁 요청이 거부된 사실이지 그 장비의 상태점검 결과가 아니다. 상태점검은 §5.1 이 정한 대로 **상태 조회 창구 응답의 상태 값**을 읽어 판정한다. 위탁이 `503` 으로 거부된 것을 상태점검의 연속 실패로 옮겨 세지 않는다 — 두 축이 같은 말(「미준비」)을 쓰더라도 재는 대상이 다르다.
- Resilience4j Retry `vlmClient` 3회 / 1s / ×2 backoff.
- CircuitBreaker `vlmClient` — failure-rate 50% / sliding-window 10 / min-calls 5 / open 30s.
- 벤더 분석 제한은 **900초**이며(기준은 §6), 초과 시 결과가 아니라 실패 콜백으로 회신된다.
- 배치는 응답을 기다리지 않고 제출만 개시한다(논블로킹 제출). 응답 신호가 전혀 없어도 미결 스위퍼가 회수한다.
