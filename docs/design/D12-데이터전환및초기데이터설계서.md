## 1. 개요

### 1.1 목적

본 문서는 AI CCTV 학습데이터 저작도구(KLID-AT)의 데이터베이스 초기 구축 및 데이터 전환 계획을 기술한다. 관제서버 기존 DB(`klid_system`)에 저작도구 전용 스키마(`klid_at`)를 추가하는 구조이므로, 기존 MNG_* 공유 테이블의 데이터 전환은 불필요하고, 신규 LS_* 테이블의 스키마 생성 + 초기 코드성 데이터 INSERT가 핵심이다.

### 1.2 범위

| 구분 | 범위 | 비고 |
|------|------|------|
| 전환 대상 | LS_* 저작도구 전용 테이블 36개 신규 생성 | Flyway V0~V47 자동 마이그레이션 |
| 공유 대상 (전환 불필요) | MNG_* 관제서버 공유 테이블 9개 | READ 위주, JPA ddl-auto=validate |
| 초기 데이터 | 공통코드(CM_CODE), 시스템 설정(LS_SYSTEM_CONFIG), YOLO 파라미터, Quartz 초기 Job | Flyway INSERT IGNORE |
| 범위 외 | 데이터마트 → 포털 DB 적재 | 관제서버 책임 |
| 범위 외 | QRTZ_* 테이블 11개 | 기존 klid_system 공유, Quartz 자동 생성 |

## 2. 중점 목표와 구축 전략

### 2.1 중점 목표

1. **무중단 스키마 구축**: 관제서버 운영 중인 `klid_system` DB에 저작도구 전용 LS_* 테이블을 추가할 때, 기존 서비스에 영향 없이 구축한다.
2. **데이터 무결성 보장**: Flyway 마이그레이션의 버전 순서 보장 + JPA `ddl-auto=validate` 기동 검증으로 스키마-엔티티 정합성을 확보한다.
3. **롤백 가능성 확보**: 각 Flyway 마이그레이션은 `IF NOT EXISTS` / `INSERT IGNORE` 패턴으로 멱등성을 보장하고, 문제 발생 시 DB 백업 기반 롤백이 가능하도록 한다.
4. **초기 데이터 최소화**: 코드성(code) 데이터와 시스템 설정값만 초기 적재하고, 운영 데이터는 시스템 운영을 통해 자연 적재한다.

### 2.2 구축 전략

| 전략 | 설명 |
|------|------|
| Flyway 자동 마이그레이션 | Spring Boot 기동 시 `db/migration/V{N}__*.sql` 순차 실행 |
| 멱등성 보장 | `CREATE TABLE IF NOT EXISTS`, `INSERT IGNORE`, `MERGE INTO` 사용 |
| 환경별 분리 | local(H2), dev/stg/prd(MariaDB 10.11) — H2/MariaDB 호환 SQL |
| MNG_* 공유 테이블 보호 | 변경 시 관제서버팀 선승인 필수, JPA ddl-auto=validate 고정 |
| DB 백업 선행 | 마이그레이션 실행 전 전체 DB 스냅샷 필수 |

### 2.3 구축 방법

```text
[사전 준비]
1. klid_system DB 전체 백업 (mysqldump --single-transaction)
2. Flyway baseline 확인 (flyway_schema_history 테이블 존재 여부)

[스키마 구축]
3. Spring Boot 기동 → Flyway 자동 실행 → V0~V47 순차 적용
4. JPA ddl-auto=validate 기동 검증 → Entity-Schema 정합성 확인

[초기 데이터 적재]
5. Flyway V3 → CM_CODE 공통코드 4건
6. Flyway V11 → LS_SYSTEM_CONFIG 시스템 설정 테이블 + 시드
7. Flyway V17 → YOLO 파라미터 3건 시드
8. Flyway V19 → YOLO 기본값 갱신

[검증]
9. 테이블 생성 확인 (COUNT 45개)
10. 초기 데이터 건수 확인
11. FK/인덱스 정합성 확인
```

## 5. 전환 상세 절차

### 5.1 데이터 전환 작업순서

```text
단계 1: 사전 점검
  ├─ 1-1. klid_system DB 접속 확인 (192.168.102.101:13307)
  ├─ 1-2. MaxScale 라우팅 상태 확인
  ├─ 1-3. 관제서버 MNG_* 테이블 존재 및 데이터 건수 확인
  └─ 1-4. flyway_schema_history 테이블 존재 여부 확인

단계 2: DB 백업
  ├─ 2-1. mysqldump --single-transaction --all-databases (전체 백업)
  └─ 2-2. 백업 파일 무결성 검증 (checksum)

단계 3: Flyway 마이그레이션 실행
  ├─ 3-1. Spring Boot 애플리케이션 기동
  ├─ 3-2. Flyway V0~V47 순차 실행 (자동)
  ├─ 3-3. flyway_schema_history에 47건 이력 확인
  └─ 3-4. 오류 발생 시 → 단계 7(비상대책) 진행

단계 4: JPA 정합성 검증
  ├─ 4-1. Spring Boot ddl-auto=validate 기동 확인
  └─ 4-2. 엔티티-스키마 불일치 시 기동 실패 → 수정 후 재시도

단계 5: 초기 데이터 검증
  ├─ 5-1. CM_CODE 4건 확인
  ├─ 5-2. LS_SYSTEM_CONFIG 3건 확인
  ├─ 5-3. LS_* 테이블 36개 존재 확인
  └─ 5-4. FK/인덱스 정합성 확인 (SHOW CREATE TABLE)

단계 6: 운영 서비스 연동 확인
  ├─ 6-1. 관제서버 MNG_* 테이블 정상 조회 확인
  ├─ 6-2. MaxScale Read/Write Splitting 동작 확인
  └─ 6-3. 저작도구 API 헬스체크 (/actuator/health)
```

### 5.3 신구 데이터 매핑 작업

| 저작도구 테이블 (LS_*) | 참조 컬럼 | 관제서버 테이블 (MNG_*) | 참조 대상 | 매핑 유형 |

| LS_DATA_RAW | VMS_CCTV_ID | MNG_RESOURCE_CCTV | CCTV_ID | FK 참조 |
| LS_DATA_RAW | LCLGV_CD | MNG_LCLGV | LCLGV_CD | FK 참조 |
| LS_DATA_RAW | EVNT_TYPE_CD | MNG_EX_EVNT_TYPE | EVNT_TYPE_CD | FK 참조 |
| LS_DATA_LBL | REG_USER_NO | MNG_ACCT_USER | USER_NO | FK 참조 |
| LS_TASK_ASSIGNMENT | ASSIGNEE_USER_NO | MNG_ACCT_USER | USER_NO | FK 참조 |
| LS_TASK_ASSIGNMENT | ASSIGNER_USER_NO | MNG_ACCT_USER | USER_NO | FK 참조 |

### 6.1 신규 데이터 처리 방안

본 저작도구의 운영 데이터는 시스템 운영을 통해 자연 적재된다.

| 데이터 유형 | 적재 방식 | 비고 |
|---|---|---|
| 영상 (LS_DATA_RAW) | 관제서버 영상 인입 또는 포털 TUS 업로드 | 자동 |
| 프레임 (LS_DATA_SRC) | 배치 파이프라인 FFmpeg 추출 | 자동 |
| 라벨 (LS_DATA_LBL) | YOLO/SAM2 자동 라벨 + WORKER 수동 편집 | 자동+수동 |
| 메타 (LS_DATA_META) | VLM 콜백 적재 + REVIEWER 수동 입력 | 자동+수동 |
| 증강 (LS_DATA_AUG) | 외부 생성형 AI 콜백 | 자동 |
| 마킹 (LS_MARKING) | WORKER/REVIEWER 자동/수동 마킹 | 수동 |
| 검수 (LS_REVIEW) | REVIEWER 검수 승인/반려 | 수동 |
| 버전 (LS_LABEL_VERSION) | Gitea 자동 커밋 | 자동 |
| 통지 폴백 (LS_CONTROL_NOTIFY_FALLBACK) | 관제서버 통지 실패 시 자동 적재 | 자동 |

### 6.2 초기 데이터 수집 구축

| 데이터 | 수집 방법 | 적재 시점 | 건수 |
|---|---|---|---|
| CM_CODE 공통코드 | Flyway V3 | DB 초기 구축 시 | 4건 |
| LS_SYSTEM_CONFIG 설정 | Flyway V11+V17 | DB 초기 구축 시 | 3건 |
| 라벨 프리셋 (LS_LABEL_PRESET) | REVIEWER가 운영 화면에서 등록 | 서비스 오픈 후 | 수동 |
| 라벨 마스터 (LS_LABEL) | REVIEWER가 관리 화면에서 등록 | 서비스 오픈 후 | 수동 |
| QRTZ_* Quartz Job 정의 | Quartz 자동 등록 (Spring Boot 기동 시) | 기동 시 | 자동 |

> **라벨 프리셋 / 라벨 마스터**는 Flyway 시드가 아닌 운영 화면(SCR-LBL-PRESET-001, /manage/presets)을 통해 REVIEWER가 직접 등록한다. 이벤트 타입별 라벨 구성은 사업 요건에 따라 다르므로 코드 하드코딩하지 않는다.

### 6.3 데이터 전환 시 비상대책 안

| 상황 | 비상 대책 | 비고 |
|------|---------|------|
| Flyway 마이그레이션 중간 실패 | (1) 실패 SQL 확인 → (2) 수정 후 재실행, 또는 (3) DB 백업 복원 후 재시도 | Flyway 원자성: 실패 SQL 이전까지 적용됨 |
| MNG_* 공유 테이블 영향 발생 | (1) 관제서버팀 즉시 통보 → (2) 변경 롤백 → (3) 관제서버 서비스 확인 | 선승인 프로세스로 사전 방지 |
| JPA validate 기동 실패 | (1) Entity 불일치 확인 → (2) 핫픽스 마이그레이션 추가 → (3) 재기동 | ddl-auto=validate 고정 |
| 전체 롤백 필요 | (1) 서비스 중지 → (2) mysqldump 백업 파일 복원 → (3) flyway_schema_history 초기화 → (4) 재기동 | 최후 수단 |
| MaxScale 라우팅 오류 | (1) MaxScale 로그 확인 → (2) Read/Write 라우팅 재설정 → (3) DBA 확인 | Master-Slave 분리 |

### 6.4 Quartz 스케줄러 테이블 (QRTZ_*)

Quartz 스케줄러 테이블 11개(`QRTZ_JOB_DETAILS`, `QRTZ_TRIGGERS`, `QRTZ_SIMPLE_TRIGGERS`, `QRTZ_CRON_TRIGGERS`, `QRTZ_BLOB_TRIGGERS`, `QRTZ_FIRED_TRIGGERS`, `QRTZ_PAUSED_TRIGGER_GRPS`, `QRTZ_SCHEDULER_STATE`, `QRTZ_LOCKS`, `QRTZ_CALENDARS`, `QRTZ_SIMPROP_TRIGGERS`)는 기존 `klid_system` DB에 공유 운영 중이다.

- **전환 불필요**: Spring Boot Quartz 자동 설정(`spring.quartz.jdbc.initialize-schema=never`)으로 기존 테이블 사용.
- **초기 Job 정의**: 배치 파이프라인 Job (`LabelingBatchJob`)은 Spring Boot 기동 시 `@PostConstruct`에서 Quartz API를 통해 자동 등록된다.
- 기존 관제서버 Quartz Job과 `SCHED_NAME` + `JOB_GROUP`으로 격리한다.
