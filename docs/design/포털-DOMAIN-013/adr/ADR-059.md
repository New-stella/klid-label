# 증강 위탁에서 이벤트 유형을 걷어내고 증강 종류를 단일값으로 합친다

## context

증강 요청 화면은 요청자에게 두 가지를 물었다. 하나는 이벤트 유형(침수·산불)이고 다른 하나는 증강 종류 카드(겨울·야간·우천)다. 둘 다 우리 용도와 맞지 않는다.

[이벤트 유형 — 벤더 창구가 무엇을 만들지 정하는 값이다] 외부 생성형 AI 창구의 이미지 증강은 배경 이미지에 이벤트 장면을 만들어 넣는 작업이다 — 그 규격의 증강 예시는 입력이 배경 이미지이고 지시문이 「원본 카메라 시점과 도로 구조를 유지하고 비 오는 여름철 야간 도로 침수 장면으로 변경해줘」다. 그래서 이벤트 유형이 그 창구의 모든 조합에서 필수이며 허용 코드가 침수·산불 둘로 닫혀 있다. 우리 증강은 이미 이벤트가 담긴 영상 프레임을 겨울·야간·우천으로 바꾸는 것이고, 영상을 재생성하지 않고 프레임 이미지만 변환하며 라벨은 원본의 좌표를 그대로 승계한다 — 무슨 장면을 만들지 정할 필요가 없다.

[그런데 화면이 그 값을 사람에게 필수로 물었다] 우리 사업의 이벤트 유형 체계는 침수(범람)·산사태·화재·쓰러짐·파손·교통사고·싸움·흉기소지·납치(유괴)·그 외·배회처럼 넓은데 창구는 침수·산불 둘만 받으므로, 대응되지 않는 영상은 사실과 다른 값을 골라야 했다. 게다가 요청에 이벤트 유형 게이트가 없어 배회 영상에 산불을 붙여 위탁하는 것이 구조적으로 가능했다.

[증강 종류 — 카드가 생성 조건의 부분집합이다] 화면은 증강 종류 카드를 고르게 한 뒤 생성 조건(시간대·계절·날씨·지형·심각도)도 함께 받았다. 겨울은 계절, 야간은 시간대, 우천은 날씨라 카드가 생성 조건의 부분집합이고, 겨울을 고른 뒤 생성 조건에서 계절을 여름으로 바꿀 수 있어 둘이 어긋날 수 있었다.

## decision

### chosen_option

이벤트 유형은 서버 중립값 고정, 증강 종류는 단일값(채택)

### justification

두 가지를 함께 정한다.

[이벤트 유형은 요청자가 고르지 않는다] 이벤트 유형은 요청 본문에서 받지 않고 서버가 중립값 ETC 로 고정 송신한다. 세부 유형은 항상 전송하지 않는다(키 자체를 보내지 않는다). 벤더의 이미지 증강은 배경 이미지에 이벤트 장면을 만들어 넣는 작업이라 이벤트 유형이 무엇을 만들지 정하는 값이다. 우리 증강은 이미 이벤트가 담긴 영상 프레임을 겨울·야간·우천으로 바꾸는 것이고, 증강은 영상을 재생성하지 않고 프레임 이미지만 변환하며 라벨은 원본의 좌표를 그대로 승계한다 — 그 값은 우리 용도의 입력이 아니다. 세부 유형은 침수 전용이라 중립값에서는 성립하지 않는다.

⚠ ETC 는 벤더와 협의가 끝난 값이나 우리가 가진 규격서 판본에는 아직 없다 — 그 판본은 이벤트 유형 허용 코드를 침수·산불 둘로 적고 그 밖의 값에 오류 코드를 규정한다. 개정판을 받으면 값과 오류 코드를 대조한다. 그때까지는 문서가 아니라 합의가 근거다. 이 단서를 지우면 다음 사람이 규격서만 보고 계약에 없는 값을 보낸다며 되돌린다 — 그 되돌림을 막는 것이 이 기록의 목적이다.

[증강 종류는 단일값으로 합친다] 처리 종류는 증강 AI 와 해상도 변경이며 증강 종류 코드는 단일값 AUGMENT 다. 무엇으로 바꿀지는 생성 조건(시간대·계절·날씨·지형·심각도)이 정한다. 증강 축의 코드값은 단일 상수 AUGMENT 로 고정하며 생성 조건에서 파생하지 않는다 — 그 값이 유형 판정에 흘러가면 경로 순회·RESL_ 네임스페이스 침범이 열린다. 단일 상수로 고정하는 것이지 조건에서 유도하는 것이 아니다.

구 WINTER/NIGHT/RAIN 은 이미 만들어진 파생본에 남아 있어 보존한다(백필하지 않는다) — 조회·표시 경로는 옛 값과 새 값을 모두 견뎌야 한다. 조회 계약의 값 집합도 확장이지 교체가 아니다 — 옛 값을 빼면 이미 있는 파생본을 표현하지 못한다.

[요청 채널은 그대로다] 요청 채널은 저작도구로 유지한다 — 이 값은 어느 채널에 배포된 것인가가 아니라 누가 요청을 보내는가를 가리키며, 포털 경로가 나중에 붙어도 같다.

## consequences

### risks

- ETC 는 합의가 근거이고 우리가 가진 규격서 판본에는 없다. 개정판을 받기 전까지는 문서로 대조할 수 없으며, 개정판에서 값이나 오류 코드가 다르면 위탁이 거부된다
- 이 결정 기록이 없으면 다음 사람이 규격서만 보고 계약에 없는 값을 보낸다고 판단해 이벤트 유형 입력을 되살린다
- 구 코드값을 백필하지 않으므로 옛 값을 다루지 않는 조회 경로가 생기면 기존 파생본이 표현되지 않는다

### neutral

- 해상도 파생(RESL_ 접두)은 이 결정의 대상이 아니다 — 외부 위탁이 없는 내부 리스케일이라 축이 다르다
- 요청 채널 값은 무변경이다 — 포털 경로가 나중에 붙어도 같다
- 생성 조건과 자유 지시문의 축은 무변경이다

### negative

- 사업 요구사항이 명시하는 겨울·야간·우천을 표현하는 자리가 종류 코드에서 요청 시 보관되는 생성 조건 원문으로 옮겨간다 — 그 겨울·야간·우천은 생성 조건 프리셋으로 제공한다
- 증강 종류 코드가 단일값이라 코드만으로는 파생본을 서로 구분할 수 없다 — 구분 축은 생성 조건 원문이다
- 조회·표시 경로가 옛 코드값과 새 코드값을 함께 다뤄야 한다

### positive

- 요청자가 사실과 다른 이벤트 유형을 고르는 자리가 사라진다
- 무엇으로 바꿀지를 정하는 축이 생성 조건 하나가 되어 종류 카드와 생성 조건이 어긋날 수 있던 자리가 없어진다
- 이벤트 유형 게이트 없이 대응되지 않는 유형을 붙여 위탁하던 경로가 닫힌다
- 지형·심각도처럼 종류 카드로 표현되지 않던 축까지 요청에 실린다

## considered_options

### 영상의 이벤트 유형에서 서버가 변환(기각)

**cons**:

- 우리 유형 체계와 창구의 허용 코드가 대응하지 않아 변환이 곧 추정이 된다
- 대응되지 않는 유형의 영상은 어느 값으로 보낼지 정할 근거가 없다

**pros**:

- 요청자가 고르지 않아도 된다
- 값이 영상의 사실에서 나온다

- **description**: 요청자에게 묻지 않고 영상이 이미 가진 이벤트 유형 코드를 서버가 창구의 허용 코드로 바꿔 싣는다.

### 증강 대상을 침수·화재 영상으로 제한(기각)

**cons**:

- 사업 목표(겨울·야간·우천 증강)와 부딪힌다
- 나머지 이벤트 유형의 영상이 증강에서 통째로 빠진다

**pros**:

- 이벤트 유형이 항상 영상의 사실과 맞는다

- **description**: 창구의 허용 코드에 대응하는 이벤트 유형의 영상만 증강 대상으로 삼는다.

### 종류 카드는 남기고 생성 조건만 제거(기각)

**cons**:

- 생성 조건이 더 넓은 표현력을 갖는데 좁은 쪽을 남기게 된다
- 지형·심각도처럼 카드로 표현되지 않는 축이 사라진다

**pros**:

- 요청 화면이 단순해진다
- 사업 요구사항이 명시하는 겨울·야간·우천이 종류 코드에 그대로 남는다

- **description**: 겨울·야간·우천 카드를 그대로 두고 생성 조건을 걷어내 입력을 하나로 줄인다.

### 이벤트 유형은 서버 중립값 고정, 증강 종류는 단일값(채택)

**cons**:

- ETC 는 합의가 근거이고 우리가 가진 규격서 판본에는 아직 없다
- 사업 요구사항이 명시하는 겨울·야간·우천을 표현하는 자리가 종류 코드에서 생성 조건 원문으로 옮겨간다
- 종류 코드만으로는 파생본을 서로 구분할 수 없다

**pros**:

- 요청자가 사실과 다른 값을 고르는 자리가 사라진다
- 두 입력이 어긋날 수 있던 자리가 없어진다
- 지형·심각도처럼 종류 카드로 표현되지 않던 축까지 요청에 실린다

- **description**: 이벤트 유형은 요청 본문에서 받지 않고 서버가 중립값 ETC 로 고정 송신하며 세부 유형은 항상 전송하지 않는다. 증강 종류 코드는 단일값 AUGMENT 로 합치고, 무엇으로 바꿀지는 생성 조건이 정한다.
