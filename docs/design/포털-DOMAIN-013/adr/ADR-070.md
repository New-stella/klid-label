# 임베드에서 문서 전역 상태의 소유권 — Remote 는 자기가 건 것만 되돌린다

## context

포털 화면 안에 저작도구 화면을 런타임으로 얹는 임베딩([[INT-013]])에서는 두 화면이 하나의 브라우저 문서를 함께 쓴다. 그래서 저작도구가 문서 수준 상태를 바꾸면 그것이 Host 화면에 그대로 걸린다.

그 연동점은 「스타일 격리 규약」으로 Host 를 건드리지 않는 축을 이미 규정했으나 대상이 스타일(CSS)뿐이다. 화면이 실행 중에 문서에 남기는 상태 — 문서 수준 스크롤 잠금, 조작 불가 표식, 포커스, 전체화면, 히스토리 — 는 어느 항목도 소유하지 않았다.

2026-09-16 개발망 실측에서 그 공백이 사고로 나타났다. 포털에 얹힌 저작도구 화면에서 창을 하나 열었다 닫으면, 창이 문서에서 사라진 뒤에도 문서 수준 스크롤 잠금 표식이 남아 **포털 페이지 전체가 새로고침 전까지 스크롤되지 않았다.**

기전은 이렇다. 우리가 가져다 쓰는 외부 화면 부품 묶음의 창은 열릴 때 문서에 스크롤 잠금 표식을 붙이고 조작 불가 표식을 함께 걸며, 그것을 **「열림 → 닫힘」 상태 전이에서만** 되돌린다. 사라질 때의 정리를 하지 않는다. 그런데 저작도구 화면들은 창을 닫을 때 상태를 닫힘으로 바꾸지 않고 **화면에서 통째로 걷어낸다** — 닫힌 창을 문서에 남겨 두면 보조기술이 그것을 또 하나의 창으로 읽기 때문이며, 그 판단 자체는 옳다. 두 사정이 겹쳐 되돌림이 한 번도 일어나지 않는다.

독립 앱으로 띄울 때는 그 문서가 우리 것이라 피해가 우리 화면 안에서 끝난다. 임베드에서는 같은 일이 Host 문서에 일어나므로 피해 범위가 다르다. 즉 이것은 한 부품의 결함이 아니라 **임베드 경계에서 문서 전역 상태를 누가 소유하는지가 정해지지 않은 자리**다. 정하지 않으면 같은 갈래(포커스·전체화면·히스토리)에서 되풀이된다.

## decision

### chosen_option

Remote 는 자기가 건 문서 전역 상태만, 자기가 사라질 때 되돌린다 — 되돌리는 자리는 공용 창 부품 안쪽이고, 창이 겹칠 수 있으므로 마지막 하나가 사라질 때만 되돌린다

### justification

적용 범위 — 마운트 앵커 밖에 남는 문서 수준 상태가 대상이다. 문서 수준 스크롤 잠금, 뒤 화면을 조작 불가로 만드는 표식, 포커스, 전체화면, 히스토리가 여기 해당한다. 앵커 안쪽에서 끝나는 상태는 대상이 아니다.

소유 규칙 — 임베드에서 문서는 Host 의 것이다. 그러므로 Remote 는 문서 전역 상태를 바꿀 때 **자기가 건 것만** 되돌리고, 자기가 걸지 않은 것은 건드리지 않는다. 되돌리는 시점은 상태 전이가 아니라 **화면에서 사라지는 시점**이다 — 우리 화면은 창을 닫을 때 상태를 바꾸지 않고 걷어내므로, 전이에만 기대면 되돌림이 일어나지 않는다.

되돌리는 자리 — 화면이 아니라 공용 창 부품 안쪽이다. 화면마다 치우게 하면 새 화면이 생길 때마다 빠지고, 그 누락은 조용하다(아무 오류도 나지 않고 Host 페이지만 굳는다).

겹친 창 — 창은 겹쳐 열릴 수 있으므로 지금 서 있는 창의 수를 세어 **마지막 하나가 사라질 때만** 되돌린다. 위에 얹힌 창이 닫힐 때 아래 창의 잠금까지 풀면 뒤 화면이 구른다.

외부 부품 묶음 — 고치지 않는다. 외부 의존이라 우리가 바꿀 수 없고, 그쪽이 새 판에서 스스로 정리하게 되더라도 같은 상태를 두 번 되돌리는 것은 결과가 같아 해롭지 않다.

채널 차이 — 이 규약은 포털 채널 산출물의 요구다. 관제 채널 산출물은 문서를 자기가 소유한 독립 앱이라 같은 일이 자기 화면 안에서 끝난다. 다만 되돌리는 자리가 공용 부품이므로 두 채널에서 같이 동작하며, 그것이 문제가 되지 않는다.

금지 — 이 결정을 근거로 창을 닫을 때 화면에서 걷어내는 방식을 되돌리지 않는다. 그 방식은 닫힌 창이 보조기술에 또 하나의 창으로 읽히는 것을 막으려는 별개 판단이며, 이 결정은 그 방식을 유지한 채 뒤를 치우는 쪽을 골랐다.

## consequences

### risks

- 마지막 창이 사라지는 순간 Host 가 자기 창 때문에 문서를 잠가 둔 상태라면 그 잠금까지 함께 풀린다. Host 창이 떠 있으면 저작도구 영역은 그 뒤에 가려 조작할 수 없으므로 실제로 겹칠 일이 없다고 보고 단순한 쪽을 골랐다 — 인지하고 수용한 위험이다
- 포커스·전체화면·히스토리는 같은 갈래인데 아직 확인하지 않았다. 규칙은 그 셋에도 적용되지만, 지금 그 셋이 실제로 어떻게 동작하는지는 실측되지 않았다

### neutral

- 관제 채널 산출물의 동작은 바뀌지 않는다 — 그 채널은 문서를 자기가 소유해 같은 일이 자기 화면 안에서 끝난다
- 외부 부품 묶음의 판을 올리는 것과 무관하게 유지된다

### negative

- 같은 상태를 외부 부품 묶음과 우리 부품이 각각 되돌리게 된다 — 결과는 같지만 되돌리는 주체가 둘이다
- 문서 전역 상태를 새로 건드리는 자리가 생길 때마다 이 규칙을 적용했는지 확인해야 한다

### positive

- 임베드에서 저작도구 창을 열고 닫아도 Host 페이지의 스크롤이 죽지 않는다
- 되돌리는 자리가 한 곳이라 창을 쓰는 화면이 늘어도 같은 사고가 재발하지 않는다
- 같은 갈래(포커스·전체화면·히스토리)가 뒤에 문제가 되면 규칙을 새로 정하지 않고 이 결정을 적용하면 된다
- 창을 닫을 때 화면에서 걷어내는 기존 방식을 바꾸지 않아 보조기술이 읽는 창의 수가 그대로다

## considered_options

### Remote 가 자기가 건 문서 전역 상태를 자기가 사라질 때 되돌린다

**cons**:

- 마지막 창이 사라지는 순간 Host 가 자기 창 때문에 잠가 둔 상태라면 그것까지 함께 풀린다
- 외부 부품 묶음이 나중에 스스로 정리하게 바뀌면 같은 일을 두 곳에서 하게 된다

**pros**:

- 되돌리는 자리가 한 곳이라 새 화면이 생겨도 빠지지 않는다
- 외부 부품 묶음을 고치지 않아 그쪽 판이 올라가도 유지된다
- 창을 걷어내어 닫는 기존 방식을 그대로 둘 수 있다 — 보조기술이 닫힌 창을 또 하나의 창으로 읽지 않는다
- 같은 갈래(포커스·전체화면·히스토리)가 뒤에 생겨도 같은 자리에 더하면 된다

- **description**: 문서 전역 상태를 바꾸는 부작용을 공용 창 부품 안쪽에서 세어 두고, 마지막 창이 화면에서 사라질 때 그 상태를 되돌린다. 외부 부품 묶음은 고치지 않는다.

### 화면들이 창을 걷어내지 말고 닫힘 상태로 두게 바꾼다

**cons**:

- 닫힌 창이 문서에 남아 보조기술이 그것을 또 하나의 창으로 읽는다 — 걷어내는 방식을 고른 이유가 그것이다
- 창을 쓰는 모든 화면을 고쳐야 하고, 새 화면이 그 관례를 지키지 않으면 조용히 되살아난다

**pros**:

- 외부 부품 묶음의 되돌림 경로를 그대로 쓴다
- 우리가 더할 코드가 없다

- **description**: 창을 닫을 때 화면에서 걷어내는 대신 상태만 닫힘으로 바꿔, 외부 부품 묶음이 스스로 되돌리게 한다.

### 문서 전역 잠금을 아예 걸지 않는다

**cons**:

- 창이 떠 있는 동안 뒤 화면이 구른다 — 무엇을 구르고 있는지 알 수 없어진다
- 외부 부품 묶음의 동작을 우리가 막아야 하는데 그 수단이 없다

**pros**:

- Host 문서에 남길 상태가 없다

- **description**: 창이 떠 있는 동안에도 문서 잠금을 걸지 않아 되돌릴 것 자체를 없앤다.
