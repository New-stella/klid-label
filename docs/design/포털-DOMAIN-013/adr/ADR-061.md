# 포털 채널 증강 요청의 생성 조건을 다섯 항목 전부 필수·닫힌 값역으로 확정한다

## context

포털 채널의 증강 요청 창구(API-231)와 그 요청을 거는 화면(SCREEN-033)·요청 현황을 보는 화면(SCREEN-044)은 신설됐는데, 정작 요청 본문의 알맹이인 생성 조건 축이 비어 있었다.

[앞선 사양이 그 축을 열어 두었다] 창구 사양은 「조건을 이루는 개별 항목과 그 허용 값역은 이 산출물에서 정하지 않는다」고 적었고, 나아가 「내부 채널 증강 요청 창구의 조건 항목과 값역을 그대로 옮겨 오지 말 것」이라고 못박았다. 두 문장이 함께 있으면 조건을 채울 값을 어디에서도 얻을 수 없다.

[그 결과 요청 조작 자체가 성립하지 않았다] 빈 조건은 접수가 거부되는데 채울 값이 정해져 있지 않았다. 화면은 무엇을 물어야 할지 알 수 없고 창구는 무엇을 받는지 말할 수 없다. 설계가 비어 있어 이 축에서 더 나아갈 수 없는 상태였다.

[되돌림을 막는 것이 이 기록의 목적이다] 이 저장소는 한 번 철회한 정책을 나중에 누군가 되살리는 사고를 반복해 왔다. 이번 결정은 앞선 사양을 정면으로 뒤집은 것이라, 무엇이 왜 뒤집혔는지가 기록으로 남지 않으면 다음 사람이 원래대로 되돌린다. 실제로 이번 라운드에서 그 일이 일어났다 — 낡은 사본과 우리가 보유한 규격서 판본만 보고 이미 확정된 값을 구 구현의 잔재로 오판했다.

## decision

### chosen_option

다섯 항목 전부 필수 + 닫힌 값역, 자유 지시문은 별개 선택 항목(채택)

### justification

포털 채널 증강 요청의 생성 조건을 관제 채널과 같은 다섯 항목으로 하고, 전부 필수로 받으며 값역을 닫는다.

[다섯 항목과 그 값역] 시간대(DAWN·DAY·DUSK·NIGHT) · 계절(SPRING·SUMMER·AUTUMN·WINTER) · 날씨(CLEAR·CLOUDY·RAIN·SNOW·FOG·WINDY) · 지형(ROAD·UNDERPASS·RIVER·URBAN·RESIDENTIAL·RURAL·MOUNTAIN·FOREST) · 심각도(LOW·MEDIUM·HIGH). 값역은 허용 코드로 닫혀 있고 자유 문자열이 아니다. 하나라도 비거나 허용 코드 밖의 값이면 입력 오류로 거부한다.

[부분 입력을 허용하지 않는다] 하나라도 비면 위탁받는 쪽이 그 자리를 어떤 기본값으로 채울지 이쪽에서 알 수 없어 같은 요청의 결과가 비결정적이 된다. 위탁 계약 자체는 최소 한 항목만 요구하므로 우리가 더 엄격한 쪽이며, 그것이 의도된 선택이다.

[자유 지시문은 조건과 별개다] 조건과 분리한 최상위 문자열 한 개로 받으며 선택 항목이다. 그 자리에 객체를 실으면 입력 오류로 거부한다. 항목과 값역은 두 채널이 같게 하지만 바깥으로 나가는 필드 이름까지 같게 한다는 결정은 하지 않는다 — 두 창구 모두 우리가 소유하므로 이름이 달라도 어긋나지 않으며, 「일관성」을 이유로 이름을 바꾸지 않는다.

[뒤집힌 서술 — 둘 다 폐기다] 앞선 사양의 「조건을 이루는 개별 항목과 그 허용 값역은 정하지 않는다」와 「내부 채널 증강 요청 창구의 조건 항목과 값역을 그대로 옮겨 오지 말 것」은 폐기한다. 두 문장을 근거로 이 결정을 되돌리지 말 것 — 되돌리면 채울 값이 없는 상태로 돌아가 요청 조작이 다시 성립하지 않는다.

[요청자가 고르지 않는 것 — 여기서 다시 정의하지 않는다] 요청자는 이벤트 유형·세부 유형·증강 종류를 고르지 않는다. 서버가 이벤트 유형에 중립 값 ETC 를 고정으로 싣고 세부 유형은 아예 보내지 않으며, 증강 종류를 고르는 자리를 요청 본문에 두지 않는다. 이 축의 결정과 그 근거는 ADR-059 가 소유하므로 여기서 다시 정의하지 않는다 — 같은 결정을 두 번 적으면 두 번째 진실원이 생겨 한쪽만 갱신되는 어긋남이 열린다. 이 결정이 하는 일은 그 결론이 포털 채널 창구에도 그대로 적용된다는 것을 못박는 것뿐이다.

[요청 현황은 셋으로 갈리고 판정은 안전한 쪽으로 닫는다] 요청 현황은 기다리는 중·도착·실패 셋으로 갈린다. 판정은 결과 도착 여부를 먼저 보고, 도착하지 않았으면 실패 사유가 있는지를 본다. 어느 것도 아니면 기다리는 중으로 둔다. 판정이 서지 않는 요청을 도착이나 실패로 단정하면, 없는 결과를 있다고 말하거나 아직 진행 중인 요청을 끝난 것으로 접게 된다. 실패 사유가 비어 있는 것은 아직 실패하지 않았다는 뜻이며, 그 값은 외부 채널로 그대로 나가므로 내부 오류 코드가 아니라 사용자에게 보여 줄 수 있는 문장이어야 한다.

## consequences

### risks

- 「조건 항목과 값역은 정하지 않는다」로 되돌리면 요청 조작이 다시 성립하지 않는다 — 빈 조건은 거부되는데 채울 값이 없어진다. 되돌리기 금지
- 위탁 시 이벤트 유형에 싣는 중립 값 ETC 는 우리가 보유한 벤더 연동정의서 판본의 허용값에 없고, 그 문서는 미지원 유형에 대한 거부도 규정한다. 그 문서만 보면 계약에 없는 값으로 읽히지만 협의가 끝난 값이며, 규격서 개정판을 받기 전까지는 문서가 아니라 합의가 근거다. 개정판을 받으면 값과 오류 코드를 대조한다. 되돌리기 금지
- 값역이 우리 쪽 사본이라 위탁받는 쪽이 값을 넓혔을 때 따라가지 못하면 정상 값을 우리가 먼저 막는다 — 사본이 두 번째 진실원이 되는 형태이므로 계약 개정 시 값역 대조가 필요하다
- 실패 사유가 외부 채널로 그대로 나가므로 내부 오류 코드나 추적 정보가 그 자리에 실리면 밖으로 새어 나간다

### neutral

- 이벤트 유형·세부 유형·증강 종류 축은 이 결정의 대상이 아니다 — ADR-059 가 소유하며 이 결정은 그 결론이 포털 채널에도 적용된다는 사실만 못박는다
- 대상 자산의 범위·인가 규칙·거부 축은 무변경이다 — 본인이 올린 준비 완료 영상 한정이고 검수를 묻지 않는다는 것도 그대로다
- 증강 결과물의 저장 모델과 외부 연동 지점은 이 결정의 대상이 아니다

### negative

- 요청자가 다섯 항목을 모두 골라야 해 입력 부담이 는다 — 위탁 계약보다 엄격한 쪽을 택한 대가다
- 값역이 닫혀 있어 위탁받는 쪽이 값을 넓히면 우리 값역을 함께 넓히기 전까지 정상 값을 우리가 먼저 막는다
- 생성 조건을 감싸는 필드 이름이 두 채널에서 서로 다르다 — 항목과 값역만 같게 하고 이름은 각 창구가 자기 이름을 쓴다

### positive

- 요청 조작이 확정된다 — 화면이 무엇을 묻고 창구가 무엇을 받는지가 한 축에서 정해져 이 축에서 멈춰 있던 자리가 풀린다
- 같은 요청이 같은 조건을 갖게 되어 위탁받는 쪽이 빈 자리를 임의로 채워 결과가 비결정적이 되던 자리가 사라진다
- 두 채널의 생성 조건이 같은 항목·같은 값역을 쓰므로 위탁 요청을 조립하는 규칙이 채널마다 갈리지 않는다
- 같은 자산에 여러 요청이 공존해도 생성 조건으로 결과를 구분할 수 있다
- 요청 현황이 실패를 따로 나르게 되어, 실패한 요청이 기다리는 중으로 보이고 재조회가 멎지 않던 자리가 닫힌다

## considered_options

### 조건 항목과 값역을 정하지 않고 열어 둔다(기각)

**cons**:

- 요청 본문을 확정할 수 없어 요청 조작이 성립하지 않는다
- 빈 조건은 접수가 거부되는데 채울 값이 정해져 있지 않아 어느 요청도 통과하지 못한다
- 화면이 무엇을 물어야 하는지 정할 근거가 없다

**pros**:

- 위탁받는 쪽이 값을 넓혀도 우리 쪽 사본이 정상 값을 먼저 막는 일이 없다
- 값역을 두 곳에서 관리하지 않아도 된다

- **description**: 앞선 사양을 그대로 두어 생성 조건의 개별 항목과 허용 값역을 이 축에서 정하지 않고, 위탁받는 쪽의 계약이 넓어질 때 우리가 먼저 좁히는 일을 피한다.

### 다섯 항목을 받되 최소 한 항목만 필수로 한다(기각)

**cons**:

- 빈 항목을 위탁받는 쪽이 어떤 기본값으로 채우는지 알 수 없어 같은 요청의 결과가 비결정적이 된다
- 결과가 뜻대로 나오지 않았을 때 무엇을 바꿔야 하는지 짚을 수 없다
- 보관된 조건이 요청마다 채워진 항목 수가 달라 같은 자산의 여러 요청을 나란히 놓고 비교하기 어렵다

**pros**:

- 요청자의 입력 부담이 적다
- 위탁 계약과 엄격도가 같아 우리 쪽에서 더 막는 자리가 없다

- **description**: 위탁 계약이 요구하는 만큼만 요구한다. 다섯 항목을 모두 제공하되 하나만 채워도 접수한다.

### 조건을 자유 문장 하나로만 받는다(기각)

**cons**:

- 같은 자산의 여러 요청을 기계적으로 구분할 축이 사라진다
- 값이 열려 있어 위탁 요청을 조립할 때마다 추정이 끼어든다
- 요청자가 무엇을 적어야 하는지 알 수 없어 결과의 편차가 커진다

**pros**:

- 화면이 단순해지고 표현할 수 있는 폭에 제한이 없다
- 값역을 관리할 일이 없다

- **description**: 구조화한 항목을 두지 않고 요청자가 쓴 지시문 한 개만 받아 그대로 위탁한다.

### 다섯 항목 전부 필수 + 닫힌 값역, 자유 지시문은 별개 선택 항목(채택)

**cons**:

- 요청자가 다섯 항목을 모두 골라야 해 입력 부담이 는다
- 값역이 닫혀 있어 위탁받는 쪽이 값을 넓히면 우리 값역을 함께 넓히기 전까지 정상 값이 거부된다

**pros**:

- 요청 조작이 확정돼 화면이 묻는 것과 창구가 받는 것이 한 축에서 정해진다
- 같은 요청이 같은 조건을 갖게 되어 결과가 비결정적이 되는 자리가 사라진다
- 같은 자산에 여러 요청이 공존해도 생성 조건으로 결과를 구분할 수 있다

- **description**: 생성 조건을 관제 채널과 같은 다섯 항목으로 하고 전부 필수로 받으며 값역을 허용 코드로 닫는다. 자유 지시문은 조건과 분리한 최상위 문자열 한 개이며 선택 항목이다.
