# 저작도구 채널별 별도 배포 — 채널별 토큰 인계로 인증/진입

## context

저작도구는 독립 로그인 UI가 없고 관제서버(내부)·포털(외부)이 발급한 JWT를 인계받아 진입한다. 두 상위 시스템과의 연동 방식(인증 전달·배포 위치)을 확정해야 한다. 양방향 M2M 통합은 deprecated(ADR-007)이며, 인증을 위한 별도 M2M 인프라를 두지 않는 전제다.

개정 사유(2026-08-27): 포털 채널이 저작도구 프론트엔드를 자기 화면 안에서 런타임으로 실행하는 임베딩 연동(INT-013)으로 확정되면서, 이 결정이 전제한 브라우저 스토리지 공유가 그 채널에서는 성립하지 않게 됐다. 포털 Host 는 토큰의 획득과 갱신을 자기가 소유하고 access token 을 자기 메모리에만 두며 브라우저 저장소를 쓰지 않는다고 회신했고, 이를 비협상 조건으로 제시했다. 저장소나 그 스냅샷을 직접 읽으면 Host 가 토큰을 갱신한 시점 이후로는 이미 무효가 된 토큰을 붙잡게 되며, 수십 분을 한 화면에 머무는 저작 화면은 그 파손을 반드시 겪는다. 따라서 배포 위치(채널별 별도 배포)는 유지하되 토큰 인계 수단만 채널별로 갈라 다시 정한다.

개정 사유 보강(2026-09-03 포털 회신 반영): 위험의 축은 저장소를 직접 읽는 것에 한정되지 않는다. 갱신 주체가 Host 이고 접근 토큰의 만료가 짧으므로, 저장 위치와 무관하게 토큰을 캐시하면 Host 가 갱신한 시점 이후로 죽은 토큰을 붙잡는다. 저장소를 쓰지 않는 것만으로는 모자라며 메모리에 들고 있어도 같은 파손이 난다.

## decision

### chosen_option

채널별 별도 배포 + 채널별 토큰 인계 수단(관제=동일 origin 브라우저 스토리지 · 포털=Host 인계 창구)

### justification

저작도구를 관제 채널·포털 채널에 각각 별도 배포한다 — 이 축은 그대로 유지한다. 달라지는 것은 토큰 인계 수단이며 채널마다 갈린다. 관제 채널은 호스트와 동일 origin 을 공유하므로 브라우저 스토리지(localStorage/sessionStorage)로 JWT 를 인계받는다(기존 그대로). 다만 인계 뒤의 수명 관리는 달라졌다 — 관제 채널도 세션을 연장하며 그 갱신 결과를 관제와 같은 키·형식으로 같은 출처 저장소에 쓴다(아래 「관제 채널 세션 연장」 절, 2026-09-10). 포털 채널은 Host 가 주입한 인계 창구로 토큰을 얻고(획득·갱신·인증 실패 통지·활동 통지) API 호출 시 전용 요청 헤더로 실어 보내며, access token 은 Host 메모리에만 두고 브라우저 저장소를 쓰지 않는다. 두 채널 모두 URL 쿼리 파라미터(?token=) 전달은 노출 위험으로 미사용이고, 저작도구가 토큰을 발급하지 않으며 단일 검증 로직으로 처리한다는 점도 그대로다. 인계 계층을 저장소 직접 읽기가 아니라 토큰을 얻는 창구 뒤로 추상화하면 두 인계 방식을 호출부 분기 없이 지원한다. 잔존 저작도구→관제 outbound 통지만 인계토큰/IP 화이트리스트로 보호(ADR-007).

## ★ 데이터 축 — 각 배포본은 자기 DB 에만 연결한다 (2026-08-31 사용자 확정, 구속)
채널별 별도 배포의 귀결이다. 관제 채널 배포본과 포털 채널 배포본이 **각각 별도 PostgreSQL DB** 를 가지며, 포털향 DB 는 포털 채널에 맞춰 **별도로 구성**한다. 한 배포본이 두 채널의 DB 를 함께 무는 구조가 아니다.
저작도구와 포털은 **서로의 DB 에 접근하지 않는다**(양방향 — 포털도 저작도구 DB 를 참조하지 않는다). 두 시스템이 주고받을 데이터는 **API** 로 설계한다. 따라서 듀얼 데이터소스 기반 포털 DB 메타 단방향 복제(INT-009)는 **폐기**다.
**두 배포본끼리도 직접 이어지지 않는다** — 서로의 DB 를 읽지 않고 서로를 직접 호출하지도 않는다.

## ★ 자산 전달 경로 — 중계자는 관제다 (2026-08-31 사용자 확정, 구속)
1. **관제 채널 배포본**에서 검수 **승인**이 나면 **관제로 완료 통지**를 보낸다.
2. **관제가 그 자산을 포털로 전달**한다 — **압축 파일** 형태가 예정이며, 포털 측 수신은 재개 가능 업로드와 배포 등재·상태 폴링 규격을 따른다.
3. 이후 **포털이 포털 채널 배포본에 자산 수신을 API 로 알린다.**

⚠ **포털 채널 배포본이 관제 채널 배포본의 DB 나 API 를 직접 물어 승인 자산을 가져오는 그림은 이 결정과 어긋난다.** 승인 자산이 포털 쪽으로 흐르는 경로는 위 3단계뿐이며 중계자는 관제다. 3단계의 통지를 받는 쪽은 **포털 채널 배포본**이다 — 그 배포본이 포털이 보유한 자산을 조회해 작업 소재로 삼는다.

## ★ 인프라 소유와 AI 파이프라인 (2026-08-31 확정, 구속)
두 배포본은 **인프라 소유 주체가 갈린다.** 관제 채널 배포본은 DB·NAS 모두 **관제지원 소유**(공유 NAS)이고, 포털 채널 배포본은 **PostgreSQL 이 별도 서버이며 저작도구가 직접 관리**하고 **NAS 는 포털이 관리하는 별도 NAS**다(공유 NAS 아님).
**포털 채널 배포본에는 추론 서버(객체 탐지·분할)가 붙지 않는다** — 오토라벨링·인터랙티브 분할이 없다. AI 파이프라인(추론·외부 시계열 위탁·비식별·배치)은 **관제 채널 배포본에만** 있다. ⚠ **외부 증강은 별개 축이다** — 추론 서버가 아니라 외부 생성형 AI 위탁이며 포털 업로드 영상 대상 제공이 확정돼 있다. 「추론 서버 미연결」을 「포털에 AI 가 전혀 없다」로 읽지 말 것.

### 포털 인프라 배치 — 저작도구 WAS 는 포털 인프라 구성자원이다 (2026-09-03 포털 회신으로 확정, 구속)
포털 채널 배포본의 저작도구 WAS 는 **포털 인프라 구성자원**(호스트네임 `klid_portal_author_was_01` · `klid_portal_author_was_02`, active-active 이중화)으로 **포털 내부망에 배치**된다. 그러므로 **포털↔저작도구 서버간 호출에는 외부 방화벽 경계가 없다** — 사용량 보고 · 환불 · 저작 현황 요약 · 일일 저작 집계 · 배포본 정리 삭제 트리거 · 소재 조회가 모두 내부망 통신이다. ⇒ 저작도구가 종전 준비하려던 방화벽 값(WAS 호스트 · 대역 · 수신포트 · 송신 IP)은 **이 축에서 불필요하다.**
⚠ **포털 연동 축 한정이다.** 관제 연동 축의 방화벽 요건은 별개이며 이 문장으로 함께 지워지지 않는다. 「방화벽이 필요 없다」를 전 축의 규칙으로 읽으면 관제 축 반입·운영 준비가 무너진다.
포털이 함께 공유한 인프라 구성자원은 포털 WEB · 포털 WAS · **포털 저작 WAS** · 포털 DB 중계 · 포털 DB · 포털 GPU 이며 각각 active-active 로 이중화된다. 실 IP·포트는 인프라 확정 시 별도 공유될 예정이다.

⚠ **확인 필요 — 포털향 DB 의 소재와 소유.** 이 절은 포털 채널 배포본의 PostgreSQL 이 별도 서버이며 저작도구가 직접 관리한다고 적고 있다. 그런데 포털이 공유한 구성자원 목록에서 DB 에 해당하는 자원(포털 DB · 포털 DB 중계)은 **포털 자기 DB 로 읽히고**, 저작도구 포털향 DB 에 해당하는 자원은 그 목록에 **보이지 않는다.** 두 서술이 같은 것을 가리키는지, 아니면 저작도구 포털향 DB 가 별도로 있는데 목록에서 빠진 것인지 **아직 알 수 없다.** 어느 쪽이라고 단정하지 말고 포털에 확인한 뒤 이 절을 확정한다 — 잘못 단정하면 DB 소유·운영 책임이 통째로 뒤바뀐다.

## ★ 매 호출 취득 · 캐시 금지 (2026-09-03 포털 회신으로 확정, 구속)
토큰은 **보호된 호출마다** 토큰 획득 창구로 취득한다. **자체 캐시를 두지 않고 자체 스토어 폴백도 두지 않는다.**
근거 — 갱신 주체가 Host 이고 접근 토큰의 만료가 짧다. 그러므로 **저장 위치와 무관하게** 캐시하면 Host 가 갱신한 시점 이후로 **죽은 토큰**을 잡는다. 저장소를 쓰지 않는 것만으로는 모자라며, 메모리에 들고 있어도 같은 파손이 난다.
⚠ **이 결정의 위험 서술을 「저장소 직접 읽기」로 좁혀 읽지 말 것.** 그렇게 읽으면 「저장소를 안 쓰니 메모리 캐시는 괜찮다」가 되고, 실패가 죽은 토큰을 붙잡는 쪽으로 난다.
⚠ **캐시 금지는 양 채널 공통이다.** 인계 수단은 채널마다 갈리지만 이 금지는 갈리지 않는다 — 관제 채널도 저장소를 직접 읽는 대신 획득 창구를 거치며 그 값을 들고 있지 않는다.
이 축의 연동 규격은 [[INT-013]] 이 담고, 이 결정을 근거로 삼는 서버간 연동 축은 [[INT-014]] 다.

## ★ 채널 판정 축 — 배포 향이 정한다 (2026-09-09 사용자 확정, 구속)
채널별 별도 배포의 귀결이다. **포털 채널 배포본에 도착하는 인계 토큰은 항상 포털 채널로 해석한다** — 토큰에 채널 값이 실려 있어도 그 값을 따르지 않는다(기본값 전환이 아니라 강제). **관제 채널 배포본은 종전대로다** — 채널 값이 있으면 그 값을, 없으면 관제 채널로 본다.
판정 축은 **설치 시점에 정하는 배포 향**이며, 이 결정이 이미 규정한 배포 향 선언(값역: 관제 채널 · 포털 채널)을 그대로 재사용한다. **인증 전용 설정을 새로 두지 않는다** — 같은 사실을 두 곳에서 선언하면 둘이 어긋나는 순간 어느 쪽이 참인지 판정할 수단이 없다. 배포 향이 선언되지 않았거나 값역 밖이면 **관제 채널로 해석한다**(fail-closed).
근거 — 저작도구는 채널마다 별도로 배포되므로 포털 채널 배포본에 도착하는 토큰은 정의상 전부 포털 채널이다. 배포본이 이미 알고 있는 사실을 상대 시스템의 토큰에 실어 달라고 요청하는 것은 우리 배포 형상을 상대에게 떠넘기는 것이다. 또 포털은 사용자 주체 토큰과 시스템 주체 토큰을 **같은 공유 서명키로 서명**하고 주체를 주체 식별자 클레임으로 가르므로, 서명키만으로는 채널 축이 갈리지 않는다.

### ★ 되돌리기 전에 알아야 할 것 — 종전 기본값의 근거는 조건부였다
종전에는 「채널 값이 없는 토큰은 관제 채널로 본다」가 fail-closed 로 정당화돼 있었다(관제 사용자 토큰 호환 · 외부 노출 없음). **그 정당화는 「이 배포본은 관제향」이라는 전제 위에서만 성립한다.** 포털 채널 배포본에서는 전제가 뒤집혀 오히려 fail-open 이 된다 — 포털 사용자가 관제 채널 사용자로 해석되어, 관제 채널 전용 경로(사용자 역할 조회 · 미배정 사용자 자동 등록 · 최종 접속 기록 · 주체 식별자 정규화)가 그대로 돌고 정작 포털 전용 창구는 차단된다.
⚠ 특히 **포털 회원 식별자와 저작도구 사용자 번호는 서로 다른 체계**인데, 관제 채널로 오인되면 포털 회원 식별자가 저작도구 사용자 번호 공간에 그대로 등록된다. 값이 겹치면 다른 사용자의 행에 매칭된다.
⚠ **종전 근거를 지우지 않는다 — 틀렸던 것이 아니라 조건부였다.** 관제 채널 배포본에서는 그 근거가 지금도 그대로 참이다.

## ★ 관제 채널 세션 연장 — 저작도구도 연장하고 저장소에 쓴다 (2026-09-10 사용자 확정, 구속)
관제 채널 저작도구도 관제지원 웹과 같은 시나리오로 세션 만료를 감시하고 연장한다.
근거 — 관제는 저작도구를 **새 탭**으로 연다. 관제의 만료 감시·연장 팝업은 **관제 탭에서만** 돌고 저작도구 탭에서는 돌지 않는다. 관제 접근 토큰의 수명은 짧아(2026-09-10 실측 30분), 저작도구가 진입 시 복사한 토큰을 쥐고 있으면 관제가 갱신해도 그 수명이 지나면 인증이 끊긴다. 한 화면에 오래 머무는 저작 작업(라벨링·검수)에서는 반드시 겪는다.
1. **토큰의 진실원** — 관제 채널 접근 토큰의 진실원은 같은 출처 저장소 키 `klid-jwt-token` 의 **현재값**이다. 보호된 호출마다 그 값을 취득하며 **진입 시 복사본을 쓰지 않는다**(위 「매 호출 취득 · 캐시 금지」의 관제 채널 적용).
2. **다른 탭 따라가기** — 다른 탭의 갱신·로그아웃을 저장소 변경 이벤트로 따라간다. 토큰 키 값이 바뀌면 새 값을 쓰고, **토큰 키가 삭제되면 로그아웃**으로 본다(관제와 같은 결말).
3. **만료 감시 + 연장 팝업** — 관제 채널의 **로그인된 모든 화면**(앱 전역)에 만료 감시와 연장 팝업을 둔다 — 셸이 감싸지 않는 전체 화면 작업 화면(라벨링 캔버스 등)을 포함하고, 로그인 전 화면은 제외한다. 가장 오래 머무는 라벨링 캔버스가 셸 밖 전체 화면이라 셸에만 두면 그 화면에서 팝업이 뜨지 않기 때문이다. 팝업은 관제지원 웹의 세션 팝업과 완전히 같다 — 버튼은 「로그아웃」과 「로그인 연장」 둘뿐이고, 「닫기」·X·ESC·배경 클릭으로는 닫히지 않는다. 「로그아웃」은 저작도구 서버의 로그아웃 창구를 불러 관제 로그아웃을 중계하게 한 뒤(아래 4) 저장소의 토큰 키를 지우고 관제 로그인 페이지로 이동한다 — 토큰 키가 지워지므로 같은 출처의 관제 탭도 함께 로그아웃된다(위 2). 상세는 [[SHELL-001]] 이 정본이다. 팝업 임계는 저장된 토큰 정보의 `sessionExpAlarm`(분) → 없으면 토큰 클레임 `sessionExpAlarm` → 없으면 **30분**이다. 남은 시간이 0 이 되면 상위 로그인 페이지로 보낸다.
4. **갱신 = 저작도구 서버가 중계하는 관제 계정 갱신** — 브라우저는 관제를 직접 부르지 않는다. 저작도구 서버가 관제 계정 창구(갱신·로그아웃, [[INT-015]])를 중계한다. 내부 채널 인계 창구의 갱신은 브라우저가 저작도구 서버의 갱신 창구를 갱신 토큰으로 부르고, 저작도구 서버가 그 갱신 토큰으로 관제 계정 갱신 창구를 호출해 결과를 돌려주는 것이다. refresh 토큰은 갱신 중계 창구([[API-247]])의 요청 본문으로만 보낸다. 인증 헤더에 refresh 토큰을 실은 요청은 저작도구가 거부한다([[ADR-063]] ⑦). 로그아웃도 같다 — 브라우저는 저작도구 서버의 로그아웃 창구를 부르고, 저작도구 서버가 관제 계정 로그아웃 창구를 호출한다. 중계 대상 관제 주소는 관제 통지 수신처 주소 설정을 재사용한다(새 주소 설정을 두지 않는다). 근거는 사용자 확정(2026-09-10)이다. 갱신 결과를 관제와 같은 키·형식으로 브라우저 저장소에 저장하는 규칙(아래 6)과 실패 결말 규칙(아래 5)은 그대로이며, 실패 판정은 저작도구 서버의 응답 코드로 전달된다 — 관제가 갱신을 거절하면 401, 관제에 닿지 못하거나 관제가 서버 오류를 내는 일시 장애면 503 이다. 저작도구가 토큰을 발급하는 것이 아니다 — 「저작도구가 토큰을 발급하지 않는다」는 그대로 참이다.
5. **선제 갱신 + 1회 재시도** — 보호된 요청 직전 남은 시간이 **10분 이하**면 먼저 갱신하고, 응답이 401 이면 갱신 후 **1회** 재시도한다. 갱신이 실패했을 때의 결말은 실패의 종류로 갈린다 — ①**관제가 갱신을 거절하면**(관제 응답의 `error` 가 0 이 아님 — 예: 서버 세션이 이미 정리돼 갱신 토큰이 없다는 응답) 선제 갱신·팝업의 「로그인 연장」·401 뒤 갱신 어느 경로든 **즉시** 세션을 비우고 상위 로그인 페이지로 보낸다. 거절된 갱신 토큰으로 다시 갱신하지 않는다. 근거 — 다른 기기 등에서 관제 서버 세션이 끊겨도 이 브라우저의 저장소 값은 그대로라 저장소 변경 추종으로는 잡히지 않는데, 갱신 시점(만료 10분 전)에는 추가 호출 없이 잡힌다. ②네트워크 오류·서버 오류(5xx) 같은 **일시 장애**로 선제 갱신이나 팝업의 「로그인 연장」 갱신이 실패하면 결과를 저장하지 않고 현재 토큰으로 계속 쓰며(팝업 경로는 실패를 안내한다), 다음 요청 때 다시 갱신을 시도할 수 있다. **남은 시간이 0 이 되면** 상위 로그인 페이지로 보낸다. ③401 뒤의 갱신이 실패하거나 재시도도 401 이면 **즉시** 상위 로그인 페이지로 보낸다. ④강제 로그아웃(①·③·남은 시간 0)은 **미저장 변경 확인 절차를 거치지 않는다** — 만료되거나 거절된 세션으로는 저장할 수 없고, 확인 창에서 멈추면 이미 끝난 세션에 갇힌다. 자동 저장도 하지 않는다 — 사람이 확인하지 않은 편집을 저장하는 부수효과를 막기 위해서다. 미저장 편집이 있으면 연장 팝업에 경고를 함께 보인다(상세는 [[SHELL-001]]).
6. **관제와 같은 키·형식으로 저장한다** — 갱신 결과를 관제가 로그인·갱신 때 쓰는 것과 **같은 키·같은 형식**으로 저장한다. 즉 **관제 채널에서 저작도구는 같은 출처 저장소에 쓴다.** 형식이 한 글자라도 다르면 관제 탭이 그 값을 읽고 깨지므로 필드 이름·단위·기본값을 관제와 글자 그대로 맞춘다.
7. **탭 간 동시 갱신 방지** — 갱신 직전 저장된 갱신 토큰을 다시 읽어 쥐고 있던 값과 다르면(다른 탭이 이미 갱신) 갱신하지 않고 새 값을 쓴다. 탭 간 잠금을 쓸 수 있는 환경이면 한 번 더 직렬화하되, 쓸 수 없는 환경에서도 재읽기 비교만으로 동작한다.
8. **갱신 토큰이 없는 진입** — 개발용 로그인처럼 갱신 토큰이 없는 진입은 갱신하지 않고 종전 동작(토큰 만료까지 사용)을 유지한다. 오류로 취급하지 않는다.
9. **포털 채널은 그대로다** — Host 인계 창구 · 전용 요청 헤더(`x-access-token`) · Host 메모리 보관(브라우저 저장소 미사용)은 이 절의 영향을 받지 않는다. 이 절의 감시·팝업·저장은 **관제 채널에서만** 동작한다.

### 폐기 — 관제 채널 한정 (2026-09-10)
다음 종전 규칙은 **관제 채널에서 폐기**다. 지우지 않고 현재 결정으로 대체한다. 포털 채널 결정은 이 폐기와 무관하다.
- [폐기] 「저작도구는 브라우저 저장소를 읽기만 하고 쓰지 않는다」 → 현재 결정: 관제 채널에서는 갱신 결과를 관제와 같은 키·형식으로 **쓴다**(위 6).
- [폐기] 「내부 채널에는 갱신 창구가 없다」 → 현재 결정: 내부 채널 인계 창구의 갱신 = 저작도구 서버가 중계하는 관제 계정 갱신 창구 호출(위 4).
- [폐기] 「세션 수명은 상위 시스템 토큰이 정하며 저작도구가 연장하지 못한다」 → 현재 결정: 관제 채널 저작도구는 만료 전에 연장한다(위 3·5). 실제로 만료되면 상위 로그인 페이지로 보낸다는 규칙은 그대로다.
⚠ 같은 규칙을 다른 말로 적은 서술 — 저작도구가 관제 채널의 저장소 값을 바꾸지 않는다거나 토큰 수명 관리를 상위 시스템만 한다고 읽히는 서술 — 도 관제 채널에서는 같은 이유로 폐기다.
⚠ 위 첫 문단의 「관제 채널은 … 브라우저 스토리지로 JWT 를 인계받는다(기존 그대로)」는 **인계 수단으로는 여전히 참**이다. 그 「기존 그대로」를 「저장소를 읽기만 한다」·「연장하지 않는다」로 넓혀 읽지 말 것 — 달라진 것은 인계 뒤의 수명 관리다.
⚠ 인지·수용한 위험(탭 간 갱신 경쟁 · 저장 형식 불일치)은 결과의 위험 항목에 적었다.

### 2026-09-10 — 관제 계정 창구 호출 경로 확정 (저작도구 서버 중계)
- 같은 날 결정 4와 결정 3의 「로그아웃」은 브라우저가 관제 계정 창구(갱신·로그아웃)를 직접 부르는 형태로 적혀 있었다. 사용자 확정(「관제 호출은 우리 와스를 통해 하는거야」)으로 브라우저 → 저작도구 서버(신설 갱신·로그아웃 창구) → 관제 계정 창구(INT-015) 중계로 고쳤다. 사용자가 이유를 밝히지 않아 근거는 사용자 확정으로만 적었다.

- 저장 형식(관제와 같은 키·형식, 브라우저 저장소)과 실패 결말 규칙(결정 5)은 바꾸지 않았다.
- 결과에 긍정(브라우저가 관제 계정 서비스에 직접 닿지 않는다)·부정(저작도구 서버의 관제 계정 호출 의존 + 로그인 검사 없이 열리는 갱신 창구) 한 줄씩을 더했고 참조에 INT-015 를 올렸다.
- 결정 4, 결정 3의 로그아웃 문장, 폐기 목록의 갱신 대체 문장 밖의 본문은 바꾸지 않았다.

## consequences

### risks

- 채널 간 배포 버전 불일치 시 동작 차이 — 릴리스 동기화 프로세스 필요(RISK 후보)
- 배포 향 선언 누락·오기는 기동 시점이 아니라 인계 진입 시점에야 드러난다 — 배포 점검 항목으로 관리해야 한다(RISK 후보)
- 관제 탭과 저작도구 탭이 동시에 갱신하면 한쪽이 교체된 옛 갱신 토큰을 쥘 수 있다. 옛 갱신 토큰 재사용 시 관제 서버가 세션 전체를 끊는지는 미확인이다(관제 확인 대상). 갱신 직전 재읽기 비교로 확률을 줄이나 관제 탭은 저작도구의 탭 간 잠금을 모르므로 완전한 배제는 불가능하다(인지·수용)
- 저작도구가 쓰는 저장 형식이 관제와 한 글자라도 다르면 관제 탭이 그 값을 읽고 깨진다(즉시 로그아웃 포함) — 저장 형식의 관제 대조를 수용 기준으로 둔다
- 관제 서버가 접근 토큰 만료 전에 세션을 정리할 수 있다(2026-09-10 실측 — 원인 미확정). 저작도구 서버는 서명·만료만 보므로 다음 갱신 시점까지(최대 약 20분) 저작도구가 동작한다 — 갱신 거절 즉시 로그아웃(결정 5의 ①)으로 그 창을 줄이며, 남는 창은 **인지·수용**한다. 같은 브라우저의 관제 로그아웃은 저장소 삭제 이벤트로 즉시 따라간다

### neutral

- 관제·포털 모두 동일 JWT 발급 서버를 사용하므로 검증 로직은 단일 유지
- 동일 origin 브라우저 스토리지 공유는 이제 관제 채널에만 성립하는 전제다 — 모든 채널에 그대로 적용된다고 읽으면 안 된다.
- 관제 채널 배포본의 채널 해석은 달라지지 않는다 — 토큰에 채널 값이 있으면 그 값을, 없으면 관제 채널로 본다
- 관제 채널의 세션 연장은 관제 계정 갱신 창구를 부르는 것이지 저작도구가 토큰을 발급하는 것이 아니다 — 「저작도구가 토큰을 발급하지 않는다」는 그대로 참이다
- 세션이 실제로 만료되면 상위 로그인 페이지로 보낸다는 규칙은 그대로다 — 관제 채널에서 달라진 것은 만료 전에 연장할 수 있다는 것뿐이다

### negative

- 저작도구 인스턴스 2벌 배포·버전 동기화 운영 부담
- 두 채널 환경설정·릴리스 절차 중복 관리 필요
- 포털 채널은 저장소를 직접 읽지 않고 Host 인계 창구를 거치므로, 두 인계 방식의 차이를 흡수하는 인계 추상화 계층이 한 겹 필요하다 — 개정 전에는 인증 진입 경로의 코드 변경이 없다는 전제였다.
- 토큰을 보호된 호출마다 다시 취득하므로 인계 창구 호출이 보호된 요청 수만큼 발생한다 — 자체 캐시로 줄이는 최적화는 이 결정이 금지한다
- 채널 해석이 배포 시점 선언에 묶이므로 배포 향을 잘못 선언하면 그 배포본이 통째로 반대 채널로 동작한다 — 토큰 단위로 바로잡을 여지가 없다
- 관제 채널에서 저작도구가 관제 소유 저장소 키에 쓰므로 저장 형식이 관제 계약에 묶인다 — 관제가 저장 형식을 바꾸면 저작도구도 함께 바꿔야 한다
- 관제 채널에서 저작도구 서버에 관제 계정 창구(갱신·로그아웃) 호출 의존이 생기고, 갱신 창구가 로그인 검사 없이 열린다 — 자격증명은 갱신 토큰이고 유효 판정은 관제가 하며, 중계 대상 주소는 설정이 정하며 요청으로는 바꿀 수 없다

### positive

- JWT가 URL·로그에 노출되지 않아 토큰 유출 위험 감소
- 별도 M2M 사용자 인증 인프라 불요로 구축·운영 단순화
- 관제(klid_at+MNG_*)·포털(포털 DB) 데이터 경계 자연 분리
- 세션 만료 시 각 상위 시스템 로그인 페이지로 리다이렉트 일관 처리
- 포털 채널 배포본이 상대 시스템 토큰의 내용에 의존하지 않고 채널을 확정한다 — 상대가 채널 값을 싣지 않거나 다르게 실어도 우리 해석이 흔들리지 않는다
- 관제 채널에서도 관제 탭이 갱신하든 저작도구가 갱신하든 다음 요청이 현재 토큰을 싣고, 만료 전 연장으로 오래 머무는 저작 작업이 끊기지 않는다
- 관제 채널에서 브라우저가 관제 계정 서비스에 직접 닿을 필요가 없다 — 관제 계정 창구(갱신·로그아웃)는 저작도구 서버만 부른다

## decision_drivers

- 독립 로그인 UI 부재 — 상위 시스템 JWT 인계 필요
- M2M 양방향 인증 인프라 미운영(ADR-007)
- URL ?token= 전달의 토큰 노출·로그 유출 위험 회피
- 관제·포털 두 채널의 데이터소스·접근 경계 분리(klid_at+MNG_* vs 포털 DB)
- 포털 Host 임베딩에서 Host 가 토큰 획득·갱신을 소유 — 저장소·스냅샷 직접 읽기는 물론 저장 위치와 무관한 캐시도 갱신 시점 이후 무효 토큰을 잡는다
- 접근 토큰의 만료가 짧아 보호된 호출마다 다시 취득해야 한다 — 자체 캐시·자체 스토어 폴백을 두면 죽은 토큰을 잡는다
- 채널별 별도 배포이므로 각 배포본은 설치 시점에 자기 채널을 이미 안다 — 그 사실을 상대 시스템의 토큰에 실어 달라고 요구하면 우리 배포 형상이 상대의 계약이 된다
- 포털이 사용자 주체 토큰과 시스템 주체 토큰을 같은 공유 서명키로 서명하므로 서명키로는 채널 축이 갈리지 않는다 — 채널 판정을 토큰 쪽에 맡길 수 없다
- 관제는 저작도구를 새 탭으로 열어 관제의 만료 감시·연장 팝업이 저작도구 탭에서 돌지 않고 관제 접근 토큰의 수명이 짧다 — 관제 채널도 스스로 세션을 연장하지 않으면 한 화면에 오래 머무는 저작 작업이 끊긴다

## considered_options

### 채널별 별도 배포 + 채널별 토큰 인계 수단(관제=동일 origin 브라우저 스토리지 · 포털=Host 인계 창구)

**cons**:

- 저작도구 인스턴스를 2벌 운영·배포해야 함
- 배포·버전 동기화 운영 부담
- 인계 수단이 채널마다 달라 그 차이를 흡수하는 추상화 계층이 필요하다
- 관제 채널에서 저작도구가 관제 소유 저장소 키에 쓰므로 저장 형식이 관제 계약에 묶인다 — 관제가 형식을 바꾸면 함께 바꿔야 한다

**pros**:

- 동일 origin이라 스토리지 공유로 JWT 전달 가능 — 별도 인증 인프라 불요
- 토큰이 URL·로그에 노출되지 않음
- 채널별 데이터소스·접근 경계 자연 분리
- Host 가 토큰 갱신을 소유하는 채널에서도 갱신 이후의 무효 토큰을 붙잡지 않는다
- 관제 채널에서도 관제 탭의 갱신 여부와 무관하게 한 화면에 오래 머무는 저작 작업이 토큰 수명에 끊기지 않는다

- **description**: 저작도구를 관제 채널·포털 채널에 각각 배포하고, 관제 채널은 호스트 시스템과 동일 웹 origin 을 공유해 localStorage/sessionStorage 로 JWT 를 전달받는다. 포털 채널은 Host 가 주입한 인계 창구로 토큰을 얻어 전용 요청 헤더로 싣고 Host 메모리에만 보관한다. 관제 채널도 관제 계정 갱신 창구로 세션을 연장하고 그 결과를 관제와 같은 키·형식으로 같은 출처 저장소에 쓴다(2026-09-10).

### 단일 배포 + URL 쿼리 파라미터(?token=) 전달

**cons**:

- 토큰이 URL·접근로그·리퍼러에 노출 — 보안 위험
- 동일 origin 스토리지 공유 이점 상실
- 프로젝트 인증·진입 방침에서 명시적으로 미사용 결정

**pros**:

- 배포 단순(1벌)

- **description**: 저작도구를 1벌만 배포하고 상위 시스템이 URL 쿼리로 토큰을 전달한다.

### 양방향 M2M 인증 인프라 재구축

**cons**:

- deprecated된 M2M 인프라 재구축 비용
- 현 사업 범위 초과
- 단순 JWT 인계로 충분한 요구를 과설계

**pros**:

- 채널 독립성 높음

- **description**: 관제/포털과 M2M 인증 채널을 새로 구축해 토큰을 교환한다.

### 관제 채널 연장 없음 — 저장소 읽기 전용 유지(종전, 2026-09-10 기각)

**cons**:

- 관제는 저작도구를 새 탭으로 열어 관제의 만료 감시·연장 팝업이 저작도구 탭에서 돌지 않는다 — 관제 탭이 갱신해 주지 않으면 짧은 토큰 수명이 지나 인증이 끊긴다
- 진입 시 복사본을 쓰면 관제가 갱신해도 옛 토큰을 쥐고 있다가 끊긴다
- 한 화면에 오래 머무는 저작 작업(라벨링·검수)에서 반드시 겪는다

**pros**:

- 관제 소유 저장소에 쓰지 않으므로 저장 형식이 관제 계약에 묶이지 않는다
- 탭 간 갱신 경쟁이 생기지 않는다

- **description**: 관제 채널 저작도구는 인계받은 토큰을 읽기만 하고 갱신·저장을 하지 않는다. 세션 수명은 상위 시스템 토큰이 정한다.
