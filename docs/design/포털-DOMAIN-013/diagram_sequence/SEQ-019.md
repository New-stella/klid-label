## description

포털 회원(PORTAL_USER)이 본인 영상을 직접 올려 프레임 단위로 수동 라벨링하고 본인 데이터를 내려받는 흐름의 시퀀스 다이어그램. 영상의 재개 가능 업로드와 이벤트 구간 마킹, 그 마킹 지점에서의 프레임 추출, 프레임 단위 라벨 전체교체 저장, 라벨 JSON 내보내기와 원본 파일 다운로드를 그린다.

프레임 이미지 서빙은 영상에서 뽑은 프레임을 내려주는 자리다.

이 경로의 자산·프레임·라벨은 공용 원장에 앉는다 — 자산은 LS_DATA_RAW, 프레임은 LS_DATA_SRC, 라벨은 LS_DATA_LBL 이고 재개 업로드 세션은 LS_TUS_UPLOAD 다. 파일은 포털 전용 저장 경로에 기록된다. 그래도 내부 배치 파이프라인(비식별·마킹·시계열·오토라벨링)과 데이터마트 적재용 뷰로는 흘러가지 않는데, 근거는 저장소가 다르다는 것이 아니라 셋이다. 첫째, 출처와 소유자로 가른다 — 출처 판별자 SRC_TYPE='PORTAL_ULD' 와 소유자 LS_DATA_RAW.PORTAL_USER_NO(라벨 축은 LS_DATA_LBL.REG_USER_NO)다. 둘째, 배치는 DB 트리거가 아니라 앱 이벤트로 발동하고 포털은 관제 인입과 별개인 자기 이벤트를 쓰므로 같은 원장에 앉아도 파이프라인이 집어가지 않는다. 셋째, 데이터마트 적재용 뷰는 검수 승인 때만 생기는 동결 메타가 드라이버인데 이 경로에는 검수가 없어, 필터로 막는 것이 아니라 구조적으로 도달하지 않는다. 회원이 직접 올린 자산이라 비식별 대상이 아니고 비식별 누락 신고 게이트도 적용되지 않는다 — 데이터마트 프레임을 포털로 내보내는 경로와 갈리는 지점이다.

자산 상태는 UPLOADED · PROCESSING · READY · FAILED 로 전이한다. 영상은 업로드 확정 시 UPLOADED 로 적재되는데, 이 상태는 추출을 기다리는 것이 아니라 마킹을 기다리는 것이다 — 업로드 직후 프레임을 뽑지 않는다. 추출을 여는 것은 마킹 저장이며, 마킹 저장 트랜잭션이 커밋된 이후에만 시작된다 — 롤백된 저장이 추출을 깨우지 않게 하기 위해서다. 고정 간격 추출이 없어진 것은 아니다. 자동 마킹의 기본 동작으로 흡수되어, 간격을 그대로 두고 완료하면 구 동작과 같은 결과가 나온다. 추출은 시작 시 PROCESSING 으로 원자 전이하고 계산된 프레임을 모두 뽑은 뒤에야 READY 로 확정하며, 중간에 실패하면 부분 파일을 정리하고 FAILED 로 마감한다. 라벨링과 다운로드는 READY 자산에서만 성립한다.

라벨 저장은 프레임 단위 전체교체이고 빈 목록은 그 프레임의 라벨을 모두 지우는 유효한 요청이다. 검증은 삭제보다 먼저 전량 수행해, 일부만 유효한 요청이 기존 라벨을 지운 채 실패하는 일이 없게 한다. 라벨 형태는 BBOX·POLYGON 만 허용하며 오토라벨링·객체 자동 분할과 추적·검수·버전관리는 이 경로에 없다. 시계열 축에서 없는 것은 외부 시계열 분석 서버로 나가는 위탁 연동이다.

업로드한 영상 자산에 한해서는 이벤트구간 마킹과 AI 증강 연동 요청이 제공된다. 마킹은 전용 화면에서 수행하며 추출보다 앞서므로 이 시퀀스 안에 그린다. 증강 요청 자리는 업로드 목록의 자산별 액션이고 그것은 이 시퀀스가 그리는 범위 밖이라 별도 흐름으로 그린다. 이 시퀀스의 범위는 업로드와 마킹, 마킹 지점에서의 프레임 추출, 프레임 단위 라벨 저장, 라벨 내보내기와 원본 다운로드다. 마킹은 되돌릴 수 없다 — 재마킹·재추출을 제공하지 않아 회복 경로는 자산을 지우고 다시 올리는 것뿐이며, 자산 삭제가 추출 중에는 거부되므로 잘못 마킹한 사용자는 추출이 끝나기를 기다려야 한다.

조회·수정·삭제·다운로드는 모두 소유자 스코프로만 이뤄지고, 남의 자산이나 남의 업로드 세션을 가리키는 요청은 존재하지 않는 것과 같은 응답을 받아 실재 여부가 응답으로 드러나지 않는다.
