### notes

### 2026-09-03 포털 확정 회신 반영
- 포털이 서버간 연동의 인증과 창구와 저장소 조건을 확정 회신했고 그 내용으로 이 연동점을 신설했다.
- 인증은 두 축(사용자 컨텍스트 · 시스템간)이며 같은 대칭 서명키와 같은 전용 요청 헤더를 쓴다. 별도 API 키 헤더 서술은 포털이 스스로 정정해 폐기했으므로 되살리지 않는다.
- 저작도구 WAS 가 포털 내부망에 배치돼 이 축에는 외부 방화벽 경계가 없다. 포털 연동 축 한정이며 관제 축에는 적용되지 않는다.
- 사용량 보고는 증강 실행 전 차단형이고 실패를 닫는다. 운영 진입 주소 확정 전까지 포털 채널 증강이 비활성이라는 대가를 인지하고 받아들였다.
- 창구 산출물이 없는 제공과 수신 셋은 역할과 인증 축만 기록했다. 없는 식별자를 지어 링크하지 않았다.
- 근거 결정은 채널별 별도 배포 결정(ADR-012)이다. 그 결정이 두 시스템이 주고받을 데이터를 API 로 설계한다고 못박았고 이 연동점이 그 API 축이다. 이 서버간 트랙만을 위한 별도 결정 기록은 아직 없다.

### 2026-09-05 공유 서명키 구조 확정과 집계 대상 범위 확정
- 공유 서명키는 새로 두지 않고 기존 인증 인계 축의 대칭 키를 그대로 쓴다. 주체 클레임으로 두 축을 가르는 형태가 이미 그 축의 구조와 같다.
- 확정된 것은 구조이고 값 교환은 남아 있다. 미교환을 지우지 않고 성격이 바뀐 것으로 적었다. 둘을 섞어 해결됨으로 적으면 배포 시점에 값이 없는 채로 발견된다.
- 서명키가 설정값이라 구현을 막지 않는다는 귀결을 함께 적었다. 값 부재는 실동작 조건이지 구현 착수 조건이 아니다.
- 포털이 말한 키가 지금 우리 검증 키와 같은 값인지는 확인되지 않아 남은 확인 항목으로 명시했다. 같다고도 다르다고도 단정하지 않았다.
- 일일 저작 집계의 대상 범위는 포털 회원의 작업으로 닫혔다. 채널별 배포본 합산을 전제하던 서술은 폐기다.
- 인증 두 축 서술과 창구 구성 표는 손대지 않았다.

### 2026-09-05 창구 산출물 실재 반영
- 제공과 수신 셋의 창구 산출물이 실재하게 되어 본문과 창구 구성 표의 부재 서술을 갱신했다. 구 서술은 갱신 표기로 남겼으며 존재 여부의 축만 지목하고 원문을 인용하지 않았다.
- 창구가 계약을 소유한다는 규칙은 그대로 두었다. 요청과 응답 계약을 이 연동점으로 옮겨 적지 않았다.
- 세 창구를 가리키는 자리는 위키링크 표기로 적어 간선이 실제로 생기게 했다. 본문의 평문 번호는 간선을 만들지 않는다.
- 인증 두 축 표와 창구 구성 표의 나머지와 소재 조달과 저장소와 통신 경계 서술은 손대지 않았다.

### 2026-09-09 주체 축 격리 규칙 수립과 시스템 주체 판정 규격 확정
- 주체 축 격리를 창구별 서술이 아니라 연동 축의 규칙으로 세웠다. 창구마다 개별로만 적혀 있으면 창구가 늘 때마다 같은 자리가 다시 빠진다.
- 격리를 양방향으로 못박고 시스템 주체 토큰이 못 들어가는 범위를 서버간 축의 사용자 창구 하나가 아니라 포털 사용자 채널 전체로 넓혔다. 시스템 주체 토큰이 특정 사용자를 가리키지 않아 소유자 비교가 의미를 잃은 채 통과하기 때문이다.
- 개별 창구의 응답 코드 값은 옮겨 적지 않았다. 그 계약은 창구 산출물이 소유한다.
- 시스템 주체 판정 규격을 열린 항목에서 확정으로 옮겼다. 배포 설정으로 주어지는 시스템 계정 주체 식별자 목록이며 비어 있으면 시스템 주체 창구가 닫힌다. 값이 없을 때 닫히는 방향이라 안전하고 설정값이라 구현을 막지 않는다.
- 이 규격의 정본은 이 연동점이고 창구 산출물은 가리키기만 한다. 저작도구 측 확정이며 포털의 수락 회신은 오지 않았다는 사실을 섞지 않고 따로 적었다.
- 통신 경계와 저작도구가 부르는 것과 소재 조달과 작업 저장소와 식별자 표기와 서명키 서술은 손대지 않았다.

### 2026-09-09 인증 축이 창구마다 갈린다
- 포털 회신에 따라 정리 삭제 트리거 창구의 인증을 사전 공유 API 키로 바꿨다. 근거는 포털의 기존 시스템간 연동 방식과 같다는 것이고 관제지원 수신 채널도 그 방식을 쓴다.
- 같은 축이 두 번 뒤집혔다. 구 서술과 그 폐기 경위를 지우지 않고 반전 사실을 표기했다. 세 번째 반전이 오면 그 기록이 판단 근거가 된다.
- 키는 저작도구가 생성해 안전 채널로 포털에 공유하며 관제지원 수신 채널이 쓰는 키와 섞지 않는다. 연동 축마다 별도 키를 두라는 포털의 명시 요청이다.
- 일일 저작 집계 창구의 인증 수단은 회신에 없어 미확정으로 명시하고 지어내지 않았다. 포털에 되물을 항목이다.
- 주체 축 격리 규칙은 지우지 않고 적용 범위를 갈랐다. 토큰 축의 창구에서는 그대로 성립하고 API 키 창구에서는 격리를 푸는 것이 아니라 격리할 대상이 없어진다. 그 창구에는 시스템 계정 토큰 자체가 없기 때문이다.
- 정리 삭제 트리거의 호출 시점이 좁혀졌다. 포털이 버전 문자열이 기존 저장값과 다를 때만 부르므로 저작도구는 버전 순서 비교가 필요하지 않다. 포털 내부 판정 로직은 복제하지 않았다.
- 본문 설명 필드는 길이 상한에 거의 닿아 있어 새 서술을 넣을 자리를 만드느라 주체 축 격리와 시스템 주체 판정의 문장을 압축했다. 주장은 하나도 빼지 않았고 상세 근거는 스펙 본문의 표가 그대로 보유한다.
- 공유 서명키 서술과 통신 경계와 저작도구가 부르는 것과 소재 조달과 작업 저장소와 식별자 표기는 그대로 두고 서명키의 적용 범위만 토큰 축으로 명시했다.

### 2026-09-09 일일 저작 집계 인증 확정과 소재 조달 규격 등재
- 일일 저작 집계의 인증을 정리 삭제 트리거와 같은 사전 공유 API 키로 확정했다. 키도 같은 키다. 직전 라운드에서 이 창구를 미확정으로 둔 것은 근거가 없어서였고 이제 근거가 생겨 미확정을 닫는 것이라 판단을 뒤집는 것이 아니다. 그 구분을 본문에 적었다.
- 경로 접두 전체가 한 인증 수단이 되어 창구마다 인증을 가를 필요가 없어졌다. 다만 접두 아래 창구가 늘어도 권한을 부여하는 판정은 창구를 정확히 지목하므로 새 창구를 열 때 그 지목 대상을 함께 넓히지 않으면 인가 요구는 걸리는데 권한을 세울 자가 없어 전건 거부된다. 닫히는 방향이라 안전하나 누락하면 조용히 안 되므로 사양에 남겼다. 코드 심볼이나 파일 경로로 적지 않고 사양 어휘로만 적었다.
- 소재 조달 창구의 규격을 등재했다. 방향이 반대라는 것을 먼저 못박았다. 정리 삭제 트리거는 포털이 우리를 부르지만 소재 조회는 우리가 포털을 부른다. 읽는 쪽이 가장 자주 혼동하는 지점이다.
- 그 창구를 번호로 부르지 않고 경로와 역할로만 식별했다. 포털 회신이 쓴 번호는 포털 프로젝트의 번호이며 우리 번호 공간과 겹쳐 같은 번호가 서로 다른 것을 가리킨다. 이 연동점이 이미 갖고 있던 식별자 표기 규칙을 그대로 지켰다. 그 창구는 포털이 소유하고 우리가 호출하는 쪽이라 우리 쪽 창구 산출물을 새로 만들지도 않았다.
- 담은 것은 응답 스키마의 복제가 아니라 우리가 그 창구를 부를 때 지켜야 할 계약면과 우리 쪽 규칙이다. 스키마 소유는 포털이라는 기존 규칙과 충돌하지 않도록 그 구분을 본문에 밝혔다.
- 우리 쪽 규칙 셋을 설계로 못박았다. 받은 절대경로를 그대로 열지 않고 응답이 함께 준 저장소 루트 하위인지 실경로로 재검증한 뒤 그 실경로로 연다. 검증한 경로와 여는 경로가 갈리면 그 사이에 바꿔치기가 들어온다. 공유 저장소 마운트가 전제인데 그 배포본의 저장소는 포털이 관리하는 별도 저장소로 정해져 있어 우리가 실제로 마운트하는지는 확인되지 않았다. 성립한다고 단정하지 않았다. 코드와 소재 구분은 비어 올 수 있으므로 실패로 다루지 않는다.
- 두 창구가 서로 이어지지 않는다는 것을 열린 항목으로 명시했다. 트리거는 데이터셋 코드를 싣고 오는데 소재 조회는 숫자 식별자를 요구하며 코드로 찾는 창구가 없다. 응답의 코드 필드는 결과일 뿐 조회 키가 아니고 비어 올 수 있어 역매칭도 신뢰할 수 없다. 해소 방향 둘을 적되 어느 쪽으로 정했다고 쓰지 않았다. 상호 확정 대상이며 추정으로 잇는 규칙을 만들지 않았다.
- 한 산출물 안의 모순을 정합했다. 전송 메타의 부재 서술이 본문과 스펙의 실재 서술과 어긋나 있었다. 실재로 갱신하고 우리가 부르는 창구에 소재 조회를 더했다.
- 본문 설명 필드가 상한에 닿아 자리를 만들었다. 도입부의 세 번째 문장은 이 브라운필드 요약이 같은 주장을 그대로 보유하므로 덜어냈고, 주체 축 격리와 시스템 주체 판정과 제공 수신 머리말과 소재 조달을 압축했다. 주장은 하나도 빼지 않았고 상세는 스펙 본문이 보유한다. 열린 항목의 운영 진입 주소 두 줄은 같은 항목이라 한 줄로 합쳤다.
- 공유 서명키 절과 통신 경계와 작업 저장소와 사용량 보고 되돌림과 식별자 표기와 정리 트리거 호출 시점은 손대지 않았다.

### 2026-09-15 조달 뒤 원장 등록 단계 반영
- 소재 조달 뒤에 원장 등록 단계가 이어진다는 서술과, 배포 압축본 내부 구성이 가정이라는 열린 항목을 스펙 본문에 더했다. 결정의 정본은 ADR-068 이고 이 연동점은 가리키기만 한다.
- 본문 설명 필드는 상한 4000자 중 3995자라 참조를 넣을 자리가 없었다. 기존 문장을 압축해 자리를 만들지 않고 설명 필드는 그대로 두었다.
- 트리거 키와 조회 키가 이어지지 않는다는 기존 열린 항목은 해소하지 않았다.

### notes

인증은 두 축이며 둘 다 같은 대칭 서명키를 공유하고 같은 전용 요청 헤더로 실린다. 사용자 컨텍스트 축은 토큰 주체가 사용자이고 사용자 세션이 살아 있는 호출에 쓴다. 시스템간 축은 토큰 주체가 시스템 계정이고 배치나 비동기라 사용자 세션이 없는 호출에 쓴다. 주체 구분은 토큰의 주체 클레임이 한다. 주체 축 격리는 양방향이라 사용자 주체 토큰은 시스템 주체 창구에 들어가지 못하고 시스템 주체 토큰은 포털 사용자 채널의 어느 창구에도 들어가지 못하며, 시스템 주체 토큰은 포털 사용자 권한을 얻지 못한다. 무엇이 시스템 계정인지는 배포 설정으로 주어지는 시스템 계정 주체 식별자 목록이 정하고 그 목록이 비어 있으면 아무도 시스템 주체가 아니어서 시스템 주체 창구가 닫힌다. 이 판정 규격의 정본은 이 연동점이다. Bearer 스킴을 쓰지 않으므로 인증 유형은 그 밖으로 둔다. 인증 수단은 창구마다 갈린다. 저작 현황 요약은 위 사용자 주체 토큰이고, 배포본 정리 삭제 트리거는 헤더 x-api-key 에 실린 사전 공유 고정 문자열을 상수시간으로 값 비교하는 API 키 축이라 서명도 만료도 주체 클레임도 없다. 그 키는 저작도구가 생성해 안전 채널로 포털에 공유하고 관제지원 수신 채널이 쓰는 키와 섞지 않는다. 연동 축마다 별도 키를 두어 한 축이 유출돼도 다른 축으로 번지지 않게 한다. 일일 저작 집계도 정리 삭제 트리거와 같은 사전 공유 API 키 헤더로 인증하며 같은 키를 쓴다. 연동 축 하나에 키 하나다. 직전에 이 창구를 미확정으로 둔 것은 근거가 없어서였고 이제 근거가 생겨 미확정을 닫는 것이라 판단을 뒤집는 것이 아니다. 그 귀결로 이 경로 접두 전체가 한 인증 수단이 되어 창구마다 인증을 가를 필요가 없다. 다만 접두 아래 창구가 늘어도 권한을 부여하는 판정은 창구를 정확히 지목하므로, 새 창구를 열 때 그 지목 대상을 함께 넓히지 않으면 인가 요구는 걸리는데 권한을 세울 자가 없어 전건 거부된다. 열리는 방향이 아니라 닫히는 방향이라 안전하나 누락하면 조용히 안 된다. 구 서술인 별도 API 키 헤더는 쓰지 않는다는 폐기다. 그 근거는 포털이 자기 문서에 한때 그렇게 적었다가 정정해 폐기한 값이라는 것이었는데, 포털이 자기 기존 시스템간 연동 방식과 같다는 근거로 그 방식으로 돌아왔다. 같은 축이 두 번 뒤집혔으므로 경위를 남긴다. 주체 축 격리는 토큰 축의 창구에만 성립한다. API 키 창구에서는 격리를 푸는 것이 아니라 격리할 대상이 없어진다. 그 창구에는 시스템 계정 토큰 자체가 없기 때문이다. 아래 공유 서명키 서술도 토큰 축의 창구에만 해당하며 정리 삭제 트리거 창구는 API 키 값 교환으로 대체된다. 서명키는 새로 두지 않고 기존 인증 인계 축이 쓰는 대칭 키를 그대로 쓴다. 구조가 확정된 것이고 키 값을 주고받는 일은 배포 시점 설정으로 남아 있다. 설정값이라 구현을 막지 않는다. 포털이 말한 그 키가 지금 우리 검증 키와 물리적으로 같은 값인지는 확인되지 않았다.

## data_format

json

## description

포털과 저작도구 사이의 서버간 연동이다. 브라우저 안에서 두 화면이 함께 실행되는 프론트엔드 런타임 임베딩(INT-013)과는 다른 축으로, 두 시스템의 서버가 서로의 창구를 직접 호출한다.

## 배치와 통신 경계
저작도구 WAS 는 포털 기반 구성의 구성자원으로 **포털 내부망**에 배치된다(각 자원 2식 동시 가동). 그래서 이 축의 모든 호출이 내부망 통신이라 **외부 방화벽 경계가 없고** 종전 준비하려던 방화벽 값(WAS 호스트명 · 대역 · 수신 포트 · 송신 주소)이 필요하지 않다. ⚠ **포털 연동 축 한정**이며 관제 연동 축의 방화벽 요건은 이와 무관하게 그대로다.

## 인증 — 수단이 창구마다 갈린다
저작 현황 요약은 **사용자 주체 토큰**(전용 요청 헤더)이고, 배포본 정리 삭제 트리거와 일일 저작 집계는 **사전 공유 API 키 헤더 `x-api-key`**(둘이 **같은 키**)다. 토큰 축은 주체 클레임으로 사용자와 시스템 계정을 가르고 Bearer 를 쓰지 않으며, 아래 공유 서명키 서술은 이 축 한정이다. API 키 축의 상세(상수시간 비교 · 서명 만료 주체 클레임 부재 · 저작도구가 생성해 공유 · 관제지원 수신 채널 키와 **섞지 않음**)는 스펙 본문 표가 정본이다.

⚠ **[반전] 「별도 API 키 헤더를 쓰지 않는다」는 폐기다.** 두 번 뒤집힌 축이라 그 경위는 스펙 본문이 그대로 보유한다.

**공유 서명키는 새로 두지 않는다 — 기존 인증 인계 축의 그 대칭 키를 그대로 쓴다.** 두 축이 같은 키를 공유하고 주체 클레임으로 갈리는 형태가 이미 그 축의 구조와 같기 때문이다. ⚠ **구조가 확정된 것이지 키 값이 오간 것이 아니다** — 값 교환은 배포 시점 설정으로 남아 있으니 둘을 섞어 「해결됐다」로 읽지 말 것. ★ **설정값이라 구현을 막지 않는다** — 값 부재는 실동작 조건이지 착수 조건이 아니라, 코드를 먼저 만들고 값은 배포 시점에 채운다.

### 주체 축 격리 · 시스템 주체 판정 — **정본은 스펙 본문의 같은 이름 두 표**
격리는 **양방향 · 토큰 축 한정**이라 시스템 주체 토큰은 포털 사용자 채널 어디에도 못 들어가 포털 사용자 권한을 얻지 못하고, ★ API 키 창구에서는 격리를 「푸는」 것이 아니라 **대상이 없어진다**. 판정 기준은 **배포 설정의 시스템 계정 주체 식별자 목록**이며 ★ **비면 그 창구가 닫혀** 안전하다. ⚠ **포털의 수락 회신은 아직 오지 않았다.**

## 저작도구가 부르는 것 — 포털이 제공한다
- **AI 사용량 보고** — 증강 실행 전에 부르는 차단형이다. 계상 단위는 요청 1건당 1이며 프레임 장수·증강 종류 수와 무관하다(근거 — 포털 한도 상수가 일일 최대 **요청 수**라, 장수로 곱하면 한 번에 소진돼 집행형 한도가 무의미해진다).
  - **실패를 닫는다** — 서버 오류·시간 초과로 보고가 성립하지 않으면 증강을 진행하지 않는다. ⚠ 그 귀결로 운영 진입 주소 확정 전까지 포털 채널 증강은 비활성이며, 이것은 부작용이 아니라 인지하고 받아들인 대가다.
  - 본인이 업로드한 영상의 증강도 계상한다 — 소재가 인계 데이터든 본인 업로드든 연산 자원을 쓴다.
- **사용량 되돌림** — 위탁 실패·취소 시 차감을 되돌린다. 비동기라 사용자 세션이 만료됐을 수 있어 **시스템간 축**으로 부르고, 대상 사용자는 작업 참조값으로 역참조한다.

## 저작도구가 제공하고 수신하는 것
**[갱신] 아래 셋은 창구 산출물이 실재하며**(구 서술은 반대) 그 산출물이 요청·응답 계약을 소유한다. 이 절은 역할·인증 축만 유지하고 스키마를 옮겨 적지 않는다.

- **저작 현황 요약 제공** ([[API-242]]) — 사용자 컨텍스트 축. 포털 화면이 사용자 식별자를 넘겨 부르면 최근 작업 한 건의 이름 · 상태 · 마지막 저장 시각을 돌려주고 **진행률과 개별 진입 링크는 넣지 않는다**. 오늘 남은 AI 사용량은 포털이 자체 계산하므로 공급하지 않는다.
- **일일 저작 집계 제공** ([[API-243]]) — 시스템간 축. 포털 배치가 한국 표준시 경계로 가져가며, 저작도구는 조회 창구만 열고 수신 주소·재시도는 포털이 관리한다.
- **배포본 정리 삭제 트리거 수신** ([[API-244]]) — API 키 축. 포털이 **버전 문자열이 기존 저장값과 다를 때만** 부르므로 버전 순서 비교가 필요 없다.

## 소재 조달 — ★ 우리가 포털을 부른다
★ **방향이 반대다**(정리 삭제 트리거는 그 반대다). 데이터셋의 **숫자 식별자**로 소재 경로 목록만 받는다(파일 바이트 없음).

★ **[확정] 조달을 시작하는 키를 얻는 경로가 생겼다.** 포털 화면에서 저작도구 자리로 진입할 때 포털이 **주소의 경로 변수**(`/portal/datasets/{숫자 식별자}`)에 싣고, 저작도구 프론트가 **직접 읽어** 우리 창구로 넘기면 우리 WAS 가 그 값으로 포털 소재 조회 창구를 부른다. ⚠ 포털이 **주입하는 것이 아니라** 우리가 주소에서 읽는다. ⚠ **[폐기] 「주소의 질의 문자열」은 사실과 다르다** — 포털이 실제로 시도했다 되돌린 형태다.

⚠ 창구는 포털 소유라 스키마를 복제하지 않는다. **계약면과 우리 쪽 규칙 넷은 스펙 본문 「소재 조달」 절이 정본**이다.

## 작업 저장소
- 저작도구에 작업영역 쓰기 권한이 부여된다. 포털 소재영역은 읽기 전용으로 분리한다. 읽는 자리와 푸는 자리를 가른다. ★ **[확정] 조달처의 배포 압축본은 포털 소유·관리 원본이라 이동 · 수정 · 삭제 · 덮어쓰기를 하지 않는다** — 우리 자리로 복사해 풀고 **그 사본으로만** 작업한다(건드리면 포털 배포본과 무결성 값이 깨진다). ⚠ **[확정] 공유 저장소를 동일 경로로 마운트**해 경로 재매핑이 필요 없으나 **그것이 실경로 재검증의 면제 사유는 아니다**(스펙 규칙 1·2).
- 해제본 보존 기간은 사용자의 저작 최초 저장 시점부터 7일이고, 삭제 트리거를 받아도 즉시 지우지 않고 **받은 시점부터 다시 7일** 뒤에 지운다(즉시 지우면 사용자가 물고 있는 진행 중 작업이 깨진다).

## 식별자 표기
포털은 별개 프로젝트라 번호 체계가 겹쳐 같은 번호가 양쪽에서 서로 다른 것을 가리킨다. 그래서 이 본문은 포털 창구를 **번호가 아니라 경로와 역할로** 식별하고, 상호 인용이 필요하면 소속 프로젝트를 접두로 밝힌다.

## 열린 항목
- 운영 진입 주소가 미확정이다. 주소 규격은 저작도구가 정의하고 포털이 그 주소로 링크를 걸며, 확정 전까지 포털 채널 증강은 비활성이다. 실제 주소·포트는 기반 구성 확정 시 별도 공유된다.
- **[갱신] 공유 서명키의 구조는 닫혔고 값 교환만 남았다**(상세는 위 「인증」 절).
- **포털이 말한 그 키가 지금 우리 검증 키와 물리적으로 같은 값인지 확인되지 않았다.** 같으면 설정 추가조차 없고 다르면 검증 경로에 분기가 필요하다. 단정하지 말 것.
- **[갱신] 일일 저작 집계의 대상 범위는 닫혔다** — 포털 회원의 작업이다. 그 귀결로 포털 채널 배포본이 자기 저장소만 세면 되고 채널별 합산이 필요 없다(저작도구 전체를 세는 쪽과 합산 전제 구 서술은 폐기). 다만 포털 회원의 작업을 무엇으로 식별하는지는 미정이며 그 계약은 [[API-243]] 이 소유한다.
- ★ **트리거의 키(데이터셋 코드)와 소재 조회의 키(숫자 식별자)가 달라 조달 경로가 이어지지 않는다.** 해소 방향 둘은 **상호 확정 대상이라 정해지지 않았다**(상세는 스펙 「열린 항목」 절). ⚠ 추정으로 잇지 말 것.
- ⚠ **[신규] 미확정 둘** — ① 트리거 **버전 표기의 세 번째 형태**가 관측됐다 ② 지정된 시스템간 키가 두 축에 **공용인지 전용인지 확인되지 않았다**(공용이면 「축마다 별도 키」 원칙상 **잠정**). 둘 다 **상호 확정 대상**이며 근거와 귀결은 스펙 「열린 항목」이 보유한다.
- 저작 화면의 영상 재생 요구가 인계 데이터용인지 본인 업로드 영상용인지 회신해야 한다. 후자라면 단기 서명 주소 창구로 이미 해결돼 있다.

## 저작도구가 여는 창구 — 인증 수단이 갈린다
| 창구 | 인증 수단 | 부르는 쪽 | 넘어오는 값 |
|---|---|---|---|
| 저작 현황 요약 | 사용자 주체 토큰 | 포털 화면 | 사용자 식별자 |
| 일일 저작 집계 | 사전 공유 API 키(정리 트리거와 **같은 키**) | 포털 배치(가져가기) | 기준일(한국 표준시) |
| 배포본 정리 삭제 트리거 | 사전 공유 API 키 | 포털 | 데이터셋 코드 · 버전 |

⚠ **[반전] 정리 삭제 트리거의 인증 수단이 토큰 축에서 사전 공유 API 키로 바뀌었다.** 구 서술 「별도 API 키 헤더를 쓰지 않는다」는 폐기이며, 그 근거였던 「포털이 한때 그렇게 적었다가 정정해 폐기했다」가 포털의 기존 시스템간 연동 방식과 같다는 근거로 뒤집혔다. 두 번 뒤집힌 축이라 경위를 남긴다.
★ **[확정] 일일 저작 집계도 사전 공유 API 키로 인증하며 정리 삭제 트리거와 같은 키를 쓴다** — 연동 축 하나에 키 하나다. 직전 라운드에서 이 창구를 미확정으로 둔 것은 **근거가 없어서**였고, 이제 근거가 생겨 미확정을 닫는 것이라 **판단을 뒤집는 것이 아니다.**

★ **귀결 — 경로 접두 전체가 한 인증 수단이 되어 창구마다 인증을 가를 필요가 없다.** 다만 사양에 남길 것이 하나 있다: 이 접두 아래 창구가 늘어도 **권한을 부여하는 판정은 창구를 정확히 지목**하므로, 새 창구를 열 때 그 지목 대상을 함께 넓히지 않으면 **인가 요구는 걸리는데 권한을 세울 자가 없어 전건 거부**된다. 열리는 방향이 아니라 **닫히는 방향이라 안전하나 누락하면 조용히 안 된다.**

⚠ **[갱신] 이 셋은 창구 산출물이 실재한다** — 저작 현황 요약 [[API-242]] · 일일 저작 집계 [[API-243]] · 배포본 정리 삭제 트리거 [[API-244]]. 그 산출물이 요청과 응답 계약을 소유하며 이 표는 인증 축과 역할만 유지한다. 구 서술은 그 셋의 존재 여부를 반대로 적었다.

## 주체 축 격리 — 양방향, 단 토큰 축 한정
| 토큰 주체 | 들어가는 창구 | 다른 축의 창구에 오면 |
|---|---|---|
| 사용자 | 포털 사용자 채널 접두 아래 | 거부한다 |
| 시스템 계정 | 그 접두 밖의 별도 접두 아래 | 거부한다 |

- **뒤쪽 방향은 포털 사용자 채널 전체에 적용된다.** 서버간 축의 사용자 창구 하나에 그치지 않으며, 시스템 주체 토큰은 포털 사용자 권한을 얻지 못한다.
- 근거 — 시스템 주체 토큰은 특정 사용자를 가리키지 않는다. 토큰 주체를 자원 소유자와 견주어 접근을 가르는 창구에 그 토큰이 도달하면 그 비교가 의미를 잃은 채 통과한다. 한 방향만 막으면 더 위험한 쪽이 열린 채 남는다.
- 경로 접두를 가르는 것이 이 규칙을 강제하는 수단이다. 거부의 응답 값은 각 창구 산출물이 소유하므로 이 표에 옮겨 적지 않는다.
- 검증은 [[AC-1103]] 이 한다.

★ **이 표는 토큰이 인증 수단인 창구에만 성립한다.** 사전 공유 API 키 창구에서는 격리를 「푸는」 것이 아니라 **격리할 대상이 없어진다** — 그 창구에는 시스템 계정 토큰 자체가 없어, 이 규칙이 막던 「시스템 계정 토큰이 포털 사용자 권한을 얻는다」가 성립하지 않는다.

## 소재 조달 — ★ 방향이 반대다
★ **정리 삭제 트리거는 포털이 우리를 부르지만, 소재 조회는 우리가 포털을 부른다.** 읽는 쪽이 가장 자주 혼동하는 지점이라 먼저 못박는다.

| 항목 | 값 |
|---|---|
| 성격 | 데이터셋의 **소재 경로 조회**. 파일 바이트를 싣지 않는다 |
| 방향 | **저작도구 → 포털** (우리가 호출) |
| 조달처 | 포털의 소재 조회 창구 |
| 조회 키 | 데이터셋의 **숫자 식별자**(경로 변수). 숫자가 아니면 없음으로 답한다 |
| 조회 키 조달 | ★ **[확정]** 사용자가 포털 화면에서 저작도구 자리로 **진입할 때 주소의 경로 변수**에 실려 온다 — 우리 라우터 **기준 경로 아래 `/portal/datasets/{데이터셋 숫자 식별자}`** 가 **확정된 진입 경로**다(아래 「진입 경로」 행). 저작도구 **프론트가 그 값을 직접 읽어** 우리 창구로 넘기고, 우리 WAS 가 그 값으로 이 창구를 부른다. ⚠ 포털이 우리에게 **주입하는 것이 아니다** — 우리가 주소에서 읽는다 |
| 진입 경로 | ★ **[확정] `/portal/datasets/{데이터셋 숫자 식별자}` 를 그대로 채택한다**(우리 라우터 기준 경로 `/workspace/authoring` 아래 · 2026-09-10 확정). 포털이 이미 이 주소로 보내고 있어 **추가 조율이 필요 없고**, 우리 관례에 맞춰 다른 모양을 회신하면 양쪽이 각각 고쳐야 하는데 얻는 것이 없다. 참고로 포털은 주소 조립을 **함수 한 곳에 묶어** 두어 변경 비용이 낮다 — ⚠ 이것은 운영 정보이지 **미확정의 근거가 아니다** |
| 풀이 책임 | ★ **[확정] 데이터셋 → 프레임 「풀이」는 저작도구 백엔드가 한다**(2026-09-10 양측). 우리가 이미 가진 포털 진입 규격은 **프레임 단위 둘뿐**이고 그 식별자는 **프레임·업로드 자산 키**라 포털의 데이터셋 숫자 식별자와 **축이 다르다** — 학습데이터 한 건을 통째로 여는 진입이 우리 규격에 **없었고**, 그래서 이 조달이 존재한다 |
| 인증 | ★ **[확정] 사전 공유 키 헤더** + **출발지 주소 허용목록**(포털 내부 창구 전 경로의 공통 보호). ⚠ 저작도구 토큰 계약이 성립하면 토큰 축으로 전환할 수 있으나 **그 전까지는 키**다 |
| 키의 축 | ⚠ **정리 트리거의 키와 다른 축이다** — 이쪽은 **포털이 발급해 우리에게 주는 키**이고, 정리 트리거 키는 **우리가 발급해 포털에 주는 키**다. 섞지 않는다 |
| 응답 봉투 | ★ **우리 표준 응답 봉투를 쓰지 않는다** — 평문 객체 그대로다 |
| 응답 내용 | 데이터셋 식별자 · 코드 · 버전 · 소재 구분 + **저장소 루트 경로** + 소재 파일 목록 |
| 파일 항목 | 파일 식별자 · 구분(배포 압축본 \| 데이터셋 영상) · 파일명 · **공유 저장소 절대경로** · 크기 · 체크섬 |
| 목록 범위 | **원본만** — 썸네일 · 미리보기 같은 파생물은 내려오지 않는다 |
| 오류 | 없는 식별자와 숫자가 아닌 경로변수는 없음 / 키 누락과 불일치는 인증 실패 / 허용목록 밖 출발지는 거부 |
| 구성 | 배포 압축 파일 한 건 + 영상 없거나 여럿 |
| 영상 경로 | 파일 구분이 데이터셋 영상인 행의 절대 경로 |
| 원본 취급 | ★ **[확정] 읽기 전용** — 조달처가 가리키는 배포 압축본은 포털이 소유·관리하는 **원본**이다. 우리는 **사본으로만** 작업한다(아래 규칙 4) |
| 스키마 소유 | 포털. 여기에 복제하지 않는다 |

⚠ **[폐기] 구 서술 「진입 주소의 질의 문자열」은 사실과 다르다.** 그때 근거로 삼은 규격 문서가 **이미 낡은 판**이었다. 포털이 그 방식을 **실제로 시도했다가 되돌렸고**, 그쪽 기록의 요지는 「질의 문자열은 저작도구 라우터 어디에도 걸리지 않아 홈으로 흘렀고, 대상이 넘어가지 않았다는 사실이 화면에 남지도 않았다」이다. ⚠⚠ **사내 운영 문서가 아직 구 규격(질의 문자열)으로 남아 있다** — 사유를 지우면 다음 사람이 그 문서를 근거로 **되돌린다. 되살리지 말 것.**

⚠ **이 표는 포털 응답 스키마의 복제가 아니다.** 창구는 포털이 소유하고 그 스키마의 정본도 포털이다. 여기 담는 것은 **우리가 그 창구를 부를 때 지켜야 할 계약면과 우리 쪽 규칙**이며, 그 구분을 지켜 개별 필드 정의를 옮겨 적지 않는다.

### 우리 쪽 규칙 — 설계로 못박는다
1. ★★ **받은 절대경로를 그대로 열지 않는다 — 그리고 그 판정의 기준점을 상대 응답에서 가져오지 않는다.** 외부가 준 경로를 우리가 파일 시스템에서 여는 구조라, ① 응답이 준 **저장소 루트가 배포 설정이 정한 허용 루트 목록 하위인지** 먼저 보고 ② 그 **교집합 하위인지 실경로로 재검증한 뒤** ③ **그 실경로로** 연다. 어긋나면 열지 않는다(fail-closed). 검증한 경로와 실제 여는 경로가 달라지면 그 사이에 바꿔치기가 들어온다.
   - ⚠⚠ **기준점이 봉쇄 대상과 같은 출처면 봉쇄가 아니다.** 「응답이 함께 준 저장소 루트 하위인지」만 보는 구 서술은 **상대 응답을 조작할 수 있는 쪽에게는 아무것도 막지 못한다** — 저장소 루트를 최상위 경로(`/`)로, 소재 경로를 아무 시스템 파일로 주면 표기 · 실경로 · 정규 파일 판정을 **전부 통과**해 우리가 그 파일을 열어 작업영역으로 복사한다. 그래서 기준점은 **우리가 아는 값**, 즉 배포 설정이 정한 허용 루트 목록이어야 한다.
   - **허용 루트 목록이 비어 있으면 조달이 닫힌다.** 값이 없을 때 열리는 것이 아니라 **닫히는** 방향이며, 이 연동점이 시스템 주체 판정에서 이미 쓰는 방향과 같다.
   - ⚠ **기존 판정 단계(표기 · 실경로 · 정규 파일)는 그대로 둔다.** 이 개정은 그 **앞에 기준점 검사를 한 겹 더 두는 것**이지 기존 단계를 대체하지 않는다. 「일관성」을 이유로 합치지 말 것.
   - ⚠ **마운트 동일성은 이 검사의 면제 사유도 아니다** — 규칙 2 옆의 경고와 동형이다. 마운트가 같아도 **응답이 가리키는 자리는 응답이 정한다.**
   - ⚠ **회귀 가드의 축을 틀리지 말 것.** 대역 응답으로 저장소 루트를 주입하면 「응답이 준 루트」를 기준으로만 봉쇄를 증명하게 되어 **시험이 설계와 같은 공백을 갖는다.** 가드는 **응답이 최상위 경로나 우리 저장소 루트를 저장소 루트로 주장해도 거부되는** 축으로 세운다.
2. ★ **[확정] 공유 저장소를 동일 경로로 마운트한다.** 경로가 로컬 절대경로이므로 포털과 우리 포털 채널 배포본이 같은 저장소를 **같은 경로로** 봐야 성립하는데, 포털이 **동일 저장소를 동일 경로로 마운트한다고 확정 회신**했다. 그 귀결로 **경로 재매핑이 필요 없다.** ⚠ **[갱신]** 구 서술 「그 배포본의 저장소는 포털이 관리하는 별도 저장소로 정해져 있어 우리가 실제로 마운트하는지 확인되지 않았다」는 **확정으로 닫혔다.**
   - ⚠⚠ **마운트 동일성은 규칙 1(실경로 재검증)의 면제 사유가 아니다.** 마운트가 같아도 **외부가 준 경로를 그대로 여는 것은 여전히 위험하다.** 「마운트가 같으니 검증이 불필요하다」로 읽지 말 것 — 규칙 1 은 그대로 살아 있다.
3. **코드와 소재 구분은 비어 올 수 있다** — 수신 원장 없이 적재된 옛 데이터가 그렇다. 비어 있다고 실패로 다루지 않는다.
4. ★★ **[확정] 원본은 읽기 전용이고 사본으로 작업한다.** 조달처가 가리키는 배포 압축본은 **포털이 소유·관리하는 원본**이라 **이동 · 수정 · 삭제 · 덮어쓰기를 하지 않는다.** 우리가 관리하는 자리로 **복사해 풀고 그 사본으로만** 작업한다. 원본을 건드리면 포털의 배포본과 무결성 값이 깨진다. 이것이 「포털 소재영역은 읽기 전용으로 분리하고 **읽는 자리와 푸는 자리를 가른다**」의 조달 축 적용이다.

### 조달 뒤 단계 — 원장 등록
소재가 준비되면 **같은 백그라운드 작업이 이어서** 해제본의 영상 · 프레임 · 원본 라벨을 공용 원장에 등록한다. 출처는 **`PORTAL_DATASET`** 이고 **검수 상태를 두지 않으며**, 등록 상태(진행 중 · 완료 · 실패)는 원장 표가 아니라 **해제본 옆 표식**으로 나타낸다. 상세 결정은 [[ADR-068]] 이 소유한다.

## 열린 항목 — 두 창구가 서로 이어지지 않는다
| 항목 | 값 |
|---|---|
| 트리거가 싣고 오는 것 | 데이터셋 **코드**(문자열) · 버전 |
| 소재 조회가 요구하는 것 | 데이터셋의 **숫자 식별자** |
| 잇는 수단 | **없다** — 코드로 찾는 창구가 없다 |
| 역매칭 | 신뢰할 수 없다. 소재 조회 응답의 코드 필드는 **결과일 뿐 조회 키가 아니고**, 게다가 **비어 올 수 있다** |

★ **귀결 — 트리거를 받아 조달을 시작하는 경로가 성립하지 않는다.**

⚠ **[구분] 사용자 진입 경로가 생긴 것과 혼동하지 말 것.** 주소의 경로 변수로 숫자 식별자를 받는 **사용자 진입 경로로는 조달이 성립**하지만, 이 항목이 말하는 **정리 트리거 구동 경로는 여전히 성립하지 않는다** — 트리거는 데이터셋 코드를 싣고 오고 조달은 숫자 식별자를 요구하며 잇는 수단이 없다. **이 항목은 해소되지 않았다.**

해소 방향은 둘이다. ① 정리 트리거 본문에 **숫자 식별자를 함께 싣는다** ② **코드로 찾는 조달 창구를 연다**. ⚠ **상호 확정 대상이라 어느 쪽으로도 정해지지 않았다** — 어느 한쪽으로 정해진 것처럼 적지 말 것. ⚠⚠ **추정으로 잇는 규칙을 만들지 말 것.**

## 열린 항목 — 버전 표기와 키 공용 여부
| 항목 | 값 |
|---|---|
| 버전 표기 관측 | 트리거가 실어 온 값으로 **접두 없는 세 자리 형태**(예: `11.0.0`)가 **실제로 관측됐다**(2026-09-10 수신) |
| 같은 축 | 앞서 물어 둔 표기 차이(`v3` 대 `v3.0`)와 **같은 축**이며, 이것이 **세 번째 표기**다 |
| 접수 영향 | **없다** — 접수는 버전 문자열을 **원문 그대로 보존**하므로 무해하다 |
| 위험 | 트리거가 말한 버전의 **소재를 찾을 때** 표기가 갈리면 **매칭이 깨진다** |
| 결정 주체 | ⚠ **표기 규칙을 우리가 정하지 않는다 — 상호 확정 대상이다** |
| 시스템간 키 값 | 협의에서 WAS 간 통신용 키로 한 값이 지정됐으나, 그것이 **두 축(정리 트리거 수신 · 소재 조회 호출)에 공용인지 한 축 전용인지 확인되지 않았다** |
| 그 귀결 | 이 연동점의 원칙은 **「연동 축마다 별도 키」**이므로 **공용이라면 그것은 잠정**이다. ⚠ **공용이라고도 전용이라고도 단정하지 말 것** |
| 키의 축은 별개 | ⚠ 위 두 축은 **발급 주체가 반대다** — 정리 트리거 키는 **우리가 발급해 포털에 주고**, 소재 조회 키는 **포털이 발급해 우리에게 준다**. 값이 같아 보여도 이 축을 섞지 말 것 |

## 열린 항목 — 배포 압축본 내부 구성
⚠ **배포 압축본의 내부 구성은 확정 서술이 없어 우리 검수 승인 산출물 구조로 가정했다**(근거와 구조가 다를 때의 동작은 [[ADR-068]]). 실제 샘플을 받으면 이 가정을 개정한다.
