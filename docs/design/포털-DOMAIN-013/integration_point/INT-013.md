## data_format

## description

포털(외부 채널) 화면 안에 저작도구 프론트엔드를 런타임으로 끼워 넣는 연동이다. 포털이 Host, 저작도구가 Remote 이며 두 번들이 같은 브라우저 문서에서 함께 실행된다.

**이 항목은 포털 측이 내린 결정을 인지·기록하는 것이지, 저작도구가 그 방식을 수용 확정했다는 뜻이 아니다.** 저작도구 쪽에는 이 연동을 결정한 문서가 없다.

## 확정 사실 (포털 측)
- 포털이 자기 프로젝트의 결정 문서로 Host/Remote 구조를 확정하고 연동점으로 등록했다. 저작도구는 Remote 를 제공하는 쪽이다.
- 포털은 통합 지점을 작업공간 하위의 저작도구 경로 한 곳만 두고, 그 영역 안의 화면 내용은 저작도구 화면정의서를 정본으로 삼는다고 명시한다.
- 그 영역에 대응하는 저작도구 화면은 SCREEN-028(포털 홈) · SCREEN-029(포털 라벨링) · SCREEN-033(포털 업로드) · SCREEN-034(포털 업로드 라벨링) 네 건이다.
- 포털이 스스로 규정하는 범위는 마운트 조건(로그인 상태 · 데스크톱 폭)과 영역 밖 상태화면(비로그인 잠금 안내 · 데스크톱 전용 안내)뿐이다.
- 저작도구 정적 자원은 포털 웹서버가 **같은 출처의 하위 경로**로 서빙한다. 저작도구 백엔드가 별도 서버로 분리되어도 이 사실은 바뀌지 않아 교차 출처 설정이 필요 없다.
- 번들은 **로그인된 사용자에게만** 로드된다 — 비로그인 분기는 Host 가 먼저 처리하고 저작도구 안에 또 하나의 인증 분기를 두지 않는다.
- 번들 로드·실행 오류는 Host 와 같은 문서에서 발생하므로 **오류 경계를 두는 것이 규정돼 있다**.
- 포털 채널이 쓰는 저작도구 API 는 브라우저가 **같은 출처로 직접 호출**한다.

## 협의 대상 — 미결
1. **셸 소유권** — 포털은 「포털 셸 + 그 안의 저작도구 영역」을 전제하며, 그 전제는 포털이 다른 통합 방식을 기각할 때 든 첫 번째 근거이기도 하다(두 셸이 겹치는 문제). 반면 저작도구의 포털 채널 화면 네 건은 자체 셸(SHELL-002)과 자체 내비게이션(NAV-002)을 갖는 독립 앱으로 설계돼 있어, 설계 층위에서는 셸이 두 벌 겹친다. 다만 그 채널 셸이 실제로 그리는 것은 제목과 사용자 표시가 놓인 머리 영역 한 줄뿐이고 내비게이션 영역도 두지 않으므로 **겹치는 표면 자체는 좁다**. 저작도구가 화면 전체를 차지하는 방식은 포털 설계에 서술이 없다.
2. **스타일 격리** — 두 번들이 같은 문서에 마운트되는데 스타일 충돌을 막는 규정이 양쪽 설계 어디에도 없다.
3. **공유 라이브러리 협상** — 렌더링 라이브러리를 한 벌만 쓸지 각자 쓸지 정한 바가 없다. 포털의 결정 문서는 "동일 기술 스택"을 전제로 삼는데, 저작도구 프론트엔드는 **납품본과 기준 구현본이 나뉘어 있고 둘의 주 버전이 서로 다르다**. 따라서 그 전제의 성립 여부는 **어느 쪽을 Remote 로 삼느냐에 달려 있어**, 정해지기 전에는 성립한다고도 아니라고도 말할 수 없다. 포털 결정 문서 자신이 "한쪽만 업그레이드할 수 없다"를 부정적 귀결로 적고 있으므로 어느 쪽을 택하든 이후 버전 정책이 두 시스템에 함께 묶인다.
4. **디자인 토큰** — 주색이 서로 다르다(포털은 코발트 계열, 저작도구는 정부 디자인시스템 정본값). 기준 단위 환산도 양쪽 설계가 확정하지 않았다. 채널마다 다른 팔레트로 떠야 한다면 색을 고정값으로 박아 둘 수 없고 토큰으로 분리해야 하며, 그 토큰을 언제 주입하느냐는 Remote 를 채널별로 산출하는지 한 벌로 산출하는지에 따라 갈린다.
5. **토큰 인계 방식** — 포털 쪽 서술이 두 갈래다(부모가 속성으로 내려주는 방식 / 요청 헤더로 싣는 방식). 저작도구의 인계 결정은 같은 출처 브라우저 저장소를 통한 인계이고, 그 결정이 검토한 선택지에 속성 전달 방식은 없었다(저장소 공유 채택 · URL 질의 문자열 기각 · 시스템 간 인증 기각). 그 결정이 전제한 "채널별 별도 배포"와 한 문서에 함께 실리는 임베딩은 전제가 달라, 금지도 허용도 아닌 미고려 방식이다. 새 결정 문서 또는 기존 결정 개정이 필요하다.

6. **동일 Remote 재사용 전제** — 포털 결정 문서는 같은 Remote 를 포털과 관제 양쪽 Host 가 재사용하는 것을 이점으로 든다. 그런데 두 채널의 배포 대상이 서로 다른 서버라면 Remote 산출물이 두 벌이 되어 그 이점은 성립하지 않는다. 통합 방식 선택 자체를 뒤집는 사유는 아니지만(캔버스 이벤트 간섭 회피·독립 배포·화면 일관성 근거는 그대로다) 포털에 알려야 할 사안이다.
7. **Host 로의 이탈 경로** — 저작도구는 인증 실패·권한 없음·토큰 만료를 자기 화면 이동과 상위 시스템 이동으로 처리한다. Host 안에 마운트되면 그 이동이 Host 문서 전체에 걸려, 저작도구 쪽 인증 분기가 Host 화면을 예고 없이 이탈시킨다. Host 가 처리하도록 위임하는 규약이 필요하다.

## 인증
인계되는 것은 상위 시스템이 발급한 서명 토큰이며 저작도구가 발급하지 않는다. 다만 그 토큰을 어디에 실어 넘길지가 위 5번으로 미확정이라, 인증 수단은 정해졌고 전달 위치는 정해지지 않은 상태다.

## 참조 주의
포털은 별개 프로젝트라 식별자 체계가 저작도구와 겹치지 않는다. 위에서 「포털 측」이라고 밝힌 문서는 모두 포털 프로젝트의 것이며, 같은 번호의 저작도구 항목과는 다른 문서다.
