### notes

상위 시스템이 발급한 서명 토큰을 인계받으며 저작도구가 발급하지 않는다. 포털 채널은 Host 가 주입한 인계 창구(토큰 획득 · 갱신 · 인증 실패 통지 · 활동 통지)에서 토큰을 얻어 전용 요청 헤더 x-access-token 으로 싣는다. Bearer 스킴을 쓰지 않으므로 auth_type 은 other 다. access token 은 Host 메모리에만 두고 브라우저 저장소에 쓰지 않는다. 내부 채널은 같은 출처 브라우저 저장소에서 서명 토큰을 넘겨받는 기존 방식을 그대로 쓰며, 저작도구는 그 직접 읽기를 토큰 획득 창구 뒤로 추상화해 두 Host 를 분기 없이 지원한다.

## description

포털(외부 채널) 화면 안에 저작도구 프론트엔드를 런타임으로 끼워 넣는 연동이다. 포털이 Host, 저작도구가 Remote 이며 두 번들이 같은 브라우저 문서에서 함께 실행된다.

저작도구 쪽에는 이 연동을 결정한 문서가 따로 없다 — 아래 「저작도구 측 결정」이 그 자리다.

## 확정 사실 (포털 측)
- 포털이 자기 프로젝트의 결정 문서로 Host/Remote 구조를 확정하고 연동점으로 등록했다. 저작도구는 Remote 를 제공하는 쪽이다.
- 포털은 통합 지점을 작업공간 하위의 저작도구 경로 한 곳만 두고, 그 영역 안의 화면 내용은 저작도구 화면정의서를 정본으로 삼는다고 명시한다.
- 그 영역에 대응하는 저작도구 화면은 SCREEN-028(포털 홈) · SCREEN-029(포털 라벨링) · SCREEN-033(포털 업로드) · SCREEN-034(포털 업로드 라벨링) 네 건이다.
- 포털이 스스로 규정하는 범위는 마운트 조건(로그인 상태 · 데스크톱 폭)과 영역 밖 상태화면(비로그인 잠금 안내 · 데스크톱 전용 안내)뿐이다.
- 저작도구 정적 자원은 포털 웹서버가 **같은 출처의 하위 경로**로 서빙한다. 저작도구 백엔드가 별도 서버로 분리되어도 이 사실은 바뀌지 않아 교차 출처 설정이 필요 없다.
- 번들은 **로그인된 사용자에게만** 로드된다 — 비로그인 분기는 Host 가 먼저 처리하고 저작도구 안에 또 하나의 인증 분기를 두지 않는다.
- 번들 로드·실행 오류는 Host 와 같은 문서에서 발생하므로 **오류 경계가 규정돼 있다**.
- 포털 채널이 쓰는 저작도구 API 는 브라우저가 **같은 출처로 직접 호출**한다.

## 저작도구 측 결정

- **셸 소유권 — 포털 셸 안으로 들어간다.** 포털이 규정한 「포털 셸 + 그 안의 저작도구 영역」 구조를 그대로 받는다. 저작도구 포털 채널의 머리 영역(SHELL-002)은 렌더하지 않는다. 다만 **그 구성을 지우지 않고 끄기만 한다** — 화면 전체를 차지하는 방식으로 뒤집히더라도 되돌릴 수 있어야 하고, 되돌릴 때 초점 표시·링크 접근성 처리까지 재현돼야 하기 때문이다.
- **Remote 로 내보내는 산출물은 납품본이다.** 포털 결정 문서가 전제한 기술 스택과 주 버전이 그쪽에서 일치한다. 다만 그 산출물은 별도 조직이 관리하므로 이 설계가 직접 바꾸지 않는다 — 여기서는 **기준 구현본이 그 자리에 그대로 올라가도 동작하도록** 갖춰 두는 것까지가 범위다.
- **그래서 기준 구현본의 주 버전을 생태계에 맞춘다.** 포털·관제·납품본이 모두 같은 세대의 렌더링 라이브러리와 스타일 도구를 쓰는데 기준 구현본만 한 세대 뒤였다. 정렬하면 Host 가 어느 쪽이든 공유 협상 없이 올라가고, 기준 구현으로서의 역할도 정확해진다(뒤처진 세대가 기준이면 맞추는 쪽이 매번 차이를 흡수한다).
- **산출물은 채널별로 따로 만든다.** 내부 채널과 포털 채널의 배포 대상이 서로 다른 서버라 하나의 산출물을 두 곳이 나눠 쓰는 구성이 성립하지 않는다. 공통 소스는 한 벌로 두고 **산출만 채널별로 가른다** — 그러면 ①반대 채널 화면이 산출물에 섞이지 않고 ②채널마다 다른 팔레트를 산출 시점에 정할 수 있으며 ③채널을 가르는 지점이 진입점·라우팅·셸 세 곳으로 좁혀진다. 공통 화면 부품은 채널을 스스로 알지 않고 넘겨받은 값으로만 동작하므로 갈래마다 복제되지 않는다.
- **토큰 인계 수단은 채널마다 갈린다.** 포털 채널은 Host 가 주입한 인계 창구에서 토큰을 얻어 **전용 요청 헤더**로 싣고, access token 은 **Host 메모리에만** 둔다(브라우저 저장소 미사용). 근거(포털 비협상) — 저장소나 그 스냅샷을 직접 읽으면 갱신 뒤 **죽은 토큰**을 잡고, 수십 분 체류하는 저작 화면은 반드시 파손된다. 내부 채널은 인계 결정(ADR-012)대로 같은 출처 브라우저 저장소를 쓴다.
  ⇒ 조치: 저장소 직접 읽기를 **획득 창구 뒤로 추상화**해 두 Host 를 분기 없이 지원한다. 앞선 「변경 0」 주장은 **어댑터 한 겹**으로 조정된다.
  ⚠ 「포털 서술이 두 갈래」라던 경고는 **폐기한다** — 두 방식은 상충이 아니라 **상보**였다.
- **Host 화면을 벗어나지 않는다.** 저작도구는 인증 실패·권한 없음을 자기 화면 이동으로 처리하는데, Host 안에 마운트되면 그 이동이 **Host 문서 전체**에 걸린다. 그런데 Host 가 선언한 화면 목록에 저작도구가 보내는 자리가 없어 **찾을 수 없는 화면**이 된다(전수 확인). 그러므로 포털 채널 빌드에서는 **이동하지 않고 그 자리에 안내를 그린다**. 기본값인 내부 채널에서는 지금처럼 이동한다 — 거기서는 그 자리가 실재하기 때문이다.
  ⚠ **토큰 만료로 상위 시스템 로그인 화면에 보내는 것은 그대로 둔다.** 그건 Host 도 해야 할 일이고, 저작도구는 복귀 주소에 현재 위치를 실어 보내므로 임베드된 상태에서 오히려 정확하다. 이것까지 막으면 만료된 세션에 갇힌다.
  ⚠ 이 결정으로 **Host 위임 규약 자체가 필요 없어진다** — 저작도구가 Host 를 건드리지 않고 자기 영역 안에서 끝내기 때문이다.
- **이 결정이 뒤집혀도 나머지는 다시 하지 않는다.** 두 방식의 차이는 머리 영역을 그리느냐 하나뿐이고, Host 하위 마운트에 필요한 나머지(경로 구조 재편 · 이탈 경로 위임 · 산출 분리 · 색 토큰 정리)는 어느 쪽이든 동일하다.
- **화면 사이 이동은 셸에 기대지 않는다.** 포털 채널 화면 네 건은 화면 안의 링크로 서로를 오간다(영상 선택 · 업로드 진입 · 목록 복귀). 내비게이션 영역이 없어도 이동이 끊기지 않으며, 이 성질이 위 결정을 되돌릴 수 있게 만드는 조건이다.
- **진입점·마운트·서빙 이름은 포털이 정한 값을 따른다.** 구체 값은 인라인 스펙에 있다.
- **이 경로로 진입한 사용자는 포털 권한 사용자로 본다 — 화면 축 한정.** 포털 채널 빌드가 그 권한으로 화면·메뉴·기능을 게이팅한다.
  ⚠ **서버 인가의 진실원은 토큰 클레임(채널·역할)이며 진입 경로가 권한을 올리지 않는다.** 진입 경로는 클라이언트가 주장하는 값이라 위조할 수 있다.

## 협의 대상 — 해소
1. **스타일 격리.** 포털 디자인 스타일이 정본이므로 **격리 책임은 저작도구**다. 번들이 빌드타임 접두어 또는 범위 한정 스타일 계층으로 자기 스타일을 격리해 Host 전역 스타일을 침범하지 않는다.
2. **디자인 토큰.** 「어느 팔레트로 뜨는가」가 답을 얻었다 — **포털 채널 산출물은 포털 주색(코발트 계열)으로 뜬다.** 팔레트는 산출 시점에 정해지며 뜬 뒤 갈아끼우지 않는다. 색을 고정값으로 박으면 갈아끼울 수 없어 **시맨틱 색의 토큰 분리가 선행**된다(범주 구분에 쓰는 색은 대상이 아니다 — 의미가 아니라 구분이라 채널이 달라도 같아야 한다).
3. **동일 Remote 재사용 전제.** 관제 쪽 설계에 프론트엔드 임베딩 서술이 없다는 실측을 포털이 **수용**했다. 통합 방식은 유지된다(캔버스 이벤트 간섭 회피·독립 배포·화면 일관성 근거 유효). 성립하지 않는 재사용 이점 한 줄은 포털이 정리한다.
4. **가드 중복.** 포털이 저작도구 UX 가드를 **허용**했다 — 서버가 최종 인가를 판정하고 가드가 Host 를 이탈시키지 않아 무해하며 포털 셸 인증 분기와 공존한다.

## 협의 미결
- **디자인 토큰의 기준 단위 환산.** 양쪽 설계 어디에도 명시가 없다(포털 회신 범위 밖). 상세는 인라인 스펙.

## 인증
상위 시스템이 발급한 서명 토큰을 인계받으며 저작도구가 발급하지 않는다. 전달 수단은 위 「토큰 인계 수단은 채널마다 갈린다」가 정본이고, 어느 채널도 Bearer 스킴을 쓰지 않는다.

## 범위 밖
서버간 API(완료 저작결과 조회 · 일일 저작집계)는 **별도 트랙**이며 이 연동점 범위가 아니다.

## 참조 주의
포털은 별개 프로젝트라 식별자 체계가 저작도구와 겹치지 않는다. 위에서 「포털 측」이라고 밝힌 문서는 모두 포털 프로젝트의 것이며 같은 번호의 저작도구 항목과 다른 문서다.

## 토큰 인계 창구 (Host 주입)
Host 가 Remote 에 인계 창구를 주입한다 — 토큰 획득 · 갱신 · 인증 실패 통지 · 활동 통지. 얻은 access token 은 전용 요청 헤더 `x-access-token` 으로 싣고 Bearer 스킴은 쓰지 않는다. 토큰은 Host 메모리에만 두고 브라우저 저장소에 쓰지 않는다.

저작도구는 같은 출처 저장소를 직접 읽던 지점을 토큰 획득 창구 뒤로 추상화해, 저장소를 쓰는 Host 와 메모리에 두는 Host 를 분기 없이 지원한다.


## 협의 미결 — 디자인 토큰의 기준 단위 환산
상대 단위(rem)의 기준값을 **양쪽 설계 어디에도 명시하지 않았다.** 포털 회신은 팔레트(주색)만 답했고 이 축은 회신 범위 밖이었다.

두 번들이 같은 문서에서 실행되므로 기준값은 Host 가 정한 하나로 수렴한다. 그 값이 저작도구가 전제한 값과 다르면 **같은 토큰이 채널마다 다른 크기로 뜬다** — 글자·간격·부품 높이가 함께 어긋나 화면 단위 보정으로 덮이지 않는다.

⇒ 기준값을 어느 쪽에 맞출지 포털과 협의해 확정해야 한다.
