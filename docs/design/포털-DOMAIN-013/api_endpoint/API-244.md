## 인증
사전 공유 API 키 축이다. 배포 시점에 양쪽이 나눠 가진 고정 문자열을 요청 헤더에 실어 부르고, 서버는 받은 값을 상수시간으로 비교한다. 주체 클레임이 없으므로 이 창구가 가르는 것은 「아는 쪽인가」 하나다.

**[갱신] 인증 축이 사전 공유 API 키로 바뀌었다.** 구 서술은 이 창구를 시스템 주체 토큰 축으로 두고 주체 클레임이 시스템 계정인지를 갈랐다.

**인증 축의 정본은 연동점 [[INT-014]] 가 소유한다.** 그 반전의 경위도 그쪽이 기록한다. 여기에 옮겨 적지 않는다 — 두 곳에 적으면 한쪽만 갱신돼 어긋난다. 이 창구는 그 축을 그대로 따르며, 그 귀결로 **키가 설정되지 않았으면 맞출 값이 없어 이 창구는 닫힌다.** 값이 없을 때 열리는 쪽이 아니라 닫히는 쪽이 기본값이다.

## 받는 것
데이터셋 코드와 버전.

## 언제 오는가
포털은 **버전 문자열이 자기가 저장한 기존 값과 다를 때만** 이 창구를 부른다. 같으면 부르지 않는다.

그 판정은 포털이 한다. 따라서 **저작도구는 버전의 앞뒤를 비교하지 않는다** — 어느 쪽이 더 새 버전인지 가릴 필요가 없다. 우리가 아는 것은 「다를 때만 온다」까지이며, 포털이 그 판정을 어떻게 내리는지는 이 창구의 사양이 아니다.

## 받은 즉시 지우지 않는다
트리거를 **받은 시점부터 다시 7일 뒤**에 올드 해제본을 지운다.

**그 유예가 있는 이유는 진행 중인 작업 때문이다.** 사용자가 그 해제본을 물고 저작하는 중일 수 있고, 받자마자 지우면 그 작업이 깨진다. ⚠ 이유 없이 「7일 지연」만 읽고 불필요한 지연으로 보아 없애지 말 것.

## 삭제는 비가역이다 — 안전 조건
- 삭제 대상 판정 조건을 **후보 조회에만 두지 않고 최종 삭제 실행문 자체에 건다.** 검사한 뒤 지우기까지의 사이에 상태가 바뀔 수 있고, 그 창을 닫는 유일한 방법이 단일 실행문이다.
- **식별자만 받아 지우는 창구를 두지 않는다.** 조건 중 하나라도 부르는 쪽이 채우게 남겨 두면 그 자리가 곧 지우기의 입구가 된다.
- 이는 파생영상 폐기에서 이미 세운 원칙과 같은 축이다.

## 같은 트리거가 다시 오면
중복 수신은 실제로 일어난다. 같은 데이터셋 코드와 버전으로 다시 오면 **성공 무처리로 답하고 유예 시작 시각을 갱신하지 않는다.** 갱신하면 중복 수신이 반복될 때마다 삭제가 무한히 미뤄져 정리가 영영 일어나지 않는다. 기준은 처음 받은 시각이다.

그 처음 받은 시각을 담는 자리는 정리 트리거 접수 원장([[ERD-035]])이다. 재수신 멱등과 유예 기산점이 그 원장 위에서 성립한다. 표 구조와 컬럼 정의는 그 원장이 소유하므로 여기에 복제하지 않는다.

알지 못하는 데이터셋 코드나 버전이 와도 같은 응답으로 답한다. 이 배포본에 해제된 적 없는 데이터셋일 수 있고, 오류로 답하면 포털이 지울 것도 없는 신호를 계속 재전송한다. 대상 유무를 응답으로 드러내지도 않는다 — 부르는 쪽이 그 사실을 알 필요가 없고, 드러내면 존재 여부를 탐색하는 수단이 된다.

## 거부 규칙 — 서버간 창구가 함께 쓰는 규칙
| 상황 | 응답 |
|---|---|
| 키 헤더가 없거나 값이 다르다 | 401 인증 실패 |
| [미발생] 주체 축 불일치 — 이 창구에서는 성립하지 않는다 | 403 권한 없음 |
| 요청 값이 형식이나 필수를 어긴다 | 400 검증 실패 |

403 은 이 창구에서 나오지 않는다. 사전 공유 API 키에는 주체가 없어 주체 축 불일치라는 사유 자체가 성립하지 않는다. 그래도 목록에서 지우지 않고 표기로 남긴다 — 없어진 것과 원래 없는 것은 읽는 쪽에 다르게 읽혀야 한다. 구 서술은 토큰의 만료와 서명 불일치를 401 사유로, 사용자 주체 토큰 거부를 403 사유로 두었다.
