- 관제 통지와 호출 대상 주소 설정만 공유하고 통지용 서비스 토큰·통지 활성화 토글·장애 격리는 따로 둔다는 규칙을 이 창구에도 적었다 — 로그아웃 창구로 나가는 헤더에는 사용자의 access 토큰만 싣는다. 주소 설정 공유는 2026-09-14 폐기다(아래 항목).

- Bearer 형식이 아니거나 값이 빈 `Authorization` 은 헤더 없음과 같이 처리한다(관제 미호출, 204).
- 수용기준 AC-1106 을 검증 대상으로 이었다(AC-1105 유지).

### 2026-09-14 — 관제 계정 창구 주소 분리 (INT-015 v8 · ADR-012 v22 반영)
- 호출 대상 주소를 관제 통지 수신처 주소 설정 재사용에서 관제 계정 창구 주소(`authoring.control-account.url`) 단독으로 바꿨다. 폴백은 두지 않는다 — 판정 원천이 둘이면 같은 사고가 조용히 재발한다.
- 근거: 관제는 계정 창구와 데이터셋 창구를 서로 다른 WAS 에 둔다(개발 서버 실측). 운영 현장에서 통지 수신처에 통지 WAS 를 넣자 갱신이 404 로 전부 실패했고, 공유 서킷이 열려 로그아웃 중계까지 막혀 관제 서버 세션이 닫히지 않았다.
- 주소가 비어 있으면 관제를 부르지 않고 관제 확인 없이 끝난다 — 204·브라우저 결말은 그대로이고 서킷 실패로 세지 않는다.
- 서킷을 통지와도, 같은 계정 창구의 갱신 중계와도 나눴다 — 갱신 서킷이 열려도 로그아웃 중계는 관제로 나간다.
- 응답 코드·로그인 검사 없음·포털 채널 404·access 토큰 전달·짧은 타임아웃·자동 재시도 없음은 무변경이다.

### Authorization

- **in**: header

**schema**:

#### type

string

- **example**: Bearer eyJhbGciOiJIUzUxMiJ9...
- **required**: false
- **description**: 관제 access 토큰을 Bearer 스킴으로 싣는다. 이 창구는 토큰을 검사하지 않고 관제 로그아웃 창구의 x-access-token 헤더로 넘기기만 한다. 없으면 관제를 부르지 않는다. Bearer 형식이 아니거나 값이 비어 있어도 없는 것과 같다.

## description

관제 채널의 세션 만료 연장 팝업(상세 [[SHELL-001]])에서 사용자가 「로그아웃」을 누르면 브라우저가 이 창구를 부르고, 저작도구 서버가 관제지원 계정 서비스의 로그아웃 창구를 대신 호출해 관제 서버 세션을 끝낸다(연동점 [[INT-015]]). 호출 시점은 팝업의 「로그아웃」을 눌렀을 때뿐이다. 저장하지 않은 편집이 있으면 화면 이탈 공통 확인 절차에서 계속을 고른 뒤에만 부르며, 취소하면 부르지 않는다. 세션 갱신은 이 창구가 다루지 않는다.

## 인증
저작도구의 로그인 검사를 하지 않는다. 요청에 실린 access 토큰이 만료 직전이거나 이미 만료된 뒤여도 거절하지 않고 로그아웃을 진행한다 — 이 창구가 불리는 때가 바로 세션 만료가 가까운 때이기 때문이다.

## 관제 호출
- 요청의 `Authorization: Bearer <access 토큰>` 에서 토큰을 읽어 관제 로그아웃 창구의 `x-access-token` 헤더로 넘긴다. 로그아웃 창구는 access 토큰을 싣는다(갱신 창구가 refresh 토큰을 싣는 것과 반대다 — [[INT-015]]).
- `Authorization` 헤더가 없으면 관제를 부르지 않는다.
- `Authorization` 이 Bearer 형식이 아니거나 토큰 값이 비어 있으면 헤더가 없는 것과 같이 처리한다 — 관제를 부르지 않고 204 를 돌려준다.
- 호출 대상 주소는 관제 계정 창구 주소(`authoring.control-account.url`)만 쓴다. 관제 통지 수신처 주소로 대체하지 않는다(폴백 없음). 관리자가 연동 주소 설정에서 바꾸면 재기동 없이 다음 호출부터 반영되며, 요청으로는 대상을 바꿀 수 없다.
- 관제 계정 창구 주소가 비어 있으면 관제를 부르지 않고 관제 확인 없이 끝난다 — 응답은 204 그대로이고 브라우저 결말(토큰 키 삭제 후 관제 로그인)도 같다. 비어 있음은 결정적 상태라 서킷 실패로 세지 않는다.
- [폐기] 「호출 대상 주소는 관제 통지 수신처와 같은 설정을 쓴다」(2026-09-14) — 관제는 계정 창구와 데이터셋 창구를 서로 다른 WAS 에 두어, 주소 하나를 나눠 쓰면 한쪽이 404 다.
- 요청 바디는 없다.

## 관제 통지와의 분리
관제 통지와는 호출 대상 주소 설정을 포함해 모두 따로 둔다([[INT-015]]). [폐기] 「호출 대상 주소 설정만 공유한다」(2026-09-14) — 주소는 위 절의 관제 계정 창구 주소다.
- 관제 로그아웃 창구로 나가는 `x-access-token` 에는 요청에 실린 사용자의 access 토큰만 싣는다. 관제 통지용 서비스 토큰은 싣지 않는다.
- 관제 통지 활성화 토글과 무관하게 동작한다 — 통지를 끈 배포에서도 관제 로그아웃 창구를 부른다.
- 장애 격리(서킷)도 통지와 따로 두고, 같은 계정 창구의 갱신 중계와도 따로 둔다 — 한쪽의 장애가 다른 쪽 호출을 막지 않는다. 갱신 장애가 누적돼 갱신 서킷이 열려도 로그아웃 중계는 관제로 나간다.
- 관제 호출 타임아웃은 짧게(3초 수준) 둔다. 브라우저가 이 응답을 받은 뒤 관제 로그인으로 이동하므로 사용자가 기다리는 시간이 곧 이 값이다. 자동 재시도하지 않는다.

## 응답
관제 응답의 성공·실패와 무관하게 항상 204 No Content 를 돌려준다. 브라우저는 이 응답과 무관하게 저장소의 토큰 키를 지우고 관제 로그인으로 이동하므로(관제지원 웹과 같은 처리) 결과를 알릴 필요가 없다. 관제 호출이 실패하면 서버 로그에 실패 사실만 남긴다.

## 채널
관제 채널 배포본에만 있는 창구다. 포털 채널 배포본에서는 404 다 — 포털 채널은 토큰을 Host 인계 창구로 받으며 관제 계정 세션을 쓰지 않는다([[ADR-012]]).

## 보안
- 토큰 원문을 로그에 싣지 않는다 — 관제 호출 실패를 기록할 때도 같다.
- 수용기준은 [[AC-1105]] 의 「로그아웃」 단언이다. 관제 통지와의 분리와 사용자 토큰 전달은 [[AC-1106]] 이 단언한다.
