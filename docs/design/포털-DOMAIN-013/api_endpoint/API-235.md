## description

포털 사용자가 확인·수정·추가한 메타를 적재한다. 대상은 자산 출처를 가리지 않는다 — 데이터마트에서 불러온 영상과 본인이 올린 영상 둘 다이며, 포털의 라벨링 화면이 하나로 합쳐져 두 출처를 같은 화면에서 다루기 때문이다. 저장처는 화면이 가르지 않고 서버가 자산 출처로 판정한다 — 화면은 어느 쪽인지 알 필요가 없고 어느 출처든 같은 저장 요청을 보낸다. 데이터마트 자산은 본인 오버레이(LS_PORTAL_USER_META)에 적재한다. ★원본(LS_DATA_META)과 동결 스냅샷을 수정하지 않는다 — 단방향이라 데이터마트로 되돌아가지 않는다. 그 오버레이의 적재 키는 (포털사용자, 영상, 프레임, 메타키)이며 같은 키를 다시 저장하면 덮어쓴다. 본인이 올린 자산은 오버레이를 거치지 않고 그 자산의 메타에 그대로 적재한다 — 원본이 본인 것이라 가려 둘 원본이 없다. 영상 축으로 표시된 원소는 프레임 참조를 비워 적재한다 — 채우면 없는 프레임을 가리키게 된다. 읽기 전용 메타와 기술 메타를 고치려는 요청은 400 이며 거부 메시지에 요청 키를 되돌려 싣지 않는다.

★사용자가 고르지 않은 값이 사람의 판정으로 승격되지 않는다. 이 창구가 담는 것은 촬영환경·프레임 설명·개인정보 판정·시계열 메타 네 축이고, 이벤트 어노테이션은 별개 창구 소관이다. 그 네 축 가운데 촬영환경·프레임 설명·개인정보 판정 셋은 원장의 컬럼에서 오며, 그 축의 유효값은 수동 저장값이 있으면 그 값이고 없으면 자동으로 계산한 값이다. 화면이 그 자동 계산값을 그대로 되돌려 보내면 오버레이 행이 생겨 사용자가 고른 값으로 승격되는데, 서버는 받은 값만으로는 사용자가 고른 것인지 자동 계산값이 되돌아온 것인지 구분하지 못한다. 그래서 방어를 두 겹으로 둔다 — ①화면 계약: 사용자가 직접 고르지 않은 항목은 보내지 않는다 ②★서버 방어: 받은 값이 원본의 현재 유효값과 같으면 오버레이 행을 만들지 않고, 이미 있으면 지운다. 두 겹 가운데 서버 방어는 단독으로 성립하므로 화면이 계약을 어겨도 오버레이가 오염되지 않는다. 이 서버 방어가 이 창구에서 성립하는 이유는 오버레이가 별도 저장소라 행이 없다는 것이 곧 원본 값을 그대로 쓴다는 뜻이기 때문이다 — 그래서 안 쓰는 것이 유효한 선택이다. 원장에 직접 쓰는 창구에서는 행이 없다는 것이 수동값을 지운다는 다른 뜻이 되어 같은 방어를 쓸 수 없다. 인지하고 받아들이는 대가로, 사용자가 자동 계산값과 우연히 같은 값을 일부러 골라도 덮었다는 표시가 서지 않는다 — 보이는 값은 같으므로 무해하다.

★★원본을 수정하지 않기 위해 기존 내부 저장 창구를 재사용하지 않는다. 촬영환경과 개인정보 판정을 고치는 내부 창구는 저장하면서 원장의 컬럼을 직접 고치고, 재검토 표시를 세우고, 관제 통지를 발행하고, 승인 시점 동결본을 다시 굳힌다. 포털이 그 창구를 그대로 부르면 이 창구의 최상위 불변 두 가지를 한 번에 위반한다 — 원본과 동결본을 수정하지 않는다 / 관제 통지와 산출물 재생성을 일으키지 않는다. 이 위반은 중복 구현을 피하려는 가장 자연스러운 판단에서 나오므로 금지로 못박는다. 재사용하는 것은 읽기와 규칙이다 — 값의 유효성 규칙(허용 코드값·최대 길이)과 자동 계산값을 도출하는 규칙은 그 규칙을 소유한 쪽을 그대로 쓴다. 복제하면 두 번째 진실원이 되어 소유자가 규칙을 바꾸는 날 포털만 조용히 뒤처지기 때문이며, 읽기 경로에는 부작용이 없다. 재사용하지 않는 것은 저장 동작이다 — 원장 컬럼 쓰기·재검토 표시·관제 통지·동결본 재동결 어느 것도 포털 경로에서 일어나지 않는다.

값 폭은 좁은 쪽에 맞춘다 — 프레임 설명은 원본 폭(1000자)이 오버레이 저장 폭(2000자)보다 좁으므로 저장 검증을 좁은 쪽인 1000자로 한다. 넓은 쪽을 허용하면 사용자가 자기 데이터를 내려받을 때 원본과 같은 자리에 들어가지 못하는 값이 생긴다.

비식별 누락 신고가 열려 있는 영상은 이 창구도 거부한다(412). 이 창구가 다루는 축에 개인정보 판정이 들어 있고, 같은 채널의 형제 창구(포털 프레임 라벨 저장·포털 프레임 이미지 서빙)와 이벤트 어노테이션 저장이 이미 그 구간에서 차단되기 때문이다. 축별로 가르지 않는다 — 한 요청이 네 축을 함께 받으므로 일부만 허용하면 우회가 생긴다. 응답 코드는 형제 창구와 같은 값을 쓴다 — 형제와 다른 코드를 쓰면 응답 자체가 영상 상태를 알려 주는 단서가 된다. 포털 사용자가 직접 올린 업로드 자산은 이 게이트의 대상이 아니다 — 내부 파이프라인의 비식별 라이프사이클이 없다.
