# 젠킨스 잡 수정 안내 — 저작도구를 포털 안에서 띄우기 위해

> 2026-09-10 · 포털 인프라 회신(「MF·Apache 반영 확정」) 기준으로 **확정된 값**을 반영한 판.
> 아파치 최종본을 로컬에 올려 **실제로 돌려 보고** 쓴 문서다(§7 실측 결과).
>
> **§3 에 web 잡 전체 스크립트가 있다 — 통째로 덮어쓰면 된다.**

---

## 1. 지금 무슨 상황인지 — 3줄

1. 저작도구 화면은 이제 **독립 웹사이트가 아니라, 포털 화면 «안에» 끼워 넣는 부품**이 됐다.
2. 그래서 **주소가 세 개 바뀐다** — 부품을 내려받는 주소 · 저작도구 API 주소 · WAR 컨텍스트.
3. 젠킨스 잡 2개가 **옛 주소를 보고 있어서** 그걸 새 주소로 맞춰야 한다.

### 용어 세 개만 (이것만 알면 아래가 다 읽힌다)

| 말 | 뜻 |
|---|---|
| **번들 / `remoteEntry.js`** | 저작도구 화면 파일 묶음. 포털이 실행 중에 이 파일을 내려받아 자기 화면에 끼워 넣는다. **옛날의 `index.html` 자리를 대신한다.** |
| **번들 주소** | 포털이 그 파일을 가져가는 주소. **`/label-remote/`** 로 확정 |
| **API 접두어** | 저작도구 백엔드를 부르는 주소 앞부분. **`/authoring-api/`** 로 확정 |

> ⚠ `/api/v1/` 은 **포털 자신의 백엔드** 주소다. 저작도구가 그걸 쓰면 요청이 **남의 서버로** 간다.
> 그래서 접두어를 따로 두는 것이다.

### 확정값 한눈에

| 항목 | 값 |
|---|---|
| 번들 URL | `/label-remote/` |
| 번들 **디스크 폴더** | `/opt/apache2_custom/www/**author**/` ← ⚠ **폴더 이름은 그대로** |
| API 접두어 | `/authoring-api/` |
| WAR 컨텍스트 | `/authoring-api` |
| 저작도구 번들 재빌드 | **불필요** (포털이 계약값을 그대로 확정했다) |

---

## 2. 오늘 할 일 — 순서대로

아파치는 **포털 쪽에서 이미 반영을 마쳤다.** 우리가 할 일만 남았다.

```
[1] web 잡  — §3 전체 스크립트로 교체
[2] was 잡  — 값 2줄 교체            (§4)
[3] 확인                             (§6)
```

> ★ **WAS 서버(리눅스)는 손댈 것이 없다.** 예전 판에는 「환경변수 1개 추가」 단계가 있었는데,
> **코드가 WAR 웹 컨텍스트에서 자동으로 도출**하게 바꿔서 사라졌다(§5).

**[1]과 [2]는 한 번에 한다.** 주소를 정하는 자리가 셋(아파치 · WAR 컨텍스트 · 프론트)인데,
**한 곳만 바꾸면 아무 신호 없이 깨진다** — WAS 는 정상 기동하고, 배포도 성공하고, 화면까지
뜨는데 **API 만 전부 404** 가 난다.

## 3. `klid portal 저작도구 web` — 전체 스크립트

**구성 → Pipeline → Script** 를 아래로 **통째로 교체**한다.

```groovy
pipeline {
    // 잡 이름에 공백이 있으면 기본 워크스페이스 경로에도 공백이 들어가 node/vite 가 종종 깨진다.
    // 공백 없는 경로로 고정한다. ★ 포털 web 잡과 «다른» 워크스페이스여야 서로 지우지 않는다.
    agent {
        node {
            label ''
            customWorkspace '/var/jenkins_home/workspace/klid-author-web'
        }
    }

    options {
        timeout(time: 30, unit: 'MINUTES')
        timestamps()
        disableConcurrentBuilds()
        buildDiscarder(logRotator(numToKeepStr: '10'))
    }

    parameters {
        string(name: 'TARGET_BRANCH', defaultValue: 'main', description: '체크아웃할 브랜치')
        choice(
            name: 'BUILD_CHANNEL',
            // ★ 이 배포본은 «포털향» 이다 (2026-09-08 확정) — 기본값이 portal 이다.
            choices: ['portal', 'control'],
            description: '''빌드 채널.
portal  = 포털 화면 «안에» 끼워 넣는 부품(Module Federation Remote). «이 서버의 기본값».
          산출물은 remoteEntry.js 이고 index.html 은 쓰이지 않는다(포털의 index.html 이 뜬다).
          ★ 이 주소를 브라우저로 «직접» 열면 화면이 안 뜬다 — 그것이 정상이며 배포 실패가 아니다.
            확인은 포털의 /workspace/authoring 에서 한다.
control = 자체 셸을 갖는 독립 앱. 브라우저에서 바로 뜬다. 배선(Apache·WAS·DB) 점검용.'''
        )
        booleanParam(name: 'RUN_LINT',  defaultValue: false, description: 'ESLint 실행 여부')
        booleanParam(name: 'RUN_TESTS', defaultValue: false, description: 'vitest 실행 여부 (E2E 는 제외)')
        booleanParam(
            name: 'DEV_LOGIN_ENABLED',
            defaultValue: true,
            description: '''개발용 로그인(/dev/login)·업로드(/admin/uploads) 노출. 개발 서버라 기본 켬.
⚠ portal 채널에서는 «적용되지 않는다» — 이 값을 나르는 klid-config.js 를 포털 안에서는 읽지 않는다.'''
        )
    }

    environment {
        // ★ 저작도구 저장소 (모노레포 — 프론트는 frontend/ 하위)
        GITEA_URL   = 'gitea.cudodev.synology.me:5001/dx_dev/klid-label.git'
        APP_DIR     = 'frontend'

        // Jenkins 와 Apache 가 같은 서버이므로 cp 로 배포.
        // WEB_ROOT 는 Jenkins 컨테이너에 bind-mount 돼 있다 (docker inspect 로 확인함).
        WEB_ROOT    = '/opt/apache2_custom/www'

        // ★ 디스크 폴더 이름. 아파치가 Alias 로 이 폴더를 SERVE_PATH 에 붙여 준다.
        //   ⚠ URL(/label-remote/)과 폴더명(author)이 «다른 것이 정상»이다 —
        //     httpd.conf: Alias /label-remote/ "/opt/apache2_custom/www/author/"
        //     여기서 헷갈려 폴더명까지 바꾸면 아파치가 «빈 폴더»를 서빙하게 된다.
        DEPLOY_DIR  = 'author'

        // ★ 브라우저가 보는 URL 접두어. 아파치 Alias 와 «같은 값»이어야 한다.
        SERVE_PATH  = '/label-remote/'
        HTTP_PORT   = '38081'

        // ★ 저작도구 백엔드 주소. httpd 의 /api/v1/ 은 «포털 자기 WAS» 라 별도 접두어를 쓴다.
        //   ⚠⚠ portal 채널에서는 klid-config.js(실행 중 주입)가 «읽히지 않는다» — 그 파일을
        //     불러 주는 것은 우리 index.html 인데, 포털 안에서는 포털의 index.html 이 뜨기
        //     때문이다. 그래서 이 값은 아래 Build 단계에서 «빌드 시점에» 굽는다.
        //     Render runtime config 단계만 고치면 portal 채널에는 «안 먹는다».
        //   ⚠ 이 값과 was 잡의 KLID_WEB_CONTEXT 를 «함께» 바꾼다. 하나만 바꾸면 아무 신호
        //     없이 API 만 전건 404 가 된다.
        //   ★ 백엔드가 응답 본문에 담아 내리는 절대 주소는 «따로 설정하지 않는다» —
        //     WAR 웹 컨텍스트에서 자동 도출한다(KLID_WEB_CONTEXT 가 곧 그 값이다).
        API_BASE_URL     = '/authoring-api/v1'

        // 401 시 이동할 상위 시스템 로그인 주소. (control 채널 점검용 — portal 은 포털이 처리한다)
        //   ★ «같은 출처 상대 경로» 다 — 절대 주소로 박으면 http/https·IP/호스트명 조합마다
        //     어긋나고, hosts 미등록 PC 에서는 아예 못 간다.
        UPSTREAM_LOGIN   = '/label-remote/dev/login'

        // 툴체인은 워크스페이스 밖에 둔다. GitSCM 이 최초 클론 시 워크스페이스를 통째로
        // 비우므로, 안에 두면 매번 지워지고 재다운로드된다. (포털 잡과 공유 — 읽기 재사용이라 안전)
        NODE_VERSION = '22.14.0'
        TOOLCHAIN    = '/var/jenkins_home/.toolchain'
        NODE_HOME    = '/var/jenkins_home/.toolchain/node-v22.14.0-linux-x64'
        PATH         = "/var/jenkins_home/.toolchain/node-v22.14.0-linux-x64/bin:${PATH}"
    }

    stages {
        stage('Initialize') {
            steps {
                script {
                    env.BRANCH = params.TARGET_BRANCH
                    echo "========================================="
                    echo "잡          : 저작도구 web (author)"
                    echo "브랜치      : ${env.BRANCH}"
                    echo "빌드 채널   : ${params.BUILD_CHANNEL}"
                    echo "린트 실행   : ${params.RUN_LINT}"
                    echo "테스트 실행 : ${params.RUN_TESTS}"
                    echo "배포 폴더   : ${env.WEB_ROOT}/${env.DEPLOY_DIR}"
                    echo "서빙 URL    : http://klid-portal-dev:${env.HTTP_PORT}${env.SERVE_PATH}"
                    echo "API 접두어  : ${env.API_BASE_URL}"
                    echo "========================================="
                    if (params.BUILD_CHANNEL == 'portal') {
                        echo '''
포털 채널 빌드 — 포털 화면 안에 끼워 넣는 «부품»입니다.
  · 산출물은 remoteEntry.js 이고, 포털이 실행 중에 그 파일을 내려받아 자기 화면에 붙입니다.
  · 포털이 토큰 창구(authBridge)를 넘겨 줘야 동작합니다.
  · 이 주소를 브라우저로 «직접» 열면 화면이 안 뜹니다 — 그것이 «정상»이며 배포 실패가 아닙니다.
  ⇒ 확인은 포털의 /workspace/authoring 에서 합니다.
    배선(Apache·WAS·DB)만 눈으로 보려면 BUILD_CHANNEL=control 로 한 번 돌리세요.
'''
                    }
                }
                sh """
                    if [ ! -w '${env.WEB_ROOT}' ]; then
                        echo 'ERROR: ${env.WEB_ROOT} 가 Jenkins 컨테이너에 마운트되지 않았거나 쓰기 권한이 없음'
                        exit 1
                    fi
                """
            }
        }

        stage('Checkout') {
            steps {
                checkout([
                    $class: 'GitSCM',
                    branches: [[name: "*/${env.BRANCH}"]],
                    userRemoteConfigs: [[
                        credentialsId: 'gitea-credentials',
                        url: "https://${env.GITEA_URL}"
                    ]]
                ])
                script {
                    env.GIT_COMMIT_SHORT = sh(returnStdout: true, script: 'git rev-parse --short HEAD').trim()
                }
                sh 'git --no-pager log -1 --pretty=format:"%h - %an: %s (%ci)"'
            }
        }

        stage('Setup Node') {
            steps {
                sh '''
                    set -e
                    mkdir -p "$TOOLCHAIN"
                    if [ ! -x "$NODE_HOME/bin/node" ]; then
                        echo "Node ${NODE_VERSION} 다운로드..."
                        curl -fsSL "https://nodejs.org/dist/v${NODE_VERSION}/node-v${NODE_VERSION}-linux-x64.tar.gz" | tar -xz -C "$TOOLCHAIN"
                    fi
                    node -v && npm -v
                '''
            }
        }

        stage('Build') {
            steps {
                dir("${env.APP_DIR}") {
                    // ★ npm 이다 — package-lock.json 이 정본. pnpm 을 쓰면 lockfile 이 무시된다.
                    sh 'npm ci --no-audit --no-fund'
                    script {
                        if (params.RUN_LINT)  { sh 'npm run lint' }
                        if (params.RUN_TESTS) { sh 'npm run test' }

                        // ★★ 채널마다 «넘길 값이 다르다». 여기가 가장 틀리기 쉬운 자리다.
                        //   portal  : VITE_BASE_PATH 를 «주지 않는다».
                        //             부품의 자산 주소는 코드에 계약값으로 고정돼 있고, 다른 값을
                        //             주면 저작도구 빌드가 «일부러 실패»한다(fail-closed).
                        //             자산만 엉뚱한 곳으로 가서 «화면이 절반만 뜨는» 사고를 막는 장치다.
                        //   control : 독립 앱이 하위 경로에서 열리므로 base 를 «줘야» 한다.
                        //             안 주면 /assets 를 포털 문서 루트에서 찾아 화면이 안 뜬다.
                        //   ⚠ 변수 «이름»을 헷갈리지 말 것 — VITE_BASE_PATH(자산 주소)와
                        //     VITE_API_BASE_URL(백엔드 주소)은 완전히 다른 값이다.
                        //     VITE_BASE_PATH 에 API 주소를 넣으면 portal 빌드가 그대로 죽는다.
                        if (params.BUILD_CHANNEL == 'portal') {
                            sh """
                                set -e
                                export VITE_API_BASE_URL='${env.API_BASE_URL}'
                                npm run build:portal
                            """
                        } else {
                            sh """
                                set -e
                                export VITE_API_BASE_URL='${env.API_BASE_URL}'
                                export VITE_BASE_PATH='${env.SERVE_PATH}'
                                npm run build:control
                            """
                        }
                    }

                    sh 'ls -lah dist/ && du -sh dist/'

                    // ★ 채널에 맞는 산출물이 나왔는지 확인한다.
                    //   이 검사가 없으면 «빌드도 배포도 성공한 채» 포털에서만 안 뜬다.
                    script {
                        if (params.BUILD_CHANNEL == 'portal') {
                            sh """
                                set -e
                                test -f dist/remoteEntry.js   || (echo 'ERROR: remoteEntry.js 없음 — 부품이 아니라 독립 앱으로 빌드됐다'; exit 1)
                                test -f dist/mf-manifest.json || (echo 'ERROR: mf-manifest.json 없음'; exit 1)
                            """
                        } else {
                            sh """
                                set -e
                                test -f dist/index.html || (echo 'ERROR: index.html 없음'; exit 1)
                                grep -q 'src="${env.SERVE_PATH}' dist/index.html \\
                                    || (echo 'ERROR: index.html 이 ${env.SERVE_PATH} 로 다시 쓰이지 않았음 (VITE_BASE_PATH 미반영)'; exit 1)
                            """
                        }
                    }
                }
            }
        }

        stage('Render runtime config') {
            steps {
                script {
                    // klid-config.js — 번들보다 먼저 로드돼 환경별 값을 주입한다.
                    //   값의 정본은 여기(잡 environment)이고 이 파일은 «생성물»이다.
                    //   ★ 브라우저로 그대로 내려간다 — 비밀값을 넣는 자리가 아니다.
                    //   ⚠ portal 채널에서는 이 파일이 «읽히지 않는다»(포털의 index.html 이 뜬다).
                    //     그래도 지우지 않는 이유는 control 채널 점검에 여전히 필요하기 때문이다.
                    def devFlag = params.DEV_LOGIN_ENABLED ? 'true' : 'false'
                    writeFile file: "${env.APP_DIR}/dist/klid-config.js", text: """\
/* 생성물 — Jenkins 잡 '저작도구 web' 이 배포 시점에 씀. 손으로 고치지 말 것. */
window.__KLID_RUNTIME_CONFIG__ = {
  VITE_API_BASE_URL: '${env.API_BASE_URL}',
  VITE_CONTROL_LOGIN_URL: '${env.UPSTREAM_LOGIN}',
  VITE_PORTAL_LOGIN_URL: '${env.UPSTREAM_LOGIN}',
  VITE_DEV_LOGIN_ENABLED: '${devFlag}',
  VITE_DEV_UPLOAD_ENABLED: '${devFlag}'
};
"""
                }
                sh "cat '${env.APP_DIR}/dist/klid-config.js'"
            }
        }

        stage('Deploy') {
            steps {
                script {
                    // 채널마다 «반드시 있어야 하는» 파일이 다르다.
                    env.REQUIRED_FILE = (params.BUILD_CHANNEL == 'portal') ? 'remoteEntry.js' : 'index.html'
                }
                sh """
                    set -e
                    cd '${env.WEB_ROOT}'

                    # 새 산출물을 옆에 풀어놓고 디렉터리 스왑 (배포 중 반쪽 상태 방지)
                    rm -rf ${env.DEPLOY_DIR}.new ${env.DEPLOY_DIR}.bak
                    mkdir -p ${env.DEPLOY_DIR}.new
                    cp -a '${WORKSPACE}/${env.APP_DIR}/dist/.' ${env.DEPLOY_DIR}.new/

                    test -f ${env.DEPLOY_DIR}.new/${env.REQUIRED_FILE} \\
                        || (echo 'ERROR: ${env.REQUIRED_FILE} 없음'; exit 1)

                    if [ -d ${env.DEPLOY_DIR} ]; then mv ${env.DEPLOY_DIR} ${env.DEPLOY_DIR}.bak; fi
                    mv ${env.DEPLOY_DIR}.new ${env.DEPLOY_DIR}

                    echo "배포 완료: \$(ls ${env.DEPLOY_DIR} | wc -l) 개 항목, 롤백본 = ${env.DEPLOY_DIR}.bak"
                """
            }
        }

        stage('Verify') {
            steps {
                // 정적 파일이라 Apache 재기동은 불필요. 끝 슬래시 필수(Alias 매칭).
                //
                // ★★ portal 채널은 «200 인가»를 보면 안 된다 (2026-09-10 실측).
                //   아파치 새 설정에서 옛 주소 /author/ 는 404 가 아니라 «포털 홈페이지» 200 을
                //   돌려준다. 그래서 `curl -fsS`(200이면 성공)로 확인하면 «틀렸는데도 통과»한다.
                //   ⇒ 잡은 초록불인데 저작도구는 하나도 안 뜨는 상태가 된다.
                //   그래서 두 가지를 본다:
                //     ① 진입 파일이 «자바스크립트»로 오는가
                //        (text/html 이면 앞단이 포털 홈페이지를 돌려주고 있다는 뜻이다)
                //     ② 없는 청크가 404 인가
                //        (200 이면 앞단 SPA fallback 이 이 경로를 덮고 있다는 뜻이다)
                script {
                    if (params.BUILD_CHANNEL == 'portal') {
                        sh """
                            set -e
                            out=\$(curl -s -o /dev/null -w '%{http_code} %{content_type}' http://localhost:${env.HTTP_PORT}${env.SERVE_PATH}remoteEntry.js)
                            code=\$(echo "\$out" | cut -d' ' -f1)
                            ct=\$(echo "\$out" | cut -d' ' -f2)
                            echo "remoteEntry.js -> HTTP \$code · \$ct"
                            [ "\$code" = "200" ] \\
                                || (echo "ERROR: 진입 파일이 HTTP \$code — 아파치 Alias ${env.SERVE_PATH} 미설정 또는 배포 실패"; exit 1)
                            echo "\$ct" | grep -qi javascript \\
                                || (echo 'ERROR: 진입 파일이 자바스크립트가 아니다 — 앞단이 포털 홈페이지를 돌려주고 있다'; exit 1)

                            miss=\$(curl -s -o /dev/null -w '%{http_code}' http://localhost:${env.HTTP_PORT}${env.SERVE_PATH}assets/no-such-chunk.js)
                            echo "없는 청크    -> HTTP \$miss"
                            [ "\$miss" = "404" ] \\
                                || (echo "ERROR: 없는 청크가 HTTP \$miss 다 — 앞단 SPA fallback 이 이 경로를 덮고 있다"; exit 1)
                        """
                    } else {
                        sh """
                            set -e
                            curl -fsS -o /dev/null -w 'index.html     HTTP %{http_code}\\n' http://localhost:${env.HTTP_PORT}${env.SERVE_PATH}
                            curl -fsS -o /dev/null -w 'klid-config.js HTTP %{http_code}\\n' http://localhost:${env.HTTP_PORT}${env.SERVE_PATH}klid-config.js
                        """
                    }
                }
            }
        }
    }

    post {
        success {
            echo "========================================="
            echo "DEPLOY SUCCESS  저작도구 web (${env.GIT_COMMIT_SHORT}, ${env.BRANCH}, ch=${params.BUILD_CHANNEL})"
            echo "  서빙 : http://klid-portal-dev:${env.HTTP_PORT}${env.SERVE_PATH}"
            echo "  화면 확인 : 포털의 /workspace/authoring (portal 채널은 직접 열면 안 뜬다)"
            echo "  롤백 : cd ${env.WEB_ROOT} && rm -rf ${env.DEPLOY_DIR} && mv ${env.DEPLOY_DIR}.bak ${env.DEPLOY_DIR}"
            echo "========================================="
        }
        failure {
            echo "DEPLOY FAILED — /opt/apache2_custom/logs/error_log 및 위 빌드 로그 확인"
        }
    }
}
```

## 3-1. 종전 스크립트에서 무엇이 왜 바뀌었나

| # | 바뀐 것 | 왜 |
|:-:|---|---|
| 1 | `BASE_PATH` **삭제** | 이 값이 빌드를 죽인다. 포털용 번들의 자산 주소는 코드에 고정돼 있어 **바깥에서 주면 안 된다** |
| 2 | `VERIFY_PATH` → **`SERVE_PATH`** 로 이름 바꾸고 값 `/label-remote/` | 검증에만 쓰는 값이 아니라 **서빙 주소 그 자체**라서. control 빌드의 base 로도 쓴다 |
| 3 | `API_BASE_URL` → **`/authoring-api/v1`** | 포털이 확정한 접두어 |
| 4 | Build 에 **`export VITE_API_BASE_URL`** 추가 | 포털 안에서는 `klid-config.js` 가 안 읽혀서, 빌드 시점에 구워야 한다 |
| 5 | Build 산출물 검사를 **채널별로** 분기 | portal 은 `remoteEntry.js`, control 은 `index.html` — 안 나누면 **control 빌드가 무조건 실패**한다 |
| 6 | Build 의 base 주입을 **채널별로** 분기 | portal 은 주면 안 되고, control 은 **줘야** 한다 |
| 7 | Deploy 파일 검사도 채널별 | 같은 이유 |
| 8 | Verify 를 **Content-Type 검사**로 교체 | 200 만 보면 **틀렸는데도 통과**한다(§7 실측) |
| 9 | `UPSTREAM_LOGIN` → `/label-remote/dev/login` | 옛 `/author/` 주소는 아파치에서 사라졌다 |
| 10 | `DEPLOY_DIR` **그대로 `author`** | 아파치가 `Alias /label-remote/ → www/author/` 로 이어 준다 |

### ⚠ 흔히 내는 실수 하나 — 실제로 나왔던 것

```groovy
export VITE_BASE_PATH='${env.API_BASE_URL}'     # ✗ 이름은 그대로 두고 «값만» 바꿈
```

이러면 `VITE_BASE_PATH=/authoring-api/v1` 이 넘어가 **portal 빌드가 그대로 죽는다**
(그게 fail-closed 가드가 잡으려는 바로 그 값이다). 그리고 `VITE_API_BASE_URL` 은
여전히 안 넘어간다. **변수 «이름»이 바뀌는 것이 요점이다.**

| 변수 | 무엇 | portal 채널 |
|---|---|---|
| `VITE_BASE_PATH` | 자산(JS·CSS) 주소 | **주면 안 됨** |
| `VITE_API_BASE_URL` | 백엔드 주소 | **줘야 함** |

## 4. 잡 `klid 저작도구 was` — 2줄

`environment { }` 에서 **값만** 바꾼다.

| 키 | 지금 | 바꿀 값 |
|---|---|---|
| `KLID_WEB_CONTEXT` | `'/author-api'` | **`'/authoring-api'`** |
| `HEALTH_PATH` | `'/author-api/actuator/health/liveness'` | **`'/authoring-api/actuator/health/liveness'`** |

> 💡 **이 잡은 잘 만들어져 있다.** WAR 안에서 실제 설정값을 **읽어서** 확인하고, 배포 후
> 아파치를 거쳐 헬스체크를 때린다. 그래서 **값이 하나라도 어긋나면 이 잡이 404 로 잡아 준다.**
> §6 의 "가장 빠른 확인법"이 이것이다.
>
> ★ **`KLID_WEB_CONTEXT` 는 이제 두 가지를 정한다** — WAR 가 붙는 자리 + 백엔드가 응답에
> 담아 내리는 영상·이미지 주소의 접두어(§5). 그래서 이 한 줄만 맞으면 둘 다 맞는다.

## 5. WAS 서버 설정 — ★할 것이 없다 (자동 도출)

**결론부터: 리눅스 서버에 아무것도 넣지 않아도 된다.**

### 원래 무슨 문제였나

저작도구 백엔드는 **영상 재생 주소**와 **프레임 이미지 주소**를 응답 안에 «완성된 주소»로 담아
내려준다. 브라우저가 그걸 그대로 `<video src=…>` 에 물기 때문이다.

그런데 그 주소가 **`/api/v1/…` 로 코드에 박혀 있었다.** 포털 앞단에서 `/api/v1/` 은
**포털 자신의 백엔드**로 가므로 —

> **영상과 이미지 요청이 전부 남의 서버로 날아가서, 화면은 뜨는데 영상이 안 나온다.**

### 어떻게 해결했나

그 접두어를 **WAR 웹 컨텍스트에서 스스로 계산**하도록 바꿨다.

```
브라우저가 부르는 주소  =  WAR 웹 컨텍스트  +  /v1
```

| 배포 | 웹 컨텍스트 | 자동으로 나오는 값 |
|---|---|---|
| 포털향 | `/authoring-api` | `/authoring-api/v1` ✅ |
| 관제향 | `/label-studio/api` | `/label-studio/api/v1` ✅ |
| 로컬(도커) | `/api` | `/api/v1` (종전과 동일) ✅ |

**왜 이게 성립하나** — 두 사실이 겹쳐서다.
1. 저작도구 컨트롤러는 **예외 없이 컨텍스트 바로 아래 `/v1` 에서 시작한다**(저장소 불변식).
2. 아파치가 접두어를 **그대로 넘긴다**(§7 실측 확인).

### 이득 — 헷갈릴 자리가 하나 없어졌다

웹 컨텍스트(`KLID_WEB_CONTEXT`)는 **was 잡에서 이미 정한다.** 그 값 하나만 바꾸면
공개 주소도 같이 움직인다. **값을 두 곳에 적게 하면, 한 곳만 바꿨을 때 아무 신호 없이
영상이 남의 서버로 간다** — 그 자리를 통째로 없앤 것이다.

⇒ **§4 의 `KLID_WEB_CONTEXT` 한 줄이 곧 이 값이다.**

### 맞게 잡혔는지 확인하는 법

WAS 기동 로그에 **한 줄** 남는다.

```
[PublicApiPath] 브라우저 호출 접두어 = /authoring-api/v1 (출처: 웹 컨텍스트('/authoring-api') + /v1)
```

```sh
# WAS 로그에서 찾기
grep PublicApiPath <WAS 로그>
```

### 혹시 값이 틀리게 나오면 (예비 수단)

앞단이 접두어를 **떼고** 넘기는 향이라면 도출이 맞지 않는다. 현재 그런 향은 없지만,
그때는 **설정으로 덮으면 된다** — 설정이 언제나 이긴다.

`/etc/klid/application.properties` 에 한 줄:

```properties
authoring.public-api-base-path=/authoring-api/v1
```

> 💡 이 파일은 DB 접속정보 등이 이미 들어 있는 **기존 설정 파일**이다. 새로 만들 것도,
> `JAVA_OPTS` 를 건드릴 것도 없다.
> ⚠ 형식이 어긋나면(스킴·호스트·`..`·질의·공백) **기동이 실패한다** — 오타를 배포 시점에
> 잡으려고 일부러 그렇게 만들었다.

## 6. 다 하고 나서 확인하는 법

### 가장 빠른 방법

> **`klid 저작도구 was` 잡을 한 번 돌린다.**
> 배포 후 아파치를 거쳐 헬스체크를 때리므로, **200 이면 값이 전부 맞은 것**이다.

### 손으로 확인하려면

```sh
# ① 부품 파일이 자바스크립트로 오는가 (text/html 이면 아직 안 됨)
curl -sI http://<개발망 호스트>:38081/label-remote/remoteEntry.js | grep -Ei 'HTTP/|content-type|cache-control'

# ② ★없는 파일이 404 인가 (200 이면 아파치 폴백이 아직 덮고 있음)
curl -sI http://<개발망 호스트>:38081/label-remote/assets/no-such-chunk.js | head -1

# ③ ★저작도구 API 가 200 인가 (404 면 접두어가 어긋남)
curl -s http://<개발망 호스트>:38081/authoring-api/actuator/health/liveness
```

### 화면으로 확인하려면

포털 프론트의 `.env.local` 에 `VITE_AUTHORING_REMOTE_ENABLED=true` 를 두고
**`/workspace/authoring`** 에 들어간다.

> ⚠ **`/label-remote/` 를 브라우저로 직접 열어도 화면은 안 뜬다.** 그건 부품을 내려받는
> 주소이지 사람이 들어가는 주소가 아니다. 정상이다.

## 7. 실측 결과 — 아파치 최종본을 로컬에 올려 확인함

포털이 반영했다는 최종 `httpd.conf` 를 로컬 Apache 2.4 에 그대로 올리고, 저작도구 실제 번들과
컨텍스트를 가진 모의 WAS 를 붙여 측정했다.

| 확인 항목 | 결과 |
|---|---|
| 문법 검사 | **통과** |
| `/label-remote/remoteEntry.js` | 200 · `text/javascript` · `no-cache, must-revalidate` ✅ |
| `/label-remote/assets/*.js` | 200 · `immutable`(장기 캐시) ✅ |
| **없는 청크** | **404** ✅ ← 이게 핵심 |
| 폰트 | `immutable` ✅ |
| `/authoring-api/…` | **200** · WAS 가 `/authoring-api/actuator/…` 를 받음(접두어 유지) ✅ |
| 압축 | CSS **870,476 B → 243,917 B** (72% 감소) ✅ |
| 옛 이름 잔재 | `/author/`·`/author-api/`·`/authoring-repo/` **0건** ✅ |

**⚠ 함께 확인된 함정** — 옛 주소 `/author/`·`/author-api/` 는 이제 **404 가 아니라 「포털
홈페이지」 200** 을 돌려준다. 그래서 §3 의 Verify 를 Content-Type 검사로 바꾼 것이다.

## 8. 자주 헷갈리는 것

**Q. 폴더는 `author` 인데 주소는 `/label-remote/` — 오타 아닌가요?**
A. 맞습니다. 아파치가 `Alias /label-remote/ → www/author/` 로 이어 줍니다.
   **`DEPLOY_DIR` 을 `label-remote` 로 바꾸면 오히려 깨집니다.**

**Q. `VITE_BASE_PATH` 와 `VITE_API_BASE_URL` 이 헷갈립니다.**
A. 앞은 **화면 파일(JS·CSS) 주소**, 뒤는 **백엔드 주소**입니다. 완전히 다릅니다.
   portal 채널에서 앞은 **주면 안 되고**, 뒤는 **줘야** 합니다.

**Q. 저작도구 번들을 다시 빌드해야 하나요?**
A. **아닙니다.** 포털이 계약값(`/label-remote/`·`./PortalApp`)을 그대로 확정했고,
   저작도구 번들은 이미 그 값으로 만들어져 있습니다.

**Q. 리눅스 서버에 뭘 넣어야 하나요?**
A. **아무것도 안 넣어도 됩니다.** 예전 판에는 환경변수 하나를 넣으라고 적었는데,
   코드가 WAR 웹 컨텍스트에서 **자동으로 도출**하도록 바꿨습니다(§5).
   맞게 잡혔는지는 WAS 기동 로그의 `[PublicApiPath]` 한 줄로 확인합니다.

**Q. 관제향(다른 배포본)도 바꿔야 하나요?**
A. **아닙니다.** 관제향은 웹 컨텍스트가 `/label-studio/api` 라 자동 도출도 그 값에 맞고,
   `/authoring-api/` 는 포털 앞단에만 있습니다.

**Q. `control` 채널은 이제 못 쓰나요?**
A. 씁니다. §3 스크립트가 채널별로 갈라 놨습니다 — `control` 로 돌리면 독립 앱이 나오고
   `/label-remote/` 를 브라우저로 직접 열어 배선을 눈으로 볼 수 있습니다.
   ⚠ 단 채널을 바꿔 돌리면 **그 폴더를 덮어씁니다.** 점검이 끝나면 `portal` 로 다시 돌리세요.

**Q. 순서를 틀리면 어떻게 되나요?**
A. web 잡을 안 고치면 **빌드가 죽습니다**(바로 보입니다).
   §3~§5 중 하나만 하면 **아무 신호 없이 API 만 전부 404** 가 납니다(안 보입니다).
   그래서 한 번에 하고 §6 으로 확인하는 게 안전합니다.

젠킨스와 무관하지만 남아 있는 항목이다. 포털도 회신에서 같은 3건을 적었다 — 인식은 일치한다.
