# 포털 정리 삭제 트리거 호출이 401 로 전건 거부된다 — 원인과 조치

> ✅ **해소 완료 (2026-09-10 17:13)** — 아래 §7 에 실측 근거와 현장 형상을 남겼다.
> 다시 같은 증상이 나면 §7 의 「현장 형상」 표부터 보면 탐색을 건너뛸 수 있다.

> 작성 2026-09-10 · 대상 창구 `POST /authoring-api/v1/portal-system/dataset-cleanups`
> 관련 `INT-014` · `API-244` · `AC-1103` · `CO-20260910-포털-소재조달-배선` §8

## 0. 한 줄 결론

**코드 결함이 아니다.** 사전 공유 API 키가 **양쪽 어디에도 주입된 적이 없어**, 창구가 설계대로
닫혀 있는 것이다(fail-closed). WAS 에 `PORTAL_CLEANUP_API_KEY` 를 넣고 포털이 같은 값을
`x-api-key` 헤더로 보내면 202 로 바뀐다.

## 1. 증상

포털 측 로그(2026-09-10 15:43):

```
ERROR ...HttpAuthoringCleanupClient - 저작도구 cleanup 통보 거절(재시도 안 함)
  POST http://<개발망 호스트>:38081/authoring-api/v1/portal-system/dataset-cleanups
  req={"datasetCode":"DS-FLOOD-2025-01","version":"11.0.0"}
  → status=401 resp=(빈 본문)
```

학습데이터가 버전업되어 포털이 정리 삭제 트리거를 보냈고, 저작도구가 401 로 거절했다.

## 2. 원인 — 값이 없어서 닫혔다

| # | 확인한 것 | 실측 |
|:-:|---|---|
| 1 | `common/security/PortalSystemApiKeyFilter` | 설정이 비면 `expectedKey = null` → `matches()` 가 **무조건 거짓** → `SecurityContext` 를 비우고 통과 → 인가 계층이 401 |
| 2 | `backend/src/main/resources/application.yml` | `cleanup-api-key: ${PORTAL_CLEANUP_API_KEY:}` — **기본 빈 값** |
| 3 | `deploy/onprem/config/backend/env.template` · `application.properties.template` | 둘 다 **빈 값으로 출고** |
| 4 | 젠킨스 WAS 잡 | 그 변수가 **선언 자체가 없다** |
| 5 | `docs/contracts/portal-회신-3차-20260909.md` §6 | `① cleanup x-api-key 값 \| 저작도구 \| **인프라 대기**` — **발급·공유가 아직 안 됐다** |

즉 **우리도 값이 없고 포털도 무엇을 보낼지 모르는** 상태다. 포털이 무엇을 실어 보내든 통과할 수 없다.

이 상황은 코드가 **미리 경고해 둔 것**이다 — 필터 생성자 주석:

> ⚠ **그 대가**: 포털이 호출을 시작했는데 우리 쪽 키가 비어 있으면 **전건 거부**가 되고,
> 포털에는 「키가 틀렸다」로 보인다.

### 왜 「비면 열림」이 아니라 「비면 닫힘」인가

배포에서 키 주입을 잊었을 때 창구가 **무인증으로 열려 있는 것**보다 아예 안 받는 편이 낫다.
값이 없을 때 닫히는 방향이라 안전하다(fail-closed). 대신 **조용하다** — 그래서 이 문서가 필요하다.

## 3. 조사 중 확인된 것 — 아파치 허용목록은 **정상 동작 중**

개발 PC(허용목록 밖)에서 같은 창구를 직접 치면:

```
$ curl -i -X POST http://<개발망 호스트>:38081/authoring-api/v1/portal-system/dataset-cleanups \
       -H 'Content-Type: application/json' -H 'x-api-key: test' \
       -d '{"datasetCode":"DS-FLOOD-2025-01","version":"11.0.0"}'

HTTP/1.1 403 Forbidden
Server: Apache
Content-Type: text/html; charset=iso-8859-1
<h1>Forbidden</h1>
```

**이 403 은 오류가 아니라 증거다.** `docs/operations/포털-아파치-설정-요청-20260910.md` 에서 요청한
IP 허용목록이 실제로 걸려 있다는 뜻이다:

```apache
<Location "/authoring-api/v1/portal-system/">
    Require ip <등록 파트너망 #1~#4>
    Require ip 127.0.0.1
</Location>
```

| 부른 쪽 | 응답 | 어디서 났나 |
|---|---|---|
| 개발 PC (허용목록 **밖**) | **403** HTML `Server: Apache` | **아파치** — 우리 앱에 닿지도 않음 |
| 포털 서버 (허용목록 **안**) | **401** | 아파치 통과 → **우리 앱**이 거절 |

⇒ 포털이 받은 401 은 **우리 앱이 낸 것**이고, 원인은 앞단이 아니라 **키**다.

### 「빈 본문」에 대하여

우리 앱의 401 은 **항상 JSON 본문을 싣는다** — `SecurityConfig.writeError` 가
`ApiResponse.error(UNAUTHORIZED)` 를 써 넣는다. 포털 로그의 `(빈 본문)` 은 그쪽 HTTP 클라이언트가
오류 본문을 읽지 않은 것으로 보인다. **본문 없음을 근거로 「앞단에서 잘렸다」고 판단하지 말 것** —
이 건에서는 그 추론이 틀렸다.

## 4. 조치

### 4-1. ★ 값이 갈 자리 — 젠킨스도 `standalone.conf` 도 아니다

대상 WAS 는 **JBoss EAP 8.1** 이고, 이 저장소는 값의 성격마다 자리를 갈라 두었다.

| 값의 성격 | 자리 | 근거 |
|---|---|---|
| 웹 컨텍스트 · 배포 향 · CORS 출처 | **WAR 에 구움**(빌드 시점) | 젠킨스가 WAR 를 떨구기만 하고 WAS 를 기동하지 않는다 |
| JVM 기동 옵션 | `$JBOSS_HOME/bin/standalone.conf` | — |
| **시크릿 (이 키가 여기다)** | **`/etc/klid/application.properties`** | `standalone.conf.example`: *"시크릿은 적지 않는다 — 그것들은 `/etc/klid/application.properties` 에 있고"* |

⚠⚠ **`-D` 시스템 프로퍼티로 넘기지 말 것** — `ps -ef` 에 그대로 보여 그 장비의 어느 계정이나
읽는다(CWE-214). 같은 파일이 그 금지를 명시한다.

⚠ **젠킨스 `environment { }` 에 넣어도 반영되지 않는다.** 굽는 값의 표
(`backend/build.gradle` 의 `klidBakedSettings`)에 이 키가 없고, 젠킨스는 WAS 프로세스를 띄우지
않는다. **아무 오류 없이 그냥 빈 값이 된다.**

★ `deploy/onprem/config/backend/application.properties.template` 에 **`PORTAL_CLEANUP_API_KEY=`
자리가 이미 비워진 채 주석까지 달려 있다.** 원래 거기 넣게 설계돼 있었다.

### 4-2. 런북 (WAS 호스트에서 그대로 붙여넣기)

**① 현장값 읽고 설정이 «어디서» 오는지 확인 — 추측하지 않는다**
```bash
source /etc/klid/was.env 2>/dev/null; echo "UNIT=$WAS_UNIT  LOG=$WAS_LOG_DIR"
ps -ef | grep '[j]boss' | tr ' ' '\n' | grep -E 'spring.config.additional-location|spring.profiles.active'
```

**②-A `-Dspring.config.additional-location=file:/etc/klid/` 가 보이면** — 정상 형상이다
```bash
sudo cp -a /etc/klid/application.properties /etc/klid/application.properties.bak.$(date +%Y%m%d%H%M)

# 자리가 이미 있으면 값만 채우고, 없으면 덧붙인다
if sudo grep -q '^PORTAL_CLEANUP_API_KEY=' /etc/klid/application.properties; then
  sudo sed -i "s|^PORTAL_CLEANUP_API_KEY=.*|PORTAL_CLEANUP_API_KEY=<키값>|" /etc/klid/application.properties
else
  echo 'PORTAL_CLEANUP_API_KEY=<키값>' | sudo tee -a /etc/klid/application.properties >/dev/null
fi

# WAS 실행 계정이 읽을 수 있어야 한다 — 못 읽으면 WAS 는 뜨고 앱만 설정 없이 돈다
sudo -u "${WAS_USER:-jboss}" head -c1 /etc/klid/application.properties >/dev/null && echo "읽기 OK"
```

**②-B 그 옵션이 «안» 보이면** — 외부 설정 주입 자체가 없다. WAS 유닛의 환경 파일을 찾는다
```bash
systemctl cat "$WAS_UNIT" | grep -iE 'EnvironmentFile|ExecStart'
```
`EnvironmentFile=` 이 있으면 그 파일에 `PORTAL_CLEANUP_API_KEY=<키값>` 한 줄을 더한다.
없으면 `standalone.conf` 에 `-Dspring.config.additional-location=file:/etc/klid/` 를 먼저 붙여
②-A 형상으로 만드는 편이 낫다(다른 시크릿도 같은 자리를 쓰게 된다).

**③ 재기동** — 설정 파일이라 재배포로는 반영되지 않는다
```bash
sudo systemctl restart "$WAS_UNIT"
```

**④ 확인 — 기동 로그 한 줄**
```bash
grep -n 'PortalSystemApiKey' "${WAS_LOG_DIR:-$WAS_HOME/standalone/log}/server.log" | tail -3
```
기대: `[PortalSystemApiKey] 정리 트리거 창구의 사전 공유 키가 설정됐습니다.`
⚠ 이 줄은 **값을 싣지 않는다**(의도) — 「설정됐다」는 사실만 남긴다.

**⑤ 왕복 확인 — 루프백은 허용목록 안이다**
```bash
curl -i -sS -X POST http://localhost:38081/authoring-api/v1/portal-system/dataset-cleanups \
  -H 'Content-Type: application/json' -H 'x-api-key: <키값>' \
  -d '{"datasetCode":"DS-FLOOD-2025-01","version":"11.0.0"}'
```
기대 **202**. 키를 일부러 틀리게 주면 **401 + JSON 본문**이 나온다(그게 정상 동작 확인이다).

**⑥ 포털에 통보** — 같은 값을 `x-api-key` 요청 헤더로 실어 달라고 전달한다.
양쪽이 같아야 통과한다.

### 4-3. ⚠ 키 값을 이 문서에 적지 않는다

위 런북의 `<키값>` 은 **일부러 비워 두었다.** 이 문서는 저장소에 커밋되므로 값을 적으면
시크릿이 이력에 영구히 남는다(CWE-798). 값은 안전 채널로만 오간다.

⚠ **개발망에서 임시로 쓰는 값이 JWT 서명 시크릿과 같은 문자열이면 운영 전에 반드시 갈라야 한다** —
한쪽이 유출되면 **토큰 위조까지 함께 열린다**(§5).

## 5. ⚠ 키를 섞지 말 것

지금 이 연동 축에 얽힌 키가 **셋이고 발급 주체가 서로 다르다.** `INT-014` 가
*"연동 축마다 별도 키를 두라"* 를 포털의 명시 요청으로 기록해 두었다.

| 키 | 발급 | 방향 | 설정 |
|---|---|---|---|
| **정리 트리거** `x-api-key` | **저작도구** | 포털 → 우리 | `PORTAL_CLEANUP_API_KEY` |
| **소재 조회** `x-api-key` | **포털** | 우리 → 포털 | (신설 예정 — `CO-20260910-포털-소재조달-배선`) |
| JWT 서명 시크릿 | 포털 | 토큰 축 | `JWT_SECRET` |

⚠ 개발 편의로 세 값을 하나로 맞춰 쓸 수는 있으나 **운영 전에 반드시 갈라야 한다.**
특히 JWT 서명 시크릿을 API 키로 돌려쓰면 한쪽이 유출될 때 **토큰 위조까지 열린다.**

★ **④ 는 이번 로그에서 새로 눈에 띈다** — 포털이 보낸 값이 `"11.0.0"` 이다. 3차 회신 §2.2 에서
`v3` 와 `v3.0` 표기 차이를 물어 둔 축인데, 실제로는 **접두 `v` 가 없는 세 자리 표기**가 왔다.
우리 접수 원장은 이 값을 **문자열 그대로 보존**하므로 접수 자체는 문제없으나, 나중에 「트리거가 말한
그 버전의 소재」를 찾을 때 **표기가 갈리면 매칭이 안 된다.** ③과 함께 확정해야 한다.

### 7-2. ★ 현장 형상 — 다음에 같은 일이 생기면 여기부터 본다

원인 규명보다 **「어느 것이 우리 것인가」를 찾는 데 시간이 더 걸렸다.** 그 답을 남긴다.

| 항목 | 값 |
|---|---|
| WAS 인스턴스 | **`/opt/jboss-eap-8-3rd`** |
| systemd 유닛 | **`jboss8-3rd.service`** |
| 애플리케이션 로그 | **`/nas-storage/logs/jboss/db-primary/jboss-server-8-3rd/server.log`** |
| 외부 설정 | `/etc/klid/application.properties` (`cudo:cudo` `640`) |
| 스프링 배선 | `-Dspring.config.additional-location=file:/etc/klid/` · `-Dspring.profiles.active=dev` |
| 배포물 | `standalone/deployments/api.war` (+ `.deployed` 마커) |

### 7-3. ⚠ 두 번 헛짚은 자리 — 같은 실수를 반복하지 말 것

**① 그 장비에 JBoss 인스턴스가 다섯 개다.**
`eap-7` · `eap-8` · `eap-8-2nd` · **`eap-8-3rd`** · `wildfly` 가 모두 running 이다.
`grep -m1 -Djboss.home.dir=` 로 첫 번째를 집으면 **`eap-7`(남의 `account.war`)** 이 잡히고,
그 인스턴스의 `server.log` 는 2025년 11월에 멈춘 파일이라 **"로그에 아무것도 없다"**로 오판하게 된다.

⇒ **인스턴스는 「-Dspring.config.additional-location 을 가진 프로세스」로 특정한다.** 실측상 다섯 중
그 옵션을 가진 것은 하나뿐이었고, `api.war` 가 놓인 곳과도 일치했다(두 축이 교차 확인된다).

```bash
ps -eo pid=,args= | grep '[j]ava' | while read -r pid rest; do
  home=$(printf '%s' "$rest" | tr ' ' '\n' | grep -m1 -- '-Djboss.home.dir=' | cut -d= -f2-)
  cfg=$(printf '%s' "$rest" | tr ' ' '\n' | grep -m1 -- '-Dspring.config.additional-location=' | cut -d= -f2-)
  [ -n "$home" ] && printf "pid=%-8s home=%-28s spring=%s\n" "$pid" "$home" "${cfg:-(없음)}"
done
```

⚠ **재기동 대상을 틀리면 남의 서비스가 죽는다.** 반드시 위로 확정한 뒤 그 유닛만 restart 한다.

**② 애플리케이션 로그가 `$JBOSS_HOME/standalone/log/` 에 없다.**
그 자리의 `server.log` 는 껍데기이고 실체는 **NAS** 에 있다. 우리 앱은 Logback 을 CONSOLE 로 쓰고
EAP 가 그 표준출력을 NAS 로 돌린다.

⇒ 로그 위치는 추측하지 말고 **프로세스가 열고 있는 파일**로 확정한다:
```bash
sudo ls -l /proc/<pid>/fd | grep -i '\.log' | sed 's/.*-> //' | sort -u
```

### 7-4. 판정에 쓸 수 있었던 가장 짧은 경로

되짚어 보면 아래 셋이면 충분했다.

| # | 확인 | 뜻 |
|:-:|---|---|
| 1 | `spring.config.additional-location` 을 가진 프로세스 | 우리 인스턴스 특정 |
| 2 | `unzip -l api.war \| grep PortalSystemApiKeyFilter` | 배포본이 그 창구를 가진 판인가 |
| 3 | `grep -c '^PORTAL_CLEANUP_API_KEY=' /etc/klid/application.properties` | 키가 들어 있는가 |

이번 건은 **1 정상 · 2 정상(오늘 06:57 빌드) · 3 = 0** 이었고, 그래서 「값만 없다」로 확정됐다.

### 7-5. 남은 것

- **포털 측 재테스트** — 우리 쪽 적용을 통보했고 포털이 자기 클라이언트로 재확인한다.
- **재기동 후 화면 정상 여부** — `[DeployFlavor] 배포 향 = PORTAL` 이 로그에 있어야 한다.
  없으면 포털 화면이 「접근 권한이 없습니다」로 막힌다(별건이나 이 재기동에 딸려 온다).
  ⚠ 이 값은 **빌드 시점에 WAR 에 굽는 값**이라, 어긋나 있으면 **설정이 아니라 재빌드**가 필요하다.
- **운영 반영 시 키 교체** — 이 값은 개발망용이다.
- **버전 표기 확인** — 실 트래픽 관측 2건이 **둘 다 접두 없는 세 자리**였다(`11.0.0` · `14.0.0`).
  규격 문서의 예시(`v3` · `v3.0`)와 형태가 다르며, **실제 표기는 일관돼 보인다.**
  ⚠ 그래도 확인이 필요한 이유는 **소재 조회 응답의 버전 필드가 같은 표기를 쓰는지 모르기 때문**이다.
  둘이 갈리면 「트리거가 말한 그 버전의 소재」를 찾지 못하고, 접수 원장의 유일 제약이
  (데이터셋 코드 + 버전)이라 **같은 버전이 다른 행으로 앉아 재수신 멱등이 조용히 깨진다**(`ERD-035`).
  ⚠ 표기 규칙을 우리가 정하지 않는다 — 상호 확정 대상이며 확정 전까지 원문을 그대로 보존한다.
