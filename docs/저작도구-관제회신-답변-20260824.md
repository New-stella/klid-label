## 0. 인입 대상 확인

이해하신 그대로입니다. `ls_data_ingest`가 관제 팀의 INSERT 대상이고, `ls_data_raw`는 저작도구가 `ls_data_ingest`를 주기 폴링해 적재하는 산출 테이블입니다(ADR-042, 적재 주체 반전).

## 1. `vms_clip_id` — `video_asset_id`로 대체 가능

`vms_clip_id`는 규격서에 "관제 영상 식별자, 저작도구 내 유일값(UNIQUE)"으로만 정의돼 있어, 값의 발급 체계를 저희가 검증하지 않는 순수 식별자입니다.

우려하신 "성격이 다른 두 식별자 혼재"는 **`src_type`이 이미 구분자 역할**을 합니다 — `src_type='RELAY'`면 clip_id, `USER_ULD`/`GENERATED`(수동 업로드·생성형AI·재난영상 요청 업로드가 이쪽으로 분류될 것으로 이해합니다)면 `video_asset_id`로 보내주시면 저희 쪽에서 값만으로 구분할 필요가 없습니다.

**결론: `video_asset_id`로 대체 전달해 주셔도 됩니다.** 다만 `vms_clip_id`에 `UNIQUE` 제약이 걸려 있으니, `video_asset_id` 체계도 전역 유일함을 관제 쪽에서 보증해 주셔야 합니다.

## 2. 개인정보 관련 값 송신 여부 — 이해 정확

`anony_incl_yn`/`psdo_incl_yn`/`prvc_incl_yn` 3개 컬럼은 값을 채우지 않고 보내시면 정확히 **N/N/Y**로 들어갑니다(컬럼 기본값). 식별/비식별 판정은 현재 저작도구 소유이므로, 관제 쪽에서 이 3필드를 채우려 애쓰지 않으셔도 됩니다.

## 3. 이벤트 발생시각 — 별도 컬럼 불필요

말씀하신 대로 `sht_dt`는 촬영일시(관제 `video.date_created`)이지 이벤트 발생시각과는 다른 개념이 맞습니다. 다만 확인 결과, **저작도구 쪽에는 이벤트 발생시각이라는 개념 자체가 처음부터 존재하지 않습니다.**

- 내부 파이프라인(VLM 시계열·이벤트 어노테이션·마킹) 전부 이벤트를 **영상 내 프레임 상대 위치**로 다루고, 절대시각(wall-clock) 기준의 "이벤트 발생시각"을 쓰는 곳이 없습니다.
- 저작도구가 생성하는 학습데이터 export JSON(NIA COCO 확장 포맷, 어노테이션 spec v1.3)의 `video` 블록 전체 필드를 봐도 `date_created` 하나뿐이고, 이벤트 발생 절대시각에 해당하는 별도 출력 필드가 없습니다.

**결론: `sht_dt`에 촬영일시만 실어 보내 주시면 충분하고, 별도 필드는 필요 없습니다.**

## 4. 썸네일 이미지 경로 — 수용, 신규 컬럼 추가

관찰하신 대로 `klid_at` 스키마에는 썸네일 계열 컬럼이 없었습니다. 관제 팀 편의를 위해 신규 컬럼을 추가하기로 했습니다.

- **`ls_data_ingest.THMB_FILE_PATH_NM`**(썸네일파일경로명, `varchar(500)`, nullable) 신설
- 값은 관제가 인입 시 채워 보내주시는 **pass-through**입니다 — 저작도구가 생성·가공하지 않습니다.
- `V_COMPLETED_VIDEO`(관제가 SELECT하시는 데이터마트 뷰)에도 그대로 노출해, 패키징 시 이 뷰 하나만 보시면 되도록 반영합니다.

값을 안 보내셔도 인입이 실패하지 않습니다(nullable).

## 5·7. 비트레이트 — 저희 쪽 설계 오류를 확인했습니다

두 항목을 묶어 답변드립니다. 재확인한 결과, **`BIT`이 색심도가 아니라 비트레이트였다는 관제 팀의 추정이 맞았습니다.**

- 저희 규격서 §10과 관련 코드 주석에는 지금까지 `BIT`을 "색심도 표기(예: `24bit`), 비트레이트가 아니다"로 명시해 왔습니다.
- 그런데 2026-07-31 설계 검토 시점에 저희가 관측한 관제 실DB `video.bit` 실제값은 `24bit` 형식이 아니라 `bit_rate=2050627` 같은 bps 단위 숫자였습니다. 당시 이 모순을 발견하고도 결론을 내리지 않고 보류해 둔 상태였습니다.
- 이번에 관제 팀이 독립적으로 같은 의심을 제기해 주셔서, 실측과 관제 측 확인이 수렴했다고 판단해 **`BIT`을 비트레이트로 재정의**하기로 확정했습니다.

**조치**:
- 규격서 §10·컬럼표의 `BIT` 설명을 "비트레이트(bps), 예: `2050627`"로 정정합니다.
- 저작도구 내부적으로도 지금까지 `ls_data_ingest.BIT`을 쓰지 않고 매번 ffprobe로 별도 비트레이트를 추출해 왔는데, 이제 관제가 보내주시는 `BIT` 값을 우선 사용하고 값이 없거나 파싱 불가할 때만 ffprobe로 폴백하도록 바꿉니다. **관제 쪽에서 별도로 하실 일은 없고, 지금처럼 실제 비트레이트 숫자를 `BIT`에 계속 보내주시면 됩니다.**
- `ls_data_ingest.bit`(원래 색심도용 varchar(20) 컬럼)과 `ls_dataset_video_meta.bit_rt`(저작도구 ffprobe 산출 컬럼)는 그대로 유지되며, 컬럼 추가는 없습니다 — 기존 컬럼의 의미만 정정합니다.

## 6. 송부자 ID — 관제 측 보관에 동의

저희 쪽 `ls_data_ingest`·`ls_data_raw` 모두 실제로 사용자(송부자) 식별 컬럼을 두고 있지 않습니다. 저작도구의 감사 추적은 저희 내부 작업자·검수자 행위 기준이라 외부 송부자 개념과는 축이 다릅니다.

**결론: 관제 측에서만 보관하시는 방향에 동의합니다. 저작도구로 전달하지 않으셔도 됩니다.**

## 8. `og_cd`(기관코드) 폐기 건 — 재추가하겠습니다

이 컬럼은 저희가 임의로 없앤 것이 아니라, **2026-08-12 관제 팀이 직접 "현행 미사용·공급 불가"로 요청**해 그 근거로 제거했던 컬럼입니다(마이그레이션 `V185`). 이번에 관제 팀이 "실제로는 데이터를 보유하고 있다"고 재확인해 주셔서, **말씀대로 바로 재추가**합니다.

- `ls_data_ingest.OG_CD`(기관코드, `varchar(20)`, nullable) 복원.
- 다만 **DROP 시점에 값이 소실**됐으므로, 재추가 이후 신규로 인입되는 행부터 값이 채워집니다(과거 행 복구는 불가).
- export JSON(`og_cd` 필드)은 이전에도 이 컬럼과 배선돼 있지 않았고(원래부터 `null` 고정 출력) 이번 재추가에서도 배선하지 않습니다. 산출물로 내보내는 게 필요하시면 별도로 말씀해 주시면 검토하겠습니다.

## 9. 재확인 요청 — VLM 위탁용 `VRFC_EVNT_TYPE_CD` (이전 요청, 아직 회신 못 받음)

이번 8건과는 별개로, 2026-08-05 개발항목 문서로 요청드렸던 건에 대해 아직 답변을 받지 못해 다시 여쭙습니다.

- **컬럼은 이미 존재합니다** — `ls_data_ingest.VRFC_EVNT_TYPE_CD`(검증이벤트유형코드, `varchar(20)`)는 저희 쪽에 이미 반영돼 있습니다.
- **외부 VLM 벤더(IntelliVIX Video VLM API v2.0.1) 이벤트 검증 위탁에 이 값이 필수**입니다 — `fire`·`fall`·`violence`·`flooding`·`car_accident`·`kidnapping` 6종 중 하나를 소문자로 채워 보내주시면 됩니다. 해당 없는 이벤트는 채우지 않으셔도 됩니다(NULL — 임의 근사값은 넣지 말아 주세요).
- **아직 값을 안 보내주고 계셔서**, 현재는 신규 인입 영상마다 VLM 위탁을 건너뛰고 사유만 기록하는 상태입니다. 데이터가 유실되진 않습니다 — 관제가 값을 채우기 시작하면 그 시점부터 신규 인입분이 자동으로 정상 위탁됩니다(과거 스킵분은 저희 쪽 수동 재처리 대상).

이 컬럼 반영 일정을 확인해 주실 수 있을까요? 저희 쪽 구현·검증은 이미 끝나 있어 **관제 송신만 시작되면 즉시 동작합니다.**
