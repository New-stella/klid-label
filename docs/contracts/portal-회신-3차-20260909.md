## 1. §2 일일 저작 집계도 `x-api-key` — 수용합니다 ✅

| 항목 | 결정 |
|---|---|
| 인증 수단 | **사전 공유 API 키**(`x-api-key`) — 정리 트리거와 동일 |
| 키 값 | **같은 키**를 씁니다 (연동 축 하나 = 키 하나) |
| 매처 | 제안대로 **접두 `/v1/portal-system/` 전체를 한 매처**로 덮습니다 |

- 저작도구 설계에 **반영 완료**했습니다. 직전 회신에서 이 창구를 「미확정」으로 남긴 것은
  근거가 없어서였고, 이번 회신이 그 근거이므로 **미확정을 닫은 것**입니다(판단을 뒤집은 것이 아닙니다).
- ⚠ 그 창구 자체는 **아직 구현 전**입니다. 인증 축만 확정됐습니다.

## 2. ★★ 진행 차단 — 정리 트리거와 소재 조회가 서로 이어지지 않습니다

**이것이 이번 회신의 핵심입니다.** 규격은 받았지만, 그것만으로는 조달을 시작할 수 없습니다.

```
포털 → 저작도구 (cleanup) :  { "datasetCode": "DS-2026-001", "version": "v3" }
저작도구 → 포털 (소재 조회) :  GET .../datasets/{datasetId}/materials      ← 숫자 ID
```

- 저작도구가 트리거로 받는 것은 **데이터셋 코드(문자열)** 입니다.
- 소재 조회가 요구하는 것은 **숫자 식별자** 입니다.
- **코드로 찾는 창구가 없습니다.** 응답의 `code` 는 결과일 뿐 조회 키가 아닙니다.
- 게다가 §3.5 에 *"원장 없이 적재된 옛 데이터는 `code` 가 `null` 일 수 있다"* 고 적혀 있어
  **역매칭도 신뢰할 수 없습니다.**

### 2.1 해소 방향 — 포털이 편한 쪽으로 정해 주십시오

| 안 | 내용 | 저작도구 부담 |
|:-:|---|---|
| **A** | 정리 트리거 본문에 **`datasetId` 를 함께 싣는다** | 접수 원장에 컬럼 1개 추가. 계약 필드 1개 증가 |
| **B** | **코드로 찾는 조달 창구**를 하나 더 연다 | 저작도구 변경 없음. 포털 창구 신설 필요 |

저작도구는 **A 를 선호**합니다 — 창구를 늘리지 않고, 트리거가 이미 그 데이터셋을 특정하고 있어
식별자를 함께 싣는 것이 자연스럽습니다. 다만 **포털 구현 부담을 저작도구가 판단할 수 없으므로
선택은 포털에 맡깁니다.**

### 2.2 함께 확인 부탁드립니다 — 버전 문자열이 같은 값입니까?

트리거 예시는 `"v3"` 이고 소재 조회 응답 예시는 `"v3.0"` 입니다.
**두 값이 같은 데이터셋을 가리키는데 문자열이 다르면**, 저작도구가 "트리거가 말한 그 버전의 소재"를
지목할 수 없습니다. 같은 값인지, 표기만 다른 것인지 알려 주십시오.

## 3. 소재 조회 규격 — 접수했습니다. 짚을 점 4가지

규격 자체는 명확합니다. 저작도구 쪽 전제를 밝혀 둡니다.

### 3.1 ★ `localPath` 는 `repoRootDir` 하위만 읽습니다 (fail-closed)

외부에서 받은 절대경로를 저작도구가 파일 시스템에서 직접 여는 구조이므로,
**응답이 함께 준 `repoRootDir` 하위인지 실경로로 재검증한 뒤 그 경로로만** 엽니다.

⇒ **`repoRootDir` 밖을 가리키는 `localPath` 는 읽지 않고 거부합니다.**
심볼릭 링크로 루트 밖을 가리키는 경우도 같습니다. 정상 동작이며 결함이 아닙니다.
포털 쪽에서 소재를 루트 밖에 두는 형상이 있다면 미리 알려 주십시오.

### 3.2 공유 마운트가 전제입니다 — 확인이 필요합니다

`localPath` 가 로컬 절대경로이므로 **포털과 저작도구 포털 채널 배포본이 같은 저장소를 공유
마운트**해야 성립합니다. 그런데 저작도구 설계상 **포털 채널 배포본의 NAS 는 포털이 관리하는
별도 NAS** 로 되어 있어, 그것이 `dataset_repo_root_dir` 과 같은 저장소인지 **확인되지 않았습니다.**
④(접속 파라미터) 공유 시 함께 회신 부탁드립니다.

### 3.3 봉투 없음 · 널 허용 — 수용합니다

- 표준 봉투를 쓰지 않는 평문 객체 응답, 그대로 파싱합니다.
- `code`·`variant`·`version` 이 `null` 로 와도 **실패로 다루지 않습니다.**
- 소재 목록이 **원본만**(파생물 제외)인 것도 그대로 전제합니다.

### 3.4 키 두 개는 서로 다른 축임을 확인합니다

| 축 | 발급 | 방향 |
|---|---|---|
| cleanup `x-api-key` | **저작도구가 발급** | 포털 → 저작도구 |
| 소재 조회 `x-api-key` | **포털이 발급** | 저작도구 → 포털 |

**섞지 않습니다.** 저작도구 쪽 설정도 두 값을 별도 항목으로 둡니다.

## 4. ⚠ 담당 표기 정정 — ②base-url · ③TLS

직전 회신에서 이 둘을 **「저작도구 담당 — 인프라 확정 대기」** 로 적었는데, **담당 표기가
과했습니다.** 정정합니다.

| # | 실제 축 | 정정된 담당 |
|:-:|---|---|
| ① **x-api-key 값** | 응용 레벨 비밀 | **저작도구** — 수신자가 발급하는 것이 맞습니다. 변동 없음 |
| ② **base-url** | 저작도구 서버의 주소 | **인프라 축** — 저작도구가 만들어내는 값이 아니라, **포털 채널 배포본을 세우는 주체**가 정하고 저작도구는 그것을 확인해 전달합니다 |
| ③ **TLS** | 서버 쪽 종단 | **인프라 축** — 종단 지점이 **앞단 프록시**입니다. 그 프록시를 포털이 운영하면 **포털이 정합니다** |

### 4.1 그래서 되묻습니다

> **포털 채널 저작도구 배포본의 앞단(리버스 프록시·도메인)은 어느 쪽이 운영합니까?**

이것이 정해지면 ②③의 담당이 자동으로 갈립니다. 관제 채널 형상에서는 저작도구 WAS 가 평문으로 뜨고
앞단 프록시가 받습니다 — 포털 채널도 같은 형상이라면 **TLS 를 켜고 끄는 자리가 애플리케이션이 아니라
그 앞단**입니다.

⚠ **①은 여전히 저작도구 몫이며 인프라 확정 대기 중**인 것은 변동 없습니다.

## 5. 식별자 표기 — 「API-132」는 양쪽에서 다른 것을 가리킵니다

포털이 소재 조회 창구를 **API-132** 로 부르시는데, **저작도구의 `API-132` 는 전혀 다른 창구**
(이벤트 어노테이션 조회)이며 이미 구현·사용 중입니다.

⇒ 저작도구 산출물에서는 그 창구를 **번호가 아니라 경로와 역할로** 표기합니다.
상호 문서에서도 번호 단독 인용 대신 **소속 프로젝트를 접두로 밝히거나 경로로** 불러 주시면
혼동이 없겠습니다.

## 7. 요약

- **일일 저작 집계 `x-api-key` 수용** — 접두 전체를 한 매처로 갑니다. 설계 반영 완료.
- **소재 조회 규격 접수** — 다만 `repoRootDir` 하위만 읽고, 공유 마운트 동일성 확인이 필요합니다.
- **★ 코드 ↔ 숫자 식별자를 잇는 수단이 없어 조달을 시작할 수 없습니다.** A/B 중 골라 주십시오.
- **②③ 담당 표기를 정정**했습니다 — 앞단 프록시 운영 주체를 알려 주시면 갈립니다.
