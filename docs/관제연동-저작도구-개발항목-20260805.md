## 1. 통지 페이로드 정합

### 1-1. 완료 통지 — 3필드 추가

`TaskCompletedPayload` 는 현재 6필드다. 관제 계약(API-251 v17)은 **required 8 + optional 1 = 9필드**라
현 형상으로 발송하면 **전량 `422 VALIDATION_FAILED`** 로 거부된다.

| 추가 필드 | wire 타입 | 조달 |
|---|---|---|
| `evnt_cls_cd` | string(≤2) | **인입 `LS_DATA_INGEST.EVNT_CLSF_CD` LATERAL 조인** (설계결정 D1) |
| `evnt_ctgry_cd` | string(≤4) | **인입 `LS_DATA_INGEST.EVNT_CTGRY_CD` LATERAL 조인** (설계결정 D1) |
| `gen_ai_yn` | `Y`\|`N` | **자기 `LS_DATA_RAW.SRC_TYPE IN ('GENERATED','AUGMENTED')`** (§3 참조) — 인입 조인이 **아니다** |

> ⚠ **구 표기 정정 (2026-08-05 실측)** — 이 표는 이벤트 2코드의 조달을
> *"`LS_DATA_INGEST.…` → `LS_DATA_RAW` 전파분"* 이라 적었으나 **사실이 아니다.
> `LS_DATA_RAW` 에 `EVNT_CLSF_CD`·`EVNT_CTGRY_CD` 두 컬럼은 존재하지 않는다.**
> 실제 구현은 **인입 LATERAL 조인**이며, 이는 뷰(`V_COMPLETED_VIDEO`)와 동일한 **설계결정 D1**
> — *관제 읽기전용 사실을 가변 마스터(`LS_DATA_RAW`)로 복사하지 않는다* — 을 따른 것이다.
> 연결 규칙은 앱의 단일 진실원 **`IngestSourceLink`** 를 재사용한다(파생영상은 `ORGNL_RAW_SN`
> 1단계 폴백, 최신 `RCPTN_SN` 1행). 조인 로직을 복제하지 말 것.
>
> ⚠ **JSON 키는 관제 스펙명이지 우리 컬럼명이 아니다** — `evnt_cls_cd`(관제, `cls`) ≠
> `EVNT_CLSF_CD`(우리 컬럼, `CLSF`). required 라 값이 `null` 이어도 **키는 남긴다.**

**대상 파일**
- `controlnotify/dto/TaskCompletedPayload.java` — record 필드 3개 추가(`@JsonProperty` snake_case 고정)
- `controlnotify/service/ControlNotifyPayloadFactory.java` — 조달 로직(인입 **1회 조회**로 3필드 공용)
- `controlnotify/repository/IngestSourceRepository`(+`Row`) — 인입 이벤트 2코드 조회

⚠ **`image_count` 조달 방식은 바꾸지 않는다.** 현재 `COUNT(LS_DATA_SRC)` 실측인데,
`LS_DATASET_EXPORT.FRME_CNT`(V173 개명, 구 `FRAME_CNT`) 로 바꾸면 통지와 export 가 같은 승인 이벤트를 소비하고
export 가 `@Async` 라 **통지 시점에 아직 값이 없다**(기존 N-6 레이스와 동일).
같은 이유로 `gen_ai_yn` 도 **동결 스냅샷이 아니라 라이브 `LS_DATA_RAW` 를 읽는다.**

> **2026-08-13 추가 완료 — `output_ver_no`.** 위 3필드와 별개로 관제가 **2026-08-12 수용 확정**한
> 선택 필드이며, 작업 트리에 이미 반영됐다. 상세는 §10-3.

## 4-1. ★ 관제 송신 요청 — 신규 인입 컬럼 `VRFC_EVNT_TYPE_CD` (2026-08-06 신설)

**§4 와 다른 축이다.** §4 는 *"관제가 이미 보내주고 있으나 우리가 흘리는 값"* 이고, 이 항목은
**관제가 아직 보내지 않는 값을 새로 보내달라는 요청**이다.

### 무엇을

| 항목 | 값 |
|---|---|
| 테이블 | `LS_DATA_INGEST` |
| 컬럼 | **`VRFC_EVNT_TYPE_CD`** (검증이벤트유형코드) |
| 타입 | `VARCHAR(20)` · NULL 허용 · DEFAULT 없음 · **CHECK 제약 없음** |
| 마이그레이션 | `V176__add_ingest_vrfc_evnt_type_cd.sql` (저작도구 측 적용 완료) |
| 허용값 | **소문자 6종** — `fire` · `fall` · `violence` · `flooding` · `car_accident` · `kidnapping` |

표준용어 근거 — `VRFC`(검증)=**행안부 공통표준단어**(1순위) + `EVNT`(이벤트)=사업표준단어 +
`TYPE`·`CD`=행안부. 도메인은 사업표준도메인 **`코드V20`** 으로 기존 `EVNT_TYPE_CD` 와 동일하다.

### 왜 필요한가

외부 VLM 벤더(**IntelliVIX Video VLM API v2.0.1**)의 이벤트 검증 엔드포인트
`POST /v1/videovlm/verify` 는 요청에 **`event_type` 이 필수**이며 값이 위 6종 enum 으로 고정돼 있다.
이 값 없이는 위탁 자체가 불가능하다.

**저작도구는 이 값을 자체 매핑표로 만들지 않는다** (2026-08-06 사용자 확정). 관제 이벤트 코드
(`EV0100010x` 등)를 우리가 6종으로 임의 변환하면, 관제가 코드 체계를 바꿀 때 우리 매핑이 조용히
어긋나고 그 오류가 **외부 벤더에 잘못된 검증 대상으로 전달**된다. 판정 주체는 이벤트를 정의하는
관제여야 한다.

### 관제에 요청하는 것

1. 인입 INSERT 시 이 컬럼에 **위 6종 중 하나를 소문자로** 채워 주기
2. 해당 없는 이벤트는 **채우지 않기**(NULL) — 임의 근사값을 넣지 말 것. 아래 "미수신 시 동작" 참조

### 미수신 시 동작 (관제 반영 전 = 현재 상태)

- 저작도구는 **값을 지어내지 않는다.** NULL 이면 VLM 위탁을 **건너뛰고**
  `LS_BATCH_PROC_LOG` 에 `PROC_STEP_CD='VLM'` / `PROC_STTS_CD='SKIPPED'` + 사유를 남긴다.
- 관제가 값을 채우기 시작하면 기존 재개 배선(`VlmWithheldResumeRunner`, 멱등 조건 = 시계열 메타 0건)이
  **자동으로 회수**한다. 별도 수동 재처리가 필요 없다.
- 즉 **관제 반영이 늦어도 데이터가 유실되지 않고 지연될 뿐**이다.

### ⚠ CHECK 제약을 걸지 않은 이유 (중요)

관제는 우리 애플리케이션을 거치지 않고 **DB 에 직접 INSERT** 한다. 컬럼에 `CHECK` 를 걸면
허용목록 밖의 값 하나가 **인입 INSERT 전체를 실패**시켜 영상 적재가 멈춘다. 그래서 DB 는 열어두고,
값 검증은 ① 우리 쓰기 통로(내부 업로드)에서 400 ② **소비 시점(VLM 위탁 직전) fail-closed 재검증**
2단으로 한다. 미지의 값이 들어와도 인입은 성공하고 위탁만 SKIPPED 된다.

### 저작도구 측 진행 상태

- ✅ 컬럼 신설 + 조달 경로(`IngestSourceRepository.findSourceMeta`, `IngestSourceLink` 재사용)
- ✅ 내부 업로드(dev 테스트용) 적재 + 6종 화이트리스트 검증
- ✅ **VLM 위탁부 소비** — `VlmTimeseriesStep(resolveEventType)` 가 인입값을 조달해 `verify` 요청 `event_type` 으로 전송. 미수신·미허용이면 위탁하지 않고 `LS_BATCH_PROC_LOG` SKIPPED 기록(값을 지어내지 않음)
- ✅ **콜백 적재** — `verify` 콜백(`results:{accuracy, description}`)을 `LS_DATA_META` 에 `vlm.description`(검수 대상) + `vlm.accuracy`(화면 전용) 2키로 원자 upsert
- ✅ **화면** — 라벨링 '메타' 탭이 서술 전문 1개를 편집 가능하게, 일치도를 읽기 전용으로 표시(검수 화면도 동일). 구 describe 구간행은 읽기 전용으로 보존·병기
- ✅ **어노테이션 `vd_description` 배선** — 위 §0-1 표 참조
- ⏳ **관제 측 작업 대기** — 인입 `VRFC_EVNT_TYPE_CD` 송신. **이것만 되면 전 구간이 동작한다.** 그 전까지 저작도구는 위탁을 스킵하고 사유를 기록하며, 값이 들어오기 시작하면 신규 인입 영상부터 정상 위탁된다(과거 스킵분은 기존 수동 재처리 대상)

### 6-0. ⚠ 1차 검토 결과는 폐기했다 — 검증 방법이 틀렸다

1차는 `program_word_search` **키워드 검색이 0건이면 "미등록"으로 단정**해 정상 컬럼 8건 이상을
"비표준"으로 잘못 보고했다. 원인은 도구 한계다:

- `program_word_search` 는 **`limit` 상한 200 + `offset` 파라미터 없음**인데 사업표준단어는 **471건**이라
  **271건이 구조적으로 조회 불가**다. `count: 200` 은 캡에 걸린 것이지 전체가 아니다.
- 한글 키워드는 **표기가 다르면 못 찾는다** — "형식"으로 찾으면 `FRM` 만 나오고 `FMT`(포맷)는 안 나온다.

**따라서 표준용어 판정은 CSV 정본 전량 대조로만 한다.** MCP 검색은 도메인·개별 확인 보조로만 쓴다.

### 6-4. ✅ `ANONY` = **익명** (2026-08-05 확정)

`ANONY_INCL_YN` 의 실사용 의미는 **익명**이다. 근거 4개가 모두 한 방향이다.

1. **3필드가 배타적 세트** — `ANONY`/`PSDO`(가명)/`PRVC`(개인정보) = 개인정보보호법 3분류.
   `ANONY`가 "비식별"이면 가명처리도 그 하위라 `PSDO` 를 포함해 세트가 성립하지 않는다.
2. **비식별 여부는 별도 컬럼이 담당** — `LS_DATA_RAW.DE_IDENT_YN`(뷰 출력 `DE_IDNTF_YN`).
3. **코드·DB 코멘트가 전부 익명** — export JSON 키 `anonymity`, V163/V166 코멘트 "익명정보 포함여부",
   코드값 축 `PRVC_TYPE_CD` 의 값도 `ANONY`/`PSDO`/`PRVC` 3분류.
4. **사업표준*용어* 등록명도 "익명여부 포함"**(#832).

`ANONY_INCL_YN` 을 쓰는 테이블은 `LS_DATA_INGEST`·`LS_DATA_RAW`·`LS_DATA_SRC`·`LS_DEADLINE` 4개이며
**`ANONY` 를 비식별 뜻으로 쓰는 컬럼은 하나도 없다.**

> ⚠ **물리명은 그대로 두고 사전도 건드리지 않는다.** 사업표준*단어* `ANONY`(#178)는 국문이 "비식별",
> 영문명이 `Anonymized` 로 서로 어긋나 있고 비식별화용 단어 `DE_IDNTF`(#614)가 따로 있어 개념도 중복이지만,
> **`createdBy: null` = KLID-BM 표준용어정의서 2026-05-28 배포분이라 우리 수정 대상이 아니다**
> (사업 사전은 관제서버·포털 프로젝트가 공유한다). 사전 불일치는 **알려진 예외**로 여기 기록만 하고,
> 우리 코드·문서·ERD 는 **일관되게 "익명"** 으로 쓴다.

## 7. 어노테이션(NIA export JSON) 정정 항목

관제 연동과 별개로, 사업 어노테이션 표준(`docs/AI기반CCTV_어노테이션_예제_sample.json`) 대조에서
드러난 불일치다.

### 7-1. `dataset.name` — 파일명이 들어가고 있다

표준 예제는 `"이상행동(신체적 충돌 싸움) 학습용 데이터셋"` 즉 **데이터셋 이름**인데,
현재 `NiaJsonBuilder.java:152` 가 `baseNameNoExt(path)` 로 **영상 파일명**을 넣는다.
→ 뷰 `DATST_NM` 과 **같은 규칙(`{이벤트명} 데이터셋 구축`)으로 통일**한다. **즉시 착수 가능.**

### 7-2. `info.year` — 재export 하면 값이 바뀐다

`NiaJsonBuilder.java:111` 이 `LocalDate.now().getYear()` 를 쓴다.
`data_etbl_yr`(구축 연도)과 같은 개념이므로 **검수 완료 연도(`RVW_CMPL_DT`)로 고정**한다.

### 7-3. `video.event_id` — 코드 축이 다르다

현재 `EVNT_TYPE_CD`(`EV02000102`)를 넣는데, 표준 예제는 `"ABF_0001"` 형태이고
인입에 `EVNT_ID`(varchar 50) 전용 컬럼이 따로 있다. → **§7-4 매핑대로 정정**(즉시 착수 가능).

### 7-4. 어노테이션 매핑 — **저작도구가 결정한다** (관제 질의 대상 아님)

어노테이션 JSON 은 저작도구 산출물이므로 매핑은 우리가 정한다. 관제 회신을 기다리지 않는다.

| 어노테이션 필드 | 매핑 | 근거 |
|---|---|---|
| `video.event_id` | 인입 `EVNT_ID` | 인입 명세상 "개별 이벤트 인스턴스 식별자". 표준 예제(`ABF_0001`)와 성격 일치 |

### 10-2. `FRME_CNT` 를 실제 프레임 수(N)로 정정 — 반영 완료

**구 증상** — `dataset/export/DatasetExportService.export()` 가 원본 벌·비식별 벌의 쓰기 건수를
**합산**(`totalWritten`)해 그대로 `FRME_CNT` 로 적재했다. 일반 영상 N프레임 → `FRME_CNT=2N`,
파생영상(비식별 1벌) → `N`. 관제 `datasets.img_nocs`·`dataset_versions.data_etbl_nocs` 가
2배로 들어갔다.

**반영** — `exportedFrameCnt` 를 `totalWritten`(벌 합계) 대신 **`Math.max(원본벌 쓰기 건수,
비식별벌 쓰기 건수)`** 로 산정하도록 고쳤다(작업 트리 실측, `DatasetExportService.export()`).
`totalWritten`/`totalSkipped` 자체는 `PARTIAL` 판정용으로 **그대로 남긴다** — FRME_CNT 축과
분리했다. `V185` 가 `LS_DATASET_EXPORT.FRME_CNT` 컬럼 COMMENT 도 함께 재지정했다(V173 이 남긴
"원본벌+비식별벌 합계" 서술이 산정 방식 변경으로 사실과 달라졌기 때문). 영상 유형(일반/파생)과
무관하게 항상 N 이 되어 현재의 비일관(N vs 2N)도 함께 해소됐다.

**건드리지 말 것**

| 항목 | 이유 |
|---|---|
| `DATA_ETBL_CPCT`(용량) | 산출 폴더 전체 바이트 합이며 관제 정의("산출 폴더 총 바이트")와 일치. 관제도 "합계 하나로 충분"으로 확정 — **2벌 포함이 정상** |
| `PARTIAL` 판정 | `totalSkipped` 기반이라 별개 축. 프레임 수 산정과 함께 건드리지 말 것 |
| `V_COMPLETED_VIDEO` 뷰 | `COALESCE(e.FRME_CNT, 0)` 로 원장 값을 그대로 노출하므로 뷰 수정 불필요 |

**수용 기준** — 일반 영상 N프레임 → `FRME_CNT=N`(2N 아님), 파생영상 → `N`. 미산출 영상은 뷰에서
여전히 `0`(NULL 아님 — 규격서 공표값). `DATA_ETBL_CPCT` 는 2벌 합산 그대로·미산출 시 NULL.

**규격서 반영** — §5-1 (12)·§5-5(산출 폴더 구조)·§7-H (2026-08-13 개정)

### 10-3. 통지 페이로드에 `output_ver_no` 추가 — 반영 완료

관제 **수용 확정**. 완료·수정 통지 **양쪽에 선택(optional) 필드**로 추가했다(작업 트리 실측).

- `controlnotify/dto/TaskCompletedPayload` · `TaskModifiedPayload` 에 필드 추가 —
  설계 진실원 `@design INT-007`(LogiCraft)
- 조달원 `LS_DATASET_EXPORT.OUTPUT_VER_NO` — `controlnotify/service/ControlNotifyPayloadFactory.resolveOutputVerNo` 에서 채움
- **`@JsonInclude(NON_NULL)` 을 필드 레벨로만** 건다 — 클래스 레벨에 걸면 required 8필드까지
  함께 생략돼 관제 검증이 전량 `422` 로 깨진다(회귀 가드
  `TaskPayloadStructureTest.requiredFieldsKeepExplicitNullKeysAfterOptionalFieldAdded`)
- 값이 없으면 키를 생략한다. 관제가 "값 없는 통지 = 산출물 변경 없음, 재픽업 불요"로 처리하기로 했다
- 직렬화 단언 테스트 — `TaskPayloadStructureTest` · `ControlNotifyPayloadFactoryTest` · `ControlNotifyServiceTest` · `ControlNotifyClientTest` 갱신

> ⚠ 완료 통지의 **required 8필드는 값이 `null` 이어도 키를 남기는** 기존 규칙을 유지한다.
> `output_ver_no` 는 optional 이라 **정반대(미전송)** 이며, `ver_expln` 과 같은 의도된 비대칭이다.

**순서 제약 없음** — 관제 수신 API 는 필드 추가 전 통지도 정상 수신한다(미기재로 처리). 관제
배포를 기다릴 필요 없이 저작도구가 먼저 보내도 안전하다.

**규격서 반영** — §4-1·§4-2 (2026-08-13 신설)

### 10-4. 규격서 §5-5 오독 방지 — 문서 정정, 코드 영향 없음

이번 왕복의 근본 원인이다. 구 §5-5「파생영상 취급」 절의 "★파생영상에는 원본 영상이 없다"가
**파생영상에 한정된 서술**인데 절 제목만으로 적용 범위가 분명하지 않아, 관제가 **모든 영상**의
이야기로 읽고 "산출 프레임은 비식별 1벌뿐"이라는 잘못된 전제로 내부 패키징 모델 재정의에
착수했었다.

**실제** — 일반 영상(관제 인입, `ORGNL_RAW_SN IS NULL`)은 산출 프레임이 **원본·비식별 2벌**
(`{OUTPUT_PATH_NM}/v{n}/orgnl/` + `/deid/`)이고, **파생영상만** 비식별 1벌이다. 이 사실은
이미 그렇게 **동작하고 있었다** — 결함이 아니라 규격서 서술이 관제에게 잘못 전달된 것이었다.

**조치** — `docs/관제-저작도구-데이터연동-규격서-20260805.md` 에서 §5-5(산출 폴더 구조, 벌 수
명시)를 신설하고, 파생영상 전용 서술은 §5-6(적용 범위 명시)으로 분리했다. **코드 변경은 없다.**
