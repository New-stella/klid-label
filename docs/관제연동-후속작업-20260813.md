## 1. 이벤트 어노테이션 단독 수정 시 재생성 누락 — 결함 수정

**우선순위 최상.** 관제가 *"수정 일정이 확정되면 공유 부탁 — 그 전까지 이 케이스를 별도 방어하지 않는다"* 고 회신했다. 즉 **고쳐질 때까지 관제는 옛 어노테이션을 정상으로 받는다.**

### 증상

이벤트 어노테이션만 단독으로 고치면 재검수는 타는데 **재승인해도 산출 폴더가 새로 생기지 않는다.** 그 값은 산출 JSON **최상위에 그대로 실리므로**, 관제가 픽업하는 파일에 이전 어노테이션이 남는다.

### 수정

`evntanno/service/EvntAnnoService.upsertOnce` 의 `TaskModifiedEvent` 발행 인자에서 `exportRegenerated` 를 **`false` → `true`** 로 바꾼다(`needsRecheck` 는 이미 `true`).

### 그 자리 주석·CLAUDE.md 의 "재동결 미배선" 사유도 함께 정정

코드 주석은 *"재동결(`materialize`)을 하지 않아 재export 만 붙이면 승인 시점 동결본이 그대로 나간다"* 고 적고 있는데, **재승인 경로에서는 성립하지 않는다.**

- `review/service/ReviewService.approve` 가 **같은 트랜잭션에서 `materialize` 를 먼저** 돌려 동결본(`EVNT_ANNO_CN`)을 갱신한다
- 재생성은 **그 뒤 flush tick** 에 일어나므로 export 는 이미 새 동결본을 읽는다

즉 별도 재동결 배선이 필요 없다. 옛 동결본 문제는 **디바운서 단독 재생성 경로**에만 있었다.

### 수용 기준

- 승인된 영상에서 **이벤트 어노테이션만** 고치고 재승인 → 새 버전 폴더 `v{n+1}` 생성 + 그 폴더의 JSON 최상위 `event_annotation` 이 **새 값**
- 다른 수정과 함께 저장한 경우는 기존대로 동작(윈도우의 `exportRegenerated` OR 누적)
- ⚠ 수정 시 **`materialize` 선행 순서가 유지되는지** 함께 확인할 것

## 2. `FRME_CNT` 를 실제 프레임 수(N)로 정정

**빠를수록 유리하다.** 관제가 *"동의 — 즉시 정정 가능. 아직 뷰 값을 실적재 전이라 2N 기준 로직이 없다"* 고 했다. **관제가 적재를 시작하면 이 창이 닫히고 재조율이 필요해진다.**

### 증상

`dataset/export/DatasetExportService.export()` 가 원본 벌·비식별 벌의 쓰기 건수를 **합산**(`totalWritten`)해 그대로 `FRME_CNT` 로 적재한다. 일반 영상 N프레임 → **`FRME_CNT = 2N`**, 파생영상(비식별 1벌) → `N`. 관제 `datasets.img_nocs` · `dataset_versions.data_etbl_nocs` 가 2배로 들어간다.

### 수정

`FRME_CNT` 적재값을 **실제 프레임 수(N)** 로 바꾼다. 영상 유형(일반/파생)과 무관하게 항상 N 이 되어 현재의 비일관도 함께 해소된다.

### 건드리지 말 것

| 항목 | 이유 |
|---|---|
| **`DATA_ETBL_CPCT`(용량)** | 산출 폴더 전체 바이트 합이며 **관제 정의("산출 폴더 총 바이트")와 일치**. 관제도 ①합계 하나로 충분으로 확정. **2벌 포함이 정상** |
| **`PARTIAL` 판정** | `totalSkipped` 기반이라 별개 축. 프레임 수 산정을 바꾼다고 함께 건드리지 말 것 |
| **`V_COMPLETED_VIDEO` 뷰** | `COALESCE(e.FRME_CNT, 0)` 로 원장 값을 그대로 노출하므로 **뷰 수정 불필요** |

### 수용 기준

- 일반 영상 N프레임 → `FRME_CNT = N`(2N 아님), 파생영상 → `N`
- 미산출 영상은 뷰에서 여전히 **`0`**(NULL 아님 — 규격서 공표값)
- `DATA_ETBL_CPCT` 는 2벌 합산 그대로 · 미산출 시 **NULL**

> 정정 후 **프레임 수(N)와 용량(2벌)의 산정 축이 다르다.** 의도된 것이며 관제도 인지했다.

## 3. 통지 페이로드에 `output_ver_no` 추가

관제 **수용 확정**. 완료·수정 통지 **양쪽에 선택(optional) 필드**.

### 구현

- `controlnotify/dto/TaskCompletedPayload` · `TaskModifiedPayload` 에 필드 추가
- 조달원: `LS_DATASET_EXPORT.OUTPUT_VER_NO`(엔티티 `LsDatasetExport.exportVerNo`)
- `controlnotify/service/ControlNotifyPayloadFactory` 에서 채움
- **`@JsonInclude(NON_NULL)`** — 값이 없으면 **키를 생략**한다. 관제가 *"값이 없는 수정 통지는 산출물 변경 없음 — 재픽업 불요로 처리"* 하기로 했다
- 직렬화 단언 테스트(`TaskPayloadStructureTest`) 갱신

> ⚠ 완료 통지의 **required 8필드는 값이 `null` 이어도 키를 남기는** 기존 규칙을 유지한다. `output_ver_no` 는 optional 이라 **정반대(미전송)** 이며, 이 비대칭은 `ver_expln` 과 같은 의도된 설계다.

### 순서 제약 없음

관제 수신 API는 **필드 추가 전 통지도 정상 수신**한다(무시가 아니라 미기재 처리). 관제 배포를 기다릴 필요 없이 **우리가 먼저 보내도 안전**하다.

### 수용 기준

- 재승인으로 새 폴더가 생긴 통지 → `output_ver_no` 에 그 버전 번호
- 폴더가 안 생긴 통지 → **키 자체가 없음**
- 완료 통지 필드 수가 기존 9개 + 1

### 수용 기준

- `VMS_CCTV_ID` 가 비어도 인입 → 원시영상 적재가 **끝까지 완주**
- 목록·상세 화면에서 그 영상이 **식별 가능한 문자열**로 표시(빈칸·`null` 노출 금지)

- 데이터마트 뷰 계약 **무변경** — `VMS_CCTV_ID` 는 V174 에서 이미 뷰 출력에서 빠졌다

## 5. CLAUDE.md 정정 3건

> **정정 대상은 병합된 CLAUDE.md 한 곳이다.** main 은 merge-base 이후 이 파일을 건드리지 않아(2026-08-13 실측) `issue-0810` 판이 그대로 이기며, main 의 더 낡은 서술("전부 미구현")은 병합으로 **자동 소멸**한다. 따라서 남는 것은 `issue-0810` 판의 **"절반만 됐다"** 서술을 고치는 일이다.

> 방치하면 다음 세션이 **이미 있는 것을 또 만든다.** 실제로 이번 라운드에서 그럴 뻔했다.

### ① "②재승인까지 통지 flush 보류 = 미구현" → **구현됨**

`issue-0810` CLAUDE.md 의 2026-08-12 자 서술이 *"`ControlNotifyDebouncer` 가 재검토 표시를 전혀 읽지 않는다(참조 0건)"* 를 근거로 미구현이라 판정했는데, **그 문장은 참이지만 결론이 틀렸다.** 그 클래스가 부르는 **리포지토리 쿼리에 2겹으로** 구현돼 있다.

- `controlnotify/debounce/LsMonNotiAcmlRepository` — **Phase 7a-2**(flush 후보 SELECT 에서 `NOT EXISTS (… REVLT_YN='Y')` 제외) + **Phase 7a-2b**(클레임 UPDATE 문 자체에도 재확인)
- 표식은 `TaskModifiedEvent.needsRecheck` → `controlnotify/listener/ReviewRecheckMarkListener` → `ReviewApprovalGate.markNeedsRecheck`, 해제는 `ReviewService.approve`

main 의 서술("전부 미구현")은 더 낡았다. **양쪽 다 정정.**

### ② `EvntAnnoService` 예외 캐비엇 해소

*"`EvntAnnoService` 는 예외 — 재동결 배선이 선행돼야 하며 **미확정**"* 을 지운다. ①사용자가 재생성 대상으로 확정했고 ②재동결은 승인 파이프라인의 `materialize` 가 이미 수행한다(→ 위 작업 1).

### ③ 정책 문장 신설 (구속)

> **작업자가 화면에서 내용을 고치면 무조건 재검수를 거치고, 재승인 시 무조건 새 버전이 나온다. 예외 없음.**

라벨 추가·수정·삭제 · 트랙 편집·병합 · 버전 롤백 · 촬영환경 수정 · 프레임 설명 수정 · 개인정보 메타 수정(프레임·영상 축) · **이벤트 어노테이션** 전부 해당.

**함께 적을 메커니즘** (이번에 혼동한 지점):

- **최초 승인** = `ReviewApprovedEvent` → `runApprovalAsync` → `doExport(rawSn, true)` 강제 재생성 → `TASK_COMPLETED`
- **재승인** = 그 이벤트를 **발행하지 않는다**(중복 방지). 표식을 지우면 축적 윈도우가 다음 flush tick 에 풀려 **디바운서가** 재생성 + `TASK_MODIFIED`
- 따라서 **"승인 경로는 항상 force=true(R6)"는 최초 승인·폴백 경로에만 적용**되고, 재승인의 재생성 여부는 축적된 `exportRegenerated`(OR 누적)가 정한다
