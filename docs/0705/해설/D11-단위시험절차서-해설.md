## 1. 이 문서는 무엇인가

### 1.1 한 문장 정의

D11 단위시험 절차서는 **AI 기반 지방정부 CCTV 관제지원시스템(2차)의 학습데이터 저작도구(AT)**를 대상으로,
각 **컴포넌트(CO) 단위**의 기능이 "정상적으로 동작하는가"를 확인하기 위한 **테스트 케이스(시험 케이스) 집합**을
정의한 CBD(Component Based Development) 표준 설계 산출물입니다.

### 1.2 문서의 정체성 — "변형본"이라는 점이 핵심

원문 서두(작성 목적)가 명시하는 대로, 이 파일은 원본인 `D11-R1-단위시험절차서.md`(전체)에서
**정상 동작 케이스만** 추려낸 **기능 검증용 변형본**입니다. 즉, 다음 두 가지 성격을 반드시 구분해야 합니다.

| 구분 | 전체 단위시험 절차서(원본) | 본 문서(D11 정상동작 한정본) |
|------|--------------------------|----------------------------|
| 포함 케이스 | 정상 + 예외 + 경계 + 권한 + 검증(음수·범위초과 등) | **정상 동작 케이스만** |
| 목적 | 결함 발견 중심의 완전 검증 | 기능이 요구대로 "동작함"을 확인 |
| 혼합 케이스 처리 | 그대로 유지 | 정상 절만 추출(원문 verbatim 아님) |

> 원문 표현: "예외·경계·권한·검증 케이스를 제외하고 각 기능의 정상 동작 케이스만 추린 기능 검증용 변형본이다.
> 혼합 케이스는 정상 절만 추출했다(원문 verbatim 아님)."

따라서 이 문서에서 "예외/경계/권한 케이스가 왜 없나?"라는 질문의 답은 **"의도적으로 제외했다"**입니다.
다만 각 케이스의 '예상결과 및 검증방법' 칸에는 CWE-209(내부 경로 노출 금지), CWE-359(PII·토큰 노출 금지),
Mass Assignment 차단 같은 **정상 흐름 안에서 지켜져야 할 보안·검증 사항**이 함께 서술되어 있습니다.

### 1.3 문서가 지향하는 상세화 수준 (개정 이력이 말해주는 것)

제·개정 이력(v1.0 → v5.6)은 이 문서가 어떤 방향으로 정교해졌는지를 그대로 보여줍니다. 핵심 진화 축은 네 가지입니다.

1. **구조 축 (v2.0)** — 단위시험을 **컴포넌트(CO) 단위 블록**으로 재편하고, 단위시험 ID를
   `KLID-AT-UT-{컴포넌트번호}`로, 케이스 ID를 `KLID-AT-UT-{컴포넌트번호}-NN`(블록마다 01부터)로 채번.
2. **검증 상세 축 (v3.0)** — '시험항목 및 처리절차'와 '예상결과 및 검증방법'을 **실제 코드·DB 설계(D8·D9)**
   기준의 다단계 절차 + 테이블·컬럼·상태값 검증 수준까지 상세화.
3. **UI 절차 축 (v4.0~)** — '시험항목 및 처리절차'를 실제 UI/기능 시험 절차(번호 단계 + `:` 상세 설명)로 재작성.
   근거 화면은 **D2 사용자인터페이스설계서**. 화면이 없는 배치·내부·콜백 케이스는 "기능 트리거 절차"로 표기.
4. **관찰 가능성 축 (v4.1~v5.6)** — DB 검증을 "INSERT 서술" → "확인 SELECT 쿼리"로 전환(v4.1),
   프로그램 ID를 D3 인터페이스 ID(`KLID-AT-IF-NNN`) 기준으로 기입(v4.2), DB-only 케이스에 실제
   FE '화면 표시' 관찰을 보강(v5.6).

개정 이력에는 **케이스 삭제/병합 근거**도 명확히 남아 있어 시험 대상 선정 원칙을 읽을 수 있습니다.

- **v4.3** — UT-002의 라벨 보존율 계산 케이스 제거: `LabelIntegrityCalculator`가 실제 실행 흐름에
  미연동(호출처 없음)이라 **기능 정상동작 시험 대상이 아님**.
- **v4.5 / v4.9 / v5.3** — 동일 동작의 부속 측면인 중복 케이스를 1케이스로 통합(검증 항목은 합집합 보존).
- **v5.0** — UT-007-02(삭제 audit) 제거: 사용자 대면 라벨 이력 조회는 검수완료 버전만 대상이며 삭제 audit은
  내부 감사 성격이라 기능정상 시험 대상이 아님.
- 케이스 총수 변화: 33 → 30 → 29 → 28 → 27 → **26**케이스(v5.3 시점).

정리하면 이 문서의 대상 선정 원칙은 **"실제 실행 흐름에 연결되어 사용자/시스템이 관찰 가능한 정상 기능만
시험한다"**이며, 미연동 유틸·내부 감사·인프라 공통 기능은 제외합니다.

### 1.5 블록 구조 (읽는 법)

각 단위시험 블록은 다음 두 부분으로 구성됩니다.

**(1) 머리표 테이블** — 컴포넌트 1:1 식별 정보

- **단위시험ID**: `KLID-AT-UT-{컴포넌트번호}` (= 관련 컴포넌트 번호와 1:1)
- **설명**: 기능 서술형(누가 무엇을 한다 + 세부 불릿). v4.6부터 RQ·UC 참조를 본문에서 걷어내고
  기능 서술로 재작성. 단, 설명 칸에는 R1 요구사항 ID·UC를 보존.
- **관련 컴포넌트 ID**: `KLID-AT-CO-NNN` (D3 컴포넌트설계서의 컴포넌트)
- **관련 프로그램 ID**: `KLID-AT-IF-NNN` (D3 인터페이스 ID). 외부 연계는 **D4 송수신 프로그램 ID(II-NNN)** 병기.
- **> 출처** 주석: 원본 D11의 어느 UT 블록에서 왔는지, 어떤 UC를 실현하는지 등의 이력.

**(2) 케이스표** — 컬럼 7개

| 컬럼 | 의미 |
|------|------|
| 케이스 ID | `KLID-AT-UT-{컴포넌트번호}-NN` |
| 케이스 명 | 검증 시나리오 서술형 이름 (v5.2에서 나열형 → 서술형으로 정규화) |
| 작업 권한 | REVIEWER / WORKER / `-`(권한 무관, 배치·내부·콜백) |
| 시험 데이터 | 준비할 입력 데이터 |
| 시험항목 및 처리절차 | 실제 UI/기능 시험 절차(번호 단계 + `:` 상세). UI 없는 케이스는 기능 트리거 절차 |
| 예상결과 및 검증방법 | 확인 SELECT 쿼리·응답·상태값·화면 표시 + "검증:" 판정 기준 |
| 시험 결과 | **공란**(실제 시험 수행 시 기입) |

### 1.6 단위시험의 위치 — V-모델 관점

소프트웨어 검증 체계에서 시험은 보통 **단위시험 → 통합시험 → 시스템시험 → 인수시험**으로 올라갑니다.
D11(단위시험)은 그 최하단, 즉 **개별 컴포넌트(클래스/메서드/API 하나)가 스스로 올바르게 동작하는가**를
가장 작은 단위로 확인하는 단계입니다.

### 1.7 D10 통합시험시나리오와의 차이 (단위 vs 통합) — 반드시 이해할 핵심

> 참고: 원문 D11에는 D10과의 직접 비교 문장이 **명시되어 있지 않습니다**. 아래 표는 D11 원문의 성격
> (컴포넌트 1:1, 개별 케이스, "정상 동작" 확인)과 일반적인 CBD 단위/통합 시험 구분을 근거로 정리한 것입니다.

| 구분 | D11 단위시험 절차서 | D10 통합시험시나리오 |
|------|-------------------|---------------------|
| 검증 단위 | 컴포넌트 1개(CO) — 클래스/메서드/단일 API | 여러 컴포넌트가 연결된 **흐름/시나리오** |
| 관심사 | "이 컴포넌트가 스스로 올바른가" | "컴포넌트들이 이어서 협업할 때 올바른가" |
| 예시(본 문서 근거) | UT-011: 비식별 배치 1개가 상태를 SUCCEEDED로 전이하는가 | (D10) 적재→비식별→마킹→VLM→프레임추출→오토라벨 **파이프라인 전체**가 끝까지 흐르는가 |
| 케이스 식별 | `KLID-AT-UT-{CO번호}-NN` | (원문 미포함) 시나리오 단위 |
| 데이터 검증 | 테이블·컬럼·상태값 SELECT + 화면 표시 | 단계 간 상태 전이의 연속성 |

D11 안에서도 파이프라인 트리거(예: UT-019 마킹 완료가 잔여 배치를 트리거)는 다루지만, 이는
"**마킹 컴포넌트가 이벤트를 발행하고 상태가 전이되기 시작하는가**"까지의 단위 관점 검증이며,
파이프라인 전 구간의 정합성은 통합시험(D10) 몫입니다. UT-019 검증란도 상태 전이가 `@Async` 배치라
**즉시 아님·폴링 필요**를 명시해, 단위시험이 관찰하는 범위의 경계를 분명히 하고 있습니다.

## 2. 섹션별 상세 해설

아래는 원문에 등장하는 순서대로 **모든 단위시험 블록과 케이스**를 해설합니다. 각 블록마다
(대상 컴포넌트/프로그램) → (설명 요지) → (케이스별 절차·입력·기대결과·판정기준)을 정리합니다.

블록 번호는 001~023 중 일부만 존재합니다(009·012·014·015·017·020 등은 본 정상동작 한정본에 미수록).
전체 케이스 수는 **26건**(v5.3 기준), 활성 R1 유스케이스 18종이 각각 정상 케이스를 1건 이상 보유합니다.

### UT-001 · 증강 요청 (CO-001)

- **관련 컴포넌트/프로그램**: KLID-AT-CO-001 / IF-001(증강 요청)·IF-002(외부 증강 연동), D4 송신 II-005(증강위탁)
- **설명 요지**: 검수자(REVIEWER)가 증강 요청 화면에서 **검수 완료 영상**을 선택해 생성형 AI 증강을
  외부 서비스에 위탁. WINTER·야간·우천 등 처리 종류와 대상 영상을 **각각 단일 선택**. 미승인 영상은 선택 불가.
- **출처**: D11 UT-03(외부 증강). RQ-SFR-11-05는 07-01과 동일 기능이라 통합.

**KLID-AT-UT-001-01 — 겨울(WINTER) 증강 단일 요청**
- 권한: REVIEWER · 데이터: 검수완료 영상·WINTER
- 절차: ① 데이터 > 증강 요청 메뉴 진입 → ② 검수완료 영상 1건 + 처리 종류 '겨울'(WINTER) 단일 선택 →
  ③ 하단 요약 확인 후 처리 요청. (검수완료 영상만 노출, 미승인 선택 불가 / 요청 성공 시 증강 결과 화면 이동)
- 기대결과:
  - `LS_DATA_AUG`에 `AUG_TYPE_CD='WINTER'`, `AUG_PROC_STTS_CD='PENDING'`, `IDMP_KEY`·`OTSD_JOB_ID` 채워진 1건.
  - `AugmentRequestResponse`(jobId·requestedAt·videoCount=1·typeCount=1) **HTTP 200**.
  - 화면: 증강 결과 화면 이동 + 성공 알림, 요청/결과 목록에 '처리 대기' 표시.
- **판정 기준**: HTTP 200 · 응답 jobId 존재 · 위 SELECT 신규 row 1건.

### UT-002 · 증강 결과 수신·새 영상 등록 (CO-002)

- **관련 컴포넌트/프로그램**: KLID-AT-CO-002 / IF-003(증강 결과 수신), D4 수신 II-006(증강결과수신)
- **설명 요지**: 외부 증강 서비스가 성공 결과를 **콜백**으로 전송하면, **서명(위·변조) 검증**과
  **중복 수신 방지(멱등)**를 통과한 결과만 원본을 부모로 하는 **새 영상**을 미검수 상태로 생성·등록.
  원본 프레임·라벨·메타를 복사하고 원본↔복사 라벨의 대응 관계를 매핑. **해상도 동일 → 좌표 재계산 없음**.
- **출처**: D11 UT-20(외부 콜백 웹훅, UC-002). 구 라벨 보존율 계산 케이스는 미연동으로 제거(v4.3).

**KLID-AT-UT-002-01 — 증강 결과 수신·새 영상 등록**
- 권한: `-` (콜백) · 데이터: 증강 SUCCESS·원본 라벨·메타
- 절차: ① 결과 콜백 수신 → ② 검수자가 증강 결과 화면(SC-023)에서 새 영상 등록·표시 확인 →
  ③ 새 영상에 원본 프레임·라벨·메타가 그대로 복사됐는지 확인.
- 기대결과:

**KLID-AT-UT-019-01 — 자동/수동 이벤트 마킹 생성**
- 권한: WORKER · 데이터: 자동·수동 요청·intervalFrames·duration
- 절차: ① 마킹 화면(SC-006) → ② 비식별 영상 재생 후 자동/수동 마킹 생성(자동은 `intervalFrames` 지정) →

  - 자동 모드: `generateAutoMarks`가 totalFrames=durationSec×30(NATIVE_FPS 고정 가정)을 frameIndex 0부터
    intervalFrames 간격으로 `frameIndex < totalFrames`까지 생성(**끝 경계 totalFrames 미포함, off-by-one 방지**).
    `durationSec` null/0 이하는 INVALID_INPUT 거부. 예: 120초×30fps=3600프레임 → interval 30=**120건**, interval 60=**60건**.
- 기대결과:
  - **HTTP 201 Created**.
  - `LS_MARKING WHERE RAW_SN={영상}` → `EVNT_NM`·`MARK_MODE_CD`·`MARK_CN`(marks JSON)·`STTS_CD` 저장 1건.
  - AUTO 시 `FRME_INTV_NOCS=intervalFrames`.
  - 자동 모드 marks 개수 = totalFrames/intervalFrames 스텝 수(끝 경계 제외).

  - **⚠ 상태 전이는 @Async 배치라 즉시 아님 — 폴링/대기 필요**(v5.5에서 UI 관찰 근거 보강).

### UT-021 · 라벨 편집 임시저장 (CO-021)

- **관련 컴포넌트/프로그램**: KLID-AT-CO-021 / IF-018(라벨 편집)
- **설명 요지**: 작업자가 라벨링 캔버스에서 객체 생성·수정 후 **임시저장(upsert)**. 도구바로 바운딩박스·폴리곤
  등을 그리고 우측 패널에서 라벨·좌표·속성 편집. 신규 라벨은 수동 저장, 오토 라벨 수정 시 **자동 라벨 여부 유지**.
  **본인 배정 프레임만 편집**, 검수 완료 후 수정만 관제 수정 통지 발행.
- **출처**: D11 UT-14(라벨링) 중 프레임 라벨 편집(임시저장 upsert). (SAM2 분할/Track은 08 블록에서 다룸)

**KLID-AT-UT-021-01 — 박스 라벨 임시저장(수동 신규·오토 수정 구분)**
- 권한: WORKER · 데이터: 수동·오토 라벨
- 절차: ① 라벨링 캔버스(SC-005) → ② 좌측 도구바 [박스]로 bbox 그리기·수정 → ③ [저장](임시저장 upsert).
  - 세부 규칙: 신규 라벨(item.id==null)은 `LsDataLbl.createManual`로 `AUTO_LBL_YN='N'` INSERT,
    오토 라벨 수정(item.id!=null)은 `updateUserContent`로 좌표/라벨만 UPDATE하고 `AUTO_LBL_YN='Y'` 유지
    (**요청 autoLblYn 무시 — Mass Assignment 차단**). 본인 미배정·재비식별 락(LOCKED) 차단, 좌표 음수/신규
    1000점 초과 검증·Douglas-Peucker simplify. **검수완료(APPROVED) 후 수정만** `TaskModifiedEvent`(LABEL_UPDATED) 발행.
- 기대결과:
  - 화면: 저장 후 편집 라벨 반영(신규=수동, 오토 수정=자동 표시 유지).
  - `LS_DATA_LBL WHERE SRC_SN={프레임}` → 신규 `AUTO_LBL_YN='N'` / 오토 수정 `AUTO_LBL_YN='Y'` 유지, `POINT_CN`=저장 좌표.
  - 검수 전 저장은 통지 미발행.
- **판정 기준**: `AUTO_LBL_YN` → 신규=N / 오토수정=Y.

### UT-023 · 검수 승인/반려 (CO-023)

- **관련 컴포넌트/프로그램**: KLID-AT-CO-023 / IF-021(검수 처리)
- **설명 요지**: 검수자가 검수 상세 화면에서 제출 영상을 승인 또는 반려. 읽기 전용 캔버스로 프레임 라벨 확인.
  승인 시 상태 전이 + 라벨 전체 스냅샷 생성 + 완료 통지 연계. 반려 시 사유(1~1000자) 필수 + 반려 이슈 생성 + 상태 전이.
- **출처**: D11 UT-17(검수 승인/반려).

**KLID-AT-UT-023-01 — 검수 승인 처리**
- 권한: REVIEWER · 데이터: IN_REVIEW 영상
- 절차: ① 검수 상세(SC-019) → ② 읽기 전용 캔버스로 라벨 확인 → ③ [승인].
  - 세부 규칙: `ReviewService.approve(videoId)`가 `LS_RAW_DATA_STATUS`를 IN_REVIEW→APPROVED 전이
    (`ReviewStateMachine.verify`) + `VersionService.commitApproved`로 라벨 전체 스냅샷(`LS_LABEL_VERSION`,
    SAVE_REASON=APPROVED) 생성 + `ReviewApprovedEvent`(TASK_COMPLETED 연계) 발행(동일 트랜잭션).
    **`@Version` 낙관적 락**으로 동시 승인 시 1건만 성공·나머지 409. 미존재 상태 404.
- 기대결과:
  - `LS_RAW_DATA_STATUS.DATA_STTS_CD` → IN_REVIEW→APPROVED.
  - `LS_LABEL_VERSION` → 스냅샷 1건 생성(검수 확정 학습데이터 버전).
  - `ReviewApprovedEvent` 발행(TASK_COMPLETED 연계).
  - 동시 승인 시 1건만 성공·나머지 **409 CONFLICT**.
  - 화면: 상태 '검수 완료(승인)' 표시.
- **판정 기준**: `DATA_STTS_CD=APPROVED`.

**KLID-AT-UT-023-02 — 검수 반려 처리(사유·이슈 생성)**
- 권한: REVIEWER · 데이터: 반려 사유
- 절차: ① 검수 상세(SC-019) → ② 검수 메모에 반려 사유 입력 → ③ [반려].
  - 세부 규칙: `ReviewService.reject(videoId, reason)`가 직전 반려 이슈를 조회해 계층 연결(`UP_DATA_ISSUE_SN`) +
    `LsDataIssue.create/createWithParent`로 `LS_DATA_ISSUE` INSERT(`ISSUE_TYPE_CD=REJECTION`,
    `ISSUE_STTS_CD=RESOLVED`, `ISSUE_RSN=사유`) + `LS_RAW_DATA_STATUS` IN_REVIEW→REJECTED 전이 +
    `LsTaskEventLog.reject` 기록 + flush(락 충돌 시 409).
- 기대결과:
  - `LS_DATA_ISSUE` → `ISSUE_TYPE_CD=REJECTION`·`ISSUE_STTS_CD=RESOLVED`·`ISSUE_RSN=반려사유`.
  - `LS_RAW_DATA_STATUS.DATA_STTS_CD` → IN_REVIEW→REJECTED.
  - `UP_DATA_ISSUE_SN` → 직전 반려 존재 시 상위 이슈 SN 연결.
  - 화면: 상태 '반려' + 반려 사유가 이슈로 표시.
- **판정 기준**: `LS_DATA_ISSUE` 1건 생성 + `DATA_STTS_CD=REJECTED`.

## 4. 예상 질문 Q&A

**Q1. 이 문서는 D11 원본과 무엇이 다른가요?**
A. 원본은 정상+예외+경계+권한+검증을 모두 포함한 전체 단위시험 절차서이고, 본 문서는 그중 **정상 동작 케이스만**
추린 기능 검증용 변형본입니다. 혼합 케이스는 정상 절만 추출했으므로 원문 verbatim이 아닙니다.

**Q2. 왜 예외·경계·권한 케이스가 안 보이나요?**
A. 의도적으로 제외했기 때문입니다. 다만 정상 흐름 안에서 지켜져야 할 보안·검증 사항(CWE-209/359, Mass Assignment
차단, 화이트리스트, off-by-one 방지, 낙관적 락 409 등)은 각 케이스의 기대결과·판정 칸에 남아 있습니다.

**Q3. 단위시험 ID와 케이스 ID 체계는 어떻게 되나요?**
A. 단위시험 ID = `KLID-AT-UT-{컴포넌트번호}`(컴포넌트와 1:1). 케이스 ID = `KLID-AT-UT-{컴포넌트번호}-NN`
(블록마다 01부터 순번). 예: UT-004 블록의 첫 케이스는 `KLID-AT-UT-004-01`.

**Q4. 커버리지 목표는 얼마인가요?**
A. **원문 D11에는 커버리지 수치가 명시되어 있지 않습니다.** 원문이 제시하는 정량 지표는 문서 말미의
"활성 R1 UC 18종 전부 정상 케이스 보유"(유스케이스 커버리지)뿐입니다. 프로젝트 공통 표준으로는 Service 레이어
80%, 핵심 로직 100% 커버리지를 지향하며, 실제 코드 검증은 JUnit5 + Testcontainers(PostgreSQL) 기반으로 수행합니다.
다만 이 수치는 본 D11 문서가 아니라 프로젝트 표준에서 온 것임을 구분해야 합니다.

**Q5. 어떤 항목이 "미검증(시험 대상 제외)"인가요?**
A. 개정 이력에 근거가 남아 있습니다. ①`LabelIntegrityCalculator`(라벨 보존율 계산) — 실행 흐름 미연동, 호출처
없음(v4.3). ②`LS_DATA_LBL_HSTRY` 삭제 audit — 내부 감사 성격, 사용자 대면 이력 아님(v5.0). ③인프라/공통 기능
(영상 목록·스트리밍·서명 URL, YOLO 파라미터·배치 주기 설정, TUS 업로드) — 각 블록 출처 주석에서 제외 명시.

**Q6. UT-013은 왜 다른 케이스와 성격이 다른가요?**
A. UT-013은 **설계 케이스(구현·테스트 후속)**입니다. SystemConfig 메커니즘 자체는 실코드로 검증됐지만
(UT-006 참조), 비식별 마스킹 옵션 키가 아직 `ConfigKeys`에 미등록이고 위탁은 `KpstProjectRequest.withDefaults()`
기본값으로 고정됩니다. 옵션 키 등록 시 UT-26 패턴 실테스트로 승격 예정이며, 절차·기대결과에 `[설계]` 태그가 붙어 있습니다.

**Q7. 경계값·off-by-one은 정상 케이스에서 어떻게 다뤄지나요?**
A. UT-019 자동 마킹에서 명시적으로 다룹니다. `generateAutoMarks`는 frameIndex 0부터 `frameIndex < totalFrames`까지
생성해 **끝 경계 totalFrames를 포함하지 않아 off-by-one을 방지**합니다. 예: 120초×30fps=3600프레임이면 interval 30 →
120건, interval 60 → 60건. UT-006은 값 범위(0.0~50.0 등)로 경계를 규정합니다.

**Q8. Mock은 어디에 쓰이나요?**
A. UT-007에서 관제서버 수신처를 mock으로 두고 통지 발송·본문·이벤트 분기를 검증합니다(mock notifyService/debouncer
호출 횟수·인자 검증). 콜백/외부 연동 케이스는 실제 외부 시스템 대신 대역을 사용해 단위 관점에서 격리 검증합니다.

**Q9. 단위시험과 통합시험(D10)의 실무적 경계는 어디인가요?**
A. 단위시험은 컴포넌트 1개의 정상 동작(예: 마킹 완료 시 `MarkingCompletedEvent` 발행 + 상태 전이 시작)까지 봅니다.
파이프라인 전 구간(적재→비식별→마킹→VLM→프레임추출→오토라벨)이 끝까지 이어지는 정합성은 통합시험 몫입니다.
UT-019 검증란이 "상태 전이는 @Async라 즉시 아님·폴링 필요"라고 명시한 것이 그 경계 표시입니다. (D10과의 직접 비교
문장은 원문에 명시되지 않음)

**Q10. 왜 어떤 케이스는 '작업 권한'이 `-`인가요?**
A. 배치·내부·콜백처럼 사용자 조작 없이 트리거되는 케이스이기 때문입니다. UT-002(콜백), UT-004(배치),
UT-007-02/03(이벤트), UT-011(배치), UT-018(배치)이 이에 해당하며, 이들은 UI 절차 대신 "기능 트리거 절차"로 표기됩니다.

**Q11. DB 검증은 왜 INSERT가 아니라 SELECT로 쓰나요?**
A. v4.1 개정에서 "INSERT 서술 → 확인 SELECT 쿼리"로 전환했습니다. 시험은 "시스템이 만든 결과를 관찰"하는 것이므로,
시험자가 INSERT를 흉내내는 대신 실제 저장 결과를 SELECT로 조회해 D8/D9 실측 키·컬럼 값과 대조합니다.

**Q12. '화면 표시' 관찰은 왜 일부 케이스에만 있나요?**
A. v5.6에서 FE 화면이 실재하는 케이스에만 '화면 표시'를 보강했습니다. 응답 DTO에 상태가 노출되지 않는
UT-011-02(비식별 위탁)·UT-022-01(VLM 메타 검토)은 UI 없음으로 판단해 **DB 검증만 유지**합니다.

**Q13. 멱등성은 어떤 케이스에서 검증되나요?**
A. UT-001(`IDMP_KEY`), UT-002(중복 수신 방지 멱등 통과), UT-007-02(`requestId`=UUID로 idempotency + 폴백 큐의
`IDMP_KEY`), UT-011-02(`REQ_ID` 요청 idempotency 식별자), UT-018(중복/blank 식별자 skip)에서 다룹니다.

**Q14. 트랜잭션 원자성은 어디서 확인하나요?**
A. UT-008-02(롤백: 라벨 교체·버전 전환·통지가 동일 트랜잭션에 원자적 커밋/롤백), UT-016-02(신고 해제·작업락 해제
동일 트랜잭션), UT-023-01(승인·스냅샷·이벤트 동일 트랜잭션)에서 확인합니다.

**Q15. 라벨 좌표가 실제로 맞는지(값 대조)는 검증하나요?**
A. 예. UT-004-01은 v4.4 개정으로 **건수 확인만으로는 부족**하다고 보고 좌표 값 대조 SELECT를 추가했습니다.
`POINT_CN`이 키프레임 5·10 BBOX의 프레임 위치별 선형 보간값(중간값)과 일치하는지 실제 좌표를 비교합니다.

**Q16. 검수 승인 시 라벨이 0건인 프레임은 어떻게 되나요?**
A. UT-007-01에서, 라벨 0건 프레임은 스냅샷 생성에서 **제외(스킵)**됩니다. 반환값 `CommitResult(created, skipped)`로
생성·스킵 건수를 구분하며, 라벨 보유 프레임만 프레임당 1행의 APPROVED 버전을 만듭니다.

**Q17. 관제 통지 본문에 절대 들어가면 안 되는 것은?**
A. 라벨/메타 본문, PII, 토큰, 원본(비-비식별) 이미지 경로입니다(CWE-359). UT-007-02가 통지 본문에 이벤트 타입·
작업 ID(RAW_SN)·요청 ID·변경 프레임/종류 같은 메타만 포함하고 본문 데이터는 미포함임을 검증합니다.

**Q18. 오토 라벨을 사람이 수정하면 자동 라벨 표시는 어떻게 되나요?**
A. UT-021에서, 오토 라벨 수정(item.id!=null)은 좌표/라벨만 UPDATE하고 `AUTO_LBL_YN='Y'`를 **유지**합니다.
클라이언트가 보낸 `autoLblYn`은 무시(Mass Assignment 차단)되며, 신규 라벨(item.id==null)만 `AUTO_LBL_YN='N'`으로 INSERT됩니다.

**Q19. '시험 결과' 칸이 왜 비어 있나요?**
A. 절차서는 시험을 "수행하기 위한" 문서이므로, 실제 통과/실패 결과는 시험 수행 시점에 기입합니다. 따라서
케이스표의 마지막 '시험 결과' 컬럼은 공란으로 설계되어 있습니다.

**Q20. 활성 R1 유스케이스 18종이 모두 커버된다는 근거는?**
A. 문서 말미에 "유스케이스 커버리지: 활성 R1 UC 18종 전부 정상 케이스 보유"라고 명시되어 있고, 서두에도 "활성 R1
기능 유스케이스 18종은 모두 정상 동작 케이스를 1건 이상 보유한다"고 선언합니다. 각 블록 출처 주석이 UC-002·004·
009·018 등 실현 UC를 밝히고 있습니다.

## 5. 다른 산출물과의 연계

D11은 단독으로 존재하지 않고, CBD 산출물 체계 안에서 여러 문서를 참조·검증합니다. 원문이 실제로 언급한 연계를
근거로 정리합니다.

### 5.1 D1 클래스설계서 — 가장 밀접

D11 케이스의 '시험항목·처리절차'와 '예상결과'에는 실제 **클래스·메서드**가 다수 등장합니다.
(관련 프로그램 ID 칸에도 클래스명 보존)

- `AiServerClient.segment`(UT-005), `generateAutoMarks`(UT-019), `LsDataLbl.createManual`/`updateUserContent`(UT-021),
  `MetaService.approveReview` / `review.approve`(UT-022), `ReviewService.approve` / `ReviewStateMachine.verify` /
  `VersionService.commitApproved`(UT-023-01), `ReviewService.reject` / `LsDataIssue.create/createWithParent` /
  `LsTaskEventLog.reject`(UT-023-02), `KpstProjectRequest.withDefaults`(UT-013), `LabelIntegrityCalculator`(제거 근거, v4.3).
- 즉 D11은 D1이 정의한 클래스·메서드가 실제로 기대 동작을 내는지 검증하는 실행 계층입니다. "어떤 메서드를 시험하나?"의
  답은 대부분 D1을 함께 봐야 완성됩니다.

### 5.2 D3 컴포넌트설계서 — 블록 편성의 기준

- 단위시험 블록은 **컴포넌트(CO) 1:1**로 편성되며(v2.0), 관련 프로그램 ID는 **D3 인터페이스 ID(`KLID-AT-IF-NNN`)**
  기준으로 기입됩니다(v4.2).
- UT-013 주석은 "D3 CO-013은 비식별 옵션 설정을 SystemConfig 메커니즘으로 실현하도록 설계돼 있다"고 D3 설계 의도를
  직접 인용합니다. 컴포넌트-인터페이스 매핑의 진실원이 D3입니다.

### 5.3 D4 송수신 프로그램 목록 — 외부 연계

- 외부 연계 컴포넌트는 **D4 송수신 프로그램 ID(II-NNN)**를 병기합니다(v4.2).
- 예: UT-001(II-005 증강위탁), UT-002(II-006 증강결과수신), UT-007(II-007 관제통지),
  UT-011(II-001 비식별위탁·II-002 비식별진행폴링), UT-022(II-004 VLM결과수신).

### 5.4 D2 사용자인터페이스설계서 — UI 절차 근거

- '시험항목·처리절차'의 실제 UI 절차(번호 단계 + `:` 상세)는 **D2를 근거**로 작성됐습니다(v4.0).
- 화면 코드가 절차에 직접 인용됩니다: SC-005(라벨링 캔버스), SC-006(마킹), SC-010(버전 관리), SC-019(검수 상세),
  SC-022(증강 요청), SC-023(증강 결과), SC-025(시스템 설정), SD-007/SD-022(승인/메타 검토 시점).

### 5.5 D8 테이블정의서 / D9 (DB 설계) — 검증 컬럼의 진실원

- '예상결과·검증방법'의 확인 SELECT는 **D8/D9 실측 키·컬럼**을 근거로 다단계 검증까지 상세화됐습니다(v3.0, v4.1).
- 등장 테이블: `LS_DATA_AUG`, `LS_DATA_AUG_LBL_MAP`, `LS_DATA_AUG_RVW`, `LS_DATA_RAW`, `LS_DATA_SRC`,
  `LS_DATA_LBL`, `LS_DATA_LBL_AI_INFO`, `LS_DATA_META`, `LS_DATA_META_REVIEW`, `LS_LABEL_VERSION`,
  `LS_RESOLUTION_EXPORT`, `LS_SYSTEM_CONFIG`, `LS_CONTROL_NOTIFY_FALLBACK`, `LS_DEIDENT_PROC_LOG`,
  `LS_DEIDENT_REPORT`, `LS_AUTH_WORK_LOCK`, `LS_MARKING`, `LS_RAW_DATA_STATUS`, `LS_DATA_ISSUE`.
- `LS_CONTROL_NOTIFY_FALLBACK.SEND_RSLT_CD`는 v5.4에서 신규 컬럼으로 추가돼 통지 발송 결과를 DB로 관찰하도록 보강됐습니다.

### 5.6 D10 통합시험시나리오 — 단위 vs 통합의 상보 관계

- D11(단위)은 컴포넌트 하나의 정상 동작을, D10(통합)은 여러 컴포넌트가 이어지는 시나리오를 검증합니다.
- D11 안의 파이프라인 트리거(UT-019 마킹 완료 → 잔여 배치 시작)는 "트리거 발행 + 상태 전이 시작"까지의 단위 관점이며,
  전 구간 정합성은 D10이 담당합니다. **단, D11 원문에 D10을 직접 언급한 문장은 명시되어 있지 않으므로**, 이 상보 관계는
  두 문서의 성격에 기반한 해석입니다.

### 5.7 R2(요구사항) / RQ·UC — 추적성

- 각 블록 '설명' 칸에 R1 요구사항 ID·UC가 보존됩니다(v4.6에서 본문 참조는 제거하되 설명 칸에는 유지).
- 출처 주석이 실현 UC를 밝힙니다: UC-002(증강 결과 수신·등록), UC-004(오토라벨), UC-009(검수 완료·수정 통지),
  UC-018(관제 학습용 적재). SFR-06-03(해상도 변경), SFR-08(라벨링 핵심), RQ-SFR-11-05/06 등이 인용됩니다.
- 최종적으로 "활성 R1 UC 18종 전부 정상 케이스 보유"로 요구사항→시험 추적성이 닫힙니다.

### 5.8 D5 아키텍처설계서 — (원문 직접 언급 여부)

- **D11 원문에는 D5를 직접 인용한 문장이 명시되어 있지 않습니다.** 다만 배치/비동기(@Async)·외부 연동·듀얼
  데이터소스 같은 아키텍처 제약이 시험 절차의 폴링 필요·트리거 방식에 반영되어 있어, 아키텍처(D5)와 정합적으로
  해석할 수 있습니다.

### 부록: 이 문서를 읽을 때의 3가지 태도

1. **"정상만 본다"를 항상 전제로** — 없는 예외 케이스를 찾지 말고, 정상 흐름 안의 보안·경계 규칙에 주목하세요.
2. **케이스 = 절차 + 기대 + 판정** — '검증:' 줄이 통과 기준의 최종 근거입니다.
3. **한 케이스는 여러 문서로 완성** — 클래스는 D1, 컴포넌트는 D3, 화면은 D2, 컬럼은 D8/D9, 요구는 R2에서 확인하세요.
