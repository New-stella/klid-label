## 1. 이 문서는 무엇인가

### 1.1 한 줄 정의

D10 통합시험 시나리오는 **"학습데이터 저작도구(AT)가 외부 시스템 6개 경계와 정상적으로 연동되는가"를 검증하기 위한 시험 설계 문서**입니다. 즉, 아직 시험을 "수행한" 문서가 아니라, 앞으로 **무엇을·어떤 순서로·어떤 값을 넣고·어떤 결과가 나와야 하는지**를 미리 규정하는 설계 산출물입니다.

### 1.2 문서 목적 (원문 "작성 목적" 근거)

원문은 목적을 다음과 같이 명시합니다.

> "각 응용 프로그램의 단위 프로그램 간 상호 연동 및 **대외 인터페이스(외부 서비스 연동)**를 포함한 사용자 요구사항을 만족하는지를 검증한다."

핵심은 두 가지입니다.

- **연동(통합)의 검증**: 단위 프로그램 하나의 내부 로직이 아니라, 프로그램들이 서로 맞물려 돌아가는지, 특히 **저작도구와 외부 시스템 사이**가 정상 동작하는지를 본다.
- **사용자 요구사항 충족 확인**: 각 시나리오는 요구사항(RQ-SFR-*)과 유스케이스(UC)에 추적됩니다.

### 1.3 범위 — 무엇을 검증하고 무엇을 검증하지 않는가 (Critical)

이 문서는 **범위를 매우 엄격하게 좁혀 놓았습니다.** 원문의 "범위 (Critical)" 블록을 그대로 정리하면 다음과 같습니다.

**포함(IN SCOPE)**
- **대외 인터페이스(외부 서비스 연동) 통합시험에 한정**한다.
- 대상 외부 경계는 6개: 비식별 서버 / 외부 VLM / 외부 증강 / 관제서버 통지 / 포털 DB / 관제 공유 DB(MNG_*).
- **정상 흐름(happy path)만** 수록한다.

**제외(OUT OF SCOPE)**
- `ai-server`(YOLO/SAM2 추론)는 **저작도구 내부 컴포넌트**이므로 외부 연동 대상에서 제외한다.
  - 단, ai-server가 경유하는 **외부 VLM 호출은 외부 연동으로 포함**한다(TS-002).
- 내부 워크플로우 통합시험(라벨링·검수·버전관리 그 자체)은 본 편에 포함하지 않는다(후속/별도 편).
- 타임아웃·콜백 중복/지연·통지 재등록 큐 등 **예외·복원력 시나리오는 제외**한다(후속 확장 대상).

즉 "정상적으로 돌아가는 외부 연동만" 다룹니다. 실패·재시도·에러 처리는 이 문서의 대상이 아니며, 원문 말미의 "후속(본 편 제외 — 예외·복원력 통합시험)" 항목으로 넘겨져 있습니다.

### 1.4 통합시험의 위치 — V-모델에서의 자리

일반적인 소프트웨어 검증 계층에서 통합시험은 단위시험과 시스템(인수)시험 사이에 위치합니다.

```
요구사항 정의 ──────────────────────────── 인수시험 (사용자 요구 충족)
  설계 (D1~D9) ──────────────────── 시스템시험
    상세설계 ──────────── 통합시험 (D10)  ← 이 문서
      구현 ──── 단위시험 (D11)
```

- **단위시험(D11 단위시험절차서)**: 개별 클래스/메서드/함수 하나가 스펙대로 동작하는지. 대상이 "부품 1개".
- **통합시험(D10, 이 문서)**: 부품들이 결합되어, 특히 **외부 시스템과 맞물려** 하나의 업무 흐름이 완성되는지. 대상이 "부품 간 연결·외부 경계".

### 1.5 D11 단위시험절차서와의 차이 (통합 vs 단위)

| 구분 | D10 통합시험 시나리오 (이 문서) | D11 단위시험절차서 |
|------|-------------------------------|-------------------|
| 검증 단위 | 프로그램 간 연동, **외부 시스템 경계** | 개별 단위 프로그램(클래스/메서드) |
| 관점 | 업무 흐름 전체가 끝까지 이어지는가 | 한 함수가 입력→출력을 정확히 처리하는가 |
| 이 문서의 특수 범위 | **대외 인터페이스(외부 6경계) 정상 흐름만** | 내부 로직·분기·엣지케이스 포함(단위 관점) |
| 외부 시스템 | 실제/모의 외부 서버와 연동 검증이 핵심 | 보통 모의(mock/stub)로 격리 |
| 시험 데이터 표기 | `【실제 변수명】"실제 값"` 형식(예: `【증강 종류】"WINTER"`) | (D11 원문 별도 — 본 해설 범위 밖) |
| 결과 기록 | 시험결과 컬럼 **공란**, T1(통합시험 결과서)에서 현행화 | (D11 별도) |

한 문장으로: **D11은 "부품이 맞나"를, D10은 "부품을 이었을 때 외부와 맞물려 돌아가나"를 본다.**

### 1.6 이 판본의 특이점 — "인터페이스 입력값본"

원문 제목은 정확히 `D10 통합시험 시나리오 (대외 인터페이스 — 외부 서비스 연동 한정) · 인터페이스 입력값본`입니다. 원문 첫 문단이 밝히듯, 이 판본은 원본 D10의 변형본으로 **제2부 시험케이스의 입력자료를 D4 인터페이스설계서의 실제 인터페이스 속성명(전달 데이터 항목) 기준으로 작성**한 것입니다.

- 인터페이스 호출 케이스(II-001~008)는 **D4 §2 인터페이스 명세의 속성명을 그대로 입력 필드로 쓰고 실제 값을 채웁니다**.
- 내부 처리 단계(DB 적재·상태 전이 등)는 해당 결과 데이터 기준으로 유지합니다.

즉 "외부에 무엇을 보내는가"는 D4 규격의 필드명으로, "내부에서 무엇이 바뀌는가"는 D9 테이블/컬럼으로 씁니다.

### 1.7 문서의 2부 구성

원문은 크게 두 부분으로 나뉩니다.

- **제1부. 시험 시나리오**: 통합시험 시나리오 5종(TS-001~005)의 정의(시나리오명·설명·관련 UC)와 각 시나리오에 속한 **시험케이스 요약목록**을 먼저 배치.
- **제2부. 시험 케이스**: 각 시나리오의 상세 시험케이스(TC-001~011)를 순번별로 모아, 업무처리내용·시험항목·사전조건·입력자료·예상결과·화면ID·시험결과(공란)·비고를 표로 제시.

케이스는 `시험시나리오 ID`로 제1부 시나리오와 추적됩니다.

### 1.8 ID 체계 (원문 "ID 체계" 근거)

| 접두사 | 의미 | 출처 산출물 |
|--------|------|------------|
| `KLID-AT-IT-TS-NNN` | 통합시험 **시나리오** | D10(이 문서) |
| `KLID-AT-IT-TC-NNN` | 통합시험 **케이스** | D10(이 문서) |
| `KLID-AT-UC-NNN` | 관련 **유스케이스** | R2 유스케이스명세서 |
| `KLID-AT-II-NNN` | **인터페이스** | D4 인터페이스설계서 |
| `KLID-AT-SC-NNN` | **화면** | D2 화면설계서 |
| `LS_*` | **테이블** | D9(테이블/DB 설계) |

- `IT` = Integration Test(통합시험), `TS` = Test Scenario, `TC` = Test Case, `II` = Interface, `SC` = Screen, `UC` = Use Case.

### 1.9 검증방법 표기 (원문 근거)

비고 컬럼에 나오는 검증방법 3종의 의미입니다.

- `auto_test`: 통합 자동 테스트(JUnit 5 + Testcontainers).
- `DB SQL 확인`: 결과 테이블을 직접 SQL로 조회해 확인.
- `manual_test`: 화면을 사람이 직접 조작해 확인.

한 케이스에 둘 이상이 병기되기도 합니다(예: `manual_test+DB SQL 확인`).

## 2. 섹션별 상세 해설

### 2.0 대상 외부 연동 경계 6종 (전체 지도)

제1부에 들어가기 전에 원문의 "대상 외부 연동 경계 (D4 근거)" 표를 이해하면 5개 시나리오가 왜 이렇게 나뉘는지 한눈에 보입니다.

| # | 외부 경계 | 인터페이스(D4) | 방향 | 요구사항 | 시나리오 |
|:-:|----------|---------------|------|---------|:-------:|
| 1 | 비식별 서버(외부 비식별 솔루션, KPST) | II-001 위탁 · II-002 진행 폴링 | outbound 요청/폴링 | RQ-SFR-09-01 | TS-001 |
| 2 | 외부 VLM 시계열 메타 서비스 | II-003 위탁 · II-004 결과 콜백 | outbound + inbound 콜백 | RQ-SFR-08 | TS-002 |
| 3 | 외부 생성형 AI(증강) 시스템 | II-005 위탁 · II-006 결과 콜백 | outbound + inbound 콜백 | RQ-SFR-07 | TS-003 |
| 4 | 관제서버(완료/수정 통지) | II-007 관제 통지 | outbound 단방향 통지 | RQ-SFR-08 | TS-004 |
| 5 | 포털 DB(데이터 Load) | II-008 포털데이터Load | inbound DB READ | RQ-SFR-19 | TS-005 |
| 6 | 관제 공유 DB(MNG_*) 학습용 적재 픽업 | (D4 번호 미할당 — "공유 READ") | inbound DB READ | RQ-SFR-11-04 (UC-018 근거) | TS-001 |

- **방향(direction)의 의미**:
  - *outbound 요청/폴링*: 저작도구가 외부로 요청을 보내고, 진행 상태를 주기적으로 물어본다(비식별).
  - *outbound + inbound 콜백*: 저작도구가 위탁(요청)한 뒤, 결과는 외부가 나중에 콜백(역방향 HTTP)으로 알려준다(VLM·증강).
  - *outbound 단방향 통지*: 저작도구가 관제서버에 알림만 보내고 응답을 업무적으로 기다리지 않는다(관제 통지).
  - *inbound DB READ*: 외부 DB에서 저작도구가 읽기만 한다(포털 DB, 관제 공유 DB).
- **주의 1 — 경계 6개인데 시나리오는 5개**: 경계 #1(비식별)과 #6(관제 공유 DB 픽업)이 **같은 흐름(TS-001)**에 묶여 있기 때문입니다. 관제 공유 DB에서 영상을 픽업해 적재한 "직후" 선두 비식별이 이어지므로, 하나의 정상 흐름으로 검증합니다.
- **주의 2 — ai-server는 경계에서 빠짐**: 원문 각주가 명시하듯, ai-server(YOLO/SAM2) ↔ 저작도구(`AiServerClient`)는 **내부 통합**이라 본 편 제외입니다.
- **주의 3 — 경계 #6은 D4 인터페이스 번호가 없음**: MNG_* 공유 DB는 "공유(READ)"라 D4에 인터페이스번호가 할당돼 있지 않습니다. 실제 컬럼 진실원은 `ERD-024`(관제 공유 클립 ERD)라고 원문이 명시합니다.

### 제1부 · 시험 시나리오 5종

제1부는 각 시나리오의 정의(4행 헤더 표)와 그 시나리오에 속한 케이스 요약목록(표)으로 구성됩니다. 여기서는 각 시나리오가 "무엇을 어떤 업무 순서로 검증하는가"를 짚습니다.

#### TS-001. 관제 학습용 영상 적재 → 선두 비식별 위탁·폴링 → 완료

- **시나리오 ID**: `KLID-AT-IT-TS-001`
- **한 줄 요약**: 관제 공유 DB에서 학습용으로 설정된 영상을 주기 배치가 픽업→저작도구 적재→적재 직후 외부 비식별 솔루션 위탁→진행 폴링으로 완료 확인→비식별 완료·마킹 진입까지.
- **관련 UC**: `KLID-AT-UC-018`(관제 학습용 적재), `KLID-AT-UC-011`(비식별 처리·API 연동).
- **프로젝트 맥락**: 이 흐름이 바로 CLAUDE.md의 배치 파이프라인 "선두"에 해당합니다. 파이프라인은 **비식별화(선두) → 마킹 → VLM → 프레임추출 → 오토라벨링** 순인데, TS-001은 그 첫 두 관문(적재 + 선두 비식별)까지를 검증합니다. 비식별이 반드시 마킹보다 먼저 완료되어야 마킹 화면에 비식별 영상이 서빙된다는 원칙(원본 노출 차단)과 직결됩니다.
- **케이스 요약목록**:
  - `TC-001` 관제 공유 DB 학습용 영상 픽업·적재 (auto_test + DB SQL 확인)
  - `TC-002` 외부 비식별 위탁 요청 (auto_test / 실 KPST 연동)
  - `TC-003` 비식별 진행 폴링·완료 처리 (완료 상태 정상 수신 케이스만)

#### TS-002. 외부 VLM 시계열 위탁 → 결과 콜백 수신 → 메타 검수 진입

- **시나리오 ID**: `KLID-AT-IT-TS-002`
- **한 줄 요약**: 마킹 완료 영상을 외부 VLM에 위탁(수락만 동기)하고, 결과 콜백을 수신·검증해 시계열 메타를 적재하고 검수 대기로 진입.
- **관련 UC**: `KLID-AT-UC-022`(외부 VLM 메타 검토).
- **프로젝트 맥락**: 파이프라인의 VLM 단계. 위탁은 **수락(accept)만 동기**로 받고, 실제 시계열 메타 결과는 VLM 서버가 **콜백(`POST /v1/vlm/result`)**으로 별도 전송합니다. 콜백을 받으면 `LS_DATA_META`에 적재하고 검수큐(`LS_DATA_META_REVIEW`)에 넣어 REVIEWER가 SCR-AUTO-002(원문에서는 라벨링 캔버스 SC-005의 시계열 메타 패널)에서 검토합니다.
- **케이스 요약목록**:
  - `TC-004` VLM 시계열 위탁 (auto_test, 모의 서버)

## 3. 핵심 용어

- **통합시험(Integration Test)**: 개별 단위 프로그램들이 결합되어, 특히 외부 시스템과 맞물린 업무 흐름이 요구사항대로 동작하는지 검증하는 시험. 이 문서는 그중 **대외 인터페이스(외부 서비스 연동) 정상 흐름**에 한정.
- **대외 인터페이스**: 저작도구가 외부 시스템(비식별 서버·VLM·증강·관제서버·포털 DB·관제 공유 DB)과 주고받는 연동 경계. 내부 컴포넌트(ai-server)는 제외.
- **시험 시나리오(Test Scenario, TS)**: 하나의 완결된 업무 흐름을 대표하는 검증 단위. 여러 시험케이스로 쪼개짐. 여기서는 TS-001~005.
- **시험 케이스(Test Case, TC)**: 시나리오를 이루는 세부 검증 단위. 각 케이스는 다시 "순번(스텝)"으로 나뉨. 여기서는 TC-001~011.
- **순번(스텝)**: 한 케이스 안에서의 개별 업무처리 단계(예: 위탁 요청 → 이력 기록).
- **사전조건(Precondition)**: 케이스/순번을 수행하기 위해 미리 갖춰져야 할 상태(예: "처리 대기 상태의 적재 영상이 존재한다").
- **입력자료(Input Data)**: 시험에 넣는 값. 이 판본에서는 **D4 인터페이스 속성명 기준**의 `【변수명】"값"` 형식(예: `【증강 종류】"WINTER"`).
- **예상결과(Expected Result)**: 정상 동작 시 나와야 하는 업무 결과 + `【검증】`(실제 확인 방법: 외부 연동/DB SQL/화면).
- **판정 기준**: 예상결과의 `【검증】` 절이 곧 판정 기준. DB SQL 조회값·HTTP 응답 코드·화면 상태가 기대와 일치하면 통과.
- **화면ID(SC)**: 관련 D2 화면. 배치성 케이스는 "화면 없음".
- **시험결과 컬럼**: 설계 단계 **공란**. T1(통합시험 결과서)에서 현행화.
- **멱등키(Idempotency Key, IDMP_KEY)**: 콜백/통지 중복 시 같은 요청을 한 번만 처리하도록 하는 식별자. VLM·증강 콜백, 관제 통지에서 핵심.
- **콜백(Callback)**: 위탁 후 외부가 나중에 결과를 역방향 HTTP로 알려주는 방식(VLM `POST /v1/vlm/result`, 증강 `/v1/augments/result`).
- **폴링(Polling)**: 저작도구가 외부에 진행 상태를 주기적으로 물어보는 방식(비식별, 30초 주기).
- **선두 비식별**: 파이프라인 첫 단계로 적재 직후 자동 실행되는 비식별화. 마킹은 반드시 비식별 완료 후.
- **KPST**: 외부 비식별 솔루션(원문 base-url `http://222.118.130.251:9989`).
- **TASK_COMPLETED / TASK_MODIFIED**: 관제서버 단방향 통지 이벤트 종류(완료/수정).
- **디바운스(Debounce)**: 짧은 시간 내 다수 수정을 모아 통지를 1회로 합치는 것(TC-010).
- **happy path(정상 흐름)**: 예외·실패 없이 성공적으로 진행되는 경로. 이 문서의 유일한 커버리지 범위.
- **B 이슈 / 설계 미기재**: 각각 "코드-문서 구조 불일치"와 "미확정 값". 시험 실행 전 결정 필요.
- **T1(통합시험 결과서)**: 이 D10 시나리오를 실제로 수행한 결과를 기록하는 후속 산출물.

## 4. 예상 질문 Q&A

**Q1. 이 문서는 시험을 이미 수행한 결과인가요?**
아니요. 설계 단계 산출물로, 시험을 **어떻게 할지** 규정합니다. 시험결과 컬럼은 공란이며 실제 결과는 T1(통합시험 결과서)에서 채웁니다.

**Q2. 왜 외부 연동만 다루나요? 라벨링·검수 통합시험은 어디에?**
원문이 범위를 "대외 인터페이스(외부 서비스 연동)에 한정"했기 때문입니다. 내부 워크플로우(라벨링·검수·버전관리) 통합시험은 "후속/별도 편"으로 미뤘습니다. 단, 검수 승인 자체는 관제 통지의 트리거이므로 TS-004에서 부분적으로 등장합니다.

**Q3. ai-server(YOLO/SAM2)는 왜 시험 대상이 아닌가요?**
저작도구 **내부 컴포넌트**(`AiServerClient`로 호출하는 내부 통합)이기 때문입니다. 다만 ai-server가 경유하는 **외부 VLM 호출**은 외부 연동이므로 TS-002로 포함됩니다.

**Q4. 왜 외부 경계는 6개인데 시나리오는 5개인가요?**
비식별 서버(경계 #1)와 관제 공유 DB 픽업(경계 #6)이 하나의 업무 흐름(TS-001)에 묶여 있어서입니다. 관제 공유 DB에서 픽업·적재한 직후 선두 비식별이 이어지므로 한 시나리오로 검증합니다.

**Q5. 각 시나리오는 어떤 유스케이스를 검증하나요?**
TS-001→UC-018·UC-011, TS-002→UC-022, TS-003→UC-001·UC-002·UC-010, TS-004→UC-009·UC-007, TS-005→활성 UC 없음(결번 UC-024).

**Q6. "정상 흐름만"이면 실패·타임아웃은 아예 안 보나요?**
이 편에서는 안 봅니다. 비식별 폴링 타임아웃·콜백 중복/지연 멱등·통지 실패 재등록 큐(DEAD_LETTER) 등은 원문 말미의 "예외·복원력 통합시험"으로 별도 확장 대상입니다.

**Q7. 시험 통과/실패는 어떻게 판정하나요?**
각 순번의 예상결과에 붙은 `【검증】` 절이 판정 기준입니다. DB SQL 조회 결과값·HTTP 응답 코드(예: 200)·화면 상태가 기대치와 일치하면 통과입니다. 예: TC-002-2는 `PROC_STTS_CD='REQUESTED'`·`POLL_STTS_CD='WAITING'`·`KPST_PRJ_ID=9001`이 조회되면 통과.

**Q8. 입력자료의 `【증강 종류】"WINTER"` 같은 표기는 무슨 규칙인가요?**
`【실제 변수명(컬럼/파라미터)】"실제 입력 값(enum·리터럴)"` 형식입니다. 이 판본은 특히 인터페이스 호출 케이스의 입력 필드를 **D4 인터페이스 속성명 그대로** 씁니다.

**Q9. TC-009에서 검수 승인 시 버전 스냅샷이 "프레임마다 1건씩"이라는데, 영상당 1건 아닌가요?**
원문은 명시적으로 "영상 1건이 아니라 라벨 보유 프레임 수만큼(다중 행)"이라고 씁니다. `LS_LABEL_VERSION`에 라벨이 있는 프레임마다 SHA-256 해시와 JSON 페이로드로 1행씩 저장됩니다.

**Q10. 완료 통지(TASK_COMPLETED)에서 프레임 카운트가 왜 0/0인가요? 검증이 되나요?**
현재 코드상 `TaskCompletedPayload.totalFrames`·`labeledFrames`가 0 고정(미구현, "추후 lookup" TODO)이기 때문입니다. 이것이 **B1 이슈**로, 라벨·메타 카운트 검증이 불가합니다. payload를 구현할지 스코프에서 뺄지 결정이 필요합니다.

**Q11. 수정 통지(TASK_MODIFIED)에서 "변경 프레임 목록"이 왜 1:1 매칭이 안 되나요?**
**B2 이슈**입니다. 코드의 `TaskModifiedPayload`가 `frameIds`와 `changeTypes`를 각각 별도 Set으로 보관해서, 어느 프레임이 어떤 변경인지 1:1 매칭이 손실되고 중복이 제거됩니다. D4의 "변경 프레임 목록" 단일 구조와 불일치하며, `[{srcSn, changeType}]` 객체 배열로 재설계가 필요합니다.

**Q12. 어떤 케이스가 실제 외부 서버에 붙고, 어떤 케이스가 모의(mock)인가요?**
비식별(TC-002/003)은 실 KPST 연동(base-url 설정 완료)입니다. VLM 위탁(TC-004)은 기본 `vlm.client.enabled=false` 토글 off로 모의 서버, 활성 시 실 위탁입니다. 증강 위탁·검수는 manual_test+auto_test 혼합입니다.

**Q13. 화면이 없는 케이스도 있나요?**
있습니다. TC-001 순번1(학습용 클립 조회)과 TS-001 대부분은 배치 연동이라 화면이 없습니다. 근거 매핑 요약에서도 TS-001은 "화면 없음(배치)"으로 표기됩니다. 반면 TC-002 순번2 이후 적재 결과는 SC-007에 노출됩니다.

**Q14. 포털(TS-005)은 유스케이스가 없는데 왜 시험에 들어갔나요?**
외부 연동 경계표(RQ-SFR-19)와 실제 `PortalLabelService` 구현이 존재하기 때문입니다. 그러나 R2에 활성 UC가 없고(결번 UC-024) 포털 전용 화면도 D2에 미확인이라, 원문은 이를 **B5 이슈("시험 근거 불명")**로 명시하고 "포털 UC·SFR 신설 또는 설계 범위 외 구현으로 처리"를 결정 필요 사항으로 남겼습니다.

**Q15. 이 문서에서 아직 확정 안 된(추정하지 않은) 부분은 무엇인가요?**
"설계 미기재 — 확인 필요" 표의 5개 항목: ①외부 REST 엔드포인트 경로(II-003·005·007 미정), ②관제 공유 DB 픽업 IF ID(D4 미할당), ③TS-004 수정 통지 변경 프레임 필드 스키마, ④TS-005 포털 UC·SFR·화면, ⑤외부 시스템 수신 담당자. 원문은 추정 대신 "미기재"로 남겼습니다.

**Q16. 커버리지(무엇이 검증되고 무엇이 미검증인가) 관점에서 정리하면?**
검증됨: 6개 외부 경계의 정상 흐름(적재+선두 비식별, VLM 위탁+콜백+메타 검수, 증강 위탁+콜백+새 영상+라벨 복사+활용 검수, 관제 완료/수정 통지, 포털 Load). 미검증(이 편 제외): 모든 예외·타임아웃·재시도·멱등 실패·통지 dead-letter, 내부 워크플로우 통합, ai-server 내부 통합, B1(완료 통지 카운트)·B2(수정 통지 매칭) 검증 불가 항목.

**Q17. TC-003 순번3에서 상태가 즉시 안 바뀐다는 경고는 무슨 뜻인가요?**
비식별 후처리가 `@Async`(비동기)라 `MARKING_READY` 전이가 즉시 나타나지 않습니다. 그래서 검증 시 폴링해서 확인해야 한다고 원문이 경고합니다.

**Q18. "증강 = 새 영상"이 케이스에서 어떻게 확인되나요?**
TC-007 순번2에서 `LS_DATA_RAW`에 `PARENT_RAW_SN=원본`인 새 RAW_SN이 `DATA_STTS_CD='PENDING'`으로 1건 생기는지 SQL로 확인합니다. 순번3에서 원본 라벨이 `COORD_RECALC_YN='N'`(좌표 재계산 없음)으로 복사됐는지도 확인합니다.

## 5. 다른 산출물과의 연계

### 5.1 R2 유스케이스명세서 (가장 밀접)

|:--------:|-------------|

| TS-002 | UC-022(외부 VLM 메타 검토) |
| TS-003 | UC-001(증강 요청), UC-002(증강 결과 수신·등록), UC-010(증강 활용 검수) |
| TS-004 | UC-009(검수 완료·수정 통지), UC-007(버전 스냅샷) |
| TS-005 | 없음(결번 UC-024 — R1 범위 외, B5 이슈) |

TS-005의 UC 부재가 B5 이슈로 이어지므로, R2와의 연계는 "잘 맞는 부분"과 "구멍(포털)"을 동시에 보여줍니다.

### 5.2 D4 인터페이스설계서

이 판본의 정체성 그 자체입니다. 제2부 입력자료가 **D4 §2 인터페이스 명세의 속성명 기준**으로 작성됐고, 외부 경계표의 II-001~008이 모두 D4 인터페이스입니다. B3(II-005 스펙 불일치)·B4(II-004/006 콜백 필수 필드 누락)는 D4를 실코드에 맞춰 정정해야 하는 항목입니다.

### 5.3 D9 (테이블/DB 설계)

예상결과의 `【검증】` DB SQL이 참조하는 모든 `LS_*` 테이블·컬럼·상태값이 D9 근거입니다. "근거 매핑 요약"이 시나리오별 핵심 테이블/상태값을 D9로 연결합니다(예: TS-001의 `LS_DATA_RAW`·`LS_DEIDENT_PROC_LOG`). 단, 관제 공유 `MNG_*`는 D9 대상이 아니라 ERD-024(관제 공유 클립 ERD)가 진실원입니다.

### 5.4 D2 (화면설계서)

케이스의 화면ID(`KLID-AT-SC-*`)가 D2 참조입니다. SC-007(적재/처리 목록), SC-005(라벨링 캔버스·시계열 메타 패널), SC-023(증강 결과), SC-019(검수 상세)가 등장합니다. 포털 전용 조회 화면이 D2에 없어(SC-005 공용 재사용) B5 이슈로 남습니다.

### 5.5 D1 / D2 / D3 / D5 / D8 (설계 상위 산출물)

- **D1(클래스/개념 설계)·D3·D5(아키텍처설계서)**: D10이 검증하는 외부 경계·컴포넌트(비식별 클라이언트, VLM 클라이언트, 증강 클라이언트, 관제 통지 클라이언트, 포털 데이터소스)의 구조 근거. 특히 배치 파이프라인·듀얼 데이터소스(관제/포털)·Resilience4j 적용은 아키텍처 설계에서 정의된 것을 시험이 확인합니다.
- **D8(ERD 등 데이터 설계)**: D9와 함께 테이블 구조 근거. 관제 공유 클립은 ERD-024가 진실원으로, MNG_*가 D8/D9 산출물 비대상(공유 READ)임을 뒷받침합니다.
- (원문에 D1·D3·D5·D8의 구체 항목 번호까지의 직접 인용은 없으므로, 세부 매핑은 각 산출물에서 확인 필요.)

### 5.6 D11 단위시험절차서

**상보 관계**입니다. D11은 개별 단위 프로그램(클래스/메서드)이 스펙대로 동작하는지를, D10은 그 단위들이 외부와 결합해 업무 흐름을 이루는지를 검증합니다. 예: 비식별 위탁 로직의 단위 정확성은 D11에서, 위탁→폴링→마킹 진입까지의 연동 흐름은 D10(TS-001)에서 봅니다. 둘 다 통과해야 "완벽"의 3축(버그 없음·보안사고 없음·요구사항 일치) 중 동작 축이 충족됩니다.

### 5.7 T1 (통합시험 결과서) — 후속

D10의 실행 결과를 담는 산출물입니다. D10의 시험결과 컬럼 공란을 T1에서 실제 결과로 채웁니다. 실행 환경은 JUnit 5 + Testcontainers(PostgreSQL) + 스텁/모의 서버 또는 연동 테스트 서버입니다.

---

> **정리**: D10은 "저작도구가 외부 6경계와 정상적으로 맞물려 돌아가는가"를, D4 인터페이스 속성명으로 입력하고 D9 테이블/D2 화면으로 판정하도록 설계한 **통합시험 설계도**입니다. 정상 흐름만 다루며, 미확정 값(설계 미기재)과 코드-문서 불일치(B 이슈)를 정직하게 노출한 뒤, 실제 결과는 T1으로 넘깁니다.
