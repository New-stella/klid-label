## 1. 이 문서는 무엇인가

### 1.1 한 문장 정의
D8 엔티티 관계 모형 설계서는 **학습데이터 저작도구가 다루는 데이터를 "엔티티(개체)와 엔티티 간 관계"로 표현하고, 각 엔티티의 속성을 명세한 논리 데이터 모델 산출물**입니다. 원문 「작성 목적」에 그대로 적혀 있습니다: *"시스템의 요구사항을 만족하기 위한 주요 엔티티 및 엔티티간의 관계를 표현하고 엔티티에 대한 명세를 기술한다."*

### 1.2 작성 방법(원문 근거)
원문 「작성 방법」은 다음을 규정합니다.
- **논리적 데이터 모델링**을 통해 **엔티티 관계 모형도(ERD)** 를 작성하여 엔티티를 식별한다.
- 작성한 ERD를 **개념적 클래스도(D1 클래스 설계서)와 비교**할 필요가 있다.
- 이때 차이가 있다: **ERD의 엔티티는 모두 속성을 가져야 하나, 개념 클래스는 "속성이 없는 기능만을 가진 클래스"가 존재할 수 있다.** (즉 데이터 저장 관점의 ERD와 행위 관점의 클래스는 1:1로 대응하지 않는다.)
- 식별한 각 엔티티는 **상세 명세**를 작성한다.

### 1.3 ERD란 무엇인가
ERD(Entity-Relationship Diagram, 엔티티 관계도)는 데이터를 **엔티티(사각형)** 와 **관계(선)** 로 그린 그림입니다. D8은 ERD를 Mermaid `erDiagram` 문법으로 14장 그려 두었습니다. 예컨대 `LS_DATA_RAW ||--o{ LS_DATA_SRC : "프레임 추출"` 은 "원시영상 1건이 여러 프레임원천을 가진다(1:N)"는 뜻입니다. Mermaid 카디널리티 기호는 [3. 핵심 용어](#3-핵심-용어)에서 상세히 풀어 씁니다.

### 1.4 CBD 체계에서 D8의 위치
이 프로젝트는 CBD(Component Based Development) 표준 산출물 체계를 따르며, 산출물은 R(요구/분석)·D(설계) 계열로 번호가 붙습니다. D8은 **설계(D) 단계의 데이터 모델링 산출물**입니다. 원문 헤더가 이를 명시합니다: 단계명 **설계**, 작성일자 2026-06-23, 버전 1.0, "LogiCraft 그래프 기반 생성(/cc-doc-gen)". 즉 D8은 LogiCraft(설계 산출물 그래프 도구)에 등록된 ITEM들로부터 자동 생성되었습니다.

D8이 다루는 ID 체계(원문 「작성 시 참고사항」):
- 프로젝트 ID: `KLID`, 서브시스템(저작도구) ID: `AT`
- ERD ID: `KLID-AT-ERD-NNN` (001~014, 총 14장)
- 엔티티 ID: `KLID-AT-EN-NNN` (001~039, 총 39개)
- 관련 클래스 ID: `KLID-AT-DC-NNN` (D1 참조)
- **표기 규칙**: 모든 ID는 전체 형식 `KLID-AT-XX-NNN`으로 표기(약식 `UC-001` 금지). 단 요구사항(`RQ-SFR-NN-NN`)·시스템시험(`KLID-ST-NNN`) 등 타 체계 ID는 원형 유지.

### 1.5 D8(엔티티 관계 모형) vs D9(데이터베이스 설계서) — 가장 중요한 구분
원문이 반복해서 강조하는 핵심 경계입니다. **D8은 논리(개념/논리) 모델, D9는 물리 모델**입니다.

| 구분 | D8 (엔티티 관계 모형 설계서) | D9 (데이터베이스 설계서) |
|------|------------------------------|--------------------------|
| 관점 | 논리 데이터 모델 | 물리 데이터 모델 |
| 타입 표기 | **논리 타입**(문자/숫자/날짜/논리/이진) | **물리 DBMS 타입**(예: `BIGINT`, `VARCHAR(128)`, `TIMESTAMP`) |
| 길이/제약 | 최대 허용 길이·논리 제약(UNIQUE, "논리 FK" 등) | **물리 제약**: `ON DELETE`, `CHECK`, 인덱스 정의 |
| FK | 물리 FK가 없어도 "논리 FK"로 관계를 표현 | 실제 물리 제약(FK constraint) 정의 |
| 인덱스 | INX(Y/N) 여부만 표시 | 실제 인덱스 정의 |

원문 §2 서두: *"'타입'은 논리 타입(문자/숫자/날짜/논리/이진)으로 표기하며, 물리 DBMS 타입·길이 제약·`ON DELETE`·`CHECK`·인덱스 정의는 D9(데이터베이스설계서)에서 다룬다."* 따라서 "이 컬럼이 실제로 무슨 SQL 타입인가, 인덱스가 실제로 어떻게 걸리나"를 물으면 그것은 D9의 몫이며, D8은 "그 컬럼이 논리적으로 무엇이고 어떤 엔티티와 관계를 맺는가"에 답합니다.

### 1.6 D8의 범위(무엇을 포함/제외하나)
- **포함**: 저작도구가 **직접 소유·구성하는 LS_* 전용 테이블 39개 전수**. 원문 §1 서두: *"저작도구가 직접 소유·구성하는 LS_* 전용 테이블을 도메인별 14개 ERD로 분리하여 작성한다."*
- **제외(참조만)**: 관제서버가 소유·제공하는 **공유 스키마 MNG_***. 이들은 **물리 설계 비대상**이며 §3에서 "참조 사실만" 기술합니다. 원문: *"관제서버 공유 스키마(MNG_*)는 물리 설계 비대상으로 §3에서 참조 사실만 기술한다."*
- **앵커(anchor) 구조**: 원문은 *"모든 엔티티 관계는 작업 단위 식별자인 원시영상(`LS_DATA_RAW.RAW_SN`)과 프레임원천(`LS_DATA_SRC.SRC_SN`)을 앵커로 연결된다"* 고 명시합니다. 즉 이 데이터 모델의 두 중심축은 **영상(RAW_SN)** 과 **프레임(SRC_SN)** 이며, 대부분의 다른 엔티티가 이 둘 중 하나를 논리 FK로 참조합니다.

## 2. 섹션별 상세 해설

원문은 크게 **§1 엔티티 관계도(ERD 14장)**, **§2 엔티티 명세서(EN 39개)**, **§3 공유 스키마 참조**, **항목 설명/작성 참고**로 구성됩니다. 아래는 도메인(ERD) 단위로 ERD 관계와 그 안의 엔티티 명세를 함께 묶어 해설합니다.

> 표기 안내: 아래에서 "1:N"은 부모 1건이 자식 N건을 가진다는 뜻이고, "1:1"은 한 건씩 대응, "자기참조"는 같은 엔티티가 자신을 FK로 가리키는 것을 뜻합니다. "논리 FK"는 물리 FK 제약 없이 논리적으로만 참조함을 의미합니다(§3 및 항목 설명 근거).

### 2.1 도메인 1 — 영상·프레임 수집 (KLID-AT-ERD-001)

**ERD 관계**
- `LS_DATA_RAW ||--o{ LS_DATA_SRC` : 원시영상 → 프레임원천 (프레임 추출, 1:N)
- `LS_DATA_RAW ||--o{ LS_DATA_RAW_HSTRY` : 원시영상 → 영상 변경이력 (1:N)
- `LS_DATA_SRC ||--o{ LS_DATA_SRC_HSTRY` : 프레임원천 → 프레임 변경이력 (1:N)
- `LS_DATA_RAW ||--o{ LS_RESOLUTION_EXPORT` : 원시영상 → 해상도 변경 산출 (1:N)
- `LS_DATA_RAW ||--o{ LS_DATA_RAW` : **자기참조**(증강 원본 참조) — 증강 결과 영상이 원본 영상을 가리킴

**핵심 엔티티 명세**

**KLID-AT-EN-001 원시영상 (LS_DATA_RAW / D1 클래스 LsDataRaw = DC-012)**
- 이 데이터 모델 전체의 1번 앵커. **라벨링 대상 원시 영상 메타**이며 "영상 단위 작업"의 식별자입니다.
- PK: `RAW_SN`(원시영상일련번호, 자동증가) — **작업 단위 식별자**.
- `VMS_CLIP_ID`(VMS클립아이디, 128자, UNIQUE): 관제 VMS 클립 식별자. **동일 클립 재수신 시 갱신(upsert) 기준키**. 원문: *"VMS 클립 식별자 유니크로 동일 클립 재수신 시 갱신 처리."*
- `PRVC_TYPE_CD`(개인정보유형코드, 16자): `ANONY/PRVC/PSDO`. 이 값에서 `PRVC_YN`(개인정보포함여부)가 **파생 산출**됩니다(원문: "유형코드 파생값").
- `DE_IDENT_YN`(비식별여부): `Y/F/N`. `F`는 실패/신고 상태를 뜻합니다(다른 도메인의 비식별 신고 흐름과 연결).
- `RAW_FILE_PATH_NM`(원본 경로, 500자): "원본 보존(불변)" — 원본은 절대 덮어쓰지 않는다는 정책.
- `PARENT_RAW_SN`(원본원시영상일련번호): **논리 FK 자기참조**. 증강 결과 영상이 원본 영상을 가리킴.
- `DATA_STTS_CD`(데이터상태코드, 기본값 `PENDING`): **배치 단계 상태**. (주의: 이는 "배치 단계" 상태이고, 작업/검수 워크플로우 상태는 별도 엔티티 EN-021 영상진행상태가 담당합니다 — 두 상태의 책임 분리.)
- 관련 유스케이스: UC-002, UC-003, UC-011, UC-016, UC-018, UC-019.

**KLID-AT-EN-002 프레임원천 (LS_DATA_SRC / LsDataSrc = DC-043)**
- 2번 앵커. **영상에서 추출한 키프레임**.
- PK: `SRC_SN`. FK: `RAW_SN`(→원시영상, 논리 FK).
- `FRM_NO`(프레임번호): `(RAW_SN, FRM_NO)` 조합이 유니크(같은 영상 안에서 프레임 번호 중복 불가).
- 핵심 설계 포인트: **원본 프레임 경로(`SRC_FILE_PATH_NM`)와 비식별 프레임 경로(`DE_IDNTF_SRC_FILE_PATH_NM`)를 같은 행에서 짝(pair)으로 관리**합니다. 데이터마트 View(V_COMPLETED_FRAME)에서 이 두 경로가 원본/비식별 페어로 노출됩니다.

**KLID-AT-EN-003 원시영상이력 / KLID-AT-EN-004 프레임원천이력**
- 둘 다 변경 이력 부속 엔티티. 관련 클래스 `- ※`(D1에 별도 설계 클래스로 분리하지 않은 부속 엔티티).
- EN-003은 `CHG_TYPE_CD`(신규수집/재수신갱신 등)와 `PREV_STTS_CD`/`NEW_STTS_CD`로 상태 전이를 기록. EN-004는 프레임 생성·비식별경로 연결 사유를 기록.

**KLID-AT-EN-005 해상도변경산출 (LS_RESOLUTION_EXPORT / LsResolutionExport = DC-017)**
- **검수 완료 원본 영상의 프레임 이미지셋을 표준 하위 해상도로 다운스케일한 산출을 1건당 1행**으로 기록. 관련 UC-003.
- 매우 중요한 정책: 원문은 *"영상·라벨·메타·신규 원시영상 행을 만들지 않으며 본 엔티티만 기록한다"* 고 못박습니다. 즉 해상도 변경은 **증강이 아니며**(새 RAW_SN을 만들지 않음), 라벨 좌표도 만들지 않고, 오직 이 한 행만 남깁니다.
- `(DATA_RAW_SN, TARGET_RES_CD)` 유니크: 같은 영상+같은 목표해상도 조합은 1행. `ORGNL_W/H`(첫 프레임 실측), `TARGET_W/H`(종횡비 보존·프리셋 기준), `OUTPUT_DIR_PATH`(내부 추적용, 응답 미노출).

### 2.2 도메인 2 — 라벨링 (KLID-AT-ERD-002)

**ERD 관계**
- `LS_DATA_SRC ||--o{ LS_DATA_LBL` : 프레임 → 라벨 (프레임 라벨, 1:N)
- `LS_DATA_LBL ||--o{ LS_DATA_LBL_AI_INFO` : 라벨 → 라벨 AI 출처 (1:N)
- `LS_DATA_LBL ||--o{ LS_DATA_LBL_ATTR_VAL` : 라벨 → 객체별 속성값 (1:N)
- `LS_DATA_RAW ||--o{ LS_DATA_META` : 영상 → 영상 메타 (1:N)
- `LS_DATA_META ||--o{ LS_DATA_META_HSTRY` : 메타 → 메타 변경이력 (1:N)
- `LS_DATA_META ||--o{ LS_DATA_META_REVIEW` : 메타 → 메타 검토상태 (1:N)

**핵심 엔티티 명세**

**KLID-AT-EN-006 데이터라벨 (LS_DATA_LBL / LsDataLbl = DC-073)**
- **현재 라벨 좌표/속성**. 프레임 단위로 도형 유형별 좌표를 보관.
- FK: `SRC_SN`(→프레임원천). `LBL_ID`(→라벨마스터, 논리 FK).
- `LBL_TYPE_CD`: `BBOX/POLYGON/SEGMENT/TRACK`(바운딩박스/폴리곤/세그멘테이션/트랙).
- `POINT_CN`(좌표내용): 도형 좌표 직렬화(길이 무제한). `TRCK_ID`(트랙아이디): 자동 추적 객체 ID.
- **설계 분리 원칙**: 데이터라벨은 **좌표만** 보관하고, AI 출처·신뢰도는 EN-007(데이터라벨AI정보)로 분리합니다.

**KLID-AT-EN-007 데이터라벨AI정보 (LS_DATA_LBL_AI_INFO / LsDataLblAiInfo = DC-078)**
- **AI 라벨 출처/신뢰도**. FK: `DATA_LBL_SN`(→데이터라벨).
- `LBL_SRC_CD`: `YOLO/SAM2/INTERPOLATE/VLM`(검출/분할/보간/시계열). `CONF_SCORE`: 0.0~1.0(**보간은 0.0**). `AUTO_LBL_YN`(자동라벨여부, 기본 Y).
- `DATA_RAW_SN`/`DATA_SRC_SN`를 함께 비정규화 보유(영상·프레임 식별자 인덱스용).

**KLID-AT-EN-008 데이터라벨속성값 (LS_DATA_LBL_ATTR_VAL / LsDataLblAttrVal = DC-074)**
- **객체별 속성값**. 라벨링된 객체 단위로 "라벨속성정의(EN-013)"의 값을 저장.
- FK: `LBL_SN`(→데이터라벨), `ATTR_ID`(→라벨속성정의). `(LBL_SN, ATTR_ID)` 유니크로 중복 차단.

| 용어 | 정의 (원문·프로젝트 맥락 기반) |
|------|-------------------------------|
| **엔티티(Entity)** | 데이터로 관리할 대상(개체). 반드시 속성을 가짐(원문 「작성 방법」). D8에서는 LS_* 테이블 1개 = 엔티티 1개. |
| **관계(Relationship)** | 엔티티 사이의 연결. ERD의 선으로 표현하며 이름(예: "프레임 추출")과 카디널리티를 가짐. |
| **카디널리티(Cardinality)** | 관계에 참여하는 건수 비율. 1:1, 1:N, N:M 등. |

## 4. 예상 질문 Q&A

**Q1. D8과 D9(데이터베이스설계서)는 뭐가 다른가요?**
D8은 **논리 모델**(엔티티·관계·논리 타입·논리 FK), D9는 **물리 모델**(실제 DBMS 타입·길이 제약·`ON DELETE`·`CHECK`·인덱스 정의)입니다. 원문 §2가 명시: 논리 타입만 D8, 물리 제약·인덱스 정의는 D9. "이 컬럼 실제 SQL 타입이 뭐냐"는 질문은 D9, "이 엔티티가 무엇을 저장하고 어디와 관계 맺느냐"는 D8.

**Q2. LS_와 MNG_ 접두사의 소유권 차이는?**
`LS_*`는 **저작도구가 직접 소유·구성하는 전용 테이블**로 D8 전수 명세 대상(39개)이고, `MNG_*`는 **관제서버가 소유·제공하는 공유 스키마**로 저작도구는 READ(검증)만 하며 **물리 설계 비대상**(§3에서 참조 사실만). MNG_* 변경 시 관제서버팀 선승인이 필요합니다.

**Q3. 이 데이터 모델의 "앵커"는 무엇이고 왜 중요한가요?**
두 앵커는 **원시영상(`LS_DATA_RAW.RAW_SN`)** 과 **프레임원천(`LS_DATA_SRC.SRC_SN`)** 입니다(원문 §1 서두). 저작도구의 작업 단위가 "영상 1건"이므로 RAW_SN이 작업 식별자이고, 라벨은 프레임 단위이므로 SRC_SN이 두 번째 축입니다. 마킹·비식별·배정·통지·증강 등 거의 모든 엔티티가 이 둘 중 하나를 (논리) FK로 참조합니다.

**Q4. "논리 FK"가 반복해서 나오는데, 물리 FK가 아니라는 게 무슨 뜻인가요?**
관계는 논리적으로 존재하지만 DB에 실제 외래키 제약(constraint)을 걸지 않았다는 의미입니다. 원문 「항목 설명」의 FK 정의: *"물리 제약 미설정 시 제약조건에 '논리 FK' 명시."* 실제 물리 FK 여부는 D9에서 다룹니다. 대량 배치·유연한 상태 관리·성능을 위해 물리 제약을 생략하는 설계 선택으로 볼 수 있습니다(원문에 사유 명시는 없음 — 명세 표기 규칙만 기재).

**Q5. 영상의 상태가 두 군데(원시영상 vs 영상진행상태)에 있는데 왜 나눴나요?**
**책임 분리**입니다. EN-001 원시영상의 `DATA_STTS_CD`는 **배치 단계 상태**(기본 PENDING, 배치 파이프라인 진행), EN-021 영상진행상태의 `DATA_STTS_CD`는 **작업/검수 워크플로우 상태**(상태 전이의 단일 출처)입니다. 검수 승인 전이는 영상진행상태에서 일어나고 이때 관제서버 완료 통지가 트리거됩니다. 두 상태를 섞으면 배치 완료가 검수 상태를 잘못 점프시키는 문제가 생기므로 분리했습니다.

**Q6. 라벨 좌표와 AI 신뢰도를 왜 다른 테이블(EN-006 vs EN-007)에 나눴나요?**
데이터라벨(LS_DATA_LBL)은 **좌표/속성만** 보관하고, AI 추론 출처(YOLO/SAM2/INTERPOLATE/VLM)와 신뢰도(CONF_SCORE)는 **데이터라벨AI정보(LS_DATA_LBL_AI_INFO)** 로 분리합니다(원문 명시). 수동 라벨은 AI 정보가 없고, 자동 라벨만 출처/신뢰도를 가지므로 선택적 부속 정보를 별도 엔티티로 뺀 정규화입니다.

**Q7. 버전관리 테이블(LS_LABEL_VERSION)은 어떻게 동작하나요?**
외부 형상관리도구(Git 등) 없이 **DB 스냅샷 방식**입니다. `LBL_PAYLOAD`에 라벨 전체를 직렬화해 저장하고, `VERSION_HASH`로 동일 스냅샷을 **멱등 식별**합니다(`(DATA_SRC_SN, VERSION_HASH)` 유니크). `ACTVTN_YN`으로 활성 버전을 식별하고, diff/rollback은 두 스냅샷을 비교해 계산합니다(원문). `SAVE_REASON_CD` enum은 원문 기준 `MANUAL/BATCH/ROLLBACK`입니다.

**Q8. 비식별 관련 엔티티가 왜 처리로그(EN-018)와 누락신고(EN-019)로 나뉘나요?**
행위 주체가 다릅니다. **비식별처리로그**는 시스템이 외부 솔루션(KPST)에 위탁한 **처리 이력**(요청/성공/실패, 폴링 진행)이고, **비식별누락신고**는 **작업자가 개인정보 노출을 발견해 신고**한 사람 행위 기록(신고자·사유·상태 OPEN/RESOLVED/DISMISSED)입니다. 원문이 "시스템 처리 이력은 비식별처리로그로 분리한다"고 명시합니다.

**Q9. KPST 폴링 모델이란 무엇인가요?**
외부 비식별 솔루션 KPST는 위탁 즉시 결과를 주지 않고 **위탁→주기 진행조회(폴링)→다운로드**로 동작합니다(원문 EN-018). 그래서 `KPST_PRJ_ID`(영상 1건=1 프로젝트), `KPST_DATASET_ID`(파일 단위), `POLL_STTS_CD`(WAITING/POLLING/DOWNLOADED), `POLL_ATTEMPT_CNT`(타임아웃 판정) 같은 폴링 상태 컬럼을 비식별처리로그에 둡니다.

**Q10. 증강(LS_DATA_AUG)과 해상도변경산출(LS_RESOLUTION_EXPORT)은 어떻게 다른가요?**
`AUG_TYPE_CD`에는 `RESOLUTION`이 있어 혼동될 수 있으나 D8 원문상 둘은 별개 엔티티입니다. **해상도변경산출(EN-005)** 은 검수 완료 원본의 프레임 이미지셋을 하위 해상도로 다운스케일하며 **새 영상/라벨/메타 행을 만들지 않고 이 엔티티 1행만 기록**합니다. **데이터증강(EN-027)** 은 외부 시스템이 생성한 4종 결과(WINTER/NIGHT/RAIN/RESOLUTION)를 관리하며 검수(EN-028)·라벨매핑(EN-029)이 딸립니다. (원문 EN-005 설명이 "새 원시영상 행을 만들지 않는다"고 명시.)

**Q11. 관제 통지에는 라벨 데이터가 포함되나요?**
아니요. LS_CONTROL_NOTIFY_FALLBACK의 `PAYLOAD_CN`은 원문상 **"메타·수정 요약(본문 미포함)"** 입니다. 즉 `TASK_COMPLETED`/`TASK_MODIFIED` 통지는 요약만 담고 라벨/메타 본문은 담지 않으며, 오류 메시지도 "마스킹 후 저장"합니다. 관제서버는 통지를 받고 별도 API로 상세를 조회하는 구조입니다.

**Q12. 멱등키(IDMP_KEY)가 여러 엔티티에 나오는데 왜 필요한가요?**
비동기 외부 연동에서 **중복 처리·중복 적재를 막기 위해서**입니다. 데이터메타(EN-009), 데이터증강(EN-027), 관제통지큐(EN-033)에서 UNIQUE로 쓰이고, 전역 원장 **Webhook멱등원장(EN-034)** 은 아예 `IDMP_KEY`를 PK로 삼아 재시작·다중 인스턴스 환경에서 멱등키 손실을 방지합니다.

**Q13. 점선(`..`) 관계는 무엇을 의미하나요?**
물리 FK가 없는 **논리 관계**입니다. 세 곳에서 등장: ①LS_DEADLINE(전역 정책, 영상 비종속), ②LS_WEBHOOK_IDEMPOTENCY(전역 멱등 원장), ③LS_SYSTEM_CONFIG↔LS_META(독립 키-값 저장소의 논리 그룹). 원문은 "변환 렌더 호환을 위해 앵커 엔티티로의 논리 점선만 표기한다(물리 FK 없음)"고 반복 설명합니다.

**Q14. 관련 클래스가 `- ※`인 엔티티는 무엇인가요?**
D1(클래스 설계서)에 **별도 설계 클래스로 정의하지 않은** 부속·이력·인프라·외부채널 엔티티입니다. 이력(HSTRY), 로그, 큐, 잠금, 프리셋 부속, 게시판, 포털, 전역 메타 등이 해당합니다. 데이터 저장은 필요하지만 독립적 행위 클래스로 모델링하지 않았다는 뜻이며, 원문 「작성 방법」의 "속성만 있고 기능 클래스가 없는 경우"에 해당하는 대칭 사례로 볼 수 있습니다.

**Q15. 데이터이슈(LS_DATA_ISSUE)는 반려와 문의를 왜 한 테이블에 담나요?**
둘 다 "영상 단위 이슈"로 스레드·댓글·상태를 공유하기 때문입니다. `ISSUE_TYPE_CD`로 `REJECTION`(반려)/`INQUIRY`(문의)를 구분하고, 반려는 생성 즉시 해소 상태로 고정(이력 성격), 문의는 등록→답변→해소 상태머신을 탑니다. `UP_DATA_ISSUE_SN` 자기참조로 재반려 계층을 만들고 `VER`(낙관적 잠금)로 동시성을 방어합니다. 댓글은 별도 LS_ISSUE_COMMENT(EN-023)로 관리합니다.

**Q16. 포털 사용자 라벨(EN-035)은 왜 원본과 분리 저장하나요?**
포털은 외부 채널이고 정책상 **원본·데이터마트를 수정하지 않기(단방향)** 때문입니다. 사용자가 데이터마트 영상을 Load해 라벨을 수정해도 결과는 LS_PORTAL_USER_LABEL에만 별도 적재되며 원본에 정합되지 않습니다. `PORTAL_USER_NO`가 "본인 데이터 접근 차단키"로 사용자 간 데이터를 격리합니다.

**Q17. 작업배정과 작업이벤트로그는 어떻게 협력하나요?**
LS_TASK_ASSIGNMENT(EN-024)는 현재 배정 상태(작업자/검수자, `(영상,사용자,작업유형)` 유니크)를 보관하고, 재배정 시 LS_TASK_ASSIGN_HISTORY(EN-025)에 이전→신규 사용자를 기록합니다. LS_TASK_EVENT_LOG(EN-026)는 ASSIGN/REASSIGN/SUBMIT/APPROVE/REJECT를 **한 테이블에 시간순 누적**해 영상 단위 통합 타임라인을 제공합니다.

**Q18. 총 몇 개의 ERD와 엔티티가 있나요?**
ERD는 도메인별 **14장**(KLID-AT-ERD-001~014), 엔티티는 저작도구 전용 LS_* **39개**(KLID-AT-EN-001~039)입니다. 여기에 §3에서 참조만 하는 MNG_* 공유 테이블 2종(MNG_CLIP_MASTER, MNG_CLIP_EVNT_LST)이 있습니다.

**Q19. 마킹은 어떻게 VLM(시계열)으로 연결되나요?**
LS_MARKING(EN-017)이 `EVNT_NM`(이벤트명)·`VIDEO_FILE_PATH_NM`(영상경로)·`MARK_CN`(마킹 배열)을 **시계열 콜백으로 전달**하고, `STTS_CD`가 `PENDING→VLM_REQUESTED→VLM_COMPLETED`로 전이합니다. VLM 결과는 LS_DATA_META에 적재되고 LS_DATA_META_REVIEW(META_TYPE_CD=VLM)에서 검토됩니다.

**Q20. 작업 잠금(LS_AUTH_WORK_LOCK)은 언제 쓰이나요?**
재비식별 등 특정 작업 동안 영상/프레임을 잠가 동시 편집을 막습니다. `LOCK_STTS_CD`(LOCKED/RELEASED), `LOCK_ID` UNIQUE, `EXPD_DT`(만료 기본 6시간)로 관리합니다. 비식별 누락 신고(EN-019) 흐름과 연동됩니다(관련 UC-016).

## 5. 다른 산출물과의 연계

D8은 CBD 산출물 그래프의 데이터 모델 노드로, 상류(요구/분석)와 하류(물리 설계)를 잇습니다.

| 산출물 | 관계 | D8과의 연결 지점 |
|--------|------|------------------|
| **R2 (유스케이스 명세서)** | 상류 | 각 엔티티의 **관련 유스케이스 ID**(`KLID-AT-UC-NNN`)가 R2를 가리킴. 원문: "R1 요구사항 연관은 R2·R3 경유." 예: 원시영상=UC-002/003/011/016/018/019. R1 기능 요구사항이 직접 쓰지 않는 운영·외부채널 엔티티(마감정의·포털라벨·게시판·전역메타)는 `- ※`. |
| **D1 (클래스 설계서)** | 병렬(개념/행위) | 각 엔티티의 **관련 클래스 ID**(`KLID-AT-DC-NNN`)가 D1 설계 클래스와 매핑. 원문 「작성 방법」이 "ERD와 개념 클래스도를 비교"하라고 명시. ERD 엔티티는 모두 속성을 갖지만 클래스는 속성 없는 기능 클래스가 있을 수 있어 1:1 대응이 아님. `- ※` 엔티티는 D1에 대응 클래스 없음. |
| **D9 (데이터베이스설계서)** | 하류·**가장 밀접** | D8(논리)→D9(물리)로 이어짐. D8이 논리 타입·논리 FK·UNIQUE만 정하고, D9가 실제 DBMS 타입·길이 제약·`ON DELETE`·`CHECK`·인덱스 정의를 확정. 같은 LS_* 테이블 39개를 물리 관점으로 재기술. |
| **R2/R3 (요구사항 추적)** | 상류 | UC를 경유해 R1 기능 요구사항(SFR)과 연결. D8은 요구사항을 만족하는 엔티티를 식별하는 것이 목적(원문 「작성 목적」). |
| **§3 관제 공유 클립 ERD (ERD-024, LogiCraft)** | 참조 | MNG_CLIP_MASTER·MNG_CLIP_EVNT_LST의 진실원. D8은 물리 설계 비대상으로 참조 사실만 남기고, 실제 스키마·적재 매핑은 관제 공유 클립 ERD에서 관리. |

원문에서 직접 확인되는 연계 대상은 위와 같습니다. **질문에서 언급된 D2·D3·D5·D10·D11과의 개별 연결은 D8 원문 본문에 명시적으로 기재되어 있지 않습니다(원문에 명시되지 않음).** 다만 CBD 표준 산출물 체계상 일반적으로 다음과 같이 이해할 수 있습니다(원문 근거 아님, 체계 통념):
- D2·D3(설계 계열): 컴포넌트/인터페이스·시퀀스 등 설계 산출물이 D8 엔티티를 데이터 근거로 참조.
- D5(아키텍처설계서): 시스템 경계(저작도구 소유 LS_* vs 관제 공유 MNG_*)가 D8의 소유권 구분과 정합.
- D10·D11: 각 CBD 후속 설계 산출물이 D8 데이터 모델을 상위 근거로 활용.

이 부분을 확정하려면 각 산출물(D2/D3/D5/D10/D11) 원문의 상호참조 표를 함께 확인해야 하며, D8 단독으로는 위 3개(R2·D1·D9) + §3 공유 클립 참조가 명시적 연계의 전부입니다.
