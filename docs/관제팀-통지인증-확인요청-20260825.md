# 저작도구 → 관제지원시스템 — 완료/수정 통지 **인증** 확인 요청

**작성일** 2026-08-25 · **작성** 학습데이터 저작도구팀
**대상** 관제지원 데이터셋 API (`klid-system-was-data-set`)
**실측 환경** dev — `http://192.168.102.246:9014` (2026-08-25 기준 배포본)
**관련 규격** 관제-저작도구 데이터연동 규격서(2026-08-05) §4 통지 규격 / `API-251`·`API-285` / `INT-007` B-4

---

## 총평

전달해 주신 통지 API 정보를 받아 dev 배포본을 대상으로 **실제 호출까지 해 보았습니다.**

- **경로·페이로드는 완전히 일치합니다** — 저작도구 쪽 추가 작업이 없습니다.
- **인증만 막힙니다.** 규격에 맞는 완전한 바디로 호출해도 **컨트롤러에 도달하지 못하고 403/401** 로 떨어집니다.

`x-access-token` 이 **관제 서버가 서명한 JWT** 임을 실측으로 확인했으나, 저작도구는 그 서명키를 갖고 있지 않아 토큰을 만들 수 없습니다. **아래 Q1~Q3 회신 전까지 dev 통지를 켤 수 없습니다**(사유는 §4).

## 1. 경로·페이로드 — 정합 확인 완료 (조치 불필요)

`GET /v3/api-docs` 로 내려받은 관제 정본 스키마와 저작도구 구현을 1:1 대조했습니다.

| 항목 | 관제 정본 | 저작도구 구현 | 판정 |
|---|---|---|:-:|
| 완료 통지 경로 | `POST /api/data-set/v2/jobs/{job_id}/notify-completed` | 동일 | ✅ |
| 수정 통지 경로 | `POST /api/data-set/v2/jobs/{job_id}/notify-updated` | 동일 | ✅ |
| 완료 바디 | required 8 (`job_id`·`event_type_cd`·`evnt_cls_cd`·`evnt_ctgry_cd`·`lclgv_cd`·`duration_sec`·`image_count`·`gen_ai_yn`) + optional `lclgv_nm`·`output_ver_no` | 동일 10필드 | ✅ |
| 수정 바디 | `job_id`·`ver_expln`·`changed_items{images[],jsons[]}`·`output_ver_no` | 동일 | ✅ |
| optional 키 생략 | `output_ver_no` 없으면 키 자체 미전송 | 동일(`@JsonInclude(NON_NULL)`) | ✅ |

## 2. 인증 실측 결과 — **3케이스 모두 차단**

동일한 **규격 준수 완료 통지 바디**로 헤더만 바꿔가며 호출했습니다.

```
POST http://192.168.102.246:9014/api/data-set/v2/jobs/999999999/notify-completed
Content-Type: application/json
{"job_id":"999999999","event_type_cd":"EV01000101","evnt_cls_cd":"01",
 "evnt_ctgry_cd":"0100","lclgv_cd":"11110","lclgv_nm":"연동점검",
 "duration_sec":30,"image_count":0,"gen_ai_yn":"N"}
```

| # | 헤더 조건 | 응답 | 응답 본문 |
|:-:|---|:-:|---|
| **A** | **헤더 없음** — 저작도구 현재 형상 그대로 | **403** | Tomcat HTML `Access Denied` (컨트롤러 미도달) |
| B | `x-access-token: dummy` | **401** | `{"error":1102,"message":"잘못된 형식의 토큰입니다."}` |
| C | JWT **형식**만 갖춘 토큰(서명 불일치) | **401** | `{"error":1103,"message":"유효하지 않은 서명입니다."}` |

**C가 핵심입니다.** JWT 파싱은 통과하고 **서명 검증 단계에서 거부**되었습니다.
→ `x-access-token` 은 고정 문자열(API Key)이 아니라 **관제 서버 서명키로 발급된 JWT** 입니다.

> 참고로 저작도구의 JWT 서명키와 관제 데이터셋 API 의 유효 서명키는 **서로 다른 값**임을 확인했습니다
> (값은 대조만 하고 기록하지 않았습니다). 따라서 저작도구가 자체적으로 유효 토큰을 만들 수 없습니다.

### 배포본 설정 확인 (참고 — 원인 파악용)

dev 배포본 설정을 확인한 결과입니다.

- `ConfigSecurity` — `anyRequest().authenticated()` + `JwtAuthenticationFilter(${jwt.secret})`
  · `permitAll` 대상은 `/v3/api-docs/**`, `/swagger-ui/**`, `/swagger-ui.html`, `/api/dev/test` **4경로뿐**
- `AccessGuard` — `x-access-token` 이 **비어 있지만 않으면 통과**시키는 컨트롤러 레벨 가드가 별도로 존재
  · `ApiDataSetNotify` 가 이 가드를 사용하나, **Security 필터가 먼저 차단하므로 현재 도달하지 않습니다.**
- OpenAPI 문서상 `x-access-token` 은 `type: apiKey`, `description: "Fixed token for all requests"`, `required: false`
  · 문서 기술(고정 토큰·선택)과 **실제 동작(JWT·필수)이 서로 다릅니다.**

## 3. 질의

### Q1. 저작도구용 `x-access-token`(JWT) 발급 ★ — **가장 중요**

저작도구가 통지 시 사용할 토큰을 **관제 측에서 발급**해 주시면 되겠습니까?
발급해 주실 경우 아래를 함께 알려주십시오.

| 항목 | 확인 필요 사항 |
|---|---|
| 발급 주체·절차 | 관제 계정 시스템 발급인지 / 별도 서비스 계정인지 |
| 만료·갱신 | 만료 시각(`exp`)이 있는지, 있다면 **갱신 방법**(갱신 API 또는 무기한 서비스 토큰) |
| 필수 클레임 | 필터가 요구하는 `sub`/역할/권한 클레임이 있는지 (DB 조회로 사용자 존재를 확인하는지) |
| 환경별 값 | dev / stg / prd 별로 값이 다른지 |

> 저작도구는 **이미 `x-access-token` 헤더를 붙일 수 있게 구현되어 있습니다.** 토큰 값만 주시면
> 환경변수 주입만으로 연동되며 **코드 변경이 없습니다.** 만료가 있는 토큰이면 갱신 로직 구현이
> 추가로 필요하므로, 가능하면 **만료 없는 서비스 토큰**을 권해 드립니다.

### Q2. 아니면 notify 2경로를 `permitAll` 로 여실 계획이었습니까?

`ApiDataSetNotify` 에 `AccessGuard`(비어있지 않은 `x-access-token` 검사)가 **별도로 붙어 있는데
현재 구조에서는 도달할 수 없습니다.** 원래 이 2경로를 `permitAll` 로 두고 `AccessGuard` 로만
보호하려던 설계였는데 Security 설정이 누락된 것인지 확인 부탁드립니다.

- **그 설계가 맞다면** → notify 2경로를 `permitAll` 에 추가해 주시면, 저작도구는 합의된 공유 문자열을
  `x-access-token` 에 실어 보내겠습니다. (그 공유 문자열 값도 함께 지정해 주십시오)
- **아니라면** → Q1 대로 JWT 발급을 부탁드립니다.

### Q3. 규격서 §4 문구 확정

규격서 §4 는 `공통: 헤더 x-access-token` 이라고만 되어 있고 **토큰 형식·발급처가 명시되어 있지
않습니다.** Q1/Q2 결론에 맞춰 규격서에 아래를 명시하고자 합니다 — 확정 내용을 알려주시면
저작도구 측 규격서를 개정하겠습니다.

> `x-access-token`: {발급 주체}가 발급한 {JWT | 고정 문자열}. {만료·갱신 정책}.

### Q4. (경미) 성공 응답 코드

규격서 §4-1/§4-2 는 **`202`** + `{dataset_version_id, status:"packaging"}` 으로 되어 있으나,
OpenAPI 문서에는 **`200`** 만 정의되어 있습니다. 실제 반환값이 무엇인지 확인 부탁드립니다.

> 저작도구는 **2xx 전부를 성공으로 수용**하므로 동작에는 영향이 없습니다. 문서 정합 차원의 확인입니다.

## 4. 회신 전까지 저작도구 조치 — dev 통지를 **켜지 않습니다**

토큰 없이 통지를 활성화하면 **승인된 영상의 통지가 유실됩니다.**

저작도구는 통지 실패분을 폴백 큐(`LS_CONTROL_NOTIFY_FALLBACK`)에 적재하고 재시도하는데,
**최대 5회 · 백오프 1·2·4·8·16분** 이후 `DEAD_LETTER` 로 종결됩니다. 401 은 계속 401 이므로
**약 31분 안에 그 구간의 모든 통지가 죽고, 자동으로 되살릴 경로가 없습니다.**

따라서 회신을 받아 토큰이 확보된 뒤에 dev 통지를 활성화하겠습니다.

| 환경 | 통지 대상 주소 | 현재 상태 |
|---|---|---|
| dev | `http://192.168.102.246:9014` (본 문서 실측 대상) | **비활성** — 토큰 확보 후 활성화 예정 |

# 관제 회신 및 저작도구 답변 (2026-08-25)

## 관제 회신 요지

> 저작도구 진입 시 관제지원을 경유하면 사용자 정보가 브라우저 세션 스토리지에 저장될 것이라 보고
> API 헤더 `x-access-token` 으로 받고자 함. 저작도구 웹에서 해당 스토리지 접근·추출이 가능한가?
> 1차 개발 정보로는 `label-studio-auth-token` 키로 저장됨. 현재는 포트가 달라 스토리지를 유실하므로
> 정상 루트로는 불가능. **잠깐 토큰 검증을 풀어두겠음.**

임시 해제 감사합니다. **해제 반영을 실측으로 확인**했습니다(§B). 다만 사용자 세션 토큰 방식은
포트 문제를 해결하더라도 **구조적으로 성립하지 않습니다**(§A-2). 운영 방식을 §C 로 제안드립니다.

---

## A. 질문에 대한 답변 — 스토리지 추출은 **불가능**합니다

### A-1. 말씀하신 포트 문제 — 진단이 정확합니다

`sessionStorage`·`localStorage` 는 **origin(scheme + host + **port**) 단위로 격리**됩니다.
dev 현재 형상은 관제 web `:14000` / 저작도구 web `:13000` 이라 **서로 다른 origin** 이며,
저작도구 웹은 관제 origin 의 스토리지를 **읽을 수 없습니다**(브라우저가 차단 — 우회 불가).

추가로 `sessionStorage` 는 **탭·창 단위**라, 같은 origin 이어도 새 탭으로 열면 값이 없습니다.
(그래서 저작도구는 인계 채널로 `sessionStorage` 가 아니라 `localStorage` 를 사용합니다.)

### A-2. ★ 더 근본적인 문제 — **통지는 브라우저가 보내지 않습니다**

이 부분이 핵심입니다. 완료/수정 통지의 **발신 주체는 저작도구 백엔드(서버)** 이며,
사용자 브라우저는 그 경로에 **존재하지 않습니다.**

| 통지 | 발신 시점·주체 | 브라우저 세션 |
|---|---|:-:|
| `notify-completed` | 검수 승인 **트랜잭션 커밋 후 비동기(@Async)** 로 서버가 발송 | 없음 |
| `notify-updated` | **디바운스 윈도우(기본 60초) 만료 후 스케줄러**가 서버에서 발송 | 없음 |
| 실패분 재전송 | **폴백 큐 재시도 잡(5분 주기)** 이 서버에서 발송 | 없음 |

즉 **사용자가 승인 버튼을 누른 뒤 로그아웃하거나 브라우저를 닫아도 통지는 나가야 하고, 실제로
그렇게 동작합니다.** 재시도는 최대 31분 뒤까지 발생하며 그 시점엔 사용자 세션이 이미 없습니다.
2노드 Active-Active 라 승인을 처리한 노드와 통지를 발송하는 노드가 다를 수도 있습니다.

> **따라서 origin(포트) 문제를 해결해 스토리지를 공유하더라도 사용자 세션 토큰 방식은 성립하지
> 않습니다.** 통지 인증에 필요한 것은 사용자 토큰이 아니라 **사용자와 무관한 서비스 인증**입니다.

### A-3. `label-studio-auth-token` 은 1차 잔재입니다 — **현행 관제 배포본은 이미 다른 키를 씁니다**

2차 저작도구 코드베이스에 `label-studio-auth-token` 은 **0건**입니다(1차 Label Studio 기반 구현의 흔적).
그리고 **관제지원 웹 배포본(`klid-system-web`)에도 그 키는 0건**입니다.

dev 배포본의 관제 웹 번들(`htdocs/assets/js/index-*.js`)을 확인한 결과입니다.

```js
be(z, "ACCESS_TOKEN_KEY", "klid-jwt-token"), be(z, "TOKEN_INFO_KEY", "tokenInfo")
... localStorage.removeItem(this.ACCESS_TOKEN_KEY)
```

**관제 웹 자신이 `ACCESS_TOKEN_KEY = "klid-jwt-token"` 을 `localStorage` 에 저장·삭제하고 있습니다.**
함께 저장하는 키도 `authority` · `userId` · `userNm` 로 확인됩니다.

저작도구는 **이 관제 실동작을 관측해 그대로 맞춰 구현**했습니다(2026-05-12 도입). 즉 저작도구가
임의로 정한 키가 아니라 **관제 측이 쓰고 있던 키**입니다.

| 용도 | 키 | 저장소 | 저작도구 동작 |
|---|---|---|---|
| JWT 인계 | `klid-jwt-token` | `localStorage` | **읽기 전용** — 인계받아 `sessionStorage` 로 이전 |
| 표시용 사용자 | `userId` · `userNm` | `localStorage` | 읽기 전용 |
| `tokenInfo` | — | `localStorage` | 읽지 않음 |
| `authority` | — | — | **의도적으로 읽지 않음** — 권한 판정의 진실원은 저작도구 서버(`LS_USER_ROLE`) |

> **결론: 로그인 인계 축은 이미 양측이 일치하며, 추가 작업이 없습니다.**
> `label-studio-auth-token` · `sessionStorage` 는 1차 시절 정보로 보입니다.

⚠ 이 채널은 **사용자 로그인 인계 축**이며, 본 문서의 **서버→서버 통지 축과는 무관**합니다.

### A-4. 다만 **동일 origin 배포**는 확인이 필요합니다 ★

위 인계가 성립하려면 관제와 저작도구가 **동일 origin(scheme + host + port)** 이어야 합니다.
dev 는 관제 web `:14000` / 저작도구 web `:13000` 이라 **현재 인계가 성립하지 않습니다.**

**상용 배포 시 두 시스템이 동일 origin(동일 도메인·동일 포트, 경로로만 구분)으로 서비스되는지**
확인 부탁드립니다. 포트나 서브도메인이 갈리면 브라우저가 스토리지 접근을 차단하므로,
그 경우에는 인계 방식 자체를 재설계해야 합니다.

## B. 임시 해제 반영 확인 (실측)

동일 요청으로 해제 전후를 비교했습니다.

| 조건 | 해제 전 | **해제 후 (현재)** |
|---|---|---|
| 헤더 없음 | `403` Tomcat HTML `Access Denied` | `401` `{"code":"UNAUTHORIZED","message":"x-access-token 헤더가 필요합니다."}` |
| `x-access-token: klid-authoring` | `401` err 1102 "잘못된 형식의 토큰입니다" | **`422 VALIDATION_FAILED`** — 컨트롤러 도달 ✅ |

401 응답이 Tomcat HTML 에서 관제 JSON 으로 바뀐 것으로 보아, Security 가 `permitAll` 로 열리고
**컨트롤러의 `AccessGuard` 만 남은 상태**로 이해했습니다. Q2 에서 여쭌 원래 설계가 맞았던 것으로
보입니다.

> 위 확인은 **고의로 불완전한 바디(`{}`)** 로 수행해 검증 단계에서 멈추게 했습니다 —
> 관제 dev 에 **데이터를 생성하지 않았습니다.**

### B-1. 요청 — 사용할 `x-access-token` 값을 지정해 주십시오 ★

값은 무엇이든 통과하지만, 저작도구는 **토큰 설정이 비어 있으면 헤더 자체를 붙이지 않도록**
구현되어 있어(빈 값 전송 방지) 현재 형상 그대로는 401 입니다.
**합의된 문자열 하나**를 지정해 주시면 그대로 주입하겠습니다. (미지정 시 `klid-authoring` 사용 예정)

### B-2. 요청 — 해제 기간과 **재잠금 전 사전 통보** ★

임시 해제 중 저작도구 dev 통지를 활성화해 실제 왕복을 검증하려 합니다.
**검증이 다시 걸리는 순간부터 발송되는 통지는 전부 401** 이 되고, 폴백 큐 재시도 5회
(백오프 1·2·4·8·16분)를 소진한 뒤 **약 31분 안에 `DEAD_LETTER` 로 종결되어 자동 복구되지
않습니다.** 아래를 알려주시면 그에 맞춰 통지를 끄겠습니다.

- 해제 유지 기간 (또는 재잠금 예정 시점)
- 재잠금 시 **사전 통보** 가능 여부

## C. 운영(prd) 인증 방식 제안 — 별도 확정이 필요합니다

§A-2 대로 통지는 서버→서버이므로 **사용자와 무관한 서비스 인증**이어야 합니다. 세 가지를 제안드리며,
관제 측 운영 정책에 맞는 것을 골라 주시면 저작도구가 맞추겠습니다.

| # | 방식 | 저작도구 작업량 | 비고 |
|:-:|---|---|---|
| **C-1** | **만료 없는 서비스 토큰** (고정 문자열 또는 `exp` 없는 JWT)을 관제가 발급 | **코드 변경 0** — 환경변수 주입만 | **권장.** 현재 임시 해제 형상을 그대로 정식화한 것 |
| C-2 | 만료 있는 JWT + 갱신 API 제공 | 토큰 갱신 로직 신규 구현 | 갱신 실패 시 통지 유실 위험이 추가됨 |
| C-3 | 인증 없이 **IP 화이트리스트**로 보호 | **코드 변경 0** | 저작도구·관제가 동일 내부망이라 성립. 통지 경로 2개 한정 |

> 어느 쪽이든 **사용자 세션 토큰(`klid-jwt-token` / `label-studio-auth-token`)을 통지에 사용하는
> 방식은 채택할 수 없습니다** — §A-2 사유.

기존 **Q3(규격서 §4 문구 확정)**·**Q4(성공 응답 코드 `202` vs `200`)** 도 함께 회신 부탁드립니다.

## D. (추가) 서버 상태 확인 엔드포인트 요청 ★

저작도구는 연동 상대의 가용성을 `/actuator/health` 로 관측합니다. 그런데 관제 데이터셋 API 에는
상태 확인용 엔드포인트가 없어 이 관측이 성립하지 않습니다.

실측(2026-08-25):

| 경로 | 응답 |
|---|---|
| `/health` · `/api/health` · `/actuator/health` | **전부 403** |

`GET /v3/api-docs` 로 받은 정본 스키마 전수에도 상태 확인 엔드포인트는 없습니다.

**이는 다른 연동 벤더와 대비됩니다.** 외부 VLM 은 규격(`video_vlm_klid_api_v1.1.0`)에
**`GET /v1/videovlm-klid/status`** — *"요청 전 서버의 처리 가능 여부를 확인한다"* — 를
정식 엔드포인트로 두고 있어, 저작도구가 위탁 전 가용성을 확인하고 헬스로도 관측합니다.

**요청**: 인증 없이 접근 가능한(`permitAll`) 상태 확인 엔드포인트를 하나 열어 주시면 좋겠습니다.
응답 본문은 무엇이든 상관없고 **200 이면 충분**합니다.

- 어렵다면 **현행 유지도 가능합니다.** 저작도구는 관제 헬스체크를 **제거**했고(통지 실패는
  메트릭·재전송 큐가 별도로 관측합니다), 이 요청은 운영 관측 편의를 위한 것이지 연동 성립 조건이 아닙니다.
- 참고로 저작도구는 판정 기준을 **「HTTP 응답이 오면 살아있는 것으로 본다」**(4xx 포함, 연결 실패만 장애)로
  바꿨습니다. 즉 상태 엔드포인트가 인증을 요구해 401/403 을 주더라도 관측은 성립합니다.
  **경로 하나가 응답만 해 주면 됩니다.**

## E. (실측) 통지가 관제에 도달했으나 **422 로 거부**됩니다 ★★ — 가장 시급

임시 해제해 주신 덕분에 **dev 에서 실제 왕복을 끝까지 돌렸습니다.** 결과를 공유드립니다.

### E-1. 배선은 정상입니다

```
검수 승인(job_id=1) → 산출물 생성 성공(프레임 2, 원본+비식별 4파일)
                    → POST /api/data-set/v2/jobs/1/notify-completed
                    → 422 VALIDATION_FAILED
```

**인증·경로·페이로드 구조는 모두 통과했습니다.** 관제 서버가 저희 요청을 받아 파싱하고
검증 단계까지 도달했다는 뜻입니다. 저작도구 쪽 연동 배선은 완성돼 있습니다.

### E-2. 거부 사유 — 관제가 보내지 않은 값을 관제가 필수로 요구합니다

관제 응답:
```json
{"code":"VALIDATION_FAILED",
 "message":"필수 9필드 검증 실패 (event_type_cd 8대 이벤트 / duration·image ≥0 / gen_ai_yn Y|N)"}
```

저희가 보낸 본문:
```json
{"job_id":"1","event_type_cd":"EV01000101","evnt_cls_cd":null,"evnt_ctgry_cd":null,
 "lclgv_cd":"11680","lclgv_nm":null,"duration_sec":11,"image_count":2,
 "gen_ai_yn":"N","output_ver_no":1}
```

메시지가 지목한 세 항목은 **모두 정상**입니다 — `event_type_cd` 는 `EV01000101`(침수)로
규격 허용 8종에 있고, `duration_sec`·`image_count` 는 0 이상, `gen_ai_yn` 은 `N` 입니다.

**실제로 비어 있는 것은 `evnt_cls_cd`·`evnt_ctgry_cd` 둘뿐이며, 이 둘은 관제 required 입니다.**

그런데 이 두 값의 **조달처가 관제 인입 원장**입니다. 저작도구는 규격 §3 대로
`LS_DATA_INGEST.EVNT_CLSF_CD`·`EVNT_CTGRY_CD` 를 조회해 싣고, **관제가 보내지 않으면 `null`**
로 둡니다(값을 지어내지 않는다는 원칙). dev 실측:

| 확인 | 결과 |
|---|---|
| `LS_DATA_INGEST` 전체 행 | **7건** |
| 그중 `EVNT_CLSF_CD` 가 채워진 행 | **1건** (나머지 6건 NULL) |
| 이번 대상(`job_id=1`)의 인입 행 | **0건** (dev 초기 데이터라 인입 경로 미경유) |

⇒ **관제가 인입에 싣지 않는 값을, 관제가 통지에서 필수로 요구하는 구조**입니다.
현재 상태로는 **거의 모든 영상의 완료 통지가 422 로 거부**됩니다.

### E-3. 요청 — 아래 중 하나를 선택해 주십시오

| 안 | 내용 | 저작도구 작업 |
|:-:|---|---|
| **E-3-a** | **인입 시 `EVNT_CLSF_CD`·`EVNT_CTGRY_CD` 를 채워 주신다** | **없음** — 이미 조회해 싣고 있습니다 |
| E-3-b | 통지 API 에서 두 필드를 **optional 로 내린다**(관제가 자체 보유값으로 채움) | 없음 |
| E-3-c | 저작도구가 `event_type_cd` 에서 두 값을 **유도**해 채운다 | 매핑표 신설 필요 — **권장하지 않음** |

**E-3-a 를 권해 드립니다.** 이벤트 분류는 관제가 소유한 사실이고, 저작도구가 `event_type_cd`
앞자리에서 유도하면 관제 코드 체계의 사본이 저작도구에 생겨 두 번째 진실원이 됩니다
(관제가 분류를 조정하면 조용히 어긋납니다).

### E-4. 참고 — 저작도구는 실패한 통지를 잃지 않습니다

거부된 통지는 재전송 큐에 적재되어 **최대 5회(백오프 1·2·4·8·16분)** 재시도합니다.
다만 이번 건은 원인이 데이터라 재시도로 해소되지 않고 약 31분 뒤 종결됩니다.
**E-3 이 정해지면 해당 영상을 재승인해 통지를 다시 발생시킬 수 있습니다** — 영구 유실은 아닙니다.

### E-5. 부수 확인 — `lclgv_nm` 도 같은 축입니다

`lclgv_nm`(지자체명)도 인입에서 조달하는데 대부분 비어 있어 `null` 로 나갑니다.
optional 이라 거부 사유는 아니지만, 관제 쪽에서 표시에 쓰신다면 **E-3-a 와 함께 채워 주시면** 됩니다.
