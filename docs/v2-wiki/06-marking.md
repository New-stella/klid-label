## 6.1 마킹이란

영상에서 **이벤트(관심 시점)를 자동/수동으로 표시**하는 단계. 마킹 완료가 잔여 배치를 기동하고, 마킹 결과는 외부 VLM 시계열 위탁의 **프레임 선택 근거**이자 FFmpeg 프레임 추출 위치의 기준이 된다.

- 마킹 결과 **저장** = 이벤트명(`EVNT_NM`) + 영상 경로(`VIDEO_FILE_PATH_NM`) + marks 배열(`MARK_CN` JSON)
  - ⚠ **이 셋을 시계열 위탁에 전달하지 않는다** — 마킹이 위탁 요청에 남기는 것은 **프레임 선택(`frame_policy`)** 과, 2026-09-07 개정으로 더해진 **추가 질문 축의 질문 문구(`prompt`) · 작업자가 고른 검증 이벤트 유형**뿐이다. 구 서술 *"마킹 결과(이벤트명 + 영상 경로 + marks 배열)를 VLM 에 전달"* 은 **폐기** → [09](09-vlm-timeseries.md)
    - ⚠ **구 서술 폐기(2026-09-07)** — *"위탁 요청에는 `frame_policy` 만 싣는다(수동 → `frame_selected` + `selected_frames` / 자동·부재 → `frame_interval`)"* 는 두 군데가 사실과 다르다. ①추가 질문 창구가 **질문 문구를 요청 본문에 직접 싣는다**(아래 6.3-2). ②모드로 갈리지 않는다 — **수동·자동 모두** 마킹 본문에서 얻은 프레임 인덱스를 `frame_selected` 로 싣고, 실을 프레임이 하나도 없을 때만 `frame_interval` 로 내린다. 도출 규칙의 단일 원천은 [09 §9.2-0](09-vlm-timeseries.md)이며 여기에 복제하지 않는다
  - ⚠ **"콜백"은 방향이 반대다** — 마킹 → VLM 은 **위탁/제출**이고, VLM → 저작도구 방향만 콜백(`POST /v1/vlm/callback`)이다
- **이벤트명은 수동 입력하지 않는다** — 영상의 이벤트 유형(`LS_DATA_RAW.EVNT_TYPE_CD`)을 서버가 자동 소싱해 `LS_MARKING.EVNT_NM` 에 채운다(API-047 계약 변경). 이벤트 유형이 미지정(null/blank)인 영상은 마킹할 수 없다(`INVALID_INPUT` 400).
  - ⚠ **구 서술 폐기** — *"VLM 전달 페이로드 형식은 무변경(자동 소싱된 값을 `EVNT_NM` 으로 그대로 전달)"* 은 사실과 다르다. 자동 소싱된 값은 `LS_MARKING.EVNT_NM` 에 **저장될 뿐** 위탁 요청 바디에 실리지 않는다. 시계열 위탁의 `event_type` 은 **다른 컬럼**(`LS_DATA_INGEST.VRFC_EVNT_TYPE_CD`, 관제 미수신이면 작업자가 마킹에서 고른 값 — 아래 6.3-2)에서 조달하며 둘을 대체·유도하지 않는다
    - ⚠ **표기 정정(2026-09-07)** — 이 줄이 쓰던 「verify 요청 바디」는 **판정 창구(`/verify`)를 쓰던 시절의 표기**다. 그 창구는 연동하지 않으며, 우리가 부르는 분석 창구는 **묘사(`describe`) · 추가 질문(`custom`)** 둘이다 → [09 §9.5](09-vlm-timeseries.md)
- **이벤트 유형은 관제 인입 평면값을 그대로 옮겨 적는다** (2026-08-09 이후 실측 정정) — 단일 원천은 `LS_DATA_INGEST.EVNT_TYPE_CD`(V166 신설 컬럼)이고, 적재(`TrainingVideoIngestTx#resolveEvntTypeCd`)는 `trimToNull(ingest.getEvntTypeCd())` 한 줄로 그 값을 `LS_DATA_RAW.EVNT_TYPE_CD` 에 복사할 뿐 어떤 테이블도 조인하지 않는다. 관제가 이 컬럼을 비워 보내면(=미송신) `null` 로 적재되고, 그 결손은 프로세스 1회 WARN(`TrainingVideoIngestTx#warnControlContractGaps`)으로만 관측되며 그 영상은 아래 마킹 가드가 400 으로 막는다. 결손 시 함께 막히는 것: 마킹 진입 · 관제 완료통지 계약 필드 · 작업/검수목록 이벤트유형 필터 · 통계 버킷 · export 메타
  > ⚠ **구 서술 폐기(2026-08-19 코드 실측)** — *"관제 인입(`LS_DATA_INGEST`)은 이벤트 **식별자**(`EVNT_ID`, 예 `ABA_0001`)만 주므로, 적재 시 `EVNT_ID` 로 관제 공유 이벤트리스트(`MNG_CLIP_EVNT_LST`)를 조회해 `EVNT_TYPE_CD` 를 도출한다(2026-08-04 수정) — 해석 실패는 매칭 없음 또는 한 이벤트에 유형이 둘 이상(`MNG_CLIP_EVNT_LST` 복합 PK)일 때다"* 는 **사실과 다르다**. `MNG_CLIP_EVNT_LST` 조인은 **V167 에서 그 테이블 자체가 제거되며 함께 폐지**된 과도기 폴백이다(`TrainingVideoIngestTx` 클래스 javadoc이 이 사실을 "구 서술 폐기 ③"으로 직접 명시한다). 인입 유형코드 컬럼이 없어 항상 null 이던 시절(V164 이전)과 그 이후 `EVNT_ID` 조인으로 해석하던 시절(V166~V167 이전) **양쪽 다 이미 지났다** — 지금은 관제가 유형코드 자체를 평면값으로 직접 보낸다. 근거: `TrainingVideoIngestTx(resolveEvntTypeCd, warnControlContractGaps)`. 이벤트 **식별자**(`EVNT_ID`)·이벤트명(`EVNT_NM`) 필드 자체는 요청 DTO(`InternalUploadCreateRequest.evntId/evntNm`)에 여전히 남아 있으나 `EVNT_TYPE_CD` 도출에는 관여하지 않는다 → [05 §5.2](05-video-management.md#52-영상-적재)의 `evntTypeCd` 입력 항목 참조.
- 마킹 대상: **비식별 영상** (구현됨, NFR-001 v1.5). 적재 직후 선두 비식별이 완료(`LsDataRaw.dataSttsCd=MARKING_READY`, `deIdntfYn='Y'`)된 영상만 마킹 진입 → [08](08-deidentification.md)

## 6.3 마킹 화면

- **비식별 영상** 스트리밍 재생 (`GET /v1/videos/{rawSn}/stream`, HTTP Range — 항상 비식별 영상 서빙, 비식별 미완료 시 NOT_FOUND 로 원본 노출 차단) → [05](05-video-management.md#53-영상-스트리밍)
- **배속 설정 0.25x ~ 4x**
- **키보드 단축키**: `Space`(마킹), `Del`(삭제), `Enter`(완료)
- **마크 칩 개별 삭제 버튼**(2026-08-08 신설) — 각 마크 칩이 `선택 버튼 + 삭제(×) 버튼` 두 개로 이뤄져, 특정 마크를 마우스만으로 지울 수 있다. 그 전에는 삭제 수단이 `Del` 단축키(선택된 마크 1건)뿐이라 마우스 사용자에게는 특정 마크를 지울 방법이 아예 없었다. **기존 `Del` 단축키는 그대로 유지**되며, 삭제 버튼의 접근성 이름에는 어느 마크인지 알 수 있도록 **타임라인과 같은 표기**를 붙인다
- **이벤트명 입력란 없음** — 영상의 이벤트 유형(`EVNT_TYPE_CD`)에서 자동 소싱(6.1)
- **'저장된 마킹 목록'(MarkingList) 없음** — 화면은 현재 작업 중 마크(타임라인/마크 칩)만 표시. 이를 백킹하던 마킹 관리 API(목록 조회 `GET /v1/videos/{rawSn}/markings`, 단건 조회 `GET .../{markingSn}`, 삭제 `DELETE .../{markingSn}`)는 FE 미사용으로 제거됨 — 마킹 API 는 생성(`POST /v1/videos/{rawSn}/markings`)만 보유
- **완료 버튼 비활성 조건**: 제출 중이거나 **자동 모드에서 `intervalFrames` 가 1 미만**일 때만 비활성이다. **마크 0건과 검증 이벤트 유형 미선택은 버튼을 죽여서 막지 않는다** — 버튼은 누를 수 있고, 눌렀을 때 사유를 알린 뒤 제출만 막는다(조용한 무반응이면 보조기술 사용자에게 아무 신호도 남지 않는다)
  - ⚠ **구 서술 폐기(2026-09-07)** — *"완료 버튼 활성 조건: 수동=마크 1건 이상"* 은 사실과 다르다. 마크 건수는 버튼 활성 여부를 정하지 않는다(`MarkingToolbar` 확정 사양)
- 비식별 누락 신고: 라벨링 단계(srcSn 기준)·**마킹 단계(rawSn 기준 `POST /v1/videos/{rawSn}/deident-report`) 모두 구현됨 — 2026-08-05 부터 마킹 화면에 신고 버튼이 있다**(그 전에는 API 만 있고 화면 진입점이 없어 마킹 중 발견해도 라벨링까지 진행해야 했다). 부수효과(작업락 + `DE_IDENT_YN='F'` + 검수완료 영상 통지 — 라벨·개인정보 3필드는 보존)는 두 경로가 동일하며 파생영상은 412 로 거부된다 → [08](08-deidentification.md#84-누락-신고-rq-sfr-09-03-uc-016)
  - **★마킹 단계 신고는 배치 단계가 `MARKING_READY` 일 때만 접수**된다(아니면 **412**, 문구 1종 — 배치 단계를 노출하지 않는다). 그 상태는 선두 비식별 성공 직후·마킹 이전이라 프레임 행도 라벨도 없어, 해소 후 **마킹부터 다시** 해도 파괴할 작업 결과가 없다.
  - **해소(resolve) 후 재개 지점이 신고 단계로 갈린다** — 마킹 단계 신고면 배치 단계를 `MARKING_READY` 로 되감고 활성 마킹(`PENDING`/`VLM_REQUESTED`)을 종결해 **재마킹 진입을 연다**(재마킹 409 해제). 라벨링 단계 신고면 마킹은 그대로 두고 **프레임 이미지만 재추출**한다.
  - FE 는 **파생영상**에서 버튼을 비활성화 + 사유 툴팁을 띄운다 — 사유를 다 적고 제출한 뒤에야 412 를 보는 동선을 없앤다(라벨링 화면과 동일 관례). ⚠ **비-`MARKING_READY` 는 버튼 비활성이 아니라 화면 진입 자체가 막힌다**(2026-08-25 · 아래 6.2-1) — 그 상태의 신고는 **라벨링 화면**이 담당한다.

## 6.3-1 화면 진입 조건 — 두 축으로 선차단 (2026-08-25 확정, 구속)

마킹 화면은 **편집기를 열기 전에** 두 축을 판정해 조건을 만족하지 않으면 **진입 자체를 막는다.**
평가 순서는 서버(`MarkingGuards`)와 **같다** — 순서가 갈리면 두 축에 모두 걸린 영상에서 화면 안내와
서버 거부 사유가 달라진다.

| 순서 | 축 | 차단 조건 | 안내 |
|:--:|---|---|---|
| ① | 비식별 | 비식별 미완료·재처리 대기(`DE_IDENT_YN` 이 `N`·`F`, 또는 비식별 진행 중·실패) | "비식별 완료 후 마킹이 가능합니다." |
| ② | 배치 단계 | 배치 단계가 `MARKING_READY` 가 아님 | "이미 다음 단계로 넘어간 영상이라 마킹할 수 없습니다." |

- **왜 선차단인가** — 서버는 ②를 *마킹 저장 시점*에 412 로 막는다. 화면이 열려 있으면 작업자가
  마크를 다 쌓은 뒤에야 거부되므로, 이미 처리가 끝난 영상에서 편집기가 멀쩡히 열리는 상태였다.
- ⚠ **차단 화면에서는 비식별 누락 신고 버튼도 함께 사라진다** — 그 상태의 신고는 어차피 서버가 받지
  않으며(§6.3 `MARKING_READY` 한정), 그 경로의 신고는 **라벨링 화면**이 담당한다.
- ⚠ **영상 상세가 아직 로딩 중일 때는 차단하지 않는다** — 확정되지 않은 값으로 막으면 로딩 구간의
  깜빡임이 정상 마킹을 가로막는다.
- **서버의 412 는 그대로 남는다** — 화면 선차단과 서버 거부는 서로를 대체하지 않는다(화면을 거치지
  않는 직접 호출의 안전망).
- ★**같은 확정으로 마킹 화면 헤더의 배치 단계 진행 표시를 제거했다** — 잔여 배치는 **마킹 완료가
  트리거**라 마킹 중에는 확인할 진행이 존재하지 않는다. 표시기(`BatchStageIndicator`) 자체는
  영상 상세가 계속 쓰므로 존치한다 → [05 영상 §5.5.5](05-video-management.md).

## 6.3-2 검증 이벤트 유형·질문 선택 (2026-09-07 확정, 구속)

외부 시계열 위탁의 **추가 질문 창구가 `custom` 으로 바뀌면서 질문 문구를 요청 본문(`prompt`)에 직접
싣게 됐다.** 그래서 마킹 화면에서 고른 질문이 곧 **사업자에게 나가는 값**이다 —
그 전에는 사업자가 이벤트 유형별로 질문을 관리했고 우리가 보관한 질문은 **기록일 뿐**이었다
→ [09 §9.4-2](09-vlm-timeseries.md) · [09 §9.5](09-vlm-timeseries.md).

### 질문 선택

- 그 영상의 **검증 이벤트 유형에 등록된 질문 목록**(`LS_VRFC_EVNT_QSTN`, 정렬순서 오름차순)에서
  작업자가 하나를 고르고, 고른 값은 마킹 원장(`LS_MARKING.VRFC_EVNT_QSTN_SN`)에 저장된다.
- **자동 마킹이면 그 유형의 첫 번째 질문이 자동 선택**된다 — 어느 모드에서도 위탁에 실을 질문은 값이 있다.
- 「고른 질문이 그 유형에 속하는가 · 아니면 첫 번째로 되돌린다」는 해석의 단일 진실원은 서버
  판정기(`VerificationEventQuestionResolver`)다. 화면·배치가 이 판정을 복제하지 않는다 — 복제하면
  화면이 보여준 질문과 산출물에 실린 질문이 조용히 어긋난다.
  ⚠ 어긋난 값은 400 이 아니라 **그 유형의 첫 번째 질문으로 교정**되며, 교정 사실을 응답으로 돌려주지 않는다.

### 검증 이벤트 유형 선택 — 관제 값이 없을 때만 노출한다

**왜 열었나** — 관제가 검증 이벤트 유형을 보내지 않은 영상은 ①질문 목록이 그 유형으로 조회되므로
**비어서 질문을 고를 수 없고** ②묘사 축 위탁도 유형이 없어 사업자가 거부한다. 즉 그 영상은
**시계열 메타를 하나도 받지 못한다.** 작업자가 유형을 고르게 하면 둘이 함께 풀린다.

- 관제 인입이 유형(`LS_DATA_INGEST.VRFC_EVNT_TYPE_CD`)을 보낸 영상에서는 **유형 선택을 아예 띄우지 않는다.**
  ⚠ **「표시하되 잠근다」가 아니다** — 그 안은 검토 후 채택되지 않았다. 되살리지 말 것.
  ⇒ 두 값이 경쟁할 일이 없으므로 **우선순위 충돌이 구조적으로 발생하지 않는다.**
- 노출 판정은 **서버가 내려주는 「고를 수 있는 유형 목록」이 비었는지**로만 한다 — 화면이 유형 코드의
  null 여부로 다시 판정하지 않는다(두 번째 진실원이 된다).
- 그 목록은 **영상 상세 조회 응답**에 실려 오며 **각 항목이 그 유형의 질문 목록을 함께 담는다**(정렬순서
  오름차순). 유형을 고른 뒤 **서버에 다시 묻지 않는다.** 목록의 조달원은 검증 이벤트 유형
  카탈로그(`LS_VRFC_EVNT_TYPE`)이며, 질문 관리 조회 경로는 검수자 전용이라 마킹 작업자가 쓸 수 없다.
- 고른 유형은 마킹 원장(`LS_MARKING.VRFC_EVNT_TYPE_CD`, V35)에 저장되고, 위탁 시 묘사 축 `event_type` 의
  **2순위 조달값**이 된다 — 조달 순서는 **관제 인입 값 → 마킹 선택값 → `null`**.
  ⚠ **`null` 폴백을 없애지 않는다** — 「값을 지어내지 않는다」가 확정 정책이라, 조달이 없으면 그대로
  보내고 사업자의 거부를 기록한다 → [09 §9.2](09-vlm-timeseries.md).
- ★ **추가 질문 축(`custom`)에는 `event_type` 을 싣지 않는다** — 그 축에서는 유형 미수신·미지원으로 인한
  거부가 구조적으로 발생하지 않는다. 유형이 필요한 것은 **질문 목록을 끌어오기 위해서**이지 그 축의
  요청 필드 때문이 아니다.

### 유형 선택은 필수다 — 단, 화면 축이다

- **선택이 노출된 영상에서 유형을 고르지 않으면 마킹을 완료할 수 없다.** 거부는 완료 버튼 비활성이
  아니라 **눌렀을 때 사유를 알리고 제출만 막는 방식**이다(§6.3 의 마크 0건과 같은 축).
- 근거: 위탁 본문에 싣는 질문 문구는 **어느 마킹 방식에서도 값이 있어야 하는데**(수동=작업자가 고름,
  자동=그 유형의 첫 번째 질문이 자동 선택), 질문을 고르려면 **유형이 먼저 정해져야** 한다.
- ★★ **「필수」는 화면 축이며, 마킹 등록 요청 스키마의 필수 목록도 원장 컬럼의 NULL 허용도 올리지 않는다.**
  관제 값이 있는 영상은 그 필드를 **애초에 보내지 않으므로**, 올리면 그 영상들의 마킹이 **전량 거부**된다.
  두 축을 같은 것으로 읽지 말 것.

### 값 판정 — 목록이 아니라 형식만 본다

- 유형 코드는 **허용목록으로 사전 차단하지 않는다**(2026-08-06 확정). 남은 검증은 **형식뿐**(소문자·숫자·
  밑줄 + 컬럼 폭 20자)이며, 판정 함수는 인입 쓰기 통로와 **같은 하나**(`LsDataIngest.isVrfcEvntTypeFormatValid`)를
  재사용한다 → [05 §5.2](05-video-management.md).
- 형식을 남긴 이유는 두 가지다 — ①컬럼 폭을 넘는 값이 입구를 통과하면 **INSERT 시점 DB 오류(500)** 로 새고
  ②이 값이 **외부 요청 본문·로그에 그대로 실려** 제어문자가 섞이면 로그 인젝션(CWE-117)·사업자측 파싱
  오류가 된다.

> **구현 상태(2026-09-07 실측)** — 화면 선택 · 마킹 등록 요청 수신 · 원장 저장 · 영상 상세 응답의
> 「고를 수 있는 유형 목록」 · 위탁 시점 조달까지 코드에 반영돼 있다.
> ⚠ 다만 **사업자 연동 자체에는 미확정 항목이 남아 있다**(API 키 값 미수신 · 비식별 영상의 사업자측
> 허용 경로 · 배포 형상의 콜백 도달 경로) → [09 §9.6](09-vlm-timeseries.md).

## 6.4 마킹 완료 → 배치 자동 시작

```
마킹 완료
  → MarkingCompletedEvent 발행
  → MarkingBatchBridge (AFTER_COMMIT)
  → deid 가드(deIdntfYn='Y' 검증) → @Async post-marking 배치 자동 시작
```

- **deid 가드 (2중)**: ①**마킹 생성 단계** — `MarkingService.create` 가 비식별 미완료(`deIdntfYn != 'Y'`) 영상의 마킹 생성을 거부(`PRECONDITION_FAILED` 412, "비식별이 완료된 영상에서만 마킹할 수 있습니다."). ②**배치 진입 단계** — `MarkingBatchBridge` 가 비식별 미완료 영상의 잔여 배치 트리거를 차단. "마킹은 비식별 완료 영상 대상" 규칙을 생성·배치 두 지점에서 일관 강제한다.
- 이후 배치는 비식별 단계를 제외한 post-marking 시퀀스(VLM→프레임추출→YOLO→SAM2→보간).

코드: `MarkingCompletedEvent`, `MarkingBatchBridge`. 이후 파이프라인 → [07](07-batch-pipeline.md).

## 6.4-1 영상당 활성 마킹 1건 (409)

- **활성 = 미종결** = `STTS_CD IN ('PENDING','VLM_REQUESTED')`. 같은 `rawSn` 에 활성 마킹이 이미 있으면 마킹 생성은 **409(CONFLICT)** 로 거부된다.
- 이유: 배치는 영상당 **최신 마킹 1건**만 VLM 에 위탁하므로(`MarkingLoadStep`/`VlmTimeseriesStep`), 활성 마킹이 2건 이상이면 나머지는 영원히 `PENDING` 인 고아 행으로 남는다.
- 종결 상태(`VLM_COMPLETED`/`VLM_FAILED`/`SKIPPED`)만 남은 영상의 **재마킹은 허용**된다(새 배치 사이클을 여는 정당한 동선).
- 동시 요청 방어는 서비스 사전 조회가 아니라 **DB 부분 유니크 인덱스** `UK_LS_MARKING_RAW_ACTVTN`(V142)가 최종 보증한다 — 위반은 409 로 변환된다.

### 6.4-1-a 배치 skip 시 마킹 종결 — `SKIPPED` (B-ISSUE-41, 2026-08-02)

- 마킹 저장(커밋)과 배치 트리거 판단(`MarkingBatchBridge`, AFTER_COMMIT)이 분리돼 있어, 브릿지가 **정당하게 skip**(검수 소유 작업 상태 / 이미 큐잉·처리중·완료 / 비식별 미완료 / 영상 미존재)해도 방금 커밋된 `PENDING` 마킹은 남았다.
- `PENDING → VLM_*` 전이는 **오직 VLM 단계**에서만 일어나고 그 단계는 배치가 돌아야 도달하므로, skip 된 마킹은 아무도 종결시키지 않는 **영구 고아**가 됐다. 활성 마킹 유일성 때문에 그 영상은 **다시는 마킹할 수 없었고**(재마킹 409), `POST /v1/videos/{rawSn}/batch/retry` 도 stage 가 `FAILED` 가 아니라 409 라 **복구 API 가 전무**했다.
- 이제 **모든 skip 분기가 그 마킹을 `SKIPPED`(종결)로 내린다**(`MarkingSkipTxService`, `REQUIRES_NEW`). 전이는 **`PENDING` 한정**이라 진행 중(`VLM_REQUESTED`)·종결 마킹을 덮지 않는다. 응답은 종전대로 201 + `batchTriggered=false` + `batchSkipReason` 이며, 영상은 재마킹으로 복구 가능하다.
- 기존 고착 행은 **V159** 가 1회 정리한다(작업 상태가 검수 소유 상태인 영상의 `PENDING` 마킹만 — 그 상태에서는 배치 진입 가드가 파이프라인을 확정 차단하므로 "곧 소비될 마킹"이 존재할 수 없다).

### 6.4-2 VLM 위탁 구간의 마킹 상태 전이 (2026-07-30)

VLM 제출이 논블로킹이 되면서 **콜백이 수락 응답(ACK)보다 먼저 도착**할 수 있게 됐다. 마킹 상태가 `VLM_REQUESTED` 에 영구 고착되는 것을 **양단에서** 막는다 → [09 §9.2-3](09-vlm-timeseries.md).

- **송신측(선커밋)** — `PENDING → VLM_REQUESTED` 전이를 **제출 전에** 독립 커밋한다(`VlmMarkingTxService`, `REQUIRES_NEW`). 전이는 `PENDING` 에서만 발생한다(종결 상태 역행 금지).
- **수신측(조회 범위 확대)** — 콜백 처리(`VlmResultService`)가 전이 대상을 `VLM_REQUESTED` 단독이 아니라 **`PENDING` + `VLM_REQUESTED`**(= 위 활성 정의와 동일)로 조회한다. 종결 상태는 포함하지 않으므로 이미 `VLM_COMPLETED` 면 0건 = 멱등 no-op.
- **단, 위탁 발급 시각 이후에 새로 생긴 `PENDING` 마킹은 제외** — 앞선 위탁이 `VLM_FAILED` 로 끝난 뒤 작업자가 **재마킹**했는데 옛 request 의 지각 콜백이 도착하면, 한 번도 위탁된 적 없는 새 마킹이 `VLM_COMPLETED`(또는 `VLM_FAILED`)로 잘못 전이된다. 발급 시각을 알 수 없는 구 원장 행은 종전대로 전부 대상(고착 방지 우선).

## 6.5 관련 데이터 (DB)

`LS_MARKING` (V45) — `EVNT_NM`(이벤트명), `MARK_MODE_CD`(AUTO/MANUAL), `FRME_INTV_NOCS`(프레임 간격), `MARK_CN`(marks JSON), `STTS_CD`(상태), **`VRFC_EVNT_QSTN_SN`(작업자가 고른 검증 이벤트 질문)**, **`VRFC_EVNT_TYPE_CD`(작업자가 고른 검증 이벤트 유형 — `varchar(20)` nullable, **V35** 신설)**, 부분 유니크 인덱스 `UK_LS_MARKING_RAW_ACTVTN`(V142 — 활성 마킹 1건). → [18](18-database.md).

- ⚠ **`VRFC_EVNT_TYPE_CD` 는 nullable 이며 그것이 확정 사양이다** — 화면에서 「필수」인 것은 **선택을 노출한 영상**에 한하고, 관제 값이 있는 영상은 이 칸을 비운 채 마킹한다(§6.3-2).
- ⚠ 이 칸을 **관제 인입 원장(`LS_DATA_INGEST`)에 쓰지 않는다** — 그 표는 관제가 직접 INSERT 하는 수신 원장이라 불변이다. 우리 선택값은 우리 원장에 둔다.
