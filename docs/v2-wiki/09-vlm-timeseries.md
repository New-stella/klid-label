## 9.1 범위 — 연동만

- **VLM 모델 본체(학습·파인튜닝·프롬프트 관리)는 외부 시스템 책임** (범위 외)
- 저작도구는 **외부 VLM 서비스를 호출해 시계열 정보를 획득하는 연동**만 보유
- 외부 벤더 = **IntelliVIX Video VLM API** (확정 계약 v2.0.1). 아래 §9.5 참조
- `ai-server/app/routers/vlm.py`(`POST /infer/vlm/verify-objects`)는 **내부 객체검증**용으로 이 외부 벤더와 무관(별개 경로, 현재 mock)

## 9.2 연동 흐름

```
[배치] BatchOrchestrator → VlmTimeseriesStep
   ① 사전조건 — 검증이벤트유형(LS_DATA_INGEST.VRFC_EVNT_TYPE_CD) 조달·정규화 (판정 아님)
                ※ 없거나 목록 밖이어도 그대로 실어 위탁한다 — 수용 여부는 벤더 응답이 정한다
                ※ 값을 지어내지는 않는다(미조달이면 null 전송 → 벤더 4xx → 확정 실패로 기록)
   ② 선커밋 — 상관키 등록(LS_WEBHOOK_IDEMPOTENCY = ISSUED) + 마킹 PENDING→VLM_REQUESTED
                ※ 둘 다 REQUIRES_NEW 독립 커밋. 제출 <앞>에 수행한다
   ③ 논블로킹 이중 제출 — 두 창구에 각각 subscribe 만 하고 즉시 반환(status="submitted")
                POST /v1/videovlm-klid/describe      (묘사 — 서술 전문 축)
                POST /v1/videovlm-klid/describe-sub  (추가 질문 — 어노테이션 초안 축)
                ※ 창구마다 별개 request_id + 원장 채널(VLM / VLM_SUB). ACK 왕복도 기다리지 않는다
   ④ 완료 핸들러 VlmSubmitOutcomeRecorder (전용 풀 vlmSubmitScheduler)
        ACK 수신  → 원장 ISSUED→ACCEPTED + LS_BATCH_PROC_LOG 기록
        제출 실패 → VLM/SKIPPED(사유) 기록 후 재개 대기  ※ 배치·작업 상태는 강등하지 않는다
        ↓ 상세 결과는 별도 콜백
[콜백] POST /v1/vlm/callback   (results = 단일 객체 {description})
   → 원장 채널로 어느 창구의 결과인지 역조회 (콜백 바디에 창구 구분자가 없다)
       VLM     → LS_DATA_META 원자 upsert(vlm.description) + 검수큐 진입 (§9.4-1)
       VLM_SUB → 이벤트 어노테이션 캡션 본문 초안 채움 (§9.4-2)
       VLM     → (같은 축) 「상황」 줄 파싱 → 캡션 후보 c1 의 사고 단계 1단계 (§9.4-2)
   → 마킹 ACTIVE(PENDING|VLM_REQUESTED) → VLM_COMPLETED  ※ 판정 축은 묘사 창구다
```

- 마킹 정보는 **`frame_policy` 로만** 반영된다 → [06](06-marking.md). `rawSn`·`eventName`·`marks` 배열은 규격 밖이라 요청 바디에 싣지 않는다
- **판정 창구(`/verify`)는 연동하지 않는다** — 그 창구만 제공하는 발생 여부·일치도는 우리 확정 경로 어디에도 쓰이지 않는다. 되살리지 말 것
- 코드: `VlmClient`, `VlmTimeseriesStep`/`VlmSubmitOutcomeRecorder`, `batch/vlm/{VlmSubmitPendingSweeper,VlmSubmitReclaimTxService}`, `webhook/VlmResultController`/`VlmResultService`

### 9.2-0 `frame_policy` 도출 규칙 (마킹 → 요청)

판정 단일 원천은 `VlmTimeseriesStep.buildRequest` 다. 화면·다른 스텝이 재유도하지 않는다.

| 마킹 | `mode` | `selected_frames` |
|------|--------|-------------------|
| 마킹 본문에서 얻은 프레임 ≥1 (**수동·자동 모두**) | `frame_selected` | 마킹 프레임 인덱스를 **정렬·중복제거·음수 제거**, 상한 **600** 초과분 절단 |
| 마킹 없음 · 쓸 프레임 0건 | `frame_interval` | (없음 — 간격은 서버가 정한다) |

- ★ **프레임은 항상 우리가 골라 목록으로 싣는다.** 마킹 모드는 그 인덱스를 **누가 골랐는지**만 가른다 — 수동이면 작업자가 지정한 프레임, 자동이면 간격으로 자동 선택된 프레임이다. 어느 쪽이든 마킹 본문에 인덱스가 들어 있으므로 도출 방법은 같다.
- ★ **`framerate` 는 싣지 않는다 (구 규격에서 폐기).** 규격 §2.5 는 **mode 만 연동 시스템이 지정하고 간격·장수 세부값은 서버가 관리한다**고 못 박으며 `frame_policy` 에 그 필드 자체가 없다.
  - ⚠ **구 서술 폐기**: *"`framerate` 는 몇 프레임당 1장(추출 간격)이라 자동 마킹의 `FRME_INTV_NOCS` 를 싣는다 · mode 무관 필수 · 0 이면 422 · 상한 없음"* 은 v2.0.1 판정 창구 규격의 것이며 **더 이상 우리 계약이 아니다.** 되살리면 정의되지 않은 필드가 실린다.
  - ⚠ **`LS_MARKING.FRME_INTV_NOCS` 자체는 그대로 쓰인다** — 자동 마킹이 프레임을 고르는 우리 쪽 설정값이다. 폐기된 것은 그 값을 **위탁 바디에 싣는 것**이지 그 컬럼이 아니다.
- **상한 600** — 규격 §2.5·§2.9. 초과하면 벤더가 400 을 내므로 우리가 먼저 자른다(구 상한 8 폐기).
- 마킹 JSON(`MARK_CN`) 파싱 실패·프레임 0건은 **예외가 아니라 `frame_interval` 폴백**(fail-secure)이고 WARN 을 남긴다. 빈 `selected_frames` 는 규격 위반이라 그 경우에만 내린다. 요청 조립은 **선커밋 이전**에 끝낸다 — 선커밋 뒤에서 터지면 파이프라인 FAILED + 전량 재실행이 되고 재개 경로(@Async)는 예외가 삼켜져 상관키만 남은 영구 대기가 된다.

### 9.2-1 URL 검증 정책 (스킴·형식만 본다)

- ★ **전 프로파일 동일 — `vlm.client.url` 은 스킴(`http`/`https`)과 형식만 본다 (2026-08-10 확정, 구속).** 평문 http·사설 대역·loopback 이 **운영에서도 통과**한다. 실 연동은 배포 기본값·노드 양쪽 모두 평문 http 이며, https 주소도 그대로 동작하므로 나중에 TLS 로 전환할 때 코드 변경이 없다.
- ⚠ **구 서술 폐기(2026-09-01)** — *"기본(운영)은 HTTPS 전용 + 사설·내부 대역 차단"*, *"개발 완화 `vlm.client.allow-insecure-url=true` 일 때만 평문 http 허용, 그 밖의 프로파일에서 켜면 기동 실패"*. **HTTPS 강제·대역 차단·프로파일 게이팅·완화 플래그가 모두 폐기**됐다(그 플래그는 켜든 끄든 결과가 같은 죽은 설정이 되어 설정 파일·환경 템플릿에서 제거). 되살리면 **운영에 평문 http 주소를 넣는 순간 기동이 막힌다.**
- **계속 차단하는 것**: 빈값·파싱 불가, `http`/`https` 외 스킴, placeholder/예제 호스트, 그리고 **정상 위탁 대상이 될 수 없는 예약 대역**(클라우드 메타데이터·링크로컬·ULA·CGNAT·멀티캐스트 등). 사설(RFC1918)·loopback 은 여기에 포함되지 않는다.
- ★ **원장에서 고른 노드 주소도 같은 정책을 거친다 (2026-09-01)** — `AiSrvrSelector` 가 후보를 고를 때 **같은 정책 객체**를 부르고, 통과하지 못한 장비는 후보에서 빠진다(경고에는 식별자만 남긴다). 그 축에는 운영자 입력 검증 입구가 없어 이 지점이 유일한 판정이며, 판정 실패는 **「그 장비 제외」이지 「위탁 실패」가 아니다**.
- ★ **이 정책이 판정하는 것은 기동 시점의 배포 기본값(과 위 노드 주소)뿐이다 (2026-08-10)** — R11 로 운영 화면에서 이 주소를 바꾸면 그 override 값은 `IntegrationEndpointUrlValidator` 만 거친다(스킴·형식 + **userinfo 금지**). 이 동작은 회귀 가드로 고정돼 있다(`TC-ENDP-021`).
- 판정 로직은 KPST 비식별 연동과 **같은 축**(`ExternalUrlPolicy.internalNetwork`)이다 → [22](22-deid-solution-api.md).

### 9.2-2 단계 미수행(skip) 기록

- VLM 단계를 건너뛰면 `LS_BATCH_PROC_LOG` 에 `PROC_STEP_CD='VLM'` / `PROC_STTS_CD='SKIPPED'` 감사 행 1건을 **사유와 함께**(`ERR_MSG_CN`) 남긴다.
- ⚠ **구 서술 폐기(2026-08-19 — `ADR-049`)** — *"`vlm.client.enabled=false` 로 건너뛴다"* 는 사실과 다르다. **설정 토글은 폐지**됐고, 건너뛰는 유일한 길은 **사람이 사유를 남기고 누르는 수동 스킵**이다(단건 `API-198`/`API-200`/`API-201` · 일괄 `API-212`/`API-213`/`API-214`). 설정으로 조용히 꺼지는 경로가 사라졌으므로 **누가 언제 왜 건너뛰었는지가 항상 남는다**.
- ★★**운영 지침 — 벤더 미연동 구간에는 「먼저 스킵」이 필수다.** (2026-08-21 보강 — 영상마다 누르지 않고 **전체 설정**으로 한 번에 세울 수 있다 → 아래 [9.2-2b](#922b-전체-건너뛰기-설정-2026-08-21--adr-050)) 토글이 없으므로 미연동 상태로 그냥 돌리면 위탁이 **실패**하고 마킹이 `VLM_REQUESTED → VLM_FAILED`(**종결 상태**)로 간다. 마킹 전이는 `PENDING` 에서만 일어나므로(`LsMarking(markVlmRequested)`) 나중에 벤더가 붙어 재수행해도 **마킹 표시는 실패로 남는다**. ⚠ 단 **차단은 아니다** — 시계열 메타 적재·검수큐 진입·승인 영상 재검수·산출물 재생성은 마킹 상태와 무관하게 정상 동작한다(`VlmResultService`). 즉 「먼저 스킵」은 표시 정확도를 위한 권장 동선이지, 안 지켰다고 시계열을 영영 못 받는 것은 아니다.
- 이 감사 행은 append-only 이며 진행 상태 조회에서 제외되므로 다음 단계 전이에 덮이지 않는다 — VLM 비활성/장애 구간에 처리된 영상을 DB 만으로 재처리 대상으로 식별할 수 있다.

**미수행 사유 카탈로그** (`VlmTimeseriesStep` 상수 — 값은 **재개 배선의 키**라 바꾸면 재개가 끊긴다)

| 사유 | 발생 시점 | 재개 대상 |
|------|----------|:--------:|
| ~~VLM 위탁 비활성 (`vlm.client.enabled=false`)~~ | ~~스텝 진입 즉시 NO-OP~~ | ✕ | **폐기(2026-08-19 — `ADR-049`)** — 토글이 사라져 **신규 발생이 없다**. 상수(`VlmTimeseriesStep(SKIP_REASON_DISABLED)`)는 이미 적재된 과거 행의 판독 키라 **존치**하며 값·문구를 바꾸지 않는다 |
| **수동 스킵** — 사람이 사유를 남기고 건너뜀 | 스텝 진입 직전 게이트(`BatchStatusService(isBundleManuallySkipped)`) | ✕ (해제 후 재수행이 담당) |
| **전체 설정 건너뛰기** — 설정 스위치가 세운 자동 표식 | 시계열 단계 **진입 직전**(`VlmDefaultSkipMarker`) | ✕ (해제 후 재수행이 담당) | 표식 축은 수동 스킵과 **같다**(`ERR_CD='MANUAL_SKIP'`). 사유 접두만 `[전체 설정 건너뛰기] ` 로 갈린다 → [9.2-2b](#922b-전체-건너뛰기-설정-2026-08-21--adr-050) |
| 비식별 누락 신고 구간 — 위탁 보류(재비식별 대기) | 외부 전송 직전 게이트 | ○ |
| ~~**검증이벤트유형 미수신** (`VRFC_EVNT_TYPE_CD` null)~~ | ~~사전조건 판정~~ | ○ | **폐기(2026-08-06)** — 이제 그대로 위탁한다. 상수는 과거 행 판독·재개용으로 존치 |
| ~~**검증이벤트유형 미지원**(허용목록 6종 밖)~~ | ~~사전조건 판정~~ | ○ | **폐기(2026-08-06)** — 동일 |
| **비동기 제출 실패** — 재개 대기 | 완료 핸들러 `onError` | ○ |
| **수락 응답·콜백 미수신** — 미결 회수 후 재개 | 스위퍼 **ACK 창** 만료 | ○ |
| **결과 콜백 미수신** — 콜백 창 만료 회수 후 재개 | 스위퍼 **콜백 창** 만료 | ○ |

> ⚠ 사유 **문자열 값**에는 아직 `describe` 라는 낱말이 남아 있다(예: `VLM describe 비동기 제출 실패 — 재개 대기`).
> 이 값은 `LS_BATCH_PROC_LOG.ERR_MSG_CN` 에 **적재된 뒤 재개 판정의 키로 다시 읽히므로**, 문구를 다듬으면
> 이미 쌓인 행이 `RESUMABLE_SKIP_REASONS` 매칭에서 탈락해 **재개가 끊긴다**. 의도적으로 그대로 둔 레거시 값이다.

- 재개 판정의 단일 원천은 `VlmTimeseriesStep.RESUMABLE_SKIP_REASONS` 이며, 재개는 `VlmWithheldResumeRunner` 가 **멱등 조건(시계열 메타 0건)** 으로 수행한다.
- ★**REVIEWER 수동 스킵은 이 카탈로그의 축이 아니다 (2026-08-12)** — 사람이 「건너뛰기」로 세운 표식은 같은 `SKIPPED` 상태값을 쓰되 **전용 `ERR_CD`(`MANUAL_SKIP`)와 강제 사유 접두(`[수동 스킵] `)** 를 갖는다. 위 재개 사유 상수를 재사용하면 훗날 비식별 신고 해소 이벤트가 그 행을 집어 **사람의 결정을 몰래 뒤집고 외부 벤더로 다시 위탁**한다. 재개 판정이 사유 **정확 일치**이므로 접두만으로 충돌이 구조적으로 불가능해지며, 사용자가 재개 사유 문자열을 그대로 입력해도 걸리지 않는다. 스킵 게이트는 **전송 직전(`VlmTimeseriesStep`) + 오케스트레이터 루프** 두 곳에 있고, 전자가 필요한 이유는 재개 러너가 이 스텝을 **직접 부르는 public 진입점**이기 때문이다. 수동 스킵으로 건너뛴 실행은 **보류 기록을 남기지 않는다**(표식이 이미 사유·행위자를 갖고 있고, 재기동마다 행을 덧붙이면 감사 테이블이 무한히 커진다) → [07 §7.5-1](07-batch-pipeline.md)
- 제출 실패를 배치 재시도 큐로 넘기지 않는 이유: 재시도 큐는 rawSn 단위로 파이프라인 **전체**를 재실행하므로, VLM 제출 1건 실패에 프레임추출·YOLO·SAM2 가 전부 다시 돈다.

### 9.2-2a 되돌리기와 재수행 — 일괄 축 · 승인 이력 예외 (2026-08-19 · `ADR-049`)

토글이 폐지되면서 **건너뛰기는 사람의 결정**이 됐고, 그 결정을 해제하는 길도 함께 제공된다.
「막는 조작에는 반드시 되돌리는 길을 함께 둔다」는 이 저장소의 관례를 따른다.

| 축 | 단건 | 일괄 (신설) |
|---|---|---|
| 스킵 | `API-198` `POST /v1/videos/{rawSn}/batch/stages/{stage}/skip` | **`API-212`** `POST /v1/videos/batch/stages/{stage}/skip` |
| 해제 | `API-200` `DELETE /v1/videos/{rawSn}/batch/stages/{stage}/skip` | **`API-213`** `DELETE /v1/videos/batch/stages/{stage}/skip` |
| 재수행 | `API-201` `POST /v1/videos/{rawSn}/batch/stages/{stage}/rerun` | **`API-214`** `POST /v1/videos/batch/stages/{stage}/rerun` |

- **일괄 축의 대상 묶음은 `VLM` 하나다.** 오토라벨을 일괄로 열면 산출물 품질 축을 사람이 **대량으로** 건너뛸 수 있게 되므로 열지 않았다. **단건 경로는 종전대로 두 묶음을 모두 받는다.**
- 일괄 계약은 기존 배치 일괄 재처리(`API-199`)를 그대로 따른다 — **상한 100 · 중복 1건 취급 · 요청 순서 보존 · 건별 사유 부분 성공**. **한 건도 처리되지 못해도 200** 이며 판정은 결과 목록으로 한다(건별 거부 사유를 상태 코드로 올리면 응답이 영상 상태를 알려주는 오라클이 된다).
- 스킵 사유는 **요청당 하나**를 받아 대상 전건에 같은 값으로 기록한다(영상마다 다른 사유를 받으면 일괄로 처리할 이유가 사라진다).
- ★★**「이미 건너뜀」·「건너뛴 상태 아님」은 실패가 아니라 성공이다** — 단건과 판정·기록 규칙이 같기 때문이다(스킵은 **append-only 로 항상 성공**하고 — 사유가 바뀌었을 수 있고 그 변경 이력 자체가 감사 대상이다 — 해제는 **멱등 no-op 성공**이다). ⇒ 일괄 축의 건별 실패는 **영상 없음 · 파생영상 · 예상 밖 오류**에서만 난다. ⚠ `API-212`/`API-213` 의 **example** 은 그 둘을 실패 사유로 보여주지만 두 ITEM 의 **본문 규범**이 「단건과 같다」이므로 **규범을 따르고 example 을 드리프트로 판정**했다 — example 대로 사전 조회 가드를 넣으면 같은 조건에서 단건과 일괄이 갈리는 비대칭이 새로 생긴다. 판단 근거는 `BatchStageBulkService` 클래스 javadoc 「D1」 절이며 **되돌리지 말 것**(설계 쪽 example 정정이 후속이다).
- **해제만으로는 시계열이 채워지지 않는다** — 실제 재수행은 rerun 이 담당하며, **건너뛰기를 해제한(clear 한) 묶음만** 수락한다(임의 지목으로 앞 작업을 건너뛴 산출물이 만들어지는 것을 막는다).
- 재수행은 **건너뛰기를 해제한 묶음의 구성원만 켜고 나머지 단계는 끈다**(`BatchBundleTogglePolicy`) — 프레임과 라벨을 다시 만들지 않으므로 **사람이 손댄 라벨이 지워지지 않는다.**
- **재수행이 실패해도 영상 상태를 훼손하지 않는다** — 선점 직전으로 복원하고 자동 재시도 큐에도 넣지 않는다. 스킵의 존재 이유가 「기다려도 성공하지 않는 작업」이라 해제해 재수행하면 **실패가 기대값**이기 때문이다. ⇒ **벤더 미연동 상태에서 눌러도 안전하다.**

#### ★승인 이력 예외 — 시계열 묶음만 (`API-201` · 구속)

한 번이라도 검수가 완료된 영상은 원래 재수행을 받지 않는다(**400**, 영구 조건). 그런데 **시계열 묶음은 예외로 받는다.**

- **왜 성립하나**: 시계열 재수행은 **확정된 라벨을 되돌리지 않고 메타만 더한다**. 들어온 서술은 승인 완료 영상의 서술이 갱신되면 재검수를 강제하는 규칙(`VlmResultService(recheckIfApproved)`)이 받아 검토 대기로 되돌리고 산출물 재생성·관제 재통지를 건다. **값이 같으면 no-op**(멱등).
- **왜 필요한가**: 벤더 연동이 늦어져 건너뛴 영상이 그대로 승인되더라도 시계열을 **나중에 받을 수 있어야** 한다. 이 예외가 없으면 그 영상은 시계열이 영구 결손된다.
- ⚠ **`AUTOLABEL` 은 예외 대상이 아니다** — 라벨을 다시 만들어 승인 시점 스냅샷과 어긋난다. 판정 지점은 `BatchStageRerunService` 한 곳이며 두 축을 함께 열지 말 것.
- ★★**예외는 「차단하지 않는다」이지 「작업 상태를 전이한다」가 아니다 (2026-08-20 · 구속)** — 승인 영상의 시계열 재수행은 검수 축(`LS_RAW_DATA_STATUS`)을 **전이하지 않는다.** 전이는 종전과 같은 조건부 UPDATE 를 타고 검수 소유 상태면 0행 no-op 이므로 `APPROVED` 가 보존되고, 그래야 데이터마트 뷰(`V_COMPLETED_*`)에서 이탈하지 않는다(구속 정책 「검수 완료·통지 건에 대한 관제 접근은 무조건 보장」).
- ★★**그 대신 배치 축(`LS_DATA_RAW`)은 반드시 마감해야 한다** — 기존 마감 경로는 작업 상태 전이가 막히면 **배치 단계도 건드리지 않고 반환**한다(두 테이블을 함께 멈추는 계약). 승인 영상은 항상 그 조건이라, 진입만 열면 **완주해도 배치 단계가 `PROCESSING` 에 영구 고착**되어 이후 모든 배치 진입이 409 가 되고 고착 회수 스윕도 회수를 포기한다. ⇒ **작업 상태는 보존하면서 배치 단계는 마감하는 전용 경로**가 짝으로 있어야 성립한다. **진입 게이트만 여는 수정은 거부보다 나쁘다.**
- ⚠ **면제 대상은 allowlist 로 선언한다** — `묶음 != 오토라벨` 같은 denylist 로 두면 **새 묶음이 추가되는 순간 자동으로 면제**받는다(fail-open). 판정 단일 지점은 `MetadataOnlyRerunPolicy` 이며, 오케스트레이터가 단계를 돌리기 전에 **실행 범위를 한 번 더 확인**해 시계열 외 단계가 켜져 있으면 아무것도 돌리지 않는다(2겹).
- ⚠ 이 예외로 재검수 강제 규칙의 **발동 경로가 하나 늘었다**(사람이 눌러야만 발동 · 건너뛰기를 해제한 묶음만 수락 · 멱등이라 폭주하지 않는다). 자동 트리거(재개 러너 · 미결 스위퍼 · 수동 재처리)가 막혀 있다는 기존 서술은 그대로 유효하다.

### 9.2-2b 전체 건너뛰기 설정 (2026-08-21 · `ADR-050`)

`ADR-050` 이 시계열 위탁 건너뛰기의 입구를 **둘로 한정**했다 — **① 전체 설정** · **② 실패 후 판단**.
이 절은 그중 **① 전체 설정**이다. 영상 5,000건 규모에서 「먼저 스킵」을 영상마다 누르게 하면
운영이 성립하지 않으므로, 스위치 하나로 그 결정을 미리 세워 둔다.

| 설정 키 | 타입 | 뜻 |
|---|---|---|
| `batch.vlm.skip-by-default` | `BOOLEAN` | 켜면 시계열 위탁을 기본으로 건너뛴다 |
| `batch.vlm.skip-by-default-reason` | `STRING` | 그 결정의 사유(표식에 함께 실린다) |

- **동작** — 스위치가 켜져 있으면 배치가 시계열 위탁 단계에 **진입하기 직전** 그 영상의 시계열 묶음에 건너뜀 표식을 세운다(`VlmDefaultSkipMarker`). 그 뒤는 **기존 스킵 게이트**가 그대로 처리하므로 **새 게이트를 만들지 않는다**. ⇒ 외부 벤더 호출은 **한 번도 일어나지 않는다** — 위탁했다가 실패시키는 것이 아니다(실패로 기록하면 재개 대상 사유에 걸려 나중에 몰래 재위탁될 수 있다).
- ★★**표식은 「위탁으로 나가는 모든 길」에서 세워진다 (2026-08-21 보강 — 구 「오케스트레이터 한 곳」 서술 폐기)** — 위탁 진입점은 오케스트레이터 하나가 아니다. `VlmWithheldResumeRunner` 가 `VlmTimeseriesStep(run·runWithMarking)` 을 **직접** 부르고, 그 러너는 **비식별 신고 해소 이벤트**(`VlmResumeBridge`)와 **주기 미결 스위퍼**(`VlmSubmitPendingSweeper` — 사람 개입 0)에서 도달한다. 오케스트레이터에만 표식을 세우면 그 경로에는 표식을 세우는 자가 없어 스킵 게이트가 **항상 통과**하고, 스위치가 켜져 있는데도 **외부 벤더가 호출된다**(위 「외부 호출 0건」이 무너진다).
  - **그래서 표식 적용을 전송 코드와 같은 메서드**(`VlmTimeseriesStep(doSubmit)`)**에 둔다** — 어떤 호출자도 우회할 수 없다(비식별 신고 게이트·수동 스킵 게이트를 그 메서드에 둔 것과 같은 논리). 오케스트레이터 쪽 적용은 **그대로 유지**한다: 거기서 표식이 서야 루프가 그 단계를 **실행하지 않고** 넘어간다(진행 행도 남기지 않는다). 두 지점은 멱등이라 표식이 두 번 쌓이지 않는다.
  - ⚠ **호출부마다 배선하는 방식으로 되돌리지 말 것** — 새 진입점이 생길 때마다 다시 샌다(실제로 그렇게 샜다). 구조는 정적 가드가 고정한다(`VlmDefaultSkipChokePointGuardTest` — 「표식이 게이트보다 앞 · 전송 지점이 하나이고 그 메서드 안에 표식이 있음 · 공개 진입점은 위임만」). 가드는 **호출부 개수를 세지 않는다**(숫자 단언은 진입점이 늘 때마다 낡아 사람이 숫자만 고치고 지나간다).
  - ⚠⚠ **표식 적재는 `REQUIRES_NEW` 여야 한다** — 그 자리는 `run` 의 **`readOnly=true` 트랜잭션 안**이라 `REQUIRED` 로 참여하면 Hibernate 가 `FlushMode.MANUAL` 이어서 **INSERT 가 flush 되지 않고 조용히 사라진다**. 그러면 직후 게이트 조회가 그 행을 찾지 못해 **외부 호출이 그대로 나간다**. 판정(설정 조회·표식 조회)은 호출자 트랜잭션에 참여하고 쓰기만 독립 커밋한다(`BatchStatusService(recordManualStageSkipInNewTx)` · 중첩 커넥션은 (영상 × 묶음)당 최대 한 번).
- ★**표식 축은 사람이 누른 것과 같다**(`ERR_CD='MANUAL_SKIP'`). 그 코드값은 **재개 판정의 키**라 새로 만들면 이미 적재된 과거 행의 배선이 끊긴다. 갈리는 것은 **사유 접두**(`[전체 설정 건너뛰기] `)뿐이며, 그것이 감사에서 「사람이 눌렀나 / 설정이 세웠나」를 구분한다. ⚠ `VlmTimeseriesStep.SKIP_REASON_*`(위탁 보류 사유) 축에는 **값을 추가하지 않는다** — 그 축은 재개 대상 판정이다.
- ★★**사람이 남긴 표식을 덮지 않는다** — 그 (영상 × 시계열 묶음)에 표식이 이미 있으면(건너뜀이든 **해제**든) 아무것도 하지 않는다. 특히 해제 표식을 덮으면 **사람이 되살린 영상이 조용히 다시 건너뛰어진다**. 판정은 기존 「(영상 × 묶음) 마지막 표식 행」 조회를 **재사용**하며, 이 성질이 곧 **멱등**이다(배치가 몇 번 진입해도 표식은 한 번만 쌓인다).
- **파이프라인은 멈추지 않는다** — 위탁 실패가 원래 파이프라인을 멈추지 않듯, 이 표식도 **파이프라인 제어 장치가 아니라** 「이 영상은 시계열 없이 확정한다」는 결정 표식이다. 프레임 추출·오토라벨링은 그대로 진행되고 파이프라인은 완주한다.
- **대상은 시계열 묶음 하나뿐** — 오토라벨은 산출물이 라벨이라 이 스위치의 대상이 아니다(일괄 축을 시계열로 한정한 것과 같은 근거).
- ★**사유 없이는 켤 수 없다** — 사유 값이 비어 있으면 스위치를 켜는 저장이 **400** 이다. 사람이 누르는 단건 건너뛰기가 사유를 필수로 두는 것과 **같은 축**이며, 건너뛴 이유가 남지 않으면 그 영상의 시계열이 왜 비어 있는지 되짚을 수 없다. **끄는 저장은 사유를 요구하지 않는다**(되돌리는 길을 막지 않는다).
  - ★**켜져 있는 동안에는 사유를 비울 수도 없다 (2026-08-21 보강)** — 켜는 검사는 **켜는 쓰기**만 보므로, 켠 뒤에 사유를 빈 값으로 저장하는 요청은 아무 판정도 만나지 않았다. 그러면 이후 자동 표식이 전부 「사유 미입력」로 남아 **건너뛴 이유를 되짚을 수 없다** — 위 규칙의 목적이 서버 축에서 절반만 달성된다. 화면이 막더라도 API 직접 호출로 열리므로 판정은 서버가 갖는다(`SystemConfigService(validateVlmSkipByDefaultReason)` — 400).
  - **끄고 나면 언제든 비울 수 있다**(되돌리는 길을 막지 않는다). ⇒ 화면은 **끌 때는 스위치를 먼저, 켤 때는 사유를 먼저** 저장해야 두 검사 사이에 갇히지 않는다. 순서가 어긋난 요청은 안전한 방향(거부)으로 떨어진다.
  - ★★**화면이 그 순서를 지키지 않아 활성화 정상 동선이 1회차에 실패하고 있었다** (2026-08-21 후속 · FE). 구 구현은 두 저장을 **스위치 먼저, 그것도 둘 다 기다리지 않고** 던졌다 — 서버가 읽는 것은 **커밋된** 값이라 사유 커밋이 늦으면 스위치가 400 으로 떨어졌고, 결과는 **사유만 저장되고 스위치는 꺼진 채** 남는 것이었다(사용자는 원인을 알 수 없는 실패만 본다). 이제 화면이 **켤 때는 사유 → 스위치, 끌 때는 스위치 → 사유** 순으로 **하나씩 기다려** 보내고, **앞이 실패하면 뒤를 보내지 않는다**(절반만 적용된 상태를 만들지 않는다).
    - ⚠ **순서만 맞추는 것으로는 부족하다 — 기다려야 한다.** 두 요청이 겹쳐 날아가면 도착 순서가 뒤집혀 같은 400 이 난다. 테스트에서도 이 축은 순서 단언으로 드러나지 않으므로(목이 즉시 응답해 「던진 순서 = 도착 순서」가 된다) 앞 요청을 붙잡아 두는 케이스를 따로 둔다.
    - ⚠ **다른 배치 설정(처리 주기·동시 처리 수)의 저장 동작은 바꾸지 않았다** — 서로 의존이 없어 순서가 무관하다.
- **시드하지 않는다** — 행이 없는 것이 정상이며 그때는 **꺼짐**이다. 그래서 두 키를 `ConfigKeys.DECLARED_TYPE` 에 등록해 최초 저장 시 행이 만들어지게 했다(연동 주소 4종과 같은 방식). **DB 마이그레이션은 없다.**
- ⚠ **폐지된 `vlm.client.enabled` 의 부활이 아니다.** 그 토글이 폐지된 이유는 「설정으로 **조용히** 꺼지고 그 사실이 산출물에도 이력에도 남지 않았다」였다. 이 스위치는 정반대로 **영상마다 사유가 담긴 감사 행을 남기고**, 그 행이 화면의 건너뛰기 표시·해제·재수행 축(`API-198`/`API-200`/`API-201` · 일괄 `API-212`~`API-214`)에 그대로 올라온다. ⇒ 되돌리는 길이 이미 있고, 누가 언제 왜 건너뛰었는지가 항상 남는다.
- **해제와 재수행은 종전 축 그대로다** — 벤더가 붙으면 스위치를 끄고, 이미 표식이 선 영상은 [9.2-2a](#922a-되돌리기와-재수행--일괄-축--승인-이력-예외-2026-08-19--adr-049) 의 **일괄 해제 → 일괄 재수행**으로 회수한다(승인 이력 영상도 시계열 묶음은 예외로 재수행을 받는다).

### 9.2-3 논블로킹 제출 · 미결 회수 (2026-07-30)

프로토콜은 원래부터 비동기였으나(ACK 만 받고 결과는 콜백) **ACK 왕복 동안 스레드를 점유**했다(`.block()`). 그 스레드는 `batch-async-`(core 2)·Quartz 워커·수동 재처리의 Tomcat 요청 스레드였다. 이제 **ACK 도 기다리지 않는다**.

- **선커밋이 제출 앞에 온다** — 상관키 등록(`ledger.recordIssued`)과 마킹 `PENDING→VLM_REQUESTED`(`VlmMarkingTxService`, REQUIRES_NEW)를 제출 **전에** 각각 독립 커밋한다. 콜백이 ACK 보다 먼저 도착해도 역조회·전이가 성립한다(**콜백 선행 레이스** 폐쇄).
- **수신부 조회 범위 확대(양단 방어)** — `VlmResultService` 가 전이 대상을 `VLM_REQUESTED` 단독에서 `LsMarking.ACTIVE_STATUSES`(PENDING + VLM_REQUESTED)로 넓혔다(`findByRawSnAndSttsCdIn`). 종결 상태(VLM_COMPLETED/VLM_FAILED)는 포함하지 않는다(역행 금지). 단 **위탁 발급 시각(원장 REG_DT) 이후에 새로 생성된 PENDING 마킹은 제외**한다 — 이전 위탁의 지각 콜백이 아직 위탁된 적 없는 새 마킹을 완료/실패로 만들지 않게 한다. 발급 시각을 알 수 없으면(구 원장 행) 종전대로 전부 대상.
- **완료 핸들러는 상태를 강등하지 않는다** — 제출 실패가 파이프라인 스레드 밖에서 오므로 `BatchOrchestrator` FAILED + 재시도 큐 사슬을 되살리지 않는다(rawSn 단위 전량 재실행이 되기 때문). 대신 `LS_BATCH_PROC_LOG` 에 `VLM/SKIPPED` + 사유를 남기고 재개(`VlmWithheldResumeRunner`, 멱등 조건 = 시계열 메타 0건)로 회수한다.
- **동기 실패 전파가 남는 것은 제출 이전 사전 조건뿐** — rawSn null · 영상 미존재 · 비식별 경로 부재 · 상관키 등록 실패.

**미결 회수 스위퍼 `VlmSubmitPendingSweeper`** — 노드 사망·재기동으로 in-flight subscription 이 사라지면 어떤 신호도 오지 않는다(실패 행이 없어 재시도 큐·회수기도 집지 못함). 이 스윕이 유일한 회수 경로이며 **창을 둘로 나눈다**.

| 창 | 원장 상태 | 임계(기본) | 회수 사유 코드 |
|----|:--------:|:---------:|---------------|
| **ACK 창** — 수락 응답조차 관측 못 함 | `ISSUED` | 30분(하한 clamp 10분) | `VLM describe 수락 응답·콜백 미수신 — 미결 회수 후 재개` |
| **콜백 창** — 수락은 받았고 결과만 안 옴 | `ACCEPTED` | 360분(하한 clamp 60분) | `VLM describe 결과 콜백 미수신 — 콜백 창 만료 회수 후 재개` |

- 두 창을 구분할 수 있는 근거는 완료 핸들러가 ACK 수신 시 원장을 `ISSUED → ACCEPTED` 로 전이하기 때문이다. 하나의 임계로 덮으면 분석 중(수십 분)인 정상 위탁을 뺏어 같은 비식별 영상을 중복 위탁한다.
- 2노드 Active-Active 정합은 **조건부 원자 UPDATE 클레임**(`VlmSubmitReclaimTxService.claim`/`claimAccepted`)이 담당한다 — Quartz 클러스터링은 트리거 중복만 막는다.
- 무한 재위탁 방지로 영상당 **회수 예산**(`max-reclaims`, 기본 3)을 두고 초과 시 기록만 남기고 재개하지 않는다. **상태 강등은 하지 않는다**.
- `@Scheduled` 가 아니라 **데몬 스레드 1개짜리 전용 스케줄러**로 돈다(`BatchRetryStaleReclaimSweeper`·`AugmentJobExpirySweeper` 동형) — 무조건적 `@EnableScheduling` 이 게이팅 없는 남의 잡까지 깨우는 것을 피한다. 자기 토글만 본다.

**설정 키** (전부 `application.yml` 미기재 — 코드 `@Value` 기본값. 필요 시 환경별 yml/환경변수로 override)

| 키 | 기본값 | 설명 |
|----|:-----:|------|
| `authoring.batch.vlm.submit-reclaim.enabled` | `true` | 미결 회수 스윕 on/off |
| `authoring.batch.vlm.submit-reclaim.interval-ms` | `900000` | 스윕 주기(하한 60,000ms) |
| `authoring.batch.vlm.submit-reclaim.initial-delay-ms` | `300000` | 기동 후 첫 스윕 지연 |
| `authoring.batch.vlm.submit-reclaim.stale-timeout-minutes` | `30` | **ACK 창** 임계(하한 10) |
| `authoring.batch.vlm.submit-reclaim.callback-timeout-minutes` | `360` | **콜백 창** 임계(하한 60) |
| `authoring.batch.vlm.submit-reclaim.batch-size` | `50` | tick 당 회수 상한(CWE-770) |
| `authoring.batch.vlm.submit-reclaim.max-reclaims` | `3` | 영상당 회수 예산 |

> 외부 호출 자체의 타임아웃은 `vlm.client.timeout-seconds`(기본 **10초**, WebClient `.timeout()` 단일 출처) + Resilience4j `vlmClient` 재시도(3회·1s·×2) / 서킷브레이커다. 논블로킹 전환 이후에도 이 값들은 그대로이며, 달라진 것은 **그 왕복을 어느 스레드도 기다리지 않는다**는 점이다.

**★ 이 패널은 텍스트 수정만 제공한다 — 승인/반려 UI 는 없다 (2026-08-03 사용자 확정, 구속)**

|------|------|

**★ 패널은 부류마다 다르게 렌더한다 (R8/R9 · 2026-08-27 이관 원문 추가)**

| 부류 | 예 | 화면 | 저장 payload |
|------|----|------|:------------:|
| **편집 슬롯** | `vlm.description`(서술 전문) · `manual-timeseries`(수동 등록) | 편집 가능 textarea(라벨 "시계열 서술" / "시계열 메타", `maxLength=2000`) | 편집한 것만 포함 |
| **레거시 구간행** | `0-8` · `8-16` … (구 describe 산출물) | **읽기 전용 병기** — 삭제·숨김하지 않는다 | 미포함 |
| ~~**읽기 전용 메타**~~ | `vlm.accuracy`(일치도) 등 BE `readOnlyMeta` | ★**표시하지 않는다**(2026-08-24 사용자 확정) — 판정 창구 미연동으로 새로 생기지 않고 남은 것은 과거 위탁분뿐이라 화면에서 뺐다. 구 동작(라벨 "일치도" + 백분율 환산)은 폐기 | 미포함 |
| **이관 원문** | `import.video.cctv_height` · `import.image.privacy_included` … BE `importedMeta` | ★**별도 참고 섹션 「이관 원문 정보」**(2026-08-27 신설) — 여섯 패널 **뒤**에 두고 **사람이 읽는 한글 이름**으로 표시한다. 이름을 정하지 못한 열쇠는 **버리지 않고 원문 열쇠 그대로**(조용한 손실 금지). 목록이 비면 **섹션째 감춘다**(이관이 아닌 영상에서는 그것이 정상) | 미포함(BE 가 400) |

- **편집 단위 = 저장 단위(`metaKey`)** — 여러 키를 하나의 textarea 로 합치지 않는다. 합치면 편집분을 키로 되돌릴 수 없어 **저장해도 아무것도 안 바뀌고 성공 토스트만 뜨는 조용한 무동작**이 된다(2026-08-03 실사고). 레거시 구간이 남은 영상이 있으므로 이 원칙은 계속 유효하다.
- **편집 여부는 알려진 키 화이트리스트**(`EDITABLE_META_KEYS`)로 판정하고 접두 문자열을 파싱하지 않는다 — BE `MetaService` 의 fail-closed 방향과 대칭이며, 새 자동 생성 키가 늘어도 편집 슬롯·저장 payload 로 새지 않는다.
- **레거시 구간은 BE 계약상 편집 가능**(`items`)하지만 화면이 편집 동선을 주지 않는다. 값 보존은 확정 정책이라 **표시는 반드시 유지**한다. 정렬은 `start_sec` **숫자** 오름차순 — 문자열 정렬이면 구간이 10개를 넘는 순간 `10-18` 이 `8-16` 앞으로 와 시간축이 깨진다.
- **편집 가능한 항목이 하나도 없으면**(메타 0건 / 레거시 구간뿐) 신규 등록 슬롯(`manual-timeseries`) 1개를 제공한다 — 레거시 영상에서도 전문을 작성할 수 있고, 그 저장이 레거시 구간 값을 덮지 않는다.
- **읽기 전용 목록은 미지의 키도 일반적으로 렌더**한다(BE 가 fail-closed 로 늘릴 수 있다). 라벨은 알려진 키만 한국어로 매핑하고 나머지는 내부 네임스페이스 접두(`vlm.`)만 떼어 표시한다 — 화면 문구에 모델명·기술 용어를 노출하지 않는다.
- ★ **검수 화면(`ReviewMetaPanel`)의 '참고 정보' 섹션도 함께 폐기**됐다 — 그 섹션의 유일한 항목이 일치도였다. 그 값만 있는 영상은 이제 **빈 상태 문구**가 뜬다(보여줄 메타가 정말로 없으므로 사실에 맞다).
  - ⚠ **BE 응답의 `readOnlyMeta` 목록과 어댑터 passthrough 는 그대로다** — 계약을 좁힌 것이 아니라 화면이 소비하지 않을 뿐이다. 되살리려면 화면 사양(SCREEN-005·SCREEN-019)부터 고쳐야 한다.
  - 라벨·값 포맷터(`readOnlyMetaLabel`·`formatReadOnlyMetaValue`)는 소비처가 0 이 되어 **제거**됐다.
- ★ **검수 화면의 '메타' 탭은 라벨링 메타 탭과 같은 구성이다** (2026-08-27 확정, 구속 · `SCREEN-019 v43`) —
  `촬영환경 → 개인정보(영상) → 프레임 설명 → 개인정보(프레임) → 시계열 메타 → 이벤트 어노테이션` 여섯
  섹션 뒤에 참고 정보로 **이관 원문 정보**(이관 영상만)와 **영상 정보**를 둔다. 각 섹션은 접을 수 있다.
  - **계기**: 구 구성은 3개뿐·역순이라 **작업자가 입력한 촬영환경·개인정보 판정(두 축)·프레임 설명을
    검수자가 확인할 경로가 아예 없었다.** 개인정보 3필드는 산출물의 원천이라 검수 없이 확정되면 안 된다.
  - **작업자 화면의 네 패널을 읽기 전용 모드로 재사용**하고 접이식 래퍼도 공유한다 — 검수 전용 표현을
    새로 만들면 같은 값이 두 벌로 갈려 한쪽만 갱신된다. 읽기 전용은 **비활성이 아니라 미렌더**다.
  - ⚠ **그 플래그의 기본값은 편집 가능**이어야 한다 — 기본값이 읽기 전용으로 새면 **작업자가 메타를
    입력하지 못한다.** 검수 화면만 명시적으로 켠다.
  - ★**검수 화면은 여전히 읽기 전용**이다(수정은 라벨링 화면, 확정은 검수 승인 시 동결). 다만 **구 단언
    「메타 패널에 버튼이 하나도 없다」는 폐기** — 사양이 섹션 접기를 요구하므로 토글 버튼은 반드시 있다.
  - ⚠ **BE 만 배포하면 회귀**였다 — 어댑터가 새 목록을 버리면 이관 영상의 메타가 **조용히 사라지고**
    (깨지는 게 아니라 안 보인다) 빈 상태 판정이 세 목록만 세어 "표시할 메타 정보가 없습니다"가 뜬다.
    변경 **전**에는 그 값이 틀린 분류로나마 보였으므로 그 축이 **악화**된다. 조회 분류·저장 거부·화면
    수용은 **세트로** 본다.
- 코드: FE `features/auto/metaKeys.ts`(판정 단일 원천) · `features/auto/api.ts`(`toFrameMeta`) · `features/label/components/TimeseriesSidePanel.tsx` · `features/review/components/ReviewMetaPanel.tsx` · `features/label/components/ImportedMetaPanel.tsx`(두 화면 공유) · `features/label/components/MetaSection.tsx`(접이식 래퍼·읽기 전용 행)

### 9.4-1 metaKey 규격 (묘사 콜백 적재)

`LS_DATA_META` 스키마는 **무변경**이다 — K/V + `(RAW_SN, META_KEY)` UK 가 아래를 그대로 수용한다.

★ **두 창구가 같은 키를 쓰지 않는다.** `(RAW_SN, META_KEY)` 가 UK 라 같은 키를 쓰면 한쪽이 유실된다 —
묘사는 아래 `vlm.description` 과 **이 표 밖의 이벤트 어노테이션**(사고 단계 1단계)을, 추가 질문은
**이 표 밖의 이벤트 어노테이션**(캡션 본문)을 채운다(§9.4-2).

| metaKey | 값 | 검수큐 진입 | 조회 응답 목록 | 수정(`PUT`) |
|---------|----|:----------:|------|------|
| `vlm.description` | 묘사 서술 전문(≤2000, `META_VL` 길이와 동일) | ✅ PENDING 1건 | `items` | 가능 |
| `vlm.accuracy` | 일치도 `0~1` 문자열. ★**과거 적재분 전용 — 새로 생기지 않고 화면에도 표시하지 않는다**(판정 창구 미연동) | ❌ | **`readOnlyMeta`**(응답에는 남지만 화면 미소비) | **400** |
| (레거시) `0-8`·`8-16` … | 구 describe 구간 서술 | 기존 유지 | `items` | 가능 |
| `manual-timeseries` | 편집 가능한 항목이 하나도 없는 영상(메타 0건 **또는 레거시 구간뿐**)의 FE 수동 등록 슬롯 — **사람이 직접 쓴 상황묘사 전문** | 신규 시 PENDING | `items` | 가능 |
| `video.*` | ffprobe/관제 인입 기술메타 (`VideoMetaService` 소유) | ❌ | `technicalMeta` | 400 |

**조회 응답 계약 — `GET /v1/frames/{srcSn}/meta` (2026-08-06)**

응답은 `items`(편집 가능) / `technicalMeta`(`video.*`) / `readOnlyMeta`(화면 전용 읽기) /
**`importedMeta`(2026-08-27 신설 — 이관 원문)** **네 목록**이며 넷 다 항상 배열이다(0건이면 빈 배열).
**기존 `items`·`technicalMeta` 및 각 항목 필드
(`metaSn`/`metaKey`/`metaVal`/`dataMetaReviewSn`/`reviewStatus`)의 이름·타입·시맨틱은 불변**이고
`readOnlyMeta`·`importedMeta` 가 **추가**됐을 뿐이다 — 단 `vlm.accuracy` 는 `items` 에서 빠진다(의도된 계약 변경).

**★`importedMeta` — 이관 원문 목록**(2026-08-27 신설 · `API-066 v7` · `SEQ-023 v8`)

외부 산출물 이관이 저작도구 스키마에 **착지할 컬럼이 없어 원문 보관한 값**이다(열쇠 접두 `import.`) —
좌표 · 위치 · 카메라 설치 높이 · 설치 방위 · 카메라 관리번호 · 데이터 출처 · 이벤트 기록 ·
이벤트 상위 계층 이름 · 외부 영상 식별자 · 원천 축 개인정보 판정. 항목 구조는 기존 세 목록과 **동일**하고,
이관으로 들어오지 않은 영상에서는 **빈 배열이 정상**이다.

- **왜 갈랐나** — 이관 원문은 **시계열 분석 결과가 아니다.** 분류 사슬이 `video.*` → `vlm.*` 순으로 보고
  **나머지를 전부 `items` 로** 떨구던 탓에, 이 값들이 「시계열 메타」로 분류돼 ①검토 대상이 아닌 값이
  검토 대상처럼 보이고 ②학습데이터 산출물의 상황묘사 조달이 그 값을 서술로 집을 여지가 생겼다.
- **저장은 `400`** 으로 거부된다. ⚠ **이것은 신설이다** — 그전까지 이 키는 **`200` 으로 수락되어 이관 원문이
  덮어써졌다.** 편집 불가 판정이 화이트리스트가 아니라 **`video.` · `vlm.` 두 접두 블랙리스트**라 `import.` 가
  양쪽을 빠져나갔기 때문이다(`EDITABLE_VLM_KEYS` 는 이름과 달리 **`vlm.` 네임스페이스 안으로 한정된**
  화이트리스트다).
  - ★**남는 규칙**: 이 저장소에서 「편집 불가」는 **블랙리스트**다. 새 키 네임스페이스를 도입하면
    **조회 분류에서는 여집합으로 새고 저장 경로에서는 아무 검사도 받지 않는다** — 조회만 고치면
    「화면엔 편집 칸이 없는데 임의 요청으로는 덮어써지는」 비대칭이 남고, 이관 원문의 경우 그 덮어쓰기는
    **되돌릴 수단이 없다.** **조회 분류와 저장 거부는 반드시 세트로 본다.**
- **분류의 소유자는 서버다** — 화면이 `import.` 접두를 파싱해 스스로 가르지 않는다. 접두를 화면에 다시
  선언하는 순간 두 번째 진실원이 된다.
- ⚠ **분기 순서는 이 사슬에서 동작을 지탱하지 않는다** — `video.` · `vlm.` · `import.` 세 접두가 **서로소**라
  순서를 바꿔도 어느 키의 소속도 달라지지 않는다(변이 실증으로 확인). 기존 판정 뒤에 두는 것은 **방어적
  관례**이며 *"순서를 바꾸면 X 가 깨진다"* 는 근거로 쓰지 말 것 — 검증자가 RED 를 기대했다가 GREEN 을 보고
  **가드 결함으로 오판**한다.

### 9.4-2 두 창구 결과의 어노테이션 적재 (초안)

**★ 2026-08-25 사업 담당 회신으로 적재 칸이 재확정됐다.** 구 서술(*"추가 질문 결과는 `answer` 축 초안으로
들어간다"*)은 **폐기**한다 — 그건 2026-08-24 확정이었고 **하루 만에 뒤집혔다.** 같은 축이 이틀 사이 두 번
뒤집혔으므로(캡션·CoT → 답변 → 다시 캡션·CoT) **세 번째로 되돌리지 말 것.**

| 어노테이션 칸 | 조달처 |
|---|---|
| `event.caption.c1.caption_text` | 추가 질문(describe-sub) 응답 서술 |
| `event.caption.c1.cot["1단계"]` | 묘사(describe) 전문에서 **「상황」 라벨 줄만** 파싱 |
| `event.question` | **저작도구가 보관하는 검증 이벤트 유형별 질문 문구**(`LS_VRFC_EVNT_QSTN`) |

- **「상황」 파싱**: 줄 단위로 훑어 그 라벨 줄을 찾고 값은 **그 줄의 줄바꿈까지**다. 다음 라벨 줄로
  이어붙이지 않는다. 줄이 없으면 **채우지 않는다**(빈 값도 넣지 않는다). 여러 번 나오면 첫 번째.
  ⚠ **라벨 목록에 의존하지 않는다** — 규격이 "장소·날씨·상황 등"이라고만 쓰고 전체 목록·순서·필수
  여부를 정의하지 않는다. 그 줄 하나만 찾는 방식이라야 사업자가 항목을 늘려도 안 깨진다.
- **CoT 는 1단계 키만** 만든다. 2단계 이후는 사람이 채울 공란이다.
- **질문 조달**: 마킹에서 고른 질문이 1순위, 없거나 그 유형 소속이 아니면 **그 유형의 첫 번째**.
  읽는 마킹 행은 **활성 마킹**이고 없으면 **최신 한 건**이다 — 두 창구의 도착 순서가 보장되지 않는데
  **마킹을 전이시키는 것은 묘사 축뿐**이라, 활성만 보면 도착 순서에 따라 기록되는 질문이 달라진다.
  ⚠ 질문 문장은 **사업자 응답에 실려 오지 않는다**(사업자 서버가 이벤트별로 관리). 그래서 우리가 보관한다.
  ⚠ **위탁 요청에 그 질문을 실을 자리가 아직 없어**, 첫 번째가 아닌 질문을 고르면 **기록된 질문과 사업자가
  실제로 쓴 질문이 달라진다** — 인지·수용한 위험이다.
- **채우지 않는 것**: `answer` · `evidence` · CoT 2단계 이후. 근거 서술은 자유 서술이라 쪼개려면 파싱이
  필요한데 규격 §5.3 이 파싱 의존을 금한다. `event_class` 는 관제 인입의 검증 이벤트 유형만 쓰고,
  그 값이 없으면 **행을 만들지 않는다**.
- **두 축이 같은 캡션 후보 `c1` 을 공유**하고 **도착 순서가 보장되지 않는다** — 나중 것이 먼저 것을 지우지
  않고 **자기 칸만** 채운다. 후보를 통째로 교체하는 구현은 금지다.
- **덮지 않는 경계**: 승인 이력이 있으면 손대지 않는다(이미 산출물로 나간 내용이다). 값이 이미 있으면
  손대지 않는다 — 사람이 쓴 값인지 앞선 자동 채움인지 구분할 수단이 없으므로 사람의 것으로 본다.
  어노테이션 검토가 종결됐으면 손대지 않는다. 같은 결과를 여러 번 받아도 두 번째부터는 아무것도 하지 않는다(멱등).
- **재검수를 발화시키지 않는다** — 재검수는 사람이 내용을 고쳤을 때의 축이며, 초안이 처음 채워지는 것은
  그 축이 아니다.
- **길이 상한이 비대칭이다** — 사고 단계 칸 상한이 서술 전문 상한보다 작다. 「상황」 값이 그 상한을 넘으면
  **자르지 않고 CoT 채움만 건너뛴다**(주 축 보호).
- **실패 격리**: 초안 채움은 **묘사 축 트랜잭션 경계 밖**에서 돈다. 초안이 실패해도 시계열 서술 적재와
  원장 처리 완료 표시를 되돌리지 않는다. ⚠ 협력자가 자기 트랜잭션에 합류하면 예외가 바깥을 rollback-only
  로 만들어 **커밋 시점에 통째로 터진다** — 그래서 별도 트랜잭션 경계를 두고 그 **바깥**에서 잡는다.
- 코드: `webhook/service/TimeseriesResultApplier`(협력자 계약) · `webhook/service/IsolatedTimeseriesDraftApplier`(격리 경계)
  · `evntanno/service/EvntAnnoResultApplier`(구현) · `evntanno/service/DescriptionSituationExtractor`(「상황」 파서)
  · `evntanno/service/MarkingSelectedQuestionReader`(마킹 선택값 조달).

- **읽기 전용 판정은 `vlm.*` 네임스페이스 안의 화이트리스트**다 — `vlm.description` 만 편집 가능하고 그 밖의
  `vlm.*` 는 전부 읽기 전용(fail-closed). 판정 범위를 접두 안으로 한정하므로 **레거시 구간 키와
  `manual-timeseries` 는 영향을 받지 않고 계속 편집 가능**하다.
- **판정 술어의 소유자는 `MetaService` 하나**다(`video.*` 는 `VideoMetaService.isTechnicalKey`). 접두·키 문자열을
  DTO·컨트롤러·FE 로 복제하지 않는다 — 소유자가 키를 늘릴 때 조용히 드리프트한다.
- **저장 경로도 서버가 직접 막는다** — 조회에서 빼는 것에 의존하지 않는다(클라이언트가 임의 payload 를 보낼 수
  있다, CWE-20/915). 거부는 `video.*` 와 **같은 400**이며 메시지에 요청받은 키를 echo 하지 않는다(CWE-117/209).

- **FE 는 이 분류를 재해석하지 않는다** — 어댑터(`features/auto/api.ts` `toFrameMeta`)가 **네 목록**을 그대로 실어
  나르고(누락 응답은 빈 배열), 화면 렌더 규칙은 §9.3 참조. 편집 슬롯 판정만 FE 화이트리스트
  (`features/auto/metaKeys.ts`)가 별도로 갖는데, 이는 BE 판정을 복제한 것이 아니라 **BE 가 편집을 허용하는
  레거시 구간 키를 화면에서만 더 좁히는** 것이다(R9 보존 정책).

> ⚠ 구 서술 **"`vlm.accuracy` 도 편집·저장이 가능하다(거부 목록은 `video.*` 뿐)" 는 폐기**(2026-08-06).
>
> ⚠ 구 서술 **"남은 갭(FE — Phase 6): 어댑터가 `readOnlyMeta` 를 읽지 않아 일치도가 화면에서 사라진 상태" 는
> 해소**(2026-08-06 Phase 6 — 어댑터 수용 + 라벨링·검수 양 화면 읽기 전용 렌더).
>

> 않고, 남은 과거 위탁분을 화면에서 빼기로 사용자가 확정했다. **어댑터 수용은 그대로**이고(계약을
> 좁힌 것이 아니다) 화면만 소비하지 않는다. 두 시점을 혼동하지 말 것 — 2026-08-06 은 "안 보이던 것을
> 보이게" 였고 2026-08-24 는 "보이던 것을 도로 뺀" 것이며, 그 사이에 값의 성격이 바뀌었다.

**적재 (콜백 경로)**

- **콜백 적재 경로의 검수큐 진입은 화이트리스트**다 — `VlmResultService` 는 `vlm.description` 에만 검토행을 만든다. "description 이 아닌 건 전부 제외"가 fail-closed 라 향후 `vlm.*` 키가 늘어도 검수큐·데이터마트 뷰로 새지 않는다. ⚠ **사람이 `PUT` 으로 신규 등록하는 키(`manual-timeseries` 등)는 별개 경로**이며 `MetaService` 가 VLM 경로와 동일하게 PENDING 검토행을 만든다(위 표의 "신규 시 PENDING") — 두 경로를 하나로 읽지 말 것.
- 적재는 `LsDataMetaRepository.upsertMeta`(PostgreSQL `ON CONFLICT`) **원자 upsert** 다. 재위탁 동시 콜백은 `request_id` 가 달라 원장 비관적 락이 걸리지 않으므로 find-then-save 로는 UNIQUE 위반·값 유실이 난다(CWE-362).
- 레거시 구간 키는 metaKey 가 달라 UK 충돌이 없으므로 신규 2키가 그대로 **추가**된다.

**★ export 조달 (2026-08-06, @req R10)**: 학습데이터 export JSON 의 `video.vd_description` 은 **① `vlm.description` → ② `manual-timeseries`(사람이 직접 쓴 전문) → ③ 없으면 레거시 구간 행을 `start_sec` 오름차순 이어붙임 → ④ 없으면 `null`** 로 조달된다(판정 단일 원천 `VlmDescriptionPolicy`, 상세는 [24 §24.4.3](24-dataset-export.md)). `vlm.accuracy` 는 **export 에 넣지 않는다**(아래 R12).

> ⚠ **구 서술 "② 없으면 레거시 구간" (즉 `manual-timeseries` 는 조달 무관 키) 는 폐기**(2026-08-06). 위 표대로 그 슬롯은 **편집 가능한 항목이 하나도 없을 때** 뜨는데, 그 조건에는 **레거시 구간뿐인 영상도 포함**된다 — 구 조달은 사람이 방금 쓴 전문을 무시하고 **편집조차 불가능한 옛 구간 이어붙임**을 대신 내보냈다(조용한 손실).
>
> 그 결과 **`manual-timeseries` 수정도 export 재생성 대상**이다(`VlmDescriptionPolicy.participates` 가 참). 다만 조달 참여 키라도 **값이 실제로 바뀌어야** 재생성한다 — 무변경 저장이 `v2·v3·v4…` 를 적층하던 결함(CWE-770)의 차단이며, 무변경 저장 자체는 **200 성공 + 통지 발행**이고 재생성 플래그만 생략된다([24 §24.4.3](24-dataset-export.md)).

**★ R12 — `accuracy` 는 화면 전용이다 (구속)**

검수큐에 넣지 않으므로 `V_COMPLETED_META`(리뷰행 INNER JOIN + `RVW_STTS_CD='APPROVED'`)에 **구조적으로 도달하지 않는다**. 학습데이터 export JSON 에도 넣지 않는다. **이것은 의도된 설계이며 "마트에 안 나온다"를 결함으로 보고하거나 뷰를 고치지 않는다.**

> ⚠ **알려진 관찰(결함 아님) — 관제 pull API 는 다른 채널이다**: 관제가 통지 수신 후 호출하는 조회 API(`TaskQueryService.getMeta`)는 `LS_DATA_META` **전 행**을 반환해 `vlm.accuracy`·`video.*` 가 포함된다. R12 가 규정한 축은 **검수큐 → `V_COMPLETED_META` → export** 이고 이 pull 은 그 축이 아니며, `video.*` 도 이전부터 그랬다. 좁히려면 **관제 계약 협의가 선행**돼야 하므로 임의로 필터를 넣지 않는다.

**★ R13 — 승인 영상의 서술이 갱신되면 재검수 + 통지 (구속)**

검수 완료(`APPROVED`) 영상이 재위탁돼 `vlm.description` 이 **실제로 달라진 경우에만**:

1. 해당 검토행을 `PENDING` 으로 되돌려 재승인을 강제한다 (`LsDataMetaReview.reopenForRecheck`).
2. `TaskModifiedEvent(META_UPDATED, srcSn=null, **exportRegenerated=true**)` 를 발행한다 — 발행 방식·페이로드는 `MetaService.update` 와 동일하며 소비는 `TaskModifiedAccumulateListener`(AFTER_COMMIT)다.

> ⚠ 구 서술 **"`exportRegenerated=false`(디스크 산출물은 그대로)" 는 폐기**(2026-08-06, @req R10) — 서술이 export JSON 의 `video.vd_description` **입력**이 되면서 디스크가 실제로 달라진다. `false` 로 두면 통지만 나가고 산출 폴더는 **옛 서술로 고착**된다. 이 트리거는 콘텐츠 해시 편입(`LabelContentHasher` `VDSC` 블록)과 **정합 세트**이나, ⚠ **현재 배포 형상에서 실제로 일하는 쪽은 이 트리거 하나**다(해시는 `force=false` 진입 경로가 0건이라 아무것도 게이트하지 않는다 — [24 §24.4.3](24-dataset-export.md)). 무변경 폭주를 막는 것은 해시가 아니라 **값 비교 가드**(`applyResults` 의 `changed`)다.

- **근거**: 뷰가 **라이브** `LS_DATA_META` 를 조인하므로, 값만 갱신하고 상태를 `APPROVED` 로 두면 REVIEWER 가 한 번도 보지 않은 새 서술이 그대로 관제로 나간다. CLAUDE.md 의 "검수 완료 후 수정 시마다 `TASK_MODIFIED` 통지" 규칙도 이 경로만 위반하고 있었다.

## 9.5 외부 확정 계약 — KLID 연동 API v1.1.0

> 원문: `docs/연동규격서/video_vlm_klid_api_v1.1.0.pdf` (IntelliVIX, 2026-08-13 "이벤트 추가 질문(describe-sub) API 추가"). 비동기 콜백 모델.
> ⚠ **구 규격 `video_vlm_api_ v2.0.1.docx` 는 이 문서로 대체됐다** — 그쪽을 근거로 계약을 되돌리지 말 것.

**엔드포인트와 우리 사용**

| 기능 | Endpoint | 콜백 결과 항목 | 우리 사용 |
|------|----------|---------------|:--------:|
| 이벤트 묘사 | `POST /v1/videovlm-klid/describe` | `{description}` | **○ 시계열 서술 축** |
| 이벤트 추가 질문 | `POST /v1/videovlm-klid/describe-sub` | `{description}` | **○ 어노테이션 초안 축** |
| 지원 이벤트 조회 | `GET /v1/videovlm-klid/events` | `{version, events[], describe_events, describe_sub_events}` | ○ 위탁 전 확인 |
| 서버 상태 조회 | `GET /v1/videovlm-klid/status` | `{status(ready\|busy\|loading), queue, pending}` | ○ 위탁 전 관측 |
| 이벤트 판정 | `POST /v1/videovlm-klid/verify` | `{detected, accuracy, description}` | **✕ 연동하지 않는다** |

> **판정 창구를 쓰지 않는 이유**: 우리가 채우려는 두 자리(시계열 서술 전문 · 이벤트 어노테이션)는 둘 다
> 사람이 읽고 고쳐 검수 승인으로 확정하는 **자연어 서술**이다. 판정 수치는 화면 참고 표시 외에 쓰인 적이
> 없고 학습데이터 산출물에도 데이터마트 노출면에도 들어가지 않는다 — 받아도 쓰이지 않고 유지 비용만 남는다.
> 근거 결정은 ADR-051.

**요청 규격 (두 창구 공통, §2.3~§2.5)**: `{request_id, event_type, media:{type, source_type(path|upload), path, frame_policy:{mode(frame_interval|uniform|frame_selected), selected_frames≤600}}, callback_url}`.
접수 응답은 **HTTP 202** + `{request_id, status:"accepted"}` → 완료 후 `callback_url` 로 결과 POST.
실패 콜백은 `{request_id, status:"failed", error:"..."}` — ★**`error` 는 객체가 아니라 문자열**이다.
- ★ `frame_policy` 에 **`framerate` 필드가 없다** — mode 만 연동 시스템이 지정하고 간격·장수는 서버가 관리한다(§2.5)
- `event_type` 7종: `fire`·`smoke`·`fall`·`violence`·`flooding`·`car_accident`·`kidnapping`. **창구마다 사용 가능한 목록이 다를 수 있어** `GET /events` 의 `describe_events`/`describe_sub_events` 로 확인한다
- 판정 항목(`detected`·`accuracy`)은 **판정 창구 전용**이라 우리 두 창구에는 오지 않는다(§2.8)
- `source_type=upload` 은 파일당 4GB, `=path` 는 서버가 허용한 경로 하위만 접근 가능
- 인증 헤더는 규격서에 **미명시**

**오류 코드 (§2.9)** — 요청 시점에 판별 가능한 문제는 콜백이 아니라 HTTP 응답으로 즉시 온다.

| 코드 | 상황 | 우리 처리 |
|:---:|------|------|
| 400 | 필수 누락·형식 오류·미지원 `event_type`·미지원 mode·허용되지 않은 경로·`selected_frames` 600 초과 | **비재시도** |
| 415 | 지원하지 않는 Content-Type | **비재시도** |
| 429 | 서버 동시 처리 한도(32건) 초과 | ★**재시도 대상** — 잠시 뒤 다시 보내면 되는 일시 상태다 |
| 503 | 서버 미준비 | 재시도(5xx 기본 정책) |

분석 과정의 오류는 HTTP 가 아니라 **실패 콜백**으로 온다. **분석 제한 900초(15분)** 를 넘긴 경우도 여기 해당한다.

**연동 유의사항 (§5)**

- 콜백 수신 후 **5초 안에 2xx** 를 반환해야 한다. 늦거나 2xx 가 아니면 **최대 3회**(최초 1회 + 재시도 2회) 재전송된다
- **3회 모두 실패하면 결과는 유실된다 — 다시 받을 수 있는 조회 API 가 없다.** 그래서 콜백 수신부는 알 수 없는 항목이
  섞여 와도 400 을 내지 않는다(§9.4-1) — 되받을 수 없는 입구에서의 엄격함은 곧 손실이다
- 같은 `request_id` 의 콜백을 **여러 번 받을 수 있다** → 멱등 처리(원장이 담당)
- **요청 순서와 콜백 도착 순서는 일치하지 않는다** → `request_id` 로 대응시킨다
- 서술은 **자연어 평문이고 형식이 고정돼 있지 않다** → 문자열 파싱에 의존하는 로직을 두지 않는다
- 동일 `request_id` 중복 요청을 서버는 **별개 작업으로 처리**한다 → 중복 방지는 우리 책임이다
