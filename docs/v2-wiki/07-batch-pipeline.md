## 7.1 파이프라인 순서 (구현됨)

비식별 선두 재배치(R1 NFR-001 v1.5)가 **구현 완료**되었다. 단계 순서는 **선언적 파이프라인**으로 관리되며 두 시퀀스로 나뉜다.

```
[pre-marking 선두]  비식별화(전체 영상 무조건, 적재 직후 자동)
[마킹]              마킹(비식별 영상 대상, 자동/수동)
[post-marking 잔여] VLM 시계열(콜백 비동기)
                     → FFmpeg(마킹 위치 기반 원본+비식별 2벌 추출)
                     → YOLO(원본만) → SAM2 → 트랙 보간
```

- **순서 관리 단일 지점**: `batch/pipeline/BatchPipelineConfig` 의 `List.of(...)` 한 줄에서 단계 순서를 정의한다 — 재배치 시 오케스트레이터/스텝 구현은 손대지 않는다.
  - `preMarkingPipeline` = `[DEIDENTIFY]`
  - `postMarkingPipeline` = `[MARKING, VLM, FRAME_EXTRACT, YOLO, SAM2, INTERPOLATE]`
- 선언적 파이프라인 구성: `batch/pipeline/{BatchStep, BatchContext, BatchPipeline, BatchPipelineConfig}`. 각 `BatchStep` 은 `isEnabled(ctx)` 로 조건부 실행을 지원한다(dev 토글).

> 구 순서(`마킹(원본) → VLM → 비식별(PRVC/PSDO만) → 프레임추출 → 오토라벨링`)와 post-marking 단계 내 비식별은 **폐지**되었다.

## 7.2 오케스트레이션

- **선두 비식별 트리거(자동)**: 영상 적재(관리화면 TUS 업로드 + dev 경로) 직후 → `VideoIngestedEvent` → `IngestDeidentifyBridge`(`@TransactionalEventListener` AFTER_COMMIT) → `AsyncDeidentifyRunner`(@Async) → `DeidentifyStep.run` → 성공 시 `LsDataRaw.dataSttsCd = MARKING_READY` 전이(마킹 진입 허용). 비식별은 **ANONY 포함 전체 영상 무조건** 실행(게이팅 폐지).
- **잔여 배치 트리거**: 마킹 완료 → `MarkingCompletedEvent` → `MarkingBatchBridge`(AFTER_COMMIT) → `AsyncBatchRunner` → `BatchOrchestrator` @Async 시작. **deid 가드** — 마킹완료 시 `deIdntfYn='Y'` 가 아니면 잔여 배치를 트리거하지 않는다. + Quartz 스케줄(1건/분).
- **`BatchOrchestrator.process()`**: 시작 시 작업 상태 `→ PROCESSING`, 완료 시 작업 상태 `→ ASSIGNED 복귀`, 실패 `→ FAILED`. **두 테이블 책임 분리** — `LsDataRaw.dataSttsCd`(배치 단계: PENDING→MARKING_READY→COMPLETED)는 완료 시 `COMPLETED` 로 마감, `LsRawDataStatus.dataSttsCd`(작업/검수 워크플로우 상태)는 ASSIGNED 로 복귀시켜 라벨링/검수 플로우가 이어진다. 배치 완료가 작업 상태를 점프시키지 않는 이유는 그러면 검수 제출(ASSIGNED→PENDING)이 상태 머신에서 차단되기 때문이다. ⚠ **구 서술 폐기(2026-08-15 코드 실측)** — *"작업 상태 `COMPLETED` 는 검수 승인 시점에만 도달하는 종결 상태"* 는 **사실과 다르다**. 검수 종결값은 **`APPROVED`** 이고 `LsRawDataStatus.STTS_COMPLETED` 는 선언만 있을 뿐 `src/main` 사용처가 **0건**이다.
- **dev 경로 = 운영 시나리오 1:1 고정 플로우**(2026-06-16 단순화): dev 업로드(`/dev/upload`)는 `DevPipelineRunner.runAsync(rawSn)` 가 **선두 비식별(무조건, local mock) → `MARKING_READY` 까지만 수행하고 정지**한다. 단계 토글(FRAME/DEIDENT/YOLO/SAM2)·합성 마킹(createSyntheticMarking)·`manualMarking` 옵션·`DevPipelineRunner` 의 `BatchOrchestrator.process` 직접 호출은 **모두 제거**되었다. 이후 검수자가 마킹 화면에서 실제 마킹(자동/수동 모드)→완료하면 기존 `MarkingCompletedEvent → MarkingBatchBridge`(AFTER_COMMIT) 경로로만 잔여 배치가 진행된다. 비식별 실패 시 `MARKING_READY` 미전이(외부 수동 재비식별 정책) — 영상 목록에 그 상태가 노출된다. 제거된 엔드포인트: `POST /v1/dev/autolabel/run`·`run-full`. FE: 영상 업로드 화면(`/dev/upload`)은 체크박스 없이 업로드 후 "마킹 대기" 안내 + 마킹 화면 링크만 제공.

### 7.2-1 외부 위탁 제출은 모두 논블로킹 (2026-07-30)

세 외부 연동(**VLM 시계열 · KPST 비식별 · 생성형 AI 증강**)은 프로토콜이 원래부터 비동기였으나(결과는 콜백/폴링) **수락(ACK) 왕복 동안 스레드를 점유**했다(`.block()`). 그 스레드가 `batch-async-`(core 2 · CallerRuns)·Quartz 워커·Tomcat 요청 스레드였기 때문에, 벤더가 느려지면 배치 풀이 통째로 마르고 역압이 커밋 스레드까지 물고 늘어졌다. 이제 **ACK 도 기다리지 않는다** — 세 연동 모두 동일 골격을 쓴다.

| 축 | 규칙 |
|----|------|
| **선커밋** | 원장/상관키(+ VLM 은 마킹 전이)를 제출 **앞**에서 `REQUIRES_NEW` 로 독립 커밋 — ACK·콜백이 먼저 도착해도 기록 대상이 존재한다 |
| **제출** | `subscribe` 만 하고 즉시 반환. 활성 트랜잭션이 있으면 **커밋 후** 구독(KPST) |
| **완료 핸들러** | 연동별 **전용 executor**(core 1 / max 2 / queue 200 / **AbortPolicy**)에서 별도 빈(`REQUIRES_NEW`)이 ACK·실패를 기록. `batchAsyncExecutor` 재사용 금지 — CallerRuns 가 포화 시 **reactor-netty 이벤트 루프**에서 JPA 를 돌려 논블로킹 이득을 정확히 되돌린다 |
| **디스패치** | 완료 신호는 `publishOn` 이 아니라 `common.async.SubmitSignalDispatch` 로 전용 풀에 **명시 투입**(VLM·KPST). 풀 거부는 "기록 유실"이지 "위탁 유실"이 아니다 — 선커밋 행이 남아 회수기가 받는다 |
| **회수** | 무신호 건은 각 연동의 기존 회수기가 집는다: VLM=`VlmSubmitPendingSweeper` / KPST=**폴링 잡**(ACK 유예 만료) / 증강=`AugmentJobExpirySweeper`. **새 스위퍼를 신설하지 않는다(이중 진실원 금지)** |
| **상태 강등 금지** | 지각 실패 신호가 이미 완료된 파이프라인을 FAILED 로 역행시키지 않는다 |
| **동시성** | 회수의 후보 선점은 **조건부 원자 UPDATE**(2노드 Active-Active) |

- **DB 스키마 변경 0건** — 기존 원장(`LS_WEBHOOK_IDEMPOTENCY`·`LS_DEIDENT_PROC_LOG`·`LS_DATA_AUG_JOB`)의 상태값만 활용한다.
- 코드: `common/config/AsyncConfig`(`vlmSubmitExecutor`/`kpstSubmitExecutor`/`augmentSubmitExecutor` + 동명 Scheduler 빈), `common/async/SubmitSignalDispatch`

### 7.3-1 오토라벨 프리셋 보류·재개 (2026-08-25 확정, 구속 · `ADR-054`)

**프리셋은 「무엇을 검출할지」가 아니라 「검출된 것 중 무엇을·어떤 형태로 저장할지」를 정하는 노이즈 필터다.** 그것이 없으면 저장 기준 자체가 없는 것이므로 **오토라벨링을 보류**한다.

- ⚠ **구 동작 폐기 — 되살리지 말 것**: 프리셋을 특정하지 못하면 `AnnotationToggle.BOTH` 로 **fail-open** 되어 검출을 전량 저장하며 완주했다. 그래서 ①프리셋 미보유가 **아무 증상 없이** 지나가고 ②운영자가 프리셋을 등록해 두고도 그것이 실효하지 않는 상태를 어디에서도 알 수 없었다. `BOTH` 상수는 제거됐고 회귀 가드가 그 부재를 고정한다.
- **보류는 실패가 아니라 건너뜀이다** — 예외를 던지지 않고 `LS_BATCH_PROC_LOG` 에 `SKIPPED` 감사 행으로 사유를 남긴다. 시계열 위탁 보류(`VlmTimeseriesStep` → `SKIP_REASON_*` → `VlmWithheldResumeRunner`)와 **같은 골격을 재사용**하며 새 패턴을 만들지 않는다.
- ★**보류는 오토라벨 묶음 전체에 걸린다** — 탐지를 보류하면 **분할·보간도 실행하지 않고 배치를 `COMPLETED` 로 마감하지 않는다.** 근거: 탐지 결과가 비면 분할이 예외 없이 빈 결과를 돌려주고 보간이 그대로 통과해 **라벨만 없는 무증상 성공**이 된다. 재개할 때는 묶음 전체를 다시 돈다.
- **사유를 구분한다** — 판정의 단일 진실원은 `PresetLabelLookupService.resolve` → `PresetResolution`(`PresetResolutionStatus`)이며 **배치·프리셋 화면·이벤트유형 화면이 이 하나를 공유**한다. 다른 곳에서 프리셋을 다시 조회해 실효성을 재유도하지 말 것.

| 사유 | 뜻 | 결과 |
|---|---|---|
| `RESOLVED` | 검출 클래스에 매핑된 활성 라벨이 1건 이상 | 수행 |
| `EVENT_TYPE_UNREGISTERED` | 영상에 이벤트 유형 코드가 없거나 마스터에 등록돼 있지 않다 | **보류** |
| `PRESET_ABSENT` | 그 유형(그룹 대표코드)에 걸린 프리셋이 없다 | **보류** |
| `PRESET_UNLINKED` | 담긴 코드가 전부 라벨 마스터에 연결돼 있지 않다 | **보류** |
| `PRESET_UNMAPPED` | 연결·활성 라벨은 있으나 전부 검출 클래스 **미매핑** | **보류** |
| `PRESET_EMPTY` | 프리셋은 있으나 **라벨을 하나도 담지 않았다** | **제외 — 묶음만 건너뛰고 배치는 완료** |

- ★**`PRESET_EMPTY` 만 성격이 다르다 — 사고가 아니라 선언이다.** 라벨을 비운 프리셋은 「그 이벤트 유형을 오토라벨 대상에서 뺀다」는 **사람의 선언**이므로 보류하지 않고 배치를 완료로 마감하며, 되살릴 것이 없어 **재개 대상도 아니다**(`RESUMABLE_SKIP_REASONS` 에 넣지 말 것 — 넣으면 프리셋을 고칠 때마다 제외 선언이 뒤집힌다). 반면 라벨은 골랐는데 전부 매핑이 없는 `PRESET_UNMAPPED` 는 **사고**라 보류한다. **둘을 같게 다루면 실수와 의도가 구분되지 않는다.**
- **재개** — 프리셋을 등록·수정하면 `PresetLabelsChangedEvent` → `AutolabelResumeBridge`(AFTER_COMMIT) → `AutolabelWithheldResumeRunner` 가 그 유형의 보류분을 다시 돈다. 조건은 **「보류 이력이 있고 지금은 프리셋이 실효하다」 둘 다**이며 둘째가 멱등을 담당한다. 2노드 동시 재개를 막기 위해 오케스트레이터 진입 가드의 **단일 조건부 UPDATE** 로 원자 선점한다. ⚠ **삭제는 재개를 촉발하지 않는다** — 프리셋이 사라지면 오히려 보류 조건이 성립한다.
- ⚠ **인지·수용한 잔여 위험** — 수정만 되고 아무도 프리셋을 등록하지 않은 영상을 감지·알림하는 장치가 없다. 그 영상은 보류인 채로 남는다.
- ⚠ **알려진 리스크(범위 밖)** — 관제가 유형별 이름(`EVNT_NM`)을 보내기 시작하면 표시명이 갈려 그룹이 쪼개지고 **그룹 대표코드가 바뀌어**, 대표코드에 걸어둔 기존 프리셋이 조용히 떨어질 수 있다.
- ⚠ **라벨링 화면의 오토라벨 버튼 경로는 대상이 아니다** — 그 경로(`AutolabelOnlineService`)는 프리셋을 쓰지 않고 라벨 마스터의 매핑만 본다. 동작·응답 계약 불변.
- **기존 영상은 소급하지 않는다** — 이미 전량 저장으로 처리된 영상은 재처리하지 않으며 신규 배치부터 적용된다.

## 7.4 큐 · 스케줄러 (Quartz)

| 컴포넌트 | 역할 |
|----------|------|

> **전용 「배치 실패 관리」 화면은 신설하지 않는다.** 영상 목록(SC-007)에 이미 배치 단계 `실패` 필터가 있어 같은 일을 하는 **두 번째 목록**을 만들지 않는다. 조치는 실패를 이미 보고 있는 자리 — 영상 상세(SC-009)와 영상 목록의 일괄 작업 바 — 에 붙인다. 화면 쪽 서술은 [05 §5.5.4](05-video-management.md) · [04 화면·IA](04-screens-ia.md).

**① 실패 단계·사유 표시** — `GET /v1/videos/{rawSn}` 응답에 `batchFailureReason`(문자열, nullable)이 신설됐다.

- 사유는 **서버가 사용자 문구로 변환한 값**이며 예외 클래스명·SQL·DB 제약명 같은 내부 원문은 응답에 싣지 않는다(CWE-209). 변환 판정의 **단일 원천은 `BatchFailureReasonPolicy`** 이고, 그 클래스는 `ERR_MSG_CN`(내부 메시지 원문)을 **인자로 받지 않는다** — 받을 수 없으면 흘릴 수도 없다. 알려진 원인 유형(`ERR_CD`)만 원인 문구를 덧붙이고 **모르는 유형은 덧붙이지 않는다**(폴백이 곧 기본 동작).
- ★**단계를 특정할 수 없는 실패도 사유만은 전달된다.** 그런 영상은 `stages` 가 **빈 배열**로 오므로, 사유를 단계 배열 안에 넣었다면 그 영상은 화면에서 아무것도 볼 수 없다(dev 실측상 원본 실패 3건 중 1건이 이 형태였다). 그래서 **영상 단위 필드**로 뒀다.
- 하위호환: 기존 `VideoDetailResponse.from(...)` 오버로드는 이 필드를 `null` 로 위임하므로 **추가만**이다.

**② 단건 재실행** — **신규 API 가 아니다.** 기존 `POST /v1/videos/{rawSn}/batch/retry`(REVIEWER)를 그대로 쓴다. 재기동은 파이프라인을 처음부터 순회하되 위 멱등 성질 덕분에 실질 작업이 실패한 단계부터 이어진다.

**②-0 ★단건 재기동은 실패(FAILED) 영상 전용이다 — 완주 영상은 받지 않는다 (2026-08-12 확정, 구 「완주 영상도 받는다」 폐기)**

- **왜 되돌렸나 (데이터 파괴 차단)**: 완주 영상을 받으면 파이프라인 **전체**가 다시 순회하는데, **트랙 보간은 건너뛰는 조건이 없어 항상 돈다.** 그 단계는 `lblSrcCd='INTERPOLATE'` 라벨을 **사람이 고쳤는지 보지 않고 전량 삭제**한 뒤 재생성하며, 삭제 이력도 승인 스냅샷도 없어 **복구 지점이 0** 이다. 완주 영상은 곧 작업자가 라벨링 중이거나 끝낸 영상이므로 이 경로는 열어 둘 수 없다.
- **허용 출발 상태는 `FAILED` 하나**다(구 `COMPLETED` 축 폐기). 단일 조건부 UPDATE 라 동시 요청 중 정확히 1건만 통과한다(CWE-362).
- **건너뛰기를 해제한 묶음의 재수행은 그 묶음을 지목하는 별도 요청**(②-2)이 담당한다 — 「문제가 생긴 곳부터 재시도한다」는 원칙에 맞춘 분리이며, 그쪽은 **묶음이 곧 범위**라 건너뛰기를 해제한 묶음만 수행한다.
- ★**이 경로에는 승인 이력 게이트를 두지 않는다**(구 400 조항 폐기). 실패 영상은 검수가 승인된 적이 없고(승인은 배치 완주 **이후**의 워크플로우다), 게이트를 남기면 기존 계약(실패 영상은 승인 이력과 무관하게 재기동)을 **도달 불가능한 조건으로 좁히기만** 한다. 승인 이력 판정이 필요한 것은 완주 영상을 받는 ②-2 쪽이다.
- **보상 롤백은 선점 직전 상태로** 되돌린다(이 경로는 항상 `FAILED`). 출발 상태를 인자로 받는 구조는 ②-2 가 공유하므로 그대로 유지한다.

**②-1 ★재기동은 요청 안에서 실행되지 않는다 — 선점까지만 하고 실행은 비동기다 (2026-08-12, 구 동기 실행 폐기)**

- **왜 바꿨나**: 재기동 1건은 프레임 추출(NAS I/O)·ai 추론(호출당 상한 60s)·외부 위탁을 포함해 **분 단위**로 걸리는데 FE 요청 타임아웃은 **30초**다. 동기로 돌리면 정상 동선에서 거의 항상 "실패했습니다"가 뜨는데 서버는 뒤에서 계속 돌아 사용자가 다시 누르고, 일괄 100건이면 요청 스레드 하나가 수십 분 점유되며 ai 서킷이 열려 무관한 기능까지 막힌다.
- **요청 안에서 하는 일 = 실패 상태 선점**(`FAILED→PROCESSING` 원자 클레임)**까지**다. 그래야 409·부분 성공 판정이 즉시 확정된다. 응답은 **접수 사실 + 접수 시점 단계**(`stage: "PROCESSING"`)이며 **200 은 완료가 아니다** — 진행 상황은 영상 상세의 단계 표시로 확인한다. 응답 스키마(필드명·타입)는 무변경이고 `stage` 가 담는 값의 의미만 바뀌었다.
- **실행은 전용 풀**(`batchReprocessExecutor` — core 2 / max 4 / **queue 4**)에서 별도 빈이 수행한다. ★**같은 빈 안에서 부르지 않는다** — `@Async` 는 프록시를 거쳐야 동작하므로 자기호출이면 **여전히 동기로 돌고 테스트만 통과**한다.
- ★**포화 정책은 `AbortPolicy` 이며 `CallerRunsPolicy` 를 쓰지 않는다.** CallerRuns 면 큐가 차는 순간 **요청 스레드에서 파이프라인이 실행**돼 고친 결함이 그대로 되살아난다. 풀을 배치 공용 풀과 **분리**하는 이유도 같은 축이다 — 일괄 100건이 선두 비식별 등 다른 배치를 굶기면 안 된다(CWE-770).
- ★**디스패치 거부는 접수 실패로 처리**한다 — 클레임을 되돌리고 **503**. 조용히 삼키면 사용자는 접수됐다고 믿는데 아무것도 돌지 않고, 선점한 `PROCESSING` 이 남아 그 영상은 **이후 모든 재기동이 409**(복구 불가)가 된다.
- ★**큐 깊이는 실행 능력에 맞춘다 — 큐 = 선점해 놓고 대기시키는 최대 건수 (2026-08-12, 구 queue 100 폐기)**. 접수는 **상태 선점(`PROCESSING` 커밋 + 자동 재시도 대기행 삭제)** 을 동반하고, `ThreadPoolExecutor` 규약상 **큐가 차기 전에는 스레드가 core 를 넘지 않는다** — 구 형상은 100건을 접수하면 **2건만 돌고 98건이 선점된 채 큐에 누웠다.** 그 구간에 노드가 재기동·재배포되면 큐가 통째로 사라지고 그 영상들은 `PROCESSING` 고착 → **이후 재기동 영구 409** 이며 대기행도 이미 지워져 **애플리케이션 안에 복구 수단이 없다**(기존 3중 차단은 전부 「러너가 실제로 돈 뒤」를 전제한다). 그래서 큐를 **실행 능력(max 4)의 1배 = 4** 로 줄였다 — 한 번에 선점된 채 대기하는 최대 건수 **4**, 총 접수 상한 **8**(core 2 + 큐 4 + 증설 2).
- **일괄 상한 100 은 그대로다** — 100건을 보내도 접수되는 것은 큐가 감당하는 만큼이고 나머지는 **건별 실패(사유 포함)** 로 돌아간다(부분 성공 정책과 이미 정합). 사유는 「지금은 밀려서 접수하지 못했다, 잠시 후 다시」라는 뜻이며 내부 실행기·풀 정보를 싣지 않는다(CWE-209).
- ⚠ **남는 위험(인지·수용)**: 폭을 줄였을 뿐 **없애지는 못했다.** 큐 4 + 실행 4 = 최대 8건은 여전히 재배포 시 `PROCESSING` 으로 고착될 수 있다. 다만 그 고착은 이제 **자동 회수된다** → §7.5-2. 또 큐가 얕아져 **평시 거부가 늘어난다** — 그건 의도된 거래다(조용한 고착보다 즉시 거부가 낫다).
  - ⚠ **[정정] 구 서술 「그 회수 수단은 없다(회수 스위퍼는 이번 범위 밖)」 → 폐기 (2026-08-13)**. 회수 스윕이 신설돼 애플리케이션 안에 복구 수단이 생겼다.
- ★**`PROCESSING` 고착 3중 차단**: ①**검수 소유 작업 상태는 클레임 전에 409**(비동기라 진입 가드의 `SKIPPED` 를 요청이 볼 수 없어, 이게 없으면 "못 돌리는 영상"이 200 으로 가려진다 — 판정 기준은 진입 가드와 **같은 클래스가 소유**하고 권위는 여전히 진입 가드의 조건부 UPDATE 다) ②경합으로 `SKIPPED` 를 만나면 **보상 롤백**(동기 시절 처리를 그대로 옮긴 것) ③오케스트레이터 자체 마감을 타지 못한 예외 이탈도 같은 보상. **마감 경로를 새로 만들지 않았다.**
- ⚠ **자동 재시도 큐(Quartz)는 이 변경의 대상이 아니다** — 이미 스케줄러 스레드에서 돌아 요청 스레드를 잡지 않으므로 **일반 진입을 그대로** 쓴다. 거기에 비동기를 한 겹 더 씌우면 잡이 즉시 반환해 `@DisallowConcurrentExecution`·`pollReady()` 클레임과 어긋난다.

**②-2 ★건너뛰기를 해제한 작업 묶음은 「그 묶음을 지목해」 다시 수행한다 — `POST /v1/videos/{rawSn}/batch/stages/{stage}/rerun` (2026-08-12 신설 · 같은 날 묶음 단위로 반전)**

REVIEWER 전용. **요청 본문 없음.** 대상은 경로 변수의 **작업 묶음**(`VLM` / `AUTOLABEL`).

- **왜 별도 요청인가**: 전체 재기동에 완주 영상을 태우면 트랙 보간이 함께 돌아 사람이 손댄 보간 라벨을 복구 지점 없이 지운다(②-0). 「문제가 생긴 곳부터 재시도한다」는 원칙에 따라 **해제한 그 묶음을 지목**해 실행한다. 별도 sub-resource 인 것은 「같은 URL 에 쿼리 파라미터로 행위 분기 금지」 규약 때문이다.
- ★**범위를 고르지 않는다 — 묶음이 곧 범위다.** 건너뛰기를 해제한 묶음만 수행하고 다른 묶음은 건드리지 않는다. 오토라벨을 재수행하면 **트랙 보간도 함께 다시 만들어져** 사람이 손댄 보간 라벨이 새로 계산된 것으로 바뀌는데, 그것은 「오토라벨을 통째로 다시 만든다」를 사용자가 고른 **예상되는 결과**이며 화면이 고르는 시점에 알린다.
- ★★**대상 묶음을 요청이 자유롭게 지정하지 못한다** — 서버는 그 영상에서 **건너뛴 적이 있는 묶음**(마지막 표식 행이 `MANUAL_SKIP` **또는** `MANUAL_SKIP_CLEARED`)만 수락하고 표식이 **아예 없는** 묶음은 **400**. 임의 묶음을 받으면 요청이 **앞 작업을 건너뛰도록 강제**할 수 있어 전제 없는 산출물이 만들어진다. 판정은 기존 스킵 판정과 **같은 축·같은 쿼리**를 쓰며(`BatchStatusService(hasManualSkipHistory)`) 규칙을 복제하지 않는다. **이 제한을 느슨하게 만들지 말 것.**
- ★★**건너뛴 상태도 그대로 수락한다 — 해제→재수행 2단계 폐지 (2026-08-21, ADR-050)**. 되살리려는 사람에게 해제와 재수행은 **한 가지 일**이고, 나누어 두면 해제만 하고 재수행을 잊었을 때 그 영상이 **건너뛰지도 수행하지도 않은** 상태로 남는다. 건너뛴 상태로 들어온 건은 재수행이 **해제 표식을 함께 남긴다** — 코드값은 사람이 누른 해제와 같고(`MANUAL_SKIP_CLEARED` — 상태 판정의 키라 새로 만들면 이미 적재된 과거 행의 배선이 끊긴다) **사유 본문**(`[수동 스킵 해제] 재수행에 따른 자동 해제`)으로만 갈린다. 이미 해제된 묶음이면 아무 행도 남기지 않는다(감사 잡음 방지).
  - ★★**순서가 계약이다** — 해제 표식은 **디스패치보다 먼저** 커밋돼야 한다. 표식이 건너뜀인 채로 파이프라인이 시작되면 오케스트레이터의 스킵 게이트가 그 묶음을 **다시 건너뛰어** 재수행이 조용히 무효가 된다(200 을 받았는데 아무것도 돌지 않는다). 판정 지점은 `BatchStageRerunService(clearSkipMarkerForRerun)` 이며 **클레임 뒤**에 둔다 — 앞에 두면 클레임 실패(409)로 끝난 요청이 표식만 풀어 그 영상이 「건너뛰지도 수행하지도 않은」 상태로 남는다.
  - **접수 거부(503) 보상에서 이 해제를 되돌리지 않는다** — 되돌리면 사람이 이미 내린 「되살린다」는 결정을 시스템이 뒤집는 셈이고, 해제 상태로 남아도 그 묶음은 여전히 재수행 대상이라 재시도가 막히지 않는다.
  - ⚠ **[폐기] 구 동작 — 마지막 표식이 `MANUAL_SKIP_CLEARED` 인 묶음만 수락(건너뛴 상태는 400)** (2026-08-21 폐기). 되살리려면 `DELETE …/skip` 을 먼저 부르고 그다음 `…/rerun` 을 불러야 했다. **되살리지 말 것.**
- ★**일괄 재수행도 같은 판정을 쓴다** — `POST /v1/videos/batch/stages/{stage}/rerun` 은 단건 서비스를 그대로 호출하며 자체 판정을 갖지 않는다. 같은 조건에 두 경로가 다르게 답하면 안 된다.
- **선점은 `COMPLETED→PROCESSING` 조건부 UPDATE** 다(완주 영상이 주 대상). ★**실패 영상은 이 경로로 받지 않는다(409)** — 오케스트레이터는 루프를 마치면 **무조건 완료로 마감**하므로, 프레임 추출에서 실패한 영상에 「시계열만」을 돌리면 **프레임이 한 장도 없는 영상이 `COMPLETED`** 가 되어 검수·산출 축으로 흘러간다. 실패 복구는 파이프라인을 처음부터 도는 ②(전체 재기동)가 담당하며, 그 경로는 실패 영상에 **사람이 만든 라벨이 없어**(라벨링·검수는 완주 이후다) 보간 재계산이 파괴가 되지 않는다.
- ★**한번이라도 검수가 완료된 영상은 받지 않는다 — 400.** 확정된 학습데이터는 되돌리지 않는다. 판정은 비식별 신고 차단·프레임 폐기 차단과 **같은 단일 원천**(`ReviewApprovalGate(hasEverApproved)` — 지금 상태가 아니라 **이력**)을 **주입해** 쓴다. 412 가 아닌 것은 승인 이력이 **영구 조건**이라 재시도 여지가 없기 때문이다. **클레임보다 먼저** 평가한다.
- **검수 소유 작업 상태는 클레임 전에 409** · **디스패치 거부는 503 + 보상 롤백**(선점 직전 상태 `COMPLETED` 로) — ②-1 과 같은 3중 차단·같은 전용 풀을 그대로 쓴다. 응답은 **접수 사실**(`{rawSn, stage, accepted:true}`)이며 **200 은 완료가 아니다.**
- ★★**재수행이 실패해도 영상 상태를 훼손하지 않는다 (2026-08-12 확정)** — 실행 중 단계 실패는 **선점 직전 상태(`COMPLETED`)로 원상 복구**하고 작업 상태도 성공 경로와 같은 `ASSIGNED` 로 되돌리며, **자동 재시도 큐에 넣지 않는다**. 일반 경로처럼 `FAILED` 로 강등하면 ①완주 영상이 실패로 뒤집히고 ②작업 상태까지 `FAILED` 가 되어 작업자가 검수 제출을 못 하며(상태 머신에 그 출발 전이가 없다) ③**자동 재시도가 범위를 모르는 채 전 단계를 돌려** 사람이 손댄 보간 라벨을 지운다 — 이 기능이 막으려던 바로 그 파괴가 실패 경로로 되살아난다. 더구나 스킵의 존재 이유가 "기다려도 성공하지 않는 작업"이라 **되돌려 재수행하면 실패가 예외가 아니라 기대값**이다. 다만 **실패 사실 자체는 배치 로그에 남긴다**(실행이 비동기라 요청이 결과를 못 받으므로 그 기록이 유일한 흔적이며, 영상 상세의 배치 실패 사유가 이 행을 읽는다). ⚠ **전체 재기동(②-0/②-1)의 강등·자동 재시도는 그대로다** — 그쪽은 대상이 실패 영상이라 강등이 맞다. 판정은 오케스트레이터의 **전용 진입**(`BatchOrchestrator(processBundleRerun)`)이 담당하고 복구는 `BatchTransitionService(restoreAfterBundleRerunFailure)` 한 곳이다.
- ★**실행 범위는 새 축을 만들지 않고 기존 stage 토글로 전달한다** — 오케스트레이터에 "이번 실행에서 어느 단계를 돌릴지"를 알리는 축은 `BatchContext` 의 stage 토글로 **이미 있었다**. 두 번째 축을 만들면 "어느 것이 이겼나"를 판정하는 규칙이 새로 필요해지고 그 규칙이 두 벌이 된다. 변환은 `BatchBundleTogglePolicy(togglesFor)` 한 곳이 담당하고, **토글 대상 목록은 상수로 적지 않고 실제 파이프라인 빈에서 읽는다** — 적으면 `BatchPipelineConfig` 와 두 벌이 되어 단계를 추가·재배치할 때 조용히 갈린다. 파이프라인에 단계가 추가되면 그 단계는 **자동으로 off** 로 들어온다(어느 묶음에도 속하지 않으므로 — fail-closed).
- ★**전 단계가 토글을 따른다(구 「FRAME_EXTRACT/YOLO/SAM2 3종만」 폐기)** — 3종만 따르면 **VLM·INTERPOLATE 가 범위를 무시하고 실행**된다. 토글이 없는 컨텍스트는 전 단계 enabled 이므로 **기존 경로(전체 재기동·자동 재시도·마킹 브리지·선두 비식별)는 동작 무변경**이다.
- **`MARKING` 은 어떤 재수행에서도 끄지 않는다** — 마킹 로드는 작업 단계가 아니라 **컨텍스트 적재기**(마킹 로드 + marks 파싱, 쓰기 없음)이고, VLM 은 마킹 엔티티를 FRAME_EXTRACT 는 파싱된 marks 를 여기서 받는다. 켜 두는 것은 범위를 넓히는 게 아니라 **범위가 성립하기 위한 전제**다.
- **수동 스킵 표식이 재수행 토글보다 우선한다** — 다시 스킵된 묶음은 토글이 켜져 있어도 실행되지 않는다(사람의 결정이 재수행 지정에 뒤집히지 않는다).
- ⚠ **알려진 성질(인지·수용)**: ②-1 이 남긴 잔여 위험(전용 풀 큐 4 만큼의 `PROCESSING` 고착 가능성)을 **그대로 공유**한다. 회수는 §7.5-2 가 담당하며 **완주 축(`COMPLETED`)으로 되돌린다** — 그것이 이 경로의 데이터 파괴를 막는 지점이다.
- ⚠ **[폐기] 구 동작 — 요청 본문 `{scope: "ONLY" | "FROM"}` 필수 · 대상이 개별 단계(`VLM`/`YOLO`/`SAM2`)** (2026-08-12 같은 날 반전). 폐기 사유: 단위가 개별 단계였기 때문에 범위 선택이 필요했고, `ONLY` 는 뒤 단계를 옛 산출물로 남겨 어긋나게 했으며 `FROM` 은 관계없는 보간까지 돌려 사람이 손댄 라벨을 지웠다. 무엇보다 **보간이 단위 밖**이라 어떤 재수행에서도 무조건 돌던 것이 반복 사고의 뿌리였다. 단위를 묶음으로 바꾸면 그 선택 자체가 사라지고 파괴가 **구조적으로 소멸**한다. 구 변환기 `BatchRerunScopePolicy`·구 enum `BatchRerunScope`·구 요청 DTO `BatchStageRerunRequest`·응답 필드 `scope` 는 모두 제거됐다. **되살리지 말 것.**

**③ 시계열 · 오토라벨 **작업 묶음** 수동 스킵 + 건너뛰기 해제** — `POST /v1/videos/{rawSn}/batch/stages/{stage}/skip`(사유 필수, 200) · 같은 경로 `DELETE`(해제, 204). 전부 **REVIEWER 전용**.

- ★★**단위는 개별 단계가 아니라 작업 묶음이다 (2026-08-12 확정, 구속)** — **`VLM`**(시계열) · **`AUTOLABEL`**(AI 탐지 · AI 분할 · **트랙 보간**) 2종. 오토라벨은 **쪼개서 부분 수행하지 않는다**: 뒤 작업이 앞 결과를 입력으로 받고 보간이 그 산출물을 재계산하므로 일부만 수행하면 산출물끼리 어긋난다. 무엇보다 **보간을 묶음 밖에 두면 어떤 재수행에서도 무조건 돌아** 사람이 손댄 보간 라벨을 복구 지점 없이 지운다 — 묶음이 그 사고를 **구조적으로 없앤다**. 묶음 정의의 단일 지점은 `BatchStageBundle` 이며, 단계 **순서**는 거기 적지 않고 `BatchPipelineConfig` 가 계속 진실원이다.
- **대상이 두 묶음뿐인 근거는 되돌릴 수 있는 성질**이다 — 시계열을 건너뛰면 영상 서술이 사람이 직접 쓴 전문으로 폴백되고, 오토라벨을 건너뛰면 프레임은 그대로 남아 작업자가 처음부터 라벨링한다. 비식별·프레임 추출은 뒤 작업과 데이터마트 산출의 **전제**라, 건너뛴 채 완료되면 산출물이 조용히 비므로 대상이 아니다(요청하면 400).
- ★★**대상은 그 묶음이 「실패한」 영상뿐이다 — 412 (2026-08-21, ADR-050)**. 정상 진행 중이거나 이미 끝난 묶음은 이 경로로 건너뛸 수 없다. 정상 영상을 미리 골라 건너뛸 수 있으면 ①이미 들어와 있는 영상만 덮어 **뒤에 들어오는 영상은 매번 다시 골라야 하고** ②근거 없이 정상 영상이 시계열·오토라벨 없이 확정된다. 미연동 구간을 통째로 덮는 몫은 **전체 설정**(`batch.vlm.skip-by-default`)이 맡아 배치가 위탁 단계에 진입하기 직전 자동으로 표식을 남긴다 — **입구는 그 둘뿐**이다.
  - **거부가 412 인 것은 일시 조건이기 때문**이다. 나중에 그 묶음이 실패하면 **같은 요청이 수락**된다. 파생영상·미지원 묶음의 **400**(영구 조건)과 갈리는 것이 의도다.
  - **해제(`DELETE`)는 이 게이트를 받지 않는다** — 차단에는 되돌리는 길이 있어야 한다.
  - **일괄 건너뛰기도 같은 판정**이며, 실패 상태가 아닌 영상은 **그 건만** 건별 실패로 돌려주고 나머지는 처리한다(부분 성공). ⚠ 사유 검증(요청 단위 400)과 **축이 다르다** — 사유는 요청당 하나라 건별로 갈릴 수 없지만 실패 여부는 **영상마다 다르다**. 실패 판정을 루프 앞으로 끌어올리지 말 것.
- ★★**「실패한 상태」의 판정 축이 묶음마다 다르다 — 통일할 수 없다.** 판정 단일 지점은 `BatchBundleFailureGate(hasFailed)` 이며 두 축의 **OR** 다.
  - **오토라벨** — 스텝이 예외를 던져 파이프라인이 서므로 **진행 행**에 `PROC_STTS_CD='FAILED'` 가 남는다(`BatchStatusService(isBundleProgressFailed)`).
  - **시계열** — 위탁 제출은 **논블로킹**이라 실패해도 예외가 위로 올라가지 않고 프레임 추출·오토라벨이 그대로 완주한다. 그래서 **진행 행이 절대 `FAILED` 가 되지 않으며**, 실패는 `VLM/SKIPPED` + **확정 실패 사유**로만 남는다. 이 축이 없으면 시계열 건너뛰기 버튼이 **영영 뜨지 않는다**.
  - ★**실패로 읽는 사유는 「결과를 끝내 받지 못한」 것뿐**이다(제출 실패 · 수락 응답 미수신 · 결과 콜백 미수신). 비식별 신고 **보류**처럼 해소되면 스스로 재개되는 사유를 실패로 읽으면 **정상 영상을 건너뛰는 길이 다시 열려** 게이트의 존재 이유가 사라진다.
  - ⚠ **알려진 한계(인지·수용)**: 벤더가 **실패 콜백으로 답한 건**은 배치 이력에 아무 행도 남기지 않고 마킹 상태(`VLM_FAILED`)만 바꾸므로 이 판정에 **잡히지 않는다**. 마킹 축을 더하면 잡히지만 그 축은 재개 성공 뒤에도 종결 상태가 그대로 남아 **더 넓게 허용**하게 되어, 「정상 영상을 건너뛰지 못하게」라는 목적상 **덜 허용하는 쪽**을 골랐다.
  - ⚠ 감사 행은 append-only 라 실패 후 재개가 **성공**해도 그 행은 남는다 — 그 영상은 이후에도 건너뛰기가 허용된다. 건너뛰기가 되돌릴 수 있는 조작(재수행)이라 감수한다.
- ⚠ **[폐기] 구 대상 — `VLM`·`YOLO`·`SAM2` 3종(개별 단계)** (2026-08-12 같은 날 반전). 그 형상에서는 **보간만 단위 밖**이라 어떤 재수행에서도 보간이 무조건 돌았고, YOLO 만 되돌리면 옛 분할·옛 보간이 남아 어긋났다. 구 개별 단계값은 이제 **400** 이다. **되살리지 말 것.**
- ★**저장은 새 테이블·새 컬럼 없이 `LS_BATCH_PROC_LOG` 를 재사용**한다. 스킵·해제 **둘 다 `PROC_STTS_CD='SKIPPED'`** 로 적재하고 `ERR_CD`(`MANUAL_SKIP` / `MANUAL_SKIP_CLEARED`)로 구분하며, **현재 상태 = (영상 × 묶음) 마지막 표식 행의 `ERR_CD`** 다. 표식은 **append-only** 라 누가·언제·왜가 모두 남고, 스킵→해제→재스킵을 몇 번 반복해도 판정 규칙이 흔들리지 않는다.
- ★★**`PROC_STEP_CD` 에는 개별 단계가 아니라 묶음 코드(`VLM`/`AUTOLABEL`)를 넣는다 — 한 행이 한 묶음의 결정을 통째로 담아 부분 상태가 표현 자체로 불가능**하다. 오토라벨 3단계에 표식을 각각 남기는 안은 채택하지 않았다: "3건 모두 서 있어야 묶음 스킵"이라는 판정이 생기고 **2건만 있는 상태가 표현 가능**해지는데 그 상태의 동작은 아무도 정의하지 않았으며, 훗날 한 단계에만 표식을 남기는 경로가 하나만 생겨도 판정이 조용히 흔들린다. 묶음 코드 한 행이면 기록·해제가 **단일 INSERT** 라 원자성을 위해 따로 애쓸 것이 없고, 감사에서도 "누가 언제 왜 오토라벨을 껐다"가 한 줄로 읽힌다.
  - **실재하지 않는 단계값을 넣어도 안전한 근거**: `PROC_STEP_CD` 를 단계로 해석하는 지점(`BatchStatusService(currentStage)`의 `BatchStage.valueOf` · `stagesFor` · `failureReasonFor`)은 전부 진행 조회(`LsBatchProcLogRepository(findTopByDataRawSnAndProcSttsCdNotOrderByRegDtDesc)` — `SKIPPED` 제외)를 통해서만 행을 읽는데, 표식 행은 `SKIPPED` 라 **그 조회에 애초에 걸리지 않는다**. 컬럼은 `VARCHAR(30)` 이고 CHECK 제약이 없으며 이 테이블을 읽는 뷰도 없다. dev DB 의 기존 `SKIPPED` 표식 행은 0건이라 마이그레이션도 불필요하다. 회귀 가드: `ManualStageSkipIT(bundleMarkerNeverReachesProgressAxis)`.
- **게이트는 단계 단위로 묻되 판정은 묶음 축**이다 — 오케스트레이터 루프는 각 단계마다 "이 단계가 속한 묶음이 스킵됐는가"를 묻고, 소속 해석은 `BatchStageBundle(containing)` 단일 지점이다. 어느 묶음에도 속하지 않는 단계(`MARKING`·`FRAME_EXTRACT`·`DEIDENTIFY`)는 항상 false = **건너뛸 수 없다**(fail-closed).
- ★**정렬 키는 시각이 아니라 PK** 다 — 같은 밀리초에 토글하면 시각 정렬로는 판정이 뒤집힌다.
- ★**해제에 새 상태값을 쓰지 않는 이유**: 진행 조회가 `SKIPPED` 행을 제외하는데 다른 상태값을 쓰면 그 행이 **최신 진행 행**이 되어 화면의 단계 표시가 엉뚱하게 바뀐다.
- ★**기존 `SKIP_REASON_*` 상수를 재사용하지 않는다.** 그 값들은 비식별 신고 해소 시 `VlmWithheldResumeRunner` 가 **재개 대상으로 집는 축**이라, 사람이 누른 스킵에 쓰면 훗날 재개 절차가 **사람의 결정을 몰래 뒤집고 외부 벤더로 다시 위탁**한다. 전용 `ERR_CD` + 사유 접두(`[수동 스킵] `) 강제로 2중 차단한다(재개 판정이 사유 **정확 일치**이므로 접두만으로 충돌이 구조적으로 불가능해진다) → [09](09-vlm-timeseries.md)
- **게이트는 두 곳에 둔다** — 오케스트레이터 루프(`BatchOrchestrator(process)`)와 **`VlmTimeseriesStep` 전송 직전**. 후자는 `VlmWithheldResumeRunner` 가 **직접 부르는 public 진입점**이라 오케스트레이터에만 두면 그 경로로 샌다(비식별 신고 게이트를 같은 메서드에 둔 것과 동일한 논리). 건너뛴 단계는 `markStage` 도 타지 않으므로 **진행 축을 오염시키지 않는다**.
  - ★**전체 설정 자동 표식도 같은 두 곳에 둔다 (2026-08-21 보강)** — 게이트는 표식을 **읽기만** 하므로, 표식을 오케스트레이터에서만 세우면 재개 러너 경로에는 세우는 자가 없어 **게이트가 항상 통과**한다(스위치가 켜져 있어도 외부 벤더 호출). 자동 표식 적용을 전송 코드와 같은 메서드에 두어 어떤 호출자도 우회할 수 없게 했다 → [09 §9.2-2b](09-vlm-timeseries.md).
- **해제는 표식만 지우고 작업을 실행하지 않는다** — 실제 실행은 **묶음 지목 재수행**(②-2)이 담당한다. 완주한 영상의 건너뛰기를 해제한 단계가 실효를 갖는 통로가 그것이며, 전체 재기동은 실패 영상 전용이다(②-0). 그래야 "해제 버튼이 무거운 외부 호출을 몰래 일으키는" 동작이 생기지 않는다. 스킵 상태가 아닌 해제는 **아무 행도 남기지 않고 204**(멱등 — DELETE 의 표준 의미).
- **현재 스킵 상태는 `GET /v1/videos/{rawSn}` 의 `skippedStages`(빈 배열 가능, 값은 **묶음 코드**, 순서 `VLM→AUTOLABEL` 고정)로 조회**한다. 필드명은 하위호환으로 유지하되 **값의 단위가 묶음으로 바뀌었다**. ★`stages` 로는 대체할 수 없다 — 건너뛴 묶음은 진행 축에 흔적을 남기지 않아 화면이 "무엇을 건너뛰었는지" 알 방법이 전혀 없다. 순서를 고정하는 이유는 순회 순서가 실행마다 흔들리면 화면이 깜빡이기 때문이다.
- ★★**지금 실패한 묶음은 `failedStages` 로 내려간다 (2026-08-21 신설 · 추가만)** — **사람이 결정하는 입구가 닫혀 있던 것을 연다.** 건너뛰기는 그 묶음이 **실패한** 영상에만 열리는데(③), 시계열 위탁은 **논블로킹**이라 실패해도 예외가 위로 올라가지 않아 **배치 상태(`status`)가 완료로 남고 `stages` 에도 실패 표시가 서지 않는다**. 화면이 그 두 신호만 보면 위탁이 확정 실패한 영상에서도 건너뛰기·재수행 버튼이 **어디에도 뜨지 않는다** — 서버는 허용하는데 사람이 누를 자리가 없는 상태였다.
  - **판정은 건너뛰기 허용을 정하는 서버 판정과 같은 지점**(`BatchBundleFailureGate(failedBundles)` → `hasFailed`)이다. 규칙을 재유도하면 화면에 뜬 버튼이 눌렀을 때 **412 로 튕긴다**.
  - 값 집합·순서·빈 배열 계약은 `skippedStages`·`clearedStages` 와 같다(`VLM`/`AUTOLABEL` · 선언 순서 고정 · 없으면 빈 배열).
  - ⚠ **스스로 재개되는 보류**(비식별 신고 등)는 담기지 않는다 — 담으면 정상 영상을 건너뛰는 길이 다시 열린다(③의 사유 선별과 같은 축).
- ★**영상 목록에서 실패한 영상을 골라낼 수 있다 — `GET /v1/videos?failedStage=VLM|AUTOLABEL` (2026-08-21 신설)**. 같은 이유다: 위탁 실패 영상은 배치 단계가 **완료**로 남으므로 `dataSttsCd=FAILED` 를 포함해 **다른 어떤 필터로도 모을 수 없었다**(일괄 건너뛰기가 쓰이는 바로 그 자리다). 술어는 판정 소유자와 같은 **OR 합성**이다 — 진행 축(`PROC_STTS_CD='FAILED'` + 그 묶음의 단계) **또는** 시계열 위탁 **확정 실패 감사 행**. `skippedStage` 와 **함께 지정할 수 있고 그때는 교집합**이다(축이 다르다 — 한쪽은 「사람이 건너뛴 상태」, 다른 쪽은 「실패한 상태」). optional·**BE 기본값 불변**·미지 값 **400**·`EXISTS` 규칙은 `skippedStage` 와 동일하다.
- ★★**해제된 묶음은 `clearedStages` 로 따로 내려간다 (2026-08-21 신설 · 추가만)** — `skippedStages` 의 **뒷면**이며 같은 축·같은 쿼리를 쓴다(`BatchStatusService(clearedBundles)`). 사람이 직접 푼 해제와 **재수행이 자동으로 푼 해제**가 모두 담긴다. **이 필드가 없으면 한 번 재수행한 영상을 화면에서 다시 재수행할 수 없다** — 재수행이 건너뜀 표식을 스스로 풀면서 그 묶음이 `skippedStages` 에서 빠지기 때문이다. 화면은 **두 목록의 합집합**으로 재수행 버튼 노출을 정한다. 두 목록 모두 화면 세션과 무관한 **영구 상태**이고 없으면 빈 배열이다(null 아님). `skippedStages` 의 시맨틱은 **바뀌지 않는다**(지금 건너뛴 상태).
- ★**영상 목록에서 건너뛴 영상을 골라낼 수 있다 — `GET /v1/videos?skippedStage=VLM|AUTOLABEL` (2026-08-21 신설)**. **지금 그 묶음이 건너뛴 상태**인 영상만 남기며 이미 되살린 영상은 남지 않는다(표식이 append-only 라 존재 여부로 판정하면 되살린 영상까지 걸린다). 벤더 연동이 끝난 뒤 회수 대상을 모으는 자리이며, 일괄 요청에 건수 상한이 있어 **이 필터가 없으면 회수가 성립하지 않는다**. 신규 파라미터는 **optional 이고 BE 기본값을 바꾸지 않는다**(보내지 않던 호출의 결과 불변). 미지 값은 0건이 아니라 **400** — 조용히 0건을 주면 화면이 "건너뛴 영상이 없다"로 오독한다(이벤트 유형 키가 미등록이면 0건인 것과 **축이 다르다**: 그쪽은 운영자가 바꾸는 데이터, 이쪽은 코드로 고정된 집합). 쿼리는 **`EXISTS`** 라 표식이 여러 개 쌓여도 목록 행이 증식하지 않는다(조인이면 `totalElements` 까지 틀어진다).
- 사유는 **필수**(공백만이면 400)이며 제어문자를 제거하고(CWE-117) 500자로 하드 절단한다. 제어문자만으로 이루어진 사유는 `@NotBlank` 를 통과하지만 정제 후 비므로 서비스가 다시 막는다.

**④ 일괄 재시작** — `POST /v1/videos/batch/retry`, 바디 `{rawSns[]}` **1~100건**(중복은 1건 취급, 요청 순서 보존).

- ★**건별 결과는 재기동을 접수했는지 여부**이지 파이프라인이 끝났다는 뜻이 아니다(②-1 — 실행은 비동기). 선점 결과가 곧 건별 결과라 부분 성공 정책·응답 스키마는 무변경이다.
- 목록 원소는 **1 이상**이어야 한다 — 단건 경로가 `@Min(1)` 로 막는데 일괄만 빠져 있으면 같은 값이 경로에 따라 400 과 "건별 실패"로 갈린다. 식별자가 될 수 없는 값은 접수 대상이 아니라 **요청 전체가 400** 이다(부분 성공은 **존재·상태** 판정에만 적용).
- ★**부분 성공**: 되는 것만 돌리고 거부분은 **사유와 함께 건별로** 반환하며 **한 건도 성공하지 못해도 200** 이다. HTTP 상태는 "요청을 처리했는가"를 말하고 각 건의 성패는 `results` 가 말한다.
- ★**일괄 배정(`POST /v1/assignments`)과 의도적으로 다른 정책**이다. 배정이 전부 실패시키는 것은 "승인된 영상에 배정 금지" 같은 **무결성 조건** 때문인데 재기동에는 그 조건이 없고, 재기동은 실패 상태를 **먼저 선점하는 쪽이 이기는** 방식이라 남이 한 건을 먼저 눌렀다고 나머지를 되돌리면 사용자가 목록에서 그 영상들을 다시 고르는 수작업을 반복하게 된다. **두 정책을 "일관성"을 이유로 통일하지 말 것.**
- **건별 트랜잭션 경계** — 이 서비스에는 `@Transactional` 을 붙이지 않는다. 붙이면 5번째 건의 런타임 예외가 앞 4건의 클레임 전이까지 롤백시키는데, 그 4건은 이미 파이프라인을 기동한 뒤라 **DB 만 되돌아가 상태가 어긋난다**. 각 건은 단건 재기동과 **같은 원자 클레임**(`FAILED→PROCESSING` 조건부 UPDATE)을 그대로 타며 여기서 상태 판정을 재구현하지 않는다.
- 예상 못 한 예외는 그 건만 실패로 격리하고 **유형·메시지를 버린 고정 문구**로 대체한다(원인은 서버 로그에 클래스명까지만 — CWE-209).

### 7.5-2 ★「처리 중」으로 고착된 영상 자동 회수 (2026-08-13 신설)

재기동(②-0/②-1)·묶음 재수행(②-2)은 요청 안에서 배치 단계를 `PROCESSING` 으로 **선점**하고 실행은 전용 풀로 넘긴다. 그 **대기 중에 노드가 재시작·재배포되면 큐가 통째로 사라지는데 선점 표시는 DB 에 남는다.** 그 영상은 이후 모든 재기동이 409 로 막히고 자동 재시도 대기 행도 접수 때 지워져 **애플리케이션 안에 복구 수단이 0**(DB 직접 수정만)이었다. 기존 3중 보상(②-1 ★)은 전부 **「러너가 실제로 돈 뒤」**를 전제하므로 이 경로를 하나도 덮지 못한다. 최대 폭은 **8건**(실행 4 + 큐 4).

**★판정 축은 「경과 시간」이 아니라 「진행이 멈췄는가」다**

- 「`PROCESSING` 인 지 N 시간」으로 판정하면 **실제로 돌고 있는 파이프라인을 죽인다** — 그 작업이 나중에 끝나며 상태를 덮어써 뒤죽박죽이 되고, 2노드 Active-Active 라 다른 노드가 돌고 있을 수도 있다.
- 기준 시각은 **①선점 표식 시각과 ②배치 진행 로그 마지막 갱신 중 더 나중**이며, 그것이 임계보다 오래됐을 때만 고착으로 본다. 판정 단일 지점은 `ProcessingStaleReclaimTxService(decide)`.
- **왜 둘을 합치나** — 진행 로그는 오케스트레이터가 **단계마다** `BatchStatusService(markStage)` 로 갱신하므로 살아 있는 파이프라인은 값이 앞으로 간다. 그런데 **큐에서 대기 중인 정상 요청**은 아직 한 단계도 실행하지 않아 진행 로그가 **직전 실행 때의 옛 시각**에 멈춰 있다 — 진행 로그만 보면 방금 접수된 요청이 즉시 「멈춤」으로 판정된다. 선점 시각이 그 구간을 덮는다.
- **임계 기본 1440분(24시간) · 설정 `authoring.batch.stuck-reclaim.stale-timeout-minutes`.** 덮어야 하는 구간은 ①선점 후 실행 시작까지의 큐 대기(앞 순번 파이프라인이 끝나야 시작한다) ②가장 긴 단일 단계(오토라벨 — 프레임마다 ai 추론) 둘이다. ★**②의 소요는 「호출당 타임아웃」이 아니라 「프레임 수 × 호출 시간」이며 프레임 수 상한은 코드에 없다**(추출 간격과 영상 길이가 정한다) — 호출당 타임아웃만 보고 「최장 단계가 1분 남짓」으로 읽으면 임계를 크게 과소평가한다. 프레임이 수천 장이면 이 단계 하나가 **몇 시간**이 될 수 있다. 기본값을 크게 잡는 이유는 **살아 있는 선점을 뺏지 않는 것이 회수 지연보다 중요하기 때문**이다 — 잘못 회수하면 완주 영상이 실패로 강등돼 사람이 손댄 보간 라벨이 파괴되는 경로가 열리지만(위 표), 늦게 회수해도 결과는 「복구가 늦어질 뿐」이다. **대가**: 실제로 고착된 영상도 최대 24시간은 재기동이 막힌 채 방치된다. 값은 운영에서 설정으로 조정할 수 있다(추후 시스템 설정 화면 노출 예정).
  - ⚠ **[정정] 구 서술 「호출당 상한 70초이나 프레임 수가 많으면 수십 분을 넘길 수 있다」 → 폐기 (2026-08-13)**. 70초는 **호출 1회의 상한**일 뿐 단계 소요의 바운드가 아니었고, 이 서술을 읽은 운영자가 「최장 단계가 70초면 24시간은 과하다」고 판단해 임계를 하한까지 내리면 **살아 있는 선점을 뺏는 창이 넓어진다**.
- ★**임계를 낮추면 무엇이 나빠지나** — 얻는 것은 **회수가 빨라지는 것뿐**이고, 잃는 것은 **「살아 있는 선점을 뺏지 않는다」는 보장**이다. 임계가 「큐 대기 + 최장 단계」보다 짧아지면 ①같은 영상에 다른 진입이 들어와 파이프라인이 2벌 돌며 외부 위탁이 중복으로 나가고 ②먼저 돌던 작업이 나중에 끝나며 상태를 덮어써 화면·산출물이 어긋난다. **하한 60분은 바닥일 뿐 「안전한 값」이라는 뜻이 아니다** — 실제 안전선은 그 배포의 프레임 수와 큐 적체가 정한다. 조정은 **올리는 방향만** 권장한다.
- ★**하한 60분이며 그 미만·0·음수·파싱 실패면 기동을 거부한다**(`ProcessingStaleReclaimProperties(validate)`) — 조용한 clamp 로 보정하지 않는다. 회수는 상태를 **되돌리는 조작**이라 증강 파생 폐기 유예와 같은 부류이고, 이 리포에는 `.env` 빈값이 기본값을 무력화해 운영에서만 다르게 동작한 실사고가 있다.
- ⚠ **노드 간 시계 동기(NTP) 전제** — 판정은 **서로 다른 노드가 각각 기록한 시각**(선점 표식 `REG_DT`·진행 로그 `MDFCN_DT`)을 스윕이 도는 노드의 현재 시각과 비교한다. 시계가 어긋나면 임계가 그만큼 밀린다(앞선 시계의 노드가 스윕을 돌면 일찍 뺏고, 뒤처지면 늦게 회수한다). 클러스터 시계 동기는 배포 운영 문서의 항목을 따른다.

**★되돌릴 곳은 「선점 직전 상태」가 정한다 — 이걸 틀리면 데이터가 지워진다**

| 선점 출발 | 어떤 요청 | 배치 단계 복구 | 작업 상태 복구 |
|---|---|---|---|
| `FAILED` | 전체 재기동(②-0, 실패 영상 전용) | `FAILED` | `FAILED` |
| `COMPLETED` | 묶음 재수행(②-2, 완주·라벨링된 영상) | `COMPLETED` | `ASSIGNED` |

- **무조건 `FAILED` 로 되돌리면 안 된다** — 완주 영상이 실패로 뒤집히면 전체 재기동 경로가 열리고, 그 경로는 파이프라인을 통째로 순회해 트랙 보간이 사람이 손댄 보간 라벨을 **전량 삭제·재생성**한다(삭제 이력도 승인 스냅샷도 없어 복구 지점 0). ②-0/②-2 를 분리한 바로 그 파괴다. 축 매핑의 단일 원천은 `ReprocessClaimOrigin`.
- ★**작업 상태도 함께 되돌린다** — 진입 가드가 `LS_RAW_DATA_STATUS` 를 `PROCESSING` 으로 전이시킨 뒤라, 배치 단계만 되돌리면 작업 상태가 `PROCESSING` 에 남아 **작업자가 검수 제출을 못 한다**(상태 머신에 그 출발 전이가 없다). `BatchTransitionService(restoreAfterBundleRerunFailure)` 가 이미 밟은 함정이라 같은 축을 재사용한다(`BatchTransitionService(reclaimStuckProcessing)`). 작업 상태 복구는 `transitionRawDataStatus` 를 그대로 쓰므로 **검수 소유 상태는 덮어쓰지 않는다**.

**★선점 직전 상태는 어디에 남는가 — 신규 컬럼·테이블 없이 기존 배치 로그 축을 재사용한다**

- 그 값은 지금까지 **호출 스레드의 인자**(`AsyncBatchReprocessRunner(runAsync)` 의 `claimOriginStatus`)로만 존재해 **노드가 죽으면 함께 사라졌다**. 그래서 선점 직후 `LS_BATCH_PROC_LOG` 에 **선점 표식**을 남긴다(`ReprocessClaimMarker`) — `PROC_STTS_CD='SKIPPED'` + 전용 `PROC_STEP_CD` 네임스페이스 + `ERR_MSG_CN` 에 출발 축. **수동 스킵 표식**(③)이 이미 확립한 관례와 같은 골격이며, 진행 조회가 `SKIPPED` 를 제외하므로 화면 단계 표시를 오염시키지 않는다.
- **열림/닫힘은 append-only 로 쌓이고 마지막 행이 정한다.** 실행이 어떤 결과로 끝나든(`AsyncBatchReprocessRunner`) · 접수가 거부돼 선점을 되돌렸든 **표식을 닫는다**. ★**닫지 않으면**, 뒤에 **다른 진입 경로**(마킹 브리지·자동 재시도 잡·dev 트리거 — 선점 직전 상태를 기록하지 않는 경로들)로 고착된 같은 영상을 스윕이 **옛 표식의 출발 상태로** 되돌린다(「전체 재기동 성공 → 완주 → 이후 다른 경로로 고착」이면 완주 영상이 `FAILED` 로 강등된다).
- ★★**그래서 표식이 「열려 있다」만으로는 부족하다 — 「이번 에피소드의 것인가」까지 본다 (에피소드 결속)**. 닫힘 행은 **유실될 수 있다**(러너 `finally` 의 기록 실패·프로세스 사망). 그러면 그 표식은 **이미 끝난 옛 에피소드의 잔재**로 남아 이후 아무 `PROCESSING` 에피소드에나 옛 출발 축이 적용된다. 판정에 조건을 하나 더 건다 — **표식이 열린 이후에 배치가 종결(완료/실패)까지 갔던 흔적이 있으면 회수하지 않는다**(`BatchStatusService(progressTerminatedAfter)`).
  - **가르는 신호는 「종결 기록의 유무」다** — 진짜 고착(큐 대기 중 노드 사망)은 **한 단계도 실행하지 못해** 표식 이후 종결 기록이 없다(진행 행이 종결 상태여도 그 시각은 표식보다 **이전**, 즉 직전 실행의 것이다). 반대로 잔재 표식은 그 뒤 파이프라인이 끝까지 가서 `markCompleted`/`markFailed` 가 진행 행을 종결 상태 + 새 갱신 시각으로 바꿔 놓았다.
  - **실행 중(`STARTED`)은 종결이 아니다** — 실행 도중 노드가 죽어 생긴 고착은 회수 대상으로 남는다.
  - ⚠ **남는 사각(인지·수용)**: 「닫힘 행 유실 + 그 뒤 다른 경로 에피소드가 **한 단계 이상 실행하다** 죽음」이면 진행 행이 `STARTED` 라 잔재 판정이 서지 않는다. 더 엄격한 규칙(**표식 이후 진행이 조금이라도 움직였으면 회수 안 함**)은 이 사각을 닫지만, 대신 **실행 중 사망 고착을 회수하지 못한다** — 현재는 후자를 회수하는 쪽을 택했다.
- ★**알 수 없으면 회수하지 않는다 (fail-closed)** — 표식이 없거나 열려 있지 않거나 값이 해석되지 않거나 **잔재로 보이면** 회수하지 않고 **보류**한다. 추측해서 되돌리는 것보다 고착을 남기는 편이 안전하다. 그 결과 **위 다른 진입 경로로 고착된 영상은 회수 대상이 아니다**(그 경로들은 선점 직전 상태를 애초에 기록하지 않는다) — 종전과 같은 상태로 남으며 사람이 본다.

**그 밖의 성질**

- ★★**되돌리기와 표식 닫기는 한 트랜잭션**이다(`ProcessingStaleReclaimTxService(reclaimAndClose)` 가 경계, 두 협력자는 그 경계에 **참여**). 따로 커밋하면 사이에서 죽거나 뒤가 던질 때 **상태는 되돌아갔는데 표식이 열린 채** 남고, 그 표식이 곧 위 잔재 문제가 된다. 조건부 UPDATE 가 0행이면(경합 패배) 표식도 닫지 않으므로 **원자 클레임 성질은 그대로**다.
- ★**회수된 영상을 자동 재시도 큐에 넣지 않는다** — 상태만 되돌리고 **사람이 다시 누르게** 한다. 자동으로 다시 돌면 같은 이유로 또 멈추고, 완주 축이면 위 파괴와 연결된다. 스윕은 재시도 큐·러너·오케스트레이터를 **의존성으로 갖지 않아** 구조로 고정돼 있다.
- **원자 클레임(CWE-362)** — 회수 자체가 「지금 `PROCESSING` 일 때만」인 단일 조건부 UPDATE 라 두 노드가 같은 영상을 동시에 집어도 **정확히 1건만** 성공하고 진 쪽은 감사 기록도 남기지 않는다. Quartz 클러스터링은 **트리거 중복만** 막고 잡 내부 레이스는 막지 못한다.
- ★**후보 스캔은 회전한다 — 앞줄이 회수 큐를 영구 점유하지 못하게** (`ProcessingStaleReclaimSweeper(advanceCursor)`). 후보 조회는 `RAW_SN` 오름차순 + tick 당 상한인데, **판정이 보류된 후보는 상태가 그대로여서 다음 tick 에도 같은 자리에 다시 뽑힌다.** 표식 없는 `PROCESSING` 은 다른 진입 경로가 남기며 **회수해 줄 다른 주체가 없어** 계속 쌓이므로, 그런 영상이 상한만큼 모이면 그 뒤의 **진짜 회수 대상이 영영 판정되지 않아 스윕이 조용히 무력화된다.** 그래서 한 tick 이 상한을 꽉 채웠으면 다음 tick 은 **그 뒤부터** 이어서 훑고, 상한에 못 미치면(끝에 닿으면) 처음으로 돌아온다. **상한 자체는 유지**한다(자원 보호, CWE-770). 커서는 **노드별 인메모리**라 새 DB 컬럼·테이블이 없고, 재기동하면 처음부터 훑는다(정확성 요구 없음 — 잃는 것은 「한 tick 늦게 본다」뿐).
- **감사** — 무엇을 왜 회수했는지 `LS_BATCH_PROC_LOG` 회수 표식 + WARN 로그로 남는다. **보류는 건별이 아니라 tick 당 1줄 요약**(건수 + 대표 `rawSn` 몇 개)이다 — 건별로 찍으면 주기마다 같은 경고가 상한만큼 반복돼 **진짜 회수 경고가 그 잡음에 묻힌다**. 다만 **보류 사실 자체는 반드시 남긴다**(그 영상은 앱이 스스로 풀 수 없어 사람이 봐야 한다). PII·토큰·내부 경로·사용자 입력은 담지 않는다(CWE-209/532/117).
- **전용 데몬 스케줄러**(`@Scheduled` 비의존, 자기 토글 `authoring.batch.stuck-reclaim.enabled`) — 형제 스윕들과 동형이며 남의 토글에 얹지 않는다.
- ⚠ **남는 위험(인지·수용 — 이 스윕이 만든 결함이 아니라 기존 진입 가드의 한계)**
  1. 프레임 수가 매우 많은 영상이 여러 건 연달아 접수되면 뒷줄의 **큐 대기가 임계를 넘을 수 있다.** 그러면 아직 살아 있는 선점이 회수되는데, 뒤늦게 실행이 시작되면 진입 가드가 배치 단계를 다시 원자 클레임하므로 **파이프라인 자체는 정상 수행**된다(상호배제가 그 구간에만 느슨해진다).
  2. 회수 **직후**에 다른 주체가 같은 영상을 선점하면, 큐에서 뒤늦게 깨어난 옛 작업이 **소유권을 확인하지 않고** 병행 실행될 수 있다 — 진입 가드는 「지금 `PROCESSING` 인가」만 보고 「그 `PROCESSING` 이 **내 것**인가」를 구분하지 못한다.
  3. 판정과 조건부 UPDATE 사이의 좁은 창에 **갓 접수된 정상 선점**이 끼어들면 그 선점을 뺏을 수 있다(판정은 무잠금이다).
  - 2·3 을 닫으려면 선점에 **소유권 토큰**을 부여하는 별도 설계가 필요하고, 기본 임계가 24시간이라 도달 가능성이 매우 낮아 **수용**한다. 운영에서 관측되면 임계를 **올린다**(내리지 않는다).

**⑤ 파생영상 취급 — 비대칭이 남아 있다 (미해결)**

- 영상 목록은 원본 전용(`ORGNL_RAW_SN IS NULL`)이라 「실패」 필터에 파생이 나오지 않는다.
- 신규 3종(**스킵 · 해제 · 일괄 재시작**)은 파생영상을 거부한다. **묶음 지목 재수행**(②-2)은 별도 거부 조항을 두지 않아도 파생영상이 도달하지 못한다 — 스킵 자체가 400 으로 막혀 **건너뛰기를 해제한 묶음이 생길 수 없기** 때문이다. 스킵·해제는 **400**(파생 여부는 생성 후 불변인 **영구 조건**이라 재시도 여지가 없다 — 412 는 "지금은 안 되지만 해소되면 된다"인 일시 조건에 쓴다). 미지원 단계와 **같은 상태코드**를 쓰는 것도 의도적이다 — 코드가 갈리면 응답이 "이 영상이 어떤 상태인지" 알려주는 오라클이 된다(CWE-209). 일괄 재시작에서는 그 **건만** 사유와 함께 실패로 기록된다.
- ⚠ **기존 단건 재기동(`POST /v1/videos/{rawSn}/batch/retry`)은 파생영상을 거부하지 않는다.** 계약 변경이라 이번 범위 밖이며 **미해결로 남았다.** 같은 조건에 두 경로가 다르게 동작하는 상태이므로, 나중에 맞출 때는 이 비대칭이 알려진 것이었음을 전제로 한다.
