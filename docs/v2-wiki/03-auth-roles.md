## 3.1 인증·진입 (독립 로그인 없음)

- 저작도구는 **독립 로그인 UI 없음** — 관제서버(내부)/포털 서버(외부)가 발급한 **JWT 토큰을 인계**받는다.
- **토큰 인계 수단은 채널마다 갈린다 (2026-08-27 · ADR-012 개정)** — 아래 표가 정본이다.

| 채널 | 인계 수단 |
|---|---|
| 관제(INTERNAL) | 관제서버와 **동일 도메인 운영** → 브라우저 스토리지(localStorage/sessionStorage) 공유로 JWT 전달 (기존 그대로) |
| 포털(PORTAL) | 포털 Host 가 주입한 **인계 창구**(토큰 획득·갱신·인증 실패 통지·활동 통지)로 토큰을 얻어 **`x-access-token` 헤더**로 전송(Bearer 미사용). access token 은 **Host 메모리에만** 두고 브라우저 저장소를 쓰지 않는다 |

  두 채널 모두 URL 쿼리(`?token=`)는 노출 위험으로 미사용.

  > ⚠ **구 서술 폐기** — *"관제서버와 동일 도메인 운영 → 브라우저 스토리지 공유로 JWT 전달"* 을 **전 채널 규칙으로 읽지 말 것.** 포털이 저작도구 프론트를 자기 화면에서 런타임 실행하는 임베딩(`INT-013`)으로 확정되면서 그 채널에서는 전제가 성립하지 않는다. 저장소나 그 스냅샷을 직접 읽으면 Host 가 토큰을 갱신한 시점 이후로는 **이미 무효가 된 토큰**을 붙잡게 되고, 수십 분을 한 화면에 머무는 저작 화면은 그 파손을 반드시 겪는다 — 포털이 **비협상 조건**으로 제시했다.
  >
  > 해법은 인계 계층을 저장소 직접 읽기가 아니라 **토큰을 얻는 창구 뒤로 추상화하는 어댑터 한 겹**이다. 그러면 관제(저장소)·포털(메모리) 두 Host 를 호출부 분기 없이 지원한다. 개정 전에는 *"인증 진입 경로의 코드 변경이 없다"* 가 전제였으나 폐기됐다.
  >
  > ⚠ **코드 미반영 (2026-08-27 실측)** — `features/auth/tokenIngress.ts` 가 `localStorage` 를 직접 읽고 기본 전략도 `localStorage` 이며, 요청 헤더는 전 경로 `Authorization: Bearer` 다. `x-access-token` 은 레포에 있으나 **방향이 반대**(저작도구 → 관제 outbound 통지 헤더 + 로그 마스킹)이고 inbound 수용은 **0건**이다. Module Federation 설정(`vite.config.ts` 의 `federation`·`exposes`·`remoteEntry`) 자체가 **0건**이다.
- 두 채널 모두 **동일 JWT 발급 서버** → 단일 검증 로직(`JwtAuthenticationFilter`).
- 토큰 `channel` 클레임으로 채널(INTERNAL/PORTAL) 분기. **저작도구 인가 역할(ADMIN/REVIEWER/WORKER/PORTAL_USER)은 JWT `role` 클레임이 아니라 저작도구 소유 `LS_USER_ROLE`(USER_NO→역할)에서 조회**한다 — JWT는 식별·인증(sub·channel·exp·서명) 전담, 인가 역할은 LS 전담(`@PreAuthorize("hasRole('REVIEWER')")`). INTERNAL 채널은 `UserRoleResolver`(Caffeine 캐시 TTL 60s)로 LS 조회, PORTAL 채널은 `PORTAL_USER` 고정.
  - (역할 분리 리팩토링 2026-06) 실제 관제 JWT의 `role` 클레임은 관제 역할(SYSTEM_ADMIN/LEARN_MANAGER 등)이라 저작도구 역할과 무관하므로, 저작도구 인가는 LS 기준으로 일원화했다. 역할 변경 시 캐시는 트랜잭션 커밋 후(AFTER_COMMIT) evict.
- 세션 만료 시 각 상위 시스템 로그인 페이지로 리다이렉트.

화면: `SC-001`(세션 인계 진입 `/ingress`) → channel 클레임으로 `/portal` 또는 `/dashboard` 라우팅. `SC-002`(관리자 등록 `/role-claim`) — role 미부여 시 진입. 화면 이름이 「역할 클레임」이던 것은 역할을 고르던 시절의 것이고, 지금은 부여 역할이 관리자 고정이라 고를 자리가 없다(`ADR-055`). 경로·엔드포인트 이름(`role-claim`)은 그대로다.

> ⚠ **구 서술 폐기(2026-08-19 코드 실측)** — 위 두 화면을 *"`KLID-AT-SC-001`"*·*"`KLID-AT-SC-002`"* 로 부르던 것은 낡은 식별자다. 코드의 1차 식별자는 `SCREEN-NNN`(LogiCraft ID)이고, `KLID-AT-SC-NNN` 헤더는 `NoticeListPage.tsx`·`NoticeDetailPage.tsx` **2개 파일에만** 남은 옛 D2 설계서 체계의 잔재다. 이 위키는 `SCREEN-NNN` 을 `SC-NNN` 으로 축약 표기한다. 근거: `04-screens-ia.md`(§4.1) · `reports/wiki-align-20260819/facts/F3-frontend-screens.md`.

## 3.2 역할

| 역할 | 코드 | 권한 |
|------|------|------|
| **관리자** | **`ADMIN`** | **사용자 관리(역할 지정) · 연동 서버 주소 · 파일 업로드 · 산출물 가져오기 · 관리자 패스워드 교체 · 위험 작업.** ★검수자 권한을 계층으로 물려받는다(`ROLE_ADMIN > ROLE_REVIEWER`) — 검수·배정을 그대로 수행하므로 겸직에 계정이 둘 필요 없다 |
| 검수자 | `REVIEWER` | 시스템 설정(배치·추론·정밀도·비식별)·라벨 마스터·프리셋·이벤트유형·비식별 신고 관리, 작업자 배정·재배정·이력 조회, 검수 승인/반려, 증강 요청·검수, 비식별 요청·옵션 설정, 버전 비교·복구, 수정 통지 발행. ⚠ **사용자 관리는 관리자 소유** |
| 라벨링 작업자 | `WORKER` | 본인 배정 영상 라벨 수정·검수 제출, AI 보조 라벨링, 라벨 버전 저장, 비식별 누락 신고(본인 배정 한정) |
| 포털 회원 | `PORTAL_USER` | (외부 채널) 데이터마트 영상 선택, 기존 라벨 확인·수정·저장, 본인 데이터 다운로드 |

> ### ★역할 4종 + 계층 (2026-08-28 확정, 구속 · `ADR-055`)
>
> ⚠ **구 서술 폐기** — *"ADMIN 역할 없음 / ADMIN 폐지 — 모든 관리 권한은 REVIEWER 에 통합"*. 그 결정(`ADR-003`)은
> **`ADR-055` 가 supersede** 했다. 되살리지 말 것.
>
> - **계층은 「관리자 → 검수자」 한 단계뿐**이다. `WORKER` 를 넣으면 작업자 전용 자리에 관리자·검수자가
>   흘러들고, `PORTAL_USER` 를 넣으면 외부 채널 사용자가 내부 권한을 얻는다(`AC-125`).
> - 계층 덕분에 **기존 `hasRole('REVIEWER')` 99곳을 하나도 바꾸지 않는다.** 배선은 `RoleHierarchy` 한 줄이다.
> - **관리 메뉴는 역할로 가른다** — 검수자에게는 관리자 항목이 보이지 않는다. 관리 화면 URL 은
>   관리자 소유가 `/admin/*`, 검수자 소유가 `/manage/*` 로 갈린다.
> - ⚠ **배포 직후 `ADMIN` 은 0명**이다 — 부트스트랩으로 최초 관리자를 만들 때까지 관리 기능이 잠긴다.

> **역할 저장·부여**: 저작도구 역할은 저작도구 소유 `LS_USER_ROLE`(USER_NO→ROLE_CD) 에 저장·조회한다 — 인가 판정의 단일 진실원이다. 구 관제 권한 매핑 테이블 2종은 참조가 0 이 된 뒤 **V165 로 삭제**됐고, 관제 사용자 마스터는 **V169 로 저작도구 소유 `LS_ACNT_USER` 로 이관**됐다(2026-08). 역할 부여/변경은 `PATCH /v1/users/{userNo}`(**ADMIN**), 첫 역할 부트스트랩은 `POST /v1/auth/role-claim`(관리자 PW + rate limit, **ADMIN 0명일 때만**). LS 역할 미배정 사용자는 보호 엔드포인트 403(fail-closed).

> **★ 역할 클레임 = 관리자 부트스트랩 전용 + 진입 시 작업자 자동등록 (2026-08-28 확정 · `ADR-055`)**
>
> ⚠ **아래 2026-08-04 블록은 폐기됐다** — 자가부여는 **`ADMIN` 이 0명일 때만** 열리고 부여 역할은 **`ADMIN` 고정**이며,
> 그 밖의 진입자는 **인증 통과 시점에 `WORKER` 로 자동 등록**된다(조건부·원자 upsert · 사용자당 사실상 1회 · 기존 역할 미덮어씀 — `AC-1016`).
> 마지막 `ADMIN` 의 강등·비활성은 **409 로 거부**한다(`AC-124`). ⚠ 「0명일 때만」은 2026-08-04 에 사용자가 **명시적으로 거부**했던
> 형태다 — 그때는 좁히면 검수자가 될 길이 없었고 지금은 **관리자가 역할을 부여**하므로 전제가 바뀌었다. **세 번째로 뒤집지 말 것.**
>
> <details><summary>구 서술 (2026-08-04, V169) — 이력 보존</summary>
>
> **★ 역할 클레임 = REVIEWER 자가부여 개방 + 사용자 자동등록 (2026-08-04 확정, V169)**
>
> - **자가부여 가능 역할 = `WORKER`·`REVIEWER`**. 구 정책(A-ISSUE-17)은 `WORKER` 단일이었고 "REVIEWER 는 기존 REVIEWER 가 `/manage` 에서 부여" 를 전제했는데, **신규 설치에는 그 REVIEWER 가 없어** 최초 부트스트랩 경로가 없었다(운영 문서가 dev 편의 경로 `/dev/login` 을 안내하던 결함). ⚠ **잔여 위험을 사용자가 인지·수용**했다 — 관리자 공유 패스워드를 아는 사람은 누구나 REVIEWER 가 되며, **그 패스워드의 관리 수준이 시스템 전체의 권한 경계**다. "보안 강화" 명목으로 WORKER 단일로 되돌리지 말 것.
> - **유지되는 방어**: rate limit(계정+전역) · BCrypt 상수시간 비교 · 평문 패스워드 로그 금지 · INTERNAL 채널 + `role==null` 게이트 · `PORTAL_USER` 거절 · 이미 역할 보유 시 409.
> - **사용자 자동등록**: 사용자 마스터 행이 없으면 클레임 시점에 만든다. 표시 정보(`userId`·`userNm`)는 **관제가 브라우저 `localStorage` 에 넣어 준 값**을 FE 가 요청에 동봉한 것이며, **사용자 식별(`userNo`)은 JWT `sub` 에서만** 취한다(바디에 `userNo` 필드 자체가 없다 — CWE-639/915). 인계값이 없으면 필드를 생략하고 기존 값을 보존한다(하위호환). 관제가 함께 넣는 `authority` 는 **읽지 않는다** — 브라우저 저장소 문자열로 권한을 판정하면 사용자가 값을 바꿔 권한을 올릴 수 있다.

## 3.3 권한 경계 (보안)

- **IDOR 차단**: WORKER는 본인 배정 외 프레임 편집 시 403 (`LabelAccessGuard`)
- **관리 화면**: 관리자 소유 `/admin/*`(사용자 관리·연동 서버 주소·파일 업로드·산출물 가져오기·패스워드 교체·위험 작업) **ADMIN 전용** / 검수자 소유 `/manage/*`(시스템 설정·라벨 마스터·프리셋·이벤트유형·비식별 신고) REVIEWER 전용
  - ⚠ **예외 1건(2026-08-19 코드 실측)** — `GET /v1/manage/labels`·`/v1/manage/labels/**`(라벨 마스터 **조회**)는 REVIEWER 전용이 아니라 **REVIEWER·WORKER·PORTAL_USER 모두 허용**된다. 포털 업로드 라벨링 화면도 이 API로 라벨 분류·표시명·색상을 읽기 때문이다. 이 예외는 `SecurityConfig`의 순서 있는 매처에서 `/v1/manage/labels`(GET) 매처가 `/v1/manage/**`(REVIEWER 전용) 매처보다 **먼저** 선언돼 있어 성립한다 — 인가 판정의 1차 원천은 메서드 `@PreAuthorize`가 아니라 이 매처 순서다(판정 단일 지점은 `SecurityConfig.securityFilterChain` — [19 §연동 서버 주소 설정](19-external-security-cvat.md#연동-서버-주소-설정-r11-2026-08-10)의 「판정 단일 지점」 원칙과 같은 취지). 근거: `reports/wiki-align-20260819/facts/F1-backend-api.md` §3(매처 10·11번).
- **포털 격리**: 저장 시 원본 미수정, `LS_PORTAL_USER_LABEL` 별도 적재 (ADR-013)

### 관리자 단기 유효창 (R11, 2026-08-10)

연동 서버 주소 4종은 **REVIEWER 권한만으로는 바꿀 수 없다**. 잘못 바꾸면 학습데이터가 통째로 다른 서버로 나갈 수 있는 값이라, **그 순간 관리자 공유 패스워드를 다시 확인**한 짧은 창에서만 저장된다.

| 축 | 정책 |
|----|------|
| 발급 | `POST /v1/manage/admin-session` (REVIEWER). 성공 200 `{token, expiresAt}` · 패스워드 불일치·미인증 401 · 권한 없음 403 · 시도 초과 429 |
| 재사용 자산 | 패스워드 해시 `authoring.auth.admin-claim-password-hash`(BCrypt·상수시간 비교) + 속도 제한(`RoleClaimRateLimiter`). **새 패스워드 체계를 만들지 않았다.** 판정은 `AdminPasswordVerifier` 한 곳이 소유하며 권한 자가부여도 같은 판정을 쓴다 |
| 진입점 분리 | 권한 자가부여(`/v1/auth/role-claim`)는 **역할이 없는 사람 전용**(이미 역할이 있으면 409)이라 그대로 쓸 수 없다. 방어는 공유하되 진입점만 나눴다 |
| 유효기간 | 기본 10분 · **상한 30분**(`authoring.auth.admin-session.ttl-minutes`). 상한 초과 설정은 상한으로 낮춰 적용하고 0 이하는 기본값으로 되돌린다 |
| 유효성 판정 | **서버가 소유**한다. 만료 시각이 서명 대상 안에 있어 클라이언트가 늘릴 수 없고, 서버는 **저장 요청마다** 서명·만료·발급 대상을 다시 본다 |
| 2노드 | **무상태 서명 토큰**(JWT 서명 키에서 파생한 별도 키로 HMAC). 어느 노드에서 발급해도 다른 노드에서 검증되며 공유 저장소·새 테이블이 필요 없다 |
| 권한 승격 없음 | 토큰에 **역할 클레임이 없다**. 소비처는 연동 주소 키 저장 한 곳뿐이고, 인가는 기존 `@PreAuthorize` + 서비스 이중 검증이 그대로 담당한다 |
| 인증 토큰과 분리 | 서명 키가 파생 키라 이 토큰은 인증 JWT 로 통하지 않고, 인증 JWT 도 이 자리에서 통하지 않는다 |
| 전달 | `X-Admin-Session` **헤더**. 바디에 두면 설정 값과 자격증명이 한 구조에 섞인다. 게이트는 컨트롤러가 아니라 **서비스**에 있어 진입점이 늘어도 우회되지 않는다 |
| 화면 | 잠금이 기본. 「관리자 설정」 → 패스워드 → 남은 시간 표시. 토큰을 브라우저 저장소에 두지 않아 **새로고침하면 잠긴다** → [19 §연동 서버 주소 설정](19-external-security-cvat.md#연동-서버-주소-설정-r11-2026-08-10) |

### 역할 표시와 메뉴 인가의 단일 진실원 (2026-08-28)

관리자 역할을 신설한 라운드가 **같은 사실을 두 곳에 적어 둔 자리**를 남겼고, 그것을 각각
한 곳으로 모은다. 이 저장소가 라벨 색·표시명에서 반복해 문제 삼은 「두 번째 진실원」 패턴이다.

**① 역할이 없는 사람에게 역할을 지어내지 않는다.**
상단 헤더와 접근 거부 화면이 역할이 없을 때 **작업자로 채우고 있었다** — 역할을 아직 받지
못한 사람에게 사실과 다른 역할을 보여준 것이다. 이제 둘 다 **「미배정」**으로 보이며 경고
아이콘을 함께 둔다(역할 없음은 정상 상태가 아니라 조치가 필요한 상태이고, 색만으로는 그
차이가 전달되지 않는다). 넷 중 하나로 임의로 채우지 않으며, **모르는 값**은 비우지 않고
받은 값을 그대로 중립 색으로 노출한다 — 「모르는 역할」과 「역할 없음」은 다른 사실이라
같은 표시로 합치지 않는다. 사양은 `SHELL-001`(상단 헤더)·`SCREEN-003`(접근 거부)이 소유한다.

> ⚠ `SCREEN-003` 은 본문이 *"claims.role 구독(**기본값 WORKER**)"* 이라고 적어 **오동작을
> 사양으로 명시**하고 있었다. 코드만 고쳤다면 다음 사람이 그 설계를 근거로 되돌렸을 자리다.

**② 좌측 메뉴 노출과 라우트 인가는 한 선언에서 파생된다.**
그 전에는 메뉴가 항목마다 허용 역할을 갖고 라우터가 자기 허용목록을 따로 걸어, 두 곳을
손으로 맞추고 있었다(코드 주석이 「같은 조건이어야 한다」고 **경고만** 했다). 설계는 이미
이걸 금지한다 — `SHELL-001` 이 *"셸과 메뉴 정의 두 곳에 같은 목록을 적으면 한쪽만 갱신돼
어긋난다"* 고 적고, `NAV-001` 이 노드마다 필요한 역할을 갖춘 완전한 단일 진실원이다.
즉 이번 변경은 설계를 바꾼 것이 아니라 **코드를 설계 쪽으로 끌어온 것**이다.

- **메뉴에 없지만 경로로 도달하는 화면**(마킹·영상 상세·라벨링 캔버스·검수 상세·증강 결과·
  공지 상세/작성/수정)의 인가도 그 선언이 함께 담는다 — 「메뉴에서 파생」만으로는 덮이지 않는다.
- **관리자 페이지의 단기 유효창은 역할과 별개 축**이다. 노출·인가를 가르는 축은 역할이며
  유효창을 노출 조건으로 쓰지 않는다(그러면 들어갈 길 자체가 사라진다).

**③ 관리 영역 화면에 접근성 기준이 생겼다.**
그 전까지 접근성 기준은 **포털 채널에만** 있었다(내부 채널에 있는 것은 웹표준·크로스브라우징
이고, 그 본문이 스스로 접근성과는 별개 관점이라고 적는다). 기준이 없으면 자동 감사를 붙여도
통과·실패를 가를 근거가 설계에 없어 **시험 코드가 사실상 사양이 된다.** `NFR-022`(내부 화면
접근성)를 신설해 **관리 영역 화면 자동 감사 위반 0(WCAG 2.1 AA)** 을 기준으로 세웠다.
적용은 사용자 관리·연동 서버 주소·패스워드 교체·위험 액션이며, 나머지 내부 화면으로 넓히는
것은 별도 결정이다. 자동 감사는 사람의 확인을 대체하지 않는다 — 위반 0 은 최소선이다.

**④ 개발 환경에서 관리자 화면을 열어 볼 수 있다.**
개발 시드에 관리자가 없어 관리자 토큰 발급이 「userNo 를 명시하라」로 막혔고, 관리자 화면이
시험으로만 고정돼 **사람이 눌러 볼 수단이 없었다.** 시드에 관리자를 넣고 기본 번호를 주되,
그 둘이 어긋나면 토큰의 주체가 다른 사람의 행을 가리키므로(과거 실제 사고) 짝을 고정하는
가드를 함께 세웠다.

## 3.4 사용자 관리 (ADMIN)

화면: `SC-024`(사용자 관리 `/admin/users`) — 사용자 목록·역할 설정. 코드: `user/UserController`.

> ⚠ **구 서술 폐기(2026-08-27)** — *"`/manage/users`"* 는 더 이상 이 화면의 주소가 아니다. 이 화면은
> **「관리자」 그룹(`/admin/*`)으로 옮겨갔고 진입에 관리자 패스워드 확인이 필요하다** — 역할을 바꾸는
> 일이라 검수자 권한 **위에** 단기 유효창이 가산된다(위 §3.3) → [04 §4.2](04-screens-ia.md).

> ⚠ **구 서술 폐기(2026-08-19 코드 실측)** — *"`KLID-AT-SC-024`"* 는 낡은 식별자다. 코드의 1차 식별자는 `SCREEN-024`(축약 `SC-024`) — 근거는 위 §3.1 각주와 동일.

- **역할 변경 저장 버튼의 활성 조건**(2026-08-08 정정) — **역할을 선택하지 않았거나 선택한 역할이 원래 값과 같으면**(변경 없음) 비활성이다. 구 동작은 미선택만 막았다. 두 사유는 동시에 성립하지 않으며 **화면이 잠긴 사유를 알린다**("변경된 내용이 없습니다. 다른 역할을 선택하면 저장할 수 있습니다") — 이유 없이 잠긴 버튼은 고장으로 읽힌다. 다른 역할로 바꿨다가 되돌리면 다시 잠긴다. 저장 진행 중 비활성은 종전과 같다.
- **역할 필터는 서버 전체 기준이다**(2026-09-01 정정) — 구 동작은 한 페이지를 먼저 가져온 뒤 **그 안에서만** 걸렀다. 그래서 ①찾는 역할의 사용자가 1페이지 밖에 있으면 결과가 비었고(뒤 페이지에 있어도 도달할 수 없었다) ②총 건수가 **필터 이전 합계**라 「3건 표시 / 총 87건」 같은 상태가 됐다. 필터를 조회 계층으로 내려 둘 다 닫았다 — 총 건수는 이제 실제 매칭 수와 같다. **역할을 지정하지 않으면 동작은 종전과 같고**(전체·등록순) 요청·응답 스키마도 바뀌지 않았다. 역할 행이 없는 사용자(미배정)는 어떤 역할 필터에도 걸리지 않는 성질이 유지된다. ⚠ 이 결함은 **한 페이지에 다 들어가는 데이터로는 재현되지 않는다** — 필터 결과가 맞는지만 보는 확인은 이 부류를 구조적으로 놓친다.
- **역할을 바꾸면 「바꾼 사람」이 남는다**(2026-09-01) — `LS_USER_ROLE.MDFR_ID` 에 인증 주체가 기록되고 로그에도 함께 실린다. 그전까지 남는 것은 대상뿐이라 **권한 상승의 주체**를 알려면 유효창 발급 로그와 시각으로 이어 붙여야 했다 → [18 §18.2](18-database.md). ⚠ 관리자 부트스트랩(최초 관리자 자가부여) 경로는 이 값을 쓰지 않아 그 행만 비어 있다(별건).
- **목록 하단 페이저에서 총 건수 표기가 사라졌다**(2026-08-08) — 공용 페이저가 총 건수 요약을 갖지 않게 되었고 이 화면에는 건수를 소유한 다른 요소가 없다 → [04 §4.2](04-screens-ia.md).
