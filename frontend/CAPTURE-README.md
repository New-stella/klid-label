# 단위시험 증적 촬영 — 실행 안내

CBD 산출물 **I2 단위시험 결과서**의 「시험결과」 칸에 들어가는 화면 증적을 찍는다.
사람이 직접 돌리는 절차이며 도구의 도움이 필요 없다.

> ★**처음부터 새로 준비해야 한다면 `CAPTURE-SCENARIO.md` 를 먼저 읽는다.**
> 이 문서는 도구 사용법이고, 그쪽이 **무엇을 어떤 순서로 준비해 찍는가**다 —
> 영상 인입 · 비식별 확인(해시) · 마킹 배정 경로 · 값의 유래 · 촬영 순서 · 검증 세 축.

---

## 1. 한 번만 하는 준비

```bash
cd frontend
npm install                        # playwright 포함
npx playwright install chromium    # 브라우저 실물
cp capture.env.example capture.env
vi capture.env                     # ← 값을 그 서버 기준으로 채운다
```

⚠ **`capture.env` 의 ID 값은 서버마다 다르다.** 남의 서버 값을 그대로 쓰면 *없는 영상·없는
프레임*을 열고도 그럴듯한 화면이 찍힌다. 실제로 그렇게 찍힌 증적이 있었다. 그 서버의 DB 에서
값을 확인해 넣는다.

```sql
-- 마킹 대상 영상 (비식별이 끝나 마킹 가능한 것)
SELECT raw_sn, vms_clip_id, data_stts_cd FROM klid_at.ls_data_raw
 WHERE data_stts_cd IN ('MARKING_READY','COMPLETED') ORDER BY raw_sn DESC LIMIT 5;

-- 프레임 번호
SELECT src_sn, raw_sn, frm_no FROM klid_at.ls_data_src ORDER BY src_sn LIMIT 20;
```

## 2. 촬영

```bash
./run-capture.sh                 # 전 케이스 + 증적 원장 생성
./run-capture.sh 003-01 014-01   # 지정한 케이스만
./run-capture.sh --list          # 촬영 가능한 케이스 목록
./run-capture.sh --manifest-only # 이미 찍힌 파일로 원장만 다시 만든다
```

돌리기 전에 스스로 점검한다 — node · playwright · chromium · **서버가 실제로 200 을 주는가** ·
dev 로그인 창구가 열려 있는가. 하나라도 어긋나면 촬영하지 않고 멈춘다. **빈 화면을 조용히
찍는 것이 가장 나쁜 결과**이기 때문이다.

### 결과

```
<CAPTURE_OUT>/KLID-AT-UT-003-01-cut1.png   …   찍힌 컷
<CAPTURE_OUT>/../capture-manifest.json           증적 원장 (산출물 생성기가 읽는다)
```

원장은 매 실행 끝에 **찍힌 파일을 훑어 다시 만든다.** 손으로 고치지 않는다.

## 3. 포털 케이스(024·027)는 준비가 하나 더 있다

**포털 화면은 관제 채널 배포본에 아예 없다.** 라우트가 빌드 시점에 빠져 404 이며 런타임
잠금이 아니다. 그래서 포털 채널로 빌드한 앱을 로컬에 따로 띄우고 그것을 가리켜야 한다.

그런데 그 앱을 `localhost` 로 띄우면 브라우저가 `Origin: http://localhost:15173` 을 보내고,
서버의 CORS 허용목록에 그 오리진이 없어 **403** 이 난다. 허용목록이 비어 있는 것은 지금
같은 출처로만 쓰이기 때문이며 **의도된 설정**이다. 그래서 서버를 고치지 않고, Origin 만 떼는
중계를 하나 띄워 우회한다.

```bash
cd frontend
set -a; . ./capture.env; set +a

node capture-origin-proxy.mjs &                                   # ① :15174 중계
BACKEND_ORIGIN=http://localhost:15174 VITE_BUILD_CHANNEL=portal \
  npx vite --port 15173 &                                         # ② 포털 채널 FE

./run-capture.sh 029-01 030-01                                    # ③ 촬영
```

실측으로 확인한 동작 — 같은 요청을 서버로 **직접** 보내면 `403`, **중계를 거치면** `401`
(= Origin 없는 요청과 같아진다. 401 은 토큰이 없다는 뜻이라 정상이다).

⚠ **이것은 촬영용 우회이지 CORS 문제의 해소가 아니다.** 포털 임베딩이 실제로 붙을 때는
서버 허용목록에 그 Host 오리진을 넣어야 한다. 이 중계가 그 사실을 가려서는 안 된다.

촬영이 끝나면 두 프로세스를 끈다.

## 4. 실패했을 때

실패는 `!! <케이스ID> 실패: <사유>` 로 나온다. 그 케이스만 다시 돌린다.

| 사유 | 뜻 | 할 일 |
|---|---|---|
| `화면 확인 실패 [...]` | 그 화면이 안 떴다 | 그 서버에 해당 데이터가 있는지 확인 |
| `영상이 재생 가능 상태가 되지 않았다 [...]` | 영상이 안 떴다 | 딸린 진단값(주소·readyState·해상도·오류코드)을 본다 |
| `미정의 케이스` | 하네스에 그 케이스가 없다 | `--list` 로 확인 |

⚠ **실패를 무시하고 넘어가지 않는다.** 실패한 케이스는 원장에 안 들어가고, 그러면 산출물의
그 자리가 빈 칸으로 나간다.
⚠⚠ **더 나쁜 경우 — 실패해도 원장은 차 있다.** 원장은 폴더의 파일을 훑어 만들므로, 그 케이스에
**앞 회차 그림이 남아 있으면** 실패했는데도 원장이 채워진다. 규격을 바꾼 회차(예: 해상도 변경)에는
**파일 크기로 낡은 것을 골라내야** 한다. 실측 2026-09-09: 실패 13건인데 원장은 48/90 그대로였다.

### ★ 한 번 돌리면 소진되는 케이스 — 다시 찍으려면 재료를 새로 만든다

이 케이스들은 **자기 전제조건을 스스로 소비**한다. 그래서 같은 서버에서 두 번째로 돌리면 실패한다.
「케이스마다 시작점을 되돌린다」가 이들에게는 성립하지 않는다.

| 케이스 | 소비하는 것 | 다시 찍으려면 |
|---|---|---|
| `011-01` 마킹 | 마킹을 완료시켜 영상이 `MARKING_READY → … → COMPLETED` 로 넘어간다 | `CAPTURE_RAW_SN` 을 **다른 `MARKING_READY` 영상**으로 바꾼다 |
| `007-01` 적재 | 그 클립이 적재돼 목록에 남는다(cut1 은 「없어야」 한다) | `CAPTURE_INGEST_CLIP` 을 **아직 적재 안 된 이름**으로 바꾸고, cut1 뒤에 인입 행을 넣는다 |
| `025-01`·`025-02` 증강 결정 | 활용 결정 대기 한 건을 채택·반려로 확정한다 | 결정 대기인 증강 결과가 남아 있어야 한다 |
| `019-01` 검수 승인 | 검수 건을 승인해 대기 목록에서 뺀다 | 승인 대기인 검수 건이 있어야 한다 |

```sql
-- 마킹 가능한 영상
SELECT raw_sn, vms_clip_id FROM klid_at.ls_data_raw
 WHERE data_stts_cd='MARKING_READY' AND de_ident_yn='Y' ORDER BY raw_sn DESC;
-- 라벨링 화면이 열리는 프레임 (배정 + 이미지 실재)
SELECT s.src_sn, s.raw_sn FROM klid_at.ls_data_src s
  JOIN klid_at.ls_task_altmnt a ON a.raw_data_id=s.raw_sn AND a.task_type_cd='LABELER'
 WHERE s.src_file_path_nm IS NOT NULL ORDER BY s.src_sn;
```
⚠ **프레임은 「배정됐는가」와 「이미지 파일이 있는가」를 둘 다 봐야 한다.** 실측 2026-09-09:
AI 케이스가 쓰던 프레임은 **배정 없는 PENDING 영상**의 것이라 화면이 안 열렸고, 추적 케이스가 쓰던
프레임은 **이미지 경로가 비어** 있어 검출이 구조적으로 0이었다. 둘 다 「AI 가 아무것도 못 찾는다」로
보였지만 **원인은 데이터**였다.

## 5. 알아 둘 것

- **촬영에 쓰는 것은 전부 `frontend/` 안에 있다** — `capture-evidence.mjs` ·
  `capture-query-evidence.mjs` · `capture-origin-proxy.mjs` · `run-capture.sh` · 이 문서.
  밖에 두면 playwright 를 못 찾고, **다음에 다시 뽑을 때 그 파일이 없다.**
- ★**찍힌 PNG 와 원장은 git 에 두지 않는다**(사용자 확정 2026-09-09). 용량이 크고 히스토리에
  영구히 남기 때문이다. `.gitignore` 가 `captures/` · `capture-manifest.json` · `capture.env` 를
  막는다 — `CAPTURE_OUT` 을 레포 안으로 잡아도 커밋되지 않는다.
  ⇒ **다른 기계에는 증적이 없다.** 산출물을 다시 뽑으려면 **촬영부터 다시** 해야 하고,
  그러려면 대상 서버가 그 상태여야 한다. 산출물 생성기에 `--captures` · `--captures-root` 로
  그 폴더를 가리켜 준다. 안 주면 증적 블록이 **아예 안 나간다**(마커도 되지 않는다).
- ★**증적은 1920×1080 화면 한 장이다**(2026-09-09 사용자 확정). 한 컷을 스크롤해 여러 장으로
  나누지 않는다 — 나뉜 장은 내용이 중간에서 잘려 어색하다. `fullPage` 로 길게 이어붙이는 것도
  하지 않는다(모니터에 없는 그림이 된다).
  ⇒ 검증 대상이 첫 화면 아래에 있으면 **부분 캡처**(`shotEl`)로 그 자리만 찍는다. 부분 캡처는
  허용되며, 스크롤 분할이 그것을 대신하지 않는다. `CAPTURE_MAX_PAGES` 를 2 이상으로 올리면
  **폐기된 그 동작이 되살아난다.**
- **컷 수와 파일 수는 다르다.** 같은 순간·같은 화면을 두 케이스가 나눠 쓰는 자리가 있어
  (`026-01`↔`026-02-cut2`, `020-01`↔`019-01-cut2`) 파일 하나가 두 번 실린다.
  원장은 **컷 수**로 세지 파일 수로 세지 않는다.
- **`prep-*` 는 촬영이 아니라 사전 준비**라 `--all` 에서 빠진다. 필요하면 이름을 직접 준다.
- 촬영은 **실제 데이터를 만들면서** 돈다(설정을 바꾸고, 라벨을 그리고, 검수를 넘긴다).
  같은 서버에서 반복해 돌려도 되도록 케이스마다 시작점을 되돌리지만, **운영 데이터가 있는
  서버에서는 돌리지 않는다.**
