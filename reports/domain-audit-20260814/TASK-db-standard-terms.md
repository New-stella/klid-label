# 별도 과제 — DB 물리명 표준용어 정합 (마이그레이션 동반)

> **사용자 확정 2026-08-15**: *"마이그레이션 별도 과제로"* + 자기등록 용어(`APLY_DT`)도 *"마이그레이션 과제에 합침"*.
> 출처: LogiCraft 도메인 감사 클러스터 **C7** · 1차 수정 라운드에서 **ERD 단독 수정 불가**로 판정돼 분리됨.

---

## 1. 왜 별도 과제인가 — ERD 는 틀리지 않았다

감사는 이것을 *"ERD 표준용어 위반"* 으로 분류했으나, **실물 스키마(`deploy/onprem/db/schema.sql`)와 대조하니 지목된 물리명이 전부 실물과 일치**한다.

⇒ **ERD 는 실물을 충실히 반영하고 있고, 비표준인 것은 DB 자신**이다.
⇒ ERD 만 고치면 **ERD↔DB 드리프트를 8건 새로 만든다.** 그래서 1차 라운드에서 **DB 를 건드리지 않는 1건만** 처리했다:

| 처리 완료 | 내용 |
|---|---|
| `ERD-021.LS_CONTROL_NOTIFY_FALLBACK.SEND_RSLT_CD` | 논리명 `발송결과코드` → **`전송결과코드`**(등록 용어명과 일치). 물리명·길이는 이미 정합 |

## 2. 대상

### ★★2-0. 착수 전 실측이 이 문서의 전제를 뒤집었다 (2026-08-15) — 아래 표보다 이것을 먼저 읽어라

**이 문서 §2-1 의 판정은 단어(word) 사전만 보고 내린 것이라 틀렸다.** 용어(term) 축을 함께 보면 결론이 갈린다.

**대상 8건 중 6건이 이미 등록된 사업표준용어다** — 출처가 우리 자신이다:
```
사업표준용어.csv
  배정아이디 ASSIGNMENT_ID · 행위자사용자번호 ACTOR_USER_NO
  대상사용자번호 SUBJECT_USER_NO · 이전사용자번호 PREV_USER_NO   (출처=KLID-저작도구 ERD-014)
  큐일련번호 QUEUE_SN · 사장큐진입일시 DLQ_DT                    (출처=KLID-저작도구 ERD-021)
반면 제안한 대체명 ALTMNT_ID · ACTR_USER_NO · TRGT_USER_NO · BFR_USER_NO 는 용어 축 0건
```

★**이 저장소는 정확히 같은 판단을 이미 내렸다** — `V5__rename_queue_outbox_columns_to_std.sql` 헤더(`PAYLOAD_CN` vs `PYLD_CN`):
> *"우선순위 규칙의 해석 단위는 **등록된 용어**이지 낱말 재조합이 아니다. 「단어 조합」은 **등록된 용어가 없을 때** 쓰는 규칙이다."*
> *"다만 **사전 자체의 갈림은 여전히 미결**이다 — 사업표준**단어**에는 `PYLD` 로만 등록돼 있어… 그 정합은 **별건**이다."*

⇒ **V5 선례를 적용하면 6종은 이미 정합**이고, 남는 것은 V5 가 "별건"으로 미룬 것과 **같은 종류의 단어↔용어 사전 갈림**이다.
⇒ §2-1 의 `QUEUE_SN`·`DLQ_DT` 항 *"양 사전 0건 — 대응 표준어가 없다"* 도 **정정 대상**이다. **용어 축에는 있다.**

### 그래서 진짜 위반은 3건이다

| 대상 | 축 | 근거 |
|---|---|---|
| **`APLY_DT`** | **용어 축 직접 충돌** | 행안부에 **`APLY_DT`=신청일시**·**`APLCN_DT`=적용일시**가 **둘 다 등록**돼 있고 우리 뜻은 적용이다 |
| `LS_TASK_ASSIGNMENT` | 단어 축(용어 등록 없음) | 테이블명은 용어 등록으로 보호되지 않는다 |
| `LS_TASK_EVENT_LOG` | 단어 축 + **자기모순** | 같은 테이블 컬럼은 이미 `EVNT_ID`·`EVNT_TYPE_CD` 인데 **테이블명만 `EVENT`** |

⚠ **`APLY_DT` 는 실수가 아니라 의도된 override 다** — 우리 사전 등록 설명에 적혀 있다: *"gov 표준 'APLY_DT=신청일시'와 약어 충돌하나 우리 의미는 적용일시라 override 등록."* **알고 내린 결정을 뒤집는 일**이므로 사용자 확정 사항이다.

### ⏸ 사용자 판정 대기 3건 (2026-08-15 질의, 미회신)
1. **해석 단위** — (가) V5 선례 유지: 6종 그대로, `APLY_DT`+테이블 2종만 / (나) V5 반전: 단어 축 위반이면 전부 개명(그러면 V5 의 `PAYLOAD_CN` 결정도 재검토 대상이고 사업사전 6개를 폐기·재등록해야 한다) / (다) 사전부터 정리
2. ✅ **`APLY_DT` override 를 뒤집기로 확정(2026-08-15 사용자)** — `APLCN_DT` 로 개명 완료(`V8`), 사업사전 override 행은 **삭제**(행안부에 이미 있어 중복이므로 개명이 아니라 삭제). ⚠ 구 서술이 든 두 번째 근거 `DE_IDNTF_APLCN_DT` 는 **물리 컬럼으로는 없고 용어 사전에는 있다** — 축을 나눠 읽을 것(아래 §2-1 표)
3. **착수 순서** — `STTS_CD` 단독 먼저 / 테이블 개명까지 한 번에 / 전부

## 4. 절차 (순서 의존)

1. **기존 데이터 검증** — `STTS_CD` 16자 초과 행 수, 개명 대상 컬럼의 참조 범위
2. **마이그레이션 작성** — 신규는 **`V7` 부터**(Flyway 스쿼시 완료: 라이브는 `V1`~`V6`)
   - 선례: **`V5__rename_queue_outbox_columns_to_std.sql`** 이 컬럼 축 개명 선례이며 헤더에 *"테이블명 자체 · 인덱스/제약 이름은 별건"* 이라 명시돼 있다
   - ⚠ **테이블 개명**(`LS_TASK_ASSIGNMENT`·`LS_TASK_EVENT_LOG`)은 인덱스·제약·FK 이름까지 따라와야 한다
   - ⚠ **마이그레이션 파일에 `${...}` 를 쓰지 말 것** — 주석 안이라도 Flyway placeholder 파싱이 실패한다
   - ⚠ **`public.` 리터럴 금지** — 스키마는 `klid_at` 이며 `current_schema()` + 비한정 식별자를 쓴다
3. **코드 반영** — 엔티티 `@Column`/`@Table` · JPQL·네이티브 쿼리 · QueryDSL Q클래스 · 테스트
   - ⚠ **식별자 rename 은 XS 가 아니다** — by-name DI·리플렉션·MapStruct 에 걸려 **컴파일은 통과하고 테스트만 잡는** 부류다
4. **`deploy/onprem/db/schema.sql` 재생성**
5. **ERD ITEM 동조** — `ERD-014`·`ERD-021`·`ERD-027`
6. **★`CDIAG`·`SCREEN` 동시 cascade** — ERD 만 고치면 새 불일치가 생긴다
   - 실측 예: **`EVNT_TYPE_CD` 가 ERD 5 / SCREEN 8 / 실물 11 로 삼중 분기** — 이 3자 정합은 이 과제와 별개로도 미해결이다
   - ⚠ **클래스 다이어그램은 Java 속성 축**이다(`eventTypeCd`) — DB 물리명(`EVNT_TYPE_CD`)과 **둘 다 맞다.** 감사가 이 혼동으로 과잉 호출 5건을 냈다
7. **사업 사전 정정** — 수정 전 **`createdBy` 확인**(`null` = KLID-BM 배포분 = 우리 대상 아님)

## 5. 위험

- **테이블 개명은 관제 협의 대상일 수 있다** — `LS_*` 는 저작도구 소유라 자체 관리 가능하나, **데이터마트 뷰 4종(`V_COMPLETED_*`)이 이 테이블들을 참조**하면 관제가 SELECT 하는 계약면이 흔들린다. 착수 전 뷰 정의 확인 필수
- **`STTS_CD` 축소는 비가역** — 초과 데이터가 있으면 잘린다
- 개명 규모가 커서 **FULL 회귀 필수**(backend 6,656 + frontend 3,142 + ai-server 145)
