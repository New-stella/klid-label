## 2. ★감사가 틀린 것 — 되돌리지 말 것

**셋 다 코드를 열어서 갈렸다.** 감사 리포트를 그대로 따랐으면 결함을 만들었을 건들이다.

### 2-1. C8 진단이 반대였다
감사: *"UC 의 `belongs_to_domain` 이 끊겨 AC 가 도메인에 안 붙는다."*
**실측 반증**: `UC-011`·`UC-013` 은 **처음부터 귀속돼 있었는데도** 딸린 AC 의 `derived_domain_ids` 가 `[]` 였다. 결정적 대조군 — `AC-022` 는 도메인이 정상 계산되는데 그 사슬의 **`UC-023` 은 자기 귀속이 아예 없다.**
⇒ 값을 만드는 것은 **`realizes_dfeats` 가 가리키는 DFEAT 의 도메인**이다. 실제 귀속 결손도 6건이 아니라 **3건**이었다.

### 2-2. C2 처방이 플랫폼상 불가능하다
감사: *"고립 ADR 을 **배선**으로 해소하라."*
**실측 반증**: `ADR-026` 에 참조 4건을 넣어도 `links.created: 0`, `get_neighbors` forward/backward **0**. 대조군 `ADR-013`(참조 5건)·`ADR-008`(2건)도 **똑같이 0**.
⇒ **ADR 의 `references` 는 애초에 그래프 엣지를 만들지 않는다.**

### 2-3. D006 「지배적 결함 4」는 오탐 — 고쳤으면 대시보드가 망가졌다
감사: *"`SCREEN-011` 의 `COMPLETED` 를 `APPROVED` 로."*
**실측 반증**: `AssignmentWorkStatus.COMPLETED(Set.of("APPROVED"))` 가 **배정 목록 표시축의 정상 매핑**이고 `DashboardPage.tsx` 진행률이 그 값을 소비한다. 이 축은 `APPROVED` 를 **반환하지 않는다.**
⇒ 바꿨으면 **검수완료 작업이 매번 진행률 0%** 로 떨어졌다. 감사가 든 논거(*"같은 화면 `sections[3]` 은 이미 APPROVED"*)는 **다른 API·다른 축**이라 반례가 못 된다.

### 2-4. 그 밖의 과잉 호출 5건
`CDIAG-013` 물리명 4건 + `CDIAG-007` `eventSeq` — **클래스 다이어그램은 Java 속성 축**인데 감사가 **DB 물리명 축**과 비교했다. `eventTypeCd`(Java)와 `EVNT_TYPE_CD`(컬럼)는 **둘 다 맞다.**

### 2-5. 소견 1건 정정
D016 이 *"`IDMP_KEY`·`DLQ` 는 자기등록이 아니다"* 로 묶었으나, CSV 실측상 **`IDMP_KEY` 만 프로젝트 등록**이고 **`DLQ_DT` 는 `ERD-021` 자기등록**이다(독립 근거가 못 된다).

## 3. ★확정 사실 — 재조사 불필요

### 3-1. `COMPLETED` 는 다섯 갈래이고 **하나만** 오류다
| 축 | 소유 | 판정 |
|---|---|---|
| **검수 워크플로** | `LsRawDataStatus.STTS_COMPLETED` | **도달 경로 없음**(`src/main` 사용 0건) — 종결은 `STTS_APPROVED`. **유일한 정정 대상** |
| 배치 단계 | `LsDataRaw.DATA_STTS_COMPLETED` | 정상·실사용 |
| FE 표시(검수 응답) | `ReviewResponse.mapToFeStatus` | 정상 계약 |
| FE 표시(배정 목록) | `AssignmentWorkStatus` | 정상 — **고치면 진행률 0%** |
| 이벤트·뷰 이름 | `TASK_COMPLETED`·`V_COMPLETED_*` | 정상 고유명사 |

### 3-2. `derived_domain_ids` 는 저장된 투영이다
UC 를 고치면 AC 는 **`stale` 표시만** 되고 값은 `[]` 그대로다. **그 AC 자신에게 메타-only 쓰기**를 해야 재계산된다(대조군 2건 확인). 다중 파생은 **합집합**.

### 3-3. 미materialize 축 4종 (플랫폼 — 우리가 고쳐도 해소 안 됨)
`ADR.references` · `EVT→EVT`(`consumes`/`triggers`) · `AC.covered_by_features` · `CDIAG.referenced_items`.
마지막 건은 무관한 두 ITEM(`CDIAG-005`·`CDIAG-010`)이 같은 증거를 줘 확정됐다 — 스키마는 `references (generic) → *` 를 선언하는데 실제로는 `realizes_features`/`depicts_dfeats` 에서만 추출된다.

### 3-4. `DE_IDENT_YN` 과 `DE_IDNTF_YN` 은 **둘 다 맞다**
뷰가 `m.de_ident_yn AS de_idntf_yn` 으로 별칭을 단다 — **테이블 컬럼**과 **관제 계약면(뷰 출력명)**. 전역 치환하면 계약면이 깨진다.

## 4. 방법론 — 이번에 확정된 절차

### 4-1. 전수 스캔의 모집단
```
kit-export                       → 873  (활성만)
kit-export?include_retired=true  → 951  (draft 664 · approved 209 · deprecated 73 · superseded 5)
```
**`kit-export` 기본 호출을 "전량"이라 보고하면 안 된다.** 실제로 누락되던 78건 안의 `UC-026` 에 잔재 2곳이 있었다.

### 4-2. 한글 손상 방어 — 바이트 대조가 유일한 방어선
서버 덤프를 기준선으로 두고 → **결정적 치환**(각 `count==1` assert)으로 기대본 생성 → MCP 를 Bash+파이썬 HTTP 로 직접 호출해 **전사 단계 제거** → 재다운로드 후 `data` 전체 바이트 대조.
**전 작업 손상 0.** 이건 규칙을 지킨 결과가 아니라 **대조가 확인해 준 것**이다.

### 4-3. 대상 목록은 늘 부족하다 — **개별 지정이 아니라 축 단위 전수로 닫아야 한다**
PM 이 감사 리포트에서 추출해 준 대상이 **여섯 번 연속 부족**했다(4→6 / "마지막 2건"→5 / 1→3 / 2→4 / 1→2 / +2). 매번 **에이전트의 전수 스캔**이 잡았다.

**원인**: 감사 리포트는 **도메인별로** 결함을 적었는데, 하나의 결정은 **도메인을 가로질러** 복제돼 있다. 리포트에서 목록을 뽑는 방식으로는 구조적으로 다 못 잡는다.

⇒ **결정 하나를 고칠 때는 그 결정을 "축"으로 잡고 951 전수 스캔으로 종결한다.** 실제로 그렇게 닫은 축:
- **검수 종결 상태값 축** — ITEM 14건 수정 후 전수 재스캔 **0건**
- **재생성·통지 트리거 축** — 진행 중(`AC-009`·`UC-009`·`CDIAG-013` 정정 후에도 `SEQ-010`·`TEST-004` 에서 추가 발견)

프롬프트에 **"모든 문자열 필드를 전수로 훑어 한 벌로 고쳐라"** + **"낱말이 아니라 축으로 판정하고 오탐은 문맥과 함께 소명하라"** 를 상설로 넣는다.

### 4-4. 낱말 단위 치환 금지
같은 낱말이 다른 축에서 정상이다 — `COMPLETED`(5축) · `만료`(디바운스 판정 vs 클레임 임차) · `DE_IDENT_YN`/`DE_IDNTF_YN` · Java 필드명 vs DB 물리명. **축을 보고 판정한다.**

## 7. 이번 라운드가 만든 손실 (정직하게 기록)

1. **`UC-024`·`UC-031` 의 `stale` 플래그가 쓰기 부수효과로 해제**됐다. 원래 사유(*"SCREEN-029/025 3필드 변경"*)가 본문에 반영돼야 했는지는 **확인되지 않았다.**
2. **`CDIAG-013` 의 `stale` 표식도 같은 방식으로 사라졌다.** 그때 `AC-009` 대조를 하지 않았고, 남아 있던 P0 는 **이후 라운드에서 별도로 찾아 고쳤다.**
⇒ **`update_item` 은 `stale` 을 자동 해제한다.** 추적 신호를 지우고 원인은 남기는 이 패턴은 감사가 지적한 *"덮어확정형 스탬프"* 와 같은 형태다.
**대책(이후 프롬프트에 상설 반영)**: 쓰기 **전에** 그 ITEM 의 `stale`·`stale_reason` 을 읽어 **보고에 기록**한다. 표식이 가리키던 다른 미해결 결함이 있으면 그것을 후속 대상으로 올린다.

3. **`SEQ-014` 의 `stale` 표식도 소실**됐다 — 사유는 *"`UC-016` 의 `data.realizes_dfeats` 변경 — realizes"* 로 **이번 축과 무관한 미해결 전파**를 추적하던 것이다. 그 신호는 이제 없다(별도 확인 필요).
4. **`SCREEN-005` 미러 재생성이 선존 드리프트를 함께 게시**했다 — route 가 `/labeling/:srcSn` → `/label/:id` 로 바뀌어 나갔다. 미러는 파생물이라 ITEM 을 따르는 것이 맞으나, **우리 축이 아닌 변경이 게시된 것**이므로 명시한다.
5. **같은 ITEM 을 축이 다른 여러 라운드가 순차 편집**했다(`AC-009` 은 페이로드 축·`domain_id` 축·트리거 축으로 세 번). 매번 *"그 축은 이미 정합됐으니 건드리지 마라"* 를 명시해 되돌림은 막았으나, **한 번에 한 축씩 도는 구조 자체가 되돌림 위험을 계속 만든다.**
