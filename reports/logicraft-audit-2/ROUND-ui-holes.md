# UI 규격 홀(결손) 검토 — 2026-08-07

> 대상: LogiCraft `screen_spec` 32 · `ui_component` 99 · `app_shell` 2 · `navigation_tree` 2 · `permission_role` 3
> 방법: `.staging-all` 로컬 사양 JSON 에 대한 **결정론적 기계 검사**(LLM 판정 0). 코드는 보지 않았다 — 이 라운드는
> **"사양만 보고 구현할 수 있는가"** 를 묻는 것이지 구현 정합을 묻는 것이 아니다.
> 성격: **읽기 전용 검토.** ITEM 을 하나도 고치지 않았다.

## 0. 한 줄

**형식은 거의 채워져 있으나(최상위 필드 32/32), 규격을 잇는 두 축 — ① 화면↔컴포넌트 이름 ② 화면↔인수기준/유스케이스 —
가 통째로 끊겨 있다.** 제3자가 이 규격만으로 구현하면 **화면이 부르는 컴포넌트의 82%를 카탈로그에서 찾지 못한다.**

## 2. P0 — 규격이 끊긴 곳 (이대로면 구현 불가)

### H1. 화면↔컴포넌트 카탈로그가 이름으로 연결되지 않는다 ★가장 큼

- **화면이 `custom_name` 으로 부르는데 카탈로그에 없다: 82 / 103건 (80%)**
- **카탈로그에 있는데 어느 화면도 `custom_name` 으로 부르지 않는다: 68 / 98건 (69%)**

즉 양쪽 모두 채워져 있는데 **서로를 못 찾는다.** 몇몇은 같은 것을 다른 이름으로 부르는 쌍으로 보인다:

| 화면이 부르는 이름 | 카탈로그에 있는 이름 |
|---|---|
| `FrameNavControl`(005) · `FrameNavControls`(019) | `FrameNavigator` (UI-052, 선언=005/029/019) |
| `DarkFrameStrip`(005·029) · `FrameStripToggle`(019) | `FrameFilmstrip` (UI-051, 선언=005/029) |
| `TimeseriesMetaReviewPanel`(019) | `TimeseriesSidePanel` (UI-056·UI-074) |
| `LabelCanvas`(019) | `ReviewLabelCanvas` (UI-058, 선언=019) |
| `ProgressOverlay`(005) | `LoadingOverlay` (UI-022, 선언=[]) |
| `PrecisionControl`(005) | `PrecisionConfigCard` (UI-088, 선언=025) |

> ⚠ 이 표는 **문자열 유사도 휴리스틱**으로 뽑은 후보다(총 18쌍 추정). 오탐이 섞여 있다
> (`AiDetectTargetPicker`↔`DateRangePicker` 같은 무의미 매칭). **사람이 확인해야 하는 목록이지 확정 매핑이 아니다.**
> 나머지 60여 건은 유사 이름조차 없어 **카탈로그에 정말 없는 것**으로 보인다.

**왜 홀인가**: SCREEN-005 를 구현하려는 사람이 `ZoomControl`·`FrameMetaPanel`·`KeypointGuide` 규격을 찾으면
카탈로그에 없다. 반대로 카탈로그의 `ToolBar`·`ObjectAttributePanel` 은 어느 화면 사양에서도 호출되지 않아
**어디에 쓰는 물건인지 규격만으로는 알 수 없다.**

### H2. 화면이 지정하는 `variant` 의 허용값이 카탈로그에 없다

- 화면 컴포넌트가 `variant` 를 **172회** 지정
- 카탈로그 `variants` 필드 보유는 **3 / 99건**

**왜 홀인가**: `variant: "danger"` 라고 적혀 있는데 그 컴포넌트가 어떤 variant 를 갖는지, 각 variant 가
무엇을 뜻하는지 규격 어디에도 없다. 구현자가 임의로 정하게 된다.

### H3. 화면↔인수기준·유스케이스 연결이 통째로 비어 있다

| 필드 | 빈 화면 |
|---|---|
| `covered_by_acceptances` | **32 / 32 (전부)** |
| `realizes_use_cases` | **30 / 32** |
| `uses_constants` | **32 / 32 (전부)** |

프로젝트에 `acceptance` 25건 · `use_case` 25건 · `constant` 2건이 실재하는데 **화면이 하나도 참조하지 않는다.**

**왜 홀인가**: ① 화면의 "완료 판정 기준"이 규격에서 도달 불가 ② 어느 유스케이스를 실현하는 화면인지 추적 불가
③ `constant` 2건은 COCO-17 키포인트 스켈레톤·COCO-80 검출 클래스인데, **키포인트를 편집하는 SCREEN-005 가
그 상수를 참조하지 않는다** — 구현자가 관절 17개 정의를 규격에서 찾을 수 없다.

### H4. 포털 채널 3화면이 셸·메뉴 어디에도 없다

| 화면 | route | 셸 | 메뉴 |
|---|---|---|---|
| SCREEN-028 포털 홈 | `/portal` | ✗ | ✗ |
| SCREEN-033 포털 업로드 | `/portal/uploads` | ✗ | ✗ |
| SCREEN-034 포털 업로드 라벨링 | `/portal/uploads/:uldSn/label` | ✗ | ✗ |
| SCREEN-029 포털 라벨링 | `/portal/label/:id` | SHELL-002 | NAV-002 |

`SHELL-002.applies_to_screens` = `['SCREEN-029']` 하나뿐이다. 포털 자산 업로드(ADR-013 예외로 신설된 실기능)는
**규격상 어떤 셸로 감싸는지도, 어떻게 도달하는지도 정의되지 않았다.**

### H5. NAV-002 가 SCREEN-028 을 "폐기"로 단정하는데 실제 상태는 `draft`(활성)

NAV-002 본문:
> "포털 홈 화면(SCREEN-028)은 폐기 상태라 제외하고 활성 화면인 포털 라벨링(SCREEN-029)만 포함한다"
> 노드 `portal-home`: "활성 SCREEN 미정(SCREEN-028 deprecated, 데이터마트 목록 홈 대체 후속 필요)"

그런데 **SCREEN-028 은 `status: draft`** 이고 정상적인 포털 홈 사양(섹션 4 · 컴포넌트 13)을 담고 있다.
둘 중 하나가 틀렸고, 그 결과 **포털 홈이 메뉴에서 도달 불가**다. NAV-002 스스로 "대체 후속 필요"라고
미결을 적어 둔 상태로 남아 있다.

기계 검사에서 "결손"으로 잡혔으나 **본문이 명시적으로 설명해 정상**인 것들:

| 관측 | 왜 정상인가 |
|---|---|
| SCREEN-010 `route` 가 빈 문자열 | purpose 가 *"별도의 독립 페이지·라우트를 두지 않는다 — SCREEN-005 헤더가 여는 패널"* 이라고 명시 |
| SCREEN-005 · SCREEN-010 이 어느 셸에도 안 붙음 | `SHELL-001.description` 이 *"라벨링 캔버스는 풀스크린이라 셸 밖에서 자체 헤더를 둔다. 라벨 이력도 이 셸이 감싸지 않는다"* 라고 명시 |
| `PrivacyBadge`(UI-015) 가 어느 화면도 안 씀 | description 이 **`[폐기]`** 로 시작하고 사유를 적어 뒀다. 관례(§2-A 표기 폐기)를 정확히 따른 상태 |
| NAV-001 의 `[폐기] 영상 목록` 노드 | 폐기 표기 + 사유 병기. 배열 원소를 지우지 않는 관례대로다 |
| SCREEN-001~004 의 `required_roles` 빈 | 인증 전 화면(진입·역할클레임·접근거부·개발로그인). 다만 **"인증 전이라 역할이 없다"는 명시는 없다** → H15 로 약하게만 기록 |
