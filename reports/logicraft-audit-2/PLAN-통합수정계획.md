### 0.1 ★P10 철회 — 레포명을 ITEM 본문에 쓰지 않는다

초안의 P10 은 GAP-F00(정의서가 테스트베드 옛 설계와 일치)의 재발을 막으려고 각 화면 `purpose` 에 기준 레포명을 박으려 했다. **이는 잘못된 처방이었고 철회한다.**

- **자기모순** — 이번 작업의 목표가 "제3자가 LogiCraft만 보고 구현 가능"하게 만드는 것인데, 그 문서에 "저 레포를 보라"고 적으면 **설계서가 스스로 자립 불가를 선언**하는 셈이다.
- **제3자는 그 레포에 접근할 수 없다.** 외부 구현자에게 무의미하거나 도달 불가능한 지시가 된다.
- **필드 오용** — `purpose` 는 화면의 목적을 적는 자리이지 우리 작업 이력·동기화 대상을 적는 자리가 아니다. **데이터 오염**이다.
- 레포명은 바뀐다. 바뀌면 전 화면이 stale 이 된다.

**GAP-F00 은 문서 내용 문제가 아니라 우리 작업 프로세스 문제다.** 따라서 처방도 프로세스 쪽에 둔다 — 감사 리포트와 auto-memory 에 "정합 기준 = 납품 FE" 를 기록하고, LogiCraft ITEM 본문에는 넣지 않는다.

SCREEN-007 처럼 **구현 상태가 사실인 서술**("현행 구현에 대응 라우트가 없다")은 남기되 레포명 없이 적는다.

### 0.3 ★P2 개정 — 기능은 합집합, 구조만 납품 FE 기준

> 사용자 확정(2026-08-07): *"지금 이 레포에만 있고 납품에는 없는 기능도 있을 수 있으니 그것도 포함되어야 해."*

| 축 | 기준 |
|---|---|
| **기능·동작** (무엇을 할 수 있는가) | **합집합** — 기존 정의서 ∪ 납품 FE ∪ 테스트베드. **어느 한 곳에만 있어도 사양에 포함** |
| **구조·명칭·동선** (어떻게 생겼는가) | **납품 FE 기준** — 같은 기능을 두 구현이 다르게 표현할 때만 적용 |
| 두 구현 어디에도 없는 기존 정의서 기능 | **보존**(P1) |

**초안의 P2 는 이 구분이 없어 "구조는 납품 FE 기준"이 기능까지 좁히는 근거로 읽힐 수 있었다.** 실제로 배치 A~E 에는 개정 전 규칙만 전달됐다 — 배열 원소 삭제는 검증으로 막혔으나(컴포넌트 총 개수 감소 0), **서술이 다시 쓰이며 테스트베드 전용 기능이 희석됐을 가능성**이 남아 소급 재점검 라운드를 별도로 돌린다(`FIXED-RECHECK.md`).

### 0.2 ★P0 — ITEM 본문은 사양만 담는다 (오염 금지)

> 사용자 확정(2026-08-07): *"logicraft 에는 쓸데없는 걸 넣어서 오염시키면 안 된다. **누가 하더라도 동일한 결과를 누락 없이 제대로 만들기 위해** 사용하는 것이다."*

| 위치 | 담는 것 | **금지** |
|---|---|---|
| ITEM **본문** — `purpose` · `sections[].description` · `components[].note` · `validation` | 화면·기능·동작·상태분기·검증규칙·권한 등 **구현에 필요한 사양** | 레포명 · **코드 파일명/심볼명** · 커밋 해시 · 세션·감사 이력 |
| **`change_summary`** (변경 이력 메타) | 무엇을·왜 바꿨는지 **+ 근거**(코드 심볼·정책 절 인용 OK) | — |

**본문의 독자는 이 저장소에 접근할 수 없는 제3자다.** 파일명을 적으면 열어볼 수 없고, 목표를 문서 스스로 배반한다. `change_summary` 는 독자가 다르므로(변경 이력을 좇는 내부자) 근거를 적어도 된다.

- ✅ `validation: "필수. 1~20자. 소문자·숫자·밑줄만. 위반 시 '형식이 올바르지 않습니다'"`
- ❌ `note: "zod 스키마는 presetSchema.ts 참조"`

**P10 과 P5 오적용은 같은 오류다 — 처방을 잘못된 레이어에 뒀다.** 둘 다 "우리 작업 프로세스 문제"(정합 기준 흔들림)를 **산출물 내용**으로 해결하려 했다. 프로세스 문제는 리포트·auto-memory 에 적는다. **LogiCraft 는 산출물이지 우리 작업 로그가 아니다.**

⚠️ 예외(오염 아님): **`[폐기]` 표기**(P8 — "이건 만들지 마라"는 사양 정보, 구현자 관점으로 서술) · **구현 상태 사실** · **화면에 실제 표시되는 UI 라벨**.

## 5.1 ★부산물 — 납품 FE 코드 결함 (사양 문제가 아니라 실제 버그)

수정 작업 중 발견. **화면정의서가 아니라 `klid-label-frontend` 코드의 결함**이므로 이 계획의 처리 대상이 아니고, FE 팀에 전달할 사항이다.

### FE-BUG-01 — 증강 요청→결과 동선이 죽은 링크 (재발)

| | 이동 대상 |
|---|---|
| 테스트베드 `AugmentRequestPage.tsx` | `navigate('/augment/result/' + targetRawSn)` — **rawSn** ✅ |
| **납품 FE `AugmentPage.tsx`** | `navigate('/augment/' + result.jobId)` — **jobId** ❌ |

- `AugmentRequestResult.jobId` 는 BE 가 `AtomicLong(System.currentTimeMillis())` 로 찍는 **placeholder** 다. 어떤 엔티티의 식별자도 아니다.
- 결과 API 는 경로변수를 `findByOriginalRawSn()` 으로 조회한다 → 1.7e12 급 placeholder 는 절대 매칭되지 않는다.
- 증상: 요청 성공 후 이동한 결과 화면이 `results=[]`·`PROCESSING` 이라 **"증강 처리 중입니다…" 배너에 영구 고착**. 폴링이 없어 새로고침해도 동일.
- **2026-07-31 에 우리 쪽에서 이미 겪고 고친 실사고**(당시 code-reviewer·build-validator 는 PASS, 적대검증만 검출)인데 납품 FE 에 미반영.
- 가중 요인: 납품 FE 의 타입 주석이 `jobId: 생성된 증강 잡 ID — 결과 화면 네비게이션용` 이라 **적극적으로 오도**한다.
- 조치: 이동 대상을 **요청한 원본 영상의 `rawSn`** 으로 변경 + 타입 주석 정정. BE 무변경.
