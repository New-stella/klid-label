## ★★ 독립 검증으로 G-report 원안을 뒤집은 항목 (P2 — 납품 FE 구조 우선)

| eventTypeCd 선택 방식 | 관제 카테고리 9종을 그룹으로 보여주고 대표 EV-코드(`memberCodes[0]`) 전송 | 이벤트유형마스터 상세 코드를 평면 목록(`GET /v1/event-types/labels`)으로 조회해 사용자가 직접 코드를 선택 (동명 라벨은 코드 병기로 구분) | **납품 FE** — 형식(EV+숫자 8자리) 검증은 두 구현 공통이므로 사양에 포함, 그룹핑 방식 서술은 채택하지 않음 |

## SCREEN-001/002/003 성격 판정 결과

G-report 의 판정(참조 구현에 실제로 마운트된 화면이며, 가드 동작을 화면으로 표현한 것이 아니다)을 그대로 채택했다. 다만 서술 방식은 과제 지시에 따라 "구현상태"(어느 저장소에 라우트가 있고 없고) 언급 없이 **무엇을 어떻게 보여줘야 하는지**만 담는 순수 사양으로 작성했다. `PortalGuard`라는 비실존 컴포넌트명은 코드 심벌명 자체를 아예 노출하지 않는 방향(역할 기반 접근 제어/채널 기반 접근 제어라는 개념어)으로 재서술해 P0 을 만족시켰다.

## JWT 인계 정책 정합 (SCREEN-001, 독자 발견)

SCREEN-001 원문은 `resolveToken` 전략에 `?token=` URL 쿼리 파라미터를 포함하고 있었다. 이는 프로젝트 CLAUDE.md 의 확정 정책("URL 쿼리 파라미터(`?token=`) 방식 미사용")과 정면으로 배치된다. 실제 테스트베드 코드(`tokenIngress.ts`)는 여전히 `?token=` 을 기본 전략에 포함하고 있어 **정책과 코드가 어긋난 상태**였다. P3(정책은 CLAUDE.md 기준)에 따라 정의서에서는 `?token=` 을 제거하고 "localStorage 또는 쿠키로만 인계받는다 — URL 쿼리 파라미터 방식은 사용하지 않는다"로 명시했다. 코드 쪽 정합(`?token=` 전략 제거 여부)은 이번 배치의 범위 밖이며 별도 확인이 필요하다.

## 미확인·남은 것

1. **테스트베드 코드의 `?token=` 지원 여부** — 위 항목 참조. 정책·정의서는 정정했으나 실제 FE 코드(`tokenIngress.ts`)가 여전히 `strategy==='all'`일 때 URL 토큰을 후보에 포함한다. 코드를 정책에 맞출지, 정책을 완화할지는 이번 배치 범위 밖.
2. **SCREEN-004 의 세부 명칭 차이(헤더 타이틀·버튼 라벨)** — 납품 FE(`DevLogin.tsx`: "KLID AI 로그인" / "선택한 역할로 진입")와 테스트베드(`DevLoginPage.tsx`: "Dev Login" / "토큰 발급 + 진입")가 다르다. 이번 라운드는 G06(3중 보안 구조) 정정에 집중했고 이 명칭 차이는 G-report 미포함 사항이라 반영하지 않았다. P2 원칙(구조·명칭은 납품 FE 우선)을 엄격히 적용하면 다음 라운드에서 정정 대상이다.
3. **`framerate`(=추출 간격, FPS 아님) 관련 서술 정정** — 이번 배치 5개 화면의 원본·실제 코드 어디에도 `framerate`/`frame_policy` 필드가 존재하지 않아(grep 결과 0건) 적용 대상이 없었다. 해당 서술은 VLM 검증 위탁·마킹 화면 쪽 스펙에 해당할 가능성이 높으며 다른 배치의 몫이다.
4. **LogiCraft 링크 그래프 warning** — SCREEN-001(preserved)·SCREEN-002(modified) 두 화면에 `BROWNFIELD_REUSE_WITHOUT_SOURCE`(legacy_source 미기재) 경고가 기존부터 존재했다. 이번 배치 범위(G-report 15건) 밖이라 손대지 않았다.
