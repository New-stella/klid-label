# 외부 시계열 분석 연동 — 문의 목록 (2026-08-24)

> 대상 규격: **KLID 연동 API v1.1.0** (`docs/연동규격서/video_vlm_klid_api_v1.1.0.pdf`)
> 배경: 저작도구가 연동하는 창구를 **묘사(`describe`) + 추가 질문(`describe-sub`)** 둘로 확정하고
> 판정(`verify`)은 연동하지 않기로 했다(변경지시서 CO-005 · 결정 기록 ADR-051). 그 구현을 마치면서
> 규격만으로는 답이 나오지 않는 항목을 모았다.
>
> 각 항목은 **회신이 없을 때 우리가 이미 정한 기본 동작**을 함께 적었다. 회신이 오면 그 기본을
> 바꾸는 방식이며, 회신 전이라고 연동이 막혀 있지는 않다.

---

## A. 벤더 문의

### A-1. `path` 방식으로 우리 비식별 저장소를 읽을 수 있는가 — **가장 시급**

규격 §2.4 는 `source_type=path` 일 때 "서버에 허용된 경로 하위만 접근 가능"이라고만 적는다.
우리는 비식별 영상 경로를 그대로 실어 보내는 **path 방식**을 전제로 구현했다.

- 분석 서버가 우리 NAS 를 **공유 마운트로 직접 읽는** 구성인가?
- 그렇다면 허용 경로(root)를 어떻게 등록하는가? 등록 창구·반영 시점은?
- 아니라면 `upload` 방식(파일당 4GB)으로 전환해야 하는데, 영상 1건이 4GB 를 넘는 경우의 권고는?

> 회신 없을 때 우리 기본: **path 방식 유지.** 접근 불가면 위탁이 400(허용되지 않은 경로)으로
> 떨어지며 그 실패를 기록한다. 즉 **연결 시점에 곧바로 드러난다.**

### A-2. 묘사·추가 질문 응답에 판정 항목이 섞여 오는가

규격 §2.8 은 `detected`·`accuracy` 를 **판정 창구 전용**으로 명시한다. 그런데 §2.7 의 콜백 예시는
세 항목을 함께 보여준다(판정 창구 기준으로 보인다).

- 묘사·추가 질문 콜백에 그 두 항목이 **절대 오지 않는다**고 봐도 되는가?

> 회신 없을 때 우리 기본: **와도 무시**한다. 여기서 400 을 내면 재전송 3회 뒤 결과가 영영
> 유실되고 다시 받을 창구가 없기 때문이다(§5.1). 즉 이 항목은 **연동을 막지 않는다** —
> 다만 "온다면 왜 오는가"를 알면 우리 쪽 기대를 정확히 적을 수 있다.

### A-3. `429` 재시도 간격 권고치

규격 §2.9·§5.2 는 "잠시 후 재시도한다"고만 적고 간격을 정하지 않는다. 우리는 창구가 둘로 늘어
**영상 1건당 호출이 2회**가 되므로 동시 처리 한도(32건)에 더 빨리 닿는다.

- 권고 재시도 간격과 최대 재시도 횟수가 있는가?
- `Retry-After` 헤더를 주는가?

> 회신 없을 때 우리 기본: 기존 지수 백오프 정책을 그대로 쓴다.

### A-4. `GET /events` 의 캐시 주기

`version` 필드가 "프롬프트나 분석 조건이 바뀌면 갱신된다"고 되어 있다.

- 우리가 이 목록을 캐시해도 되는가? 권장 갱신 주기는?
- `version` 이 바뀌면 기존 위탁 결과의 해석이 달라지는가(과거 결과 재해석 필요 여부)?

> 회신 없을 때 우리 기본: 위탁 전 조회하되 **게이트로 쓰지 않는다**(조회 실패가 위탁을 막지 않는다).

### A-5. 인증 헤더

규격서에 인증 관련 기술이 **없다**.

- 실제 운영에서 API 키·토큰이 필요한가? 필요하다면 헤더 이름과 발급 절차는?
- 반대로 우리가 받는 **콜백**에 서명·인증 헤더를 붙여 줄 수 있는가?
  (현재 우리는 무서명 전제로 IP 허용목록 + 요청 식별자 발급 게이트 + 속도 제한 3계층으로 막고 있다.)

### A-6. 추가 질문의 질문 문장

규격 §3.3 은 질문 문장을 **서버가 이벤트별로 관리**하며 연동 시스템이 지정하지 않는다고 한다.

- 이벤트별 질문 문장의 **현재 전문**을 받을 수 있는가? (검수자 화면에 "무엇을 물었는지"를
  보여주려면 필요하다. 지금은 우리가 그 문장을 모르므로 답변만 표시한다.)
- 질문 문장이 바뀌면 통지받을 수 있는가?

### A-7. 분석 제한 900초를 넘긴 경우의 실패 콜백 형태

§2.9 는 900초 초과도 실패 콜백으로 온다고 한다.

- 그때 `error` 문자열에 **시간 초과임을 식별할 수 있는 표현**이 들어가는가?
  (우리는 자연어 파싱에 의존하지 않으려 하므로, 재시도 가치가 있는 실패인지 가르려면
  구분 가능한 형태가 필요하다. 없으면 전부 동일한 확정 실패로 다룬다.)

## B. 관제 문의

### B-1. `smoke`(연기) 이벤트를 인입으로 보내는가 — **미확정, 우리 목록 6종 유지 중**

KLID 규격은 이벤트 **7종**(`fire`·`smoke`·`fall`·`violence`·`flooding`·`car_accident`·`kidnapping`)을
지원한다. 우리가 아는 목록은 **6종**으로 `smoke` 가 없다.

- 관제 인입(`LS_DATA_INGEST.VRFC_EVNT_TYPE_CD`)이 `smoke` 를 보낼 계획이 있는가?

> 현재 우리 동작: **조달값을 그대로 실어 보내고 수용 여부는 벤더 응답이 정한다.** 따라서
> 관제가 `smoke` 를 보내면 **우리 목록에 없어도 그대로 위탁되고 정상 처리**된다. 목록 6종은
> 화면 프리셋일 뿐 차단 기준이 아니다. 이 문의는 **연동을 막지 않으며**, 답을 받으면 화면
> 프리셋과 문서 표기를 맞추려는 것이다.

### B-2. 관제 이벤트 코드 ↔ 벤더 이벤트 값의 매핑을 누가 소유하는가

우리는 **매핑표를 만들지 않는다**(사본이 두 번째 진실원이 되면 벤더가 값을 넓혔을 때 정상 값을
우리가 먼저 막게 된다). 관제가 보내는 값을 그대로 싣는다.

- 관제가 보내는 값이 **벤더 값과 같은 어휘**라고 보아도 되는가?
- 다르다면 변환은 관제 쪽에서 해 주는가?

> 회신 없을 때 우리 기본: 조달값 그대로 전송. 어휘가 다르면 벤더가 400 으로 거부하고
> 우리는 그 실패를 기록한다(조용히 넘어가지 않는다).

### B-3. 인입 값이 아직 채워지지 않은 영상의 처리

관제가 검증 이벤트 유형을 보내기 전 영상은 값이 비어 있다.

- 소급 채움 계획이 있는가? 있다면 시점은?

> 현재 우리 동작: 값이 없으면 **비운 채로** 위탁한다(지어내지 않는다). 벤더 필수 필드라
> 400 이 예상되며 그 거부를 기록한다. **자동 재위탁 트리거는 없으므로**, 관제 값이 채워진 뒤
> 그 영상들을 다시 태우려면 별도 조치가 필요하다.

## C. 우리 쪽에서 이미 정한 것 (문의 아님 · 참고용)

| 항목 | 확정 |
|---|---|
| 연동 창구 | 묘사 + 추가 질문 둘. **판정 창구는 연동하지 않는다** |
| 프레임 선택 | 항상 우리가 골라 목록으로 싣는다(마킹 프레임 · 상한 600). `framerate` 는 규격에 없어 싣지 않는다 |
| 콜백 결과 | `{description}` 단일. 모르는 항목은 무시(재전송 3회 뒤 유실되므로 엄격함이 곧 손실) |
| 실패 콜백 | `error` 는 문자열. 객체로 받으면 전량 거부되어 실패 사실을 잃는다 |
| 재시도 | 429 만 재시도. 400·415 는 비재시도 |
| 결과 적재 | 묘사 → 시계열 서술 전문 / 추가 질문 → 이벤트 어노테이션 답변 초안 |

## D. 회신 대기 중에도 막히지 않는 것 / 막히는 것

- **막히지 않음**: B-1·B-2·B-3(조달값 그대로 전송) · A-2·A-3·A-4·A-7(기본 동작 있음)
- **막힘**: **A-1(경로 접근성)** — 이것만 해결되면 실연동 왕복이 성립한다. A-5(인증)는 필요 여부에 따라 갈린다.
- **화면 완성도에만 영향**: A-6(질문 문장) — 없어도 답변은 표시된다.
