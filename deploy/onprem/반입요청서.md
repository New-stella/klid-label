## 2. 반입 대상 서버 구성과 역할별 반입물

매체는 한 벌이고, 설치 시 `--role` 로 어느 서버인지만 고른다. 역할을 주지 않으면 한 대에 전부 설치된다.

| | **서버 A `--role=app`** | **서버 B `--role=ai`** |
|---|---|---|
| 역할 | 프론트엔드 + 백엔드 | AI 추론 서버 |
| 올라가는 것 | httpd(정적 자산 서빙 + `/api` 리버스프록시) · **외부 WAS 에 `api.war`** · (옵션)PostgreSQL 16 | ai-server(파이썬 3.11 + 오프라인 휠 + YOLOX/SAM2 모델) |
| systemd 유닛 | `httpd` (+`postgresql-16`) — **백엔드는 유닛이 아니다**(WAS 가 기동 주체) | `klid-ai-server` |
| 쓰는 반입물 | `artifacts/backend`(api.war) · `artifacts/frontend/dist` · `syspkgs/{rpm,gpg,postgresql,ffmpeg,ffmpeg-src}` · `db` · `config` | `vendor/{wheels,sam2}` · `models/{weights,hf-cache}` · `runtimes/python` · `syspkgs/{rpm,gpg}` |
| ffmpeg | **전제조건** — 관제지원시스템 측이 설치. 우리는 검증만 한다(§3-3) | 사용하지 않는다 |
| GPU | 해당 없음 | 장비에 GPU 가 있으나 **이번 반입은 CPU 전용** |
| 파이썬 | 필요 없음 | **장비에 파이썬이 없어 런타임 전체를 반입** |

> 서버 A 는 서버 B 의 9300 포트에 도달해야 한다. `AI_SERVER_URL` 기본값이 `http://127.0.0.1:9300`
> (단일 서버 기준)이므로 2대 구성에서는 **반드시 서버 B 주소로 바꿔야 한다.**

## 3. ★ 반입 제외 대상 (명시)

무엇을 반입하지 **않는지**를 먼저 밝힌다. 아래는 전부 의도적 제외이며 각각 근거가 다르다
(§3-1 자바 런타임 · §3-2 재빌드 도구 · §3-3 ffmpeg **설치** · §3-4 그 밖).

### 3-1. 자바 런타임 (JDK/JRE) — 반입하지 않는다

대상 서버 A 에는 **JBoss EAP 8.1(standalone) + Java 17** 이 이미 설치·구동 중이다
(2026-09-04 현장 실측 — 호스트 `klid-ai-gen-was-01`, `JBOSS_HOME=/GCLOUD/JBOSS/jboss-eap-8.1`,
Java `/usr/lib/jvm/java-17-openjdk`, 실행 계정 `jboss`).
⚠ 구 서술 폐기(2026-09-04): *"관제지원시스템 WAS 와 동일 사양인 Tomcat 10.1.x"*.
EAP 8.x 는 Jakarta EE 10 이라 Spring Boot 3.3 의 `jakarta.*` 와 맞고, `api.war` 는 톰캣을
`WEB-INF/lib-provided/`(컨테이너가 읽지 않는 자리)에 두어 컨테이너 중립이므로 **WAR 는 그대로 쓴다**. 백엔드는 그 WAS 에 **`api.war` 로 반입**되며 프로세스 수명주기는
WAS 가 소유한다. 자바 런타임을 한 벌 더 반입하면 같은 장비에 두 벌이 공존해 운영 혼선만 생긴다.

- 매체의 `runtimes/jdk/` 는 **비어 있다**(디렉터리 골격만 남김).
- 설치 스크립트도 자바를 설치하지 않는다. `runtimes/jdk` 가 비어 있어도 설치가 완주한다.

> ⚠ **ai-server 의 파이썬 런타임은 이와 무관하게 그대로 반입한다.** 자바를 뺐다고 함께 빠지지 않는다 —
> 서버 B 에는 파이썬이 아예 없기 때문이다.

### 3-2. 현장 재빌드 도구 — 반입하지 않는다

계약상 **폐쇄망 현장에서 소스를 재빌드할 요구가 없음**을 확인했다. 따라서 아래를 반입하지 않는다.

| 미반입 품목 | 원래 용도 | 현재 상태 |
|---|---|---|
| JDK 17 full (javac) | 백엔드 `bootWar` 재빌드 | `buildtools/jdk/` 비어 있음 |
| Node.js 20 | 프론트엔드 `vite build` 재빌드 | `buildtools/node/` 비어 있음 |
| Gradle 8.8 + 의존성 캐시 | 백엔드 오프라인 빌드 | `buildtools/gradle*/` 비어 있음 |
| `node_modules`(645 패키지) | 프론트엔드 오프라인 빌드 | 미수집 |

대신 **사전 빌드된 산출물**(`api.war`, 프론트엔드 `dist`)을 반입한다.
빌드 도구를 켜서 반입하려면 `WITH_BUILDTOOLS=1` 로 수집해야 하며, 그때는 그 목록(특히
`node_modules` 645 패키지)의 **라이선스 고지 의무가 새로 생긴다** — 이번 반입은 그 대상이 아니다.

### 3-3. ffmpeg — 설치하지 않는다. 단 **예비물로는 매체에 담는다**

이 구분이 중요하다. 두 문장은 서로 다른 사실이다.

| | 사실 |
|---|---|
| **설치 주체** | **관제지원시스템 측이 서버 A 에 설치한다.** 우리 설치 스크립트는 **자동 설치하지 않고 검증만** 한다(`19-verify-ffmpeg.sh`). 없으면 설치를 **중단**한다 |
| **매체 동봉** | **담는다.** `syspkgs/ffmpeg/` 에 RPM 261개(전이 의존성 전량, 로컬 저장소 포함) + `syspkgs/ffmpeg-src/` 에 GPL 대응 소스 SRPM 3건 |
| **설치 방법** | 자동 설치 경로 없음. 관제 측이 설치하지 않은 것이 확인됐을 때만 **사람이** `sudo ./scripts/install/install-ffmpeg.sh` 로 별도 실행 |

**왜 자동이 아닌가**: 서버 A 는 관제지원시스템과 **공동 배치**다. 관제가 이미 설치한 ffmpeg 를
우리 설치가 덮어쓰면 관제 기능이 깨진다. 그래서 `install.sh` 의 단계 목록에 `install-ffmpeg.sh` 를
**넣지 않았다**(파일명에 번호 접두가 없는 것이 그 표식이다).

**왜 그래도 담는가**: 폐쇄망이라 필요해졌을 때 받아올 수 없다. ffmpeg 는 RHEL 8 의 base/AppStream 에
없고 EPEL + RPM Fusion + PowerTools(CRB) 세 리포가 필요해, 현장에서 조달할 방법이 사실상 없다.

> **라이선스**: 예비물 ffmpeg 는 RPM Fusion 의 **GPLv3+** 빌드다. 설치하지 않더라도 **매체에 담아
> 넘기는 것 자체가 재배포**이므로 대응 소스(SRPM)를 함께 반입한다(§6-4).

### 3-4. 그 밖에 반입하지 않는 것

- **애플리케이션 소스코드**: 반입 대상이 아니다(사전 빌드 산출물만 반입).
- **`klid-backend.jar`**: 개발 환경 전용 산출물이라 **매체에 담지 않는다**(2026-08-30 제외 완료 — §7-3).
  수집 스크립트가 **만들지도 복사하지도 않으며**(`10-build-backend.sh`), WAR 반입 형상에서는 설치도
  하지 않는다(`12-install-backend.sh`). 베어메탈 형상(`INSTALL_BACKEND_SYSTEMD_UNIT=1`)으로 갈 때만
  빌드머신에서 `WITH_BACKEND_JAR=1 ./scripts/package.sh` 로 다시 수집한다 — 그 매체 없이 베어메탈로
  설치하면 설치가 **사유와 함께 중단**된다(조용히 넘어가 기동만 실패하는 상태를 만들지 않는다).
- **KPST 비식별 서버**: 외부 시스템이며 폐쇄망에 별도 설치되어 있어야 한다(본 패키지 비포함).

```
VITE_DEV_LOGIN_ENABLED=true      →  /dev/login      (개발용 토큰 발급 화면)
VITE_DEV_UPLOAD_ENABLED=true     →  /admin/uploads  (영상 수동 업로드 화면)
```

설치 시 생성되는 런타임 설정(`/etc/klid/frontend.env` → `klid-config.js`)의 템플릿 기본값도
**둘 다 `true`** 다. 즉 **운영자가 손대지 않으면 두 화면 모두 노출된다.**

### 8-2. 두 화면의 성격은 다르다 — 하나로 묶어 읽으면 안 된다

| | `/dev/login` (개발용 로그인) | `/admin/uploads` (수동 업로드) |
|---|---|---|
| 성격 | **폐쇄망 브링업 전용** | **운영 상시 기능**(2026-08-24 확정) |
| 대응 백엔드 | `/v1/dev/tokens` | `/v1/dev/upload` |
| 백엔드 기본값 | **`false`**(fail-closed) | 운영 프로파일에서 **`true`**(의도적) |
| 운영 프로파일에서 | **기동 가드가 켜짐을 금지한다** — `prd`·`stg` 에서 이 토글이 켜져 있으면 **애플리케이션이 부팅을 거부**한다 | 정상 동작. **검수자(REVIEWER) 인가**가 걸려 있다 |
| 결과 | 화면은 보이지만 **토큰을 받을 수 없다**(엔드포인트 404) | 화면과 API 가 함께 동작한다 |

### 8-3. 근거

1. **개발용 로그인 화면만으로는 아무것도 얻을 수 없다.**
   `/v1/dev/tokens` 는 인증 없이 임의 권한 토큰을 발급하는 경로라, 애플리케이션에 **부팅 거부
   가드**가 있다. 운영 계열 프로파일(`prd`·`stg`)에서 이 토글이 켜져 있으면 애플리케이션이
   기동하지 않는다. 설정 파일의 `false` 한 줄에 의존하지 않고(환경변수 하나로 덮일 수 있으므로)
   **기동 자체를 실패시켜** 정책을 강제한다. 따라서 운영 형상에서 이 화면은 **동작하지 않는 껍데기**다.

2. **폐쇄망 브링업에 필요하다.**
   저작도구는 자체 로그인 UI 가 없고 관제서버·포털이 발급한 토큰을 인계받는다. 설치 직후
   관제서버가 아직 연결되지 않은 구간에서는 **저작도구가 살아 있는지 확인할 방법이 이 화면뿐**이다.
   화면을 지운 채 반입하면 브링업 실패 시 원인 판별 수단이 사라진다.

3. **수동 업로드는 개발용이 아니라 운영 동선이다.**
   외부에서 받은 영상을 운영자가 직접 올려야 하는 동선이 실제로 있고 그 입구가 이 화면이다.
   설정 키 이름에 `DEV` 가 들어 있어 오해를 부르지만, 2026-08-24 에 **운영 노출로 확정**된 기능이며
   검수자 권한 인가가 걸려 있다.

4. **재빌드 없이 끌 수 있다.** ← 과거에는 재빌드가 필요했으나 지금은 아니다.
   프론트엔드 설정의 정본은 산출물이 아니라 **`/etc/klid/frontend.env`** 다.

   ```bash
   sudo $EDITOR /etc/klid/frontend.env
   #   VITE_DEV_LOGIN_ENABLED=false
   #   VITE_DEV_UPLOAD_ENABLED=false        ← 업로드까지 끌 경우에만
   sudo /opt/klid/bin/klid-frontend-config   # 반영 — 재빌드·재설치·웹서버 재기동 모두 불필요
   ```

   이 명령이 설정을 읽어 웹 문서 루트의 `klid-config.js` 를 다시 생성하고, 브라우저는 그 파일을
   번들보다 먼저 읽는다. 캐시 금지 헤더가 걸려 있어 즉시 반영된다.
   생성기는 **명시 열거된 키만** 내보내므로(allowlist) 설정 파일의 다른 값이 브라우저로 새지 않는다.

   > ⚠ **수동 업로드를 끌 때는 백엔드도 함께 꺼야 한다** — `/etc/klid` 의 백엔드 설정에
   > `DEV_UPLOAD_ENABLED=false` 를 명시하고 WAS 를 재기동한다. 한쪽만 끄면 화면과 API 중
   > 하나만 사라져 운영자가 원인을 찾기 어렵다.
   > 개발용 로그인은 백엔드가 이미 꺼져 있으므로 프론트엔드만 끄면 된다.

### 8-4. 권고

브링업 검증이 끝난 시점에 **`VITE_DEV_LOGIN_ENABLED=false` 로 바꾸고 위 반영 명령을 1회 실행**할
것을 권고한다. 그대로 두어도 보안 노출은 없으나(§8-3-1), 운영자가 그 화면을 눌러 보고
"왜 안 되는가"를 묻게 된다.

#### 9-1-3. ★★ 회신 요청 항목과 직결된 실측 결과 — 어느 패키지가 걸리는가

보호 장치를 켜고 돌려 보니 **세 단계 중 둘이 멈췄다.** 무엇을 올리려 했는지 그대로 적는다.

| 설치 단계 | 결과 | 바꾸려던 패키지 |
|---|---|---|
| ai 서버의 영상 라이브러리 | **통과** — 세 판 모두 무변경 | 없음 |
| 번들 PostgreSQL 16 | **중단** | `openssl-libs` → `1.1.1k-17.el8_10` (**1건**) |
| 번들 httpd | **중단** | `audit-libs` → `3.1.2-1.el8_10.1` · `libselinux` → `2.9-11.el8_10` · `libsemanage` → `2.9-12.el8_10` (**3건**) |

**중요한 사실 둘.**

1. **판이 낮아서 생긴 일이 아니다.** 매체를 수집한 판과 같은 8.10 에서도 똑같이 걸렸다.
   원인은 매체가 **수집 시점의 최신 보안 패치**를 물고 있고 시험용 이미지가 그 패치를 아직
   안 받았기 때문이다. **귀사 장비가 최신 보안 패치를 받은 상태라면 이 넷은 애초에 걸리지
   않는다**(1겹에서 걸러져 그냥 지나간다).
2. **실제 설치에서는 이 둘을 타지 않을 가능성이 높다.**

   | 대상 | 왜 안 타나 |
   |---|---|
   | PostgreSQL | 전제조건으로 **빈 데이터베이스 1개를 미리 받기로** 했다. 그러면 이 단계 자체를 건너뛴다 |
   | httpd | 관제지원시스템과 공동 배치라 **이미 설치돼 있을 가능성이 높다**. 있으면 설치를 건너뛰고 설정·자산 배치만 한다 |

**따라서 회신에 넣어 주시면 가장 도움이 되는 것**은 아래 넷의 현재 판이다.

```
rpm -q openssl-libs audit-libs libselinux libsemanage
rpm -q postgresql-server httpd     # 이미 있는지만 확인
cat /etc/redhat-release
```

넷 중 하나라도 위 표보다 **낮으면** 그 판에 맞춰 다시 수집해 넣겠다. 같거나 높으면 그대로
설치된다. **회신이 늦어져도 장비가 훼손되는 일은 없다** — 보호 장치가 그 자리에서 멈추고
무엇이 걸렸는지 화면에 찍기 때문이다.

> 기존 WAS, 관제 공동 배치)은 리허설에서 재현되지 않았다.

| **PostgreSQL** | **16**. ① 매체의 번들 RPM 설치(기본) 또는 ② 기존 PostgreSQL 사용. 어느 쪽이든 **빈 데이터베이스 1개**(control) + 접속 사용자만 준비 | A |
| 권한 | 설치는 root/sudo | A·B |
| CPU / GPU | **이번 반입은 CPU 전용**. 서버 B 에 GPU 가 있으나 사용하지 않는다(CUDA 미반입). GPU 를 쓰려면 재수집이 필요하며 이번 범위가 아니다 | A·B |
| 메모리 | 권장 8 GiB 이상 (WAS JVM + ai-server torch CPU) | A·B |
| 디스크 | 앱·런타임·모델 약 2 GiB + 영상 저장소(별도 산정) | A·B |
| **NAS 마운트** | 영상·프레임 저장 경로(예 `/nas-storage`)가 마운트되고 서비스 계정이 쓸 수 있어야 함 | A |
| **KPST 비식별 서버** | 폐쇄망에 별도 설치·접근 가능(본 패키지 비포함, 외부 시스템). 비식별은 파이프라인 선두 필수 단계라 운영에서 우회할 수 없다 | A |
| **네트워크 규칙** | 서버 A: 80(외부 인바운드는 이것만 노출 권장) · 8080(WAS) · 5432(DB) · KPST 비식별 포트. **서버 A → 서버 B 의 9300 도달 필수** | A·B |

## 11. 반입 및 설치 절차 요약

```
[빌드머신 — 인터넷 필요. RPM·pip 휠은 el8 x86_64 환경에서 수집]
  1) ./scripts/package.sh
       api.war · 프론트 dist · pip 휠(CPU) · 파이썬 런타임 · 시스템 RPM · ffmpeg RPM(예비물)
       · GPG 키 · 모델 · (L)GPL 대응 소스 · 라이선스 고지 집합
  2) 무네트워크(--network none) 설치 리허설 통과 확인
  3) deploy/onprem/ 폴더 전체를 반입 매체로 복사 (잔재 정리 상태 확인 — §7)

[서버 A — 폐쇄망, RHEL 8.9. 프론트 + 백엔드]
  4) 체크섬 대조 (§5-1 의 SHA256SUMS)
  5) sudo ./scripts/install.sh --role=app
       (옵션)PostgreSQL → api.war 배치 → 프론트 dist + httpd → DB·유저 초기화 → DB 스키마 로드
       → ffmpeg 전제조건 검증(없으면 여기서 중단)
       → 프론트 런타임 설정 게이트(상위 로그인 주소가 비면 중단) → AI 서버 주소 확인(경고만)
       ★ DB·유저 초기화와 스키마 로드는 <옵트인>이다(DB_INIT_RUN=1 / SCHEMA_LOAD_RUN=1).
         주지 않으면 수동 절차만 출력하고 성공으로 끝나며, 그래도 <기동은 된다> — 화면·배치가
         DB 를 처음 쓸 때 깨진다(docs/03-install.md 「테이블을 만드는 주체」).
  6) sudo $EDITOR /etc/klid/application.properties     # DB 접속·JWT 시크릿 등
     sudo $EDITOR /etc/klid/was.env                    # WAS 현장값
     sudo $EDITOR /etc/klid/frontend.env               # 상위 로그인 주소(필수) · 개발화면 토글(§8)
  7) ★ WAS 설정 이관 — docs/10-was-settings.md 체크리스트 완수
       (건너뛰면 기동·일반 요청은 정상이고 대용량 업로드만 조용히 깨진다)
  8) ★ /opt/klid/app/api.war 를 WAS 배포 디렉터리로 사람이 복사 (파일명 변경 금지)
  9) sudo systemctl enable --now httpd

[서버 B — 폐쇄망, RHEL 8.9. ai-server]
 10) 체크섬 대조
 11) sudo ./scripts/install.sh --role=ai
 12) sudo $EDITOR /etc/klid/ai-server.env
 13) sudo systemctl enable --now klid-ai-server
     ★ 서버 A 의 AI_SERVER_URL 을 이 장비 주소로 바꿀 것 (기본값은 127.0.0.1)
```

설치 검증:

```bash
curl -fsS http://127.0.0.1:8080/api/actuator/health/liveness   # 백엔드 (WAS 기동 후, 서버 A)
curl -fsS http://127.0.0.1/                                     # 프론트엔드 (서버 A)
curl -fsS http://127.0.0.1:9300/health                          # ai-server (서버 B)
```

## 12. 심의 유의사항

1. **자바 런타임 미반입** — 대상 WAS 가 이미 Java 17 로 구동 중이므로 반입하지 않는다(§3-1).
   따라서 이 매체만으로는 백엔드가 단독 실행되지 않으며, WAS 가 전제조건이다.
2. **ffmpeg 은 담되 설치하지 않는다** — 관제지원시스템과 공동 배치라 자동 설치가 관제를 깨뜨릴 수
   있다. 예비물로만 동봉하며 별도 명령으로만 설치한다(§3-3). 담아서 넘기는 것 자체가 재배포이므로
   GPL 대응 소스(SRPM)를 함께 반입한다.
3. **카피레프트 7건 + wheel 번들 2건에 대한 대응 소스를 실물로 동봉했다**(§6-3·§6-4).
   대응성은 soname ↔ 소스 선언 버전 기계 대조로 확인했으며, 불일치 시 수집이 중단되도록 자동화되어 있다.
4. **"허용적 라이선스라 의무가 없다"는 서술을 쓰지 않았다** — MIT·BSD·Apache-2.0 도 재배포 시
   고지·사본 제공 의무가 있으며, 371건 전부의 전문을 동봉해 이행했다(§6-1·§6-2).
5. **개발용 로그인 화면이 켜진 채 반입된다**(§8). 운영 프로파일에서는 백엔드 기동 가드가 해당
   엔드포인트를 구조적으로 차단하므로 실질 노출은 없으나, **사실을 먼저 밝히고 재빌드 없이 끄는
   절차를 함께 제공**한다.
6. **검증 범위의 한계**(§9-2) — 무네트워크 리허설은 조달 누락과 오프라인 설치를 검증하지만,
   **WAS 기동·대용량 업로드·SELinux Enforcing·실기동 추론·방화벽·NAS 는 검증하지 않았다.**
   특히 **WAS 설정 이관은 누락돼도 기동·일반 요청이 정상이라 신호가 없으므로**, 대상 장비에서
   대용량 업로드를 1회 수행해 확인해야 한다.
7. **리허설 배포판이 대상과 다르다** — Rocky Linux 8.10 에서 수행했다. 같은 RHEL 8 계열이고
   glibc 2.28 로 동일하나 동일 배포판은 아니다.
8. **매체 잔재 정리**(§7) — 네 건(`src/` 40.2 MiB · 파이썬 바이트코드 2.8 MiB ·
   실행 가능 jar 83.6 MiB · macOS `.DS_Store` 6 KB)을 **모두 제거했다.** 미조치 항목은 없으며,
   매체 생성 직전에 §7-5 의 명령으로 용량을 한 번 더 실측한다.
