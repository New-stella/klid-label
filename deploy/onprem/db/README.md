# 온프렘 DB 산출물 — 세 가지를 헷갈리지 말 것

| 파일/폴더 | 성질 | 누가 바꾸나 |
|---|---|---|
| `schema.sql` | **생성물**. `gen-schema-sql.sh` 가 마이그레이션 전량을 클린 PG 에 적용해 덤프한다. 마이그레이션이 늘면 **덮어써서 다시 만든다**. | 빌드머신 스크립트 |
| `baseline/` | **동결본**. 특정 시점의 `schema.sql` 을 그대로 얼려 둔 것. **다시 만들지 않는다.** 상용 현장이 실제로 설치한 스키마가 무엇이었는지의 기준점. | 사람이 상용 반입 때 1회 |
| `incremental/` | 동결본 **이후**의 변경. 현장에는 스키마 전체가 아니라 이 증분만 넘긴다. | 마이그레이션이 늘 때 |

## 왜 갈라 두는가

온프렘은 Flyway 를 끄고(`SPRING_FLYWAY_ENABLED=false`) 설치 시 스키마 파일을 1회 로드한다.
그래서 **현장 DB 를 갱신할 유일한 수단이 사람이 SQL 을 적용하는 것**인데, 갱신할 때
`schema.sql` 을 통째로 다시 주면 그건 갱신이 아니라 **재설치**다 — 현장 데이터가 사라진다.

동결본이 없으면 "현장이 지금 어느 형상인가"를 되짚을 근거가 사라진다. `schema.sql` 은
재생성으로 계속 덮어써지므로 **과거 반입 시점의 내용을 갖고 있지 않기 때문**이다.

## 규칙

1. 상용 반입 시점의 `schema.sql` 을 `baseline/` 에 얼린다(파일명에 날짜 + 마이그레이션 경계).
2. 그 이후 추가되는 마이그레이션은 **원본 파일 그대로** `incremental/` 로 모은다.
3. 현장에는 **동결본(최초 1회) + 그 뒤 증분(순서대로)** 을 넘긴다.
4. 다음 상용 반입에서 기준선을 새로 잡을 때만 `baseline/` 에 **새 파일을 추가**한다.
   기존 동결본은 지우지 않는다 — 어느 현장이 어느 기준선인지 갈릴 수 있다.
