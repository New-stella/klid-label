# 기준선 이후 증분 SQL

동결본 `../baseline/schema-baseline-20260904-V31.sql` 는 **V1~V31 적용 결과**다.
그 이후 추가되는 마이그레이션(**V32 부터**)을 여기에 모아 현장에 넘긴다.

지금은 비어 있다 — V31 이 마지막이고 그것까지 동결본에 들어 있다.

## 담는 방법

`backend/src/main/resources/db/migration/V{n}__*.sql` 을 **파일명까지 그대로 복사**한다.
손으로 다시 쓰거나 여러 개를 하나로 합치지 않는다 — 합치면 부분 적용에서 어디까지 갔는지
알 수 없고, 다시 쓰면 개발 환경이 실제로 적용한 것과 어긋난다(그 어긋남은 조용하다).

## ★ 현장 적용 시 반드시 — `search_path`

`V1__baseline.sql` 만 `klid_at.` 로 스키마를 한정하고 **V2 이후는 전부 비한정 식별자**다.
따라서 `search_path` 가 `klid_at` 이 아닌 채로 적용하면:

- `ALTER TABLE`·`DROP` 은 **없는 표를 찾다 실패**하고 (시끄러워서 오히려 안전하다)
- `CREATE TABLE IF NOT EXISTS` 는 **`public` 에 빈 표를 새로 만든다** — 오류가 나지 않는다.
  앱은 `klid_at` 을 보므로 그 표는 영원히 비어 있고, 아무도 모른다.

접속 옵션으로 주는 것이 가장 안전하다(파일 내용을 건드리지 않고 세션이 갈릴 여지도 없다):

```bash
PGOPTIONS='-c search_path=klid_at' psql -v ON_ERROR_STOP=1 -d "$DB" -f V32__....sql
```

적용 후 대상 스키마를 확인한다:

```sql
SELECT table_schema, table_name FROM information_schema.tables
 WHERE table_name = '<이번에 만든 표>';   -- klid_at 하나만 나와야 한다
```

## 적용 순서·횟수

번호 오름차순으로 **한 번씩만**. `ON_ERROR_STOP=1` 로 돌려 중간 실패가 다음 파일로 넘어가지
않게 한다.

## ⚠ 무엇이 적용됐는지 남기는 자리가 아직 없다 (미확정)

온프렘은 Flyway 를 끄고 스키마 파일을 로드하므로 `flyway_schema_history` 가 **없다**.
즉 현장 DB 만 봐서는 어느 증분까지 적용됐는지 알 수 없고, 지금은 **인수인계 문서에 사람이
적는 것**이 유일한 근거다. 증분이 몇 개 쌓이면 이 방식은 깨진다.

정하지 않고 남겨 둔다 — 선택지는 대략 셋이며 어느 쪽도 지금 임의로 도입하지 않는다.

1. 적용 이력 표를 하나 두고 적용 스크립트가 기록 (Flyway 를 켜지 않고 최소로 흉내)
2. 설치 시 Flyway `baseline-version` 을 동결본 번호로 잡고 이후는 Flyway 에 맡김
   (2노드 동시 기동 시 advisory lock 경합을 피하려고 끈 것이므로 그 판단을 뒤집는 셈)
3. 현행 유지 — 인수인계 문서로만 관리
