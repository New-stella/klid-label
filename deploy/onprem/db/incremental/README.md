# 기준선 이후 증분 SQL

동결본 `../baseline/schema-baseline-20260904-V31.sql` 는 **V1~V31 적용 결과**다.
그 이후 추가되는 마이그레이션(**V32 부터**)을 여기에 모아 현장에 넘긴다.

무엇이 들어 있는지는 **이 폴더를 직접 보는 것**이 정본이다. 여기에 목록을 다시 적지 않는다 —
적어 두면 증분이 늘 때마다 한쪽만 갱신되어 어긋난다(실제로 그렇게 낡았던 자리다).

## 담는 방법

`backend/src/main/resources/db/migration/V{n}__*.sql` 을 **파일명까지 그대로 복사**한다.
손으로 다시 쓰거나 여러 개를 하나로 합치지 않는다 — 합치면 부분 적용에서 어디까지 갔는지
알 수 없고, 다시 쓰면 개발 환경이 실제로 적용한 것과 어긋난다(그 어긋남은 조용하다).

## ★ 현장 적용 시 반드시 — `search_path`

`V1__baseline.sql` 만 `klid_at.` 로 스키마를 한정하고 **V2 이후는 전부 비한정 식별자**다.
따라서 `search_path` 가 `klid_at` 이 아닌 채로 적용하면:

- `ALTER TABLE`·`DROP` 은 **없는 표를 찾다 실패**하고 (시끄러워서 오히려 안전하다)
- `CREATE TABLE IF NOT EXISTS` 는 **`public` 에 빈 표를 새로 만든다** — 오류가 나지 않는다.
  앱은 `klid_at` 을 보므로 그 표는 영원히 비어 있고, 아무도 모른다.

접속 옵션으로 주는 것이 가장 안전하다(파일 내용을 건드리지 않고 세션이 갈릴 여지도 없다):

```bash
PGOPTIONS='-c search_path=klid_at' psql -v ON_ERROR_STOP=1 -d "$DB" -f V32__....sql
```

적용 후 대상 스키마를 확인한다:

```sql
SELECT table_schema, table_name FROM information_schema.tables
 WHERE table_name = '<이번에 만든 표>';   -- klid_at 하나만 나와야 한다
```

## 적용 순서·횟수

번호 오름차순으로 **한 번씩만**. `ON_ERROR_STOP=1` 로 돌려 중간 실패가 다음 파일로 넘어가지
않게 한다.

## ★ 적용은 스크립트가 하고 이력은 DB 에 남는다 (2026-09-06 확정)

**`scripts/apply-migrations.sh` 가 이 폴더의 정본 적용 수단이다.** 위 「적용 순서·횟수」와
「search_path」 규칙을 스크립트가 강제하므로, 손으로 psql 을 돌리는 것은 그 스크립트를 쓸 수
없을 때의 예외 경로다.

```bash
./scripts/apply-migrations.sh --status     # 현황만 (아무것도 바꾸지 않음)
./scripts/apply-migrations.sh --dry-run    # 적용 예정 목록
./scripts/apply-migrations.sh              # 미적용분을 번호순으로 적용
./scripts/apply-migrations.sh --mark-only  # ★ 신규 설치 직후 전용 — 실행 없이 기록만
```

적용 이력은 **`klid_at.ls_schm_aplcn_hstry`** 에 남는다(파일명·버전·sha256·상태·적용자·일시).
이 표는 **설치 도구가 소유**하며 앱은 읽지 않는다 — `flyway_schema_history` 와 무관하고,
`16-load-schema.sh` 의 테이블 개수 판정에서도 이 이름 하나만 제외한다.

무엇이 닫혔나 — 구 서술 *"무엇이 적용됐는지 남기는 자리가 아직 없다(미확정)"* 는 폐기다.
그 선택지 셋 중 **①(적용 이력 표 + 스크립트 기록)** 이 채택됐다.
⚠ **②(Flyway 를 켜고 `baseline-version` 지정)는 기각됐다** — 여러 노드가 함께 뜨는 형상에서
기동 시 advisory lock 경합을 피하려고 끈 것이므로 그 판단을 뒤집지 않는다. 되살리지 말 것.
③(문서로만 관리)은 증분이 쌓이면 깨진다는 원래 진단 그대로다.

**스크립트가 지키는 것 (손으로 할 때도 같아야 한다)**

- 한 파일 = 한 트랜잭션 = 한 세션. 같은 트랜잭션 안에서 자문 잠금 → 중복 재확인 → 실행 →
  이력 기록을 하므로, 여러 노드가 동시에 돌려도 한 번만 적용된다. 실패하면 그 파일은
  **통째로 롤백**되고 뒤 번호는 실행하지 않는다.
- **이미 적용된 파일의 내용이 바뀌면 멈춘다**(sha256 대조). 증분 파일은 한 번 나가면 고치지
  않는 것이 규칙이므로, 바꿔야 하면 새 번호로 추가한다.
- 적용 후 **`public` 오생성을 검사**한다(위 search_path 함정의 사후 확인).
- `CONCURRENTLY`·`VACUUM` 처럼 트랜잭션 안에서 못 도는 문장이 든 파일은 **받지 않고 멈춘다** —
  조용히 절반만 적용되는 것보다 낫다. 그런 파일은 절차를 따로 정해 사람이 적용한다.

⚠⚠ **`--mark-only` 는 신규 설치 직후에만 쓴다.** 설치가 로드한 `schema.sql` 은 그 시점의 증분을
이미 **포함**한 통합본이라 같은 증분을 다시 실행하면 멱등하지 않은 문장에서 실패하고, 그렇다고
기록을 안 남기면 다음 회차에 미적용으로 보여 또 실행된다. 기존 운영 DB 에 쓰면
**적용하지 않은 것을 적용했다고 기록**한다.
