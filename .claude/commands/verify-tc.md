# 테스트케이스 전수 검증 (실동작 기준)

`docs/test-cases/` 카탈로그(A~H 8클러스터, ~1,210+ 케이스)를 **목업서버 연동 풀스택이 떠 있는 정상 시나리오 위에서** 전수 검증하고 회차별 폴더에 결과를 기록한다.
**1차 검증 → 결함 수정 → 2차 폴더에 재검증** 사이클 반복이 운영 모델이다.

인자: `$ARGUMENTS`
- 1번째 = 클러스터(`A`~`H`) / `all`(A부터 순서대로) / `resume`(체크포인트에서 이어서)
- 2번째 = 회차 폴더명(생략 시 `1차`)
- 비면 `README.md` 순서에서 **결과 파일이 없는 첫 클러스터**부터

---

## ★ 0. 대전제 — 실동작 환경 (사용자 확정 2026-07-25, 타협 불가)

> 이 검증은 **"코드가 그렇게 보인다"가 아니라 "실제로 그렇게 동작한다"**를 판정한다.

1. **목업서버 기동 필수** — 외부 연동(비식별 KPST · VLM · 증강)은 **전부 `mock-server`(FastAPI :9400)가 대신 수행**한다. 실벤더를 호출하지 않는다.
2. **로컬은 무조건 목업서버를 바라본다** — 내부 목 모드(`DEIDENTIFY_MOCK_MODE=true` 류)로 외부 호출을 건너뛰는 우회는 금지.
3. **자체 채움(self-fill) = 결함** — 본 프로그램이 외부 응답 없이 값을 만들어 넣거나 하드코딩 기본값으로 메꾸면 **결함으로 기록**한다. 값은 항상 외부 연동 응답에서 와야 한다.
4. **배치를 실제로 구동**한다 — 파이프라인(비식별→마킹→VLM→프레임추출→오토라벨링→보간)이 흐르는 정상 시나리오를 만들어 그 위에서 판정한다.
5. **풀스택 기동** — PostgreSQL + backend + ai-server + mock-server + frontend.

### 착수 전 환경 게이트
`_raw/stack-bringup.md` 를 확인한다.
- 없으면 → **먼저 풀스택 기동 에이전트를 띄워** 기동·헬스·외부연동 실배선을 실측 기록시킨다(§2 참조)
- 있으면 → 기동 상태·배선 O/X 를 읽고, **배선이 X 인 항목은 그 연동에 걸린 케이스 판정 시 반드시 반영**한다
- 스택이 안 뜨거나 배선이 깨져 정상 시나리오를 못 만들면 → **임의로 정적 판정으로 후퇴하지 말고 사용자에게 에스컬레이션**한다

## 1. 시작 전 로드 (순서 준수)

1. `docs/test-cases/README.md` — 클러스터 순서(A→H)·ID 프리픽스·표 규약
2. `docs/test-cases/UNCERTAINTIES.md` — **PASS/FAIL 판정 기준**. 확정 항목은 반드시 그 판정으로:
   - #1 포털 SAM2 노출 = **문서가 정본, 정책 위반 → 결함(FAIL)**. 정상기능 케이스로 두지 않음
   - #3 TASK_COMPLETED payload 0/null 하드코딩 = **구현 누락 결함(FAIL)**. 기대값은 실카운트 — *self-fill 금지 원칙과 같은 뿌리*
   - #4 관제 조회 API 본인배정 검증 부재 = **의도된 광범위 허용 → IDOR 아님**. 해당 케이스 제외
   - #2·#5~#25 = 미확정 → `확인필요` 표기, 사실만 기록(임의 확정 금지)
3. 해당 클러스터 파일 `docs/test-cases/{A~H}-*.md`
4. `_raw/stack-bringup.md`(환경 실태) + `_raw/test-baseline.md`(자동테스트 결과)
5. 이전 회차 결과가 있으면 그 회차 `ISSUES.md` — **재검증 시 이전 이슈 해소 여부를 반드시 대조**

> README 케이스 수는 어림값이다. **`grep -c '^| TC-'` 로 실제 행 수를 세어 기록**한다(A는 ~120 표기인데 실제 156건이었다).

## 2. 환경 준비 (회차당 1회)

### 2-1. 풀스택 기동 → `_raw/stack-bringup.md`
- mock-server 가 배선된 compose(통상 `docker-compose.local.yml`)로 기동
- 헬스 실측: mock-server(:9400) · backend `/actuator/health` + Flyway · ai-server(:9300) · frontend(:5173) · DB `klid_at`
- **★ 외부 연동 실배선 검증** — 설정 파일 문구가 아니라 **런타임 실효값**으로:
  - `docker compose exec`/`docker inspect` 로 backend 실효 환경변수 덤프 → 외부 연동 URL 이 mock-server 를 가리키는지
  - 내부 목 모드 플래그 실효값 — `true` 면 **결함 기록**
  - mock-server 로그 tail → backend 가 실제로 인바운드 요청을 보내는지
- 알려진 함정: `vlm.client.url` 은 `base-url` 과 **다른 키** · `MOCK_OUTPUT_BASE` 미설정 시 fail-closed · `retrieve_progress` 는 GET + body

### 2-2. 자동테스트 baseline → `_raw/test-baseline.md` (없을 때만)
- backend `./gradlew cleanTest test --continue` — ⚠ `test` 만 돌리면 `UP-TO-DATE` 캐시로 **실제 실행이 안 된다**. `cleanTest` 필수
- frontend `npx vitest run` / ai-server `.venv/bin/python -m pytest tests/ -q` (시스템 python 엔 pytest 없음)
- macOS 엔 `timeout` 명령 없음 → 백그라운드 + 폴링
- ⚠ **gradle 테스트 동시 실행 금지** — test-results XML 충돌로 위양성 실패. baseline 1개만 실행하고, 정적 검증 에이전트에겐 **빌드/테스트 실행을 명시 금지**하고 이 파일을 참조시킨다

### 2-3. 정상 시나리오 데이터 구동 (클러스터 성격에 따라)
B~E 처럼 파이프라인이 걸린 클러스터는 검증 전에 **실제로 영상 1건을 파이프라인에 태워** 정상 흐름을 만든다.
적재 → 비식별(목업서버) → 마킹 → VLM 콜백 → 프레임추출 → 오토라벨링 → 배정 → 라벨링 → 검수승인 → export
각 단계의 상태 전이(`LS_DATA_RAW.dataSttsCd`, `LS_RAW_DATA_STATUS`)와 **목업서버 인바운드 로그**를 근거로 남긴다.

## 3. 검증 방법 (케이스 1건마다)

| 순서 | 방법 |
|:--:|------|
| 1 | **실동작 확인 (최우선)** — 스택에 실제 요청을 보내거나 파이프라인을 태워 기대결과가 나오는지 확인. 응답·DB상태·목업서버 로그를 근거로 |
| 2 | **정적 대조** — 근거의 **파일(+심볼)** 을 열어 기대결과와 대조. 그 판정이 없으면 Grep 으로 실제 위치를 찾아 **근거 드리프트로 집계**. ⚠ 근거는 **`파일명(심볼명)`** 형식이며 라인번호를 적지 않는다(2026-08-05 확정) — **라인 부재는 드리프트가 아니다.** 정정 대상은 **파일 리네임·삭제·이동 · 판정 주체의 클래스 이동 · 심볼 리네임**뿐. 또 **심볼 없는 파일명 단독 행은 미보강 상태이지 결함이 아니다**(일괄 백필 안 함) — 다만 그 행을 이번 회차에 정정한다면 **심볼을 함께 채운다** |
| 3 | **테스트 커버 확인** — 기존 자동 테스트를 Grep 해 `파일:메서드명` 기록 + `_raw/test-baseline.md` 에서 통과 여부 대조 |
| 4 | **외부 연동 케이스** — 목업서버를 실제로 경유했는지 확인. 경유 없이 값이 채워졌으면 **self-fill 결함(FAIL)** |

### 판정값
| 값 | 의미 |
|----|------|
| **PASS** | 실동작으로 기대결과 확인(또는 정적 대조가 확실하고 실동작이 이를 뒷받침) |
| **FAIL** | 기대결과와 다름 = 결함. **self-fill(외부 응답 없이 자체 채움)도 여기** |
| **PARTIAL** | 일부만 충족 / 방어가 불완전 |
| **BLOCKED** | 풀스택으로도 재현 불가(외부 실벤더 필요·특수 인프라 등) — **사유 필수**. ⚠ "환경 안 띄워서 못 봄"은 BLOCKED 가 아니라 **환경을 띄워서 해결할 일** |
| **N/A** | 전제가 코드에 없음 — 미구현 갭이면 FAIL 승격 판단 후 사유 기록 |
| **확인필요** | UNCERTAINTIES 미확정 — 사실만 기록 |

### ★ 확증편향 금지 (이 검증의 성패)
**"코드가 있으니 PASS" 는 검증이 아니다.** 실패 모드는 **거짓 PASS** 다.
기대결과의 단언을 하나씩 **반증 시도**한다 — 경계값·null·예외경로·fail-open·우회 경로를 실제 분기와 실동작으로 확인한다.
(실제로 이 방식이 A 클러스터에서 HMAC 필터 URL 인코딩 우회, 공유 정적 패스워드 권한상승 같은 HIGH 결함을 잡아냈다. 정적 대조만으로는 전부 PASS 였다.)

## 4. 에이전트 분할·모델

- 클러스터 파일의 `## ` 섹션으로 2~4분할해 **병렬** 실행(케이스 50~60건/에이전트)
- 각 에이전트는 **결과 파일 1개만 Write**, 그 외 **모든 파일 수정 금지**(프로덕션·테스트·문서·설정 전부)
- 최종 응답은 20줄 이내 요약만(표 원문 붙여넣기 금지 — 메인 컨텍스트 보호)
- 실동작 확인을 위한 **HTTP 요청·DB 조회·로그 조회는 허용**, **빌드/테스트 실행과 파일 수정은 금지**

### 모델 (memory `verification-agent-model-policy` 정본)
| 구간 | 모델 |
|------|:----:|
| 정적 대조 대다수 | **sonnet** |
| **보안 필터 · 동시성/Race · 상태전이 · 외부연동 계약**(A-3~A-5, B 배치·PII, D 상태전이, E export) | **opus** |
| 환경 기동 · baseline 실행 | **sonnet** |

> `model` 을 생략하면 세션 모델(opus)을 상속해 비용이 샌다 — **항상 명시**.

### 구간별 반증 포인트 (프롬프트에 포함)
- **인증/인가**: 우회 경로, fail-open catch, 권한 자가부여·상속으로 인한 수직 상승(CWE-269/862)
- **서명/HMAC**: 상수시간 비교, replay 방지(nonce·시간창), **URL 인코딩·경로 정규화 불일치로 필터 스킵**(CWE-436)
- **외부 연동**: 목업서버 미경유 self-fill, 타임아웃·재시도·서킷브레이커 실동작, 계약 필드 불일치, 실패 시 fail-closed 여부
- **배치/동시성**: race, 중복 실행(Quartz 클러스터), 부분 실패 시 상태 정합, 트랜잭션 경계, PII 노출
- **상태전이**: 불법 전이 차단, 되돌리기, 동시 전이
- **예외/로깅**: 스택트레이스·내부경로 유출(CWE-209), PII·토큰 마스킹, Log Injection(CWE-117)
- **쿼리**: N+1, 무페이징 전체조회, 인덱스 부재

## 5. 이슈 기록 형식 (Critical — 수정 작업의 입력)

FAIL / PARTIAL / 확인필요 **전건**. 수정 후 다음 회차에 이 블록으로 대조하므로 축약 금지.

```markdown
### [{클러스터}-ISSUE-{nn}] {TC-ID} — {한 줄 제목}
- **심각도**: CRITICAL / HIGH / MEDIUM / LOW
- **기대 동작(기대효과)**: 보장해야 하는 것 + 왜 필요한지
- **현재 동작(이슈 내용)**: 실제 동작 (file:line + 스니펫 3~5줄, 실동작이면 요청/응답·DB상태·로그 근거)
- **재현/확인 경로**: 어떤 입력·조건에서 드러나는지 (가능하면 실행 가능한 curl/SQL)
- **영향**: 보안/데이터정합/기능 영향 (보안이면 CWE 번호)
- **수정 방향(제안)**: 어디를 어떻게 (⚠ **구현은 하지 않는다**)
```
이슈 ID 는 에이전트별 시작번호를 나눠 부여(part1=01~, part2=11~, part3=21~) — 병렬 충돌 방지.

> **⚠ 판정 셀 표기 규칙 (집계 정확도)**: 결과 표의 판정 컬럼에는 **`PASS` / `FAIL` / `PARTIAL` / `BLOCKED` / `N/A` / `확인필요` 여섯 토큰 중 하나만** 넣는다. `PASS(LIVE)`·`PASS(정적)`·`**PASS**` 처럼 꾸미면 회차 집계가 어긋난다(1차에서 실제로 발생). 실동작/정적 구분은 **`근거 확인` 컬럼에 `[실동작]` / `[정적]` 접두로** 적는다.

## 6. 클러스터 완료 처리

1. `_raw/{X}-part*.md` 를 `cat` 으로 `{X}-result.md` 병합(**메인 컨텍스트에 내용을 싣지 말 것**)
2. 이슈를 `ISSUES.md` 에 누적(클러스터 헤딩 + 심각도순)
3. `.claude-progress.md` 갱신
4. **컨텍스트 점검 (Critical)** — 클러스터 경계에서 사용률 **60% 초과 시 즉시 정지**하고 사용자에게 보고:
   완료 클러스터 · 판정 집계 · 주요 결함 3~5건 · 다음 클러스터 · 재개 방법(`/verify-tc {클러스터}` 또는 `resume`)
   사용자가 compact 후 재개를 지시한다. **임의로 계속 진행하지 않는다.**
5. 60% 미만이고 `all` 모드면 다음 클러스터 자동 진행

## 7. 전 클러스터 완료 시

`SUMMARY.md`:
- 클러스터별 집계표(총/PASS/FAIL/PARTIAL/BLOCKED/N/A/확인필요) + 합계·PASS율
- **심각도순 결함 TOP**(CRITICAL·HIGH 전건)
- **self-fill 결함 목록** — 외부 연동을 안 타고 자체 채운 경로 (별도 섹션, 이 프로젝트의 핵심 관심사)
- BLOCKED 사유별 묶음 = 다음 회차에 필요한 것
- 근거 드리프트 목록 = 카탈로그 자체의 정합성 결함
- UNCERTAINTIES 중 이번에 **사실이 확정된 항목** → 원본 갱신 제안

이어서 AskUserQuestion: **결함 수정 착수(`/cc` DEV_FIX)** / 카탈로그 정정 / 종료.

## 8. 절대 규칙

- 이 커맨드는 **검증 전용 — 코드를 고치지 않는다.** 결함은 기록만 하고, 수정은 사용자 지시로 별도 `/cc` 사이클에서 developer 에이전트가 수행한다.
  (근거: 검증 중 코드가 바뀌면 앞뒤 판정 기준이 어긋나 회차 결과를 신뢰할 수 없다)
- 검증 에이전트에게 **빌드/테스트 실행 금지**를 명시(baseline 담당 1개 예외).
- PASS 판정에는 **반드시 확인한 근거**(실동작 응답 또는 코드 인용)를 남긴다. 근거 없는 PASS 금지.
- **환경을 안 띄운 채 정적 판정으로 후퇴하지 않는다.** 못 띄우면 에스컬레이션.
- 결과 파일 외 어떤 파일도 에이전트가 수정하지 못하게 프롬프트에 못박는다.
