## §1 배경

사용자 신고: *"비식별 실패했을때 다시 할 수단이 없어."*

영상이 들어오면 파이프라인 맨 앞에서 비식별이 **한 번** 자동으로 돈다
(`VideoIngestedEvent` → `IngestDeidentifyBridge` → `AsyncDeidentifyRunner.runAsync` → `preMarkingPipeline` = `DeidentifyStep`).
이게 실패하면 영상은 `LS_DATA_RAW.DE_IDENT_YN='F'` · 비식별 이력(`LS_DEIDENT_PROC_LOG`) 실패 행 ·
`DATA_STTS_CD` 는 `PENDING` 그대로(= `MARKING_READY` 미도달)로 멈춘다. 이후 마킹에 들어갈 수 없다.

코드 실측으로 확인한 「다시 할 길」이 **하나도 없다**:

| 기존 경로 | 왜 못 쓰나 |
|---|---|
| 배치 재처리 `POST /v1/videos/{rawSn}/batch/retry` (API-167) | `BatchOrchestrator` 가 **post-marking 파이프라인만** 돈다 — 비식별 단계가 없다 |
| 검수완료 재비식별 `POST /v1/videos/{rawSn}/redeident` (API-112) | `ApprovedRedeidentService` 가 **APPROVED 영상만** 받는다(미승인 409). 화면 진입점도 SCREEN-009 에서 제거됨 |
| 비식별 신고 해소 `POST /v1/deident-reports/{rprtSn}/resolve` | **OPEN 신고가 있어야** 한다. 파이프라인 실패는 신고를 만들지 않는다 |
| 자동 트리거 | 적재 직후 1회뿐. 자동 재비식별 큐는 **정책상 없다**(설계 결정 3) |

⇒ 외부 비식별 서버가 잠깐 죽었거나 위탁 ACK 가 유실되기만 해도 그 영상은 **영구 고착**된다
(저장소 직접 수정 말고는 복구 수단이 없다).

**정책과의 관계**: CLAUDE.md 의 *"자동 재비식별 큐 없이 외부 프로그램에서 수동 재비식별"* 은
**「자동 큐를 두지 않는다」**가 핵심이다. 이번 기능은 **사람이 눌러야만 도는 수동 재시도**라
그 정책을 뒤집지 않는다. **자동 트리거(스윕·재시도 큐·스케줄)는 추가하지 않는다.**

## §2 변경 요지

**새 버튼·새 API 를 만들지 않는다. 기존 「배치 재시작」(건별 API-167 · 일괄 API-199)이 비식별 실패 영상도 처리한다.**
(사용자 확정 2026-09-16 — *"비식별 실패도 배치 실패아냐?"*)

1. 화면은 이미 비식별(DEIDENTIFY) 단계 실패를 **배치 실패로 보여 주고 재시작 버튼을 띄운다**
   (영상 상세 단계 표시 `status=FAIL` → 배치 실패 패널). 그런데 서버는 그 영상을 거절한다 — 이 불일치를 없앤다.
2. 재시작 대상 영상이 **선두 비식별 실패 형상**이면, 기존 경로(마킹 이후 단계) 대신 적재 직후와 **같은 선두 비식별 단계**를
   다시 태운다(외부 위탁 또는 출처유형 제외 원본 복사 — 처리 시점 설정으로 판정). 성공하면 `DE_IDENT_YN='Y'` + `MARKING_READY`.
3. 그 밖의 영상은 **지금과 똑같이** 동작한다.
4. 한 영상에 동시에 한 건만 수락(4노드 Active-Active). 자동 재시도·스윕·스케줄은 추가하지 않는다.

> 사용자 대화 기록:
> - *"비식별 실패했을때 다시 할 수단이 없어."* — 신고.
> - *"그럼 일괄재시작이 필요없는거 아냐? 다 각자 재시작이 있는데"* — 일괄은 건별을 여러 건에 한 번에 거는 기능이라 유지. 외부 서버 장애 뒤 실패가 몰릴 때 필요.
> - *"지금 비식별 실패하고 선택해서 재시도 해도 아무 반응없는데 뭐하는 버튼이야"* — 코드상 건마다
>   「배치가 실패한 영상만 재기동할 수 있으며…」(`BatchReprocessService.NOT_CLAIMABLE_REASON`)로 거부되고,
>   결과 창에 0건 접수 + 사유가 떠야 한다. 「아무 반응 없음」이면 결과 창 표시도 확인 대상(프론트 수용기준).
> - *"비식별 실패도 배치 실패아냐?"* — 맞다. 화면이 이미 그렇게 보여 준다. 그래서 기존 재시작에 포함한다(별도 버튼안 기각 —
>   기존 재시작 버튼이 비식별 실패에서 계속 뜨고 계속 거절되는 상태가 남기 때문).

## §3 도메인별 변경 상세

### DOMAIN-012 (비식별화) — `klid-d012-implementer`  (※ 수정 위치 `batch/` 는 공유 기반, API-167·199 설계 소유는 DOMAIN-003 — cross_domain)

- **대상**: `batch/service/BatchReprocessService.retry` (건별 · API-167) · `batch/service/BatchBulkRetryService.retryOne` (일괄 · API-199 — 건별 `retry` 를 그대로 부르므로 **건별만 바꾸면 일괄이 따라온다**. 일괄 쪽 별도 분기 금지) · 신설 비식별 재시도 협력자(이름은 구현 판단 — 예: 선두 비식별 재시도 서비스) · `batch/runner/AsyncDeidentifyRunner` · `batch/service/KpstDeidentTxService` · 출처유형 제외 실패/성공 경로.
- **분기**: `retry(rawSn)` 에서 존재 확인(404) 뒤, **선두 비식별 실패 형상**이면 비식별 재시도로, 아니면 **기존 코드 그대로**.
  - 형상 판정(한 함수 — 일괄·건별 공용): `DE_IDENT_YN='F'` **그리고** `LS_DATA_RAW.DATA_STTS_CD = PENDING`(마킹 준비 미도달). 실패 후 실제 값이 PENDING 인지 **실측 확인**하고 다르면 실제 형상에 맞춘 뒤 §7 에 기록.
  - 형상에 들어온 뒤의 거부(순서대로, 409 는 사유 문구를 각각 한국어로):
    1. 파생영상(`ORGNL_RAW_SN IS NOT NULL`) → 400 (일괄은 기존 `DERIVATIVE_REASON` 이 먼저 거른다)
    2. 승인 이력(`ReviewApprovalGate.hasEverApproved`) → 409 (**이력**으로 판정)
    3. OPEN 비식별 신고 존재 → 409 (그 `'F'` 는 신고 표식 — 해소 경로가 따로 있다. `'F'` 이중 의미를 여기서 가른다)
    4. 진행 중 위탁 원장(`POLL_STTS_CD IN ('WAITING','POLLING')`) → 409
    5. 작업락 선점 실패(이미 잠김 / partial unique index 위반) → 409
  - 형상이 아니면 기존 판정·메시지·상태코드 **그대로**(비식별 미실패 영상에 대한 응답 불변).
- **실행**: 판정·락 선점을 커밋한 **뒤** 기존 `AsyncDeidentifyRunner.runAsync(rawSn)` 를 호출한다(러너·스텝 복제 금지). 디스패치 거부(`TaskRejectedException`)면 락을 풀고 기존과 같은 503.
  - 위탁 종류(`REQ_KND_CD`)는 **기존 배치 경로 값(null)** — `REDEIDENT` 로 두면 완료가 「APPROVED 유지 경로」로 가 `MARKING_READY` 전이·예약 마킹 깨우기·신고 해소가 빠진다. 배치 완료(`applyBatchCompletion`)는 이미 `'Y'` + `markMarkingReady()` + 보유 락 해제를 한다.
  - `DE_IDENT_YN` 을 `'N'` 으로 되돌리지 **않는다**(되돌림 경로 0건이 다른 판정의 전제). 진행 중 여부는 락·위탁 원장으로 판단.
  - 배치 단계 `DATA_STTS_CD` 를 PROCESSING 으로 선점하지 **않는다**(선두 비식별은 원래 그 축을 건드리지 않는다 — 건드리면 `MARKING_READY` 전이 조건과 회수 스윕이 꼬인다). 선점 표식(`recordReprocessClaimOpened`)·`retryQueue.clearIfIdle` 도 이 분기에서는 쓰지 않는다.
- **응답(API-167)**: 모양 불변 `{rawSn, stage}`. 비식별 재시도 접수 시 `stage` 는 **접수 시점 실제 단계(PENDING)** 를 싣는다(설계 확정값 우선). 200 유지.
- **락 해제 누락 방지(핵심 함정)**: 배치 경로의 실패 종결은 「배치 경로는 락이 없다」를 전제로 **REDEIDENT 일 때만** 락을 푼다. 다음 **모든 종결**에서 이 기능이 잡은 락을 풀어야 한다 — 안 풀면 영원히 409:
  - `KpstDeidentTxService.failSubmit` · `failPolling` · `markRawDeidentFailed` · `markTimeoutIfExpired` · ACK 유예 만료 회수(`KPST_ACK_MISSING`) · 취소 종결(`KPST_SUBMIT_CANCELED`)
  - `AsyncDeidentifyRunner.runAsync` catch(제출 이전 실패) · 출처유형 제외 실패(`DeidentExclusionTxService.recordFailure`)
  - 출처유형 제외 **성공**(동기 완료 분기 — KPST 완료 지점을 안 탄다)
  - ★ **이 기능이 잡은 락만** 푼다 — 같은 `TARGET_RAW` 락을 트랙 병합·검수완료 재비식별도 쓴다. 락 종류 구분 수단을 엔티티에서 확인하고, 없으면 새 락 팩토리로 구분. **스키마 변경이 필요해지면 멈추고 메인 보고**(Phase 3.5).
  - ⚠ 병행 작업 주의: 워크트리 `stream-deid-fix-20260916`(CO-20260916-마킹영상재생-차단결함)이 `KpstDeidentTxService` 완료 지점(ADR-072 재생 인덱스 재배치)을 건드린다 — 충돌 최소화를 위해 완료 지점 본문은 가능한 한 손대지 않는다.
- **불변**: 적재 직후 자동 1회 트리거 · 검수완료 재비식별(API-112) · 신고 해소 · 단계 지목 재수행 · 비식별 미실패 영상의 재시작 동작 · 일괄 요청/응답 모양(1~100건, 부분 성공, 전건 실패도 200) · 원본 경로 폴백 금지 · 비식별 파일명 조합 금지.
- **주의**: 감사 INFO `[BatchReprocess] deident retry claimed rawSn={}`(식별자만). 판정은 read-then-check 라 **락 INSERT 유니크 위반이 최종 방어**. 판정과 락 선점은 같은 트랜잭션.
- **수용기준(설계 확정 후 AC 번호로 치환)**
  - 선두 비식별 실패 영상 건별 재시작 → 200 · 락 1건 · 러너 1회 · 완료 시 `'Y'` + `MARKING_READY` + 락 해제 · 배치 단계 선점 없음.
  - 같은 영상이 일괄 재시작에 섞여도 같은 결과(성공 1건), 배치 실패 영상은 기존대로 재기동.
  - 거부 1~5 각각 해당 코드·사유, 러너 호출 0.
  - 동시 2요청 → 정확히 1건 수락.
  - 위 종결 지점 각각에서 락이 풀려 **재요청이 다시 수락**(지점별 시험).
  - 다른 기능이 잡은 `TARGET_RAW` 락은 풀리지 않는다.
  - 비식별 미실패 영상의 기존 재시작 시험 전건 그대로 통과. WORKER 403.

### 프론트 (SCREEN-009 영상 상세 · SCREEN-008 영상 목록) — `klid-web-implementer`

- **백엔드 뒤에 진행.** API 경로·응답 모양이 불변이라 코드 변경은 작을 것으로 본다.
- **영상 상세**: 비식별 단계 실패에서 뜨는 기존 재시작 버튼이 이제 동작한다 — 안내 문구가 「마킹 이후 단계를 다시 돈다」 식으로 비식별 실패와 어긋나면 고친다. 응답 `stage=PENDING` 을 오류로 취급하지 않는지 확인.
- **영상 목록 일괄 재시작**: 선택 조건이 비식별 실패 영상을 막고 있으면 넓힌다. ★ **「누르면 아무 반응이 없다」 신고 확인** — 전건 거부(0건 접수) 응답에서도 결과 창(`BulkRetryResultModal`)이 뜨고 사유가 보이는지 시험으로 결박한다. 안 뜨면 원인을 찾아 고치고, 뜨는데 알아보기 어려우면 「0건 접수」 안내를 분명히 한다.
- **불변**: 구 `requestRedeident` 진입점을 되살리지 않는다(SCREEN-009 확정 사양). 새 버튼을 만들지 않는다.
- **수용기준**: 비식별 실패 영상에서 재시작 → 접수 안내 · 일괄 결과 창이 전건 거부에도 뜸 · WORKER 비노출 · 접근성.

## §8 2차 라운드 — 재위탁 프로젝트 이름 충돌 (2026-09-17)

### 발견 경위 (246 실반영 검토)
PR #228 을 246 에 올리고 성공 경로를 실제로 돌렸다(테스트 영상 raw 44 — 목업을 내린 채 올려 위탁 전 실패를 만듦 → 목업 재기동 → 재시작).

⇒ 재시작 **경로 자체는 정상**이나, 위탁 프로젝트 이름이 `raw{rawSn}` 고정이라 **위탁이 한 번 나간 영상은 재위탁이 영원히 409** 다. KPST 규격에도 「동일 이름 프로젝트가 있으면 409」가 명시돼 있고(위키 22.3.3), 이전 프로젝트를 지우는 호출은 0건이다. 재시작이 가장 필요한 경우(폴링 실패·시한 초과·확인 응답 누락)에 동작하지 않는다. 검수완료 재비식별(API-112)도 같은 이름을 쓴다.

### 사용자 확정
- **회차별 고유 이름**(권장안): 그 영상의 **첫 위탁은 종전대로 `raw{rawSn}`**, 다시 위탁할 때는 **이번 회차 비식별 이력 번호를 붙여** 겹치지 않게 한다(예 `raw44r57`). 영문·숫자만 — 규격서가 허용 문자 규칙을 구체적으로 적지 않아 기존 이름과 같은 문자 집합에 머문다. 검수완료 재비식별에도 같이 적용한다. 외부 산출물을 지우지 않는다.
- 기각: 재위탁 전 이전 프로젝트 삭제(확인 응답 누락처럼 이전 번호를 모르는 경우 불가 + 외부 산출물·이력 삭제 위험) · 알려진 한계로 두기.

### DOMAIN-012 변경 상세 (2차)
- 대상: `batch/service/KpstDeidentService`(`projectName` · 위탁 요청 조립 · 원장 선발급 순서) · 관련 시험.
- 「첫 위탁」 판정: 그 영상에 **이전 비식별 위탁 이력 행이 있는가**(이번 회차 원장 제외). 판정은 한 곳. 제출 이전 실패만 있던 영상도 외부에 프로젝트가 없으므로 첫 이름이 맞지만, 단순화를 위해 「이전 행이 하나라도 있으면 접미」도 허용 — 어느 쪽이든 **KPST 에 같은 이름을 두 번 보내지 않는** 것이 불변식이다(구현 판단 · 근거 보고).
- 접미에 쓰는 회차 번호는 **이번 회차 원장 행 번호**(선커밋되는 `PROC_LOG_SN`) — 원장 발급이 요청 조립보다 먼저인지 확인하고, 아니면 순서를 맞춘다.
- 불변: 이름 외 위탁 요청 필드 · 폴링·회수·완료 경로 · 산출물 경로·파일명 규칙 · 첫 위탁 이름.
- 수용기준: 같은 영상 두 번째 위탁의 이름이 첫 번째와 다름 · 세 번째도 앞 둘과 다름 · 첫 위탁은 `raw{rawSn}` 그대로 · 검수완료 재비식별도 접미 · 영문·숫자만.
