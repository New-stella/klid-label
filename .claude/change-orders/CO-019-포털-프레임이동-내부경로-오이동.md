## §1 배경

포털 사용자가 포털 라벨링 화면에서 **다음 프레임을 선택하면 "이 화면에 접근할 수 없습니다"** 접근 거부
화면이 뜬다(사용자 신고). 라벨링 작업 자체가 프레임을 오가며 하는 일이라, 이 결함은 포털 라벨링을
**첫 프레임 한 장으로 제한**한다.

**근본 원인 — 프레임 이동 경로가 내부 채널로 하드코딩돼 있다.**

포털 라벨링 화면(`PortalLabelingPage`)은 내부 라벨링 화면(`LabelingPage`)을 **그대로 재사용**하고,
채널 분기는 `portalMode`(토큰 `channel === 'PORTAL'`) 플래그로 화면 안에서 한다. 그런데 프레임 이동
핸들러 `performJump` 는 이동 경로를 내부 경로로 고정해 두었다:

```
frontend/src/pages/label/LabelingPage.tsx:381
navigate(`/label/${target.srcSn}`, { replace: true });
```

포털 사용자는 `/portal/label/:id` 에서 작업 중인데 이동 결과가 `/label/:id` 다. 그 라우트는
`router/index.tsx:233` 에서 `ChannelGuard channel="INTERNAL"` + `RoleGuard allow=[REVIEWER, WORKER]`
로 감싸여 있으므로, PORTAL 채널·PORTAL_USER 역할은 `guards.tsx:89`(채널 불일치)에서
`/forbidden` 으로 리다이렉트되고 `ForbiddenPage` 의 문구 "이 화면에 접근할 수 없습니다" 가 뜬다.

즉 **인가가 잘못된 것이 아니라 화면이 잘못된 주소로 이동한 것**이며, 가드는 정상 동작했다.

**설계는 이미 정확하다** — `SCREEN-029`(포털 라벨링 화면)의 route 가 `/portal/label/:id` 로 규정돼
있다. 따라서 이 건은 설계 드리프트가 아니라 구현 결함 단독이며 LogiCraft ITEM 수정 대상이 없다.

## §2 변경 요지

`LabelingPage.performJump` 가 프레임 이동 경로를 **채널에 따라** 만들도록 고친다 — 포털이면
`/portal/label/{srcSn}`, 내부면 기존대로 `/label/{srcSn}`. `replace: true` 등 나머지 동작은 그대로다.

## §3 도메인별 변경 상세

### 프론트 (SCREEN-029) — `klid-web-implementer`

- **대상 화면·컴포넌트**: `frontend/src/pages/label/LabelingPage.tsx` — `performJump`
  (포털 진입점은 `frontend/src/pages/portal/PortalLabelingPage.tsx`, 이 파일은 `LabelingPage` 를
  감싸기만 하므로 수정 대상이 아니다)
- **소비 API 계약**: 없음 — 클라이언트 라우팅 전용 변경이다. BE 변경 0.
- **변경**:
  - `performJump` 안의 `navigate(\`/label/${target.srcSn}\`, { replace: true })` 를
    **채널 기반 경로 계산**으로 바꾼다. 이미 같은 컴포넌트가 보유한 `portalMode` 플래그를 쓴다
    (새 플래그·새 store 조회를 만들지 않는다).
  - 경로 조립을 **한 곳으로** 모은다. 같은 화면에서 프레임 이동 지점이 늘어날 때 또 하드코딩이
    복제되지 않도록, 파일 안 지역 헬퍼(예: `frameRoute(srcSn)`)로 뽑고 `performJump` 가 그것을 쓴다.
    ⚠ 새 공용 모듈을 만들거나 라우터 상수 파일을 신설하지는 말 것 — 이 CO 의 범위는 이 결함 하나다.
- **불변(건드리면 안 되는 것)**:
  - `replace: true` 를 유지한다. 그 주석이 명시하듯 X(닫기)로 뒤로 갈 때 **이전 프레임이 아니라
    진입 이전 경로(작업 목록)** 로 빠지게 하는 계약이다. push 로 바꾸면 포털·내부 양쪽의 뒤로가기
    동선이 함께 깨진다.
  - `performJump` 첫 줄의 `isEditBlockedNow(currentFrame?.srcSn)` fail-closed 가드와
    `target.srcSn !== data.srcSn` 동일 프레임 no-op 조건을 그대로 둔다.
  - 같은 파일의 나머지 `navigate` 호출 8곳은 **건드리지 않는다**. `navigate(-1)` 7곳은 채널 무관이고,
    `navigate('/task')`(line 218)는 검수 제출 성공 콜백인데 포털은 검수 제출 자체가 미노출이라
    도달 불가다. 이 CO 에서 "포털 대응"을 이유로 그 줄들을 함께 고치지 말 것.
  - `portalMode` 판정식(`useAuthStore((s) => s.claims?.channel === 'PORTAL')`)을 바꾸지 않는다.
  - 라우터(`router/index.tsx`)·가드(`guards.tsx`)를 **고치지 않는다**. 가드는 정상 동작했다.
    `/label/:id` 의 `ChannelGuard`/`RoleGuard` 를 느슨하게 푸는 방향은 **오답이며 금지**한다 —
    그건 포털 사용자에게 내부 화면을 여는 인가 결함이 된다.
- **주의**:
  - 포털 업로드 라벨링 화면(`PortalUploadLabelingPage`, SCREEN-034)은 **별개 페이지**다. 이 CO 의
    대상이 아니며, 그 화면에 같은 결함이 있는지는 확인만 하고 있으면 §7 에 보고한다(이 CO 에서
    고치지 않는다 — 범위 확대 금지).
- **수용기준**:
  1. 포털 채널(`channel='PORTAL'`, role `PORTAL_USER`)에서 프레임을 이동하면 `/portal/label/{srcSn}`
     으로 이동하고 접근 거부 화면이 뜨지 않는다.
  2. 내부 채널(`INTERNAL`)에서 프레임을 이동하면 기존과 동일하게 `/label/{srcSn}` 로 이동한다(회귀 없음).
  3. 두 경우 모두 `replace: true` 로 이동한다.
  4. **mutation 실증**: 수정한 경로 계산을 옛 동작(`/label/` 고정)으로 되돌리면 새 테스트가
     **실패해야 한다**. 통과하면 그 테스트는 아무것도 지키지 않는 것이므로 다시 만든다.
