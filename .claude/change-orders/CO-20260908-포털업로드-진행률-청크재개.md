## §1 배경

포털 사용자가 영상을 업로드할 때 두 가지가 겹쳐 **데이터는 서버에 올라갔는데 사용자는 처음부터 다시 올려야 하는** 상태가 난다.

### 결함 ① — 진행률이 청크 경계에서만 갱신된다

`frontend/src/features/upload/api/tusClient.ts` 의 `uploadFile` 이 `onProgress` 를 **시작 시 1회(338행)** 와 **`patchChunk` 완료 후(349행)** 에만 부른다. 청크가 8MB(`DEFAULT_CHUNK_SIZE`)라 27MB 파일이면 눈금이 `0 → 30 → 59 → 89 → 100` **다섯 번뿐**이고, 한 청크가 올라가는 동안은 막대가 완전히 멈춰 보인다.

같은 파일의 `TUS_CHUNK_UPLOAD_MS_PER_MB = 8_000` 대로면 **한 청크당 60초 넘게 정지한 것이 정상 범위**다. 즉 느린 회선에서는 **정상 동작조차 고장으로 읽힌다.** axios `onUploadProgress` 는 프론트 전체 사용처가 0건이다.

### 결함 ② — 청크 1회 실패가 곧 업로드 실패다

`uploadFile` 의 while 루프(341~351행)에 `patchChunk` 실패를 잡는 곳이 없어 예외가 그대로 올라간다. **재시도 0.** `fetchOffset`(209행 — `HEAD` 로 서버 오프셋 조회)이 이미 있고 재개 경로에서 쓰이는데(325행) **실패 시 그것으로 되돌아오는 경로가 없다.**

게다가 `pages/portal/PortalUploadPage.tsx` 가 `useTusUpload` 를 쓰면서 그 훅의 `pause`/`resume` 을 **렌더하지 않는다**(파일 내 언급 0건). 훅에는 있는데 화면이 안 쓰는 상태다.

### 실제 사고 (`klid-label-32` 가 246 포털향에서 실측)

27MB mp4 업로드 시 막대가 0% 에서 안 움직이다 `timeout of 94000ms exceeded` 로 실패했는데, **서버는 1번 청크(8,388,608B)를 정상 수신·처리**했다 — `ls_tus_upload` 두 행이 `uld_offset=8388608 · IN_PROGRESS` 이고 `reg_dt→mdfcn_dt` 가 1.2초였다.

⇒ **데이터는 서버에 있는데 사용자는 처음부터 다시 올려야 했다.**

### ⚠ 204 응답 유실 자체는 이 CO 의 범위가 아니다

재현 시도 7종(BE 직결 curl · 프록시 경유 · 같은 파일 4청크 · LAN PATCH×3 · Playwright fetch · FE 자체 `uploadFile` 4회 · 실제 화면)이 **전부 정상**이라 서버·프록시·FE·LAN 은 무결하고 **사용자 Chrome 에서만 유실**된다(확장/보안소프트 의심). 그 원인은 `klid-label-32` 가 계속 잡는다.

**이 CO 가 고치는 것은 그 상황을 견디지 못하는 두 결함이다.** 원인 규명과 별개로, 청크 하나가 실패했다고 이미 올라간 데이터를 버리는 것은 그 자체로 결함이다.

## §2 변경 요지

1. `patchChunk` 에 axios `onUploadProgress` 를 배선해 `offset + loaded` 로 **바이트 단위** 진행률을 보고한다. **청크 완료 시점의 기존 보고는 그대로 둔다** — 최종 오프셋이 서버 응답값으로 확정되게.
2. 청크 타임아웃·네트워크 오류 시 `fetchOffset`(HEAD)으로 **서버 오프셋을 재동기화한 뒤 자동 재시도**한다(상한 1~2회 — 값은 제안). 넘으면 종전대로 실패로 올린다.
3. `PortalUploadPage` 에 **「일시정지」·「이어서 올리기」를 노출**한다.
4. `PortalTusUploadController` 에 **`@design` 태그를 심는다**(현재 0건).

## §3 도메인별 변경 상세

### 프론트 (SCREEN-033) — `klid-web-implementer`

- **대상 파일**
  - `frontend/src/features/upload/api/tusClient.ts` — `uploadFile`(338·341~351행) · `patchChunk` · `fetchOffset`(209행)
  - `frontend/src/pages/portal/PortalUploadPage.tsx` — `pause`/`resume` 렌더
  - `frontend/src/features/upload/**` 의 `useTusUpload` — `resume` 경로 재사용
  - 백엔드: `PortalTusUploadController` — `@design` 태그만 추가(로직 무변경)

- **소비 API (기존 창구 — 신규·변경 없음)**
  - `HEAD /v1/portal/uploads/tus/{uldId}` → **`API-166`** — 재개용 오프셋 조회. **회복 동선의 진입점**
  - `PATCH /v1/portal/uploads/tus/{uldId}` → **`API-169`** — 청크 업로드

- **변경**

  1. **바이트 단위 진행률.** `patchChunk` 에 axios `onUploadProgress` 를 배선해 `offset + loaded` 로 보고한다.
     ⚠ **청크 완료 후의 기존 보고를 지우지 마라** — 그것이 서버 응답값으로 최종 오프셋을 확정하는 자리다. 새 보고는 그 위에 얹는 것이지 대체가 아니다.

  2. **청크 실패 → 오프셋 재동기화 → 자동 재시도.** `patchChunk` 가 타임아웃·네트워크 오류로 죽으면 `fetchOffset`(HEAD)으로 서버가 실제로 어디까지 받았는지 다시 묻고 그 지점부터 이어 올린다. 상한을 넘기면 실패로 올린다.

  3. **「일시정지」·「이어서 올리기」 노출.**
     ★**자동 재시도가 상한을 넘겨 실패로 올라온 뒤에도 「이어서 올리기」가 보이고 눌린다.** 누르면 서버 오프셋을 재동기화해 그 지점부터 이어 올린다(새 세션 생성 없음). **숨기는 것은 완료·미시작 상태뿐이다.**

  4. **`@design` 태그 심기.** `PortalTusUploadController` 에 `API-166`·`API-169` 태그를 단다.

- **★★불변 — 세션을 새로 만들지 않는다 (가장 중요)**

  자동 재시도든 「이어서 올리기」든 **기존 세션의 오프셋 재동기화로만** 이어 붙인다. **세션을 새로 만들지 마라.**

  근거(실측): **속도 제한은 접수 창구(POST)에만 있다.** 세션을 새로 만드는 방향으로 가면 429 를 때린다(반복 시험 6회 중 3회). 반면 **PATCH·HEAD 반복에서는 429 가 한 번도 관측되지 않았다**(8MB PATCH 연속 6회 전부 204 · 1.1초대).

  ★**기존 구현이 이미 그 방향이다** — `useTusUpload.resume` 은 `state.uploadId` 가 있으면 그 세션 식별자를 그대로 넘겨 `fetchOffset` 만 호출하고 세션 생성 경로를 타지 않는다. **자동 재시도도 같은 경로를 재사용하고 별도 흐름을 새로 만들지 마라.**

- **그 밖 불변**

  1. **TUS 계약을 바꾸지 마라** — `PATCH`+`Upload-Offset` · `HEAD` 오프셋 조회 · 204 · `DEFAULT_CHUNK_SIZE` 8MB · 타임아웃 공식(`BASE + MS_PER_MB × MB`) · `uploadFile` 반환 계약.
  2. ★**관제 업로드 화면(`/uploads`)도 같은 클라이언트를 쓴다** — 포털만 고치겠다고 분기를 치지 마라. 회귀 확인 필요.
  3. ★**진행률이 뒤로 가지 않게 하라** — 재동기화로 이전 보고보다 작아질 수 있는데, 막대가 뒤로 가면 **또 다른 고장으로 읽힌다.**
  4. **검증은 프록시 경유로만** — 브라우저에서 BE(18085) 직접 호출은 CSP(`connect-src 'self' ws: wss:`)로 차단된다. 직결로 스크립트를 짜면 **화면과 다른 조건을 시험**하게 된다.

## §5 검증

> 항목 ①~④ 는 원본 CO §5 에서 그대로 받았다. ⑤ 는 이 세션이 보탰다(원본 불변 목록에는 있었으나 검증 항목에는 없었다).

1. 청크 진행 중 `onProgress` 가 **여러 번 불리고 값이 단조 증가**한다.
   ★**재동기화 경로를 실제로 태운 뒤 확인한다** — 정상 경로만 태우면 통과해도 아무것도 안 지킨다(단조성이 깨질 수 있는 유일한 자리가 재동기화 지점이다).

3. **새 세션을 만들지 않는다**는 단언 — 자동 재시도와 「이어서 올리기」 **양쪽 모두**. 한쪽만 걸면 다른 쪽으로 샌다.
4. `PortalUploadPage` 시험 — 진행 중·중단에서 두 버튼이 보이고 **완료·미시작에는 안 보인다**. ★**자동 재시도 소진 후 실패 상태에서도 「이어서 올리기」가 보이고 눌린다.**
5. **관제 업로드 화면(`/uploads`) 회귀** — 진행률 배선·재시도 경로 변경이 그쪽 동작을 바꾸지 않는다.

- ★**변이 검증**: 위 가드마다 「그 배선을 끊으면 실제로 RED 가 되는지」 확인한다. **통과만으로 가드라고 주장하지 마라.**

  이관 세션이 처음엔 그렇게 적었다가 `klid-label-32` 실측(**429 는 POST 한정 · PATCH 연속 6회 전부 204**)으로 바로잡았다. 429 를 만나면 재시도 대상으로 다루되 **그것이 주된 경로는 아니다.**
  **되살리지 말 것** — 주 경로로 설계하면 **세션 재생성 쪽으로 끌려갈 유인**이 생기고, 그 방향이 바로 §3 이 금지하는 것이다. (기각 사실보다 이 근거가 재발 방지에 쓰인다.)
- **자동 재시도 상한 값(1~2회)은 확정이 아니라 제안**이다 — 이관 세션의 판단이며 조정 가능하다. **확정된 것은 「소진 후 수동 경로가 남는다」쪽이다.**
- **204 응답 유실의 원인 규명은 이 CO 범위 밖**이다 — `klid-label-32` 가 계속 잡는다.

## §8 조율 — FE 전체 회귀 배타 구간 (세 갈래)

이 저장소에서 **FE 전체 스코프 회귀는 동시에 하나만** 돈다. 근거는 이관 세션의 실측이다:

> FE 전체 스코프에서 **부하성 flaky** 가 실측됐다 — 매번 1~4건 실패하는데 **희생자가 실행마다 바뀌고** 격리하면 전부 통과하며, **「다른 작업이 돌지 않는 시점」에야 연속 2회 클린 그린**을 얻었다.
> ⇒ 겹쳐 돌리면 **초록을 못 믿는 게 아니라 빨강을 못 믿게 된다.** 한 건이라도 나오면 진짜 결함인지 가리려 격리 재실행 왕복이 붙어 오히려 느려진다.
