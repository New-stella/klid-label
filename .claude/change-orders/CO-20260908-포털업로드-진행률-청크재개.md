## §1 배경

포털 업로드 화면에서 28,220,079B(약 27MB) mp4 를 올리자 **진행률 막대가 0% 에서 전혀 움직이지 않다가**
`timeout of 94000ms exceeded` 로 실패했다.

그런데 **서버는 1번 청크(8,388,608B)를 정상 수신·처리했다** — `ls_tus_upload` 두 행이
`uld_offset=8388608 · IN_PROGRESS` 이고 `reg_dt → mdfcn_dt` 가 1.2초다(11:42:52.04 → 11:42:53.23).
즉 요청은 도달·처리됐는데 204 응답만 브라우저로 돌아오지 않았고, 진행률이 0% 에 머물다 청크
타임아웃으로 끊겼다.

> 위 관측과 아래 재현 시도는 **다른 세션(klid-label-32)이 246 포털향 스택에서 실측해 넘긴 것**이다.
> 이 CO 의 두 결함 주장은 이쪽에서 **코드로 직접 재확인**했다(§1 「코드 확인」).

### 응답 유실 자체는 이 CO 의 범위가 아니다

넘겨받은 재현 시도 7종이 **전부 정상**이었다 — BE 직결 curl 204 · Vite 프록시 경유 완료 · 같은 27MB
파일 4청크 완료 · LAN 경유 8MB PATCH ×3 각 0.97~1.18초 · Playwright 에서 fetch 4청크 204 · **FE 자체
`tusClient.uploadFile`** 4회 반복 실패 0 · 실제 화면에서 그 파일 업로드 완료. 즉 서버·프록시·FE
코드·LAN 은 무결하고 **사용자 Chrome 에서만 응답이 유실**된다(확장/보안소프트 의심). 그 원인 규명은
사용자 DevTools 확인이 필요한 **별건**이며 여기서 다루지 않는다.

**이 CO 가 고치는 것은 그 상황을 견디지 못하는 우리 쪽 두 결함이다.**

### 코드 확인 (이 세션에서 직접 대조)

**결함 1 — 진행률이 청크 경계에서만 갱신된다.**
`frontend/src/features/upload/api/tusClient.ts` 의 `uploadFile` 은 `onProgress` 를 **시작 시 1회**
(338행)와 **`patchChunk` 가 완료된 뒤**(349행)에만 부른다. 청크가 8MB(`DEFAULT_CHUNK_SIZE`)라 27MB
파일이면 눈금이 0 → 30 → 59 → 89 → 100 **다섯 번뿐**이고, 한 청크가 올라가는 동안은 완전히 멈춰
보인다. 같은 파일의 `TUS_CHUNK_UPLOAD_MS_PER_MB = 8_000`(상향 1Mbps 가정)대로면 **한 청크당 60초 넘게
정지한 것이 정상 범위**다. 즉 느린 회선에서는 **정상 동작조차 고장으로 읽힌다.** axios 의
`onUploadProgress` 는 프론트 전체에서 사용처가 0건이다.

**결함 2 — 청크 실패가 곧 업로드 실패다.**
`uploadFile` 의 while 루프(341~351행)에 `patchChunk` 실패를 잡는 곳이 없어 예외가 그대로 위로 나가
업로드 전체가 실패한다. `fetchOffset`(209행, HEAD 로 서버 오프셋 조회)은 이미 있고 재개 경로에서
쓰이는데(325행), **실패 시 그것으로 되돌아오는 경로가 없다.** 게다가
`frontend/src/pages/portal/PortalUploadPage.tsx` 는 `useTusUpload` 를 쓰면서도 그 훅의 `pause`/`resume`
을 **렌더하지 않는다**(파일 내 언급 0건). 그래서 이번처럼 **서버에 8MB 가 이미 들어가 있는데도**
사용자는 처음부터 다시 올려야 하고, 그 8MB 는 만료까지 방치된다.

## §2 변경 요지

1. `patchChunk` 에 axios `onUploadProgress` 를 배선해 진행률을 **바이트 단위**(`offset + loaded`)로
   보고한다 — 청크 안에서도 막대가 움직인다.
2. 청크 타임아웃·네트워크 오류 시 `fetchOffset`(HEAD)으로 **서버 오프셋을 재동기화해 자동 재시도**
   한다(1~2회). 이번 증상은 데이터가 이미 서버에 있으므로 **즉시 30% 지점부터 재개되어 자가 치유**된다.
3. 포털 업로드 화면에 **「일시정지」·「이어서 올리기」를 노출**한다 — 훅(`useTusUpload`)에 이미 있는
   `pause`/`resume` 을 화면이 렌더하지 않아 사람이 개입할 수단이 없었다. 자동 재시도 상한을 넘겨
   실패한 뒤에도 **처음부터 다시 올리지 않고 이어서 올릴 수 있게** 한다(2026-09-08 사용자 확정).

1·2 는 관제(`/uploads`)·포털(`/portal/uploads/tus`) 두 화면이 공유하는 클라이언트에 들어가고,
3 은 포털 화면에 들어간다.

## §3 도메인별 변경 상세

### 프론트 (DOMAIN-013 포털 · SCREEN-033) — `klid-web-implementer`

- **대상 파일·심볼**
  - `frontend/src/features/upload/api/tusClient.ts` — `patchChunk`(266행) · `uploadFile`(306~353행) · `fetchOffset`(209행) · `TUS_CHUNK_UPLOAD_BASE_MS` / `TUS_CHUNK_UPLOAD_MS_PER_MB`
  - `frontend/src/features/upload/hooks/useTusUpload.ts` — 진행률 소비부(변경이 필요하면) · `pause`/`resume`(계약 유지)
  - `frontend/src/pages/portal/PortalUploadPage.tsx` — 「일시정지」·「이어서 올리기」 노출
  - 회귀 시험 — 위 세 축 각각

- **변경**
  1. **바이트 단위 진행률**: `patchChunk` 가 axios 요청에 `onUploadProgress` 를 걸고, 그 `loaded` 를
     상위로 전달해 `uploadFile` 이 `onProgress(offset + loaded, file.size)` 로 보고하게 한다.
     청크 완료 시점의 기존 보고(349행)는 **그대로 두어** 최종 오프셋이 서버 응답값으로 확정되게 한다.
  2. **실패 시 오프셋 재동기화 후 자동 재시도**: `patchChunk` 실패를 잡아 `fetchOffset` 으로 서버가
     실제로 받은 오프셋을 다시 읽고, 그 지점부터 이어서 재시도한다. **재시도 횟수에 상한을 둔다**
     (1~2회). 상한을 넘으면 종전대로 실패로 올린다.
  3. 재시도 대상은 **타임아웃·네트워크 오류**로 한정한다. 4xx(요청 자체가 잘못됨)는 재시도하지 않는다.
     429 를 만나면 재시도 대상으로 다루되 **그것이 주된 경로는 아니다** — 실측상 429 는 **접수 창구(POST)
     한정**이고 청크 전송(PATCH)·오프셋 조회(HEAD) 반복에서는 한 번도 관측되지 않았다(8MB PATCH 연속
     6회 전부 204·1.1초대). 즉 재시도를 기존 세션 경로로 묶는 한 이 벽에 부딪히지 않는다.
  4. `shouldPause` 로 일시정지를 확인하는 기존 루프 동작을 유지한다.
  5. **`PortalUploadPage` 에 「일시정지」·「이어서 올리기」를 렌더한다.** 훅의 `pause`/`resume` 을 그대로
     쓰고 훅 계약을 바꾸지 않는다. 버튼은 **업로드가 진행 중이거나 중단된 상태에서만** 보이게 하고,
     이어서 올리기는 반드시 **기존 세션의 오프셋 재동기화**로 이어 붙인다(새 세션 생성 금지 — 아래
     429 항목과 같은 이유). 완료·미시작 상태에서는 노출하지 않는다.

- **불변(건드리면 안 되는 것)**
  - **TUS 프로토콜 계약**(`PATCH` + `Upload-Offset`, `HEAD` 로 오프셋 조회, 204 응답)을 바꾸지 않는다.
  - `DEFAULT_CHUNK_SIZE = 8MB` 를 이 CO 에서 바꾸지 않는다 — 진행률이 안 보이던 것이 결함이지 청크
    크기가 결함이 아니다. 크기를 줄이면 요청 수가 늘어 아래 429 벽에 더 자주 부딪힌다.
  - 청크 타임아웃 공식(`BASE + MS_PER_MB × MB`)을 이 CO 에서 바꾸지 않는다.
  - `uploadFile` 의 반환 계약(`{ uploadId, uploadOffset, completed, ingestStatus }`)을 유지한다.
  - **관제 업로드 화면도 같은 클라이언트를 쓴다** — 포털만 고치겠다고 분기를 치지 말 것.

- **주의**
  - **속도 제한은 접수 창구(POST)에만 있다** — `POST /v1/portal/uploads/tus` 연속 생성 시 429 가 난다
    (반복 시험 6회 중 3회). 사용자가 실패 후 연타하면 이 벽에 부딪힌다. 자동 재시도나 「이어서 올리기」가
    **세션을 새로 만드는 방향으로 가면 이 제한을 때린다** — 반드시 **기존 세션의 오프셋 재동기화**로
    하고 새 세션을 만들지 않는다.
  - ★**기존 구현이 이미 그 방향으로 되어 있다** — `useTusUpload.resume` 은 `state.uploadId` 가 있으면
    그 세션 식별자를 그대로 넘겨 `fetchOffset`(HEAD)만 호출하고 세션 생성 경로를 타지 않는다. 자동
    재시도도 **같은 경로를 재사용**하고 별도 흐름을 새로 만들지 말 것.
  - 브라우저에서 BE(18085)를 직접 부르는 경로는 **CSP `connect-src 'self' ws: wss:`** 로 차단된다 —
    프록시가 유일한 경로다. 검증 스크립트를 짤 때 직결로 부르면 화면과 다른 조건을 시험하게 된다.
  - **진행률 보고가 뒤로 가지 않게 한다** — 재시도로 오프셋을 재동기화하면 이전에 보고한 값보다
    작아질 수 있다. 막대가 뒤로 가면 사용자는 그것을 또 다른 고장으로 읽는다.

- **수용기준**
  - 8MB 청크를 올리는 동안 진행률이 **청크 안에서도** 증가한다(0 → 30 → 59 … 계단식이 아니다).
  - 청크 1회가 타임아웃·네트워크 오류로 실패해도 **서버가 이미 받은 오프셋부터 자동 재개**되어
    업로드가 완주한다. 이번 증상(1번 청크 처리됨 + 응답 유실)에서 처음부터 다시 올리지 않는다.
  - 재시도 상한을 넘으면 종전대로 실패가 사용자에게 드러난다(조용히 삼키지 않는다).
  - 자동 재시도가 **새 업로드 세션을 만들지 않는다**(429 유발 금지).
  - 관제 업로드 화면(`/uploads`)에 회귀가 없다.
  - 포털 업로드 화면에 「일시정지」·「이어서 올리기」가 보이고, 자동 재시도 상한을 넘겨 실패한
    뒤에도 그 버튼으로 **처음부터가 아니라 이어서** 올릴 수 있다.
  - 그 버튼이 완료·미시작 상태에서는 노출되지 않는다.

    최종 확정은 반드시 서버 응답 오프셋으로 한다(그래서 청크 완료 시점 보고를 남긴다).
  - 자동 재시도는 **실패를 감출 수 있다**. 상한과 로그를 두어 반복 실패가 드러나게 한다.

    만들 뿐이다. 별건으로 남는다.

## §5 검증

- `tusClient` 회귀 시험 2축: ①청크 진행 중 `onProgress` 가 여러 번 불리고 값이 단조 증가한다
  ②`patchChunk` 가 1회 실패하면 `fetchOffset` 으로 재동기화해 재개하고, 상한 초과 시 실패로 올린다.
- 새 세션을 만들지 않는다는 단언(429 회귀 가드) — 자동 재시도와 「이어서 올리기」 **양쪽** 모두.
- `PortalUploadPage` 시험: 진행 중·중단 상태에서 두 버튼이 보이고 완료·미시작에서는 보이지 않는다.
- 수동 시나리오(246 포털향, BE 18085 · FE 13005): 27MB mp4 업로드 → 막대가 연속 이동 → 완료·목록 등재.

## §6 관련 설계 ITEM  ★구현 전에 먼저 확정한다

| ITEM | 타입 | 무엇을 어떻게 | 근거 |

| API-166 | api_endpoint | `HEAD /v1/portal/uploads/tus/{uldId}`(재개용 오프셋 조회)에 **클라이언트가 청크 실패 시 이 창구로 서버 오프셋을 재동기화해 이어 올린다**는 회복 동선을 명시. 현재는 조회 규격만 있고 그것이 실패 회복의 진입점이라는 사실이 규정돼 있지 않다 | 코드 확인(`fetchOffset` 이 이 창구를 부른다) |
