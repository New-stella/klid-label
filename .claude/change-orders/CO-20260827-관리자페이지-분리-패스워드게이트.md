# CO-20260827 — 관리자 페이지 분리 + 패스워드 게이트

- 생성일: 2026-08-27
- 요청자: 사용자 (대화 확정)
- 상태: 게이트② 통과 — 설계 선반영(Phase 3.6) 진행 중

## §1 배경

검수자(REVIEWER)에게 **관리 권한이 전부 얹혀 있다**. 사용자 계정의 역할을 바꾸고, 외부 연동
서버 주소를 바꾸고, 영상을 업로드하는 일이 검수 업무와 같은 권한 하나로 묶여 있다.

특히 연동 서버 주소는 잘못 바꾸면 **학습데이터가 통째로 외부로 나갈 수 있는 값**이다. 이 위험은
이미 인지·기록돼 있고(`CLAUDE.md` 연동 주소 절의 잔여 위험), 그래서 주소 축만은 관리자 패스워드
단기 유효창(`POST /v1/manage/admin-session`, ADR-046)으로 이미 2단계가 걸려 있다.

문제는 **그 2단계가 주소 축에만 있다**는 것이다. 사용자 역할 변경·업로드는 REVIEWER 권한만으로
그냥 된다. 직무분리(SoD) 관점에서 감리 지적 표면이고, 오조작 위험도 그대로다.

### 왜 ADMIN 역할을 만들지 않는가 (기각 근거)

논의 초기에는 `Role.ADMIN` 신설안을 검토했고 **기각**했다. 근거:

1. **겸직이 구조적으로 막힌다.** `LS_USER_ROLE` 은 `USER_NO` **단일 PK** 이고 그 값은 JWT `sub`
   = **관제 사용자번호**다. 저작도구엔 자체 로그인이 없으므로 겸직자(관리+검수)에게 계정 2개를
   주려면 **관제서버에 계정 2개를 만들어 달라고 협의**해야 한다 — 우리가 만들 수 없다.
2. **부트스트랩 락아웃.** 사용자 관리를 ADMIN 전용으로 옮기면 "ADMIN 을 만들 수 있는 사람이
   ADMIN 뿐"인 순환이 생긴다. 이 프로젝트는 같은 사고를 이미 겪었다(`RoleClaimService` 주석:
   *"실제로는 아무도 채우지 않아 DBA 가 손으로 넣기 전까지 아무도 역할을 받을 수 없었다"*).
3. 그 락아웃을 자가부여 개방으로 풀면 **"패스워드를 아는 사람이 ADMIN"** 이 되어, ADMIN 역할안의
   유일한 우위(개인 단위 권한 회수)마저 반쯤 상쇄된다.

### 왜 패스워드 게이트로 충분한가 (채택 근거 — 실측)

관리자 세션 토큰은 **`actor.sub()` 에 바인딩**된다:
`adminSessionTokenService.verify(token, actor.sub(), now)`.
즉 역할 승격이 아니라 **그 사람에게 잠깐 열리는 창**이고, 요청은 여전히 본인 JWT 로 인증된다.
⇒ **공유 패스워드인데도 "누가 했는지"가 개인 단위로 남는다**
(`log.info("[AdminSession] opened actor={}")` + `LS_SYSTEM_CONFIG.MDFR_ID`).

"공유 패스워드는 감사 추적이 안 된다"는 통념이 이 코드 앞에서 성립하지 않으며, 이것이 채택의
결정적 근거다.

## §2 변경 요지

**역할 체계를 손대지 않고**, 관리 기능을 별도 주소(`/admin/*`)로 분리해 **진입 시 관리자
패스워드**를 요구한다. 이미 있는 관리자 단기 유효창(ADR-046 · API-194)을 주소 축에서
**관리 기능 공통 진입**으로 넓히는 것이다.

```
검수자 JWT(기존)  →  /admin 진입  →  관리자 패스워드
                                       ↓ AdminSession 단기 유효창 (10분 · 상한 30분 · 본인 sub 바인딩)
                    사용자관리 · 연동주소 · 업로드 · 위험액션 · 패스워드변경
```

### 게이트 범위 — 쓰기만. 조회는 REVIEWER 그대로

| 대상 | 엔드포인트 | 현재 | 변경 후 |
|---|---|---|---|
| 사용자 역할 변경 | `PATCH /v1/users/{userNo}` (API-004) | REVIEWER | REVIEWER + 관리자 세션 |
| 연동 주소 4종 | `PUT /v1/manage/configs/{key}` (API-069) | REVIEWER + 관리자 세션 | **무변경** |
| 업로드 (TUS) | `/v1/uploads` 쓰기(POST·PATCH·DELETE) | REVIEWER | REVIEWER + 관리자 세션 |
| 업로드 (dev) | `POST /v1/dev/upload` (API-152) | REVIEWER | REVIEWER + 관리자 세션 |
| 위험 액션 | — | **API 없음(placeholder)** | 화면만 이동 |
| 패스워드 변경 | 신규 | — | REVIEWER + 관리자 세션 + 현재 패스워드 |

- ★**GET 을 막지 않는다** — 배정 화면이 `GET /v1/users/workers` 로 작업자 목록을 읽는다.
  막으면 배정이 깨진다.
- ★**포털 업로드(`/v1/portal/uploads/**`)는 대상이 아니다** — PORTAL_USER 본인 자산 업로드
  (ADR-013 예외)라 묶으면 그 기능이 통째로 죽는다.
- `PUT /v1/manage/configs/{key}` 는 **이미 게이트돼 있으므로 재구현하지 않는다.** 판정 지점
  `IntegrationEndpoint.isEndpointKey()` 를 그대로 둔다.

## §3 도메인별 변경 상세

### 공유기반 선처리 (메인 직접, Phase 3.5)

1. **관리자 세션 게이트를 단일 지점으로 추출** — 현재 `X-Admin-Session` 검증이
   `SystemConfigService.doUpdate` **안에 인라인**이다. 사용자관리·업로드로 넓히면서 호출처마다
   배선하면 샌다(이 저장소 확정 원칙 「게이트 호출처마다 배선하면 샌다」).
   → `common/` 에 인터셉터 또는 `@RequiresAdminSession` 애노테이션으로 추출하고, 기존
   `SystemConfigService` 는 그 단일 지점을 쓰도록 정리한다. **판정 로직을 복제하지 않는다.**
2. **관리자 패스워드 저장 테이블 신설 (Flyway)** — 다음 번호는 **V21**(전 워크트리 실측 V20).
   ⚠ **`LS_SYSTEM_CONFIG` 에 넣지 말 것** — `GET /v1/manage/configs`(API-068)로 BCrypt 해시가
   REVIEWER 전원에게 노출되어 오프라인 대입 대상이 된다.

   **표준용어 판정 결과 (CSV 정본 대조 완료 — 새 약어를 만들지 않았다)**

   | 컬럼 | 근거 | 도메인 |
   |---|---|---|
   | `PSWD_HASH` | **사업표준용어 「비밀번호해시」에 이미 등록** | `번호V100` (BCrypt 60자 → 충분) |
   | `MDFR_ID` | 공공표준단어 수정자=MDFR (프로젝트 기존 관례와 동일) | 기존 컬럼 관례 따름 |
   | `PSWD_MDFCN_DT` | **공공표준용어 「비밀번호수정일시」에 이미 등록** | `연월일시분초D` |

   - 테이블명은 공공표준단어 관리자=`MNGR` + 비밀번호=`PSWD` 조합에 소유 접두 `LS_` (예: `LS_MNGR_PSWD`).
   - **버전 컬럼을 두지 않는다** — 세션 무효화를 서명키 혼합으로 하므로 불필요(§3 DOMAIN-001 4번).
   - **단일 행 테이블**이므로 행이 둘 이상 생기지 않도록 고정 PK 또는 CHECK 로 강제한다.
   - ⚠ 우선순위는 **공공 → 사업**이다. `PSWD_HASH` 만 사업 출처인 것은 공공에 「해시」가
     `해시태그` 밖에 없기 때문이며(실측), 규칙상 정당한 보충이다.

### DOMAIN-001 (사용자·권한) — `klid-d001-implementer`

code_root: `auth/` `user/`

1. **`PATCH /v1/users/{userNo}`(API-004)에 관리자 세션 요구 추가.**
   - 이 API 는 **`role` 만 쓰기 가능**하다(API-004 v5: *"계정 활성 여부는 외부 시스템 소유값·읽기
     전용"*). 즉 이 엔드포인트가 곧 역할 부여/변경이라 게이트 대상으로 정확히 맞다.
   - `@PreAuthorize("hasRole('REVIEWER')")` 는 **유지**하고 그 위에 관리자 세션 게이트를 얹는다.
   - `GET /v1/users`·`/workers`·`/{userNo}` 는 **건드리지 않는다.**
2. **관리자 패스워드 변경 API 신설.**
   - 요건: REVIEWER + 유효 `X-Admin-Session` + **현재 패스워드 재확인**
     (세션만으로 바꾸면 세션 탈취 = 계정 완전 탈취).
   - BCrypt cost≥12. 기동 가드(`$2a$/$2b$/$2y$` prefix 검증, 평문이면 기동 실패) **유지**.
   - 평문·해시는 **로그·응답에 절대 금지**(`LogMaskingPatterns` 에 `X-Admin-Session` 이 이미 등록).
3. **`AdminPasswordVerifier` 저장소 env → DB 이전.**
   - 현재 `@Value("${authoring.auth.admin-claim-password-hash:}")` 를 생성자로 받아 **`final`
     불변 필드**로 들고 있어 런타임 변경이 구조적으로 불가능하다.
   - **부트스트랩: DB 미설정이면 env 폴백**(최초 배포가 막히지 않게). 둘 다 없으면 `matches`
     항상 false = fail-closed 유지.
   - 🟢 부수 이득: 2노드 Active-Active 에서 env 방식은 패스워드 교체마다 양 노드 재기동이
     필요했는데 DB 로 가면 없어진다.
4. **패스워드 변경 시 기존 관리자 세션 전량 무효화 — 서명키에 현재 패스워드 해시를 섞는다.**
   - `AdminSessionTokenService` 는 무상태 서명이고 payload 가
     `v1|subject|expiryEpochSeconds` + HMAC-SHA256 이다.
   - **채택**: HMAC derivedKey 유도에 **현재 패스워드 해시를 함께 넣는다.** 패스워드가 바뀌면
     이전 토큰의 서명이 **자동으로 검증에 실패**한다.
   - **기각(방안 A)**: payload 에 패스워드 버전을 넣고 검증 때 DB 와 대조하는 안. 버전 컬럼·조회가
     늘고, 검증 경로마다 DB 를 한 번 더 읽어야 한다. 채택안은 **상태를 하나도 늘리지 않고** 같은
     결과를 낸다 — 그래서 아래 ERD 에 버전 컬럼이 없다.
   - **`PAYLOAD_VERSION` 을 올린다**(`v1` → `v2`). 기존 토큰과 형식을 구분해, 배포 시점에 떠 있던
     토큰이 새 검증 로직에서 조용히 통과하지 않게 한다.
   - ⚠ **잔여 위험(인지·수용)**: 서명키가 패스워드 해시에 의존하므로, 해시를 읽지 못하면(DB 장애)
     토큰 검증이 전부 실패한다. **fail-closed 라 방향은 안전**하며, env 폴백이 있으면 그 값으로 유도한다.
5. ⚠ **`RoleClaimService` 의 자가부여 화이트리스트(`WORKER`·`REVIEWER`)를 건드리지 않는다.**
   이번 변경은 역할을 늘리지 않는다.
6. ⚠ **`AdminSessionController` 의 rate limit 이 역할 승격과 전역 버킷을 공유하는 것은 의도**다
   (클래스 javadoc 이 명시). **축을 분리하지 말 것.**

**불변**: `Role` enum 3종 · `LS_USER_ROLE` 스키마 · `UserRoleResolver` 판정 · 기존 GET 계약.

### DOMAIN-003 (영상·프레임 수집) — `klid-d003-implementer`

code_root: `video/` `upload/` + **`dev/`(업로드 한정)** — 매핑표 미등재였으나 업로드 성격이라 DOMAIN-003 담당으로 **확정**(사용자 확정, SCREEN-027 과 동일 담당)

1. **TUS 는 업로드 생성(`POST /v1/uploads`) 1회에만 관리자 세션을 요구한다** (사용자 확정).
   - `PATCH /{uploadId}`(청크) · `DELETE /{uploadId}`(취소) · `HEAD`(offset) · `OPTIONS`(디스커버리)
     에는 **세션을 요구하지 않는다.** 대용량 영상이 유효창(10분)을 넘겨도 업로드가 끊기지 않는다.
   - ★**이것이 안전한 이유(실측)** — 업로드 ID 가 허가증이 되는데, **소유자 검증이 이미 완비돼 있다.**
     `TusUploadController` javadoc: *"세션 소유자 검증(HIGH-8)은 서비스에서 USER_NO(토큰 sub) 기준
     수행"*. `getForOwner(uploadId, actor.sub())` · `appendChunk(uploadId, actor.sub(), ...)` ·
     `cancel(uploadId, actor.sub())` 가 모두 sub 를 넘기고, `LsTusUpload.USER_NO`(NOT NULL) +
     `isOwnedBy` 로 대조한다. 즉 **업로드 ID 를 알아도 소유자가 아니면 이어 쓸 수 없고**, 그 소유자는
     관리자 세션을 연 바로 그 사람이다(둘 다 토큰 `sub` 축).
   - ⚠ **소유자 검증을 새로 만들지 말 것** — 이미 있다. 기존 배선을 확인만 하고 그대로 둔다.
   - ⚠ 기존 `@PreAuthorize("hasRole('REVIEWER')")` 는 **5개 메서드 전부에서 유지**한다(세션 게이트는
     생성에만 얹고 역할 가드는 그대로).
2. **`POST /v1/dev/upload`(API-152)에 관리자 세션 요구 추가** — `DevAutolabelTestController`.
   기존 런타임 토글(`DEV_UPLOAD_ENABLED`)·`@PreAuthorize` 는 **유지**하고 그 위에 얹는다.

**불변**: 포털 업로드(`/v1/portal/uploads/**`) 전 경로 · TUS 프로토콜 헤더 계약.

6. ⚠ **`/manage/admin/*` 중첩안·`/system/*` 안은 기각됨** — 후자는 `SecurityConfig` 의
   `/v1/system/**` 매처와 이름이 충돌한다.

## §4 영향·리스크

- **역할 체계 무변경** — REVIEWER `@PreAuthorize` 98곳/47파일 중 **하나도 바꾸지 않는다.**
  게이트를 얹을 뿐 역할 매처를 건드리지 않는다.
- ✅ **TUS 유효창 문제는 해소** — 생성 1회만 요구하므로 대용량 업로드가 끊기지 않는다.
  잔여 위험은 "업로드 ID 를 쥔 채 유효창이 끝난 뒤에도 청크를 계속 올릴 수 있다"인데, 소유자
  검증이 그 사람을 그 세션의 소유자로 한정하므로 **권한이 남에게 새지 않는다**(인지·수용).
- ⚠ **패스워드 저장소 이전은 배포 순서에 민감하다** — env 폴백이 없으면 배포 직후 관리 기능이
  전면 차단된다(fail-closed). 폴백을 반드시 넣는다.
- ⚠ **번호 선점** — 형제 워크트리 `portal-0827` 이 같은 커밋(`b36bb870`)에서 병렬 작업 중이다.
  Flyway 는 전 워크트리 V20 이라 **V21** 이 다음이나, 착수 시 재확인한다(과거 실사고 있음).
- 운영 문서 갱신 필요 — `deploy/onprem/docs/04-configuration.md` 의
  `ADMIN_CLAIM_PASSWORD_HASH` 항목이 "env 필수"에서 "초기 부트스트랩용"으로 바뀐다.

**★401 vs 403 은 갈린 것이 아니다 (코드 실측 — 다음 사람이 같은 오독을 하지 않도록)**
한 에이전트가 *"발급 창구는 401, 소비 창구는 403 이라 두 축이 갈려 있다"* 고 보고했으나
**오독이다.** 실측:
- `AdminSessionTokenService.verify` javadoc — *"실패는 모두 `ErrorCode.FORBIDDEN`(403) 이며

⇒ **다른 상황에 다른 코드**이며 정합하다. 이번 fan-out 3건 모두 403 을 써서 계열이 일치한다.
**"일관성" 명목으로 하나로 통일하지 말 것.**

**확정된 관례 (fan-out 전체 적용)**
- 유효창 전달은 기존 헤더를 재사용한다 — 새 헤더를 만들지 않는다.
- `brownfield.decided_by` 는 **단일 값이라 원 귀속을 덮지 않는다.** 이미 다른 결정에 귀속된
  계약은 그대로 두고, ADR-046 의 `references` 로 그래프를 잇는다. 근거 링크가 **없던** 계약에만
  ADR-046 을 채운다(API-158 이 그 경우였다).

`MOD-045` · **`API-069`**(두 에이전트가 독립 지적) · TUS 계열 `API-156`·`160`·`162`·`164`.

올렸다. **좁힘은 유지가 맞다** — 사용자 확정 범위가 「시스템 설정 중 **주소 변경만**」이고
배치·추론·정밀도·비식별 설정은 검수자가 계속 바꾼다. 다만 **서술은 다듬어야 한다**:
"이 토큰은 주소 변경에만 효력이 있다"(폐기된 축)가 아니라 **"토큰은 관리 기능 공통이나,
이 창구에서는 주소 키에만 요구된다"**로 고친다. 축과 적용 지점을 구분하는 것이 요점이다.

### TUS 계열 비대칭 명시 — 메인 직접 처리 (2026-08-27)

`API-162`(이어 올리기) **v6** · `API-164`(취소) **v3** · `API-160`(진행 위치) **v4** ·
`API-156`(프로토콜 능력) **v3**. 넷 다 「관리자 단기 유효창을 이 창구에서 요구하지 않는다」와
그 근거를 계약에 명시했다.

**왜 명시하는가** — 요구 대상을 「운영·관리 성격의 쓰기」라는 **성질로 규정**했기 때문에,
적지 않으면 그 규칙을 읽은 사람이 ①취소·이어올리기도 쓰기니까 요구를 붙여 **전송을 끊거나**
②"왜 시작만인가"로 되물어 같은 논의를 반복한다. 둘 다 사고다.

**근거로 적은 것**: 대용량 전송이 유효창보다 오래 걸린다는 것 + **이어 올리기 경로가 그 전송의
소유자만 진행하도록 이미 판정**한다는 것(전송 식별자를 알아도 소유자가 아니면 못 쓴다). 그 소유자가
곧 유효창을 연 사람이라 권한이 새지 않는다. ⚠ 이 소유자 판정은 **신설이 아니라 기존 규칙**임을
본문에 명시했다 — 구현자가 새로 만들려 하지 않도록.

**검증**: specialist 없이 메인이 직접 처리(짧은 서술 추가라 위임이 낭비). 서버 기준선을 받아
**순수 추가(insert)** 로만 편집 → 기준선 대비 `replace`·`delete` opcode **0**(기존 본문의 문자
치환이 원리적으로 불가) · 재조회 완전일치 4/4 · 한글 3축 clean(희귀 음절 42건 전부 정상어) ·
`parameters` 무변경(요구하지 않으므로 헤더를 넣지 않았다).

유효창이 없을 때 대신 열리는 자리).

**★도구 함정 — `source_hash` 오라클의 기준이 바뀌었다 (규칙 파일 반영)**
해시 기준은 **「내가 보낸 sections」가 아니라 「서버가 저장한 sections」** 다. 서버가 스키마 기본값
(`components[].columns: []`·`options: []`)을 채우므로 보낸 원본으로 계산하면 어긋난다 — 실측에서 같은
화면이 `11c41ef0…`(보낸 원본) / `5b031ba8…`(서버 저장본)으로 갈렸다. **재조회한 sections 로 계산하지
않으면 정상 업로드가 「미러 stale」로 오판된다.**
같은 계열로 `erd` 테이블에는 `indexes`, `api_endpoint` 응답에는 `content_type` 이 자동으로 붙는다
— **스키마 기본값 채움은 타입·필드를 가리지 않는다**고 보는 편이 안전하다.

**★내 검사가 무효였던 사고 1건 (정직 기록)**

않아 **route 를 하나도 못 보고 있었다.** sanity 앵커(이미 아는 route 가 잡히는지)를 넣고서야 드러났고
전수 덤프로 다시 돌려 확정했다(중복 0 · `/admin` 계열 6). 이 저장소의 「0건을 믿지 마라」와 같은 형태다.

**★내가 만든 불일치 1건 (정직 기록)** — 위임 프롬프트에 렌더 라벨을 「메인 페이지」로 지시해 신설 4건이

### 시안 축 — 구현 단계로 넘길 함정 (Phase 4 담당자가 읽을 것)

**★잠금 표시의 CSS 특정도 — 빠뜨리면 잠금이 무력화된다**
`.only-unlocked { display:none }` **하나만으로는 부족하다.** 클래스가 둘인 선택자
(`.config-card > .card-content`)에 특정도로 져서 **해제 상태 본문이 처음부터 노출된다.**
기존 시스템 설정 시안이 `.config-card > .card-content.only-unlocked` 로 **2중 선택자**를 쓰는 이유가
이것이며, 신설 연동 주소 화면도 같은 방식으로 고쳤다. **시안을 화면 코드로 옮길 때 이 규칙을
빠뜨리면 잠금이 걸린 것처럼 보이면서 실제로는 열려 있다.**

**★자동완성 차단 속성은 게시 렌더에서 사라진다**
패스워드 입력의 `autocomplete="off"` 를 **서버 sanitizer 가 게시본에서 떨어뜨린다.** 로컬 원본과
화면 사양(컴포넌트 note)에는 남아 있으므로 **구현에서 코드로 지켜야 한다** — 렌더만 보고 옮기면 빠진다.

**★유효창 게이지는 보조 표현이다**
남은 시간의 **정본은 분·초 텍스트**이며 게이지 막대는 시안이 더한 보조 요소다. 구현에서 생략해도
사양 위반이 아니다(색 단독 신호 금지 규정을 지키기 위한 장치였다).

## §8 ★★머지 후 반드시 할 것 — 온프렘 스키마 재생성 (잊으면 배포가 깨진다)

**머지 후 메인 워크트리에서 `deploy/onprem/scripts/gen-schema-sql.sh` 를 1회 실행한다.**

### 왜 (지금 이미 깨져 있다)
온프렘은 **Flyway 를 돌리지 않고**(`SPRING_FLYWAY_ENABLED=false`) 설치 시 `deploy/onprem/db/schema.sql`
을 1회 로드하며, 앱은 **`ddl-auto: validate`** 다. 그런데 그 파일이 마이그레이션을 따라오지 못했다 —
**대상 테이블의 CREATE 블록 안** 기준 실측:

| 마이그레이션 | 누락 |
|---|---|
| V16·V17 | `ls_data_ingest.thmb_file_path_nm` |
| **V20** | `ls_portal_user_label.lbl_id` · `trck_id` |
| **V21**(이 CO) | `ls_mngr_pswd` 전체 |

`LsPortalUserLabel` 엔티티가 `LBL_ID`·`TRCK_ID` 를 실제로 매핑하므로 **그 형상으로 온프렘에 배포하면
기동이 실패한다**(`missing column`). 그 파일 헤더는 *"Flyway 적용 결과와 100% 동일하므로 validate 통과
보장"* 이라고 선언하는데 **그 보장이 이미 깨져 있다.**

⚠ **로컬·dev 는 Flyway 로 돌아 전 시험이 초록이어도 온프렘만 깨진다. FULL 회귀로 절대 안 잡힌다.**

### 왜 지금 돌리지 않는가 (형제 세션과 합의, 그쪽 사용자 확정)
지금 어느 한쪽이 돌리면 **남의 미머지 마이그레이션이 상대 브랜치 덤프에 섞이거나 반쪽만 해소**된다.
**둘 다 머지된 뒤 메인에서 1회** 돌리면 **V16·V17·V20·V21 이 함께** 해소되고 섞임이 없다.
온프렘 배포가 임박하지 않아 그 대가를 받아들였다.

### ★검사 방법 주의 (내가 한 번 틀렸다)
**파일 전체 grep 으로 확인하지 말 것** — `lbl_id` 가 **다른 테이블에도 있어** 위양성 「누락 없음」이 난다.
반드시 **대상 테이블의 CREATE 블록 안**에서만 봐야 한다. 형제 세션도 이 주의를 받아 블록 범위로 재검증했다.

### 근본 원인 (별건 — 이 CO 에서 만들지 않음)
**강제하는 가드 시험이 0건**이다. 재생성은 이번만 막고 **다음 마이그레이션에서 같은 자리에 다시 빠진다.**
⇒ 가드는 **버전 비교로는 부족하고 컬럼 단위**여야 한다 — 이번 건이 「표는 있는데 컬럼이 빠진」 형태다.
엔티티가 `@Column` 으로 매핑하는 이름이 `schema.sql` 의 **그 표 블록 안**에 있는지 보는 시험이면
V16 시점에 걸렸다.

방향을 거꾸로 걸어야 이 부류가 닫힌다. 형제 세션이 자기 제안을 스스로 고쳐 준 지적이다.
