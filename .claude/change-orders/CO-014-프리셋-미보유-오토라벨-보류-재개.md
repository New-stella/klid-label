## §1 배경

### 사용자가 제기한 문제

"관제서버에서 오는 이벤트와 매핑이 되어야 오토라벨링 프리셋이 등록되어 오토라벨링이 진행된다 — 어떤 플로우가 좋은가."

### 실측으로 드러난 실제 배선 (질문의 전제 두 가지가 코드와 다르다)

1. **이벤트 유형은 이미 자동 등록된다.** 관제 인입을 소비할 때 `EventTypeAutoRegistrar.register` 가 미등록 유형코드를 `LS_EVNT_TYPE` 에 `INSERT ... ON CONFLICT` 로 넣고 관제칸(`EVNT_NM`·분류·카테고리)만 갱신한다. 상용에는 `V15__seed_event_type_and_label_master.sql` 로 카테고리 11 · 유형 16 · 라벨 마스터 9종이 이미 시드돼 있다. **이 축은 정상이며 이번 변경 대상이 아니다.**

2. **프리셋은 "무엇을 검출할지"가 아니다.** 검출 대상을 정하는 것은 라벨 마스터의 COCO 매핑(`LS_LABEL.DTCT_TYPE_CD`)이고, 프리셋은 **검출된 것 중 무엇을 어떤 형태(BBOX/POLYGON)로 저장할지** 정하는 노이즈 필터다(`PresetLabelLookupService.togglesFor` → `YoloAutolabelStep.resolveToggle`).

3. **따라서 프리셋이 없어도 오토라벨링은 멈추지 않는다.** `togglesFor` 가 빈 값을 돌려주면 `resolveToggle` 이 `AnnotationToggle.BOTH` 로 **fail-open** 하여 전 검출 결과가 그대로 저장된다. 배치는 `COMPLETED` 로 완주하고 아무 신호도 남지 않는다.

### 근본 문제 — 무증상

- **미보유가 보이지 않는다.** 신규 이벤트 유형이 자동 등록돼도 프리셋 없이 배치가 성공으로 완주하고, 노이즈가 낀 라벨이 그대로 검수자에게 넘어간다.
- **프리셋을 등록해도 무효화될 수 있다.** `togglesFor` 의 토글 맵 키는 마스터의 `DTCT_TYPE_CD` 다. 프리셋에 담은 라벨이 전부 COCO 미매핑(`dtct_type_cd IS NULL`)이면 맵이 비어 **또 `BOTH` 로 폴백**한다. 운영자는 필터를 걸었다고 믿는데 실제로는 안 걸린 상태다.
- **이건 가상의 우려가 아니다.** V15 시드의 폴리곤 3종(화재·연기·침수)이 정확히 `dtct_type_cd` NULL 이다 — COCO 에 대응 클래스가 없어 의도적으로 비운 것이며, 그 라벨만 담은 프리셋은 지금 구조에서 무효가 된다.
- **빈 값의 사유가 구분되지 않는다.** `togglesFor` 가 `Optional.empty()` 를 돌려주는 경로가 네 가지인데(미등록 이벤트 코드 · 프리셋 없음 · 라벨 전부 미연결 · 라벨 전부 COCO 미매핑) 호출자는 그 넷을 구분할 수 없다. 보류 판정도 화면 표시도 이 구분 없이는 성립하지 않는다.

### 사용자 확정 (2026-08-25, 구속)

- 프리셋 미보유·무효면 **오토라벨링을 보류**한다(정석안 선택 — fail-open 유지안·기본 프리셋 폴백안 기각).
- 보류 시 **배치 전체를 보류**한다(YOLO 만 보류하고 나머지 진행하는 안 기각).
- 등록 동선은 **미보유 목록 + 수동 등록**(프리셋 껍데기 자동 생성안·관제 코드→라벨 매핑표 도입안 기각).
- **보류 폭을 그대로 수용한다** — 설정 토글로 감싸 단계 도입하는 안·매핑을 먼저 채우고 배포하는 안은 기각. ⚠ 이 판단의 근거는 dev 수치가 아니라 **"필터가 없는 채로 저장하는 것보다 보류가 정확한 신호"** 라는 성질이다(dev 분포의 대표성 한계는 아래 경고 참조).
- **이벤트 코드가 없거나 마스터에 미등록인 영상도 같이 보류한다** — 프리셋을 특정할 수 없으므로 fail-closed 로 일관한다. 통과+경고안·둘을 갈라 처리하는 안은 기각.

**★추가 확정 (2026-08-25 후속) — 라벨 0건 프리셋은 「오토라벨 안 함」의 명시적 의사표시다**

- **라벨을 하나도 담지 않은 프리셋을 허용**한다. 그것은 그 이벤트 유형을 **오토라벨 대상에서 빼겠다는
  사람의 선언**이며, 그 유형의 영상은 **보류하지 않고 배치를 완료로 마감**하되 오토라벨 묶음만 건너뛴다.
- ⚠ **미매핑 무효와 갈라야 한다** — 라벨은 골랐으나 전부 AI 검출 클래스 매핑이 없는 프리셋은 **종전대로
  보류**다. 둘을 같게 다루면 **실수와 의도가 구분되지 않는다**: 출하 시드의 화재·연기·침수 라벨은
  설계상 검출 클래스 매핑이 없어(대응 COCO 클래스가 없다) 운영자가 화재 유형에 그 라벨들로 프리셋을
  만들면 **의도와 무관하게** 무효가 된다. 그 사고까지 조용히 완료시키면 이 변경지시서가 없애려는
  무증상 상태가 그대로 돌아온다.
- **계약 영향**: 프리셋 등록·수정의 라벨 목록 최소 개수를 **0 으로 연다**(현재는 최소 1). 화면도
  라벨을 비운 채 저장할 수 있어야 하고, 그 선택의 뜻(오토라벨 제외)이 저장 시점에 드러나야 한다.
- **연결 상태 축이 하나 는다** — 프리셋은 있으나 오토라벨 대상이 아닌 상태다. 보류를 유발하지 않으므로
  **보류 거르기에 포함되지 않는다.**
- ⚠ 이 확정은 바로 위 「프리셋 미보유·무효면 보류」의 **예외를 하나 만든 것**이지 그 결정을 뒤집은 것이
  아니다. 뒤집힌 것은 없다.

## §2 변경 요지

1. `PresetLabelLookupService.togglesFor` 가 **빈 값의 사유를 구분해 반환**하도록 반환 타입을 바꾼다(선결 조건).
2. `YoloAutolabelStep` 의 `BOTH` fail-open 폴백을 폐기하고, 프리셋 미보유·무효면 **보류(SKIPPED + 사유 기록)** 로 끝낸다.
3. 배치 파이프라인에 **보류 종결 경로**를 신설한다 — 보류가 나면 이후 단계(SAM2·INTERPOLATE)를 실행하지 않고, 클레임을 해제하되 `COMPLETED` 로 마감하지 않는다.
4. **프리셋 등록 시 재개** — 이벤트 발행 → AFTER_COMMIT 리스너 → 보류분 재처리 러너(VLM 보류 재개와 같은 골격).
5. **관리 화면에 프리셋 연결 상태 3값을 노출**하고 미보유만 필터할 수 있게 한다. 프리셋 등록 화면에는 라벨별 COCO 매핑 여부를 표시·경고한다.

## §3 도메인별 변경 상세

### 공유기반 선처리 (메인 직접, Phase 3.5)

- **대상**: `batch/pipeline/BatchContext.java` · `batch/orchestrator/BatchOrchestrator.java`
- **문제**: 현재 오케스트레이터에는 **"실패가 아닌 조기 중단"을 표현할 수단이 없다.** 정상 완주(`markRawDataCompleted` + `markCompleted` → `BatchStage.COMPLETED`) 또는 `RuntimeException`(→ `markRawDataFailed` + 재시도 큐 → `BatchStage.FAILED`) 둘뿐이다. 예외로 보류를 표현하면 실패 상태가 되어 자동 재시도 큐가 무한히 재시도하고 작업 상태가 `FAILED` 로 역행한다.
- **변경**:
  1. `BatchContext` 에 보류 표식을 추가한다 — `withhold(BatchStage stage, String reason)` / `isWithheld()` / `withheldStage()` / `withheldReason()`. 스텝이 자기 판단으로 세운다.
  2. `BatchOrchestrator` 의 스텝 루프에서 매 `step.execute(ctx)` 직후 `ctx.isWithheld()` 를 확인하고, 참이면 **루프를 break** 한다.
  3. 보류로 빠져나왔으면 `markRawDataCompleted`·`statusService.markCompleted` 를 호출하지 **않는다.** 대신 **클레임을 반드시 해제**하고(아래 주의) `retryQueue` 에 등록하지 않은 채 `BatchStage.SKIPPED` 를 반환한다.
  4. 클레임 해제 방식은 `BatchTransitionService` 에 보류 전용 메서드를 신설하거나 기존 복구 전이를 재사용한다 — **어느 쪽이든 배치 단계가 `PROCESSING` 으로 남으면 안 된다.**
- **불변**:
  - 정상 완주 경로·실패 경로의 기존 동작·반환값·상태 전이를 바꾸지 않는다.
  - 묶음 재수행 경로(`rerunRestoreStatus != null`)의 상태 복구 규약(`API-201`)을 건드리지 않는다.
  - `preserveReviewOwnedStatus`(면제 모드) 분기의 전용 마감 로직을 건드리지 않는다.
  - `BatchStep` 인터페이스의 트랜잭션 경계 규약(`execute` 에 `REQUIRES_NEW`)을 유지한다 — `BatchStepTransactionBoundaryTest` 가 정적으로 강제한다.
- **주의 (Critical)**:
  - ★**클레임 해제를 빠뜨리면 그 영상이 영구 고착된다.** 진입 가드가 배치 단계를 `PROCESSING` 으로 원자 클레임하므로, 보류로 빠져나가면서 해제 전이를 실행하지 않으면 이후 **모든 진입(자동 재시도 잡·수동 재처리 포함)이 클레임에 막힌다.** `BatchOrchestrator` 의 실패 경로 주석(B-ISSUE-01)이 같은 함정을 이미 경고한다.
  - ★**보류만 만들고 재개를 안 만들면 그게 곧 영구 고착이다.** 이 저장소의 확립된 원칙 — "차단엔 되돌리는 길, 보류엔 끝". 재개(D004)와 **반드시 세트로** 구현한다.
  - 보류는 실패가 아니므로 `retryQueue.enqueue` 도 `markFailed` 도 하지 않는다. 다만 `retryQueue.clear` 를 호출할지는 판단이 필요하다 — 이전 실패로 큐에 있던 항목을 보류가 지워서는 안 된다(보수적으로 건드리지 않는다).
  - 새 컬럼·테이블 없음 — 보류 기록은 기존 `LS_BATCH_PROC_LOG` 의 SKIPPED 감사 행을 재사용한다. **따라서 Flyway 마이그레이션도 표준용어 판정도 필요 없다.**
- **수용기준**: 보류가 발생한 영상의 `LS_DATA_RAW.DATA_STTS_CD` 가 `COMPLETED` 가 아니고 `PROCESSING` 으로도 남지 않으며, 같은 영상에 대한 후속 배치 진입이 클레임에 막히지 않는다.

### DOMAIN-004 (AI 보조 라벨링) — `klid-d004-implementer`

- **대상 파일·심볼**:
  - `batch/policy/PresetLabelLookupService.java` (`togglesFor` · `AnnotationToggle`)
  - `batch/step/YoloAutolabelStep.java` (`run` · `resolveToggle`)
  - `batch/runner/` — 재개 러너 신설 (참고: `VlmWithheldResumeRunner`)
  - `batch/listener/` — 재개 브릿지 신설 (참고: `VlmResumeBridge`)
  - `batch/status/BatchStatusService.java` — 기존 `recordStageSkipped` 재사용
- **변경**:
  1. **`togglesFor` 의 반환을 사유 있는 결과로 바꾼다.** `Optional<Map<...>>` 대신 결과 레코드(예: `PresetResolution`)를 돌려주며, 최소 다음을 구분한다 — `RESOLVED`(실효 토글 맵 보유) · `EVENT_TYPE_UNREGISTERED`(`filterKeyOf` 가 빈 값) · `PRESET_ABSENT`(그 키에 프리셋 없음) · `PRESET_UNLINKED`(코드가 전부 `labelId=null`) · `PRESET_UNMAPPED`(연결·활성 라벨은 있으나 전부 `DTCT_TYPE_CD` 미매핑/비활성). **이 판정이 D010·D014·프론트가 공유하는 단일 진실원이다 — 다른 곳에서 재유도하지 않는다.**
  2. **`YoloAutolabelStep` 의 `BOTH` 폴백을 폐기한다.** `resolveToggle` 의 `togglesOpt.isEmpty() → BOTH` 분기를 제거하고, `run` 진입 직후 프리셋 판정이 `RESOLVED` 가 아니면 **추론·적재를 시작하지 않고** 보류로 끝낸다.
     - `BatchStatusService.recordStageSkipped` 로 `(rawSn, YOLO, SKIPPED, 사유)` 감사 행을 남긴다.
     - 사유 상수는 `VlmTimeseriesStep.SKIP_REASON_*` 과 같은 관례로 이 스텝에 정의하고, **재개 대상 사유 집합**(`RESUMABLE_SKIP_REASONS` 대응)도 함께 둔다.
     - `ctx.withhold(BatchStage.YOLO, reason)` 로 표식을 세워 오케스트레이터가 이후 단계를 중단하게 한다.
     - ★**`RESOLVED` 가 아닌 모든 사유가 보류 대상이다** (사용자 확정 2026-08-25). `EVENT_TYPE_UNREGISTERED` — 영상에 이벤트 코드가 아예 없는 경우와 코드는 있으나 `LS_EVNT_TYPE` 에 미등록인 경우를 **모두 포함** — 도 보류한다. 프리셋을 특정할 수 없으므로 fail-closed 로 일관한다. 단 **사유는 구분해 기록**해 어느 쪽인지 나중에 판독할 수 있게 한다.
  3. **재개 러너·브릿지 신설.** `VlmWithheldResumeRunner` 골격을 그대로 따른다:
     - 재개 조건 두 가지를 **모두** 만족할 때만 재개 — ① `(rawSn, YOLO, SKIPPED, 재개 대상 사유)` 감사 행 존재 ② 프리셋 판정이 이제 `RESOLVED` 다. 두 번째가 멱등성을 담당한다(보류 기록은 append-only 라 지워지지 않는다).
     - `@Async("batchAsyncExecutor")` 로 돌고 실패는 삼켜 로깅만 한다 — 재개 실패가 프리셋 등록 트랜잭션(이미 커밋됨)에 영향을 주면 안 된다.
     - **재개는 오토라벨 묶음 전체를 다시 돈다**(YOLO → SAM2 → INTERPOLATE). 단계 지목 재수행 축(`BatchStageRerunService`·`API-201`)이 이미 있으므로 **그것을 재사용할 수 있는지 먼저 확인**하고, 재사용 가능하면 새 경로를 만들지 않는다.
     - ⚠ **2노드 Active-Active 원자 클레임** — 같은 영상을 두 노드가 동시에 재개하지 않도록 조건부 UPDATE 로 클레임한다. 선례: `BatchTransitionService.tryClaimReprocessFromFailed`. Quartz 클러스터링은 트리거 중복만 막고 잡 내부 레이스는 막지 않는다.
- **불변**:
  - ★**온라인 오토라벨 경로(`label/service/AutolabelOnlineService`)를 건드리지 않는다.** 그 경로는 프리셋을 쓰지 않고 `labelMasterService.mappedDetectClasses()` 만 본다. 동작·응답 계약이 변하면 안 된다(AC5).

## §4 영향·리스크

### 하위호환

- **API 응답은 추가만** — 기존 필드 불변이라 외부 FE 팀 소비에 영향 없다.

- ⚠ **배치 동작은 실제로 바뀐다.** 지금까지 조용히 완주하던 영상이 앞으로는 보류된다. dev 실측은 58건 중 31건이 보류 대상으로 나왔으나, **그 데이터는 이 기능 개발 전에 입력된 것이라 상용 폭을 대표하지 않는다**(§1 경고). **상용 배포 전에 같은 쿼리로 상용 현황을 실측하는 것이 필수**이며, 그 결과가 크면 프리셋·COCO 매핑을 먼저 채운 뒤 배포할지 그때 판단한다.

### 되돌리기

- 보류 판정을 `RESOLVED` 가 아니어도 통과시키는 쪽으로 되돌리면 기존 fail-open 동작으로 복귀한다. 설정 토글로 감쌀지는 §5 검증 후 판단.

### 리스크

- **이벤트 코드가 없는 영상도 보류한다 (확정).** `EVENT_TYPE_UNREGISTERED` 사유에는 두 가지가 섞여 있다: ① 영상에 `EVNT_TYPE_CD` 가 아예 없음 ② 코드는 있는데 `LS_EVNT_TYPE` 에 미등록. **둘 다 보류**하되 사유를 구분해 기록한다. dev 실측상 ①은 0건이다. ⚠ 인지·수용한 대가 — dev 업로드처럼 이벤트 코드 없이 들어오는 경로가 새로 생기면 그 영상도 오토라벨링을 못 받는다.
- ★**기존 보류분이 쌓인다.** 재개 트리거는 프리셋 등록뿐이다. 프리셋을 영영 안 만들면 그 영상은 계속 보류 상태로 남는다 — 이건 의도된 동작이지만, **보류 영상이 얼마나 쌓였는지 볼 수단이 없으면** 다시 무증상이 된다. 이벤트 유형별 연결 상태 화면(R5)이 그 대리 신호지만 "보류된 영상 N건"을 직접 보여주지는 않는다. **인지·수용하는 잔여 항목**으로 남긴다.
- **클레임 고착** — §3 공유기반 주의 참조. 이 CO 최대의 함정.
- **그룹 재편 — 이 CO 가 이미 커버한다 (2026-08-25 사용자 판단, 구 「범위 밖 리스크」 서술 폐기)**. 관제가 `EVNT_NM` 을 보내기 시작하면 표시명이 갈려 그룹이 쪼개지고 `filterKeyOf` 의 대표코드가 바뀌어 기존 프리셋과 어긋난다. **구 서술은 그것을 "조용히 미매칭"이라 불렀는데, 그 「조용히」가 성립하는 것은 fail-open 인 현재 구조에서뿐이다.** 이 CO 를 적용하면 어긋난 유형은 ①보류되고(R1) ②관리 화면에 미연결로 표시되며(R5) ③프리셋을 걸면 재개된다(R4). 즉 별도 감지 장치가 필요 없다.
  - 반대 방향은 오히려 이득이다 — 비대표 코드에 걸려 원래 매칭되지 않던 프리셋은 그룹이 쪼개지면 **자기 그룹의 대표가 되어 살아난다**.
  - ⚠ 이 현상은 가정이 아니라 **실측이다** — dev 실제 DB(`postgis-klid`)에서 `EV02000102` 의 관제 수신명이 「일반화재」로 채워져 있어 화재 그룹이 이미 둘로 갈려 있다(다른 유형은 전부 NULL). 대응은 갈린 그룹마다 프리셋을 따로 거는 것으로 끝난다.

## §5 검증

### 수용 기준

- **AC1** — 프리셋 미보유 이벤트 유형의 영상이 배치를 타면, YOLO 라벨이 0건 저장되고 `LS_BATCH_PROC_LOG` 에 `(YOLO, SKIPPED, 사유)` 감사 행이 남으며, `LS_DATA_RAW.DATA_STTS_CD` 가 `COMPLETED` 로 가지 않는다. SAM2·INTERPOLATE 도 실행되지 않는다.
- **AC2** — 프리셋은 있으나 라벨이 전부 COCO 미매핑인 경우도 AC1 과 같게 보류되며, 사유가 "프리셋 없음"과 **구분되어** 기록된다.
- **AC3** — 그 이벤트 유형에 실효 프리셋을 등록하면 보류된 영상의 오토라벨 묶음이 재개되어 라벨이 저장된다. 이미 재개된 영상을 다시 트리거해도 중복 적재되지 않는다(멱등).
- **AC4** — 이벤트 유형 관리 화면에서 유형별 프리셋 연결 상태 3값이 구분되어 보이고, 미보유만 필터할 수 있다. 같은 표시명 그룹의 비대표 코드도 대표코드의 프리셋을 반영해 표시된다.
- **AC5** — 온라인 오토라벨 경로(`POST` 라벨링 화면 오토라벨)의 동작·응답 계약이 변하지 않는다(회귀 가드).
- **AC6** — 프리셋 등록 화면에서 라벨별 COCO 매핑 여부가 보이고, 전부 미매핑인 프리셋 저장 시 경고가 뜨되 저장은 성공한다.

### 검증 방법

- **자동 테스트** — 각 AC 에 대응하는 단위·통합 테스트. 특히 ① 보류 후 클레임이 해제됐는지(후속 진입이 409 가 아닌지) ② 재개 멱등 ③ 온라인 경로 회귀 가드.
- **배치 통합 시험** — Testcontainers 기반 배치 IT 로 보류 → 프리셋 등록 → 재개 → 라벨 적재 전 구간.
- **문서 동기화** — 동작·정책이 바뀌므로 `docs/v2-wiki/` 해당 페이지와 `docs/test-cases/` 카탈로그를 **같은 커밋에서** 갱신한다.

**구현 중 확정 — 설계에 조항이 없어 되받아 넣은 것 (2026-08-25)**
- **`API-186` 수정 응답은 프리셋 연결 상태를 싣지 않는다** — 표시명을 바꾸면 그룹이 쪼개져 대표코드가 바뀌는데 그룹 색인 캐시 무효화가 확정 이후라 같은 처리 안에서는 **수정 전 그룹**으로 판정된다. 옛 값을 실으면 「프리셋이 조용히 떨어진」 상태를 **연결됨으로 정반대 안내**한다. 화면은 저장 후 목록을 재조회한다(표시명 변경은 같은 그룹의 다른 행 상태도 바꾸므로 어차피 재조회가 맞다).
- **이벤트 유형을 특정할 수 없는 해석 결과는 `UNLINKED` 로 낮춘다** — 설계는 「이 목록에 나타나지 않는다」로만 규정했으나 코드는 총함수여야 한다. 예외를 던지면 그 한 건 때문에 **관리 화면 전체가 실패**하고, 보류 여부 축에서 `UNLINKED` 와 동치라 거르기가 어긋나지 않는다.
- **`AC-116` 이 세 상태로 뒤처져 있었다** — `LINKED_EXCLUDED` 신설이 `ADR-054`·`AC-119`·`API-185` 에는 반영됐는데 이 AC 만 낡아 있었다. 거르기 축도 「미연결만」이 아니라 **보류 유형 전체**로 정정했다(제외 선언은 보류를 유발하지 않아 결과에 들어가지 않는다).
  - ⚠ 이로써 §6 「미결」의 **거르기 범위** 항목이 해소됐다 — 화면은 `미연결`만이 아니라 **보류 전체**를 거른다.
