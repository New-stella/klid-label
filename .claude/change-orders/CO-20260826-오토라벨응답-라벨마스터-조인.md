# CO-20260826 오토라벨 응답이 라벨 마스터를 조인하지 않는다

## 1. 무엇이 문제인가

영상 상세 → **오토라벨 결과** 탭의 「라벨별 분포」가 **라벨명을 영어로만** 보여준다.
라벨 마스터 화면에는 한글 등록명이 나오는데 여기만 다르다. 색상도 전부 같은 파랑이다.

사용자 신고: *"상세화면에 라벨별 분포는 왜 다 영어로만 나오지? 라벨마스터랑은 다르게 나오네"*

## 2. 원인

두 화면이 **서로 다른 경로**를 타고, 그중 하나만 라벨 마스터를 조인한다.

| 경로 | 표시명 | 색상 |
|---|---|---|
| 라벨링 화면·라벨 마스터 | `LS_DATA_LBL` + **`LS_LABEL` 조인**(`labelId`) → 마스터 등록명 | 마스터 `COLR_VL` |
| **영상 상세 오토라벨 탭** | `LS_DATA_LBL.LABEL_NM` **원문** | `#3B82F6` **하드코딩** |

`VideoQueryService` 의 응답 조립이 한 값을 두 필드에 복사한다 — `labelCode` 와 `labelName` 이
같은 `getLabelNm()` 이고, 색은 상수다. AI 가 쓴 `LABEL_NM` 은 COCO 클래스명(영문)이라 영어로 보인다.

**이건 드리프트가 아니라 낡은 채로 남은 것이다.** DTO 주석이 이유를 스스로 적어 뒀다 —
*"라벨 색상/표시명 코드 테이블은 **V1 시점 미존재** — labelCode 를 labelName 으로 fallback,
color 는 기본값 사용. 추후 연계 시 확장."* 라벨 마스터가 생기기 전에 만들어진 응답이다.

⚠ **프론트를 고쳐서 될 일이 아니다.** 화면에 `resolveLabelDisplayName` 을 끼워도 그 함수는
2026-08-03 에 *"COCO 한글 사전은 마스터와 어긋나는 두 번째 진실원"* 이라는 이유로 치환 로직이
전부 제거된 **통과 함수**다. 서버가 마스터를 조인해 내려줘야 한다.

## 3. 도메인별 변경 상세

### DOMAIN-003 (영상·프레임 수집) — `video/service/VideoQueryService.java`

오토라벨 결과 응답 조립에서 라벨 마스터를 조인한다.

- **`labelName`** — 마스터에 연결된 라벨은 **마스터 등록명**. 미연결 라벨은 **저장된 라벨명 원문
  그대로**(지어내지 않는다). **절대 null 로 내리지 않는다** — 화면이 이 값을 그대로 그려 빈칸이 된다.
- **`color`** — 마스터 등록 색상. 미연결이면 **null**. **서버가 임의 기본색을 만들지 않는다.**
  화면은 이미 `?? '#4ECDC4'` 로 자기 폴백을 갖고 있다.
- **`labelCode`** — **무변경.** 화면이 이 값으로 분포를 묶으므로 의미를 바꾸면 그룹핑이 흔들린다.
- 조인은 **N+1 을 만들지 않는다** — 목록 경로가 이미 쓰는 batch 조회 방식을 따른다.

### 공유 경로 `batch/` 동반 확장 (경계 교차 — 장부 명시)

이 변경은 도메인 소유가 아닌 **공유 경로 `batch/` 2파일**을 함께 고친다.

| 파일 | 변경 |
|---|---|
| `batch/repository/AutoLabelInfoProjection.java` | `getLabelId()` **추가** |
| `batch/repository/LsDataLblRepository.java` | `findAutoLabelInfoByRawSn` 네이티브 쿼리에 `l.LBL_ID AS labelId` **추가** |

**왜 불가피한가**: 그 투영에 `labelId` 가 없으면 마스터를 조회할 키 자체가 없어
**§5 의 AC4(배치 조회 1회)가 성립 불가능**하다. 라벨마다 다시 조회하면 그게 곧 N+1 이다.

**왜 안전한가**: 둘 다 **순수 추가**다 — 기존 getter 4개·술어·정렬(`ORDER BY l.LBL_SN ASC`)·
파라미터 바인딩(`:rawSn` 만, 문자열 연결 없음)이 전부 무변경이고, 그 쿼리·투영의
**기존 소비자는 `VideoQueryService` 1곳뿐**이다(grep 실측).

⚠ **인터페이스에 메서드가 늘었으므로 익명 구현체는 컴파일이 깨진다.** 저장소에 2곳뿐이며
이번에 함께 갱신했다. 앞으로 이 투영에 필드를 더할 때도 같은 확인이 필요하다.

⚠ **절차상 미준수 1건 (기록)**: `conventions.md` 「코드 레이아웃」은 `batch/` 를 공통으로 규정하고
*"도메인 에이전트가 임의 수정 금지 — 필요하면 `notes_for_main.needs_core_change` 로 요청"* 이라고
못박는데, 이번 구현은 그 에스컬레이션 없이 진행됐다. 기술적 위험은 위 근거대로 0 이라 코드를
되돌리지 않고 **사실만 장부에 남긴다.** 다음 라운드부터는 공유 경로 변경 시 먼저 올릴 것.

**불변**: 응답 필드 구성·순서·타입(색만 nullable 로 넓힘) · 인가(REVIEWER/WORKER) ·
`confidence`·`createdBy` 산출 · 프론트 코드(변경 0건이어야 한다).

## 4. 영향 없음을 확인한 것

- **프론트 변경 0건** — 화면이 이미 null 색상을 폴백 처리한다.
- **다른 워크트리와 무충돌** — gui 는 backend 변경 0건, portal 의 backend 변경 33건은
  전부 `dataset/export/*` 축이라 `video/` 를 건드리지 않는다(실측).

## 5. 수용 기준

1. 마스터에 연결된 라벨은 분포 바에 **마스터 등록명**이 나온다.
2. 마스터 색상이 있으면 그 색으로 막대가 그려지고, 라벨마다 색이 갈린다.
3. 마스터 미연결 라벨은 **저장된 원문**이 그대로 나오고 화면 폴백색을 쓴다(빈칸·오류 없음).
4. 라벨 N종을 담은 영상에서 쿼리 수가 **N 에 비례해 늘지 않는다**.
5. 프론트 소스 변경 0건.

## 6. 관련 설계 ITEM

- **`API-044`** (GET /v1/videos/{rawSn}/labels/auto, v5) — **선반영 대상.**
  현재 본문이 결함을 사양으로 박아 뒀다: `color` = *"표시 색상 (기본값 #3B82F6)"*,
  `labelName` = *"라벨 표시명 (코드 테이블 미존재 시 labelCode fallback)"*.
  「코드 테이블 미존재」 전제가 무효다.
- `SCREEN-009` section[5] 는 분포 바의 **존재**만 규정하고 표시명·색 출처를 말하지 않는다 —
  응답 필드 계약이라 `API-044` 가 소관이다. 화면 사양은 건드리지 않는다.

## 7. 구현 로그

- **설계 선반영** — `API-044` v5 → v8 로 결함 서술(기본색 `#3B82F6` · 코드 테이블 미존재 전제)을 걷어냈다.
- **구현** — `VideoQueryService.getAutoLabels` 가 마스터를 조달한다. 선행으로 `AutoLabelInfoProjection`
  에 `labelId` 를, 네이티브 쿼리에 `LBL_ID` 투영을 더했다(§3 「공유 경로 batch/ 동반 확장」).
  `DEFAULT_LABEL_COLOR` 상수는 유일 사용처가 사라져 제거했다(잔존 참조 0건 확인).
- **활성 필터를 DB 에서 처리한다** — `findByLabelIdInAndUseYn(ids, 'Y')`. 애플리케이션에서
  `USE_YN` 을 재판정하지 않으므로 비활성 판정이 두 곳으로 갈리지 않는다.
- **검증** — 되돌림 5종(구 조달 복귀 · per-id 루프 · 활성필터 제거 · dedup 제거 · `LBL_ID` 투영 제거)이
  전부 RED. 독립 QA 가 그중 2종을 재현하고 **보고되지 않은 변형 1종을 새로 만들어**(마스터 조회에
  `labelId` 대신 `lblSn` 을 넘기는 잘못된 키) 2건 RED 를 확인했다.
  ⚠ 그 축의 가드는 사실상 테스트 한 건에 의존해 얇다 — **삭제·완화하지 말 것.**
- **회귀** — backend FULL `849 XML / 7,724 tests / 0 실패`(8분 13초). `cleanTest` 강제 실행이
  로그로 확인됐고 XML 849건이 전부 그 빌드 시각 이후 생성됐다(UP-TO-DATE 스킵·잔재 아님).
- **설계 빚 회수** — 「비활성 마스터는 미연결과 동일 취급」 규칙이 v8 확정 이후 구현 지시로만
  내려가 설계에 빠져 있었다. `API-044` **v9** 로 `color`·`labelName` description 에 명시했다.
  `SCREEN-009` 는 본문 대조 후 편집 불요(판정을 서버에 위임하는 서술이라 화면 동작 불변).

### 남은 것 (별건)

- `API-044` 를 검증하는 **수용기준(AC)이 0건**이다. 「라벨 표시명·색상의 마스터 조달」 축을
  규정하는 AC 가 프로젝트 전체에 없다.
- `API-044.brownfield.decided_by` 가 비어 있어 근거 정책(`ADR-034`)으로 가는 링크가 없다.
- 같은 미연결 축을 `API-037`·`API-082`·`API-177` 이 **서로 다른 수위로** 서술한다.
  한 결정이 층마다 따로 적히는 이 저장소의 반복 패턴이라 「결정 = 축」으로 한 번에 닫을 대상이다.
- FE 타입 `LabelObject.color` 가 `string`(non-nullable)인데 서버가 `null` 을 보낸다.
  소비처가 `?? '#4ECDC4'` 폴백을 가져 런타임은 안전하나 타입이 계약과 어긋난다.
  같은 파일의 `confidence: number` 도 이전부터 같은 상태다.
