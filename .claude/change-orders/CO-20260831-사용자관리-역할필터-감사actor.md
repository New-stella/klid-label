## §1 배경

2026-08-31 **수용기준 71건 전수 판정**(읽기 전용 검증 에이전트 5대)에서 `AC-1018`(관리자 사용자 관리 화면)이 `partial` 로 나왔다. 사유는 둘이고 **둘 다 실측으로 재확인**했다.

### 결함 ① — 역할 필터가 「가져온 페이지 안에서만」 걸러진다

`user/service/UserService.searchUsers` 는 `userRepository.searchByKeyword(keyword, pageable)` 로 **한 페이지를 먼저 가져온 뒤** 그 안에서 역할을 거른다:

```java
Stream<LsAcntUser> filtered = page.getContent().stream();
if (role != null && !role.isBlank()) {
    filtered = filtered.filter(u -> role.equals(roleByUserNo.get(u.getUserNo())));
}
...
return new PageImpl<>(items, pageable, page.getTotalElements());
```

**증상 둘**:
- **1페이지 밖의 해당 역할 사용자가 조회되지 않는다.** 20건씩 끊어 오는데 그 20건 안에 그 역할이 없으면 결과가 비고, 뒤 페이지에 있어도 도달할 수 없다.
- **총건수·페이지수가 어긋난다.** `totalElements` 가 **필터 이전 원본 페이지 합계**라 "3건 표시 / 총 87건" 같은 상태가 된다.

★ **이건 몰라서 난 것이 아니라 적어 두고 미룬 것이다.** 코드 주석이 스스로 밝힌다:

> *"주의: role 필터는 페이지 컨텐츠에 인메모리로 적용되므로 필터 시 totalElements 가 실제 매칭 수보다 클 수 있다(작업자 모수가 적어 실용상 허용). **근본 해결(SQL JOIN 필터)은 후속.**"*

「작업자 모수가 적어 실용상 허용」이라는 전제는 **관리자 역할 신설(`ADR-055`)로 역할이 4종이 되면서 약해졌다** — 역할별로 거르는 동선 자체가 그때 생겼다.

### 결함 ② — 역할 변경 기록에 「바꾼 사람」이 없다

```java
log.info("[User] role changed userNo={}, before={}, after={}", userNo, currentRole, nextRole);
```

**대상만 남고 주체가 없다.** `user/entity/LsUserRole` 의 컬럼도 `USER_NO`·`ROLE_CD`·`REG_DT`·`UPD_DT` 넷뿐이라 **영속 기록에도 주체가 없다**. 개인 단위 추적은 별도 `[AdminSession] opened actor=` 줄과 **시각으로 이어 붙여야** 가능하다.

⚠ **권한 상승은 감사에서 가장 중요한 사건이다.** 누가 누구를 관리자로 올렸는지가 남지 않는 것은 그 자체로 결함이다.

★ `update(Long userNo, UserUpdateRequest req)` 에 **actor 파라미터가 아예 없다** — 컨트롤러는 `TokenClaims` 를 갖고 있으나 서비스로 넘기지 않는다.

## §2 변경 요지

1. **역할 필터를 조회 계층으로 내린다** — 필터가 서버 전체 기준으로 걸리고 `totalElements` 가 실제 매칭 수와 맞는다.
2. **역할 변경에 주체를 남긴다** — `LS_USER_ROLE.MDFR_ID` 신설 + 로그에 actor 추가.

### DOMAIN-001 (사용자·권한) — `klid-d001-implementer`

**대상 파일·심볼**

| 파일 | 무엇 |

**변경 ① — 역할 필터를 조회로 내린다**

- `LsAcntUser` 와 `LsUserRole` 은 **ID 참조**(연관 매핑 없음)다. JPQL `EXISTS` 서브쿼리로 거는 것이 이 저장소 관례에 맞다 — 네이티브 SQL 로 내려가지 마라.
- **`role` 이 없으면 지금과 똑같이 동작해야 한다**(전체 반환). 기본 동선이 바뀌면 안 된다.
- **`totalElements` 가 실제 매칭 수여야 한다.** 「필터 적용 후 목록 + 필터 이전 합계」 조합을 남기지 마라 — 그게 이번에 고치는 결함이다.
- **미배정(역할 행 없음) 사용자는 어떤 역할 필터에도 안 걸린다** — 지금 성질이며 유지한다(주석에 명시돼 있다).
- ⚠ **정렬은 등록순(`userNo` ASC)이 유지돼야 한다.** 컨트롤러가 그렇게 고정하고 있고 화면이 그 순서를 전제한다.

**변경 ② — 역할 변경에 주체를 남긴다**

- **`LS_USER_ROLE.MDFR_ID` 신설.** ★ **`VARCHAR(30)`** 으로 한다 — `LsSystemConfig`·`LsNotice`·`LsMngrPswd`·`LsOtsdCtgryMpng`·`LsVrfcEvntType` 다섯 엔티티가 이미 `@Column(name="MDFR_ID", length=30)` 이다. **표준용어(수정자=MDFR·ID)·표준도메인이 이미 검증된 물리명이니 새로 짓지 마라.**
- **Flyway 파일은 `V22__` 로 시작한다** — 현재 최신이 `V21` 이고 이 번호는 메인이 확정했다. ⚠ 번호를 임의로 바꾸지 마라(병렬 브랜치 충돌의 원인).
- 마이그레이션은 **기존 행을 깨지 않아야 한다** — `MDFR_ID` 는 nullable 이고 기존 행은 null 로 남는다(그 값은 "이 컬럼이 생기기 전에 바뀐 것"을 뜻한다).
- **actor 를 컨트롤러 → 서비스로 넘긴다.** ⚠ **요청 바디에서 받지 마라** — 그건 위조 가능한 값이다. `SecurityContext`/`TokenClaims` 에서만 온다(이 저장소의 `AdminSessionGate.currentSubject` 가 같은 이유로 그렇게 한다).
- **로그에도 actor 를 남긴다** — `[User] role changed userNo={}, before={}, after={}` 에 주체를 더한다. ⚠ **PII·토큰을 싣지 마라**(사용자 식별자만).

**불변 (건드리면 안 되는 것)**

- **`update` 가 `LS_USER_ROLE` 만 갱신하는 성질** — 사용자 마스터(`LS_ACNT_USER`)는 이 화면이 쓰지 않는다(javadoc 이 못박음).
- **마지막 관리자 강등 차단**(`guardLastAdmin` + `lockUserNosByRoleCd` 의 `FOR UPDATE`) — 조회 후 UPDATE 로 바꾸지 마라. 두 관리자가 서로를 동시에 내리면 둘 다 통과한다. 회귀 가드 `user/LastAdminGuardIT`.
- **역할 캐시 무효화가 `AFTER_COMMIT`** 인 성질(커밋 전 evict 는 동시 요청이 옛 값을 재캐싱한다).
- **N+1 방지** — 역할 조회가 페이지당 1회인 성질(`findByUserNoIn`).
- `user/AutoWorkerRegistrationIT` · `user/LastAdminGuardIT` · `common/security/RoleHierarchyTest` 는 **무수정 통과**해야 한다.

**수용기준**

1. 역할 필터가 **서버 전체 기준**으로 걸린다 — 2페이지 이상 데이터에서 뒤 페이지의 해당 역할 사용자가 1페이지에 나온다.
2. 필터 적용 시 **`totalElements` 가 실제 매칭 수**와 같다.
3. `role` 미지정이면 **지금과 동일**(전체 반환·등록순).
4. 미배정 사용자는 어떤 역할 필터에도 안 걸린다.
5. 역할 변경 시 **`MDFR_ID` 에 주체가 남고** 로그에도 주체가 실린다.
6. 요청 바디로 actor 를 주입해도 **무시된다**(위조 차단).
7. 기존 행(`MDFR_ID` null)이 조회·갱신에서 깨지지 않는다.
8. 불변 절의 가드가 무수정 통과, 백엔드 전건 GREEN.

**Flyway 번호(`V22`)만 메인이 확정했고 파일 작성은 도메인 구현에 포함한다** — `LS_USER_ROLE` 은 D001 소유 테이블이라 `common/`·앱 진입점 같은 공유 기반이 아니다. 번호 충돌만이 공유 위험이었고 그것은 위에서 닫았다.

## §4 영향·리스크

- **하위호환**: `GET /v1/users` 의 요청·응답 스키마 **무변경**. 바뀌는 것은 필터 결과의 정확성과 `totalElements` 값이다. ⚠ 지금 잘못된 총건수를 보고 만든 화면 로직이 있다면 그것이 드러날 수 있다(그게 정상이다).
- **관제 계약면**: 영향 0.
- **되돌리기**: 코드 revert + `MDFR_ID` 는 nullable 이라 남겨도 무해(드롭 마이그레이션을 서두르지 마라 — 비가역이다).
- **리스크**: `EXISTS` 서브쿼리가 정렬·페이징과 함께 돌 때 실행계획이 나빠질 수 있다. 사용자 모수가 작아 실용상 문제는 없을 것으로 보나, **N+1 이 되살아나지 않는지**는 확인해야 한다.

## §5 검증

- 백엔드 전건 회귀. 신규 시험은 **2페이지 이상 데이터**로 필터를 걸어야 한다 — 1페이지에 다 들어가는 fixture 로는 이 결함이 재현되지 않는다(그래서 지금까지 안 잡혔다).
- **변이로 확인하라**: 필터를 인메모리로 되돌린 판·`totalElements` 를 원본 합계로 되돌린 판·actor 를 안 남기는 판에서 각각 RED 가 나야 한다.
- `docs/test-cases/` 는 **케이스 표가 동결**돼 있다(2026-08-27) — 행을 추가하지 않는다.

## §6 관련 설계 ITEM

**설계 반영 불요 — 이건 「설계가 옳고 코드가 어긋난」 경우다.**

`AC-1018` 이 이미 *"역할필터를 확정하면 서버 재조회"* 와 *"바꾼 사람이 개인 단위로 기록"* 을 규정하고 있다. 코드가 그것을 못 지키고 있을 뿐이므로 **ITEM 을 고치지 않는다** — 고치면 결함을 사양으로 만드는 것이 된다.

⚠ 이 저장소의 「LogiCraft 먼저」 규칙은 **사양을 바꿀 때** 적용된다. 사양이 이미 옳으면 코드가 따라가는 것이 맞고, 그 판정 근거는 정합 모드의 규칙(*"코드가 확정 정책과 충돌하면 정의서를 고치지 말고 코드 결함 후보로 보고"*)이다.

**구현 요지**

- **역할 필터를 조회 계층으로** — `searchByKeyword` → `searchByKeywordAndRole` (JPQL 상관 `EXISTS`). JOIN 을 쓰지 않은 이유는 역할 행이 둘 이상일 때 사용자가 중복되기 때문이다. 서비스는 `page.map(...)` 으로 페이징 메타를 승계해 인메모리 필터와 `PageImpl` 재조립을 함께 걷었다. count 쿼리는 손으로 적지 않고 Spring Data 유도에 맡겼다 — 손으로 적으면 술어가 한쪽만 바뀌어 총건수가 조용히 어긋난다.
- **역할 변경에 주체** — `LS_USER_ROLE.MDFR_ID varchar(30)`(V22, nullable·백필 없음). `upsertRole` 단일 문장이 역할과 주체를 함께 써 부분 기록이 남지 않는다. 값은 `TokenClaims.sub()` 에서만 오고 제어문자 제거(CWE-117) 후 저장·로그에 싣는다.
- **온프렘 스키마 재생성**(메인 수행) — `deploy/onprem/db/schema.sql` 은 수기 편집 금지 생성물이라 `gen-schema-sql.sh` 로 V1~V22 전량 적용 후 재덤프했다. 안 했으면 온프렘 설치본에서 역할 변경이 `column "mdfr_id" does not exist` 로 죽는다(온프렘은 Flyway 를 쓰지 않고 이 덤프만 로드한다).

**QA 가 독립 증명한 것 — AC2 는 변이 없이 수치 삼각측량으로 확정됐다**

`workerFilterPagesThroughAllMatches` 가 `content` 20건(=pageSize)이라 `PageableExecutionUtils` 단축 경로가 **성립하지 않아** count 쿼리가 반드시 실행된다. 그 상태에서 `totalElements` 가 **24** 다 — 단축 경로였다면 20, 술어가 count 에 안 걸렸다면 26 이므로, 24 는 「count 가 실행됐고 그 쿼리에 `EXISTS` 가 걸려 있다」로만 설명된다. 이 자리가 이번 CO 에서 가장 뚫리기 쉬웠다(검수자 1건/page0 시험만 있었다면 count 가 실행조차 안 돼 술어 누락이 숨는다).

**미반영·보류 항목**:

- `AC-1018` 의 나머지 절(20건 페이징·등록순·검색/역할 필터 확정 시 1페이지 리셋·유효창 가산)은 **이미 충족**돼 있다(판정 회차 확인). 이번 CO 는 어긋난 두 축만 닫는다.

**QA 가 남긴 후속 3건 — 전부 low, 이번 범위 밖**

1. **관리자 부트스트랩 경로에 주체가 없다** (`auth/service/RoleClaimService`) — 최초 관리자 자가부여는 `MDFR_ID` 를 쓰지 않아 그 행만 null 이다. 「권한 상승은 감사에서 가장 중요한 사건」이라는 이 CO 의 근거에 정확히 해당하는 자리인데 비어 있다. CO §3 의 대상 심볼이 아니라 범위 위반은 아니다. **별건 CO 로 다룰 것** — actor 와 대상이 같아 값이 자명하고 문장이 하나라 원자성도 유지된다. 「자가부여라 주체 기록이 불요」로 판단한다면 **그 판단을 주석에 명시**해 다음 감사가 같은 지적을 반복하지 않게 한다.
2. **2-arg 오버로드 4곳이 시험 전용이다** (`LsUserRoleRepository.upsertRole` 2-arg · `UserService.update` 2-arg · `LsUserRole.of` · `changeRole`) — `src/main` 호출처가 0건이고 시험 하네스만 쓴다. 누가 나중에 2-arg 를 부르면 **주체 없이 역할이 바뀌는데 컴파일도 되고 예외도 안 난다**(조용한 감사 공백). 기능 결함은 아니므로 지금 지울 필요는 없으나, 「운영 창구는 3-arg 만」을 문서가 아니라 **아키텍처 시험으로 고정**하는 편이 안전하다. 지우는 선택은 `LastAdminGuardIT`·`LsUserRoleRepositoryIT` 가 그 오버로드를 써서 시험 수정을 동반한다.
3. **30자 초과 subject 가 조용히 절단된다** (`UserService.normalizeActor`) — 절단 결과가 「다른 식별자처럼 보이는 문자열」이 되어 감사가 사실과 다른 주체를 가리킬 수 있다. 실사용 subject 가 숫자 userNo 라 도달성은 사실상 0. 바꾼다면 절단 대신 **「초과면 null + WARN」** 이 이 CO 가 명시한 원칙(*"지어낸 값보다 빈 값이 낫다"*)과 더 정합하다.

**QA 가 못 본 것(정직 기재)**: 런타임 E2E 미수행(FE 변경 0건이라 화면에서 필터·총건수 표시를 확인하지 않았다 — §4 가 예고한 「잘못된 총건수를 전제한 FE 로직」이 있는지는 이번 검증 밖) · 변이 검증 M1~M3 는 구현 에이전트 주장이며 QA 의 관측이 아니다(권한상 재현 불가, 다만 AC2 는 위 삼각측량으로 독립 증명됨) · `EXISTS` 서브쿼리의 실행계획·대규모 모수 성능 미측정 · 온프렘 설치 스크립트 실행 검증 미수행(컬럼 존재는 grep 으로만 확인).
