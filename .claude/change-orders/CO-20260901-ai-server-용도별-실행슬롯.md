## §1 배경

작업자가 라벨링 화면에서 SAM2 클릭 분할이나 추적을 누르면, **오토라벨링 배치가 돌고 있는 동안에는 응답이 오지 않는다.**

근본 원인은 ai-server 에 있다. 엔드포인트 4개가 전부 `async def` 로 선언돼 있는데 그 안에서 부르는 추론은 **블로킹 호출**이다.

| 파일·행 | 엔드포인트 |
|---|---|
| `ai-server/app/routers/yolo.py:62` | `POST /infer/yolo/predict` |
| `ai-server/app/routers/yolo.py:215` | `POST /infer/yolo/track` |
| `ai-server/app/routers/sam2.py:122` | `POST /infer/sam2/segment` |
| `ai-server/app/routers/sam2.py:143` | `POST /infer/sam2/track` |

`run_in_threadpool` 사용처가 **0건**이라, 추론이 도는 동안 FastAPI 이벤트 루프가 통째로 잡힌다. 그래서 모든 요청이 **도착 순서로 완전 직렬화**된다. 배치가 프레임 N 건을 밀어 넣으면 그 뒤에 도착한 사용자 클릭은 N 건이 다 끝날 때까지 기다린다.

동시 요청으로 VRAM 이 늘지 않았던 것(선행 측정 +0 MiB)도 같은 이유다 — 애초에 동시에 돌지 않고 한 줄로 서 있었다.

### 실측 — 얼마나 심각한가 (cudo_246 Tesla T4, 2026-09-01)

배치 큐 120건을 포화시킨 뒤 인터랙티브 요청 1건의 지연:

```
현행 (단일 큐)     첫 요청  21,918.8 ms      ← 21.9초
슬롯 분리          첫 요청     268.9 ms      (p50 240.0 / max 293.9)
유휴 (배치 없음)              141.2 ms
```

**21.9초 → 0.27초.** 이것이 이 변경의 값이다.

전체 측정 절차·재현 명령·판정 근거는 `reports/ai-server-slot-split-20260901.md`.

### 왜 장비·프로세스·포트를 늘리지 않는가 (인계받은 제약)

> ⚠ **2026-09-01 정정 — 아래 제약 1이 설계와 어긋난다.** `INFRA-001` v5 는 ai-server 가
> **협력 파트너 소유 GPU 장비 두 대에 이중화로** 올라간다고 명시한다. "한 대만 들어갈 수
> 있다"와 "장비가 총 한 대다"는 **다른 문장**인데 후자로 읽었다. 상세는 §9.

1. H100 없음 — 검증은 Tesla T4(15GiB)로 한다
2. **ai-server 가 한 대만 들어갈 수 있다** — 장비 분리 불가
3. **포트가 9300 하나만 열려 있다** — 외부 포트 추가 불가. 루프백(127.0.0.1:9301)은 방화벽과 무관하나, 9300 에 얹을 리버스 프록시를 딥러닝팀 장비에 설치해야 해 협의 부담이 커 미채택

## §2 변경 요지

ai-server **프로세스 1개 · 포트 9300 을 그대로 두고**, 앱 내부에 용도별 실행 슬롯 두 개를 만든다.

```
ai-server (프로세스 1 · 포트 9300)
  ├── batch_slot        ThreadPoolExecutor(max_workers=1)   ← 파이프라인 전용
  └── interactive_slot  ThreadPoolExecutor(max_workers=1)   ← 저작도구 전용
```

- 라우터의 블로킹 추론을 **해당 슬롯으로 오프로드**한다(현재 `run_in_threadpool` 0건 → 이벤트 루프를 놓아준다).
- 어느 슬롯으로 갈지는 요청 헤더 **`X-Workload: batch`** 로 가른다.
- **배치만 명시하고 기본값은 인터랙티브다.** 표시할 곳이 배치 2곳뿐이라 빠뜨릴 여지가 적고, 빠뜨려도 **사용자 경험이 보호되는 쪽으로 틀린다**.
- SAM2 는 슬롯마다 **별도 인스턴스**를 쓰고, YOLOX ONNX 세션은 **공유**한다(공유 안전성 실측 확인 — §5).

## §3 도메인별 변경 상세

### 공유기반 선처리 (메인 직접, Phase 3.5)

- **대상**: `backend/.../common/client/AiServerClient.java` · `backend/.../common/config/WebClientConfig.java`
- **문제**: `AiServerClient` 의 5개 메서드가 **요청 DTO 만** 받는다(`predictYolo` · `predictYoloTrack` · `segment` · `track` · `verifyObjects`). 헤더를 실을 자리가 없다.
- **변경**: 배치 호출 경로에서만 **요청 시점에** `X-Workload: batch` 헤더를 얹는다. WebClient **빈을 늘리지 않는다.**
  - ⚠ **구 권장안 폐기(2026-09-01)** — *"배치 전용 WebClient 빈을 하나 더 두고 `.defaultHeader` 를 건다"*. 호출부 시그니처를 안 건드리는 장점이 있으나, **빈 개수를 baseUrl 축에 묶어** LB CO 가 단일 URL 을 노드 목록으로 쪼갤 때 `2(용도) × N(노드)` 조합 폭발이 난다.
  - **요청 시점 헤더는 용도 축과 노드 축을 직교시킨다** — LB CO 가 노드 선택기를 넣을 때 용도 축을 건드릴 필요가 없다. LB CO 의 명시 요청이기도 하다(§9).
  - `aiServerWebClient` 빈의 `@Value("${authoring.integration.ai-server.base-url}")` **단일 문자열 고정 구조를 더 굳히지 않는다** — 나중에 노드별로 쪼갤 자리다. 헤더 로직을 그 구조에 엮지 말 것.
- **불변**:
  - `authoring.integration.ai-server.base-url` 설정 키·`IntegrationEndpointExchangeFilter`(연동 주소 런타임 재작성) · `largeBufferStrategies()` · Resilience4j `circuitBreaker`/`retry`/`AiWaitBudgetPolicy.PER_CALL_TIMEOUT` 는 **양쪽 WebClient 에 동일하게** 적용된다. 배치용만 빠뜨리면 배치가 서킷브레이커 밖으로 샌다.
  - 새 컬럼·테이블 없음 → Flyway 무관, 표준용어 판정 대상 아님.

### DOMAIN-004 (AI 보조 라벨링) — `klid-d004-implementer`

#### (가) ai-server — 슬롯 도입

- **대상 파일·심볼**
  - `ai-server/app/main.py` — 슬롯 생성·종료(lifespan)
  - `ai-server/app/routers/yolo.py:62,215` · `ai-server/app/routers/sam2.py:122,143` — 블로킹 추론 오프로드 + 헤더 판정
  - `ai-server/app/models/sam2_loader.py` — 싱글톤 → 슬롯별 인스턴스
- **변경**
  1. 슬롯 2개(`batch_slot` · `interactive_slot`, 각 `max_workers=1`)를 앱 수명주기에 묶어 생성하고 shutdown 에서 정리한다.
  2. 엔드포인트 4개에서 블로킹 추론부를 해당 슬롯으로 오프로드한다. 슬롯 선택은 `X-Workload` 헤더가 정확히 `batch` 일 때만 배치, **그 밖의 모든 경우(미지정·빈값·오타·대소문자 불일치)는 인터랙티브**.
  3. `sam2_loader` 의 predictor 싱글톤을 **슬롯별 인스턴스**로 가른다.
  4. YOLOX 는 세션을 **공유한다** — 새로 만들지 않는다(§5 실측 근거).
- **불변(건드리면 안 되는 것)**
  - **엔드포인트 경로·요청/응답 스키마 무변경.** 경로는 `/infer/yolo/predict` · `/infer/yolo/track` · `/infer/sam2/segment` · `/infer/sam2/track` 다(`main.py` 의 `include_router` prefix). `/api/v1/...` 아니다.
  - `POST /infer/vlm/verify-objects` 는 **대상 아님** — `vlm_loader.get_vlm_model()` 이 항상 `None` 을 돌려주는 mock 전용이라(`"real load not implemented yet"`) GPU 작업이 없다. 슬롯을 붙이지 말 것.
  - 기동 가드(`startup_guard.verify_deployment_settings` · `verify_models_available`) · mock 폴백 정책(`env_mock`/`weights_missing`/`load_failed`) 무변경.
- **주의 — 실측으로 확증된 불변식 3가지. 어기면 조용히 깨진다**

  1. **SAM2 는 슬롯마다 별도 인스턴스.** `SAM2ImagePredictor.set_image` 가 이미지 임베딩을 인스턴스 필드에 보관한다(`routers/sam2.py:270` 의 `_predict_masks`). 공유하면 마스크가 어긋날 뿐 아니라 **크래시한다** — 실측: 공유 12회 중 어긋남 1건 + `TypeError: 'NoneType' object is not subscriptable`(`sam2_image_predictor.py:418`, `self._features["high_res_feats"]`)로 스레드 사망. 분리 시 20/20 정합.
     > 지금 안 터지는 것은 **이벤트 루프가 막고 있기 때문**이다. 오프로드하는 순간 열리는 문이다.

  2. **인터랙티브 트래커 clipId 의 요청 단위 UUID 를 유지할 것.** ByteTrack 트래커를 공유하면 24/24 프레임에서 track_id 가 어긋난다(`_TRACKERS_LOCK` 은 **캐시 딕셔너리만** 보호하고 트래커 객체는 보호하지 않는다).

     | 경로 | clipId |
     |---|---|
     | 배치 `batch/step/YoloAutolabelStep:325` | `String.valueOf(rawSn)` → `"123"` |
     | 인터랙티브 `label/service/YoloTrackService:129` | `rawSn + ":" + UUID.randomUUID()` → `"123:a1b2…"` |

     인터랙티브가 요청 단위 UUID 를 써서 **절대 같은 트래커 핸들을 잡지 않는다** → 현재 도달 불가. **"같은 영상이니 rawSn 으로 통일하자"는 최적화를 하면 그 순간 붕괴가 실경로가 된다**(해당 코드에 이미 그 이유가 주석으로 있다 — `YoloTrackService:126-128`).

  3. **각 슬롯은 `max_workers=1` 고정.** 슬롯 안에서 늘리면 그 슬롯 내부에서 1·2 가 그대로 재현된다.

- **수용기준**
  - `X-Workload: batch` 로 큐가 포화된 상태에서 헤더 없는 요청의 응답이 **1초 이내**(T4 실측 269ms, 여유 포함)
  - `X-Workload` 미지정·빈값·오타·대소문자 불일치가 전부 인터랙티브로 떨어진다(fail-safe 방향)
  - SAM2 인스턴스가 슬롯 수만큼 존재하고, 두 슬롯 동시 가동 시 마스크가 단독 실행 결과와 **바이트 동일**
  - 엔드포인트 4개의 요청/응답 스키마 무변경 — 기존 계약 테스트 그대로 통과

#### (나) 백엔드 — 배치 표시 2곳

- **대상 파일·심볼**: `batch/step/YoloAutolabelStep.java` · `batch/step/Sam2SegmentStep.java`
- **변경**: 이 두 곳의 ai-server 호출만 **배치 슬롯으로** 나가게 한다(공유기반에서 만든 배치 WebClient 경유).
- **불변**: `clipId = String.valueOf(rawSn)`(`YoloAutolabelStep:325`) 유지 · 배치 파이프라인의 스텝 순서·트랜잭션 경계(ADR-030) 무변경.

## §4 영향·리스크

- **하위호환**: ai-server 엔드포인트 경로·스키마 무변경. `X-Workload` 는 **추가 헤더**라 보내지 않는 호출자(구 버전 백엔드 포함)는 인터랙티브로 동작한다 — 깨지지 않는다.
- **되돌리기**: 슬롯 오프로드를 걷어내면 현행(직렬) 동작으로 복귀. DB·스키마·저장 데이터 변경이 없어 되돌리기가 코드 revert 로 끝난다.
- **리스크**
  - ⚠ **인터랙티브 지연이 배치 가동 중 141ms → 240ms 로 늘어난다.** 대신 21.9초가 사라지므로 순이익이지만, "느려지는 구간이 생긴다"는 것은 사실이다 — 인지·수용.
  - ⚠ **배치 처리량이 인터랙티브 서빙 중 약 16% 감소**(단독 ~5 job/s → 4.2 job/s). 인지·수용.
  - ⚠ **VRAM 이 SAM2 두 번째 인스턴스만큼 늘어난다**(+295 MiB). 목표 형상 피크 1,567 MiB 로 예산(1,935) 안이다. H100 은 CUDA 컨텍스트가 커서 1.75~1.95 GiB **추정**(실측 아님).
  - ⚠ 이번 검증은 **인프로세스 재현**이라 FastAPI 이벤트 루프 → 오프로드 → 슬롯 배선이 실제로 그렇게 도는지는 **HTTP 레벨 재확인이 남는다**(§5).

**즉 LB 이중화 요청은 이 「미해결」 3지선다를 푸는 것이다.**

### 하마터면 낼 뻔한 사고 — 기록해 둔다

§6 에 `INFRA-001` 의 `replicas: 2 → 1` 을 **"드리프트 교정"으로** 넣어놨었다. 실행했으면 **맞는 설계 기록을 잘못된 방향으로 지웠다.**

원인은 제약 문장을 잘못 읽은 것이다 — **"우리가 추가로 한 대를 더 넣을 수는 없다"(= 이미 있는 2대 안에서 해결하라)** 와 **"장비가 총 1대다"** 는 전혀 다른 제약인데 후자로 단정했다. 인계 메시지의 요약된 제약을 설계 원문과 대조하지 않은 것이 근인이다.

⇒ **`INFRA-001` 은 이 CO 에서 건드리지 않는다. LB CO 소유.**

### 그럼에도 슬롯 분리는 버리지 않는다 (잠정 판단 — 피어 회신으로 확정)

LB 와 슬롯은 **배타가 아니라 다른 축**이다.

| 축 | 담당 | 없으면 |
|---|---|---|
| LB 이중화 | 장비 간 가용성·분산 | 한 대 죽으면 오토라벨링 정지 |
| 용도별 슬롯 | **인스턴스 내** 배치↔인터랙티브 공정성 | 한 인스턴스 안에서 21.9초 대기 |

- **페일오버 순간이 결정적이다.** 한 대가 죽어 남은 한 대로 몰리면 배치와 인터랙티브가 **다시 섞인다.** 그때 슬롯이 없으면 21.9초가 그대로 재현된다. 슬롯은 이중화의 **안전망**이다.
- `INFRA-001` 이 말하는 "가속기를 여럿이 나눠 쓴다"(비식별화·생성형 AI·시계열 분석이 같은 장비에)도 같은 방향이다 — 슬롯은 ai-server 가 **스스로 통제할 수 있는 유일한 축**이다.

### 소유 분할 (제안 — 피어 확인 대기)

| 대상 | 소유 |
|---|---|
| `INFRA-001` | **LB CO** |
| `API-113`·`API-119`·`API-120`·`API-121` (선택 헤더 `X-Workload` 추가) | **이 CO** |
| `common/client/AiServerClient` · `common/config/WebClientConfig` | ⚠ **충돌 가능** — 3지선다 2번(백엔드가 목록 보유)을 고르면 LB CO 도 이 두 파일을 건드린다 |

`API-122`(`/infer/vlm/verify-objects`)는 양쪽 다 범위 밖 — `vlm_loader` 가 항상 `None` 을 돌려주는 mock 전용이라 GPU 작업이 없다. LB 가중치 계산에서 GPU 부하로 세면 안 된다.

### LB 설계에 넘긴 실측 (피어에 전달 완료)

동시 요청이 들어와도 **VRAM 이 늘지 않는다**(+0 MiB 실측) — 이벤트 루프가 막혀 애초에 겹쳐 돌지 않기 때문이다. 즉 현행 형상에서 한 장비에 요청을 몰아도 **메모리로는 티가 안 나고 지연으로만 드러난다.** LB 헬스체크가 `/health` 만 보면 포화된 장비를 계속 정상으로 판정한다 — 지연 기반 판정이나 큐 깊이 노출이 필요할 수 있다.

### 재개 조건

피어 회신 3가지 — ①LB 가 헤더 기반 라우팅을 하는가 ②3지선다 중 몇 번인가 ③LB CO 가 `API-113/119/120/121` 을 건드리는가.

- **헤더 라우팅 가능 + 장비 2대** → 기각 대안 중 "장비 용도 분리"가 최선안으로 되살아난다. 슬롯은 페일오버 안전망으로 격하하되 **남긴다**.
- **라운드로빈/페일오버만** → 슬롯 분리가 주 해법 그대로.

## §10 ✅ 보류 해제 — LB 범위 확정 (2026-09-01, 사용자 확정 · `lb-test` 피어 경유)

| 항목 | 확정 |
|---|---|
| GPU 장비 | **물리 2대** — §9 의 "한 대만" 제약은 **해제**됐다. `INFRA-001` 의 `replicas: 2` 는 드리프트가 아니라 맞는 기록이었다 |
| 포트 | **9300 유지** |
| LB 방식 | 3지선다 중 **②백엔드가 목록을 갖고 분산** — Spring 안 **클라이언트 사이드 LB**. 별도 LB 프로세스·nginx 안은 기각 |
| **순서** | **★슬롯 분리가 먼저, LB 가 그 다음. 이 CO 가 선행이다** |

### 왜 장비가 2대여도 슬롯 분리를 하는가 (순서의 근거)

1. **클라이언트 LB 는 노드를 가르지, 노드 안을 가르지 못한다.** ai-server 는 HTTP 요청을 받아 `batch_slot`/`interactive_slot` 중 하나를 골라야 하는데, 요청에 용도가 실려 있지 않으면 고를 수 없다. `X-Workload` 가 **슬롯 선택용**인 이유이며, 노드 선택은 호출 지점이 컴파일 타임에 알아서 헤더가 필요 없다 — **두 개의 다른 결정이다.**
2. **노드별 용도 고정으로 헤더를 대신하면 페일오버가 죽는다.** 노드 A=배치 전용/B=인터랙티브 전용으로 설정하면, 한 대가 죽을 때 그 용도가 통째로 정지하거나 남은 한 대에 두 용도가 몰린다. 그 인스턴스에 슬롯이 없으면 **21.9초가 그대로 재현**된다.
3. **직렬 처리 상태로 장비만 늘리면 처리량 목적이 반만 찬다.** 실측 — 워커 1개 5.2 req/s → 2개 8.1 req/s(**+56%**, GPU 병목이라 선형 아님). 각 대의 동시성이 1이면 2대로 늘려도 `1.0 × 2` 이지 2배가 곱해지지 않는다. **슬롯 분리가 선행돼야 LB 가 제 값을 한다.**

### 소유 분할 (확정)

| 대상 | 소유 |
|---|---|
| `INFRA-001` (「미해결」 3지선다 → ②확정 서술) | **LB CO** |
| `API-113`·`API-119`·`API-120`·`API-121` (선택 헤더 `X-Workload`) | **이 CO** — 클라이언트 LB 는 ai-server API 계약을 바꾸지 않는다 (LB CO 잠정 판단, 설계 확정 시 목록 재확인) |
| ai-server `app/` | **이 CO** |
| `common/client/AiServerClient` · `common/config/WebClientConfig` | **이 CO 선점** — LB CO 는 이 머지 뒤에 얹는다 |
| `common/config/Resilience4jConfig` (서킷 용도별 분리) | **LB CO** — §6 의 외부 의존 |
| `AiServerHealthIndicator` · `IntegrationEndpoint*` · 노드 목록 설정 | **LB CO** |

`API-122`(`/infer/vlm/verify-objects`)는 양쪽 범위 밖 — mock 전용이라 GPU 부하가 없다. LB 가중치 계산에서 GPU 부하로 세지 않기로 합의.

### 이 CO 의 실측이 LB 설계를 바꾼 것 (회수 기록)

- **"동시 요청에도 VRAM +0 MiB — 포화가 메모리로 안 드러나고 지연으로만 드러난다"** → LB CO 의 `AiServerHealthIndicator` 가 `/health` 만 보고 있어 **포화된 장비를 계속 정상 판정**한다는 것이 드러났다. 지연 기반 판정·큐 깊이 노출이 LB 설계에 들어간다.
- **워커 1→2 가 +56% 에 그친다(GPU 병목)** → 한 노드 처리량이 부하에 비례하지 않고 일찍 꺾인다. 비식별화까지 도는 1번 장비는 더 이르다. 정적 가중치로 맞추기 어려운 형태라 실시간 큐 깊이가 정적 가중보다 나을 수 있다(LB CO 판단 사항).

## §11 범위 변경 — 백엔드 서킷 용도별 분리를 이 CO 로 이관 (2026-09-01, `lb-test` 피어 합의)

§6 에 "외부 의존(LB CO 소유)"로 적었던 **서킷브레이커 용도별 분리가 이 CO 소유로 넘어왔다.**

**근거** — ①LB·장비 대수와 무관하게 성립하는 결함이라 LB 설계 확정을 기다릴 이유가 없다(1대여도 배치가 인터랙티브를 30초 죽인다) ②사용자가 「슬롯 분리 먼저」로 순서를 정했고 LB 는 이제 설계 탐색 착수 단계라 대기가 짧지 않다 ③**슬롯 분리와 서킷 분리는 짝**이라 따로 하면 각자 반쪽만 검증된다.

⚠ **이것은 범위 확장이다.** 원래 CO 는 ai-server 내부 슬롯 + 배치 표시였고, 여기에 백엔드 Resilience4j 축이 더해진다.

### 추가 대상 — 공유기반 (메인 직접, Phase 3.5)

- **대상 파일**: `common/config/Resilience4jConfig.java:18-20` · `application.yml:780`(`ai:` 서킷 설정)
- **현상**: `registry.circuitBreaker("ai")` **단일 인스턴스**를 `AiServerClient` 의 5개 호출이 공유(실패율 50% / open 30초).
- **변경**: 서킷을 **용도별로** 가른다. 가르는 축은 **호출 지점의 용도**(컴파일 타임)이며 **서킷은 `X-Workload` 헤더를 읽지 않는다**(백엔드가 이미 안다).

### ★ 서킷 이름 규약 — LB CO 가 노드 축을 얹을 자리를 비워 둔다

최종 형상은 **용도 × 노드 2축**이다. 이 CO 가 용도 축을 넣고, LB CO 가 그 위에 노드 축을 얹는다(한 장비 장애가 다른 장비를 차단하면 안 되므로).

```
이 CO      ai-batch · ai-interactive
LB CO 이후  ai-batch-{nodeId} · ai-interactive-{nodeId}
```

- **이름 조립은 헬퍼 한 곳에서만** 한다 — 문자열을 호출부마다 이어붙이면 두 축이 붙는 순간 표기가 갈린다.
- ⚠ **`nodeId` 는 `[a-z0-9]+` 로 제한**해야 한다. 구분자가 하이픈인데 `nodeId` 에 하이픈이 들어가면 `ai-batch-gpu-01` 이 어디서 갈리는지 **파싱으로 복원되지 않는다**. 이름을 되읽는 코드(메트릭 라벨·대시보드)가 조용히 어긋난다.
- `application.yml` 은 `configs.default` 에 공통값을 두고 인스턴스별로 덮어쓴다 — 인스턴스가 `2 × N` 으로 늘어나므로 값을 복제하지 않는다.
- ⚠ **`vlm-verify`(API-122) 는 이 축이 아니다** — mock 전용이라 GPU 부하가 없다. 배치·인터랙티브 어느 쪽으로도 묶지 말고 별도로 두거나 기존 `ai` 를 유지한다.

### 수용기준 (추가)

- 배치 호출이 연속 실패해 배치 서킷이 open 된 상태에서 **인터랙티브 호출이 정상 통과**한다(그 반대도 성립).
- 서킷 이름이 헬퍼 1곳에서만 조립된다(문자열 리터럴 이어붙이기 0건).

## §12 전제 — 이 CO 의 실측값이 유효한 범위 (2026-09-01)

**실측 268.9ms 는 「ai-server 프로세스가 GPU 를 혼자 쓸 때」의 값이다.**

`INFRA-001` 과 사용자 확정에 따르면 같은 GPU 장비에 다른 프로세스가 함께 온다. 장비 구성이 **비대칭**인 것도 확정됐다:

| | 장비 A | 장비 B |
|---|---|---|
| ai-server | ✅ | ✅ |
| 시계열(외부 VLM 벤더 · 별도 프로세스) | ✅ | ✅ |
| 비식별(KPST) | ✅ | ❌ |
| 증강(생성형 AI) | ❌ | ✅ |

> ⚠ **2026-09-01 정정** — 직전 판에 *"비식별·증강이 **둘 다** 장비 1 에"* 로 적혀 있었다. 사용자 원문
> *"비식별이랑 증강은 한대씩만 들어갈거래"* 를 「합쳐서 한 대」로 오독한 것을 LB CO 가 사용자
> 재확인으로 정정했다(*"증강이랑 비식별이 1에 다들어가진않을거고 따로 들어가겠지"*). **「각각 한 대씩
> 따로」** 가 맞다. 어느 쪽이 A 인지는 미정이며 아래 이유로 **정할 필요도 없다.**

⇒ **이 CO 의 슬롯 분리는 ai-server 프로세스 안만 다스린다.** 이웃 프로세스와의 GPU 경합은 막지 못한다 — ai-server 가 통제할 수 있는 축이 아니다.

**따라서 이웃이 붙은 뒤 268.9ms 가 커질 수 있다. 그것은 이 CO 의 결함이 아니다.** 슬롯 분리가 보장하는 것은 *"배치 큐가 아무리 길어도 인터랙티브가 그 뒤에 줄서지 않는다"* 이지 절대 지연값이 아니다. 개선의 본질은 **21.9초 → 0.27초** 라는 자릿수 변화이며, 이웃 경합으로 0.27이 0.4가 되더라도 그 성질은 유지된다.

⚠ 운영에서 지연이 커지면 **먼저 이웃 프로세스 부하를 확인**할 것. **두 장비 다 무거운 이웃을 하나씩 가지므로 어느 한쪽만 의심하지 말 것** — 어느 쪽이 무거운지는 시간대에 따라 뒤바뀐다:

- **비식별**은 영상 적재 직후 파이프라인 **선두에 몰린다**(적재가 몰리는 시간대에 그 장비가 무겁다).
- **증강**은 검수자가 요청할 때만 돈다(요청이 없으면 그 장비가 한가하다).

⇒ **정적 가중치로는 못 맞춘다.** 이 사실이 LB CO 의 분산 정책을 「정적 가중」에서 **「실시간 큐 깊이 판정」**으로 확정시켰고, 그래서 §13 의 큐 노출이 *"있으면 좋은 것"* 이 아니라 **LB 설계가 성립하기 위한 전제**가 됐다.

⚠ **구 서술 폐기** — *"특히 장비 1(비식별·증강까지 도는 쪽)이 먼저 포화된다"*. 그 전제로 보면 **엉뚱한 장비만 들여다보게 된다.**

## §13 범위 추가 — 슬롯 부하 노출 (2026-09-01)

> ⚠ **출처: `lb-test` 피어가 사용자에게 물어 받은 답을 전달한 것**이다(같은 사용자, 중복 질문 방지로 소비자 쪽이 물었다). 이 CO 의 사용자에게도 확인을 올렸다.

§6 「미결」로 올렸던 **슬롯별 큐 깊이·대기 시간 노출**이 **이번 CO 에 포함**으로 확정됐다. 판단 근거는 이 CO 의 실측이었다 — *"슬롯 분리 후엔 큐 120건에서도 max 293.9ms 라 지연으로는 포화를 못 읽는다"* + *"지금 안 넣으면 LB 착수 때 ai-server 를 두 번 고치게 된다"*.

### 노출할 것

슬롯마다 **①대기 건수 ②가장 오래 기다린 건의 대기 시간** 2개. 형태는 이 CO 가 정한다.

### 설계 제약

- **`/health` 에 얹지 않는다 — 별도 경로.** "살아있는가"와 "여유가 있는가"를 한 값에 섞으면, 포화를 이유로 헬스가 내려가 LB 가 **살아있는 노드를 이탈시키고** 남은 한 대에 전부 몰린다. 페일오버 사고를 스스로 만드는 셈이다. (`/health` 는 `{"status":"ok"}` 상수 그대로 둔다.)
- ★**이 경로 자체가 슬롯을 거치면 안 된다.** 슬롯 뒤에 두면 포화 시 이 응답도 함께 늦어져 **정확히 필요한 순간에 못 읽는다.** 이벤트 루프에서 바로 답해야 한다.
- 값 읽기는 **O(1)** 이어야 한다(큐를 순회하지 않는다). 대기 건수는 큐 크기로 바로 나오고, 최장 대기 시간은 **제출 시각을 태스크에 실어** 큐 머리 것만 본다.
- 대기 건수는 **근사값이어도 된다**(경합 중 정확한 스냅샷을 만들려고 잠그지 않는다 — 잠그면 이 관측이 슬롯을 방해한다). LB 는 추세를 읽지 정확한 정수를 쓰지 않는다.
- **인증 없음**(ai-server 는 상태·인증이 없는 것이 원칙) 대신 **내부망 전용 경로**로 둔다. 라벨 내용·경로·PII 를 절대 싣지 않는다 — 숫자 2개씩만.

### 수용기준

- 배치 슬롯 큐가 포화된 상태에서 부하 경로가 **100ms 이내** 응답한다(슬롯을 안 거친다는 증거).
- 배치 120건 투입 시 대기 건수가 실제로 증가하고, 소진되면 0 으로 돌아온다.
- `/health` 응답 본문이 **변경되지 않았다**(기존 계약 보존).

**하이픈 금지 — `[a-z0-9]+`.** 구분자를 바꾸는 대신 값을 제한하는 쪽으로 정해졌다.


⇒ 이 CO 는 **용도 축 헬퍼 1개**만 만든다. LB CO 가 **그 헬퍼에 노드 인자를 추가**하는 형태로 얹는다(새 헬퍼를 따로 만들지 않기로 합의).

## §15 이 CO 의 수치를 다른 축에 전용하지 말 것

`5.2 → 8.1 req/s` · `+56%` · `268.9ms` · `1,567 MiB` 는 전부 **ai-server(YOLOX/SAM2) 동기 추론** 기준이다.

**외부 VLM 벤더 시계열(축 B)에 그대로 옮기면 안 된다** — 부하의 성질이 다르다:

- `VlmTimeseriesStep` 은 `.block()` 이 아니라 `subscribe()` 로 **제출만 개시**하고 즉시 반환한다. 스텝이 확정적으로 말하는 사실은 "제출을 개시했다" 뿐이다.
- 결과는 **콜백**(`POST /v1/vlm/callback`)으로 별도로 오고, 벤더 분석은 영상 길이에 따라 **수십 분** 걸린다(콜백 창 기본 360분).
- ⇒ **요청 수·응답 지연으로는 축 B 부하가 전혀 안 읽힌다.** 제출은 항상 빠르고, 그 노드가 몇 건을 물고 있는지는 응답에 나타나지 않는다. **위탁 중 건수(원장 `ISSUED`/`ACCEPTED`)가 실제 부하에 가깝다.**

⇒ **부하 판정 수단이 축마다 다르다** — 축 A(ai-server)는 슬롯 큐를 노출받고(§13), 축 B 는 우리 원장을 센다(노드에 물어볼 필요가 없다). LB CO 가 이 비대칭을 설계에 반영한다.

## §16 관측 항목 — 트래커 캐시 회전 (지금 고치지 않는다)

`ai-server/app/models/yolox_loader.py:61-62` 가 ByteTrack 트래커 캐시를 **LRU 10개 + TTL 5분**으로 둔다.

```python
_MAX_TRACKERS: int = 10
_TRACKER_TTL_SEC: float = 300.0
```

두 축의 clipId 수명이 다르다:

| 축 | clipId | 수명 |
|---|---|---|
| 배치 `YoloAutolabelStep:325` | `String.valueOf(rawSn)` | 영상 단위 — 배치 실행에 걸쳐 유지 |
| 인터랙티브 `YoloTrackService:129` | `rawSn + ":" + UUID` | **요청 1건** — 요청마다 새로 생긴다 |

⇒ 인터랙티브 요청이 몰리면 새 clipId 가 계속 캐시에 들어와 **10개 상한에서 배치 트래커를 밀어낼 수 있다.** 밀려나면 다음 프레임에서 `frameIndex` 리셋과 무관하게 **track_id 가 새로 매겨진다.**

⚠ **이 CO 가 이 축을 악화시킬 수 있다** — 지금은 요청이 직렬화돼 캐시 회전이 느리지만, 슬롯을 나누면 배치와 인터랙티브가 **진짜로 동시에** 들어와 회전이 빨라진다.

**그러나 지금 고치지 않는다.** 근거 없이 상한을 올리는 것은 **회전이 실제로 일어나는지도 모르는 채 동작을 바꾸는 것**이기 때문이다. 구현 후 **실측으로 회전율을 관측**하고, 배치 트래커가 실제로 밀려나는지 확인한 뒤 판단한다.

⚠ **판단 근거를 「메모리 예산」으로 적지 말 것** — 이 캐시는 **가속기 메모리를 쓰지 않는다.** ByteTrack 은 칼만 필터 + IoU 매칭이라 상태가 전부 호스트 메모리에 있고 그 크기도 작다. 상한을 올리는 비용은 사실상 메모리가 아니라 **동작 변경**이다. (구 서술 *"근거 없이 상한만 올리면 메모리 예산만 흔든다"* 는 부정확해 폐기했다.)

⇒ **관측 항목**: 배치 슬롯이 연속 가동되는 동안 인터랙티브 트랙 요청을 반복 투입해, 배치 track_id 가 중간에 갈리는지 확인한다. 갈리면 상한 조정 또는 **슬롯별 캐시 분리**를 별건으로 올린다.

★**이 측정은 LB 도입 *전*(단일 노드)에 한다 — 그것이 보수적인 조건이다.** LB 가 들어오면 인터랙티브 요청이 두 노드로 갈려 **노드당 캐시 압력이 대략 절반**이 되므로 값이 더 낙관적으로 나온다. 단일 노드에서 통과하면 LB 이후에도 통과하지만, **그 역은 성립하지 않는다** — LB 이후 값으로 판정하면 페일오버로 한 노드에 몰릴 때를 놓친다.

⚠ 배치는 clip 고정으로 **한 노드에 묶이는데** 인터랙티브는 부하 기반으로 갈리므로, **배치가 묶인 노드에 인터랙티브가 몰리는 조합**이 최악이다. 그것이 곧 단일 노드 조건과 같다.

### ★ 실측 결과는 LB CO 에 반드시 회신한다 (외부 의존)

LB CO 의 결정서가 **「남는 노출은 배치가 자기 항목을 갱신하지 않는 구간뿐」** 이라는 문장을 갖고 있고, **그 문장이 이 관측 숫자에 걸려 있다.** 회전이 실제로 일어나면 그쪽 문장을 손봐야 한다.

⇒ **재고 나서 알리지 않으면 그쪽 문서가 근거 없이 서 있게 된다.** 측정 완료 시 결과를 전달하는 것까지가 이 항목의 완료 조건이다.

### 보강 — 완충은 배정 방식이 아니라 축출 규칙에서 나온다 (2026-09-01 실측)

`_TRACKERS` 는 모듈 수준이고 **키가 `clip_id` 하나뿐이라 슬롯 축이 없다** — 두 슬롯이 하나를 공유하고 상한 10 은 합계다. **그러나 배치 추적기는 화면 요청이 몰려도 밀려나지 않는다:**

| | 배치 | 화면 |
|---|---|---|
| `clip_id` | 영상 단위 — 처리 내내 **같은 키** | **요청마다 새 키** |
| 접근 | **프레임마다** `move_to_end` | 요청 하나 동안만 |
| LRU 위치 | 사실상 **항상 최신** | 쌓이며 **자기들끼리 먼저 축출** |

축출은 `popitem(last=False)`(가장 오래 안 쓴 것)이라 매 프레임 갱신되는 배치 항목이 대상이 되지 않는다. 그리고 **화면 항목이 축출되는 것은 무해하다** — 그 추적기는 HTTP 호출 하나만 살면 되고 다음 요청은 어차피 새로 만든다.

⇒ **완충은 실재하되 배정 방식과 무관한 층(축출 규칙)에 있다.** 남는 노출은 **배치가 자기 항목을 갱신하지 않는 구간뿐**이다 — ①유휴가 TTL 300초를 넘길 때 ②프레임 사이 공백에 다른 clip 이 상한 10 만큼 회전할 때.

### 함께 기록 — clip 고정이 보장하지 않는 것 (LB CO 에 전달함)

트래커 상태는 **그 노드 프로세스 메모리**에 있다. 따라서 LB 가 clip 을 노드에 아무리 잘 고정해도:

- 배치가 **5분 넘게 쉬면** TTL 로 만료되어 track_id 가 새로 매겨진다
- **노드가 재기동되면** 트래커가 통째로 사라진다

⇒ **clip 고정이 보장하는 것은 "같은 노드로 간다"이지 "트래커가 살아 있다"가 아니다.** 이 구분을 모르면 track_id 가 갈렸을 때 **LB 배정 결함으로 오진**하게 된다(실제로는 TTL 만료이거나 재기동).

## §17 측정 장비 ≠ 배포 장비 (2026-09-01)

**이 CO 의 모든 수치는 검증 장비 Tesla T4 실측이고, 배포 대상 가속기는 다르다.**

- 검증: cudo_246 Tesla T4 (15,360 MiB · 드라이버 550.163.01 · CUDA 12.4)
- 배포: `INFRA-003` 이 **H100 NVL ×2** 로 규정 (LB CO 가 확인)

✅ **사용자 확정 (2026-09-01, LB CO 경유)** — *"H100 이 운영 · T4 는 개발검증"*. 즉 두 장비의 역할 구분이
추정이 아니라 확정이다.

⚠ **이것은 착오가 아니라 인계 시점의 확정 제약이다** — *"H100 없음 — 검증은 cudo_246 의 Tesla T4 로 한다"*. 즉 **H100 을 우리가 측정할 수 없어서** T4 로 잰 것이지, T4 를 배포 대상으로 오인한 것이 아니다.

⇒ **T4 실측은 보수적 하한으로서 유효하다.** 더 느린 장비에서 성립하면 더 빠른 장비에서도 성립한다.

### 무엇이 달라지고 무엇이 그대로인가

| | 배포 환경에서 |
|---|---|
| 절대 지연값(268.9 / 141.2 / 58.6 / 161.0 ms) | **달라진다** — 더 빨라질 것 |
| 처리량(5.2 → 8.1 req/s) | **달라진다** |
| VRAM 피크 1,567 MiB | **달라진다** — CUDA 컨텍스트가 커서 1.75~1.95 GiB 로 **추정**(실측 아님). 다만 H100 NVL 은 메모리가 훨씬 커서 예산 압박이 사라진다 |
| **「배치 큐가 길어도 인터랙티브가 그 뒤에 줄서지 않는다」** | **그대로다** — 이 성질은 가속기 성능이 아니라 **대기 구조**에서 나온다. 오히려 빠를수록 잘 지켜진다 |
| 불변식 3가지(SAM2 분리·트래커 clipId·슬롯 1) | **그대로다** — 전부 상태 공유의 문제이지 성능 문제가 아니다 |
| ORT 세션 공유 안전성 | **그대로다** — 스레드 안전성은 장비 사양과 무관 |

⇒ **수용기준 중 절대값에 묶인 것은 배포 환경에서 재확인한다**(부하 경로 100ms 이내 · 인터랙티브 1초 이내). 구조에 묶인 것(슬롯이 서로 안 막는가 · 마스크가 단독 실행과 같은가 · 서킷이 용도별로 갈리는가)은 T4 결과로 확정된다.

## §18 배포 창 주의 — LB CO 의 마이그레이션과 순서가 겹친다 (2026-09-01)

**이 CO 는 마이그레이션을 하나도 추가하지 않는다.** 그러나 **LB CO(`lb-test`)의 `V24` 는 하위호환이 아니다** — 부모 테이블에서 컬럼을 지우므로 **구 jar 가 기동 검증에서 죽는다.**

⇒ 파일 교집합은 0 이지만 **같은 배포 창에 들어가면 순서가 얽힌다:**

- `V24` 는 **롤링 재기동이 성립하지 않는다.** 전 노드를 교체한 뒤 적용하는 순서가 필요하다(그쪽 마이그레이션 헤더에 명시돼 있다).
- 이 CO 는 스키마를 안 건드리므로 **단독으로는 롤링이 가능**하다. 두 변경을 한 창에 묶으면 그 성질을 잃는다.

⇒ **가능하면 배포 창을 나눈다.** 묶어야 하면 `V24` 의 제약이 창 전체를 지배한다는 것을 배포 절차에 명시할 것.

## §19 계약 보강 — `API-224` 의 필수 필드 (2026-09-01)

LB CO 의 독립 QA 가 **자기 부하 파서에서** 결함을 하나 잡았다: 슬롯 객체는 왔는데 `running` 만 없으면 **0 으로 채워 원장에 확정**하고 있었다. 그러면 그 장비가 **「가장 한가한 노드」가 되어 요청을 빨아들인다.**

**그 빈틈의 절반은 우리 쪽에 있었다** — `API-224` v1 이 슬롯 안쪽 속성을 나열만 하고 **`required` 를 적지 않았다.** 즉 값 하나가 빠진 응답도 규격을 어기지 않는 것으로 읽혔고, **소비자가 fail-closed 할 근거가 규격에 없었다.**

⇒ `API-224` v2 로 세 곳에 `required` 를 못박았다:
- `slots` → `[batch, interactive]`
- `slots.batch` · `slots.interactive` → `[running, queued, oldest_wait_ms]`

⚠ **우리 구현은 처음부터 세 값을 다 보낸다** — 실무상 안 터진다. 문제는 **롤아웃 중 부분 구현**이나 다음 사람이 필드를 하나 빼는 경우이며, 그때 규격이 「빠져도 된다」로 읽히면 안 된다.

> **같은 계열의 결함이 이번 라운드에 셋 나왔다** — ①헤더 배선을 지키는 시험 부재 ②`started[]` 가드를 지키는 시험 부재 ③필수 여부를 적지 않은 응답 규격. 전부 **「동작은 맞는데 그 동작을 지키는 것이 없다」** 형태다. 양쪽이 각각은 맞는데 **이어지는 지점만 무방비**인 것이 이 저장소의 반복 패턴이다.
