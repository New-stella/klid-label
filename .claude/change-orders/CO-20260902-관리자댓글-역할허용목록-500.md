## §1 배경

관리자(ADMIN)가 검수 화면에서 이슈(반려/문의) 스레드에 **댓글을 달면 500 이 난다.**

근본 원인은 **한 층만 뒤처진 역할 허용목록**이다. `ADR-055`(2026-08-28)로 관리자 역할이 신설되고
`ROLE_ADMIN > ROLE_REVIEWER` 계층이 들어오면서 관리자가 검수자용 창구를 그대로 통과하게 됐는데,
댓글 테이블의 CHECK 제약만 옛 2종(`WORKER`/`REVIEWER`)으로 남아 저장 시점에 제약 위반이 터진다.

**나머지 층은 전부 이미 관리자를 전제하고 있다** — 그래서 이건 "새 기능"이 아니라 **뒤처진 한 층을 맞추는 일**이다.

| 층 | 상태 | 근거 |
|---|---|---|
| 창구 인가 | ✅ 통과 | `IssueController:96-97` `hasAnyRole('WORKER','REVIEWER')` + `Role.INHERITS = Map.of(ADMIN, Set.of(REVIEWER))` |
| 서비스 | ✅ 전제됨 | `IssueThreadService:97` 주석 *"actor.role() 은 위 분기에서 WORKER/REVIEWER/**ADMIN** 으로 좁혀져 non-null 이며"* |
| 프론트 라벨 | ✅ 지원 | `frontend/src/features/review/issueLabels.ts` 의 `ISSUE_AUTHOR_ROLE_LABEL` 에 `ADMIN: '관리자'` (주석까지 *"관리자도 문의·댓글을 쓴다"*) |
| 시험 의도 | ✅ 존재 | `IssueThreadRoleHierarchyTest.adminCommentAnswersOpenInquiry` 가 `authorRoleCd == "ADMIN"` 을 단언 |
| **DB CHECK** | ❌ **2종** | `schema.sql:1180` `ck_ls_issue_comment_role CHECK (author_role_cd IN ('WORKER','REVIEWER'))` |
| **ERD-023** | ✅ v11 에서 해소 | `AUTHOR_ROLE_CD.code_values` 에 `ADMIN` 추가 (이 CO 착수 전 선반영) |

### ★ 왜 시험이 있는데도 살아남았나 (재발 방지의 핵심)

`IssueThreadRoleHierarchyTest.adminCommentAnswersOpenInquiry` 는 **바로 이 시나리오를 이미 검증한다.**
관리자로 댓글을 달고 저장된 작성자 역할이 `ADMIN` 인지까지 단언한다. 그런데 그 시험은 **순수 Mockito**
(`mock(IssueCommentRepository.class)`)라 **DB 에 닿지 않는다** — 그래서 CHECK 제약이 **한 번도 실행되지 않았다.**

⇒ 이 CO 의 회귀 가드는 반드시 **DB 를 실제로 태우는 시험**이어야 한다. mock 기반 시험을 하나 더 늘리는
것으로 대체하면 **같은 방식으로 또 통과한다.**

## §2 변경 요지

- `ck_ls_issue_comment_role` 의 허용값을 `('WORKER','REVIEWER')` → **`('ADMIN','WORKER','REVIEWER')`** 로 넓힌다.
- 신규 Flyway 마이그레이션 **`V27`** + 온프렘 `deploy/onprem/db/schema.sql` 동시 반영.
- DB 를 실제로 태우는 회귀 가드를 추가해 **관리자 댓글이 영속되는지**를 확인한다.
- **인가는 건드리지 않는다** — 관리자가 댓글을 다는 것은 막아야 할 동작이 아니라 정상 동작이다.

## §4 영향·리스크

- **하위호환**: CHECK 제약을 **넓히기만** 하므로 기존 데이터·기존 호출자에 영향 없다. 저장돼 있던
  `WORKER`/`REVIEWER` 행은 그대로 유효하다. 관제 계약면(데이터마트 뷰 4종)에 이 컬럼은 노출되지 않는다.
- **되돌리기**: `V27` 을 역으로 적용(제약을 2종으로 재생성)하면 된다. 단 그 사이 저장된 `ADMIN` 행이 있으면
  재생성이 실패하므로, 롤백 전 해당 행 처리 여부를 먼저 판단해야 한다.
- **리스크**
  - `schema.sql` 을 빠뜨리면 **신규 온프렘 설치에서만 재발**한다(dev/stg 에서는 드러나지 않는 조용한 파손).
  - 회귀 가드를 mock 으로 만들면 **같은 결함이 같은 방식으로 다시 통과**한다.
