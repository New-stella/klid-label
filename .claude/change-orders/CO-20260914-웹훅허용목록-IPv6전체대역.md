## §1 배경

- 2026-09-14 사용자 확정: 외부에서 들어오는 콜백 허용 대역은 인프라 방화벽이 막으므로 앱에서는 전면 개방한다(커밋 `4ea6bb15e` — 설치 템플릿 두 창구 `0.0.0.0/0`).
- 그런데 증강 콜백 허용 목록 클래스 주석(`GenAiWebhookIpAllowlist` 29행)은 전면 허용 예시로 **`0.0.0.0/0,::/0`** 을 권한다.
- 값 검사기 `WebhookCidrParser.isIpv6Literal` 은 마지막 판정이 `groups > 0 && groups <= 8` 이라, `::` 만으로 된 주소(16진 그룹 0개)를 **IP 리터럴이 아니라고 거부**한다. 거부는 `BeanInitializationException` 이므로 **`::/0` 을 넣으면 기동이 막힌다**(코드 확인. 실제 기동 재현은 하지 않았다).
- 같은 검사기에는 반대 방향 결함도 있다 — 구조 검증이 느슨해 아래가 **리터럴로 통과**한다: `::` 가 두 번 나오는 `1::2::3`, 콜론 하나로 시작·끝나는 `:1`·`1:`, `::` 없이 그룹이 8개 미만인 `1:2:3`, IPv4 꼬리가 마지막이 아닌 `::1.2.3.4:5`. 통과한 값은 `IpAddressMatcher` 생성에서 예외가 나 결국 거부되긴 하지만(설정값 경로), 요청 경로의 `ClientIpResolver.isValidIp` 는 이 판정만 믿고 `IpAddressMatcher.matches` 로 넘긴다.
- 그래서 설치 템플릿에 「`::/0` 은 쓰지 말 것 — 기동을 막는다」는 경고를 남겨 두었다. 사용자는 주석만 고치는 안 대신 **검사기가 `::/0` 을 받게 고치는 안**을 골랐다.

## §2 변경 요지

1. `WebhookCidrParser` 의 IPv6 리터럴 판정을 RFC 4291 §2.2 텍스트 표기 규칙대로 정확히 한다 — `::` 압축(그룹 0개 포함)은 받고, `::` 2회 이상·콜론 하나로 시작/끝·압축 없는 그룹 수 불일치·IPv4 꼬리 위치 오류·5자리 이상 그룹은 거부한다.
2. 호스트명 금지·DNS 조회 금지 원칙은 그대로 둔다(판정은 문자열 구조만으로 끝낸다).
3. `::/0` 이 모든 IPv6 원격 주소와 매칭되는지, IPv4-매핑 IPv6 원격 주소(`::ffff:a.b.c.d`)가 어느 대역과 매칭되는지 시험으로 고정한다.
4. 두 허용 목록 클래스 주석·설치 템플릿 경고·설치 문서를 실제 동작에 맞게 고친다.

## §3 도메인별 변경 상세

### 공유기반 `common/security/webhook/` — `klid-d016-implementer`

> `common/` 은 도메인 소속이 아니나, 이 패키지의 소비자는 콜백 수신 게이트(DOMAIN-016 `webhook/`·DOMAIN-007 증강 콜백·DOMAIN-003/011 시계열 콜백)뿐이고 스키마·시그니처 변경이 없어 단일 에이전트에 맡긴다.

- **대상 파일·심볼**
  - `backend/src/main/java/kr/co/cudo/authoring/common/security/webhook/WebhookCidrParser.java` — `isIpLiteral` · `isIpv6Literal`(private) · `compile`(주소 폭 판정 `address.indexOf(':')` 은 유지)
  - `.../GenAiWebhookIpAllowlist.java` 클래스 주석(28~30행) · `.../WebhookIpAllowlist.java` 클래스 주석(전면 허용 표기가 있으면)
  - 신규 시험 `backend/src/test/java/kr/co/cudo/authoring/common/security/webhook/WebhookCidrParserTest.java` (현재 이 파서 전용 시험이 없다)
  - 필요 시 `GenAiWebhookIpAllowlistTest.java` 에 `::/0` 매칭 시험 추가
- **변경**
  1. IPv6 판정 규칙(모두 만족해야 리터럴):
     - 길이 ≤ 45, 영역 식별자(`%eth0`)는 받지 않는다(현행과 같음 — 받게 하면 매처 동작이 달라진다).
     - `::` 는 0회 또는 1회. `:::` 는 거부.
     - `::` 로 시작/끝나는 경우를 빼면 단일 콜론으로 시작·끝나면 거부(`:1`, `1:`).
     - IPv4 점4분 꼬리는 **마지막 그룹에만** 허용하며 16비트 그룹 2개로 센다.
     - 16진 그룹은 1~4자.
     - `::` 가 없으면 그룹 수(IPv4 꼬리는 2)가 **정확히 8**, 있으면 **7 이하**(0 포함 — `::` 단독 허용).
  2. 판정은 문자열 구조만으로 한다. `InetAddress.getByName` 을 판정에 쓰지 않는다(요청 경로 DNS 조회 차단 L-3 · 호스트명 금지 원칙). 표준 라이브러리 리터럴 전용 경로(예: `sun.net.util.IPAddressUtil`)는 내부 API 라 쓰지 않는다. 외부 라이브러리 추가 금지.
  3. 거부 메시지 형식·`parseStrict` 시그니처·`none` 의미는 바꾸지 않는다.
- **불변(건드리면 안 되는 것)**
  - 형식 오류는 프로파일과 무관하게 **기동 차단**(DEV_FIX N-4). 경고 후 버리는 방식으로 되돌리지 않는다.
  - VLM 허용 목록 「빈 값=미적용(stg/prd 기동 차단) · `none`=명시적 미적용」, 증강 허용 목록 「빈 값·`none`=전면 차단(fail-closed)」 의미 불변.
  - IPv4 판정·프리픽스 길이 상한(IPv4 32 · IPv6 128) 불변.
  - `ClientIpResolver` 의 `normalize`(대괄호·포트 제거)·신뢰 프록시 판정 흐름 불변 — 판정기가 정확해질 뿐이다.
- **주의**
  - `ClientIpResolver.isValidIp` 가 같은 판정기를 **요청마다** 부른다(XFF·remoteAddr). 이번 수정으로 `::`(미지정 주소)가 원격 주소로 들어오면 리터럴로 인정된다 — 매처가 판정하므로 보안 완화는 아니지만 시험에 명시한다.
  - IPv4-매핑 IPv6: Java `InetAddress` 는 `::ffff:10.0.0.1` 을 `Inet4Address` 로 돌려준다고 알려져 있다 — **추정이므로 시험으로 실측해 고정**하라(`0.0.0.0/0` 매칭 여부 · `::/0` 매칭 여부). 현행 동작을 바꾸지 않는다.
  - 테스트 메서드명은 한글 서술형.
- **수용기준**
  - `::`, `::/0`, `::1`, `::1/128`, `fe80::/10`, `2001:db8::/32`, `1:2:3:4:5:6:7:8`, `::ffff:192.0.2.1`, `1::` 가 `parseStrict` 를 통과한다.
  - `:::`, `1::2::3`, `:1`, `1:`, `1:2:3`, `1:2:3:4:5:6:7:8:9`, `1::2:3:4:5:6:7:8`, `12345::`, `::ffff:192.0.2.1:1`, `::g`, `fe80::1%eth0`, `::/129` 는 `BeanInitializationException` 으로 거부된다.
  - `webhook.genai.allowed-ip-cidrs=0.0.0.0/0,::/0` 로 허용 목록이 만들어지고, IPv4 원격 주소와 IPv6 원격 주소(`2001:db8::5`) 모두 허용된다.
  - `webhook.vlm.allowed-ip-cidrs` 에도 같은 값이 기동을 막지 않는다.
  - 기존 웹훅 게이트 시험(`WebhookGateInterceptorTest`·`HmacWebhookFilterTest`·`ForwardedHeadersConfigGuardTest`·`GenAiWebhookIpAllowlistTest`·`WebhookPathBypassSecurityIT`) 회귀 통과.

## §4 영향·리스크

- **하위호환**: 기존에 기동하던 설정값은 모두 계속 기동한다 — 단, 잘못된 IPv6 표기가 우연히 `IpAddressMatcher` 를 통과해 기동하던 경우가 있었다면 이제 기동이 막힌다(실제 배포 설정은 IPv4 뿐이라 해당 없음으로 판단 — 템플릿·246 설정 기준).
- **되돌리기**: 파서 1파일·시험 revert.
- **리스크**: 판정기를 느슨하게 만들면 요청 경로에서 비리터럴이 매처로 흘러 DNS 조회가 날 수 있다 → 거부 수용기준을 함께 고정해 막는다.
