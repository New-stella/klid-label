## §1 배경

포털은 저작도구 프론트를 **자기 화면에서 런타임 실행하는 Host** 다. 그 채널에서 access token 은
**Host 메모리에만** 있고 브라우저 저장소에는 없다.

지금 저작도구는 토큰을 **저장소에서 직접 읽는다.** 그러면 **Host 가 토큰을 갱신한 시점 이후로
이미 무효가 된 토큰을 붙잡는다** — 수십 분을 한 화면에 머무는 저작 화면은 그 파손을 반드시 겪는다.
포털이 **비협상 조건**으로 제시했고, `INT-013` 이 조치를 이렇게 못박았다:

> 저작도구는 같은 출처 저장소를 직접 읽던 지점을 **토큰 획득 창구 뒤로 추상화**해,
> 저장소를 쓰는 Host 와 메모리에 두는 Host 를 **분기 없이** 지원한다.

이번 작업이 정확히 그것이다.

## §2 변경 요지

**토큰을 「어디서 얻는가」를 한 곳으로 모으고, 호출부가 채널을 분기하지 않게 한다.**

- 인계 창구 어댑터를 신설한다 — 계약 이름 4종은 `INT-013` 이 정한 그대로
- 요청 인터셉터가 스토어를 직접 읽지 않고 **어댑터에 묻는다**
- 포털 채널에서는 토큰을 **브라우저 저장소에 쓰지 않는다**
- 내부(관제) 채널의 **동작은 0 변경** — 이건 리팩터링이다

## §3 도메인별 변경 상세 — 프론트엔드 (`frontend/`)

### 현재 실측 (PM 이 직접 확인)

토큰 흐름:

| 단 | 지점 | 하는 일 |
|---|---|---|
| ① 인계 | `features/auth/tokenIngress.ts` (222줄) | `localStorage['klid-jwt-token']` **읽기 전용** 인계. 전략 상수 `TOKEN_INGRESS_STRATEGIES` · 기본값 `DEFAULT_INGRESS_STRATEGY = 'localStorage'` |
| ② 보관 | `stores/useAuthStore.ts` | `setToken`/`setTokenAndClaims` 가 **`sessionStorage` 기록** + 메모리. `hydrate` 가 sessionStorage 에서 복원 |
| ③ 부착 | `lib/api/client.ts:48-52` | 요청 인터셉터가 `useAuthStore.getState().token` 을 **직접 읽어** `Authorization: Bearer` 부착 |
| ④ 401 | `lib/api/client.ts:74-88` | 헤더 없이 나간 요청 1회 재시도 → `clear()` + `redirectToUpstreamLogin()` |

### 해야 할 것

1. **인계 창구 어댑터 신설**
   계약 이름 4종을 **그대로** 쓴다 — `getAccessToken` · `refresh` · `onUnauthorized` · `notifyActivity`.
   ⚠ **이 이름은 포털이 정본으로 제시한 계약이고 Host 가 주입하는 객체의 키다.**
   개념만 맞추고 새로 짓지 말 것 — **이름이 어긋나면 실행 시점에 창구를 못 찾는다.**

2. **토큰 조달을 어댑터 경유로 전환**
   ③의 인터셉터가 `useAuthStore` 를 직접 읽지 않고 어댑터에 묻는다.
   **내부 채널의 어댑터 구현은 지금 동작 그대로**(store → sessionStorage).

3. **포털 채널에서는 저장소에 쓰지 않는다**
   Host 메모리에서 얻어 쓰고 끝낸다. ②의 sessionStorage 기록이 포털 채널에서 **일어나지 않아야 한다.**

4. **채널 판정은 기존 `isPortalEmbedChannel()` 재사용**
   `import.meta.env` 를 다시 읽어 **판정을 두 벌로 만들지 말 것.**

### 불변 (깨면 안 되는 것)

- **내부(관제) 채널 사용자에게 보이는 변화가 0** 이어야 한다
- `tokenIngress.ts` 의 기존 보안 주석을 **지우지 말 것** — `alg=none` 거부 · URL 쿼리 채널
  미사용 근거(CWE-598/CWE-200) · `authority` 를 의도적으로 읽지 않는 이유(CWE-807)
- 어댑터 상단에 **「저장소를 직접 읽으면 갱신 뒤 죽은 토큰을 잡는다」는 근거**를 남긴다 —
  다음 사람이 되돌리지 않도록

| **`backend/**`** | 이 CO 범위 밖 |

### 판단이 필요한 지점 (구현자가 정하고 근거 보고)

- **401 처리를 어떻게 가를 것인가.** `INT-013` 에 두 서술이 함께 있다 —
  ①「Host 화면을 벗어나지 않는다: 포털 채널에서는 이동하지 않고 그 자리에 안내를 그린다」
  ②「⚠ **토큰 만료로 상위 시스템 로그인 화면에 보내는 것은 그대로 둔다.** 그건 Host 도 해야 할
  일이고, 저작도구는 복귀 주소에 현재 위치를 실어 보내므로 임베드된 상태에서 오히려 정확하다.
  **이것까지 막으면 만료된 세션에 갇힌다**」
  ⇒ 두 서술은 **층이 다를 수 있다**(인가 실패 vs 토큰 만료). `INT-013` 을 직접 읽고 판정하되,
  **확신이 안 서면 401 경로는 이번에 건드리지 말고 `onUnauthorized` 창구만 만들어 두고 보고하라.**
  잘못 가르면 만료된 세션에 갇히거나 Host 문서 전체가 튄다.
- **`notifyActivity` 를 이번에 배선할지** — 창구만 열고 호출 지점은 후속으로 미뤄도 된다
- **`refresh` 의 호출 시점** — 만료 임박 판정을 넣을지, 창구만 열어 둘지

## §4 영향·리스크

- **관제 채널 회귀가 최대 리스크다.** 토큰 조달 경로를 바꾸므로 잘못하면 **전 API 가 401** 이 된다
- 포털 채널 경로는 **MF 배선(슬라이스 2) 전까지 실행되지 않아** 이번 변경으로 사용자에게 노출되지 않는다
- 공유기반·백엔드·DB 영향 없음 → 메인 세션(`deploy/onprem`·backend) 작업과 **충돌 지점 없음**

## §8 후속 — 슬라이스 2 에 반드시 동반해야 할 것 (QA 지적)

★★ **MF 배선만 켜고 창구 배선을 빠뜨리면 Host 문서 전체가 튄다.**
`registerHostTokenHandoff` 의 **프로덕션 호출자가 0건**이고 Remote 진입점 `AuthoringRemote` 는
props 를 받지 않아 **Host 가 창구를 넣어 줄 seam 자체가 없다.** 이 상태로 MF 만 켜면 fail-closed 로
전 API 가 401 → `clear()` → `redirectToUpstreamLogin()` 이 되어, `INT-013` 이 인가 축에서 막으려던
**바로 그 증상(Host 문서 이탈)이 배선 실패 시 재현**된다.

⇒ 슬라이스 2 에서 **같은 커밋에** 넣을 것:
- ① `AuthoringRemote` 가 Host 로부터 창구를 받는 seam (props 또는 Host 가 부르는 등록 함수)
- ② 그 seam → `registerHostTokenHandoff` 배선, 언마운트 시 해제
- ③ **포털 채널 claims 조달** — 저장소를 안 쓰므로 복원할 것이 없다. Host 토큰을 디코드해
  **메모리로만** 스토어에 넣는 배선이 필요하다(`setToken` 은 이미 포털 채널에서 저장소를 안 건드린다)
- ④ 「포털 채널인데 창구 미등록」을 **만료와 구분해 제자리 안내**로 처리하는 안을 설계와 함께 검토

**포털에 물어야 할 것**: Host 가 창구 객체를 **어떤 수단으로** Remote 에 넘기는가.
`INT-013` 은 계약 이름 4종만 규정하고 **주입 경로**(전역 키 / MF 노출 모듈의 props / 초기화 인자)를
정하지 않았다. 그래서 이번에 **전역 키를 발명하지 않고** 등록 함수 하나로 두었다 — 실제 수단이
정해지면 그 한 줄만 이으면 된다.

**그 밖의 QA 지적 2건 (low, 이번 범위 밖)**
- `build:portal` 산출물은 이번 변경으로 토큰 미부착이 **정상**이다(창구 미등록 → fail-closed).
  배포 회귀는 아니다 — `deploy/`·`.github/` 에 그 스크립트 참조가 0건이고 MF 배선도 없어 어디에도 올라가지 않는다.
- 포털 채널에서도 `tokenIngress` 가 여전히 localStorage 를 **읽어** claims 를 채운다(쓰기가 아니라 AC 위반은 아니다).
  내부 채널을 쓰던 브라우저로 포털에 들어오면 **가드는 통과하는데 API 는 전부 401** 이 될 수 있다.
  슬라이스 2 에서 포털 채널 인계 전략을 창구로 단일화할지 함께 판정할 것.
