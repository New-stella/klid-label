## §1 배경 (발견 경위)

`CO-20260916-선두비식별-실패-수동재시도` 의 246 실반영 검토 중 발견했다.
JBoss 경유 개발 업로드 영상(raw 44)의 비식별이 목업에서 `OUTPUT_WRITE_FAILED` 로 끝났다.

- 목업 로그: `watermark 임시 디렉터리 준비 실패 … PermissionError errno=13` → `production failed … reason=OUTPUT_WRITE_FAILED`
- 246 실측: JBoss 컨테이너는 `uid=0(root)` 로 돌고, 위탁 전에 백엔드가 만드는 산출물 디렉터리
  (`/app/storage/raw/dev-upload/44/deid`)가 `drwxr-xr-x root root` 다. 목업 컨테이너는 `uid=999(app)` 라 쓰지 못한다.
- 상위 디렉터리(`dev-upload/`)는 `drwxrwxr-x polkitd input` — 이전 도커 백엔드 시절에는 같은 계정으로 만들어져 문제가 없었던 것으로 **보인다(미확인)**.

## §2 영향

- **246**: JBoss 경유로 새로 적재·업로드되는 영상 중 백엔드가 새로 산출물 디렉터리를 만드는 경우 비식별이 전부 실패할 수 있다(관제 인입 경로도 같은 생성 코드를 탄다면 동일 — **확인 필요**).
- **현장(온프렘)**: 공유 마운트(no-copy) 모델에서 실제 KPST 가 WAS 와 **다른 계정**으로 돌면 같은 문제가 난다. 현장 WAS 계정·KPST 계정·NAS 권한(umask·그룹) 확인이 선행돼야 한다.

## §3 검토할 방향 (미확정 — 사용자 판단 필요)

1. 백엔드가 디렉터리를 만들 때 그룹 쓰기 권한을 준다(umask/`PosixFilePermissions`) — 공유 그룹 전제 필요, 권한 확대의 보안 판단 필요.
2. 배포 형상에서 해결 — WAS 실행 계정과 KPST 계정을 같은 그룹으로 두고 setgid 디렉터리·umask 002 를 운영 설정으로 둔다(코드 무변경).
3. 246 한정 — JBoss 컨테이너를 목업과 같은 uid 로 돌리거나 목업을 root 로 돌린다(개발 환경만).
