## §1 배경

`CO-022`(PR #151 → `3bcf89eb` main 머지)로 이관 대상 탐색 창구 둘(`GET /v1/imports/folders` · `/files`)을 신설했다. 246 원격 서버에 더미를 만들어 실검증했고 다섯 축 전부 PASS 였다. 그 과정에서 **후속 관측 2건**이 나왔다.

### 1-1. 잘린 목록에서 빠진 항목은 도달할 수 없다

담는 개수 상한(기본 2,000)에 걸리면 목록이 잘리는데, **상한에서 멈춘 뒤에 정렬**하므로 빠지는 자리가 이름 앞뒤를 가리지 않고 흩어진다. 246 실측(하위폴더 2,500개):

```
반환 2000건 / 누락 500건
누락 앞10: sub-00002, sub-00015, sub-00016, sub-00018, sub-00023, ...
누락 끝3 : sub-02485, sub-02486, sub-02497
```

`sub-00002` 는 빠졌는데 `sub-02499` 는 들어 있다. 화면에 페이징도 필터도 없으므로 **한 단계씩 내려가는 길만으로는 그 자리에 영영 닿을 수 없다.**

### 1-2. 읽을 수 없어 빠진 항목은 흔적이 없다

`stat` 이 실패해 항목이 목록에서 빠지면 응답이 `entries: []` 인데, **「진짜 빈 폴더」와 구분되지 않고 서버 로그에도 기록이 없다.** 246 실측(`chmod 0644` 부모 아래 3건):

```
GET /folders?path=…/perm2  → {"entries":[],"truncated":false}
docker logs klid-backend --since 3m | grep "ImportBrowse|skipped|truncated"  → 0건
```

**같은 클래스가 길이 초과 skip 에는 정확히 이 논거로 이미 카운터+WARN 을 갖고 있다.** 권한 축만 비대칭이었다.

## §2-0 ★라운드 도중 방향이 두 번 바뀐 경위 (지우지 말 것)

| 회차 | 채택 | 폐기 사유 |
|:--:|---|---|
| ① | **이름으로 찾기(`keyword`)** — 잘린 목록에서 이름으로 항목을 되찾는다 | 근거 붕괴(아래) |
| ② | **되돌리기 — 검색 없애기** | 전제 붕괴(아래) |
| ③ | **커서 페이징(`cursor`/`nextCursor`)** — 확정 | — |

**①→② 근거**: 검색의 유일한 설계 근거가 *"절단되면 빠진 항목에 도달할 수 없다"* 였는데, **실제 저장소를 측정하니 절단이 일어나지 않았다.** 246 의 허용 저장소 루트 4곳 전부에서 한 단계 최대 팬아웃이 **160건**(상한 2,000의 8%)이었다. 절단 재현에 썼던 2,500개 폴더는 **시험용으로 만든 것**이었다.

| 루트 | 1단계 하위폴더 | 최대 팬아웃(깊이 무관) |
|---|---:|---:|
| `storage/raw` | 12 | 160 |
| `storage/deidentified` | 2 | 80 |
| `nas-storage/.../upload/v2` | 14 | 14 |
| `genai-out` | 1 | 3 |

**②→③ 근거**: 위 측정은 **현재 dev 데이터**였다. 사용자가 *"오천건 정도가 있을순 있어"* 라고 지적했고, 그러면 **절단은 실제 문제**가 된다(목표 규모는 영상 5,000건이고 `frames/deid/` 는 rawSn 하나당 폴더 하나다). 이어서 *"비동기나 큐로 해서 부하가 없게 한두건씩 처리하면 되지않아? 빠르게 할 필요없어"* 라고 방향을 제시했다.

**왜 페이징이 검색보다 나은가**: 검색은 **이름을 알 때만** 도달하게 하고, 페이징은 **전부** 도달하게 한다. 절단 자체가 사라지므로 문제가 뿌리에서 없어진다.

**상한을 그냥 올리는 안은 채택하지 않았다** — 5,000건이면 `stat` 5,000회가 한 요청에 몰려 NAS 에서 초 단위로 갈 수 있고 응답 JSON 도 1MB 급이 된다. *"부하가 없게"* 라는 지시와 반대 방향이다.

**상한 자체를 없애는 안도 채택하지 않았다** — ①막는 대상이 우리 데이터가 아니라 **외부 업체 인계 폴더**라 규모를 모른다(모르는 것에 상한을 안 두면 fail-open) ②`api-design.md` 「페이징 없는 목록 전체 조회 금지」·`security.md` 「Unrestricted Resource Consumption(API4:2023)」과 충돌 ③설계가 이미 그 질문에 답해 뒀다 — `application.yml` 주석이 *"탐색은 보조 수단이라 목록이 완전하지 않아도 손으로 적는 길이 남아 있다. 다만 조용히 자르면 화면이 잘린 목록을 전부인 것으로 보여 주므로 알림은 생략할 수 없다"*.

## §2 변경 요지

1. **탐색 두 창구를 커서 페이징으로 바꾼다.** 잘라 버리는 대신 나눠서 이어 준다.
2. **읽을 수 없어 빠진 항목의 건수를 WARN 으로 남긴다.** 건수만 — 이름·경로는 남기지 않는다.

**하지 않는 것**: 상한 제거 · 이름 검색 · 응답 계약의 나머지 변경 · 하위 트리 재귀 탐색.

## §3 도메인별 변경 상세

### DOMAIN-017 (외부 산출물 이관) — `klid-d017-implementer`

> ⚠ **디스패처 매핑표 정정**: 매핑표는 이 도메인을 *"(신설 — 코드 미착수)"* 로 적고 있으나 **사실이 아니다.** 실제 code_root 는 **`transfer/`** 다.

- **대상**: `transfer/controller/ImportBrowseController.java` · `transfer/service/ImportBrowseService.java` · 시험 2종 · `application.yml`

#### R1. 커서 페이징

**`collect` 의 동작 (확정 사양)**

1. `DirectoryStream` 으로 **이름만 전부 읽는다**(stat 하지 않는다 — 값싸다). **이름 오름차순 정렬.**
2. **커서보다 큰 이름부터** 본다 — **배타(strictly greater)**. 준 그 이름은 다시 돌려주지 않는다.
3. 순서대로 **살펴본다**: 경로 길이 초과면 세고 건너뛰고, 아니면 `readAttributes(NOFOLLOW)` 로 종류를 판정해 들어맞으면 담는다.
4. **멈추는 조건 셋**: 담은 것이 `page-size` 도달 / **살펴본 것이 `scan-limit` 도달** / 이름 소진.
5. **`nextCursor`** = 마지막으로 **살펴본** 항목의 이름. **이름이 소진됐으면 `null`.**

★ **`scan-limit` 이 설계의 핵심이다.** 담는 것은 종류가 들어맞는 것뿐이라, 안 맞는 항목이 이어지면 **담을 것을 못 채운 채 계속 stat** 하게 된다(영상 파일 몇 개가 이미지 수천 장 사이에 있는 자리가 정상 형상이다). 이게 없으면 부하가 그대로 몰려 페이징을 넣은 취지가 사라진다.

★ **담은 것이 0건이어도 `nextCursor` 는 온다.** 그게 정상이다.

★ **「살펴본다」의 정의**: 커서 뒤의 항목을 하나 집어 판정하는 것. 길이 초과로 걸러지든 stat 을 하든 **모두 1건으로 센다**.

**설정** — `authoring.import.browse.max-entries` 를 대체:
- `page-size: ${IMPORT_BROWSE_PAGE_SIZE:200}`
- `scan-limit: ${IMPORT_BROWSE_SCAN_LIMIT:2000}` (기존 2000 승계)

⚠ `scan.max-entries`(적재 훑기 상한)는 **별개 축**이다. 낱말이 비슷하다고 함께 건드리면 다른 기능을 부순다(실제로 `DFEAT-056`·`SEQ-026`·두 API 문서에서 같은 함정이 각각 경고됐다).

**`cursor` 검증** — `maxLength 255`. 초과·형식 위반은 **400**, 거부 사유에 값 원문 미노출(CWE-209). **루트 목록 조회에도 같은 길이 검증을 건다**(같은 창구가 위치 유무에 따라 받아들이는 폭이 달라지면 안 된다).

#### R2. 권한 skip 관측 — **이번 철회 대상 아님, 그대로 유지**

- `stat` 실패로 빠진 항목의 **건수만** WARN. 0건이면 미기록. 기능 변경 0.
- ⚠ **경로 원문·이름 조각 금지**(CWE-117). 이 서비스가 **항목 이름을 아예 로그에 쓰지 않는** 성질이 로그 인젝션을 구조적으로 막는다(246 실측: 제어문자 이름 8종에도 로그 오염 0회).
- `readAttributes(NOFOLLOW)` 1회로 모은 구조 유지 — 그게 관측을 가능하게 한 것이다.

## §4 영향·리스크

- **계약 변경**: `truncated` → `nextCursor`(응답), `cursor` 신설(요청). **소비자가 우리 FE 하나뿐**이라 양쪽을 함께 바꾼다. 두 필드를 같이 두면 "더 있다"의 진실원이 둘이 되므로 교체를 택했다.
- **되돌리기**: 파라미터·필드·페이징 루프를 되돌리면 원상복귀.
- **리스크**
  - `nextCursor` 대신 담긴 개수로 끝을 판정하면 **폴더가 있는데 "없음"으로 보인다**(BE·FE 양쪽).
  - `scan-limit` 을 빼면 부하가 그대로 몰려 페이징의 취지가 사라진다.
  - 누적 dedup 을 빼면 재조회·연타에서 같은 항목이 두 번 쌓인다.

- **★인지·수용한 한계**: 이어받는 동안 그 폴더의 내용이 바뀔 수 있고, **이어받을 자리보다 앞선 이름**으로 생긴 항목은 이번 탐색에서 보이지 않는다. **중복이 생기는 것보다 이쪽이 안전하다** — 두 번 쌓이면 화면이 거짓을 보여주지만, 못 본 항목은 다시 열면 보이고 직접 입력하는 길도 그대로 있다.
- **★자리 번호(offset)를 쓰지 않는 이유**: 앞쪽 항목이 지워지면 뒤가 밀려 **같은 항목을 두 번 주게 된다.** 인계 폴더는 외부가 계속 쓰는 자리라 탐색 도중 파일이 늘고 주는 것이 정상이다.

## §5 검증

### ★가드 설계 — 직전 라운드가 변이로 실증해 준 것

**① 양 끝만 가드하면 가운데 단이 통째로 빠져도 통과한다.** ⇒ **인접 단끼리** 묶는다.

| 가드 | 무엇을 고정 |
|---|---|
| 컨트롤러 ↔ 서비스 | `cursor` 가 실제로 서비스 인자에 도달한다 |
| 커서 ↔ 결과 | **같은 항목이 두 번 돌아오지 않는다**(배타) |
| `scan-limit` ↔ `nextCursor` | **담은 것이 0건인데 `nextCursor` 가 온다** |
| 이어받기 ↔ 완주 | 끝까지 이어받으면 **하나도 빠짐없이, 중복 없이** 모인다 |
| 훅 ↔ HTTP | 커서가 실제 요청 파라미터에 실린다 |
| `nextCursor` ↔ 종료 판정 | 담긴 것이 0건이어도 「더 보기」가 계속 보인다 |
| 누적 ↔ 중복 | 같은 항목이 두 번 와도 한 번만 쌓인다 |

**② 가드의 제외 목록은 그 자체가 탈출구다.** 예외를 두면 **확정 명단으로 못박아 증감 시 실패**시키고 **항목마다 사유를 값으로 강제**한다. docstring 경고로는 못 막는다.

**③ ★e2e 가 중간 산출물을 하드코딩해 출발하면 앞 구간이 커버리지에서 사라진다.**
직전 라운드에 **정확히 그 일이 났다** — FE 픽스처가 「루트 목록이 잘린다」는 **서버가 만들 수 없는 상황**을 전제로 깔아서, 간판 가드(`TC-FE-1074`, Critical)가 실제로는 아무것도 지키지 못했다. **픽스처가 서버 실동작으로 가능한 상황인지 먼저 따진다.** 한계는 시험 주석·카탈로그에 **명시**한다 — 덮은 척하지 않는다.

**④ 변이 실증을 붙인다** — 가드를 빼면 실제로 RED 가 되는지 확인하고 결과를 보고한다.

### ★이 라운드에 실제로 난 사고 둘 (프로토콜이 잡았다)

1. **`mark_implementation` 쓰기에서 한글 1자 손상 + 배열 원소 1건 소실이 동시 발생** — `빔을`→`빈을`. 그 도구는 `subtasks` **배열 전체를 교체**하므로 스물몇 건을 옮겨 적는 동안 일어난다. **길이도 개수도 늘어 있어 육안으로는 「추가만 했다」로 보였다.** 쓰기 전 기준선 스냅샷 + difflib 대조로만 잡혔다.
   ⇒ **배열에 원소를 더할 때는 `patch add` 를 쓴다** — 보존 원소를 재전송하지 않아 손상 자체가 불가능하다.
2. **변이 실증 중 `git checkout -- <file>` 로 미커밋 작업이 통째로 날아갔다** — 다음 변이 스크립트의 `assert` 가 패턴 부재로 터져서야 드러났다. **안 터졌으면 엉뚱한 기준선 위에서 돈 결과를 보고할 뻔했다.** 되돌리기는 **작업본 사본(`cp`)** 으로만 한다.

### ★가장 좋았던 쓰기 방식 (다음에 재사용할 것)

`API-222` 의 마지막 문단은 **손 타이핑이 0자**다 — 짝 창구 `API-221` 의 그 문단을 **서버 바이트로 받아** 한 구절만 치환했다. 두 문단이 그 한 곳 빼고 바이트 동일이라 **손상이 들어올 자리가 없다.**

### 여전히 덮지 못하는 축 (덮은 척하지 않는다)

- **이어받는 도중 폴더 내용이 바뀌는 축** — 두 요청 사이에 다른 프로세스가 끼어들어야 해 결정적 재현 불가(설계가 인지·수용)
- **런타임 E2E 미수행** — 실제 서버를 띄워 두 계층을 태운 확인은 안 했다. 화면 시험은 여전히 axios mock 픽스처 위에 서 있어 **BE↔FE 가 같은 방향으로 함께 틀리는 결함은 원리적으로 안 잡힌다**(직전 라운드에 그게 런타임까지 갔다)
- **대형 폴더 실측** — 5,000건 규모의 이어받기 왕복 횟수·응답 시간 미측정(246 실측은 2,500건 기준)
- **`TC-FE-1087`(루트에서 「더 보기」 부재)은 계약을 못 박지 못한다** — 화면은 `nextCursor` 유무로만 판정하므로 BE 가 루트도 나눠 주기로 바뀌면 화면은 순순히 버튼을 띄운다. 그 축은 BE 시험 몫
- **`TC-FE-1085` 의 전용 QueryClient 는 현재 형상에서 판정을 가르지 않는다** — `Modal` 이 마운트를 유지해 GC 가 돌지 않기 때문. 미래 형상 변화에 대한 보험일 뿐이며 **「gcTime 함정을 막았다」고 주장할 근거는 없다**
