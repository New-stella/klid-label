## §1 배경

### 현장 장애 (2026-09-14, 현장 WAS `klid-ai-gen-was-01`)
- 관제 채널 저작도구의 세션 연장 팝업에서 「로그인 연장」을 누르면 "관제 서버에 연결할 수 없습니다" 가 뜨고 연장되지 않는다.
- 서버 로그 순서:
  1. `[ControlAccount] refresh unavailable cause=malformed-body status=404` — 3회
  2. `[ControlAccount] refresh unavailable cause=CallNotPermittedException` — 서킷 오픈
  3. `[ControlAccount] logout relay failed cause=CallNotPermittedException` — **로그아웃 중계까지 막힘**
- 사용자는 관리자 페이지 「연동 서버 주소」에서 「관제 통지 수신처」 주소를 이미 설정한 상태였다. 그 값은 `IntegrationEndpointResolver` 가 호출 시점에 읽어 정상 반영된다(코드 확인).

### 근본 원인 — 주소 하나를 서로 다른 WAS 의 두 창구가 나눠 쓴다
- 세션 중계(`ControlAccountClient` — 갱신 `POST /api/account/auth/refresh`, 로그아웃 `POST /api/account/auth/logout`)는 `WebClientConfig#controlAccountWebClient` 에서 **관제 통지 수신처 주소(`authoring.control-notify.url`)를 재사용**한다. `CO-20260910-관제향-토큰갱신-세션연장` 의 사용자 확정 「관제 통지 주소 재사용」이었다.
- 그런데 관제는 두 창구를 **서로 다른 WAS** 에 둔다. 246 관제 웹서버(`/etc/httpd/conf.d/klid.conf`) 실측:
  - `ProxyPass /api/data-set/ balancer://general-cluster` → `eap8:18080` (data-set·clip·genai·ingest·setting 등)
  - `ProxyPass /api/account/ balancer://general-cluster-2` → `eap7:28080` (account · gpkisecureweb)
- 246 에서 갱신 경로를 직접 호출한 결과:

  | 대상 | 결과 |
  |---|---|
  | 관제 웹서버(apache) 경유 | `401 {"error":900205,"message":"리프레시 토큰이 없습니다."}` — 창구 있음 |
  | eap7(계정 WAS) 직접 | 위와 같은 401 JSON |
  | **eap8(통지 WAS) 직접** | **`404` HTML 에러 페이지** — 현장 로그 `malformed-body status=404` 와 같은 모양 |

- 통지(`ControlNotifyClient`)의 경로는 `/api/data-set/v2/jobs/{jobId}/notify-completed`·`/notify-updated` 라 data-set WAS 가 받는다.
- ⇒ **주소 하나로는 WAS 에 직접 붙이는 순간 통지·세션 중 한쪽이 반드시 404** 다. 두 창구를 모두 넘겨주는 관제 웹서버 주소를 넣으면 둘 다 되지만, 사용자는 **주소를 창구별로 따로 보기로 확정**했다(2026-09-14: *"주소를 2개 따로 봐야 할것 같네"*).
- API 모양(경로·메서드·헤더·바디)은 관제 자신의 프론트 번들(`assets/js/index-*.js` 의 `REFRESH_TOKEN:"/api/account/auth/refresh"` · `x-access-token: refresh_token` · 바디 `null`)과 **일치**한다 — API 결함이 아니다.
- 참고: 246 저작도구 WAR(9/9 빌드)에는 세션 중계 코드가 없어(커밋 `944b90025` 은 9/10) 246 에서는 이 기능이 돈 적이 없다. 246 저작도구 설정은 `CONTROL_NOTIFY_URL=http://apache`(관제 웹서버)라 새 WAR 였다면 증상이 없었을 것으로 **예상**된다(실행 확인은 아님).

### 부수 결함 — 로그아웃이 갱신 실패에 끌려 막힌다
- 갱신과 로그아웃이 같은 서킷 인스턴스(`controlAccount`)를 쓴다. 갱신이 5회 이상 일시 장애로 집계되면 서킷이 열려 **로그아웃 중계도 보내지 못한다**. 브라우저 쪽 토큰 삭제·로그인 화면 이동은 진행되지만 **관제 서버 세션이 닫히지 않는다.**

### 게이트① 사용자 확정 (2026-09-14)
1. **새 주소는 독립 설정, 통지 주소로 폴백하지 않는다** — 한 설정이 다른 창구에 몰래 쓰이는 구조가 이번 사고의 원인이므로 판정 원천을 하나로 둔다.
2. **갱신·로그아웃 서킷 분리를 이번 범위에 넣는다.**

## §2 변경 요지

1. 연동 주소에 **「관제 계정 창구」** 를 신설한다 — 설정 키 `authoring.control-account.url`(환경변수 `CONTROL_ACCOUNT_URL`). 설정 칸 축(한 곳뿐이라 고를 일이 없는 축)에 앉고, 관리자 페이지 「연동 서버 주소」에서 재기동 없이 바꾼다.
2. 세션 중계(갱신·로그아웃)는 **이 주소만** 쓴다. 관제 통지 수신처 주소는 **통지만** 쓴다. 폴백 없음.
3. 새 주소가 비어 있으면 세션 중계는 **관제를 부르지 않고** 일시 장애로 끝난다(브라우저 결말은 기존 「일시 장애」 규칙 그대로). 비어 있음은 결정적 상태라 서킷 실패로 집계하지 않는다.
4. 서킷을 **갱신·로그아웃 둘로 나눈다.** 갱신 장애가 로그아웃 중계를 막지 않는다.
5. 설치 템플릿·설치 문서·CLAUDE.md·위키에서 두 주소의 용도와 「무엇을 넣어야 하는가」(관제 웹서버 또는 해당 창구를 가진 WAS)를 바로잡는다.

## §4 영향·리스크

- **하위호환**
  - 기존 배포본은 새 키가 비어 있으므로 **배포 직후 세션 연장이 동작하지 않는다**(현장·246 모두). 배포 절차에 계정 주소 설정을 **필수 단계로** 넣어야 한다 — 설치 문서·회차 매체 안내에 반영.
  - API 계약·DB 스키마 변경 없음(설정 행이 새로 생길 뿐, 시드 없음).
- **되돌리기**: 계정 주소에 관제 웹서버 주소를 넣으면 이전과 같은 결과. 코드 되돌리기는 커밋 revert.
- **리스크**
  - 배포 후 계정 주소를 비워 두면 조용히 연장 불가 — WARN 분류 문자열과 설치 문서의 필수 표기로 막는다.
  - `NFR-013` 잔여 위험(관리자가 주소를 바꾸면 사용자 세션 자격증명이 그 주소로 전송)은 **계정 주소** 축으로 옮겨 간다 — 통지 주소를 바꿔도 더 이상 자격증명이 나가지 않는다(위험 표면이 좁아진다).
