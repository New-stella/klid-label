## §1 배경 — 셋은 같은 뿌리다

| # | 경로 | 증적 원문 |
|---|---|---|
| 1 | 홈 > 관리 > **프리셋 관리** (`KLID-AT-IF-029`) | 프리셋 편집 시 라벨을 **20개 초과** 선택 후 저장 클릭 시 **저장되지도 않고 아무 반응이 없음** |
| 2 | 홈 > 관리 > **이벤트 유형 관리** | 입력 값 없이 입력 시 **서버 에러가 발생하고 에러 내용이 그대로 보임**(사용자 단에서 처리 필요) |
| 3 | 홈 > 관리 > **이벤트 유형 관리** | 입력 값 없이 입력 시 **서버 에러가 발생함**(사용자 단에서 처리 필요) |

**공통 원인**: 입력 시점 검증이 화면에서 완결되지 않는다. 그래서
①막히는데 왜 막혔는지 보이지 않거나 ②서버까지 가서 서버 문구가 그대로 나온다.

### 증적 2·3 에 실제로 노출된 문자열

```
questions[16].qstnCn: 질문 문구는 비어 있을 수 없습니다.,
questions[18].qstnCn: 질문 문구에는 개행·제어문자를 넣을 수 없습니다., …
```
```
questions[1].qstnCn: 질문 문구는 4000자 이하여야 합니다
```

⚠ **필드 경로(`questions[16].qstnCn`)가 사용자에게 그대로 보인다.** 이 저장소 보안 규칙이
*"에러 메시지에 스택트레이스·내부 경로·DB 스키마 노출 금지"* 를 규정하는 자리와 같은 축이다 —
사용자는 자기가 **몇 번째 질문의 무엇을** 고쳐야 하는지 알 수 없고, 대신 내부 구조만 본다.

### 증적 1 의 실체 — 「무반응」이 아니라 「보이지 않음」 (실측)

- 스키마에 상한 검증이 **이미 있다** — `labelIds.max(LABEL_IDS_MAX_COUNT)`, 상수 `20`.
- 그런데 저장 버튼 조건은 **`submitting || eventTypeCd === ''`** 뿐이라 **개수가 들어 있지 않다.**
  ⇒ 버튼이 눌리고, 검증은 실패하지만, **그 실패가 사용자 눈에 들어오지 않는다.**
- 화면에는 「21 / 20개 선택」과 「최대 20개」가 떠 있으나 **저장 버튼에서 먼 자리**에 작게 있다.

⚠ **「검증이 없다」가 아니라 「검증 결과가 도달하지 않는다」**이다. 고칠 자리가 다르다 —
검증을 새로 만들지 말고 **이미 있는 판정을 화면에 드러내고 버튼 조건에 넣는다.**

## §2 변경 요지

1. **막을 것은 누르기 전에 막고, 왜 막혔는지 그 자리에서 보인다.** 상한 초과면 저장 버튼을
   비활성하고 사유를 **버튼 근처**에 둔다(먼 자리의 작은 안내로 대신하지 않는다).
2. **서버 검증 메시지를 사용자에게 그대로 내보내지 않는다.** 화면이 **필드별로** 받아 그 입력칸
   옆에 사람 말로 보인다. 필드 경로·인덱스 표기를 노출하지 않는다.
3. **입력 시점에 화면이 먼저 판정한다** — 빈 값·길이 초과·개행/제어문자. 서버는 **백스톱**으로 남는다
   (서버 검증을 없애지 않는다 — 화면을 우회한 호출이 있다).

## §3 변경 상세

### 증적 1 — 프리셋 관리 (프론트)

- 저장 버튼 조건에 **상한 초과**를 넣는다. 지금은 `submitting || eventTypeCd === ''` 뿐이다.
- 초과 시 **버튼 근처에 사유**를 보인다(「최대 20개까지 선택할 수 있습니다 — 현재 21개」).
- ⚠ **선택 자체를 막을지, 선택은 두고 저장만 막을지**를 먼저 정한다. 지금 화면은 21개가 **선택된
  상태로 표시**된다(「21 / 20개 선택」). 선택을 막으면 사용자가 무엇을 빼야 할지 고를 수 없다 —
  **선택은 허용하고 저장을 막으면서 초과분을 드러내는 쪽**이 자연스럽다. 판정은 화면 사양에서.
- ⚠ **상한 값을 화면에 새로 적지 마라** — 상수(`LABEL_IDS_MAX_COUNT`)가 이미 있고 표기가 그것을
  참조한다. 문구에도 그 상수를 쓴다.

### 증적 2·3 — 이벤트 유형 관리 / 질문 목록 (프론트 + 필요 시 서버)

- **화면이 저장 전에 판정한다**: 빈 값·공백만 · 길이 상한 · 개행/제어문자.
- **오류는 그 질문 행 옆에** 보인다 — 어느 질문인지 화면이 이미 알고 있다(N번째 행).
  배너 한 줄에 전부 이어 붙이지 않는다.
- **서버 400 이 오더라도** 화면은 그 원문을 그대로 표시하지 않는다. 필드 경로를 사람이 읽는
  위치 표기로 바꾸거나, 그럴 수 없으면 **일반 안내 + 해당 행 강조**로 내린다.
- ⚠ **서버 검증을 없애지 않는다.** 화면을 우회한 호출이 있고, 길이·제어문자는 로그 인젝션·DB 오류의
  입구다. 서버는 **백스톱**으로 그대로 둔다.
- ⚠ **상한 값(4000 등)을 화면이 따로 적지 마라** — 서버 계약에서 오는 값을 쓴다. 양쪽에 적으면
  한쪽만 고쳐진다(이 저장소가 반복해 겪은 형태).

## §4 하위호환

- 서버 계약 변경 없음(응답 코드·스키마 불변). **화면 동작만 바뀐다.**
- 서버 검증은 그대로 — 화면이 먼저 막을 뿐이다.

---

## §5 범위 밖

- 다른 화면의 같은 부류 문제 전수 점검 — 이번엔 **증적 3건만** 고친다.
  ⚠ 다만 같은 뿌리가 다른 화면에도 있을 가능성이 높다. **전수 점검은 별건**으로 남긴다.
- 서버 검증 메시지 자체의 문안 개선 — 화면이 가공하므로 이번엔 건드리지 않는다.

### ★이 라운드가 드러낸 것 — 증적 3건보다 컸다

1. ★★**증적 2·3 은 구현 결함이 아니라 사양 결함이었다.** `SCREEN-038` 이 *"화면이 서버가 준 거부 사유를 그대로 보여준다"* 를 **네 곳에서 규정**하고 있었다(목적·섹션 설명·오류 알림·저장 결과 알림). **코드만 고쳤으면 다음 라운드에 사양을 근거로 되돌아왔을 건이다** — 설계를 먼저 고치는 순서가 값을 한 지점.
2. **증적 1 은 「검증 부재」가 아니라 「검증 결과 미도달」**이었다. 상한 판정은 이미 있었고 저장 가능 조건에 개수가 빠져 있었다 — 고칠 자리가 다르다.
3. **`SCREEN-038` 에 실현 사용례가 없었다**(활성 36건 전수 확인). `UC-044` 로 메웠다. ⚠ **결손은 반쪽만 닫혔다** — 이벤트유형 관리에 대응하는 **기능 층이 없어** 신설 수용기준의 도메인 귀속이 여전히 빈다(DOMAIN-014 의 기능은 시스템 설정 하나뿐). 기능 신설은 소유 도메인부터 갈려 있어(화면=영상·프레임 수집 / 코드=시스템 설정) 별개 결정이다.
4. **같은 화면의 두 절이 서로 반대였다** — 표시명 저장 직후 「행만 갱신」 vs 창구의 「목록 재조회」. **창구가 맞다**(표시명이 그룹을 가르므로 같은 그룹 다른 행 상태도 바뀐다). 사용자 확정으로 **조건 이탈 행은 사라지되 안내가 그 사실을 알린다**(붙잡아 두는 안·조건을 자동으로 푸는 안은 기각).
5. ⚠ **내가 만든 갈림 하나** — `UC-044` 를 화면 옛 판 기준으로 쓴 직후 화면을 고쳐 같은 결정이 두 층에서 갈렸다. 같은 라운드에서 닫았다. **신설과 정정을 같은 라운드에 섞으면 이 형태가 생긴다.**

### 잔여 (별건 큐)

- 정적 렌더 미러·시안(`SD-006`·`SD-023`) — 사양보다 낡음. ⚠ **미러 신선도를 해시로 확정하지 못했다** — 저장된 해시를 어떤 직렬화로도 재현하지 못해 양성 대조에 실패했다. 근거는 생성 시각뿐이다.
- 저장 성공 안내의 **실제 문구** 미확정(사양은 「그 사실을 함께 알린다」까지).
