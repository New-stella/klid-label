## §1 배경

2026-09-16 온프렘(현장) 실측 중, 비식별이 완료된 영상(rawSn 9)의 **마킹 화면에서 영상이 재생되지 않는** 문제를 진단했다. 원인이 하나가 아니라 **서로 독립된 세 가지**가 겹쳐 있었고, 하나씩 걷어내며 확인했다.

### 건 1 — 경로 접두가 두 번 붙는다

마킹 화면이 검은 화면에 `00:00 / 00:00` 으로 멈춰 있고 브라우저 콘솔에 `NotSupportedError: The element has no supported sources` 가 떴다. 네트워크를 보니 요청 주소가 이랬다.

```
https://www.aicctv.go.kr/label-studio/label-studio/api/v1/videos/9/stream?exp=...
                         ~~~~~~~~~~~~~~~~~~~~~~~~~
```

`/label-studio` 가 **두 번** 붙었고, 그 결과 응답이 영상이 아니라 `Content-Type: text/html` 1162바이트 — SPA 의 `index.html` 이었다. `<video>` 가 HTML 을 받으니 "지원하는 소스가 없다"가 된다.

원인은 **같은 값을 쓰는 세 곳이 서로 반대 규약을 기대**하는 데 있다.

| 만드는 곳 | 화면이 받아서 하는 일 | 서버가 줘야 할 형태 |
|---|---|---|
| `VideoStreamService:221` (마킹 영상) | `toDeployedApiUrl` 로 **배포 접두를 붙임** | 접두 **없이** |
| `PortalUploadStreamService:102` (포털 업로드 영상) | 〃 | 〃 |
| `ReviewService:538` (프레임 이미지 `imageUrl`) | **가공 없이 그대로** `img.src` 에 사용 (`CanvasShell.tsx:450`) | 접두 **포함** |

세 곳 모두 `publicApiPath.of(...)` 라는 **하나의 값**을 쓴다. 그런데 화면 쪽 규약이 갈려 있어 **설정 하나로는 셋을 동시에 만족시킬 수 없다.**

그 값은 설정(`authoring.public-api-base-path` / env `PUBLIC_API_BASE_PATH`)이 없으면 `PublicApiPath:69` 가 **WAR 컨텍스트 경로에서 유도**한다. 온프렘 컨텍스트가 `/label-studio/api` 라 유도값이 `/label-studio/api/v1` 이 되고, 여기에 화면이 `/label-studio` 를 한 번 더 붙여 이중이 됐다. **온프렘처럼 접두가 붙는 배포에서만 드러나는 결함**이라 그동안 보이지 않았다.

현장에서는 `PUBLIC_API_BASE_PATH=/api/v1` 을 넣어 **영상 재생만 살렸다.** 그 대가로 지금 **프레임 이미지가 깨진 상태**이며, 마킹을 끝내고 라벨링·검수로 넘어가면 작업 자체가 불가능해진다. 즉 이 임시조치는 마킹 구간 동안만 유효하다.

### 건 2 — 비식별 산출물이 faststart 가 아니다

접두를 고치니 재생은 시작됐지만 중간에 멈췄다. VLC 로는 같은 파일이 끝까지 정상 재생됐고, 그래서 파일 자체는 온전하다는 것이 확인됐다.

mp4 의 인덱스(`moov` atom) 위치를 찍어 보니 이랬다.

```
$ grep -abo moov body-mask.mp4
242736011:moov          # 파일 크기 232MB — 사실상 맨 끝
```

`moov` 가 끝에 있으면 브라우저는 재생을 시작하기 전에 **파일 끝까지 Range 로 왕복**해 인덱스를 받아야 하고, 버퍼링·시크마다 그 왕복이 반복된다. VLC 는 파일을 통째로 읽으니 영향이 없다. 현장에서 그 파일 하나를 `ffmpeg -i in -c copy -movflags +faststart` 로 재패키징하자 **끊김이 눈에 띄게 줄었다**(완전히 사라지지 않은 이유는 건 3이다).

KPST(외부 비식별 솔루션)가 산출물을 faststart 로 만들지 않는다. 벤더 수정이 근본이지만 시간이 걸리고, 그동안 현장 작업이 막힌다.

### 건 3 — 스트림 서명이 60초에 만료된다

faststart 를 적용한 뒤에도 재생 중 갑자기 멈추고 **처음 위치로 되돌아가는** 증상이 남았다. 실제 영상은 많이 남아 있는 상태였다. 멈추는 순간의 네트워크를 보니 `stream` 요청이 **401** 이었다.

4대 WAS 의 `AUTHORING_STREAM_SIGN_SECRET` 이 동일함을 확인했으므로 노드 간 키 불일치는 배제됐다. 남은 원인은 `authoring.stream.url-ttl-seconds` 의 **기본값 60초**다. 연쇄는 이렇다.

```
서명 만료(60초) → Range 요청 401 → <video> error
  → onSrcError → 상위가 서명 URL 재발급 → src 교체
  → 브라우저가 처음부터 다시 로드 → 재생 위치 0 으로 리셋
```

체감상 "시간과 무관하게" 끊기는 것처럼 보이는데, **발급 시점부터 60초**라 로딩·버퍼링에 쓴 시간이 먼저 깎여 실제 재생은 그보다 짧기 때문이다.

구조를 보면 인증이 **이중**이다. URL 쿼리의 서명(`exp`+`sig`+`u`, **60초**)과 `klid_stream_nonce` 쿠키(HttpOnly · Path 한정 · SameSite=Lax · **Max-Age=3600**). `<video>` 가 Authorization 헤더를 못 싣는다는 제약은 **쿠키가 이미 해결하고 있고**, 서명은 그 위에 덧씌운 두 번째 자물쇠인데 **짧은 쪽이 재생을 끊고 있다.**

현장에서는 `AUTHORING_STREAM_URL_TTL_SECONDS=600`(코드 상한)으로 완화했다. 10분 넘는 영상은 여전히 같은 자리에서 끊긴다.

## §2 변경 요지

1. **경로 접두 — 서버가 확정 사양을 따르게 고친다.** ⚠ *방향 반전(Phase 3.6, 사용자 확정)*: 당초 "서버가 완전한 경로를 주고 FE 에서 `toDeployedApiUrl` 을 제거"로 적었으나 **폐기**. `API-114` v3(2026-09-09)이 *"응답 url 은 API 기준 경로이며 배포 접두를 포함하지 않는다 · 소비 측이 배포 접두를 붙인다"* 를 **명시 확정**했고 `SEQ-036` v4·`SCREEN-006` v54 도 같은 날 그 흐름으로 맞춰져, **FE 는 이미 사양대로**다. 결함은 서버 쪽 — 스트림 URL 조립 2곳(`VideoStreamService:221` · `PortalUploadStreamService:102`)이 이미지용 공용 접두(`PublicApiPath` — 미설정 시 WAR 컨텍스트에서 `/label-studio/api/v1` 을 유도)를 함께 쓰고 있었다. **서버의 스트림 2곳만 접두 없는 API 기준 경로(`/api/v1`)로 고치고 FE·이미지 주소는 무변경.** 반영 후 `PUBLIC_API_BASE_PATH` 는 **제거**해야 이미지 주소가 컨텍스트 유도값으로 돌아온다(현장 임시조치 `/api/v1` 은 스트림은 살리고 이미지를 깨뜨린 상태).
2. **비식별 완료 회수 직후 산출물이 faststart 가 아니면 1회 재패키징**한다(`-c copy -movflags +faststart`). 무손실이며 경로·파일명을 바꾸지 않는다.
3. **재생 구간 인증을 nonce 쿠키 축으로 단일화**해 서명 만료로 인한 재생 중단을 구조적으로 없앤다. 아울러 재발급이 일어나는 경우에도 **재생 위치를 보존**한다.

## §3 도메인별 변경 상세

> 이 절이 각 구현 에이전트에 `change_detail` 로 그대로 전달된다.

### 공유기반 선처리 (메인 직접, Phase 3.5) — 건 3

- **대상 파일·심볼**: `common/security/StreamSignatureFilter`(`AUTHORITY_STREAM_SIGNED` 부여 경로 · `doFilterInternal`) · `common/security/StreamNonceCookie`(`resolveOrIssue` · 쿠키 봉인/검증)
- **변경**: 재생 구간 인증 판정축을 **서명(exp+sig+u) + 쿠키** 이중에서 **쿠키 단독**으로 옮긴다. 필터는 nonce 쿠키의 봉인을 검증해 발급자(userNo)를 복원하고, 그 결과로 기존과 동일한 인증 컨텍스트(`CHANNEL_INTERNAL` + `STREAM_SIGNED` authority)를 세운다.
- **불변**:
  - `AUTHORITY_STREAM_SIGNED` 라는 **권한 이름과 그 의미(사용자가 합성 불가한 서버 전용 권한)는 유지**한다 — `VideoController` 의 `@PreAuthorize("... or hasAuthority('STREAM_SIGNED')")` 가 그것으로 판정하며, 이름을 바꾸면 인가 배선이 조용히 끊긴다.
  - 쿠키의 **HttpOnly · Path 한정 · SameSite=Lax · 서버 비밀 + userNo 봉인**은 그대로 둔다. 이것이 사용자 바인딩과 CSRF 방어의 근거다.
  - 영상 단위 인가(`labelAccessGuard.verifyRawAccess`)는 **진입부 판정 그대로** 유지한다(CWE-639 IDOR · 캐시 히트가 인가를 건너뛰지 않아야 한다).
- **주의**:
  - 서명 검증 코드를 지우기 전에 **쿠키만으로 발급자 복원이 가능한지** 먼저 확인할 것. 지금 nonce 는 "서버 비밀 + userNo 로 봉인"돼 있으므로 복원 자체는 성립하나, 그 값을 principal 에 채우는 배선이 서명 경로에 묶여 있으면 함께 옮겨야 한다.
  - `StreamUrlSigner` 를 **삭제하지 말 것.** 발급 창구(`/stream-url`)가 URL 을 만들고 TTL 을 알려주는 계약이 남아 있고, 되돌리기 여지도 남긴다. 검증 축만 쿠키로 옮긴다.
  - ~~포털 업로드 스트림도 같은 필터를 탄다~~ → **사실과 다름(코드 실측).** 포털은 전용 필터 `portal/config/PortalStreamSignatureFilter` + `PortalStreamUrlSigner` 를 쓴다. 공용 필터를 고쳐도 포털 판정은 바뀌지 않으며, 포털 제외 결정(2026-09-16)과도 맞는다.
- **✅ 반영(커밋 `0f51c9a2f`)**: 필터는 쿼리 `u` 로 쿠키 봉인을 검증한다 — 봉인이 서버 비밀 + 발급자로 계산되므로 검증 통과가 곧 「서버가 이 `u` 에게 발급한 쿠키」라는 확인이고 그 `u` 가 발급자다. `exp`·`sig` 는 읽지 않는다. `u` 누락이면 개입하지 않는다(→401). 쿠키 형식은 **무변경**(배포 직후 기존 쿠키도 유효). 생성자에서 `StreamUrlSigner` 의존을 뺐고 클래스는 존치.
- **수용기준**:
  - 유효한 nonce 쿠키가 있으면 `exp` 가 지난 URL 로도 Range 요청이 통과한다.
  - 쿠키가 없거나 봉인 검증에 실패하면 **거부**한다(fail-closed).
  - 다른 사용자에게 발급된 쿠키로는 통과하지 못한다.

### DOMAIN-003 (영상·프레임 수집) — `klid-d003-implementer` — 건 3

- **대상 파일·심볼**: `video/service/VideoStreamService`(`issueSignedUrl` · `stream` 진입부) · `video/service/StreamUrlSigner`(TTL 기본값) · `video/controller/VideoController`(`/{rawSn}/stream-url` · `/{rawSn}/stream`)
- **변경**:
  - ★ **건 1 (경로 접두)** — `issueSignedUrl` 이 URL 을 `publicApiPath.of(...)` 로 만드는 것을 **접두 없는 API 기준 경로**(`/api/v1/videos/{rawSn}/stream?...`)로 바꾼다. 사양 근거 `API-114`: *"응답 url 은 API 기준 경로이며 배포 접두를 포함하지 않는다. 발급 측은 컨텍스트를 알 수 있더라도 붙이지 않고, 결합은 소비 측 한 곳에서만 한다."* ⚠ `PublicApiPath` **자체는 건드리지 말 것** — `ReviewService` 의 `imageUrl` 이 그 값(컨텍스트 포함)을 그대로 쓰고 FE 도 가공 없이 쓴다. 스트림만 그 값에서 떼어낸다. 기준 경로 상수는 `PublicApiPathDefaults.DEFAULT_BASE_PATH`(`/api/v1`)가 이미 있다.
  - 공유기반에서 인증축이 쿠키로 옮겨진 것을 전제로, 스트림 진입부의 판정이 서명에 의존하지 않게 정리한다.
  - `authoring.stream.url-ttl-seconds` **기본값을 재검토**한다. 쿠키 축으로 옮기면 URL 의 `exp` 는 인증 수단이 아니라 캐시 무효화·감사 표식 성격이 되므로, 60초라는 짧은 값을 유지할 근거가 사라진다. 기본값과 상한(현재 600초 클램프)의 의미를 함께 정한다.
- **불변**:
  - `/stream-url` 응답 스키마(`url` · `exp` · `ttlSeconds`)는 **필드를 빼지 않는다** — 화면이 이미 소비 중이다.
  - 비식별 유효성 게이트(`DE_IDNTF_YN != 'Y'` 면 거부)와 비식별 누락 신고 차단(`requireNotUnderDeidentReport`)은 **그대로** 유지한다.
  - 원본 노출 경로(`?raw=true`, REVIEWER 한정)의 조건을 건드리지 않는다.
- **주의**: 스트림 메타 캐시(`stream-meta`, 5분 TTL)는 **비식별 미완료 상태를 캐싱하지 않는다**는 성질에 기대고 있는 코드가 있다. 캐시 키·조건을 바꾸면 그 성질이 깨지는지 확인할 것.
- **수용기준**: 발급 후 60초가 지난 뒤에도 같은 재생 세션의 Range 요청이 성공한다. 비식별 미완료·신고 구간 영상은 종전대로 거부된다.

### DOMAIN-012 (비식별화) — `klid-d012-implementer` — 건 2

- **대상 파일·심볼** (설계 근거 `ADR-072` · `DFEAT-041` · `SEQ-012` · `INT-005` — ⚠ 이 파일의 기존 `@design AC-046` 은 **폐기된 ITEM** 이라 대체 `AC-1063`/`AC-1064` 로 교체할 것): `batch/service/KpstDeidentTxService`(`applyBatchCompletion` 부근 — 완료 확정 및 `DE_IDNTF_FILE_PATH_NM` 기록 지점) · `batch/service/KpstDeidentService`(회수 경로) · ffmpeg 호출은 기존 `net.bramp.ffmpeg` 배선 재사용
- **변경**: 비식별 완료가 확정돼 산출물 경로가 기록된 **직후**, 그 파일의 `moov` atom 위치를 확인해 파일 앞이 아니면 `-c copy -movflags +faststart` 로 **1회 재패키징**한다. 경로·파일명은 바꾸지 않는다.
- **불변**:
  - `DE_IDNTF_FILE_PATH_NM` 의 **값을 바꾸지 않는다** — 관제가 이 값으로 산출물을 픽업하므로 계약면이다.
  - 비식별 완료 상태 전이(`DE_IDENT_YN='Y'` · `MARKING_READY`)와 그 순서를 건드리지 않는다.
  - 재패키징은 **무손실**이어야 한다. 재인코딩(`-c` 생략 등) 금지.
- **주의 (★ 이 도메인 특유의 함정)**:
  - **임시 파일을 export 디렉터리 안에 두지 말 것.** (근거 실측: 결과 회수 폴백 `scanSingleUsable` 은 **숨김 파일도 무결성만 보고 센다** — 이름으로 거르지 않는다.) 결과 회수 폴백이 **단일 산출물**을 전제해 파일이 둘이면 *"비식별 결과 산출물이 모호합니다(다중 파일)"* 로 실패하고, 재위탁 시 `cleanExportDir` 가 그 디렉터리의 정규 파일을 지운다. 같은 파일시스템의 **디렉터리 밖**에서 만들고 **원자적 rename** 으로 들여놓는다.
  - **대용량 I/O 를 DB 트랜잭션 안에서 하지 말 것.** `DeidentExclusionService`(복사는 트랜잭션 밖) / `DeidentExclusionTxService`(기록만 짧은 독립 트랜잭션) 가 쓰는 패턴을 그대로 따른다. `DeidentifyStep.run` 에 `@Transactional` 을 되돌리지 말라는 기존 경고와 같은 이유다.
  - **fail-open** — 변환에 실패하면 원본 산출물을 그대로 두고 로그·이력에만 남긴다. 비식별 완료를 실패로 뒤집지 않는다(재생이 불편할 뿐 데이터는 온전하다).
  - **멱등** — 이미 faststart 면 건너뛴다. 벤더가 고치면 자동으로 no-op 이 되어야 하고, 그래야 나중에 걷어내지 않아도 된다.
  - **동시 실행 제한** — 여러 영상이 한꺼번에 완료되면 ffmpeg 프로세스가 몰린다. 전용 풀 등으로 동시 수를 제한한다.
  - 재비식별(REDEIDENT) 회차에서도 같은 경로를 타므로 **자동으로 재적용**되어야 한다.
- **수용기준**:
  - 완료 후 산출물의 `moov` 가 파일 앞에 있다.
  - 재패키징 전후 재생 길이·해상도·코덱이 동일하다(무손실).
  - 변환 실패 시에도 비식별 완료 상태와 `DE_IDNTF_FILE_PATH_NM` 이 보존된다.
  - 이미 faststart 인 파일에는 ffmpeg 가 호출되지 않는다.

## §4 영향·리스크

- **하위호환**
  - 건 1은 **서버 응답 필드를 바꾸지 않는다**(값의 형태만 바뀐다). 다만 `PUBLIC_API_BASE_PATH` 를 명시 설정한 배포가 있으면 그 값이 다시 의미를 갖게 되므로, **현장 임시조치(`/api/v1`)를 되돌려야 한다.** 배포 문서에 반영 필요.
  - 건 3은 인증 방식 변경이라 **이미 발급된 서명 URL 의 취급**이 달라진다. 되돌리기 여지를 위해 `StreamUrlSigner` 는 남긴다.
  - 건 2는 파일 내용 재배치라 관제 계약면(`DE_IDNTF_FILE_PATH_NM`)에 영향이 없다.
- **되돌리기**
  - 건 1 — FE 되돌림 + `PUBLIC_API_BASE_PATH` 재설정.
  - 건 2 — 후처리를 끄면 종전 동작(끊김 있는 재생)으로 복귀. 이미 변환된 파일은 그대로 두어도 무해하다.
  - 건 3 — 필터의 판정축을 서명으로 되돌림. `StreamUrlSigner` 를 남기는 이유가 이것이다.
- **리스크**
  - ★ **건 3은 인증 구조 변경이다.** 쿠키 검증에 구멍이 생기면 영상이 인가 없이 노출된다(CWE-359). 보안 검토를 별도로 받아야 한다.
  - 건 1을 프론트만 고치고 배포하면, 접두를 명시 설정한 환경에서 **경로가 한 번도 안 붙는** 반대 방향 오류가 난다. 배포 설정 정리가 함께 가야 한다.
  - 건 2의 임시 파일이 export 디렉터리에 남으면 **다음 회수가 "다중 파일 모호"로 실패**한다. 위 제약을 어기면 비식별 파이프라인이 통째로 막힌다.

## §5 검증

- **자동**: 각 도메인 단위·통합 테스트. 건 3은 「쿠키 있음/없음/타인 쿠키」 3축과 「exp 경과 후 통과」를 반드시 포함.
- **수동(온프렘 재현 시나리오)**:
  1. 마킹 화면 진입 → 네트워크에서 `stream` 요청 URL 에 접두가 **한 번만** 붙는지.
  2. 응답 `Content-Type` 이 `video/*` 인지(`text/html` 이면 건 1 미해소).
  3. 60초·10분을 넘겨 연속 재생 → 끊김·위치 리셋이 없는지.
  4. 완료된 비식별본에 `grep -abo moov <파일> | head -1` → 오프셋이 파일 앞인지.
- **회귀**: 프레임 이미지(`imageUrl`)가 라벨링·검수 화면에서 정상 표시되는지 — 건 1의 통일이 이쪽을 깨지 않아야 한다.
- 목서버 기동 불필요(건 2는 실제 산출 파일이 필요하므로 온프렘 또는 dev 실파일로 확인).

- **mock 동기 완료 경로(AsyncDeidentifyRunner)에는 미적용** — 외부 산출물이 아니므로. 적용 여부는 설계 판단.

- **범위 밖 (별건으로 남김)**
  - 마스킹 방식 허용값 정정 — 코드 `ConfigKeys.NUMBER_ALLOWED_VALUES` 는 `{0,2,3}` 인데 벤더 실측 유효값은 `{0,1,2}`(3=블러는 400). 화면 라벨(색상0/모자이크2/블러3)의 근거가 규격서 §22.3.3 에 **없어** 각 값의 의미를 벤더에 확인해야 한다. **확인 전 수정 금지** — 잘못 고치면 표시와 실제 마스킹이 어긋난다.
  - `masking_range` 의 의미 확인 — 규격서는 "범위 **코드**(int, 기본 1)" 인데 우리는 "배율 0.5~2.0 실수"로 다룬다. dev 에 `1.2` 가 들어 있다.
  - 비식별 실패 영상 재비식별 조작 신설 — 현재 `DE_IDENT_YN='F'` 영상을 화면에서 되살릴 수단이 없다(일괄 재시작은 `DATA_STTS_CD='FAILED'` 만 받는다).
  - 외부 호출 실패 시 요청·응답 로깅 보강 — 이번 진단에서 KPST 400 의 사유를 서버 로그로 알 수 없어 curl 재현으로 확인해야 했다.
- **벤더 문의 2건**
  - 파일명에 점이 여러 개면 `POST /project` 가 400 (`...00011.mp4_crop_227.1-242.2.mp4` · `body_crop_178.8-533.0.mp4` · `...00111.mp4.mp4` 3건 실패, 점 하나인 `body.mp4` 만 성공). 우리 코드로는 못 고친다 — `files` 는 KPST 가 공유 마운트에서 직접 읽을 **실제 파일명**이다.
