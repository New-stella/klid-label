# CO-20260904-관제JWT인계-진입수용

> 상태: 작성 · 생성일 2026-09-04 · 브랜치 (미정)
> klid-dispatch · 영향: DOMAIN-001(사용자·권한) + 공유기반(common/security) · **보안 리뷰 필수 게이트**

## §1 배경 — 실측으로 확인된 근본원인

관제서버(`http://192.168.102.246:8088`, 「AI CCTV 관제지원시스템」)가 발급한 JWT 를 저작도구가
인계받아 진입해야 하는데 지금은 안 된다. 2026-09-04 관제 `admin` 계정으로 **직접 로그인해 발급된
실제 토큰**(`localStorage['klid-jwt-token']`, HS512, 580자)을 우리 시크릿으로 검증해 확인했다.

### 관제 토큰 실측 (klid-jwt-token)
- **서명 검증: 통과** — 관제 시크릿(91B, sha256 앞12 `bfc68751`)으로 우리 `verifyWith(key)` 통과.
  alg=HS512 이고 우리 검증은 토큰 선언 HMAC 알고리즘을 따르므로 무관.
- **클레임**: `sub="admin"`(로그인 ID, **문자열**) · `exp` 있음(30분) · `iat` 있음 ·
  **`iss` 없음** · `channel` 없음 · `name` 없음. 그 외 관제 고유 클레임
  (`userId`·`userNm`·`authority=SYSTEM_ADMIN`·`sessionId`·`type`·`userOgCd`·`userSido`·`userSgg`·
  `inaccessible_menus`) 다수.
  ★**이름은 `userNm` 에 있다** — 우리 코드는 `name` 클레임을 읽는데 관제는 `userNm` 에 넣는다.
  즉 `name` 은 부재이고 이름 값은 `userNm` 에 실린다.

### 관제 LogiCraft 대조 (project 95f00d2e, KLID 2차 관제지원시스템)
- 권한 코드가 우리와 **완전히 다른 체계**다 — `SYSTEM_ADMIN`·`PLTF_MANAGER`·`PLTF_OPERATOR`·
  `LGA_WIDE`·`LGA_LOCAL`·`LEARN_MANAGER`(저작도구 작업자)·`relay_server`(ROLE-001~007).
- 관제↔저작도구 연동 규격은 **DB fetch(INT-018, JDBC basic)** 와 **통지 수신(notify-completed/
  updated)** 뿐 — **「관제 JWT → 저작도구 SSO 진입」 규격이 관제 설계에 없다.** 우리 코드
  (`JwtAuthenticationFilter`)와 `CLAUDE.md` 서술로만 존재하는 인계 축이다.

### 필터 실동작 재현 (2026-09-04, 관제 실토큰으로 우리 로직 그대로 재현)
관제 admin 재로그인 → 발급 토큰으로 우리 `JwtAuthenticationFilter` 단계를 재현:
- ① 시크릿 서명검증(HS512) **통과** · ③ exp 있음(30분) · ④ channel 없음→INTERNAL — **정상**
- ② issuer 게이트: `iss=None` → **현재 거부**(유일한 차단 지점). 완화하면 통과.
- 식별: `userId="admin"`(문자열 5자, USER_ID 20자 컬럼에 적합) · `sub` 도 "admin"(숫자 아님).
- 이름: `name` 부재 · **`userNm="시스템관리자"`** — ③ 폴백이 이 값을 채운다.
⇒ **세 축(①②③)이 실측으로 확정됐다.** 남은 미확인은 `USER_ID='admin'` 행의 우리 마스터 실재
   여부뿐이며(운영 DB), 없으면 §5 대로 무권한 fail-closed.

## §2 확정 원칙 (사용자 확정, 구속)

- ★**권한(역할)은 매핑하지 않는다.** 관제 `authority`(`SYSTEM_ADMIN` 등)를 우리 `Role` 로 변환하지
  않는다. **이미 코드가 그렇게 돼 있다** — *"JWT 의 role 클레임은 더 이상 인가에 사용하지 않는다"*.
  우리가 토큰에서 인가에 쓰는 것은 **`sub` 하나**이고, 그 `sub` 로 우리 DB(`LS_USER_ROLE`)에서
  역할을 조회한다. **이 CO 는 권한 축을 한 줄도 건드리지 않는다.**
- **관제는 발급 형식을 바꾸지 않는다.** 우리가 인계받는 쪽이다. 관제 토큰을 있는 그대로 검증해서
  쓴다. 그러니 아래 두 지점을 **우리 쪽에서 흡수**한다.

## §3 도메인별 변경 상세

### DOMAIN-001 (사용자·권한) — `klid-d001-implementer`
공유기반 `common/security` 를 건드리므로 메인 조율 하에 진행(Phase 3.5 성격이나 도메인 소유 코드다).

**대상 파일**
- `common/security/JwtAuthenticationFilter.java` — issuer 게이트 통과 + sub 조회 축
- `auth/jwt/JwtIssuerValidator.java` — iss 없음 허용 정책
- `user/repository/*` + `UserRoleResolver`(위치는 구현자가 확인) — USER_ID 조회 경로 신설

**① issuer 게이트: iss 없음을 허용한다**
- 현재 `JwtIssuerValidator.isAllowed(null)` → `false`(iss null/blank fail-closed, A-ISSUE 계열).
  관제 토큰은 `iss` 가 없어 맨 앞 게이트에서 막힌다.
- **iss 가 없는 토큰은 통과**시킨다. ⚠ **iss 가 있는데 허용목록 밖이면 여전히 거부**(기존 그대로) —
  「iss 없음 허용」과 「아무 iss 나 허용」은 다르다. 전자만 연다.
- ⚠ **시크릿 검증·exp 필수는 유지**한다. issuer 게이트를 여는 것이지 서명·만료 방어를 푸는 게 아니다.
  iss 완화 후 남는 방어가 「시크릿+exp」임을 주석에 명시(보안 리뷰가 이 지점을 본다).

**② 식별 축: 관제 `userId` 클레임을 USER_ID 로 조회한다 (2026-09-04 사용자 확정)**
- ★**식별 키는 `userId` 클레임이다** — `sub`(표준 필드, 관제가 무엇을 넣을지 계약 보장 없음)가
  아니라 관제가 「사용자 ID」로 **의도해 넣은 `userId`** 를 우리 `LS_ACNT_USER.USER_ID` 조회 키로
  쓴다. (이번 토큰은 `sub`·`userId` 둘 다 `admin` 이라 값은 같으나 계약 근거가 다르다.)
- 현재 `parseUserNo(sub)` 는 Long 파싱 실패 시 null → 무권한. **기존 숫자 `sub`(USER_NO) 경로는
  무변경**(내부 토큰·포털). 관제 토큰은 `userId` 를 읽어 **USER_ID 로 조회**한다.
  ⚠ 판정 순서는 구현자가 정하되 **내부·포털의 숫자 sub 경로가 절대 안 깨지게** 한다(회귀 0).
- ⚠⚠ **`LS_ACNT_USER.USER_ID` 에 UNIQUE 제약이 없다**(실측: PK 는 `user_no` 뿐, schema.sql 확인).
  `userId` 조회가 **다중 매칭될 수 있다**(CWE-639 추측 매칭). 둘 중 하나로 처리:
  - (a) **다중/0건이면 fail-closed**(role=null, 무권한) — 추측으로 아무 행이나 고르지 않는다. **기본 권장.**
  - (b) USER_ID 에 UNIQUE 인덱스 추가(마이그레이션) — 단 기존 데이터에 중복이 있으면 기동 실패하므로
    선정리가 필요하고, 관제 로그인 ID 체계가 유일 보장인지 확인 선행. **(a)가 안전하고 되돌릴 게 없다.**
- **자동등록(AC-1016)은 숫자 sub(USER_NO 신규 삽입) 전용이다** — 관제 `userId` 로 USER_ID 조회가
  0건이면 삽입할 userNo 가 없어 자동등록 대상이 아니다. **무권한 fail-closed 로 흐른다**(현행과 동일).
  즉 관제 사용자가 우리 마스터에 없으면 진입은 되나 무권한이다 — 이게 맞는지는 §5 미결.

**③ 이름 클레임: name 이 없으면 userNm 을 읽는다**
- 우리 필터는 `body.get("name")` 으로 표시 이름을 읽어 **자동등록 사용자의 표시명**으로 쓴다.
  관제 토큰은 `name` 이 없고 이름을 **`userNm`** 에 넣는다 → 자동등록 사용자 이름이 빈다.
- **`name` 우선, 없으면 `userNm` 폴백**으로 흡수한다. 내부 토큰(`name` 보유)은 무변경.
- ⚠ 이름은 표시용일 뿐 **인가에 쓰지 않는다**(권한 축 아님). 없어도 진입 자체는 막지 않는다.

**구현 구조 (코드 실측 2026-09-04 — 구현자 지침)**
- ① `common/security/JwtIssuerValidator.isAllowed`: `issuer == null` 이면 현재 `false`. **null 은 통과**로
  바꾸되 **blank(빈 문자열)와 「값 있는데 allowed 밖」은 그대로 거부**(iss 를 실제로 넣었는데 목록 밖인
  건 여전히 막아야 한다 — null 과 구분).
- ② 식별은 **2단 조인 신설**이다. 현재 `UserRoleResolver.resolve(Long userNo)` → `LsUserRoleRepository.
  findByUserNo` 로 userNo→role 만 있다. userId(문자열)→role 경로가 없다:
  `관제 userId → [신설] UserRepository.findUserNoByUserId(String) → userNo → resolve(userNo)`.
  ⚠ `LS_ACNT_USER.USER_ID` 유일 제약 없음 → 신설 조회는 **다중/0건이면 empty 반환(fail-closed)**,
  단건일 때만 userNo. `findByUserNo` 캐시(@Cacheable userRole key=userNo)는 그대로 재사용.
- ③ 이름: 필터 `body.get("name")`(현 110행) → **`name` 없으면 `userNm` 폴백**. upsert(`UserRepository`)는
  이미 `userNm` 을 받으므로 필터에서 넘기는 값만 바꾸면 된다(135행 registerAsWorker·174행 AUTH_NAME_ATTR).

**불변**
- 권한(role) 판정 로직·`LS_USER_ROLE` 조회·자동등록·PORTAL 채널 분기 무변경.
- 숫자 sub(USER_NO) 경로 무변경 — 내부 토큰·포털 토큰이 그대로 돈다.
- 시크릿 검증·exp 필수·channel 기본값(null→INTERNAL) 무변경.

**수용기준**
1. iss 없는 관제 토큰이 issuer 게이트를 통과한다.
2. iss 가 있고 허용목록 밖인 토큰은 **여전히 거부**된다(회귀 없음).
3. 시크릿 불일치·exp 없음 토큰은 **여전히 거부**된다(방어 유지).
4. 관제 `userId` 클레임이 USER_ID 로 유일 매칭되면 그 사용자로 역할 조회된다.
5. 관제 `userId` 가 USER_ID 에 다중/0건 매칭이면 fail-closed(무권한, 예외 없음).
6. 숫자 sub 경로가 종전과 동일하게 동작한다(내부·포털 회귀 0).
7. 관제 토큰(name 부재·userNm 보유)으로 자동등록되면 표시명이 userNm 값으로 채워진다.
8. 내부 토큰(name 보유)의 표시명은 종전대로 name 값이다(회귀 0).

## §4 영향·리스크
- **인가 게이트 완화라 보안 리뷰가 필수 게이트다**(Phase 5.5 에 cc-security-reviewer 성격 포함).
- 설정 축(운영, 이 CO 밖): 배포 `.env` 의 `JWT_SECRET` 을 관제 값으로 맞춰야 실제로 검증 통과한다
  (현재 다름 — 해시 18ce97ce vs bfc68751). 이건 운영 시크릿 주입이라 코드 변경 아님.

## §5 미결 (사용자·관제팀 판단 필요 — 구현 전 확인)
1. **관제 사용자 sub 를 우리 마스터와 잇는 매칭 키가 실재하는가.** `CLAUDE.md` 사용자등록 절이
   *"접속자와 명부 행을 이을 매칭 키가 없다"* 를 확정 사실로 적어 자동등록을 택한 바 있다.
   관제 `userId`(`admin`)가 우리 `LS_ACNT_USER.USER_ID` 와 같은 값으로 존재하는지 미확인.
2. **어떤 관제 계정이 저작도구에 진입하는 시나리오인가.** 테스트한 것은 `SYSTEM_ADMIN` 인데,
   저작도구 작업자는 관제 `LEARN_MANAGER` 다. 진입 대상 계정이 확정돼야 한다.
3. **관제 사용자가 우리 마스터에 없을 때** 무권한 진입(현행)이 맞는지, 아니면 다른 정책인지.

### §5-c 보안 리뷰 F-1 (Medium) — 인가 신원과 principal 신원 분리 (2026-09-04 발견)
인가는 `userId→userNo` 로 해석하나 `TokenClaims` 는 raw `sub`("admin")를 신원으로 나른다. 다운스트림
per-user 스코핑·소유권·감사(`VideoQueryService`·`LabelAccessGuard`·`dataset/*MetaService`)가 전부
`parseUserNo(actor.sub())` 를 써서 비숫자 sub 는 401. **현재 fail-closed(안 샘)** 이나 ①관제 인계
사용자가 진입 후 per-user 작업이 401(기능 절반) ②잠재 fail-open — `parseUserNo` 를 손대면 신원
혼동이 뒤집힐 수 있고 관제 admin 여럿의 `sub="admin"` 공유가 감사 신원을 붕괴(CWE-778).
근본 해법: `TokenClaims` 에 해석된 `userNo` 를 실어 principal 을 단일 신원으로 통일 → 다운스트림 전환.
**범위가 인증 신원 모델·다운스트림 다수에 걸쳐 커지고, 설계(ADR-063 개정) 선반영이 필요하다.** 처리
방향(이 CO 에서 함께 정합 vs 별도 후속 CO)은 사용자 판단 대기.
**★해소 확정 (2026-09-04 사용자 확정): 이 CO 에서 함께 정합 + Option B(필터 sub 정규화).**
- `sub` 는 두 갈래로 쓰인다 — ①`parseUserNo(sub)` 숫자 파싱(30+ 사이트) ②문자열 그대로 감사
  `regId`/`mdfcnId`·work lock 키·portal owner·issue `reportedUserNo` 비교·RoleClaim/AdminSession 키(50+ 사이트).
  내부/포털 토큰은 sub 가 이미 숫자(userNo)라 둘이 일치. 관제만 sub="admin"(로그인 ID)이라 ①→null→401 ②→"admin" 저장→감사 붕괴.
- **해법: JwtAuthenticationFilter 한 곳에서 관제 토큰 sub 를 해석된 userNo(문자열)로 치환**해 내부/포털과 동형으로.
  다운스트림 파싱·문자열 직접사용 양쪽이 자동으로 올바른 식별자를 본다 → 기능 갱·감사 붕괴 둘 다 해소, 다운스트림 무변경.
- **해석 실패(관제 사용자가 마스터에 없음·다중 매칭) 시 sub 를 치환하지 않고 raw 유지 → parseUserNo=null → 기존 fail-closed 그대로.**
- ⚠ 인지·수용: 관제 토큰의 저장 식별자 의미가 '로그인 ID'→'userNo' 로 바뀐다(내부 토큰과 일치하므로 정합). raw 로그인 ID 를
  필요로 하는 다운스트림은 실측상 없음(sub 는 전부 파싱 대상이거나 opaque 식별자).
- ⚠ 기각한 안(보안 원문 제안): TokenClaims 에 userNo 필드 추가 + 파싱 사이트만 전환 — 문자열 직접사용 50+곳의 감사 붕괴
  미해소, 완전 수정 시 blast radius 100+, 도메인별 private parseUserNo 누락 위험. Option B 가 1곳 변경으로 더 넓게 고친다.
- 설계 선반영: ADR-063 개정(principal 신원 정규화) → UC-041/AC cascade → 필터 구현.

### §5-d 보안 F-2·F-3 (Low)
- F-2: iss 완화로 issuer allowlist 가 공격자 방어가치를 잃음(시크릿 단일축 수렴) — 위협모델(온프렘
  내부망·시크릿=신뢰앵커)상 수용. 단 세 issuer 동일 시크릿 공유 시 channel 격리가 독립 강제돼야
  함(현재 SecurityConfig 에서 강제 — OK). 시크릿 로테이션·유출대응 운영 문서화 전제.
- F-3: `catch` 에서 `Channel.valueOf` IAE 메시지(사용자통제 channel 클레임값)를 debug 로그에 echo
  (CWE-117). debug+서명필요라 저위험. `LogSanitizer` 적용 검토(후속).

## §5-b ★설계가 우리 흡수와 정반대였다 (2026-09-04 ADR-063 cascade 로 발견)

ADR-063 을 신설하며 cascade 로 `UC-041`(인증 인계와 채널·역할 인가)·`AC-1016`(그 happy-path
수용기준)을 열어 보니 **이미 반대 규칙이 명세**돼 있었다:
- `UC-041` step2 = *"발급처 허용 목록 검증 — 목록 밖이면 거부"*(iss 부재 카브아웃 없음)
- `UC-041` step4 = *"주체 식별자가 숫자가 아니면 거부"*
- `AC-1016` = 같은 두 문구, 그리고 **`implementation=implemented/passing`**

⇒ **관제 토큰 거부는 「버그」가 아니라 「설계대로」였다.** 코드가 UC-041·AC-1016 을 정확히 구현한 것.
⇒ 그래서 **코드만 고치면 다음 QA 가 「AC-1016 위반」으로 되잡는다.** 설계를 먼저 뒤집어야 한다
   (사용자 확정 2026-09-04, LogiCraft 먼저 원칙). 순서: UC-041 → AC-1016(depends_on_completion).
⚠ `AC-1016` 문구를 뒤집으면 `verification_status` 를 passing→unverified 로 내린다(옛 기준 통과
   기록이라 새 기준 검증 아님). `implementation.status` 자체는 무변경(코드 반영은 Phase 4).
✅ 무관 확인: `AC-1017`(negative)은 ADR-063 과 이미 일치 · `SCREEN-001`(클라이언트 디코드)은 서버
   검증 계층 아님 — 둘 다 건드리지 않는다.
