# CO-20260905 관제 진입자 userNo 자동발급 + 권한안내/부트스트랩 화면

> 관제 JWT 인계 로그인이 **실제 관제 계정에서 끝까지 동작하지 않는 결함**을 실토큰 E2E 로 확인하고 고친다.
> 선행 CO-20260904(관제 JWT 인계 진입 수용 + F-1 principal 정규화, 머지 완료)의 후속 결함 수정.

## §1 배경 — 실토큰 E2E 로 확인된 결함 (2026-09-05)

로컬 백엔드(8080, context `/api`) + **사용자 DB 싹 비운 첫 진입자 상태**에서 관제 admin 실토큰
(HS512 · iss 없음 · `sub="admin"` · `userId="admin"` · **숫자 userNo 없음** · exp 30분)으로:

| 요청 | 결과 |
|---|---|
| `GET /api/v1/me` | **200** `{userId:"admin", role:null, channel:INTERNAL}` — 진입은 되나 무권한 |
| `GET /api/v1/users` | **403 FORBIDDEN** — 무권한 |
| `POST /api/v1/auth/role-claim` (ADMIN, 로컬 실패스워드) | **400 "userNo 형식이 올바르지 않습니다"** |

**근본원인**: 관제 토큰은 **문자열 로그인ID("admin")로 식별**하고 숫자 userNo 가 없다. 우리 인가는
숫자 `USER_NO` 로 도는데 `LS_ACNT_USER` 에 `USER_ID='admin'` 행이 없어 해석 0건 → 무권한.
role-claim 은 `Long.parseLong(sub)` 이라 "admin" 에서 400. 자동등록(`AutoWorkerRegistrar`)은
`numericSub!=null` 게이트라 관제(비숫자 sub) 경로에선 안 돈다.
**상용은 사용자 시드가 아예 없어**(`DevSeedRunner=@Profile("local")` 실측) 관제 사용자 전원이 userNo 를
못 얻고 부트스트랩도 못 해 **관제 채널이 통째로 잠긴다.**

## §2 확정 원칙 (사용자 확정 2026-09-05, 구속)

- **"내부 사용자 등록 시나리오는 없다"** — 관제가 인증·관리하고 우리는 토큰으로 신원만 받는다.
  이 수정은 회원가입 화면이 아니라, 관제가 이미 인증한 사용자에 대해 우리 DB 에 로컬 식별
  레코드(userNo)를 **진입 순간 투명하게** 만드는 것이다(V169 가 의도한 "역할 클레임 시점 자동등록"의
  연장 — 실제 토큰이 숫자 userNo 대신 로그인ID 를 싣는다는 사실 하나를 메운다).
- **역할은 자동부여하지 않는다**(role=null 유지) — 관제 authority 를 우리 역할로 매핑 금지(ADR-021).
  첫 진입자는 관리자 비밀번호로 ADMIN 부트스트랩, 이후 사용자는 관리자가 역할 부여.
- **기본 관리자 비밀번호 = 전 환경(상용 포함) `admin`, 로그인 후 변경 가능** ([[admin-bootstrap-password-default-admin]]).
- **포털(PORTAL 채널)·숫자 sub 경로 무영향** — 신설 경로는 INTERNAL 채널 + 비숫자 sub 만.

## §3 도메인별 변경 상세

### DOMAIN-001 (사용자·권한) — `klid-d001-implementer` + 공유기반 마이그레이션(메인 Phase 3.5)

**① userNo 시퀀스 신설 (마이그레이션)**
- `LS_ACNT_USER.USER_NO` 발급용 시퀀스 신설. 관제가 sub 에 싣는 숫자 userNo·dev 시드(1001~9001)와
  **겹치지 않는 높은 disjoint 범위**에서 발급(예 `9,000,000,000` 시작). 충돌 가드 필수.
- 표준용어·표준도메인 준수(conventions.md — CSV 정본 grep). 시퀀스 물리명도 표준 조합.

**② USER_ID 부분 유니크 인덱스 신설 (마이그레이션)**
- `UNIQUE (USER_ID) WHERE USER_ID IS NOT NULL` — 재진입·2노드 동시진입에 같은 사용자가 두 행으로
  갈리는 것을 막는다(그러면 이후 조회가 다중매칭 fail-closed 로 **다시 잠긴다**).
- ⚠ **V169 가 의도적으로 안 걸었던 제약을 되돌리는 것**이다(그땐 관제가 userNo 를 줬는데 이제 우리가
  발급하니 USER_ID 가 안정 키가 되어야 한다). 기존 데이터에 **중복 USER_ID 있으면 마이그레이션이
  막히니 사전점검 + 안전 처리**(상용은 빈 테이블이라 무해, dev 시드는 distinct).

**③ 진입 시 관제 사용자 자동 프로비저닝 (auth/·user/·common/security)**
- 관제(비숫자 sub, **INTERNAL 채널**) 진입자가 `userId` 클레임으로 `LS_ACNT_USER` 조회 0건이면 →
  시퀀스에서 userNo 발급 + `(USER_NO, USER_ID=userId, USER_NM=userNm)` **원자적 upsert(USER_ID 기준,
  `ON CONFLICT (USER_ID) DO NOTHING` + 재조회)**. 재진입 시 같은 행 → 같은 userNo.
- **role 은 자동부여하지 않는다**(role=null). AutoWorkerRegistrar 의 WORKER 자동부여를 이 경로로
  확장하지 않는다.
- F-1 정규화(구현됨)가 발급 userNo 로 이어져 sub 가 정규화되고 role-claim `parseLong` 성공.
- ⚠ **숫자 sub(내부·포털)·PORTAL 채널 경로 무변경**(회귀 0). 신설 프로비저닝은 INTERNAL+비숫자 sub 만.
- ⚠ 동시성(CWE-362): 2노드 Active-Active 에서 같은 신규 userId 동시진입 → 부분유니크가 한쪽만
  INSERT 성공시키고 나머지는 재조회로 같은 userNo. 조회-후-INSERT 창을 원자 upsert 로 닫는다.
- ⚠ Mass Assignment(CWE-915): userNo 는 **시퀀스/서버가 발급**하고 요청 바디·토큰의 임의 숫자를
  신뢰하지 않는다. userId·userNm 은 표시용(제어문자 제거·길이 상한).

**④ 관리자 부트스트랩 기본 비밀번호 = 'admin' (설정 — 공유기반)**
- `application-local.yml` 의 `authoring.auth.admin-claim-password-hash` 기본값을 **BCrypt('admin')**
  로 교체(현재 'admin1234' 해시). `application.yml`(dev/stg/prd)에 **`${ADMIN_CLAIM_PASSWORD_HASH:<BCrypt('admin')>}`
  기본값 부여**(현재 기본값 없이 env 필수). 평문 금지 — BCrypt(cost 12) 해시만.
- 변경 경로: 로그인 후 `AdminPasswordService` 로 사용자가 바꾼다.
- ⚠ 기본 크레덴셜을 상용에 두는 트레이드오프(CWE-798/1392)는 **사용자 인지·수용**. 변경 권고 UX 로 완화.

**불변**
- role-claim 자체 로직(부트스트랩 창=ADMIN 0명, 관리자 패스워드, 조건부 UPDATE) 무변경.
- 권한(authority→Role) 매핑 금지. 시크릿·iss·exp·channel 게이트 무변경. 스키마는 시퀀스+부분유니크만 추가.

**수용기준**
1. 관제 실토큰(비숫자 sub) 첫 진입 시 `LS_ACNT_USER` 에 새 userNo(높은 범위)로 행이 생기고 role=null.
2. 재진입 시 **같은 userNo**(중복 행 안 생김). 2노드 동시진입도 1행.
3. 그 상태에서 `POST /v1/auth/role-claim`(ADMIN, 'admin') → **성공**, 사용자가 ADMIN 이 됨(창 열림 시).
4. 재진입 시 ADMIN 역할로 진입(`/me` role=ADMIN, `/users` 200).
5. 숫자 sub(내부·포털)·PORTAL 경로 회귀 0 — 프로비저닝 미진입.
6. 발급 userNo 가 관제 숫자 userNo·시드와 충돌하지 않는다.

### 프론트 (klid-web-implementer)

**⑤ 진입 후 서버 role 확인 라우팅 (SessionIngressPage)**
- 현재 INTERNAL 이면 서버 role 확인 없이 `/dashboard` 로 보낸다 → role=null 사용자는 전 API 403 으로
  대시보드가 깨진다. → 진입 후 `/me` 로 서버 role 확인 → **role=null 이면 신규 안내 페이지로** 라우팅.
  (role 있으면 종전대로 대시보드.)

**⑥ 신규 안내/부트스트랩 페이지 1개, 상태로 갈림**
- **부트스트랩 창 열림(ADMIN 0명)** → 관리자 비밀번호 입력 폼 → `POST /v1/auth/role-claim` → 성공 시
  ADMIN 으로 재진입(첫 관리자 부트스트랩). 창 열림 판별: role-claim 응답(409=닫힘) 또는 상태.
- **창 닫힘(ADMIN 존재)** → "관리자에게 권한을 요청하세요" 순수 안내.
- ⚠ FE 에 현재 role-claim(관리자 등록) 페이지가 없다(DevLoginPage 만). 이 페이지가 그 역할을 겸한다.
- 보안: 관리자 비밀번호 평문은 폼 제출 순간만, 로그·상태 미저장(CWE-256). `dangerouslySetInnerHTML` 금지.
