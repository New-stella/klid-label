## §1 배경

사용자 확인(2026-08-28): **런북이 올라갈 서버는 레드햇 엔터프라이즈 리눅스 8.9** 다.

그런데 온프렘 패키지 전체가 **Rocky Linux 9(RHEL 9 계열, glibc 2.34)** 를 타깃으로 쓰여 있다.
문서 7개에 49건, `scripts/lib/versions.sh`·`README.md` 에 하드코딩돼 있다.

**RHEL 8 은 8.0~8.10 전 버전이 glibc 2.28 로 고정**이다. 이 한 줄이 아래 판정의 전제이며 측정이 필요 없다.

## §2 축별 판정

### ❌ 깨지는 것

**① ffmpeg 정적 바이너리 — `versions.sh` 가 스스로 조건을 적어 뒀다**

> *"glibc: BtbN 빌드는 glibc 에 동적 링크(약 **glibc 2.31** 기반 빌드) … Rocky 9 의 glibc 2.34 는
> 상위호환이므로 정상 동작한다(**빌드 glibc ≤ 대상 glibc**)."*

RHEL 8.9 는 **2.28 < 2.31** 이라 그 부등식이 뒤집힌다. 프레임 추출·`ffprobe` 가 `GLIBC_2.31 not found` 로 죽는다.
⚠ *"약 2.31"* 은 저자의 어림값이라 **실측으로 확정해야 한다**(§5).

**② 시스템 RPM** — `mesa-libGL`·`libglvnd-glx`·`glib2` 를 `rockylinux:9` 컨테이너에서 `dnf download` 한다.
el9 RPM 은 RHEL 8 에 설치되지 않는다.
⚠ **타깃에 이미 설치돼 있으면 이 축이 통째로 사라진다** — 실측 항목이다.

**③ PostgreSQL 16 RPM** — `PGDG_REPO_RPM_URL` 이 `EL-9-x86_64` 로 고정. `EL-8-x86_64` 로 바꿔야 한다.
⚠ 타깃에 PG 가 이미 있으면 `SKIP_POSTGRES=1` 로 우회 가능(기존 옵션).

### ✅ 이미 맞는 것 — 재수집 불필요

**pip wheel** — torch 가 **`manylinux_2_28`** 이고 그 태그가 **정확히 glibc 2.28 = RHEL 8 기준선**이다.
⚠ 문서(`01-prerequisites.md:8`)는 *"glibc 2.34 호환이라 그대로 쓴다"* 고 적었는데, 근거가 낡았을 뿐
**결론은 RHEL 8 에서도 참**이다. 서술만 정정한다.

**Temurin JRE/JDK 17** — glibc 2.17+ 지원.

### ⚠ 실측 전까지 단정하지 않는 것

- **python-build-standalone** `cpython-3.11.15 x86_64-unknown-linux-gnu` 의 glibc 하한
- **Node 20** — 공식 하한이 glibc 2.28 이라 RHEL 8.9 가 **정확히 경계선**. 다만 빌드머신용이라
  타깃 영향이 없을 수 있다(설치 스크립트가 타깃에 node 를 올리는지 확인 필요)

## §4 ★미확정 — 사용자 결정 필요: ffmpeg 를 무엇으로 바꾸나

`versions.sh` 에 **라이선스 정책이 구속으로 박혀 있다**:

> *"라이선스: **LGPL 빌드를 쓴다**(지방정부 납품 — GPL 의무 회피). … 우리는 인코딩을 하지 않으며
> GPL 코덱(libx264/x265 = 인코더)은 불필요하다."*

glibc 2.28 이하로 내리는 후보가 셋인데 셋 다 대가가 있다:

| 후보 | 장점 | 대가 |
|---|---|---|
| **BtbN 의 더 옛 dated 태그** | 조달 경로·검증 절차 무변경 | ffmpeg 버전이 내려간다. 어느 태그부터 glibc 2.28 이하인지 확인 필요 |
| **완전 정적 빌드**(johnvansickle 류) | glibc 무관 — 이 문제가 영구 소멸 | **GPL** 이라 위 정책과 정면 충돌 |
| **el8 컨테이너에서 자체 빌드** | LGPL 유지 + glibc 정확히 맞음 | 빌드 파이프라인이 하나 는다. 재현성·핀 관리 부담 |

### ✅ 확정 (2026-08-28 사용자) — **관제와 같은 경로: 시스템 RPM 설치본 호출**

정적 바이너리 번들을 **그만둔다.** 관제가 쓰는 형상과 맞춘다.

**근거 실측** — 관제 `OSS-077` 이 `license_risk: review_required` · `needs-verification` 로 **미확정**이었고
본문이 *"서버 설치본을 실측해 갱신할 것"* 을 요구했다. dev 서버(`cudo_246`)에서 그 실측을 했다:
```
ffmpeg 3.4.13 · --enable-gpl --enable-libx264 --enable-libx265
RPM License: GPLv2+ · Vendor: RPM Fusion · Source: ffmpeg-3.4.13-1.el7.src.rpm
```
관제의 가설(*"H.264 인코딩을 하므로 GPL 빌드일 가능성이 높다"*)이 맞았다.

⚠ **폐기되는 정책**: `versions.sh` 의 *"라이선스: **LGPL 빌드를 쓴다**(지방정부 납품 — GPL 의무 회피)"*.

| | |
|---|---|
| **얻는 것** | glibc 문제 **소멸**(el8 RPM 이므로 §2-① 이 통째로 사라진다) · 관제와 형상 일치 · GPL 이지만 **별도 프로세스 호출**이라 `OSS-077` 이 적은 대로 코드 전염 우려가 낮다 |
| ⚠ **대가** | 정적 번들을 택했던 **원래 이유가 되살아난다** — *"ffmpeg 는 base/AppStream 에 없고 RPM Fusion/EPEL 미러가 필요해 **폐쇄망에서 의존성 지옥**에 빠진다."* **폐쇄망 RPM Fusion el8 의존성 확보 방안이 새 숙제다** |

### 별건 갭 — 기록

**저작도구에는 번들 ffmpeg 바이너리의 OSS 항목이 없다.** `OSS-014` 는 **Java 래퍼**
(`net.bramp.ffmpeg`, BSD-2-Clause)뿐이라, 배포물에 넣는 실행 파일이 OSS 대장에 없었다.
이번 확정으로 성격이 「시스템 RPM 의존」으로 바뀌므로 그에 맞춰 OSS 항목을 신설해야 한다.
관제 `OSS-077` 도 실측값으로 갱신할 수 있다(우리가 측정했다).

## §5 실측 대기 항목 (폐쇄망 — 사용자가 서버에서 실행)

```bash
{
echo "### OS"; cat /etc/redhat-release; uname -m
echo "### glibc"; ldd --version | head -1
echo "### 이미 설치된 런타임 의존 RPM (있으면 수집 불필요)"
rpm -q mesa-libGL libglvnd-glx glib2 2>&1
echo "### ffmpeg 유무"; command -v ffmpeg ffprobe 2>&1 || echo "없음"
echo "### PostgreSQL 유무"; rpm -qa | grep -iE '^postgresql' | head; command -v psql 2>&1 || echo "psql 없음"
echo "### 기타 환경"; getenforce 2>&1; systemctl is-active firewalld 2>&1
echo "### dnf 리포"; dnf repolist --quiet 2>&1 | head -5
} 2>&1
```

빌드머신에 ffmpeg tarball 이 이미 있으면 함께:
```bash
objdump -T <ffmpeg 경로> | grep -o 'GLIBC_[0-9.]*' | sort -uV | tail -3
```

이 결과가 §2 의 ⚠ 세 항목과 §4 의 선택지를 확정한다. **그 전까지 조달물 명세를 고치지 않는다** —
추측으로 핀을 바꾸면 빌드머신에서만 드러나는 오류가 된다.

## §6 영향·리스크

- **배포 차단급이다.** ①이 사실이면 프레임 추출·영상 길이 산출이 타깃에서 동작하지 않는다.
- 되돌리기는 쉽다(전부 텍스트) — 다만 **빌드머신에서 wheel·RPM 재수집이 필요할 수 있고** 그건 시간이 든다.
- ⚠ **역할체계 CO(`CO-20260828-역할체계-admin신설-계층-부트스트랩`)와 별개 축**이다. 사용자 확정으로
  분리했다 — 섞으면 「역할 체계 반전」이라는 그 CO 의 성격이 흐려진다. 다만 **런북 §G(최초 관리자
  부트스트랩)는 그 CO 가 이미 고쳤고**, 이 CO 는 같은 파일의 **OS 축**만 건드린다.

## §7 구현 로그 (2026-08-30)

### 반영한 것

| 축 | 무엇을 |
|---|---|
| **OS 전환** | el9 → el8 참조 100건(문서·스크립트·설정 17파일). `versions.sh` 의 `PGDG_REPO_RPM_URL` 을 EL-9 → EL-8, RPM 수집 컨테이너를 `rockylinux:8` + `--platform linux/amd64` 로 |
| **ffmpeg 정책 반전** | 정적 바이너리 핀 제거. §4 확정대로 **시스템 RPM 경로**로 갈아탔고, 구 LGPL 정책은 지우지 않고 「구 정책 폐기(2026-08-28)」 표기로 남겼다 |
| **§4 의 새 숙제 해소** | *"폐쇄망 RPM Fusion el8 의존성 확보"* — el8 컨테이너에서 `--resolve --alldeps` 로 받아 `createrepo_c` 로 **로컬 리포지토리**를 만들었다. RPM 파일 직접 설치는 glibc 충돌로 실패하지만, 로컬 리포 + `dnf install <이름>` 은 dnf 가 스스로 골라 통과한다(수집 261 → 설치 105, glibc 무변) |
| **자동 설치 안 함** | 사용자 확정 — 관제가 같은 장비에 설치하므로 덮어쓰면 관제 기능이 깨진다. 별도 명령(`install-ffmpeg.sh`)으로만 설치하고, 이미 있으면 건너뛴다 |
| **동작 확인 게이트** | 존재 여부만으로는 부족해 **실제 1프레임 추출 + `ffprobe` 판독**까지 확인하는 단계를 두었다(없으면 `die`) |

### 오프라인 예행연습으로 확인한 것

`--network none` · `rockylinux/rockylinux:8` · `--platform linux/amd64` 에서 실행했다(DNS 해석 실패로 차단 자체를 먼저 확인).

- GPG 키 반입 · 로컬 리포 설치(glibc 무변) · httpd 모듈러 패키지 · SELinux 도구
- **`import cv2` 4.13.0 성공** — 이 확인이 처음이며, `mesa-libGL`·`libglvnd-glx` 를 담은 근거가 됐다
- torch 2.12.0+cpu · onnxruntime · sam2 · fastapi 반입
- ffmpeg 3단계(없으면 die → 번들 설치 → 동작 확인)
- `--role=ai` · `--role=app` 양쪽 완주(RC=0)

### 예행연습이 덮지 못한 것 (정직하게)

컨테이너 한계라 **현장에서 처음 도는 구간**이다: WAS 기동·`api.war` 실행 · WAS 설정 이관 효과(**대용량 업로드는 현장에서 1회 해야 하고, 빠뜨려도 신호가 없다**) · PostgreSQL 실기동(`systemctl` 이 스텁) · **스키마 적재 단계는 한 번도 실행되지 않았다**(`SKIP_DB_INIT=1` 로 우회) · SELinux Enforcing · ai-server 실기동·추론 · 실제 RHEL 8.9.

### 별건 갭 (§4 말미) — 미해소

번들 ffmpeg 의 OSS 항목 신설과 관제 `OSS-077` 갱신은 **아직 하지 않았다.** 관제 프로젝트는 쓰기 권한이 없어(`E_AUTH_FORBIDDEN`) 우리 쪽에서 갱신할 수 없고, 우리 항목 신설은 관제팀 설치본 확인(아래)이 선행돼야 값이 맞는다.
