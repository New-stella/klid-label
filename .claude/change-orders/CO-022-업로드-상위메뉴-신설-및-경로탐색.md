## §1 배경

### 1-1. 메뉴가 성격이 다른 자리에 섞여 있다

LNB 「관리」 그룹은 원래 **운영 설정을 다루는 자리**다 — 사용자 관리·시스템 설정·라벨 관리·프리셋 관리·비식별 신고·이벤트유형 관리. 그런데 그 끝에 **데이터를 집어넣는 화면 둘**이 붙어 있다.

| 화면 | 경로 | 하는 일 |
|---|---|---|
| 외부 산출물 이관 (SCREEN-039) | `/manage/imports` | **서버에 이미 있는 폴더**를 검사해 저작도구로 가져온다 |
| 수동 업로드 (SCREEN-027) | `/dev/upload` | **내 PC 파일**을 올려 파이프라인에 태운다 |

둘 다 "설정"이 아니라 "적재"다. 그런데 「관리」에 섞여 있어 ①찾기 어렵고 ②서로 형제 관계라는 사실이 메뉴에 드러나지 않는다. 실제로 두 화면은 **같은 목적(데이터를 들여온다)을 서로 다른 방식(서버 폴더 / 내 PC 파일)으로 수행**하는 짝이다.

### 1-2. 산출물 경로를 손으로 타이핑해야 한다

`SCREEN-039` 의 입력은 텍스트 두 칸이다 — `산출물 폴더 경로`(필수)·`원본 영상 경로`(선택). 도움말은 *"허용된 저장소 범위 밖이면 서버가 받지 않습니다"* 뿐이고, **그 범위 안에 무엇이 있는지 화면이 알려주지 않는다.** 검수자는 NAS 경로를 외우거나 다른 곳에서 복사해 와야 하고, 오타 한 글자에 `NOT_FOUND` 를 받는다.

이건 서버가 판정만 하고 안내는 하지 않는 비대칭이다. 판정 근거(허용 루트 목록)를 서버가 이미 갖고 있으므로, **그 목록을 화면에 내려주면 타이핑이 선택으로 바뀐다.**

### 1-3. 이 개명은 이틀 만의 2차 개명이다 (인지하고 진행)

`CO-008`(2026-08-24)이 「영상 업로드」 → 「수동 업로드」 개명을 이미 수행했고, 그때 `SCREEN-027` 제목과 `NAV-001` 노드(`manage-manual-upload`, 「관리」 그룹)를 확정했다. 이번 CO 는 그 결정을 **부정하는 것이 아니라 상위 맥락을 바꾸는 것**이다 — 「업로드」 그룹이 생기면 항목명의 `수동`·`외부 산출물` 접두가 그룹명과 겹치거나 방식 구분을 흐린다. 사용자가 세 후보를 미리보기로 비교한 뒤 **방식 축(`산출물 가져오기` / `파일 업로드`)** 을 선택했다.

## §2 변경 요지

1. LNB 에 **`업로드` 그룹을 신설**하고(`게시판`과 `관리` 사이) 두 화면을 「관리」에서 그리로 옮긴다.
2. 메뉴명·화면 제목을 **`산출물 가져오기`**(구 외부 산출물 이관) / **`파일 업로드`**(구 수동 업로드)로 바꾼다.
3. **서버 폴더 탐색 API 를 신설**해 허용 루트 하위를 나열하고, `SCREEN-039` 의 경로 입력에 **선택 모달**을 붙인다. 직접 타이핑은 그대로 남긴다.

**하지 않는 것**: URL(`/manage/imports`·`/dev/upload`) · 라우트 가드 조건 · 설정키 · 클래스명 · 도메인명(DOMAIN-017 은 계속 「외부 산출물 이관」) 변경. LNB 를 접기/펼치기 아코디언으로 바꾸는 것(**사용자가 두 안 중 그룹 헤더 유지를 명시 선택**). 수동 업로드 화면에 경로 탐색을 붙이는 것(그 화면에는 파일시스템 경로 입력 자체가 없다).

## §3 도메인별 변경 상세

### DOMAIN-017 (외부 산출물 이관) — `klid-d017-implementer`

> ⚠ **디스패처 매핑표 정정**: 매핑표는 이 도메인의 code_root 를 *"(신설 — 코드 미착수)"* 로 적고 있으나 **사실과 다르다.** CO-001~CO-004 로 구현이 끝났고 실제 code_root 는 **`transfer/`** 다(`controller/` `service/` `dto/` `entity/` `parser/` `repository/` + 루트의 `ImportSourcePolicy`·`ImportPathPolicy`·`ImportMetaKeys`).

- **대상 파일·심볼**
  - 신설: `transfer/controller/ImportBrowseController.java` (또는 기존 `ImportScanController` 에 병합 — 아래 판단 참조)
  - 신설: `transfer/service/ImportBrowseService.java`
  - 신설: `transfer/dto/ImportBrowseResponse.java`
  - 수정: `backend/src/main/resources/application.yml` — `authoring.import` 블록에 `browse.max-entries` 추가
  - 재사용(수정 금지): `transfer/ImportSourcePolicy.java`

- **변경**

  **① 탐색 엔드포인트 2개** — 클래스 레벨 `@RequestMapping("/v1/imports")` + `@PreAuthorize("hasRole('REVIEWER')")` 아래에 둔다(기존 `ImportScanController` 와 동일 계약면).

  | 엔드포인트 | 파라미터 | 돌려주는 것 |
  |---|---|---|
  | `GET /v1/imports/folders` | `path` (선택) | `path` 생략 시 **허용 루트 목록**, 지정 시 그 폴더의 **하위 폴더 목록** |
  | `GET /v1/imports/files` | `path` (필수) | 그 폴더의 **영상 파일 목록** |

  > **동사형 URL(`/browse`)을 쓰지 않는다** — `.claude/rules/api-design.md` 가 URL 동사 사용을 금지한다. 두 개의 명사 리소스로 가르면 「폴더 고르기」와 「파일 고르기」가 각각 자기 자원을 갖는다. **한 엔드포인트에 `kind=folder|file` 로 분기하지 말 것** — 같은 URL 의 쿼리 파라미터 행위 분기도 같은 규칙이 금지한다.

  **② 판정은 `ImportSourcePolicy` 를 호출만 한다 — 복제 금지 (Critical)**
  - `path` 가 주어지면 **`verifyFolder(path)`** 를 호출하고 **그 반환 실경로로만** `Files.list` 한다. 표기 경로로 다시 열지 말 것(CWE-367 — 그 정책의 javadoc 이 이 이유를 이미 적어 뒀다).
  - `path` 가 비면 **`readableRoots()`** 를 그대로 목록으로 돌려준다. 허용 루트 목록을 이 서비스가 따로 조립하지 않는다 — 목록이 두 벌이 되면 한쪽만 넓어진다(정책 javadoc 의 명시된 설계 의도).
  - 경로순회(CWE-22)·심링크 우회(CWE-59)·길이·범위 밖 400·메시지에 입력 원문 미노출(CWE-209)은 **전부 그 정책이 이미 한다.** 같은 검사를 여기서 다시 쓰지 말 것.

  **③ 나열 상한 + 절단 고지 (CWE-770)**
  - `@Value("${authoring.import.browse.max-entries:2000}")` 로 상한을 두고, `application.yml` 의 `authoring.import` 블록에 `browse: { max-entries: ${IMPORT_BROWSE_MAX_ENTRIES:2000} }` 를 **명시 선언**한다(기존 `scan.max-entries` 와 같은 형태 — 그 선례가 `application.yml:642-644`).
  - **잘랐으면 잘랐다고 응답이 알린다** — `truncated: true`. 이 저장소는 조용한 절단을 결함으로 취급한다(이벤트유형 옵션의 `truncated` 선례).

  **④ 나열 규칙**
  - `Files.list` 는 **`NOFOLLOW_LINKS` 기준으로 종류를 판정**한다 — 심링크는 폴더로도 파일로도 세지 않고 **건너뛴다**. 이관 검사(`ImportScanService`)가 이미 "폴더 안의 바로가기를 건너뛴 사실"을 경고로 다루므로 축이 같다.
  - 이름이 `.` 으로 시작하는 항목은 목록에서 제외한다(숨김).
  - **읽기 권한이 없는 하위 항목은 목록에서 빠질 뿐 요청 전체를 실패시키지 않는다** — 한 폴더의 권한 문제로 탐색이 통째로 죽으면 안 된다. 다만 **그 폴더 자체를 열 수 없으면** 정책이 던지는 예외를 그대로 올린다.
  - 정렬은 **이름 오름차순**(`Comparator.naturalOrder()`). 파일시스템 순서는 비결정적이라 화면이 매번 달라진다.
  - `files` 는 **영상 확장자만**(`.mp4`·`.mov`·`.avi` — 대소문자 무시) 돌려준다. 이 필드의 최종 소비자가 `verifyVideoFile` 로 다시 검증되는 「원본 영상 경로」이기 때문이다. 확장자 목록은 상수 한 곳에 두고 매직 문자열을 흩지 않는다.

  **⑤ 응답 계약** — `ApiResponse<T>` 래퍼 안에:
  ```
  {
    "path": "<판정된 실경로 — 화면이 그대로 입력칸에 넣는다>",
    "parent": "<상위 경로. 허용 루트 자신이면 null>",
    "entries": [{ "name": "00000073", "path": "/nas-storage/handover/00000073" }],
    "truncated": false
  }
  ```
  - `parent` 가 **허용 루트를 벗어나면 `null`** 이어야 한다. 여기서 루트 위로 올라가는 길을 열어 주면 정책이 막은 범위를 응답이 되돌려 주는 꼴이다.
  - `path` 는 **판정에 사용한 실경로**를 돌려준다. 화면이 이 값을 입력칸에 넣고, 그 값이 다시 `verifyFolder` 를 통과해야 하므로 표기 경로를 돌려주면 심링크 폴더에서 왕복이 어긋난다.

- **불변(건드리면 안 되는 것)**
  - `ImportSourcePolicy` 의 판정 로직·상수(`FOLDER_PATH_MAX=300`·`VIDEO_PATH_MAX=1000`)·예외 코드. **읽기 전용으로 재사용**한다.
  - 기존 `POST /v1/imports/scan`(API-205)·적재(API-206)·이력(API-207/208)·분류 대응(API-209/210/211)·API-215 의 요청·응답 계약. **탐색은 완전히 새 엔드포인트이며 기존 계약을 넓히지 않는다.**
  - `VideoArtifactRootResolver` 의 허용 루트 구성.

- **주의**
  - **허용 루트 밖은 400 이고 부재는 404 다** — 그 갈림은 정책이 소유한다. 탐색 API 가 자기 판단으로 코드를 바꾸지 말 것. 특히 **존재 여부를 범위 검사보다 먼저 보지 않는다**(CWE-209 — 정책이 그 순서를 의도적으로 잡아 뒀다).
  - **디렉터리가 아주 클 수 있다.** NAS 인계 폴더는 수천 건이 정상 범위다 — 상한 없이 `Files.list().toList()` 하지 말 것.
  - 마운트가 끊기면 목록이 **비어서** 돌아온다. 그건 "폴더가 비었다"와 구분되지 않으므로, 화면이 오해하지 않도록 빈 목록도 정상 응답으로 내려보내고 판단은 화면에 맡긴다(억지 오류를 만들지 말 것).

- **수용기준**
  - `GET /v1/imports/folders`(파라미터 없음) → `readableRoots()` 와 **같은 목록**이 돌아온다.
  - 허용 루트 밖 경로 → **400**, 메시지에 입력 원문이 들어 있지 않다.
  - 허용 루트 안의 존재하지 않는 경로 → **404**.
  - `..` 를 섞은 경로가 정규화 후 루트 밖으로 떨어지면 → **400**.
  - 루트 안의 심링크가 밖을 가리키면 → **400**(실경로 기준 재판정에 걸린다).
  - 하위 항목이 상한을 넘으면 → 목록이 잘리고 `truncated: true`.
  - WORKER 토큰 → **403**(클래스 레벨 `@PreAuthorize`).
  - `files` 응답에 폴더·비영상 파일·심링크가 섞이지 않는다.

## §4 영향·리스크

- **하위호환**
  - 기존 API 계약 변경 **0건**. 탐색은 신규 엔드포인트 2개 추가뿐이다.

  - DB 변경 0건 → 데이터 마이그레이션·롤백 부담 없음.

- **되돌리기**
  - 메뉴·제목: 커밋 되돌리기로 끝난다(상태를 남기지 않는 순수 표시 변경).

- **리스크**
  - ⚠ **허용 루트 하위가 열거 가능해진다 (사용자 인지·수용)**. 범위 자체는 이관 화면이 이미 경로를 받아주던 그 범위와 **정확히 같아** 새 표면이 열리는 것은 아니지만, "그 안에 무엇이 있는지"는 새로 보인다. 사용자가 이 점을 명시 안내받고 진행을 선택했다. **이것을 결함으로 재분류해 되돌리지 말 것.**
  - 판정 로직을 복제하면 허용 루트가 두 벌이 되어 한쪽만 넓어진다 — §3 이 "호출만 한다"를 Critical 로 못 박은 이유다.
  - 상한 없는 나열은 대용량 NAS 폴더에서 응답 폭주(CWE-770)가 된다.
  - LNB 항목 이동 중 `allow` ↔ 라우트 가드 대응이 깨지면 인가 비대칭이 생긴다.

**`ADR-039` v6 — 사용자 확정 후 개명 완료**: 본문 8회 + 제목 1회의 옛 화면명을 `파일 업로드` 로 바꿨다. 9회 전부 **현재 살아있는 화면**을 가리켰고 역사적 "옛 이름" 참조는 하나도 없어 일괄 치환이 성립했다(문자 단위 diff 로 변경 구간이 전부 `수동`→`파일` 임을 확인). **결정 자체는 불변** — 두 축의 기본값이 갈린다는 것도, 파일 업로드가 운영 상시 기능이고 dev 로그인은 운영 부팅을 거부한다는 것도 그대로다.
> ADR 은 결정 시점 기록이라 소급 개명하지 않는 것이 통례인데 여기서 따르지 않은 이유는, 이 ADR 이 **지금도 유효한 운영 정책**을 규정해 옛 이름을 두면 독자가 그 화면을 찾지 못하기 때문이다. 경위는 `change_summary` 에 보존했다(그래서 `change_summary` 에만 옛 이름 1회가 남는다 — 의도).

**보지 않은 층 (정직 고지)**: `docs/v2-wiki/` · `docs/test-cases/` · 로컬 키트 스냅샷(`docs/design/`·`docs/screen-design/`) · 코드. 이 셋은 Phase 4~6 대상이다.
