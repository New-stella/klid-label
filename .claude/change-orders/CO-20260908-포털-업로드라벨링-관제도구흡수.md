## §1 배경

사용자가 포털향 저작도구에 들어가 라벨링 화면을 열었더니 **평소 쓰던 화면이 아니라 처음 보는 미니멀한 화면**이 떴다. 사용자 원문:

> "포털향 저작도구의 라벨링 화면이 아예 엉뚱한 화면이 됐다. 원래 멀쩡한 화면이었는데 어느 순간 엉뚱한 미니멀한 화면으로 바뀌었다. 기존 관제서버용 라벨링 도구에서 AI 기능만 빼면 되는 것 아니냐."

실측한 원인은 **포털 라벨링의 본문이 두 벌**이라는 것이다. `frontend/src/pages/portal/PortalLabelingPage.tsx`(디스패처)가 주소의 `?source=upload` 표기 유무로 갈라진다.

| 출처 | 렌더하는 본문 | 정체 |
|---|---|---|
| 데이터마트 (`/portal/label/{srcSn}`) | `pages/label/LabelingPage.tsx` **2,243줄** | 관제용 라벨링 도구 + `portalMode` 게이팅. **사용자가 기대하는 그 화면이며 이미 정상 동작한다** |
| 업로드 자산 (`?source=upload`) | `pages/portal/PortalUploadLabelingView.tsx` **459줄** | 처음부터 새로 짠 별도 미니멀 화면 |

미니멀 화면은 `CanvasShell` 만 라벨링 코어에서 빌려 쓰고 **툴바(SELECT/PAN/BBOX/POLYGON 4종을 자체 구현)·우측 객체 패널(`ObjectClassTree`)·프레임 필름스트립·라벨 선택 모달·라벨 속성 패널·단축키·캔버스 옵션바가 전부 없다.** 라벨 분류 선택도 도구바 옆의 `<select>` 하나로 대체돼 있다.

**즉 "관제 도구에서 AI만 뺀" 자산은 이미 만들어져 잘 돌고 있는데, 업로드 갈래만 그것을 안 쓰고 따로 만든 것이 문제다.** `portalMode` 가 실제로 가리는 것을 실측하면 정확히 사용자가 말한 그 형태다.

| 가려지는 것 | 배선 지점 |
|---|---|
| SAM2 분할 · 자동추적(TRACK) · 키포인트 도구 | `features/label/types.ts:218 PORTAL_HIDDEN_TOOLS` (단일 소스) |
| 오토라벨 액션 | 도구바 `portalHidden` 플래그 (`ToolBar.tsx:363` 부근 `visible()`) |
| 자동추적 패널 | `LabelingPage.tsx:2090` `{!portalMode && <AutoTrackPanel …>}` |
| 속성 패널의 추적 실행 | `LabelingPage.tsx:2116` `track={portalMode ? undefined : …}` (도구바 차단과 별개의 2중 방어) |
| 트랙 rename/merge · 검수 제출 · 버전관리 · 비식별 신고 · 프레임 폐기·복원 | 각 지점 `portalMode` 분기 (`:646` `:837` `:1261` `:1283` `:1308` `:1825~1831` `:2154`) |

**언제 갈라졌나 (git 이력)**

- `d8613f4ef feat(portal): 포털 전용 이미지/영상 업로드 + 수동 라벨링 (ADR-013 예외)` — 여기서 미니멀 화면이 신설됐다.
- `b258d82b7 feat(portal): 포털 라벨링을 한 화면으로 합친다` — **주소만** 하나로 합치고 본문은 두 벌 그대로 남겼다. 그 커밋의 의도(「같은 작업을 한 자리에서 배우게 한다」)는 이 CO 가 완성한다.

현재 포털의 실제 진입 동선이 업로드 자산 쪽이라(「내 저작 작업」 목록 창구가 코드에 0건) 사용자가 보는 것은 **항상** 미니멀 화면이다.

### 갈라져 있던 진짜 제약

프레임 라벨의 조회·저장 **창구**가 출처마다 다르다.

| 축 | 업로드 자산 | 데이터마트 |
|---|---|---|
| 라벨 조회 | `GET /v1/portal/uploads/frames/{uldFrmeSn}/labels` (`useUploadFrameLabels`) | `GET /v1/portal/frames/{srcSn}/labels` (`useLabels(srcSn, portalMode)` → `getPortalLabels`) |
| 이미지 | `GET /v1/portal/uploads/frames/{uldFrmeSn}/image` (`useUploadFrameImage`) | `GET /v1/portal/frames/{srcSn}/image` (`useImageBlob(srcSn, {portalMode})`) |
| 저장 | `PUT /v1/portal/uploads/frames/{uldFrmeSn}/labels` — **최상위 raw 배열** (`useSaveUploadLabels`) | 포털 저장 경로 (`useSavePortalLabels`) |
| 프레임 목록 | 자산 상세 `getUpload(uldSn).frames[]` | 라벨 응답의 `data.siblings[]` |
| 경로 `:id` 가 가리키는 것 | 자산(`uldSn`) — 현재 프레임은 `?frame=` 이 나른다 | 프레임(`srcSn`) 자체 |

⚠ **그런데 `ADR-058` 이후 이 차이는 표가 아니라 창구에만 남아 있다.** 업로드 자산은 공용 원장에 앉아 있고 **자산 식별자가 곧 영상 식별자, 프레임 식별자가 곧 공용 원장의 프레임 PK** 다 — 폐기 대상 화면의 주석이 이미 그렇게 적고 있다(*"업로드 자산의 프레임·자산 식별자는 공용 원장의 프레임 PK·영상 PK 그 자체다(창구·화면의 이름만 업로드 어휘로 남아 있다)"*). 즉 필요한 것은 데이터 모델 변환이 아니라 **창구 이름 번역**이다.

⚠ **`:id` 비대칭은 없앨 수 없다.** 업로드가 자산으로 여는 이유는 목록에서 행을 누르는 시점에 **첫 프레임 식별자를 알 수 없기** 때문이다(목록 응답이 프레임 식별자를 싣는 것은 단일 프레임 자산뿐). 이 제약은 그대로다.

### 흡수 이음매가 좁은 이유 (실측)

`LabelingPage` 는 프레임 목록을 **별도 조회가 아니라 라벨 응답의 `data.siblings`** 에서 파생한다(`LabelingPage.tsx:288~314`). 현재 프레임 인덱스도 `frames.findIndex(f => f.srcSn === data.srcSn)` 로 정한다(`:317`). 즉 화면이 요구하는 것은 **`{ srcSn, frameNo, siblings[], videoId, items[] }` 모양의 `data` 하나**이며, 업로드 출처에서 그 모양을 만들어 주면 **화면 본문은 손댈 것이 거의 없다.**

  5. **미저장 편집 보호를 잃지 않는다.** 폐기 화면은 전체교체 PUT 때문에 「dirty>0 이면 조회 응답으로 덮지 않고, 첫 로드에 한해 병합」을 걸고 있었다(`PortalUploadLabelingView` 의 `loadedFrmeSnRef` 블록). `LabelingPage`·`useLabels`(`refetchOnWindowFocus:false` · `staleTime:30s`)의 동등 방어가 이 자리를 실제로 덮는지 **실측으로 확인**한다. 확인 없이 "코어에 있겠지"로 넘기지 말 것 — 이건 작업 통째 유실 경로다.
  6. **메타 다섯 축·이벤트 어노테이션(`PortalWorkMetaTab`)이 사라지지 않는다.** 업로드 자산에도 촬영환경·프레임 설명·개인정보 판정·시계열 메타·이벤트 어노테이션이 표시·수정돼야 한다(2026-09-02 확정). `LabelingPage.tsx:2007` 의 포털 전용 메타 본문이 그 자리를 덮는지 확인하고, 덮으면 중복 배치하지 않는다. **저장처는 화면이 가르지 않고 서버가 자산 출처로 판정한다.**
  7. **라벨 내보내기·원본 파일 내려받기를 이 화면에 두지 않는다** — 자산 단위 조작이라 자산 목록 화면의 행 액션이 갖는다(확정 사양). 흡수하면서 되살리지 말 것.
  8. **비식별 누락 신고 게이트는 업로드 갈래에 없다** — 내부 파이프라인의 비식별 라이프사이클 자체가 없다. `portalMode` 가 이미 가리므로 별도 조건을 이어붙이지 않는다.
  9. **`labelId` 배선 유지.** `classId` 만 채우면 저장 후 라벨 마스터 조인이 끊겨 색·라벨명·속성 정의가 함께 죽는다(저장 **전**에는 정상으로 보여 발견이 늦는 실사고 이력). 생성 payload 는 `OverlayLayer.newLabelFrom` 단일 진입점을 거친다.
  10. **데이터마트 갈래의 동작을 바꾸지 않는다.** 이 CO 는 업로드 갈래를 끌어올리는 것이지 데이터마트 갈래를 건드리는 것이 아니다. `useLabels`·`useImageBlob` 에 축을 더할 때 **기본값이 현행 동작**이어야 한다.

- **주의 (이 화면 특유의 함정)**

  - **썸네일 창구 전파 누락**이 가장 놓치기 쉽다(변경 4번). 메인 캔버스만 고치면 화면은 뜨는데 필름스트립이 통째로 깨진다.
  - **`CanvasShell` 의 `srcSn` 계약.** 폐기 화면은 `uldFrmeSn` 을 `srcSn` 자리에 어댑팅하고 *"본 화면은 SAM 미노출이라 srcSn 기반 SAM2 훅은 발화하지 않는다"* 로 안전을 확보했다. 흡수 후에도 같은 어댑팅을 쓰되 **SAM2 훅이 `portalMode` 로 확실히 꺼져 있는지** 확인한다 — 켜지면 업로드 프레임 PK 로 내부 SAM2 창구를 부른다.
  - **`useLabelStore` 진입/이탈 정리.** 폐기 화면은 `reset()` 을 진입·이탈에 걸어 다른 화면 잔존을 막았다. `LabelingPage` 의 동등 처리를 확인한다.
  - **저장 후 dirty 해제.** 폐기 화면은 `onSuccess` 에서 `clearDirty()` 를 부르지 않으면 위 5번 가드가 계속 걸려 **그 프레임이 서버와 영영 재동기화되지 않는다**고 주석에 적어 뒀다. 같은 함정이 흡수 경로에도 있다.
  - **`?frame=` 값이 목록에 없을 때** 첫 프레임으로 읽는다(현행). 예외를 던지거나 빈 화면을 내지 않는다.

- **수용기준**

  1. `/portal/label/{uldSn}?source=upload` 로 진입하면 **데이터마트 갈래와 동일한 화면 구조**가 뜬다 — 도구바 · 우측 객체 패널 · 프레임 필름스트립 · 라벨 속성 · 단축키 · 캔버스 옵션바.
  2. 그 화면에 **SAM2 분할 · 자동추적 · 키포인트 · 오토라벨 진입점이 하나도 없다**(도구바·패널·단축키 전부).
  3. 트랙 rename/merge · 검수 제출 · 버전관리 · 비식별 신고 · 프레임 폐기 진입점이 없다.
  4. 라벨 조회·이미지·저장이 **자산 축 창구**(`/portal/uploads/frames/...`)로 나간다. 데이터마트 갈래는 종전대로 프레임 축 창구로 나간다.
  5. 필름스트립 썸네일도 자산 축 창구로 나간다(404/403 없음).
  6. 프레임 이동 시 `?frame=` 만 바뀌고 이력에 쌓이지 않는다. 뒤로가기·새로고침·주소 공유가 두 갈래에서 같게 동작한다.
  7. 저장 중 캔버스·도구·프레임 이동이 차단되고 진행 오버레이가 뜨며 거기서 취소할 수 있다.
  8. 미저장 편집이 있는 상태에서 조회 응답이 도착해도 작업본이 사라지지 않는다.
  9. 자산이 `READY` 가 아니면 상태별 안내가 뜬다(`FAILED` / 준비 중). 프레임 0건은 `role="status"` 상태 안내다.
  10. 메타 다섯 축·이벤트 어노테이션 패널이 업로드 자산에서도 보이고 수정·저장된다.
  11. 저장 후 재조회에서 라벨의 **색·라벨명·속성 정의가 유지**된다(`labelId` 조인 생존).
  12. `PortalUploadLabelingView.tsx` 가 저장소에서 사라지고 참조 0건이다.

**해당 없음.** BE·`common/`·`batch/`·`db/migration/`·앱 진입점 변경 없음. 프론트 데이터 계층 안에서 끝난다.

### ★이 라운드에서 배운 것

1. **기준선을 `git archive HEAD frontend` 만으로 뜨면 가짜 빨강 43건이 난다.** FE 시험 여섯이 `readFileSync` 로 `deploy/onprem/`·`backend/` 를 읽는 **배포형상 정합 가드**라 그 파일이 없으면 죽는다. 구현 담당이 그것을 「기준선이 원래 빨갛다」로 보고했고 **독립 QA 가 완전 기준선을 떠서 정정**했다(557/4832 전건 초록).
   ⚠ **결론이 맞아도 서술이 틀리면 위험하다** — 「기준선이 원래 빨갛다」가 장부에 남으면 **다음 라운드가 진짜 회귀를 그 문장 뒤에 숨긴다.**
   ⇒ **앞으로 FE 기준선은** `git archive HEAD frontend backend deploy ai-server mock-server docker …` 로 뜬다.

2. ★**시험이 통과하는 시점·상태가 결함이 드러나는 시점·상태와 다른 함정 4종** — 이 라운드에서 둘, 같은 날 타 세션에서 둘이 실측됐다.

   | 함정 | 시험이 놓치는 것 | 이 라운드 사례 |
   |---|---|---|
   | 비동기를 동기로 읽음 | 효과가 반영되기 **전에** 읽는다 | 「미저장 편집이 안 덮인다」가 `refetchQueries()` 직후 동기 단언이라 **덮어쓰는 구현에서도 초록**이었다 |
   | 진입 순서 미재현 | 실사용이 지나는 **전이**를 안 지난다 | (타 세션) |
   | 왕복 후 상태 미확인 | 깨지는 **시점 이후**를 안 본다 | `labelId` 는 **저장 전에는 정상으로 보이고 저장 후에만** 끊긴다 |
   | **해제만 단언** | **걸리는 쪽을 안 본다 — 애초에 안 걸려도 통과** | 승계본이 저장 **중** 차단은 안 보고 **취소 후 풀리는 것**만 봤다 |

   ⇒ **변이 검증으로만 잡힌다. 통과만으로 가드라고 주장하지 않는다.**
