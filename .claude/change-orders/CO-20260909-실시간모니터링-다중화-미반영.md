# CO-20260909 — 실시간 모니터링이 AI·시계열 장비 다중화를 보여주지 않는다

| | |
|---|---|
| 생성일 | 2026-09-09 |
| 대상 도메인 | DOMAIN-014(시스템 설정) · 프론트 |
| 발견 경위 | 사용자 지적 — *"시스템 설정 실시간 모니터링에 AI 서버가 단중화만 보고 있는 것 같다"* |
| 심각도 | **높음** — 장비 절반이 죽어도 화면이 「정상」이라 부분 장애를 운영자가 못 본다 |

## §1 배경

시스템 설정 화면의 **실시간 모니터링(외부 연동 상태)** 은 컴포넌트마다 **배지 하나**만 그린다.
그런데 AI 추론과 외부 시계열 분석은 **장비를 여러 대 등록해 그중에서 골라 보내는 계통**이다
(`SCREEN-042` 장비 원장). 그 다중화가 화면에 전혀 드러나지 않는다.

**구현이 사양을 어긴 것이 아니라 사양이 다중화를 모른다.** `SCREEN-025` 의 그 부품 사양은
*"응답이 돌려주는 컴포넌트별 상태(UP/DOWN 등)를 표시한다"* 가 전부다 — 장비 원장이 나중에
생겼는데 이 카드가 그것을 배우지 못한 상태다.

⚠ **백엔드는 이미 다 계산해서 보내고 있다.** `GET /v1/manage/health` 응답의 `details` 에
`nodes` · `byNode` · `usable` · `reachable` · `unselectable` · `ledgerStatus` · `observation` 이
들어 있다. **화면이 그걸 버린다**(`latencyMs` 와 `url` 만 읽는다).

## §2 지금 실제로 일어나는 일

판정이 `usable == 0 ? UNKNOWN : (reachable > 0 ? UP : DOWN)` 이라 이렇게 된다.

| 상황 | 백엔드가 아는 것 | 화면 | 문제 |
|---|---|---|---|
| 2대 중 1대 무응답 | `usable=2 reachable=1` | **정상** | 가용량 절반 손실이 안 보인다 |
| 원장은 가용인데 식별자 형식 오류 | `unselectable=1` | **정상** | 영영 고를 수 없는 장비인데 초록이다 |
| 상태점검 배치 꺼짐 | `observation=disabled` | 표시 없음 | 원장 값이 낡았는데 그걸 모른다 |
| 등록 0대 / 전부 못 고름 | `usable=0` + `reason` | **알 수 없음** | **사유를 안 알려 준다** — 조치가 갈리는데 |

★ 마지막 줄이 특히 중요하다. **「알 수 없음」은 "장비가 응답을 안 한다"가 아니라 "보낼 장비가
원장에 없다"** 는 뜻이다. 그 상태면 오토라벨링·분할·시계열 위탁이 **아예 나가지 않는다.**
백엔드는 사유까지 구분해 두었다(`no-usable-node` / `no-selectable-node-id-format`) — 조치가
완전히 다르기 때문이다(장비를 올리는 것 vs 원장의 식별자를 고치는 것). 화면이 그걸 버린다.

## §3 변경 요지

### ① 화면이 자체 헬스체크를 하지 않는다 (사용자 확정)

> *"헬스체크는 어차피 2중화 쪽에서 하니깐 굳이 저 화면에서 또 헬스체크를 호출할 필요는 없을 듯"*

지금은 **요청마다 장비 수만큼 동기 핑**이 나간다(`healthProbe.ping(node)` 를 노드 루프 안에서
호출). 화면은 주기 폴링이므로 관리자가 열어 두면 그 핑이 계속 나간다. 그런데 **상태점검 배치가
이미 같은 일을 주기적으로 하고 원장에 결과를 쓴다**(`CHCK_DT`, 연속 실패 임계 도달 시 상태 전이).

⇒ **모니터링 카드는 원장과 상태점검 결과를 읽어 보여준다.** 자체 핑을 하지 않는다.

- **얻는 것**: 중복 관측 제거 · 화면을 열어 둔 만큼 늘던 부하 제거 · 무엇보다 **화면이 보여주는
  상태와 실제로 장비를 고르는 판정이 같은 원천**이 된다(지금은 두 관측이 어긋날 수 있다).
- ⚠ **대가(인지·수용 대상)**: 원장 값은 **주기 × 연속 실패 임계**만큼 늦다. 즉 방금 죽은 장비가
  잠시 「가용」으로 보인다. 그래서 **마지막 점검 시각을 함께 보여주고**, **상태점검이 꺼져 있으면
  반드시 그 사실을 표시**해야 한다(꺼진 채로 원장 값을 보여주면 그것은 거짓말이 된다).

### ② 다중화를 화면에 드러낸다 — AI 추론과 외부 시계열 **둘 다** (사용자 확정: *"vlm도 동일하게"*)

```
비식별 서버        [정상]        12ms

AI 추론 서버      [주의]  2대 중 1대 응답      ▾
  └ ai-infer-01   응답      원장 가용
  └ ai-infer-02   무응답    원장 가용
  └ 상태점검 켜짐

외부 시계열 분석   [정상]  2대 중 2대 응답      ▾

데이터베이스       [정상]         3ms
```

- 배지 옆에 **가용/응답 수 요약**을 병기해 부분 장애가 접힌 상태에서도 드러나게 한다.
- 펼치면 **장비별**로 식별자 · 응답 여부 · 원장 상태 · **고를 수 없음 표식** · 마지막 점검 시각.
- **상태점검 켜짐/꺼짐**을 함께 표시한다.
- **「알 수 없음」이면 사유를 문장으로 말한다** — 「등록된 장비가 없다」 / 「식별자 형식이 맞지 않아
  고를 수 있는 장비가 없다」. 조치가 다르므로 반드시 갈라 적는다.
- 단일 대상(비식별 서버 · 데이터베이스)은 **지금 모양 그대로 둔다**. 다중화 축이 아니다.

### ③ 하지 않을 것

- **판정 자체는 바꾸지 않는다** — `reachable > 0 → UP` 을 「한 대라도 죽으면 주의」로 내리지 않는다.
  그 값은 전체 상태(`allUp`)에도 쓰이고 다른 관측 창구도 같은 인디케이터를 본다. **판정을 옮기면
  그것들이 함께 바뀐다.** 이번 변경은 **표시**를 고치는 것이지 판정을 옮기는 것이 아니다.
  (부분 장애는 판정이 아니라 **요약 문구와 펼침**으로 드러낸다.)
- 백엔드 응답 계약(`details` 필드 구성)은 **추가 없이 그대로 쓴다**. 화면이 이미 오는 값을 안 읽고
  있을 뿐이다. 다만 ①에 따라 **인디케이터가 요청마다 핑하지 않도록** 하는 변경은 백엔드에 있다.

## §4 영향·리스크

- **영향**: 시스템 설정의 실시간 모니터링(AI 추론 · 외부 시계열 두 칸) · 두 헬스 인디케이터.
- **비영향**: 장비 원장 화면(`SCREEN-042`) · 라우팅·선택 로직 · 상태점검 배치 자체.
- **리스크**: ① 로 관측이 원장 기준이 되면서 **표시가 최대 (주기 × 임계)만큼 늦는다.** 그 지연을
  「마지막 점검 시각」과 「상태점검 켜짐 여부」로 드러내지 않으면 오히려 지금보다 나빠진다.

## §5 검증

1. 장비 2대 중 1대를 내린 상태에서 **접힌 배지만 보고도** 부분 장애를 알 수 있다.
2. 상태점검을 끈 상태에서 화면이 **꺼져 있음을 표시**한다.
3. 등록 0대와 식별자 형식 오류가 **서로 다른 문장**으로 안내된다.
4. 화면을 열어 둔 동안 **장비로 나가는 핑이 늘지 않는다**(①의 실측 근거).
5. 단일 대상 두 칸(비식별·데이터베이스)의 표시가 **바뀌지 않는다**.

## §8 온프렘에서 「알 수 없음」이 뜨는 이유 — 화면이 못 말하는 것의 실사례

**사용자 확인 (2026-09-09)**: *"지금은 방화벽이 안 뚫려 있다. 지금이 6일 배포향이라 그럴 것"*

연쇄는 이렇다.

```
방화벽 차단 → 상태점검 핑 연속 실패 → 연속 실패 임계(기본 3) 도달
           → 폴러가 장비를 자동으로 「이용불가」로 내림
           → usable = 0  → UNKNOWN(알 수 없음)
```

★**방화벽만 막혔다면 「연결 끊김」이 떠야 한다**(`usable>0` · `reachable=0` → DOWN).
「알 수 없음」이 뜬다는 것은 **원장이 이미 전부 이용불가로 내려갔다**는 뜻이고, 곧
**장비는 원장에 등록돼 있다**는 뜻이다(등록이 없으면 실패할 대상 자체가 없다).

⚠ **구 서술 폐기** — 이 절은 원래 *"설치·운영 문서에서 장비 등록 절차를 찾지 못했다. 시드도 0건이니
온프렘 원장이 비어 있어 그것이 「알 수 없음」의 설명이다"* 였다. **근거가 약했다** — 문서에서 못 찾은
것을 없다고 단정했고, 위 연쇄가 훨씬 잘 맞는다. 되살리지 말 것.
(등록 절차가 문서에 있는지 자체는 여전히 확인되지 않았으나, 그것이 이 증상의 원인은 **아니다**.)

### ★이 사례가 곧 이 CO 의 근거다

그 순간 백엔드는 이것을 **이미 알고 있었다.**

| 백엔드가 담아 보낸 값 | 뜻 |
|---|---|
| `ledgerStatus` 가 전 장비 `UNAVAILABLE` | 상태점검이 자동으로 내린 것 |
| `observation: enabled` | 상태점검 자체는 돌고 있다 |
| `reason: no-usable-node` | 식별자 형식 문제가 아니라 가용 장비가 0 |

셋만 보였어도 **「상태점검이 계속 실패해 장비가 전부 내려갔다 → 망을 보라」** 로 바로 읽혔다.
지금 화면은 **「알 수 없음」 넉 자**뿐이라 등록 누락인지 · 사람이 내려 둔 것인지 · 망 문제인지
구분되지 않는다. §3-② 의 「사유를 문장으로 말한다」가 정확히 이 자리를 겨냥한다.

⚠ 온프렘 배포본은 **2026-09-06 향**이다(`BUILD-INFO` `built_at=2026-09-06` · `git_commit=aa30f887`).
이 CO 의 수정이 반영되려면 재배포가 선행된다.
