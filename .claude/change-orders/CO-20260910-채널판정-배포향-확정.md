## §1 배경

### 증상 (2026-09-10 개발망 실측)

포털 Host 안에서 저작도구 Remote 가 **정상 로드되는데** 화면이 「접근 권한이 없습니다」로 막힌다.
배선은 전부 통했다 — `remoteEntry.js` 200 · 청크 전부 200 · 앱 부팅 · 라우터 동작 ·
Host 인계 창구(`authBridge`) 4종 모두 주입됨 · `/authoring-api/v1/me` **200**.

### 포털이 넘기는 인계 토큰 (실측)

클레임은 **`sub` · `loginId` · `role` · `typ` · `iat` · `exp`** 뿐이다. **`channel` 과 `iss` 가 없다.**
`role` 값은 `"ADMIN"`(포털 어휘)이고 `sub` 는 포털 회원 식별자(`mbrId`) 문자열이다.

★ **이것은 포털의 결함이 아니라 계약대로다.** `INT-013` 「계약 경계 — 상대에게 채널 값을 요구하지
않는다」가 명시한다 — *"저작도구가 채널마다 별도로 배포되므로 배포본이 이미 알고 있는 사실이고,
그것을 상대의 토큰에 실어 달라고 요청하는 것은 우리 배포 형상을 상대에게 떠넘기는 것"*.
같은 문서가 *"채널 클레임이 없는 것은 누락이 아니다"* 라고 못박는다.

### 근본 원인 — 확정된 설계가 코드에 없다

`ADR-012` 「★ 채널 판정 축 — 배포 향이 정한다」(2026-09-09 사용자 확정, **구속**)가 이 상황을
이미 규정했는데 **구현이 따라오지 않았다.** `AC-1103` 이 그 사정을 적어 두고 있다 —
*"채널 판정 축 결정의 전파 표식이 **네 차례 지워져** 상기시켜 줄 장치가 남아 있지 않았다"*.

실측 확인: `KLID_DEPLOY_FLAVOR` 는 `deploy/onprem/**` 설치 스크립트와
`frontend/src/lib/buildChannel.ts` **주석**에만 있고 `backend/src/main` 에 **0건**이다.

### 지금 실제로 벌어지는 일

```
포털 토큰 도착 (channel 없음)
 └ BE  JwtAuthenticationFilter:157  channelStr == null ? INTERNAL : valueOf(...)
        → INTERNAL 로 해석
        → UserRoleResolver 가 관제 userNo 로 LS 조회 → 없음
        → AC-1016 작업자 자동 등록이 돌아 WORKER 로 «등록»
        → /v1/me 가 {channel:"INTERNAL", role:"WORKER"} 200
 └ FE  useAuthStore.decodeJwtPayload  channel 부재 → Channel.INTERNAL
        → ChannelGuard channel="PORTAL" 이 거부 → PortalEmbedNotice(forbidden)
```

`ADR-012` 가 이 fail-open 을 정확히 예견해 두었다 — *"포털 사용자가 관제 채널 사용자로 해석되어,
관제 채널 전용 경로(사용자 역할 조회 · 미배정 사용자 자동 등록 · 최종 접속 기록 · 주체 식별자
정규화)가 그대로 돌고 정작 포털 전용 창구는 차단된다"*. **실측이 그 서술과 정확히 일치한다.**

### ★ 범위가 작다 — 포털 분기는 이미 다 있다

`JwtAuthenticationFilter` 의 `else` 가지(= PORTAL)는 **이미 계약대로 구현돼 있다**:
`role = Role.PORTAL_USER` 고정 · LS 미조회 · 자동 등록 안 돎 · 최종접속 기록 안 함 ·
`sub` 를 문자열 원문으로 보존. **발동하지 않았을 뿐이다.**

## §2 변경 요지

**채널 판정의 입력을 「토큰 클레임」에서 「배포 향」으로 바꾼다.**

1. 백엔드에 **배포 향** 개념을 들인다 — 값역 `control`|`portal`, 미선언·값역 밖이면 **`control`**(fail-closed).
   `ADR-012` 가 *"인증 전용 설정을 새로 두지 않는다"* 고 못박았으므로 **이미 규정된
   `KLID_DEPLOY_FLAVOR` 를 그대로 재사용**한다.
2. 배포 향이 `portal` 이면 인계 토큰의 채널 값을 **읽지 않고** `PORTAL` 로 **강제**한다(기본값 전환이 아니다).
   `control` 이면 **종전 그대로**(값 있으면 그 값, 없으면 `INTERNAL`).
3. 프론트도 같은 축으로 맞춘다 — **빌드 채널이 `portal` 이면** 토큰의 채널 값을 읽지 않고 `PORTAL` 로
   확정하고, **상대 시스템의 역할(`role`)을 인가 축에 쓰지 않는다**(`null` 로 낮춘다).

⚠ **관제 채널은 한 톨도 바뀌지 않는다.**

## §3 도메인별 변경 상세

### 공유기반 선처리 — 메인 직접 (Phase 3.5)

`common/security` 와 `common/config` 는 도메인 소속이 아니므로 메인이 직접 처리한다.

- **대상 파일·심볼**
  - 신규 `backend/src/main/java/kr/co/cudo/authoring/common/config/DeployFlavor.java` (enum: `CONTROL`, `PORTAL`)
  - 신규 `backend/src/main/java/kr/co/cudo/authoring/common/config/DeployFlavorResolver.java`
    (또는 동등한 단일 빈 — **판정은 한 곳**)
  - `backend/src/main/resources/application.yml` — `authoring.deploy.flavor: ${KLID_DEPLOY_FLAVOR:control}`
  - `backend/src/main/java/kr/co/cudo/authoring/common/security/JwtAuthenticationFilter.java:156-157`
  - `backend/.env.example` — 키 문서화

- **변경**
  1. **배포 향 해석 빈**
     - 값 읽기: `@Value("${authoring.deploy.flavor:}")`. 공백 트림 + **대소문자 무시** 매칭.
     - 값역 밖·공백·null → **`CONTROL`** (fail-closed). **예외를 던져 기동을 막지 않는다** —
       `ADR-012` 가 *"관제 채널로 해석한다"* 로 규정했다(기동 실패가 아니다).
     - `@PostConstruct` 로 **기동 로그 1줄**을 남긴다 — `PublicApiPath.announce()` 와 같은 형태
       (확정값 + 출처). `ADR-012` 위험 절이 *"배포 향 선언 누락·오기는 기동 시점이 아니라 인계
       진입 시점에야 드러난다"* 고 적어 둔 자리이며, 이 로그가 그 관측 수단이다.
     - ⚠ **값역 밖이었다는 사실은 로그에 드러나야 한다** — 조용히 `control` 로 떨어지면
       오기를 영영 못 찾는다. 출처 문구를 「선언(`portal`)」 / 「기본값(미선언)」 /
       **「기본값(값역 밖: '<받은값>')」** 으로 갈라 적는다.
  2. **`JwtAuthenticationFilter` 채널 판정 교체**
     - 현재: `Channel channel = channelStr == null ? Channel.INTERNAL : Channel.valueOf(channelStr);`
     - 변경 후: 배포 향이 `PORTAL` 이면 **`channelStr` 을 아예 읽지 않고** `Channel.PORTAL`.
       `CONTROL` 이면 **위 식 그대로**.
     - 판정 자체는 **해석 빈이 소유**하고 필터는 결과만 받는다(두 곳에서 판정하지 않는다).
  3. **★낡은 지시문 3곳을 함께 고친다 — 이걸 빼면 다음 사람이 결정을 되돌린다**

     | 자리 | 지금 문구 | 왜 위험한가 |
     |---|---|---|
     | `JwtAuthenticationFilter:321`(javadoc) | *"채널 판정은 여전히 JWT `channel` 클레임이 소유한다"* | **확정 결정의 정반대를 「지시」한다.** 서술이 아니라 지시문이라 작업 근거로 읽힌다 |
     | `JwtAuthenticationFilter:247`(주석) | *"channel 클레임 없는 토큰은 위에서 INTERNAL 로 기본값 처리(fail-closed: 내부 사용자 호환)"* | 포털 향에서는 그 처리가 **fail-open** 이다(`ADR-012`) |
     | `SecurityConfig:222`(주석) | *"channel 클레임 없는 토큰은 `JwtAuthenticationFilter` 에서 INTERNAL 로 기본값 처리되므로"* | 위와 같음. **인가 설정 파일**에 있어 더 강하게 읽힌다 |

     - 셋 다 **조건부로 고쳐 쓴다** — *"관제 향에서는 …"*. `ADR-012` 가 *"종전 근거를 지우지 않는다 —
       틀렸던 것이 아니라 **조건부였다**"* 고 명시했으므로 **지우지 말고 조건을 붙인다.**
     - 새 문구는 **판정 소유자**(배포 향 해석 빈)를 가리키고 `@design ADR-012` 를 단다.
     - ⚠ 이 세 자리는 **낱말이 아니라 형태로 훑어** 찾은 것이다(`채널 판정` · `channel 클레임` ·
       `채널 클레임`). 구현 중 같은 축을 **그 낱말 없이** 말하는 자리를 더 만나면 함께 고치고 보고한다.

- **불변(건드리면 안 되는 것)**
  - `channel == Channel.INTERNAL` 가지의 **모든 것** — `resolveUserNoByUserId` · `controlUserProvisioner`
    · `autoWorkerRegistrar` · `lastLoginRecorder` · principal `subject` 정규화. 손대지 않는다.
  - `else` 가지(`role = Role.PORTAL_USER`)도 **그대로** 둔다 — 이미 계약대로다.
  - `CHANNEL_*` authority 부여 · `SecurityConfig` 채널 격리 · `Channel.valueOf` 의 미지값 예외(관제 향).
  - 관제 인계 토큰의 **`channel` 부재 → `INTERNAL`** 규칙(`ADR-063`)은 관제 향에서 **유지**한다.

- **주의**
  - ⚠ `ADR-012` 는 **「인증 전용 설정을 새로 두지 않는다」** 고 못박았다. `authoring.auth.channel`
    같은 **새 축을 만들지 말 것** — 같은 사실이 두 곳에 선언되면 어긋났을 때 판정 수단이 없다.
  - ⚠ 값역은 FE `BUILD_CHANNELS`(`control`|`portal`)와 **같은 낱말**이다. `internal` 은 폐기된 구
    값이라 쓰지 않는다(`buildChannel.ts` 주석의 확정 규칙 — 그 낱말은 인증 채널 축을 가리킨다).
  - ⚠ 키 이름은 **둘로 유지**한다 — 빌드타임 `VITE_BUILD_CHANNEL` / 설치시점 `KLID_DEPLOY_FLAVOR`.
    값만 같게 맞추고 **키를 합치지 않는다**(같은 주석의 확정 규칙).
  - ⚠ 이것은 `CO-20260902-채널-판별자-단일화` 와 **다른 축**이다. 그건 「이 **영상**이 어느 채널의
    자산인가」(자산 소유)이고, 이것은 「이 **배포본**이 어느 채널인가」(배포 향)다. 섞지 말 것.

- **수용기준**
  - 배포 향 `portal` + 토큰에 `channel` **없음** → 해석 채널 `PORTAL`, `role=PORTAL_USER`,
    자동 등록·최종접속 기록·`sub` 정규화 **모두 미발동**, `sub` 는 토큰 원문 그대로.
  - 배포 향 `portal` + 토큰에 `channel="INTERNAL"` **있음** → 그래도 `PORTAL`(강제, 값 무시).
  - 배포 향 **미선언** → `CONTROL` 로 떨어지고 종전 동작 그대로.
  - 배포 향 **값역 밖**(`"Portal!"` 등) → `CONTROL` + 그 사실이 기동 로그에 드러난다.
  - 배포 향 `control` → 기존 시험 **전건 무변경**.

### 프론트 — `klid-web-implementer`

- **대상 화면·컴포넌트**: 화면이 아니라 인증 스토어 —
  `frontend/src/stores/useAuthStore.ts` 의 `decodeJwtPayload`
- **소비 API 계약**: 없음(토큰 디코드 축). 역할은 기존 `/v1/me` 경로가 이미 조달한다.
- **변경**
  1. **채널** — `isPortalEmbedChannel()`(`@/lib/buildChannel`)이 참이면 `raw.channel` 을 **읽지 않고**
     `Channel.PORTAL` 로 확정한다. 거짓이면 **종전 로직 그대로**
     (부재→`INTERNAL` / 값 있으면 `isChannel` 검사 / 미지값→`null`).
  2. **역할** — 포털 빌드에서는 토큰의 `role` 을 **인가 축에 쓰지 않는다** → `role = null`.
     근거는 `INT-013` *"상대 시스템의 역할(저작도구 인가 축에 쓰지 않는다)"* 이며 **BE 의 PORTAL
     가지와 대칭**이다(BE 도 토큰 role 을 버리고 `PORTAL_USER` 로 고정한다).
- **불변**
  - 관제 빌드(`control`) 동작 **무변경** — 특히 「부재는 INTERNAL」(`ADR-063`)과 「모르는 역할 값은
    역할 미부여로 낮춘다」 규칙을 **그대로** 둔다.
  - `sub`·`exp` 미보유 시 `null` 반환하는 fail-closed 게이트 유지.
  - `setServerRole` 은 손대지 않는다.
- **주의**
  - ★ **역할을 `PORTAL_USER` 로 «채워 넣지» 말 것.** `null` 로 비우는 것이 맞다 —
    `sessionBootstrap` 이 `/v1/me` 로 받은 서버 역할을 `setServerRole` 로 덮으므로 정상 경로는
    그것으로 채워진다. FE 가 역할을 지어내면 **서버 조회가 실패했을 때 있지도 않은 권한을
    화면이 인정**하게 된다(fail-open).
  - `null` 로 두면 서버 조회 실패 시 `RoleGuard` 가 `ServerRoleUnknownNotice`(재시도 제공)로
    떨어진다 — 「권한 없음」으로 오안내하지 않는 것이 옳은 동작이다.
  - ⚠ `!claims.role && claims.channel === 'INTERNAL'` 가지(역할 부여 안내)는 포털 빌드에서
    채널이 `PORTAL` 이라 **닿지 않는다.** 그 가지를 건드리지 말 것.
  - `isPortalEmbedChannel()` 은 **모듈 상수로 굳히지 않는다**(매 호출 `import.meta.env` 재독 —
    `buildChannel.ts` 가 그 이유를 적어 뒀고 시험이 `vi.stubEnv` 로 값을 바꾼다).
- **수용기준**
  - 포털 빌드 + `channel` 없는 토큰 → `claims.channel === 'PORTAL'`, `claims.role === null`.
  - 포털 빌드 + `channel:"INTERNAL"` 실린 토큰 → 그래도 `PORTAL`(값 무시).
  - 포털 빌드 + `role:"ADMIN"` 실린 토큰 → `claims.role === null`.
  - 관제 빌드 → 기존 시험 **전건 무변경**.

## §4 영향·리스크

- **하위호환**
  - 관제 채널: 배포 향 미선언 시 `control` 로 떨어지므로 **기존 배포본은 동작이 바뀌지 않는다.**
  - 관제 계약면(데이터마트 뷰·통지)에 영향 없음.
  - 포털 채널: 지금 **막혀 있던 것이 열리는** 방향이라 회귀 대상이 없다.
- **되돌리기**: 배포 향을 선언하지 않으면(또는 `control`) 종전 동작으로 완전히 되돌아온다. 코드 롤백 불필요.
- **리스크**
  - ★ `ADR-012` 가 적어 둔 위험 그대로 — **배포 향을 잘못 선언하면 그 배포본이 통째로 반대 채널로
    동작한다.** 토큰 단위로 바로잡을 여지가 없다. 그래서 기동 로그가 필수 관측 수단이다.
  - **운영 조치 필요** — 개발망 WAS 잡(`klid 저작도구 was`)의 `environment { }` 에
    `KLID_DEPLOY_FLAVOR = 'portal'` 을 넣어야 이 변경이 실제로 발동한다. 넣지 않으면
    `control` 로 떨어져 **지금과 똑같이 막힌다**(코드는 맞는데 안 고쳐진 것처럼 보인다).
  - **이미 난 부작용** — 포털 계정 `qaadmin0903`(포털 `mbrId` = 토큰 `sub`)이 저작도구에
    **INTERNAL WORKER 로 자동 등록**됐을 수 있다. 이 CO 는 신규 발생을 막을 뿐 **기존 행을
    지우지 않는다.** 확인·정리는 §5 참조(운영 조치).

## §5 검증

### 자동 시험 (필수 회귀 가드)

| # | 대상 | 단언 |
|:-:|---|---|
| 1 | BE | 배포 향 `portal` + `channel` 없는 토큰 → `PORTAL` · `PORTAL_USER` |
| 2 | BE | 배포 향 `portal` + `channel:"INTERNAL"` 토큰 → 그래도 `PORTAL`(**강제** 확인) |
| 3 | BE | 배포 향 `portal` → 자동 등록기·최종접속 기록기·프로비저너가 **호출되지 않음**(mock verify) |
| 4 | BE | 배포 향 미선언 → `CONTROL`, 종전 동작 |
| 5 | BE | 배포 향 값역 밖 → `CONTROL` + 로그에 그 사실 |
| 6 | FE | 포털 빌드 → `channel==='PORTAL'`, `role===null` (`vi.stubEnv`) |
| 7 | FE | 관제 빌드 → 종전 동작 무변경 |

★ **3번이 이 CO 의 핵심 가드다** — 포털 회원이 내부 사용자로 등록되는 것을 막는 자리다.

### 수동 확인 (개발망)

WAS 잡에 `KLID_DEPLOY_FLAVOR='portal'` 추가 → 재배포 → 포털 web 잡 재배포 후:
1. WAS 기동 로그에 배포 향 = `portal` 이 찍히는가
2. `https://<포털>/workspace/authoring` 에서 저작도구 화면이 **뜨는가**
3. `/authoring-api/v1/me` 가 `{channel:"PORTAL", role:"PORTAL_USER"}` 를 주는가

### 운영 조치 (코드 아님) — 이미 난 부작용 정리

**무엇이 쓰였는지 코드로 특정했다.** 포털 토큰의 `sub` 는 **숫자**(포털 `mbrId`)라 관제 채널의
`numericSub` 경로가 그대로 열렸고, 그 결과 두 자리가 건드려진다.

| 대상 | 무엇이 일어났나 | 성질 |
|---|---|---|
| `LS_USER_ROLE` | `AutoWorkerRegistrar` → `insertRoleIfAbsent(sub, 'WORKER')` | **행이 새로 생긴다** |
| `LS_ACNT_USER.LAST_LGN_DT` | `LastLoginRecorder` → 조건부 `UPDATE` | **행을 만들지 않는다**(있을 때만 갱신) |
| `LS_ACNT_USER`(신규) | `ControlUserProvisioner` | **돌지 않았다** — 숫자 `sub` 라 진입 조건 밖 |

⇒ 정리 대상은 **`LS_USER_ROLE` 한 곳**이다.

**★ 두 경우를 갈라야 한다 — 번호만 보고 지우면 안 된다.**

1. **그 번호의 관제 사용자가 없던 경우** — 고아 역할 행 하나가 생긴 것이다. 지우면 끝난다.
2. **그 번호의 관제 사용자가 실재하는 경우** — `ADR-012` 가 경고한 *"값이 겹치면 다른 사용자의
   행에 매칭된다"* 가 실제로 일어난 것이다. 이때:
   - 그 사용자에게 **이미 역할이 있었다면** `DO NOTHING` 이라 **역할은 무사하다.**
   - 역할이 **없었다면** 그 사람이 지금 WORKER 로 보인다 — 지우면 원래대로 돌아간다.
   - 어느 쪽이든 **`LAST_LGN_DT` 는 오염됐다**(남의 접속이 그 사람 기록으로 남았다).
     되돌릴 원본이 없으므로 **정정 불가**이며, 휴면 계정 판단에 쓰지 말라고 알려야 한다.

**절차** — ①`LS_ACNT_USER` 에 그 번호가 실재하는지 먼저 확인 ②`LS_USER_ROLE` 행의 `REG_DT` 가
포털 접속 시각대와 맞는지 대조 ③둘을 종합해 판단한 뒤 삭제. **개발망 한정이며 운영 배포 전이므로
데이터 위험은 낮다.**

⚠ 이 CO 는 **신규 발생만 막는다** — 기존 행은 지우지 않는다.

### ★사양 파급 — 인지·수용 확정

포털 향에서 **「`/me` 실패 + 토큰 역할 有 → 통과」 폴백이 원리적으로 도달 불가**가 됐다(입력이 항상
`null`). 그래서 `/v1/me` 가 5xx 인 동안 포털 사용자는 화면에 못 들어가고 재시도 안내를 본다.

**그 폴백을 살리는 쪽이 더 나쁘다** — 포털 토큰의 `role` 은 `"ADMIN"`(포털 어휘)이고 우리
`Role.ADMIN` 과 **글자가 같아서**, 폴백을 두면 서버가 죽은 동안 포털 회원이 저작도구 관리자로 읽힐
길이 열린다. `INT-013` 의 *"상대 시스템의 역할은 저작도구 인가 축에 쓰지 않는다"* 가 이 자리다.

⇒ **귀결**: 포털향 배포본에서 `GET /v1/me` 가 `PORTAL_USER` 를 주는 것이 **진입의 단일 전제**가 됐다.
정상 경로의 안전망은 실재를 확인했다(`features/auth/sessionBootstrap` 의 스토어 구독이
`serverRoleStatus==='unacquired'` 전이에서 `ensureServerRole()` 을 부른다). **런타임 E2E 는 미검증** —
배포 후 브라우저로 확인해야 한다.

**미반영·보류 항목**: 없음.
