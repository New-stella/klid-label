# CO-20260916-사용자-이름수정

> 사용자 표시 이름을 관리 화면에서 고칠 수 있게 한다.
> **되돌릴 수 있는 변경**이며 실삭제와 성질이 다르다 — 그래서 갈랐다.

| | |
|---|---|
| 작성 | 2026-09-16 |
| 영향 도메인 | DOMAIN-001(사용자·권한) · 프론트(SCREEN-024) |
| 공유기반 선처리 | **없음** — 스키마 변경 0건 |
| 상태 | 📝 작성 |

---

## §1 배경

### 지금 이름을 고칠 방법이 없다 (실측)

사용자 표시 이름(`LS_ACNT_USER.USER_NM`)의 **쓰기 경로는 등록 시점 둘뿐**이고 **둘 다 조건부**다.

| 경로 | 조건 | 쓰기 문장 | 기존 이름을 덮나 |
|---|---|---|---|
| `AutoWorkerRegistrar.registerAsWorker` | `role == null && numericSub != null` | `upsertUser` = **`DO UPDATE`** | **덮는다** — 다만 아래 이유로 **도달하지 않는다** |
| `ControlUserProvisioner` → `insertWithIssuedUserNo` | 관제 인계(비숫자 `sub="admin"`) | **`DO NOTHING`** | **안 덮는다** |

⚠ **첫 행의 차단은 SQL 이 아니라 호출 조건이다 — 그 구분을 흐리지 말 것.**
`upsertUser` 의 `USER_NM` 규칙은 `COALESCE(NULLIF(EXCLUDED.USER_NM, ''), 기존값)` 이라
**들어온 이름이 비어 있지 않으면 이긴다.** 그런데도 관리자 수정이 원복되지 않는 근거는 따로 있다.

**창이 닫혀 있는 근거 (2026-09-16 전수 실측)** — 「숫자 sub + 역할 행 없음」 조합이 생기지 않는다:

| 확인 항목 | 실측 |
|---|---|
| `upsertUser` 호출처 | 자동등록·관리자 부트스트랩 **둘뿐이며 같은 트랜잭션에서 역할 행을 함께 만든다** |
| `LS_USER_ROLE` 의 `DELETE` | `backend/src/main` 에 **0건** |
| dev 시드 | 사용자 6행과 **역할 6행을 함께** 넣는다 |
| 최종로그인 UPDATE | `LAST_LGN_DT` **한 칸만** 건드린다 |
| 관제 인계 사용자 | `sub` 가 끝까지 비숫자라 **자동등록 분기에 진입하지 않는다** |

★**그리고 관제 경로의 이름 갱신은 의도된 설계다** — 회귀 가드
`RoleClaimAutoRegisterIT(역할클레임시_기존_사용자는_이름이_갱신된다)` 가 「옛이름 → 새이름」 갱신을
**명시적으로 결박**한다. 짝으로 `표시정보_미전달시_기존값이_보존된다` 도 있다.
⇒ **이 경로를 「빈 값일 때만 채운다」로 바꾸면 그 시험이 RED 다. 바꾸지 말 것.**

⇒ **저작도구에서 고칠 창구만 없다.** 관제 쪽 원복 위험은 실재하지 않는다.

- 저작도구에서 고칠 창구가 **없다**(`PATCH /v1/users/{userNo}` 는 역할만 받는다).
- 관제에서 이름을 바꿔도 **반영되지 않는다**(덮어쓰지 않으므로).

**한번 잘못 들어온 이름은 저장소를 직접 고치는 것 말고 방법이 없다.**

⚠ 처음에는 *"관제가 새로 로그인하면 덮어써질 테니 기능이 필요 없지 않나"* 로 판단이 기울었으나,
**실측 결과 덮어써지지 않아** 그 전제가 성립하지 않았다. 그래서 기능이 필요하다.

### 가장 가까운 선례는 역할 변경이다

같은 창구(`API-004`)가 이미 역할을 받는다. **같은 자원의 부분 수정**이므로 그 창구에 칸을 하나
더하는 것이 자연스럽고, `role` 이 `null` 이면 미변경인 규약을 이름도 그대로 따른다.

⚠ 「같은 URL 에 파라미터로 행위 분기 금지」 규약은 **쿼리 파라미터로 동사를 가르는 것**을 막는
규칙이지, PATCH 본문에 수정 가능한 칸을 더하는 것과 다르다.

## §2 변경 요지

1. **기존 창구 `PATCH /v1/users/{userNo}`(`API-004`)에 이름 칸을 더한다.** 선택이며 보내지 않으면
   미변경(역할과 같은 규약).
2. **인가는 그대로 관리자 전용**(사용자 확정) — 그 창구가 이미 `hasRole('ADMIN')` + 관리자 유효창을
   써서 **인가 배선 변경이 0** 이다.
3. **정규화는 기존 판정기를 재사용**한다 — `UserDisplayNames.normalize`(공백·제어문자 제거 + 컬럼 폭
   절단). **새로 적지 않는다**(두 번째 진실원 방지).
4. **수정일시만 갱신**한다(사용자 확정). 수정자 칸을 새로 만들지 않아 **스키마 변경 0건**.
5. 화면(`SCREEN-024`)에서 이름을 편집한다.

## §3 도메인별 변경 상세

### 공유기반 선처리 — **없음**

**DB 변경 0건.** `USER_NM varchar(100) NOT NULL DEFAULT ''` 와 `MDFCN_DT` 가 이미 있다.
마이그레이션을 만들지 말 것.

### DOMAIN-001 (사용자·권한)

- 요청 DTO(`UserUpdateRequest`)에 이름 칸 추가. **선택**이고 `null` 이면 미변경.
- **검증** — 정규화 **후** 판정한다:
  - 공백만이거나 정규화 후 비면 **400**(빈 이름으로 만들 수 없다 — 화면이 「작성자: 1」 꼴로 무너진다).
  - ★**컬럼 폭(100)을 넘으면 절단이 아니라 거부(400)** 다 (2026-09-16 사용자 확정).
    근거는 **기존 선례가 이미 그렇다**는 것이다 — 관제 인계 경로의 `userNm` 도 입구에서 길이로 거절되며,
    정규화기 주석이 *"상위 계층이 먼저 거절하지만 다른 호출자가 생겨도 컬럼 길이를 넘지 않도록
    여기서도 자른다(방어 심층화)"* 라고 그 2단 구조를 명시한다.
    ⇒ **정규화기의 절단은 그대로 둔다** — 도달하지 않는 마지막 방어선으로 남기고, 판정은 입구가 한다.
    ⚠ 영상 제외 사유는 「절단」으로 갔으나 **축이 다르다** — 이름은 식별에 쓰이는 값이라
    조용히 잘리면 다른 사람으로 보인다. 그 결론을 이 자리에 가져오지 말 것.
  - 제어문자·개행 제거는 기존 정규화기가 한다.
- **멱등** — 같은 값을 다시 보내면 **아무것도 바꾸지 않는다**(수정일시도 밀지 않는다).
  ★기존 upsert 가 이미 `IS DISTINCT FROM` 으로 같은 규율을 갖고 있다 — 그 방식을 따른다.
- **응답** — 바뀐 이름이 반영된 현재 프로필.

**불변 (반드시 지킬 것)**
- ★**관제 인계 경로를 건드리지 않는다.** `upsertUser`·`insertWithIssuedUserNo` 의 조건과 충돌 규약을
  그대로 둔다 — 그것을 바꾸면 **저작도구에서 고친 이름이 다음 진입에 원복**되거나, 반대로 관제가
  보낸 이름이 영영 안 들어온다.
- **역할 변경 경로와 섞지 않는다.** 마지막 관리자 강등 거부(409) 같은 역할 축 판정은 이름 축과
  무관하며, 이름만 보낸 요청이 그 판정에 걸리면 안 된다.
- **`USER_ID`·`USE_YN` 은 이 창구가 건드리지 않는다.**

### 프론트 — SCREEN-024 (사용자 관리)

- 이름 칸을 **편집 가능**하게 한다. 관리자에게만 보인다.
- 저장 시 위 창구를 부른다. **역할만 바꿀 때 이름을 함께 보내지 않는다**(미변경 규약을 화면도 따른다).
- ★**서버 검증 문구를 그대로 내보내지 않는다** — 화면이 필드별로 받아 **사람 말로** 보여주고,
  필드 경로·배열 순번 표기를 노출하지 않는다. 입력 시점에 화면이 먼저 판정한다(빈 값·공백만·길이 초과).
  ⚠ **구 서술 폐기(2026-09-16)** — *"검증 문구·상한은 서버 응답을 그대로 쓴다"* 는 바로 직전 라운드
  (`CO-20260916-입력검증-화면처리`)에서 확정한 구속 정책과 **정면으로 충돌**한다. 발주처 오류 증적
  2·3 이 정확히 그 동작(서버 문구 원문 노출)을 결함으로 지적한 건이다. **되살리지 말 것.**
- **상한 값 자체는 화면이 따로 적지 않는다** — 이미 정해진 단일 원천의 값을 쓴다. 양쪽에 적으면
  한쪽만 고쳐진다. (이 줄이 구 서술에서 살릴 가치가 있던 부분이며, 위 문구 축과는 별개다.)

## §4 하위호환

- 이름 칸은 **선택**이라 **보내지 않던 기존 호출의 동작이 달라지지 않는다.**
- 응답 스키마는 **추가만** — 기존 키·타입·뜻 불변.
- 인가 축 무변경(이미 관리자 전용).

## §5 이 라운드의 범위 밖

- ★**사용자 실삭제** — **별도 CO 로 미룬다**(사용자 확정, 2026-09-16). 비가역이라 설계가 훨씬 무겁다.
  그쪽 구속 결정은 이미 굳어 있다: **실삭제 · 이력 행은 남긴다 · 관리자는 삭제할 수 없다 ·
  역할·배정 동반 삭제**. ⚠ 「자기 자신만 삭제 금지」는 동시 실행에서 뚫리므로 **되살리지 말 것.**
- **본인이 자기 이름을 고치는 동선**(`/me` 축) — 이번엔 두지 않는다.
- **수정자 기록** — 수정일시만 남긴다. 필요해지면 그때 칸을 만든다.
- **관제 쪽 이름과의 동기화** — 저작도구 값이 이기고 관제로 되돌려 보내지 않는다.

★**「신규 AC」는 폐기된 방식이다 (2026-09-16 정정)** — 2026-08-31 에 **세분 단정 AC 131건이 폐기**되고
UC 흐름 단위 4자리 체계로 통합됐다(*"세분 단정 AC 폐기(사용자 확정)"*). 이름 수정은 **같은 화면·같은
창구·같은 모달**이라 새 흐름이 아니므로 `AC-1018`(happy)에 수정 동선을, `AC-1019`(negative)에 빈 값·
길이 초과 거부를 넣는다. ⚠ **3자리 AC(`AC-0XX`·`AC-8XX`)를 근거로 인용하지 말 것 — 전부 폐기다.**

**수용기준에 반드시 담을 것**

1. 이름 수정 성공 · 멱등(같은 값이면 수정일시도 밀지 않는다)
2. 빈 이름·공백만 **400** · 길이 초과 **400**
3. 인가 — 관리자 전용이며 유효창이 가산된다(작업자·검수자는 불가)
4. ★**서버 거부 문구·필드 경로가 화면에 그대로 나타나지 않는다**
5. ★**반영 범위를 명시한다** — 고친 이름은 **저장값을 읽는 자리**(목록·배정·검수 화면)에 반영되지만
   **본인 화면 상단에는 반영되지 않는다.** `/me` 는 **토큰 이름이 먼저**이고 저장값 보강조회는 토큰에
   이름이 없을 때만 돌기 때문이다(회귀 가드가 그 우선순위를 결박한다). **결함이 아니라 설계된 동작**이며,
   적어 두지 않으면 다음 사람이 결함으로 재보고한다.

⚠ **구 서술 폐기(2026-09-16)** — *"★가장 중요한 수용기준은 「관제가 다시 로그인해도 고친 이름이
유지된다」이다"*. 그 보장은 **이미 성립한다**(§1 실측 표). 수용기준으로 세울 수는 있으나 **이 CO 의
존재 이유는 아니다** — 존재 이유는 **고칠 창구가 없다**는 것 하나다.

⇒ **CO §6 을 손으로 적은 목록만 믿으면 절반이 빠진다.** 상위 ITEM 을 고친 뒤 **영향 분석을 실제로 돌려야** 나온다.

### ★이 라운드가 드러낸 설계 결함 셋 (원래 어긋나 있던 것)

1. **기능 층이 조달 순서를 거꾸로 적고 있었다** — *"표시 이름의 진실원은 저작도구 보관값이고 인계 토큰의
   이름 클레임은 보조 조달원"*. 실측은 반대다(토큰에 이름이 있으면 **토큰 이름이 표시된다**, 회귀 가드가 결박).
   **두 축이 한 문장에 섞여 있었다** — 누가 표시값을 정하는가(응답)와 응답이 무엇을 먼저 쓰는가(토큰).
2. **셸 층이 한 축의 결론을 다른 축에 유추 적용**하고 있었다 — *"인가의 진실원을 보관값으로 두는
   역할 표시와 **같은 축이다**"*. 인가는 보관값이 맞지만 **이름은 토큰이 먼저**다.
3. **개념 모델이 이름을 「화면이 보내는 표시용 값」으로만** 적어 **소유 사실이 어디에도 없었다.**

### ★유효창 주어가 네 층에 좁게 적혀 있었다

유효창 요구는 **창구 전체에 걸린다**(이름만 고쳐도 필요하다 — 코드상 메서드 단위로 걸린 것을 실측).
그런데 사용례·화면·시퀀스가 *"**역할 변경에는** 유효창이 필요하다"* 로 적어 **이름 축의 요구가 침묵**하고 있었다.
셋 다 「저장 전체」로 넓혔다. ⚠ **인가를 바꾼 것이 아니라 서술을 사실에 맞춘 것**이다 — 요구 범위·판정 주체·거부 코드는 불변.
★화면에서는 제가 지목한 두 자리 외에 **「남은 유효 시간」 구성요소 메모**에도 같은 한정이 있었다 —
**낱말이 아니라 본문 전수로 훑어야** 나온다.

## §8 사용자 확정 (2026-09-16 · 설계 라운드 종료 시점)

| 물은 것 | 답 |
|---|---|
| 이름이 저장 폭을 넘을 때 | **거부(400)** — 절단 아님 |
| 수용기준의 검증 상태값이 `passing` 인 채 남은 것 | **그대로 두고 구현·QA 뒤 맞춘다** |
| 담당들이 지시 밖에서 판정해 이미 쓴 것 셋 | **둘만 수용** — 미배정 저장 버튼 규칙 완화 · `AC-1019` 제목 확장. ⇒ **감사 주체 넓힘은 원복**(완료) |
| 글자 수 상한 때문에 삭제된 셸 문장 | **그대로 둔다**(뜻이 새 문장에 흡수됨) |
| 다음 단계 | **커밋하고 구현으로** |

★**「미배정 사용자는 역할 선택 전까지 저장 버튼 비활성」이 완화됐다** — 이름이 편집 가능해지면서
옛 규칙이 **미배정 사용자의 이름만 고치는 저장까지 막기** 때문이다. 화면 사양은
*"역할을 고르기 전까지 **역할이** 저장되지 않는다"* 로 좁혀졌다. **구현이 이것을 따라야 한다.**

★**감사 기록 주체는 역할 축이다** — 이름 수정은 **수정일시만 남기고 수정자 칸이 없다.**
⇒ 구현에서 **이름 수정에 감사 로그를 새로 만들지 말 것.**

### ★이 라운드가 남긴 노하우 (되풀이 방지)

1. ★★**`change_summary` 도 손상 검사 대상이다.** 한 담당이 자기 쓰기에서 「보낸」을 치환 문자로
   손상시켰는데(**본문은 무손상**) 그 자리는 **본문만 검증하는 관례의 사각**이었다.
   ⚠ 프로젝트 규칙의 *"변경 이력 필드는 검사에서 제외"* 는 **「알려진 오타 문자열 검색」 제외**를 뜻하는데
   (오타를 *설명*하는 자리라서), 실제로는 **손상 검사 자체를 건너뛰는 것**으로 작동해 왔다. **둘은 다르다** —
   치환 문자·라틴 혼입은 오타 설명이 아니라 손상이며 어느 필드에서든 잡아야 한다.
2. ★**쓰기 전 dry-run 이 실제로 사고를 막았다.** 한 담당이 dry-run 에서 `delete` 1건을 보고 **쓰기를 중단**한 뒤
   그 편집을 **삭제가 아닌 명시적 넓힘**으로 재작성해 `delete` 0 으로 만들었다. 주의력이 아니라 절차가 잡았다.
3. ★**원문과 정형 필드의 불일치를 구조로 막을 수 있다** — 시퀀스 담당이 **생성기가 기준선 원문을 바이트
   동일하게 재생성함을 먼저 증명한 뒤** 그 생성기로 새 원문을 만들어 **불일치를 구조적으로 불가능하게** 했다.
4. ⚠⚠ **병렬 담당끼리 스크래치 파일을 덮는다 — 2회 관측.** 한 담당의 부분 조회 결과가 다른 담당의
   기준선 파일을 덮었고(`data_projected_to` 가 남의 것이었다), **부분 조회본을 전체 본문으로 오인하면
   전체 교체 시 절단 사고**가 난다. 두 번 다 자력 방어했으나 **다음엔 놓칠 수 있다.**
   ⇒ 위임 프롬프트에 **①파일명에 자기 ID 접미 ②읽은 기준선의 `id`·전체조회 여부 assert ③기준선은
   편집과 같은 프로세스에서 새로 받기**를 박을 것.
5. **「낱말로 훑기」는 뚫린다** — 유효창 주어를 「역할 변경」으로 훑었는데 화면의 **구성요소 메모**에
   같은 한정이 숨어 있었다. **본문 전수 + 성질 우회 축**을 갈라 훑어야 나온다.

### 사전 실측에서 바로잡은 것 (2026-09-16)

1. **`upsertUser` 는 `DO NOTHING` 이 아니라 `DO UPDATE` 다.** CO 최초본이 그 경로를 SQL 이 아니라
   호출 조건으로 적어 두 경로가 같은 이유로 막힌 것처럼 읽혔다. **결론(원복되지 않는다)은 그대로
   맞으나 근거가 달랐다** — 근거를 §1 에 실측으로 다시 세웠다.
2. **프론트 절이 직전 라운드 확정과 충돌**했다(*"서버 응답을 그대로 쓴다"*). 발주처 오류 증적이
   지적한 바로 그 동작이라 폐기했다.
3. **「신규 AC」가 폐기된 방식**이었다 — 현행은 UC 흐름 단위 통합 AC 다.
4. **`SEQ-018`·`ERD-029` 가 대상에서 빠져 있었다.**
