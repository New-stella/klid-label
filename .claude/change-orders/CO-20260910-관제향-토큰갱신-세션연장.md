## §1 배경

관제지원 웹은 로그인 세션을 스스로 연장한다. 만료가 다가오면 팝업을 띄워 연장을 권하고, API 요청 직전 만료가 가까우면 자동으로 재발급받는다. 저작도구는 이 동작이 **전혀 없다.**

**2026-09-10 실측**(246 관제 웹에 실제 로그인한 브라우저 + 관제 번들 `index-*.js` 의 토큰 관리 코드):

1. **저작도구는 관제 화면 안이 아니라 새 탭에서 열린다.** 관제는 `window.open(origin + '/label-studio', '_blank')` 로 연다. 관제의 만료 감시·연장 팝업은 **관제 탭에서만** 돈다. 참고로 관제의 `RelayAdminViewPage` 는 저작도구가 아니라 **중계서버 관리자** iframe 화면이다(외부 시나리오 문서가 이것을 「저작도구 뷰」로 적었는데 틀렸다).
2. **관제 토큰은 짧다.** `sessionTime=30` 이라 access 토큰 수명이 **30분**이고, 팝업 임계 `sessionExpAlarm=5`(분)가 토큰 클레임에 실려 온다.
3. **저작도구는 진입 시 토큰을 한 번 복사해 둔다.** 내부 채널은 진입 화면이 `localStorage['klid-jwt-token']` 을 읽어 우리 스토어(sessionStorage `klid_jwt`)로 옮기고, 이후 요청은 **그 복사본**을 쓴다. 그래서 관제 탭이 토큰을 갱신해도 우리는 옛 토큰을 쥐고 있다가 30분 뒤 401 → 관제 로그인 화면으로 튕긴다. 라벨링·검수처럼 한 화면에 오래 머무는 작업에서 **반드시** 겪는다.

### 실측한 관제 계약 (구현이 따를 값)

| 항목 | 값 |
|---|---|
| access 토큰 | HS512 · `sub="admin"`(로그인 아이디 문자열) · **`iss`·`channel`·`role` 없음** · 클레임 `userId`·`userNm`·`authority`·`sessionId`·`type="access"`·`sessionExpAlarm`·`sessionTime`·`eventDate`·`rawVideoDate`·`inaccessible_menus`·`userOgCd`·`userSido`·`userSgg`·`iat`·`exp` |
| refresh 토큰 | HS512 · `type="refresh"` · 같은 `sessionId` · 수명 7일 |
| 저장 (관제 `saveTokens(session, refresh)`) | `localStorage['klid-jwt-token']` = access 원문 · `localStorage['tokenInfo']` = JSON `{access_token, refresh_token, authority, userSido, userSgg, userOgCd, expiresAt(=exp*1000), issuedAt(=iat*1000), sessionExpAlarm, sessionTime, eventDate, rawVideoDate, inAccessibleMenus(=inaccessible_menus ‖ [])}` · `localStorage['userNm']` = `userNm` 클레임 |
| 삭제 (관제 `clearTokens`) | `tokenInfo` · `klid-jwt-token` 두 키 삭제. 관제는 `storage` 이벤트로 둘 중 하나가 사라지면 로그인 화면으로 보낸다 |
| 갱신 API | `POST /api/account/auth/refresh` · 헤더 `x-access-token: <tokenInfo.refresh_token>`(★access 가 아니라 refresh) · 바디 없음 → `200 {error:0, message:"success", data:{session_token, refresh_token}}` |
| 갱신 결과 | `sessionId` 유지 · **refresh 토큰도 새로 발급(교체)** · **옛 access 토큰은 갱신 뒤에도 유효**(우리 `/v1/me` 200 확인) · 옛 refresh 토큰 재사용 시 동작은 **미시험**(세션 전체가 끊길 수 있어 시험하지 않았다) |
| 관제 웹 자체 동작 | ① 모든 API 요청 직전 남은 시간 ≤10분이면 **선제 갱신**(갱신 중 동시 요청은 대기열에서 새 토큰을 기다림) ② 401 이면 갱신 후 **1회 재시도** ③ 1초 간격 감시 — 남은 시간 ≤ `sessionExpAlarm`(없으면 `"30"`)분이면 연장 팝업 **1회**(「N분 N초 후 자동 로그아웃 됩니다」), 0 이면 로그아웃 |
| 우리 백엔드 수용 | 위 access 토큰으로 `/v1/me` → **200** · `sub="admin"`(비숫자) → `userId` 클레임으로 사용자 조회 → userNo 9001 → ADMIN · `channel` 없음 → INTERNAL · `iss` 없음 → 허용. 토큰 **수용**을 위한 백엔드 변경은 불필요(⚠ 단 WAS 경유 결정으로 중계 API 2건과 `type=refresh` 거부는 신설 — §3 「백엔드」) |

⚠ 외부 문서 「관제지원 토큰 갱신 시나리오」는 갱신 응답을 `{sessionToken, refreshToken}` 으로 적었으나 **실측은 `data.session_token` / `data.refresh_token`** 이다.

### 함께 드러난 설계·문서 오류

2026-09-05 에 「관제 인계 JWT 실측 계약」으로 기록된 *"HS256 · sub=숫자 userNo · iss=klid-auth · role·channel 있음 · 만료 1시간"* 은 **실제 관제 토큰이 아니었다.** 우리 개발 로그인(`DevLoginPage`)이 같은 키 `klid-jwt-token` 에 쓰는 토큰이었을 가능성이 높다 — 그 기록이 함께 적은 부속 키 `klid-user-id`·`klid-authority` 는 **`DevLoginPage` 만 쓰는 키**다(관제 번들에는 없다). 이 기록이 `ADR-063` 정정 단락과 프로젝트 `CLAUDE.md` 「★★관제 인계 JWT 실측 계약」 절에 들어가 있고, 그 결과 *"비숫자 sub → userId 조회 경로는 휴면 코드"* 라는 잘못된 결론이 퍼져 있다. **실제로는 관제 진입마다 쓰이는 경로다.**

## §2 변경 요지

1. 관제 채널에서 access 토큰의 진실원을 **`localStorage['klid-jwt-token']` 현재값**으로 바꾼다(진입 시 복사본 아님). `storage` 이벤트로 다른 탭의 갱신·로그아웃을 따라간다.
2. 셸에 **만료 감시 + 연장 팝업**을 둔다(관제 Layout 과 같은 규칙).
3. 내부 채널 인계 창구의 `refresh()` 를 ~~**관제 갱신 API 호출**로~~ **저작도구 갱신 중계(`API-247`) 호출**로 구현하고(⚠ WAS 경유 결정으로 교체 — 브라우저는 관제를 직접 부르지 않는다), 결과를 **관제 `saveTokens` 와 같은 키·형식**으로 저장한다.
4. 요청 인터셉터에 관제와 같은 **선제 갱신(≤10분)** + **401 시 갱신 후 1회 재시도**를 넣는다.
5. 두 탭이 같은 refresh 토큰으로 **동시에 갱신하지 않게** 막는다.
6. 설계(`ADR-012`·`INT-013`·`ADR-063`)와 `CLAUDE.md`·위키의 틀린 서술을 바로잡는다.

  4. **갱신 호출** — `internalTokenHandoff.refresh()`:
     - `tokenInfo.refresh_token` 이 없으면(개발 로그인 등) **갱신하지 않고** 현재 토큰을 돌려준다(종전 동작). 오류로 취급하지 않는다.
     - `POST {VITE_CONTROL_REFRESH_URL}` · 헤더 `x-access-token: <refresh_token>` · 바디 없음. **`apiClient` 를 쓰지 않는다**(우리 base URL·`Authorization` 헤더·401 인터셉터와 엉킨다). `withCredentials` 불필요(같은 출처).

     - 성공 시 **관제 `saveTokens` 와 같은 저장**: `tokenInfo` 13필드(새 access 토큰을 디코드해 채움 — §1 표의 매핑 그대로) + `klid-jwt-token` + `userNm`. 필드 이름·단위(ms)·기본값(`inAccessibleMenus` 는 `[]`)을 관제와 **글자 그대로** 맞춘다 — 다르면 관제 탭이 우리가 쓴 값을 읽고 깨진다. 관제가 로그인 때만 쓰는 `authority`·`pwd_change_recommended`·`contextMenu` 는 **쓰지 않는다**(관제 갱신도 안 쓴다).
     - 실패 시 저장하지 않는다. ~~팝업 경로면 오류 안내만 하고 만료 시 로그아웃, 인터셉터 경로면 아래 5 의 규칙.~~ ⚠ **폐기 — 아래 최종 규칙으로 대체(2026-09-10 사용자 확정 「갱신 거절 시 즉시 로그아웃」)**
     - **★실패 결말 최종 규칙**
       - **A. 관제 거절**(응답 `error≠0` — 예: `900205 리프레시 토큰이 없습니다`, 서버 세션 정리) → 경로(선제·팝업·401 뒤) 무관 **즉시** 세션 비우기 + 관제 로그인 이동. 거절된 refresh 토큰으로 **다시 갱신하지 않는다.** 근거: 다른 기기 등에서 관제 서버 세션이 끊겨도 이 브라우저 저장소 값은 그대로라 저장소 추종으로는 잡히지 않는다 — 추가 호출 없이 갱신 시점(만료 10분 전)에 잡는다. 그 전까지의 창(최대 약 20분)은 **인지·수용**.
       - **A-예외. 거절 직후 저장소 재확인** — 거절을 받으면 로그아웃하기 **전에** `tokenInfo.refresh_token` 을 다시 읽어, 값이 바뀌었으면(다른 탭·관제 탭이 이미 갱신) **로그아웃하지 않고 그 새 토큰을 쓴다.** 값이 그대로일 때만 로그아웃한다. 근거: 동시 갱신으로 이 탭이 교체된 옛 refresh 토큰을 들고 거절된 경우 멀쩡한 세션을 끊게 된다. **경로를 가리지 않는다** — 401 뒤의 갱신이 거절된 경우에도 같은 예외를 적용한다(사유가 같다). 비교 대상은 `tokenInfo.refresh_token` 으로 고정(위치를 적지 않으면 구현이 다른 값을 본다).
       - **B. 일시 장애**(네트워크 오류·5xx) → 저장하지 않고 현재 토큰으로 계속(팝업 경로는 실패 안내), 다음 요청 때 재시도 가능, 남은 시간 0 이면 로그아웃.
       - **C. 401 뒤** 갱신 실패·재시도도 401 → 즉시 로그아웃.
       - **D. 강제 로그아웃(A·C·0)은 미저장 변경 확인 절차를 거치지 않는다** — 만료·거절된 세션으로는 저장할 수 없고 확인 창에서 멈추면 끝난 세션에 갇힌다. 자동 저장하지 않는다. 미저장 편집이 있으면 연장 팝업에 「저장하지 않은 작업이 있습니다」 경고를 함께 보인다(사용자 확정 「팝업에서 경고 + 만료 시 이동」). ⚠ A·C 까지 D 를 넓힌 것은 만료와 같은 이유로 메인이 통일한 판단이다(사용자 이견 시 조정).
  5. **요청 인터셉터**(내부 채널만 — 포털 채널은 `resolveTokenHandoff()` 가 포털 창구를 돌려주므로 자연히 제외되게 창구 수준에서 구현할 것):
     - **선제 갱신**: 요청 직전 남은 시간 ≤ **10분** 이고 refresh 토큰이 있으면 먼저 갱신하고 새 토큰을 싣는다. 갱신 중에 들어온 요청은 **같은 갱신을 기다린다**(갱신은 한 번만 나간다).
     - **401 재시도**: 기존 「헤더 없이 나간 요청 재시도」 분기는 유지. 그 밖의 401 이면 refresh 토큰이 있을 때 **갱신 후 1회 재시도**. 재시도도 401 이거나 갱신이 실패하면 **기존 동작**(스토어 비우기 + 상위 로그인 이동).
     - `skipAuthRedirect` 요청(관리자 패스워드 확인 등)은 **갱신·재시도 대상이 아니다** — 그 401 은 세션 만료가 아니다.
  6. **탭 간 동시 갱신 방지**: 관제 탭과 저작도구 탭(여러 개일 수 있다)이 같은 refresh 토큰으로 동시에 갱신하면, 한쪽이 교체된 refresh 토큰을 쥔 채 남는다.
     - 갱신 직전 `tokenInfo` 를 **다시 읽어**, 쥐고 있던 refresh 토큰과 다르면(다른 탭이 이미 갱신) **갱신하지 않고** 새 값을 쓴다.
     - 가능하면 Web Locks(`navigator.locks.request`)로 한 번 더 직렬화한다. ⚠ Web Locks 는 **보안 컨텍스트(https·localhost) 전용**이라 246 dev(`http://…:8088`)에서는 `undefined` 다 — 없으면 위 재읽기 비교만으로 동작해야 한다(오류로 멈추지 말 것).
     - ⚠ 관제 탭은 우리 잠금을 모른다. 완전한 배제는 불가능하며 재읽기 비교가 1차 방어다(인지·수용).
- **불변(건드리면 안 되는 것)**
  - **포털 채널 동작 무변경** — 포털 창구(`portalTokenHandoff`)·`x-access-token` 요청 헤더·Host 메모리 원칙(`INT-013`)을 건드리지 않는다. 새 감시·팝업·저장은 **관제 채널 빌드에서만** 동작한다(`isPortalEmbedChannel()` 재사용).
  - 내부 채널 요청 헤더는 종전대로 `Authorization: Bearer`(`buildAuthHeader`).
  - 인가 역할의 진실원은 `/v1/me` 다. 토큰 교체가 **같은 사용자**면 서버 역할 재확보로 화면을 스피너·재진입으로 돌리지 않는다(갱신마다 화면이 깜빡이면 안 된다). `setToken` 이 `serverRoleStatus` 를 `'unacquired'` 로 되돌리는 동작을 그대로 쓰면 그렇게 된다 — **토큰만 교체하는 경로가 필요**하다. 사용자(`sub`)가 바뀐 경우만 재확보한다.
  - `authority` 등 브라우저 저장소의 권한 문자열을 **읽어 판정에 쓰지 않는다**(기존 원칙 유지 — 쓰기만 관제 형식에 맞춘다).
  - 토큰·refresh 토큰 원문을 **로그에 싣지 않는다.**
- **주의**
  - 개발 로그인(`DevLoginPage`)은 `klid-jwt-token` 만 쓰고 `tokenInfo` 를 쓰지 않는다. 개발 진입이 새 로직 때문에 로그아웃되거나 오류가 나면 안 된다(갱신 없이 만료까지 사용 — 종전과 같음).
  - URL 쿼리(`?token=`) 채널은 계속 쓰지 않는다.
  - `useAuthStore` 의 sessionStorage 보관(`klid_jwt`)은 새로고침 복원용으로 남겨도 되나, **localStorage 값이 있으면 그것이 우선**이다.
  - 파일 상단·창구 주석의 *"localStorage 는 읽기만 — 저작도구가 새로 쓰지 않는다"* · *"내부 채널에는 갱신 창구가 없다"* · *"세션 수명은 상위 시스템 토큰이 정하며 저작도구가 연장하지 못한다"* 는 **이번 결정으로 폐기**다. 지우지 말고 폐기 표기 + 현재 판단으로 대체한다(이 저장소 관례 — 낡은 지시문이 다음 라운드의 작업 지시로 읽힌다).
- **수용기준** (Phase 3.6 에서 AC 로 확정)
  1. 관제 탭이 갱신해 `klid-jwt-token` 이 바뀌면, 저작도구의 **다음 요청**은 새 토큰을 싣는다(새로고침 없이).
  2. 남은 시간이 임계 이하가 되면 연장 팝업이 **1회** 뜨고, 버튼은 「로그아웃」·「로그인 연장」 둘뿐이며(닫기·X·ESC·배경 클릭 닫힘 없음) 둘 중 하나를 누르면 같은 토큰 수명 동안 다시 뜨지 않는다. 「로그아웃」은 관제 로그아웃 API 호출 뒤 성공·실패 무관하게 토큰 키를 지우고 관제 로그인으로 간다.
  3. 「로그인 연장」을 누르면 갱신 API 가 refresh 토큰으로 호출되고, `tokenInfo`(13필드)·`klid-jwt-token`·`userNm` 이 관제 `saveTokens` 와 **같은 모양**으로 저장되며, 팝업이 닫히고 만료 기준이 새 토큰으로 바뀐다.
  4. 남은 시간 0 → 스토어 비움 + 관제 로그인 이동.
  5. 남은 시간 ≤10분에서 API 요청 시 선제 갱신 1회 후 새 토큰으로 요청된다. 동시 요청 N건이어도 갱신 호출은 1회.
  6. 401 → 갱신 후 1회 재시도. 재시도 실패·갱신 실패 → 기존 로그아웃.
  7. 다른 탭이 이미 갱신한 경우 이 탭은 갱신 API 를 호출하지 않는다(refresh 토큰 재읽기 비교).
  8. `klid-jwt-token` 삭제(관제 로그아웃) → 저작도구도 로그아웃 이동.
  9. `tokenInfo` 없는 진입(개발 로그인)은 갱신 없이 종전대로 동작하고 오류가 없다.
  10. 포털 채널 빌드는 감시·팝업·저장이 **동작하지 않는다**(기존 포털 창구 시험 전건 그대로 통과).

### 팝업 재표시 규칙 (2026-09-10 최종)

임계에 닿으면 팝업을 띄우되 **매 감시 주기마다 되풀이하지 않는다.** 재표시 억제가 유지되는 경우는 둘뿐이다 — **①「로그인 연장」 성공 ②「로그아웃」으로 실제 이탈.** **미저장 확인에서 취소해 화면에 남으면 억제가 풀려** 다음 감시 주기에 임계 이하면 다시 뜬다(취소는 「지금 나가지 않겠다」이지 「안내를 그만 받겠다」가 아니다).

⚠ **판단 후 그대로 둔 문면 1건** — `AC-1105.then[16]` 의 예외 열거가 「확인 절차 없이 로그아웃한 경우」로 좁게 적혀 있다. 확인에서 **계속**을 골라 로그아웃한 갈래도 화면을 실제로 떠나 재표시가 성립하지 않으므로 **결과가 같고 상충이 아니다.** 라운드를 더 쓰지 않고 이 근거를 남긴다.

## §4 영향·리스크

- **하위호환**: ~~백엔드·API 계약 무변경.~~ ⚠ 폐기 — 백엔드에 API 2건(`API-247`·`API-246`)이 **신설**되고 인증 필터가 `type=refresh` 토큰을 **거부**하게 됐다(기존 API 계약은 무변경). 관제 채널에서 저작도구가 **관제 저장소에 쓰기 시작**한다 — 형식이 한 글자라도 다르면 **관제 탭이 깨진다**(관제는 `tokenInfo.expiresAt` 을 읽어 즉시 로그아웃할 수 있다). 수용기준 3 이 이것을 막는다.
- **refresh 토큰 교체 경쟁**: 관제 탭과 동시에 갱신하면 한쪽이 옛 refresh 토큰을 쥔다. 옛 refresh 토큰 재사용 시 관제 서버가 **세션 전체를 끊는지 미확인** — 끊는다면 드물게 양쪽 모두 로그아웃될 수 있다. 재읽기 비교로 확률을 줄인다(인지·수용). 관제팀 확인 대상.
- **★관제 서버 세션이 먼저 끝날 수 있다 (2026-09-10 실측)** — 로그인 약 25분 뒤, access 토큰이 아직 6분 남았는데 관제 일반 API(`/api/account/user/info`)가 `401 {error:1111, "세션이 비활성 상태입니다."}` 를 냈고, 갱신은 `401 {error:900205, "리프레시 토큰이 없습니다."}` 로 실패했다(refresh 토큰 자체는 7일 남음 → **서버가 세션을 정리한 것**). 관제 화면에서 「로그인 연장」을 눌러도 실패했고 0초에 관제가 두 키를 지우고 로그인 화면으로 보냈다.
  - **원인 미확정** — 후보: ①같은 계정 중복 로그인으로 기존 세션 종료 ②그 전에 한 수동 갱신 호출(17:21)의 영향 ③서버 유휴 만료. 사용자는 중복 로그인 여부를 모른다.
  - ✅ **재현 결과 — 갱신 호출은 세션을 끊지 않는다 (2026-09-10 18:0x 실측)**: 새로 로그인한 세션에서 ①일반 API 200 → ②갱신 `error 0`(sessionId 유지) → ③**새 토큰 200 · 옛 access 토큰도 200** → ④20초 뒤 200. 즉 후보 ②는 **즉시 영향으로는 기각**된다. ⚠ 시차를 둔 영향(갱신 20여 분 뒤 정리)까지 배제한 것은 아니며, 후보 ①·③도 아직 가리지 못했다. **관제 확인 대상**: 중복 로그인 시 기존 세션 종료 정책 · 서버측 세션 유휴/절대 수명.
  - ⇒ 이 CO 의 전제(갱신으로 세션을 이어 간다)는 실측으로 **성립**한다. 구현 착수 가능.
  - 설계 귀결: 갱신 실패 코드(`error≠0`)는 **재시도하지 않고** 실패로 처리해 만료 시 로그아웃 — 관제와 같다.
  - ⚠ **저작도구 서버는 서명·만료만 보므로 관제 세션이 끝나도 access 토큰 만료(최대 30분)까지 저작도구는 계속 동작한다.** 관제 로그아웃이 같은 브라우저라면 저장소 삭제 이벤트로 즉시 따라가지만, 다른 기기에서의 세션 종료는 따라가지 못한다(인지·수용 후보 — 사용자 확인 대상).
- **★관제 통지 창구는 토큰을 실제로 검증한다 (2026-09-10 실측 — `ADR-063` 결정 ⑥ 관련, 이 CO 범위 밖)** — `POST /api/data-set/v2/jobs/SELFTEST/notify-completed` 에 바디 `{}` 로: 헤더 없음 → 401 · 임의 문자열 → `1102 잘못된 형식의 토큰` · 서명 틀린 JWT → `1103 유효하지 않은 서명` · (세션이 끊긴) 실제 관제 사용자 토큰 → `1111 세션 비활성`. 08-25 의 「무엇이든 통과(422)」는 **관제 임시 해제 기간**이었고 지금은 다시 잠겼다. 관제가 **세션 활성까지 확인**하므로 우리 통지 토큰(세션 정보 없음)은 서명 방식을 HS512 로 맞춰도 통과하지 못할 가능성이 크다 → 형식 정합이 아니라 **관제 협의(서비스 토큰·IP 허용 등)** 가 선행 과제다. 별건으로 분리한다.
- **되돌리기**: 프론트 단독 변경이라 이전 번들로 교체하면 원복된다. 저장소에 우리가 쓴 값은 관제 형식과 같으므로 원복 후에도 관제 동작에 영향이 없다.
- **dev(246)**: 관제 웹(`:8088/`)과 저작도구(`:8088/label-studio/`)가 같은 출처라 로컬 저장소 공유가 성립한다. Web Locks 는 http 라 없다(§3 6).

### 백엔드 구현 중 확정한 경계 (2026-09-10 — 구현 에이전트 보고를 메인이 관례로 판정)

- 관제가 **refresh 토큰 없이 성공**(HTTP 200·`error 0`·`session_token` 만)을 주면 **201 로 access 만 옮기고 WARN** — 세션은 30분 연장되고 다음 갱신이 불가능해 만료 시 로그아웃된다(503 으로 막는 것보다 사용자에게 유리).
- `session_token` 이 빈 문자열 → 형식 불일치(503) · **401 이 아닌 4xx + `error≠0` → 거절(401)** · 해석 불가 4xx → 일시 장애(503) · 200 이 아닌 2xx → 일시 장애(503).
- 로그아웃과 갱신이 **같은 `controlAccount` 서킷**을 공유한다(같은 계정 서비스) — 관제 「거절」은 결과값으로 흘려 서킷 실패 집계에서 뺐다.
- 포털 향 404 는 **본문 해석·검증보다 먼저** 판정한다(잘못된 본문이 400 으로 창구 존재를 드러내지 않게).
- ⚠ **잔여 위험(인지·수용, `NFR-013` 등재)**: 관리자가 관제 통지 주소를 바꾸면 **사용자의 관제 세션 자격증명(refresh 7일·access)이 그 주소로 전송**된다. 호스트 변경 시 자격증명을 떼는 가드는 연장 기능을 죽이므로 둘 수 없다.
