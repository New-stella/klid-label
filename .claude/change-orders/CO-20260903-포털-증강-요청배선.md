# CO-20260903 — 포털 증강 요청 배선 (설계 확정분 코드 반영)

- 상태: 작성 (설계 라운드 완료 후 착수)
- 근거 결정: `API-231` **v5** · `API-232` **v3** · `SCREEN-033` **v36** · `SCREEN-044` **v7** · `DFEAT-053` **v20** · `UC-027`
- 범위: 백엔드(`portal/` · `augment/`) + 프론트(`frontend/`)
- ⚠ 설계 **선반영 완료** — 이 CO 는 ITEM 을 고치지 않는다.

## 1. 지금 무엇이 막혀 있나

증강 **요청 접수 창구는 섰는데 위탁에 닿지 않는다.** 요청이 원장에 행만 쌓이고 위탁 이벤트를
발행하지 않아, 사용자가 요청하면 화면이 **영원히 「결과 대기 중」**으로 보인다.

담당이 지어내지 않고 멈춘 것이 맞다 — 생성 조건의 항목·값역이 그때 미정이었다. **이번 라운드가
그것을 확정했으므로 이제 배선할 수 있다.**

## 2. 확정된 계약

### 2-1. 요청 본문
- **생성 조건 5항목, 전부 필수, 값역 닫힘** — 시간대·계절·날씨·지형·심각도.
  **코드 값역의 정본은 접수 창구**이고 화면은 그것을 인용한다.
- **자유 지시문은 선택**이며 **별개 문자열**이다. ⚠ 그 자리에 **객체를 실으면 400** 이다.
- ★**이벤트 유형·세부 유형·증강 종류를 요청 본문에 두지 않는다.** 서버가 **중립값 `ETC`** 를
  고정 송신하고 세부 유형은 **필드 자체가 없다.**
  - ⚠⚠ **되돌리지 마라.** 우리가 보유한 벤더 규격서 판본에는 그 값이 **없어서**, 문서만 보면
    「계약에 없는 값」으로 읽힌다. **협의가 끝난 값**이며 규격서 개정판을 받으면 대조한다.
    **실제로 그 문서만 보고 「구 구현의 잔재」로 오판한 사례가 있었다.**

### 2-2. 요청 현황 목록 — 3구분
| 결과 도착 여부 | 실패 사유 | 판정 |
|---|---|---|
| 참 | — | **결과 도착** |
| 거짓 | 비어 있음 | **결과 대기 중** |
| 거짓 | 있음 | **실패** |

이 **차례대로** 판정하고, 어느 것도 아니면 **대기**로 둔다(fail-closed).
**목록 하나로 판정이 성립해야 한다** — 실패를 가리려고 행마다 단건 조회를 부르지 않는다.

### 2-3. 실패의 귀결
- **실패한 요청은 재조회를 멈춘다**(지금은 실패가 대기로 보여 재조회가 영영 멎지 않는다).
- **실패 행에 후속 작업 진입·내려받기를 노출하지 않는다.**
- **목록 행에는 「결과 확인」 진입만** 둔다 — 후속 작업과 내려받기는 **결과 확인 구역**이 낸다
  (목록에도 두면 같은 조작이 두 자리에 생긴다).

## 3. ★★실패 사유 — 첫 구현에서 어기기 쉬운 자리

실패 사유는 **외부 채널로 나가는 값**이다. **사용자에게 보여 줄 수 있는 문장**이어야 하며
내부 오류 코드·경로·제약명이 섞이면 안 된다.

⚠ **같은 저장소에 이미 어기는 자리가 있다** — 다른 실패사유 필드가 `"프레임 추출 실패:
RuntimeException"` 처럼 **예외 클래스명을 그대로** 싣는다. **그 방식을 복사하면 첫 구현에서 곧바로
이 제약을 어긴다.**

## 4. 낡은 주석 셋 — 함께 고친다

설계가 바뀌어 **근거가 반대 방향이 된** 자리들이다. 그대로 두면 다음 사람이 옛 결론을 되살린다.

1. 프론트 목록 응답 타입 주석 — *"실패 사유는 목록 계약에 없다 → 목록만으로는 대기와 실패를 못
   가른다"*. **그 공백은 닫혔다.**
2. 프론트 생성 조건 표기 모듈 — 근거로 *"항목·값역을 정하지 않는다"*·*"내부 채널 조건을 옮겨 오지
   말 것"* 을 인용한다. **둘 다 폐기된 서술이다.**
3. 백엔드 요청 DTO javadoc — 같은 폐기 문장을 근거로 인용한다.

⚠ **「모르는 항목도 드러낸다」는 규칙은 그대로 유효하다** — 그 코드가 이미 만족하고 있으니
**함께 걷어내지 마라.** 더할 것은 「아는 다섯 항목을 정해진 차례로 + 우리말 이름」이다.

## 5. 하지 말 것

- **관제 증강 경로를 무르게 하지 마라.** 요청 자격(검수 완료)은 그대로 선다.
- **채택·반려를 만들지 마라.** 파생 등재 게이트를 포털 목록에 재사용하지 마라.
- **증강 입력의 조달처 분기를 뒤집지 마라** — 관제=비식별본 기본값, 포털만 원본, **폴백 없음**.
- **새 채널 판별자를 만들지 마라** — 아키텍처 가드가 지킨다.
- 결과물 저장 루트: **포털 자산의 파생물은 포털 저장 루트 아래**여야 한다. 그렇지 않으면
  사용자가 자기 결과물을 **조회도 내려받기도 못 한다**(서빙 가드가 그 범위만 허용).

## 6. 수용 기준

1. 포털 회원이 **생성 조건 5항목**을 골라 요청하면 **외부 위탁이 실제로 나간다.**
2. 요청 본문에 **이벤트 유형·세부 유형·증강 종류가 없다.** 위탁 시 중립값이 고정으로 실린다.
3. 항목 누락·값역 밖은 **입력 오류로 거부**된다.
4. 목록 **하나로** 3구분이 성립한다. 실패 행은 재조회가 멎고 후속·내려받기가 안 뜬다.
5. 실패 사유에 **예외 클래스명·내부 경로가 섞이지 않는다.**
6. **관제 증강 무변경** — 소스 동치 또는 되돌림 실증.
7. 회귀 무열화 — 백엔드 기준선 **8,483 / 실패 0 / XML 936** · 프론트 **542 파일 / 4,610건**.
