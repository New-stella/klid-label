## §1 배경

사용자가 개발서버(192.168.102.246)에서 저작도구를 열었더니 **「관리자 등록」 화면**이 떴고,
본문이 *"이 시스템에는 아직 관리자가 없습니다"* 라고 말했다. 그런데 **관리자는 이미 등록돼 있다.**

### 실측 (2026-09-07, 246 실 앱 DB `postgis-klid` → `klid`, 스키마 `klid_at`)

```
  user_no   |  user_id  |   user_nm    |   role_cd   |         user_eml_addr
       1001 | reviewer1 | 김검수       | REVIEWER    | reviewer1@cudo.co.kr   ← dev 시드
       1002 | reviewer2 | 이검수       | REVIEWER    | reviewer2@cudo.co.kr   ← dev 시드
       2001 | worker1   | 최라벨       | WORKER      | worker1@cudo.co.kr     ← dev 시드

       9001 | admin     | 시스템관리자 | ADMIN       | admin@cudo.co.kr       ← dev 시드
 9000000001 | pcgtest1  | 찬기차장1    | REVIEWER    | (NULL)                 ← 실제 관제 진입
 9000000002 | test11111 | test11111    | (없음)      | (NULL)                 ← 실제 관제 진입
```

관리자(9001)가 실재하므로 **부트스트랩 창구는 이미 닫혀 있다.** 그 상태에서 화면이 열려 있으니
사용자가 패스워드를 넣어도 `RoleClaimService` 의 ④번 게이트(관리자 0명 검사 — **패스워드 검증보다 앞**)에
먼저 걸려 `409 "이미 관리자가 있어 자가부여가 닫혀 있습니다"` 만 돌아온다. **막다른 화면**이다.

같은 세션의 화면 상단(GNB)에는 역할 배지가 「관리자」로 **정상** 표시되는데 이름만 **"사용자"**,
아바타 이니셜은 **"사"** 로 나온다. 사용자 관리 목록에는 같은 사람의 이름이 정상으로 뜬다.

### 근본 원인 — 하나다: **FE 가 서버 진실원을 부분적으로만 받아 쓴다**

`GET /v1/me` 응답 `MeResponse(userId, name, role, channel)` 는 필요한 값을 **다 준다.**
그런데 `SessionIngressPage` 가 `role` **하나만** 꺼내 `useAuthStore.setServerRole` 로 주입하고
`userId`·`name` 은 버린다. 그리고 「창구가 열려 있는가」는 서버에 **묻는 수단 자체가 없다**.
그 결과가 아래 R1~R3 이며, R4 는 같은 라운드에서 처리하는 사양 변경이다.

### 왜 지금 이 화면에 도달했나 (증거)

```

       at 2026-09-04T08:08:26.000Z. Current time: 2026-09-07T01:08:44.285Z.
```

⚠ 인프라 문제가 아니다 — `/label-studio/api/v1/me`·`:13000/api/v1/me` 모두 토큰 없을 때 401 로

### R5 의 근거

관제 인계 토큰에는 **이메일 클레임이 없다**(실측 계약: `sub`·`iss`·`role`·`channel`·`name`·`exp`).
따라서 관제로 실제 진입한 사용자는 `user_eml_addr` 가 **영구히 NULL** 이다(위 표의 아래 두 줄).
지금 이메일이 보이는 6건은 **전부 `db/seed/dev-seed.sql` 의 dev 시드**이며 운영에는 없다.
즉 운영에서 이 컬럼은 **전 행이 빈 칸**이 된다. 반면 로그인ID 는 실제로 들어온다.


### R6 의 근거

조회 창구의 검색 키워드는 **이미 로그인ID·이름·이메일 3축 부분일치**다 — 서버는 진작 아이디로 찾고
있었고 화면 사양만 「이름 또는 이메일」로 좁게 적혀 있었다. R5 로 목록에서 이메일이 사라지면 화면이
**안내하지 않는 숨은 매칭 축**이 남는다. 운영에서 이메일이 전 행 빈 값이므로 그 축은 실익도 없다.
→ **이름·로그인ID 2축으로 통일**한다. 화면 문구(placeholder)는 사용자 표현대로 「이름 / 아이디를
입력하세요.」로 하고, 사양 서술에서는 목록 컬럼명과 같은 어휘 「로그인ID」를 쓴다.

⚠ 이건 **조회 창구 계약 변경**이다(R5 와 달리 표시만 바꾸는 것이 아니다). 검색 축에서 이메일을 빼면
이메일로 찾던 조회는 결과가 달라진다 — 운영 데이터에는 해당 행이 없어 영향이 없으나, 개발 시드 계정을
이메일로 찾던 동선은 사라진다. 인지·수용한 대가다.

> ★ **`user_eml_addr` 컬럼과 응답 필드 `email`/`userEmail` 은 존치한다.** 화면 표시만 바꾼다.
> 컬럼을 지우면 이미 적재된 시드·과거 행의 값을 표현할 수 없고 계약이 깨진다.
> `UserSummaryResponse` 에 `loginId` 가 **이미 있으므로 BE 계약 변경은 없다** — FE 표시 변경뿐이다.

## §3 도메인별 변경 상세

### DOMAIN-001 (사용자·권한) — `klid-d001-implementer`

**대상**: `backend/src/main/java/kr/co/cudo/authoring/auth/`

**변경 — 부트스트랩 창구 개폐를 FE 가 알 수 있게 노출한다 (R1 의 서버측 절반)**

판정 재료는 이미 있다: `LsUserRoleRepository.countByRoleCd(String roleCd)`.
`RoleClaimService` 가 ④번 게이트에서 쓰는 바로 그 값이다. **판정 로직을 복제하지 말고
그 단일 판정 지점을 재사용**한다(두 번째 진실원을 만들지 않는다 — 이 저장소의 반복 결함 패턴).

**노출 방식 = 별도 조회 창구 신설** (사용자 확정 2026-09-07).
- **`MeResponse` 를 확장하지 않는다.** 그 응답은 관제 진입 경로의 핵심이라 필드 추가가
  다른 소비자에게 번지고, 「나에 대한 응답」에 시스템 전역 상태를 얹는 것은 응집도가 낮다.
- **인증을 요구한다.** 미인증자에게 관리자 존재 여부를 알릴 이유가 없다 — 이 화면에는
  인증 후에만 도달한다.
- **FE 는 `role == null` 일 때만 부른다.** 역할 보유자는 애초에 이 창구를 타지 않으므로
  일반 진입 지연은 증가하지 않는다.
- 정확한 경로·응답 형태는 Phase 3.6 에서 확정한 `design_refs` 를 따른다.

**불변**:
- `RoleClaimService` 의 **게이트 순서를 바꾸지 않는다.** ④(관리자 0명)가 패스워드 검증보다
  **앞**인 것은 의도다 — 뒤로 내리면 닫힌 창에서도 패스워드 정오답이 401/409 로 갈려
  **패스워드 오라클**이 된다. 회귀 가드가 이 순서를 고정하고 있다.
- 응답에 **관리자 수를 그대로 노출하지 않는다.** 필요한 것은 「열림/닫힘」 boolean 이다.
  인원수는 미인증자에게 줄 정보가 아니다.
- `AutoWorkerRegistrar` 의 동작(조건부·`DO NOTHING`·fail-open)을 건드리지 않는다.

**수용기준**:
- 관리자가 0명이면 「열림」, 1명 이상이면 「닫힘」이 응답에 실린다.
- 닫힘 판정과 `RoleClaimService` 의 409 판정이 **같은 조회**에서 나온다(갈리면 화면과 서버가 어긋난다).

### 프론트 (SCREEN-002 · SHELL-001 · SCREEN-024) — `klid-web-implementer`

**대상**: `frontend/src/`

#### R1+R2 — 창이 닫혀 있으면 관리자 등록 화면을 띄우지 않는다

- `pages/RoleClaimPage.tsx`
  - 서버에서 받은 **창구 개폐**로 분기한다.
    - **열림**(관리자 0명) → 지금 화면 그대로. 문구도 그대로 참이다.
    - **닫힘** → *"이 시스템에는 아직 관리자가 없습니다"* 를 **띄우지 않는다.** 대신
      「역할이 아직 부여되지 않았습니다 — 관리자에게 역할 부여를 요청하세요」 안내를 보여준다.
      패스워드 입력칸·등록 버튼을 **노출하지 않는다**(눌러도 409 뿐인 막다른 길).
  - ⚠ 파일 상단 javadoc 의 폐기 이력 주석(*"작업자/검수자 중 하나를 고른다"* 등 되살리지 말 것)은
    **그대로 보존**한다. 지우면 같은 실수가 되돌아온다.
- `router/guards.tsx` · `features/auth/SessionIngressPage.tsx`
  - `role == null` 이라는 이유만으로 관리자 등록 화면에 보내지 않는다. 판정 축은
    **「역할 없음」 + 「창구 열림」** 둘이다.

#### R3 — `/me` 실패를 사양으로 위장하지 않는다

`SessionIngressPage.routeInternal` 의 `catch` 가 지금은 모든 실패를 role=null 로 뭉개 `/role-claim` 으로 보낸다.
실패 종류를 갈라야 한다:
- **401(인증 실패·토큰 만료)** → 상위 시스템 재로그인 유도(`redirectToUpstream`). 이 화면의 기존
  만료 처리(`ERROR_EXPIRED`)와 **같은 결말**이어야 한다.
- **그 밖의 조회 장애(5xx·네트워크)** → **오류 화면**으로 표시한다. "관리자가 없습니다"로 바꾸지 않는다.

⚠ 이 파일에는 *"유효 세션이 막다른 길에 빠지지 않게"* 라는 폴백 근거 주석이 있다. 그 취지는
**살리되**(유효 세션은 막지 않는다) **유효하지 않은 세션까지 부트스트랩 화면으로 보내는 부분만**
고친다. 주석도 함께 갱신한다.

#### R4 — 서버가 아는 이름을 헤더가 쓴다

- `stores/useAuthStore.ts` — `setServerRole` 이 role 만 주입한다. `/me` 가 주는 **`name`(및 필요 시 `userId`)도
  함께 주입**하도록 넓힌다(이름을 바꾸든 인자를 늘리든 구현 판단).
- `features/auth/SessionIngressPage.tsx` — `me.name` 을 버리지 말고 주입한다.
- `components/layout/Gnb.tsx:22` · `components/layout/PortalLayout.tsx:57` — 두 곳 모두
  `claims?.name ?? '사용자'` 다. **폴백 자체는 남긴다**(이름이 정말 없을 수 있다). 고치는 것은
  "서버가 아는데도 폴백으로 떨어지던" 원인이다.

⚠ **역할 배지는 건드리지 않는다.** `CurrentRoleBadge` 가 역할 없음을 「미배정」으로 그리는 것은
과거에 `?? Role.WORKER` 로 거짓 역할을 보여주던 결함을 고친 결과다(`SHELL-001`). 되돌리지 말 것.

## §6-B 수용기준 분할 — 근거는 측정이다 (2026-09-07 사용자 확정)

`AC-1016` 보강 후 실측:

```
scenario.when : 1개
scenario.then : 13개
```

★**그 13 중 둘은 그 `when` 의 결과가 아니다.**

| `then` | 관측에 필요한 트리거 |
|---|---|
| 「개폐 조회 응답에 관리자 인원수가 없다」 | **개폐 조회 호출** — 진입과 다른 사건 |
| 「등록 창구가 거절을 가릴 때 쓰는 개폐가 같은 조회에서 나온다」 | **등록 제출** — 진입과 다른 사건 |

`when` 하나에 매달린 `then` 이 그 `when` 으로 **관측되지 않는다** — Gherkin 이 깨졌고, 이것이
분할선이 실재한다는 **기계적 증거**다. 「길어서 나눈다」가 아니다.

부수적으로 `verification_method` 가 `automated_test` 라, 13축을 한 시험으로 묶으면 **어느 축이
깨졌는지 실패 보고가 말해 주지 않는다**(검증 단위 소실).

### 분할선

| 남김 (`AC-1016`) | 떼어냄 (신설) |
|---|---|
| `then[0]~[7]` — 토큰을 **어떻게 해석하는가**(인증·인가·식별·principal 정규화·역할 계층·세션 만료) | `then[8]~[12]` — 역할 없는 사람을 **어디로 보내고 그 판정 근거를 어디서 얻는가** |

신설 AC 의 축: `given` = 역할 없이 인증에 성공한 내부 진입자 / `when` = 진입 처리가 창구 개폐를
조회한다 / `then` = 열림·닫힘 두 갈래 · 창구 셋 도달 · 인원수 미노출 · 개폐 판정 단일 진실원 ·
이름 동시 조달. `UC-041` step7·step9 와 **1:1** 로 붙고 `API-245`·`SCREEN-002`·`SHELL-001`·`ADR-055`
축을 검증하게 된다.

⚠ 동반 필수: **`UC-041.covered_by_acceptances` 갱신**.

## §6-D 사용자 확정 대기 — 이번 라운드가 **드러냈지만 손대지 않은** 것

★이것들은 **이번 라운드가 만든 문제가 아니라 드러낸 문제**다. 전부 계약 변경이라 임의로 처리하지
않았다. 구현과 무관하게 진행할 수 있으나, 방치하면 다음 라운드가 같은 것을 다시 발견한다.

### 「내 정보」 창구 두 벌의 정합 (판정: 중복 아님 — 의도적 분리)

`GET /v1/me`(`API-006`)와 `GET /v1/users/me`(`API-005`)는 **용도·소유 기능·코드 패키지가 갈리는 별개
창구**다(전자=세션 주체 축, 후자=사용자 도메인 프로필 축). 폐기·통합 대상이 아니다.
다만 **정합되지 않은 축 넷**이 남는다:

| 축 | 어긋남 |
|---|---|
| **이름 키 어휘** | 같은 값·같은 조달원인데 한쪽은 `userNm`, 다른 쪽은 `name` |
| **부재 표현** | 한쪽은 `nullable`, 다른 쪽은 non-nullable + 404. ★**역할 없는 진입자가 실재하는데**(실측) 그 사람이 후자를 부르면 무엇이 오는지 **계약에 없다** |
| **security 목록** | `API-005` 응답 역할 값역에는 관리자가 들어갔는데 `security` 는 여전히 검수자·작업자뿐 — **관리자가 못 부르는 창구가 관리자 역할을 응답한다**고 적힌 형태 |
| **`API-005` 의 생존** | FE 호출 **0건** · 화면 `consumes` **0건** · 유일한 역참조는 기능 목록 등재뿐. 그런데 `implementation = implemented / 100` |

⇒ **`API-005` 를 살아있는 계약으로 유지할지가 먼저 정해져야** 나머지 세 축의 정합에 의미가 생긴다.

계약에 만들** 뻔했다. 담당이 적지 않고 되물었다 — **승인.**

대신 원래 의도를 참인 형태로 담았다: *"같은 코드라도 두 창구에서 뜻이 다르다. 사유를 상태코드

⚠ `description` 본문은 **의도적으로 미변경** — 1,800자를 통째 재작성하면 이 채널의 직렬화 때문에
