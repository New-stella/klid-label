## §1 배경

2026-08-25, dev(cudo_246)에서 관제 완료/수정 통지를 처음 활성화한 순간
저작도구의 **`/actuator/health` 전체가 `DOWN`** 으로 떨어졌다.

원인은 `ControlNotifyHealthIndicator` 가 관제서버의 `GET {base}/health` 를 핑해 그 결과로
UP/DOWN 을 판정하는데, **관제지원 데이터셋 API 에 그 경로가 없다**는 것이다.

실측(2026-08-25 · `192.168.102.246:9014`):

| 경로 | 응답 |
|---|---|
| `/health` · `/api/health` · `/actuator/health` | **전부 403** |

관제 `ConfigSecurity` 는 `anyRequest().authenticated()` 이고 `permitAll` 은
`/v3/api-docs/**` · `/swagger-ui/**` · `/swagger-ui.html` · `/api/dev/test` 4경로뿐이라 헬스가 열릴 여지가 없다.
관제 OpenAPI 정본(`/v3/api-docs`) 전수에도 헬스 엔드포인트는 없다. 즉 **구조적으로 영원히 DOWN** 이다.

### ★ 더 깊은 원인 — 판정 기준이 틀렸다

"경로가 없었다"로만 보면 재발한다. 더 정확한 원인은 **HTTP 응답이 왔는데 DOWN 으로 판정한 것**이다.
**403 은 서버가 살아 있다는 증거**다. 현재 인디케이터 3종 전부 `toBodilessEntity()` 를 써서
**4xx·5xx 면 예외 → DOWN** 이 된다. 외부 벤더 루트가 401·403·404 를 주는 것은 흔한 일이므로,
이 판정 기준을 그대로 두면 어떤 벤더를 붙여도 같은 사고가 반복된다.

**사용자 확정(2026-08-25)**
- 관제서버는 헬스체크가 필요 없다.
- 판정 기준은 **「HTTP 응답이 오면 UP, 연결 자체가 안 되면(타임아웃·커넥션 거부) DOWN」**.

#### (2) 신설 — `VlmHealthIndicator`

- **위치**: `backend/src/main/java/kr/co/cudo/authoring/observability/health/VlmHealthIndicator.java`
- **빈 등록 조건**: `vlm.client.url` 이 **비어 있지 않을 때만** 등록한다.
  ADR-049 상 VLM 미연동 판정은 **url 주입 여부**가 한다(활성/비활성 토글은 폐지됐다).
  url 이 비면 위탁 자체가 실패하는 형상이므로, 그때 핑해서 DOWN 을 만들면 **관제와 같은 상시 DOWN** 이 된다.
  → 등록하지 않는 편이 맞다.

  ⚠⚠ **`@ConditionalOnProperty(name = "vlm.client.url")` 로는 이 목적을 달성할 수 없다.**
  (이 CO 초안이 그렇게 지시했으나 **틀렸다** — 2026-08-25 구현·QA 양쪽이 실측으로 반증했다.)
  - `application.yml` 이 `vlm.client.url: ${VLM_SERVICE_URL:}` 로 **키를 항상 정의**하므로,
    미주입 형상은 "키 없음"이 아니라 **"키 있음 + 빈 문자열"** 이다.
  - `@ConditionalOnProperty` 는 `havingValue` 미지정 시 **"키 존재 && 값이 false 가 아님"** 으로 판정한다
    (`OnPropertyCondition.isMatch` → `!"false".equalsIgnoreCase(value)`) — 즉 **빈 문자열도 매칭**시킨다.
  - 실증: 조건만 그 애너테이션으로 바꾸자 `VlmHealthIndicatorRegistrationTest` 2건이 FAILED.
  - ⇒ 판정 축이 **"키 존재"가 아니라 "값이 비지 않음"** 이므로 **값을 보는 조건**을 써야 한다.
    ★ 단 SpEL 표현식(`@ConditionalOnExpression`)은 쓰지 않는다 — `Environment.resolvePlaceholders` 가
    **SpEL 파싱 이전에** 값을 치환하므로 url 에 작은따옴표가 있으면 표현식이 깨져 **기동이 실패**한다
    (QA 가 `http://host/a'b` 로 재현). **문자열 파싱이 없는 커스텀 `Condition`** 을 쓴다.

  > 이 함정은 `${ENV:}` 형태로 기본 빈값을 두는 이 저장소의 모든 연동 설정에 공통이다.
  > "단순화하자"며 `@ConditionalOnProperty` 로 되돌리면 조용히 회귀한다 — 회귀 가드가 그것을 막는다.
- **핑 방법**: **`VlmClient.fetchStatus()` 를 그대로 호출한다.** 새 경로를 만들지 않는다.
  - 규격 §3.5 `GET /v1/videovlm-klid/status`. `VlmClient.STATUS_PATH` 상수와 메서드가 이미 있고
    `VlmTimeseriesStep` 이 위탁 전 가용성 확인에 쓰고 있다.
  - 응답 타입 `VlmServerStatus(status, queue, pending)` — `ready` / `busy` / `loading`.
- **판정 (★사용자 확정 기준)**
  - **응답이 오면 `UP`** — `busy`·`loading` 도 UP 이다(서버는 살아 있다). detail 에 `status`·`queue`·`pending` 을 싣는다.
  - **연결 자체가 안 되면 `DOWN`** — 타임아웃·커넥션 거부.
  - **4xx·5xx 도 UP** 으로 본다(응답이 왔으므로 서버는 살아 있다). detail 에 `httpStatus` 를 싣는다.
    → `retrieve()`/`toBodilessEntity()` 가 아니라 **`exchangeToMono`** 로 상태코드를 잡아야 한다.
      `fetchStatus()` 는 `retrieve()` + `bodyToMono` 라 4xx 에서 예외가 되므로, **그 예외가
      `WebClientResponseException`(=응답이 온 경우)이면 UP 으로 처리**한다.
      `VlmClient` 를 고치지 말고 **인디케이터에서 예외 종류로 가른다.**
- **타임아웃**: 기존 인디케이터와 동일하게 **2초**. `fetchStatus()` 자체 타임아웃(`vlm.client.timeout-seconds`,
  기본 10s)이 더 길므로 인디케이터 쪽에서 2초로 한 번 더 감싼다 — 헬스가 10초를 잡아먹으면 안 된다.
- **detail 규약**: `service: "vlm"` + 위 필드. **CWE-209 — 예외는 클래스명만 노출**하고
  스택트레이스·URL·토큰을 싣지 않는다(기존 3종과 동일).
- **테스트**: 신설. 최소 4케이스 —
  `상태ready면_UP` · `상태busy여도_UP` · `4xx응답이어도_UP` · `연결불가면_DOWN`.
  기존 `ControlNotifyHealthIndicatorTest` 의 목서버(MockWebServer 등) 골격을 참고하되,
  **삭제되는 파일을 참조하지 말고 독립 작성**한다.

### DEV_FIX 1 에서 추가로 드러난 사실 (CO 초안이 몰랐던 것)
**「200인데 본문이 이상하다」는 한 종류가 아니라 두 종류이고 예외 타입이 갈린다.** 목서버 4형상 프로브로 실측:

| 응답 형상 | 던져지는 예외 | 처리 |
|---|---|---|
| `200` + `application/json` + HTML 본문 | `DecodingException`(cause `JsonParseException`) | UP + `decoded=false` |
| `200` + `text/html` | **`WebClientResponseException(status=200)`**(cause `UnsupportedMediaTypeException`) | UP + `httpStatus=200` + `decoded=false` |
| `200` + `application/json` + 빈 본문 | 예외 없음, 결과 `null` | 기존 null-safe 분기가 처리 |
| 타임아웃 · 커넥션 거부 | `ReactiveException`(←`TimeoutException`) · `WebClientRequestException` | **DOWN** |

⚠ **`WebClientResponseException` 은 이름과 달리 「오류 상태코드 예외」가 아니다** — 디코더가 없으면 `200` 에도 던져진다.
한쪽만 잡으면 **절반이 조용히 DOWN** 이 된다.

QA 가 `javap` 로 계층을 실측해 안전성을 구조적으로 확인했다 — `WebClientResponseException` 과
`WebClientRequestException` 은 **형제**(공통 부모 `WebClientException`)이고 `DecodingException` 은
`CodecException` 계열로 **완전 분리**라, 세 catch 가 서로소이며 **연결 실패가 UP 으로 새는 경로가 없다.**

### 회귀 총계 검증 (QA 실측)

### ★ CO 초안이 틀렸던 지점 (기록 — 같은 실수 방지)
초안 §3(2)가 지시한 `@ConditionalOnProperty(name = "vlm.client.url")` 는 **AC4 를 충족할 수 없었다.**
구현 에이전트가 실험으로 반증(조건만 바꾸자 RegistrationTest 2건 FAILED)했고 QA 가 독립 확인(SpEL 직접 평가 +
