## §1 배경

2026-09-16 현장 WAS(`klid-ai-gen-was-01`)에서 영상 `rawSn=9` 의 시계열 위탁이 실패했다.
로그에 남은 것은 아래뿐이었다.

```
[Vlm] describe submit request_id=15d54683-… pinned=true
[Vlm] custom submit request_id=69277629-… pinned=true
[Vlm] non-retryable 4xx status=400        ← 두 창구 모두
[Batch][VlmTimeseries] submit failed (no status demotion) rawSn=9 cause=NonRetryableExternalException
```

벤더(IntelliVIX KLID 연동 API v1.2.0 §2.10)는 400 응답 본문의 `detail` 에 거부 사유를 담아 보내는데,
우리는 **그 본문을 읽고 버린다.** 그래서 「허용되지 않은 경로」인지 「파일 없음」인지 「형식 오류」인지
우리 쪽에서 알 방법이 없고, 벤더 서버 로그를 받아 봐야만 원인을 알 수 있다.

조사해 보니 외부 연동 전반이 같은 상태다.

| 연동 | 클라이언트 | 현재 로그 |
|---|---|---|
| 비식별(KPST) | `KpstDeidentifyClient` | 2줄 — 예외 타입·상태 코드만 |
| 시계열 | `VlmClient` | 4줄 — 전송 사실·4xx 상태 코드만 |
| 증강 | `HttpExternalAugmentClient` | 8줄 — 상태 코드만, 본문 없음 |
| AI 추론 | `AiServerClient` | **0줄** |
| 관제 통지 | `ControlNotifyClient` | **0줄** |
| 관제 계정 창구 | `ControlAccountClient` | 7줄 — 결과 분류만 |
| 포털 소재 조달 | `PortalMaterialsClient` | 주소 미설정만 |

공통으로 **대상 주소·소요 시간·오류 응답 본문**이 없다.

## §2 변경 요지

1. 외부향 `WebClient` 빈 전부에 **공통 호출 로그 필터 하나**를 붙인다. 호출마다
   `연동 이름 · 메서드 · 대상(host:port + 경로, 쿼리 제외) · 상태 코드 · 소요 ms` 를 남긴다.
2. **4xx·5xx 일 때만** 응답 본문을 읽어 **1000자로 자르고 제어문자를 치환하고 토큰·비밀류 값을 가린 뒤** WARN 으로 남긴다.
   본문을 읽은 뒤에도 뒤쪽의 기존 `onStatus` 처리(재시도 분류·벤더 코드 파싱)가 **똑같이** 본문을 읽을 수 있어야 한다.
3. 관제 계정 창구는 응답에 세션 토큰이 실릴 수 있어 **본문을 기록하지 않는다**(상태 코드·소요 시간만).
4. 정상 응답 본문·요청 본문은 평소 기록하지 않는다. 요청 본문은 **DEBUG 레벨에서만** 남긴다.
5. DB(`LS_BATCH_PROC_LOG`)는 건드리지 않는다. 기존 클래스별 로그도 그대로 둔다.

## §3 도메인별 변경 상세

### 공유기반 선처리 (Phase 3.5) — 전부 이 절이다

- **신규**: `backend/src/main/java/kr/co/cudo/authoring/common/client/ExternalCallLoggingFilter.java`
  - `static ExchangeFilterFunction of(String integration, boolean logErrorBody)` 형태의 팩토리.
    `integration` 은 로그의 연동 이름(`DEIDENTIFY`·`VLM`·`AUGMENT`·`AI_SERVER`·`CONTROL_NOTIFY`·`CONTROL_ACCOUNT`·`PORTAL_MATERIALS`).
    가능한 곳은 `IntegrationEndpoint.name()` 을 쓴다(값 복제 금지).
  - 로그 형식(`[도메인] 행위 키=값`):
    - 완료: `[ExternalCall] completed integration=VLM method=POST target=gpu01:9500/v1/videovlm-klid/describe status=400 elapsedMs=163`
      — 2xx·3xx 는 INFO, 4xx·5xx 는 WARN.
    - 오류 본문: `[ExternalCall] error body integration=VLM status=400 length=87 body={"detail":"..."}`
      — 1000자 초과 시 잘라 내고 `truncated=true` 를 붙인다.
    - 연결 실패·타임아웃(응답 없음): `[ExternalCall] failed integration=VLM method=POST target=… elapsedMs=… cause=<예외 단순 클래스명>` — WARN. **예외 메시지 원문은 남기지 않는다**(CWE-209, 기존 관례).
    - 요청 본문(DEBUG 활성 시에만): `[ExternalCall] request body integration=… body=…` — 같은 절단·치환·마스킹 적용.
      ⚠ 요청 본문은 `ClientRequest` 에서 바로 꺼낼 수 없다(`BodyInserter`). 구현 비용이 크면 **이 항목만 보류**하고 §7 에 사유를 남긴다 — 핵심은 오류 응답 본문이다.
  - `target` 은 **스킴·userinfo·쿼리스트링·프래그먼트를 뺀** `host:port + path` 만. 쿼리에 키가 실릴 수 있다(CWE-532).
  - **헤더 값은 어떤 경우에도 기록하지 않는다**(`Authorization`·`x-access-token`·`X-API-Key`·포털 소재 API 키).
  - 오류 본문 처리:
    - `response.bodyToMono(String)` 로 한 번 읽고(없으면 빈 문자열), **`response.mutate().body(읽은 본문)` 으로 되돌려** 다음 단계에 넘긴다.
      ⇒ `VlmClient.toNonRetryable4xx` 의 벤더 코드 파싱, `HttpExternalAugmentClient`·`KpstDeidentifyClient`·`ControlAccountClient` 의 본문 해석이 **변함없이** 동작해야 한다.
    - 읽는 크기는 기존 `maxInMemorySize` 를 넘지 않게 한다. 본문 읽기가 실패하면 **로그만 생략**하고 원래 응답을 그대로 넘긴다(관측이 요청 결과를 바꾸면 안 된다).
    - 치환: CR·LF·TAB 등 제어문자 → `_` (CWE-117).
    - 마스킹: JSON 키가 `token`·`access`·`refresh`·`secret`·`password`·`api_key`·`apikey`·`authorization`·`session` 을 포함하면(대소문자 무시) 그 값을 `***` 로. `Bearer <값>` 꼴도 가린다.
  - `logErrorBody=false` 면 오류 본문을 **읽지도 않는다**(관제 계정 창구).
  - 소요 시간은 `System.nanoTime()` 차이로 계산한다. (Micrometer 계측은 이번 범위 밖)
- **배선**: 아래 빈 각각에 필터를 **주소 재작성·전송 가드보다 뒤(안쪽)** 에 붙인다 — 실제로 나가는 URL(재작성·핀 적용 후)을 기록해야 하고, 가드가 막은 요청은 가드가 이미 ERROR 를 남긴다.
  | 빈 | 파일 | integration | 본문 |
  |---|---|---|---|
  | `kpstDeidWebClient` | `common/config/KpstWebClientConfig` | `DEIDENTIFY` | 기록 |
  | `kpstDeidProgressHttpClient` (있으면 같은 방식) | 같은 파일 | `DEIDENTIFY` | 기록 |
  | `vlmWebClient` | `common/config/WebClientConfig` | `VLM` | 기록 |
  | `aiServerWebClient` | 같은 파일 | `AI_SERVER` | 기록 |
  | `controlNotifyWebClient` | 같은 파일 | `CONTROL_NOTIFY` | 기록 |
  | `controlAccountWebClient` | 같은 파일 | `CONTROL_ACCOUNT` | **기록 안 함** |
  | `portalMaterialsWebClient` | 같은 파일 | `PORTAL_MATERIALS` | 기록 |
  | 증강 위탁 빈 | `augment/integration/AugmentApiWebClientConfig` | `AUGMENT` | 기록 |
  - `deidentifyWebClient` 는 주입처 0건인 죽은 빈이라 **건드리지 않는다.**
  - ⚠ `ai-server` 는 추론 이미지(base64)를 응답으로 받을 수 있다 — 오류일 때만 읽으므로 평소 영향은 없지만, 오류 본문도 1000자로 자른다.
- **불변**
  - 기존 클래스별 로그 문구·레벨 · `SKIP_REASON_*` 문자열 · 재시도 분류(429만 재시도) · 서킷 브레이커 판정 · `EXPLICIT_TARGET_ATTRIBUTE` 처리 · 전송 가드 순서.
  - 요청·응답의 실제 내용(필터가 관측 외 동작을 하면 안 된다).
  - `LS_BATCH_PROC_LOG` 등 DB.
- **주의**
  - 필터 순서: `WebClient.Builder.filter()` 는 **먼저 등록한 것이 바깥**이다. 로그 필터를 맨 뒤에 등록해야 재작성된 URL 을 본다. 시험으로 고정한다.
  - `vlmWebClient` 의 `stripCredentialOnHostChange` 처럼 조건부로 붙는 필터가 있다 — 그보다도 뒤에 붙인다.
  - `logback-spring.xml` 에 이 로거 레벨을 따로 둘 필요는 없다(루트 INFO). 단 prd 에서 INFO 가 켜져 있는지 확인하고, 꺼져 있으면 완료 로그는 INFO 라 안 보인다는 점을 §7 에 남긴다.
  - 표준용어·DB 변경 없음.
- **수용기준**
  1. 외부 서버가 400 과 `{"detail":"path not allowed"}` 를 돌려주면, 로그에 `status=400` 과 그 `detail` 이 **한 줄로** 남고, `VlmClient` 는 기존대로 `NonRetryableExternalException` 을 낸다.
  2. 400 본문에 `{"code":40001,"detail":"…"}` 가 오면 `VlmClient` 가 `vendorCode=40001` 을 **여전히** 파싱한다(본문 재사용 확인).
  3. 1000자 넘는 오류 본문은 1000자로 잘리고 `truncated=true` 가 붙는다.
  4. 오류 본문의 개행은 로그에서 한 줄로 치환된다.
  5. 오류 본문에 `"access_token":"abc"` 가 있으면 로그에 `abc` 가 나오지 않는다.
  6. 요청 URL 에 `?key=secret` 이 붙어 있어도 로그의 `target` 에 쿼리가 없다.
  7. `Authorization`·`x-access-token`·`X-API-Key` 헤더 값이 어떤 로그에도 나오지 않는다.
  8. 관제 계정 창구가 401·500 을 받아도 본문이 기록되지 않고 상태 코드만 남는다.
  9. 연결 실패·타임아웃이면 `failed` 로그가 예외 단순 클래스명과 함께 남고, 예외 전파는 그대로다.
  10. 2xx 응답은 본문을 읽지 않는다(한 줄 INFO 만).
  11. 주소 재작성이 적용된 요청은 **재작성된** host 가 기록된다.
  12. 위 8개 빈 전부에 필터가 붙어 있다(배선 시험).

> **범위 추가 (2026-09-16 사용자 확정, QA 1라운드 후)** — `NFR-038` v3 로 설계 먼저 갱신.
> - 주기 점검 호출(시계열 장비 상태점검·비식별 헬스 핑)은 **성공 시 DEBUG**, 실패·취소는 평소 레벨. 위탁 직전 상태 조회는 INFO 유지.
> - **취소(대기 시간 초과 포함)도 기록** — `[ExternalCall] cancelled …`. AI 추론은 INFO(사용자 취소가 잦음), 나머지와 주기 점검은 WARN. 완료 로그와 중복 금지.
> - KPST 진행 조회(`kpstDeidProgressHttpClient`, reactor-netty HttpClient 직사용)는 훅(`doOnRequest`/`doOnResponse`/…)으로 completed·failed 를 단다. 오류 본문은 이 경로에서 기록하지 않는다.

## §4 영향·리스크

- **하위호환**: 외부 계약·API·DB 무변경. 로그 줄이 늘어날 뿐이다.
- **로그 양**: 호출 1건당 INFO 1줄. 배치는 1건/분 수준이고 AI 추론은 화면 조작마다 1줄이라 부담이 작다. 오류 본문은 오류일 때만.
- **되돌리기**: 필터 등록 줄만 지우면 된다.
- **리스크**
  - 본문 재사용을 잘못하면 **기존 오류 처리가 빈 본문을 받아** 벤더 코드 파싱이 조용히 깨진다 → 수용기준 2로 막는다.
  - 마스킹 누락 시 토큰이 로그에 남는다 → 관제 계정 창구는 본문 기록 자체를 끈다. 나머지는 수용기준 5·7.
  - 내부 주소(host:port)가 로그에 남는다 — 이미 `[ExternalUrl]` 로그가 같은 값을 남기고 있고 서버 로그는 내부 전용이라 수용한다. 예외 메시지·DB 컬럼에는 싣지 않는 기존 규칙은 그대로다.

**범위 밖 — 별건 보고**: `VlmTimeseriesStep.observeServerStatus` 가 인자 없는 `fetchStatus()` 로 배포 기본 주소(`vlm.client.url`)에 상태 조회를 보낸다. 그 값이 빈 WAS(`klid-ai-gen-was-01`)에서는 위탁마다 `[IntegrationEndpoint] … 연동 주소가 설정되지 않아` ERROR 가 찍힌다. 실제 위탁은 노드 원장의 장비(`gpu01vlm`)로 핀되어 나가므로, 상태 조회도 그 장비로 보내야 하는지 결정이 필요하다.

**남은 한계 (인지·수용)**:
- 마스킹 범위는 **JSON 문자열 키의 값**이다. 문자열 안에 이스케이프돼 들어간 JSON(`"detail":"… \"token\":\"x\" …"`)·FastAPI 422 의 `input` 되풀이·작은따옴표 JSON·폼 인코딩(`k=v`)은 가리지 않는다 — 지금 나가는 요청 본문에 자격증명 필드가 없어 드러날 경로는 확인되지 않았다. `k=v` 꼴은 운영 레이아웃의 전역 마스커(`LogMaskingPatterns`)가 한 번 더 덮는다. 요청 본문에 자격증명을 싣게 되면 그때 다시 봐야 한다.
- 비정형 JSON(괄호 짝 불일치·깊이 257 이상·닫히지 않은 문자열)은 **입력 끝까지** 가려 뒤따르는 사유가 로그에서 사라질 수 있다(관측 손실, 유출 아님). `accessCount` 처럼 키 이름에 낱말이 든 비자격증명 필드도 가려진다.
- **요청 본문 DEBUG 기록은 보류** — 나가는 바이트를 가로채야 해 관측이 요청을 바꿀 위험이 있다.
- **KPST 진행 조회**(reactor-netty 직사용)는 완료·실패·취소 로그만 남기고 **오류 본문은 기록하지 않는다**. 상대가 응답 전에 연결을 끊으면 종료 훅 순서에 따라 `failed` 대신 `cancelled` 로 남을 수 있다(실측에서는 `failed`).
- 비식별 헬스 핑(`/`)이 실벤더에서 404 면 헬스 호출마다 WARN 이 남는다 — 기존 헬스 판정이 이미 DOWN 이므로 그 사실을 따르는 것이다.
- 운영(prd)은 `kr.co.cudo.authoring=INFO` 라 `completed` 가 보이고, 주기 점검 성공(DEBUG)은 보이지 않는다.
