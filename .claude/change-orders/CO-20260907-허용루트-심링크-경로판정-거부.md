## §1 배경

### 현장 증상 (온프렘 `klid-ai-gen-was-01`, 2026-09-07 · 사용자 스크린샷 5매)

관리자 화면 「업로드 → 산출물 가져오기」(SCREEN-039)의 **산출물 폴더 선택** 창에서:

| 단계 | 화면이 보여준 것 | 서버가 실제로 다룬 값 |
|---|---|---|
| 1. 창을 연다 | 루트 목록에 `nas-storage` 1건 | 설정 `STORAGE_RAW_MOUNT_ROOTS=/nas-storage` |
| 2. 그것을 누른다 | 하위 목록은 **정상**, 그런데 빵부스러기가 `허용 저장소 > nas-storage1` 로 바뀐다 | 응답 `path` = `/nas-storage1` (**실경로**) |
| 3. 그 아래 `klid-at` 을 누른다 | **400 「허용된 저장소 범위 밖의 경로입니다」** | 요청 `path` = `/nas-storage1/klid-at` |
| 4. 「상위로」 | **계속 비활성** | 응답 `parent` 가 늘 `null` |

즉 **루트 바로 아래에서 한 걸음도 나갈 수 없다.** 현장 `/nas-storage` 는 `/nas-storage1` 을 가리키는
심링크다(빵부스러기가 실경로로 바뀐 것이 근거 — 확정 확인은 현장 `readlink -f /nas-storage`).

### 근본 원인 — 서버가 자기가 내준 경로를 자기가 거부한다

`transfer/ImportSourcePolicy.verifyUnderReadableRoots` 는 세 단계로 판정한다.

1. **표기 기준** — `roots.stream().noneMatch(candidate::startsWith)`
2. **실경로 기준(조상)** — `roots.stream().noneMatch(root -> nearest.startsWith(realOrNearest(root)))`
3. **실경로 기준(대상)** — `roots.stream().noneMatch(root -> real.startsWith(realOrNearest(root)))`

**2·3 은 루트를 `realOrNearest(root)` 로 펴서 비교하는데 1 만 설정 원문 그대로 비교한다.**
`roots` 의 실체는 `VideoArtifactRootResolver` 의 `normalize()` = `Paths.get(v).toAbsolutePath().normalize()`
까지만 한 **표기 경로**(`/nas-storage`)다.

그런데 이 메서드가 **성공 시 돌려주는 것은 `candidate.toRealPath()`** 인 실경로(`/nas-storage1`)이고,
`ImportBrowseService.collect` 는 그 실경로를 응답 `path`·`entries[].path` 에 싣는다. 화면은 계약대로
그 값을 그대로 되돌려 보낸다(API-221 이 *"화면은 이 값을 그대로 입력칸에 넣는다"* 로 규정).

⇒ `/nas-storage1/klid-at`.startsWith(`/nas-storage`) 가 **거짓**이라 1 에서 떨어진다. 2·3 은 통과할
값인데 **가장 느슨해야 할 검사가 가장 먼저 막는다.**

「상위로」 비활성도 같은 뿌리다 — `resolveParent` 가 부모를 `verifyFolder` 에 넣어 보고 거부되면
`null` 을 싣는데, 실경로 루트(`/nas-storage1`)의 부모는 `/` 이고 그것이 1 에서 거부돼 **항상 `null`** 이다.

### 같은 결함이 공유기반에도 있다

`common/storage/VideoArtifactRootResolver.verifiedBaseUnder` 가 **똑같은 lexical-first 구조**다
(`boolean lexicalOk = roots.stream().anyMatch(base::startsWith)` → 이후 `realOrNearest` 재검사).
지금은 터지지 않는다 — 적재가 만드는 경로는 `ImportPathPolicy.rawFilePath(storageRawPath, …)` 가
설정값(`/nas-storage`) 기준으로 조립해 표기가 자기들끼리 일관되기 때문이다. 그러나 관제 인입이나
사람 입력으로 **실경로 표기(`/nas-storage1/…`)가 한 번이라도 섞이는 순간 403** 이 된다.

### 왜 지금까지 시험에 안 걸렸나 (★재발 방지의 핵심)

`ImportSourcePolicyTest` 는 macOS 에서 **이미 심링크 루트 위에서 돌고 있다** — `@TempDir` 가
`/var/folders/…` 이고 `/var` 는 `/private/var` 심링크다. 그런데도 전건 통과한다. 이유는
**시험이 판정기가 돌려준 실경로를 다시 판정기에 넣어 보지 않기 때문**이다:

```java
Path verified = policy.verifyFolder(folder.toString());   // 표기 경로를 넣는다
assertThat(verified).isEqualTo(folder.toRealPath());      // 실경로가 나오는 것만 확인한다
```

**왕복(round-trip)을 한 번도 닫지 않았다.** 그래서 「탐색이 준 값을 되넣으면 거부된다」는 이 결함이
시험 밑을 그대로 통과했다. Linux CI(`/tmp` 가 심링크 아님)에서는 아예 재현되지도 않는다
⇒ 새 회귀 가드는 **명시적으로 심링크를 만들어** 플랫폼과 무관하게 고정해야 한다.

### 이 CO 는 확정된 결정을 뒤집는다 (★기록 필수)

`deploy/onprem/docs/04-configuration.md:325` 의 ⚠⚠ 블록이 이 증상 2가지(「상위로」 항상 비활성 ·
탐색이 준 위치를 넣으면 400)를 **정확히 예언해 두고** 이렇게 적었다:

> 판정기(`ImportSourcePolicy`·`VideoArtifactRootResolver`)를 고치는 대신 **운영 규약으로 고정**한 항목이다.

**사용자가 2026-09-07 에 그 결정을 명시적으로 뒤집었다**(정석안 = 판정기 수정 선택). 이 저장소는
「철회된 정책 재시도」가 반복 사고 패턴이므로, 반전 근거를 ADR 로 남기고 온프렘 문서의 그 블록도
함께 갱신한다(규약을 지우는 것이 아니라 *"이제 판정기가 심링크 루트를 받아들인다"* 로 바꾼다).

**운영 규약이 성립하지 않은 이유**: 규약은 *"루트를 실경로로 지정하라"* 인데, 그렇게 하면
이미 DB 에 적재된 `/nas-storage/…` 표기 경로들이 **같은 lexical 검사에서 403** 이 된다(위 문단).
즉 규약을 지켜도 다른 축이 깨지므로, 규약만으로는 닫히지 않는 결함이다.

## §2 변경 요지

**표기 기준 검사가 허용 루트의 실경로도 함께 인정하게 한다.** 후보 경로가 루트의 **표기** 또는
**실경로** 중 하나로 시작하면 1단계를 통과시키고, 2·3단계(실경로 재검사)는 그대로 둔다.

- **심링크가 없는 형상에서는 동작이 완전히 동일하다** — `realOrNearest(root) == root` 라 판정 결과가
  비트 단위로 같다. 넓어지는 것은 **루트의 표기와 실경로가 갈리는 경우 하나뿐**이다.
- **방어 축을 하나도 잃지 않는다** — `..` 순회(CWE-22)는 `candidate` 가 이미 `normalize()` 된 값이라
  두 표기 어느 쪽으로도 루트 밖으로 떨어지고, 범위 밖을 가리키는 심링크(CWE-59)는 2·3단계가 계속 막는다.
- `ImportSourcePolicy` 와 `VideoArtifactRootResolver` **둘 다** 고친다 — 같은 결함이고, 한쪽만 고치면
  「탐색은 되는데 적재하면 403」이라는 더 헷갈리는 형태로 남는다.

- **수용기준**:

  - 허용 루트 **밖**을 가리키는 심링크는 여전히 거부된다.

- **하위호환**: 판정이 **넓어지기만** 한다(좁아지는 경우 없음). 지금 통과하는 요청은 전부 계속 통과한다.
  심링크가 없는 형상에서는 판정 결과가 변경 전과 **완전히 동일**하다.
- **API 계약 변경 없음** — 응답 스키마·상태코드·필드 의미가 모두 그대로다. 바뀌는 것은
  「지금까지 잘못 거부하던 것을 받아들인다」뿐이다.
- **되돌리기**: 두 판정기의 lexical 검사를 원래 형태로 되돌리면 즉시 원복(스키마·데이터 변경 없음).
- **리스크**:
  - `VideoArtifactRootResolver` 는 산출물 쓰기 축이라 **회귀 표면이 넓다**(main 23파일). 전체 회귀 필수.
  - ⚠ **1단계를 넓히면서 2·3단계를 함께 손대면 CWE-59 방어가 뚫린다.** 이 CO 의 유일한 실질 위험이
    여기다 — 「일관성」을 이유로 세 검사를 하나로 합치려는 시도를 막아야 한다. 세 단계는 서로 다른
    것을 막는다(표기 순회 / 조상 심링크 / 마지막 요소 심링크).
  - `realOrNearest` 를 판정 시점마다 부르면 파일시스템 접근이 는다 — 다만 2·3단계가 **이미 매 판정마다**
    그것을 부르고 있어 **새로운 비용 패턴이 아니다**(아래 설계 결정 1의 근거).

### 설계 결정 2건 (이 CO 가 확정한다)

**결정 1 — 루트 실경로를 「판정 시점마다」 해석한다.** 생성 시 1회 해석해 보관하지 않는다.
- 근거 ①: 2·3단계가 **이미 매 판정마다** `realOrNearest(root)` 를 부른다. 1단계에 같은 것을 더하는
  것은 새 비용 패턴이 아니라 **기존 패턴과의 정합**이다.
- 근거 ②: 온프렘에서 NAS 마운트가 서비스 기동보다 늦게 붙을 수 있다. 기동 시 1회 해석하면
  그때 마운트가 없어 조상으로 폴백한 값이 **영구히 stale** 로 굳는다.
- 근거 ③: 탐색의 항목별 루프에는 들어가지 않는다 — `verifyFolder` 는 요청당 1회(+`resolveParent` 1회)라
  CWE-770 관점의 증폭이 없다.

**결정 2 — 두 판정기를 함께 고치고, `realOrNearest` 중복을 없앤다.**
- 근거: 같은 결함이다. 한쪽만 고치면 「탐색은 되는데 적재하면 403」이 되어 지금보다 진단이 어렵다.
  두 클래스가 같은 함수를 각자 갖고 있는 현 상태가 이미 「한쪽만 바뀐다」의 조건이다.

### ★라운드 1 이 드러낸 것 — 예상 밖의 발견 둘

**① AC-1080 은 「대조 후 변경 없음」이 아니었다.** 거부 5축이 **한 건도 없었고**, 같은 UC 의
AC-1079(happy)·AC-1081(edge) 어디에도 없었다. 즉 **「무엇이 안 넓어졌는지」가 수용기준 층에 통째로
비어 있었다.** 특히 *허용 범위 안의 이름이 실제로는 범위 밖을 가리키는 바로가기* 축 — 이번 변경에서
가장 뚫리기 쉬운 자리 — 이 없었다. 넓히는 변경을 하면서 이걸 안 채웠으면, 다음 사람이 이 기준을
근거로 방어를 함께 풀었을 것이다.

**② 위치 판정을 쓰는 창구가 설계 층에서 세어진 적이 없었다.**
ADR-065 자신이 *"허용 범위 목록이 두 벌이 되면 안 된다"* 를 결정 동인으로, *"읽는 축과 쓰는 축이 서로
다른 규칙을 가지면 탐색은 되는데 적재에서 거부된다"* 를 기각 근거로 못 박았는데, **그 「모든 자리」가
몇 곳인지 아무도 세지 않았다.**

⚠⚠ **이 CO 자신이 그 함정에 걸렸다 — 기록해 둔다.** 라운드 1 회수 시점에 여기에 *"창구는 넷"* 이라고
적었는데 **틀렸다.** 라운드 3 에서 한 에이전트가 API-215 를 찾아 올렸고, 코드로 확인하니 **일곱**이었다
(마킹 이관 축 둘이 더 있었다). CLAUDE.md 가 *"「N종」 같은 개수 표기를 쓰지 마라 — 경로가 하나 늘 때마다
그 숫자를 인용한 모든 층이 동시에 틀린다"* 로 못 박은 바로 그 패턴이다.
**다행히 `ADR-065` 본문에는 개수를 적지 않았다**(*"위치를 판정하는 모든 자리가 같은 것을 쓴다"*) —
그 서술이 옳았고, 개수를 적은 이 문서만 틀렸다. **앞으로도 개수를 적지 말 것.**

**① `AC-1033` 에서 두 검토자의 판정이 갈렸다.** 관찰은 같았다(*"예외 5종에 위치 거부 축 0건"*)는데
한쪽은 「무관」, 다른 쪽은 「넣어야 함」으로 결론이 반대였다. **넣는 쪽으로 확정**했고 근거는 같은
라운드의 `AC-1080` 선례다 — 그것도 「대조 후 판단」으로 시작했는데 축이 통째로 비어 있었다.

**② `TEST-007`·`TEST-008` 은 「지시가 스키마상 불가능」했다.** `test_scenario` 타입은 `brownfield`
블록 자체를 받지 않아 `decided_by` 를 넣을 자리가 없다(**지시 오류**). 두 에이전트가 원자 거부를 받고
그 op 만 빼고 재시도했으며, 근거는 `change_summary`·`notes` 에 문장으로 보존됐다.

**③ 「폴더 안 바로가기 건너뛰기」와 이번 축은 낱말이 같아 계속 섞일 뻔했다.** 전자는 폴더 *내부 항목*
규칙이고 이번 것은 *허용 루트 자체* 축이다. 전 건에 이 구분을 명시적으로 실어 보냈고, 각 에이전트가
미접촉 근거를 따로 제출했다. `DFEAT-056` v5 가 만든 갈라 쓰기 문장을 나머지가 재사용했다.

**④ 「0건」을 주장하지 않는 보고가 정착했다.** `CDIAG-036` 담당은 *"「잔재 0건」이 아니라 「연 9건에서
0건, 36건 미확인」"* 으로, `SD-038` 담당은 *"게시본을 1바이트 단위로 대조한 것은 아니다"* 로,
`SCREEN-032` 담당은 잔여 위험을 *"같은 바이트 길이의 한글 1자 치환"* 하나로 좁혀 적었다.

★ **문구 기준은 API-221 v18 이다** — 같은 결정을 네 층이 나눠 서술하므로 층마다 다른 낱말을 쓰면
다음 사람이 서로 다른 규칙으로 읽는다. 각 에이전트에 그 본문의 어휘를 재사용하도록 지시했다.

**미반영·보류 항목**:
- ★**세 번째 판정기에도 같은 패턴이 있다 — 이번 CO 범위 밖, 별건 조사 필요** (2026-09-07 실측).
  `common/storage/StorageSubtreePolicy.verifyDeidentifiedFile` 이 **똑같은 lexical-first 구조**다:
  ```
  193:  if (!resolved.startsWith(base))     ← base 원문(표기)과 비교
  206:  realBase = base.toRealPath();       ← 여기서는 base 를 실경로로 편다
  ```
  **두 번째 검사는 base 를 펴는데 첫 번째는 안 편다** — 이 CO 가 고치는 것과 같은 패턴이다.
  - **범위에 넣지 않은 근거**: `ImportSourcePolicy` javadoc 이 이 둘을 명시적으로 **다른 판정기**로
    규정한다(*"비식별 전용 서브트리에 있는 파일 한 개를 판정"*). `base` 가 허용 루트 **목록**이 아니라
    **호출자가 주는 값**이라 축이 다르고, 범위를 계속 넓히면 이 CO 가 닫히지 않는다.
  - ⚠ **그러나 잠재 결함은 실재한다** — 비식별 산출물 경로(`LS_DEIDENT_PROC_LOG.DE_IDNTF_FILE_PATH_NM`)는

    걸린다. 이 CO 와 달리 **아직 현장에서 관측되지 않았을 뿐**이다.
  - 설계 층: `CDIAG-043`(`StorageSubtreePolicy.verifyDeidentifiedFile` 오퍼레이션 설명)이 같은 계열
    문형을 갖고 있다. 한 에이전트가 후보로 올렸으나 **같은 판정기인지 코드 실측이 선행돼야 한다**며
