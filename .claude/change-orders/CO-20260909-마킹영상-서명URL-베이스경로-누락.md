# CO-20260909 — 마킹 영상 서명 URL 이 배포 베이스 경로를 잃는다

| | |
|---|---|
| 생성일 | 2026-09-09 |
| 대상 도메인 | DOMAIN-011(마킹) · DOMAIN-013(포털, 확인 대상) · 프론트 |
| 발견 경위 | CBD 단위시험 증적 재촬영 중 246 dev 실측 |
| 심각도 | **높음** — 온프렘 배포 형상에서 마킹 화면 영상이 재생되지 않는다 |

## §1 배경

CBD 단위시험 증적(`KLID-AT-UT-019-01` 자동/수동 이벤트 마킹 생성)을 다시 찍으려고
246 dev 에서 마킹 화면을 열었더니 영상이 **「영상을 불러오는 중…」** 에서 멈췄다.

이 결함은 **로컬(`localhost:13000`)에서는 드러나지 않는다.** 로컬은 앱이 루트(`/`)에
서비스돼 `/api/v1/...` 이 그대로 맞기 때문이다. **베이스 경로가 있는 배포에서만** 나타나며,
관제 채널은 온프렘·246 둘 다 컨텍스트가 `/label-studio` 다
(`deploy/onprem/docs/03-install.md` · `deploy/dev-server-246/README.md`).

즉 **개발 환경에서는 영원히 안 보이고 실제 배포에서만 깨지는** 부류다.

## §2 변경 요지

영상 스트림 서명 URL 이 **배포 베이스 경로를 포함하도록** 고친다.

```
실제(결함): http://192.168.102.246:8088/api/v1/videos/26/stream?exp=…&u=2001&sig=…   → 404
기대:       http://192.168.102.246:8088/label-studio/api/v1/videos/26/stream?exp=…&u=2001&sig=…
```

apache 에서 `/api/v1/**` 는 **관제 시스템의 경로 공간**이라 저작도구 영상이 없다.
저작도구 API 는 `/label-studio/api/**` 로만 프록시된다.

## §3 도메인별 변경 상세

### 공통 — 원인

| 자리 | 내용 |
|---|---|
| `backend/src/main/java/kr/co/cudo/authoring/video/service/VideoStreamService.java:208` | `String url = "/api/v1/videos/" + rawSn + "/stream?exp=" + …` — **하드코딩 절대경로** |
| `frontend/src/pages/MarkingPage.tsx:348` | `const videoSrc = streamUrl?.url ?? '';` — 그 값을 `<video src>` 에 **그대로** 사용 |

다른 API 호출은 axios `baseURL`(`VITE_API_BASE_URL=/label-studio/api/v1`)을 타서 정상이다.
`<video>` 는 **인증 헤더를 실을 수 없어** 서명 URL 을 쓰는 유일한 경로이고, 그래서 이 문제를
혼자 겪는다(서명 URL 이 존재하는 이유 자체가 그 제약이다 — `StreamUrlSigner` 머리말).

### 수정 방향 — FE 권장 (확정은 설계 판단)

**FE 에서 배포 접두를 붙이는 쪽**을 제안한다.

- 응답 계약(`StreamUrlResponse.url` 이 `/api/v1/…` 절대경로)이 **불변** → 외부 FE 팀 소비·기존
  시험·포털 창구에 영향이 없다.
- 배포 베이스를 아는 층이 **FE** 다(BE 는 자기가 어느 컨텍스트에 붙는지 모른다).

구현 골자:
```
axios baseURL 에서 끝의 '/api/v1' 을 떼어 배포 접두를 얻는다
  '/api/v1'                     → ''            (로컬)
  '/label-studio/api/v1'        → '/label-studio'
  'https://host/api/v1'         → 'https://host'
그 접두를 BE 가 준 상대 URL 앞에 붙인다.
baseURL 이 그 꼴이 아니면 원래 값을 그대로 쓴다(fail-safe — 현재 동작 유지).
```

⚠ **BE 에서 고치는 안**(상대경로 반환)은 계약 변경이라 포털·시험·외부 소비까지 번진다.
크기를 비교해 판단할 것.

### 함께 볼 것 — 같은 형태가 더 있는가

- `frontend/src/features/portal/uploads/markingApi.ts` — `/portal/uploads/{uldSn}/stream-url`.
  같은 구조로 보인다. **같은 결함인지 확인하고 함께 고친다.**
- 서명 URL·서버 반환 경로를 `<video>`·`<img>` 등에 **직접** 넣는 다른 자리가 있는지 전수로 본다.

### 재시도 폭주 (별건 분리 가능)

404 가 나면 스트림 URL 을 재발급받아 재시도하는 루프가 **상한 없이** 돈다.
실측: **7초 동안 150회 이상**(매 요청 새 서명 발급).
경로를 고쳐도 다른 이유로 404 가 나면 같은 폭주가 재현되므로, 상한·백오프가 필요한지 판단한다.

## §4 영향·리스크

- **영향**: 온프렘 관제 채널 + 246 dev 의 마킹 화면 영상 재생. 포털 업로드 마킹도 확인 대상.
- **비영향**: 로컬 개발 환경(증상 없음) · 라벨링 화면 프레임 이미지(axios 경로라 정상).
- **리스크**: FE 수정이면 낮다(계약 불변). BE 수정이면 계약 변경이라 파급이 크다.

## §5 검증

1. **회귀 가드 — 베이스 경로가 있는 조건을 반드시 재현한다.**
   로컬 조건만으로는 지금도 통과하므로 그 시험은 이 결함을 **영원히 못 잡는다.**
   - `baseURL='/label-studio/api/v1'` → `<video src>` 가 `/label-studio/api/v1/videos/…/stream` 인지 단정
   - `baseURL='/api/v1'`(로컬) → 기존 동작 유지 단정
   - 두 조건을 **함께** 두어 한쪽만 맞는 수정이 통과하지 않게 한다
2. **246 실동작** — 재배포 후 `/marking/26` 에서 `video.readyState > 0` 그리고 `videoWidth > 0`.
   배포 절차 정본은 `deploy/dev-server-246/README.md`(JBoss WAR + apache 정적 —
   `:13000`/`:18081` docker compose 스택이 **아니다**).

## §6-2 ★두 번째 결함 — 스트림 nonce 쿠키 Path (2026-09-09 실측)

**FE 수정만으로는 246에서 재생되지 않는다.** 접두를 붙이면 404 가 **401** 로 바뀔 뿐이다.

원인: `common/security/StreamNonceCookie.buildCookie` 가 쿠키 Path 를
`request.getContextPath() + "/v1/videos"` 로 만든다. 즉 **앱이 아는 내부 경로**를 쓰는데,
프록시가 접두를 재작성하면 **브라우저가 보는 경로**와 갈린다. `ProxyPassReverse` 는
Location 계열만 고치고 `Set-Cookie` 의 Path 는 고치지 않는다.

### ★향에 따라 갈린다 — 온프렘은 무관하다

| 향 | 앱 컨텍스트 | 쿠키 Path | 브라우저 경로 | 판정 | 근거 |
|---|---|---|---|---|---|
| **passthrough**(온프렘 반입본) | `/label-studio/api` | `/label-studio/api/v1/videos` | `/label-studio/api/v1/videos/…` | 일치 **(추론)** | 레포 산출물 |
| **strip**(246 dev) | `/label-studio` | `/label-studio/v1/videos` | `/label-studio/api/v1/videos/…` | 불일치 **(실측)** | 246 실호출 |

★★**검증된 것과 추론을 가른다 — 이 구분을 지우지 말 것.**

- **실측한 것**: 246 에서 세 조건을 실제로 호출해 404 / 401 / 206 을 관측했다.
- **추론한 것**: 온프렘 쪽 「일치」는 **레포의 반입 WAR 이 선언한 컨텍스트에서 계산한 값**이다.
  `deploy/onprem/artifacts/backend/api.war` 의 `WEB-INF/jboss-web.xml` →
  `<context-root>/label-studio/api</context-root>` · `BUILD-INFO.txt` → `web_context_flavor=passthrough`.
- ⚠ **온프렘에서 관측한 적이 없다** — `Set-Cookie` 도, 영상 재생도. 현장에서 확인한 것은
  **API 도달뿐**이고 그것은 두 향에서 모두 참이라 향을 가르지 못한다.
- ⚠ **현장에 그 WAR 이 올라가 있다는 것도 확인되지 않았다.** 향은 빌드 인자로 바뀌고
  현장 httpd conf 원본이 우리 저장소에 없다.
- ⚠⚠ **온프렘 마킹 영상 재생은 지금 되고 있을 수 없다** — URL 결함(404)이 두 향 공통이고 FE 수정이
  아직 반영되지 않았다. 즉 온프렘의 올바른 상태 표기는 「정상」이 아니라 **「미확인」**이다.

⇒ 쿠키 축은 **246 에서 실증된 dev 서버 프록시 설정 문제**다. §1 의 *"온프렘도 같은 조건"* 은
**URL 축(404)에만** 확실히 해당한다. 쿠키 축이 온프렘에 없다는 것은 **아직 추론이며 현장 확인이 필요하다.**

### 온프렘 확인 절차 (FE 반영 후 현장에서 1회)

1. `https://<사이트>/label-studio/api/v1/videos/{rawSn}/stream-url` 응답의 **`Set-Cookie` Path** 관측
   → `/label-studio/api/v1/videos` 면 일치, `/label-studio/v1/videos` 면 strip 향이라 이 결함이 있다.
2. 마킹 화면에서 **실제 재생** 확인(`video.readyState > 0` · `videoWidth > 0`).
   1번이 일치인데 2번이 안 되면 원인이 다른 데 있다.
⚠ **API 200 은 판정 근거가 아니다** — 두 향에서 모두 참이다.

### 실측 (246, 영상 26)

| 조건 | 결과 |
|---|---|
| 접두 없음 (수정 전 FE) | **404** |
| 접두 결합 + 쿠키 없음 (FE 수정만) | **401** |
| 접두 결합 + 쿠키 있음 | **206**, 1024바이트 |

### ★246 조치 — 임시조치를 걷어내고 **passthrough 향으로 정렬**했다 (제품 코드 변경 아님)

**사용자 판단**: *"246도 passthrough 로 맞추면 되지 않아?"* — 프록시로 쿠키 Path 를 덧대는 것보다
**향을 현장과 같게 맞추는 쪽**이 맞다. 그러면 불일치가 **원인 자체로 사라지고**, 무엇보다
**증적을 실제 납품 형상에서 찍게 된다**(구 상태는 고객이 쓰지 않는 형상이었다).

**두 가지를 함께 움직였다** — 한쪽만 바꾸면 아무 신호 없이 API 만 전건 404 다.

| # | 대상 | 변경 |
|---|---|---|
| ① | 배포 WAR 의 `WEB-INF/jboss-web.xml` | `<context-root>` `/label-studio` → **`/label-studio/api`** |
| ② | apache `klid.conf`(vhost `RewriteRule`·`ProxyPassReverse` + 전역 `ProxyPass` 쌍) | 전달 대상 `…/label-studio/` → **`…/label-studio/api/`**(벗기지 않음) |
| ③ | 임시조치 `ProxyPassReverseCookiePath` | **제거** — 불필요해졌다 |

FE 는 그대로다 — `VITE_API_BASE_URL` 은 **두 향에서 같다**(`/label-studio/api/v1`).

⚠ **WAR 을 다시 빌드하지 않고 배포본의 `jboss-web.xml` 만 교체**했다(항목 2,092개 재포장).
코드가 바뀌지 않아야 지금 잡은 결함과 섞이지 않기 때문이다.
