## §1 배경

PR #208 은 「새로고침하면 권한 요청 안내로 튕긴다」를 고쳤다. 인가의 진실원은 서버이고 그 값을
메모리에만 두었던 것이 원인이라, 확보 절차(`features/auth/sessionBootstrap`)를 한 자리로 모으고
앱 부팅과 진입 화면이 함께 부르게 했다. 조회를 한 번만 하도록 **모듈 스코프 캐시**를 두었다.

리뷰에서 **그 캐시가 세션 교체를 건너 살아남는다**는 것이 드러났다. 새로고침(문서 재적재)에서는
모듈이 새로 뜨므로 캐시가 비지만, **같은 화면 수명 안에서 세션이 갈리는 경로**가 있다. 그 경로를
지나면 캐시가 히트하면서 **스토어에는 아무것도 재적용되지 않아**, 고쳤다는 바로 그 증상이
다시 나타난다.

### 근본 원인 — 캐시와 스토어가 서로를 모른다

`sessionBootstrap.ts` 의 `attempt` 는 **모듈 스코프이고 토큰 문자열로만 키를 잡는다.** 프로덕션에
이것을 무효화하는 경로가 **하나도 없다**(`resetServerRoleResolution` 의 사용처는 시험 3파일과
`src/test/setup.ts` 뿐 — 실측). 반면 스토어 쪽은 세션이 갈릴 때 상태를 되돌린다.

- `useAuthStore.clear()` 는 `token` · `claims` · `serverRoleStatus` 를 비운다. **`attempt` 는 모른다.**
- `setToken()` 은 `claims` 를 **토큰 디코드값으로 재구성**한다. 확보 절차가 주입해 둔 역할이 지워진다.
- `ensureServerRole()` 은 캐시가 히트하면 **`setServerRole` 도 `setServerRoleStatus` 도 부르지 않고**
  이전 promise 만 돌려준다. 즉 「캐시된 결과」가 「그 결과가 앉아 있어야 할 스토어」에 닿지 않는다.

### 재현 경로 (새로고침 없이, 한 페이지 수명 안 · 관제 채널)

1. 진입 → `/me` 200(role=ADMIN) → 역할 주입, `serverRoleStatus='ready'`, `attempt={T, ADMIN}`
2. 아무 API 가 401 → `lib/api/client.ts` 응답 인터셉터가 `clear()` → `serverRoleStatus='idle'`.
   `clear()` 가 지우는 것은 `forgetPersistedToken()` 이 다루는 **세션 저장소 키 하나뿐**이고,
   관제 인계가 읽는 **`localStorage['klid-jwt-token']` 의 T 는 그대로 남는다.**
3. `redirectToUpstreamLogin()` 이 **문서를 떠나지 못한다.** `redirectToUpstream` 은 그 채널의 로그인
   주소가 설정에 없으면 `false` 를 돌려주고 `location.assign` 을 부르지 않는데, **호출부가 그
   반환값을 무시한다.** 246·온프렘이 그 형상이다. → RoleGuard 가 `/ingress` 로 보낸다.
4. 진입 화면이 `setToken(T)` → **`claims.role = null`**(관제 토큰의 역할값은 우리 역할 집합과 겹치지
   않아 디코드에서 강등된다 — 이것이 원래 결함의 출발점이었다)
5. `ensureServerRole()` → `attempt.token === T` **히트** → 스토어 재적용 없음, `serverRoleStatus` 는
   `'idle'` 그대로
6. `RoleGuard` 는 `'pending'` 과 `'failed' && !claims.role` 만 분기하고 **`'idle'` 분기가 없어**
   역할 미부여 판정까지 떨어진다 → **`/role-claim` 으로 튕긴다.** = 이 PR 이 고쳤다는 그 증상

### 같은 뿌리의 두 번째 결과 — `'idle'` 이 두 뜻을 겸한다

`'idle'` 이 「세션이 없다」와 「세션은 있는데 확보가 누락됐다」를 **함께** 뜻한다. 후자는 판정을
멈춰야 하는 상태인데 어느 분기에도 걸리지 않아 **조용히 통과**한다. 토큰에 우리 역할이 실려 있는
세션에서는 서버 역할을 한 번도 확인하지 않은 채 화면이 열린다 — fail-closed 가 아니다.

### 시험이 못 잡은 이유

`src/test/setup.ts` 가 매 시험 앞에서, 그리고 각 케이스가 다시 한 번 `resetServerRoleResolution()`
으로 캐시를 비우고 시작한다. **캐시가 세션 교체를 건너 살아남는 축을 지나는 케이스가 0건**이다.
가드의 이름이 무엇이든, 그 축을 지나지 않으면 이 결함은 통과한다.

## §2 변경 요지

1. **확보 캐시가 세션 교체를 건너 살아남지 않게 한다.** 세션이 갈리면 캐시도 함께 갈리거나,
   캐시가 히트해도 결과가 스토어에 **멱등 재적용**되어야 한다.
2. **`'idle'` 이 두 뜻을 겸하지 않게 상태 축을 가른다.** 「세션 없음」과 「세션 있는데 미확보」는
   판정이 정반대다 — 전자는 통과, 후자는 보류.
3. **응답을 스토어에 쓰기 전에 그 응답이 지금 세션의 것인지 확인한다.** 늦게 도착한 옛 조회가
   새 세션에 역할을 주입하고 대기 게이트를 조기에 푸는 것을 막는다.
4. **확인 실패에 앱 안에서의 재시도 수단을 준다.** 화면이 "잠시 후 다시 시도해주세요"라고 적으면서
   할 수 있는 시도를 주지 않는 상태를 해소한다.

## §3 도메인별 변경 상세

### 프론트 (SCREEN-001 · SCREEN-002 · SCREEN-003) — `klid-web-implementer`

- **대상 화면·컴포넌트**
  - `frontend/src/features/auth/sessionBootstrap.ts` — `attempt` · `ensureServerRole` · `resolveServerRole` · `restoreSession`
  - `frontend/src/stores/useAuthStore.ts` — `serverRoleStatus` 값역 · `clear` · `setToken` / `setTokenAndClaims`
  - `frontend/src/router/guards.tsx` — `RoleGuard` 의 확보 상태 분기 · `ServerRoleUnknownNotice`
  - 시험: `features/auth/__tests__/sessionRefreshRoleRestore.test.tsx` · `__tests__/AppSessionBootstrap.test.tsx` ·
    `router/__tests__/` 의 가드 시험 · `features/preset/__tests__/PresetEditModal.test.tsx`

- **변경**

  **(1) [HIGH] 캐시가 세션 교체를 건너지 않게 한다**
  구현 방식은 아래 둘 중 하나 또는 조합이며 **판단은 구현 쪽에 맡긴다.**
  - ① 세션이 갈리는 지점(`clear` · `setToken` / `setTokenAndClaims`)에서 `attempt` 를 무효화한다.
    스토어가 부트스트랩 모듈을 직접 import 하면 순환이 생기므로, **구독 또는 콜백 등록**으로
    방향을 뒤집을 것(스토어가 알리고 부트스트랩이 듣는다).
  - ② 캐시가 히트해도 결과를 스토어에 **멱등 재적용**한다. 이때 재적용이 **지금 세션의 토큰과
    맞을 때만** 일어나야 한다(아래 (3)과 같은 조건).

  ⚠ 어느 쪽을 고르든 **①과 ②는 서로를 대체하지 않는다** — ①만 하면 무효화 지점을 하나라도
  빠뜨릴 때 다시 열리고, ②만 하면 「같은 토큰인데 서버 역할이 그 사이 회수된」 경우를 못 본다.
  둘 중 하나만 한다면 **그 선택의 한계를 코드 주석과 최종 보고에 명시**할 것.

  **(2) [HIGH] `'idle'` 이 겸하는 두 뜻을 가른다**
  「세션 없음(물을 것이 없다 — 통과)」과 「세션은 있는데 아직 확보하지 않았다(판정 보류)」를
  구분한다. 값을 하나 더 두든 파생 판정자를 두든 무방하나, **`RoleGuard` 가 후자에서 역할 판정에
  도달하지 못해야 한다.**
  ⚠ **초기값을 `'pending'` 으로 바꾸지 말 것.** 스토어에 상태를 직접 심는 화면 시험 약 25개
  파일이 영구 스피너에 걸린다 — 그 근거가 `useAuthStore.ts` 의 `serverRoleStatus` javadoc 에
  이미 적혀 있고, 이번 변경이 그것을 뒤집는 것이 아니다.
  ⚠ **`isHydrated` 를 넓히지 말 것.** 같은 javadoc 이 금지한다(첫 화면이 조회만큼 늦어진다).

  **(3) [MEDIUM] 응답을 쓰기 전에 지금 세션의 것인지 확인한다**
  `resolveServerRole` 진입 시 토큰을 캡처하고, `setServerRole` / `setServerRoleStatus` 를 부르기 전에
  `useAuthStore.getState().token === capturedToken` 을 확인한다. 다르면 **쓰지 않는다.**
  성공 경로와 **실패(catch) 경로 양쪽**에 건다 — 실패만 빠뜨리면 `clear()` 직후 도착한 인플라이트
  응답이 세션 없는 상태에 `'failed'` 를 남겨, 다음 진입이 근거 없이 오류 안내로 떨어진다.

  **(4) [MEDIUM] 확인 실패에 앱 안에서의 재시도 수단을 준다**
  `/me` 가 일시 장애로 한 번 실패하면 그 토큰에 대해 **문서를 새로 불러올 때까지 영구히 `failed`**
  다. 화면 문구는 "잠시 후 다시 시도해주세요"인데 사용자가 할 수 있는 시도가 없다.
  `ServerRoleUnknownNotice` 에 **재시도 조작**을 두고, 그것이 확보를 다시 태우게 한다(실패 결과를
  캐시에서 떨어뜨리거나 재시도가 캐시를 우회하도록). 화면에 조작이 생기므로 **SCREEN 사양 선반영
  대상**이다.
  ⚠ 재시도가 **자동 반복이 되지 않게** 할 것 — 사람이 누를 때만 다시 태운다. 자동 재시도는
  장애 구간에 조회 폭주를 만든다.

  **(5) [LOW] 공허한 단언 정리**
  `PresetEditModal.test.tsx` 신규 describe 의 `warmUp` 두 번째 `waitFor`
  (`mock.history.get.length >= 2`)는 **첫 번째가 통과한 시점에 이미 참**이라, 주석이 말하는
  「응답 반영(쿼리 성공 → 리렌더)까지 흐르게 둔다」를 하지 않는다. 실제로 그 일을 하는 단언으로
  바꾸거나, 하지 않는다면 주석을 사실에 맞춘다.

- **불변(건드리면 안 되는 것)**
  - **공유 `Select` 부품 무변경** — 소비처 22곳 전수 조사가 선행돼야 한다(선행 CO 의 판단 유지).
  - **브라우저 저장소에 새로 쓰지 않는다.** 포털 채널은 access token 을 메모리에만 둔다
    (`persistToken` 의 포털 가드). 서버 역할도 저장소에 눕히지 않는다.
  - `ChannelGuard` · `AuthenticatedGuard` 에 확보 대기를 붙이지 않는다 — 전자는 채널만 보고
    후자는 역할 미부여 사용자를 **일부러 통과시키는** 자리다(`RoleGuard` javadoc).
  - **확보 조회를 가드로 끌어올리지 않는다** — 역할 보유자의 모든 라우트 전환이 그 조회를
    기다리게 된다. 조회는 부팅·진입에서 끝내고 가드는 결과만 읽는다.
  - 「확인하지 못함」과 「역할 없음」을 다시 뭉치지 않는다 — 뭉치면 서버 장애가
    *"아직 관리자가 없습니다"* 로 위장된다.
  - 오류 문구는 진입 화면과 **같은 상수**를 계속 공유한다.

- **주의**
  - 스토어 → 부트스트랩 방향 의존을 만들지 말 것(순환). 필요하면 부트스트랩이 스토어를 **구독**한다.
  - `redirectToUpstream` 의 반환값을 호출부가 무시하는 것은 이 결함의 **전제 조건**이지만
    이번 범위가 아니다(§4 참조). 그것에 기대어 「어차피 이동하니 괜찮다」고 판단하지 말 것 —
    이동하지 않는 배포 형상이 실재한다.

- **수용기준**
  - `AC-1016`(재확보) · `AC-1017`(재확보 실패 — 확인 못 함 ≠ 역할 없음) 확장분을 따른다.
  - **① 같은 토큰으로 `clear()` → `setToken()` 재수립을 지나도 역할 보유자가 화면에 도달한다.**
    이 축을 지나는 시험이 반드시 있어야 한다 — 없어서 결함이 통과했다.
  - ② 세션은 있는데 확보 전인 상태에서 **역할 판정에 도달하지 않는다.**
  - ③ 옛 토큰의 응답이 늦게 도착해도 새 세션의 역할·확보 상태를 **바꾸지 않는다.**
  - ④ 확인 실패 화면에서 재시도하면 확보가 **다시 수행된다**(자동 반복 아님).

## §4 영향·리스크

- **하위호환**: 서버 계약 변경 없음. `GET /v1/me` 호출 횟수는 재시도 조작을 사람이 누를 때만 는다.
- **되돌리기**: 프론트 단독 변경이라 커밋 되돌리기로 원복된다. 스키마·마이그레이션 없음.
- **리스크**
  - 상태 축을 가르는 변경이 **가드 분기 전체**에 닿는다. 초기값이나 `isHydrated` 를 잘못 건드리면
    화면 시험 다수가 영구 스피너에 걸린다(그 함정이 이미 실측돼 javadoc 에 적혀 있다).
  - 캐시 무효화를 넣으면 「조회 1회」 성질이 약해질 수 있다 — 세션이 갈릴 때만 다시 묻는지,
    라우트 전환마다 묻는지 **호출 횟수로 확인**할 것.
- **범위 밖 (이번에 하지 않는다 — 근거 포함)**
  - `redirectToUpstreamLogin()` 이 `redirectToUpstream` 의 `false` 반환을 무시하는 것.
    로그인 주소 미설정 시 **떠나지 못하는데 떠난 것처럼 진행**한다. 이 CO 의 재현 경로가 그 위에
    서 있으나, 고치는 자리가 `lib/api/client.ts`(공유기반)이고 「주소가 없을 때 무엇을 보여줄
    것인가」가 별도 화면 결정이라 **별건**이다. ⚠ 이 CO 의 수정은 그 축이 남아 있어도 성립해야
    한다 — 캐시·상태 축을 고치는 것이지 이동을 고치는 것이 아니다.
  - 포털 실 Host 형상의 「새로고침 복원」 시험. 현재 `★포털_채널도_…` 케이스는 스토어에 토큰을
    먼저 심고 부팅해 **실 Host 순서를 재현하지 않는다**(실 포털에서 `hydrate()` 는 저장소를 읽지
    않아 부팅 시점 스토어가 비어 있고, 토큰이 들어가는 유일한 지점은 진입 화면이다). Host 스텁
    하네스가 필요해 별건이며, **「채널 불문」 주장보다 커버리지가 좁다**는 사실을 PR 본문에 남긴다.
  - `getMe()` 응답 역할값에 런타임 검증(`isKnownRole`)이 없는 것. PR 이전에도 같아 회귀가 아니고,
    알 수 없는 값은 `roleSatisfiesAny` 에서 걸려 `/forbidden` 이 되므로 권한 상승이 아니다.

- **정적 렌더 미러 3건 stale** — `SCREEN-001`·`SCREEN-002`·`SCREEN-003`. ⚠ 셋 다 **이번 편집
  이전부터 이미 어긋나 있었고** 이번에 차이가 더 벌어졌다. 별도 렌더 라운드 대상.

  하지 않았다.
- **검증 메타** — `AC-1016`·`AC-1017`·`AC-1098` 의 검증 상태·증빙·마지막 실행이 **이번 단언 이전
  시점 값**이다. 시험이 붙는 시점에 갱신해야 한다.

### 이 라운드에서 실제로 있었던 사고 (같은 실수 방지)
★**병렬 담당들이 공용 임시 디렉터리의 같은 이름 파일을 덮어써, `SCREEN-001` v20 에 다른 화면의

유실은 없다. 이후 담당들에게 **전용 하위 디렉터리 + 파일명에 ITEM ID + 기준선은 쓰기 직전 같은
스크립트에서 재조회**를 지시해 재발하지 않았다. 메인이 사후에 `API-006`·`UC-041`·`SCREEN-002`·
`SCREEN-003` 본문을 **직접 열어 오염 없음을 확인**했다.

해소임을 대조로 확인했다. **표식이 안 보이는 것을 해소로 읽으면 안 된다.**
