## §1 배경

포털 데이터셋 소재가 준비되면 백그라운드 작업이 해제본의 영상·프레임·원본 라벨을 원장에 등록하고, 그 결과를 해제본 옆 표식 파일(`registration.json`)에 `IN_PROGRESS`·`DONE`·`FAILED` 로 남긴다(`ADR-068`). 데이터셋 영상 목록 창구(`API-253`)는 그 표식을 읽어 등록 상태를 답하고, **표식이 없거나 진행 중 표식이 10분 넘게 멈췄을 때만** 등록을 다시 시작시킨다. **`FAILED` 표식은 그대로 답하고 끝난다** — 다시 시작하는 경로가 자동으로도 수동으로도 없다. `ADR-068` 은 이것을 알려진 공백으로 적어 두었다.

**2026-09-16 개발망 실사고.** 데이터셋 5149·5150 이 16:49·16:51 에 옛 코드에서 `VIDEO_FILENAME_MISSING` 으로 실패해 `FAILED` 표식이 남았다. 같은 날 파서를 고쳐(실물 배포본 스키마 대응, `59be0f8db`) WAS 를 새로 올렸는데도 두 데이터셋은 계속 「영상을 등록하지 못했습니다」로 보였다. 화면의 「다시 확인」은 재조회일 뿐이고, 소재를 다시 가져오는 창구(`API-248`)도 이미 준비된 해제본은 덮어쓰지 않아 표식을 건드리지 못한다. 결국 서버(`/nas-storage/data/author/portal/materials/{id}/current/registration.json`)에서 표식 파일을 **수동으로 지워야** 풀렸다.

파서는 배포본 스키마가 갈릴 때마다 고쳐질 수밖에 없다(`ADR-068` 이 그렇게 정했다). 그때마다 이미 실패한 데이터셋을 서버에서 손으로 풀어야 한다면 운영이 되지 않는다. 또 화면이 실패 **사유**를 보이지 않아 사용자는 무엇이 잘못됐는지, 다시 눌러 볼 가치가 있는지 알 수 없다.

## §2 변경 요지

1. **재착수 창구 신설** — `POST /v1/portal/datasets/{datasetId}/registration`(포털 회원). 표식이 `FAILED` 이면 등록을 다시 착수하고 `IN_PROGRESS` 로 답한다. 진행 중이면 새로 시작하지 않고 현재 상태를, `DONE` 이면 다시 하지 않고 `DONE` 을 답한다(멱등). 소재 미준비는 409, 대기열 포화는 503(`API-248` 과 같은 규약).
2. **목록 응답에 실패 사유 추가** — `API-253` 200 응답 `registrationFailureReason`(nullable · `FAILED` 일 때만 값). 화면이 사유를 문구로 바꿔 보이고, 같은 답이 돌아올 사유(구조 불일치)는 재착수를 권하지 않는다.
3. **화면** — 「데이터셋 영상」 구역의 등록 실패 판에 사유 문구 + 「다시 등록」 버튼(재착수 창구 호출 → 목록 재조회 → 등록 중 폴링 재개). 「다시 확인」(재조회)은 조회 실패·모르는 상태 판에 그대로 남는다.
4. **자동 재시작은 두지 않는다** — 구조 불일치는 재착수해도 같은 사유로 다시 실패하며, 자동으로 되풀이하면 확정 실패에서 같은 일이 끝없이 돈다(`SCREEN-046` 이 조달 착수에 대해 이미 같은 이유로 자동 재시도를 배제했다). 파서가 고쳐진 뒤 사람이 한 번 누르는 것으로 충분하다.

## §3 도메인별 변경 상세

> 이 절이 각 구현 에이전트에 `change_detail` 로 그대로 전달된다.

### DOMAIN-013 (포털) — `klid-d013-implementer`

- **대상 파일·심볼** (`backend/src/main/java/kr/co/cudo/authoring/portal/`):
  - `controller/PortalDatasetVideoController` — 창구 추가 `POST /{datasetId}/registration`(클래스 `@RequestMapping("/v1/portal/datasets")` 그대로). `@PreAuthorize("hasRole('PORTAL_USER')")`, 토큰 주체 없으면 401(기존 `list` 와 같은 검사).
  - `service/PortalDatasetVideoService` — `resolveRegistrationState(datasetId)` 를 **재사용**해 현재 상태를 정한 뒤, `FAILED` 일 때만 `registrationService.tryClaim` → `registrationRunner.runAsync` 로 재착수하는 메서드 신설(예: `restartRegistration(long datasetId)`). 클레임 실패(다른 경로가 진행 중)면 `IN_PROGRESS` 로 답한다. `TaskRejectedException` 이면 `release` 후 `ErrorCode.SERVICE_UNAVAILABLE`(메시지는 `PortalMaterialsProvisionService` 의 대기열 포화 문구와 같은 결로). 등록 토글(`registrationService.isEnabled()`)이 꺼져 있으면 409 `CONFLICT`(「등록이 꺼져 있어 다시 시작할 수 없습니다」 — 목록 창구가 토글 off 를 `FAILED` 로 답하는 것과 대칭). 소재 미준비는 `list` 와 같은 409 문구.
  - `dto/PortalDatasetVideoPageResponse` — 필드 **추가** `PortalDatasetRegistrationFailureReason registrationFailureReason`(nullable, `FAILED` 일 때만 non-null). 조달처는 `workspace.readRegistration(datasetId).failureReason()`. 기존 필드 이름·순서·타입 불변.
  - 재착수 응답 DTO 신설(예: `dto/PortalDatasetRegistrationResponse(registrationState, registrationFailureReason)`) — 두 필드 이름·enum 은 목록 응답과 **같은 것**을 쓴다.
  - `resolveRegistrationState` 의 상태 결정 로직은 **바꾸지 않는다** — 목록 조회는 여전히 `FAILED` 를 재시작하지 않는다.
- **변경 순서·표식**: 재착수가 클레임에 성공하면 `registerClaimed` 가 첫 줄에서 `IN_PROGRESS` 표식을 덮어쓴다(기존 동작) — 별도 표식 삭제 코드를 두지 않는다. 표식이 `FAILED` 인데 `inFlight` 에 있으면(이 노드가 이미 재착수 중) `IN_PROGRESS`.
- **불변**: 등록 본체(`registerClaimed`)·파서·멱등 키·`ADR-068` 의 원장 규약 무변경. `API-253` 의 기존 필드·409 규약·재기동 회복(표식 없음·오래된 진행 중) 무변경. `API-248` 조달 착수는 건드리지 않는다. 내부 채널 토큰은 403(기존 인가 축).
- **주의**: `inFlight` 는 노드 로컬이다 — 다른 노드가 재착수 중이어도 이 노드는 표식이 `IN_PROGRESS`(신선)로 바뀐 뒤에야 안다. 그 창에서 두 노드가 같은 데이터셋을 동시에 등록할 수 있으나 등록이 멱등이라 행이 늘지 않는다(`ADR-068` 이 이미 수용한 성질 — 새 잠금을 만들지 말 것). 응답에 내부 경로·표식 파일 이름을 싣지 않는다.
- **수용기준** (신설 AC 참조 — Phase 3.6 확정 ID 를 `design_refs` 로 받는다):
  - `FAILED` 표식 + 진행 중 없음 → `POST` 200 `{registrationState: IN_PROGRESS}` 이고 등록이 실제로 다시 돌아 파서가 읽을 수 있는 배포본이면 `DONE` + 영상 행 생성, 읽을 수 없는 배포본이면 같은 사유의 `FAILED` 로 끝난다(원장 행 0).
  - `DONE` 표식 → `POST` 200 `{registrationState: DONE}` 이고 등록이 다시 돌지 않는다(표식 `updatedAt` 불변).
  - 신선한 `IN_PROGRESS` 표식 또는 이 노드 진행 중 → 200 `IN_PROGRESS`, 새 작업 없음.
  - 소재 미준비 → 409. 토큰 없음 401 · 내부 채널 403 · 대기열 포화 503(선점 되돌림).
  - `GET …/videos` 가 `FAILED` 일 때 `registrationFailureReason` 을 싣고, 그 밖의 상태에서는 `null`.
  - 회귀: `PortalDatasetRegistrationIT`(구조 불일치 → FAILED → 재착수 → 같은 사유 FAILED · 파서 통과 구성으로 바꾼 뒤 재착수 → DONE) + 컨트롤러 인가 계약 시험. 기존 시험 전건 통과.

### 프론트 (SCREEN-046 데이터셋 영상 구역) — `klid-web-implementer`

- **대상 화면·컴포넌트**: `frontend/src/features/portal/materials/components/DatasetVideoSection.tsx` · `hooks/useDatasetVideos.ts` · `api.ts` · `types.ts` · (신설) 등록 실패 사유 표기 모듈(조달 사유 모듈 `failureReason.ts` 와 같은 모양 — 통신 모듈에 표기를 두지 않는다) · 관련 시험 `__tests__/DatasetVideoSection.test.tsx`.
- **소비 API 계약**: `API-253` 200 에 `registrationFailureReason: string | null` 추가(enum 값은 `PortalDatasetRegistrationFailureReason` — `CONTENT_MISSING`·`SYMLINK_REJECTED`·`NO_VIDEO`·`VIDEO_FILENAME_MISSING`·`AMBIGUOUS_VIDEO_KEY`·`INVALID_VIDEO_KEY`·`PAIR_MISMATCH`·`DOCUMENT_UNREADABLE`·`IMAGE_NOT_JPEG`·`INVALID_VALUE`·`DISABLED`·`IO_ERROR`). 신설 `POST /v1/portal/datasets/{datasetId}/registration` → 200 `{registrationState, registrationFailureReason}` / 409 / 503.
- **변경**:
  - 등록 실패 판(`dataset-videos-registration-failed`): 제목은 유지하고 설명을 **사유 문구**로 바꾼다(우리 표에 없는 값은 폴백 문구, 사유 코드를 그대로 찍지 않는다). 걸음은 「다시 등록」 — 재착수 창구를 부르고 성공하면 목록 쿼리를 무효화해 등록 중 폴링이 재개된다. 재착수 요청 자체가 거부되면(409·503·네트워크) 그 판 안에서 서버 안내 문장을 보이고 버튼은 다시 누를 수 있다. 같은 답이 돌아올 사유(구조 불일치 계열)는 버튼을 숨기지 않고 보조 위계로 낮추며 문구가 「같은 소재로는 같은 결과입니다」를 말한다(`SCREEN-046` 조달 실패의 「다시 시도」와 같은 규칙).
  - 조회 실패·모르는 상태 판의 「다시 시도」·「다시 확인」(재조회)은 그대로.
  - 요청 중에는 버튼을 비활성(연타 방지 — 서버 멱등이지만 요청을 겹치지 않는다).
- **불변**: 관제향 화면·공통 부품 무변경(포털 전용 계층만). 목록 행·페이저·진입 규칙 무변경. 등록 중 폴링 예산 규칙(`polling.ts`) 무변경.
- **수용기준**: FAILED 응답에서 사유 문구가 보이고 「다시 등록」이 재착수 창구를 부른 뒤 목록을 재조회한다(시험: 호출 순서·무효화). 모르는 사유 값이면 폴백 문구. 재착수 409/503 이면 안내 문장 노출 + 버튼 재활성. 포털 스위트·tsc·lint 통과.

## §4 영향·리스크

- **하위호환**: `API-253` 은 필드 추가만(기존 소비자 무영향). 신설 창구는 추가. 표식 파일 형식 무변경.
- **되돌리기**: 창구·필드 제거로 원복. 표식·원장 데이터에 남는 흔적 없음.
- **리스크**: 재착수를 누르는 것으로 실패한 등록이 반복 실행될 수 있으나 등록은 멱등이고 사람이 누르는 것이라 폭주하지 않는다(자동 재시도를 두지 않는 이유). 재착수 중 다른 노드와 겹칠 수 있으나 `ADR-068` 이 수용한 성질.
