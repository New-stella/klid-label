## 1. 사용자 확정 (구속) — 되돌리지 말 것

1. **저작도구와 포털은 서로의 DB 에 접근하지 않는다**(양방향). 데이터 교환은 API.
   ⇒ 듀얼 데이터소스(`PortalDataSourceConfig`·`@PortalRepo`) 기반 메타 단방향 복제 **폐기**.
   ⚠ **정책만 확정, 코드는 아직 철거 전.** 「이미 걷어냈다」로 읽지 말 것.
2. **채널별 별도 배포** — 한 서비스가 양쪽에 붙는 구조가 아니다. **두 배포본끼리도 직접 이어지지 않는다.**
3. **인프라 소유가 갈린다** — 관제향: DB·NAS 모두 관제지원 소유(공유 NAS) / 포털향: **DB 는 저작도구가
   직접 관리**(별도 서버) · **NAS 는 포털이 관리**하는 별도 NAS.
4. **포털향에 `ai-server` 미연결**(오토라벨·인터랙티브 분할 없음). AI 파이프라인은 관제향에만.
   ⚠ **외부 증강은 별개 축** — ai-server 가 아니라 외부 위탁이고 포털 업로드 영상 대상 제공은 확정(`ADR-013` v10).
5. **자산 전달 3단계 — 중계자는 관제**
   ① 관제향 검수 승인 → 관제로 완료 통지
   ② 관제가 자산을 포털로 전달(**압축 파일** · **우리 export 산출물 중 비식별 벌만**)
   ③ 포털이 **포털향 배포본**에 자산 수신을 API 로 알림
   ⚠ ③ 수신자를 「관제향」으로 적었다가 정정한 이력 있음. 관제향이면 ①의 주체로 되돌아가는 **순환**이라 성립 안 함.
6. **서버간 API** — ②일일 저작집계 **신설 확정**(KST 자정 경계) / ①완료 저작결과 조회는 **포털에 역질문**
   (본인 데이터라 회원 토큰으로 충분해 보임. MF 영역인지 포털 직접 렌더인지에 달림).

## 5.5 ★사용자 확정 (2026-08-31, 구속) — 포털 데이터셋 소재 전달

**저작도구는 포털 NAS 에서 파일을 직접 읽는다. 다만 그 경로는 포털이 API 로 알려 주는 값을 그대로 쓴다**
(포털 제시 안 A). 저작도구가 경로를 조합·추측하지 않는다 — 비식별 영상 경로에서 이미 확립된 규칙과 같은 축이다.

- **NAS 는 포털 NAS 가 맞다**(사용자 확인). 포털향 배포본이 이미 그 NAS 를 쓰므로 경계가 넓어지지 않는다.
- ★**압축은 별도 폴더에서 푼다**(사용자 지시). 같은 NAS 안이어도 **읽는 자리 ≠ 푸는 자리**로 가른다.
  근거 — ①포털 폴더는 포털 소유라 쓰면 「읽기만」 약속이 깨진다(읽기전용 마운트면 애초에 불가)
  ②원본 데이터셋 무영향 ③동시 편집 시 같은 자리에 풀면 서로를 덮는다 ④작업 후 정리 대상 판정 불가.
- ⚠ **격리는 zip slip 방어가 아니다** — 엔트리 이름에 상위 이동이 있으면 격리 폴더 밖으로 나간다.
  엔트리마다 해제 실경로가 목적지 하위인지 확인 + 절대경로·심링크 엔트리 거부 + 총량·엔트리 수 상한이 필요하다.
- ★★**이 저장소에 압축 「해제」는 처음이다** — `ZipOutputStream`(쓰기) 1곳뿐이고 `ZipInputStream`/`ZipFile` **0건**.
  zip slip 방어는 재사용할 물건이 없고 **새로 만들어야 한다**(숨은 공수). 경로 축은 `common/storage/StorageSubtreePolicy`
  (실경로 재검증 + `NOFOLLOW_LINKS`)를 재사용할 수 있으나 **엔트리 이름 검증 축은 없다.**
- **폴더 배치는 포털에 역질문**(사용자 지시) — NAS 소유자가 정하는 것이 맞다. Q1~Q7 로 아티팩트에 실었다.

## 8. 함정 (이 세션에서 실제로 걸린 것)

- **heredoc 인용 누락** — `<<PY` 로 열면 셸이 백틱을 실행해 토큰이 **빈 문자열로 들어간다.** 반드시 `<<'PY'`.
- **`| tail` 이 종료코드를 삼킨다** — `$?` 가 `tail` 것이 된다. 파이프 없이 재실행해 판정할 것.
- **로컬 키트는 미러라 stale** — 서버 원본으로 판정할 것. 정적 렌더는 **`source_hash` 오라클**
  (ITEM `sections` 의 sha256 재계산 대조)로 판정.
- **`frontend/node_modules` 가 비어 있다** — 첫 검증 전 `npm ci` 필요.
- **워크트리 정책** — 키트 SYNC 금지 · IMPREC 기록 금지 · 머지 방식 PR 고정.

### 10-10. ★반전 — 좌측 메뉴의 주인 (2026-09-01 사용자 지시)

> "워크스페이스 메뉴는 아마 우리 화면 뜰때는 안보일것 같은데? 헤더 빼고는 다 저작도구 화면일거야"

**§10-6 의 「LNB 는 Host 가 그린다」 전제를 뒤집는다.** Host 는 **머리 영역만** 그리고,
그 아래는 좌측 메뉴를 포함해 **전부 저작도구**가 렌더한다.

- 시안을 그렇게 고쳤다 — 좌측 메뉴는 우리 것이고 **우리 3항목만** 담는다
  (내 작업·내 업로드·증강). 모양은 포털 `LnbPanel` 규격을 그대로 따른다.
- **사용자 카드는 두지 않는다**(`MenuOnly` 변형) — 신원은 Host 머리 영역이 이미 보여 준다.
- **`NAV-002` 등재 협의가 불필요해진다**(§10-6 의 결합 비용 소멸). 목적지를 늘려도
  포털 배포가 필요 없다.

⚠ **포털 설계와는 어긋난다 — 확인 항목이다.** `SHELL-001` 은 `applies_to_screens` 에
`SCREEN-012` 를 포함하고 `lnb` 영역(워크스페이스·마이페이지, `source_nav_id NAV-002`)이
살아 있는 것으로 규정한다. 즉 **포털 문서상으로는 우리 화면에서도 LNB 가 보인다.**
어느 쪽이 맞는지 회신으로 확정해야 하며, 시안은 사용자 지시(=LNB 없음)를 따랐다.

### 10-11. ★★「내 학습데이터」(SCREEN-013)가 우리 「내 작업」과 정면 충돌한다

`SCREEN-013` v41 본문 실측:

> 두 종류의 데이터를 하나의 목록으로 관리: **(1) 저작도구에서 저작 완료된 학습데이터
> (저장 완료 시 자동 이동)**, (2) 학습데이터 검색에서 다운로드 진행한 데이터셋 …
> **PC 다운로드 버튼으로 결과물 다운로드. 보존기간 임박 시 다운로드 권유 안내 표시.**

섹션 본문:
> ① 저작 완료분 — **`tb_athrng_job`(authoring 스키마). 포털 WAR 이 직접 읽을 수 없어
> 저작도구 WAS API 경유로 얻는다(ADR-013). ※ 구체 경로는 EXTSYS-002 소관으로 미정.**

즉 포털은 **저작 저장물의 목록·다운로드·만료 안내를 자기 화면에서 제공**하도록 설계돼 있다.
그런데 우리는 2026-09-01 사용자 확정으로 **같은 것을 `SCREEN-028` 이 갖는다**고 정했다
(*"사용자가 저장한 리스트 자체는 우리가 보여주는거야"* · *"거기서 다운로드도 해야하고"*).

**양쪽이 같은 목록·같은 다운로드·같은 만료 안내를 각자 갖고 있다.**

- 가능한 경계: 우리=**진행 중**(이어쓰기) / 포털=**완료 결과물**(다운로드).
  포털 상수 `CONST-019`(IN_PROGRESS·COMPLETED·CANCELLED)가 그 경계를 지지한다.
- ⚠ 그러나 `SCREEN-013` 은 *"**저장** 완료 시 자동 이동"* 이라고 적어 **저장 시점**을 말한다.
  우리 「내 작업」은 저장 시점부터 목록에 올린다 — **그 문구대로면 겹친다.**
- ⚠ 우리 `SCREEN-028` 은 행마다 **내려받기**를 갖는다(사용자 확정). 다운로드도 겹친다.

⇒ **회신으로 경계를 확정해야 한다.** 우리가 만든 `API-225 GET /v1/portal/user-works` 가
포털이 「미정」으로 남긴 그 창구일 가능성이 높다 — 그렇다면 우리는 목록을 **보여주기도 하고
공급하기도** 하게 된다. 그 이중 역할이 의도인지 확인이 필요하다.

### 10-12. ★포털이 전제한 우리 테이블 `tb_athrng_job` 은 존재하지 않는다

- 우리 저장소 실측: `athrng` **0건**(backend/src·deploy 전체)
- 우리 포털 테이블은 `ls_portal_tus_uld` · `ls_portal_uld` · `ls_portal_uld_frme` ·
  `ls_portal_uld_lbl` · `ls_portal_user_label` **5종**

`CONST-019` 가 *"저작도구 작업 세션(`tb_athrng_job.stts`)의 상태값. authoring 스키마 소속"*
이라고 단정하고 `SCREEN-013` 이 그 테이블을 소스로 지목한다. **포털이 우리 스키마를
추정해 적어 둔 것**이며 실물과 다르다. 회신에 포함할 것.

### 10-13. 포털이 우리에게 기대하는 공급 두 가지 (미확인)

1. **`SCREEN-011` 대시보드 카드 ②** — *"저작도구 작업 현황 — 진행중·업로드 처리중·

   → **우리가 통지해야 한다.** 그 통지 경로가 우리 설계에 없다.
2. **`CONST-022` 저작 파이프라인 단계** = `FRAME_EXTRACTION` · `AUTO_LABELING` ·

   ⚠ **포털 채널은 오토라벨링·검수가 미제공**인데 값역에 들어 있다.
   ("포털 전용 저작도구 형상에서는 단계 단순화 가능"이라고 여지를 뒀으나 미확정)

### 10-15. ★확정 — 저작 저장물 소유 · 증강 자체 수행 (2026-09-01 사용자 확정, 구속)

> "저작 저장물 목록 다운로드는 우리 화면이야. 증강요청은 우리가 알아서 할거고
> 저작도구내에서 결과 확인 및 작업후 다운로드 할 수 있어야해"

**① 저작 저장물의 목록·이어쓰기·내려받기는 저작도구 화면이 소유한다.**
§10-11 의 「양쪽 충돌」은 **우리 쪽으로 확정**됐다. 포털 `SCREEN-013` 의 ①「저작 완료분」
소스는 포털측 재검토 대상이며, 그 요청을 아티팩트로 보냈다.
⚠ **화면 소유와 데이터 공급은 별개다** — 포털이 요약·연계 목적으로 목록을 받아 가는 것은
여전히 가능하고, 우리 `API-225` 를 그 창구로 계속 제공한다. **다만 「목록 공급」과
「파일 다운로드」는 다른 축**이며 다운로드는 우리 화면에서만 일어난다.

**② 증강은 저작도구가 자체 수행하고, 결과 확인·후속 작업·다운로드까지 우리 안에서 끝난다.**
- 증강 **요청** — 우리가 처리(대상·조건·외부 위탁 전부)
- 결과 **확인** — 우리 화면

### 10-20. 다음 라운드 착수 지점 — 포털 증강 API 신설

**목표**: `SCREEN-044`「포털 증강 화면」이 소비할 창구를 설계한다. 지금 `consumes_apis` 가

**필요한 창구(추정 — 확정 아님)**: 증강 요청 접수 · 요청 현황 목록 조회 · 결과 조회 ·

`SCREEN-044` 는 나머지 셋을 부른다 — 진입이 갈려 있으니 소비 화면을 섞지 말 것.

**설계 시 지켜야 할 제약 (전부 이번 라운드에서 확정된 것)**
1. **본인이 올린 영상 한정.** 데이터마트에서 불러온 영상은 대상이 아니다.

   대상이 검수 완료 영상)과 성질이 다르다.
3. **비동기 위탁.** 요청 즉시 결과가 나오지 않는다. 상태 값역은 **아직 미확정**이며
   `SCREEN-044` 도 「대기·완료·실패를 구분한다」까지만 적었다 — 코드값을 지어내지 마라.
4. **외부 채널 증강 요청 창구(Host 의 것)를 호출하지 않는다.** 우리가 자체 수행한다.
5. **파생물은 포털 자산 계보**(`LS_PORTAL_*` 축). 내부 채널 파생 모델(원본 영상 원장에

   그것을 선점하지 않게 할 것.
6. **인가는 본인 자산으로 좁힌다** — 타인 자산 대상 요청·조회는 거부.
7. 표준용어·표준도메인은 CSV 정본 grep 으로 판정(MCP 검색으로 「미등록」 판정 금지).

**★★쓰기가 이어받은 문장을 손상시킬 수 있다 — 추가분만 검사하면 못 잡는다 (구속 교훈)**

⇒ **필드 전문을 의도본과 맞대야만** 드러난다. `v32` 에서 다시 옮겨 적지 않고 **의도본에서 기계로 만든

목적지 셋(내 작업·내 업로드·증강)은 **본문 상단 이동 탭**으로 오간다(사용자 선택).

### ★★같은 축의 두 번째 반전 — 세 번째로 뒤집지 말 것

| 시점 | 좌측 메뉴 소유 |
|---|---|
| 최초 | **Host** — 상대 셸 정의가 그렇게 규정, 우리는 §10-10 에서 「회신 대기」로 뒀다 |
| 2026-09-01 (§10-10) | **저작도구** — 사용자 지시로 뒤집음 |
| 2026-09-02 (지금) | **Host** — 되돌림. **상대 설계와 같은 쪽으로 수렴**했고 회신 대기 축이 이것으로 닫혔다 |

**함께 폐기된 구 근거는 서로 반대 방향의 둘이며 둘 다 폐기다** — *"포털이 보유한 화면이 적어
메뉴 트리가 필요 없다"*(화면이 다섯이 되어 성립 안 함) · *"화면이 늘어 좌측 메뉴를 둔다"*
(목적지가 여럿인 건 맞으나 **그리는 주체**가 Host 다).

### 목적지 이동 수단을 「본문 상단 탭」으로 고른 근거 (실측)

- 상대 셸의 좌측 사이드바는 `levels 2→3` 이라 3단을 그리지만, **상대 메뉴의 저작도구 항목에
  자식 노드가 없다** — 우리 목적지가 놓일 자리가 지금 없다.
- 상대는 *"마운트 영역 안은 저작도구 화면정의서가 정본"* 이라고 명시했다.
- **본문 상단 탭은 상대 자신도 쓰는 확립된 패턴**이다(섹션 탭 영역 실재).
- ⇒ **상대 메뉴에 우리 하위 노드를 등재하지 않는다** — 등재하면 이동 수단이 둘이 되고 목적지가
  늘 때마다 상대 배포가 필요해진다.

## §10-29. 목록 페이저 누락 — 사양 3건 정정 (2026-09-02)

### 발단

사용자 질문 「페이징은 있어야 하지 않을까?」. 내가 시안 노트에 *"현재 사양에 목록 페이징
규정이 없다"* 고 적어 페이저를 빼 둔 것이 계기였다. **그 판단이 틀렸다.**

### ★한 층만 보고 「사양에 없다」고 결론냈다 — 반복되는 실패 형태

근거로 삼은 것은 **화면 사양의 섹션 컴포넌트 목록**뿐이었다. 그런데 **소비 창구 계약**에는
페이징이 명시돼 있었다:

| 창구 | 계약 본문 |
|---|---|
| `API-225` | *"영상 단위로 묶어 **페이징 조회**한다"* |
| `API-142` | *"본인이 업로드한 자산 목록을 **페이징 조회**한다 … 페이지 크기는 최대 100 으로 클램프"* |
| `API-232` | *"최근 것부터 **페이징**해 돌려준다 … 페이지 크기를 상한으로 잘라 낸다"* |

⇒ 빠뜨린 것은 시안이 아니라 **화면 사양**이었다. 창구는 페이지로 내려주는데 화면에 쪽을
옮길 수단이 없으면 **첫 쪽 뒤의 데이터에 도달할 길이 없다.**

### 고친 것

| ITEM | 버전 | 내용 |
|---|---|---|
| `SCREEN-028` | v32→**v33** | `Pagination` 컴포넌트 + 섹션 서술에 페이징 문단 |
| `SCREEN-033` | v29→**v30** | `Pagination` 컴포넌트만 — ⚠ 섹션 서술이 **984/1000자**라 여유가 16자뿐이어서 설명을 컴포넌트 주석에 실었다 |
| `SCREEN-044` | v3→**v4** | `Pagination` 컴포넌트 (섹션 서술 389/1000, 여유 있음) |

### 갭이 아니라고 판정한 것 (실측 근거)

- **정렬 UI** — ⚠ **여기 적었던 근거가 틀렸다(2026-09-02 감사에서 정정).** 구 서술은
  *"창구가 정렬을 파라미터로 받지 않는다"* 였는데, **`API-232` 에서만 참**이고
  **`API-225`·`API-142` 에는 `sort` 쿼리 파라미터가 실재**한다(`API-225` 는 「허용 목록 밖이면 400」,
  `API-142` 는 Spring Pageable sort). 한 창구를 읽고 셋으로 일반화한 것이며 **페이징 때와 같은 결의
  실수**다. **결론은 그대로 갭 아님**이나 근거가 바뀐다 — 아래 판정선 때문이지 「창구가 안 받아서」가 아니다.
- **`API-142` 의 `type` 필터(IMAGE/VIDEO)** — 화면에 없어도 **도달 불가가 생기지 않는다.**
  ★판정선: **페이저가 없으면 뒤쪽 데이터에 못 간다. 필터가 없어도 페이징으로 전부 간다.**
  창구가 가진 능력을 화면이 다 노출해야 하는 것은 아니다.

1. **와이어프레임(정적 렌더)이 확실히 낡았다** — 이번에 `sections` 를 실제로 바꿨기 때문이다.

2. ~~포털 5화면 `uses_components` 공백~~ — **갭이 아니다(정정).** `screen_spec` **38화면 전수

3. **`SCREEN-033` 섹션 서술이 상한에 거의 닿았다**(984/1000). 다음 편집은 재배치가 선행돼야 한다.

## §10-31. 포털 디자인 시스템을 우리 저장소에 등록 (2026-09-02)

### 발단 — 탭이 어색했던 진짜 이유

사용자 지시 「내작업 업로드 증강 버튼을 다른 포털 디자인 시안들을 참고해서 어색하지 않게」.
포털 게시본을 **직접 렌더해 실측**했더니 내가 그린 탭이 네 곳에서 어긋나 있었다.

| | 내가 그렸던 것 | 포털 실측 |
|---|---|---|
| 밑줄 | 2px | **4px** (가운데에서 양옆으로 펴짐) |
| 글자 | 16px / 500 | **15px / 600** |
| 항목 간격 | 22px | **8px** |
| 바 구분선 | 있음 | **없음** — 활성 항목 밑줄만 |

★ 포털 「내 학습데이터」가 **같은 문제(한 화면에서 두 갈래 가르기)를 KRDS line 탭으로** 이미 풀고
있었다. 우리가 새로 디자인할 자리가 아니었다.

### ★★더 큰 것 — 시안 전체가 다른 디자인 시스템이다

`INT-013` 이 명시한다 — *"포털 채널은 포털 디자인 시스템을 **전면 채택**한다 — 주색만이 아니라
형태·타이포·간격·그림자·컨트롤 높이까지 그대로 따른다"*. 대비표도 있다:
주색 **코발트 `#2e45dc`** · 본문 기준 **15px**(관제 17px) · 모서리 **6·8·12·16·24** · **굵기 상한 600**.

그런데 `SD-024` 는 **관제 축(DS-001 KRDS Public)** 으로 그려져 있다 — 본문 17px, 모서리 4/6/8, 주색 `#256ef4`.

⚠ **가장 헷갈리는 지점** — 포털의 정부 디자인시스템 기본 primary 는 **우리와 같은 `#256ef4`** 인데,
포털이 그 위에 브랜드 코발트 `#2e45dc` 로 **덮어쓴다**. 토큰 이름이 같고 값이 다르다.
**이름으로 같은 색이라고 판단하면 조용히 다른 색이 뜬다.**

### 등록 — `DS-002` 신설

사용자 지시 「포털 디자인 시스템을 우리 로지크래프트에 넣을 수 없나?」 → 등록했다.

- **값 필드 9종은 전사 없이 파일에서 그대로 실어 보냈다**(tokens · typography_use · color_usage ·
  elevation_levels · responsive_breakpoints · layout · shape_principle · whitespace_principle · do_rules)
  — 되받아 대조 결과 **전건 IDENTICAL**.
- **산문 6종은 다시 썼다** — 원본에 상대 레포 경로가 섞여 있어 그대로 복사하면 우리 ITEM 이
  오염된다(본문은 사양만 담는다는 규율). 값은 건드리지 않고 서술만 바꿨다.
- ★**사본임을 본문에 못박았다** — *"우리가 값을 바꾸면 두 번째 진실원이 된다"*. 고칠 것이 생기면
  상대에 제기하고, 상대가 바꾸면 다시 옮겨 온다. 출처 버전을 적어 둔 이유가 낡음을 보기 위해서다.
- `DS-001`(관제 축)은 건드리지 않았다. 둘 다 `is_in_use` 이며 `applies_to` 로 채널이 갈린다.

### 연결의 한계 (실측)

**`ui_component` 만 디자인 시스템을 참조한다**(`design_system_id`). `screen_spec`·`screen_design` 에는
그 필드가 **없다.** 그래서 `DS-002` 는 화면·시안과 그래프로 이어지지 않고, 참조는 서술로만 걸린다.

### 남은 결정 (사용자)

**`SD-024` 를 `DS-002` 로 전면 재작성할지.** 토큰 교체만이 아니라 본문 기준 크기(17→15) ·
모서리 값 · 굵기 상한까지 바뀐다. 지금은 **탭 규격만** 맞춰 뒀고 나머지는 관제 축 그대로다.
⚠ 목업(`reports/`)은 애초에 포털 토큰으로 그려져 **이미 맞다** — 어긋난 것은 키트 시안 쪽뿐이다.

## §10-32. 압축 전 인계 — 이번 라운드의 도구 사실과 자산 (2026-09-02)

### 새로 알아낸 도구 사실 (거부당하고 나서야 알게 되는 것들)

| 사실 | 왜 중요한가 |
|---|---|
| **`create_item` 은 최상위 `title` 이 필수**다(`data.name` 과 별개) | 없으면 `invalid_type ... path:["title"]` 로 거부. 값 필드를 다 채워도 이것 하나로 실패한다 |
| **`get_design_render` 의 html·css 는 `renders[]` 아래**에 있다 | 최상위에서 찾으면 `0 바이트`가 나와 **손상으로 오인**한다(실제로 그렇게 한 번 오판했다) |

| **패치 스크립트를 `import` 하면 최상위 호출이 재실행된다** | 함수만 쓰려고 import 했다가 앞선 쓰기가 다시 돌았다. **앵커 count 단언이 막아 줬다**(`anchor count=0`) — 그 가드가 없었으면 이중 적용이었다 |
| **Playwright 스크립트는 `frontend/` 안에 둬야 한다** | `/tmp` 에 두면 `ERR_MODULE_NOT_FOUND: playwright`. 기존 예시가 `frontend/shot.mjs` 다 |
| **`fullPage` 는 max(내용, 뷰포트)** 를 찍는다 | 뷰포트 높이를 크게 잡으면 아래 여백이 통째로 들어간다. 작게 잡아야 내용에 맞게 잘린다 |

## §10-33. SD-024 를 DS-002 로 전면 재작성 (2026-09-02)

§10-31 이 남긴 결정을 닫았다. 시안이 **관제 축(DS-001)** 으로 그려져 있었는데, 이 화면은
포털 채널에만 서므로 그 자리가 아니었다. `INT-013` 이 *"포털 채널은 그 채널의 디자인 시스템을
전면 채택한다 — 주색만이 아니라 형태·타이포·간격·그림자·컨트롤 높이까지"* 를 못박는다.

### 바뀐 여덟 축

| 축 | DS-001 (관제) | DS-002 (포털) |
|---|---|---|
| 주색 | `#256ef4` | **코발트 `#2e45dc`** · hover `#2336b8` |
| 중립 | KRDS gray `#6d7882` 계열 | **slate `#64748b` 계열** |
| 본문 기준 | 17px | **15px** |
| 굵기 상한 | 800 | **600** |
| 모서리 | 4 / 6 / 8 | 태그 6 · 입력·페이저 8 · 타일 12 · 표면 16 · 패널 24 · **버튼은 캡슐** |
| 그림자 | 카드에 항상 sm | **기본 없음**(평면이 출발점) |
| 표 헤더 | 14/600 | **14/500 + slate-500** — 굵기보다 색으로 죽인다 |
| 자간 | 0 | **-0.5px**(본문에 한 번) |

### ★원칙 문장만으로는 안 갈렸다 — 상대 스타일시트를 열어 확정했다

「명령은 둥글게」가 버튼을 **캡슐**로 만드는지 8px 로 만드는지는 문장으로 판정되지 않는다.
그 채널 스타일시트에서 2차 층이 `버튼 라운드 → max`, `굵기 상한 → 600`, `본문 자간 → -0.5px`,
`페이저·입력 → 8px` 로 덮는 선언을 **직접 봤다**. 내가 앞서 그린 목업이 버튼을 8px 로 두고
있었는데 그게 틀렸던 것이고, 이번에 목업도 함께 캡슐로 고쳤다.

### ★`stroke-width` 누락 — 「새 사실」이 아니라 한 파일만 빠진 것이었다 (2026-09-02 정정)

되받아 대조에서 `svg` 의 `stroke-width` 속성이 **전건 제거**되는 것을 보고 CSS 에 같은 값을
선언해 두 판을 맞췄다. **처음에 나는 이것을 새로 알아낸 사실로 적었는데 틀렸다.**

자매 시안 셋(`SD-025`·`026`·`027`)을 열어 보니 **이미 같은 대비책이 들어 있었고**, `SD-025` 의
주석은 그것을 **2026-08-14 에 확인했다고 날짜까지 적어 두고 있었다.** 제거 목록도 그 노트들이
`stroke-width`·`stroke-linecap`·`stroke-linejoin`·`accept`·`multiple`·`tabindex`·`scope` 로
이미 열거하고 있었다.

⇒ 실제 사실은 이것이다 — **알려진 함정인데 `SCREEN-028` 한 파일에만 적용이 빠져 있었고, 그
파일의 노트는 「해 두었다」고 적고 있었다.**

> ★**노트가 말한다고 파일에 있는 것이 아니다.** 문서를 근거로 「되어 있다」고 판정하지 말 것.
> ★**그리고 「내가 처음 발견했다」고 적기 전에 자매 산출물을 먼저 열어 볼 것.** 이 저장소는

## §10-34. 자매 포털 시안 셋도 DS-002 로 (2026-09-02)

§10-33 이 남긴 것을 닫았다. `SD-025`(SCREEN-029 포털 라벨링) · `SD-026`(SCREEN-033 포털 업로드) ·
`SD-027`(SCREEN-034 포털 업로드 라벨링) 셋 다 포털 채널 화면인데 관제 축으로 그려져 있었다.
바뀐 여덟 축은 §10-33 표와 같다. **`SD-025` v5 · `SD-026` v8 · `SD-027` v10.**

### 방법 — 토큰 이름은 두고 값만 갈았다

세 파일 모두 같은 원본에서 나와 토큰 블록과 타이포 사다리가 사실상 동일했다. 그래서
**정확일치 + 등장횟수 단언**으로 짜인 공통 변환 하나를 만들어 세 파일에 돌렸다(필수 16건이
전건 정확히 1회씩 맞았고, 하나라도 어긋나면 파일을 건드리지 않고 멈추게 했다).

- `--n-*`·`--p-*`·`--sp-*` 는 **스케일 위치를 가리키는 이름**이라 값만 갈아끼웠다 —
  `--sp-sm` 하나만도 사용처가 53곳이라, 이름을 바꾸는 쪽이 훨씬 위험했다.
- ⚠ **`--radius-*` 만은 이름이 가리키는 역할이 바뀌었다** — `sm`=6(태그) · `md`=8(입력·페이저) ·
  `lg`=16(표면). 이 사다리에만 있는 12·24 는 `--radius-tile`·`--radius-panel` 로 더했다.
  덕분에 기존 사용처 대부분이 **자동으로 맞는 값에 착지**했고, 손으로 고칠 것은 버튼(캡슐)과
  안내 배너(타일)뿐이었다.
- `--shadow-sm: none` 으로 두어 카드·표 셸이 **한 줄도 안 고치고** 평면이 됐다.

### ★내가 낸 결함 하나 — 그리고 그것이 드러낸 옛 오류 하나

변환 중에 `--border-strong` 을 이 시스템이 명시한 입력 보더 **slate-300** 으로 내렸다. 그런데
그 값은 **흰 면 위 1.47:1** 이라 WCAG 1.4.11(3:1)에 미달하고, 그 토큰이 실제로
**컨트롤 경계**(`SCREEN-033` 정렬 컨트롤 · `SCREEN-034` 셀렉트)에 쓰이고 있었다. slate-500(4.76:1)로
되돌리고 근거를 토큰 옆에 남겼다.

★ 이걸 계산하다 **어제 `SCREEN-028` 에 내가 적은 「slate-300 은 흰 면 위 3.0:1 로 1.4.11 을
넘긴다」가 거짓**임을 알았다. 실제 1.47:1 이다. 그 파일의 `--border-input` 도 slate-500 으로
고치고 주석을 정정했다. **대비 수치를 근거로 쓸 때는 계산하고 쓸 것 — 그럴듯한 숫자를 적으면
그것이 다음 사람의 근거가 된다.**

### 검증

- CSS 왕복 **세 건 모두 IDENTICAL**.
- HTML 차이는 정규화 후 **알려진 제거 항목뿐**(주석 · `scope` · `stroke-*` · `accept` ·
  `multiple` · `tabindex` · 대소문자 정규화 · head 주입) — 내용 손실 0.
- 세 화면 렌더 확인. 희귀 음절 분석 네 화면 합계 630종 중 118종 전수 확인, **한글 손상 0건**.

### ★남은 것 — 이번에 손대지 않은 두 가지 (설계 변경이라 별건)

1. **`SCREEN-033`(포털 업로드)은 본문 상단 이동 탭의 목적지 셋 중 하나인데 시안에 탭줄이 없다.**
   `SCREEN-028` 시안만 그것을 그린다. 셸이 탭 영역을 한 번만 선언하는 구조라 화면 사양에
   중복 선언하지 않는 것은 맞으나, **시안은 그 자리에 무엇이 서는지 보여 줘야 한다.**
   ⚠ 같은 화면이 `page-head` 로 제목을 또 그린다 — 탭의 활성 항목과 같은 말이라
   `SCREEN-028` 이 걷어낸 바로 그 중복이다. **화면 사양을 먼저 고쳐야 하는 건이다.**
2. **페이저 현재 쪽 표시가 화면마다 다르다** — `SCREEN-028` 은 틴트, `SCREEN-033` 은 채움이다.

3. ⚠ **`SCREEN-044`(증강)는 여전히 시안 자체가 없다.**

## §10-36. 폐기 표기도 걷어냈다 — 화면 축 산출물은 실제 구성만 적는다 (2026-09-02, 사용자 확정)

> "[폐기] 도 빼고 아예 내용을 없애버려야 하는거 아냐?"

2026-08-08 확정은 *"화면정의서는 발주처 산출물이라 본문에 폐기 문구를 두지 않고 실제 화면 구성만
적는다(원소째 제거)"* 를 **`screen_spec` 에만** 적용하고 있었다. 사용자가 그것을 **화면 축 산출물
전체로 확대**하기로 확정했다.

### 대상 판정 — 검사기를 먼저 고쳤다

전수 스캔에서 `list_items` 가 **본문을 돌려주지 않는다**(메타만)는 것을 알아, 처음 스캔이

⇒ 이미지 축 `[폐기]` 표기를 든 ITEM **9건** + 결정 기록 `ADR-013`.

### 고친 것 — 폐기 틀만 걷고 살아 있는 규칙은 긍정문으로

★**통째로 지우면 안 되는 이유가 문장 안에 섞여 있었다.** *"자산 종류 값역에서 이미지 값을 없애지
않는다 — 없애면 이미 적재된 행이 판독 불가가 된다"* 는 폐기 서술이 아니라 **현행 규칙**이다.

`fragments` 가 **메시지 인덱스로 구간을 가리킨다**(`start_index`/`end_index`). 앞의 11건을

메시지가 의도한 것인지(청크 전송 · 프레임 추출 · 목록 폴링) **하나씩 확인**했다.
⚠ 이 ITEM 은 스스로 *"흐름도에는 그 분기를 지우지 않고 폐기로 표기해 남긴다"* 고 적고 있었다 —
그 결정이 이번에 뒤집혔고 change_summary 에 명시했다.

  참인 문장이 하나도 남지 않는다. `status` 를 `deprecated` 로 내리는 것은 **금지**(키트 export
  에서 영구 소거되어 오염·한글·감소 검사에서 이탈한다). **판단이 필요한 유일한 잔여다.**

## §10-39. 압축 전 인계 — 이미지 축 종결 · 마킹 화면 신설 · 라벨링 통합 · 메인 머지 (2026-09-02)

### ★이번 라운드의 머리기사 — 왜 같은 지적을 세 번 받았나

사용자가 **세 차례** *"이미지 업로드 없다니깐?"* → *"몇번을 강조해서 없어지질 않네"* 를 말했다.
원인은 판단이 아니라 **검사기가 본문을 한 번도 안 봤다는 것**이다.

`kit-export` 응답의 ITEM 은 `id`·`type`·`version`·`status`·**`raw_json`**·`skeleton_md`·`links` 로 이뤄지고
**본문은 `raw_json["data"]` 에 있다.** 최상위 `data` 를 훑는 검사기는 **1,556건 전부에서 0건**을 내며

⇒ 규칙: **검사기를 믿기 전에 「내가 이미 아는 사실」을 그 검사기가 잡는지 먼저 단언한다.**
`assert any(it["id"]=="ERD-028" and IMG.search(body(it)) for it in items)` 한 줄이면 이 부류가 통째로 막힌다.
이 사실은 memory `kit-export-body-lives-in-rawjson` 에도 남겼다.

⚠ **내가 두 번 틀렸다** — 처음엔 *"`raw_json` 은 파이썬 repr 문자열"* 이라고 에이전트 둘에게 알렸는데
**중첩 dict** 였다(정정 메시지를 보냈다). `ast.literal_eval` 은 실패한다.

| **`screen_spec` 은 `deprecated` 가 옳다** | 다운로더가 별도 보관한다. ⚠ 단 **보관본은 폐기 처리 시점 판**이라 **상태를 내리기 전에 본문을 받아 둬야** 한다(실제로 필요했다) |

### 진행 상태 — 어디까지 왔나

- **설계: 완료.** ITEM 신설 5(`SCREEN-045`·`API-238`~`241`) + 개정 30여 건. 되받아 대조 전건 통과.
  와이어프레임 5건 재생성해 **전건 최신**. 위키 8개 문서 + 시험 카탈로그 회차 갱신.
- **메인 머지: 완료**(`3600b1ce`). 충돌 0 — 겹친 파일은 셋뿐이었고 **양쪽 생존을 확인**했다.
- **구현: 단계 ① 진행 중.** 순서는 ①스키마·응답 → ②포털 창구 4 → ③마킹 화면 → ④순서 반전 →
  ⑤라벨링 통합 → ⑥이미지 잔재. **④⑤가 기존 동작을 바꾸는 쪽이라 위험하다.**
  다음 Flyway 는 **V27**(내가 잡아 뒀다).

### 압축 후 이어갈 지점

1. **단계 ① 회수** — 마킹 원장 두 칸 제거 + 식별자 폭 확대 + 응답 조인 전환. `deploy/onprem/db/schema.sql`
   동기화 여부를 반드시 확인할 것(뒤처지는 known 함정).
2. **단계 ②~⑥** 를 순서대로. 각 단계 뒤 **독립 QA**(`klid-qa-verifier`)를 붙인다.
3. **전체 회귀는 단계가 다 끝난 뒤 1회** — backend 약 8분 24초 + frontend 약 38초.
4. **머지 후 메인에서** 키트 SYNC·IMPREC. 이 트리에서는 유예했다.
5. **미결 4건** — 추출 장수 상한을 화면에 주는 창구 없음(저장 **전** 경고 불가) · 서명 주소의 브라우저
   결속 수단 · 확인창 방식의 채널 내 비대칭 · 캔버스 부품 이름 불일치(**기존 드리프트**).
6. **마킹 화면 고충실 시안 0건** — 와이어프레임은 있다. 이 저장소는 신설 화면에 시안이 뒤따르는 통례라
   결함은 아니다.

### 내가 이번 라운드에 틀린 것

1. **검사기가 본문을 안 봤다** — 위 머리기사. 세 번 오보의 원인.
2. **`raw_json` 형식을 잘못 알렸다** — repr 문자열이 아니라 dict.
3. **절단 방향을 거꾸로 지시했다** — *"앞에서부터인지 적으라"* 고 했는데, 같은 도메인의 추출 사양이
   이미 **「전 구간을 고르게 다시 뽑는다」** 였다. 에이전트가 선례를 찾아 뒤집었다.
4. **행 수를 근거 없이 적었다** — 시안 정리 뒤 「준비 완료 2행」이라 썼는데 실제로는 1행. 세어서 고쳤다.
5. **질문을 복잡하게 해 사용자가 *"뭔소리야"*** — 응답 필드 처리는 물을 게 아니라 기본값으로 그냥
   하면 되는 일이었다.

⇒ **1·2·4 는 「확인할 수 있는 것을 확인하지 않고 말했다」는 한 가지 형태다.**
