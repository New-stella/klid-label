## 1. 사용자 확정 (구속) — 되돌리지 말 것

1. **저작도구와 포털은 서로의 DB 에 접근하지 않는다**(양방향). 데이터 교환은 API.
   ⇒ 듀얼 데이터소스(`PortalDataSourceConfig`·`@PortalRepo`) 기반 메타 단방향 복제 **폐기**.
   ⚠ **정책만 확정, 코드는 아직 철거 전.** 「이미 걷어냈다」로 읽지 말 것.
2. **채널별 별도 배포** — 한 서비스가 양쪽에 붙는 구조가 아니다. **두 배포본끼리도 직접 이어지지 않는다.**
3. **인프라 소유가 갈린다** — 관제향: DB·NAS 모두 관제지원 소유(공유 NAS) / 포털향: **DB 는 저작도구가
   직접 관리**(별도 서버) · **NAS 는 포털이 관리**하는 별도 NAS.
4. **포털향에 `ai-server` 미연결**(오토라벨·인터랙티브 분할 없음). AI 파이프라인은 관제향에만.
   ⚠ **외부 증강은 별개 축** — ai-server 가 아니라 외부 위탁이고 포털 업로드 영상 대상 제공은 확정(`ADR-013` v10).
5. **자산 전달 3단계 — 중계자는 관제**
   ① 관제향 검수 승인 → 관제로 완료 통지
   ② 관제가 자산을 포털로 전달(**압축 파일** · **우리 export 산출물 중 비식별 벌만**)
   ③ 포털이 **포털향 배포본**에 자산 수신을 API 로 알림
   ⚠ ③ 수신자를 「관제향」으로 적었다가 정정한 이력 있음. 관제향이면 ①의 주체로 되돌아가는 **순환**이라 성립 안 함.
6. **서버간 API** — ②일일 저작집계 **신설 확정**(KST 자정 경계) / ①완료 저작결과 조회는 **포털에 역질문**
   (본인 데이터라 회원 토큰으로 충분해 보임. MF 영역인지 포털 직접 렌더인지에 달림).

## 5.5 ★사용자 확정 (2026-08-31, 구속) — 포털 데이터셋 소재 전달

**저작도구는 포털 NAS 에서 파일을 직접 읽는다. 다만 그 경로는 포털이 API 로 알려 주는 값을 그대로 쓴다**
(포털 제시 안 A). 저작도구가 경로를 조합·추측하지 않는다 — 비식별 영상 경로에서 이미 확립된 규칙과 같은 축이다.

- **NAS 는 포털 NAS 가 맞다**(사용자 확인). 포털향 배포본이 이미 그 NAS 를 쓰므로 경계가 넓어지지 않는다.
- ★**압축은 별도 폴더에서 푼다**(사용자 지시). 같은 NAS 안이어도 **읽는 자리 ≠ 푸는 자리**로 가른다.
  근거 — ①포털 폴더는 포털 소유라 쓰면 「읽기만」 약속이 깨진다(읽기전용 마운트면 애초에 불가)
  ②원본 데이터셋 무영향 ③동시 편집 시 같은 자리에 풀면 서로를 덮는다 ④작업 후 정리 대상 판정 불가.
- ⚠ **격리는 zip slip 방어가 아니다** — 엔트리 이름에 상위 이동이 있으면 격리 폴더 밖으로 나간다.
  엔트리마다 해제 실경로가 목적지 하위인지 확인 + 절대경로·심링크 엔트리 거부 + 총량·엔트리 수 상한이 필요하다.
- ★★**이 저장소에 압축 「해제」는 처음이다** — `ZipOutputStream`(쓰기) 1곳뿐이고 `ZipInputStream`/`ZipFile` **0건**.
  zip slip 방어는 재사용할 물건이 없고 **새로 만들어야 한다**(숨은 공수). 경로 축은 `common/storage/StorageSubtreePolicy`
  (실경로 재검증 + `NOFOLLOW_LINKS`)를 재사용할 수 있으나 **엔트리 이름 검증 축은 없다.**
- **폴더 배치는 포털에 역질문**(사용자 지시) — NAS 소유자가 정하는 것이 맞다. Q1~Q7 로 아티팩트에 실었다.

## 8. 함정 (이 세션에서 실제로 걸린 것)

- **heredoc 인용 누락** — `<<PY` 로 열면 셸이 백틱을 실행해 토큰이 **빈 문자열로 들어간다.** 반드시 `<<'PY'`.
- **`| tail` 이 종료코드를 삼킨다** — `$?` 가 `tail` 것이 된다. 파이프 없이 재실행해 판정할 것.
- **로컬 키트는 미러라 stale** — 서버 원본으로 판정할 것. 정적 렌더는 **`source_hash` 오라클**
  (ITEM `sections` 의 sha256 재계산 대조)로 판정.
- **`frontend/node_modules` 가 비어 있다** — 첫 검증 전 `npm ci` 필요.
- **워크트리 정책** — 키트 SYNC 금지 · IMPREC 기록 금지 · 머지 방식 PR 고정.

### 10-10. ★반전 — 좌측 메뉴의 주인 (2026-09-01 사용자 지시)

> "워크스페이스 메뉴는 아마 우리 화면 뜰때는 안보일것 같은데? 헤더 빼고는 다 저작도구 화면일거야"

**§10-6 의 「LNB 는 Host 가 그린다」 전제를 뒤집는다.** Host 는 **머리 영역만** 그리고,
그 아래는 좌측 메뉴를 포함해 **전부 저작도구**가 렌더한다.

- 시안을 그렇게 고쳤다 — 좌측 메뉴는 우리 것이고 **우리 3항목만** 담는다
  (내 작업·내 업로드·증강). 모양은 포털 `LnbPanel` 규격을 그대로 따른다.
- **사용자 카드는 두지 않는다**(`MenuOnly` 변형) — 신원은 Host 머리 영역이 이미 보여 준다.
- **`NAV-002` 등재 협의가 불필요해진다**(§10-6 의 결합 비용 소멸). 목적지를 늘려도
  포털 배포가 필요 없다.

⚠ **포털 설계와는 어긋난다 — 확인 항목이다.** `SHELL-001` 은 `applies_to_screens` 에
`SCREEN-012` 를 포함하고 `lnb` 영역(워크스페이스·마이페이지, `source_nav_id NAV-002`)이
살아 있는 것으로 규정한다. 즉 **포털 문서상으로는 우리 화면에서도 LNB 가 보인다.**
어느 쪽이 맞는지 회신으로 확정해야 하며, 시안은 사용자 지시(=LNB 없음)를 따랐다.

### 10-11. ★★「내 학습데이터」(SCREEN-013)가 우리 「내 작업」과 정면 충돌한다

`SCREEN-013` v41 본문 실측:

> 두 종류의 데이터를 하나의 목록으로 관리: **(1) 저작도구에서 저작 완료된 학습데이터
> (저장 완료 시 자동 이동)**, (2) 학습데이터 검색에서 다운로드 진행한 데이터셋 …
> **PC 다운로드 버튼으로 결과물 다운로드. 보존기간 임박 시 다운로드 권유 안내 표시.**

섹션 본문:
> ① 저작 완료분 — **`tb_athrng_job`(authoring 스키마). 포털 WAR 이 직접 읽을 수 없어
> 저작도구 WAS API 경유로 얻는다(ADR-013). ※ 구체 경로는 EXTSYS-002 소관으로 미정.**

즉 포털은 **저작 저장물의 목록·다운로드·만료 안내를 자기 화면에서 제공**하도록 설계돼 있다.
그런데 우리는 2026-09-01 사용자 확정으로 **같은 것을 `SCREEN-028` 이 갖는다**고 정했다
(*"사용자가 저장한 리스트 자체는 우리가 보여주는거야"* · *"거기서 다운로드도 해야하고"*).

**양쪽이 같은 목록·같은 다운로드·같은 만료 안내를 각자 갖고 있다.**

- 가능한 경계: 우리=**진행 중**(이어쓰기) / 포털=**완료 결과물**(다운로드).
  포털 상수 `CONST-019`(IN_PROGRESS·COMPLETED·CANCELLED)가 그 경계를 지지한다.
- ⚠ 그러나 `SCREEN-013` 은 *"**저장** 완료 시 자동 이동"* 이라고 적어 **저장 시점**을 말한다.
  우리 「내 작업」은 저장 시점부터 목록에 올린다 — **그 문구대로면 겹친다.**
- ⚠ 우리 `SCREEN-028` 은 행마다 **내려받기**를 갖는다(사용자 확정). 다운로드도 겹친다.

⇒ **회신으로 경계를 확정해야 한다.** 우리가 만든 `API-225 GET /v1/portal/user-works` 가
포털이 「미정」으로 남긴 그 창구일 가능성이 높다 — 그렇다면 우리는 목록을 **보여주기도 하고
공급하기도** 하게 된다. 그 이중 역할이 의도인지 확인이 필요하다.

### 10-12. ★포털이 전제한 우리 테이블 `tb_athrng_job` 은 존재하지 않는다

- 우리 저장소 실측: `athrng` **0건**(backend/src·deploy 전체)
- 우리 포털 테이블은 `ls_portal_tus_uld` · `ls_portal_uld` · `ls_portal_uld_frme` ·
  `ls_portal_uld_lbl` · `ls_portal_user_label` **5종**

`CONST-019` 가 *"저작도구 작업 세션(`tb_athrng_job.stts`)의 상태값. authoring 스키마 소속"*
이라고 단정하고 `SCREEN-013` 이 그 테이블을 소스로 지목한다. **포털이 우리 스키마를
추정해 적어 둔 것**이며 실물과 다르다. 회신에 포함할 것.

### 10-13. 포털이 우리에게 기대하는 공급 두 가지 (미확인)

1. **`SCREEN-011` 대시보드 카드 ②** — *"저작도구 작업 현황 — 진행중·업로드 처리중·

   → **우리가 통지해야 한다.** 그 통지 경로가 우리 설계에 없다.
2. **`CONST-022` 저작 파이프라인 단계** = `FRAME_EXTRACTION` · `AUTO_LABELING` ·

   ⚠ **포털 채널은 오토라벨링·검수가 미제공**인데 값역에 들어 있다.
   ("포털 전용 저작도구 형상에서는 단계 단순화 가능"이라고 여지를 뒀으나 미확정)

### 10-15. ★확정 — 저작 저장물 소유 · 증강 자체 수행 (2026-09-01 사용자 확정, 구속)

> "저작 저장물 목록 다운로드는 우리 화면이야. 증강요청은 우리가 알아서 할거고
> 저작도구내에서 결과 확인 및 작업후 다운로드 할 수 있어야해"

**① 저작 저장물의 목록·이어쓰기·내려받기는 저작도구 화면이 소유한다.**
§10-11 의 「양쪽 충돌」은 **우리 쪽으로 확정**됐다. 포털 `SCREEN-013` 의 ①「저작 완료분」
소스는 포털측 재검토 대상이며, 그 요청을 아티팩트로 보냈다.
⚠ **화면 소유와 데이터 공급은 별개다** — 포털이 요약·연계 목적으로 목록을 받아 가는 것은
여전히 가능하고, 우리 `API-225` 를 그 창구로 계속 제공한다. **다만 「목록 공급」과
「파일 다운로드」는 다른 축**이며 다운로드는 우리 화면에서만 일어난다.

**② 증강은 저작도구가 자체 수행하고, 결과 확인·후속 작업·다운로드까지 우리 안에서 끝난다.**
- 증강 **요청** — 우리가 처리(대상·조건·외부 위탁 전부)
- 결과 **확인** — 우리 화면

### 10-20. 다음 라운드 착수 지점 — 포털 증강 API 신설

**목표**: `SCREEN-044`「포털 증강 화면」이 소비할 창구를 설계한다. 지금 `consumes_apis` 가

**필요한 창구(추정 — 확정 아님)**: 증강 요청 접수 · 요청 현황 목록 조회 · 결과 조회 ·

`SCREEN-044` 는 나머지 셋을 부른다 — 진입이 갈려 있으니 소비 화면을 섞지 말 것.

**설계 시 지켜야 할 제약 (전부 이번 라운드에서 확정된 것)**
1. **본인이 올린 영상 한정.** 데이터마트에서 불러온 영상은 대상이 아니다.

   대상이 검수 완료 영상)과 성질이 다르다.
3. **비동기 위탁.** 요청 즉시 결과가 나오지 않는다. 상태 값역은 **아직 미확정**이며
   `SCREEN-044` 도 「대기·완료·실패를 구분한다」까지만 적었다 — 코드값을 지어내지 마라.
4. **외부 채널 증강 요청 창구(Host 의 것)를 호출하지 않는다.** 우리가 자체 수행한다.
5. **파생물은 포털 자산 계보**(`LS_PORTAL_*` 축). 내부 채널 파생 모델(원본 영상 원장에

   그것을 선점하지 않게 할 것.
6. **인가는 본인 자산으로 좁힌다** — 타인 자산 대상 요청·조회는 거부.
7. 표준용어·표준도메인은 CSV 정본 grep 으로 판정(MCP 검색으로 「미등록」 판정 금지).

**착수 방식**: `mc-logi-update` 위임. 창구는 신규 생성이라 번호를 지어내지 말고
서버가 부여한 값을 쓸 것. 워크트리 제약(키트 쓰기·SYNC·IMPREC 금지)은 그대로 적용.

### 10-21. 포털 증강 창구 라운드 — 완료 (2026-09-01)

#### ★확정 — 증강 저장 테이블을 채널별로 가르지 않는다 (2026-09-01 사용자 지시, 구속)

> "db테이블을 포털이나 관제향이나 가르지 않고 동일한거 쓰면 되잖아. 어차피 따로 배포되는데"

**메인이 실측으로 확인한 전제 (추정 아님)**
- 배포 스키마는 **`deploy/onprem/db/schema.sql` 한 벌(62테이블)** 이고 **양쪽 배포본이 같은 것을 로드**한다
  ⇒ 포털 배포본 DB 에 `ls_data_aug`·`ls_data_aug_lbl_map`·`ls_data_aug_job` 등이 **이미 있다**
- **`ls_data_aug` 에 FK 가 없다** — 제약은 PK 1개 + UNIQUE 2개(`otsd_job_id`·`idmp_key`)뿐이고
  `src_sn`·`new_raw_sn` 은 맨 `bigint` 다. (이 스키마 전체엔 FK 50개가 있고 27개 테이블이
  `ls_data_raw` 를 FK 로 문다 — 증강 테이블만 안 문다)
- ⇒ **새 테이블을 만들 이유가 없다.** 「포털 자산 계보에 속하며 내부 파이프라인 계보에 넣지
  않는다」가 든 근거는 *"포털 자산은 그 원장과 완전히 분리돼 있어 그대로 쓸 수 없다"* 인데,
  그건 **한 DB 안에서 섞일 때의 걱정**이고 DB 가 물리적으로 갈리면 섞일 자리가 없다.

**★부모 구분자는 필요 없다 — 메인의 초기 우려가 틀렸다**
`ls_data_aug.src_sn` 이 두 원장을 가리켜 모호해질까 우려했으나 **성립하지 않는다.** 포털 채널에서
**증강 대상은 업로드 영상 하나뿐**이라(「데이터마트에서 불러온 영상은 대상이 아니다」 — `AC-1070`
then · `DFEAT-053` description · `SCREEN-044` purpose 세 곳이 못박음) `src_sn` 이 가리킬 PK 공간이
애초에 하나다. **구분자 컬럼·마이그레이션 불요.**

**⚠ 실제로 어긋나는 자리는 결과물 컬럼이다 (ERD 라운드로 이월)**
`ls_data_aug` 의 결과물 포인터는 **`new_raw_sn`** 인데 포털에서 거기 담길 값은 **`uld_sn`** 이다 —
후속 작업 화면과 내려받기 창구 둘 다 `{uldSn}` 을 받기 때문이다(`SCREEN-034` 경로 · `API-157` ·
`API-159`). **컬럼 이름과 담기는 값이 갈린다.** 창구 계약에는 영향이 없다(창구는 `resultUldSn` 을
돌려준다). ⚠ 이 저장소의 「동명이표 주의」 관례상 그냥 두지 말고 ERD 라운드에서 판정할 것.
