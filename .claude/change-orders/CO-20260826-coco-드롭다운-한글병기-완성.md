# CO-20260826 COCO 탐지 클래스 드롭다운의 한글 병기를 완성한다

## 1. 무엇이 문제인가

라벨 관리(SCREEN) → 라벨 추가·수정의 **「AI 탐지 클래스」 선택 목록**이 한글과 영문이 뒤섞여 보인다.

```
사람 (person) · 자전거 (bicycle) · 자동차 (car) · 오토바이 (motorcycle)
airplane                    ← 영문
버스 (bus) · 기차 (train) · 트럭 (truck) · 보트 (boat)
신호등 (traffic light) · 소화전 (fire hydrant) · 정지 표지판 (stop sign)
parking meter · bench       ← 영문
새 (bird) · 고양이 (cat) · 개 (dog)
horse · sheep · cow · ...   ← 영문
```

사용자 신고: *"아직 코코 라벨에 한글로 정의가 안된것들이 많은것 같아"*

운영자가 라벨 마스터에 COCO 매핑을 지정할 때 이 목록에서 고르는데, 표기가 일관되지 않아
같은 목록 안에서 어떤 항목은 읽히고 어떤 항목은 안 읽힌다.

## 2. 원인

**결함이 아니라 의도된 부분 번역이 남은 것이다.** 사전 자체가 그렇게 적어 뒀다 —
*"CCTV 관제 관련 이동체 등 일부에 한글 병기(표시 편의). 없으면 영문 id 표시."*

`COCO_LABEL_KO` 에 **80종 중 14종**만 있고 나머지 66종은 영문 폴백으로 떨어진다.
관제에 쓸모가 적은 클래스(주방·음식·가전)를 굳이 번역하지 않은 판단이었으나,
목록은 80종 전체가 그대로 노출되므로 **화면에서는 그냥 뒤섞여 보인다.**

**번역 판단 근거(되묻지 말 것)**
- `mouse` = **마우스** — COCO 의 mouse 는 쥐가 아니라 컴퓨터 마우스다.
- `orange` = **오렌지** — 색이 아니라 과일이다.
- `frisbee` = **원반** — "프리스비"는 상표명.
- `tv` = **TV** — 한글 음차("티비")보다 원문 표기가 통용된다.
- `hair drier` — COCO 원문 철자가 `drier` 다. **id 는 그대로 두고** 한글만 붙인다.

**불변 (어기면 매핑이 깨진다)**
- **`COCO_IDS` 배열은 손대지 않는다** — 값·순서·문자열 전부. BE `CocoClasses.LABELS` allowlist 와
  정확히 일치해야 하며 불일치 매핑은 BE 가 400 으로 거부한다.
- `CocoClass.id` 는 계속 **영문 COCO 문자열**이다. 한글은 `label` 에만 들어간다.
- `COCO_LABEL_KO` 는 **모듈 private 을 유지**한다(export 금지). 2026-08-03 확정으로 라벨 **표시명**은
  마스터 등록명이 진실원이며, 이 사전을 표시명 경로에서 import 하면 마스터와 어긋나는
  **두 번째 진실원**이 된다. 파일 주석이 그 이유를 적어 뒀으니 지우지 말 것.
- `isCocoClass()` 동작 불변.
- 표시 형식 `"{한글} ({id})"` 불변 — 66종도 같은 형식으로 붙는다.

## 4. 영향 없음을 확인한 것

- **BE 변경 0건** — 전송·저장 값인 `id` 가 그대로다.
- **설계 ITEM 변경 0건** — `CONST-002`(CocoClasses allowlist)는 **영문 id 목록만** 규정하고
  한글 병기를 규정하지 않는다. 화면 사양도 이 표기를 다루지 않는다(실측: 설계 키트에서
  COCO 를 언급하는 ITEM 은 `CONST-002`·`ADR-019`·`CDIAG-005`·`SCREEN-005` 이며 어느 것도
  드롭다운 표기 형식을 규정하지 않는다).
- **라벨 표시명 경로 무관** — 그 경로는 이 사전을 참조하지 않는다(모듈 private).

## 5. 수용 기준

1. 「AI 탐지 클래스」 드롭다운의 **80종 전부**가 `한글 (english)` 형식으로 나온다
   (영문만 나오는 항목이 0건).
2. 매핑을 저장하면 **영문 COCO 문자열이 그대로 전송**되어 BE 가 400 을 내지 않는다.
3. `COCO_IDS` 배열이 BE `CocoClasses.LABELS` 80종과 **순서·문자열 완전 일치**한다.
4. `COCO_LABEL_KO` 가 여전히 export 되지 않는다.
5. BE 소스 변경 0건.

## 6. 관련 설계 ITEM

**없음(— 해당없음).** 위 §4 참조 — 표기는 사양 아래 세부다. 선례: `CO-017`(설계 ITEM 0건).

## 7. 구현 로그

- **구현** — `COCO_LABEL_KO` 를 14종 → 80종으로 채웠다. 66종 한글값은 **손으로 타이핑하지 않고
  §3 표를 파싱해 생성**했다(전사 구간 0 — 이 저장소 한글 손상 사고의 구조적 차단).
  사전 순서를 `COCO_IDS` 순으로 재배치했고, 부분 번역을 전제하던 낡은 주석 1문장을 갱신했다.
- **`tv` 예외를 데이터로 못박았다** — 최초 가드가 `TV (tv)` 를 형식 위반으로 FAIL 시켰는데,
  그건 §3 이 확정한 표기다. 여기서 한글 검사를 느슨하게 고쳤다면 **66종이 다시 영문으로
  돌아가도 초록이 됐을 것**이라, 검사를 완화하는 대신 `NON_HANGUL_LABELS` allowlist 로 고정했다.
- **검증** — 독립 QA 가 §3 표를 **직접 파싱해** 66/66 대조했다(구현자 기대본을 경유하지 않아,
  전사 오류가 기대본에 함께 들어가 대조를 통과하는 경로가 닫혔다).
  `COCO_IDS` ↔ BE `CocoClasses.LABELS` 는 순서 유지 해시가 양쪽 동일.
- **가드 변이 8종 중 2종이 살아남았다** — M3(번역값 오류) · M6(`COCO_IDS` 순서 교환).
- **M3 후속 폐쇄** — 80쌍을 테스트 상수로 고정하는 가드 2종을 더해 닫았다.
  `dog:'고양이'` · `airplane:'항공기'`(한글이지만 다른 값) 두 변이로 **RED 를 실행 확인**했고,
  같은 변이에서 기존 형식 가드는 통과해 **죽인 것이 신규 가드임이 확정**됐다.
- **회귀** — frontend FULL `469 파일 / 3,811 tests`(직전 3,809 + 신규 2, 정확히 일치).

### 남은 것 (별건)

- **M6 는 여전히 열려 있다** — `COCO_IDS` 의 순서 교환이 통과한다. 추정이 아니라
  `horse`↔`sheep` 교환을 실행해 `7 passed` 로 **재현 확인**했다.
  현재 순서 검사는 spot-check 4곳(`ids[0]/[4]/[62]/[79]`)뿐이라 나머지 76개 위치가 미검증이다.
  ⚠ **이번 변경이 만든 공백이 아니라 기존 공백**이며 `COCO_IDS` 는 손대지 않았다.
- 진짜 해소는 spot-check 확대가 아니라 **FE↔BE allowlist 드리프트 가드**다.
  현재 저장소에 그 축이 없다(`CocoClassesDriftTest` 는 BE↔ai-server 축).
  선례는 있다 — 다른 축에서 테스트가 반대편 소스 파일을 읽어 계약을 고정한다.
