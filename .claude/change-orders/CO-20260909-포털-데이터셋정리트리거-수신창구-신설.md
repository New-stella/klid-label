## §1 배경

### 요청
포털팀이 이렇게 요청했다 — *"관제지원에서 학습데이터가 넘어오면 포털 저작도구쪽에 버전업이 되었다고 수신 받아야 하는 API 개발되면 알려달라."* 포털은 데이터마트와 버전 정보를 전달받으면, 저작도구가 **이전에 압축을 풀었던 구 데이터마트 해제본을 정리하고 신규 데이터마트로 갱신**하기를 기대한다.

### 이 창구가 서 있는 자리 — 자산 전달 3단계의 ③
`ADR-012` 가 못박은 자산 전달 경로는 셋이다.

1. **관제 채널 배포본**에서 검수 승인 → 관제로 완료 통지
2. **관제가 그 자산을 포털로 전달**(압축 파일)
3. **포털이 포털 채널 배포본에 자산 수신을 API 로 알린다** ← **이 CO 가 여는 창구**

⚠ 포털 채널 배포본이 관제 채널 배포본의 DB 나 API 를 직접 물어 승인 자산을 가져오는 그림은 그 결정과 어긋난다. 중계자는 관제이고, 승인 자산이 포털로 흐르는 경로는 위 셋뿐이다.

### 설계는 이미 있고 코드가 0건이다
2026-09-09 실측:

| 축 | 설계 | 코드 |
|---|---|---|
| 삭제 트리거 수신 창구 | **`API-244`**(v4, `implementation=planned`) · `INT-014`(v4) · `DFEAT-055`(v18) · `ADR-012`(v13) | **0건** (`portal-system` · `dataset-cleanup` · `API-244` · `INT-014` 각 backend 전체 0건) |
| 신규 데이터마트 조달(pull·압축 해제·적재) | `INT-014` 「소재 조달」에 **원칙만** — 조회 창구는 **포털 소유이고 응답 스키마 미회신** | 0건 |
| 시스템 주체(system) 토큰 인가 축 | `API-244`·`INT-014` 가 요구 | **0건** |
| 지울 대상인 해제본 저장소·원장 | — | **0건** |

즉 포털이 부를 주소가 없다. 그 자리를 채우는 것이 이 CO 다.

### ★ 실측으로 드러난 설계 갭 — 시스템 주체 토큰이 포털 사용자 창구 전체를 연다

`common/security/JwtAuthenticationFilter` 는 `channel` 클레임이 `PORTAL` 이면 **주체를 보지 않고 `role = Role.PORTAL_USER` 로 고정**한다. 그리고 `SecurityConfig` 의 `/v1/portal/**` 매처는 `CHANNEL_PORTAL` + `ROLE_PORTAL_USER` 결합을 요구한다.

⇒ **포털이 발급한 시스템 계정 토큰이 지금 이 필터를 통과하면 `ROLE_PORTAL_USER` 를 얻어 포털 사용자 창구 전부에 접근한다.**

이것이 왜 위험한가 — 포털 사용자 창구들의 IDOR 방어축은 `portalUserNo = token sub` 다(예: `PortalLabelService` javadoc 「보안: IDOR (CWE-639)」). 시스템 계정의 sub 로 그 판정이 돌면 소유자 비교가 **의미를 잃은 채 통과**한다.

#### ⚠ 갭의 자리를 처음에 잘못 짚었다 — 정정 (2026-09-09)

이 CO 는 처음에 *"`API-244` 가 사용자 주체 → 시스템 창구 한 방향만 규정하고 역방향이 없다"* 고 적었다. **그 서술은 부정확하다.** 설계를 대조하니 서버간 창구 셋이 **각자 자기 축의 역방향을 이미 규정하고 있었다**:

| 창구 | 축 | 이미 규정된 거부 |
|---|---|---|
| `API-242` 저작 현황 요약 (`/v1/portal/authoring-summary`) | 사용자 주체 | *"시스템 주체 토큰으로 부르면 거부한다"* — **역방향 있음** |
| `API-243` 일일 저작 집계 (`/v1/portal-system/authoring-stats/daily`) | 시스템 주체 | *"사용자 주체 토큰으로 부르면 거부한다"* |
| `API-244` 정리 삭제 트리거 (`/v1/portal-system/dataset-cleanups`) | 시스템 주체 | *"사용자 주체 토큰으로 부르면 거부한다"* |

**진짜 갭은 두 자리다.**

1. **포털 사용자 채널 창구 전체에 대한 규칙이 없다.** `API-242` 는 서버간 축의 사용자 창구 **하나**일 뿐인데, 코드 실측이 드러낸 위험은 그 하나가 아니라 **`/v1/portal/**` 아래 라벨링·업로드·증강 등 모든 사용자 창구**다. 창구마다 개별 서술로 흩어져 있으면 새 창구가 생길 때마다 다시 빠진다.
2. **그 규칙을 세울 자리인 `INT-014` 의 「인증 — 두 축」 표가 격리를 규칙으로 세우지 않았다** — 각 축을 *"쓰는 자리"* 만 적고, **다른 축의 자리에 들어가면 어떻게 되는지**를 적지 않았다.

⇒ 그러므로 이 라운드는 **개별 창구에 서술을 더하는 것이 아니라, 연동 축 소유자인 `INT-014` 에 채널 전역 규칙을 세운다.** `API-244` 는 그 규칙을 가리키기만 한다(계약을 두 곳에 적으면 한쪽만 갱신된다는 이 저장소의 원칙).

### ★ 시스템 주체 판정 규격이 없다
`INT-014` 는 *"주체 구분은 토큰의 주체 클레임이 한다"* 고만 적었고 **어떤 값이 시스템 계정인지는 규격이 없다.** `API-244` 가 경로·요청 본문 속성명을 「저작도구가 정의해 통보할 초안」으로 둔 것과 같은 처지이므로, **주체 판정 규격도 우리가 초안을 내서 포털에 통보**한다.

## §2 변경 요지

1. **수신 창구 신설** — `POST /v1/portal-system/dataset-cleanups`. 데이터셋 코드와 버전을 받아 **접수 원장에 기록**하고 202 로 답한다.
2. **시스템 주체 인가 축 신설** — 포털 채널 토큰을 **사용자 주체 / 시스템 주체** 로 가른다. 경로 접두를 갈라(`/v1/portal/**` ↔ `/v1/portal-system/**`) **양방향으로** 막는다.
3. **접수 원장 신설** — 유예 기산점(**처음 받은 시각**)을 보존해야 하므로 표가 필요하다. Flyway `V36`.
4. **실제 해제본 삭제는 이번 범위 밖** — 지울 대상이 코드에 없다. 이번 산출물은 **"받아서 기록만 한다"가 정상**이다.

### 공유기반 선처리 (메인 직접, Phase 3.5)

#### (가) Flyway `V36` — 접수 원장 신설

표준용어 판정을 **행안부 공통표준 CSV 정본 grep 으로 끝냈다**(1순위 = 행안부, 2순위 = 사업표준).

| 개념 | 약어 | 출처 |
|---|---|---|
| 데이터셋 | `DATST` | 공통표준단어 |
| 정리 | `ARNGMT` | 공통표준단어 |
| 트리거 | `TRGR` | 공통표준단어 |
| 수신일시 | `RCPTN_DT` (도메인 `연월일시분초D`) | 공통표준**용어** — 조합이 아니라 등록된 용어다 |
| 버전번호 | `VER_NO` (도메인 `번호V50`) | 공통표준**용어** |
| 코드 | `CD` | 공통표준단어 |

- **테이블**: `LS_DATST_ARNGMT_TRGR` (데이터셋 정리 트리거)
- **컬럼(초안 — 도메인 확정은 구현 시 CSV 재대조)**:
  - `DATST_ARNGMT_TRGR_SN` — PK, 시퀀스
  - `DATST_CD` — 데이터셋 코드. ⚠ **폭 판정 주의**: 코드값 표준도메인은 `VARCHAR(20)` 이나 **포털의 데이터셋 코드 표현 형식이 미회신**이다(`API-244` 열린 항목). 20 이 좁을 가능성을 검토하고, 정하면 그 값을 포털 통보 규격에 함께 싣는다.
  - `VER_NO` — 버전. 도메인 `번호V50`. ⚠ `API-244` 요청 스키마가 `type: string` 이라 **숫자 파싱을 하지 않는다** — 버전 표기법이 미회신이라 문자열로 보존한다.
  - `RCPTN_DT` — **처음 받은 시각**. 유예 기산점이며 **재수신으로 갱신하지 않는다**.
  - 등록자·등록일시 등 이 레포의 기존 원장 관례를 따른다.
- **유니크**: `(DATST_CD, VER_NO)` — 재수신 멱등의 근거. 이 제약이 있어야 "성공 무처리 + 기산점 미갱신"이 경합에서도 성립한다.

⚠ **`ON CONFLICT DO NOTHING` 으로 처리한다** — 조회 후 INSERT 는 두 요청이 동시에 오면 둘 다 통과해 기산점이 갈린다. 판정을 실행문 자체에 거는 이 레포의 원칙과 같은 축이다.

⚠ 마이그레이션 SQL 에 **`public.` 리터럴을 박지 않는다**(`current_schema()` + 비한정 식별자). `${...}` 도 주석 안이라도 쓰지 않는다(Flyway placeholder 파싱 실패).

#### (나) `common/security` — 시스템 주체 축

- **대상**: `JwtAuthenticationFilter` · `SecurityConfig`
- **변경**:
  1. 포털 채널 토큰의 **주체 축을 판정**한다. 판정 기준은 **설정값 allowlist**(시스템 계정 주체 식별자 목록)로 두고, **비어 있으면 아무도 시스템 주체가 아니다(fail-closed → 403)**.
     - 근거: 공유 서명키와 같은 논리다 — **설정값이라 구현을 막지 않으며**, 값이 없을 때 창구가 **열리지 않고 닫히는** 방향이라 안전하다.
  2. 시스템 주체로 판정되면 **`ROLE_PORTAL_USER` 를 부여하지 않는다.** 대신 전용 authority 를 부여해 `/v1/portal/**` 에 **도달하지 못하게** 한다.
  3. `SecurityConfig` 에 `/v1/portal-system/**` 매처를 **`/v1/portal/**` 매처보다 먼저** 두고, `CHANNEL_PORTAL` + 시스템 주체 authority 결합을 요구한다.
- **불변**:
  - `JwtAuthenticationFilter.PORTAL_TOKEN_HEADER` 가 헤더명의 **단일 진실원**이다 — 리터럴 `"x-access-token"` 을 새로 박지 않는다.
  - **INTERNAL 채널 경로를 건드리지 않는다.** 관제 인계 토큰 처리(비숫자 sub → userId 해석 · 자동 등록 · principal 정규화 · 최종로그인 기록)는 무변경이다.
  - 기존 포털 **사용자** 토큰의 동작이 바뀌면 안 된다 — allowlist 에 없는 주체는 종전대로 `ROLE_PORTAL_USER` 다.
  - `STREAM_SIGNED` 계열 권한은 여기서 부여하지 않는다(기존 불변).
- **주의**: ★**인가 매처는 순서가 있다.** `/v1/portal-system/**` 를 `/v1/portal/**` 뒤에 두면 접두가 겹치지 않아 지금은 우연히 동작하더라도, 이 레포는 *"인가 1차 원천은 `@PreAuthorize` 가 아니라 `SecurityConfig` 의 순서 있는 매처"* 라는 사고 이력이 있다. 순서를 명시적으로 확정하고 시험으로 고정한다.
- **수용기준**:
  - 사용자 주체 토큰으로 `/v1/portal-system/dataset-cleanups` → **403**
  - 시스템 주체 토큰으로 임의의 `/v1/portal/**` 사용자 창구 → **거부**(역방향 격리)
  - allowlist 미설정 상태에서 어떤 포털 토큰으로도 시스템 창구 → **403**(fail-closed)
  - 토큰 없음·서명 불일치·만료 → **401**

### DOMAIN-013 (포털) — `klid-d013-implementer`

- **대상 파일·심볼**: `portal/` 하위 신설 — 컨트롤러 1 · 서비스 1 · 엔티티 1 · 리포지토리 1 · 요청 DTO 1
- **변경**: `POST /v1/portal-system/dataset-cleanups` (operationId `receivePortalDatasetCleanupTrigger`)
  - 요청 본문: `{ datasetCode: string(minLength 1), version: string(minLength 1) }` — **둘 다 required**
  - 인증 헤더: `x-access-token` (**Bearer 스킴 미사용**, 별도 API 키 헤더 미사용)
  - 동작: 접수 원장에 `(DATST_CD, VER_NO, RCPTN_DT=now)` 를 기록하고 **202** 로 답한다.
  - 응답: **202** 접수 / **400** 검증 실패 / **401** 인증 실패 / **403** 주체 축 불일치
- **불변 — 설계가 못박은 것(뒤집지 말 것)**:
  1. **받은 즉시 지우지 않는다.** 수신 시점부터 **7일 유예** 뒤 삭제한다. 사용자가 해제본을 물고 저작 중이면 그 작업이 그 자리에서 깨진다. ⚠ *"불필요한 지연"* 으로 보고 없애지 말 것.
  2. **보존 규칙의 정본은 `DFEAT-055`** 다. 이 창구는 **그 규칙을 깨우는 입구일 뿐**이며, 보존 기간·기산점·정리 절차를 **이 창구에 복제하지 않는다.**
  3. **재수신은 성공 무처리이고 기산점을 갱신하지 않는다.** 갱신하면 중복 수신이 반복될 때마다 삭제가 무한히 미뤄져 정리가 영영 일어나지 않는다. 기준은 **처음 받은 시각**이다.
  4. **알지 못하는 데이터셋 코드·버전도 같은 202 로 답한다.** 대상 유무를 응답으로 드러내지 않는다 — 드러내면 존재 여부를 탐색하는 수단이 되고, 오류로 답하면 포털이 지울 것도 없는 신호를 계속 재전송한다.
  5. **거부 응답에 내부 경로·예외 흔적·저장 구조를 싣지 않는다.**
  6. **연동의 인증 축·창구 구성·어휘는 `INT-014` 가 소유한다** — 이 창구 코드·주석에 그 계약을 복제하지 않는다.
- **주의**:
  - ⚠ **이번 산출물은 "받아서 기록만 한다"가 정상이다.** 삭제 실행을 지어내지 말 것 — 지울 해제본 저장소·원장이 코드에 0건이다.
  - ⚠ **식별자만 받아 지우는 창구를 두지 않는다.** 이번엔 삭제 실행이 없지만 원장·후속 배선이 그 방향을 열어 두면 안 된다. 삭제가 붙을 때 판정 조건은 **후보 조회가 아니라 최종 삭제 실행문 자체**에 건다(파생영상 폐기에서 세운 원칙과 같은 축).
  - ⚠ 로그에 토큰·헤더 값을 남기지 않는다(`LogMaskingPatterns` 가 `x-access-token` 을 이미 마스킹 대상으로 갖고 있다).
- **수용기준**:
  - 정상 요청 → 202, 원장 1행, `RCPTN_DT` 기록
  - **같은 `(datasetCode, version)` 재수신 → 202 이고 `RCPTN_DT` 가 첫 수신 값 그대로**
  - `datasetCode` 누락·빈 문자열 → 400
  - `version` 누락·빈 문자열 → 400
  - 알지 못하는 데이터셋 → **202**(404 가 아니다)
  - 응답 본문에 내부 경로·스택·테이블명이 없다

### 범위 밖 — 착수하지 말 것

- **신규 데이터마트 조달**(포털 소재 조회 창구 pull · 압축 해제 · 적재) — 그 창구는 **포털 소유이며 응답 스키마가 아직 회신되지 않았다.** 추정으로 만들면 두 번째 진실원이 된다.
- **실제 해제본 삭제 실행** — 조달 축이 생긴 뒤에 붙인다.
- **프론트 변경 없음** — 서버간 창구이며 화면이 없다.

## §4 영향·리스크

- **하위호환**:
  - 신규 경로 접두라 기존 호출자 영향 0.
  - ⚠ **`JwtAuthenticationFilter` 는 전 채널 공용이다.** 포털 사용자 토큰·관제 인계 토큰의 동작이 바뀌면 회귀 범위가 인증 전체다. allowlist 미설정이 **기존 동작과 동일**해야 한다.
  - 관제 계약면(`V_COMPLETED_*` 뷰 · 통지 페이로드) **무관**.
- **되돌리기**: 창구·인가 매처 제거 + `V36` 은 표 추가라 되돌릴 때 DROP 마이그레이션 분리(되돌릴 수 없는 작업을 한 묶음에 넣지 않는 이 레포 원칙).
- **리스크**:
  1. **역방향 격리를 빠뜨리면** 시스템 계정 토큰이 포털 사용자 창구 전부를 연다 — 이 CO 의 최대 리스크.
  2. **인가 매처 순서**를 틀리면 격리가 조용히 무력해진다.
  3. **재수신 기산점 갱신**을 실수로 넣으면 정리가 영영 일어나지 않는다(증상이 조용하다 — 아무 오류도 나지 않는다).
  4. **실동작은 서명키 값 교환 전까지 성립하지 않는다.** 구현은 막히지 않으나 배포 시점에 값이 필요하다.

  가능성이 높으나 확인한 것은 아니다)
- 삭제 입구 0건·유예 상수 0건 판정은 **신규 파일 안만** 본 결과다(다른 곳에서 `EntityManager` 로
  네이티브 DELETE 를 쓰는 경로는 이 검사가 못 본다 — 현재 그런 코드는 없다)

### 남은 후속

- 해제본 저장소가 서면 **삭제 실행 축**이 별건으로 필요하다
- 포털 소재 조회 창구 스키마가 회신되면 **조달(pull·압축 해제·적재) 축**
- 운영 런북에 **시스템 계정 식별자 등록 절차**. ⚠ 그때 `PortalDatasetCleanupTriggerClosedByDefaultTest`
  의 전제(등록 0건)가 깨진다 — 시험을 지우지 말고 빈 목록을 명시 주입해 조건을 되살릴 것
