## §1 배경

사용자 원문: *"작업자가 영상 처리 현황을 알 필요가 있나 싶네."*

### 현재 상태 (실측)

좌측 메뉴 「영상」 그룹의 **「영상 처리 현황」** 항목이 검수자·작업자 **양쪽에 열려 있고**, 그 화면과 하위 영상 상세 화면의 라우트 가드도 양쪽을 허용한다.

그 안에 있는 것:

| 화면 | 내용 |
|---|---|
| 영상 처리 현황(목록) | 영상별 배치 단계·실패·건너뜀 상태, 상태 필터, **여러 건 일괄 재시도** |
| 영상 상세 | 배치 단계 진행 표시기, **배치 실패 조치 패널 — 재시도 · 건너뛰기 · 재수행 버튼**, 비식별 이력 |

### ⚠ 근거 정정 (2026-08-27 — 착수 중 실측으로 뒤집힌 것)

착수 시 「작업자에게 재시도·건너뛰기·재수행 버튼이 노출된다」를 근거로 잡았으나 **사실이 아니다.**

- **배치 실패 조치는 이미 검수자 전용이다** — 영상 상세가 그 패널을 검수자일 때만 렌더하고, 화면 사양(SCREEN-009)도 「배치 실패 사유 + 조치 (REVIEWER 전용)」로 이미 그렇게 규정한다.
- **영상 목록도 이미 작업자용으로 갈라져 있다** — 사양(SCREEN-008)이 *"REVIEWER 는 전체 영상을, WORKER 는 본인에게 배정된 영상만 조회"* 라고 규정하며, 일괄 작업 바·행 선택·배정 동선은 전부 검수자 전용이다.

⇒ **작업자에게 실제로 남아 있던 것은 「본인 배정 영상의 배치 처리 단계 확인」 하나**다. 그것을 닫을지가 이번 결정의 실체이며, 사용자가 이 정정된 사실을 확인한 뒤 **그래도 닫는 쪽**을 택했다.

### 작업량이 작다는 근거 (전수 확인)

| 확인 항목 | 결과 |
|---|---|
| 이 메뉴로 들어가는 앱 내 링크 | 좌측 메뉴 1곳 + 영상 상세의 breadcrumb + 개발용 화면 1곳 |
| 영상 상세로 가는 앱 내 링크 | **영상 처리 현황 목록 자기 안(2곳)뿐** |
| 작업 목록·라벨링·검수에서 이 화면으로 가는 경로 | **0건** |
| 메뉴 그룹이 통째로 사라지는 처리 | **이미 있음** — 그룹의 보이는 항목이 0개면 그룹 헤더까지 사라진다(「업로드」 그룹이 같은 방식으로 작업자에게 안 보인다) |

⇒ 작업자가 이 화면에 도달하는 **정상 동선이 앱 안에 없다.** 메뉴를 통해서만 들어간다.

## §2 변경 요지

「영상 처리 현황」 메뉴 항목과 그 화면·영상 상세 화면의 접근 권한을 **검수자 전용**으로 좁힌다. 작업자에게는 「영상」 그룹이 통째로 보이지 않고, 주소를 직접 입력해도 들어가지 못한다.

⚠ **메뉴만 감추는 것이 아니라 라우트 가드도 함께 좁힌다** — 한쪽만 바꾸면 「메뉴는 없는데 주소로는 들어가진다」(또는 그 반대)가 된다. 이 규약은 메뉴 정의 파일 주석이 이미 명시하고 있다.

## §3 도메인별 변경 상세

### 프론트 (NAV-001 · SCREEN-008 · SCREEN-009) — `klid-web-implementer`

  - `frontend/src/router/index.tsx` — `video/status` · `video/:id` 두 라우트의 가드

- **소비 API 계약**: 변경 없음

- **변경**
  1. 메뉴 항목의 허용 역할을 **검수자만**으로 좁힌다.
  2. 두 라우트의 가드를 **검수자 전용**으로 바꾼다(이 파일이 이미 쓰고 있는 검수자 전용 상수를 그대로 쓴다 — 새 상수를 만들지 않는다).
  3. 「영상」 그룹의 유일한 항목이 검수자 전용이 되므로, 작업자에게 **그룹 헤더까지 사라지는지** 확인한다(이미 있는 처리라 코드 변경은 필요 없어야 한다 — 동작만 확인).

- **불변**
  - **메뉴 그룹의 순서를 바꾸지 않는다** — 그룹 순서는 사양이 정하며 회귀 가드가 물고 있다.
  - 영상 처리 현황 화면·영상 상세 화면의 **내용을 바꾸지 않는다.** 이번 변경은 접근 권한 축만이다.
  - 개발용 화면에서 이 목록으로 가는 링크는 그 화면 자체가 검수자 전용이므로 **그대로 둔다**.
  - 검수자의 동선은 **완전히 그대로**다.

- **주의**
  - ⚠ **메뉴와 라우트 가드를 반드시 같은 값으로** 맞춘다. 갈리면 위 §2 의 어긋남이 난다.
  - ⚠ 작업자로 로그인한 상태에서 그 주소를 직접 열었을 때 **어떤 화면이 뜨는지**(접근 거부 안내인지 빈 화면인지) 확인하고, 기존 검수자 전용 화면들과 **같은 처리**인지 대조한다.
  - ⚠ 작업자 계정으로 진행 중이던 세션이 그 화면에 머물러 있을 수 있다 — 라우트 가드가 그 경우도 막는지 확인한다.

- **수용기준**
  - 작업자에게 좌측 메뉴의 **「영상」 그룹 전체가 보이지 않는다**(헤더 포함).
  - 작업자가 영상 처리 현황·영상 상세 주소를 직접 입력하면 **다른 검수자 전용 화면과 같은 방식으로 거부**된다.
  - 검수자의 메뉴·화면·동선은 **변경 전과 완전히 동일**하다.
  - 메뉴 그룹 순서가 변경 전과 동일하다.

## §4 영향·리스크

- **하위호환**: 서버 계약·저장 데이터 변경 0. 화면 접근 권한만 좁힌다.
- **되돌리기**: 허용 역할 값 3곳을 되돌리면 원상복구.
- **리스크**
  - **작업자가 본인 배정 영상의 배치 처리 단계를 확인하던 경로가 사라진다.** 작업 목록에 상태 표시가 있어 완전한 단절은 아니지만, 「내 영상이 아직 준비 중」을 이 화면에서 보던 동선은 없어진다. **사용자가 정정된 사실을 확인한 뒤 이 대가를 알고 선택했다.**
  - **작업자용 조회 스코핑 구현이 도달 불가 코드가 된다** — 목록을 본인 배정분으로 좁히는 경로가 살아 있으나 작업자가 그 화면에 못 들어가므로 실행되지 않는다. **지우지 않는다**(권한을 되돌리면 다시 필요하고, 서버 측 스코핑은 권한 축과 무관하게 유효하다). 그 사실을 코드 주석이 아니라 이 변경지시서에 남긴다.
  - 메뉴 그룹 순서 회귀 가드가 검수자 기준이라 이번 변경에 영향받지 않는 것으로 보이나, **실제로 통과하는지 확인**한다.

## §5 검증

- **자동**
  - 작업자 역할에서 좌측 메뉴에 「영상」 그룹이 **렌더되지 않음**을 단언(「업로드」 그룹의 기존 가드와 같은 형태).
  - 검수자 역할에서는 **그대로 렌더됨**을 단언.
  - 메뉴 그룹 순서 회귀 단언(기존 가드).
  - 라우트 가드 단언 — 작업자로 두 주소 진입 시 거부.
- **변이 실증**: 허용 역할을 다시 양쪽으로 되돌렸을 때, 메뉴만 좁히고 라우트를 안 좁혔을 때 각각 RED 가 되는지 확인한다.
- **수동 시나리오**: 작업자 계정으로 로그인 → 좌측 메뉴에 「영상」 없음 확인 → 주소 직접 입력 → 거부 확인. 검수자 계정으로 전환 → 전부 정상 확인.
- **카탈로그**: `docs/test-cases/` 의 메뉴·권한 관련 케이스를 갱신한다.

### 확정 과정에서 뒤집히거나 확인된 것

- **「영상」 그룹 노드 자체에는 역할을 걸지 않았다 — 걸면 안 된다.** 그 그룹에 마킹 노드(`/marking/:rawSn`)가 함께 있고 **역할 제한이 없다**(마킹은 작업자의 일이다). 그룹에 걸었다면 **작업자의 마킹 진입이 막혔다.** 유일 항목이 검수자 전용이면 기존 「보이는 항목이 없으면 그룹째 감춘다」 규칙이 처리한다.
- **`API-042`(영상 목록 창구)의 작업자 스코핑은 유지**한다. 화면이 아니라 **서버측 IDOR 방어**라 화면 폐쇄와 독립이고, 다른 활성 소비 화면(대시보드·증강 요청)이 있으며, 시험 카탈로그가 그 축을 검증 중이다. **걷어내면 직접 호출 IDOR 이 다시 열린다.**
- **`AC-016` 은 무변경**이다. 두 검증자가 독립적으로 본문을 대조해 *"when 절에 행위자가 없고 작업자 조건은 신고 경로 given 에 한정돼 정면 모순이 아니다"* 로 일치했다.
- **`ROLE-001` 의 작업 목록 권한(*"전체 기준으로 조회"*)은 그대로 둔다** — 그쪽은 대비항(작업자의 본인 배정분 한정)이 **아직 살아 있어** 한정구가 여전히 뜻을 갖는다. *"같은 표현이니 함께 정리"* 로 지우지 말 것.

### ⚠ 인지하고 남긴 것 — 다시 논의하지 말 것

**`ROLE-002` 의 두 화면 권한을 `[폐기]` 표기로 남겼다(원소째 제거하지 않음, 사용자 확정).** 그 대가로 **`granted_on` 그래프 간선이 그대로 남아** 두 화면의 접근 역할 선언과 어긋난다 — 표기로는 간선이 끊기지 않기 때문이다(실측 확인). 즉 **그래프만 훑는 감사는 이것을 모순으로 잡는다.** 그건 결함이 아니라 **감사 흔적을 원소에 남기기로 한 선택의 알려진 대가**다. 되돌리려면 원소째 제거가 유일한 수단이며, 그때는 폐기 사유가 `change_summary` 에만 남는다.

### 미해결 (별도 축 — 이번 범위 밖)

- **`UC-016.related_screens` 에 SCREEN-008 이 없다** — 본문은 인용하는데 링크가 없어 SCREEN-008 확정이 **전파 신호를 한 번도 만들지 못했다.** 이번 정정은 사람이 지목해 잡힌 것이지 cascade 가 잡아준 것이 아니다. 같은 형태(*본문은 인용하는데 링크는 없음*)가 다른 유스케이스에도 있는지 전수 스캔 권고.
- **폐기 화면 참조 잔재** — 12개 남짓한 컴포넌트가 `referenced_by_screen_ids` 에 폐기된 영상 목록 화면을 들고 있다. 그 필드는 **그래프 링크를 만들지 않아** 자동 추적이 되지 않는다. 별도 정리 라운드 대상.
- **`ROLE-001` 의 검수 상세 권한 원소** — 그 축의 `stale` 표식이 이번 쓰기로 함께 해제됐다. 현행 검수 상세 사양과 여전히 맞는지 별도 재확인 필요.
