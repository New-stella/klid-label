## §1 배경

사용자 지적: *"포털쪽은 전반적으로 SD 디자인을 제대로 안 입힌것 같아."*

조사 결과 **화면별 손질 문제가 아니라 채널 디자인 시스템이 통째로 미도입**이었다.

### 무엇이 없나

포털 시안은 **2026-09-02 에 `DS-001`(관제 축) → `DS-002`(포털 채널 전용)로 전환**됐다. 시안 CSS 머리말이 여덟 축을 명시한다.

| 축 | 관제(DS-001) | 포털(DS-002) |
|---|---|---|
| 주색 | `#256EF4` | **`#2E45DC` 코발트** · hover `#2336B8` |
| 중립 | KRDS gray `#6D7882` 계열(웜) | **slate `#64748B` 계열(쿨)** |
| 본문 기준 | 17px | **15px** |
| 굵기 상한 | 800 | **600** (위계는 크기와 색으로) |
| 모서리 | 4 / 6 / 8 | **태그 6 · 입력·페이저 8 · 타일 12 · 표면 16 · 패널 24 · 명령(버튼) 캡슐** |
| 그림자 | 카드에 `sm` | **기본 없음**(평면이 출발점) |
| 표 헤더 | 굵기로 죽임 | **색으로 죽임**(14/500 + slate-500) |
| 자간 | 0 | **-0.5px**(본문에 한 번) |

**그런데 FE 에 그 토큰 레이어가 없다** — `frontend/` 전역에 `2e45dc`·`DS-002` **각 0건**이고 `tailwind.config.js` 는 전량 DS-001(KRDS)이다(`#256EF4`).

⇒ **포털 화면 전부가 관제 축 토큰 위에 서 있다.**

### ★설계 층에는 이미 있다 — 구현만 못 따라갔다

`DS-002`(`design_system`, v1)가 2026-09-02 에 등재돼 있고 그 사유가 정확히 이 문제다:

> *"포털 채널 산출물은 주색만이 아니라 형태·타이포·간격·그림자·컨트롤 높이까지 이 시스템을 따르는데, **값이 우리 안에 없어 화면을 그릴 때마다 상대 산출물에서 캐내야 했고 실제로 어긋남이 났다**(이동 탭 규격 네 가지·시안 전체의 시스템 축)."*

⚠ **`DS-002` 는 상대(포털 Host) 정의 v9 의 참조 사본이다.** ITEM 본문이 못박는다 — *"★이것은 사본이며 **값을 우리가 고치지 않는다** — 고치면 두 번째 진실원이 된다."*

### 판정 근거 — 두 담당이 독립으로 수렴

`SCREEN-033`·`SCREEN-028` 대조를 서로 모르는 두 담당에게 맡겼는데, **둘 다 독립적으로 이 결론에 도달**했다. 그리고 **둘 다 오케스트레이터가 준 전제를 깨고 보고했다.**

⚠ **오케스트레이터가 잘못된 전제를 줬다** — *"tailwind 팔레트가 시안 CSS 변수와 1:1 동일하니 새 hex 는 불필요"*. 그건 `SCREEN-009`(관제·DS-001) 선례에서 온 것이고 **포털에서는 거짓**이다. 시안 CSS 머리말이 바로 그 함정을 경고하고 있었다:

> *"⚠ 토큰 이름이 관제 축과 같고 값만 다르다 — **이름으로 같은 색이라고 판단하면 조용히 다른 색이 뜬다.** 두 축의 값을 섞지 않는다."*

**앞으로 포털 화면을 대조·구현할 때 이 전제를 다시 주지 말 것.**

## §5 검증

1. **관제 채널 값 무변경** — `designTokens.test.ts` 통과 + 관제 화면 회귀.
2. **포털 화면이 DS-002 값을 쓴다** — 주색·중립·본문 크기·굵기·반경·그림자.
3. **`tableSurfaceConvention` 가드가 두 축을 각각 검사한다** — 포털은 DS-002 규격으로, 관제는 DS-001 규격으로. **어느 쪽도 무검사가 되지 않는다.**
4. **raw hex 가 컴포넌트에 박히지 않았다.**
5. 위 §3-D 내용 결함 7건이 실제로 해소됐다.
6. **BE·FE 전체 회귀** 무열화.
- ★**변이 검증**: 가드의 채널 축을 지우면 RED 가 되는지 · 포털 토큰을 관제 값으로 되돌리면 RED 가 되는지.
- ★**시험이 통과하는 시점·상태가 결함이 드러나는 시점·상태와 같은지 확인하라** (2026-09-08 정리 — 넷 다 실측에서 나왔다):

  | 함정 | 시험이 놓치는 것 |
  |---|---|
  | 비동기를 동기로 읽음 | 효과가 반영되기 **전에** 읽는다 |
  | 진입 순서 미재현 | 실사용이 지나는 **전이**를 안 지난다 |
  | 왕복 후 상태 미확인 | 깨지는 **시점 이후**를 안 본다 |
  | **해제만 단언** | **걸리는 쪽을 안 본다 — 애초에 안 걸려도 통과한다** |

  ⚠ 넷째가 이 CO 에 직접 온다 — 가드의 채널 축을 시험할 때 **「포털이 DS-002 로 검사된다」만 단언하면
  관제 축이 통째로 빠져도 통과**한다. **두 축이 각각 걸리는 것**을 둘 다 봐야 한다.

- **브라우저 실렌더 대조는 이 라운드에서 하지 않는다** — 정적 대조로 잡히는 것을 먼저 닫고, 남는 축(실데이터 밀도·오버플로)은 잔여로 명시한다.

끝내 켜지지 않았다.** 같은 종류의 상류 변경이 앞 라운드에서는 켰으므로 **이 전파는 항상 도는 것이
아니다.** 표식이 꺼진 채 사양과 정면으로 어긋나 있는 산출물이 실재했다.

⇒ **시안·미러·사본 층의 정합 판정은 표식이 아니라 본문 직접 대조로 한다.**
특히 `DS-002` 는 **상대(포털 Host) 정의 v9 의 사본**이라, 상대가 v10 으로 갔어도 우리 표식은
움직이지 않는다. 착수 시 **상대 정의의 현재 판본을 확인**하고, 우리 사본이 뒤처졌으면 그 사실을
보고하라(사본 갱신은 이 CO 범위 밖이며 별도 판단이다).

⚠ 반대로 **표식이 켜져 있다고 이번 축과 관련 있는 것도 아니다** — `stale_reason` 은 축 하나만
보여 준다(`SD-024`·`SD-026` 의 사유는 `UC-024` 대안 흐름 전파였고 시각 축과 무관했다).

### ★DS-002 ITEM 에서 나온 것 — 상대에 제기할 대상

ITEM `dont_rules` 가 *"우리가 이 사본의 값을 고치지 않는다 — 정본은 외부 채널의 정의다. **고칠 것이 있으면 상대에 제기하고**, 반영되면 다시 옮겨 온다"* 고 하므로 **고치지 않고 남긴다.**
