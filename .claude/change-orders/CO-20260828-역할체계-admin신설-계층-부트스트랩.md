## §1 배경

### 열쇠가 하나다

사용자 지적(2026-08-28): *"어차피 동일한거 아냐? 어차피 검수자 화면에 관리자 메뉴가 상시 노출이 되고 있는거잖아."*

실측으로 확인됐다. **역할 자가부여와 관리자 유효창이 같은 패스워드를 쓴다** — 둘 다 같은
`AdminPasswordVerifier` 를 주입받고, `RoleClaimRateLimiter` javadoc 이 *"공유는 의도다. 두 진입점이
같은 관리자 패스워드를 …"* 로 명시한다. 그래서 실제 경로는 이렇다.

```
관제 JWT 보유  →  [패스워드]  →  검수자 획득(role-claim)
                                   ↓  (검수자 화면에 관리자 메뉴 상시 노출)
                              →  [같은 패스워드]  →  관리자 유효창  →  관리 기능 전부
```

**비밀 하나로 끝까지 간다.** 「역할 획득」과 「관리자 진입」은 코드 경로가 다를 뿐, 열쇠가 같아서
공격자 관점에선 한 구멍이다.

### 그리고 등록 경로가 자가부여 하나뿐이다

`RoleClaimService.claim()` 이 패스워드를 통과시킨 뒤 `upsertUser`(사용자 행 생성)와
`upsertRole`(역할 부여)을 **연달아** 한다. 즉 **본인이 자기 행을 만들고 자기 역할을 고른다.**
사용자 행이 생기는 다른 경로가 없어서, 이 창구를 좁히거나 없앨 수도 없었다.

부작용도 있다 — **배정하려면 그 사람이 먼저 자가부여를 해야 목록에 뜬다.**

## §2 변경 요지

1. **`Role` enum 에 `ADMIN` 신설** (ADMIN·REVIEWER·WORKER·PORTAL_USER 4종).
2. **계층 `ROLE_ADMIN > ROLE_REVIEWER`** — 관리자가 검수 권한을 물려받는다(겸직 불필요).
3. **자가부여를 관리자 부트스트랩 전용으로 축소** — `ADMIN 이 0명일 때만` 열리고 부여 역할은 `ADMIN` 고정.
4. **그 외 진입자는 `WORKER` 로 자동 등록** — JWT 검증 통과 시점에 사용자 행 + 역할을 만든다.
5. **역할 부여는 관리자가 사용자 관리 화면에서** ADMIN/REVIEWER/WORKER 로 지정.
6. **마지막 ADMIN 의 강등·비활성 차단** — 부트스트랩 창이 다시 열리지 않게.
7. **관리자 메뉴를 역할로 가른다** — 검수자에게는 관리자 항목이 좌측 메뉴에 아예 보이지 않는다.
8. **「산출물 가져오기」를 관리자 소속으로** 옮기고 쓰기 창구를 관리자 전용으로 (보류 CO 승계).

## §2.5 ★이것은 확정 정책의 정면 반전이다

**2026-08-27 확정(B안)을 폐기한다** — *"ADMIN 역할을 만들지 않고, 관리자 페이지를 별도 주소로 빼고
진입에 관리자 패스워드를 요구한다. 역할 체계는 손대지 않는다."*

당시 A안(ADMIN 역할 신설)을 기각한 사유가 **둘 있었는데, 몰랐던 사실 두 개로 무효화됐다.**

| 당시 기각 사유 | 무효가 된 근거 |
|---|---|
| **겸직 불가** — `LS_USER_ROLE` PK 가 `USER_NO` 단일(=관제 사용자번호)이라 한 사람이 관리자와 검수자를 겸할 수 없고, 계정 2개를 관제에 요청해야 한다 | `common/security/RoleHierarchy` 빈이 **이미 존재하는데 값이 비어 있다**(`RoleHierarchyImpl.fromHierarchy("")`). 한 줄을 채우면 관리자가 검수 권한을 물려받아 **겸직이라는 개념 자체가 불필요**해진다. 당시 실측 목록에 이 빈이 없었다 |
| **부트스트랩 락아웃** — 사용자 관리가 관리자 전용이면 관리자를 만들 사람이 관리자뿐이고, 자가부여로 풀면 *"패스워드를 아는 사람이 관리자"* 가 되어 A안의 우위가 반감된다 | 자가부여를 **「관리자가 0명일 때만」** 으로 조건화하면 그 창이 **최초 1회로 닫힌다.** 관리자가 생긴 뒤에는 패스워드를 알아도 아무것도 할 수 없다 |

⚠ **여전히 유효해서 되짚지 말아야 할 것**: 관리자 세션 토큰이 `actor.sub()` 에 바인딩되어
**공유 패스워드인데도 감사 기록이 개인 단위로 남는다.** *"공유 패스워드는 추적이 안 된다"* 를
근거로 쓰지 말 것. 패스워드는 이번 변경 뒤에도 **부트스트랩 1회 + 관리자 유효창** 용도로 남는다.

⚠ **검토했으나 기각된 안 — 사용자 명부(사전 등록)**: 관리자가 이름·이메일을 미리 등록해 두고
접속 시 잇는 방식. **매칭 키가 없어서** 성립하지 않는다 — 이메일이 JWT 클레임에 없고(서명돼 오는 것은
`sub`·`role`·`channel`·`exp`·`name` 뿐), 이름은 유일성 제약이 없으며, 계정(`userId`)은 **요청 바디로
오는 위조 가능한 표시 정보**다(`RoleClaimRequest` javadoc 이 CWE-639 로 명시 기각). 게다가 §2-4
(자동 등록)가 그 문제를 통째로 없앤다 — 접속하면 행이 저절로 생기므로 미리 만들 이유가 없다.
사용자 평: *"명부설정도 그다지 필요가 없고 일만 늘리는 것 같은데."* **되살리지 말 것.**

## §3 도메인별 변경 상세

### 3-A. 공유기반 (`common/security/`) — ★메인 선처리 (Phase 3.5)

도메인 소속이 아니다. 도메인 fan-out 전에 메인이 먼저 처리한다.

- **대상 파일·심볼**
  - `common/security/Role.java` — enum
  - `common/security/RoleHierarchy.java` — 계층 빈
  - `common/security/JwtAuthenticationFilter.java` — 자동 등록 훅 지점
  - `common/security/UserRoleResolver.java` — 역할 해석 + 캐시
  - `common/security/SecurityConfig.java` — 관리 경로 매처
- **변경**
  1. `Role` enum 에 `ADMIN` 추가. **선언 순서는 맨 앞**(ADMIN·REVIEWER·WORKER·PORTAL_USER).
  2. `RoleHierarchy` 의 빈 문자열을 **`ROLE_ADMIN > ROLE_REVIEWER`** 로 채운다.
  3. **자동 작업자 등록** — INTERNAL 채널이고 역할 해석이 `null` 이면 사용자 행 + `WORKER` 역할을
     만든다. 위치는 `JwtAuthenticationFilter` 의 역할 해석 직후(`lastLoginRecorder.record(userNo)`
     바로 옆)가 자연스럽다. 실제 쓰기는 DOMAIN-001 이 제공하는 원자 upsert 를 호출만 한다.
  4. 자동 등록 성공 시 **`userRoleResolver.evict(userNo)`** 로 캐시를 비우고 그 요청부터 역할이 잡히게 한다.
- **불변**
  - ★**`PORTAL_USER` 를 계층에 넣지 않는다.** 채널이 다르고 `SecurityConfig` 가 채널 격리를 강제한다.
    계층에 끼우면 포털 사용자가 내부 권한을 얻는다.
  - ★**`WORKER` 를 계층 아래에 넣지 않는다.** `hasRole('WORKER')` 로 **작업자에게만** 열린 자리가 있고
    (`hasRole('WORKER')` 2곳), 계층에 넣으면 관리자·검수자가 그 자리에 흘러든다. 이번 계층은
    **`ADMIN > REVIEWER` 한 단계뿐**이다.
  - ★**자동 등록이 매 요청 쓰기가 되면 안 된다.** `UserRepository.touchLastLogin` 처럼
    **조건부·원자 upsert** 여야 한다(2노드 Active-Active 에서 조회 후 INSERT 는 PK 위반으로 트랜잭션이
    깨진다 — `LsAcntUser` javadoc 이 이미 그 이유로 upsert 를 강제한다).
  - ★**자동 등록 실패가 요청을 죽이면 안 된다** — `lastLoginRecorder` 와 같은 fail-open. 다만
    역할이 안 잡히므로 그 요청은 무권한으로 흐른다(fail-closed 인가는 그대로).
  - `UserRoleResolver.resolve` 는 **`unless = "#result == null"`** 이라 null 을 캐시하지 않는다 —
    자동 등록 뒤 재조회가 곧바로 새 역할을 잡는다. **이 옵션을 지우면** 무권한이 캐시되어 그 사용자가
    고착하므로 건드리지 말 것.
  - `ROLE_CD` 는 `VARCHAR(32)` 라 **DDL 변경이 없다**(마이그레이션 불필요).
  - `SecurityConfig` 의 기존 `hasRole(Role.REVIEWER.name())` 매처는 **계층 덕분에 손대지 않는다.**
    관리자 전용으로 올릴 경로만 골라 `ADMIN` 으로 바꾼다.
- **수용기준**
  - 관리자 토큰으로 검수자 전용 API(`hasRole('REVIEWER')`)가 **200**.
  - 포털 토큰으로 내부 API 는 여전히 **403**.
  - 관리자 토큰으로 `hasRole('WORKER')` 전용 자리는 여전히 **403**(계층이 한 단계뿐임을 고정).
  - 역할 미보유 INTERNAL 사용자가 아무 API 나 호출하면 그 시점에 `WORKER` 로 등록되고,
    **같은 요청 또는 다음 요청부터** 작업자 권한이 잡힌다.
  - 자동 등록이 **매 요청마다 UPDATE 를 만들지 않는다**(같은 사용자 연속 호출 시 쓰기 1회).

### 3-B. DOMAIN-001 (사용자·권한) — `auth/` `user/`

- **대상 파일·심볼**
  - `auth/service/RoleClaimService` — `claim()` · `allowedClaimRoles()`
  - `auth/dto/RoleClaimRequest` · `RoleClaimResponse`
  - `user/service/UserService` — `updateUser()`
  - `user/dto/UserUpdateRequest` — `@Pattern` 화이트리스트
  - `user/repository/UserRepository` · `LsUserRoleRepository` — 자동 등록용 원자 upsert
  - `user/entity/LsAcntUser`
- **변경**
  1. **자가부여를 부트스트랩 전용으로 축소** — `claim()` 진입에 **「ADMIN 이 0명인가」** 게이트를 세운다.
     1명이라도 있으면 **409**(또는 403) 로 거절하고 *"이미 관리자가 있어 자가부여가 닫혀 있습니다.
     관리자에게 역할 부여를 요청하세요."* 안내.
  2. `allowedClaimRoles()` 를 **`List.of(Role.ADMIN)`** 으로 축소. 요청 바디의 `role` 은 더 이상
     선택지가 아니다 — **ADMIN 고정**으로 부여한다.
  3. `UserUpdateRequest` 의 `@Pattern` 에 **`ADMIN` 추가** (`^(ADMIN|REVIEWER|WORKER|PORTAL_USER)$`).
  4. **마지막 관리자 보호** — `updateUser()` 가 ADMIN → 다른 역할로 바꾸려 할 때 **그 사람이 마지막
     ADMIN 이면 거절**(409). 활성/비활성 토글이 있으면 같은 판정을 건다.
  5. 자동 등록용 **원자 upsert 제공** — 사용자 행과 `WORKER` 역할을 한 번에 만드는 경로.
     기존 `upsertUser` + `LsUserRoleRepository.upsertRole` 조합을 재사용하되 **역할이 이미 있으면
     덮어쓰지 않는다**(관리자가 지정한 역할이 자동 등록에 되돌려지면 안 된다).
- **불변**
  - ★**`RoleClaimRequest` 에 `userNo` 를 두지 않는다** — 사용자 식별은 JWT subject 에서만(CWE-915/639).
    이번 변경이 이 규칙을 건드리지 않는다.
  - ★**`allowedClaimRoles()` 의 화이트리스트 구조 자체는 유지한다** — `Role` enum 이 늘 때 새 역할이
    자동으로 자가부여 대상이 되면 안 된다(deny-by-default). 값만 좁힌다.
  - ★**마지막 ADMIN 판정은 조회 후 UPDATE 로 하면 안 된다** — 2노드에서 둘이 동시에 서로를 강등하면
     둘 다 통과해 ADMIN 0명이 된다. **조건부 UPDATE 또는 잠금**으로 원자적으로 판정한다.
  - 관리자 패스워드는 **사라지지 않는다** — 부트스트랩과 관리자 유효창에 계속 쓰인다.
  - `PORTAL_USER` 는 자가부여 대상이 아니다(기존 거절 유지).
- **수용기준**
  - ADMIN 0명 상태에서 자가부여 → **ADMIN 으로 부여**되고 성공.
  - ADMIN 1명 이상 상태에서 자가부여 → **거절**(안내 문구 포함). 패스워드가 맞아도 거절.
  - 요청 바디에 `role: REVIEWER` 를 실어도 **ADMIN 으로 부여**되거나 거절된다 — 요청 값이 결과를
    바꾸지 못한다.
  - 관리자가 다른 사용자를 ADMIN 으로 지정 → 성공.
  - 마지막 ADMIN 을 REVIEWER 로 강등 → **409**.
  - 관리자가 2명일 때 1명 강등 → 성공.

  2. **「관리자」 그룹 5개 항목의 `allow` 를 `['ADMIN']` 으로.** 검수자에게 안 보인다.
  3. 라우트에 **`internalAdminOnly = [Role.ADMIN]`** 을 신설해 관리자 화면에 건다.
  4. 「산출물 가져오기」를 `/manage/imports` → **`/admin/imports`** 로 옮기고 「관리자」 그룹으로.
     구 주소는 새 주소로 보낸다(북마크 보존). 「업로드」 그룹은 항목이 비어 사라진다.
  5. 사용자 관리 화면의 역할 선택지에 **「관리자」 추가**. 마지막 관리자 강등 시도의 **409 를 사용자
     문구로** 보여준다.
  6. `Lnb.tsx` 의 주석 *"★유효창을 메뉴 노출 조건으로 쓰지 않는다"* 를 **갱신**한다 — 그 제약은
     ADMIN 역할이 없어서 생긴 것이고, 이번에 사라진다. 다만 **유효창을 노출 조건으로 쓰지 말라는
     결론 자체는 유지**된다(가르는 축이 역할로 바뀔 뿐).
- **불변**
  - ★**`allow` 는 라우트 가드와 같은 조건이어야 한다** — 갈리면 「메뉴는 없는데 주소로는 들어가진다」.
  - ★**진입 화면(`/admin`)에 `AdminSessionGuard` 를 걸지 않는다** — 자기 자신으로 무한히 되돌아간다.
  - **역할 가드가 바깥, 유효창이 안쪽** 순서는 유지. 뒤집으면 「패스워드를 아는 사람이 관리자」가 된다.
  - 파일 업로드의 `isDevUploadEnabled()` 토글 판정은 그대로. 라우트와 메뉴가 **같은 판정**을 써야 한다.
- **수용기준**
  - 검수자로 로그인하면 좌측 메뉴에 **관리자 항목이 하나도 보이지 않는다**(그룹 자체가 사라진다).
  - 관리자로 로그인하면 관리자 항목이 보이고, **검수·배정 메뉴도 그대로 보인다**(계층).
  - 검수자가 `/admin/users` 를 주소로 직접 열면 접근 거부.
  - 구 주소 `/manage/imports` 가 `/admin/imports` 로 이어진다.
  - 사용자 관리에서 역할을 「관리자」로 바꿀 수 있고, 마지막 관리자 강등은 안내와 함께 거부된다.

## §4 영향·리스크

- **하위호환 — 기존 검수자는 그대로 검수자다.** 이번 변경은 기존 `LS_USER_ROLE` 행을 건드리지 않는다.
  ⚠ 그래서 **배포 직후에는 ADMIN 이 0명**이고, 그동안 관리 기능은 아무도 못 쓴다. 누군가 자가부여로
  최초 관리자를 만들어야 열린다 — **배포 런북에 이 절차를 넣어야 한다.**
- ⚠ **최초 부트스트랩 순간에는 여전히 「패스워드를 아는 사람이 관리자」다.** 1회뿐이고 관리자가
  생기는 즉시 닫히지만, **배포 직후 그 창을 누가 먼저 차지하느냐는 경쟁**이다. 운영자가 배포 직후
  곧바로 잡는 것으로 흡수한다(인지·수용).
- ⚠ **관리자를 전부 잃으면 DB 직접 수정이 유일한 복구다.** 마지막 관리자 보호가 「창이 다시 열리는
  것」을 막는 대가다. 운영 런북에 복구 SQL 을 남긴다.
- **자동 등록으로 사용자 행이 늘어난다** — 관제 계정으로 한 번이라도 들어온 사람은 전부 작업자로
  등록된다. 배정 목록이 길어지지만 **배정 전에는 아무 데이터도 볼 수 없어** 실질 위험은 없다.
  오히려 「배정하려면 그 사람이 먼저 자가부여를 해야 한다」는 운영 문제가 풀린다.
- **되돌리기**: enum·계층 한 줄·게이트라 코드는 되돌리기 쉽다. 다만 **자동 등록으로 생긴 사용자
  행과 역할은 남는다**(데이터는 되돌아가지 않는다).

`no matches found` 로 죽었고, **grep 이 실행조차 안 된 빈 출력을 「프로세스 없음」으로 읽어**
빌드를 이중 기동했다 — 이 저장소가 위양성의 원인으로 명시한 바로 그 상황이다.

발견 즉시 둘 다 종료 → 결과 디렉터리 제거 → **단일 클린 런**으로 재실행했고, 런 내내 wrapper 가
1개임을 주기 관측해 무오염을 증명했다. **위 수치는 그 단일 런의 것이다.**

⇒ 이 저장소에 이미 기록된 파일 검색 도구의 상대시각 침묵 실패와 **같은 계보**다.
**「출력이 비었다」와 「명령이 실행되지 않았다」는 셸에서 구분되지 않는다** — 부재를 근거로
파괴적·중복 행동을 하기 전에 **양성 대조**를 거쳐야 한다.

### ★★프론트엔드도 같은 구조로 막혀 있다 — 그리고 더 심하다 (2026-08-28 PM 실측)

D009 가 **범위를 넘지 않고 멈춰서 보고**한 두 건을 근거로 프론트 전수를 재봤다. 백엔드와 **같은 형태의
결함이 프론트에도 있고, 한 지점은 「버튼이 안 보인다」가 아니라 「로그인 자체가 안 된다」다.**

#### ① 로그인 차단 — HIGH, 이게 가장 심각하다

프론트 역할 상수에 **관리자가 아예 없다**(검수자·작업자·포털 회원 3종). 그런데 토큰 해석기가
**엄격한 허용목록**으로 검증하고, 실패하면 그 역할만 버리는 것이 아니라 **클레임 객체 전체를 버린다**:

```
if (hasRole && !isRole(raw.role)) return null;      // ← 전체를 null 로
function isRole(v) { return Object.values(Role).includes(v); }   // Role 에 ADMIN 없음
```

**개발용 로그인은 이미 관리자 토큰을 발급한다** — 그 요청 스키마의 허용값이 이번 CO 에서
`{ADMIN, REVIEWER, WORKER, PORTAL_USER}` 로 넓혀졌다. ⇒ **관리자 토큰을 받으면 프론트가 미인증으로
떨어뜨린다.** 화면 문제가 아니라 진입 자체가 막힌다.

#### ② 역할 동등 비교 — 프론트에도 흩어져 있다

`role === Role.REVIEWER` 계열 **21곳**(테스트 제외). 관리자에게 전부 거짓이 되어 화면 기능이 사라진다.

| 화면 | 무엇이 사라지나 |
|---|---|
| 영상 목록 · 영상 상세 · 작업 목록 · 검수 목록 · 작업자 통계 | 검수자 기능 일체 |
| 공지 목록 · 공지 상세 | 작성·수정·삭제·발행 버튼 (D009 가 지적한 2곳) |
| 배정 모달 | 검수자 변경 |
| 라벨링 · 이벤트 어노테이션 · 증강 진행 · 버전 이력 · 프리셋 관리 | 각 검수자 동선 |

⇒ **백엔드를 다 열어도 관리자는 여전히 아무것도 못 한다.** 이 축을 닫아야 CO 가 끝난다.

#### 처리 방침

1. **역할 상수에 관리자를 더한다** — ①의 로그인 차단이 여기서 풀린다. **선행 조건**이라 이것부터.
2. **계층 판정을 프론트에도 한 곳에 두고** 21곳을 그리로 옮긴다. ⚠ 프론트는 백엔드의 상속 선언을
   읽을 수 없어 **구조적으로 사본**이다 — 그래서 **판정을 한 곳에만** 두고(화면마다 복제 금지)
   계약 시험으로 두 축이 갈리지 않게 고정한다.
3. 관리자 전용 화면 노출(`NAV-001`)·사용자 관리 역할 선택지·이슈 작성자 한글 라벨은 같은 배치로 처리.

⚠ **작업자 전용 비교(`role === Role.WORKER`)는 그대로 둔다** — 관리자가 작업자 자리에 흘러들면 안 된다
(백엔드에서 `hasRole(WORKER)` 를 작업자만 참으로 둔 것과 같은 이유).
