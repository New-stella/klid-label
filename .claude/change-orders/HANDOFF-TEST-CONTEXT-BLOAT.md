# 인계 — 백엔드 시험 컨텍스트 비대화로 전체 회귀가 완주하지 못한다

> 작성 2026-08-25 · 발견 경위: CO-014 작업 중 전체 회귀가 두 번 연속 GC 에 묶임
> 이 문서는 **별도 세션이 단독으로 착수**할 수 있게 쓴 것이다. CO-014 를 알 필요는 없다.

## 1. 증상

`./gradlew cleanTest test`(전체 회귀)가 **결과를 하나도 내지 못한 채 매달린다.**

- 테스트 워커 힙(2g) Old 영역이 **100%** 로 차고 회수되지 않는다
- Full GC 가 **12초에 27회**, GC 점유율 **94%**
- **결과 XML 도 `BUILD` 줄도 안 나온다** → 로그에 `FAILED` 가 없다는 것이 통과의 증거가 되지 못한다
- 교착이 아니다. 전 스레드 `RUNNABLE` 이며 회수할 게 없는데 GC 가 무한히 도는 상태다

⚠ **CPU 로 진행 여부를 판정하지 마라.** GC 스레드가 도는 것과 일하는 것이 CPU 로는 구분되지 않는다
(실제로 CPU 783% 를 「진행 중」으로 오독한 사고가 있었다). 판정은 반드시 아래로 한다:

```bash
W=$(pgrep -f "org.gradle.internal.worker" | head -1)
jstat -gcutil $W ; sleep 12 ; jstat -gcutil $W
# Old(O) 가 안 내려가고 FGC 가 12초에 20회 넘게 늘면 그 실행은 끝나지 않는다
```

## 2. 원인 (측정값 — ★그대로 믿지 말고 다시 재라)

`backend/src/test/java` 기준. 재측정 명령을 함께 적었다. **`grep -a` 를 반드시 쓴다** — 이 저장소에는
`file` 이 정상 UTF-8 소스를 `data` 로 오판해 **grep 이 소스 10개를 말없이 건너뛴** 실사고가 있다.

> ★**아래 수치는 두 번 정정됐다.** 최초 작성자(`grep` 기반)가 틀렸고, 다른 세션이 렉서 기반 추출기로
> 다시 재면서 **두 번** 바로잡았다. 그 정정 과정 자체가 이 문서에서 가장 값어치 있는 부분이니 §2-1 을 반드시 읽어라.

|---|---:|---:|
| 시험 클래스 총수 | 843 | — |
| **`@SpringBootTest`** | **309** | 316 (주석 언급 7건 혼입) |
| **서로 다른 컨텍스트 키** | **74** | 52 (파서 결함 2종) |

| 컨텍스트 크기 분포 | `[149, 74, 5, 3, 3, 2×6, 1×63]` 합 309 | — |
| 웹 계층 미사용 `@SpringBootTest` | **196** | 202 |
| `@MockBean`/`@SpyBean` 보유 클래스 | **43** (조합 34종, **26종이 1클래스 전용**) | — |
| `@DynamicPropertySource` 보유 | **18** | — |
| `@TestPropertySource` 선언 종류 | 11 | — |
| **캐시 상한** | **32** (Spring 기본) | — |

**309개 중 223개가 단 2개 컨텍스트에 있고, 나머지 86개가 72개 컨텍스트에 흩어져 있다.**
74개가 32칸을 두고 다툰다 → **스래싱이 확정적**이다.

### §2-1 ★순진한 `grep` 은 세 축 전부에서 틀린다 (재측정하려면 이걸 먼저 읽어라)

최초 작성자와 재측정자가 **각각 다른 방식으로** 틀렸다. 셋 다 실측으로 확인됐다.

1. **주석 안 언급을 센다.** `grep -ral '@SpringBootTest'` = 316 인데 실제 어노테이션은 **309**다.
   나머지 7건은 전부 javadoc·라인주석 안의 언급이다(*"왜 @SpringBootTest 가 아니라…"* 같은).
   `@DynamicPropertySource` 도 같다 — `grep -ral` 은 20, 실제는 **18**(주석 1 + 인프라 클래스 1).
   → **줄 선두 어노테이션만 세라**: `grep -ralE '^\s*@SpringBootTest'`
2. **같은 줄 선언에서 엉뚱한 타입을 집는다.** 이 저장소에는 `@MockBean private VlmClient vlmClient;`
   처럼 **한 줄로 쓴 선언**이 실재한다. 줄 단위 정규식이 줄 끝까지 삼킨 뒤 **다음 필드의 타입**을 집는다
   (실측 오추출: `VlmClient → Long`, `AiServerClient → ListAppender`). → 개행을 넘나드는 단일 패턴으로 뽑고,
   **`grep -ral` 파일 수와 추출 건수를 교차검증**하라(43 = 43 이어야 한다).
3. **`@DynamicPropertySource` 는 Y/N 이 아니다 — 클래스마다 별도 컨텍스트다.**
   `spring-test` 의 `DynamicPropertiesContextCustomizer` 는 `equals`/`hashCode` 를 **`Set<Method>`** 로 구현한다.
   선언 클래스가 다르면 `Method` 객체가 달라 **절대 같아지지 않는다** — 프로퍼티 값이 완전히 동일해도 갈린다.
   ⇒ **이 저장소는 `@SpringBootTest` 309개에 공통 베이스 클래스가 없다(`extends` 0건)**. 그래서 이 18개가
   **전부 각자 독립 컨텍스트**다. 이 축의 처방은 프로퍼티 통일이 아니라 **베이스 클래스로 끌어올리기**다
   (같은 `Method` 객체가 되어 공유된다).

4. **문자열 리터럴 안의 어노테이션 「이름」을 센다 — 검사기가 자기 자신을 오탐한다.**
   이 축을 세는 가드를 만들면 그 가드의 **실패 메시지 문자열**에 어노테이션 이름이 들어간다.
   실측: `.as("@SpringBootTest 를 한 건도 못 찾았다 — 스캔이 유효하지 않다")` 때문에 `310/75` 가 나왔다.
   → **한 번 훑어 두 벌을 만든다**(길이 동일 → 인덱스 공유): 주석·리터럴 **내용을 지운 판**으로 **탐지**하고,
   주석만 지운 판에서 **추출**한다. ⚠ 리터럴을 통째로 지우면 안 된다 — **프로퍼티 값이 컨텍스트를 가르는
   축**이라 그 내용이 필요하다.

⇒ **`grep` 으로 이 네 축을 세지 마라.** 문자열·주석을 걸러내는 렉서로 뽑고 교차검증하라.

### 산수

`backend/build.gradle` 의 `test` 블록에 **`forkEvery`·`maxParallelForks` 선언이 0건**이라 309개가
**한 JVM** 에서 돈다. Spring 은 테스트 컨텍스트를 **캐시에 살려 두고 기본 상한이 32** 다.
JPA·Hibernate·Flyway·Quartz·WebClient 를 물고 있는 컨텍스트 하나가 **50~150MB** 급이므로
**32칸만 차도 2GB 힙을 넘는다.** 그런데 **서로 다른 컨텍스트가 74개**라 32칸을 두고 서로를 밀어낸다.

### ★실측: 컨텍스트 1개 ≈ 60MB — 캐시는 고장난 적이 없다

나선 상태의 **살아 있는 워커**에서 직접 떴다(OOM 을 기다리지 않고 `jcmd GC.class_histogram`·`GC.heap_dump`).

```
33          DefaultListableBeanFactory      ← 살아 있는 컨텍스트 33개 (상한 32 + 생성 중 1)
 1          DefaultContextCache
3,303,000   aspectj ShadowMatchImpl   158MB   ← 컨텍스트당 약 10만 개
3,303,000   aspectj ExposedState      105MB   ← ShadowMatchImpl 과 1:1
1,604,119   java.lang.reflect.Method  141MB
            AspectJ 합계 315MB · AspectJ+Method 451MB (상위 20 합계 1,295MB 중)
```

⇒ **컨텍스트 1개 ≈ 60MB**, 그러므로 **32칸 × 60MB ≈ 1.9GB vs 워커 힙 2GB.**

★**캐시는 설계대로 32칸을 채웠다. 그 32칸이 힙보다 컸을 뿐이다.** 넘치지도, 무한히 쌓이지도 않았다.
이 사실이 §3 의 처방 판단을 바꾼다(→ §3-3).

**컨텍스트 원가의 정체는 Spring AOP 포인트컷 매칭 캐시다.** `AspectJExpressionPointcut` 의
```java
private transient Map<Method, ShadowMatch> shadowMatchCache;   // ★ static 이 아니다 (spring-aop 6.1.8 확인)
```
가 **인스턴스 필드**라 포인트컷 → 어드바이저 빈 → 컨텍스트 소유이고, 컨텍스트가 닫히면 함께 회수된다.
⇒ **누수가 아니라 컨텍스트당 정상 원가**다. 이 앱은 `@Transactional`·`@Async`·`@Cacheable`·`@Scheduled`·
`@PreAuthorize`·Resilience4j 5종 등 포인트컷 어드바이저가 십수 개이고,
`빈 수백 × 메서드 십수 × 어드바이저 십수 ≈ 10만/컨텍스트` 로 실측치와 일치한다.

⚠ **60MB 는 평균이고 편차가 크다.** 웹 계층을 띄우는 것·Testcontainers 를 무는 것이 더 크다.
상한을 정할 때는 평균이 아니라 **큰 쪽**으로 잡아라 — 하필 큰 컨텍스트 N개가 동시에 캐시에 있는
조합에서 터진다.

### ★이건 단조 증가한다

`@MockBean` 조합을 새로 쓰는 시험이 하나 늘 때마다 컨텍스트가 하나 늘고 **되돌아가지 않는다.**
그래서 이 문제는 "언젠가 터지는" 것이 아니라 **터지는 시점이 정해져 있는** 것이다.

## 3. ⚠ 이미 실패한 처방 — 되풀이하지 마라

1. **힙 상향** — `maxHeapSize = '2g'` 가 바로 그 처방이었다. 그 옆 주석이 *"통합 테스트 추가로 캐시되는
   컨텍스트 수가 늘어 워커 OutOfMemoryError 가 간헐 발생한다"* 라고 그때를 기록하고 있다.
   **시간을 벌어 둔 패치였고 그 시간이 끝났다.** 또 올리면 같은 자리에 다시 온다.
2. **「이번 변경이 천장을 넘겼다」로 귀속** — 2026-08-25 에 그렇게 판단했다가 **교차 관측으로 기각**됐다.
   같은 시각 **다른 워크트리(다른 브랜치·다른 작업)** 의 워커도 99.82% 로 같은 증상이었다.
   최근 추가된 `@SpringBootTest` 를 범인으로 지목하기 전에 **다른 워크트리를 먼저 확인하라.**
3. **캐시 상한만 걸고 「해결」로 닫기** — `spring.test.context.cache.maxSize` 를 낮추면 회귀가
   완주할 수 있다. **그것만으로 닫았다고 보고하지 마라** — 컨텍스트 종류가 줄어든 것이 아니므로
   §2 의 「단조 증가」는 그대로 진행되고, 재생성 대가(시간)가 얼마나 붙었는지도 함께 내야 한다.

   ⚠ **★ 초판의 이 항목은 「완화이지 해결이 아니다」로 그 처방을 사실상 봉인했는데 그건 틀렸다
   (2026-08-26 실측으로 뒤집힘).** 봉인의 전제가 「캐시가 고장나서 넘친다」였는데, 힙 실측은
   **캐시가 설계대로 32칸을 채웠고 그 32칸(≈1.9GB)이 힙(2GB)보다 컸다**는 것을 보여준다(→ §산수).
   그러면 상한을 낮추는 것은 회피가 아니라 **캐시를 힙에 맞게 사이징하는 것**이며, **즉효인 유일한 축**이다.

   | 상한 | 상주(≈60MB/개) |
   |---:|---:|
   | 32 (기본) | 1.9GB ← 2GB 힙에서 회수 불가 |
   | 16 | 0.96GB |
   | 8 | 0.48GB |

   ★**단 상한만 낮추면 스래싱이 된다 — 짝이 필요하다.** 지금 캐시가 비효율인 진짜 이유는 크기가 아니라
   **지역성**이다(309개 중 223개가 2개 컨텍스트를 쓰는데 실행 순서가 컨텍스트와 무관해 서로를 밀어낸다).
   **컨텍스트 시그니처로 클래스를 묶는 `ClassOrderer`**(`junit-platform.properties`)와 함께 걸면 컨텍스트마다
   정확히 한 번만 생성되어 재생성 대가가 최소가 된다. ⚠ 실행 순서를 바꾸므로 **숨어 있던 순서 의존이
   드러난다**(→ §5). 그때는 설정을 되돌릴 것이 아니라 그 의존을 고쳐라.

   ⇒ **§4-B(종류 줄이기)와 대체재가 아니라 짝이다.** 상한은 회귀를 지금 완주시키고, §4-B 는 그 교환의
   시간 비용을 줄인다.

   ### ★★실증됨 (2026-08-26) — 그 교환은 순서화가 있으면 거의 공짜다

   `cache.maxSize=8` + 시그니처 순서화로 **전체 회귀가 완주했다.**

   | | 이전 | 이후 |
   |---|---|---|
   | 결과 | **23분 무진전**(미완주) | **7분 9초 완주** |
   | Full GC | 2,284회 · GC 점유 76~100% | **1회 · 0.197초** |
   | Old 최고 | 99.97% 고착 | ~87%(정상 회수) |
   | 실행 | — | 7,508건 · XML 831 |
   | **컨텍스트 기동** | — | **75회** ← 정적 예측 74 와 사실상 일치 |

   ★**캐시를 32→8 로 줄였는데 재생성이 이론적 최소치(=컨텍스트 종류 수)다.** 순서화가 같은 컨텍스트를
   연속 실행시키므로 컨텍스트마다 정확히 한 번만 만들어진다. 그래서 「메모리를 시간으로 바꾼다」는
   대가가 **사실상 발생하지 않았고**, 오히려 종전 실측(8분 35초~9분 56초)보다 빨랐다.

   ⇒ **"상한을 낮추면 시간으로 바뀐다"는 대가는 순서화가 없을 때만 발생한다.** 둘을 반드시 함께 넣어라.

   ### ★★그 전까지의 초록은 「간헐 성공」이 아니라 「벼랑 끝」이었다

   ```
   캐시 32칸 × ~60MB ≈ 1.9GB   vs   워커 힙 2GB      ⇒ 여유 5% 남짓
   ```
   32칸에 **어느 컨텍스트가 앉느냐**에 따라 넘기도 하고 안 넘기도 한다(웹 계층 유무·Testcontainers
   물림 여부로 크기가 다르다). 실측으로 **같은 코드가** 9분 완주 → 23분 무진전 → 7분 완주로 움직였다.

   ⇒ **초록이 나왔다고 안전했던 것이 아니다.** 「간헐 실패」로 분류해 재실행으로 넘기지 마라 —
   그건 여유가 5% 인 상태를 운으로 통과한 것이고, 시험이 하나 늘 때마다 그 확률이 나빠진다.

## 4. 할 일

### 4-A. 먼저 — 실패를 보이게 만든다 (완료 · 접근 1회 폐기됨)

지금은 힙이 차도 OOM 을 안 던지고 무한히 GC 만 돈다. **침묵하는 매달림을 명확한 실패로 바꾼다.**

```groovy
timeout = java.time.Duration.ofMinutes(30)      // 벽시계 — GC 종류·실패 형태와 무관하게 동작
jvmArgs '-XX:+HeapDumpOnOutOfMemoryError', "-XX:HeapDumpPath=${testHeapDumpDir}"
```

값은 이 저장소가 `CLAUDE.md` 에 선언한 빌드 예산(`buildTimeout: 1800`)에 맞춘다. 정상 회귀는 9~10분급이라
정상 실행에는 걸리지 않는다.

#### ⚠ 폐기된 접근 — GC 과부하 임계 (되살리지 마라)

초판은 `-XX:GCTimeLimit=90 -XX:GCHeapFreeLimit=5` 로 「회수 불가면 즉시 OOM」을 만들려 했다.
**실측으로 두 단계에 걸쳐 무너졌다.**

1. **기본 GC(G1)에서는 그 두 플래그가 조용히 무시된다.** 거부되지도 않는다 — 이 검사는 Parallel GC 의
   적응형 크기 정책에만 구현돼 있다. 실측(JDK 17.0.15): `Parallel+90/5` → `GC overhead limit exceeded` /
   `G1+90/5` → `Java heap space`(기본 98/2 와 동일).
2. **Parallel GC 로 바꿔도 발화하지 않았다.** 플래그가 워커에 정확히 걸린 것을 인자로 확인한 상태에서
   **23분 · Full GC 2,127회 · GC 점유 76%(순간 100%) · Old 99.97% 고착** 인데 OOM 이 없었다.

⇒ **위약이다. 다시 넣지 마라** — 달아 두면 「탐지기가 있는데 안 울렸으니 메모리 문제가 아니다」라는
잘못된 판단을 부른다. 침묵을 실제로 끝내는 것은 **타임아웃**이다.

★**OOM 을 기다리지 말고 살아 있는 워커를 직접 열어라.** 이 문서의 핵심 수치(§산수)는 전부 그렇게 얻었다:
```bash
W=$(pgrep -f "org.gradle.internal.worker" | head -1)
jcmd $W GC.class_histogram | head -25          # 무엇이 힙을 먹는가
jcmd $W GC.heap_dump -all=false /path/dump.hprof   # 3GB 급, 5초
```
⚠ macOS 에는 `timeout` 명령이 없다 — `timeout 60 jcmd ...` 로 감싸면 **command not found 로 빈 출력**이 나오고
그것을 「JVM 이 응답하지 않는다」로 오독하게 된다(실제로 그 오독이 있었다).

### 4-B. 본체 — 컨텍스트 다양성을 줄인다

★**우선순위는 「한계 기여도」로 정한다** — 그 축을 완전히 통일했을 때 74가 몇으로 주는가.
아래는 렉서 기반 실측이다(추정 아님).

| 순위 | 축 | → | 감소 | 비고 |
|:--:|---|---:|---:|---|
| **1** | **`@MockBean`/`@SpyBean`** | 53 | **−21** | 43클래스에 34종, **26종이 1클래스 전용** |
| **2** | **`@TestPropertySource`** | 56 | **−18** | 11종 |
| **3** | **`@DynamicPropertySource`** | 66 | **−8** | 18개가 **전부 독립** — 처방이 다르다(아래) |
| 4 | `@SpringBootTest(properties=)` | 70 | −4 | |

| 6 | 중첩 `@TestConfiguration` | 72 | −2 | |
| 7 | `@Import` | 73 | −1 | |

1. **`@MockBean` 조합을 합친다 (최대 지렛대).** 조합이 다를 때마다 **새 컨텍스트**가 생긴다.
   26종이 단 한 클래스에서만 쓰이므로, 공용 목 묶음 하나로 모을 여지가 크다.
   4개 이상이 공유하는 조합은 `BatchOrchestrator`(4) 하나뿐이다.
2. **`@TestPropertySource` 를 합친다.** 값이 **진짜로 충돌**하는 것(`enabled=true` vs `false`)은 못 합친다 —
   합칠 수 있는 것만 골라라.
3. **`@DynamicPropertySource` 는 프로퍼티를 통일해도 안 줄어든다.** §2-1 ③ 참조 — `Set<Method>` 동일성이라
   **선언 클래스가 다르면 무조건 갈린다.** 처방은 **공통 베이스 클래스로 끌어올리기**다(같은 `Method` 객체가
   되어 공유된다). 이 저장소는 `extends` 가 0건이라 아직 아무도 이 축을 쓰지 않았다.

#### ⚠ 「웹 미사용 196개를 슬라이스로 내린다」는 **컨텍스트 수를 줄이는 일이 아니다**

최초 문서가 이것을 1순위에 뒀으나 **틀렸다.** 그 196개는 대부분 **149개짜리 최대 그룹**에 속하는데,
컨텍스트가 하나 사라지려면 그 그룹의 **마지막 클래스**를 옮겨야 한다 — 149개를 다 옮겨야 1개가 준다.

**무가치하다는 뜻은 아니다.** 총 실행시간·컨텍스트 로드 횟수는 줄인다.
**「힙에 상주하는 컨텍스트 수」와 「실행 시간」은 다른 지표이며, 이 문서가 잡으려는 것은 앞의 것이다.**

#### 값싼 병합 후보 (실측으로 지목됨)

- `ApprovedRedeidentControllerTest` 와 `KpstHttpBootIntegrationTest` — **프로퍼티 4개가 완전히 동일**,
  `@AutoConfigureMockMvc` 유무로만 갈린다
- KPST `poll-interval-sec=3600` 계열이 **4갈래**(목·`poll-max-attempts` 차이)
- 포털 스윕(`portal.upload.sweep`/`portal.retention.sweep`)이 **3갈래**
- `authoring.control-notify.enabled` 가 **3갈래**

#### ⚠ 도달 가능한 바닥 — 32 아래로 못 갈 수도 있다

프로퍼티 군집을 **전량** 통일해도 바닥이 **24~27** 수준이고, 목·동적프로퍼티까지 이상적으로 없앤 하한이
**10 내외**로 추정된다. 그런데 그 대부분은 값이 **진짜로 충돌**하거나 **외부 경계를 목으로 막아야 하는**
정당한 이유가 있어 실제로는 못 없앤다.

⇒ **「74를 32 아래로 내린다」가 프로퍼티·목 정리만으로 가능한지는 아직 미확정이다.** 안 되면 남는 축은
`forkEvery`(JVM 을 갈아 캐시를 비운다)나 캐시 상한 조정이며, 그건 **완화책**이다(§3-3).

## 5. 이 저장소 특유의 함정 (모르면 시간을 버린다)

| 함정 | 내용 |
|---|---|
| **빌드 슬롯은 머신 단위** | 워크트리가 여러 개여도 Gradle 데몬·Docker·포트를 **머신 전체가 공유**한다. 동시에 돌리면 **양쪽 다 위양성**이다. 실측 사고: 한쪽 실행이 상대 워커를 SIGTERM 으로 죽여 `83 failed` 가 났고 그것은 판정이 아니라 중단이었다(`exit 143`). 아래 락 절차를 쓴다 |
| ★**락은 사람이 아니라 실행 단위로 잡는다** | 위 사고의 실제 원인은 「세션은 슬롯을 넘겼는데 **그 세션의 에이전트는 그 사실을 몰라** 혼자 재시도했다」이다. **세션끼리 말로 주고받는 것으로는 막히지 않는다** — gradle 을 부르는 **위임 프롬프트에 락 절차를 넣어라** |
| **`cleanTest` 없으면 통과처럼 보인다** | Gradle `test` 는 `UP-TO-DATE` 로 **실행 없이** 스킵된다. 반드시 `cleanTest test`, 그리고 결과 XML **개수와 타임스탬프**로 실행 증거를 확인하라 |
| **강제 종료 시 고아 컨테이너** | `TESTCONTAINERS_RYUK_DISABLED='true'` 라 JVM 을 kill 하면 Testcontainers 컨테이너가 남는다. `docker ps -a` 에서 **랜덤 이름**(예 `fervent_jackson`) 컨테이너를 찾아 손으로 지워라. 상시 스택은 `klid-*` 이름이니 그건 건드리지 마라 |
| **`grep` 이 소스를 조용히 건너뛴다** | `file` 이 정상 UTF-8 을 `data` 로 오판해 **소스 10개가 스캔에서 빠진** 사고가 있다. 항상 **`grep -a`**. 0건이 나오면 「위반 없음」이 아니라 **「스캔이 됐는가」를 먼저 의심**하라 |
| **환경변수가 테스트 워커까지 안 간다** | `FOO=1 ./gradlew test` 로는 워커에 안 들어간다(이미 뜬 데몬 환경을 물려받음, `--no-daemon` 으로도 안 됨). `systemProperty` 를 쓰거나 `-D` 가 워커에 전달되게 배선하라 |
| **부분 실행으로 종결되지 않는 부류** | 픽스처·정리 코드(`@BeforeEach`/`@AfterEach`)·공유 자원(고정 경로 temp·포트)을 건드리면 **결과가 실행 조합에 의존**한다. 조합 3회 통과가 전체 1회 실패를 배제하지 못한다(실측: 조합 검증 통과한 `@AfterEach` 가 전체에서 37건을 깨뜨렸다) |
| ★**순서를 바꾸는 것은 위험한 만큼 「드러내는 도구」다** | 전체 회귀가 오래 안 돌면 **순서 의존이 아무도 실패하지 않는 형태로 조용히 쌓인다.** 실행 순서를 한 번 흔들자 잠복 결함 2종이 즉시 나왔다 — ①정리 스크립트가 자식 테이블 하나(`LS_DATA_LBL_ATTR_VAL`)를 빠뜨려 **선행 클래스가 그 행을 남겼을 때만** FK 위반 ②"원복" 코드가 **detached 엔티티**를 고쳐 UPDATE 가 아예 나가지 않았고(주석만 원복, 실제 무동작) 게다가 `finally` 가 아니라 본문 끝에 있었다. 둘 다 **격리 실행하면 통과**한다. ⇒ 순서화 도입 라운드는 시끄럽지만 그 소음이 곧 회수다 |

### 슬롯 락 절차 (세션이 둘 이상일 때 필수)

```bash
# 잡기 — mkdir 은 원자적이라 경합이 없다
if mkdir /tmp/klid-gradle-slot.lock 2>/dev/null; then
  printf '%s\n%s\n%s\n' "$(date -Iseconds)" "<세션이름>" "$$" > /tmp/klid-gradle-slot.lock/owner
else
  echo "사용 중:"; cat /tmp/klid-gradle-slot.lock/owner; exit 1
fi

# 놓기 — 반드시. 실패 경로에서도 놓아라
rm -rf /tmp/klid-gradle-slot.lock
```

⚠ **고아 락 회수 경로를 반드시 둔다**("차단엔 되돌리는 길"). 막혔을 때 `owner` 의 시각이 예산(30분)을 크게
넘겼고 **워커가 0개**면 고아로 보고 지운 뒤 잡는다. **지우기 전에 상대에게 한 줄 알린다.**
