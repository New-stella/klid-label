## §1 배경

브랜치 `onprem-jboss-0904-roles` 가 2026-09-04 현장 실측을 반영해 설치 스크립트를 웹·WAS·AI **3역할**로
가르고 웹 컨텍스트를 현장 httpd 에 맞췄다. 그 브랜치를 포함해 설치 스크립트 44개(약 9,700줄)를
전수 재검토한 결과 결함 셋이 나왔다.

**① 배포하면 API 가 전부 404 된다.** 현장 웹의 httpd 가 이렇게 잡혀 있다:

```
ProxyPass /label-studio/api/  balancer://label-cluster/label-studio/api/
BalancerMember http://10.177.22.80~83:8080   (WAS 4대)
```

즉 WAS 가 받는 경로는 `/label-studio/api/v1/...` 다. 그런데 브랜치는 컨텍스트를 `/label-studio`
한 세그먼트로 두었다. 나머지 한 세그먼트 `/api` 를 `application.yml` 의
`server.servlet.context-path: /api` 가 채워 줄 것으로 본 것인데, **그 값은 WAR 배포에서 무시된다.**
이 저장소가 이미 네 곳에서 그렇게 못 박고 있다 — `ServletInitializer.java` javadoc,
`deploy/onprem/docs/00-overview.md:56`, `docs/03-install.md:478`, `docs/06-troubleshooting.md:277`.
컨트롤러 66개는 전부 `@RequestMapping("/v1")` 이므로 실제로 서빙되는 경로는 `/label-studio/v1/...` 이고,
현장이 보내는 `/label-studio/api/v1/...` 는 **핸들러가 없어 404** 다.

종전 형상이 동작하던 이유도 같은 규칙이다: 컨텍스트 `/api` + 컨트롤러 `/v1` = `/api/v1`.

⚠ 이 장애는 **아무 신호가 없다.** WAS 는 정상 기동하고 배포도 성공이며 로그도 조용하다.
"배포는 됐는데 화면이 전부 안 된다"로만 드러난다 — `docs/06-troubleshooting.md:277` 이 기술한 바로 그 증상이다.

**② PostgreSQL 을 우리가 배포하지 않기로 확정됐다(2026-09-05 사용자).** 현장 DB 는 외부 제공이다
(`--db-hosts=10.177.199.148:19999,10.177.199.149:19999`). 그런데 설치 스크립트는 여전히 번들 PG16 을
설치하고(`USE_BUNDLED_POSTGRES` 기본 **1**) `CREATE DATABASE`·`CREATE ROLE` 을 시도하며,
매체는 PG RPM **218개 · 140,481,418 B(134.0 MiB)** 를 싣고 반입 심사에 그것을 신고하고 있다.
외부 DB 에는 그 권한이 없으므로 성립하지 않는다.

**③ 브랜치가 자기 문서와 어긋난다.** `반입요청서.md` 는 파일 수·용량만 갱신됐고 서술은 옛 형상이다
("대상 장비 2대", "`--role=app`/`--role=ai`", "api.war 파일명이 곧 웹 컨텍스트 `/api`").
여기에 2026-08-31 에 철거된 포털 DB 복제 설정(`PORTAL_DB_*`·`META_REPLICATION_ENABLED`)이
설정 템플릿과 문서에 그대로 남아, **백엔드 코드에 소비처가 0건인 값**을 현장에서 채우라고 안내한다.

## §2 변경 요지

1. `jboss-web.xml` 의 컨텍스트를 `/label-studio` → **`/label-studio/api`** 로 고친다(한 줄 + 헤더 주석 정정).
   브랜치의 나머지(프론트 `VITE_API_BASE_URL`, 헬스체크 3곳)는 이미 이 값을 전제하므로 함께 맞아떨어진다.

3. 철거된 포털 DB 복제 잔재와 옛 형상 서술(2대·`--role=app`·`api.war` 컨텍스트)을 정합한다.

     - `:164` "**파일명이 곧 웹 컨텍스트 `/api` 이므로 이름을 바꾸면 안 된다**" →
       `jboss-web.xml` 이 컨텍스트를 고정하므로 **파일명과 무관**하다(A 항목과 정합)
     - `:37` "httpd(정적 자산 서빙 + `/api` 리버스프록시)" → `install-web.sh` 는 현장 httpd 설정을
       건드리지 않는다(정적 자산만 배치)
  4. `docs/` 의 `/api` 컨텍스트·`api.war` 기준 서술 정합(10개 파일).
- **불변**: `config/frontend/httpd-klid.conf.template` 은 `--with-httpd-conf` 를 줄 때만 쓰이는
  **우리가 만드는 경우**의 템플릿이다. 현장 형상과 다르다고 지우지 말 것.
- **수용기준**: `grep -rn 'PORTAL_DB_\|META_REPLICATION' deploy/onprem/` → 0건.
  `grep -rn '빈 DB 2개\|portal DB' deploy/onprem/docs/` → 0건.

### 범위 밖 — 현장 확인 요청 항목 (구현하지 말 것)

라우터 basename 이 `/label-studio` 이므로 `/label-studio/videos` 같은 경로를 **새로고침하거나 직접 열면**
httpd 가 `index.html` 로 되돌려 줘야 한다(SPA 폴백). 그 `FallbackResource` 는 **우리 템플릿**
(`config/frontend/httpd-klid.conf.template:57`)에 있는데, `install-web.sh` 는 기본적으로
**현장 httpd 설정을 건드리지 않는다**(현장 공용 설정 보존이 의도된 결정).
현장 httpd 에 `/label-studio/*` SPA 폴백이 있는지 **우리가 알 수 없다.**
없으면 **첫 진입만 되고 링크·새로고침이 404** 되는 형태로 드러난다.

→ 현장 회신 문항: *"`/label-studio/` 아래 존재하지 않는 경로(예 `/label-studio/videos`)로 요청이 오면
`index.html` 을 돌려주도록 잡혀 있습니까? (`FallbackResource /index.html` 또는 동등한 Rewrite)"*

## §4 영향·리스크

- **하위호환**:
  - A 는 **웹 컨텍스트 계약면을 바꾼다.** 다만 브랜치의 `/label-studio` 는 **한 번도 배포된 적이 없고**
    나머지 구성요소가 이미 `/label-studio/api` 를 전제하므로, 실제로는 **깨진 것을 맞추는 방향**이다.
  - 관제서버가 호출하는 저작도구 API 주소가 이 컨텍스트를 탄다 — **관제팀 공유 필요.**
  - B 는 매체 구성을 바꾼다 → **반입 심사 재제출 대상**(파일 수·용량·SHA256SUMS 영역 수 변동).
- **매체 재산출**(B 의 6번):
  - `syspkgs/postgresql/` **실측 218 파일 · 140,481,418 B** 가 빠진다.
  - 총계 예상: 6,664 → **6,446 파일** / 1,540,828,442 → **1,400,347,024 B**
  - `SHA256SUMS` 영역 표: **11개 → 10개**(`syspkgs/postgresql/SHA256SUMS` 217항목 제거)
  - ⚠ 위 값은 **예상이지 확정이 아니다.** 다른 변경이 파일 수를 함께 바꾸므로
    매체 재생성 후 `find`/`stat` **실측으로 재산출**하고, 반입요청서의 **3자 검산**
    (개요표 총계 ↔ 영역표 합계 ↔ 실측)이 맞는지 확인한다.
- **되돌리기**: 전부 git revert 가능. 매체는 재생성으로 복구.
  A 는 한 줄이라 되돌리기가 가장 싸다.
- **리스크**:
  - ⚠ **A 를 빠뜨리면 배포가 전면 실패한다.** 그리고 그 실패는 로그가 조용해서 원인 추적이 어렵다.
  - ⚠ **B 와 C 를 따로 하면 그 사이에 설치가 깨진다** — 단계 번호 하드코딩 때문이다. 같은 커밋에 묶는다.
  - ⚠ D-1 을 "설정을 지우면 기동이 안 될 텐데"로 되돌리려는 시도가 나올 수 있다.
    **철거 이전 사실이다** — 코드 소비처 0건을 먼저 확인할 것.

### 이 라운드가 남긴 사실 3가지

1. **설계에도 같은 P0 가 있었다** — DEPLOY-001 v37 이 컨텍스트 `/label-studio` 와
   API 기준 `/label-studio/api/v1` 을 동시에 말했다. 같은 명세의 설치 절차 2번이 이미
   「애플리케이션 설정은 외부 WAS 에서 적용되지 않는다」고 적어 두었는데 컨텍스트만 그 규칙 밖으로 셌다.
2. **`analyze_impact` 는 이 축을 한 건도 못 잡았다.** 값을 실제로 보유한 6건 중 dependent 로 뜬 것이 0건이고
   값을 갖지도 않은 ADR 만 떴다. 담당 넷이 각각 독립 실증했다. **낱말 전수 스캔만이 잡는다.**
3. **2026-09-04 반입 매체의 백엔드 산출물은 구 컨텍스트로 만들어져 있다** — 그대로 설치하면
   API 가 전건 실패한다. 산출물을 다시 만들어야 하며 그 사실을 FILE-039 에 명시했다.

### 미결 — 사용자 판단 필요 (이 CO 범위 밖으로 뺄지 포함할지)

- **포털 데이터베이스 잔재의 범위** — 「메타 복제」·「PORTAL_DB」·「포털 DB」를 품은 ITEM 다수
  (EXTSYS-006 · INT-009 · MOD-043 · MOD-050 등). 그중 **ADR-012 같은 결정 기록은 보존이 정상**이고
  나머지는 잔재라 섞여 있다. 특히 **INT-009 는 연동점 전체가 폐기 축**이라 본문 수정이 아니라
