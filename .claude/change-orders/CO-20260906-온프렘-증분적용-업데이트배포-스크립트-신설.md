## §1 배경

**증분 마이그레이션이 매체에 실리는데 적용하는 단계가 없었다.**

- 온프렘은 Flyway 를 끈다(확정). 테이블을 만드는 경로는 설치의 `schema.sql` 로드 하나뿐이다.
- 그 뒤 추가된 마이그레이션은 `deploy/onprem/db/incremental/` 에 모아 현장에 넘기는데,
  **설치 스크립트 전체에 `incremental` 참조가 0건**이었다(실측). 즉 아무도 적용하지 않는다.
- 매체 자체에는 실린다 — 매체는 `deploy/onprem/` 을 통째로 복사한 것이라(`90-finalize-media.sh`)
  그 폴더가 자동으로 따라간다. **빠진 것은 담는 일이 아니라 적용하는 일이다.**

**★ 이 누락이 위험한 이유는 조용하기 때문이다.**
`ddl-auto=validate` 는 이 앱에서 Hibernate 에 도달하지 않아 **표가 없어도 기동이 성공**한다.
새 WAR 만 올라가고 DB 가 뒤처지면 화면·배치가 그 표를 처음 건드릴 때 비로소 터진다.
**어떤 회귀도 이것을 잡지 못한다** — 로컬·dev·전건 회귀는 Flyway 로 돌기 때문이다.

**또 하나 — 어디까지 적용됐는지 남기는 자리가 없었다.**
`db/incremental/README.md` 가 그 사실을 **미확정**으로 명시하고 선택지 셋을 적어 두고 있었다.

## §3 변경 상세 — 공유기반 선처리(메인 직접)

### A. `apply-migrations.sh`

모드: `--status`(현황만) · `--dry-run` · (기본)적용 · `--mark-only`(실행 없이 기록만).

**지키는 것**

- **한 파일 = 한 트랜잭션 = 한 세션.** 같은 트랜잭션 안에서 `pg_advisory_xact_lock` → 중복 재확인 →
  `\i` → 이력 INSERT. 여러 노드가 동시에 돌려도 한 번만 적용되고, 실패하면 그 파일이 통째로 롤백되며
  뒤 번호는 실행하지 않는다. PostgreSQL 은 DDL 도 트랜잭션이라 성립한다.
- **`PGOPTIONS='-c search_path=<스키마>'` 강제.** `V1` 만 스키마를 한정하고 `V2` 이후는 전부 비한정
  식별자다. search_path 가 어긋나면 `CREATE TABLE IF NOT EXISTS` 가 **`public` 에 빈 표를 만들고
  오류를 내지 않는다** — 앱은 대상 스키마를 보므로 그 표는 영원히 비어 있다. 적용 후 그 오생성을 검사한다.
- **이미 적용된 파일의 내용이 바뀌면 멈춘다**(sha256 대조). 증분 파일은 한 번 나가면 고치지 않는 것이
  규칙이므로, 바꿔야 하면 새 번호로 추가한다.
- **트랜잭션 밖에서만 도는 문장(`CONCURRENTLY`·`VACUUM` 등)이 든 파일은 받지 않고 멈춘다** —
  조용히 절반만 적용되는 것보다 낫다.

⚠ **`--mark-only` 는 신규 설치 직후 전용.** 설치가 로드한 `schema.sql` 은 그 시점의 증분을 이미
**포함**한 통합본이라 같은 증분을 다시 실행하면 멱등하지 않은 문장에서 실패하고, 기록을 안 남기면
다음 회차에 미적용으로 보여 또 실행된다. **기존 운영 DB 에 쓰면 적용하지 않은 것을 적용했다고 기록한다.**

### B. 적용 이력 표 `klid_at.ls_schm_aplcn_hstry`

물리명·자료형은 행안부 공통표준용어/표준도메인을 따른다(정본 CSV 대조):
스키마 `SCHM` · 적용 `APLCN` · 이력 `HSTRY` · 일련번호 `SN` · 파일 `FILE` · 명 `NM` ·
버전 `VER` · 해시 `HASH`(사업) · 값 `VL` · 상태 `STTS` · 코드 `CD` · 등록자 `RGTR` · 일시 `DT`.

| 컬럼 | 자료형 | 뜻 |
|---|---|---|
| `SCHM_APLCN_HSTRY_SN` | `bigint` identity, PK | 스키마적용이력일련번호 |
| `APLCN_FILE_NM` | `varchar(200)` NOT NULL | 적용파일명 |
| `VER_NM` | `varchar(20)` NOT NULL | 버전명(`V33`) |
| `FILE_HASH_VL` | `varchar(64)` NOT NULL | 파일해시값(sha256) |
| `APLCN_STTS_CD` | `varchar(20)` NOT NULL | 적용상태코드(`SUCCESS`\|`FAILED`) |
| `RGTR_ID` | `varchar(100)` | 등록자ID(적용 수행자) |
| `REG_DT` | `timestamp` NOT NULL | 등록일시 |

부분 유니크 `uk_ls_schm_aplcn_hstry_ver (VER_NM) WHERE APLCN_STTS_CD='SUCCESS'` —
성공은 버전당 1회뿐이고 실패 기록은 여러 번 남을 수 있어야 재시도가 된다.

⚠ **이 표는 Flyway 마이그레이션이 아니라 설치 도구가 만든다.** `schema.sql` 에 없고 앱은 읽지 않으며
`flyway_schema_history` 와 무관하다.

### C. `deploy-update.sh`

**WAR 배포 자체는 다시 만들지 않고 `install/17-deploy-jboss.sh` 에 위임한다** — 그쪽이 컨텍스트
판정(WAR 안 `jboss-web.xml`)·JVM 옵션 배선·`.deployed`/`.failed` 판정을 이미 갖고 있다. 다시 구현하면
두 번째 진실원이 되어 반드시 갈린다.

이 스크립트가 더하는 것은 업데이트 회차에만 필요한 넷이다:

1. **순서 강제(DB 먼저)** — 미적용 증분이 하나라도 있으면 **WAR 를 올리지 않고 멈춘다.**
   반대로 DB 를 먼저 올리는 것은 안전하다(옛 WAR 는 새 표를 안 볼 뿐). **되돌릴 수 없는 쪽을 뒤에 둔다.**
2. **기존 WAR 백업** — 되돌릴 수단을 확보한 뒤에 바꾼다.
3. **실제 헬스 호출** — 17 은 확인용 명령을 화면에 찍어 주기만 한다. 업데이트 회차엔 그것으로 부족하다.
4. **`--rollback`** — 직전 백업 WAR 로 되돌린다. ⚠ **DB 는 되돌리지 않는다**(그 판단은 사람이 한다).

**백업은 파일만 뜬다. DB 는 뜨지 않는다** — 운영 DB 백업은 용량·시점·보관 정책이 현장 소관이고,
임의로 뜨면 디스크를 채우거나 "백업이 있다"는 잘못된 안심을 준다. 대신 배포 전에 확인만 묻는다.

### D. `16-load-schema.sh` 판정 보정

`existing` 개수 조회에서 `ls_schm_aplcn_hstry` **한 이름만** 제외한다.
이력 표는 `schema.sql` 에 없어 그대로 세면 **기대 +1** 이 되어 판정이 매번 "기대와 다릅니다"로 갈라진다.
⚠ 진짜 불일치를 가리는 예외가 아니다 — 이 이름 하나만 뺀다.

## §5 검증 (실측)

현장과 같은 조건(V31 동결본이 적재된 DB)을 PG16 컨테이너에 재현해 돌렸다.

| 단계 | 결과 |
|---|---|
| `--status`(적용 전) | 미적용 2건 정확히 식별 |
| 실제 적용 | `V32`·`V33` 성공 · `klid_at` 78 → 81 테이블 |
| **재실행(멱등)** | "적용할 것이 없습니다 — 최신입니다" |
| 오버레이 두 표 | `ls_portal_user_meta` · `ls_portal_user_evnt_anno` 생성 확인 |
| **`public` 오생성** | **0건** |
| 해시 불일치 방어 | 이력을 조작하니 의도대로 중단 |
| 구문 | `bash -n` 3파일 통과 (shellcheck 미설치) |

**구현 중 잡은 자체 혼입 결함 — 둘 다 실증 후 수정**

1. **fail-open** — 미적용 건수 파싱에 GNU 전용 `\+` 를 써서 다른 sed 에서 **빈 결과**가 나왔다.
   그대로 뒀다면 *미적용 2건인데 0 으로 읽혀 그냥 배포* 된다. 이 스크립트의 존재 이유인 순서 강제가
   **정확히 반대 방향으로** 무너지는 자리다. POSIX 정규식으로 바꾸고 **파싱 실패는 0 이 아니라 중단**으로
   만들었다.
2. **빈 배열 전개** — 옵션 없이 부르면 `"${arr[@]:-}"` 가 **빈 문자열 인자 하나**를 만들어, 위임받는
   배포 단계가 "알 수 없는 옵션"으로 즉시 죽었다. **옵션 없이 부르는 것이 기본 사용법**이라 그 경로가
   항상 깨져 있었다. `${arr[@]+"${arr[@]}"}` 가드로 두 자리를 고쳤다.

⚠ 둘 다 **`bash -n` 과 정상 경로 실행으로는 드러나지 않았다** — ①은 이 저장소의 개발 환경과 대상 환경의
sed 가 달라서, ②는 옵션을 준 채로만 시험해서다. 실패 방향을 직접 재현해야 잡히는 부류다.
