## §1 배경

### 무엇이 있었나

포털 채널 배포본은 관제 채널 배포본의 DB 를 읽지 않는다(`ADR-012`). 그래서 포털 회원이
**관제에서 검수 승인된 학습데이터**를 작업 소재로 쓰려면, 그 자산이 포털을 거쳐 우리에게
**파일로** 와야 한다. 그 조달 경로가 이번 대상이다.

직전 라운드(`CO-20260909-포털-2차회신-…`)에서 포털이 조달 창구의 응답 규격을 회신했고 우리는
그것을 `INT-014` v9 에 등재했다. 그러나 그때 **착수하지 못했다** — 3차 회신 §2 가 「진행 차단」으로
올린 이유가 있었다:

```
포털 → 저작도구 (정리 트리거) : datasetCode="DS-…", version="v3"   ← 문자열 코드
저작도구 → 포털 (소재 조회)   : GET .../datasets/{datasetId}/materials  ← 숫자 ID
                                            ↑ 잇는 수단이 없다
```

### 무엇이 바뀌었나

2026-09-10 포털이 규격 문서를 보내 **다른 진입 경로**를 열었다. 사용자가 포털에서
`/workspace/authoring?datasetId=4704` 로 진입하면 그 **숫자 식별자를 URL 로 직접 받는다.**
즉 트리거를 거치지 않고도 조달을 시작할 수 있다.

### ★ 착각하지 말 것 — 차단 사유는 «그대로 열려 있다»

이 문서가 연 것은 **사용자 진입 경로**다. 3차 회신 §2 가 막아 세운 **트리거 구동 조달 경로**는
여전히 잇는 수단이 없고 A/B 선택도 미회신이다. `INT-014` 「열린 항목」 절을 **해소됨으로 고치지 말 것.**

## §2 변경 요지

1. **FE** — 포털 채널 진입 시 `window.location.search` 에서 `datasetId` 를 읽어 우리 창구로 넘긴다.
2. **BE 창구 신설** — FE 가 `datasetId` 를 넘길 자리(규격 문서가 우리에게 넘긴 «우리 몫» 결정).
3. **BE 조달 클라이언트** — 포털 내부 창구를 `x-api-key` 로 호출해 소재 경로 목록을 받는다. 봉투 없는 평문 JSON.
4. **★ 경로 재검증** — 받은 절대경로를 그대로 열지 않고 `repoRootDir` 하위인지 **실경로로** 재검증한 뒤 그 실경로로 연다.
5. **zip 사본·해제** — 포털 소재영역은 읽기 전용. 우리 작업영역으로 복사해 해제하고 사본으로만 작업.

**범위 밖(다음 라운드)** — 해제한 산출물을 원장(`LS_DATA_RAW`·`LS_DATA_SRC`·`LS_DATA_LBL`)에 적재해
포털 라벨링 화면 소재로 잇는 것.

## §2-1 게이트② 확정 사항 (2026-09-10 사용자 확정, 구속)

| # | 결정 | 근거 |
|:-:|---|---|
| ① | **조달 base-url 을 `IntegrationEndpoint` 에 넣지 않는다** — 별도 설정 키로만 둔다 | 그 enum 5종은 **관리자 설정 화면**에서 주소를 바꾸는 대상인데 그 화면은 **포털 채널에 비노출**이다. 넣으면 정작 쓰는 포털에서는 안 보이고 관제 배포본에만 쓸모없는 항목이 뜬다 |
| ② | **`datasetId` 는 필수 진입 조건이 아니다** — 없거나 숫자가 아니면 **평소대로 「내 작업」** 으로 진입 | 포털 업로드·증강은 `datasetId` 없이 쓰는 정상 경로다. 안내·오류로 막으면 그 동선이 멀쩡한데 함께 죽는다 |
| ③ | **해제 위치는 저장소 기준경로 아래 조달 전용 서브트리** | 새 설정 키·새 NAS 프로비저닝이 필요 없고 `StorageSubtreePolicy` 규약과 같은 집에 앉는다 |

### ⚠ 메인이 정한 것 (사용자 확정 아님 — 되돌릴 수 있다)

**창구는 비동기다. 이번 라운드에 원장 표를 두지 않는다.**

- 규격 예시의 배포 zip 이 **1GB**(`fileSize: 1048576000`)다. 복사·해제를 요청 안에서 끝내면 타임아웃이 난다
  → **`POST` 202 착수 + `GET` 상태 조회** 두 창구
- 상태는 **파일시스템으로 표현**한다(임시 디렉터리에 풀고 완료 시 **원자적 rename**). 표를 만들면
  마이그레이션·표준용어 판정이 붙어 이번 범위를 넘고, **적재 라운드에 원장이 필요해지면 그때 두는 편이
  낫다**(지금 두면 적재 설계가 이 표에 끌려간다)
- ⚠ 이번 라운드엔 **화면에 보이는 것이 없다**(적재가 다음 라운드라 조달 결과를 쓰는 자리가 아직 없다).
  그래서 창구 모양의 사용자 가시성이 낮고, 되돌리기 비용도 낮다

## §8 별건 — 운영 조치 (이번 코드 범위 밖, 같은 연동 축이라 장부에 남긴다)

**포털의 정리 트리거 호출이 401 로 전건 거부되고 있다** (2026-09-10 실측 · 포털 로그
`POST …/v1/portal-system/dataset-cleanups → status=401`).

**원인 — 코드 결함이 아니라 값 미주입.**

| # | 실측 | 결과 |
|:-:|---|---|
| 1 | `PortalSystemApiKeyFilter` | 설정이 비면 `expectedKey=null` → 무조건 불일치 → 401 (fail-closed, 설계대로) |
| 2 | `application.yml` | `cleanup-api-key: ${PORTAL_CLEANUP_API_KEY:}` — 기본 빈 값 |
| 3 | 배포 템플릿 2종 | 둘 다 빈 값으로 출고 |
| 4 | 젠킨스 WAS 잡 | 그 변수가 **없다** |
| 5 | 3차 회신 §6 | `① cleanup x-api-key 값 \| 저작도구 \| 인프라 대기` — **발급·공유 자체가 미완** |

**외부에서 친 호출이 403(Apache)로 막힌 것은 정상이다** — 우리가 요청한 `Require ip` 허용목록이
실제로 적용됐다는 증거이며(`docs/operations/포털-아파치-설정-요청-20260910.md`), 포털 서버는 그
목록 안이라 통과해 우리 앱까지 도달했다. 포털 로그의 `(빈 본문)` 은 그쪽 클라이언트가 본문을 읽지
않은 것이다 — 우리 401 은 항상 JSON 본문을 싣는다(`SecurityConfig.writeError`).

**조치**: WAS 에 `PORTAL_CLEANUP_API_KEY` 주입 + 포털이 같은 값 송신 → 202.
**판별**: 기동 로그 `[PortalSystemApiKey]` 줄 — 「설정되지 않았습니다」=미주입 / 「설정됐습니다」=불일치 / **줄 없음**=배포 WAR 이 창구 이전 판.
