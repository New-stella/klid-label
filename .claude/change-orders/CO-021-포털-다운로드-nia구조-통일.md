# CO-021 — 포털 데이터마트 다운로드 산출 구조를 검수 승인 export(NIA COCO 확장)와 통일한다

- 상태: 📝 작성
- 대상 도메인: 공유기반(db) · DOMAIN-010(라벨링 — dataset/export) · DOMAIN-013(포털) · 프론트
- 생성일: 2026-08-26
- 선행: CO-019(포털 프레임 이동) · CO-020(포털 범위 ADR-013 개정)

---

## §1 배경

포털 사용자가 데이터마트 영상의 작업 데이터를 ZIP 으로 내려받으면, 그 산출물이 저작도구가 검수
승인 시점에 만드는 학습데이터 export 와 **다른 구조**로 나온다.

| 축 | 검수 승인 export | 포털 ZIP (현행) |
|---|---|---|
| 폴더 | `{영상루트}/v{n}/{orgnl\|deid}/` | `{rawSn}/` |
| 라벨 | 프레임마다 `0000.json` (NIA 최상위 9키) | `labels.json` 1개 (자체 shape) |
| 좌표 | `bbox` / `polygon` / `keypoints` | `points[[x,y]]` |
| 이미지 | `0000.jpg` (원본·비식별 2벌) | `frames/0000.jpg` (비식별 1벌) |
| 영상 | 없음 | `video.{ext}` |

**이것은 코드 결함이 아니다** — 구현은 `API-203` 원문 그대로이고 드리프트 0건이다. 어긋난 것은
**설계끼리**이며, 그래서 코드가 아니라 설계를 먼저 고친다.

통일하는 근거는 둘이다.

1. **재적재 왕복 자산 요구를 반만 충족한다.** `CLAUDE.md` 의 export 개인정보 정책이 *"export JSON 이
   다시 읽혀 적재되는 자산이 된다(차후 데이터마트를 업로드하는 기능)"* 를 확정 근거로 삼고 있는데,
   포털 산출물은 스키마가 달라 그 경로에 들어갈 수 없다.
2. **같은 라벨의 좌표 표현이 두 형식으로 갈려 있다.** 이 저장소가 반복해서 겪은 「두 번째 진실원」
   패턴이며, 한쪽만 갱신되면 조용히 어긋난다.

## §2 변경 요지

포털 ZIP 의 라벨 산출을 **프레임마다 `{FRM_NO 4자리}.json`(NIA 9키)** 으로 바꾸고 `labels.json` 을
제거한다. 메타 블록은 **검수 승인 export 와 완전히 같은 조달 규칙**을 따른다(사용자 확정 2026-08-26).

착수 순서도 함께 확정했다 — **A(이 CO) 를 먼저 하고, 포털 전용 메타 편집(별건)은 뒤에 온다.**
따라서 이 CO 의 메타 조달처는 **검수 승인 시점 동결 스냅샷 하나**이며, 포털 편집분 오버레이는
그 별건이 생길 때 조달처를 하나 더 얹는 방식으로 확장한다.

### 확정 요구

| # | 요구 |
|---|---|
| R1 | 프레임마다 `{FRM_NO 4자리 zero-pad}.json`(NIA 9키) 산출. 파일명 규칙은 기존 단일 지점 `ExportFileNaming` 재사용 |
| R2 | `labels.json` 제거. 두 형식 병존 금지 |
| R3 | `LS_PORTAL_USER_LABEL` 에 `LBL_ID`·`TRCK_ID` 추가(Flyway) + 포털 라벨 저장 경로(BE·FE)가 그 값을 실어 보낸다 |
| R4 | 이미지는 비식별벌만 유지. NIA `image`/`video` 블록도 비식별(deid) kind 기준 |
| R5 | 메타 블록(개인정보 3필드·`event_id`·`vd_description`)을 export 와 동일한 조달 규칙으로 채운다 |
| R6 | 순서는 설계 ITEM 확정(Phase 3.6) → 코드 반영 → `@design` 추적 |

### ★유지할 것 (통일 대상 아님 — 되돌리지 말 것)

- ZIP 최상위 `{rawSn}/` 접두, 파일명 `portal-video-{rawSn}-{yyyyMMdd}.zip`(서버 생성 고정명)
- 게이트 3종 **순서** 403(데이터마트 미노출) → 412(비식별 신고 구간) → 410(본인 저장 라벨 0건).
  이 순서는 오라클 누출 차단(CWE-209)이라 바꾸지 말 것
- **라벨 병합 규칙 — 입도는 「프레임 단위」다 (2026-08-26 코드 실측 정정)**: 프레임마다 그 프레임의
  본인 저장분이 (좌표가 있는 행으로) 1건이라도 있으면 그 프레임은 본인 것만, 없으면 그 프레임만
  데이터마트 원본. 판정 단일 원천 `PortalLabelService.mergeFrameItems` 재사용.
  ⚠ **구 서술 폐기** — *"본인 저장분이 1건이라도 있으면(영상 전체에서) 본인 것만"* 은 **사실과 다르다.**
  그건 영상 단위 전부-아니면-전무이고, 실제 규칙은 프레임마다 독립 판정이라 **한 영상 안에서 어떤
  프레임은 본인 것, 어떤 프레임은 원본**이 될 수 있다. 프레임별 문서로 바뀌면 이 입도가 **문서마다
  드러나므로** 잘못 이해하면 산출물이 통째로 어긋난다. 판정 근거 = `mergeFrameItems` javadoc
  (*"프레임 단위 … 다운로드가 같은 규칙을 프레임 전체에 적용"*) + `@design AC-035`
- 트랜잭션 경계 분리(`PortalDatamartDownloadTxService` = DB 단계 readOnly /
  `PortalDatamartDownloadService` = 경로검증·파일 open·스트리밍은 트랜잭션 밖). 한 빈으로 합치지 말 것
- `StreamingResponseBody` 스트리밍(메모리 적재 금지), 동시 스트리밍 상한 `Semaphore`,
  `Cache-Control: no-store`, 경로 판정기 2축(프레임=`StorageSubtreePolicy.verifyDeidentifiedFile` /
  영상=`VideoArtifactRootResolver`), `openNoFollow`
- **원본 폴백 금지**(`AC-034`) — 포털은 비식별본만 서빙한다는 불변 규칙

## §3 도메인별 변경 상세

### 공유기반 선처리 (메인 직접, Phase 3.5)

**Flyway `V20__add_portal_user_label_master_and_track.sql`**

`LS_PORTAL_USER_LABEL` 에 두 컬럼 추가:

| 물리명 | 타입 | 근거 |
|---|---|---|
| `LBL_ID` | `BIGINT` (nullable) | `LS_LABEL.LBL_ID` 와 동일 — 라벨 마스터 참조. NIA `annotations[].category_id` 의 조달처 |
| `TRCK_ID` | `VARCHAR(30)` (nullable) | `LS_DATA_LBL.TRCK_ID` 와 동일 — NIA `annotations[].track_id` 의 조달처 |

- **표준용어 신규 등록 불필요** — 둘 다 기존 자산의 물리명·타입·크기를 그대로 재사용한다
  (신규 약어 생성 0). 타입·크기를 임의로 바꾸지 말 것.
- **기존 행은 백필하지 않는다.** null 로 두고 재저장 시 자연 복구된다. 라벨명 소급 매칭은
  동명이인·비활성 마스터 오매칭 위험이 있어 채택하지 않는다 — `CLAUDE.md` 의 `labelId=null` 행
  처리 선례와 같은 축이다.
- **FK 를 걸지 않는다** — 포털 전용 저장소는 내부 파이프라인과 분리 운영이고, 마스터가 비활성화돼도
  포털 사용자의 과거 작업이 삭제되면 안 된다. 참조 무결성은 조회 시점 join 으로 처리한다.
- 착수 직전 **Flyway 번호를 재확인**할 것. 확인 시점(2026-08-26) 기준 로컬·`origin/main`·형제
  워크트리 5곳 전부 `V19` 가 최신이라 `V20` 이 안전하나, 이 저장소는 번호 선점 사고 이력이 있다.
- **`FlywaySquashBaselineIT` 3곳을 손수 갱신**해야 한다. 파일 목록이 코드포인트 순이라
  `V11__` 이 `V1__baseline` 보다 앞에 온다 — 정렬 주의.

### DOMAIN-010 (라벨링 — `dataset/export`) — `klid-d010-implementer`

**① NIA 컨텍스트 조립기 공유 추출 (R5 의 핵심)**

현재 `DatasetExportTxService.doExport` 안에 **NIA 컨텍스트 조달 블록이 private 으로 갇혀 있다.**
포털이 같은 값을 내려면 이 블록을 재사용 가능한 컴포넌트로 빼야 한다.

조달 축(전부 `rawSn` 단위 1회 조회):

| 입력 | 조달처 |
|---|---|
| `meta` | `LsDatasetVideoMeta` 활성 스냅샷 |
| `raw` | `LsDataRaw` |
| `ingestEvntId` | `IngestSourceRow.getEvntId()` (`video.event_id` 의 유일한 조달처) |
| `srcPrivacy` | `resolveSourcePrivacy(raw, ingest, dataMetas)` |
| `vdDescription` | `VlmDescriptionPolicy.resolve(dataMetas)` |
| `usedLabels` | `loadUsedLabels(allLabels)` |
| `eventAnnotation` | `meta.getEvntAnnoCn()` 동결본 파싱 |
| `deidVideoPath` | 최신 SUCCEEDED `LsDeidentProcLog.getDeIdntfFilePathNm()` |

**★복제하면 반드시 깨지는 지점이 둘이다 — 추출로만 해결된다.**

1. **조달 순서 의존**: 원천 축(`resolveSourcePrivacy`)은 반드시 **`dataMetas` 로드 뒤**여야 한다.
   외부 산출물 이관 영상은 관제 인입 행이 없어 그 값이 메타에 원문 보관돼 있기 때문이다.
   **순서를 되돌리면 이관 영상의 원천 3필드가 전부 null 로 산출된다** (기존 코드 주석이 명시).
2. **파생영상 판정**: `raw` 가 null 이거나 파생이면 `SourcePrivacyMeta.NONE` 이며 그때 원천 3필드는
   **두 블록 모두 null 이 정상**이다(결손 아님). 상수를 대신 싣지 말 것.

- 추출한 조립기는 **`DatasetExportTxService` 와 포털이 같은 빈을 주입**해 쓴다.
- **기존 export 산출 결과가 바이트 단위로 달라지면 안 된다** — 추출은 리팩토링이며 동작 변경이
  아니다. 회귀 가드로 이를 고정할 것.
- `prepareContext` 는 3~8인자 오버로드 체인이다. **축소 오버로드(3인자)를 쓰면 메타 필드가 조용히
  null 이 되므로**, 조립기는 항상 8인자 경로를 탄다.

**② 포털 라벨 → NIA annotation 어댑터**

`LabelToAnnotationMapper.toAnnotation(LsDataLbl, Integer)` 는 **내부 파이프라인 엔티티만** 받는다.
포털 저장분은 `LsPortalUserLabel` 이라 타입이 다르다.

- 두 엔티티가 **공통으로 제공할 수 있는 것**(`lblTypeCd`·`labelNm`·`pointCn`·`labelId`·`trackId`)을
  받는 좁은 입력 형태로 매핑기를 확장하거나, 포털 엔티티를 그 형태로 옮기는 어댑터를 둔다.
- **판정 로직(bbox/polygon/keypoints 분기·좌표 파싱)을 복제하지 말 것** — 복제하면 두 산출물의
  좌표 해석이 갈린다. 이 CO 가 없애려는 바로 그 결함이다.
- `LBL_ID`·`TRCK_ID` 는 R3 의 컬럼 추가에 의존한다. 그 전에는 null 이며, **null 을 지어내 채우지
  않는다**(기존 행은 백필 대상이 아니다).

**불변**: `ExportFileNaming.jsonFileName(frameNo)` / `imageFileName(frameNo)` 를 그대로 쓴다.
포털용 파일명 규칙을 새로 만들지 말 것.

### DOMAIN-013 (포털) — `klid-d013-implementer`

**① 다운로드 산출 구조 전환**

- `PortalDatamartDownloadTxService` 가 현재 **`LsDatasetVideoMeta` 를 전혀 읽지 않는다**
  (`portal/` 전체에 참조 0건, 리포지토리는 raw·src·lbl·portalUserLabel 넷뿐). 위 조립기를 주입해
  컨텍스트를 확보한다.
- 프레임마다 NIA 문서를 만들어 ZIP 에 **`{rawSn}/frames/{FRM_NO 4자리}.json`** 으로 넣는다 —
  **이미지와 같은 자리에 이름만 다른 짝**으로 둔다(`frames/0000.jpg` ↔ `frames/0000.json`).
  ⚠ **구 서술 폐기(2026-08-26 실측 정정)** — 이 자리에 `{rawSn}/{FRM_NO 4자리}.json`(frames 없이
  루트 바로 아래)이라고 적혀 있었으나 **API-203 과 어긋난다.** 진실원은 ITEM 이며 API-203 이
  `frames/` 아래 짝으로 두는 근거까지 명시하고 있다. 또 현행 포털 ZIP 의 이미지가 이미
  `frames/` 아래라, 루트로 옮기면 이 변경의 범위가 아닌 이미지 경로까지 함께 바뀐다.
- **`labels.json` 과 `PortalDatamartDownloadResponse` 의 자체 shape 를 제거**한다(R2).
  제거로 참조가 끊기는 곳을 함께 정리할 것.
- **`build(context, frame, kind)` 의 kind 는 항상 비식별(deid)** 이다(R4). 원본 kind 로 만들면
  NIA `image`/`video` 블록에 원본 절대경로가 실려 `AC-034` 를 정면으로 위반한다(CWE-359).

**② 포털 라벨 저장 경로에 두 값 배선**

- `PortalUserLabelRequest` 에 `labelId`·`trackId` 를 추가한다(둘 다 선택).
- `PortalLabelService` 저장 경로가 그 값을 `LsPortalUserLabel` 에 적재한다.
- **`labelId` 를 신뢰하지 말고 서버에서 검증**한다 — 활성 라벨 마스터에 실재하는 id 인지 확인하고,
  아니면 거부하거나 null 로 떨군다(FE 요청을 그대로 믿으면 임의 값이 `category_id` 로 나간다).
  `AutolabelOnlineService.resolveDetectClasses` 가 같은 원칙을 쓰는 선례다.
- `trackId` 는 `VARCHAR(30)` 상한을 입구에서 검증한다(넘으면 INSERT 시점 DB 오류로 새어 500 이 된다).

**불변**: 게이트 3종 순서 · 병합 규칙 · 트랜잭션 경계 · 스트리밍/동시성/캐시 헤더/경로 판정기
(§2 「유지할 것」 전부).

### 프론트 (SCREEN-029 포털 라벨링) — `klid-web-implementer`

- 포털 라벨 저장 시 `labelId`·`trackId` 를 요청에 실어 보낸다.
- **`labelId` 조달은 내부 라벨링 화면의 확정 규칙을 그대로 따른다** — `CLAUDE.md` 의
  「라벨 표시 색상의 단일 진실원」 절이 *"마스터 연결의 실체는 `labelId` 다 — 라벨을 만들거나 분류를
  바꾸는 모든 경로가 `labelId` 를 채워야 한다"* 를 구속 규칙으로 두고 있고, `classId` 만 채우면
  저장 후 마스터 연결이 끊기는 실사고가 이미 있었다. 포털도 같은 함정에 그대로 노출된다.
- 라벨명 → 마스터 PK 역해석이 필요하면 `resolveLabelIdByName`(fail-closed — 0건·2건 이상이면 null)
  을 재사용한다. 추측으로 채우지 말 것.
- **백엔드 먼저, 프론트 뒤**(계약 의존).

| 기존 포털 라벨 행 | `LBL_ID`·`TRCK_ID` 가 null 이라 그 프레임의 `category_id`·`track_id` 도 null 로 나간다. **재저장 시 자연 복구**되며 백필하지 않는다 |
| 데이터마트 원본 폴백분 | 본인 저장분이 없어 `LS_DATA_LBL` 로 폴백된 프레임은 두 값이 **정상 채워진다** |

### ★R3 이 무너뜨리는 「근거」 하나 — 결론은 유지한다 (Critical)

위키가 **「포털 트랙 rename/머지 미제공」** 의 근거를 셋으로 대고 있다:

1. `LS_PORTAL_USER_LABEL` 에 `trackId` 컬럼 **부재** ← **R3 이 이것을 무너뜨린다**
2. 포털 프레임 라벨 로더가 `trackId` 를 **null 로 스트리핑**
3. 자동추적의 `trackId` 는 화면 세션 안에서만 쓰이고 저장되지 않음

**근거 ①이 사라져도 결론(트랙 편집 미제공)은 그대로 유지한다.** `ADR-013` v9 개정(CO-020)에서도
트랙 rename/merge 는 미제공 유지 대상으로 명시됐다. 이 저장소가 반복해서 겪은 *"근거가 무너졌다고
결론을 뒤집는"* 패턴을 여기서 차단한다 — **위키의 근거 서술만 정정하고 결론은 건드리지 않는다.**

### ★그 결과 드러난 진짜 설계 갈림 — `TRCK_ID`·`LBL_ID` 는 「편집」이 아니라 「보존」을 위한 것이다

근거 ②(로더가 `trackId` 를 null 로 스트리핑)가 그대로면 **화면이 그 값을 애초에 받지 못하므로
저장 요청에 되돌려 보낼 값이 없다.** 그러면 R3 의 컬럼은 포털 저장분에서 영원히 비어 있다.

이 컬럼들이 풀려는 문제의 실체는 **원본 연결의 보존**이다:

> 데이터마트 원본에서 불러온 라벨을 포털 사용자가 수정해 저장하면, 원본이 갖고 있던 **마스터
> 연결(`LBL_ID`)과 트랙 연결(`TRCK_ID`)이 저장 왕복에서 끊긴다.**

따라서 성립 조건은 **라벨 조회 응답이 두 값을 실어 보내고, 화면이 그것을 그대로 보존해
되돌려 주는 것**이다. 화면에 **노출하지는 않는다** — 트랙 번호 변경 UI 는 계속 숨긴 채,
값만 왕복시킨다. 결론(편집 미제공)과 충돌하지 않는다.

⚠ 이것은 `API-110`·`API-083` 응답 확대를 뜻하므로 **계약 변경**이다. §6 에서 판정 대상으로
올려 뒀으며, 판정 결과에 따라 R3 의 실효성이 갈린다.

### ★형제 경로에 같은 구조가 있다 — 이번 범위 밖으로 둔다 (근거 명시)

`ERD-028`(포털 **업로드 자산** 라벨 `LS_PORTAL_ULD_LBL`)도 라벨 유형 코드·라벨명·좌표만 보유해
같은 결손을 갖는다. 그러나 **이번 범위에 넣지 않는다**:

- 이 CO 의 대상은 **데이터마트 작업 데이터** 내려받기다. 포털 업로드 자산 내려받기는 **별개 축**
  이며, 테스트케이스 카탈로그가 두 축을 두고 *"혼동 금지"* 를 명시하고 있다.
- 업로드 자산은 본인이 올린 것이라 **데이터마트 원본에서 불러온 연결이 애초에 없다.** 위 「보존」
  논거가 성립하지 않으므로 컬럼을 추가할 근거도 다르다.

⚠ 다만 이 저장소는 **같은 결함이 형제 경로에 남아 있던 전례**가 있다(대용량 전송 상한이 한쪽만
고쳐졌던 건). 범위 밖으로 두는 것은 *"필요 없다"* 가 아니라 *"근거가 다르므로 따로 판단한다"* 는
뜻이며, 별건으로 올린다.

### 설계 결손 후보 (이번 라운드에서 드러남 — 지어내지 않고 남긴다)

- **동시 산출 상한**이 `API-203` 본문에 **서술이 없다.** 구현에는 실재하나(요청량 제한 429 와는
  다른 축이다), 설계에 없으니 이번에 지어내 채우지 않았다. 별도 ITEM 소관인지 결손인지 판정 필요.
- **스트리밍 산출(메모리에 통째로 담지 않는다)** 도 명시 서술이 없고 중단 처리 문단이 함축할 뿐이다.

이번 라운드는 「추가만」 축이라 건드리지 않았다.

| ITEM | 잔존 |
|---|---|
| `API-110` | 최상위 서술·응답 설명에 응답 클래스명 · 화면 컴포넌트명 · 내부 전용 필드명 |
| `AC-035` | 비고에 코드 심볼 인용 |

⚠ `AC-034` 는 이번 라운드에서 담당이 같은 종류의 인용을 **사양 어휘로 바꿨다**(조달 축의 실질은
보존). 그 정리를 이번 범위로 인정할지는 판단이 필요하다 — 인정하면 위 둘도 같은 기준으로 함께
정리하는 것이 일관되고, 인정하지 않으면 `AC-034` 만 축이 갈린 상태가 된다.

### 구현 추적이 사양보다 뒤처진 상태 (기록만)

`API-082` 의 구현 추적이 완료로 남아 있는데 이번 라운드로 **사양이 코드보다 앞섰다.**
구현 라운드가 끝나면 자연히 맞춰지므로 지금 손대지 않는다 — 다만 그 사이에 이 값을 근거로
「이미 구현됨」이라 판단하지 말 것.

### 확정 — 라운드 2 스텝 1 (응답 3종)

| ITEM | 버전 | 추가 위치 |
|---|---|---|
| `API-110` | v3 → **v4** | 프레임 라벨 로더 200 응답의 라벨 원소 |

세 응답의 형태가 맞았다. `API-110` 확대로 **왕복 보존의 성립 조건이 닫혔다.**

⚠ **병렬 실행이 만든 오관측 1건 — 기각함**: `API-082` 담당이 *"형제 조회 응답 두 건이 아직
두 값을 담지 않아 확정과 어긋난다"* 고 보고했으나, 이는 **그 담당이 작업을 시작한 시점의 상태**다.
병렬로 돌아 서로의 결과를 보지 못했다. 세 담당의 변경 필드 목록을 대조하면 세 건 모두 해당
스키마 경로에 두 값을 추가했다. **그 보고를 근거로 재큐잉하지 말 것**(중복 작업이 된다).

> 이 패턴은 앞으로도 재발한다 — 같은 라운드에서 병렬로 도는 담당들은 서로의 결과를 못 보므로,
> 「형제 ITEM 이 아직 안 됐다」는 관측은 **메인이 완료 보고를 대조해 판정**해야 한다.

축을 섞으면 어느 결정이 무엇을 바꿨는지 추적이 끊긴다.

  하고 산출 문서의 분류·트랙 식별자를 채운다. **값이 있다는 것과 편집할 수 있다는 것은 다른 축이니
  근거가 무너졌다고 결론을 뒤집지 말 것.**
- 같은 근거가 **같은 파일에 3곳 복제**돼 있어 함께 정정했다(한 곳만 고치면 다음 감사가 나머지를
  다시 잡는다 — 이 저장소의 「결정이 층마다 따로 적힌다」 패턴).
