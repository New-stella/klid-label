## §1 배경

### 증상 (사용자 신고, 2026-09-01)

246(dev)에서 **관리자로 접속하면 검수자 메뉴가 전부 보이는데, 실제로 그 메뉴에 들어가면 모두 "권한이 없습니다"** 가 떴다. 시스템 설정 화면은 틀만 뜨고 "시스템 설정을 불러올 수 없습니다" 로 끝났다.

### 근본 원인 (246 실서버 실측으로 확정)

원인은 **다섯 단계로 이어진 사슬**이며, 마지막 단계만 보면 오진한다.

| # | 사실 | 근거 |
|---|---|---|
| 1 | 인가 역할의 진실원은 JWT `role` 클레임이 **아니라** DB `LS_USER_ROLE` 이다 | `common/security/JwtAuthenticationFilter` 역할 조달부 (클레임은 인가에 쓰지 않는다) |
| 2 | dev 토큰 발급 창구는 **dev 프로파일(246)에서도 열려 있다** | 246 에서 `POST /v1/dev/tokens` 201 실측 |
| 3 | 그런데 dev 계정의 역할 시드는 **`@Profile("local")` 전용**이라 dev 환경에 도달하지 않는다 | `dev/../DevSeedRunner.java:55` |
| 4 | 시드 파일에는 `9001, admin1, 박관리, ADMIN` 이 **이미 있다**(2026-08-28 추가). 그런데 246 DB 에는 1001·2001·3001 만 있고 **9001 이 없었다** | `dev-seed.sql:85,101` vs `klid-pg-dev` 실측 |
| 5 | 역할 없는 9001 로 진입하자 `AutoWorkerRegistrar` 가 **WORKER 로 등록**했고, `insertRoleIfAbsent` 가 `ON CONFLICT DO NOTHING` 이라 그 뒤로 **영구 WORKER** 가 됐다 | `klid-pg-dev` 에 `user_no=9001, role_cd=WORKER, reg_dt=2026-08-31 09:52` |

그 결과 **프론트는 토큰 클레임(ADMIN)으로 메뉴를 그리고 백엔드는 DB(WORKER)로 인가**해, 메뉴는 전부 보이는데 API 는 전부 막히는 상태가 됐다.

### 실측 서명 (승격 전, ADMIN 토큰 · 246)

| 창구 형태 | 응답 |
|---|---|
| `hasAnyRole('REVIEWER','WORKER')` — `/v1/videos` · `/v1/notices` · `/v1/manage/labels` | **200** |
| `hasRole('REVIEWER')` — `/v1/manage/configs` · `/v1/users` · `/v1/reviews` · `/actuator/metrics` | **403** |

정확히 **WORKER 권한의 모습**이다.

### ★ 배제된 가설 — 다시 조사하지 말 것

**역할 계층(`RoleHierarchy`)은 정상이다.** `Role.INHERITS` · `RoleHierarchy` 파생 · `SecurityConfig` 수동 주입 · `TokenClaims.hasRole` 전부 올바르다. 9001 을 ADMIN 으로 승격한 뒤 위 403 창구 6개가 **전부 200** 이 된 것이 그 증거다.

⚠️ 위 표에서 `hasRole` 만 막히는 것을 보고 **「Spring Security 가 `hasRole` 에만 계층을 안 먹인다」고 오판하기 쉽다.** 실제로 이번 조사에서 그 오판을 한 번 거쳤다. 그 패턴은 계층 결함이 아니라 **주체가 WORKER 라서** 생긴 것이다.

### 이미 완료된 운영 조치 (코드 수정 대상 아님)

246 에서 관리자 부트스트랩 창구(`POST /v1/auth/role-claim`)로 9001 을 ADMIN 으로 승격해 증상은 해소됐다. 승격 후 위 6개 창구 전부 200 을 재실측했다.

## §2 변경 요지

**dev 로그인이 발급하는 표준 계정(`DevTokenService` 의 역할별 기본 `USER_NO`)을 작업자 자동 등록 대상에서 제외한다.**

- 그 계정들은 dev 편의를 위해 **역할이 시드로 주어지는 것이 전제**인 계정이다. 시드가 없는 환경에서 자동 등록이 빈자리를 WORKER 로 메우면, **고른 역할과 실제 인가가 어긋난 채 굳어** 이번 증상이 된다.
- 제외하면 그 계정은 **역할 없음(null)** 으로 남아 관리자 부트스트랩 화면으로 유도된다 — 이는 **설계 의도와 일치**한다(`CLAUDE.md`: *"배포 직후 ADMIN 은 0명이라 누군가 부트스트랩으로 최초 관리자를 만들 때까지 관리 기능이 잠긴다"*).
- **운영 경로(관제·포털 인계 토큰)의 자동 등록 동작은 그대로 둔다.**

## §3 도메인별 변경 상세

### DOMAIN-001 (사용자·권한) — `klid-d001-implementer`

**대상**
- `backend/src/main/java/kr/co/cudo/authoring/user/service/AutoWorkerRegistrar.java` (판정 추가 지점 1순위)
- `backend/src/main/java/kr/co/cudo/authoring/dev/service/DevTokenService.java` (역할별 기본 `USER_NO` 상수 보유 — `DEFAULT_USER_NO_REVIEWER=1001` · `_WORKER=2001` · `_PORTAL=3001` · `_ADMIN=9001`)

**변경**

1. **dev 표준 계정은 자동 등록하지 않는다.** `AutoWorkerRegistrar.registerAsWorker(userNo, userNm)` 가 dev 표준 `USER_NO` 집합에 해당하면 **아무것도 하지 않고 `null` 을 반환**한다(= 역할 미배정 상태 유지). 기존 조기 반환(`userNo == null` · `existsById` · 트랜잭션 실패)과 **같은 계약**이라 호출부(`JwtAuthenticationFilter`)는 바꿀 필요가 없다.

2. **판정의 단일 지점을 만든다.** dev 표준 `USER_NO` 집합이 지금 `DevTokenService` 의 `private static final` 에만 있다. `AutoWorkerRegistrar`(user 패키지)가 그것을 참조하려면 **공용 위치로 승격**해야 한다. 상수를 두 곳에 복제하지 말 것 — 복제하면 dev 계정이 늘 때 한쪽만 갱신돼 같은 결함이 재발한다. `DevTokenService` 는 승격된 그 상수를 쓰도록 고친다(값은 불변).

3. **제외는 dev 로그인이 켜진 환경에서만 적용한다.** 판정을 `authoring.dev.login.enabled` 에 연동해, 그 토글이 꺼진 운영 형상에서는 **제외 자체가 동작하지 않게** 한다. 근거: prd 에는 그 `USER_NO` 를 쓰는 실제 사용자가 존재할 수 있고, 그 사용자가 자동 등록에서 조용히 빠지면 **운영 정책이 훼손**된다. 토글이 꺼져 있으면 종전과 100% 동일하게 동작해야 한다.

**불변 (깨면 안 되는 것)**

- **운영 정책 「역할 없는 내부 채널 진입자는 작업자로 자동 등록」은 유지**한다(`AC-1016`). dev 표준 계정 **외** 진입자의 동작은 한 글자도 바뀌면 안 된다.
- **「이미 부여된 역할을 덮어쓰지 않는다」** 유지 — `existsById` 조기 반환을 제거하지 말 것.
- **관리자 부트스트랩 정책을 우회하는 길을 새로 만들지 않는다.** 이 변경은 역할을 **부여하지 않는** 방향이라 우회가 생기지 않는다. dev 경로가 DB 에 ADMIN 을 심는 설계로 바꾸지 말 것(그건 무인증 창구가 최고 권한을 자가부여하는 길이 된다).
- **dev 토큰 창구의 prd 이중 차단**(`authoring.dev.login.enabled` 빈 부재 + permitAll 매처 부재)을 약화시키지 말 것.
- `JwtAuthenticationFilter`(공유기반 `common/`)는 **건드리지 않는다** — 계약이 같아 수정이 불필요하다.

**주의**

- ⚠️ **제외 대상은 ADMIN(9001)만이 아니라 4종 전부**다. 1001·2001·3001 도 시드가 없는 환경에서는 같은 방식으로 어긋난다(REVIEWER 를 골랐는데 WORKER 로 굳는 식). 246 은 그 셋의 역할이 이미 있어 `existsById` 로 걸러지므로 **영향 없다**.
- ⚠️ **인지·수용한 대가**: 시드가 없는 dev 환경에서 dev 로그인 계정은 **역할이 없는 상태**가 된다. 관리자는 부트스트랩 1회로 만들고, 검수자·작업자 역할은 그 관리자가 사용자 관리 화면에서 부여한다. 이는 실제 운영 흐름과 같다.
- ⚠️ **local 은 영향 없다** — 시드가 `DO UPDATE` 로 역할을 강제 적용하므로 `existsById` 단계에서 이미 걸러진다.

**수용기준**

1. dev 로그인 토글이 켜진 환경에서 dev 표준 `USER_NO`(1001·2001·3001·9001)로 진입해도 `LS_USER_ROLE` 에 행이 **생기지 않는다**.
2. dev 표준 `USER_NO` 가 **아닌** 내부 채널 진입자는 종전대로 WORKER 로 자동 등록된다.
3. dev 로그인 토글이 **꺼진** 형상에서는 dev 표준 `USER_NO` 여도 종전대로 자동 등록된다.
4. 이미 역할이 있는 사용자의 역할은 어느 경우에도 덮이지 않는다.
5. dev 표준 `USER_NO` 집합이 `DevTokenService` 와 판정기에 **복제돼 있지 않다**(단일 지점).

### 공유기반 선처리 (Phase 3.5)

**해당 없음.** 스키마 변경 없음, `common/`·`batch/`·앱 진입점 변경 없음. 상수 승격이 `dev/` → 공용 위치로 가는데, 이는 도메인 에이전트의 `code_root`(`auth/` `user/`) 밖일 수 있다 — 그 경우 배치 위치를 게이트에서 확정한다.
