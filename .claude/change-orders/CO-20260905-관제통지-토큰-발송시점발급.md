# CO-20260905 관제 통지 x-access-token — 정적 장수명 → 발송 시점 동적 발급(관제 규칙 정합)

## §1 배경 / 왜

저작도구 → 관제 아웃바운드 완료/수정 통지(`ControlNotifyClient` → `POST {base}/api/data-set/v2/jobs/{jobId}/notify-completed|notify-updated`)는 관제 inbound SPI 가 **`x-access-token` 헤더의 JWT 를 검증**한다(정적키→401 "잘못된 형식의 토큰", 유효 서명 JWT→인증통과).

**실측(2026-09-05, 실제 관제 로그인 토큰 디코드)** — 관제 발급 토큰 규칙: **alg=HS256 · iss="klid-auth" · exp=iat+3600(1시간) · 공유 시크릿(우리 `JWT_SECRET` 과 동일) HMAC 서명**. 관제 통지 엔드포인트는 우리 시크릿 서명 JWT 를 수용함(우리 발급 토큰으로 호출 시 401 이 아니라 **422 업무검증**(9필드) 단계 도달 — 인증 통과 확인).

**현재 상태(임시)**: 246 은 우리가 발급한 **HS512 · exp 2046년(20년) 정적 토큰**을 `authoring.control-notify.token`(→ `WebClientConfig.controlNotifyWebClient` 의 `defaultHeader`)에 고정해 동작 중. 문제 둘: ①20년 고정 자격증명 유출 시 장기 유효(CWE-798) ②관제 규칙(HS256·iss·짧은 수명)과 형식 불일치.

**결정(사용자 확정 2026-09-05)**: 통지 토큰을 **발송 시점에 매번 새로 발급**하고 규칙을 관제와 동일하게 맞춘다. 통지는 **사용자 요청 스레드가 아니라 백그라운드**(디바운서 flush·폴백 재시도 잡·export 복구기)에서 나가므로 사용자 인계 토큰을 실을 수 없고(컨텍스트 없음+만료), **우리가 서비스 토큰을 발급**하는 것이 유일하게 성립한다.
- ⚠ **수명은 하드코딩 금지** — 관제 수명 정책이 바뀔 수 있으므로 우리 토큰 exp 도 **설정값**(짧은 기본)으로 둔다.

## §2 변경 요지

`WebClientConfig.controlNotifyWebClient` 의 **정적 `defaultHeader(x-access-token)` → 발송 시점 동적 발급 `ExchangeFilterFunction`** 으로 교체.
- 발급 규칙: **HS256 · iss=`klid-auth` · exp=now+`token-ttl-seconds`(설정, 짧은 기본 예 300s) · 공유 시크릿(`JWT_SECRET`) HMAC**. sub 는 서비스 식별자(예 `klid-authoring-notify`). 관제가 요구하지 않는 사용자 클레임(role·channel·name)은 넣지 않아도 되나, 설계에서 「관제 토큰과의 형식 정합」 관점에서 최소 포함 여부 판단.
- **하위호환**: `authoring.control-notify.token` 정적 설정값이 **있으면 그것을 우선**(관제팀이 별도 토큰을 주는 경우), 없으면 동적 발급. 둘 다 없고 시크릿도 없으면 헤더 미부착(기존 fail-safe 유지).
- **보안**: 시크릿·토큰 값 로그 노출 금지(CWE-532). 발급 실패는 통지를 죽이지 않고 fail-safe(미부착/폴백 큐)로 흡수하되, enabled 인데 발급 불가면 기동/발송 WARN.

## §3 도메인별 변경 상세

### DOMAIN-016 (관제 통지) — `klid-d016-implementer`
- **대상 파일**:
  - `common/config/WebClientConfig.java` — `controlNotifyWebClient` 빈: `builder.defaultHeader(CONTROL_NOTIFY_TOKEN_HEADER, token)` 제거하고, **발송 시점 x-access-token 을 붙이는 `ExchangeFilterFunction`** 추가. 정적 token 설정값이 있으면 그 값을, 없으면 발급기로 생성한 값을 헤더에 set.
  - 신규 서비스 토큰 발급기(예 `common/client/ControlNotifyTokenProvider` 또는 `common/security` 하위) — HS256 + iss=klid-auth + exp=now+ttl + `JWT_SECRET` 서명. 서명 스트림 전용(로그 금지). jjwt 사용(기존 의존).
  - 설정: `authoring.control-notify.token-ttl-seconds`(신규, 기본 300 등 짧게), `authoring.control-notify.token`(기존, 하위호환 override), `JWT_SECRET`(기존 재사용) — `application.yml` control-notify 블록.
- **불변**:
  - 관제 규칙 정합: **HS256**(HS512 아님), **iss=klid-auth**. 값 하드코딩 금지 — iss·ttl 은 설정 가능하게(iss 기본 klid-auth).
  - 정적 override 우선순위 유지(관제팀 토큰 대비).
  - 평문 http(내부망) 경고는 유지, 값 노출 금지.
  - 통지 발송 경로·페이로드(9필드 등)·디바운스·폴백은 **무변경** — 헤더 토큰 소스만 바뀐다.
- **수용기준**:
  - enabled+시크릿 있음 → 매 통지에 새 HS256/iss=klid-auth/미래 exp 토큰이 붙는다(두 통지의 토큰이 다르다).
  - 정적 `token` 설정값이 있으면 그 값이 그대로 나간다(override).
  - 시크릿·토큰 미설정 → 헤더 미부착(기존 동작), 통지 자체는 죽지 않음.
  - 로그·응답·예외에 토큰/시크릿 평문 0.
